1. 실행 계획은 성적표가 아니라 작업 설명서다

EXPLAIN에서 ALL이 나오면 나쁘고 ref가 나오면 좋다고 외우기 쉽습니다. 그러나 3행 테이블을 전부 읽는 것은 저렴하고, 인덱스로 500만 행을 찾아 본문까지 접근하는 것은 비쌀 수 있습니다. 실행 계획은 ‘어떻게 일할 것인가’를 보여 줍니다. 좋고 나쁨은 실제 작업량과 업무의 지연 목표를 대입해 판단합니다.

기본 EXPLAIN은 계획과 추정을 보여 줍니다. EXPLAIN ANALYZE는 쿼리를 실제 실행해 추정과 실측을 함께 보여 줍니다. 8.0.18부터 도입되었고 8.0에서는 TREE 출력입니다. 운영에서 무거운 SELECT에 붙이면 실제 부하가 발생합니다. 문장 종류에 따른 지원 범위도 있으므로 학습에서는 작은 SELECT만 사용합니다.

2. 먼저 읽을 여섯 열

열읽는 질문주의
table어느 입력을 처리하나?실제 테이블 외 파생·물질화 결과도 가능
type어떤 접근 방식인가?속도 순위표로만 외우지 않기
key실제로 선택한 인덱스는?possible_keys는 후보일 뿐
rows몇 행을 검사할 것으로 예상하나?InnoDB에서는 추정값
filtered그중 조건 통과 비율은?낮은 값은 많은 후보가 탈락한다는 뜻
Extra필터·정렬·커버링 같은 추가 작업은?문구 하나로 전체 성능 판단 금지

예를 들어 rows=10000, filtered=2이면 다음 단계로 10000×0.02=200행이 넘어갈 것으로 추정한다는 의미입니다. 이것은 실제 200행이라는 보장이 아닙니다. 조인에서 앞 단계의 추정 오차가 뒤의 반복 횟수 오차로 커질 수 있습니다.

3. 접근 유형을 실제 행동으로 번역하기

const는 유니크한 상수 조건 등으로 한 행을 고정하는 접근입니다. eq_ref는 이전 조합마다 유니크한 한 행을 찾는 조인 접근입니다. ref는 같은 키의 여러 후보를 찾을 수 있습니다. range는 인덱스 범위를, index는 인덱스 전체를, ALL은 전체 테이블을 스캔하는 의미로 이해하면 출발하기 좋습니다. 세부 조건과 다른 유형은 공식 정의로 확인합니다.

index는 이름이 좋아 보여도 전체 인덱스 스캔일 수 있습니다. 다만 좁은 커버링 인덱스를 전부 읽는 것이 넓은 테이블을 읽는 것보다 저렴할 수 있습니다. Using filesort는 인덱스 순서만으로 해결되지 않는 정렬을 뜻하며 반드시 디스크 파일을 썼다는 뜻은 아닙니다. Using temporary 역시 항상 디스크 임시 테이블을 뜻하지 않습니다.

4. 실습: 읽는 양을 줄이는 전후 비교

CREATE DATABASE IF NOT EXISTS mysql_school;
USE mysql_school;
DROP TABLE IF EXISTS plan_demo;
CREATE TABLE plan_demo(
 id INT PRIMARY KEY, warehouse_id INT NOT NULL,
 expected_date DATE NOT NULL, memo VARCHAR(200) NOT NULL
) ENGINE=InnoDB;
INSERT INTO plan_demo
WITH RECURSIVE seq AS (
 SELECT 1 n UNION ALL SELECT n+1 FROM seq WHERE n<1000
)
SELECT n,MOD(n,10),
 DATE_ADD('2026-01-01',INTERVAL MOD(n,30) DAY),REPEAT('p',150)
FROM seq;
EXPLAIN ANALYZE
SELECT id,expected_date FROM plan_demo
WHERE warehouse_id=1
ORDER BY expected_date,id LIMIT 10;
CREATE INDEX ix_wdi ON plan_demo(warehouse_id,expected_date,id);
ANALYZE TABLE plan_demo;
EXPLAIN ANALYZE
SELECT id,expected_date FROM plan_demo
WHERE warehouse_id=1
ORDER BY expected_date,id LIMIT 10;

변경 전에는 창고 열에 인덱스가 없으므로 후보를 찾고 정렬하는 작업이 필요할 수 있습니다. 변경 후에는 창고를 고정한 인덱스 구간에서 날짜·id 순으로 읽고 10건을 얻는 경로가 가능합니다. 실제 계획이 이 경로를 택했는지 확인합니다. 결과가 빠르다는 것만 보지 말고 스캔 행·정렬 노드·LIMIT에서 읽기가 멈추는 위치를 봅니다.

학습 데이터가 작아 시간 차이는 거의 없을 수 있습니다. 그런 경우 ‘몇 배 빨라졌다’는 숫자를 꾸며내지 않습니다. 접근 경로와 작업량 변화를 먼저 설명하고, 성능 주장을 하려면 더 큰 대표 데이터·반복 측정·동시 부하를 사용합니다.

5. actual time, rows, loops를 함께 읽기

설명을 위해 만들어 낸 가상 노드가 actual time=0.02..0.08 rows=3 loops=100이라고 합시다. 첫 숫자는 첫 행까지, 둘째는 해당 반복의 완료까지 걸린 시간이며 단위는 ms입니다. 여러 반복이 있으면 시간과 행 수는 반복당 평균으로 해석합니다. 대략 3×100=300행을 반환한 노드로 이해할 수 있습니다. 반올림 때문에 곱셈이 정확한 총계와 다를 수 있습니다.

부모 노드 시간은 자식 실행 시간을 포함합니다. 모든 노드의 시간을 더하면 중복 계산합니다. 바깥 입력이 100배 늘어 안쪽 loops가 늘었는지, 각 반복이 느려졌는지 구분하세요. 조인의 문제는 한 번의 조회가 느린 것이 아니라 작은 조회를 너무 많이 반복하는 것일 수 있습니다.

6. 목록 쿼리와 COUNT 쿼리는 왜 다른 인덱스를 고를까?

WHERE가 같아도 SELECT 열, ORDER BY, LIMIT, 집계가 다르면 해야 할 일이 다릅니다. 목록은 앞의 20건만 정렬 순서대로 얻으면 끝날 수 있습니다. COUNT는 조건에 맞는 전체 행을 세야 합니다. 목록이 본문 열을 여러 개 요구하지만 COUNT는 좁은 인덱스만 읽을 수 있는 경우도 있습니다.

EXPLAIN FORMAT=JSON
SELECT id,expected_date FROM plan_demo
WHERE warehouse_id=1 ORDER BY expected_date,id LIMIT 10;
EXPLAIN FORMAT=JSON
SELECT COUNT(*) FROM plan_demo WHERE warehouse_id=1;

두 쿼리가 같은 인덱스를 쓰더라도 작업량은 다를 수 있고, 서로 다른 인덱스를 쓰는 것도 오류가 아닙니다. ‘WHERE를 복사했으니 계획도 같아야 한다’고 보지 말고 결과를 만들기 위한 전체 요구를 비교합니다.

7. 느린 SQL 진단 기록을 남기는 법

  1. 정확한 SQL, 바인딩 타입과 대표 파라미터, 버전을 기록합니다.
  2. 현재 인덱스와 테이블 크기, 값의 편향을 확인합니다.
  3. EXPLAIN으로 위험한 읽기량을 먼저 추정합니다.
  4. 작은 검증 환경에서 EXPLAIN ANALYZE로 오차와 실제 병목을 찾습니다.
  5. 한 번에 한 변화만 적용하고 결과 동일성을 확인합니다.
  6. 읽기 지연뿐 아니라 쓰기 비용·인덱스 크기·계획 안정성을 비교합니다.

DB 실행은 50ms인데 서비스가 2초라면 풀 대기·네트워크·ORM 객체 매핑·N+1도 봐야 합니다. EXPLAIN ANALYZE는 클라이언트가 전체 결과를 수신하고 화면을 렌더링하는 시간의 대체 측정이 아닙니다. 반대로 대량 결과 전송 때문에 느린 API는 반환 열·행을 줄이는 것이 핵심일 수 있습니다.

8. 상세 면접 Q&A

EXPLAIN의 rows는 실제 읽은 행 수인가요?

InnoDB에서는 추정입니다. 실측은 EXPLAIN ANALYZE의 실제 행 수와 반복 횟수 등을 확인합니다. 추정과 실제가 크게 다르면 통계·분포·상관관계·조건 해석을 원인 후보로 봅니다. 추정값을 운영 처리량처럼 보고하면 안 됩니다.

Using filesort면 반드시 튜닝해야 하나요?

정렬이 있다는 사실을 나타낼 뿐입니다. 수십 행 정렬은 저렴할 수 있고 인덱스를 억지로 쓰는 경로가 더 비쌀 수도 있습니다. 정렬 입력 크기·메모리·디스크 spill·실제 시간을 보고 판단합니다.

actual time을 전부 더하면 전체 시간이 되나요?

아닙니다. 부모가 자식 시간을 포함하므로 중복됩니다. 노드별 반복과 입력·출력 행 수를 보고 시간을 설명해야 합니다. 루트 시간도 애플리케이션 전체 응답시간과는 다릅니다.

COUNT와 목록의 WHERE가 같은데 계획이 다른 이유는?

필요한 열, 정렬, 조기 종료, 집계 요구가 다르기 때문입니다. 목록은 LIMIT으로 일찍 멈추고 COUNT는 전체 후보를 처리할 수 있습니다. 반환 목적이 다른 두 SQL에 같은 인덱스를 강제할 이유는 없습니다.

튜닝 전후 결과가 같은지 왜 확인하나요?

빠르게 틀린 결과를 내는 것은 개선이 아닙니다. 조인 중복·NULL·날짜 경계·정렬 동률·페이지 경계가 바뀔 수 있습니다. 대표 데이터와 경계값에서 행 집합과 필요한 순서를 검증한 뒤 성능을 비교합니다.

한 번 실행한 시간으로 개선율을 발표해도 되나요?

캐시·초기화·동시 부하·측정 오차가 섞입니다. 조건을 통제해 반복하고 분포와 실제 읽기량을 함께 기록합니다. 작은 실습에서 0.1ms 차이를 운영의 10배 개선처럼 해석하지 않습니다.
