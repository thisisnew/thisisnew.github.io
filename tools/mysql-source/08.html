1. 복합 인덱스는 여러 목록이 아니라 하나의 사전이다

주소록을 시·구·이름 순서로 정리했다고 합시다. 같은 시 안에서 구가 정렬되고, 같은 구 안에서 이름이 정렬됩니다. 이름만 전체적으로 정렬된 것은 아닙니다. (warehouse_id, status, expected_date) 인덱스도 이런 사전식 순서입니다. 세 열에 각각 별도 인덱스를 만든 것과 다른 구조입니다.

이 인덱스에서는 특정 창고·특정 상태·특정 날짜 범위가 하나의 연속 구간에 모이기 쉽습니다. 반면 날짜만 지정하면 날짜가 여러 창고·상태마다 흩어집니다. 그래서 왼쪽 열부터 조건이 맞는지가 중요합니다. 단, 왼쪽 조건이 없으면 ‘어떤 방식으로도 인덱스를 사용할 수 없다’는 절대 규칙은 아닙니다. 전체 인덱스 스캔이나 제한적인 skip scan 같은 다른 경로도 있습니다.

2. 동등 조건과 범위 조건의 순서

창고=1, 상태=WAITING으로 고정한 뒤 날짜 범위를 잡으면 해당 묶음 안의 날짜를 연속으로 읽습니다. 반대로 창고=1, 날짜가 한 달 범위이고 그 뒤에 상태가 있다면 날짜별로 여러 상태가 섞입니다. 후행 상태가 검색 범위를 똑같이 좁혀 주지는 못할 수 있습니다.

그렇다고 “범위 뒤 열은 무조건 아무 소용 없다”도 틀립니다. 후행 열이 인덱스에서 조건을 검사하는 ICP에 쓰이거나 필요한 결과 열을 제공해 커버링에 기여할 수 있습니다. 시작·종료 경계를 좁히는 역할, 후보를 거르는 역할, 결과 열을 제공하는 역할을 구분하면 이 문제가 명확해집니다.

3. 독립 실습 데이터 만들기

CREATE DATABASE IF NOT EXISTS mysql_school;
USE mysql_school;
DROP TABLE IF EXISTS order_index_demo;
CREATE TABLE order_index_demo (
 id INT PRIMARY KEY,
 warehouse_id INT NOT NULL,
 status VARCHAR(16) NOT NULL,
 expected_date DATE NOT NULL,
 memo VARCHAR(200) NOT NULL,
 KEY ix_wsd(warehouse_id,status,expected_date)
) ENGINE=InnoDB;
INSERT INTO order_index_demo
WITH RECURSIVE seq AS (
 SELECT 1 n UNION ALL SELECT n+1 FROM seq WHERE n<1000
)
SELECT n, MOD(n,5), IF(MOD(n,10)=0,'WAITING','DONE'),
 DATE_ADD('2026-01-01',INTERVAL MOD(n,30) DAY), REPEAT('m',100)
FROM seq;
ANALYZE TABLE order_index_demo;

이 자료는 의도적으로 창고와 상태 사이에 상관관계가 있습니다. n이 10의 배수면 창고가 0이므로 WAITING은 모두 창고 0입니다. 실제 업무 데이터에도 이런 편향이 있습니다. 무작위 균등 데이터에서만 빠른 인덱스를 운영에도 그대로 적용하면 예상과 달라질 수 있습니다.

EXPLAIN FORMAT=JSON
SELECT id, expected_date FROM order_index_demo
WHERE warehouse_id=0 AND status='WAITING'
  AND expected_date>='2026-01-01' AND expected_date<'2026-02-01'
ORDER BY expected_date;

EXPLAIN FORMAT=JSON
SELECT memo FROM order_index_demo
WHERE status='WAITING' AND expected_date>='2026-01-15';

첫 쿼리는 선두 두 열을 고정하고 날짜 범위를 읽는 형태입니다. 반환 id는 보조 인덱스에 포함된 PK로 얻을 수 있어 커버링 후보입니다. 두 번째는 warehouse_id 조건이 없고 memo가 필요합니다. 실제 계획을 비교하되 이 작은 테이블에서 반드시 특정 type이 나와야 한다고 기대하지 않습니다.

4. ICP와 커버링을 같은 말로 외우지 않기

ICP(Index Condition Pushdown)는 인덱스 레코드만으로 검사할 수 있는 조건을 엔진 쪽에서 먼저 평가해 불필요한 본문 접근을 줄이는 기법입니다. 택배 목록에 무게가 적혀 있다면 상자를 꺼내기 전에 무게 조건으로 제외하는 것과 같습니다. 커버링은 필요한 모든 정보를 목록에서 얻어 상자를 꺼낼 필요가 적어지는 것입니다. 둘 다 이득을 주지만 이유가 다릅니다.

EXPLAIN의 Using index condition과 Using index는 다릅니다. 앞은 ICP, 뒤는 커버링 접근과 연결됩니다. key 열에 인덱스 이름이 있다고 두 표현이 항상 나타나는 것도 아닙니다. 선택한 경로, 필요한 열, 조건의 평가 위치를 함께 봅니다.

5. 인덱스가 있는데도 검색에 불리한 SQL

-- 날짜 열 자체의 정렬을 활용하기 어려워질 수 있는 형태
SELECT * FROM order_index_demo WHERE YEAR(expected_date)=2026;
-- 같은 의미의 범위 조건 후보
SELECT * FROM order_index_demo
WHERE expected_date>='2026-01-01' AND expected_date<'2027-01-01';

이 예에서는 expected_date가 ix_wsd의 세 번째 열이라는 추가 제약도 있습니다. 함수만 없앴다고 지금 인덱스로 효율적인 범위 검색이 보장되지 않습니다. 실험하려면 날짜 선두 인덱스도 별도 후보로 비교해야 합니다. 문제를 하나씩 분리해서 보는 것이 중요합니다.

문자열 코드 열에 숫자 파라미터를 비교하면 암묵적 형 변환 때문에 원래 문자열 정렬의 검색 이점을 잃을 수 있습니다. Java에서 문자열 코드는 setString으로 바인딩하는 식으로 타입을 맞춥니다. LIKE 'ABC%'는 접두 범위 검색 후보가 될 수 있지만 LIKE '%ABC%'는 일반 B-tree의 시작점을 정하기 어렵습니다. collation과 문자열 길이, 반환량도 함께 고려합니다.

6. 정렬과 페이지네이션까지 함께 설계하기

검색이 빨라도 결과를 별도로 정렬하면 추가 비용이 생깁니다. (창고, 상태, 날짜)에서 창고·상태가 하나의 값이면 날짜 순서로 읽기 좋습니다. 상태가 여러 값이면 상태별 날짜 묶음이어서 전역 날짜 순서와 다를 수 있습니다. ORDER BY 방향이 섞이는 경우에도 인덱스의 정렬 방향을 검토해야 합니다.

동일 날짜가 많으면 날짜만으로 페이지를 넘길 때 순서가 불안정합니다. id를 추가한 정렬과 커서를 사용하면 경계를 명확히 할 수 있습니다. 다음은 첫 페이지에서 마지막으로 본 날짜·id가 주어졌을 때의 형태입니다.

SELECT id, expected_date FROM order_index_demo
WHERE warehouse_id=0 AND status='WAITING'
  AND (expected_date > '2026-01-11'
       OR (expected_date='2026-01-11' AND id>100))
ORDER BY expected_date, id LIMIT 20;

대량 OFFSET은 앞의 행들을 건너뛰기 위한 작업이 계속 커질 수 있습니다. 커서 방식은 이전 경계 이후를 찾는 데 유리하지만 임의의 100페이지로 바로 이동하는 UX와는 다릅니다. 또한 중간 삽입·수정이 있는 동안 여러 페이지를 읽는 일관성 정책도 별도 문제입니다.

7. 인덱스 후보를 고르는 실제 순서

우선 자주 실행되고 총 비용이 큰 SQL을 고릅니다. 동등 조건, 범위, 정렬, 반환 열을 적습니다. 후보 인덱스를 만들고 대표 파라미터별 EXPLAIN ANALYZE를 비교합니다. 읽는 행·본문 접근·정렬·시간뿐 아니라 INSERT/UPDATE 비용과 인덱스 크기를 기록합니다. ‘카디널리티 높은 열부터’는 모든 경우를 해결하는 공식이 아닙니다. 조회 형태가 먼저입니다.

운영 중 보조 인덱스를 추가할 때는 지원 여부를 확인하고 ALGORITHM=INPLACE, LOCK=NONE처럼 원하는 조건을 명시해 불가능하면 오류로 알게 할 수 있습니다. 이것이 메타데이터 잠금·I/O·임시 공간·복제 지연을 없애 주지는 않습니다. 작은 학습 테이블과 운영의 수억 행 테이블은 변경 절차가 달라야 합니다.

여섯 개의 인덱스 항목을 종이에 정렬해 보기

복합 인덱스가 어렵다면 실제 항목 몇 개를 정렬하는 것이 가장 빠릅니다. (창고, 상태, 날짜) 순서에서 먼저 창고를 비교하고 같을 때만 상태를 비교하며 그것도 같을 때 날짜를 비교합니다. 아래 상태 문자열의 표시 순서는 설명용이며 실제 비교는 자료형과 collation에 따릅니다.

창고상태날짜관찰
0DONE1월 10일0번 창고의 DONE 묶음
0DONE1월 20일그 안에서 날짜순
0WAITING1월 5일상태가 달라지면 날짜는 다시 시작
0WAITING1월 15일같은 상태 안에서 날짜순
1DONE1월 1일다른 창고 묶음
1WAITING1월 30일별도 구간

창고=0, 상태=WAITING이면 두 행이 모여 있고 그 안에서 날짜가 정렬되어 있습니다. 창고=0만 고정하면 날짜는 전체적으로 정렬되지 않습니다. 1월 20일 뒤에 1월 5일이 나옵니다. 이것만 이해해도 “인덱스 안에 날짜가 있는데 왜 filesort를 하나요?”에 답할 수 있습니다.

인덱스가 하는 네 가지 일을 나누어 평가하기

역할질문효과
탐색 경계어디부터 어디까지 읽나?읽을 인덱스 범위 감소

한 열이 탐색 경계를 좁히지 못해도 나머지 역할에는 기여할 수 있습니다. 예를 들어 날짜 범위 뒤의 상태 조건은 방문할 구간을 크게 줄이지 못하더라도 인덱스에서 검사해 memo가 있는 본문을 읽기 전에 탈락시킬 수 있습니다. “범위 뒤 열은 못 쓴다”라는 축약은 어떤 역할을 말하는지 빼면 오해를 만듭니다.

선택도 높은 열을 무조건 앞에 놓으면 생기는 문제

조회가 항상 창고=0, 상태=WAITING을 고정하고 날짜순으로 20건을 가져온다고 합시다. 두 동등 조건 뒤에 날짜를 두면 해당 묶음에서 정렬된 순서로 읽을 기회가 있습니다. 날짜 값의 종류가 가장 많다는 이유로 날짜를 맨 앞에 두면 여러 창고·상태의 행을 훨씬 많이 훑을 수도 있습니다.

동등 조건 두 열이 항상 함께 사용된다면 두 열의 순서를 바꾸어도 그 조회의 후보 범위는 비슷할 수 있습니다. 그때는 창고만 조회하는 다른 쿼리가 많은지, 상태만 조회하는 배치가 있는지, 정렬과 인덱스 공유가 가능한지 따져야 합니다. 카디널리티는 중요한 정보지만 쿼리 패턴을 대신하는 만능 규칙은 아닙니다.

또한 반환 열을 모두 인덱스에 붙여 커버링을 만들면 키가 커지고 쓰기 부담도 늘어납니다. 매우 자주 실행되는 작은 목록 조회에는 도움이 될 수 있지만 가끔 쓰는 관리 화면 때문에 큰 memo까지 넣는 것은 손해일 수 있습니다. 호출 빈도와 누적 비용을 기준으로 우선순위를 정합니다.

조건 1%가 함정인 이유: ICP를 숫자로 해석하기

설명용으로 인덱스 범위에 10,000개 후보가 있고 그중 후행 조건을 만족하는 것은 100개라고 합시다. 본문을 읽은 뒤 조건을 검사하면 최대 10,000번 수준의 본문 접근이 필요할 수 있습니다. 인덱스에 해당 조건의 열이 있고 ICP가 적용된다면 인덱스에서 9,900개를 제외하고 100개만 본문으로 갈 기회가 있습니다.

이 경우에도 인덱스 후보 10,000개를 읽는 일 자체가 사라진 것은 아닙니다. 더 좋은 선두 열 구성으로 범위 자체를 100개에 가깝게 줄일 수 있다면 추가 개선 여지가 있습니다. ICP가 표시됐다는 사실만으로 최적화가 끝난 것은 아닙니다. 반대로 커버링이면 필요한 결과를 인덱스에서 얻어 본문 접근을 줄이는 다른 종류의 이득이 있습니다.

날짜 조건을 반열린 구간으로 쓰는 이유

날짜와 시간이 함께 저장된 DATETIME 열에서 하루를 조회할 때 >= '2026-01-01' AND < '2026-01-02'처럼 시작을 포함하고 다음 날을 제외하는 방식이 유용합니다. '23:59:59'까지만 쓰면 소수 초가 있는 데이터의 마지막 부분을 놓칠 수 있습니다. YEAR나 DATE 함수를 열에 적용하는 형태보다 원래 열 값의 범위로 표현하기도 쉽습니다.

단, 인덱스의 선두 조건과 시간대 의미는 별도입니다. 함수만 제거해도 복합 인덱스의 세 번째 열을 단독으로 효율적으로 찾는 것이 자동 보장되지는 않습니다. 앱에서 한국 날짜를 UTC 경계로 변환해야 하는 시스템이라면 먼저 업무 하루의 시작과 끝을 정확히 정해야 합니다. 빠르지만 하루가 어긋난 SQL은 올바른 튜닝이 아닙니다.

OFFSET과 커서의 차이는 ‘넘기는 방법’이다

페이지 크기 20으로 OFFSET 100000을 요청하면 결과 20개 앞의 많은 행을 지나가야 할 수 있습니다. 인덱스 순서로 읽더라도 앞부분을 처리하는 작업이 계속 커질 수 있습니다. 커서는 마지막으로 본 (날짜,id)를 주고 그 뒤부터 시작할 경계를 표현합니다.

날짜만 커서로 삼으면 같은 날짜에 여러 행이 있을 때 문제가 생깁니다. 날짜가 같은 나머지 행을 건너뛰거나 다시 읽을 수 있기 때문에 유일한 id를 보조 정렬 기준으로 넣습니다. 정렬이 오름차순이면 더 큰 경계, 내림차순이면 더 작은 경계 방향이 필요합니다. SQL 조건과 ORDER BY가 같은 순서를 표현하는지 확인합니다.

커서 방식도 여러 요청 전체에 하나의 스냅샷을 자동 제공하지 않습니다. 이미 본 행의 날짜가 바뀌거나 새 행이 끼어들면 결과 의미를 별도로 정해야 합니다. 정렬 키를 변경하지 않는 정책, 조회 기준 시점 고정, 중복 허용·제거 같은 요구를 설계합니다. 빠른 페이지 이동과 전체 목록의 시점 일관성은 다른 문제입니다.

목록과 COUNT의 인덱스를 따로 평가하는 연습

대기 상태인 주문 20개를 화면에 보여 주는 SQL은 정렬된 20개를 찾으면 멈출 수 있습니다. 하지만 “총 몇 건인가”는 나머지 모든 일치 행을 확인해야 합니다. 같은 WHERE라도 하나의 최적 인덱스로 두 문제를 항상 동시에 해결할 수는 없습니다. 목록 지연만 측정하고 COUNT가 전체 응답시간을 잡아먹는 문제를 놓치지 마세요.

앞 실습에서는 창고와 상태가 상관되어 WAITING이 모두 창고 0에 있습니다. 일부러 이 관계를 글로 설명한 이유는 실무의 편향을 관찰하기 위해서입니다. 상태를 DONE으로 바꾸거나 다른 창고를 지정해 후보 수가 달라지는 것을 확인하고, 결과가 0행인 파라미터만으로 성능을 평가하지 않습니다.

확장 수업 ① — 복합 인덱스의 정렬을 손으로 수행하기

(warehouse_id, status, expected_date) 인덱스는 창고 순서로 묶고, 같은 창고 안에서 상태 순서로 묶고, 같은 창고·상태 안에서 날짜로 정렬합니다. 사전이 첫 글자, 둘째 글자, 셋째 글자를 순서대로 비교하는 것과 같습니다. 열별로 독립적인 정렬 목록 세 개를 만든 것이 아닙니다.

창고 1의 WAITING만 찾으면 해당 묶음 안에서 날짜가 이어집니다. 그러나 창고 1의 모든 상태를 찾으면 날짜 순서는 상태별로 끊깁니다. DONE의 1월 20일 뒤에 WAITING의 1월 1일이 나올 수 있습니다. 이 때문에 선행 열을 단일 값으로 고정하는 조건과 여러 값으로 열어 놓는 조건은 ORDER BY 충족 여부에서 차이가 납니다.

조건·요구같은 인덱스에서의 사고 과정
warehouse=1, status='WAITING', 날짜 범위한 묶음의 날짜 구간으로 좁힐 후보
warehouse=1, 모든 status, 날짜순상태별 날짜 순서와 전체 날짜 순서는 다름
status='WAITING'만여러 창고 묶음에 흩어져 있음. 다른 접근 전략 평가 필요
warehouse IN (1,2), 날짜순창고별 정렬을 합친 결과가 전체 날짜순인 것은 아님

확장 수업 ② — 범위 축소·ICP·커버링을 한 예제로 분리하기

인덱스가 (창고, 날짜, 상태)이고 창고=1, 날짜가 한 달, 상태=WAITING을 조회한다고 합시다. 창고와 날짜로 탐색 범위를 잡으면 그 달의 인덱스 항목을 읽습니다. 날짜가 범위로 열려 있으면 뒤의 상태 조건이 보통 그 전체를 단일 연속 구간으로 줄여 주지는 못합니다. 하지만 상태가 인덱스에 있으니 읽은 항목에서 조건을 먼저 검사하는 데는 사용할 수 있습니다.

설명용으로 그 달의 항목 10만 개 중 WAITING이 1,000개라면, ICP는 조건에 맞지 않는 99,000개에 대해 원본 행을 가져오는 일을 줄이는 데 도움이 될 수 있습니다. 그렇다고 인덱스 항목 자체를 처음부터 1,000개만 읽었다는 뜻은 아닙니다. 실제 적용 여부는 실행 계획의 Using index condition과 조건 위치로 확인합니다.

조회에 필요한 모든 열을 인덱스에서 제공할 수 있다면 커버링 후보입니다. 반대로 memo가 필요하고 인덱스에 없다면 일치 항목의 원본 행이 필요합니다. 좁은 탐색 범위, 인덱스 단계의 필터, 원본 행 접근 감소, 정렬 제거는 서로 관련 있지만 다른 이점입니다. 하나를 얻었다고 나머지까지 모두 얻었다고 말하지 않습니다.

확장 수업 ③ — 목록과 집계의 인덱스를 선택하는 순서

입고 목록은 특정 창고·상태의 최근 20건을, 집계는 같은 조건의 전체 건수를 요구한다고 합시다. 목록은 정렬 순서대로 20개를 찾으면 일찍 멈출 수 있습니다. COUNT는 일치하는 나머지 행도 세어야 하므로 조기 종료 이점을 얻지 못합니다. WHERE가 같아도 해야 하는 전체 일이 다릅니다.

  1. 결과의 의미를 먼저 적습니다. 상태를 하나만 고정하는지, 여러 상태를 묶는지, 정렬에 동률이 있는지 확인합니다.
  2. 대표 바인딩 값을 고릅니다. 작은 창고·큰 창고, 평일·성수기처럼 분포가 다른 경우를 포함합니다.
  3. 동등 조건 묶음 뒤에 범위·정렬 열을 두는 후보를 만들고, 실제 다른 조회의 선행 열 활용도도 비교합니다.
  4. 원본 행 접근을 줄이는 열 추가가 필요한지 평가합니다. 큰 memo까지 무작정 넣지 않습니다.
  5. SELECT 개선과 INSERT·UPDATE 비용, 저장 공간을 함께 측정합니다.

창고와 상태가 모두 항상 동등 조건이면 두 열의 순서를 “선택도가 높은 것부터”라는 규칙 하나로 결정할 필요는 없습니다. 다른 쿼리가 창고만 사용하는지, 어떤 정렬과 범위가 뒤따르는지, 실제 비용 추정이 어떤지가 더 중요할 수 있습니다. 인덱스는 한 SQL만의 장식이 아니라 공유하는 저장 구조입니다.

확장 수업 ④ — 커서에 날짜만 넣으면 왜 행을 놓칠까?

날짜가 같은 주문이 여러 개라면 마지막 날짜만 저장하고 다음 페이지를 날짜>마지막날짜로 찾을 때 같은 날짜의 남은 주문을 건너뜁니다. 날짜>=마지막날짜로 바꾸면 이미 본 주문이 반복됩니다. 따라서 날짜와 고유 id를 함께 정렬하고 둘을 커서에 담아야 합니다. 다음은 동률이 있는 작은 독립 실습입니다.

CREATE DATABASE IF NOT EXISTS mysql_school;
USE mysql_school;
DROP TABLE IF EXISTS cursor_case;
CREATE TABLE cursor_case (
 id INT PRIMARY KEY, expected_date DATE NOT NULL,
 KEY ix_date(expected_date)
) ENGINE=InnoDB;
INSERT INTO cursor_case VALUES
 (1,'2026-01-01'),(2,'2026-01-01'),(3,'2026-01-02');
SELECT id,expected_date FROM cursor_case
ORDER BY expected_date,id LIMIT 1; -- id=1
SELECT id,expected_date FROM cursor_case
WHERE expected_date>'2026-01-01'
ORDER BY expected_date,id; -- id=3만 나와 2를 놓침
SELECT id,expected_date FROM cursor_case
WHERE expected_date>'2026-01-01'
   OR (expected_date='2026-01-01' AND id>1)
ORDER BY expected_date,id; -- id=2,3

커서를 쓰면 데이터가 변경되는 동안 모든 페이지가 하나의 시점처럼 보장되는 것은 아닙니다. 정렬 열이 바뀌면 이미 본 행이 뒤로 이동하거나 아직 안 본 행이 앞으로 이동할 수 있습니다. 전체 시점 일관성이 꼭 필요한 보고서와 최신 목록을 계속 보여 주는 화면은 요구가 다릅니다. 커서 값에 쓰는 열의 변경 가능성과 NULL·시간대 처리까지 정해야 합니다.

8. 상세 면접 Q&A

(a,b,c)에서 a 조건이 없으면 인덱스는 무조건 못 쓰나요?

효율적인 선두 범위 탐색이 어려운 것이 기본 원칙입니다. 그러나 전체 인덱스 스캔, 커버링, 조건을 만족하는 skip scan 등이 가능할 수 있습니다. “사용 여부”보다 “얼마나 좁게 읽는가”로 평가하는 것이 정확합니다.

범위 조건 뒤의 열은 왜 그래도 유용할까요?

탐색 경계를 추가로 좁히는 역할이 제한되어도 인덱스에서 필터링하거나 결과 열을 제공할 수 있습니다. ICP·커버링·정렬 기여를 각각 확인해야 합니다. key_len 하나만 보고 모든 후행 열이 무의미하다고 결론내리지 않습니다.

단일 인덱스 세 개가 복합 인덱스 하나와 같나요?

아닙니다. 복합 인덱스는 사전식 순서의 하나의 자료구조입니다. 여러 단일 인덱스를 결합하는 index merge가 선택될 수 있지만 후보 결합 비용과 정렬 활용이 다릅니다. 자주 쓰는 조건 조합에 맞춰 비교해야 합니다.

상태값처럼 종류가 적은 열은 인덱스에 쓸모없나요?

아닙니다. 전체 비율, 특정 상태의 희소성, 다른 열과의 조합, 정렬 요구가 중요합니다. WAITING이 전체의 0.1%인 업무라면 유용할 수 있습니다. 값 종류 개수와 특정 값의 선택도는 같은 개념이 아닙니다.

LIKE와 =는 같은 인덱스를 쓰면 성능도 같나요?

조건이 만드는 탐색 범위와 비교 의미가 다를 수 있습니다. 접두 LIKE는 여러 값을 포함하는 범위가 될 수 있고 collation도 영향을 줍니다. 인덱스 이름이 같다는 사실만으로 읽기량이 같다고 판단하지 않습니다.

인덱스를 추가했는데 안 쓰면 실패인가요?

반드시 그렇지는 않습니다. 작은 테이블이나 대부분의 행을 반환하는 조건에서는 스캔이 더 저렴할 수 있습니다. 통계·대표 파라미터·실제 읽기량을 확인합니다. FORCE INDEX는 비교 실험 도구로 사용할 수 있지만 증거 없이 영구 적용하지 않습니다.

꼬리 질문: 복합 인덱스 순서는 WHERE에 적은 순서와 같아야 하나요?

답변: 일반적인 AND 조건의 작성 순서를 바꾼다고 인덱스의 물리 정렬 순서가 달라지지는 않습니다. 인덱스 정의와 조건의 의미가 중요합니다.

확인: 동등·범위 조건과 정렬 요구를 분리해 계획을 비교합니다. SQL을 보기 좋게 재배치한 효과와 인덱스 재설계 효과를 혼동하지 않습니다.

꼬리 질문: 상태가 두 값뿐이면 인덱스에서 빼야 하나요?

답변: 값 종류가 적다고 항상 쓸모없는 것은 아닙니다. WAITING이 전체의 0.1%이고 그것을 자주 조회하면 중요한 필터일 수 있습니다.

설계: 다른 선두 조건과 결합한 후보 수, 정렬, 호출 빈도를 봅니다. 낮은 카디널리티와 낮은 선택도는 특정 값의 편향을 고려하면 단순히 같은 이야기가 아닙니다.

꼬리 질문: IN 조건도 = 조건처럼 정렬을 보장하나요?

답변: 여러 값은 여러 구간을 만들 수 있으므로 단일 값으로 고정한 경우와 다릅니다. (상태,날짜)에서 상태 두 개를 읽으면 상태별 날짜순과 전체 날짜순이 다릅니다.

검증: 실제 ORDER BY 요구와 정렬 노드를 확인합니다. IN 목록이 짧다는 이유만으로 filesort가 사라진다고 예상하지 않습니다.

꼬리 질문: 커버링이면 FORCE INDEX를 넣어도 되나요?

답변: 커버링은 이점 중 하나이지 모든 파라미터에서 최선이라는 보장은 아닙니다. 넓은 인덱스를 대부분 읽는 경로보다 다른 접근이 나을 수 있습니다.

운영: 강제 전 대표·극단 파라미터와 데이터 증가 조건에서 실측합니다. 힌트를 넣었다면 이유와 제거·재검토 조건도 남깁니다.

심층 면접: 범위 조건 뒤의 인덱스 열은 쓸모없다는 말이 왜 부정확한가요?

답변: 탐색 구간을 얼마나 줄이는지와 읽은 항목을 어떻게 활용하는지를 혼동한 표현입니다. 뒤의 열이 주된 범위를 줄이지 못해도 ICP의 필터나 커버링에 기여할 수 있습니다.

예시: (창고, 날짜, 상태)에서 창고=1·한 달 범위를 읽으면서 상태를 인덱스에서 검사하면 원본 행 접근을 줄일 수 있습니다. 그러나 읽은 인덱스 항목 수까지 상태 일치 건수와 같아지는 것은 아닙니다.

검증: key 이름만 보지 않고 사용한 키 부분, 조건 위치, 실제 반복·출력 행, 원본 행 접근이 필요한 열을 함께 확인하겠습니다.

심층 면접: 커서 페이지네이션으로 바꾸면 OFFSET의 모든 문제를 해결하나요?

답변: 깊은 페이지에서 앞 행을 대량으로 건너뛰는 비용을 줄일 수 있지만 적절한 인덱스와 안정적인 정렬 기준이 필요합니다. 임의의 100번째 페이지로 바로 이동하는 기능도 별도 설계가 필요합니다.

정합성: 동률을 해소하는 고유 키를 커서에 포함하고, 페이지 사이에 정렬 열이 바뀌는 경우의 중복·누락 의미를 정해야 합니다. 커서 자체는 여러 요청을 같은 스냅샷으로 묶지 않습니다.

검증: 정적 데이터에서 모든 페이지를 연결한 결과가 전체 정렬 결과와 같은지, 동시 변경 때 사용자에게 약속한 동작을 지키는지 나누어 확인하겠습니다.
