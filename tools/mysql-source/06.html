1. 잠금은 ‘동시에 하면 안 되는 작업’을 줄 세운다

창고의 마지막 상품 한 개를 두 사람이 동시에 가져가면 안 됩니다. 한 사람이 수량을 확인하고 출고를 확정하는 동안 다른 사람은 기다려야 할 수 있습니다. 잠금은 이런 경쟁을 제어합니다. 하지만 창고 전체 문을 잠글지, 선반 하나를 잠글지, 빈 선반 자리에 새 물건을 놓는 것까지 막을지는 상황마다 다릅니다.

InnoDB의 행 잠금은 실제로 인덱스 레코드를 기반으로 동작합니다. SQL의 WHERE에 적힌 업무 조건만 보고 “한 행 잠금”이라고 단정하면 안 됩니다. 어떤 인덱스로 어떤 범위를 훑었는지, 격리 수준은 무엇인지, 유일한 값을 찾았는지에 따라 잠금 범위가 달라집니다.

2. 레코드·갭·넥스트키를 숫자로 이해하기

인덱스에 10, 20, 30이 있다고 합시다. 레코드 잠금은 예를 들어 20이라는 기존 항목을 보호합니다. 갭 잠금은 10과 20 사이 같은 ‘비어 있는 구간’에 삽입하지 못하도록 합니다. 넥스트키 잠금은 레코드와 그 앞 갭을 결합합니다. 20에 대한 넥스트키 구간은 개념적으로 (10,20]입니다. 실제 SQL이 이 한 구간만 잠근다는 뜻은 아니고, 검색 과정에 따라 여러 구간과 끝 경계를 잠글 수 있습니다.

왜 없는 것을 잠글까요? “가격 10~20 상품이 3개다”라고 읽은 뒤 같은 범위에 다른 사람이 새 상품을 추가하면 집합이 바뀝니다. 기존 행만 막아서는 삽입을 막지 못합니다. 갭 보호는 이런 범위 변경과 연결됩니다. RR의 잠금 읽기·변경에서는 범위 잠금이 중요하고, RC에서는 일반 검색의 갭 잠금이 줄지만 외래 키·중복 키 검사 등의 예외가 남습니다.

전체 유니크 키에 대한 동등 조건으로 존재하는 한 행을 찾는 경우는 레코드 잠금만으로 처리할 수 있습니다. 반대로 찾는 값이 없거나 복합 유니크 키의 일부만 조건에 넣었다면 같은 결론을 적용하면 안 됩니다.

3. S·X·의도 잠금, 그리고 latch

용어목적오해 방지
S, 공유 잠금여러 읽기 잠금의 공존을 허용모든 일반 SELECT가 S 잠금을 잡는 것은 아니다.
X, 배타 잠금충돌하는 다른 잠금과 변경을 제한테이블 전체 잠금이라는 뜻이 아니다.
IS·IX, 의도 잠금테이블 아래에 행 잠금을 잡으려는 의도를 표시IX끼리 공존할 수 있다. 테이블 전체 X와 다르다.
Latch내부 메모리 구조를 짧게 보호업무 트랜잭션의 행 잠금과 생명주기가 다르다.
Metadata lock사용 중인 테이블 정의를 보호행 잠금이 없어도 DDL은 기다릴 수 있다.

잠금 목록에서 IX를 봤다고 “테이블 전체가 잠겼다”고 보고하면 잘못된 대응을 할 수 있습니다. 의도 잠금은 상위 계층이 하위 잠금의 존재를 빠르게 판단하도록 하는 표시입니다. 무엇과 충돌하는지를 봐야 합니다.

4. 실습 A: 한 행의 대기를 만들고 관찰하기

1편 서버의 mysql_school에서 준비합니다. 이후 터미널 A와 B를 따로 열어 같은 스키마를 사용합니다.

CREATE DATABASE IF NOT EXISTS mysql_school;
USE mysql_school;
DROP TABLE IF EXISTS lock_demo;
CREATE TABLE lock_demo(id INT PRIMARY KEY, qty INT NOT NULL)
  ENGINE=InnoDB;
INSERT INTO lock_demo VALUES(10,10),(20,20),(30,30);
-- 세션 A
START TRANSACTION;
SELECT * FROM lock_demo WHERE id=20 FOR UPDATE;
-- 아직 COMMIT하지 않습니다.

-- 세션 B: 아래 UPDATE는 A가 끝날 때까지 대기합니다.
SET SESSION innodb_lock_wait_timeout=10;
UPDATE lock_demo SET qty=qty-1 WHERE id=20;

-- A에서 10초 안에 실행하면 B가 이어서 진행할 수 있습니다.
COMMIT;

B가 시간 초과 오류를 받았다면 UPDATE가 성공한 것이 아닙니다. A를 정리한 뒤 B에서 다시 실행해야 합니다. A의 잠금은 연결이 열린 동안 영원히 유지되는 것이 아니라 해당 트랜잭션이 끝날 때 해제됩니다. 명시적 트랜잭션 없이 autocommit 상태에서 FOR UPDATE만 실행하면 이후 업무까지 보호하는 긴 구간을 만들 수 없습니다.

-- 대기 중 세 번째 관리자 연결에서 관찰
SELECT ENGINE_TRANSACTION_ID, OBJECT_SCHEMA, OBJECT_NAME,
       INDEX_NAME, LOCK_TYPE, LOCK_MODE, LOCK_STATUS, LOCK_DATA
FROM performance_schema.data_locks
WHERE OBJECT_NAME='lock_demo';
SELECT * FROM performance_schema.data_lock_waits;

GRANTED는 이미 획득, WAITING은 기다리는 요청입니다. 잠금 데이터 표시 형식은 버전·페이지 상태에 따라 달라질 수 있으므로 문자열을 통째로 외우지 않습니다. 기다리는 쪽과 막는 쪽을 연결하는 것이 핵심입니다.

5. 실습 B: 서로 다른 행인데 삽입이 막히는 이유

-- A, 이전 트랜잭션을 끝낸 뒤
SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;
START TRANSACTION;
SELECT * FROM lock_demo WHERE id BETWEEN 10 AND 20 FOR UPDATE;

-- B
INSERT INTO lock_demo VALUES(15,15);
-- A의 범위 보호 때문에 대기할 수 있습니다.

-- A
ROLLBACK;

15는 원래 없던 행입니다. 따라서 “15를 수정하는 다른 트랜잭션이 없는데 왜 막히지?”라는 질문의 답이 갭입니다. 실제 범위 잠금은 검색 경계 바깥의 인접 구간까지 영향을 줄 수 있으므로 정확한 잠금 목록도 함께 봅니다. B에서 삽입이 성공했다면 다음 반복 전에 15를 지우고 초기 상태를 맞춥니다.

6. 실습 C: 데드락은 대기와 다르다

순서AB
1START TRANSACTION; UPDATE lock_demo SET qty=qty+1 WHERE id=10;
2START TRANSACTION; UPDATE lock_demo SET qty=qty+1 WHERE id=20;
3UPDATE lock_demo SET qty=qty+1 WHERE id=20; → 대기
4UPDATE lock_demo SET qty=qty+1 WHERE id=10; → 순환 대기 형성

기본 데드락 감지가 활성화되어 있으면 한 트랜잭션이 희생되어 롤백되고 오류가 발생합니다. 어느 쪽이 희생되는지 고정해서 기대하지 마세요. 살아남은 쪽도 실습 정리를 위해 ROLLBACK합니다. SHOW ENGINE INNODB STATUS의 최근 데드락 정보를 확인하면 양쪽 SQL과 잠금 관계를 볼 수 있습니다.

잠금 시간 초과는 기본 설정에서 실패한 문장만 취소될 수 있지만, 데드락은 선택된 트랜잭션 전체가 롤백됩니다. 애플리케이션에서 오류 처리 범위를 구분해야 합니다. 실패한 트랜잭션은 명시적으로 정리하고, 재시도는 새 트랜잭션으로 전체 업무를 수행하며 횟수 제한·짧은 backoff·멱등성을 갖추는 편이 안전합니다.

7. 운영 개선: 기다림을 없애기보다 불필요한 경쟁을 줄이기

여러 상품을 수정한다면 같은 키 순서로 처리해 순환 가능성을 줄입니다. 인덱스로 검사 범위를 좁히고, 트랜잭션 안에서 외부 API를 기다리지 않습니다. 이것이 모든 데드락을 없앤다는 뜻은 아닙니다. 보조 인덱스·외래 키·삽입 경로에서도 경쟁이 생길 수 있어 정상적인 재시도 설계는 남겨 둡니다.

NOWAIT는 잠금 획득이 불가능하면 즉시 오류를, SKIP LOCKED는 잠긴 행을 건너뛴 결과를 얻는 데 사용합니다. SKIP LOCKED는 작업 큐의 여러 작업자가 서로 다른 일을 가져가는 데 유용하지만, 빠진 행이 있으므로 전체 재고나 정산 집계에 무심코 사용하면 틀린 결과가 됩니다. 기다리지 않는 대신 결과의 의미가 달라집니다.

잠금 대기를 그림 없이 읽는 법: 누가 누구의 무엇을 기다리나?

창고 직원 A가 20번 상품을 수정 중이고 B도 20번을 바꾸려 한다면, B는 A가 보유한 권리 때문에 기다립니다. 이때 중요한 정보는 느린 SQL 하나가 아니라 기다리는 요청, 잠금 보유자, 잠긴 인덱스 레코드, 보유자의 트랜잭션 시작 시점입니다. 기다리는 쿼리만 종료해도 보유자가 그대로면 다음 요청이 또 막힙니다.

잠금은 “행에 자물쇠 하나”라는 비유로 시작할 수 있지만 InnoDB는 인덱스 레코드를 중심으로 다룹니다. 보조 인덱스로 행을 찾아 갱신하면 보조 인덱스와 클러스터드 인덱스 관련 잠금이 생길 수 있습니다. 따라서 WHERE에 쓴 업무 열과 잠금 화면의 INDEX_NAME이 다르다고 이상한 것은 아닙니다.

S·X·IS·IX를 한 번에 구분하기

기호의미대표 충돌 관계
S공유 잠금다른 S와 함께 가능, 같은 대상 X와 충돌
X배타 잠금다른 트랜잭션의 같은 대상 S·X와 충돌
IS아래 레코드에 공유 잠금을 잡으려는 의도테이블 수준 잠금과의 충돌 판단에 사용
IX아래 레코드에 배타 잠금을 잡으려는 의도다른 IX가 있다는 이유만으로 전체 DML이 직렬화되지는 않음

서로 다른 상품을 수정하는 A와 B가 모두 테이블 수준 IX를 보유할 수 있습니다. IX를 테이블 전체의 X 잠금으로 읽으면 “InnoDB가 결국 테이블 전체를 잠근다”는 잘못된 결론에 도달합니다. 의도 잠금은 상위 수준에서 하위 잠금의 존재를 효율적으로 확인하도록 돕습니다.

10·20·30 사이의 빈 공간을 잠그는 이유

인덱스에 키 10, 20, 30이 있다고 합시다. 레코드 잠금은 20 자체를 보호합니다. 갭 잠금은 10과 20 사이처럼 새 값이 들어갈 틈의 삽입을 제어합니다. next-key 잠금은 레코드와 그 앞의 갭을 함께 보호하는 형태입니다. 수학적으로 (10,20]이라고 쓰면 10은 제외하고 20은 포함한다는 뜻입니다.

왜 빈 곳을 보호할까요? “10보다 크고 20 이하인 모든 작업을 확인한 뒤 처리”하는 중에 15가 새로 끼어들면 확인한 집합과 처리 집합이 달라질 수 있습니다. 기존 20만 잠가서는 15 삽입을 막지 못합니다. RR에서 범위 검색의 잠금이 넓어질 수 있는 배경입니다.

다만 WHERE의 논리 범위가 잠금 범위와 항상 정확히 일치하지는 않습니다. 엔진은 실제 인덱스 검색 경로와 종료 경계를 따라 잠금을 획득합니다. 존재하는 유니크 키를 동등 조건으로 찾는 경우와, 없는 키를 찾는 경우도 다릅니다. 그래서 앞 실습의 BETWEEN 결과만 보고 잠긴 레코드와 갭을 추측하지 말고 data_locks에서 확인해야 합니다.

갭 잠금은 삽입을 억제하는 목적이어서 서로 다른 트랜잭션의 갭 잠금끼리 공존할 수 있습니다. 이름에 S·X가 붙었다고 일반 레코드 잠금의 충돌 표를 그대로 적용하면 안 됩니다. 삽입 시에는 insert intention 잠금 등 별도 동작이 얽힙니다. 다른 위치에 삽입하는 요청이 언제나 모두 같은 방식으로 막히는 것도 아닙니다.

같은 행을 기다리는 상황과 데드락의 결정적 차이

A가 10을 잡고 B가 10을 기다리는 것은 한 방향 대기입니다. A가 끝나면 해결될 수 있습니다. A가 10을 잡은 채 B의 20을 기다리고, B가 20을 잡은 채 A의 10을 기다리면 순환이 생깁니다. 서로 상대가 먼저 끝나야 하므로 어느 쪽도 스스로 진행하지 못합니다.

기본 데드락 감지는 이 순환을 찾아 한 트랜잭션을 희생시킵니다. “마지막 SQL만 다시 실행”하면 되는 것으로 오해하기 쉽지만 희생된 트랜잭션의 이전 변경도 롤백됩니다. 출고 생성→재고 차감→이력 기록 중 이력에서 데드락이 났다면 출고 생성부터 새 트랜잭션으로 다시 판단해야 할 수 있습니다.

반면 잠금 시간 초과는 기본적으로 기다리던 문장만 롤백될 수 있습니다. 먼저 성공한 다른 문장이 트랜잭션 안에 남아 있는데 앱이 잘못 COMMIT하면 부분 업무가 확정될 수 있습니다. DB의 오류 범위와 Spring의 예외 변환·롤백 규칙을 함께 확인하고 실패한 업무 트랜잭션을 명시적으로 종료하는 것이 중요합니다.

재시도는 새 트랜잭션 바깥에서 관리하기

구조적으로는 “재시도 루프 → 새 트랜잭션 시작 → 전체 업무 → 성공 시 커밋” 순서가 필요합니다. 이미 실패한 동일 트랜잭션 내부에서 같은 SQL을 반복하면 올바른 재시도가 아닐 수 있습니다. Spring을 사용한다면 프록시 경계, 자기 호출, rollback-only 상태를 고려해 재시도 담당과 트랜잭션 담당의 경계를 분명히 합니다.

재시도 가능 오류만 대상으로 횟수를 제한하고 짧은 지연과 무작위 편차를 두면 모두가 동시에 다시 충돌하는 일을 줄일 수 있습니다. 네트워크 오류처럼 커밋 결과가 불명확한 경우는 데드락으로 확실히 롤백된 경우와 다릅니다. 외부 결제나 메시지 발송을 재시도 블록 안에서 반복하면 부작용이 중복될 수 있어 요청 ID와 Outbox 등 별도 설계가 필요합니다.

LOCK=NONE인데 서비스가 멈춘 상황을 해석하기

Online DDL이 동시 DML을 허용해도 테이블 정의를 보호하는 메타데이터 잠금(MDL)은 필요합니다. A가 테이블을 사용한 트랜잭션을 끝내지 않으면, B의 ALTER가 필요한 MDL을 기다릴 수 있습니다. 그 뒤 새 요청까지 대기열의 영향을 받을 수 있습니다. “인덱스는 온라인으로 만들었으니 잠금 문제는 없다”는 판단은 불완전합니다.

이때 행 잠금만 보는 data_lock_waits에 원인이 명확히 드러나지 않을 수 있습니다. 메타데이터 잠금과 세션 상태도 조사해야 합니다. 운영 대응은 대기 중 DDL과 오래된 트랜잭션 중 무엇을 종료할지 업무 영향에 따라 결정합니다. DDL의 취소·롤백 비용과 배포 재시도도 고려해야 합니다.

마지막으로 인덱스 추가는 성능뿐 아니라 잠금 범위를 바꿀 수 있습니다. 검색 범위가 줄면 경쟁을 완화할 수 있지만, 새로운 보조 인덱스 유지 작업이 추가될 수도 있습니다. 실행 계획과 잠금 관찰을 함께 남겨야 변경 효과를 설명할 수 있습니다.

확장 수업 ① — 잠금은 WHERE 문장에 붙는 자물쇠가 아니다

WHERE status='WAITING'이라고 썼다고 “WAITING이라는 단어”에 자물쇠가 생기는 것은 아닙니다. InnoDB는 실행 과정에서 접근하는 인덱스 레코드와 필요한 범위를 잠급니다. 어떤 인덱스로 어떤 구간을 탐색했는지, 유일한 키를 정확히 찾았는지, 격리 수준과 SQL 종류가 무엇인지가 중요합니다.

기본 키 id=20으로 존재하는 한 행을 찾는 경우와, 인덱스가 없는 상태 열로 많은 행을 검사하는 경우는 최종 변경 행 수가 1이어도 잠금 과정이 다를 수 있습니다. 최종 결과만 보고 “한 행을 바꾸니 한 행만 잠갔겠지”라고 추정하지 마세요. 실행 계획과 실제 data_locks·data_lock_waits를 함께 읽어야 합니다.

레코드 잠금은 저장된 항목을 보호하고, 갭 잠금은 사이에 새 항목이 끼어드는 것을 제어합니다. 넥스트키는 레코드와 그 앞의 갭을 함께 생각하는 개념입니다. 다만 인덱스의 실제 탐색 범위, 경계값 존재 여부와 최적화에 따라 관찰되는 잠금은 달라지므로 모든 BETWEEN 쿼리에 같은 잠금 목록을 외워 적용하면 안 됩니다.

확장 수업 ② — 갭 잠금끼리는 왜 함께 존재할 수 있을까?

일반적인 S·X 레코드 잠금에서는 여러 읽기는 함께 가능하고 배타적 쓰기는 충돌한다는 설명이 도움이 됩니다. 그러나 갭 잠금에 그 표를 그대로 가져오면 헷갈립니다. 갭 잠금의 핵심 목적은 그 구간의 삽입을 억제하는 것이며, 서로 다른 트랜잭션의 갭 잠금이 같은 구간에 공존할 수 있습니다.

운동장에 “새 차량 진입 금지” 표지판을 두 관리자가 동시에 세운다고 생각해 봅시다. 표지판 두 개는 서로 배제할 필요가 없지만 새 차량의 진입은 막습니다. 이 비유는 갭 잠금의 삽입 억제 성격을 이해하기 위한 것이며 실제 잠금 모드 전체를 대신하지는 않습니다.

INSERT에는 삽입 의도 잠금도 관련됩니다. 서로 다른 위치에 삽입하는 작업들이 무조건 같은 갭 전체를 독점하지 않게 하지만, 다른 트랜잭션이 보유한 갭·넥스트키 잠금에 막힐 수 있습니다. 그래서 “S와 X 이름이 다르니까 반드시 충돌” 또는 “서로 다른 id니까 절대 안 기다림”이라는 단순 규칙 모두 부족합니다.

확장 수업 ③ — 대기 연결 하나가 어떻게 풀 고갈로 커지는가?

A가 재고 행을 갱신하고 커밋 전에 외부 API를 5초 기다립니다. B·C·D도 같은 재고를 갱신하려다 기다립니다. 이 연결들은 일을 끝내고 풀에 반환되지 못합니다. 후속 요청은 이제 DB 행 잠금에 도달하기 전에 애플리케이션의 연결 풀에서 기다릴 수 있습니다. 하나의 오래 열린 트랜잭션이 두 층의 대기열을 만드는 것입니다.

관측즉시 내릴 수 없는 결론다음 확인
앱 연결 대기 증가풀 크기만 작다점유 중인 연결이 무엇을 기다리는가?
DB CPU 낮음DB 문제가 아니다행 잠금·메타데이터 잠금 대기가 있는가?
차단 세션이 Sleep아무 작업도 하지 않는다미완료 트랜잭션과 보유 잠금이 있는가?
대기 SQL이 단순 UPDATE인덱스 추가가 답이다같은 한 행에 업무가 집중되는가?

차단 연결을 종료하면 무조건 즉시 정상화되는 것도 아닙니다. 진행한 변경이 크면 롤백에 시간이 걸릴 수 있습니다. 어떤 업무인지, 변경량이 얼마인지, 종료 시 재시도 폭주가 생기는지를 확인합니다. 근본적으로는 잠금 보유 구간을 짧게 하고, 같은 자원의 경쟁을 줄이며, 제한된 재시도를 설계해야 합니다.

확장 수업 ④ — 1213과 1205를 구분하고 다시 시작하기

데드락 오류 1213에서는 InnoDB가 희생 트랜잭션을 롤백합니다. 잠금 대기 시간 초과 1205는 기본 동작에서 해당 문장만 롤백될 수 있습니다. 두 오류 모두 그냥 같은 연결에서 다음 UPDATE를 보내는 방식으로 처리하면 앞서 성공한 문장의 잔여 상태를 잘못 다룰 수 있습니다. 애플리케이션의 프레임워크가 추가로 전체 롤백을 수행하는지도 구분합니다.

업무 단위 재시도는 실패한 시도를 완전히 종료한 뒤 새 트랜잭션으로 시작하는 구조가 명확합니다. Spring에서는 예외를 트랜잭션 경계 밖으로 전달하고, 바깥 재시도 루프가 프록시를 통해 트랜잭션 메서드를 새로 호출하는지 확인합니다. 같은 객체 내부 호출은 일반적인 프록시 기반 선언적 트랜잭션에서 기대한 경계를 만들지 못할 수 있습니다.

재시도에는 최대 횟수, 전체 시간 예산, 짧은 지연과 무작위 분산을 둡니다. 요청 ID로 중복 효과를 막고 외부 호출이 이미 성공했는지도 고려합니다. 데드락은 실패한 명령 한 줄만 재전송하면 되는 문법 오류가 아니라, 함께 묶었던 판단과 변경을 다시 검토해야 하는 동시성 사건입니다.

8. 상세 면접 Q&A

WHERE id=1이면 항상 한 행만 잠그나요?

인덱스, 유일성, 실제 행 존재 여부, 격리 수준을 함께 봅니다. PK로 존재하는 한 행을 찾는 것과 인덱스 없는 열의 조건은 다릅니다. 최종 변경 행 수가 적어도 검색 중 많은 레코드를 잠글 수 있습니다.

갭 잠금은 빈 공간을 왜 잠그나요?

기존 행의 변경을 막는 것만으로는 새로운 행 삽입을 막을 수 없기 때문입니다. 범위 집합을 보호하려면 그 사이에 들어올 수 있는 위치도 다뤄야 합니다. 레코드 잠금과 삽입 방지 목적을 구분하면 이해하기 쉽습니다.

데드락이 발생하면 DB 설계가 잘못된 건가요?

반드시 그렇지는 않습니다. 정상적인 동시 처리에서도 발생할 수 있습니다. 빈도가 높으면 접근 순서와 인덱스·트랜잭션 길이를 개선하고, 낮은 빈도에도 제한된 재시도를 준비합니다. 무조건 한 세션을 강제 종료하는 운영은 근본 해결이 아닙니다.

시간 초과와 데드락을 같은 방식으로 처리해도 되나요?

롤백 범위가 다를 수 있어 주의해야 합니다. 기본 시간 초과는 문장 단위 취소일 수 있고 데드락 희생자는 트랜잭션 전체가 취소됩니다. 앱 프레임워크의 rollback 정책까지 확인하고 새 트랜잭션 재시도 경계를 명확히 만듭니다.

LOCK=NONE이면 DDL이 아무도 막지 않나요?

아닙니다. 지원되는 작업에서 동시 DML을 허용한다는 뜻이며 메타데이터 잠금은 남습니다. 오래 열린 트랜잭션이 DDL 완료를 막고 그 대기가 다른 요청에도 영향을 줄 수 있습니다. 알고리즘과 잠금 옵션, 장기 트랜잭션을 함께 확인합니다.

SKIP LOCKED면 공정하게 처리되나요?

공정성을 자동 보장하지 않습니다. 오래 잠긴 작업은 반복해서 건너뛰어질 수 있습니다. 큐라면 재시도·작업 임대 만료·오래된 항목 탐지 같은 정책이 필요합니다. 전체 집합의 정확한 스냅샷을 반환하는 도구로 사용하면 안 됩니다.

꼬리 질문: IX 잠금이 보이면 테이블 전체가 잠긴 건가요?

답변: 테이블 수준의 의도 잠금은 맞지만 테이블 전체에 대한 배타 잠금과는 다릅니다. 서로 다른 행을 수정하는 여러 트랜잭션이 IX를 동시에 가질 수 있습니다.

확인: TABLE/IX만 보고 범인을 정하지 말고 실제 레코드 잠금과 대기 관계를 확인합니다. 자물쇠 이름보다 어느 객체의 어느 권한이 충돌하는지 설명하는 것이 정확합니다.

꼬리 질문: RC로 바꾸면 모든 갭 잠금이 없어지나요?

답변: 일반적인 검색·스캔에서 갭 잠금 사용이 줄지만 외래 키 검사와 중복 키 검사 등 예외가 있습니다. 모든 잠금 대기가 없어지는 것은 아닙니다.

판단: 동일 행 X 잠금 경쟁은 여전히 남습니다. RC 전환 전에 업무의 반복 읽기 가정과 실제 충돌 종류를 확인해야 합니다.

꼬리 질문: SKIP LOCKED로 가져온 작업은 처리 완료까지 보호되나요?

답변: 잠금은 해당 트랜잭션이 끝나면 해제됩니다. 작업을 골랐다는 사실만으로 장시간 처리 소유권이 영구 유지되지 않습니다.

설계: 짧은 트랜잭션에서 작업을 선점 상태로 바꾸고 커밋한 뒤 처리한다면, 상태·소유자·임대 만료·재수행 정책이 필요합니다. 처리 중 프로세스가 죽는 경우와 중복 실행을 함께 설계합니다.

꼬리 질문: 같은 순서로 UPDATE하면 데드락이 완전히 없어지나요?

답변: 공통 키 순서는 순환 가능성을 줄이지만 완전한 제거 보장은 아닙니다. 보조 인덱스, 외래 키, 서로 다른 실행 경로도 잠금 획득에 영향을 줍니다.

운영: 정상적인 제한 재시도를 유지하고 데드락 로그의 실제 인덱스와 SQL을 분석합니다. 앱의 호출 순서만 보고 엔진 내부의 모든 잠금 순서가 같다고 가정하지 않습니다.

심층 면접: UPDATE는 한 행만 바꿨는데 다른 상품 INSERT가 막힙니다. 왜 그런가요?

답변: 최종 변경 행 수와 잠금 범위가 항상 같지 않기 때문입니다. 실행 계획의 인덱스 탐색 범위, 격리 수준, 갭·넥스트키 잠금, 유일 키·외래 키 검사를 확인합니다.

예시: RR에서 범위 잠금 읽기가 10과 20 사이의 삽입을 제어하면 id=15는 기존 id=10·20과 다른 값이어도 기다릴 수 있습니다. 잠금 대상은 기존 행뿐 아니라 삽입 가능한 위치도 포함될 수 있습니다.

검증: data_lock_waits로 대기자와 차단자를 연결하고 data_locks의 인덱스와 잠금 모드를 확인하겠습니다. WHERE 문자열만 보고 범위를 단정하지 않겠습니다.

심층 면접: 데드락을 줄이기 위해 모든 작업을 한 번에 큰 트랜잭션으로 묶어도 될까요?

답변: 오히려 잠금 보유 시간과 동시 보유 자원이 늘어 경쟁과 롤백 비용이 커질 수 있습니다. 함께 원자적으로 확정해야 하는 최소 업무 범위를 먼저 정하겠습니다.

개선: 동일 자원 접근 순서를 맞추고, 검색 범위를 줄이는 인덱스를 검토하며, 잠금 보유 중 외부 대기를 줄입니다. 큰 배치를 나누는 경우에는 부분 완료를 허용할 수 있는지와 재개 위치를 설계해야 합니다.

한계: 접근 순서를 맞춰도 보조 인덱스·외래 키·다른 경로의 잠금 때문에 모든 데드락이 사라진다고 보장하지 않습니다. 원인 기록과 제한된 업무 재시도를 함께 유지하겠습니다.
