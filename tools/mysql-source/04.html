1. ‘저장 완료’ 버튼을 누른 직후 전원이 꺼진다면

재고를 10에서 9로 바꾼 뒤 성공 응답을 받았습니다. 그런데 DB 서버 전원이 꺼졌습니다. 다시 켰을 때 재고는 9여야 할까요? 업무가 기대하는 답은 그렇습니다. 하지만 메모리는 전원이 꺼지면 사라집니다. 따라서 메모리에서 값을 바꾼 것만으로는 성공을 약속할 수 없습니다. 복구에 충분한 정보를 안정적인 저장소에 남기는 과정이 필요합니다.

회의 중 큰 원본 문서 전체를 매번 출력하는 대신 변경 지시를 작은 장부에 순서대로 기록한다고 생각해 보세요. 원본 출력이 늦어져도 장부를 적용하면 다시 만들 수 있습니다. 이것이 redo를 이해하는 출발점입니다. 다만 실제 redo는 SQL 문장을 그대로 저장한 일기장이 아니라 InnoDB 내부 변경을 재현하는 정보입니다.

2. redo, undo, binlog는 목적부터 다르다

기록주된 질문역할
Redo데이터 파일에 덜 반영된 변경을 어떻게 복구하나?InnoDB crash recovery
Undo변경 전 상태가 필요하면 어떻게 하나?롤백, 일관된 읽기의 과거 버전 구성
Binary log서버의 변경 이벤트를 다른 서버나 복구 작업에 어떻게 전달하나?복제와 시점 복구의 기반

‘redo는 커밋한 트랜잭션만 담는다’는 설명은 틀립니다. 커밋 전에 발생한 변경의 redo도 기록될 수 있습니다. crash recovery는 먼저 redo로 페이지 상태를 복원하고, 확정되지 않은 트랜잭션의 변경은 undo 등을 사용해 취소하는 작업을 포함합니다. redo와 undo는 서로 경쟁하는 선택지가 아니라 서로 다른 방향의 복구 재료입니다.

3. UPDATE부터 COMMIT까지, 무엇이 언제 안전해지나

단순화한 개념 흐름은 다음과 같습니다. 행을 찾아 필요한 잠금을 획득하고, 이전 상태를 되돌릴 정보와 변경을 재현할 정보를 만들며, 버퍼 풀의 페이지를 변경합니다. 실제 구현은 여러 내부 작업과 로그 레코드가 엮이므로 이 순서를 모든 함수의 정확한 호출 순서로 외우지는 마세요. 핵심 제약은 데이터 페이지를 내보내기 전에 복구에 필요한 redo가 먼저 보존되어야 한다는 WAL(Write-Ahead Logging) 원칙입니다.

COMMIT은 트랜잭션의 확정 경계입니다. 기본적인 내구성 설정에서는 커밋에 필요한 redo를 안정적인 저장장치로 flush하는 과정이 중요합니다. binlog가 활성화되면 엔진의 확정과 binlog의 기록이 어긋나지 않도록 조정하는 과정도 필요합니다. 그렇지 않으면 원본 DB에는 반영되었는데 복제에 전달할 이벤트가 없는 문제가 생길 수 있습니다.

그렇다고 커밋마다 디스크 동기화가 정확히 한 번씩 발생한다고 단정할 수는 없습니다. 여러 트랜잭션의 로그 flush를 묶는 group commit이 있습니다. ‘개별 트랜잭션이 기다리는 내구성 조건’과 ‘실제 저장장치 호출 횟수’는 다릅니다.

4. 내구성 설정을 읽는 법

SELECT @@innodb_flush_log_at_trx_commit, @@sync_binlog,
       @@log_bin;
SHOW VARIABLES LIKE 'innodb_redo_log_capacity';
SHOW GLOBAL STATUS LIKE 'Innodb_log_waits';

innodb_flush_log_at_trx_commit=1은 각 커밋에서 redo write·flush를 요구하는 정책입니다. 2는 커밋마다 파일에 write하지만 flush는 보통 주기적으로 수행합니다. 0은 write와 flush가 주기적입니다. 운영체제 캐시에 write했다는 것과 전원 장애에도 살아남을 저장소에 flush했다는 것은 다릅니다. 주기적 작업은 정확한 시계처럼 보장되지 않으므로 “최대 정확히 1초만 잃는다”고 약속하면 안 됩니다.

sync_binlog=1은 binlog의 동기화 정책에 해당합니다. redo 설정만 강하게 하고 binlog 쪽은 약하게 두면 두 기록의 장애 특성이 달라집니다. 실제 보장은 디스크·파일시스템·가상화 계층이 동기화 요청을 올바르게 지키는지에도 달려 있습니다. 속도 개선을 위해 값을 바꾸려면 어떤 장애에서 어떤 데이터를 잃을 수 있는지 먼저 합의해야 합니다.

5. 체크포인트와 doublewrite가 추가로 필요한 이유

로그를 영원히 보관할 수는 없습니다. 변경된 페이지를 데이터 파일에 충분히 반영하면 그 이전 redo 일부를 재사용할 수 있습니다. 어디까지의 복구 부담을 데이터 파일이 맡을 수 있는지 진전시키는 경계가 체크포인트와 연결됩니다. redo 공간을 늘리면 쓰기 폭주를 흡수할 여유가 생길 수 있지만, 지속적인 디스크 쓰기 능력 자체가 늘어나는 것은 아닙니다. 8.0.30부터 redo 용량 관리는 innodb_redo_log_capacity 중심으로 바뀌었습니다.

또 다른 문제는 페이지를 쓰다 전원이 꺼져 앞 절반만 새 데이터가 되는 torn page입니다. redo가 있다고 손상된 기본 페이지를 항상 그대로 고칠 수 있는 것은 아닙니다. doublewrite는 페이지를 원래 위치에 쓰기 전 별도 영역에 기록하는 방식으로 복구에 사용할 온전한 페이지를 확보합니다. 이름에 write가 두 번 들어가지만 저장장치 비용이 무조건 정확히 두 배라는 뜻은 아닙니다. 배치와 순차 I/O 특성이 다릅니다.

6. 실습: 확정·취소·재접속을 구분하기

CREATE DATABASE IF NOT EXISTS mysql_school;
USE mysql_school;
DROP TABLE IF EXISTS durability_demo;
CREATE TABLE durability_demo(id INT PRIMARY KEY, qty INT NOT NULL)
  ENGINE=InnoDB;
INSERT INTO durability_demo VALUES(1,10);
START TRANSACTION;
UPDATE durability_demo SET qty=9 WHERE id=1;
ROLLBACK;
SELECT qty FROM durability_demo; -- 10
START TRANSACTION;
UPDATE durability_demo SET qty=8 WHERE id=1;
COMMIT;
SELECT qty FROM durability_demo; -- 8

같은 로컬 서버를 docker restart mysql-school로 재시작하고 다시 조회하면 8이 유지되어야 합니다. 이것은 정상 재시작의 보존 실습이지 전원 장애 내구성 증명이 아닙니다. 컨테이너 kill도 호스트 OS 전원 차단과 같지 않습니다. OS 캐시가 살아 있을 수 있기 때문입니다. ‘강제 종료했는데 안 잃었으니 설정 2도 완전히 안전하다’는 결론을 내리면 안 됩니다.

7. 장애 시나리오: 커밋은 됐는데 응답을 못 받았다

클라이언트가 COMMIT을 보냈고 서버는 성공적으로 확정했습니다. 그 직후 네트워크가 끊기면 클라이언트는 오류만 봅니다. 이때 재시도하면 중복 출고가 생길 수 있습니다. DB의 원자성이 ‘클라이언트가 결과를 반드시 안다’는 보장까지 주는 것은 아닙니다.

업무 요청에 고유한 요청 ID를 붙이고 UNIQUE 제약으로 중복 처리를 막는 방법을 생각해 볼 수 있습니다. 예를 들어 출고 요청 ID가 이미 처리되었다면 저장된 결과를 조회합니다. 단순히 모든 SQL 오류를 실패로 보고 같은 재고 차감을 반복하는 것은 위험합니다. 커밋 결과 불명확성과 확실한 롤백을 구분해야 합니다.

8. 상세 면접 Q&A

COMMIT 후 데이터 페이지가 아직 더티여도 괜찮나요?

복구에 필요한 로그가 내구성 조건을 충족했다면 가능합니다. crash 후 redo를 적용해 데이터 파일에 없던 변경을 재현할 수 있습니다. 커밋은 모든 데이터 페이지를 즉시 flush하는 명령이 아닙니다. 로그와 페이지를 분리해야 쓰기 성능과 복구가 함께 성립합니다.

Redo가 있는데 undo가 왜 필요한가요?

Redo는 변경을 재현하고 undo는 이전 상태를 구성합니다. 장애 복구 과정에서 아직 확정되지 않은 변경이 redo로 다시 나타날 수 있으므로 이를 취소할 정보가 필요합니다. 실행 중인 일반 SELECT가 과거 버전을 읽는 데도 undo가 사용됩니다.

Redo를 크게 하면 쓰기가 영원히 빨라지나요?

아닙니다. 일시적인 쓰기 증가를 흡수하고 체크포인트 압박을 완화할 수 있지만, 장기적으로 생성되는 더티 페이지를 저장장치가 처리해야 합니다. 버퍼 크기는 지속 처리량을 대체하지 못합니다. 복구 시간과 디스크 공간도 함께 고려합니다.

Binlog는 백업인가요?

완전한 기준 백업을 대체하지 않습니다. 기준 백업 이후의 이벤트를 적용해 특정 시점으로 복구하는 데 사용합니다. 기준 데이터, 필요한 로그 범위, 위치나 GTID, 복구 절차가 함께 있어야 합니다. 로그가 남아 있다는 사실만으로 복구 가능성을 확정하지 않습니다.

Doublewrite를 끄면 성능이 좋아지나요?

일부 비용은 줄 수 있지만 부분 페이지 쓰기에서의 복구 보호를 잃을 수 있습니다. 저장장치의 원자적 쓰기 지원 등 구체적인 전제 없이 끄는 것은 성능 튜닝으로 권할 수 없습니다. 먼저 실제 병목이 이 경로인지 측정해야 합니다.

커밋 응답이 끊기면 롤백된 것으로 처리하나요?

확정 여부를 모를 수 있습니다. 서버는 이미 확정했는데 응답만 유실되었을 수 있기 때문입니다. 요청 식별자·중복 방지 제약·결과 조회를 결합해 재시도 가능하게 설계합니다. 이 문제는 트랜잭션 격리 수준을 높이는 것만으로 해결되지 않습니다.
