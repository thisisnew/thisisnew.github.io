1. 출입증, 열쇠, CCTV를 혼동하지 않기

출입증은 누구인지 확인하고 어느 방에 들어갈 수 있는지 결정합니다. 금고의 열쇠는 내용을 읽게 해 주고, CCTV는 일어난 일을 기록하며, 경비원은 의심스러운 행동을 탐지합니다. IAM·KMS·CloudTrail·GuardDuty도 목적이 다릅니다. 암호화했다고 권한이 올바른 것은 아니고, 공격을 탐지한다고 취약한 코드를 고치는 것도 아닙니다.

먼저 사용자 요청을 생각해 봅시다. 고객 로그인은 Cognito 같은 고객 신원 서비스가 맡을 수 있고, 앱이 AWS API를 호출하는 권한은 IAM role로 부여합니다. DB 비밀번호는 Secrets Manager에서 관리하고, 저장 데이터 암호화에는 KMS를 활용합니다. 웹 공격의 일부는 WAF로 걸러내며, 감사와 위협 탐지는 별도 서비스를 연결합니다.

2. IAM: 인증과 인가를 분리하기

인증은 호출자가 누구인지, 인가는 그 호출이 허용되는지 판단하는 과정입니다. IAM user는 장기 신원과 자격 증명을 가질 수 있고, role은 신뢰 정책에 따라 주체가 맡아 임시 자격 증명으로 행동하는 역할입니다. 애플리케이션에 access key를 하드코딩하는 대신 EC2 instance profile·ECS task role·Lambda execution role 등을 이용하면 자격 증명의 배포와 교체 부담을 줄일 수 있습니다.

정책은 Action·Resource·Condition·Effect 등으로 허용과 거부를 표현합니다. 기본은 암묵적 거부이고 필요한 허용이 있어야 합니다. 적용 가능한 명시적 Deny는 Allow보다 우선합니다. identity policy·resource policy·permissions boundary·session policy·SCP는 모두 같은 종류의 허용장이 아닙니다. boundary와 SCP는 권한의 최대 범위를 제한하며 자체로 앱에 권한을 주지 않습니다. cross-account와 resource policy의 주체 유형에 따라 평가가 달라지므로 복잡한 경우 단순 합집합 공식 하나로 결론 내리지 않습니다.

3. KMS: 데이터를 암호화하는 키의 수명주기

큰 데이터를 모두 KMS API에 직접 보내 암호화하는 방식만 있는 것은 아닙니다. envelope encryption에서는 데이터 키로 본문을 암호화하고, 그 데이터 키를 KMS key로 보호합니다. 저장할 것은 암호문과 암호화된 데이터 키이며 평문 키는 필요한 동안만 사용합니다. 복호화할 때 KMS 권한과 키 정책이 맞아야 데이터 키를 얻고 본문을 읽을 수 있습니다.

S3 읽기 권한이 있어도 SSE-KMS 객체의 키를 사용할 수 없으면 읽기가 실패할 수 있습니다. 반대로 키 권한이 있다고 버킷 접근 권한까지 생기는 것은 아닙니다. 키 교체는 새 암호화에 사용할 키 재료를 바꾸는 과정이며 기존 데이터 전체를 즉시 다시 암호화하는 것과 구분합니다. 키 삭제는 해당 키로 보호한 데이터를 되살릴 수 없게 만들 수 있으므로 데이터 보존과 복구 계획에 포함해야 합니다.

CloudHSM은 전용 HSM과 더 직접적인 암호화 장치 제어 요구에서 검토하는 선택지입니다. KMS와 동일한 운영 책임·통합 편의성을 제공하는 대체 이름이 아닙니다. ACM은 인증서 발급·관리·지원 서비스 연동, Secrets Manager는 DB 비밀번호·API 비밀 등 secret 저장과 교체라는 역할입니다.

4. Secrets Manager: 저장보다 교체가 어렵다

비밀번호를 안전한 곳에 넣어도 앱이 로그에 출력하거나 메모리에 무기한 캐시하면 문제가 남습니다. secret 교체는 새 값을 만들고 대상 시스템에 적용하고 검증하며 앱이 새 값을 쓰도록 만드는 과정입니다. DB 비밀번호만 바꾸고 연결 풀이나 캐시를 고려하지 않으면 배포 없이도 접속 장애가 생깁니다. 새 secret 조회 권한과 KMS 복호화 권한, 회전 작업의 네트워크 접근을 함께 확인합니다.

직원 로그인을 중앙화하는 IAM Identity Center, Microsoft 디렉터리 통합을 돕는 Directory Service, 앱 내부 권한 정책을 다루는 Verified Permissions도 IAM과 목적이 겹쳐 보이지만 책임 범위가 다릅니다. 고객의 “자기 주문만 조회” 권한은 AWS API role 하나로 저절로 구현되지 않습니다. 애플리케이션이 리소스 소유자를 검증해야 합니다.

WAF 규칙은 정상 요청을 차단할 수 있으므로 관찰·카운트 모드와 샘플링으로 영향을 확인하고 적용합니다. CAPTCHA도 자동화 남용 대응 도구이지 사용자의 실제 업무 권한을 증명하는 절차가 아닙니다. Firewall Manager는 여러 계정의 방어 정책을 중앙 관리하는 목적입니다.

6. 증거·공유·컴플라이언스

Artifact는 AWS 규정 준수 문서 접근, Audit Manager는 감사 증거 수집과 평가 지원, Resource Access Manager는 지원 리소스의 안전한 공유와 관련됩니다. Audit Manager는 현재 공식 목록에서 신규 고객을 받지 않는 유지보수 단계로 안내됩니다. 기존 소개의 역할과 새 고객의 도입 가능성을 구분합니다. 유지보수 목록 AWS가 인증을 보유했다는 이유만으로 고객의 애플리케이션이 자동으로 모든 규정을 준수하는 것은 아닙니다. 데이터 분류·보존·접근 검토·증거 수집은 자신의 워크로드 조건으로 확인해야 합니다. 공용·계정 간 공유는 IAM Access Analyzer 등으로 의도한 범위인지 점검합니다.

7. 가상 장애: 버킷 권한은 있는데 파일이 안 읽힌다

운영 앱에 S3 GetObject를 허용했는데 AccessDenied가 발생했습니다. 객체는 고객 관리형 KMS key로 암호화되어 있었고 앱 role은 해당 키를 사용할 수 없었습니다. 확인 순서는 호출 주체, 버킷·객체 ARN, 정책의 Deny와 조건, endpoint policy, KMS key policy와 필요한 권한입니다. 문제를 빨리 해결하려고 Action: *, Resource: *를 붙이면 원인을 숨기고 피해 범위를 키울 수 있습니다.

종이 실습으로 “고객→앱→S3→KMS” 경로마다 어떤 신원이 어떤 권한을 쓰는지 적어 보세요. 고객 로그인 토큰과 앱의 AWS 임시 자격 증명을 같은 것으로 적었다면 인증 경계부터 다시 정리해야 합니다.

8. 상세 면접 Q&A

Q. IAM role이 있으면 비밀번호가 전혀 필요 없나요?

AWS API 접근에서 장기 access key를 줄이는 데 유용하지만 모든 외부 시스템이 IAM 인증을 지원하는 것은 아닙니다. DB나 외부 SaaS가 별도 secret을 요구할 수 있습니다. role로 Secrets Manager에 접근해 secret을 가져오는 것처럼 두 기능을 결합하기도 합니다.

Q. KMS와 Secrets Manager의 차이는 무엇인가요?

KMS는 암호화 키 관리와 암호 연산·서비스 통합을 제공하고, Secrets Manager는 애플리케이션이 사용할 비밀 값과 회전 수명주기를 관리합니다. Secrets Manager가 저장 데이터를 보호하는 데 KMS를 사용할 수 있습니다. 열쇠 관리와 비밀번호 보관·교체는 연결되지만 같은 책임은 아닙니다.

Q. WAF를 설치하면 SQL 인젝션을 해결한 건가요?

일부 공격 패턴을 줄이는 방어 계층을 추가한 것입니다. 파라미터 바인딩·입력 처리·DB 최소 권한 등 코드와 데이터 접근 설계는 여전히 필요합니다. 우회 가능한 패턴이나 업무 로직 취약점을 WAF 하나에 맡기지 않습니다.

Q. 암호화된 백업이면 랜섬웨어에도 안전한가요?

읽기 보호와 삭제·변조 방지는 다릅니다. 공격자가 백업 삭제나 키 삭제 권한을 얻으면 암호화만으로 복구를 보장할 수 없습니다. 별도 계정·제한된 권한·보존 잠금·복구 테스트를 조합해 공격과 실수의 범위를 줄입니다.

깊이 읽기: 권한과 암호화를 실제 요청 순서로 해석하기

인증서와 출입증과 금고 열쇠

인증은 “누구인가”를 확인하고 인가는 “무엇을 해도 되는가”를 결정합니다. 암호화는 권한 없이 내용을 읽기 어렵게 만드는 보호 수단입니다. 서버가 TLS를 사용한다고 해당 사용자가 모든 데이터를 읽어도 되는 것은 아니며, S3 객체가 암호화되었다고 공개 접근 정책이 무해해지는 것도 아닙니다. 각 보호 수단이 막는 위험을 별도로 적어야 합니다.

예를 들어 앱이 S3의 고객 사진을 읽는다면 실행 중인 IAM role의 임시 자격증명으로 API 요청을 서명합니다. S3는 해당 action과 resource에 대한 정책을 평가합니다. SSE-KMS로 보호된 객체라면 KMS 사용 권한과 키 상태 등이 추가로 중요합니다. 네트워크 경로, S3 권한, KMS 권한 중 하나가 막혀도 결과는 접근 실패일 수 있지만 수정할 설정은 다릅니다.

정책을 읽는 다섯 질문

  1. Principal: 실제 호출자는 누구인가? 내 노트북의 사용자와 운영 task의 role은 다를 수 있습니다.
  2. Action: ListBucket인가 GetObject인가? 목록 조회와 객체 읽기는 다른 권한입니다.
  3. Resource: 버킷 ARN인가 객체 ARN인가? 이름이 비슷해도 범위가 다릅니다.
  4. Condition: 특정 네트워크·암호화·태그·조직 조건이 맞는가?
  5. Guardrail: 명시적 deny와 조직 정책·경계 등 적용되는 제한은 무엇인가?

이렇게 요청을 구체화하면 “S3 권한을 줬다”는 모호한 말을 줄일 수 있습니다. 같은 계정과 교차 계정, role ARN과 session principal에 대한 resource policy 평가에는 차이가 있으므로 모든 정책을 단순 교집합으로만 외우지 않습니다. 다만 명시적 deny가 있는 요청에 allow를 계속 추가해도 해결되지 않는다는 점은 핵심입니다.

봉투 암호화의 두 종류 키

큰 짐을 보낼 때 내용물 전체를 본사 금고 안에 넣는 대신 상자를 작은 열쇠로 잠그고 그 열쇠를 다시 본사의 보호 아래 두는 비유가 유용합니다. Envelope encryption에서는 data key로 데이터를 암호화하고 그 data key를 KMS key로 보호합니다. 암호문 데이터와 암호화된 data key를 함께 보관하고, 읽을 때 권한 있는 경로에서 data key를 복호화해 사용합니다. 서비스별 실제 호출·캐시 방식은 다를 수 있습니다.

이 구조에서 KMS key 회전은 기존 모든 데이터의 암호문을 즉시 새로 쓰는 작업과 같지 않습니다. 이전 데이터를 읽기 위한 키 재료의 관리와 새 암호화에 쓰는 재료를 서비스가 다룹니다. 키를 비활성화하거나 삭제하면 권한 정책이 맞아도 복호화가 영향을 받을 수 있으므로 데이터 보존·복구 계획과 키 수명주기를 함께 관리해야 합니다.

Secret 회전은 값을 바꾸는 API 한 번이 아니다

DB 비밀번호를 Secrets Manager에서 새 값으로 저장해도 DB 사용자 비밀번호가 자동으로 같은 시점에 바뀌고 모든 애플리케이션 캐시가 갱신된다고 가정하면 안 됩니다. 회전 절차는 새 자격증명 준비, 대상 시스템 적용, 테스트, 현재 버전 전환 같은 흐름과 실패 복구를 포함합니다. 구체적 동작은 선택한 회전 방식에 따릅니다.

앱은 secret을 매 요청마다 원격 조회하면 비용과 지연이 커질 수 있어 캐시할 수 있습니다. 하지만 무기한 캐시하면 회전 후 인증 실패가 길어집니다. 적절한 갱신과 실패 시 재조회, 기존 연결의 수명, 새 연결 생성 동작을 검증합니다. 비밀정보를 잘 보관하는 것과 실제 서비스가 중단 없이 새 값을 쓰는 것은 서로 다른 완료 기준입니다.

보안 서비스를 탐지·예방·평가로 나누기

WAF 규칙은 웹 요청을 필터링하는 데 쓰고, GuardDuty는 위협 탐지 결과를 제공하며, Inspector는 지원되는 자원의 취약점 등을 평가하고, Macie는 S3의 민감 데이터 식별에 도움을 줍니다. Security Hub는 보안 상태와 findings를 모아 검토하는 흐름에 연결됩니다. 이름을 여러 개 켰다는 사실보다 어떤 위험을 어떤 증거로 찾고 누가 조치할지 정의해야 합니다. 서비스별 지원 범위·로그 소스·자동 대응은 구성에 따라 확인합니다.

더 깊은 면접 Q&A: 보안을 한 겹으로 설명하지 않기

Q. AccessDenied가 나면 AdministratorAccess를 붙여 원인을 찾으면 되나요?

답변: 과도한 권한으로 우회하기 전에 실제 principal, action, resource, condition과 deny 근거를 확인합니다. 로그의 요청 ID와 호출 경로를 연결하면 원인이 S3 정책인지 KMS인지 조직 제한인지 좁힐 수 있습니다.

꼬리 질문: 넓은 권한에서 성공했다는 결과는 필요한 최소 권한을 증명하지 못합니다. 허용해야 할 정상 요청과 거부해야 할 요청을 함께 테스트해야 최소 권한 정책의 경계를 검증할 수 있습니다.

Q. 임시 자격증명은 유출되어도 안전한가요?

답변: 만료 시간이 있어 장기 키보다 노출 시간을 제한할 수 있지만 유효한 동안 권한 범위 안에서 악용될 수 있습니다. 권한 축소, 짧은 세션, 조건 제한, 탐지와 사고 대응이 여전히 필요합니다.

주의: 자격증명을 새로 발급했다고 이전 세션이 항상 즉시 무효화되는 것은 아닙니다. 해당 서비스와 세션의 철회 방법을 확인하고, 이미 수행된 데이터 접근이나 정책 변경도 조사합니다.

Q. KMS를 사용하면 애플리케이션에서 평문이 사라지나요?

답변: 데이터를 처리하려면 어느 지점에서는 평문이 필요할 수 있습니다. KMS는 키 관리와 암호 연산을 보호하지만 앱 메모리·로그·응답으로 흘러간 평문까지 자동으로 제거하지 않습니다.

예: 암호화된 DB에서 읽은 주민정보를 디버그 로그에 찍으면 로그 저장소가 새로운 노출 경로가 됩니다. 수집 최소화, 마스킹, 접근 제한, 보존 기간을 데이터 경로 전체에 적용합니다.

Q. 최소 권한은 배포 후 한 번 정하면 끝인가요?

답변: 기능과 조직이 바뀌면 필요한 권한도 변합니다. 사용 흔적과 업무 요구를 검토해 불필요한 권한을 줄이고, 새 권한 요청에는 목적·자원 범위·기간·담당자를 남깁니다.

운영 연결: 긴급 권한이 계속 남는 것을 막기 위해 만료와 사후 검토를 포함합니다. 정상 배포·복구 경로를 지나치게 막아 사람들이 우회 계정을 만들게 하지 않도록 실제 운영 절차와 함께 설계합니다.

직접 풀어 보기: 암호화된 파일을 관리자도 못 읽는다

S3 객체는 존재하고 앱 role에는 객체 읽기 권한이 있습니다. 그런데 SSE-KMS 객체만 읽지 못합니다. 버킷 정책을 더 넓히기 전에 무엇을 확인해야 할까요? 실제 계정의 정책 평가를 단순화한 학습 상황입니다.

해설 펼치기 — 판단 과정과 조건을 바꾼 경우

키 경로: 사용된 KMS key의 식별자·리전·상태와 호출 주체가 필요한 복호화 권한을 갖는지 확인합니다. Key policy와 IAM·grant 등 해당 경로의 허용 방식과 조건을 검토합니다.

추가 제한: 명시적 deny나 조직 정책, 호출 서비스·암호화 맥락 조건이 적용되는지도 봅니다. S3 allow를 추가하는 것만으로 다른 계층의 거부가 해결되지 않습니다.

증거: S3와 KMS의 관련 요청 기록·오류·시각을 연결합니다. 객체를 새로 올려 암호화를 바꾸는 우회는 원래 데이터 보호 요구와 키 문제를 숨길 수 있습니다.

복구 설계: 같은 문제가 백업 복원 계정에서도 생길 수 있습니다. 데이터 복사본뿐 아니라 해당 키와 권한을 사용할 수 있는지 복구 훈련에서 확인해야 합니다.
