1. 저장할 수 있다는 것과 잘 조회할 수 있다는 것

창고에 물건을 넣을 공간이 있다는 사실만으로 작업이 빨라지지는 않습니다. 상품번호로 찾을지, 유통기한 순서로 찾을지, 같은 발주서의 상품을 묶어 찾을지에 따라 배치가 달라집니다. DB도 데이터 모양뿐 아니라 조회 패턴·변경 원자성·지연·확장 방식으로 선택합니다. “데이터가 많으니 NoSQL”이나 “정합성이 중요하니 언제나 관계형” 같은 한 줄 규칙은 조건을 너무 많이 생략합니다.

2. RDS: 관리형 관계형 DB의 책임 경계

RDS는 지원 관계형 엔진의 설치·백업·패치·복제 등 운영 기능을 관리형으로 제공합니다. 하지만 느린 쿼리·잘못된 인덱스·긴 트랜잭션·과도한 연결은 애플리케이션 설계 문제로 남습니다. MySQL을 RDS로 옮겨도 WHERE 조건과 인덱스가 맞지 않는 전체 스캔은 저절로 사라지지 않습니다. DB 엔진과 버전·파라미터·인스턴스·스토리지·배포 형태를 함께 이해해야 합니다.

애플리케이션의 커넥션 풀 크기는 서버별 값입니다. 앱 20대가 각각 최대 50개 연결을 만들면 잠재적으로 1,000개 연결이 생깁니다. 앱을 자동 확장할 때 DB 연결 한도를 같이 계산하지 않으면 DB가 먼저 포화됩니다. RDS Proxy 같은 연결 관리 도구는 도움이 될 수 있지만 모든 세션 상태·트랜잭션을 무한히 다중화하는 기능은 아닙니다. 긴 트랜잭션과 세션 고정 조건도 검토합니다.

3. Multi-AZ와 Read Replica: 정확한 배포 형태를 말하기

구성 주목적 읽기 경로 핵심 주의점
전통적 Multi-AZ DB 인스턴스 고가용성 standby를 읽기 대상으로 사용하지 않음 장애 조치 때 연결 재수립 필요
Multi-AZ DB 클러스터 고가용성과 읽기 활용 두 reader 인스턴스에서 읽기 지원 지원 엔진·구성 조건 확인
Read Replica 읽기 분산·일부 복구 활용 replica endpoint로 읽음 일반적으로 비동기 복제 지연 고려
Aurora 클러스터 분산 스토리지와 DB 인스턴스 계층 writer와 reader 역할 구분 읽기 일관성·승격·연결 동작 확인

“Multi-AZ는 읽기를 못 한다”는 말은 첫 번째 형태의 standby에 대해서만 정확합니다. 시험이나 면접에서는 배포 형태를 명시하세요. 읽기 복제본은 쓰기 직후의 데이터를 아직 적용하지 않았을 수 있습니다. 사용자가 주문을 저장한 직후 “주문 없음”을 보지 않게 하려면 해당 조회를 writer로 보내거나 일관성 요구를 만족하는 별도 방식을 설계합니다. 읽기를 분산한다고 쓰기 처리량이 같은 비율로 늘어나지는 않습니다.

4. Aurora: 컴퓨팅과 스토리지의 역할 분리

Aurora는 MySQL/PostgreSQL 호환 엔진과 분산된 클러스터 스토리지 구조를 사용합니다. 공개 문서는 여러 AZ에 걸친 스토리지 복제와 장애 복구를 설명합니다. DB 인스턴스와 데이터 저장 계층을 분리해 읽기 인스턴스 추가와 장애 복구를 지원한다는 점이 핵심입니다. 일반 MySQL의 파일 복제 토폴로지와 완전히 같은 구조라고 가정하지 마세요. 반대로 호환성이 있으니 모든 플러그인·버전·운영 동작이 같다는 뜻도 아닙니다.

writer endpoint와 reader endpoint는 용도가 다릅니다. reader endpoint는 읽기 연결을 분산하는 역할이며 각 SQL 문장을 가장 한가한 서버로 다시 분산하는 마법의 프록시로 이해하면 안 됩니다. 연결 풀을 오래 유지하면 부하가 균등하지 않을 수 있습니다. Aurora Serverless도 용량 조정의 하한·상한·전환 동작·지원 버전 조건을 확인해야 하며, 언제나 비용이 0으로 줄어드는 것으로 일반화하면 안 됩니다.

5. DynamoDB: 테이블보다 접근 패턴을 먼저 설계

DynamoDB는 key-value/document 모델을 제공하는 관리형 DB입니다. partition key는 데이터와 부하를 나누는 중요한 기준이고 sort key는 같은 partition key 안에서 정렬과 범위 조회를 표현하는 데 사용됩니다. warehouseId만 partition key로 쓰면 가장 큰 창고의 요청이 집중될 수 있습니다. warehouseId#date처럼 분산을 바꾸면 특정 조회를 여러 키로 나누어 읽어야 할 수도 있습니다. 쓰기 분산과 조회 편의는 함께 설계합니다.

Query는 키 조건에 맞는 데이터를 읽는 동작이고 Scan은 넓은 범위를 훑습니다. 필터를 붙였다고 읽기 자체가 항상 줄어드는 것은 아닙니다. 필요한 접근 경로를 보조 인덱스로 만들되 저장·쓰기 비용도 계산합니다. 기본 테이블과 LSI는 강한 일관성 읽기를 선택할 수 있는 반면 GSI 읽기는 그와 같은 강한 일관성 옵션을 제공하지 않습니다. 글로벌 테이블의 일관성 모드는 제품·리전 지원과 설정을 확인해야 하므로 “모든 글로벌 테이블은 언제나 동일한 일관성”이라고 외우지 않습니다.

조건부 쓰기는 “현재 상태가 WAITING일 때만 변경” 같은 경쟁 제어에 유용합니다. 트랜잭션 기능도 있지만 관계형 조인 모델과 동일한 사용 경험은 아닙니다. TTL은 만료 즉시 정확한 시각에 지워지는 스케줄러가 아니므로, 만료된 항목을 업무에서 즉시 제외해야 한다면 읽기 조건과 애플리케이션 검증이 필요합니다.

6. ElastiCache와 MemoryDB: 빠름보다 원본의 위치

cache-aside에서는 앱이 캐시를 먼저 읽고, 없으면 DB에서 조회해 캐시에 채웁니다. DB 변경 후 캐시 무효화를 실패하면 오래된 값이 남습니다. TTL은 오래된 상태의 기간을 줄일 수 있지만 정합성을 즉시 보장하지는 않습니다. 캐시 미스가 한꺼번에 발생하면 DB가 몰리는 cache stampede가 생길 수 있어 만료 분산·요청 병합·사전 갱신을 고려합니다.

ElastiCache는 지원 엔진과 구성에 따라 캐시 기능을 제공합니다. MemoryDB는 내구성 있는 인메모리 데이터베이스라는 역할로 구분합니다. “메모리니까 다 없어져도 되는 데이터”와 “Redis 호환이면 모든 내구성 계약이 같다”는 둘 다 잘못입니다. 엔진·복제·영속성·장애 조치 조건을 확인하고 원본 저장 책임을 명시해야 합니다.

7. 목적별 DB와 원문 속 나머지 제품

Neptune은 관계 탐색이 중요한 그래프, DocumentDB는 MongoDB 호환 문서 모델, Keyspaces는 Cassandra 호환 워크로드, Timestream 계열은 시계열, RDS for Db2는 Db2 엔진 호환 요구와 연결해 이해합니다. 호환이라는 말은 특정 원본 제품의 모든 기능과 버전이 동일하다는 뜻이 아닙니다. 실제 사용하는 연산·드라이버·일관성·마이그레이션 도구를 확인해야 합니다. Lightsail 관리형 DB는 단순한 패키지형 운영이라는 맥락이고, RDS on VMware는 공식 목록상 2022-05-01 지원 종료 제품입니다. Timestream for LiveAnalytics는 신규 고객이 들어갈 수 없는 유지보수 단계이며 Timestream for InfluxDB와 동일 제품이 아닙니다. 종료 목록 · 유지보수 목록

8. 가상 장애: 저장은 됐는데 화면에는 없다

주문 쓰기를 writer에 커밋하고 조회는 replica로 보냈습니다. replica가 2초 뒤처져 사용자는 재주문했습니다. 문제는 저장 실패가 아니라 조회 경로와 일관성 요구의 불일치입니다. 쓰기 직후에는 writer 조회, 주문 요청 ID의 멱등 처리, 복제 지연 경보를 함께 적용할 수 있습니다. 캐시까지 있으면 DB 복제 지연과 캐시의 오래된 값을 별도로 조사해야 합니다.

9. 상세 면접 Q&A

Q. RDS Multi-AZ를 쓰면 장애 때 오류가 전혀 없나요?

장애 탐지와 전환 동안 기존 연결이나 진행 중 트랜잭션은 실패할 수 있습니다. 앱은 DNS 변경과 연결 재수립·제한된 재시도·멱등성을 지원해야 합니다. 인프라 고가용성은 모든 요청의 무중단 성공 보장과 다릅니다.

Q. DynamoDB는 NoSQL인데 트랜잭션이 없나요?

트랜잭션 기능이 있습니다. NoSQL이라는 분류만으로 원자성이나 일관성을 단정하면 안 됩니다. 다만 지원 연산·범위·비용·제약을 확인해야 하고 관계형 DB의 조인과 스키마 모델을 그대로 옮기기보다 접근 패턴 중심으로 설계해야 합니다.

Q. 캐시를 추가하면 항상 빨라지나요?

적중률이 낮거나 데이터 변경이 잦으면 네트워크 호출과 무효화 비용만 늘 수 있습니다. 오래된 데이터를 허용할 수 있는지도 중요합니다. 적중률·DB 부하·p99·오래된 값으로 인한 업무 영향을 함께 측정해야 합니다.

Q. 읽기 복제본을 늘리면 쓰기 병목도 해결되나요?

읽기를 옮겨 writer의 자원을 확보하는 간접 효과는 있을 수 있지만 쓰기 자체를 여러 writer로 나누는 것은 아닙니다. 실제 병목이 쓰기 잠금·로그·스토리지라면 트랜잭션과 데이터 모델·배치·파티셔닝 등의 다른 접근이 필요합니다.
