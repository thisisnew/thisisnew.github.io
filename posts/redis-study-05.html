이번 장의 질문

Redis에 SET을 보내 OK를 받았다. 바로 뒤에 서버의 전원이 끊겼다면 그 값은 남아 있을까? 이 질문에 “AOF를 켰으니 남는다”라고만 답하면 중요한 조건을 놓친 것이다. 데이터가 메모리에서 바뀌는 시점, 운영체제에 전달되는 시점, 저장장치에 동기화되는 시점, 응답을 돌려주는 시점은 서로 다른 사건이다. AOF를 이해한다는 것은 이 사건의 순서와 실패 지점을 설명할 수 있다는 뜻이다.

이 장은 제공된 학습 자료 05장의 AOF 부분을 재구성했다. 파일 구조는 Redis 7.0 이후의 다중 파일 AOF를 중심으로 설명하고, 이전 방식은 비교 대상으로만 다룬다. 정확한 설정 기본값, 명령 지원, 관리형 서비스의 제한은 실행 버전에서 확인한다. 문서의 latest 주소가 설치된 Redis의 버전을 뜻하지는 않는다. 공식 영속성 문서

1. AOF는 무엇을 기록하는가

AOF는 Append Only File의 약자다. 직역하면 뒤에 내용을 덧붙이는 파일이다. RDB가 어느 순간의 데이터 모양을 저장한다면, AOF는 데이터를 재구성할 수 있는 변경 기록을 유지한다. 서버가 시작할 때 이 기록을 읽고 상태를 되살릴 수 있다. 하지만 “클라이언트가 보낸 모든 바이트를 영원히 보존하는 감사 로그”와는 다르다. 내부적으로 재생 가능한 형태로 기록될 수 있고, 재작성 후에는 과거의 개별 행위가 사라진다.

예를 들어 카운터가 0에서 시작해 100번 증가했다면 현재 값은 100이다. 원래 변경 이력을 끝까지 읽는 방식은 100번 증가를 재생해야 한다. 현재 상태만 복원하면 되는 경우에는 100이라는 값을 만드는 짧은 표현으로 바꿀 수 있다. AOF rewrite가 하는 일은 바로 이런 현재 상태의 재표현이다. 누가 언제 어떤 이유로 증가시켰는지를 보존하려면 별도의 업무 이벤트 로그가 필요하다.

은행 장부 비유를 써 보자. RDB는 오후 3시의 계좌 잔액표, AOF는 그 이후 잔액을 바꾸는 기록에 가깝다. rewrite는 지금의 잔액으로 새 장부를 열고 이후 거래를 이어 적는 일이다. 다만 Redis AOF가 법적 감사 장부라는 뜻은 아니다. Redis는 복원에 필요한 데이터를 관리할 뿐 업무 거래의 정당성, 외부 DB와의 원자성, 사용자 신원까지 자동 보장하지 않는다. 비유를 쓰되 보장 범위까지 함께 좁혀야 한다.

2. 쓰기 경로를 네 개의 층으로 나누기

처음 배울 때는 다음 그림을 기억하면 된다. 세부 구현은 버전에 따라 변하지만 구분 자체는 유용하다.

클라이언트 명령
    ↓
Redis가 메모리 상태 변경
    ↓
AOF 기록 준비와 파일 write
    ↓
운영체제 페이지 캐시
    ↓ fsync 계열 동기화
저장장치의 내구성 경계

페이지 캐시는 운영체제가 파일 데이터를 잠시 보관하는 메모리 영역이다. write 호출이 성공했다고 곧바로 물리 저장장치에 모든 데이터가 안전하게 남았다는 뜻은 아니다. 운영체제는 성능을 위해 쓰기를 묶고 나중에 전달할 수 있다. Redis 프로세스만 죽고 운영체제가 살아 있으면 페이지 캐시가 남아 복구될 수 있지만, 호스트 전원까지 사라지면 같은 결과를 기대할 수 없다.

fsync는 파일 변경을 내구성 있는 저장 영역으로 동기화하도록 운영체제에 요청하는 동작이다. 이것도 저장장치, 파일시스템, 가상화 계층이 약속을 제대로 지킨다는 전제를 포함한다. 그래서 “always면 어떤 재난에도 한 바이트도 잃지 않는다”는 표현은 과장이다. 파일이 있는 디스크 전체가 사라지는 장애는 다른 위치의 복제나 백업으로 다뤄야 한다.

장애 실험에서도 이 층을 구별해야 한다. 프로세스를 정상 종료하는 실험은 종료 처리 자체가 기록을 정리할 수 있으므로 전원 장애와 같지 않다. 강제 프로세스 종료도 OS의 페이지 캐시를 없애지 않으므로 호스트 손실을 완벽히 재현하지 않는다. 실험 결과로 “데이터가 한 번도 안 사라졌으니 무조건 안전하다”라고 결론 내리면 실험한 장애 모델보다 넓은 주장을 한 셈이다.

3. appendfsync 세 정책을 비교하기

정책 기본 생각 주로 얻는 것 반드시 받아들일 비용
always AOF를 추가한 쓰기 묶음의 동기화를 응답 경로에 반영 더 강한 로컬 내구성 저장장치 지연이 응답에 직접 영향
everysec 대략 1초 주기로 백그라운드 동기화 처리량과 내구성의 절충 최근 동기화 이후의 쓰기 유실 가능
no Redis가 명시적으로 동기화하지 않고 OS 정책에 맡김 동기화 부담 감소 OS·장치 상태에 좌우되는 더 큰 유실 창

always를 명령마다 디스크를 반드시 따로 한 번씩 두드리는 방식으로 이해하면 안 된다. 여러 클라이언트 또는 파이프라인에서 처리된 쓰기가 묶여 하나의 동기화를 공유할 수 있다. 이것을 group commit, 즉 묶음 커밋이라고 부른다. 그렇다고 파이프라인이 공짜 내구성을 만드는 것은 아니다. 네트워크 왕복과 동기화 횟수를 줄일 여지는 있지만 저장장치가 감당할 수 있는 지속 처리량은 여전히 제약이다.

everysec는 흔히 “최대 1초 유실”이라고 소개된다. 입문용으로는 마지막 주기 이후의 쓰기가 위험하다는 뜻으로 읽으면 된다. 운영 계약서에는 디스크 지연, 커널 스케줄링, 동기화 지연, 관련 설정 변경을 무시한 절대 상한으로 적지 않는다. 정상적인 주기와 실제 실패 상황의 보장을 구분하고, 원하는 RPO에 맞춰 관측과 복구 시험을 설계한다. no도 “정확히 30초마다 저장”이라는 규칙이 아니다. OS의 정책과 상태에 맡긴다는 점이 본질이다.

설정 선택은 데이터 성격에서 시작한다. 원본 DB에서 다시 가져올 수 있는 상품 설명 캐시와 Redis에만 존재하는 작업 상태는 유실 영향이 다르다. 먼저 “얼마나 잃어도 되는가”를 업무 언어로 정하고, 그다음 지연과 처리량을 측정한다. 가장 강한 정책을 무조건 고르는 것도 답이 아니다. 동기화가 느려져 요청이 시간 초과되고 재시도가 폭증하면 전체 시스템의 가용성과 중복 처리 위험이 커질 수 있다.

4. 다중 파일 AOF: base, incremental, manifest

Redis 7.0 이후 AOF는 하나의 큰 파일만으로 생각하면 안 된다. 일반적으로 AOF 전용 디렉터리 아래에 세 가지 역할의 파일이 있다.

  • base 파일: 재작성 시점의 기준 상태. 설정에 따라 RDB 또는 AOF 형식일 수 있다.
  • incremental 파일: 기준 상태 이후의 변경을 이어 적는 파일. 여러 개가 존재할 수 있다.
  • manifest 파일: 어떤 base와 incremental 파일들을 어떤 순서로 사용해야 하는지 나타내는 목록.

manifest는 목차에 가깝다. 책의 목차만 복사해도 본문이 없으면 읽을 수 없고, 본문 일부만 복사해도 어느 판의 어떤 순서인지 모르면 복원이 잘못된다. AOF 디렉터리를 백업할 때 파일 한 개가 아니라 서로 일치하는 파일 집합을 생각해야 하는 이유다.

예시 파일명에 들어 있는 숫자나 접미사는 구현과 상태에 따라 다를 수 있으므로 이름을 고정해 스크립트를 작성하지 않는다. appenddirname, appendfilename, 실제 manifest를 확인한다. 특히 base가 RDB 형식이면 cat으로 열었을 때 읽을 수 있는 명령 문자열만 나오는 것이 정상은 아니다. “AOF인데 바이너리가 들어 있으니 손상됐다”라는 진단은 형식을 오해한 것이다.

복구는 개념적으로 다음과 같다.

manifest 읽기
 → 지정된 base 로드
 → 지정된 incremental 파일들을 순서대로 적용
 → 현재 데이터 상태 구성

여기서 한 incremental 파일을 임의로 빼면 이후 명령은 실행되더라도 업무적으로 올바른 상태가 아닐 수 있다. 카운터 증가, 리스트 조작, 키의 타입 변경은 이전 상태에 의존한다. “서버가 시작된다”와 “정확한 데이터로 복구되었다”는 다른 검증 단계다.

5. rewrite를 시간순으로 추적하기

현재 데이터는 1 GiB지만 같은 키를 수백 번 수정했다면 AOF 기록은 훨씬 커질 수 있다. 파일이 커지면 디스크 공간과 재시작 재생 시간이 늘어난다. rewrite는 오래된 명령 파일을 편집기로 압축하는 일이 아니라 메모리의 현재 상태를 기준으로 새로운 기반을 만드는 작업이다.

다중 파일 방식의 흐름을 단순화하면 다음과 같다.

  1. 재작성을 시작할 수 있는 상태인지 검사한다. 다른 백그라운드 작업 때문에 지연되거나 예약될 수 있다.
  2. 부모 프로세스는 이후 쓰기를 담을 새 incremental 파일을 사용한다.
  3. fork로 만들어진 자식은 기준 시점의 데이터를 읽어 새 base를 작성한다.
  4. 부모는 계속 클라이언트 요청을 처리하면서 기준 시점 이후의 변경을 기록한다.
  5. 새 base가 완성되면 새 base와 필요한 incremental 파일들을 가리키는 임시 manifest를 준비한다.
  6. manifest를 원자적으로 교체해 새 파일 세대를 유효하게 만든다.
  7. 더 이상 필요 없는 이전 세대 파일을 정리한다.

원자적 교체는 관찰자가 반쯤 수정된 목차를 보지 않도록 하는 핵심 장치다. rewrite 중간에 실패했다고 기존의 복원 가능한 기록을 먼저 버리지 않도록 설계되어 있다. 하지만 이것이 “디스크 공간을 0까지 써도 괜찮다”거나 “백업 중 파일을 아무렇게나 복사해도 된다”는 뜻은 아니다. 실패를 견디는 전환 규칙과 자원 부족을 예방하는 운영은 별개다.

Redis 7.0 이전 단일 파일 방식은 부모가 기존 AOF를 유지하면서 rewrite 중 변경을 메모리 버퍼에도 보관하고, 새 파일에 그 변경을 이어 붙이는 구조로 설명된다. 이 설명을 다중 파일 방식에 그대로 가져와 “항상 모든 rewrite 변경이 큰 별도 메모리 버퍼에 쌓인다”라고 단정하지 않는다. 다만 다중 파일 방식에서도 fork와 copy-on-write의 메모리 비용은 사라지지 않는다.

6. copy-on-write와 디스크 여유가 필요한 이유

fork 이후 부모와 자식은 처음에는 같은 물리 메모리 페이지를 공유할 수 있다. 부모가 어떤 페이지를 수정하면 자식이 보는 과거 상태를 보존하기 위해 페이지 복사가 일어난다. 이것이 copy-on-write, 줄여서 COW다. 키 하나를 바꾸더라도 OS가 복사하는 단위는 그 키의 문자열 길이가 아니라 메모리 페이지다. 따라서 “새 값이 10바이트니 추가 메모리도 10바이트”라는 계산은 틀릴 수 있다.

rewrite 시간이 길고 그동안 여러 페이지가 계속 바뀌면 추가 메모리 부담이 커진다. 동시에 디스크에는 이전 복구 경로를 유지한 채 새 base와 새 incremental을 생성해야 한다. 운영 용량은 평소 데이터 크기뿐 아니라 세대가 겹치는 시간의 최대 점유량을 포함해야 한다. 디스크가 느리면 rewrite가 오래 걸리고, 오래 걸리면 COW와 incremental이 더 커지는 악순환도 생긴다.

따라서 시작 전에는 RAM 여유, 컨테이너 한도, 디스크 여유, 쓰기 대역폭, 최근 rewrite 시간, 백그라운드 작업 상태를 함께 본다. 장애 중 급하게 반복 호출하는 것은 해결책이 아니다. 재작성은 파일을 줄일 가능성이 있지만 새 파일을 만들 공간이 없는 상태에서는 실패를 반복할 수 있다. 공간을 확보할 때도 AOF 파일을 임의 삭제하지 않고, 승인된 비관련 로그 정리나 볼륨 증설 등 복구 경로를 보존하는 방법을 고른다.

7. 격리 실습 A: 파일 구조와 rewrite 관찰

다음은 Redis 7.0 이상을 대상으로 한 일회용 로컬 실습이다. 운영 서버 주소를 대입하지 않는다. 포트 16385가 비어 있는지 확인하고, 충돌하면 전체 명령을 같은 빈 포트로 바꾼다. bash, redis-server, redis-cli가 필요하다. 실습값과 파일명은 예상 관찰 기준이며 이 글에서 실제 실행 결과를 주장하지 않는다.

LAB=$(mktemp -d /tmp/redis-aof-lab.XXXXXX)
printf '실습 경로: %s\n' "$LAB"
cat > "$LAB/redis.conf" <<CONF
bind 127.0.0.1
port 16385
protected-mode yes
daemonize no
dir $LAB
save ""
appendonly yes
appendfsync everysec
appenddirname appendonlydir
auto-aof-rewrite-percentage 0
CONF
redis-server --version
redis-server "$LAB/redis.conf"

서버를 띄운 터미널은 그대로 두고 두 번째 터미널에서 다음을 실행한다. 마지막까지 명시적 호스트와 포트를 유지한다.

redis-cli -h 127.0.0.1 -p 16385 SET lab:counter 0
for i in $(seq 1 2000); do
  redis-cli -h 127.0.0.1 -p 16385 INCR lab:counter >/dev/null
done
redis-cli -h 127.0.0.1 -p 16385 GET lab:counter
redis-cli -h 127.0.0.1 -p 16385 INFO persistence
redis-cli -h 127.0.0.1 -p 16385 BGREWRITEAOF
redis-cli -h 127.0.0.1 -p 16385 INFO persistence

반복문은 단순한 관찰용이며 성능 벤치마크가 아니다. 매번 별도 CLI 프로세스와 연결을 만들기 때문에 Redis 자체 처리량을 보여 주지 않는다. 기대하는 논리값은 2000이다. rewrite 뒤에도 값은 2000이어야 한다. 달라졌다면 파일 크기보다 먼저 명령 오류, 대상 인스턴스, 다른 쓰기 발생 여부를 조사한다.

INFO persistence에서는 aof_rewrite_in_progress, aof_rewrite_scheduled, aof_last_bgrewrite_status, aof_current_size, aof_base_size 등을 관찰한다. 제공되는 필드는 버전에 따라 달라질 수 있다. 작은 데이터는 rewrite가 매우 빨리 끝나 1인 순간을 놓칠 수 있다. 한 번 0을 봤다는 이유로 작업이 안 했다고 판단하지 말고 이전/이후 상태와 서버 로그를 함께 확인한다. 완료 여부를 시간 지연 1초 같은 임의 sleep만으로 단정하지 않는다.

첫 번째 터미널에서 기록한 LAB 경로를 두 번째 터미널에 정확히 넣고 파일 목록을 읽는다.

# 실제 출력된 임시 경로로 바꾼 뒤 실행한다.
LAB=/tmp/redis-aof-lab.실제접미사
find "$LAB/appendonlydir" -maxdepth 1 -type f -print
cat "$LAB/appendonlydir/appendonly.aof.manifest"

manifest를 읽는 것은 안전하지만 내용을 직접 편집하는 단계는 아니다. rewrite 전후의 세대와 파일 목록, 전체 파일 크기를 비교한다. 중간 쓰기를 거의 하지 않은 작은 카운터 실험에서는 기록이 줄어드는 경향을 기대할 수 있지만 정확한 바이트 수는 버전, 파일 형식, 메타데이터에 달려 있다. 예상 비율을 실제 측정값처럼 적지 않는다.

8. 격리 실습 B: 정상 재시작과 내구성 검증의 차이

앞선 실습에서 rewrite가 끝나고 상태가 정상인지 확인한 뒤 실습 서버만 정상 종료한다.

redis-cli -h 127.0.0.1 -p 16385 SHUTDOWN
# 원래 LAB 값이 있는 첫 번째 터미널에서
redis-server "$LAB/redis.conf"

다시 연결해 GET lab:counter와 INFO persistence를 확인한다. 2000이 복원되면 이 구성과 정상 종료·재시작 경로에서 값이 복원되었다는 증거다. 여기서 얻지 못한 증거도 적는다. 갑작스러운 전원 손실의 유실 범위, 디스크 고장 시 생존 여부, 모든 장애 시점에서의 복구 가능성은 이 실습으로 검증하지 않았다.

강제 종료를 무조건 추가하는 대신 먼저 장애 모델을 표로 만든다. 프로세스 크래시, OS 크래시, 볼륨 손실은 서로 다르다. 실제 장애 주입은 일회용 VM과 테스트 볼륨, 관찰용 클라이언트, 외부에 남기는 승인 기록을 준비한 뒤 실시한다. 응답 받은 순번과 복구된 마지막 순번을 비교해야 하며, 실험 부하와 fsync 정책도 함께 기록한다. 이 글에서는 호스트 종료나 디스크 손상 명령을 제공하지 않는다.

9. RDB만 쓰던 인스턴스에서 AOF를 켤 때

흔한 실수는 설정 파일에 appendonly yes를 추가하고 곧바로 재시작하는 것이다. 지금 메모리에 있는 데이터를 AOF의 복구 가능한 초기 상태로 만들어 놓지 않았다면, 다음 시작에서 기대와 다른 파일을 읽을 수 있다. 전환은 “설정 한 줄”이 아니라 현재 상태를 새 영속성 경로로 옮기는 작업이다.

안전한 계획은 다음 순서로 작성한다. 실제 운영 적용은 변경 승인과 버전별 문서를 따른다.

  1. 최신 정상 RDB를 확보하고 다른 장애 영역에 복사한다. 파일이 존재한다는 것뿐 아니라 복원 가능성을 확인한다.
  2. 현재 Redis 버전, dir, AOF 관련 설정, 디스크와 메모리 여유를 기록한다.
  3. 실행 중인 인스턴스에서 AOF 활성화를 수행해 현재 메모리 상태를 기반으로 초기 기록을 만들게 한다.
  4. 재작성 진행·예약 상태가 모두 끝났는지, 최근 재작성과 쓰기 상태가 정상인지 확인한다.
  5. 이후 새 쓰기가 AOF에 반영되는지 검사한다.
  6. 권위 있는 설정 원본에 같은 정책을 반영한다. CONFIG REWRITE를 쓰는 환경인지 배포 설정을 수정해야 하는 환경인지 구별한다.
  7. 검증된 복구 절차에 따라 재기동 시험을 진행하고 대표 데이터와 TTL, 자료형을 비교한다.

처음부터 RDB를 끄는 것이 필수는 아니다. 전환 안정성이 확인되기 전에 기존 복구 경로를 없애면 되돌아갈 선택지가 줄어든다. 정상 여부를 키 개수 하나로 판단하지 않는다. 값이 달라도 개수는 같을 수 있으므로 업무상 대표 키, 카운터, 자료형, 만료 상태까지 살펴본다.

10. 손상 복구: 원본 보존이 첫 번째 명령이다

AOF 문제는 크게 마지막 기록이 덜 쓰인 끝부분 절단과 중간에 잘못된 바이트가 있는 중간 손상으로 나눠 생각한다. 끝부분 절단은 마지막 불완전 기록을 제외하면 그 이전까지 일관된 기록이 남아 있을 수 있다. aof-load-truncated 정책은 이 상황에서 가용성과 엄격한 중단 중 어떤 쪽을 택할지에 영향을 준다. 중간 손상은 이후 기록이 무엇에 의존하는지까지 문제가 되므로 위험이 더 크다.

문제가 생겼을 때 원본에 곧바로 --fix를 실행하지 않는다. 다음 순서가 우선이다.

  • 자동 재시작을 포함해 파일을 계속 바꿀 주체를 통제한다.
  • 로그, 구성, manifest와 관련 AOF 파일 전체를 보존한다.
  • 원본을 읽기 전용으로 남기고 별도의 작업 복사본을 만든다.
  • 해당 Redis 버전에 맞는 redis-check-aof 사용법으로 먼저 수정 없이 검사한다.
  • 어떤 파일의 어떤 위치부터 손상인지, 대체 백업과 비교해 얼마나 잃을지 판단한다.
  • 복구 책임자의 승인 아래 복사본에 수정 작업을 하고, 격리 서버에서 복구 검증한다.

redis-check-aof --fix는 사라진 업무 정보를 추측해서 되살리는 마법이 아니다. 유효하지 않은 지점 뒤를 버리는 방식이라면 파일 앞부분의 손상 하나로 상당한 기록이 제거될 수 있다. 다중 파일 형식에서는 단일 .aof만 골라 고치는 오래된 절차를 그대로 적용하지 말고 manifest 및 버전별 도구 입력 형식을 확인한다. 바이너리 base를 일반 텍스트 편집기로 고치려는 행동도 피한다.

11. 운영 장애 시나리오와 지표 해석

디스크가 가득 찼다. aof_last_write_status, 서버 로그, 파일시스템 여유와 inode를 함께 확인한다. 단순히 AOF를 꺼서 쓰기를 재개하면 내구성 정책을 바꾸는 큰 결정이 된다. 복구 경로를 보존하면서 공간을 확보하고, 어떤 요청이 성공했는지 애플리케이션 기록과 맞춘다. 클라이언트가 시간 초과를 받았다고 쓰기가 반드시 실행되지 않은 것은 아니므로 재시도는 멱등성을 고려해야 한다.

rewrite가 계속 실패한다. 실패 원인은 디스크 공간, 권한, fork 실패, 메모리 압력, 저장장치 오류 등으로 나뉜다. 최근 상태 하나만 보고 반복 요청하지 않는다. 실패 후에도 AOF가 계속 증가할 수 있으므로 성장률과 남은 용량으로 대응 시간을 추정한다. 쓰기량이 초당 20 MiB이고 남은 공간이 10 GiB라면 단순 나눗셈은 약 512초지만, 새 base 생성과 다른 파일 증가를 고려하면 실제 안전 시간은 더 짧다. 이 숫자는 계산 예시이지 운영 예측값이 아니다.

평균 응답은 괜찮은데 가끔 수백 ms가 튄다. p99 지연, 디스크 동기화 지연, rewrite 실행 시각, fork 시간, COW 메모리, 호스트의 I/O 경합을 같은 시간축에 놓는다. 평균값만 보면 드문 동기화 지연이 숨겨질 수 있다. fsync 정책을 약하게 바꾸기 전에 내구성 요구와 저장장치 병목을 함께 검토한다.

애플리케이션에서 WAIT를 사용하므로 디스크는 안전하다고 믿는다. WAIT는 복제본의 확인을 기다리는 명령이지 일반적으로 로컬 AOF 동기화 완료와 같은 보장이 아니다. Redis 7.2에 도입된 WAITAOF는 해당 연결의 선행 쓰기에 대한 AOF 동기화를 기다리는 별도 기능이다. 지원 버전과 AOF 설정을 확인해야 하며, 반환값과 시간 초과를 해석해야 한다. 이것도 외부 DB와의 분산 트랜잭션이나 모든 failover 시나리오의 무손실을 자동으로 제공하지 않는다. WAITAOF 공식 명세

12. 애플리케이션의 책임: 응답을 못 받았을 때

AOF를 잘 구성해도 클라이언트의 시간 초과 문제는 남는다. 서버가 명령을 실행하고 기록한 뒤 응답이 네트워크에서 사라질 수 있다. 클라이언트는 성공을 보지 못했지만 서버에는 반영되었다. 이때 INCR를 무조건 다시 보내면 두 번 증가한다. 이를 “불확실한 결과”라고 부르면 좋다. 실패와 미실행은 같은 말이 아니다.

업무 작업에 요청 ID를 붙이고 이미 처리한 ID인지 검사하는 설계, 원본 DB의 유일 제약, 멱등한 상태 전이 등을 검토한다. Redis 안에서 여러 명령을 원자적으로 묶는 것과 외부 시스템까지 정확히 한 번 처리하는 것도 구별한다. AOF는 Redis 상태의 내구성 수단이지 결제 API와 데이터베이스 사이의 모든 불확실성을 해결하는 수단이 아니다.

면접 질문과 상세 답변

1. AOF를 켜면 SET의 OK 응답은 디스크 저장 완료를 뜻하나요?

fsync 정책을 보지 않고는 단정할 수 없다. 메모리 변경, 운영체제 페이지 캐시에 대한 write, 내구성 동기화는 서로 다른 단계다. everysec는 최근 동기화 이후의 쓰기가 응답되었어도 장애 시 사라질 수 있다. always는 동기화를 응답 경로에 반영하지만 저장장치 자체 손실이나 외부 시스템과의 일관성까지 해결하지 않는다. 좋은 답변은 “AOF 유무”보다 “어떤 장애 모델에서 어떤 경계까지 확인했는가”를 말한다.

2. everysec이면 정확히 1초 넘는 유실은 절대 없나요?

공식 설명의 약 1초 손실 창은 정상적인 동기화 주기를 이해하는 데 유용하지만, 모든 저장장치 정체와 커널 지연을 배제한 수학적 상한으로 사용해서는 안 된다. 실제 동기화 지연과 관련 설정, 장애 유형을 관찰해야 한다. RPO가 엄격하면 측정한 정상 상태만이 아니라 지연과 장애 주입을 포함한 검증이 필요하다. “대략적 운영 특성”과 “계약상 절대 보장”을 분리하는 것이 핵심이다.

3. AOF rewrite는 기존 로그를 처음부터 읽어 압축하나요?

기본 개념은 현재 메모리 데이터셋을 기준으로 새로운 복원 표현을 만드는 것이다. 따라서 같은 카운터를 수없이 증가시킨 과거를 모두 유지할 필요가 없다. 현재 값과 필요한 자료구조 상태를 저장하면 된다. 이 때문에 rewrite는 감사 이력 보존과 양립하지 않을 수 있고, 오래된 개별 작업을 조사하려면 별도의 로그가 필요하다. 새 base는 설정에 따라 RDB 형식일 수도 있으므로 항상 텍스트 명령 묶음이라고 생각하지 않는다.

4. 다중 파일 AOF에서 manifest가 중요한 이유는 무엇인가요?

manifest는 복원에 사용해야 할 base와 incremental 파일의 조합과 순서를 연결한다. 파일 몇 개가 존재한다는 사실만으로 같은 세대의 완전한 복구 집합이라고 볼 수 없다. rewrite 중에 파일을 서로 다른 시점에 복사하면 manifest가 참조하는 파일이 누락될 수 있다. 백업과 복구는 개별 파일이 아니라 일관된 집합 단위로 다루며, 복사 뒤 실제 로드 시험까지 해야 한다.

5. rewrite는 백그라운드인데 왜 서비스 지연과 메모리 사용이 늘 수 있나요?

백그라운드는 비용이 없다는 뜻이 아니다. fork 자체의 준비 비용, 페이지 테이블 관련 비용, 부모 쓰기에 따른 COW, 새 base를 쓰는 디스크 I/O가 발생한다. 자식과 부모는 CPU·메모리 대역폭·저장장치를 공유한다. 데이터가 크거나 쓰기가 많고 디스크가 느리면 작업이 길어져 추가 부담이 늘 수 있다. 그래서 p99 지연과 자원 여유를 재작성 시간축에 맞춰 관찰한다.

6. AOF 손상 때 redis-check-aof --fix부터 실행하면 안 되나요?

수정은 되돌릴 수 없는 기록 제거를 포함할 수 있으므로 원본 보존과 무수정 검사가 먼저다. 특히 중간 손상에서는 그 뒤의 유효해 보이는 기록도 버려질 수 있어 유실 범위가 커진다. 버전에 맞는 도구와 다중 파일 입력 형식을 확인하고, 복사본에서 복구한 뒤 대표 데이터와 업무 불변식을 검증해야 한다. 복구 도구의 성공은 업무 데이터의 완전성을 증명하지 않는다.

7. RDB에서 AOF로 바꿀 때 설정만 고치고 재시작해도 되나요?

현재 메모리 상태를 AOF의 초기 복구 경로로 만들어 두는 절차가 필요하다. 먼저 정상 백업을 보존하고 실행 중인 서버에서 AOF를 활성화한 뒤 초기 재작성 완료와 쓰기 상태를 확인한다. 그 다음 원본 설정을 영속화하고 안전하게 재기동을 검증한다. 기존 파일 구조와 시작 시 로드 우선순위를 모른 채 설정만 바꾸는 것은 데이터 손실 위험이 있다.

8. WAIT와 WAITAOF는 어떻게 다른가요?

WAIT는 해당 연결의 선행 쓰기에 대해 복제본의 처리 확인을 기다리는 기능이다. WAITAOF는 지원되는 버전에서 AOF 동기화 확인을 기다리는 별도 명령이다. 둘 다 반환된 확인 수와 시간 초과를 해석해야 하고, 같은 연결의 선행 쓰기라는 범위가 중요하다. 커넥션 풀에서 무관한 연결로 호출하면 기대한 쓰기를 기다리는 설계가 아닐 수 있다. 어느 쪽도 Redis와 외부 데이터베이스를 하나의 원자적 트랜잭션으로 만들지 않는다.

9. AOF 파일이 줄었으니 백업도 필요 없나요?

아니다. rewrite는 현재 상태를 효율적으로 복원하게 하는 작업이며 과거 정상 시점 보존이 아니다. 잘못된 삭제나 덮어쓰기도 현재 상태가 되어 재작성에 반영될 수 있다. 같은 디스크의 AOF는 디스크 손실에 취약하다. 별도 장애 영역에 보관한 여러 시점의 백업과 복원 훈련이 필요하다. 다음 장에서 이 차이를 복구 시간과 복구 시점 목표로 확장한다.

정리와 공식 자료

AOF의 핵심은 “로그를 쓴다”가 아니라 어느 경계까지 기록했는지, 어느 파일 집합이 현재 복구 경로인지, 실패했을 때 무엇을 보존해야 하는지다. 정책·파일 구조·운영 절차를 함께 이해해야 내구성을 설명할 수 있다.

  • Redis persistence: fsync, 다중 파일 구조, 재작성, 전환 및 복구 절차.
  • BGREWRITEAOF: 백그라운드 재작성 명령과 상태 해석.
  • INFO: 실행 버전의 persistence 필드 확인.
  • WAITAOF, WAIT: 내구성 확인과 복제 확인의 범위.
