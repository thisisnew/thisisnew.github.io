암호화와 복구: 데이터·로그·키를 끝까지 보호하기

읽는 방법

비유로 개념을 잡고 SQL을 실행하기 전 결과를 예상해 보세요. 이번 개정에서는 단계별 동작 추적에 더해, 전편에 네 가지 확장 수업과 심층 면접 답변을 추가했습니다. 본문의 수치 예시는 설명용이고, 실행 환경에 따라 달라지는 값은 따로 표시했습니다. 기준은 MySQL 8.0·InnoDB, 재현용 서버는 8.0.36입니다. 처음 시작한다면 1편의 서버 준비만 먼저 진행하면 됩니다.

전체 학습 지도·검증 범위

1. 암호화는 ‘누가 무엇을 훔쳤을 때’를 먼저 정해야 한다

창고 장부를 금고에 넣어도 출입 권한을 가진 직원은 장부를 읽을 수 있습니다. 디스크 암호화도 비슷합니다. 저장 파일이 유출되는 상황을 막는 데 도움이 되지만, 정상 SQL 권한을 가진 사용자의 조회를 막는 기능은 아닙니다. 위협을 구분하지 않으면 암호화를 켰다는 사실만으로 개인정보 보호가 끝났다고 착각하게 됩니다.

위협주요 대응한계
네트워크에서 내용 도청TLS와 인증서 검증정상 계정의 잘못된 조회 권한은 해결하지 못함
디스크 파일 유출Data-at-rest encryption키도 함께 유출되면 보호가 약해짐
앱 계정으로 과도한 조회최소 권한·접근 통제·감사저장 암호화만으로는 차단되지 않음
DB 운영자도 일부 원문을 몰라야 함애플리케이션 계층 암호화 등 별도 설계검색·정렬·키 관리가 어려워질 수 있음

2. 모든 데이터를 한 비밀번호로 직접 잠그지 않는 이유

InnoDB 저장 암호화는 마스터 키와 테이블스페이스 키의 두 계층을 사용합니다. 데이터는 테이블스페이스 키로 보호하고, 그 키를 마스터 키로 암호화해 관리합니다. 수많은 문을 같은 열쇠로 직접 여는 대신 각 방 열쇠를 보관하는 열쇠함을 별도 열쇠로 잠그는 구조입니다.

마스터 키를 회전할 때 모든 데이터 페이지를 처음부터 같은 방식으로 재암호화하는 것과는 비용 구조가 다릅니다. 데이터 키를 감싸는 보호를 바꾸는 작업과 실제 데이터 키를 바꾸는 작업을 구분해야 합니다. 키를 분리하면 회전과 관리가 유연해지지만, 그 키를 보존·복구하는 책임도 생깁니다.

3. Keyring은 부가 파일이 아니라 복구에 필요한 핵심 자산이다

Keyring은 서버가 암호화 키를 저장하고 조회하는 체계입니다. 사용할 수 있는 컴포넌트·플러그인은 MySQL 세부 버전과 에디션, 배포 형태에 따라 다릅니다. ‘플러그인 파일 하나를 복사하면 된다’는 식으로 모든 환경에 같은 설치 명령을 제공하면 위험합니다. 여기서는 기능 확인과 이미 준비된 keyring을 사용하는 실습을 구분합니다.

암호화된 데이터 파일만 백업하고 필요한 키를 잃으면 정상적인 복원이 불가능할 수 있습니다. 백업 대상에는 데이터·로그·설정·키의 복구 절차가 함께 들어가야 합니다. 데이터와 키를 같은 공개 폴더에 두면 분리의 이점이 줄어듭니다. 접근 권한과 키 회전 이력도 관리해야 합니다.

4. 실습 A: 설정을 바꾸지 않고 보호 범위를 확인하기

1편의 로컬 서버에서 실행합니다. 이 단계는 암호화 기능을 새로 설치하지 않는 읽기 전용 점검입니다. 결과가 비어 있거나 OFF여도 기본 학습 서버에서는 정상일 수 있습니다.

SELECT VERSION();
SHOW VARIABLES LIKE 'require_secure_transport';
SHOW SESSION STATUS LIKE 'Ssl_cipher';
SHOW VARIABLES LIKE 'innodb_redo_log_encrypt';
SHOW VARIABLES LIKE 'innodb_undo_log_encrypt';
SHOW VARIABLES LIKE 'binlog_encryption';
SELECT PLUGIN_NAME,PLUGIN_STATUS FROM information_schema.PLUGINS
WHERE PLUGIN_NAME LIKE 'keyring%';
SELECT * FROM mysql.component;

컴포넌트와 플러그인은 다른 설치 체계입니다. 플러그인 목록이 비었다고 keyring이 반드시 없다고 단정하지 않습니다. 반대로 목록에 이름이 있어도 실제 사용할 수 있는 키 저장소와 시작 시 로딩이 정상인지 확인해야 합니다. 현재 세션의 Ssl_cipher가 비어 있다면 그 연결이 TLS를 쓰지 않을 수 있습니다. docker exec로 소켓 접속한 학습 환경과 원격 TCP 연결을 구분하세요.

5. 실습 B: keyring이 준비된 별도 환경에서만 실행

전제: 해당 버전에 맞는 keyring을 설정하고, 재시작 시 로딩과 키 백업·복원 경로까지 확인한 로컬 실습 서버여야 합니다. 기본 1편 서버에서 바로 성공한다고 가정하지 않습니다. 준비되지 않은 경우 이 절은 읽기 실습으로 남겨 두세요.

CREATE DATABASE IF NOT EXISTS mysql_school;
USE mysql_school;
CREATE TABLE encrypted_demo (
 id INT PRIMARY KEY, note VARCHAR(100) NOT NULL
) ENGINE=InnoDB ENCRYPTION='Y';
INSERT INTO encrypted_demo VALUES(1,'보호할 학습 데이터');
SHOW CREATE TABLE encrypted_demo;
SELECT NAME,ENCRYPTION
FROM information_schema.INNODB_TABLESPACES
WHERE NAME='mysql_school/encrypted_demo';
SELECT * FROM encrypted_demo;

정상 권한으로 SELECT하면 평문이 나옵니다. 이것은 암호화 실패가 아니라 서버가 읽기 경로에서 복호화하기 때문입니다. ENCRYPTION='Y'는 테이블스페이스 보호를 뜻하며 모든 로그·백업·네트워크까지 한 번에 암호화한다는 뜻은 아닙니다. redo, undo, binlog의 보호 정책도 따로 확인합니다.

마스터 키 회전 명령은 ALTER INSTANCE ROTATE INNODB MASTER KEY입니다. 이 글에서는 실행 필수 실습으로 두지 않습니다. 키 회전 후 재시작과 복원까지 확인할 수 있는 격리 환경에서만 실험하세요. 명령이 성공했다는 메시지와 복구 가능성은 다른 증거입니다.

6. 백업은 파일이 아니라 복원 가능한 절차다

논리 백업은 CREATE TABLE·INSERT 같은 형태로 데이터와 구조를 재현합니다. 물리 백업은 저장 파일 구조를 다룹니다. 둘 다 장단점이 있고 활성 DB 파일을 아무렇게나 복사하는 것은 일관된 백업이 아닙니다. 여기서는 작은 InnoDB 학습 테이블을 논리적으로 저장하고 다시 읽는 실습을 합니다.

-- 먼저 mysql 클라이언트에서 준비
CREATE DATABASE IF NOT EXISTS mysql_school;
CREATE TABLE IF NOT EXISTS mysql_school.backup_demo (
 id INT PRIMARY KEY, note VARCHAR(100) NOT NULL
) ENGINE=InnoDB;
INSERT INTO mysql_school.backup_demo VALUES(1,'restore-test')
 ON DUPLICATE KEY UPDATE note='restore-test';
CREATE DATABASE IF NOT EXISTS mysql_school_restore;

컨테이너의 대화형 셸에서 덤프를 파일로 만든 뒤 mysql 클라이언트의 SOURCE로 읽습니다. 이렇게 하면 비밀번호 입력과 SQL 파일 입력을 분리할 수 있습니다.

docker exec -it mysql-school sh
# 이제 컨테이너 안입니다.
mysqldump -uroot -p --single-transaction --no-tablespaces \
  --set-gtid-purged=OFF mysql_school backup_demo > /tmp/backup-demo.sql
mysql -uroot -p mysql_school_restore
# mysql 프롬프트에서:
SOURCE /tmp/backup-demo.sql;
SELECT * FROM backup_demo;
# id=1, note=restore-test 확인 후 exit

--single-transaction은 InnoDB의 일관된 읽기를 활용합니다. 비트랜잭션 테이블이나 백업 중 DDL까지 무조건 안전하게 만들어 주지 않습니다. 또한 이 실습은 테이블 하나의 복원입니다. 계정·역할·루틴·이벤트·GTID·전체 인스턴스 복구를 모두 검증한 것이 아닙니다. 저장 암호화된 테이블을 논리 dump하면 내용이 평문일 수 있어 백업 파일 자체의 보호가 필요합니다.

7. 장애 시나리오: 데이터 파일은 있는데 키가 없다

가상의 복구 훈련에서 새 서버에 암호화된 데이터를 가져왔지만 키 저장소가 누락되었습니다. 파일은 존재하므로 디스크 장애가 아니지만 데이터를 읽을 수 없습니다. 해결 방향은 암호화를 끄는 것이 아니라 올바른 키와 로딩 구성, 권한, 버전 호환성을 복구하는 것입니다. 읽을 수 없는 데이터를 설정 하나로 평문으로 바꾸는 우회는 없습니다.

복구 훈련에서는 ‘기동 성공’ 다음에 업무 불변식도 확인합니다. 재고가 음수가 아닌지, 주문과 이력이 연결되는지, 기준 시점 이후 이벤트를 어디까지 적용했는지 점검합니다. 목표 복구 시간(RTO)과 허용 데이터 손실 범위(RPO)를 측정해야 실제 운영 계획이 됩니다.

8. 전체 시리즈를 하나의 요청으로 연결하기

이제 출고 API 한 건을 따라가 보세요. 계정이 인증되고 권한을 통과합니다. 옵티마이저가 인덱스 경로를 고릅니다. 버퍼 풀에서 페이지를 찾고, 트랜잭션과 잠금으로 경쟁을 제어합니다. 변경에는 undo·redo가 연관되고 커밋 정책에 따라 확정됩니다. 페이지는 나중에 압축·암호화 등 저장 정책에 맞춰 기록됩니다. 느리면 실행 계획·잠금·I/O 중 어느 구간인지 찾고, 장애가 나면 로그·백업·키를 사용해 복구합니다.

이 연결이 이해되면 설정 이름을 외우는 대신 “어느 단계의 어떤 비용과 보장을 바꾸는가”를 질문할 수 있습니다. 실무 판단의 출발점은 기능 수가 아니라 데이터가 지나가는 경로를 설명할 수 있는 능력입니다.

보호할 데이터가 지나가는 길을 하나씩 표시하기

개인정보가 앱에서 DB로 가고, DB 파일에 저장되고, 로그에 남고, 백업으로 복사되는 과정을 생각해 봅시다. 한 지점만 암호화해도 다른 지점이 평문일 수 있습니다. 창고 문을 잠갔지만 배송 중 상자나 사무실 복사본은 그대로 노출된 상황과 같습니다.

위치보호 수단별도로 확인할 것
앱과 DB 사이TLS·인증서 검증실제 연결의 TLS 사용과 호스트 검증
테이블스페이스 파일InnoDB 저장 암호화키 로딩·접근 정책
redo·undo·binlog각 로그의 암호화 옵션버전·지원 조건·기존 로그 처리
논리 dump백업 파일 자체 암호화·접근 제어평문 임시 파일과 전송 경로
애플리케이션 로그민감 값 최소 기록·마스킹SQL 파라미터·오류 메시지

저장 암호화는 서버가 정상 조회 시 복호화하므로 권한 있는 SELECT 결과는 평문입니다. 공격자가 앱의 SQL 권한을 탈취한 상황까지 파일 암호화 하나로 막을 수 없습니다. 어떤 공격을 막으려는지 정해야 필요한 통제가 보입니다.

봉투 암호화: 데이터 키와 마스터 키를 두는 이유

각 테이블스페이스에 데이터를 보호하는 키가 있고, 이 키를 마스터 키로 감싸 관리한다고 생각해 보세요. 많은 문서에 쓰는 방 열쇠를 각각 만들고, 열쇠들을 별도 금고에 넣는 구조입니다. 마스터 키를 회전하면 데이터 키를 감싸는 보호를 바꿀 수 있어 모든 데이터 페이지를 같은 방식으로 새로 암호화하는 것과 비용이 다릅니다.

하지만 마스터 키 회전이 모든 위험을 지우는 것은 아닙니다. 예전에 유출된 평문이나 이미 유출된 데이터·키 조합이 마법처럼 사라지지 않습니다. 회전은 앞으로의 키 사용을 관리하고 노출 범위를 줄이는 절차의 일부입니다. 어떤 키가 어떤 백업에 필요한지 이력을 남기는 것이 중요합니다.

현재 DB가 열리는 것과 오래된 백업이 열리는 것은 별개다

월요일에 백업을 만들고 화요일에 키를 회전했다고 합시다. 수요일 서버가 정상이라고 월요일 백업의 복원까지 검증된 것은 아닙니다. 백업 당시의 키와 메타데이터, 사용하는 백업 도구의 키 처리 방식이 필요할 수 있습니다. 필요한 과거 키를 정책 없이 지우면 보관 중인 백업이 쓸모없어질 수 있습니다.

키 보관 정책은 데이터 보관 정책과 연결됩니다. 1년 전 백업을 복원해야 한다면 그 백업에 필요한 키를 어떻게 복구할지 정해야 합니다. 동시에 키를 데이터와 같은 공개 위치에 보관하면 파일 유출 보호의 의미가 약해집니다. 접근 주체, 키 저장소 백업, 복원 권한, 감사 기록을 나누어 설계합니다.

기동 시 keyring이 준비되기 전에 암호화된 데이터를 읽으려 하면 실패할 수 있습니다. 그래서 플러그인·컴포넌트 이름을 확인하는 것뿐 아니라 재시작 후 실제 암호화 테이블을 읽는 검증이 필요합니다. 설치 방식은 MySQL 버전·배포판·에디션별로 달라 하나의 명령을 모든 서버에 복사하지 않습니다.

백업·복제·redo가 서로 대체되지 않는 이유

수단잘 해결하는 문제단독으로 해결하지 못하는 문제
Redo로컬 엔진의 crash recovery디스크 전체 손실·과거 시점 임의 복원
복제본장애 전환·읽기 분산의 기반잘못된 DELETE가 복제되는 상황
기준 백업백업 시점 데이터 재구성그 이후 변경까지 자동 복구
Binlog기준 백업 이후 변경 적용기준 데이터 없이 모든 과거 재구성 보장

운영자가 10시에 잘못된 DELETE를 실행했다면 복제본도 그 변경을 받을 수 있습니다. 복제본이 있다는 사실만으로 논리 오류를 되돌릴 수는 없습니다. 기준 백업과 필요한 로그를 보존하고 잘못된 작업 직전까지 적용하는 시점 복구 절차가 있어야 합니다.

시점 복구를 시간표로 이해하기

가상의 사고입니다. 02:00 기준 백업이 있고, binlog가 빠짐없이 보존되어 있으며, 10:03에 잘못된 삭제가 일어났습니다. 목표는 백업을 별도 서버에 복원하고 백업 이후부터 잘못된 트랜잭션 직전까지 정상 변경을 적용하는 것입니다. “10시 3분까지만”이라는 시각만으로 경계를 무심코 정하면 같은 시각의 여러 정상 트랜잭션을 놓칠 수 있습니다.

  1. 원본을 보존하고 잘못된 변경의 트랜잭션·로그 위치 또는 GTID를 식별합니다.
  2. 기준 백업이 어느 로그 위치·GTID와 일치하는지 확인합니다.
  3. 격리된 새 환경에 백업과 필요한 키·설정을 복구합니다.
  4. 필요한 로그 범위를 순서대로 적용하되 사고 트랜잭션을 포함하지 않도록 경계를 검증합니다.
  5. 행 수뿐 아니라 주문·재고·이력의 관계와 앱 기능을 확인합니다.
  6. 복원본을 서비스에 반영하는 방법과 사고 이후 정상 변경의 처리 방식을 결정합니다.

실제 명령은 GTID 사용, 백업 도구, 로그 암호화, 버전에 따라 달라집니다. 위 절차는 복구 계획을 이해하는 설명이며 이 글의 작은 논리 백업 실습이 전체 PITR을 검증한다는 뜻은 아닙니다. 복원 과정에서 원본을 덮어쓰지 않는 격리 환경이 중요한 이유입니다.

RPO와 RTO를 숫자로 말하기

RPO는 허용할 수 있는 데이터 손실의 시간 범위, RTO는 서비스를 복구하는 목표 시간입니다. 예를 들어 RPO 5분, RTO 1시간이라면 장애 직전 최대 5분 수준의 손실을 목표 범위로 두고 1시간 안에 복구해야 한다는 요구입니다. 구체적인 계약에서는 측정 시작·종료 시점과 손실 정의를 명확히 해야 합니다.

하루 한 번 백업만 있고 이후 변경 로그를 복구할 수 없다면 5분 RPO 요구를 충족하기 어렵습니다. 백업 다운로드에 40분, 복원에 50분, 검증에 20분이 걸리면 최소 110분이어서 1시간 RTO를 넘습니다. 이 숫자는 예시이며 실제 환경에서 시간을 측정해야 합니다. 파일 생성 성공 여부만으로 복구 준비도를 판단하지 않는 이유입니다.

복원 성공 판정을 업무 불변식까지 확장하기

서버가 켜지고 SELECT가 된다는 것은 시작입니다. 주문은 존재하는데 품목이 없거나 재고 차감과 출고 이력이 어긋날 수 있습니다. 중요한 행 수, 금액·수량 합계, 참조 관계, 중복 요청 ID, 복구 기준 이후 이벤트의 적용 여부를 확인해야 합니다. 행 수가 같아도 값이 다를 수 있어 중요한 키 범위의 비교도 필요합니다.

검증하는 쪽의 계정·TLS·키 접근도 실제 서비스와 맞아야 합니다. root로 복원본을 읽을 수 있어도 서비스 계정 역할이 누락되면 앱은 실패합니다. 데이터만의 복원과 실제 업무 재개는 다른 단계입니다. 2편의 권한과 1편의 연결 진단이 마지막 복구 단계에서 다시 필요해집니다.

이제 전체 요청을 설명해 보세요. 계정이 연결하고 SQL을 계획하며 인덱스와 버퍼 풀로 행을 찾습니다. MVCC와 잠금이 동시성을 제어하고 redo·undo가 변경과 복구를 지원합니다. 압축·암호화는 저장의 비용과 보호 방식을 바꾸며 백업·로그·키는 장애 이후 업무를 되살리는 재료가 됩니다. 각각을 따로 암기하는 대신 이 경로에서 어떤 일을 맡는지 말할 수 있어야 합니다.

확장 수업 ① — 무엇을 훔쳤을 때 무엇이 보이지 않아야 할까?

암호화 설계는 “암호화 ON”이라는 상태보다 보호하려는 경계를 먼저 정해야 합니다. 네트워크 패킷을 엿보는 사람, 디스크 파일을 복사한 사람, DB SELECT 권한을 가진 사람은 서로 다른 위치에 있습니다. 같은 기술이 세 경우를 전부 해결하지 않습니다.

상황관련 보호남는 문제
통신 구간을 관찰TLS와 서버 신원 검증클라이언트·서버 안에서의 평문 처리
저장 파일을 유출저장 데이터 암호화와 키 분리키까지 함께 유출되면 보호 약화
정상 계정으로 SELECT권한·업무 접근 통제투명한 저장 암호화는 조회를 차단하지 않음
덤프 파일을 유출백업 파일 자체의 암호화와 접근 통제원본 테이블 암호화가 자동으로 따라오지 않음

InnoDB의 저장 암호화는 애플리케이션이 정상적으로 조회하면 데이터를 사용할 수 있도록 투명하게 동작합니다. 따라서 암호화한 테이블에서 SELECT가 평문을 반환한다고 암호화가 실패한 것은 아닙니다. SQL 결과, 애플리케이션 로그, CSV 다운로드, 백업의 보호는 각각 따로 확인해야 합니다.

확장 수업 ② — 큰 창고 열쇠와 열쇠 보관함의 열쇠

테이블스페이스 데이터를 암호화하는 키와 그 키를 보호하는 마스터 키를 구분합니다. 창고마다 열쇠가 있고 열쇠를 보관하는 금고의 잠금장치가 별도로 있다고 생각하면 쉽습니다. InnoDB는 암호화된 테이블스페이스 키를 헤더에 보관하고, keyring에서 관리하는 마스터 키를 사용해 필요한 키를 해석합니다.

마스터 키 회전은 큰 데이터 파일의 모든 내용을 새로 암호화하는 작업과 다릅니다. 테이블스페이스 키를 새 마스터 키로 다시 보호하는 과정이 핵심입니다. 따라서 데이터 용량 전체를 읽고 다시 쓰는 작업으로 단순 환산하지 않습니다. 반대로 테이블 자체의 암호화 속성을 변경하는 작업과도 동일하지 않습니다.

이 구조는 키 회전을 효율적으로 만들지만 복구 의존성을 추가합니다. 파일이 온전해도 필요한 키를 얻지 못하면 읽을 수 없습니다. keyring 파일이나 서비스의 설정, 접근 자격, 사용한 컴포넌트와 버전, 백업 시점의 키를 복구 절차에 포함해야 합니다. 키 보관소가 “있다”는 사실보다 복구 대상이 실제로 접근하고 필요한 키를 가져올 수 있는지가 중요합니다.

확장 수업 ③ — 백업 성공과 복구 성공 사이의 거리

RPO는 허용할 수 있는 데이터 손실 구간, RTO는 복구까지 허용할 수 있는 시간 목표입니다. 매일 자정 백업만 있고 오후 3시에 장애가 나면 자정 이후 변경을 되살릴 추가 수단이 없는 경우 최대 약 15시간의 데이터가 대상이 됩니다. binlog를 적절히 보관해 백업 이후 변경을 재적용할 수 있다면 손실 구간을 줄일 수 있지만, 로그의 연속성·위치·키와 복구 절차가 맞아야 합니다.

백업 파일을 5분 만에 내려받았다고 RTO가 5분인 것은 아닙니다. 서버 준비, 데이터 적재, 로그 적용, 키 접근 복구, 무결성 검사, 애플리케이션 연결 전환까지 시간이 걸립니다. 용량이 늘면서 복원 시간이 어떻게 바뀌는지도 실제로 측정해야 합니다.

잘못된 DELETE가 오후 2시 10분에 커밋되었다면 “최신까지 복구”하면 그 삭제도 다시 적용될 수 있습니다. 어느 시점에서 멈춰야 하는지, 정상 변경을 얼마나 보존할지 결정해야 합니다. 삭제된 테이블만 별도 환경에 복구해 필요한 데이터를 가져오는 방식 등도 고려할 수 있습니다. 복구는 파일 복사뿐 아니라 어떤 업무 상태를 목표로 하는지 정하는 일입니다.

확장 수업 ④ — 복구 리허설에서 실제로 확인할 순서

  1. 대상 고정: 백업 시각, 서버 버전, 방식, 포함 스키마·객체와 목표 시점을 기록합니다. 논리 덤프와 물리 백업은 절차가 다릅니다.
  2. 독립 환경 준비: 원본과 분리된 서버에서 필요한 키와 설정을 준비합니다. 실수로 운영 시스템이 복구 서버에 쓰지 않도록 연결을 분리합니다.
  3. 복원과 재적용: 선택한 도구의 절차대로 복원하고 필요한 로그만 적용합니다. 도구가 성공 종료했는지도 기록합니다.
  4. 데이터 검사: 행 수, 핵심 업무 합계, 제약, 대표 레코드를 비교합니다. 행 수가 같은 것만으로 내용 일치를 선언하지 않습니다.
  5. 서비스 검사: 애플리케이션 계정으로 실제 조회와 허용된 쓰기를 확인하고 재시작 후에도 정상인지 봅니다.
  6. 시간·실패 기록: 전체 경과 시간과 수작업 단계를 남기고 키 누락·권한 부족 등 실패를 복구 문서에 반영합니다.

앞의 mysqldump 실습은 작은 비암호화 테이블의 논리 백업·복원 경로를 확인합니다. 암호화된 물리 백업의 복구나 실제 전원 장애 내구성을 증명하지 않습니다. --single-transaction 역시 모든 엔진과 DDL 상황을 무조건 일관되게 만드는 옵션이 아닙니다. InnoDB의 일관된 읽기를 활용하는 동안 스키마 변경 등 전제를 관리해야 합니다.

학습을 마치면 1편의 “서버에 연결한다”부터 이 편의 “키와 데이터를 복구해 다시 연결한다”까지 한 경로로 설명할 수 있어야 합니다. 페이지·로그·트랜잭션·인덱스·권한은 별도 암기 항목이 아니라, 데이터를 정확하게 저장하고 필요한 시간 안에 다시 사용할 수 있게 만드는 서로 연결된 장치입니다.

9. 상세 면접 Q&A

저장 암호화하면 SELECT 권한이 있는 사람도 못 읽나요?

아닙니다. 서버는 정상 읽기 과정에서 복호화해 결과를 반환합니다. 저장 파일 유출 보호와 SQL 권한 통제는 별개입니다. DB 운영자까지 원문 접근을 제한하려면 애플리케이션 계층 등 다른 암호화 경계를 검토해야 합니다.

키를 잃으면 데이터 파일로 복원할 수 있나요?

필요한 키 없이는 정상 복호화가 불가능할 수 있습니다. 그래서 키 관리와 복구는 백업 설계의 일부입니다. 데이터 파일 존재 여부만 확인하는 백업 점검은 부족하며 격리된 새 환경에서 실제 복원을 수행해야 합니다.

마스터 키 회전은 데이터 전체 재암호화인가요?

마스터 키가 테이블스페이스 키를 보호하는 두 계층 구조에서는 데이터 키를 감싸는 보호를 바꾸는 것과 모든 데이터 페이지를 새 데이터 키로 암호화하는 것이 다릅니다. 명령의 대상과 키 계층을 구분해서 설명해야 합니다.

ENCRYPTION='Y'면 binlog도 암호화되나요?

테이블스페이스 설정만으로 모든 로그의 보호를 가정하면 안 됩니다. binlog·redo·undo는 각 정책과 지원 조건을 따로 확인합니다. 논리 백업 파일과 네트워크 전송도 별도 보호 대상입니다.

--single-transaction이면 모든 백업이 무조건 일관적인가요?

주로 트랜잭션 테이블의 스냅샷에 의존합니다. 비트랜잭션 테이블과 백업 중 DDL에는 별도 주의가 필요합니다. 계정·루틴·복제 위치 등 포함 범위도 확인해야 합니다. 옵션 하나로 전체 시스템 복구가 완성되지 않습니다.

복구가 성공했는지 무엇을 확인하나요?

서버 기동과 테이블 조회뿐 아니라 행 수·중요 집계·업무 관계·키 접근·복구 시점·애플리케이션 동작을 확인합니다. 실제 소요 시간과 로그 적용 범위를 기록해 RTO와 RPO 요구를 만족하는지 평가합니다.

꼬리 질문: 마스터 키를 회전했으니 이전 키를 바로 지워도 되나요?

답변: 현재 서버만 보고 결정하면 안 됩니다. 보관 중인 백업과 로그, 백업 도구의 키 관리 방식에서 과거 키가 필요한지 확인해야 합니다.

검증: 보존 기간의 대표 백업을 격리 환경에서 복원하고 필요한 키 집합을 기록합니다. 키 폐기와 백업 폐기를 독립적으로 운영하면 복원 불능이 생길 수 있습니다.

꼬리 질문: 복제본이 있으니 백업을 줄여도 되나요?

답변: 복제는 정상 변경뿐 아니라 실수로 한 변경도 전달할 수 있습니다. 장애 전환 수단과 과거 복구 수단은 구분해야 합니다.

사례: 잘못된 DELETE가 복제되면 원본과 복제본에 모두 반영될 수 있습니다. 별도 보존 백업과 로그, 실제 복구 훈련이 필요합니다.

꼬리 질문: 암호화된 테이블을 mysqldump하면 파일도 암호화되나요?

답변: 저장 암호화가 논리 dump의 내용을 자동으로 보호한다고 가정하면 안 됩니다. 정상 SQL로 읽은 값이 평문으로 출력될 수 있습니다.

대응: dump 저장·임시 파일·전송·보관의 암호화와 접근 권한을 따로 설계합니다. 암호화 옵션이 덤프 DDL에 남더라도 INSERT 값 자체의 기밀성이 보장되는 것은 아닙니다.

꼬리 질문: 백업 복원 실습 한 번으로 운영 복구를 검증했나요?

답변: 작은 테이블의 논리 복원은 그 범위의 증거입니다. 전체 인스턴스, 암호화 키, 로그 적용, 권한, 앱 연동과 복구 목표까지 검증한 것은 아닙니다.

확장: 실제 복구 단위에 맞춰 데이터 규모와 버전·키·계정·로그를 포함한 훈련을 수행하고 소요 시간과 미검증 항목을 남깁니다. 성공의 범위를 정확히 말하는 것이 신뢰할 수 있는 운영입니다.

심층 면접: 암호화된 DB 파일만 백업하면 재해 복구가 가능한가요?

답변: 필요한 키와 키 접근 환경이 없으면 불가능할 수 있습니다. 데이터뿐 아니라 백업 시점에 필요한 키, keyring 구성, 권한과 도구의 복원 절차를 함께 확보해야 합니다.

구분: 논리 덤프는 서버가 읽은 데이터를 SQL 형태로 내보내므로 원본의 저장 암호화가 덤프 파일에 그대로 적용되는 것이 아닙니다. 물리 백업과 키 의존성을 동일하게 취급하지 않습니다.

검증: 원본 서버 없이 독립 환경에서 복원하고 실제 데이터를 읽어 보겠습니다. 키 회전 후에도 보관 중인 과거 백업을 복원할 수 있는지 확인해야 합니다.

심층 면접: 복제 서버가 있으니 별도 백업은 필요 없지 않나요?

답변: 일반적인 복제는 가용성을 높이는 데 도움이 되지만 과거 상태로 되돌아갈 독립 백업을 대신하지 않습니다. 잘못된 DELETE나 UPDATE도 복제될 수 있습니다.

예시: 운영자가 모든 주문 상태를 잘못 바꾼 트랜잭션이 복제 서버에도 적용되었다면 현재 복제본만으로 정상 상태를 얻기 어렵습니다. 이전 백업과 필요한 로그, 목표 복구 시점이 있어야 합니다.

설계: 장애 전환, 백업 보관, 시점 복구, 키 복구를 각각 시험하고 RPO·RTO를 측정하겠습니다. 서버가 켜진 것과 업무 데이터가 맞는 것은 별개의 검증 항목입니다.
