암호화와 복구: 데이터·로그·키를 끝까지 보호하기

읽는 방법

비유로 개념을 잡고 SQL을 실행하기 전 결과를 예상해 보세요. 본문의 수치 예시는 설명용이고, 실행 환경에 따라 달라지는 값은 따로 표시했습니다. 기준은 MySQL 8.0·InnoDB, 재현용 서버는 8.0.36입니다. 처음 시작한다면 1편의 서버 준비만 먼저 진행하면 됩니다.

전체 학습 지도·검증 범위

1. 암호화는 ‘누가 무엇을 훔쳤을 때’를 먼저 정해야 한다

창고 장부를 금고에 넣어도 출입 권한을 가진 직원은 장부를 읽을 수 있습니다. 디스크 암호화도 비슷합니다. 저장 파일이 유출되는 상황을 막는 데 도움이 되지만, 정상 SQL 권한을 가진 사용자의 조회를 막는 기능은 아닙니다. 위협을 구분하지 않으면 암호화를 켰다는 사실만으로 개인정보 보호가 끝났다고 착각하게 됩니다.

위협주요 대응한계
네트워크에서 내용 도청TLS와 인증서 검증정상 계정의 잘못된 조회 권한은 해결하지 못함
디스크 파일 유출Data-at-rest encryption키도 함께 유출되면 보호가 약해짐
앱 계정으로 과도한 조회최소 권한·접근 통제·감사저장 암호화만으로는 차단되지 않음
DB 운영자도 일부 원문을 몰라야 함애플리케이션 계층 암호화 등 별도 설계검색·정렬·키 관리가 어려워질 수 있음

2. 모든 데이터를 한 비밀번호로 직접 잠그지 않는 이유

InnoDB 저장 암호화는 마스터 키와 테이블스페이스 키의 두 계층을 사용합니다. 데이터는 테이블스페이스 키로 보호하고, 그 키를 마스터 키로 암호화해 관리합니다. 수많은 문을 같은 열쇠로 직접 여는 대신 각 방 열쇠를 보관하는 열쇠함을 별도 열쇠로 잠그는 구조입니다.

마스터 키를 회전할 때 모든 데이터 페이지를 처음부터 같은 방식으로 재암호화하는 것과는 비용 구조가 다릅니다. 데이터 키를 감싸는 보호를 바꾸는 작업과 실제 데이터 키를 바꾸는 작업을 구분해야 합니다. 키를 분리하면 회전과 관리가 유연해지지만, 그 키를 보존·복구하는 책임도 생깁니다.

3. Keyring은 부가 파일이 아니라 복구에 필요한 핵심 자산이다

Keyring은 서버가 암호화 키를 저장하고 조회하는 체계입니다. 사용할 수 있는 컴포넌트·플러그인은 MySQL 세부 버전과 에디션, 배포 형태에 따라 다릅니다. ‘플러그인 파일 하나를 복사하면 된다’는 식으로 모든 환경에 같은 설치 명령을 제공하면 위험합니다. 여기서는 기능 확인과 이미 준비된 keyring을 사용하는 실습을 구분합니다.

암호화된 데이터 파일만 백업하고 필요한 키를 잃으면 정상적인 복원이 불가능할 수 있습니다. 백업 대상에는 데이터·로그·설정·키의 복구 절차가 함께 들어가야 합니다. 데이터와 키를 같은 공개 폴더에 두면 분리의 이점이 줄어듭니다. 접근 권한과 키 회전 이력도 관리해야 합니다.

4. 실습 A: 설정을 바꾸지 않고 보호 범위를 확인하기

1편의 로컬 서버에서 실행합니다. 이 단계는 암호화 기능을 새로 설치하지 않는 읽기 전용 점검입니다. 결과가 비어 있거나 OFF여도 기본 학습 서버에서는 정상일 수 있습니다.

SELECT VERSION();
SHOW VARIABLES LIKE 'require_secure_transport';
SHOW SESSION STATUS LIKE 'Ssl_cipher';
SHOW VARIABLES LIKE 'innodb_redo_log_encrypt';
SHOW VARIABLES LIKE 'innodb_undo_log_encrypt';
SHOW VARIABLES LIKE 'binlog_encryption';
SELECT PLUGIN_NAME,PLUGIN_STATUS FROM information_schema.PLUGINS
WHERE PLUGIN_NAME LIKE 'keyring%';
SELECT * FROM mysql.component;

컴포넌트와 플러그인은 다른 설치 체계입니다. 플러그인 목록이 비었다고 keyring이 반드시 없다고 단정하지 않습니다. 반대로 목록에 이름이 있어도 실제 사용할 수 있는 키 저장소와 시작 시 로딩이 정상인지 확인해야 합니다. 현재 세션의 Ssl_cipher가 비어 있다면 그 연결이 TLS를 쓰지 않을 수 있습니다. docker exec로 소켓 접속한 학습 환경과 원격 TCP 연결을 구분하세요.

5. 실습 B: keyring이 준비된 별도 환경에서만 실행

전제: 해당 버전에 맞는 keyring을 설정하고, 재시작 시 로딩과 키 백업·복원 경로까지 확인한 로컬 실습 서버여야 합니다. 기본 1편 서버에서 바로 성공한다고 가정하지 않습니다. 준비되지 않은 경우 이 절은 읽기 실습으로 남겨 두세요.

CREATE DATABASE IF NOT EXISTS mysql_school;
USE mysql_school;
CREATE TABLE encrypted_demo (
 id INT PRIMARY KEY, note VARCHAR(100) NOT NULL
) ENGINE=InnoDB ENCRYPTION='Y';
INSERT INTO encrypted_demo VALUES(1,'보호할 학습 데이터');
SHOW CREATE TABLE encrypted_demo;
SELECT NAME,ENCRYPTION
FROM information_schema.INNODB_TABLESPACES
WHERE NAME='mysql_school/encrypted_demo';
SELECT * FROM encrypted_demo;

정상 권한으로 SELECT하면 평문이 나옵니다. 이것은 암호화 실패가 아니라 서버가 읽기 경로에서 복호화하기 때문입니다. ENCRYPTION='Y'는 테이블스페이스 보호를 뜻하며 모든 로그·백업·네트워크까지 한 번에 암호화한다는 뜻은 아닙니다. redo, undo, binlog의 보호 정책도 따로 확인합니다.

마스터 키 회전 명령은 ALTER INSTANCE ROTATE INNODB MASTER KEY입니다. 이 글에서는 실행 필수 실습으로 두지 않습니다. 키 회전 후 재시작과 복원까지 확인할 수 있는 격리 환경에서만 실험하세요. 명령이 성공했다는 메시지와 복구 가능성은 다른 증거입니다.

6. 백업은 파일이 아니라 복원 가능한 절차다

논리 백업은 CREATE TABLE·INSERT 같은 형태로 데이터와 구조를 재현합니다. 물리 백업은 저장 파일 구조를 다룹니다. 둘 다 장단점이 있고 활성 DB 파일을 아무렇게나 복사하는 것은 일관된 백업이 아닙니다. 여기서는 작은 InnoDB 학습 테이블을 논리적으로 저장하고 다시 읽는 실습을 합니다.

-- 먼저 mysql 클라이언트에서 준비
CREATE DATABASE IF NOT EXISTS mysql_school;
CREATE TABLE IF NOT EXISTS mysql_school.backup_demo (
 id INT PRIMARY KEY, note VARCHAR(100) NOT NULL
) ENGINE=InnoDB;
INSERT INTO mysql_school.backup_demo VALUES(1,'restore-test')
 ON DUPLICATE KEY UPDATE note='restore-test';
CREATE DATABASE IF NOT EXISTS mysql_school_restore;

컨테이너의 대화형 셸에서 덤프를 파일로 만든 뒤 mysql 클라이언트의 SOURCE로 읽습니다. 이렇게 하면 비밀번호 입력과 SQL 파일 입력을 분리할 수 있습니다.

docker exec -it mysql-school sh
# 이제 컨테이너 안입니다.
mysqldump -uroot -p --single-transaction --no-tablespaces \
  --set-gtid-purged=OFF mysql_school backup_demo > /tmp/backup-demo.sql
mysql -uroot -p mysql_school_restore
# mysql 프롬프트에서:
SOURCE /tmp/backup-demo.sql;
SELECT * FROM backup_demo;
# id=1, note=restore-test 확인 후 exit

--single-transaction은 InnoDB의 일관된 읽기를 활용합니다. 비트랜잭션 테이블이나 백업 중 DDL까지 무조건 안전하게 만들어 주지 않습니다. 또한 이 실습은 테이블 하나의 복원입니다. 계정·역할·루틴·이벤트·GTID·전체 인스턴스 복구를 모두 검증한 것이 아닙니다. 저장 암호화된 테이블을 논리 dump하면 내용이 평문일 수 있어 백업 파일 자체의 보호가 필요합니다.

7. 장애 시나리오: 데이터 파일은 있는데 키가 없다

가상의 복구 훈련에서 새 서버에 암호화된 데이터를 가져왔지만 키 저장소가 누락되었습니다. 파일은 존재하므로 디스크 장애가 아니지만 데이터를 읽을 수 없습니다. 해결 방향은 암호화를 끄는 것이 아니라 올바른 키와 로딩 구성, 권한, 버전 호환성을 복구하는 것입니다. 읽을 수 없는 데이터를 설정 하나로 평문으로 바꾸는 우회는 없습니다.

복구 훈련에서는 ‘기동 성공’ 다음에 업무 불변식도 확인합니다. 재고가 음수가 아닌지, 주문과 이력이 연결되는지, 기준 시점 이후 이벤트를 어디까지 적용했는지 점검합니다. 목표 복구 시간(RTO)과 허용 데이터 손실 범위(RPO)를 측정해야 실제 운영 계획이 됩니다.

8. 전체 시리즈를 하나의 요청으로 연결하기

이제 출고 API 한 건을 따라가 보세요. 계정이 인증되고 권한을 통과합니다. 옵티마이저가 인덱스 경로를 고릅니다. 버퍼 풀에서 페이지를 찾고, 트랜잭션과 잠금으로 경쟁을 제어합니다. 변경에는 undo·redo가 연관되고 커밋 정책에 따라 확정됩니다. 페이지는 나중에 압축·암호화 등 저장 정책에 맞춰 기록됩니다. 느리면 실행 계획·잠금·I/O 중 어느 구간인지 찾고, 장애가 나면 로그·백업·키를 사용해 복구합니다.

이 연결이 이해되면 설정 이름을 외우는 대신 “어느 단계의 어떤 비용과 보장을 바꾸는가”를 질문할 수 있습니다. 실무 판단의 출발점은 기능 수가 아니라 데이터가 지나가는 경로를 설명할 수 있는 능력입니다.

9. 상세 면접 Q&A

저장 암호화하면 SELECT 권한이 있는 사람도 못 읽나요?

아닙니다. 서버는 정상 읽기 과정에서 복호화해 결과를 반환합니다. 저장 파일 유출 보호와 SQL 권한 통제는 별개입니다. DB 운영자까지 원문 접근을 제한하려면 애플리케이션 계층 등 다른 암호화 경계를 검토해야 합니다.

키를 잃으면 데이터 파일로 복원할 수 있나요?

필요한 키 없이는 정상 복호화가 불가능할 수 있습니다. 그래서 키 관리와 복구는 백업 설계의 일부입니다. 데이터 파일 존재 여부만 확인하는 백업 점검은 부족하며 격리된 새 환경에서 실제 복원을 수행해야 합니다.

마스터 키 회전은 데이터 전체 재암호화인가요?

마스터 키가 테이블스페이스 키를 보호하는 두 계층 구조에서는 데이터 키를 감싸는 보호를 바꾸는 것과 모든 데이터 페이지를 새 데이터 키로 암호화하는 것이 다릅니다. 명령의 대상과 키 계층을 구분해서 설명해야 합니다.

ENCRYPTION='Y'면 binlog도 암호화되나요?

테이블스페이스 설정만으로 모든 로그의 보호를 가정하면 안 됩니다. binlog·redo·undo는 각 정책과 지원 조건을 따로 확인합니다. 논리 백업 파일과 네트워크 전송도 별도 보호 대상입니다.

--single-transaction이면 모든 백업이 무조건 일관적인가요?

주로 트랜잭션 테이블의 스냅샷에 의존합니다. 비트랜잭션 테이블과 백업 중 DDL에는 별도 주의가 필요합니다. 계정·루틴·복제 위치 등 포함 범위도 확인해야 합니다. 옵션 하나로 전체 시스템 복구가 완성되지 않습니다.

복구가 성공했는지 무엇을 확인하나요?

서버 기동과 테이블 조회뿐 아니라 행 수·중요 집계·업무 관계·키 접근·복구 시점·애플리케이션 동작을 확인합니다. 실제 소요 시간과 로그 적용 범위를 기록해 RTO와 RPO 요구를 만족하는지 평가합니다.
