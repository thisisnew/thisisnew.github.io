AdminClient와 MirrorMaker 2 운영

한 번에 외우려 하지 말고 비유와 실제 기술의 차이부터 읽어 보세요. 각 절은 동작 원리, 정상 처리, 장애 위험을 함께 설명합니다.

1. AdminClient

5살도 이해하는 이야기

게시판을 관리하는 교장실 이 비유를 실제 기술로 연결해 보겠습니다.

정확한 내부 동작

AdminClient는 Topic 생성·조회·삭제, Config 변경, Consumer Group 조회 등 관리 작업을 비동기 API로 수행한다.

Kafka AdminClient createTopics(), describeTopics(), describeConfigs()는 작업별 Future를 반환한다. 호출 성공 여부를 명시적으로 확인한다.

언제 문제가 될까?

삭제와 설정 변경은 운영 영향이 크므로 관리자 계정에 최소 권한을 부여하고 변경 로그를 남긴다.

2. MirrorMaker 2

5살도 이해하는 이야기

다른 마을로 공지를 복사하는 배송차 이 비유를 실제 기술로 연결해 보겠습니다.

정확한 내부 동작

서로 다른 Kafka 클러스터 간 Topic 데이터를 복제하는 기능이며 Connect 기반으로 동작한다.

원본과 대상의 Topic 네이밍 정책, 복제 지연, 내부 토픽, Connector 상태를 함께 관리한다.

언제 문제가 될까?

복제본이 생겼다고 양쪽 쓰기가 자동 일치하지 않으며 재해 복구 전환 시 중복·누락과 Offset 변환을 확인한다.

🎯 확인 질문: MirrorMaker 2의 동작과 장애 위험은?

정답: 서로 다른 Kafka 클러스터 간 Topic 데이터를 복제하는 기능이며 Connect 기반으로 동작한다. 원본과 대상의 Topic 네이밍 정책, 복제 지연, 내부 토픽, Connector 상태를 함께 관리한다.

실무 포인트: 복제본이 생겼다고 양쪽 쓰기가 자동 일치하지 않으며 재해 복구 전환 시 중복·누락과 Offset 변환을 확인한다.

3. 클러스터 간 Offset

5살도 이해하는 이야기

서로 다른 책장의 책갈피 이 비유를 실제 기술로 연결해 보겠습니다.

정확한 내부 동작

원본 클러스터의 Offset 숫자를 대상 클러스터에 그대로 복사해 시작 지점으로 사용하면 안 될 수 있다.

복제된 레코드는 대상 파티션의 고유 오프셋을 가지므로 Offset 동기화·체크포인트 정책을 이해해야 한다.

언제 문제가 될까?

재해 복구 리허설에서 소비 시작 위치와 업무 멱등성을 검증한다.

🎯 확인 질문: 클러스터 간 Offset의 동작과 장애 위험은?

정답: 원본 클러스터의 Offset 숫자를 대상 클러스터에 그대로 복사해 시작 지점으로 사용하면 안 될 수 있다. 복제된 레코드는 대상 파티션의 고유 오프셋을 가지므로 Offset 동기화·체크포인트 정책을 이해해야 한다.

실무 포인트: 재해 복구 리허설에서 소비 시작 위치와 업무 멱등성을 검증한다.

4. 관리 API의 비동기 결과

5살도 이해하는 이야기

신청서를 냈다고 허가가 난 건 아님 이 비유를 실제 기술로 연결해 보겠습니다.

정확한 내부 동작

관리 요청 Future를 기다리지 않으면 토픽 생성이 완료되기 전에 Producer가 전송을 시작할 수 있다.

예외 원인과 Topic별 결과를 구분하고 타임아웃을 설정해야 한다.

언제 문제가 될까?

이미 존재하는 토픽과 인증 실패, 인가 실패는 서로 다른 분기다.

🎯 확인 질문: 관리 API의 비동기 결과의 동작과 장애 위험은?

정답: 관리 요청 Future를 기다리지 않으면 토픽 생성이 완료되기 전에 Producer가 전송을 시작할 수 있다. 예외 원인과 Topic별 결과를 구분하고 타임아웃을 설정해야 한다.

실무 포인트: 이미 존재하는 토픽과 인증 실패, 인가 실패는 서로 다른 분기다.
