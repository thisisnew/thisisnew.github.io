Connector 직접 개발: SourceTask·SinkTask

도트 게임 속 스테이지를 진행하듯, 쉬운 비유부터 기술적인 흐름과 장애 대응을 함께 익혀봅시다. 비유의 한계를 기억하고 실제 용어를 직접 설명해 보세요.

실습과 점검

테스트 토픽과 격리된 Kafka 클러스터에서 각각의 이벤트 Key, Partition, Offset, 처리 성공 여부를 기록하며 결과를 추적하세요. 상태를 사용하는 기능은 앱 재시작 시 복구 시간도 측정합니다. 운영 클러스터의 오프셋을 임의로 수정하거나 Topic을 삭제해서는 안 됩니다.

상세 학습 1. Connector와 Task 생명주기

Connector는 주로 설정을 검증하고 실제 Task 클래스와 Task별 설정을 정의해요. Worker는 Task를 생성·시작·중지합니다.

여기서 Connector의 `start`가 모든 데이터를 직접 이동시키는 메서드라고 생각하면 틀려요. 실제 SourceTask와 SinkTask의 실행 진입점을 구분해야 합니다.

상세 학습 2. SourceTask.poll을 만드는 과정

SourceTask는 외부 API나 파일, DB 같은 소스를 조회해 SourceRecord를 만들어 반환할 수 있어요. SourceRecord에는 어느 외부 파티션의 어느 위치에서 읽었는지 나타내는 sourcePartition과 sourceOffset 같은 정보가 들어갑니다.

이후 재시작 시 진행 위치를 복구하려면 이 식별자가 안정적으로 유지되어야 합니다.

파일 라인 번호를 Offset으로 쓰더라도 파일 교체·회전이 일어나면 어떤 파일의 몇 번째 줄인지 구분하는 방식이 필요해요.

상세 학습 3. SinkTask.put은 일괄 처리와 예외가 중요

SinkTask는 Kafka에서 온 레코드 목록을 받습니다.

여기서 DB Batch Insert를 수행할 수 있지만 DB 커밋 성공과 Kafka 오프셋 진행은 원자적으로 묶여 있지 않을 수 있습니다.

DB 저장 후 Worker가 죽으면 같은 레코드를 다시 받을 가능성을 고려해야 해요. 외부 대상에 Event ID UNIQUE 제약을 두거나 Upsert 전략을 검토해야 합니다.

상세 학습 4. 느린 외부 API와 재시도

외부 API가 느려졌다고 SourceTask.poll이 영원히 블로킹되면 Worker가 Task를 종료·교체하는 데 문제가 생길 수 있습니다.

SinkTask.put도 동일해요. 각 요청의 타임아웃과 재시도 횟수를 명확히 설정하고 일시 오류와 영구 오류를 구별하세요. 처리량이 충분한 경우에도 외부 제공자의 Rate Limit를 무시하면 연쇄 장애가 날 수 있습니다.
