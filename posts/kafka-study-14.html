1. Kafka Connect를 왜 쓸까?

🕹️ 아주 쉬운 비유

급식실에서 재료를 교실마다 매일 옮기는데 선생님들이 날마다 새로운 운반 프로그램을 만든다면 번거롭겠지요. 정해진 배송 체계를 마련하면 편리합니다.

🔍 실제로 어떻게 움직일까?

Kafka Connect는 외부 데이터 소스와 Kafka 토픽 사이에서 데이터를 지속적으로 이동시키는 프레임워크입니다. 외부→Kafka는 Source Connector, Kafka→외부는 Sink Connector입니다.

Connector는 데이터 이동 방식과 설정을 정의하며 Task는 실제 병렬 작업을 수행합니다. Worker는 Task를 실행·관리하는 프로세스입니다. 세 개념을 혼동하면 장애 때 어디를 재시작해야 하는지 판단하기 어렵습니다.

⚠️ 실무에서 겪는 상황

DB에서 이벤트를 수집하다가 Connector 상태가 RUNNING인데 Task가 FAILED라면 전체가 정상이라는 뜻이 아닙니다. Task 상태 및 오류 원인을 확인해야 합니다.

🎯 이해도 확인: Kafka Connect를 왜 쓸까?에서 가장 중요한 점은?

Connector/Task/Worker는 각각 설정 단위, 실행 단위, 프로세스 단위라는 차이가 있습니다.

DB에서 이벤트를 수집하다가 Connector 상태가 RUNNING인데 Task가 FAILED라면 전체가 정상이라는 뜻이 아닙니다. Task 상태 및 오류 원인을 확인해야 합니다.

2. bootstrap.servers와 group.id

🕹️ 아주 쉬운 비유

버스를 타려면 처음 찾아갈 정류장 주소가 필요하고, 같이 일하는 운송팀에는 팀 이름이 필요해요.

🔍 실제로 어떻게 움직일까?

bootstrap.servers는 Worker가 클러스터를 찾을 최초 Broker 주소 목록입니다. 모든 Broker 주소를 넣을 필요는 없지만 한 주소만 적으면 장애 시 초기 연결이 어려워질 수 있습니다.

Connect Distributed Worker의 group.id는 함께 협력하는 Connect 클러스터를 식별합니다. 업무 메시지를 읽는 일반 Consumer Group의 group.id와 의미상 구분해야 합니다.

⚠️ 실무에서 겪는 상황

Worker를 세 대 띄웠는데 서로 다른 group.id로 설정하면 하나의 Distributed Connect 클러스터로 협력하지 않습니다.

🎯 이해도 확인: bootstrap.servers와 group.id에서 가장 중요한 점은?

부트스트랩 연결·클러스터 그룹 식별을 구분하세요.

Worker를 세 대 띄웠는데 서로 다른 group.id로 설정하면 하나의 Distributed Connect 클러스터로 협력하지 않습니다.

3. 세 내부 토픽: config / offset / status

🕹️ 아주 쉬운 비유

배송센터는 '직원에게 어떤 일을 시켰는가', '어디까지 배송했는가', '누가 고장 났는가'를 별도 장부에 적습니다.

🔍 실제로 어떻게 움직일까?

config.storage.topic은 Connector 설정을 저장하고, offset.storage.topic은 Source Connector의 읽기 진행 위치를 저장합니다. status.storage.topic은 Connector와 Task 상태를 저장합니다.

이 토픽들은 Worker 클러스터가 장애 후 설정·진행·상태를 복구하는 기반입니다. 적절한 파티션 수와 복제 계수, 압축 정책, ACL을 함께 고려해야 합니다. 일반 Producer의 업무 토픽과 역할이 다릅니다.

⚠️ 실무에서 겪는 상황

offset 저장이 실패했는데 외부 시스템으로 데이터를 보낸 뒤 프로세스가 종료되면 일부 데이터가 중복 이동할 가능성이 있습니다. 외부 대상의 멱등 처리가 중요합니다.

🎯 이해도 확인: 세 내부 토픽: config / offset / status에서 가장 중요한 점은?

설정/오프셋/상태 저장 목적이 서로 다른 세 개의 내부 토픽을 구별하세요.

offset 저장이 실패했는데 외부 시스템으로 데이터를 보낸 뒤 프로세스가 종료되면 일부 데이터가 중복 이동할 가능성이 있습니다. 외부 대상의 멱등 처리가 중요합니다.

4. key.converter, value.converter, header.converter

🕹️ 아주 쉬운 비유

한국어 주문서를 영어 서식으로 옮기는 통역 규칙이 없으면 받는 사람이 글자를 읽지 못할 수 있습니다.

🔍 실제로 어떻게 움직일까?

Converter는 Kafka Connect 내부 데이터 표현과 Kafka 레코드의 직렬화 형식을 변환합니다. Key와 Value Converter를 독립적으로 지정할 수 있으며 header.converter도 별도 개념입니다.

JSON Converter의 schemas.enable 설정 여부는 실제 출력 JSON의 형태에 영향을 줄 수 있습니다. Kafka Connect의 Converter와 일반 Kafka Producer의 Serializer는 역할이 비슷하지만 API와 데이터 모델이 동일하지 않습니다.

⚠️ 실무에서 겪는 상황

Connector는 살아 있는데 Sink 대상이 JSON을 해석하지 못하면 converter 선택과 schemas.enable, 키·값 데이터 구조부터 점검하세요.

🎯 이해도 확인: key.converter, value.converter, header.converter에서 가장 중요한 점은?

외부 연계의 데이터 모델과 Converter 설정, 스키마 호환을 한 세트로 이해해야 합니다.

Connector는 살아 있는데 Sink 대상이 JSON을 해석하지 못하면 converter 선택과 schemas.enable, 키·값 데이터 구조부터 점검하세요.

5. offset.flush.interval.ms와 timeout

🕹️ 아주 쉬운 비유

운송 기록을 5초에 한 번 장부에 적는다면 마지막 기록 전에 정전이 나면 어디까지 배송했는지 불확실해져요.

🔍 실제로 어떻게 움직일까?

Source Task는 자신이 읽은 외부 소스의 진행 위치를 Connect가 유지하도록 합니다. offset.flush.interval.ms는 오프셋 저장 주기와 관련되고 offset.flush.timeout.ms는 저장 완료 대기 시간에 영향을 줍니다.

저장 주기를 줄이면 복구 재처리량을 낮추는 데 도움이 될 수 있으나 저장 오버헤드와 외부 소스의 커밋 의미를 고려해야 합니다. 원본 시스템에 따라 오프셋 의미가 다릅니다.

⚠️ 실무에서 겪는 상황

장애 후 중복 수집이 발생했다면 Source Offset 저장과 실제 Kafka 전송 완료의 시점을 조사해야 합니다.

🎯 이해도 확인: offset.flush.interval.ms와 timeout에서 가장 중요한 점은?

정확한 외부 소스 진행 위치는 'Kafka 메시지를 소비한 오프셋'과 다른 것입니다.

장애 후 중복 수집이 발생했다면 Source Offset 저장과 실제 Kafka 전송 완료의 시점을 조사해야 합니다.

6. plugin.path와 플러그인 격리

🕹️ 아주 쉬운 비유

배송 차량에 필요한 도구를 정해진 창고에 보관해야 직원이 쉽게 찾습니다.

🔍 실제로 어떻게 움직일까?

plugin.path는 Connect Worker가 커넥터와 Converter 등 플러그인 코드를 발견하는 경로입니다. 워커 런타임은 플러그인 로딩과 클래스 충돌 문제를 관리해야 합니다.

플러그인 디렉터리에 JAR을 배치했다고 실행 중인 모든 Worker가 즉시 새로운 Connector를 인식하는 것은 아닙니다. 배포와 재시작 필요 여부를 검토하고 모든 Worker에 동일한 버전을 배포해야 합니다.

⚠️ 실무에서 겪는 상황

한 Worker에서는 Connector 클래스가 보이는데 다른 Worker에서는 ClassNotFound 오류라면 플러그인 설치 버전과 경로가 일치하는지 비교하세요.

🎯 이해도 확인: plugin.path와 플러그인 격리에서 가장 중요한 점은?

plugin.path는 Kafka Topic 경로가 아닌 JVM 플러그인 발견 경로입니다.

한 Worker에서는 Connector 클래스가 보이는데 다른 Worker에서는 ClassNotFound 오류라면 플러그인 설치 버전과 경로가 일치하는지 비교하세요.

7. 정확히 한 번 Source 지원의 경계

🕹️ 아주 쉬운 비유

운송 장부에 도장이 한 번만 찍혀도 외부 창고 문서가 한 번만 수정됐다고 할 수는 없습니다.

🔍 실제로 어떻게 움직일까?

Connect 설정의 exactly.once.source.support는 Source Connector 측 Kafka 기록과 오프셋 처리의 정확히 한 번 지원 능력과 관계됩니다. 실제 보장은 Connector 구현이 해당 기능을 지원하는지와 구동·마이그레이션 설정에 따라 달라집니다.

Sink Connector가 외부 DB나 API에 정확히 한 번만 반영한다는 뜻은 아닙니다. Source와 Sink의 경계를 구분하고 외부 시스템의 멱등 키 또는 거래 처리 제약을 고려하세요.

⚠️ 실무에서 겪는 상황

Kafka 내부 Exactly-once가 MySQL과 S3까지 자동으로 확장된다고 주장하면 위험합니다.

🎯 이해도 확인: 정확히 한 번 Source 지원의 경계에서 가장 중요한 점은?

정확히 한 번이라는 표현은 Source Kafka 트랜잭션과 외부 시스템 경계를 나눠 설명해야 합니다.

Kafka 내부 Exactly-once가 MySQL과 S3까지 자동으로 확장된다고 주장하면 위험합니다.

8. 보안과 REST API: 무엇을 보호할까?

🕹️ 아주 쉬운 비유

배송 관리실 전화번호가 외부에 노출되면 아무나 운송 계획을 고칠 수 있어요.

🔍 실제로 어떻게 움직일까?

Connect Worker는 Kafka Broker 접근을 위한 security.protocol, SASL/SSL 등의 클라이언트 설정이 필요할 수 있습니다. REST API의 listeners, admin.listeners 등 설정은 워커 관리 인터페이스의 접근성에 영향을 줍니다.

Kafka ACL과 Connect REST API의 접근 제어는 다른 층위입니다. 인증된 Worker라고 해서 REST 엔드포인트가 자동으로 안전하게 보호되는 것은 아닙니다.

⚠️ 실무에서 겪는 상황

관리 REST를 외부 인터넷에 직접 노출하지 말고 네트워크·인증·관리 권한을 따로 설계하세요.

🎯 이해도 확인: 보안과 REST API: 무엇을 보호할까?에서 가장 중요한 점은?

브로커 통신 보안과 REST 관리 인터페이스 보안을 분리합니다.

관리 REST를 외부 인터넷에 직접 노출하지 말고 네트워크·인증·관리 권한을 따로 설계하세요.

💻 직접 실행하거나 코드로 확인하기

예시 설정은 원리를 익히는 학습용입니다. 실제 사용 중인 Kafka 및 Java 클라이언트 버전, 네트워크 접근성, 인증 정책에 맞게 수정하세요.

# distributed worker 예시 (환경에 맞게 조정)
bootstrap.servers=broker1:9092,broker2:9092
group.id=connect-cluster-1
config.storage.topic=connect-configs
offset.storage.topic=connect-offsets
status.storage.topic=connect-status
key.converter=org.apache.kafka.connect.storage.StringConverter
value.converter=org.apache.kafka.connect.json.JsonConverter
value.converter.schemas.enable=false
plugin.path=/opt/kafka/plugins
