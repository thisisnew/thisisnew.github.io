1. AWS를 처음 만나면 왜 이름부터 막힐까

물류센터를 처음 방문했다고 생각해 봅시다. 냉장창고, 검수대, 컨베이어, 출입증 발급실 이름을 외운다고 입고 시스템을 설계할 수 있는 것은 아닙니다. 상품이 언제 도착하고, 누가 검사하며, 불량이면 어디로 보내고, 정전이 나면 무엇을 지킬지 알아야 시설을 배치할 수 있습니다. AWS도 같습니다. EC2는 프로그램을 실행할 곳, S3는 파일을 보관할 곳, SQS는 나중에 처리할 일을 맡기는 곳입니다. 각각의 기능보다 요청이 들어와서 데이터가 남기까지의 흐름을 먼저 이해해야 이름이 기억됩니다.

이 연재는 첨부 공부팩의 23개 PDF를 로드맵·CORE·DEEP DIVE 순서로 대응시킵니다. 원문을 그대로 복사한 번역본이 아니라, 개념과 설계 질문을 한국어로 재구성한 학습 해설입니다. 원문의 참고 링크·반복 설명·제품 홍보 문구까지 문장 단위로 옮긴 것은 아닙니다. 공개되지 않은 AWS 내부 구현은 추측으로 채우지 않고, 문서에서 보장하는 동작과 일반적인 분산 시스템 원리를 구분합니다.

2. 먼저 완성할 한 장의 그림

사용자가 검수 사진을 올린다고 해 봅시다. DNS는 서비스 주소를 찾고, 로드 밸런서는 살아 있는 애플리케이션으로 요청을 보냅니다. 애플리케이션은 사용자의 권한을 확인한 뒤 사진을 S3에 저장하고, 사진의 주소와 검수 결과는 관계형 DB에 기록합니다. 후속 알림은 큐로 넘깁니다. 운영자는 지표와 로그로 성공 여부를 확인하고, 장애가 나면 복구 계획에 따라 서비스를 되살립니다.

질문 주로 만나는 서비스·개념 반드시 연결할 조건
코드는 어디서 실행하나 EC2, Lambda, ECS/EKS, Fargate 실행 시간, 상태, 운영 책임
사진·파일은 어디에 남기나 S3, EBS, EFS, FSx 객체·블록·파일 접근 방식
요청은 어떤 길로 가나 VPC, ALB/NLB, Route 53, CloudFront 경로·접근 제어·캐시
업무 상태는 어떻게 보존하나 RDS/Aurora, DynamoDB 트랜잭션·조회 패턴·복제
느린 일을 어떻게 분리하나 SQS, SNS, EventBridge 재시도·중복·독립 소비
누가 무엇을 할 수 있나 IAM, KMS, Secrets Manager 인증·인가·키 관리
고장과 낭비를 어떻게 발견하나 CloudWatch, CloudTrail, Config, 비용 도구 지표·감사·구성·귀속

이 흐름은 유일한 정답 아키텍처가 아닙니다. 사진 업로드는 사전 서명 URL로 S3에 직접 보낼 수도 있고, 업무 성격에 따라 DB나 실행 환경도 달라집니다. 학습의 목적은 구성을 외우는 것이 아니라 바꿨을 때 생기는 책임과 손해를 설명하는 것입니다.

3. 권장 학습 순서와 완료 기준

첫 회전은 0113편입니다. 서비스마다 “무엇을 해결하는가, 비슷한 대안과 어떻게 다른가, 장애가 나면 무엇이 남는가”를 설명해 보세요. 02편에서 계정·리전·AZ를 구분한 뒤 0309편의 구성 요소를 연결합니다. 10~12편은 비용·이전·분석이라는 목적에 맞춰 앞의 지식을 다시 사용합니다. 13편은 설계를 여섯 관점에서 검토하는 방법입니다.

두 번째 회전은 비교 중심입니다. EC2와 Lambda, EBS와 EFS, Multi-AZ와 Read Replica를 비교하면서 반드시 전제를 붙입니다. 예를 들어 “Multi-AZ는 읽기 확장용이 아니다”라는 문장을 모든 RDS 배포 형태에 적용하면 틀립니다. 전통적인 Multi-AZ DB 인스턴스의 standby와 읽기를 지원하는 Multi-AZ DB 클러스터는 다릅니다.

세 번째 회전은 1422편의 심화입니다. 보안은 SEC 111, 신뢰성은 REL 113, 성능은 PERF 14, 비용은 COST 111의 설계 질문을 따라갑니다. 단순 제품 소개보다 팀이 무엇을 결정하고 어떻게 검증할지가 중요해집니다. 이 공부팩의 성능 심화 발췌는 PERF 14이며, 프레임워크 전체와 발췌 범위가 같지는 않습니다.

기간은 사람마다 다릅니다. 원래 로드맵의 CORE 710일, 비교 45일, 선택 심화 3~7일은 계획 예시이지 합격 보장이 아닙니다. 하루 공부 시간을 먼저 정하고, 설명하지 못한 비교 쌍을 다음 학습 대상으로 삼는 편이 낫습니다.

4. 글 한 편을 공부하는 실제 방법

  1. 상황부터 읽습니다. “원본 사진은 잃으면 안 되고, 썸네일은 재생성 가능하다”처럼 제약을 적습니다.
  2. 비유를 자신의 말로 바꿉니다. 비유의 어느 부분이 실제 시스템과 다른지도 말합니다.
  3. 정상 흐름을 그립니다. 요청·저장·응답·후속 처리 순서를 써 봅니다.
  4. 한 곳을 고장 냅니다. DB는 저장했는데 응답이 사라지면 재시도가 어떤 결과를 만드는지 묻습니다.
  5. 접힌 Q&A를 먼저 스스로 답합니다. 정답을 외우기보다 선택 이유와 대안이 탈락한 조건을 비교합니다.
  6. 증거를 남깁니다. 읽은 문서, 설정, 예상 결과, 관찰 결과를 분리합니다. 이 연재의 사고 실험은 AWS 계정에서 실행한 테스트 결과가 아닙니다.

5. 시험 문제를 실무 판단으로 바꾸기

“최소 운영 부담”은 직접 브로커를 설치하는 것보다 관리형 큐가 유리할 수 있다는 신호입니다. 그러나 기존 JMS 호환 코드가 중요하면 Amazon MQ를 검토해야 합니다. “가장 저렴한 저장소”도 복구 시간이 몇 시간이어도 되는지, 매일 읽는지에 따라 달라집니다. 정답을 바꾸는 단어는 서비스 이름보다 지연 시간, 데이터 손실, 호환성, 운영 부담, 비용에 숨어 있습니다.

실무에서는 시험보다 미확정 조건이 많습니다. 그럴 때 질문을 생략하지 마세요. “몇 초 내 복구가 필요한가”, “마지막 몇 분의 데이터 손실을 허용하는가”, “중복 알림은 허용되는가”라는 질문이 아키텍처의 출발점입니다.

6. 상세 면접 Q&A

Q. AWS 서비스를 많이 외우면 좋은 설계를 할 수 있나요?

서비스 지식은 후보를 찾는 데 필요하지만 선택을 결정하지는 못합니다. 예를 들어 파일 저장이라는 말만으로 S3와 EFS를 고를 수 없습니다. HTTP로 객체를 읽는지, 기존 프로그램이 POSIX 파일 경로와 잠금을 요구하는지를 확인해야 합니다. 요구사항을 접근 방식·성능·장애 허용 범위로 분해한 뒤 서비스의 계약과 맞춰야 합니다.

Q. 백엔드 개발자는 보안을 어디까지 공부해야 하나요?

자신의 코드가 어떤 신원으로 어떤 데이터에 접근하는지, 자격 증명을 어디에서 얻는지, 권한 거부를 어떻게 조사하는지까지는 핵심입니다. 조직 전체 보안 관제 전문가가 될 필요는 없지만, role과 장기 키의 차이·KMS 키 권한·로그의 개인정보 노출·네트워크 경로를 모르면 안전한 애플리케이션을 설계하기 어렵습니다.

Q. 심화 편을 처음부터 모두 읽어야 하나요?

전체를 완독하려면 먼저 CORE로 용어와 정상 흐름을 잡고 심화로 돌아오는 편이 이해에 유리합니다. 예를 들어 재시도 폭주를 배우기 전에 큐와 timeout을 모르면 각 권장사항이 서로 연결되지 않습니다. 시험 준비에서는 약점을 우선하고, 실무 설계에서는 자신이 책임지는 경로를 우선하세요.

Q. 공식 문서가 있으면 이 해설은 왜 필요한가요?

공식 문서는 기능의 조건과 한계를 확인하는 기준입니다. 해설은 여러 문서에 흩어진 개념을 한 상황으로 연결하고, 생략된 배경을 설명하는 역할을 합니다. 둘이 충돌하면 현재 공식 문서와 실제 설정을 다시 확인해야 합니다. 이 연재의 제품 상태 확인일은 2026-10-20이며 변동 가능한 조건은 링크에서 재확인해야 합니다.
