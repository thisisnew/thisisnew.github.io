1. 빠른 창고보다 짧은 동선

검수 담당자가 상품 하나를 확인할 때마다 창고 끝까지 걸어가면 창고 면적을 늘려도 업무는 빨라지지 않습니다. 데이터 시스템에서는 불필요한 쿼리·큰 응답·멀리 떨어진 왕복이 긴 동선입니다. PERF 3은 데이터 저장과 접근, PERF 4는 네트워크와 전달 경로를 다룹니다. 먼저 일을 덜 하게 만들고, 그다음 필요한 일을 효율적으로 수행할 자원을 고릅니다.

2. PERF 3: 접근 패턴이 저장소를 결정한다

관계형 트랜잭션과 유연한 조인이 중요한지, key로 단건을 빠르게 찾는지, 그래프를 순회하는지, 대량 열 집계를 하는지 분리합니다. 단일 DB로 모든 요구를 해결할 수도 있지만 전문 저장소를 추가하면 데이터 동기화와 운영 복잡성이 생깁니다. 목적별 저장소는 성능을 얻는 대신 복제·일관성·실패 경계를 추가하는 선택입니다.

PERF03-BP01~05는 저장소 선택, 구성 옵션, 성능 지표, 쿼리 개선, 캐싱을 포함합니다. 저장 공간만 늘려도 IOPS나 처리량이 함께 늘어나는지는 제품과 유형에 따라 다릅니다. read replica는 읽기를 옮기지만 복제 지연이 있고, partition key 분산은 쓰기 집중을 줄이지만 조회 fan-out을 늘릴 수 있습니다. 선택할 때 데이터 크기뿐 아니라 요청 분포와 변경 빈도를 기록합니다.

3. 인덱스·쿼리·파일 형식

인덱스는 찾는 경로를 줄이지만 쓰기와 저장 비용을 추가합니다. warehouse_id, created_at 인덱스가 창고별 시간 범위 조회에 유용할 수 있지만 모든 쿼리를 해결하지는 않습니다. 실제 실행 계획·읽은 행 수·정렬·임시 테이블·잠금 대기를 확인해야 합니다. SELECT * 대신 필요한 열, N+1 대신 적절한 일괄 조회, 큰 offset 대신 안정된 정렬 키를 이용한 페이지 방식 등을 요구에 맞게 검토합니다.

분석 파일은 행 지향 JSON/CSV와 열 지향 Parquet의 접근 비용이 다릅니다. 날짜 파티션은 관련 없는 파일을 건너뛰는 데 도움이 되지만 지나친 세분화와 작은 파일은 메타데이터 오버헤드를 늘릴 수 있습니다. “압축하면 무조건 빠르다”도 아닙니다. 전송·디스크 읽기는 줄지만 CPU 비용이 늘므로 병목과 포맷·엔진 지원에 따라 검증합니다.

IOPS·처리량·지연은 각각 횟수·바이트량·시간입니다. 4KiB 랜덤 읽기와 1MiB 순차 읽기는 같은 요청 수라도 전혀 다른 대역폭을 필요로 합니다. 인스턴스와 볼륨, 클라이언트 동시 요청 수가 함께 결과를 결정합니다. 제품의 최대 수치를 서로 더하는 대신 end-to-end 경로의 가장 좁은 구간을 찾습니다.

4. 캐시는 일관성과 실패를 추가한다

cache-aside는 읽기 미스 시 DB에서 가져와 채우는 방식입니다. 쓰기 후 삭제를 했어도 경쟁 중인 오래된 읽기가 뒤늦게 캐시를 다시 채울 수 있습니다. TTL만 짧게 잡는 것은 오래된 값의 기간을 제한하는 수단이지 모든 경쟁을 해결하는 증명은 아닙니다. 데이터 버전·단일 갱신 책임·업무상 허용 지연에 따라 전략을 정합니다.

cache stampede는 많은 요청이 동시에 미스나 만료를 만나 원본에 몰리는 현상입니다. TTL jitter, 요청 병합, 사전 갱신, 허용 가능한 stale 응답 등을 검토합니다. negative caching은 존재하지 않는 값의 반복 조회를 줄일 수 있지만 나중에 생성된 데이터가 늦게 보일 수 있습니다. hot key는 특정 데이터 하나에 부하가 집중되는 문제이므로 전체 캐시 노드를 늘리는 것만으로 선형 해결되지 않을 수 있습니다.

캐시가 죽었을 때 모든 요청을 DB로 보내는 무제한 fallback은 DB까지 무너뜨릴 수 있습니다. 제한된 동시성·중요 요청 우선·일부 기능 축소를 설계합니다. 적중률뿐 아니라 원본 부하, p99, stale 결과, 메모리와 eviction을 측정해야 합니다.

5. PERF 4: 거리와 왕복 횟수

광속과 경로 때문에 멀리 있는 서비스와의 통신에는 지연 하한이 있습니다. 왕복 50ms가 필요한 순차 호출 20개는 다른 비용을 빼도 약 1초가 됩니다. 병렬화·batching·캐시·데이터와 컴퓨팅의 근접 배치로 왕복을 줄일 수 있습니다. 하지만 병렬화는 상대 시스템에 순간 부하를 늘릴 수 있고 batch는 응답을 모으는 대기 시간을 추가합니다.

PERF04-BP01~07은 네트워크 영향 이해, 기능 평가, 전용 연결/VPN 선택, LB, 프로토콜, 위치, 지표 기반 조정입니다. Direct Connect의 일정한 경로 특성, VPN 암호화와 인터넷 경로, CloudFront 캐시, Global Accelerator의 네트워크 전달을 목적에 맞게 구분합니다. 사용자와 가깝게 배치하는 것과 DB와 가깝게 배치하는 것의 이득이 다를 수 있습니다.

6. 연결·프로토콜·페이로드

HTTP 연결 재사용은 매번 TCP/TLS 연결을 만드는 비용을 줄입니다. HTTP/2 등의 다중화는 여러 요청의 전송 패턴을 바꾸지만 애플리케이션 병목을 자동 제거하지는 않습니다. 클라이언트·프록시·LB·서버가 실제로 어떤 프로토콜을 사용하는지 확인해야 합니다. 커넥션 풀을 너무 작게 잡으면 대기하고, 너무 크게 잡으면 상대 한도와 자원을 압박합니다.

압축은 대역폭을 줄이지만 CPU를 사용하고 작은 응답에서는 이점이 작을 수 있습니다. MTU·패킷 손실·재전송·DNS 지연·TLS handshake도 측정 대상입니다. jumbo frame은 경로 전체가 지원해야 하며 일부 구간 불일치가 있으면 기대와 다른 동작이 생길 수 있습니다. 단일 서버에서 잘 된 설정을 인터넷 전체 경로에 그대로 적용하지 않습니다.

7. 보안·신뢰성과의 트레이드오프

모든 계층을 같은 AZ에 두면 일부 교차 AZ 지연·비용을 줄일 수 있지만 장애 격리가 약해집니다. 검사를 줄이면 지연이 줄 수 있지만 필요한 보안을 포기해서는 안 됩니다. 먼저 최소 보안·가용성 목표를 정하고 그 안에서 성능을 최적화합니다. CDN 캐시 키를 단순화해 적중률을 높일 때 사용자별 응답이 섞이지 않는지도 확인합니다.

8. 가상 사례와 검증 절차

API 한 건이 상품 100개를 순차 조회하고 각 호출 왕복이 10ms였다면 네트워크 대기만 약 1초입니다. 서버 크기 변경보다 일괄 조회나 필요한 데이터 사전 집계가 효과적일 수 있습니다. 그러나 일괄 응답이 지나치게 커지면 메모리·직렬화·timeout 문제가 생기므로 적절한 batch 크기를 측정합니다.

실험은 baseline을 잡고 쿼리 수·응답 바이트·DB 읽은 행·연결 대기·p99를 기록한 뒤 한 변수를 바꿉니다. 목표 지연을 만족했더라도 CPU와 비용이 크게 증가하지 않았는지 확인합니다. 캐시가 따뜻한 상태와 비어 있는 상태를 모두 봐야 운영 배포 직후의 성능을 예상할 수 있습니다.

9. 상세 면접 Q&A

Q. DB가 느리면 인스턴스를 키우면 되나요?

실행 계획·락·연결 대기·I/O·데이터 접근량부터 확인합니다. 잘못된 쿼리 구조는 큰 인스턴스에서도 비효율적일 수 있습니다. 자원 증설은 측정된 병목과 업무 목표를 기준으로 선택하고 쿼리 개선과 비교합니다.

Q. 캐시 적중률 99%면 안전한가요?

남은 1%가 피크에서 DB 용량을 넘을 수 있고, 캐시 장애 때 100%가 원본으로 향할 수 있습니다. 적중률뿐 아니라 절대 요청량·원본 처리량·장애 시 제한·재가열 속도를 확인해야 합니다.

Q. 네트워크 대역폭이 충분한데 왜 느린가요?

대역폭은 한 번에 얼마나 운반하는지, 지연은 왕복에 얼마나 걸리는지입니다. 작은 요청을 순차로 많이 보내면 대역폭은 남아도 지연이 누적됩니다. 패킷 손실·연결 수립·DNS·애플리케이션 대기도 분리해 측정합니다.

Q. 같은 AZ에 모으면 성능상 최선인가요?

일부 통신 지연과 비용은 줄 수 있지만 AZ 장애의 공통 영향을 키웁니다. 요구하는 가용성과 데이터 손실 목표를 먼저 만족해야 합니다. 성능 최적화는 다른 필수 목표를 무시하는 선택이 아닙니다.

깊이 읽기: 데이터를 덜 읽고 덜 옮기는 것이 빠른 이유

서버를 키우기 전에 읽은 양부터 줄이기

도서관에서 책 한 권을 찾으려고 모든 책장을 순서대로 훑는 일과 색인으로 위치를 찾는 일을 비교해 보세요. 인덱스는 필요한 후보를 줄이는 데 도움을 주지만 저장 공간과 쓰기 유지 비용을 가져옵니다. 쿼리에 맞지 않는 인덱스는 기대만큼 도움을 주지 못합니다. 반환한 행 수가 적더라도 검사한 행 수가 많으면 비용이 클 수 있습니다.

애플리케이션에서도 필요하지 않은 열과 큰 JSON·이미지·중복 데이터를 매번 가져오면 DB와 네트워크·직렬화 비용이 함께 증가합니다. 한 요청을 더 빠르게 만드는 방법은 더 강한 CPU뿐 아니라 불필요한 작업 자체를 제거하는 것입니다. 다만 데이터 크기를 줄이는 변경이 사용자 기능이나 검증 정보를 잃지 않는지 확인합니다.

N+1을 왕복 횟수로 이해하기

주문 목록 한 번을 읽은 뒤 각 주문의 상품을 따로 100번 조회한다고 합시다. 개별 쿼리가 빠르더라도 네트워크 왕복과 DB 실행 준비가 누적됩니다. 가상으로 각 순차 호출의 왕복만 5ms라면 100회에 500ms가 들 수 있습니다. 배치 조회나 적절한 join·fetch 전략으로 왕복을 줄이는 선택을 검토합니다.

무조건 한 SQL로 합치면 된다는 뜻은 아닙니다. 큰 join이 중복 행을 폭발시키거나 pagination 의미를 바꿀 수 있습니다. 데이터를 어떤 크기로 읽고 조립할지, 필요한 열·행과 인덱스, 실행 계획을 함께 봅니다. 최적화는 호출 횟수 하나가 아니라 전체 작업량을 줄이는 방향이어야 합니다.

캐시를 시간차가 있는 복사본으로 이해하기

캐시는 원본과 별도로 보관한 복사본입니다. 복사본이 있다는 사실은 언제 갱신하고 언제 버리고 장애 때 무엇을 줄지 결정해야 한다는 뜻입니다. 상품 소개는 잠시 오래된 값을 허용할 수 있지만 결제 가능 잔액이나 재고 확정 판단은 같은 계약으로 처리하면 위험합니다. 캐시 적용 단위를 API와 데이터의 의미에 맞춥니다.

TTL을 짧게 하면 최신성에 유리하지만 원본 조회가 늘고, 길게 하면 원본 부하가 줄지만 오래된 값의 위험이 커집니다. TTL 만료 순간의 동시 요청, 존재하지 않는 키 반복 조회, 인기 키 하나에 집중되는 요청을 각각 생각합니다. 만료 시간 분산, 요청 합치기, 제한된 negative caching 같은 방법은 서로 다른 문제를 겨냥합니다. 실제 최신성 요구와 실패 처리를 먼저 정합니다.

네트워크 성능은 대역폭만이 아니다

대역폭은 단위 시간에 옮길 수 있는 양, 지연은 왕복에 걸리는 시간입니다. 넓은 고속도로도 목적지가 멀면 첫 도착은 늦습니다. 작은 요청을 순차로 많이 보내는 작업은 대역폭보다 왕복 지연이 중요할 수 있고, 대용량 파일 전송은 대역폭·병렬성·읽기 쓰기 속도가 중요할 수 있습니다.

연결을 매번 새로 만들면 DNS·TCP·TLS 같은 준비 비용이 반복될 수 있습니다. 연결 재사용은 이를 줄일 수 있지만 오래된 연결, idle timeout, 풀 크기, 장애 후 재연결을 관리해야 합니다. 압축은 전송 바이트를 줄이되 CPU 비용을 쓰고, 이미 압축된 자료는 효과가 작을 수 있습니다. 모든 요청에 같은 최적화를 적용하지 않습니다.

위치를 가까이 두되 장애 경계는 유지하기

앱과 DB를 가까이 두면 지연·전송 경로가 유리할 수 있습니다. 하지만 모든 복제본을 같은 장애 범위에 모으면 신뢰성을 해칠 수 있습니다. 성능만 보고 다중 AZ 구성을 제거하는 것은 요구 자체를 바꾸는 선택일 수 있습니다. 지연 목표와 장애 목표를 함께 만족하는 위치·복제·읽기 경로를 설계합니다.

더 깊은 면접 Q&A: 빠름과 정확성을 함께 유지하기

Q. 캐시 적중률 99%면 잘 설계된 것인가요?

답변: 적중률만으로는 데이터 정확성과 실제 지연·비용을 알 수 없습니다. 중요하지 않은 작은 요청만 적중하고 비싼 요청은 계속 miss일 수 있고, 오래된 값이 많이 적중할 수도 있습니다.

평가: 요청 유형별 적중률, 원본 부하 감소, 사용자 지연, 낡은 데이터 허용 범위, 장애 시 동작을 함께 봅니다. 캐시가 업무 계약을 만족하는지가 먼저입니다.

Q. 압축은 네트워크 비용을 줄이니 항상 켜야 하나요?

답변: 압축·해제 CPU와 지연, 데이터의 압축 가능성, 작은 payload의 오버헤드를 비교해야 합니다. JPEG 같은 이미 압축된 데이터는 추가 이점이 작을 수 있습니다.

실험: 같은 데이터에서 전송 바이트와 전체 응답 시간, CPU·비용을 측정합니다. 전송량만 줄고 CPU 포화로 지연이 늘었다면 요구에 맞는 개선이 아닐 수 있습니다.

Q. 읽기 replica를 사용자와 가까운 리전에 두면 끝인가요?

답변: 읽기 지연은 줄일 수 있지만 복제 지연과 최신성, 쓰기 위치, 리전 간 전송·복구를 검토해야 합니다. 사용자에게 가까워도 방금 쓴 정보가 아직 없으면 업무 문제가 생길 수 있습니다.

선택: 읽기 종류별로 허용하는 지연된 데이터 범위를 정하고 중요한 직후 조회는 다른 경로를 사용할 수 있습니다. 거리 최적화와 일관성 설계를 분리해서 설명합니다.

Q. DB 쿼리가 10ms인데 API는 왜 1초인가요?

답변: 연결 풀 대기, 여러 쿼리의 합, 외부 호출, 결과 변환, 직렬화, 큐 대기, 네트워크 전송이 더해질 수 있습니다. 한 SQL 실행 시간은 전체 요청 시간의 일부입니다.

조사: 요청 전체 trace를 단계별로 나누고 측정 시작·끝이 어디인지 확인합니다. DB 서버가 기록한 실행 시간과 애플리케이션이 느낀 호출 시간도 다를 수 있습니다.

직접 풀어 보기: 순차 호출 백 번과 큰 호출 한 번

상품 100개의 정보를 원격 서비스에서 가져옵니다. 현재는 순차로 100번 호출하고 각 왕복은 10ms입니다. 한 번에 묶는 API를 만들면 항상 100배 빨라질까요?

해설 펼치기 — 판단 과정과 조건을 바꾼 경우

줄일 수 있는 부분: 순차 왕복 시간만 단순 합산하면 1초입니다. 묶음 호출은 연결·왕복·요청 준비의 반복을 줄일 수 있습니다. 하지만 서버의 조회·계산과 데이터 전송은 여전히 필요합니다.

새 비용: 큰 payload, 메모리 사용, 한 항목 실패의 처리, timeout과 최대 요청 크기를 고려합니다. 너무 큰 배치보다 제한된 크기의 여러 배치가 적합할 수도 있습니다.

비교: 순차·제한 병렬·배치 방식의 전체 지연과 원격 서버 부하를 같은 입력에서 측정합니다. 무제한 병렬화는 상대 서비스를 과부하시키고 우리 연결 풀도 소모할 수 있습니다.

조건 변경: 각 다음 요청이 이전 결과에 의존한다면 단순 배치가 불가능할 수 있습니다. 데이터 의존성과 업무 의미를 먼저 확인해야 올바른 최적화입니다.
