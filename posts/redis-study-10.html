Sentinel 장애 전환과 운영 API

장애 감지부터 클라이언트 재연결까지 따라가며 Sentinel 조회·변경 API를 안전하게 구분한다.

첨부 Redis 학습 자료의 주제를 쉬운 설명과 공식 문서 근거로 재구성했습니다. 명령·설정의 버전 조건은 본문을 확인하세요. 장애 시나리오와 수치는 별도 표시가 없으면 학습용 가정이며, 코드가 실려 있다는 사실만으로 실행 검증을 의미하지 않습니다. 검증 범위와 남은 한계

실행 검증 기록: 로컬 Sentinel 통합 시험은 Redis 7.2.5에서 정상 primary 종료 뒤 자동 승격, 이전 primary의 replica 재편입, 한 Sentinel의 발견 전용 계정에 대한 조회 허용·강제 전환 거부를 확인했다. 실제 호스트·네트워크 분할·전원 장애·Spring 클라이언트 재연결은 이 시험의 범위에 포함하지 않았다. Java 예제 검사는 본문의 완전한 클래스와 소스 파일 일치, 컴파일 및 독립 main 실행 범위를 따로 기록한다.

처음 이해할 바탕. 감지했다는 말과 복구됐다는 말 사이에는 일이 많다

자동 장애 전환을 처음 배우면 “원본이 죽으면 복제본이 원본이 된다”라고 외우기 쉽다. 틀린 출발점은 아니지만 그 사이의 판단과 작업을 생략한 문장이다. 실제로는 누군가 이상을 관찰하고, 다른 감시자의 의견을 확인하고, 전환할 권한을 얻고, 후보를 선택하고, 역할을 바꾸고, 클라이언트가 새 주소에 연결해야 한다. 이 과정의 여러 지점에서 시간이 걸리거나 실패할 수 있다.

식당의 주문 접수 담당자가 자리를 비운 상황을 생각해 보자. 동료 한 명이 “연락이 안 된다”고 말한 것은 첫 관찰이다. 관리자들이 대체 담당자를 정하는 것은 다른 일이다. 새 담당자가 업무를 시작하는 것과 손님들이 새 창구를 찾아오는 것도 다르다. Sentinel에서 감지·승인·승격·발견·서비스 회복을 구별하는 이유가 여기에 있다.

각 단계는 운영 지표의 질문을 만든다. SDOWN은 어떤 감시자가 무엇을 보았는가를 묻게 한다. ODOWN은 필요한 공동 판단이 이루어졌는가를 묻게 한다. 역할 변경은 어떤 데이터 노드가 쓰기를 맡았는가를 묻게 한다. 첫 성공 요청은 애플리케이션이 실제로 그 노드에 도착했는가를 보여 준다. 이름이 다른 사건을 하나의 완료 시각으로 합치지 않는다.

이 구별이 있으면 장애가 오래 지속될 때 조사 방향도 달라진다. 서버 승격은 빨리 끝났는데 클라이언트가 예전 주소를 계속 사용했을 수 있다. 주소 발견은 성공했는데 인증이나 네트워크 때문에 새 연결이 실패했을 수도 있다. 서버 설정 하나를 바꾸기 전에 어느 단계가 길었는지 확인하는 것이 먼저다.

1. 장애 전환은 한 번의 명령이 아니라 상태 변화다

출고 조회 서비스에서 primary 연결이 끊겼다고 가정하자. Sentinel 하나가 즉시 새 서버를 만드는 것이 아니다. 각 Sentinel이 일정 시간 유효한 응답을 받지 못하면 SDOWN을 표시하고, 충분한 감시자가 primary 장애에 동의하면 ODOWN에 도달한다. 이후 한 Sentinel이 해당 전환을 실행할 권한을 얻고, 적절한 replica를 고르고, 승격 명령을 보내고, 실제 역할 변경을 확인한다. 다른 replica의 복제 대상과 클라이언트 경로도 따라 바뀌어야 한다.

SDOWN은 한 감시자의 주관적 장애 판단이고 ODOWN은 정족수 기반의 primary 장애 판단이다. 이 장에서는 먼저 흐름의 단계로 이해하고, 구체적인 판정과 선출 규칙은 11~12장에서 다룬다. 중요한 점은 감지, 승인, 승격, 전파, 애플리케이션 복구가 같은 시각에 끝나지 않는다는 것이다. down-after-milliseconds를 5초로 설정했다고 고객 오류가 정확히 5초만 지속된다고 약속할 수 없다.

2. 먼저 읽기 전용 운영 API로 현황을 파악한다

SENTINEL MASTERS는 감시 중인 논리 primary 그룹들을 보여 준다. SENTINEL MASTER 이름은 한 그룹의 상세 상태를 보여 준다. SENTINEL REPLICAS 이름은 발견한 replica, SENTINEL SENTINELS 이름은 다른 감시자, SENTINEL GET-MASTER-ADDR-BY-NAME 이름은 현재 primary 주소를 보여 준다. 운영 대시보드에 모든 출력을 무작정 저장하기보다 주소·역할·플래그·quorum·알려진 감시자 수·최근 응답 시각처럼 질문에 답하는 필드를 선택한다.

redis-cli -p 26379 SENTINEL MASTERS
redis-cli -p 26379 SENTINEL MASTER logistics-main
redis-cli -p 26379 SENTINEL CKQUORUM logistics-main
redis-cli -p 26380 SENTINEL GET-MASTER-ADDR-BY-NAME logistics-main
redis-cli -p 26381 SENTINEL GET-MASTER-ADDR-BY-NAME logistics-main

같은 논리 이름을 모든 곳에서 정확히 사용해야 한다. 이름은 DNS 이름이나 Redis의 임의 키가 아니라 Sentinel이 감시 그룹을 식별하는 서비스 이름이다. 클라이언트가 다른 이름을 질의하면 주소를 얻지 못한다. 주소 결과를 영구 캐시하지도 않는다. 장애 전환 이후 기존 주소는 replica가 될 수 있기 때문이다. Sentinel 지원 클라이언트는 접속 실패와 역할 변경을 감지하고 현재 primary를 다시 찾아야 한다.

3. 장애 전환 실습: 사라진 포트보다 바뀐 역할을 관찰한다

공통 토대 실습에서 최초 primary가 6379임을 실제 조회로 확인한 뒤, 테스트 데이터만 있는 그 프로세스를 정상 종료한다. 이 실험은 abrupt crash가 아니라 정상 종료 실험이다. 영속성을 꺼 두었으므로 데이터를 보존하는 테스트가 아니다.

redis-cli -p 6379 SET shipment:S100:status READY
redis-cli -p 6380 GET shipment:S100:status
# 반드시 현재 primary가 6379이고 일회용 인스턴스인지 확인한 뒤 실행한다.
redis-cli -p 6379 SHUTDOWN NOSAVE
# 다른 터미널에서 로그를 관찰한다.
tail -f "$LAB/26379/sentinel.log"
# 시간이 지난 후 각 Sentinel에서 다시 조회한다.
redis-cli -p 26379 SENTINEL GET-MASTER-ADDR-BY-NAME logistics-main

예상 관찰은 6380 또는 6381 가운데 적절한 후보가 primary로 바뀌고, Sentinel이 새 주소를 반환하는 것이다. 어느 포트가 선택된다고 고정해서 기대하지 않는다. 우선순위·복제 진행도·후보 상태가 선택에 영향을 준다. 로그에는 +sdown, +odown, 선출·승격 관련 이벤트, +switch-master 같은 전환 흔적이 나타날 수 있다. 이벤트 이름과 세부 순서는 버전과 경로에 따라 다를 수 있으므로 로그 한 줄만으로 완료를 판정하지 않는다.

새 주소에 ROLE과 읽기·쓰기를 실행해 역할과 애플리케이션 경로를 확인한다. 종료했던 6379를 동일 설정으로 다시 시작하면 Sentinel이 현재 논리 구성을 적용해 새 primary의 replica로 재구성하는지 관찰한다. 이때 과거 primary라는 이유로 자동으로 주도권을 되찾는 것이 아니다. 재시작과 재동기화 동안 서비스 지연과 네트워크 사용량도 기록한다.

4. 조회 API와 변경 API를 섞지 않는다

SENTINEL SET은 감시 그룹의 런타임 설정을 바꾸는 명령이고 SENTINEL CONFIG SET은 지원되는 전역 설정을 바꾸는 경로다. 적용 범위와 지원 버전이 다르므로 명령 도움말과 운영 버전을 확인한다. 한 Sentinel에서 바꾼 임의의 정책 설정이 모든 Sentinel에 자동으로 배포된다고 가정해서는 안 된다. 필요한 변경을 각 인스턴스에 적용하고 다시 조회해 일치 여부를 확인한다. 구성 전파와 정책 설정 배포는 같은 의미가 아니다.

SENTINEL MONITOR, REMOVE, RESET, FAILOVER는 상태를 바꾸므로 별도의 작업 승인과 롤백 계획이 필요하다. 특히 SENTINEL FAILOVER 이름은 운영자가 강제 전환을 요청하는 API이며 정상 자동 장애 판단·과반 동의 경로와 같은 시험이라고 보면 안 된다. 자동 장애 전환이 안 되는 원인을 숨기기 위해 먼저 이 명령을 쓰면, 정작 quorum 문제나 감시자 통신 문제를 검증하지 못한다. 또한 이 명령을 Cluster의 CLUSTER FAILOVER와 동일한 안전한 동기화 절차로 이해해서도 안 된다.

5. Pub/Sub 이벤트와 운영 자동화의 경계

Sentinel 이벤트를 구독하면 역할 변경을 운영 채널이나 모니터링 시스템에 전달할 수 있다. 그러나 Pub/Sub은 구독자가 연결되지 않았던 동안의 메시지를 자동으로 보관하고 재전달하는 영속 로그가 아니다. 이벤트는 신속한 알림 신호로 사용하고, 정기적인 상태 조회를 함께 사용해 현재 사실을 확정한다. “switch-master 알림을 못 받았으니 전환은 없었다”는 결론은 틀릴 수 있다.

외부 스크립트는 실패해도 Sentinel 본체와 별도로 조사한다. 알림 웹훅의 timeout을 Redis 데이터 장애와 혼동하지 않는다. 스크립트가 다시 실행될 수 있음을 고려해 멱등하게 작성하고 비밀 값이 인자나 로그에 노출되지 않게 한다. 애플리케이션은 알림을 받아 내부 주소를 직접 덮어쓰는 임시 구현보다, 검증된 Sentinel 지원 클라이언트의 발견·재연결 기능을 활용하는 편이 안전하다.

실습 공통 토대: 감시망과 데이터망을 따로 확인하기

이 절은 09~12장을 각각 독립적으로 읽어도 실습 전제를 놓치지 않도록 제공하는 복습이다. Sentinel은 데이터를 저장하는 Redis의 다른 이름이 아니다. 데이터 Redis는 주문 상태를 읽고 쓰는 데이터 평면이고, Sentinel은 현재 쓰기를 받을 주 서버를 알려 주고 장애 전환을 조정하는 제어 평면이다. 운영자는 두 평면의 정상 여부를 각각 확인해야 한다. 감시가 정상이어도 Redis의 디스크가 가득 찰 수 있고, 데이터 읽기가 정상이어도 Sentinel 사이의 연결이 끊어져 다음 장애를 처리하지 못할 수 있다.

물류센터에 비유하면 Redis primary는 출고 장부를 수정하는 현재 담당자, replica는 그 장부를 받아 적는 대기 담당자, Sentinel은 담당자 교체를 결정하는 관리위원이다. 장부 복사는 비동기다. 원 담당자가 출고 승인 도장을 찍은 순간 대기 담당자가 마지막 줄까지 받아 적었다는 뜻은 아니다. 관리위원 세 명이 교체에 동의해도 복사되지 않은 장부 한 줄을 복원할 수는 없다. 이 비유의 한계도 분명하다. Redis는 사람처럼 빠진 주문의 의미를 추론하거나 장부 두 권을 자동 병합하지 않는다. 어느 서버를 기준으로 삼을지 결정하고 나면 이전 서버는 새 기준의 데이터를 복제하게 된다.

격리된 실습 환경 만들기

아래는 로컬의 일회용 테스트 환경을 만드는 예제다. 이 교재에서 실행한 결과가 아니며 명령 뒤의 관찰 설명은 예상되는 관찰이다. 이미 같은 포트를 쓰는 서비스가 있으면 중단하고 빈 포트로 바꾼다. 인증을 생략하는 이유는 오직 loopback 실습의 복잡도를 낮추기 위해서다. 공유 호스트, 외부 공개 VM, 운영 서버에서는 그대로 사용하지 않는다. 방화벽으로 외부 접근을 차단하고 로컬 사용자에게도 민감한 데이터가 없는 환경을 쓴다. 운영 도입에는 인증, TLS, 비밀 관리, 독립 장애 도메인 배치가 추가로 필요하다.

# 필요한 프로그램이 설치되어 있는지와 실제 버전을 먼저 기록한다.
redis-server --version
redis-cli --version
LAB=$(mktemp -d /tmp/redis-sentinel-study.XXXXXX)
printf '%s\n' "$LAB"

for p in 6379 6380 6381; do
  mkdir -p "$LAB/$p"
  cat > "$LAB/$p/redis.conf" <<EOF
port $p
bind 127.0.0.1
protected-mode yes
dir $LAB/$p
pidfile $LAB/$p/redis.pid
logfile $LAB/$p/redis.log
daemonize yes
save ""
appendonly no
EOF
  if [ "$p" != 6379 ]; then
    printf 'replicaof 127.0.0.1 6379\n' >> "$LAB/$p/redis.conf"
  fi
  redis-server "$LAB/$p/redis.conf"
done

for p in 26379 26380 26381; do
  mkdir -p "$LAB/$p"
  cat > "$LAB/$p/sentinel.conf" <<EOF
port $p
bind 127.0.0.1
protected-mode yes
dir $LAB/$p
pidfile $LAB/$p/sentinel.pid
logfile $LAB/$p/sentinel.log
daemonize yes
sentinel monitor logistics-main 127.0.0.1 6379 2
sentinel down-after-milliseconds logistics-main 5000
sentinel failover-timeout logistics-main 60000
sentinel parallel-syncs logistics-main 1
EOF
  redis-server "$LAB/$p/sentinel.conf" --sentinel
done

여기서 save ""와 appendonly no는 실습을 단순화하기 위한 영속성 비활성화다. 재시작하면 데이터가 남는다고 기대하지 않는다. 운영에 이 설정을 복사해서는 안 된다. 세 Redis와 세 Sentinel이 한 컴퓨터에서 실행되므로 프로토콜은 관찰할 수 있지만 실제 고가용성은 제공하지 않는다. 컴퓨터 하나가 멈추면 여섯 프로세스가 동시에 사라진다. daemonize를 지원하지 않는 배포 환경이라면 각 프로세스를 별도 터미널에서 foreground로 시작하고 종료할 대상을 직접 추적한다.

정상 상태를 숫자와 관계로 기록하기

redis-cli -p 6379 INFO replication
redis-cli -p 6380 INFO replication
redis-cli -p 26379 SENTINEL MASTER logistics-main
redis-cli -p 26379 SENTINEL REPLICAS logistics-main
redis-cli -p 26379 SENTINEL SENTINELS logistics-main
redis-cli -p 26379 SENTINEL CKQUORUM logistics-main
redis-cli -p 26379 SENTINEL GET-MASTER-ADDR-BY-NAME logistics-main

처음에는 6379가 master이고 다른 두 인스턴스가 그 서버를 복제하는 관계가 예상된다. 일부 출력 필드에는 호환성 때문에 과거 용어 slave가 남아 있다. 단어보다 역할과 연결 대상 주소를 읽는다. master_link_status:up은 복제 링크가 연결되었다는 뜻이지 데이터 유실 가능성이 없다는 증명은 아니다. SENTINEL SENTINELS는 요청받은 Sentinel 자신을 제외한 다른 감시자를 보여 주므로 정상적인 세 감시자 구성에서 목록의 두 항목을 보고 한 대가 사라졌다고 오해하지 않는다.

CKQUORUM은 현재 관점에서 장애 판단 정족수와 장애 전환 승인을 받을 수 있는지 검사하는 운영 진단이다. 이 결과가 정상이라고 미래의 복제 지연, 데이터 노드 장애, 클라이언트의 재연결 실패까지 검증되지는 않는다. 따라서 관찰 기록에는 Sentinel 응답만 쓰지 말고 Redis 역할, replica 연결, 애플리케이션 성공률을 함께 적는다. 서로 다른 Sentinel에 같은 조회를 반복해 인식이 일치하는지도 비교한다. 발견 정보가 전파되는 동안 짧은 차이가 있을 수 있으므로 한 번의 서로 다른 응답만으로 영구 분할을 선언하지 않는다.

실습을 마친 뒤의 정리

실습 전 포트가 비어 있었고 이 절에서만 생성한 인스턴스라는 것을 확인한 뒤, 테스트 데이터가 필요 없을 때만 각 포트를 종료한다. killall redis-server처럼 호스트의 모든 Redis를 종료하는 명령은 쓰지 않는다. 아래 종료 명령도 운영 포트에 그대로 실행하면 장애를 만들므로 현재 실습 대상임을 다시 확인한다.

# 일회용 실습 인스턴스만 대상으로 한다.
for p in 26379 26380 26381 6379 6380 6381; do
  redis-cli -h 127.0.0.1 -p "$p" SHUTDOWN NOSAVE
done
# 로그 분석이 끝날 때까지 $LAB 디렉터리는 보존한다.

종료 도중 연결이 닫혔다는 메시지는 종료 요청이 수락된 상황에서도 보일 수 있다. 프로세스와 포트 상태로 후속 확인한다. 로그에는 실제 주소와 운영 정보가 남으므로 공유 전에 확인한다. 이 실습의 목적은 명령을 외우는 것이 아니라, 설정 → 발견 → 판단 → 승인 → 승격 → 재연결을 서로 다른 증거로 확인하는 습관을 만드는 것이다.

실행 추적 워크숍: 주문 조회 요청 하나를 끝까지 따라가기

요청 lookup-827이 배송 상태를 읽는 중 primary 연결이 끊겼다고 하자. 로그에 연결 예외가 나타난 시각과 Sentinel의 SDOWN 시각을 같은 것으로 취급하지 않는다. 애플리케이션의 timeout이 더 짧으면 고객은 먼저 오류를 경험한다. 반대로 연결 풀에 남은 연결이 잠시 살아 있어 일부 요청은 성공할 수도 있다. 측정할 대상은 평균 응답 시간이 아니라 시간대별 성공률과 오류 종류다.

상대 시점 Sentinel 관찰 클라이언트 관찰 해석
T0 아직 기존 primary를 가리킴 한 요청에서 timeout 명령 미실행 여부는 모름
T1 한 감시자의 SDOWN 기존 연결 반복 실패 국소 감지 단계
T2 ODOWN·선출 시도 새 연결도 실패할 수 있음 판단과 전환 수행이 진행 중
T3 후보 승격을 INFO로 확인 일부 클라이언트가 새 주소 발견 서버 전환과 클라이언트 전환이 겹침
T4 새 주소 인식이 수렴 새 연결의 조회 성공 서비스 회복 증거 확보
T5 나머지 replica 재구성 정상 성공률 유지 보호 수준 복구 확인

표의 시간은 실측 결과가 아니라 순서를 설명하는 논리 시점이다. 실제 로그에서는 네트워크 지연 때문에 순서가 엇갈려 보일 수 있고, 서로 다른 호스트의 시계 차이도 있다. 로그에는 wall clock과 함께 요청 경과 시간을 기록하고, correlation ID로 애플리케이션 요청을 묶는다. 전환 전체를 한 스톱워치 숫자로만 표현하면 어느 단계가 느렸는지 알 수 없다.

재연결 상태를 애플리케이션 코드로 생각하기

// 라이브러리 구현을 대체하는 코드가 아닌 장애 처리 상태 모델이다.
enum RedisPathState {
    CONNECTED, REQUEST_UNCERTAIN, DISCOVERING,
    VERIFYING_ROLE, RECONNECTING, RECOVERED, DEADLINE_EXCEEDED
}

REQUEST_UNCERTAIN은 중요하다. 쓰기 명령을 보낸 뒤 연결이 끊겼다면 “실패했으니 다시 쓰자”가 아니라 “적용됐는지 모른다”는 상태를 먼저 표현한다. 읽기 요청은 같은 조건으로 재시도하기가 상대적으로 쉽지만, 출고 수량 INCR는 재실행할 때 한 번 더 증가할 수 있다. 업무 요청 ID로 원장 결과를 조회하거나 멱등하게 처리 가능한 형태로 바꿔야 한다. 연결 회복 로직과 업무 재실행 로직을 같은 catch 블록에 숨기지 않는다.

Sentinel 지원 클라이언트는 알려진 Sentinel에서 현재 primary를 다시 발견하고, 연결한 서버의 역할이 기대한 것인지 확인하는 절차를 가져야 한다. 특정 Sentinel 하나가 안 된다고 전체 발견을 즉시 실패시키기보다 다른 seed를 시도할 수 있어야 한다. 반대로 오래된 주소를 무제한 반복해서 붙잡으면 새 primary가 정상이어도 업무는 회복되지 않는다. 실제 라이브러리의 timeout·재연결·풀 재생성 동작은 사용하는 버전으로 테스트한다.

운영 API 출력에서 다음 행동을 고르기

CKQUORUM이 실패하고 replica는 정상이라면 먼저 감시자 통신과 멤버십 인식을 조사한다. 이때 replica를 강제로 승격하는 명령부터 실행하면 원인을 숨기고 이중 쓰기 위험을 만들 수 있다. CKQUORUM은 정상인데 후보 선택이 실패한다면 후보의 SDOWN·연결 단절 시간·priority·인증을 조사한다. 새 주소가 반환되지만 애플리케이션만 실패한다면 ACL·광고 주소·네트워크·클라이언트 모드를 조사한다. 같은 “전환 실패”라도 다음 명령이 달라진다.

운영자가 SENTINEL FAILOVER를 실행했다면 작업 기록에 반드시 수동 강제 요청이라고 적는다. 이 명령은 다른 Sentinel의 정상 자동 합의를 동일하게 거치는 시험이 아니다. 자동 전환 시험의 성공 횟수에 섞지 않는다. 기존 primary가 살아 있는 상태에서 일으킨 강제 Sentinel 전환을 정상 협력형 Cluster 전환과 동일한 무손실 유지보수 방식으로 설명해서도 안 된다.

감시자 수를 바꾸는 작업의 완료 조건

새 Sentinel을 추가할 때는 현재 primary를 가리키는 초기 설정으로 시작하고 다른 Sentinel들이 그 존재를 발견한 뒤 다음 추가를 진행한다. 제거할 때는 단순히 프로세스를 끄는 일과 남은 감시자의 알려진 멤버십을 정리하는 일을 구분한다. 오래된 replica나 감시자 정보를 자동으로 즉시 잊을 것이라 기대하지 않는다. RESET 같은 상태 변경 명령은 발견 정보를 지우고 다시 채우게 할 수 있으므로 현재 인식과 복구 절차를 확인한 뒤 한 인스턴스씩 수행한다.

완료 선언에는 세 증거가 필요하다. 첫째, 여러 Sentinel의 현재 primary 조회가 같은 역할 변경을 반영한다. 둘째, 애플리케이션이 새 경로에서 실제 명령을 성공시킨다. 셋째, 의도한 replica 수가 새 primary를 정상 복제한다. 첫 번째만 충족하면 제어 평면은 회복했지만 고객 경로는 미확인이고, 두 번째만 충족하면 다음 장애를 버틸 보호 수준이 부족할 수 있다.

상태 변화 해설. 로그 한 줄씩을 어느 단계의 증거로 읽을까

Sentinel 로그에는 상태 변화와 시도, 결과를 나타내는 여러 이벤트가 남을 수 있다. 초보자에게는 많은 기호가 한꺼번에 보여 어렵다. 우선 이벤트 이름을 모두 외우기보다 관찰·판단·실행·확인·안내라는 종류로 묶어 보자. 같은 실패에도 어느 지점까지 갔는지 구별할 수 있으면 충분한 출발이다.

종류 이 단계의 질문 증거의 예 이것만으로 완료라 할 수 없는 것
관찰 유효 응답이 사라졌는가? 특정 Sentinel의 SDOWN·응답 기록 공동 판단과 승격
판단 장애 판단·수행 권한이 충족됐는가? ODOWN·선출 관련 로그 적격 후보의 실제 승격
실행 후보에 역할 변경을 요청했는가? 후보 선택·전환 시도 요청이 적용됐는가
확인 새 노드가 primary로 동작하는가? INFO·ROLE·전환 상태 애플리케이션의 새 연결
안내·서비스 새 주소를 발견하고 요청이 성공하는가? 주소 질의·클라이언트 로그·업무 결과 복제 여유와 모든 기능의 정상

특정 이벤트의 세부 순서와 이름은 버전과 경로에 따라 확인한다. 여기서 중요한 습관은 한 줄의 로그를 전체 시스템의 최종 상태로 확대하지 않는 것이다. switch-master를 보았더라도 다른 replica의 재구성이 끝나지 않았을 수 있다. 사용자 요청이 성공해도 원하는 복제 대수가 다시 확보됐는지는 별도로 본다.

같은 사건을 여러 Sentinel이 서로 다른 시점에 기록할 수도 있다. 로그를 모을 때 호스트와 프로세스, 감시 그룹, 시각을 함께 보관해야 한다. 한 파일의 마지막 줄만 보고 모든 감시자가 같은 상태라고 생각하지 않는다. 시계가 어긋나면 단순 시간 정렬에도 오차가 생기므로 이벤트의 원인과 결과 관계도 함께 읽는다.

시간 예산 해설. down-after를 줄인 만큼 RTO가 줄어들까

down-after-milliseconds는 감시자의 유효 응답 관찰과 관련된 입력이다. 전체 복구 시간을 직접 지정하는 값은 아니다. 감지 뒤 승인과 후보 선택, 역할 변경, 발견과 재연결이 필요하다. 그중 어느 단계가 병목인지 모른 채 감지 시간만 줄이면 잘못된 판단과 불필요한 전환을 늘릴 수도 있다.

다음은 설명용 시간선이다. 0초에 사용자 요청이 실패하기 시작했고, 5초에 감지 조건이 충족되고, 7초에 전환 수행 권한을 얻고, 9초에 새 primary가 확인되었다고 하자. 클라이언트는 12초에 새 주소를 찾고 14초에 첫 쓰기를 성공시켰다. 복제 여유는 30초에 회복됐다. 이 경우 5초와 9초, 14초, 30초는 모두 다른 질문의 답이다.

가상 시각 사건 줄일 시간을 찾는 관점
0초 첫 사용자 실패 실제 영향 시작을 어떻게 관측했나
5초 장애 감지 응답 기준과 관찰 간격은 어떤가
7초 수행 권한 확보 감시자 통신과 승인 조건은 충분한가
9초 primary 역할 확인 후보의 준비와 제어 명령은 정상인가
12초 클라이언트 새 주소 발견 재발견 주기와 실패 처리 경로는 어떤가
14초 첫 업무 쓰기 성공 새 연결·인증·요청 재개는 정상인가
30초 필요한 복제 여유 회복 재동기화와 자원 여유는 충분한가

실제 단계가 항상 이렇게 고정 길이로 순차 실행되는 것은 아니다. 일부 작업은 겹칠 수 있고 실패와 재시도가 추가될 수 있다. 표는 시간 구간의 의미를 나누는 모델이다. 관측한 실제 시각이 있다면 각 차이를 계산해 병목 후보를 찾고, 측정하지 못한 구간은 추정이라고 표시한다.

Java 시간선 예제. 역할 회복과 사용자 회복을 따로 계산하기

아래 코드는 가상 사건의 시각을 밀리초로 받아 구간을 출력한다. Sentinel 내부 타이머와 클라이언트를 실행하지 않는다. Java 21에서 독립 실행할 수 있는 계산 모델이다. 순서가 잘못된 입력을 거절해, 모순된 시간 기록으로 그럴듯한 숫자를 만드는 실수를 줄인다.

public final class SentinelFailoverTimelineLesson {
    record Timeline(long impactStart, long detected, long authorized,
                    long promoted, long discovered, long firstWrite,
                    long redundancyRestored) {
        Timeline {
            long[] times = {impactStart, detected, authorized, promoted,
                    discovered, firstWrite, redundancyRestored};
            for (int i = 0; i < times.length; i++) {
                if (times[i] < 0 || (i > 0 && times[i] < times[i - 1])) {
                    throw new IllegalArgumentException("non-monotonic teaching timeline");
                }
            }
        }
        long serverRoleRecoveryMillis() { return promoted - impactStart; }
        long userWriteRecoveryMillis() { return firstWrite - impactStart; }
        long discoveryAndReconnectMillis() { return firstWrite - promoted; }
        long redundancyGapAfterServiceMillis() { return redundancyRestored - firstWrite; }
    }

    public static void main(String[] args) {
        Timeline t = new Timeline(0, 5000, 7000, 9000, 12000, 14000, 30000);
        if (t.serverRoleRecoveryMillis() != 9000) throw new AssertionError("server");
        if (t.userWriteRecoveryMillis() != 14000) throw new AssertionError("user");
        if (t.discoveryAndReconnectMillis() != 5000) throw new AssertionError("client");
        if (t.redundancyGapAfterServiceMillis() != 16000) throw new AssertionError("replicas");
        boolean rejected = false;
        try {
            new Timeline(0, 5000, 4000, 9000, 12000, 14000, 30000);
        } catch (IllegalArgumentException expected) {
            rejected = true;
        }
        if (!rejected) throw new AssertionError("contradictory sequence accepted");
        System.out.println("server role recovery ms=" + t.serverRoleRecoveryMillis());
        System.out.println("first user write ms=" + t.userWriteRecoveryMillis());
        System.out.println("replica redundancy ms=" + t.redundancyRestored());
    }
}

이 클래스는 설명상 모든 사건이 지정한 순서로 발생한다고 가정한다. 실제 측정 도구는 분산된 시계 오차와 동시 사건, 누락된 로그도 다뤄야 한다. 따라서 계산이 통과했다고 실제 RTO를 측정한 것은 아니다. 확인한 것은 같은 시간선에서 서버 역할 회복과 사용자 쓰기 회복, 복제 여유 회복이 다른 숫자가 된다는 관계다.

특히 첫 성공 한 건이 전체 서비스 안정화를 뜻하지는 않는다. 일부 인스턴스만 새 주소를 찾았거나 특정 기능만 성공했을 수 있다. 실제 완료 기준에는 오류율과 지연, 여러 애플리케이션 인스턴스의 연결, 업무 정합성 검사가 필요할 수 있다. 그 기준을 추가하면 최종 완료 시각도 달라진다.

API 읽기 연습. 조회 결과를 질문과 연결하기

Sentinel 운영 API를 배울 때는 명령 목록을 암기하기보다 질문을 먼저 쓰는 편이 쉽다. “현재 쓰기 주소는 어디인가?”에는 GET-MASTER-ADDR-BY-NAME이 연결된다. “이 감시자가 어떤 상태로 알고 있는가?”에는 MASTER가 연결된다. “다른 감시자와 후보를 어떻게 발견했는가?”에는 SENTINELS와 REPLICAS가 연결된다. CKQUORUM은 현재 인식하는 조건에서 판단·승인에 필요한 감시자 상태를 점검하는 데 쓰인다.

조회 하나가 모든 증거를 제공하지는 않는다. 주소를 얻었다면 실제 데이터 노드의 역할과 접근 가능성을 확인해야 한다. replica 목록에 나타나도 지금 승격 가능한 후보인지 따로 봐야 한다. CKQUORUM이 성공해도 새 primary가 감당할 자원과 애플리케이션의 인증까지 검사했다고 볼 수는 없다. API의 답과 업무의 질문 사이에 빠진 조건을 적어 보자.

출력을 자동 수집할 때도 비밀이 섞일 수 있는 전체 구성을 무조건 공개하지 않는다. 필요한 상태 필드와 대상 식별자, 시각을 선택한다. 로그의 양보다 질문에 답할 수 있는 자료인지가 중요하다. 명령의 출력 순서나 사람이 보는 공백에 의존하는 임시 파서는 버전과 도구 표현 차이에도 취약할 수 있다.

클라이언트 예제. 발견한 주소가 실제 primary인지 확인하기

서비스 발견 결과는 연결할 후보를 알려 준다. 그러나 발견 직후에도 상태가 바뀔 수 있고 감시자마다 일시적으로 서로 다른 구성을 알 수 있다. 공식 클라이언트 지침은 연결한 데이터 노드의 역할 확인 같은 절차를 다룬다. 직접 구현한다면 전체 명세를 검토해야 하고, 일반 애플리케이션은 검증된 Sentinel 지원 드라이버를 사용하는 편이 이해하기 쉽다.

아래는 이미 조회와 역할 확인을 수행했다고 가정한 후보 목록에서 올바른 역할을 선택하는 교육용 모델이다. 실제 네트워크와 인증, 재연결을 구현하지 않는다. 주소를 얻은 사건과 쓰기 역할을 확인한 사건이 다르다는 관계만 검사한다.

import java.util.List;

public final class SentinelDiscoveryValidationLesson {
    enum Role { PRIMARY, REPLICA, UNKNOWN }
    record Endpoint(String host, int port) {}
    record CheckedCandidate(Endpoint endpoint, boolean reachable, Role reportedRole) {}

    static Endpoint firstVerifiedPrimary(List<CheckedCandidate> candidates) {
        return candidates.stream()
                .filter(CheckedCandidate::reachable)
                .filter(candidate -> candidate.reportedRole() == Role.PRIMARY)
                .map(CheckedCandidate::endpoint)
                .findFirst()
                .orElseThrow(() -> new IllegalStateException("no verified primary"));
    }

    public static void main(String[] args) {
        Endpoint oldAddress = new Endpoint("127.0.0.1", 16390);
        Endpoint newAddress = new Endpoint("127.0.0.1", 16391);
        List<CheckedCandidate> observed = List.of(
                new CheckedCandidate(oldAddress, true, Role.REPLICA),
                new CheckedCandidate(newAddress, true, Role.PRIMARY));
        if (!newAddress.equals(firstVerifiedPrimary(observed))) {
            throw new AssertionError("stale discovered address was trusted");
        }
        boolean rejected = false;
        try {
            firstVerifiedPrimary(List.of(
                    new CheckedCandidate(oldAddress, false, Role.PRIMARY),
                    new CheckedCandidate(newAddress, true, Role.UNKNOWN)));
        } catch (IllegalStateException expected) {
            rejected = true;
        }
        if (!rejected) throw new AssertionError("unverified role accepted");
        System.out.println("verified primary=" + firstVerifiedPrimary(observed));
        System.out.println("unreachable and unknown candidates rejected");
    }
}

보고된 역할은 관찰 시점의 정보다. 함수가 반환한 뒤 실제 쓰기를 보내기 전에 역할이 바뀔 수도 있다. 그러므로 역할 확인은 실제 명령 오류와 재발견 처리까지 없애는 보장이 아니다. 이 모델을 완성된 클라이언트 알고리즘이라고 사용하지 않는다. 연결 수명과 시간 예산, 오류 분류는 드라이버의 실제 계약을 확인해야 한다.

또한 PRIMARY라고 응답한 모든 서버 가운데 첫 번째를 고르면 분산 시스템 전체에서 정당한 서버가 보장된다는 뜻도 아니다. 후보 목록은 올바른 Sentinel 발견 경로와 감시 그룹에서 왔다고 가정했다. 출처가 임의인 서버들을 모아 역할 문자열만 비교하는 보안·리더 판단 도구가 아니다. 모델 입력의 전제를 명시하는 습관이 중요하다.

변경 API 해설. 강제 전환 시험과 자동 판단 시험은 질문이 다르다

운영자가 강제 전환을 요청해 성공했다면 후보를 승격하고 새 주소를 사용하게 하는 일부 경로를 확인할 수 있다. 그러나 원본이 응답하지 않는 상황에서 감시자들이 장애를 판단하고 필요한 승인을 얻는 경로를 같은 방식으로 검사한 것은 아니다. 자동 장애 전환 실패의 원인이 quorum이나 감시자 통신이라면 수동 요청의 성공만으로 그 원인이 해결됐다고 말할 수 없다.

시험의 이름을 목적에 맞게 붙인다. “운영자 요청에 따른 역할 전환 시험”, “primary 연결 종료 뒤 자동 판단 시험”, “클라이언트 재발견 시험”처럼 어떤 계기가 있었는지 적는다. 서로 보완할 수 있지만 대체할 수 있는 것은 아니다. 같은 포트가 primary가 되었다는 최종 모양만 비교하면 경로의 차이를 놓친다.

변경 명령은 조회 명령과 권한도 다를 수 있다. 발견만 하는 애플리케이션에 임의의 failover 권한을 줄 필요는 없다. 테스트를 편하게 하려고 광범위한 계정을 사용하면 운영의 최소 권한을 검증하지 못한다. 다음 인증 장의 허용·거부 검사와 연결해 실제 역할별 계정으로 시험한다.

Sentinel의 정책 변경도 한 감시자에서 수행했다고 모든 곳에 같은 값이 적용되는지 추측하지 않는다. 발견한 새 구성이 퍼지는 것과 운영자가 바꾼 모든 정책을 배포하는 것은 다르다. 적용 대상과 버전을 확인하고, 필요한 인스턴스에서 다시 조회해 의도한 정책이 유지되는지 확인한다.

이벤트 해설. 알림을 놓쳤을 때도 현재 상태를 알 수 있어야 한다

Pub/Sub 알림은 사건을 빠르게 알아차리는 데 유용하다. 그러나 구독하지 않았던 동안의 메시지가 자동으로 쌓여 있다가 모두 재전달되는 영속 로그로 생각하면 안 된다. 알림 처리 프로그램을 재시작하는 동안 전환이 일어났다면 이벤트를 보지 못했을 수 있다. 그래서 이벤트 부재는 전환 부재의 증거가 아니다.

모니터링은 이벤트와 상태 조회를 함께 쓸 수 있다. 이벤트를 받으면 관련 그룹의 상태를 다시 확인하고, 주기적인 조회로 놓친 변화가 있는지 점검한다. 이때 조회 결과의 시점과 출처를 기록한다. 알림 내용을 그대로 영구 진실로 저장하기보다 현재 상태와 대조해 갱신하는 편이 오해를 줄인다.

외부 알림 실패와 데이터 서비스 실패도 분리한다. 웹훅이 늦거나 메시지 전송이 실패했다고 Redis의 역할 전환 자체가 실패했다고 결론 내릴 수는 없다. 반대로 알림이 성공했다고 애플리케이션 요청까지 정상이라는 뜻도 아니다. 각 도구의 상태를 적절한 질문에 연결한다.

이벤트 기반 자동화가 상태를 변경한다면 재실행의 의미를 설계해야 한다. 같은 알림을 여러 번 처리해도 안전한지, 오래된 알림이 뒤늦게 도착했을 때 최신 상태를 덮어쓰지 않는지 확인한다. Sentinel의 감시와 외부 운영 자동화의 책임을 섞지 않아야 원인을 조사하기 쉽다.

복구 관찰 연습. 돌아온 이전 primary를 특별 취급하지 않기

이전 primary가 재시작하면 예전 역할을 자동으로 되찾아야 한다고 생각하기 쉽다. 그러나 이미 새 primary가 채택된 구성에서는 현재 결정을 따라 replica로 재구성되는 경로를 이해해야 한다. 과거에 쓰기를 받았다는 사실이 앞으로도 계속 리더일 권리를 뜻하지 않는다.

이때 데이터의 복구도 중요하다. 이전 primary가 독자적으로 받은 쓰기를 새 primary와 업무 의미에 맞게 자동 병합한다고 기대하지 않는다. 복제와 재동기화는 현재 채택한 이력을 따라가는 방향으로 동작할 수 있다. 중요한 업무 상태는 독립적인 요청 이력과 권위 있는 근거를 통해 대조해야 한다. 다음 합의 장에서 이 분할 상황을 자세히 다룬다.

실습에서는 돌아온 프로세스의 포트가 열렸다는 사실만 기록하지 않는다. ROLE과 상위 대상, 복제 링크와 초기 동기화, 데이터 샘플을 확인한다. 새 primary가 서비스를 계속하는 동안 재동기화 때문에 자원 피크가 발생할 수 있으므로 지연과 네트워크, 메모리도 관찰한다. 복귀한 노드는 단순 생존이 아니라 현재 구성에 정상 편입됐는지 확인해야 한다.

면접 질문과 깊이 있는 답변

답을 펼치기 전에 원리, 장애 반례, 운영 확인 방법의 세 순서로 말해 보자. 짧은 정의만 외우기보다 어떤 조건에서 그 설명이 깨지는지를 덧붙이는 것이 중요하다.

SDOWN 로그가 보이면 장애 전환이 완료된 건가요?

아닙니다. 한 감시자가 응답을 신뢰하지 못하는 단계입니다. 정족수 판단, 전환 수행자 승인, 적격 후보 선택, 실제 승격, 구성 전파, 클라이언트 재연결이 남을 수 있습니다. 로그와 역할 조회 및 실제 업무 요청을 연결해 단계별 완료를 판정해야 합니다.

down-after를 5초로 하면 RTO도 5초인가요?

이 값은 감지 조건의 일부이지 전체 복구 시간 보장이 아닙니다. 승인과 후보 선택, 재구성, DNS·연결 timeout, 클라이언트 재시도 때문에 더 길어질 수 있습니다. RTO는 업무 요청이 다시 성공하는 기준으로 측정하며 감지 시간과 따로 기록합니다.

GET-MASTER-ADDR-BY-NAME 결과를 계속 써도 되나요?

현재 알려진 주소를 반환하는 조회이므로 영구 불변값이 아닙니다. 장애 전환 뒤 주소와 역할이 달라질 수 있습니다. Sentinel 지원 클라이언트를 사용하고 연결 실패 또는 역할 오류 때 새 주소를 발견하는 경로를 시험해야 합니다. 기존 커넥션 풀도 변화에 대응해야 합니다.

CKQUORUM 성공은 어떤 의미인가요?

현재 Sentinel 관점에서 장애 판단과 전환 승인을 위한 감시자 조건을 점검한 결과입니다. 새 primary의 데이터 최신성이나 애플리케이션 ACL, 클라이언트 재연결까지 검증한 결과는 아닙니다. 예방 점검에 유용하지만 실제 전환 시험을 대체하지 않습니다.

SENTINEL FAILOVER로 자동 장애 전환을 검증할 수 있나요?

강제 전환 요청과 정상 자동 판단 경로는 다릅니다. 이 명령은 자동 ODOWN·승인 경로의 모든 조건을 같은 방식으로 시험하지 않으므로 통신이나 quorum 문제가 가려질 수 있습니다. 강제 전환 시험은 별도로 표시하고 자동 전환은 실제 격리된 장애 조건에서 관찰해야 합니다.

한 Sentinel의 SET 변경이 모든 곳에 배포되나요?

임의의 감시 정책 변경이 모든 Sentinel에 자동 동기화된다고 가정하면 안 됩니다. 전환 결과의 구성 전파와 운영 설정 배포는 다릅니다. 각 인스턴스에 필요한 변경을 적용하고 조회로 일치 여부를 확인하며 재시작 후 상태도 점검합니다.

switch-master 알림을 받으면 모든 replica도 준비됐나요?

새 primary 정보가 알려지는 시점과 나머지 replica의 재동기화 완료 시점은 다릅니다. 주소 전환 후에도 복제 여유가 부족할 수 있습니다. 애플리케이션 회복과 redundancy 회복을 별도 지표로 관리하고 다음 유지보수는 보호 수준이 회복된 뒤 진행합니다.

Pub/Sub 알림이 없으면 전환이 없었던 건가요?

아닙니다. 구독 연결이 끊겨 있던 동안 이벤트를 놓칠 수 있습니다. Pub/Sub은 영속 재생 로그가 아니므로 상태 조회와 서버 로그를 함께 사용합니다. 이벤트는 빠른 신호이고 현재 역할·주소·epoch 같은 조회는 사실을 확정하는 증거로 활용합니다.

자동화 보충. 완료를 기다릴 때는 성공 조건과 마감 조건을 함께 둔다

전환 요청 뒤 5초를 자고 다음 명령을 실행하는 스크립트는 작업 시간이 항상 같다고 가정한다. 빠른 환경에서는 불필요하게 기다리고 느린 환경에서는 아직 준비되지 않은 상태에서 다음 단계를 시작할 수 있다. 관찰할 역할과 주소, 필요한 동작의 조건을 정하고 제한된 시간 안에서 상태를 다시 읽는 방식이 더 명확하다.

이때 대기 반복 자체도 설계가 필요하다. 마감 시간과 조회 간격, 연속 오류 처리, 실패 시 보존할 정보를 정한다. 응답을 파싱하지 못했거나 이름이 없다는 결과를 준비 완료로 바꾸지 않는다. 조회가 실패했다고 값이 바뀌었다는 뜻도 아니다. 관측 불가와 조건 불충족을 다른 상태로 기록하면 진단이 쉬워진다.

자동화의 마지막 단계가 강제 전환을 다시 요청하는 것이라면 특히 주의해야 한다. 아직 진행 중인 작업을 실패로 오해해 반복 요청하면 관측을 더 복잡하게 만들 수 있다. 상태 조회와 상태 변경을 분리하고, 변경은 목적과 현재 상태를 확인한 제한된 경로로 수행한다. 복구 완료를 만들어 내는 것이 아니라 완료 조건을 확인하는 도구로 시작하는 편이 이해하기 쉽다.

추가 면접 문답: 전환의 단계와 완료 기준을 말하기

새 primary가 확인됐는데 사용자 오류가 계속되면 어디부터 볼까요?

서버의 역할 전환과 클라이언트의 재발견·연결 교체를 나누어 본다. 실제 오류 대상 주소가 어디인지, 어느 인스턴스가 새 주소를 알았는지, 데이터 포트와 인증에 문제가 없는지 확인한다. 모든 애플리케이션이 같은 순간에 새 연결을 얻는다고 가정하지 않는다.

첫 성공 한 건과 전체 안정화도 구분한다. 오류율과 지연, 여러 인스턴스의 연결, 필요한 업무 동작이 기준을 만족하는지 확인한다. down-after 값을 줄이는 조치는 이 구간의 원인을 확인한 뒤 검토해야 한다.

CKQUORUM은 통과했지만 모든 replica의 priority가 0이면 어떻게 되나요?

감시자의 정족수 관련 조건을 만족해도 모든 replica가 승격 금지라면 적격 승격 후보가 없다. CKQUORUM은 후보 선택과 모든 서비스 복구 조건을 대신 검사하지 않는다. 적격 replica와 제어 명령 권한, 자원, 네트워크, 클라이언트의 새 연결이 필요하다. 결과를 전환 전체의 성공 보장으로 넓히지 않는다.

배치 검토와 상태 점검, 실제 격리 전환 시험을 목적에 맞게 결합한다. 무엇을 확인했는지와 남은 조건을 함께 말하면 답변이 정확해진다.

점검용 강제 전환과 primary 종료 시험의 결과를 같은 항목으로 기록해도 되나요?

시작 조건과 검증한 경로가 다르므로 기록을 구분해야 한다. 강제 요청 경로와 자동 장애 판단·승인 경로는 같은 질문의 시험이 아니다. 수동 전환은 일부 제어와 역할 변경 경로를 확인할 수 있어도 감시자들이 실제 장애 상황에서 필요한 판단과 승인을 얻는지를 대신 검증하지 않는다.

시험의 시작 조건과 관찰한 단계를 구분해 기록한다. 자동 전환이 실패했다면 감시자 통신, 알려진 구성, quorum과 승인 조건, 후보 적격성을 단계별로 조사한다. 수동 명령으로 최종 모양을 만들었다고 원인이 사라진 것은 아니다.

알림 수집 프로그램을 재시작한 뒤 현재 primary를 어떻게 확인하나요?

구독 연결이 없거나 처리 프로그램이 중단된 동안 알림을 놓칠 수 있으므로 그 결론은 부족하다. 현재 상태를 조회하고 각 노드의 역할과 관련 로그를 대조한다. 알림은 빠른 신호이고 상태 조회는 현재 사실을 확인하는 경로로 사용할 수 있다.

반대로 알림 한 건을 받았다고 모든 replica와 클라이언트가 준비됐다고 선언하지 않는다. 그 알림이 어떤 단계의 사건을 뜻하는지 확인하고 서비스 완료 기준을 따로 검사해야 한다.
