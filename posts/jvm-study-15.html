1. 한 대의 창고 단말기를 여러 직원이 쓴다면

직원 A와 B가 수량 10을 동시에 읽고 각자 1을 더한 뒤 11을 기록하면 한 번의 증가가 사라집니다. 실행 순서를 조율해야 할 때 같은 자원에 들어가는 열쇠가 필요합니다. Java의 synchronized는 객체와 연결된 **모니터(Monitor)**를 이용하는 동기화 구문입니다.

모니터는 단순히 “객체에 붙은 boolean 잠금값”으로만 설명하기에는 부족합니다. 소유자, 재진입, 경합과 대기, wait/notify 규칙이 관련됩니다. 락을 갖지 못한 요청이 기다리는 것과 JVM 전체 작업을 위해 애플리케이션 실행을 멈추는 STW는 서로 다른 현상입니다.

2. 원자성과 가시성을 함께 보기

synchronized는 같은 모니터를 사용하는 임계 구역에 한 번에 한 스레드가 들어가도록 합니다. 같은 스레드가 이미 가진 모니터를 다시 획득할 수 있는 재진입도 지원합니다. 임계 구역 전체의 복합 동작을 묶는 데 사용할 수 있습니다.

또한 같은 모니터의 unlock은 이후 lock과 happens-before 관계를 만듭니다. 단순히 동시에 못 들어가게 하는 것뿐 아니라 쓰기 결과가 올바르게 보이는 동기화 규칙과 연결됩니다. 서로 다른 모니터로 각각 보호하면 같은 변수여도 이 상호 배제가 성립하지 않습니다. volatile int count도 count++ 전체를 원자적으로 만들지는 않습니다. 근거: JLS §17.4.5

3. 정확히 2만 번 증가하는 코드

// file: Lesson15.java
public class Lesson15 {
    static final class Counter {
        private int value;
        synchronized void increment() { value++; }
        synchronized int read() { return value; }
        void blockIncrement() {
            synchronized (this) { value++; }
        }
    }
    public static void main(String[] args) throws InterruptedException {
        Counter counter = new Counter();
        Runnable job = () -> {
            for (int i = 0; i < 10_000; i++) counter.increment();
        };
        Thread first = new Thread(job, "inspection-a");
        Thread second = new Thread(job, "inspection-b");
        first.start();
        second.start();
        first.join();
        second.join();
        System.out.println(counter.read());
    }
}

javac --release 21 -g Lesson15.java
java Lesson15
javap -c -v -p 'Lesson15$Counter'
java -Xlog:safepoint=info Lesson15

출력은 20000입니다. 같은 Counter의 모니터로 증가를 보호합니다. 두 join은 스레드 완료를 기다립니다. 동기화를 제거한 변형은 종종 더 작은 값이 나올 수 있지만, 짧은 실험에서 우연히 20000이 나왔다고 스레드 안전성을 증명한 것은 아닙니다.

4. synchronized 메서드와 블록의 바이트코드

동기화된 메서드는 method_info의 ACC_SYNCHRONIZED 플래그로 표시될 수 있습니다. 명령 목록에 monitorenter가 없다고 락이 없다는 뜻이 아닙니다. 인스턴스 동기화 메서드는 수신 객체, static 동기화 메서드는 해당 Class 객체와 연결된 모니터를 사용합니다.

동기화 블록은 보통 monitorenter·monitorexit와 예외 처리 경로로 표현됩니다. 정상 종료와 예외 종료 모두 모니터를 놓아야 하기 때문입니다. blockIncrement를 javap로 보고 예외 표까지 확인하세요. 서로 다른 객체 두 개에 synchronized를 걸면 하나의 전역 락이 되는 것이 아닙니다. 근거: JVMS §3.14

5. BLOCKED·WAITING·RUNNABLE과 wait/sleep

BLOCKED는 Java 모니터 진입 대기와 연결됩니다. WAITING·TIMED_WAITING에는 join, park, wait, sleep 등의 상황이 포함될 수 있습니다. RUNNABLE도 실제 CPU를 계속 쓰고 있다는 뜻만은 아닙니다. 네이티브 I/O 상태가 그렇게 보이는 경우도 있어 OS CPU 표본과 스택을 함께 봅니다.

Object.wait()는 해당 객체 모니터를 가진 상태에서 호출하며 대기 중 그 모니터를 놓습니다. Thread.sleep()은 현재 가지고 있는 모니터를 자동으로 놓지 않습니다. notify는 조건 충족을 영구 보장하거나 곧바로 CPU 실행권을 넘기는 마법이 아닙니다. wait는 조건 확인을 반복하는 패턴과 함께 사용해야 합니다.

락을 오래 잡고 DB·네트워크를 기다리면 같은 락을 쓰는 다른 요청도 막힐 수 있습니다. 스레드 수를 늘리면 대기자만 늘어 Heap과 Native 비용까지 악화될 수 있습니다. 임계 구역을 줄이되 보호해야 할 불변식이 깨지지 않도록 설계해야 합니다.

6. Safepoint는 무엇을 안전하게 만드는가

HotSpot은 GC의 특정 단계나 VM 작업을 수행할 때 스레드 상태를 안전하게 관찰·처리할 수 있어야 합니다. Safepoint는 이런 작업을 위한 안전한 실행 상태와 협조 메커니즘에 관련됩니다. Java 소스의 세미콜론마다 무조건 존재하는 지점이나 OS가 스레드를 임의로 선점하는 모든 순간과 같지 않습니다.

정지 로그를 읽을 때는 안전 상태에 도달하기까지의 시간과 실제 정지 상태에서 작업한 시간을 구분합니다. 애플리케이션이 느려진 전체 시간을 GC 작업 시간으로만 해석하면 safepoint 진입 지연이나 CPU 부족을 놓칠 수 있습니다. 또한 모든 safepoint가 GC 때문은 아닙니다. 반대로 특정 스레드만 협조하는 handshake와 전역 safepoint도 구분할 필요가 있습니다.

컴파일된 코드의 oop map 등 정보는 안전한 상태에서 어느 값이 객체 참조인지 판단하는 데 도움을 줍니다. 이는 07편의 class 파일 StackMapTable과 같은 자료구조라고 단정하면 안 됩니다. 하나는 JIT 실행과 런타임 관측의 구현 정보이고 다른 하나는 바이트코드 검증용 타입 정보입니다.

7. Java 21 가상 스레드는 무엇이 다른가

플랫폼 스레드는 OS 스레드와 연결되어 실행됩니다. 가상 스레드는 JVM이 스케줄링하며 캐리어 플랫폼 스레드 위에 올라가 실행합니다. 많은 블로킹 I/O 동시 작업을 효율적으로 다루려는 기능이지 CPU 코어 수를 늘리거나 DB 커넥션 한도를 없애는 기능이 아닙니다.

다음 예제는 JDK 21 이상에서 컴파일합니다. 완료 순서는 보장하지 않고 합계만 확인합니다.

// file: VirtualThreads.java
import java.util.concurrent.Executors;
import java.util.concurrent.Future;
import java.util.ArrayList;
import java.util.List;

public class VirtualThreads {
    public static void main(String[] args) throws Exception {
        List<Future<Integer>> tasks = new ArrayList<>();
        try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
            for (int i = 0; i < 100; i++) {
                tasks.add(executor.submit(() -> {
                    Thread.sleep(10);
                    return 1;
                }));
            }
            int total = 0;
            for (Future<Integer> task : tasks) total += task.get();
            System.out.println("completed=" + total);
        }
    }
}

JDK 21에서는 synchronized 구역 안에서 블로킹할 때 캐리어에 pinning되는 조건 등이 중요합니다. 이 설명을 모든 최신 JDK의 영구 특성으로 외우지 마세요. JDK 24의 JEP 491은 synchronized 관련 pinning을 개선했습니다. 이 연재는 21을 기준으로 하므로 긴 I/O를 락 안에서 수행하는 경로와 JFR의 pinning 관측을 확인합니다. 가상 스레드를 사용해도 공유 상태의 동기화와 외부 자원의 동시성 제한은 필요합니다.

8. 장애 사례: CPU는 낮은데 요청이 밀림

검수 서비스가 synchronized 블록 안에서 외부 API를 2초 기다린다고 가정합니다. 같은 모니터가 필요한 요청들은 실행할 CPU가 남아도 대기할 수 있습니다. 이를 GC 정지로 오인해 Heap을 늘리면 락 병목은 그대로입니다.

시간 간격을 둔 thread dump에서 같은 모니터 소유자와 대기자들이 반복되는지 확인하고, JFR의 락 대기와 외부 호출 시간을 연결합니다. 전역 safepoint 로그에 같은 기간 정지가 있었는지도 비교합니다. CPU 부족·락 경합·외부 대기·GC는 관측 자료를 나누어야 구분할 수 있습니다.

더 깊이: 락 경합·교착·Safepoint 지연의 차이

락 경합은 한 자원을 여러 스레드가 필요로 하는 상황입니다. 소유자가 빠르게 완료하면 정상적으로 진행할 수 있습니다. 교착은 A가 가진 락을 B가 기다리고 B가 가진 락을 A가 기다리는 식으로 서로 필요한 자원을 놓지 못해 진행이 막히는 상황입니다. 단순히 BLOCKED가 많이 보인다고 모두 교착은 아닙니다.

락 순서를 일관되게 정하고 임계 구역의 외부 I/O를 줄이며, 타임아웃 가능한 락·자원 API의 필요성을 검토할 수 있습니다. 다만 timeout을 걸었다고 중간에 변경한 업무 상태가 자동 롤백되는 것은 아닙니다. 동시성 제어와 트랜잭션 보상·정합성도 구분해야 합니다.

Safepoint 도달 지연은 다른 질문입니다. JVM이 필요한 안전 상태를 기다리느라 시간이 걸리는지, 실제 VM 작업이 오래 걸리는지를 봅니다. CPU 제한과 스레드 스케줄링도 영향을 줄 수 있으므로 정지 로그의 총시간을 특정 GC 단계 하나로 치환하지 않습니다.

심화 Q. JVM 안에서 synchronized를 걸면 여러 서버의 재고 갱신도 보호되나요?

같은 JVM 안에서 같은 모니터를 사용하는 스레드끼리의 규칙입니다. 서버가 세 대라면 각 프로세스의 객체와 모니터는 별개이므로 전역 업무 동기화가 되지 않습니다.

DB 조건부 갱신·트랜잭션·유일 제약 등 공유 자원의 정합성 설계가 필요합니다. JVM 모니터의 범위를 네트워크 전체로 확대해서 설명하면 안 됩니다.

차근차근 이해하기: 같은 값과 같은 락을 공유하는지 먼저 본다

두 스레드가 같은 재고 수량을 읽고 하나씩 줄인다고 가정합시다. 값이 10일 때 둘 다 10을 읽고 각각 9를 저장하면 두 번의 감소 요청 후에도 9가 됩니다. 이것은 한 스레드의 계산이 다른 스레드의 갱신을 덮어쓴 상황입니다. Java 소스 한 문장인지보다 읽기·계산·쓰기 전체가 다른 작업과 어떻게 섞일 수 있는지가 중요합니다.

순서 스레드 A 스레드 B 공유 count
1 10을 읽음 대기 10
2 계산 중 10을 읽음 10
3 9를 저장 계산 중 9
4 완료 9를 저장 9

이 표는 가능한 실행 순서의 예입니다. 실제로 매번 같은 잘못된 결과가 나와야만 경쟁이 있는 것은 아닙니다. 짧은 로컬 실험에서 우연히 정답이 나왔다고 동시성 안전성을 증명할 수 없습니다.

synchronized는 같은 모니터를 사용할 때 연결된다

모니터를 회의실 열쇠라고 생각해 봅시다. 같은 열쇠를 쓰는 사람끼리는 한 번에 한 명씩 들어가게 만들 수 있습니다. 그러나 서로 다른 열쇠를 들고 같은 자료를 수정하면 조정이 되지 않습니다. 인스턴스 synchronized 메서드는 그 수신 객체의 모니터를 사용합니다. 서로 다른 인스턴스의 메서드를 호출하면 모니터도 서로 다릅니다.

또한 락을 잡고 쓰는 쪽만 있다고 충분한 것은 아닙니다. 읽는 쪽이 어떤 동기화 규칙으로 최신 상태를 관찰하는지도 필요합니다. 같은 모니터의 unlock과 이후 lock 사이에는 happens-before 관계가 있으므로, 배타 실행뿐 아니라 가시성과 순서의 의미도 얻습니다. 이 관계를 단순히 “매번 모든 CPU 캐시를 통째로 비운다”로 설명하면 구현과 사양을 혼동하게 됩니다.

volatile을 붙여도 count++는 복합 연산이다

volatile은 해당 변수의 읽기·쓰기와 관련된 가시성·순서 보장을 제공하지만, 읽어서 계산하고 다시 쓰는 전체 동작을 자동으로 하나의 원자적 갱신으로 묶지 않습니다. 따라서 volatile count에 대한 count++도 경쟁할 수 있습니다. 카운터라면 적절한 원자적 갱신 API나 락을 검토하고, 여러 필드의 일관된 상태를 지켜야 한다면 전체 불변조건을 보호해야 합니다.

예를 들어 balance 감소와 reserved 증가가 함께 맞아야 한다면 각각의 필드 접근이 안전하다는 것만으로 두 값의 합에 관한 규칙이 지켜지는 것은 아닙니다. 보호할 단위를 데이터 한 칸이 아니라 업무상 함께 성립해야 하는 조건으로 정의해야 합니다.

wait와 sleep을 대기 이유로 구분하기

sleep은 일정 시간 실행을 쉬게 하는 API이고, 현재 보유한 모니터를 자동으로 놓지 않습니다. Object.wait는 해당 모니터를 소유한 상태에서 호출해야 하며 그 모니터를 놓고 기다립니다. 깨어난 뒤에는 다시 모니터를 획득해야 진행할 수 있습니다. wait가 다른 모니터까지 전부 해제하는 것도 아닙니다.

조건 대기는 보통 while로 조건을 다시 검사합니다. 알림이 왔다는 사실이 지금도 원하는 조건이 성립한다는 보장은 아니고, 허위 깨움도 고려해야 하기 때문입니다. 알림은 데이터를 대신 전달하는 주문서가 아니라 “조건이 바뀌었을 수 있으니 확인하라”는 신호로 이해하면 쉽습니다.

가상 스레드가 바꾸는 비용과 바꾸지 않는 한계

가상 스레드는 대기 중심 작업에서 많은 동시 작업을 표현하는 비용을 줄이는 데 유용합니다. 그러나 DB 연결이 20개뿐이라면 가상 스레드를 1만 개 만든다고 동시에 DB 쿼리 1만 개가 처리되는 것은 아닙니다. 오히려 기다리는 작업과 보유 데이터가 늘 수 있습니다. 외부 자원 용량과 동시성 제한은 여전히 필요합니다.

Java 21에서는 synchronized 내부의 일부 블로킹처럼 carrier를 붙잡는 pinning 조건을 구분해야 합니다. 이 내용은 버전 의존적이므로 JDK 24의 변경을 Java 21에 소급해 설명하지 않습니다. 스레드 수를 늘리기 전에 CPU 작업인지 I/O 대기인지, 실제 병목 자원이 무엇인지부터 확인하세요.

확인 문제. synchronized 블록이 있는데도 결과가 틀리면 JVM 버그일까요?

판단: 먼저 모든 관련 경로가 같은 모니터와 같은 규칙을 사용하는지 확인해야 합니다. 읽는 경로가 락을 사용하지 않거나, 호출마다 다른 객체를 락으로 쓰거나, 보호 구간 밖에서 복합 갱신을 수행하면 문제가 남을 수 있습니다.

예: 조회를 락 안에서 하고 계산 후 저장을 별도의 락 구간에서 하면 그 사이에 다른 갱신이 들어올 수 있습니다. 원자적으로 유지해야 할 전체 작업을 정의한 뒤 해당 경계를 보호해야 합니다.

꼬리질문: 서버가 두 대라면요? 각 JVM의 모니터는 다른 프로세스의 작업을 함께 잠그지 않습니다. 공유 DB 데이터의 일관성은 DB 트랜잭션·제약과 분산 환경의 동시성 설계를 포함해 해결해야 합니다.

심화 실험실: AtomicInteger라도 재고 차감 전체가 원자적이지 않을 수 있다

한 동작이 안전한 것과 두 동작의 묶음이 안전한 것은 다르다

은행 창구가 잔액 조회와 인출을 각각 정확하게 처리해도, 두 직원이 모두 마지막 잔액을 본 뒤 각각 인출하면 문제가 됩니다. AtomicInteger의 get과 decrementAndGet이 각각 원자적이어도 그 둘을 연결한 조건부 차감이 하나의 원자적 연산이 되는 것은 아닙니다.

// file: Deep15.java
import java.util.concurrent.CountDownLatch;
import java.util.concurrent.atomic.AtomicInteger;
public class Deep15 {
    public static void main(String[] args) throws Exception {
        AtomicInteger stock = new AtomicInteger(1);
        CountDownLatch checked = new CountDownLatch(2);
        Runnable buy = () -> {
            boolean available = stock.get() > 0;
            checked.countDown();
            try { checked.await(); }
            catch (InterruptedException e) {
                Thread.currentThread().interrupt();
                return;
            }
            if (available) stock.decrementAndGet();
        };
        Thread a = new Thread(buy);
        Thread b = new Thread(buy);
        a.start(); b.start(); a.join(); b.join();
        System.out.println("broken=" + stock.get());
        stock.set(1);
        System.out.println("first=" + takeOne(stock));
        System.out.println("second=" + takeOne(stock));
        System.out.println("fixed=" + stock.get());
    }
    static boolean takeOne(AtomicInteger stock) {
        for (;;) {
            int current = stock.get();
            if (current <= 0) return false;
            if (stock.compareAndSet(current, current - 1)) return true;
        }
    }
}

javac --release 21 Deep15.java
java Deep15

출력은 broken=-1, first=true, second=false, fixed=0입니다. latch는 두 스레드가 모두 재고 1을 읽도록 순서를 만들어 오류를 재현합니다. 단순히 수천 번 실행해서 운 좋게 실패하기를 기다리지 않습니다. 수정된 takeOne은 읽은 값이 여전히 같을 때만 변경하고, 경쟁에서 졌다면 현재 값을 다시 읽습니다.

CAS가 보호하는 범위를 정확히 말하기

CAS는 compare-and-set, 즉 기대한 값과 같을 때 바꾸는 원자적 조건부 연산입니다. 이 예제에서는 stock 한 값의 조건과 변경을 연결합니다. 하지만 DB에 주문을 저장하고 Kafka로 이벤트를 보내는 전체 과정이 원자적으로 되는 것은 아닙니다. JVM 안의 원자 변수, DB 트랜잭션, 분산 메시지 전달은 서로 다른 경계입니다.

여러 필드를 함께 일관되게 바꾸려면 같은 락으로 묶거나 상태 전체를 불변 객체로 구성해 원자적으로 교체하는 등 별도 설계가 필요합니다. 여러 AtomicInteger를 하나씩 바꾸는 것만으로 여러 값의 불변식이 유지되지는 않습니다. 또한 CAS 루프는 경쟁이 심하면 재시도가 늘고 특정 스레드의 공정성을 자동 보장하지 않습니다.

happens-before는 “바로 보인다”보다 정확한 규칙이다

Thread.start() 이전의 준비 작업과 시작한 스레드의 동작, 스레드 종료와 성공한 join 이후의 관측 사이에는 happens-before 관계가 있습니다. 이 예제에서 main이 join한 뒤 결과를 읽는 것과 두 작업 스레드가 동시에 조건을 검사하는 것은 다른 문제입니다. 결과 관측이 안전하다고 중간 업무 연산도 원자적인 것은 아닙니다.

volatile도 마찬가지입니다. 가시성과 순서에 대한 보장이 있어도 if (stock > 0) stock--를 하나의 원자적 묶음으로 만들지 않습니다. 스레드 안전성을 설명할 때는 어떤 값, 어떤 연산 묶음, 어떤 관측 관계를 보장하는지 구체적으로 말해야 합니다.

Java 21 가상 스레드에도 같은 원칙이 적용된다

가상 스레드를 사용해도 공유 재고 변수의 경쟁 조건은 사라지지 않습니다. 더 많은 대기를 저렴하게 표현할 수 있다는 것과 DB 연결·외부 API 처리 용량이 늘어난다는 것도 다릅니다. Java 21에서는 synchronized 안에서의 일부 블로킹이 carrier pinning 문제와 연결될 수 있으므로 관찰이 필요합니다. 이후 JDK의 변경을 Java 21 동작에 소급해서 설명하지 않습니다.

심화 면접. AtomicInteger를 썼는데도 재고가 음수가 되었습니다. 어떻게 설명하겠습니까?

답변: 원자적인 개별 메서드 호출 사이에 다른 스레드가 끼어들 수 있습니다. 조회와 조건 판단, 차감 전체를 하나의 원자적 규칙으로 만들지 않으면 두 요청이 같은 재고를 보고 모두 차감할 수 있습니다.

해결: 단일 값이면 CAS 반복으로 조건부 변경을 구현할 수 있고, 여러 값이면 공통 락이나 상태 모델을 검토합니다. latch로 두 요청의 조회 시점을 맞추면 경쟁을 결정적으로 재현할 수 있습니다.

경계: 서버가 여러 대라면 이 메모리 변수는 서버별로 따로 존재합니다. 전체 재고 정합성은 DB의 조건부 갱신 등 실제 공유 저장소의 동시성 정책까지 설계해야 합니다.

추가 근거: AtomicInteger CAS, JLS happens-before, Java 21 가상 스레드.

9. 상세 면접 Q&A

Q1. synchronized는 원자성만 제공하나요?

같은 모니터의 상호 배제와 unlock→이후 lock의 happens-before를 함께 봐야 합니다. 올바른 공유 규칙 없이 다른 락으로 읽으면 같은 보호를 얻지 못합니다. volatile과 복합 연산 원자성의 차이도 구분합니다.

구체적으로: 같은 모니터의 unlock 이후 다른 스레드의 lock은 happens-before 관계를 형성합니다. 공유 상태의 관찰과 순서를 설명하는 언어 수준의 보장입니다.

꼬리질문까지: 락을 사용하는 쓰기 경로만 있고 읽기 경로가 다른 규칙을 쓰면 전체 접근을 다시 검토해야 합니다.

Q2. javap에 monitorenter가 없으면 동기화되지 않은 메서드인가요?

동기화 메서드는 ACC_SYNCHRONIZED 플래그로 표시될 수 있습니다. 블록의 명령과 메서드 플래그를 함께 확인해야 합니다. static과 인스턴스 메서드가 사용하는 모니터도 다릅니다.

구체적으로: synchronized 메서드는 ACC_SYNCHRONIZED 플래그로 나타날 수 있습니다. 블록 형태의 monitorenter·monitorexit만 검색하면 메서드 수준 동기화를 놓칩니다.

꼬리질문까지: 인스턴스 메서드와 static 메서드가 어떤 모니터를 사용하는지도 구분해야 합니다.

Q3. sleep은 락을 놓나요?

sleep은 보유한 모니터를 자동으로 놓지 않습니다. wait는 해당 모니터의 소유 규칙을 만족해야 하고 대기 중 그 모니터를 놓습니다. 긴 sleep이나 I/O를 임계 구역 안에 두면 다른 스레드가 계속 막힐 수 있습니다.

구체적으로: synchronized 안에서 sleep하면 그동안 같은 모니터를 원하는 다른 스레드는 기다릴 수 있습니다. 쉬고 있다는 사실과 락을 놓았다는 사실은 다릅니다.

꼬리질문까지: Object.wait는 해당 모니터를 놓지만 보유한 모든 락을 놓는 것은 아니며, 다시 진행하려면 재획득이 필요합니다.

Q4. Safepoint는 GC와 같은 말인가요?

GC는 안전 상태를 필요로 하는 중요한 작업 중 하나이지만 전부는 아닙니다. 전역 협조·관측 메커니즘과 수행할 작업을 구분해야 합니다. 도달 시간과 작업 시간, 다른 VM 작업도 로그에서 따로 확인합니다.

구체적으로: GC 외에도 JVM이 특정 작업을 일관되게 수행하기 위해 실행 상태를 안전하게 관찰하거나 조정해야 하는 경우가 있습니다. Safepoint 로그는 도달 시간과 작업 시간을 나누어 읽어야 합니다.

꼬리질문까지: GC pause 하나만으로 모든 정지 원인을 설명하지 말고 같은 시간대의 safepoint 기록을 확인하세요.

Q5. 가상 스레드를 늘리면 CPU 계산도 무한히 빨라지나요?

아닙니다. 실제 계산 병렬성은 CPU와 캐리어 실행 자원에 제한됩니다. 가상 스레드는 주로 많은 블로킹 작업을 저렴하게 표현하는 데 유리합니다. DB 풀·API 한도·메모리 등 외부 제약은 따로 제한해야 합니다.

구체적으로: 계산 가능한 CPU 코어 수와 처리 자원은 그대로입니다. 가상 스레드는 대기 중심 동시성의 표현 비용에 장점이 있고 무한한 계산 능력을 만드는 장치는 아닙니다.

꼬리질문까지: DB 연결이나 외부 API 제한도 남으므로 작업 개수와 동시에 사용하는 자원을 별도로 제어해야 합니다.

Q6. Java 21의 pinning 설명을 JDK 24에도 그대로 적용하나요?

그대로 적용하면 안 됩니다. JEP 491은 synchronized 관련 pinning을 개선했습니다. 사용하는 JDK의 기능·버전과 실제 스택·JFR 이벤트를 기준으로 진단해야 합니다. 모든 지연을 pinning 한 단어로 설명하지 않습니다.

구체적으로: 동일한 synchronized 사용이라도 런타임 버전의 구현 변화에 따라 carrier를 붙잡는 조건이 달라질 수 있습니다. 21의 제약을 24의 보장처럼 말하거나 그 반대로 설명하면 안 됩니다.

꼬리질문까지: 문제 재현과 해결 안내에는 JDK 패치 버전·해당 JEP의 적용 버전을 함께 적으세요.

심화 교재: 모니터와 가시성

비유를 통해 개념 잡기

공용 계산대를 한 명만 사용하게 하는 통제는 모니터 락이며, 전 직원이 최신 공지판을 확인하게 하는 것은 가시성에 가깝다. 공지판만 최신이라고 동시에 계산대를 사용하는 문제가 없어지진 않는다.

HotSpot JDK 21과 JVM 사양을 구별하며 깊게 보기

synchronized는 락 소유에 따른 상호 배제를 제공하고, 같은 모니터에 대한 unlock 이후 lock에는 happens-before 관계가 생긴다. volatile은 가시성과 순서 규칙을 제공하지만 복합 증가식을 원자적으로 만들지 않는다. BLOCKED와 WAITING은 다른 대기 이유를 나타낸다.

직접 실험하기

jcmd <PID> Thread.print -l

Java 21에서 본문 실습 파일을 컴파일한 다음 실행하고, 관측값이 일정하지 않은 경우 JVM 옵션과 실행 환경을 기록한다.

운영 관점의 검증 순서

  1. 재현 입력과 실행 환경을 기록한다.
  2. 현상이 JVM 사양이 보장하는 규칙인지 HotSpot의 최적화·휴리스틱인지 구분한다.
  3. 명령 출력·바이트코드·로그를 비교하고 하나의 조건씩 바꿔 반증한다.

추가 심화 면접 Q&A

volatile count에 count++를 하면 안전한가요?

아니다. 읽기, 더하기, 쓰기를 하나의 원자적 갱신으로 묶지 않기 때문이다. AtomicInteger.incrementAndGet이나 동기화된 임계 구역을 써야 한다.
