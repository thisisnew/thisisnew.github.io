1. 이 시리즈가 해결하려는 문제

Redis를 공부할 때 처음 만나는 설명은 보통 “메모리에 저장하므로 빠르다”입니다. 그 말만으로는 운영 문제를 풀 수 없습니다. 빠른 저장소가 갑자기 응답하지 않을 때, 요청을 다시 보내도 되는지, replica로 읽어도 되는지, 성공 응답을 받은 재고 차감이 장애 뒤 사라질 수 있는지를 판단해야 하기 때문입니다. 이 시리즈는 명령이 성공한 순간부터 장애 후 복구까지 데이터가 어떻게 움직이는가를 이해하는 데 초점을 맞춥니다.

입고 시스템을 생각해 봅시다. 작업자가 PDA로 상품을 스캔하면 상품명은 잠깐 오래된 값이어도 업무를 계속할 수 있을 수 있습니다. 반면 입고 확정 수량을 두 번 더하거나 작업 완료 기록을 잃으면 재고 정합성 문제가 됩니다. 두 데이터에 같은 TTL과 같은 재시도 정책을 적용하면 안 됩니다. 기술 이름보다 먼저 데이터의 역할과 허용 가능한 실패를 정하는 연습을 할 것입니다.

출발 자료는 제공된 Redis 운영 문서 공부팩입니다. 운영 설정·영속성·복제·Sentinel·Cluster·성능·보안·내부 구현의 주 학습 30편을 한국어 교재로 재구성했습니다. 원본 전체 Redis 개발 문서를 번역한 자료는 아닙니다. 이 안내는 원본에 빠져 있던 기본기를 별도로 보충합니다. 원본 파일에 있던 “latest”는 고정된 제품 버전이 아닙니다. 문서 설명과 실제 실행 버전을 구별하고, 버전에 민감한 옵션은 해당 편의 출처와 사용 중인 서버를 함께 확인하세요.

각 편의 장애 사례는 학습용 시나리오입니다. 명령의 예상 출력은 실행 증거가 아닙니다. 독립 실행 가능한 Java 21 실습 코드와 실제 단일 서버 검사 기록도 제공합니다. 실제 수행된 검사와 제외된 범위는 검증 기록에 분리합니다. 코드가 컴파일된 사실과 다중 노드 장애 안전성을 검증한 사실도 같지 않습니다.

처음 읽는 사람을 위한 준비 1. 서버와 클라이언트를 두 사람으로 생각하기

Redis를 처음 보면 SET name Mina처럼 짧은 명령이 화면에 나타나기 때문에 Java의 Map과 비슷한 함수로 느껴질 수 있다. 값에 이름을 붙여 저장한다는 점에서는 비슷하지만, 가장 먼저 알아야 할 차이는 Redis 서버가 애플리케이션과 별개의 프로세스일 수 있다는 것이다. Java 프로그램 안의 Map을 읽는 일과 네트워크 너머 Redis에 요청하는 일은 실패 방식이 다르다.

작업자와 창고 관리자를 떠올려 보자. 작업자는 “123번 상품의 이름을 알려 주세요”라고 요청한다. 관리자는 자기 장부에서 값을 찾아 대답한다. 여기서 작업자가 클라이언트이고 관리자가 서버다. 작업자가 장부를 직접 펼치는 것이 아니라 요청과 응답을 주고받는다는 점이 중요하다. 요청이 관리자에게 전달되지 않을 수도 있고, 관리자가 답했는데 작업자가 듣지 못할 수도 있다.

컴퓨터에서도 비슷한 일이 생긴다. 클라이언트가 명령을 바이트로 만들어 연결에 보낸다. 서버가 명령을 해석하고 데이터를 읽거나 바꾼다. 서버가 결과를 바이트로 보내면 클라이언트가 결과를 해석한다. Redis가 명령을 처리하는 시간 외에도 연결, 전송, 대기, 응답 해석에 시간이 든다. “메모리에서 값을 읽으니까 네트워크 비용은 무시해도 된다”는 결론은 나오지 않는다.

같은 컴퓨터에서 Redis와 Java를 실행해도 두 프로그램은 별개의 프로세스일 수 있다. 같은 컴퓨터라는 사실은 장애 가능성을 없애지 않는다. Redis 프로세스만 종료될 수도 있고 Java만 재시작될 수도 있다. 다만 두 프로그램이 같은 호스트에 있으면 호스트 장애를 함께 겪을 수 있다. 프로세스의 경계와 컴퓨터의 경계를 나누어 생각하면 이후 복제와 장애 전환을 이해하기 쉬워진다.

redis-cli는 서버가 아니라 클라이언트 도구다. CLI에서 명령을 입력하면 이 도구가 Redis 서버로 요청을 보낸다. Java에서 Lettuce나 다른 클라이언트를 사용하는 것도 같은 역할의 라이브러리로 요청을 만드는 것이다. Spring Data Redis는 애플리케이션이 그런 작업을 다루기 쉽게 도와주는 추상화를 제공하지만 네트워크와 서버의 실패를 없애 주지는 않는다.

처음 읽는 사람을 위한 준비 2. Map으로 시작하되 Map에서 멈추지 않기

Java의 Map<String, String>은 이름으로 값을 찾는 가장 익숙한 출발점이다. 아래 코드는 Redis를 사용하지 않는다. 네트워크가 없는 작은 모델로 “키가 같으면 같은 자리를 가리킨다”는 개념을 먼저 확인한다. Java 21로 실행할 수 있다.

import java.util.HashMap;
import java.util.Map;

public final class LocalKeyValueLesson {
    public static void main(String[] args) {
        Map<String, String> names = new HashMap<>();
        names.put("goods:123:name", "배추");
        names.put("goods:124:name", "당근");
        names.put("goods:123:name", "알배기배추");

        if (names.size() != 2) throw new AssertionError("same key should replace");
        if (!"알배기배추".equals(names.get("goods:123:name"))) {
            throw new AssertionError("wrong value");
        }
        if (names.get("goods:999:name") != null) {
            throw new AssertionError("missing key should return null");
        }
        System.out.println(names.get("goods:123:name"));
    }
}

같은 키 123을 두 번 저장했지만 키 수가 3개가 되지 않는다. 같은 이름이 같은 위치를 가리키기 때문이다. 이것이 키-값 모델의 첫 번째 직관이다. 반면 키가 비슷하게 생겼더라도 123과 124는 다르다. goods:라는 접두사가 같다는 이유로 두 값이 같은 객체의 필드가 되는 것은 아니다. 어떤 관계로 묶을지는 자료형과 애플리케이션 규칙으로 정한다.

이 모델에서 Redis로 넘어갈 때 추가해야 할 조건을 보자. Map은 해당 Java 프로세스의 메모리에 있고, 다른 Java 인스턴스가 자동으로 같은 Map을 공유하지 않는다. Redis에 여러 애플리케이션이 연결하면 같은 키를 함께 읽고 쓸 수 있다. 공유는 편리하지만 동시에 누가 값을 바꿀 수 있는지, 여러 작업을 어떻게 묶을지 고민해야 한다.

또한 이 HashMap은 자동 만료가 없다. 값을 넣고 60초를 기다린다고 사라지지 않는다. Redis는 키의 수명을 설정할 수 있지만 모든 쓰기 방식에서 수명이 저절로 생기는 것은 아니다. 영속성도 다르다. Java 프로세스가 종료되면 이 Map의 내용은 사라지고, Redis는 설정에 따라 디스크 복원 경로를 가질 수 있다. “Redis도 메모리니까 무조건 꺼지면 끝”과 “Redis니까 항상 복구된다”는 둘 다 조건을 빠뜨린 설명이다.

마지막으로 HashMap의 메서드 호출은 네트워크 응답을 기다리지 않는다. Redis 요청은 타임아웃이 생길 수 있고, 타임아웃 뒤의 최종 데이터 상태가 불확실할 수 있다. Map 예제를 그대로 Redis로 바꿨을 때 catch 블록만 추가하면 충분하지 않은 이유다. 실패를 어떻게 해석할지 서비스 계약까지 확장해야 한다.

처음 읽는 사람을 위한 준비 3. 네 가지 질문으로 Redis의 역할 정하기

새 기능에 Redis를 넣기 전에 다음 네 질문을 순서대로 해 보자. 첫째, 이 값이 없어지면 어디에서 다시 만들 수 있는가? 상품 이름은 DB에서 다시 읽을 수 있을 수 있다. 반면 Redis에만 기록한 입장 순번은 다른 이력이 없으면 그대로 재구성하기 어려울 수 있다. 재생성 가능성이 캐시와 원본 상태를 구분하는 중요한 기준이다.

둘째, 얼마나 오래된 값을 허용할 수 있는가? 상품 소개 문구와 결제할 금액은 같은 기준을 쓰기 어렵다. “캐시는 5분”처럼 기술 설정으로 시작하지 말고 사용자가 어떤 잘못된 결과를 보게 되는지부터 묻는다. 5분은 단순 시간 숫자가 아니라 그 기간 동안 발생할 수 있는 업무 오차에 대한 결정이다.

셋째, 같은 요청이 두 번 실행되면 어떤 일이 생기는가? 이름을 같은 문자열로 덮어쓰는 것과 수량을 3 증가시키는 것은 다르다. 전자는 데이터 값만 보면 같을 수 있지만 TTL이나 부수 효과까지 보면 차이가 있을 수 있고, 후자는 반복할수록 수량이 바뀐다. 재시도 정책을 명령 이름만 보고 단순 분류하지 말고 실제 업무 효과를 살핀다.

넷째, Redis가 응답하지 않을 때 무엇을 할 것인가? DB로 우회할지, 요청을 거절할지, 오래된 값을 제공할지, 잠시 대기시킬지 정해야 한다. 어떤 선택이든 비용이 있다. DB 우회는 DB 부하를 늘리고, 거절은 가용성을 낮추며, 오래된 값은 신선도를 낮춘다. 이 선택은 장애가 난 뒤 즉흥적으로 결정하기보다 평소 설계에 포함하는 편이 좋다.

이 네 질문은 초보자에게 너무 운영적인 것처럼 보일 수 있다. 그러나 명령을 외울 때도 기준이 된다. SET의 TTL 옵션을 배우면 두 번째 질문과 연결하고, Lua를 배우면 세 번째 질문과 연결하고, Sentinel을 배우면 네 번째 질문과 연결한다. 단편적인 기능이 왜 필요한지 설명할 수 있게 된다.

3. Redis를 책상, 데이터베이스를 장부라고 생각해 보기

작업자는 장부 보관실에 매번 가는 대신 자주 보는 상품 정보를 책상 위 메모에 적습니다. 메모가 있으면 빨리 읽고, 없으면 장부에서 찾아 다시 적습니다. 이것이 뒤에서 설명할 cache-aside의 출발점입니다. 책상에는 공간 한계가 있고, 종이가 오래되면 버려야 하며, 다른 사람이 장부를 고쳤는데 메모가 그대로면 잘못된 내용을 보게 됩니다.

이 비유에는 한계가 있습니다. Redis가 언제나 “버려도 되는 메모”인 것은 아닙니다. 세션·작업 상태·대기열·카운터 등 서비스가 복원하기 어려운 데이터를 보관할 수도 있습니다. 그러면 메모를 잃어도 괜찮다는 전제부터 바뀝니다. 캐시용 Redis를 운영하던 설정을 그대로 대기열 저장소에 복사하면, 메모리 부족 시 키를 내보내는 정책 때문에 업무 데이터가 사라질 수 있습니다.

원본 데이터(source of truth)란 충돌이 났을 때 최종적으로 믿을 근거입니다. 상품 조회 캐시는 MySQL에서 재생성할 수 있지만, Redis에만 있던 대기 순번은 MySQL에 없다면 재생성할 수 없습니다. “Redis를 쓴다”는 말 대신 다음처럼 요구사항을 적어야 합니다.

데이터 최종 근거 허용 가능한 손실/오래됨 장애 시 선택
상품 설명 캐시 MySQL 업무에서 정한 짧은 지연 조회량 제한을 두고 DB 조회
재고 확정 기록 보통 DB의 트랜잭션 기록 중복·유실 불허 요구 멱등키·고유 제약·이력 대조
임시 대기 순번 설계에 따라 Redis 서비스 계약에 따라 결정 재입장 정책 또는 영속화
API 호출 횟수 Redis 또는 별도 집계 정확도 요구에 따라 결정 보수적 제한/임시 차단/허용 중 선택

표는 정답이 아니라 요구사항을 쓰는 예시입니다. 특히 장애 시 무조건 DB로 우회하면 평소 캐시가 흡수하던 요청이 DB에 몰려 두 번째 장애를 만들 수 있습니다.

4. 키, 값, 자료구조를 처음부터 구분하기

키(key)는 보관함 이름이고 값(value)은 그 보관함의 내용입니다. goods:123:name과 goods:124:name은 다른 키입니다. 콜론은 사람이 읽기 쉽게 정한 규칙일 뿐 디렉터리를 자동 생성하지 않습니다. 문자열 키 아래에 어떤 자료구조의 값을 둘지 선택합니다.

자료구조 쉬운 그림 입고 도메인의 예 주의점
String 한 장의 값 또는 숫자 상품 JSON, 단순 카운터 숫자 문자열만 증가 연산 가능
Hash 한 객체의 이름 붙은 칸들 상품의 이름·상태·센터 코드 필드별 조회가 가능해도 전체 조회는 크기에 비례
List 앞뒤로 넣고 빼는 줄 간단한 처리 목록 신뢰성 있는 작업 처리에는 ACK·재처리 설계 필요
Set 중복 없는 이름표 모음 오늘 스캔한 상품 ID 정렬된 순서가 없음
Sorted Set 점수 붙은 이름표 입장 시간순 대기열 같은 점수의 정렬 기준과 동시성 고려
Stream ID 붙은 이벤트 기록 작업 이벤트 소비 ACK·보존·재처리·멱등 처리 필요

이 표는 선택을 돕는 독자적인 업무 예시이며, 지원 명령과 버전별 확장은 공식 자료구조 안내에서 확인합니다. 자료형 이름과 메모리 안의 구현은 다릅니다. 예를 들어 같은 Hash라도 원소 개수와 크기에 따라 압축된 표현이나 해시 테이블 표현을 사용할 수 있습니다. 03편에서 이 차이를 다룹니다.

명령 시간 복잡도도 익혀야 합니다. O(1)은 데이터 전체 개수와 무관한 작업량이라는 뜻이지, 네트워크·큰 응답·메모리 압력까지 항상 일정하다는 뜻이 아닙니다. O(N)은 살펴봐야 할 원소가 늘수록 일이 늘어난다는 뜻입니다. 작은 개발 데이터에서 빠른 전체 조회 명령이 운영의 거대한 키에서는 이벤트 루프를 오래 점유할 수 있습니다.

다음 예시는 이미 만든 폐기 가능한 로컬 학습 Redis에서만 실행하세요. 운영 주소를 복사해 쓰지 마세요. 설명용 포트 16379를 사용하며, 서버를 이 포트에 직접 준비하지 않았다면 명령을 실행하지 않습니다.

redis-cli -h 127.0.0.1 -p 16379 SET study:goods:123:name '배추' EX 60
redis-cli -h 127.0.0.1 -p 16379 GET study:goods:123:name
redis-cli -h 127.0.0.1 -p 16379 HSET study:goods:123 status AVAILABLE center IC
redis-cli -h 127.0.0.1 -p 16379 HGET study:goods:123 status
redis-cli -h 127.0.0.1 -p 16379 SADD study:scanned:today 123 123 124
redis-cli -h 127.0.0.1 -p 16379 SCARD study:scanned:today

마지막 Set의 크기는 다른 작업이 없고 새 키였다면 2가 예상됩니다. 같은 값 123이 두 번 입력되어도 하나의 원소이기 때문입니다. 반복 실행 전에 상태가 남아 있다는 점도 실습 결과의 일부입니다. 테스트를 재현할 때는 새 키 접두사를 쓰거나 자신이 만든 키만 정리합니다.

5. TTL과 eviction: 시간이 끝난 것과 자리가 부족한 것

TTL(time to live)은 키가 유효하게 남아 있을 시간입니다. SET ... EX 60은 값 저장과 만료 설정을 하나의 명령으로 요청합니다. 값 저장 뒤 별도 EXPIRE를 보내는 사이 애플리케이션이 죽으면 만료 없는 키가 남을 수 있으므로, 처음부터 TTL이 필요한 String에는 한 명령을 쓰는 편이 낫습니다. 일반 SET으로 값을 덮어쓰면 기존 TTL이 사라질 수 있으므로, 의도한 옵션을 명시해야 합니다. SET 명령

만료(expiration)와 퇴거(eviction)는 이유가 다릅니다. 만료는 약속한 시간이 끝난 것이고, 퇴거는 메모리 한도에 맞추기 위해 정책에 따라 키를 내보내는 것입니다. TTL이 10분 남아 있어도 퇴거 대상이 될 수 있습니다. noeviction은 데이터가 무한히 들어간다는 뜻이 아니라, 한도에 도달하면 메모리가 필요한 쓰기가 오류로 실패할 수 있다는 뜻입니다. 퇴거 정책

redis-cli -h 127.0.0.1 -p 16379 SET study:ttl value EX 60
redis-cli -h 127.0.0.1 -p 16379 TTL study:ttl
redis-cli -h 127.0.0.1 -p 16379 SET study:ttl changed
redis-cli -h 127.0.0.1 -p 16379 TTL study:ttl

TTL 조회에서 -1은 키에 만료가 없음을, -2는 키가 없음을 뜻합니다. 첫 TTL은 명령 사이 시간이 흐르므로 정확히 60이라고 고정하지 않습니다. 타이머 테스트는 오차 범위와 마감 시간을 두고, CI가 바쁠 때 몇 밀리초 지연됐다고 실패하지 않도록 설계합니다. EXPIRE 설명

상품 캐시 10만 개가 모두 같은 순간에 만들어져 5분 뒤 동시에 만료되는 상황을 생각해 봅시다. 값이 없어지는 것 자체보다 그 직후 DB로 향하는 재조회가 문제입니다. TTL에 작은 무작위 차이(jitter)를 주면 재생성 시간이 분산됩니다. 단, 오래된 데이터를 얼마나 허용하는지 먼저 정해야 하며, jitter는 정합성을 보장하는 장치가 아닙니다.

기본기 보충 B. TTL은 타이머이고 eviction은 자리 정리다

TTL을 냉장고 음식의 유통기한으로 생각해 보자. 시간이 지나면 먹어서는 안 되는 음식이 된다. eviction은 냉장고 공간이 부족할 때 무엇을 꺼낼지 정하는 문제다. 유통기한이 아직 남아 있어도 공간 때문에 꺼낼 수 있고, 공간이 넉넉하다고 유통기한이 지난 음식이 다시 유효해지는 것은 아니다. 두 규칙은 목적이 다르다.

Redis에서 TTL이 있다는 이유로 키가 정해진 시간 동안 반드시 존재한다고 가정하면 안 된다. 명시적 삭제, 값 교체, eviction, 장애가 먼저 일어날 수 있다. 캐시의 정상 동작에는 miss가 포함된다. “방금 저장했으니 다음 조회는 반드시 hit”라는 전제를 동시성과 장애가 있는 환경에 무조건 적용하지 않는다.

그렇다면 TTL을 설정한 뒤에는 최신성이 완벽히 보장될까? TTL은 오래된 값이 남는 기간을 제한하는 한 수단이지만, 정확한 업무 최신성과 같은 개념은 아니다. DB가 바뀐 직후 TTL이 많이 남아 있으면 옛 값이 계속 보일 수 있다. 또 오래된 DB 조회 결과가 나중에 캐시에 들어오는 경쟁 상황이 있으면 TTL의 시작 시점도 생각해야 한다. 그래서 갱신 시 무효화, 버전 비교, 원본 확인 같은 정책이 함께 논의된다.

모든 키에 같은 TTL을 주면 관리가 쉬워 보이지만 동시에 만료될 가능성이 있다. 배치가 새벽에 많은 캐시를 한꺼번에 채우면 만료도 몰릴 수 있다. 작은 무작위 차이를 주는 jitter는 재생성 요청을 시간에 분산하는 아이디어다. 하지만 업무상 허용되는 최대 오래됨을 넘지 않도록 TTL의 범위를 정해야 한다. 무작위라는 이유로 정책의 근거가 없어져도 되는 것은 아니다.

TTL 조회 결과가 -1이면 만료가 없는 키, -2이면 키가 없는 상태를 의미한다. 이 값들을 “시간이 음수니까 오류”로 처리하면 안 된다. API가 특별한 상태를 숫자로 표현한 것이다. 실제 애플리케이션 코드에서는 라이브러리가 이런 상태를 어떤 타입과 값으로 전달하는지 확인한다. 숫자만 외우기보다 의미를 해석하는 습관이 중요하다.

6. Cache-aside와 오래된 값이 되살아나는 경주

Cache-aside는 애플리케이션이 캐시를 직접 확인하고 채우는 패턴입니다. 조회 시 캐시에 값이 있으면 반환하고(hit), 없으면(miss) DB를 조회한 뒤 캐시에 저장합니다. 단순해 보이지만 DB와 Redis는 서로 다른 시스템이므로 한쪽 성공이 다른 쪽 성공을 보장하지 않습니다.

일단 캐시에 값을 넣는 위치를 다음과 같이 그릴 수 있습니다. 아래 Java는 개념을 보이는 골격이며, 실제 DB·Redis 연결 코드가 아닙니다. 문자열을 사용해 직렬화 문제를 일부러 숨기지 않고 분리했습니다.

import java.time.Duration;
import java.util.Optional;

public final class GoodsQuery {
    interface Cache {
        Optional<String> get(String key);
        void put(String key, String value, Duration ttl);
    }
    interface Repository { Optional<String> findName(long goodsId); }
    private final Cache cache;
    private final Repository db;
    public GoodsQuery(Cache cache, Repository db) {
        this.cache = cache;
        this.db = db;
    }
    public Optional<String> name(long id) {
        String key = "goods:name:" + id;
        Optional<String> hit = cache.get(key);
        if (hit.isPresent()) return hit;
        Optional<String> value = db.findName(id);
        value.ifPresent(v -> cache.put(key, v, Duration.ofSeconds(60)));
        return value;
    }
}

이 코드가 프로덕션 완성본이 아닌 이유를 찾아봅시다. Redis 장애가 예외로 나오면 DB 조회까지 도달하지 않습니다. 반대로 예외를 모두 무시하고 DB로 우회하면 DB가 과부하될 수 있습니다. 존재하지 않는 ID는 매번 DB에 갑니다. 동일 키의 동시 miss는 여러 DB 조회를 일으킵니다. DB를 읽은 후 값을 캐시에 넣기 전 다른 요청이 데이터를 변경할 수 있습니다.

가장 중요한 경쟁 상황을 시간순으로 봅시다.

  1. 조회 요청 A가 캐시 miss를 만나 DB의 옛 이름 “배추”를 읽습니다.
  2. 수정 요청 B가 DB 이름을 “알배기배추”로 커밋합니다.
  3. B가 Redis의 상품 캐시를 삭제합니다.
  4. 늦어진 A가 예전에 읽었던 “배추”를 Redis에 저장합니다.
  5. 다음 사용자는 다시 옛 이름을 받습니다.

따라서 “DB 커밋 후 캐시 삭제”는 유용한 기본 전략이지 모든 경주를 없애는 증명이 아닙니다. TTL로 오래됨의 시간을 제한하고, 데이터 버전을 비교하거나, 갱신과 캐시 채우기를 같은 일관성 규칙 아래 묶거나, 필요한 경우 캐시를 사용하지 않는 선택까지 검토합니다. 버전 비교도 버전 정보와 값의 갱신이 원자적으로 이루어지고 모든 writer가 같은 규칙을 따를 때 의미가 있습니다.

“삭제를 두 번 하면 완벽하다”는 주장도 조심해야 합니다. 두 번째 삭제 이후까지 A가 지연되면 비슷한 문제가 남을 수 있습니다. 지연 삭제는 특정 지연 분포에서 위험을 낮추는 운영 기법일 수 있지만, 시간 가정 없이 정확성을 증명하지 못합니다. 주문·재고 확정의 최종 판단은 캐시 조회 결과만으로 내려서는 안 됩니다.

기본기 보충 A. hit와 miss를 요청 한 건의 순서로 읽기

캐시 hit는 필요한 값을 캐시에서 찾았다는 뜻이고, miss는 찾지 못했다는 뜻이다. 영어 단어 자체는 어렵지만 의미는 단순하다. 책상 위 메모에서 원하는 상품명을 찾았으면 hit이고, 메모가 없어서 원본 장부를 보러 가면 miss다. 다만 Redis 통신 오류를 miss와 자동으로 동일하게 취급하지 않는다. 값이 없는 상태와 값을 확인하지 못한 상태는 다르다.

캐시가 비어 있는 첫 요청의 순서를 천천히 보자. 애플리케이션이 Redis에서 키를 조회한다. 값이 없다는 정상 응답을 받는다. DB에서 값을 읽는다. 읽은 값을 Redis에 일정한 수명과 함께 저장한다. 사용자에게 DB에서 읽은 결과를 반환한다. 다음 요청은 아직 유효한 키가 있으면 Redis에서 값을 읽고 DB 조회를 줄일 수 있다.

이 흐름에서 Redis 저장이 실패하면 사용자 응답도 반드시 실패해야 할까? 재생성 가능한 조회 캐시라면 DB에서 얻은 값을 반환하고 캐시 쓰기 실패를 별도로 관측하는 선택이 가능하다. 하지만 캐시 쓰기 실패를 조용히 모두 무시하면 지속적인 장애를 늦게 발견할 수 있다. 사용자 응답의 성공과 캐시 갱신의 상태를 분리해 기록하는 설계가 필요하다.

반대로 Redis 읽기가 실패했을 때 무조건 DB를 조회해도 될까? 평소 초당 1만 건 중 99%를 캐시가 처리했다면 DB에는 약 100건이 도착했을 수 있다. 캐시 장애로 1만 건이 모두 DB로 향하면 100배의 조회가 될 수 있다. 이 숫자는 설명용 가정이지만, 작은 원본 부하가 캐시 덕분에 가능했던 서비스는 장애 시 부하 이동을 대비해야 한다는 원리를 보여 준다.

따라서 cache-aside 구현에는 단순 if문 외에 요청 제한, fallback 예산, 오류 분류, 관측이 붙는다. 처음부터 모든 패턴을 한꺼번에 구현할 필요는 없지만, 기본 예제가 무엇을 생략했는지 알아야 한다. 학습용 10줄 코드와 운영용 서비스가 다른 이유를 줄 수가 아니라 책임의 수로 이해하면 된다.

7. Stampede, penetration, hot key를 다른 문제로 보기

Stampede는 인기 키가 사라진 순간 여러 요청이 동시에 원본을 읽어 캐시를 채우는 현상입니다. Penetration은 존재하지 않는 데이터 요청이 캐시를 통과해 계속 원본까지 가는 상황입니다. Hot key는 한 키에 요청이 집중되는 현상입니다. 셋을 모두 “Redis 증설”로 해결할 수는 없습니다.

예를 들어 상품 A를 초당 2,000번 조회하고 DB 조회가 30ms라고 가정합시다. 캐시가 비어 있는 30ms 동안 평균 약 60개의 요청이 들어올 수 있습니다. 이 수치는 설명용 가정이며 실제 시스템의 도착 분포와 동시성에 따라 달라집니다. 같은 조회를 한 작업으로 합치거나(single-flight), 갱신 중 허용 가능한 옛 값을 제공하거나(stale-while-revalidate), TTL을 분산시키는 방식을 고려합니다.

단일 JVM 안의 single-flight는 다른 서버 인스턴스의 조회를 합쳐주지 않습니다. 분산락을 추가하면 전역 중복을 줄일 수 있지만, 락 대기·만료·장애·소유권 관리라는 새 문제가 생깁니다. 또 트래픽이 없는 키에 복잡한 락까지 넣는 것은 비용 대비 효과가 작을 수 있습니다. 어떤 키가 뜨거운지 관측하고, 원본 저장소가 버틸 수 있는 부하 예산을 먼저 정하세요.

존재하지 않는 상품을 짧게 음수 캐싱(없다는 결과를 보관)하면 반복 DB 조회를 줄일 수 있습니다. 그러나 조금 뒤 실제 상품이 생성되었는데도 없다는 응답이 남을 수 있으므로 짧은 TTL과 생성 시 무효화가 필요합니다. Bloom filter는 “없음”을 빠르게 걸러낼 수 있는 후보이지 사용자 인증이나 정확한 재고 판단을 대신하는 도구는 아닙니다. 필터 갱신 누락과 삭제·재생성 정책도 설계해야 합니다.

8. 원자성과 트랜잭션, 롤백은 같은 단어가 아니다

원자성이라는 말을 들으면 먼저 “무엇을 기준으로 하나인가?”를 물어야 합니다. 하나의 INCR는 중간 값을 다른 요청에 노출하지 않고 증가시킵니다. 하지만 GET으로 값을 읽고 Java에서 1을 더한 뒤 SET으로 쓰는 두 명령은 그 사이 다른 요청이 끼어들 수 있습니다. Redis가 명령을 순차 처리해도 애플리케이션의 여러 명령 묶음까지 저절로 하나가 되지는 않습니다.

MULTI/EXEC는 명령들을 모아 실행하며, 실행 중 다른 클라이언트 명령이 끼어들지 않는 범위를 제공합니다. 그러나 실행 단계에서 어떤 명령이 잘못된 자료형 오류를 낸다고 앞서 성공한 명령을 되돌리지 않습니다. WATCH는 읽은 키가 바뀌었는지 확인하는 낙관적 동시성 제어에 사용합니다. 충돌 후 재시도는 애플리케이션이 횟수와 시간 한도를 정해야 합니다. 트랜잭션 공식 문서

아래는 빈 로컬 학습 인스턴스에서 “실행 오류가 모든 변경을 취소하지 않는다”를 관찰하는 예입니다. 각 줄을 같은 redis-cli 세션에 입력해야 합니다.

SET study:counter 0
SET study:not-a-list hello
MULTI
INCR study:counter
LPUSH study:not-a-list x
INCR study:counter
EXEC
GET study:counter

EXEC 결과 배열에는 성공 결과와 WRONGTYPE 오류가 함께 나올 수 있습니다. 다른 변경이 없다면 counter는 2가 예상됩니다. “요청 하나가 실패했다”와 “모든 데이터 변경이 취소됐다”는 다릅니다. 큐에 넣는 단계의 문법 오류와 실행 단계의 자료형 오류도 구별해야 합니다.

Lua로 조건 확인과 변경을 한 번에 실행할 수도 있습니다. 하지만 스크립트 역시 외부 DB의 트랜잭션이 아니고 실행 오류 때 모든 이전 쓰기를 자동 롤백하지 않습니다. 키의 자료형·필수 인자·허용 범위를 먼저 확인하고 실제 쓰기는 뒤에 배치하는 설계가 중요합니다. Cluster에서 함께 처리할 키의 슬롯 제약도 17편에서 배웁니다.

기본기 보충 C. 동시성은 정말 같은 순간에 실행될 때만 생기지 않는다

두 요청이 같은 값을 읽고 각자 계산한 뒤 저장하면 최종 결과가 기대와 달라질 수 있다. 두 CPU가 완벽히 같은 나노초에 명령을 실행해야만 발생하는 문제가 아니다. 여러 단계의 작업 사이에 다른 요청의 단계가 끼어드는 것만으로 충분하다. Redis가 각 명령을 순차적으로 처리하더라도 애플리케이션의 여러 명령 전체가 하나로 묶이지 않는 이유다.

초기 재고가 10이라고 하자. 요청 A가 GET으로 10을 읽는다. 요청 B도 GET으로 10을 읽는다. A는 1을 빼서 9를 저장한다. B도 자신이 읽은 10에서 1을 빼서 9를 저장한다. 두 번 차감하려 했는데 최종값은 8이 아니라 9다. 이 현상을 lost update, 즉 갱신 유실이라고 부른다. 명령들은 차례대로 실행됐지만 업무 작업은 서로 끼어들었다.

순서 요청 A 요청 B Redis에 보관된 값
1 GET 결과 10 대기 10
2 계산 준비 GET 결과 10 10
3 SET 9 계산 준비 9
4 완료 SET 9 9

Redis의 DECR 같은 원자적 명령을 사용하면 단순 감소는 서버의 한 명령으로 처리할 수 있다. 하지만 “0보다 클 때만 감소하고 주문 ID 중복도 막는다”는 요구가 생기면 조건이 더 많아진다. 명령 하나의 기능으로 충분한지, 조건 확인과 변경을 같은 보호 범위로 묶어야 하는지 검토해야 한다. 단순 카운터와 재고 업무 전체를 같은 문제로 취급하지 않는다.

Java의 synchronized를 붙이면 해결될까? 한 JVM 안에서 같은 잠금을 사용하는 스레드들을 조율할 수는 있다. 하지만 서로 다른 애플리케이션 인스턴스의 잠금은 자동으로 공유되지 않는다. 서버 A의 synchronized와 서버 B의 synchronized는 각자의 문지기다. 공유 Redis를 여러 인스턴스가 바꾼다면 서버 쪽의 원자적 연산이나 일관된 분산 조정 방식이 필요하다.

이때도 “분산락을 쓰면 끝”이라고 넘어가지 않는다. 락의 수명, 소유자 확인, 프로세스 정지, 저장 대상의 검증 등 새로운 조건이 생긴다. 기능을 하나 추가하면 어떤 실패를 막고 어떤 실패가 남는지 구분해 설명하는 것이 이 연재의 기본 태도다.

기본기 보충 D. 원자성, 격리, 내구성을 서로 다른 질문으로 나누기

트랜잭션을 배울 때 여러 보장을 한 단어로 뭉뚱그리기 쉽다. 하지만 최소한 세 질문을 나누어 보자. 작업 중간에 다른 명령이 끼어드는가? 실패하면 앞선 변경을 되돌리는가? 성공한 변경이 장애 뒤에도 남는가? 이 질문들은 서로 다르다. 하나에 “예”라고 답한다고 나머지가 따라오지 않는다.

Redis MULTI/EXEC는 명령을 모아 실행하는 기능이다. 실행 중 다른 클라이언트의 명령이 사이에 끼어들지 않는 범위를 제공하지만, 실행 오류가 났을 때 앞서 성공한 쓰기를 SQL 트랜잭션처럼 자동으로 롤백하는 모델은 아니다. 문법 오류로 큐에 넣지 못하는 경우와 실행 중 자료형 오류가 나는 경우도 구별해야 한다. “Redis 트랜잭션은 원자적”이라는 짧은 문장만 외우면 어떤 의미의 원자성인지 설명하지 못하게 된다.

Lua 스크립트도 다른 명령의 개입 없이 조건 확인과 변경을 수행하는 데 유용하지만, 런타임 오류 이전의 변경을 자동으로 모두 되돌리는 장치가 아니다. 그래서 인자 검증, 키의 자료형 검증, 범위 검사를 실제 쓰기보다 먼저 수행하는 구성이 중요하다. 외부 DB와 함께 처리하는 일은 또 다른 경계다. Redis 안의 스크립트가 MySQL의 커밋을 대신 원자적으로 묶지는 않는다.

내구성은 별도다. Redis가 메모리에서 증가 명령을 처리하고 응답했더라도, 디스크 기록과 복제의 상태에 따라 장애 후 그 변경이 남는지가 달라질 수 있다. 04~08편에서 RDB, AOF, 복제를 나누어 공부하는 이유다. 서버 한 곳에서 명령을 안전하게 순서대로 처리하는 것과 시스템 장애 후 데이터를 보존하는 것은 서로 다른 문제다.

9. 파이프라인은 단체 배송이지 단체 트랜잭션이 아니다

한 사람에게 편지를 보내고 답장을 받아야 다음 편지를 보내는 방식은 왕복 시간이 큽니다. 파이프라이닝은 답장을 매번 기다리지 않고 여러 명령을 보내 왕복 비용을 줄이는 방식입니다. 명령 처리 자체를 무료로 만들거나 원자성을 추가하지는 않습니다. 많은 요청과 응답을 쌓아두면 클라이언트와 서버 메모리도 사용하므로 배치를 무제한 키우지 않습니다. 파이프라이닝 설명

가령 네트워크 왕복이 1ms이고 명령 작업이 0.05ms라는 가정을 두면, 단건 100회는 대략 105ms 규모로 생각할 수 있습니다. 한 번에 묶으면 왕복 횟수는 줄지만 실제 소요 시간은 버퍼·패킷·스케줄링·응답 크기에도 좌우됩니다. 이 계산은 병목을 이해하는 모형이지 보장된 성능 수치가 아닙니다.

서버가 일부 명령을 처리한 뒤 연결이 끊기면 어느 명령까지 처리되었는지 모를 수 있습니다. 파이프라인 전체를 그대로 다시 보내면 INCR가 중복될 수 있습니다. “더 빠르게 보내기”와 “실패를 정확히 처리하기”는 각각 설계해야 합니다. 23편에서는 처리량만 높게 보이는 벤치마크 대신 지연 분포와 실제 요청 패턴을 함께 측정합니다.

10. 타임아웃이 의미하는 것은 실패가 아니라 결과 불확실일 수 있다

요청을 보냈는데 제한 시간 안에 응답이 안 왔습니다. 가능한 원인은 여러 가지입니다. 서버에 도착하지 않았을 수도 있고, 서버 큐에서 기다릴 수도 있고, 실행은 끝났지만 응답만 늦었을 수도 있습니다. 그래서 “타임아웃이면 무조건 다시 실행”은 쓰기 연산에서 위험합니다.

입고 수량 3을 더하는 요청이 실행된 뒤 응답만 유실되었다면, 재시도로 3을 다시 더하면 실제 입고 3개가 6개가 됩니다. 요청마다 안정적인 업무 ID를 만들고, 이미 처리했는지 판단하는 결과와 변경을 같은 보호 범위에서 기록하는 멱등 설계가 필요합니다. Redis에서 중복 방지 키만 먼저 저장하고 DB 변경 전에 죽으면, 재시도가 막혀 실제 업무는 수행되지 않는 반대 문제가 생깁니다.

외부 DB의 확정 작업이라면 DB 고유 제약·업무 상태 전이·트랜잭션·Outbox와 연결하는 편이 자연스러울 수 있습니다. Redis는 조회 가속이나 중복 요청의 부하 완화에 활용하되 정확성의 마지막 근거가 무엇인지 분명히 합니다. 네트워크가 있는 시스템에서는 실패 응답 하나에 최종 업무 결과를 모두 담을 수 없을 때가 있습니다. 이때 조회 가능한 처리 ID와 대조 절차가 중요합니다.

기본기 보충 E. 타임아웃 뒤에는 세 개의 이야기가 가능하다

타임아웃은 정해진 시간 안에 결과를 받지 못했다는 관측이다. 요청이 실행되지 않았다는 확정 통보가 아니다. 택배 주문을 보냈는데 확인 메시지를 못 받은 상황을 생각해 보자. 주문이 접수되지 않았을 수도 있고, 접수되어 처리 중일 수도 있고, 처리됐는데 확인 메시지만 늦었을 수도 있다. 같은 “응답 없음”에서 서로 다른 실제 상태가 가능하다.

Redis에서도 첫째, 요청이 서버에 도착하지 않았을 수 있다. 둘째, 도착했지만 아직 실행되지 않았을 수 있다. 셋째, 이미 실행되었는데 응답만 받지 못했을 수 있다. 클라이언트의 타임아웃 예외만으로 셋을 항상 구별할 수는 없다. 따라서 쓰기 요청의 재시도는 명령이 두 번 실행될 가능성을 고려해야 한다.

예를 들어 입고 수량을 3 증가시키는 INCRBY를 보냈다. 서버는 증가시켰지만 응답이 사라졌다. 클라이언트가 같은 명령을 다시 보내면 추가로 3이 증가할 수 있다. “실패했으니까 재시도”라는 문장은 클라이언트의 관측 실패와 업무 처리 실패를 혼동한 것이다. 이런 경우를 다루기 위해 안정적인 요청 ID와 처리 결과 조회가 중요해진다.

멱등성은 같은 요청을 여러 번 처리해도 의도한 업무 효과가 한 번 처리한 것과 같도록 만드는 성질이다. 여기서 중요한 단어는 같은 요청이다. 재시도할 때마다 새 UUID를 만들면 서버는 서로 다른 요청으로 볼 수 있다. 업무 요청이 처음 만들어질 때 부여한 식별자를 재시도에도 유지해야 한다. 요청 ID의 범위와 보존 기간도 업무 계약의 일부다.

또한 중복 방지 키와 실제 변경을 따로 쓰면 그 사이에 실패 구간이 생긴다. 먼저 “처리했음”을 기록한 뒤 실제 변경 전에 죽으면 변경하지 않았는데 재시도가 막힌다. 먼저 변경한 뒤 기록 전에 죽으면 재시도가 중복 변경을 만들 수 있다. 같은 저장소 안에서 보호 범위를 묶을 수 있는지, 외부 DB 트랜잭션과 연결해야 하는지 검토해야 한다.

이 내용을 처음부터 모든 구현으로 외울 필요는 없다. 우선 “타임아웃은 결과 불확실일 수 있다”와 “재시도는 같은 업무를 다시 실행할 수 있다”를 정확히 기억하자. 뒤의 Lua, 복제, 장애 전환을 공부할 때 이 두 문장이 계속 등장한다.

Java 사고 실험. 중복 처리 방지와 변경을 한 경계로 묶어 보기

아래 코드는 Redis 구현이 아니라 단일 JVM 안의 학습 모델이다. 요청 ID별 결과를 기억하고 재고 변경과 결과 기록을 한 synchronized 구간에 둔다. 네트워크와 장애 복구를 일부러 제외해, 중복 요청의 의미부터 읽을 수 있게 했다. Java 21에서 독립 실행할 수 있다.

import java.util.HashMap;
import java.util.Map;
import java.util.Objects;

public final class IdempotentStockLesson {
    record Result(boolean accepted, int remaining) {}
    record Processed(int quantity, Result result) {}

    static final class Stock {
        private int remaining;
        private final Map<String, Processed> processed = new HashMap<>();

        Stock(int initial) {
            if (initial < 0) throw new IllegalArgumentException("negative stock");
            this.remaining = initial;
        }

        synchronized Result reserve(String requestId, int quantity) {
            Objects.requireNonNull(requestId);
            if (requestId.isBlank() || quantity <= 0) {
                throw new IllegalArgumentException("invalid request");
            }
            Processed prior = processed.get(requestId);
            if (prior != null) {
                if (prior.quantity() != quantity) {
                    throw new IllegalArgumentException("request ID reused with new quantity");
                }
                return prior.result();
            }
            boolean accepted = remaining >= quantity;
            if (accepted) remaining -= quantity;
            Result result = new Result(accepted, remaining);
            processed.put(requestId, new Processed(quantity, result));
            return result;
        }
    }

    public static void main(String[] args) {
        Stock stock = new Stock(10);
        Result first = stock.reserve("receiving-001", 3);
        Result retry = stock.reserve("receiving-001", 3);
        Result second = stock.reserve("receiving-002", 2);
        if (!first.equals(retry)) throw new AssertionError("retry changed result");
        if (first.remaining() != 7) throw new AssertionError("first request");
        if (second.remaining() != 5) throw new AssertionError("duplicate subtraction");
        System.out.println("first=" + first);
        System.out.println("retry=" + retry);
        System.out.println("second=" + second);
    }
}

processed는 요청 ID를 처리 결과와 연결한다. 같은 ID가 다시 들어오면 재고를 다시 줄이지 않고 기록한 결과를 반환한다. 결과에 quantity도 함께 저장한 이유는 같은 ID로 다른 수량을 보냈을 때 잘못된 결과를 재사용하지 않기 위해서다. 업무 요청을 식별한다는 것은 문자열만 같다는 뜻이 아니라 그 ID가 어떤 입력을 대표하는지도 정한다는 뜻이다.

실패한 재고 예약도 기록한다는 점을 주목하자. 첫 요청 때 재고가 부족했다면 같은 요청 ID의 재시도는 이전 실패 결과를 돌려준다. 이후 재고가 보충되었더라도 같은 ID를 새 시도로 취급하지 않는 정책이다. 이것이 모든 서비스의 정답은 아니다. 실패를 얼마나 오래 기억할지, 새로운 업무 시도에 새 ID를 부여할지 요구에 맞게 결정해야 한다. 멱등 처리에도 제품 정책이 들어간다.

synchronized는 이 객체를 공유하는 같은 JVM의 스레드 사이에서 메서드 실행을 조율한다. 다른 JVM의 Stock 객체와는 아무 관계가 없다. 또한 프로세스가 종료되면 remaining과 processed가 함께 사라진다. 저장 도중의 장애를 복구하는 영속성 구현도 없다. 따라서 이 예제를 그대로 여러 서버의 재고 처리에 사용하면 안 된다. 모델이 보여 주는 것은 중복 판정과 변경의 논리적 결합이다.

실제 저장소로 옮길 때는 그 결합을 어떻게 유지할지 다시 묻는다. Redis 안의 키들로 처리한다면 원자적 스크립트와 키 배치 조건, 영속성 및 복제의 한계를 고려한다. DB가 최종 근거라면 고유 제약과 트랜잭션으로 요청 기록과 업무 변경을 묶는 설계를 고려한다. 어떤 저장소를 쓰든 처리 기록과 실제 효과가 갈라지는 구간을 숨기면 안 된다.

11. 분산락이 재고 정합성을 대신해 주지는 않는다

분산락은 여러 프로세스가 같은 작업을 동시에 하지 않도록 조율하는 수단입니다. 흔한 기본은 소유자별 고유 토큰을 값으로 넣고 NX와 만료를 함께 설정하는 것입니다. 해제할 때 단순 DEL 대신 현재 값이 자기 토큰인지 확인해야, 만료 후 다른 사람이 얻은 락을 지우지 않습니다. 분산락 공식 패턴

그러나 안전한 해제만으로 모든 문제가 끝나지는 않습니다. 작업자 A가 락을 얻고 오랫동안 멈췄습니다. TTL이 끝나 B가 락을 얻어 작업합니다. A가 깨어나 자신이 여전히 소유자라고 생각하며 DB를 변경하면 둘이 동시에 일할 수 있습니다. 락 연장도 프로세스 정지와 네트워크 분할이라는 가정을 지워주지는 않습니다.

이 상황에서 저장 대상이 단조 증가하는 권한 번호(fencing token)를 검사해 오래된 작업자의 쓰기를 거절하도록 만들 수 있습니다. 하지만 토큰을 발급하기만 하고 DB가 비교하지 않으면 아무 효과가 없습니다. 토큰 생성 자체의 장애 후 단조성도 요구 조건입니다. “Redisson을 썼다”라는 라이브러리 선택과 “실패한 소유자의 늦은 쓰기가 막힌다”라는 정확성 증명은 다른 일입니다.

실무 질문으로 바꾸면 더 쉽습니다. “락을 잡은 다음 JVM이 40초 멈추고 락 TTL은 30초라면 어떤 일이 생기는가?”에 답할 수 있어야 합니다. 30초와 40초는 사고를 설명하는 가정이며 적정 TTL 권고가 아닙니다. 업무 처리 시간의 분포, 정지 시간, 장애 시 복구 정책을 함께 고려하세요.

  • Redis 오류 시 어떤 기능은 우회하고 어떤 기능은 실패시키는가?
  • 재시도 대상 명령은 멱등한가? 요청 ID를 계속 유지하는가?
  • Sentinel/Cluster 전환 후 새 토폴로지를 어떻게 발견하는가?
  • 직렬화 형식이 변경되면 기존 캐시를 읽을 수 있는가? 키에 버전 접두사가 필요한가?
  • TTL과 최대 값 크기, hot key 지표를 어떤 대시보드에서 확인하는가?

예를 들어 JSON 필드 이름을 바꾼 새 배포와 이전 배포가 동시에 실행되면 둘이 같은 키를 서로 다른 형식으로 읽을 수 있습니다. 블루그린 배포에서는 서버 수만 두 배가 되는 것이 아니라 캐시를 읽고 쓰는 코드 버전도 둘이 될 수 있습니다. 키 버전을 나누면 호환성 위험은 낮아지지만 캐시 적중률 하락과 일시적 메모리 중복이라는 비용이 생깁니다.

운영 입문. 복제, 영속성, 백업은 왜 세 과목인가

복제는 다른 Redis 서버가 데이터를 따라오게 하는 기능이다. 한 서버가 사용할 수 없을 때 다른 복제본을 활용하는 설계의 재료가 된다. 그러나 잘못된 삭제도 복제될 수 있다. 복제본이 있다는 이유로 어제의 올바른 데이터를 꺼낼 수 있다고 보장하지 않는다. 복제는 시간 여행 기능이 아니다.

영속성은 프로세스의 메모리에 있던 데이터를 디스크에 남기고 복원하는 경로다. RDB와 AOF는 기록 방식과 복구 특성이 다르다. 하지만 디스크가 같은 장애 영역에 있거나 파일이 손상되거나 잘못된 변경이 반영되면 영속성만으로 모든 사고를 해결할 수 없다. 파일이 존재하는지와 원하는 시점의 데이터를 복원할 수 있는지는 다른 질문이다.

백업은 복원 가능한 사본을 적절한 위치와 시점에 보관하는 운영 체계다. 파일을 복사했다는 사실만으로 백업이 완성되지는 않는다. 그 사본을 다른 환경에 복원해 데이터와 기능을 확인할 수 있어야 한다. 접근 권한, 보관 기간, 암호화, 삭제 사고로부터의 분리도 중요하다. 백업은 명령 하나보다 복구 절차에 가깝다.

쉽게 비유하면 복제는 옆 직원이 현재 장부를 따라 적는 것이고, 영속성은 작업 중인 내용을 보관 가능한 장부에 기록하는 것이며, 백업은 특정 시점의 장부 사본을 별도 장소에 보관하는 것이다. 세 비유는 완전히 정확한 구현 설명은 아니지만, 어떤 사고를 대비하는지 구별하는 데 도움이 된다.

이 구별을 알고 04~08편을 읽으면 옵션 이름이 목적과 연결된다. “AOF를 켰다”보다 “어떤 시점까지의 손실을 허용하고 어떤 장애에서 복원할까?”가 먼저다. “replica가 두 개다”보다 “어떤 데이터까지 받았고 누가 새 primary를 찾을까?”가 먼저다.

운영 입문. Sentinel과 Cluster를 하나의 축으로 줄 세우지 않기

Sentinel과 Cluster를 처음 접하면 초급과 고급 제품처럼 생각하기 쉽다. 그러나 해결하려는 문제가 다르다. Sentinel은 주로 primary와 replica 집합을 감시하고 장애 전환을 조정하며 클라이언트가 현재 primary를 찾도록 돕는 역할을 한다. 데이터 전체를 여러 primary에 자동으로 나누는 샤딩 기능과는 다르다.

Cluster는 키들을 슬롯에 대응시키고 여러 primary에 나누어 배치하는 모델이다. 데이터를 나누면 한 서버에 모든 키를 넣지 않을 수 있지만, 함께 처리할 여러 키가 서로 다른 곳에 있을 수 있다는 제약이 생긴다. 같은 저장소처럼 보이는 API 뒤에서 클라이언트가 올바른 노드를 찾고 이동 중인 키에 대응해야 한다. 13~19편에서 그 과정을 다룬다.

초보자에게 중요한 질문은 “어느 것이 더 좋나요?”보다 “무엇이 부족한가요?”다. 한 primary의 용량과 처리 한계는 충분하지만 자동 장애 전환이 필요하다면 한 종류의 설계를 검토한다. 데이터를 여러 primary에 나누어야 한다면 다른 조건이 추가된다. 단순히 노드 수가 많으면 상위 호환이라고 생각하지 않는다. 노드가 늘면 장애 감지와 운영 경로도 늘어난다.

또한 어떤 구성도 클라이언트의 재시도와 업무 멱등성을 자동으로 끝내 주지 않는다. primary가 바뀌는 동안 결과를 못 받은 쓰기가 있을 수 있다. 이전 노드와 새 노드가 어떤 상태인지, 클라이언트가 언제 새 주소를 알게 되는지, 비동기 복제의 유실 가능성을 어떻게 받아들이는지 알아야 한다. 기초의 타임아웃 질문이 고가용성 구성에서도 그대로 이어진다.

13. 실습 기록을 남기는 방법

실습 결과를 “잘 됨” 한 줄로 남기면 나중에 무엇을 검증했는지 알 수 없습니다. 다음 항목을 같이 적으세요.

  1. Redis 서버 버전, 클라이언트 버전, Java 버전과 실행 OS.
  2. 단일 노드인지, replica가 있는지, Sentinel/Cluster인지.
  3. 변경한 설정과 데이터 크기, 요청 수, 동시 연결 수.
  4. 명령을 보낸 시각과 오류를 관측한 시각, 서버 로그와 지표.
  5. 예상 결과와 실제 결과, 재현하지 못한 조건.
  6. 만든 키·프로세스·파일을 어떻게 안전하게 정리했는지.

이 시리즈의 학습 코드는 운영 서버를 향하도록 작성되지 않았습니다. 직접 재현할 때도 먼저 주소와 포트를 출력하고, 폐기 가능한 인스턴스인지 확인하세요. 장애 실험·강제 종료·ACL 변경·디스크 복구는 개인 학습 인스턴스에서 수행합니다. 백업을 “만들어 봤다”와 “다른 인스턴스에 복원해 업무 데이터를 대조했다”는 다른 검증입니다.

학습 방법 보충. 한 편을 네 번 나누어 읽어도 괜찮다

이 연재는 한 번에 모든 세부를 외우기 위한 글이 아니다. 처음에는 무엇이 문제인지와 비유만 읽어도 된다. 두 번째에는 명령이 처리되는 순서를 따라간다. 세 번째에는 작은 실습과 예상 결과를 비교한다. 네 번째에는 면접 질문을 접은 상태에서 자기 말로 설명한 뒤 답변을 펼쳐 빠진 조건을 확인한다. 긴 글을 여러 번 읽는 것은 실패가 아니라 학습 방법이다.

각 편에서 새 용어를 만나면 세 칸으로 메모해 보자. 첫 칸에는 쉬운 뜻을 적고, 두 번째에는 어디에 쓰이는지 적고, 세 번째에는 무엇을 보장하지 않는지 적는다. 예를 들어 TTL은 “유효한 수명”, “캐시의 오래됨과 보관 기간 관리”, “그 시간 동안 반드시 존재하거나 최신임을 보장하지 않음”으로 적을 수 있다. 뜻만 외우는 것보다 오해를 줄이는 데 도움이 된다.

실습은 결과를 예측한 뒤 실행하는 편이 좋다. 예측 없이 명령을 따라 치면 출력이 맞는지 틀린지 판단하기 어렵다. SET으로 값을 덮어쓴 뒤 TTL이 어떻게 될지 먼저 생각하고, 실제 결과를 확인한 뒤 왜 그런지 설명한다. 예상과 다른 결과가 나왔을 때 버전과 입력 조건을 조사하는 과정이 이해를 만든다.

면접 답변은 길게 말하는 연습과 짧게 말하는 연습을 나눈다. 먼저 30초 안에 핵심과 한계를 말한다. 그 다음 요청받으면 내부 순서, 예제, 실패 시나리오를 풀어 설명한다. 자세한 교재를 읽는 목적은 언제나 길게 답하기 위해서가 아니라, 짧게 답할 때도 근거가 흔들리지 않게 하기 위해서다.

스스로 확인할 기준은 다음과 같다. 용어를 다른 말로 설명할 수 있는가? 명령 두세 개의 순서를 바꾸면 결과가 왜 달라지는지 말할 수 있는가? 정상 상황 외에 실패 한 가지를 제시할 수 있는가? 확인에 필요한 지표나 명령을 하나 고를 수 있는가? 네 질문에 답하면 다음 편으로 넘어가도 좋다. 모든 옵션의 기본값을 외울 때까지 멈춰 있을 필요는 없다.

14. 접었다 펼치는 기초 면접 문답

Q1. Redis가 빠르다는 말만으로 선택하면 왜 부족한가요?

속도는 요구사항 중 하나일 뿐입니다. 데이터의 최종 근거, 손실 허용 범위, 오래된 조회 허용 시간, 장애 시 우회 정책을 먼저 정해야 합니다. 예를 들어 상품 설명 캐시는 DB에서 복원할 수 있지만 Redis에만 있는 입고 작업 상태는 같은 방식으로 버릴 수 없습니다. 답변할 때는 “조회 가속 목적이며 원본은 MySQL, Redis 장애 때는 DB 부하 한도 안에서만 우회”처럼 실패 정책까지 붙이면 설계가 구체적입니다.

Q2. TTL이 있으니 메모리 부족과 오래된 값 문제는 모두 해결되나요?

아닙니다. TTL은 키의 유효 시간을 제한하지만 입력 속도와 값 크기가 충분히 크면 만료되기 전에 메모리 한도에 닿을 수 있습니다. 또한 TTL 동안에는 오래된 값이 남을 수 있고, 잘못된 값으로 갱신되면 그 시점부터 다시 TTL이 시작될 수 있습니다. 메모리 정책과 갱신 정합성 정책을 따로 설계해야 합니다. 무조건 짧게 줄이면 원본 조회 부하가 늘어나는 점도 함께 설명해야 합니다.

Q3. DB 수정 후 캐시 삭제를 하면 항상 최신 데이터가 보이나요?

아닙니다. DB 수정 전 값을 읽은 느린 조회가 캐시 삭제 뒤 옛 값을 다시 넣는 경주가 가능합니다. 먼저 시간순으로 A의 조회, B의 커밋, B의 삭제, A의 저장을 그려 설명하세요. 요구되는 최신성에 따라 TTL, 버전 검사, 갱신 규칙, 원본 직접 조회 등을 선택합니다. 단순히 “삭제를 한 번 더 한다”는 방법만으로 무한한 지연과 모든 실패를 해결했다고 말해서는 안 됩니다.

Q4. Redis는 단일 스레드라서 GET 후 SET도 안전하지 않나요?

개별 명령의 실행 순서와 애플리케이션의 여러 명령을 하나로 묶는 것은 다릅니다. A가 GET한 뒤 B가 GET·SET을 끝내고 A가 옛 값에 기반한 SET을 하면 갱신이 사라질 수 있습니다. 숫자 증가라면 INCR, 조건에 따른 변경이라면 적절한 Lua나 WATCH 기반 재시도를 검토합니다. Redis 프로세스 전체에 스레드가 하나뿐이라는 뜻으로 단순화하지 않는 것도 중요합니다.

Q5. MULTI/EXEC는 MySQL 트랜잭션과 무엇이 다른가요?

Redis는 묶인 명령의 실행 중 다른 명령이 끼어들지 않는 성질을 제공하지만 실행 중 오류가 발생했다고 이미 수행된 변경을 모두 롤백하지 않습니다. 오류가 명령을 큐에 넣는 시점인지 실행하는 시점인지도 구분해야 합니다. MySQL과 Redis를 하나의 트랜잭션처럼 사용하려면 두 시스템 사이 커밋 경계를 별도로 설계해야 하며, Spring 애너테이션 이름이 같다는 이유로 분산 원자성이 생기지 않습니다.

Q6. 파이프라인을 쓰면 명령 전체가 원자적인가요?

아닙니다. 파이프라인은 응답을 매번 기다리는 비용을 줄이는 전송 방식입니다. 원자적 조건 확인·갱신과는 목적이 다릅니다. 배치 크기가 지나치게 크면 버퍼 메모리와 지연에 부담을 줄 수 있고, 연결 중단 뒤 부분 성공을 다루는 문제도 남습니다. 성능 개선을 설명할 때는 왕복 감소와 실행 보장을 분리하는 것이 핵심입니다.

Q7. INCR가 타임아웃이면 재시도하면 되나요?

서버가 이미 증가시켰지만 응답이 유실되었을 수 있어 단순 재시도는 중복을 만들 수 있습니다. 먼저 결과 불확실 상태를 인정해야 합니다. 업무 ID로 중복을 판단하고 결과를 조회할 수 있게 하거나, 최종 저장소의 멱등 제약을 사용합니다. 단순한 통계 카운터라면 일부 오차를 허용할 수 있지만 입고 확정 수량에는 같은 판단을 적용하면 안 됩니다.

Q8. 분산락을 쓰면 재고가 절대 틀리지 않는다고 할 수 있나요?

그렇게 단정할 수 없습니다. 락 만료 후 이전 소유자가 재개하거나 장애 전환 중 락 정보가 사라지는 조건을 따져야 합니다. 안전한 토큰 비교 해제, 필요 시 저장 대상의 fencing 검사, DB 제약과 업무 멱등성이 각각 어떤 실패를 막는지 구분합니다. 락을 업무 정확성의 유일한 장벽으로 쓰기 전에 프로세스 정지와 네트워크 분할의 시간순 시나리오를 검증해야 합니다.

Q9. Sentinel과 Cluster 중 어느 것이 더 좋은가요?

문제가 다릅니다. Sentinel은 일반적으로 한 primary와 replica 집합의 장애 감시·전환과 위치 발견에 사용합니다. Cluster는 여러 primary에 키를 분할하며 슬롯과 리다이렉션을 다룹니다. 데이터와 부하가 한 primary에 들어가는지, 다중 키 연산이 필요한지, 운영 복잡성을 감당할 수 있는지부터 봅니다. 노드 수가 많다는 사실 자체가 더 강한 일관성이나 무손실을 뜻하지 않습니다.

Q10. 이 30편만 읽으면 Redis 전체를 공부한 건가요?

아닙니다. 제공 자료는 운영 문서 중심이며 이 안내에서 개발 기본기를 보충합니다. 검색·벡터·모듈·제품별 관리형 기능 전체를 포괄하지 않습니다. 목표는 Java/Spring 백엔드 개발자가 설정, 실패 보장, 관측, 복구와 코드의 경계를 설명할 수 있게 되는 것입니다. 부족한 범위를 숨기기보다 자신의 서비스에 필요한 기능을 공식 문서와 실행 버전에 맞춰 추가하는 것이 좋습니다.

Q11. Java Map 대신 Redis를 쓰는 이유를 초보자에게 설명해 주세요.

Map은 보통 해당 Java 프로세스 안의 자료구조이고 Redis는 별도 서버를 통해 여러 클라이언트가 데이터를 공유할 수 있는 저장소다. Redis는 자료형별 연산, 만료, 영속성 및 복제 같은 기능을 제공할 수 있다. 하지만 네트워크 지연과 통신 실패, 공유 데이터의 동시성, 운영 비용이 추가된다.

따라서 “Redis가 무조건 더 빠르기 때문”이라고 답하지 않는다. 프로세스 내부 Map 접근보다 네트워크 요청이 더 많은 비용을 가질 수 있다. 필요한 것은 여러 인스턴스의 공유인지, 수명 관리인지, 서버 측 원자적 연산인지 먼저 설명한다. 로컬 캐시가 적합한 경우와 중앙 캐시가 필요한 경우도 다르다.

Q12. 캐시 miss와 Redis 장애는 같은 처리로 묶어도 되나요?

둘은 다른 사건이다. miss는 서버에 정상적으로 물어봤고 필요한 값이 없다는 결과를 받은 것이다. 장애는 값을 확인하지 못했거나 요청 처리에 문제가 생긴 것이다. 제품 정책상 둘 다 DB 조회로 이어질 수는 있지만 관측과 부하 제한까지 동일하게 숨기면 안 된다.

예를 들어 Redis가 계속 실패하는데 모두 정상 miss로 기록하면 캐시 장애를 늦게 발견할 수 있다. DB로 갑자기 요청이 몰리는 것도 제어하기 어렵다. 사용자 응답 경로와 내부 오류 관측을 분리하고, 장애 fallback에 별도 예산과 제한을 둔다고 설명하는 것이 좋다.

Q13. 멱등성을 위해 요청마다 UUID를 생성하면 충분한가요?

식별자를 만든다는 것과 재시도에서 같은 업무를 식별한다는 것은 다르다. 재시도할 때마다 새 UUID를 만들면 서버가 서로 다른 요청으로 볼 수 있다. 최초 업무 요청의 ID를 유지하고, 같은 ID가 어떤 입력과 결과에 대응하는지 기록해야 한다.

기록과 실제 변경의 원자적 관계도 필요하다. 기록만 남고 변경이 안 되거나, 변경만 되고 기록이 안 되는 실패 구간이 있으면 중복 또는 누락이 생긴다. ID의 생성 위치, 재사용 규칙, 보존 기간, 충돌 시 처리까지 함께 설명해야 한다.

Q14. Redis에서 원자적으로 처리했으면 장애 뒤에도 안전한가요?

원자적 실행과 장애 후 내구성은 다른 보장이다. 다른 명령이 중간에 끼어들지 않게 처리했더라도, 그 변경이 어떤 디스크 기록과 복제 상태에 있는지에 따라 장애 후 결과가 달라질 수 있다. 메모리 안의 순서 보장만으로 모든 장애에서 데이터가 남는다고 말할 수 없다.

면접에서는 먼저 어떤 작업의 원자성인지 설명하고, 영속성·복제·복구의 조건을 따로 말한다. 외부 DB와 함께 처리하는 업무라면 시스템 간 경계도 추가한다. 보장 범위를 정확히 나누는 답변이 기능 이름 하나로 전체 안전성을 약속하는 답변보다 낫다.

Q15. 이 연재를 공부한 뒤 실제 서비스에 적용할 첫 단계는 무엇인가요?

설정을 바로 바꾸기보다 현재 Redis의 역할부터 기록하는 것이 좋다. 어떤 키가 재생성 가능한 캐시이고 어떤 키가 중요한 상태인지, TTL과 크기 상한은 무엇인지, 장애 시 어떤 코드 경로가 실행되는지 확인한다. 이어 서버 버전과 구성, 클라이언트 버전, 오류와 지연 지표를 연결한다.

그 다음 격리 환경에서 작은 실험으로 가설을 확인한다. 운영 변경이 필요하면 목적, 대상, 기존값, 새 값, 확인 지표와 되돌릴 조건을 정한다. 이 연재의 실습이 작은 로컬 인스턴스부터 시작하는 이유는 명령 사용법과 운영 변경의 책임을 단계적으로 배우기 위해서다.
