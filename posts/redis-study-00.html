1. 이 시리즈가 해결하려는 문제

Redis를 공부할 때 처음 만나는 설명은 보통 “메모리에 저장하므로 빠르다”입니다. 그 말만으로는 운영 문제를 풀 수 없습니다. 빠른 저장소가 갑자기 응답하지 않을 때, 요청을 다시 보내도 되는지, replica로 읽어도 되는지, 성공 응답을 받은 재고 차감이 장애 뒤 사라질 수 있는지를 판단해야 하기 때문입니다. 이 시리즈는 명령이 성공한 순간부터 장애 후 복구까지 데이터가 어떻게 움직이는가를 이해하는 데 초점을 맞춥니다.

입고 시스템을 생각해 봅시다. 작업자가 PDA로 상품을 스캔하면 상품명은 잠깐 오래된 값이어도 업무를 계속할 수 있을 수 있습니다. 반면 입고 확정 수량을 두 번 더하거나 작업 완료 기록을 잃으면 재고 정합성 문제가 됩니다. 두 데이터에 같은 TTL과 같은 재시도 정책을 적용하면 안 됩니다. 기술 이름보다 먼저 데이터의 역할과 허용 가능한 실패를 정하는 연습을 할 것입니다.

출발 자료는 제공된 Redis 운영 문서 공부팩입니다. 운영 설정·영속성·복제·Sentinel·Cluster·성능·보안·내부 구현의 주 학습 30편을 한국어 교재로 재구성했습니다. 원본 전체 Redis 개발 문서를 번역한 자료는 아닙니다. 이 안내는 원본에 빠져 있던 기본기를 별도로 보충합니다. 원본 파일에 있던 “latest”는 고정된 제품 버전이 아닙니다. 문서 설명과 실제 실행 버전을 구별하고, 버전에 민감한 옵션은 해당 편의 출처와 사용 중인 서버를 함께 확인하세요.

각 편의 장애 사례는 학습용 시나리오입니다. 명령의 예상 출력은 실행 증거가 아닙니다. 독립 실행 가능한 Java 21 실습 코드와 실제 단일 서버 검사 기록도 제공합니다. 실제 수행된 검사와 제외된 범위는 검증 기록에 분리합니다. 코드가 컴파일된 사실과 다중 노드 장애 안전성을 검증한 사실도 같지 않습니다.

  • Cluster: 데이터를 여러 primary에 나누고, 클라이언트가 올바른 노드를 찾아가는 과정을 배웁니다. 어떤 다중 키 연산이 가능한지 함께 살핍니다.
  • 성능·보안·구현: 느린 요청을 측정 구간별로 나누고, 필요한 권한만 주며, 내부 자료구조와 이벤트 루프까지 내려갑니다.

각 편을 읽은 뒤 “어떤 조건에서 보장되는가?”, “어떤 실패에서 깨지는가?”, “어떤 지표로 확인할까?”, “복구 후 무엇을 대조할까?”라는 네 질문에 자기 말로 답해 보세요. 이름을 외우는 대신 조건을 설명할 수 있으면 면접과 운영 모두에 도움이 됩니다.

3. Redis를 책상, 데이터베이스를 장부라고 생각해 보기

작업자는 장부 보관실에 매번 가는 대신 자주 보는 상품 정보를 책상 위 메모에 적습니다. 메모가 있으면 빨리 읽고, 없으면 장부에서 찾아 다시 적습니다. 이것이 뒤에서 설명할 cache-aside의 출발점입니다. 책상에는 공간 한계가 있고, 종이가 오래되면 버려야 하며, 다른 사람이 장부를 고쳤는데 메모가 그대로면 잘못된 내용을 보게 됩니다.

이 비유에는 한계가 있습니다. Redis가 언제나 “버려도 되는 메모”인 것은 아닙니다. 세션·작업 상태·대기열·카운터 등 서비스가 복원하기 어려운 데이터를 보관할 수도 있습니다. 그러면 메모를 잃어도 괜찮다는 전제부터 바뀝니다. 캐시용 Redis를 운영하던 설정을 그대로 대기열 저장소에 복사하면, 메모리 부족 시 키를 내보내는 정책 때문에 업무 데이터가 사라질 수 있습니다.

**원본 데이터(source of truth)**란 충돌이 났을 때 최종적으로 믿을 근거입니다. 상품 조회 캐시는 MySQL에서 재생성할 수 있지만, Redis에만 있던 대기 순번은 MySQL에 없다면 재생성할 수 없습니다. “Redis를 쓴다”는 말 대신 다음처럼 요구사항을 적어야 합니다.

데이터 최종 근거 허용 가능한 손실/오래됨 장애 시 선택
상품 설명 캐시 MySQL 업무에서 정한 짧은 지연 조회량 제한을 두고 DB 조회
재고 확정 기록 보통 DB의 트랜잭션 기록 중복·유실 불허 요구 멱등키·고유 제약·이력 대조
임시 대기 순번 설계에 따라 Redis 서비스 계약에 따라 결정 재입장 정책 또는 영속화
API 호출 횟수 Redis 또는 별도 집계 정확도 요구에 따라 결정 보수적 제한/임시 차단/허용 중 선택

표는 정답이 아니라 요구사항을 쓰는 예시입니다. 특히 장애 시 무조건 DB로 우회하면 평소 캐시가 흡수하던 요청이 DB에 몰려 두 번째 장애를 만들 수 있습니다.

4. 키, 값, 자료구조를 처음부터 구분하기

키(key)는 보관함 이름이고 값(value)은 그 보관함의 내용입니다. goods:123:name과 goods:124:name은 다른 키입니다. 콜론은 사람이 읽기 쉽게 정한 규칙일 뿐 디렉터리를 자동 생성하지 않습니다. 문자열 키 아래에 어떤 자료구조의 값을 둘지 선택합니다.

자료구조 쉬운 그림 입고 도메인의 예 주의점
String 한 장의 값 또는 숫자 상품 JSON, 단순 카운터 숫자 문자열만 증가 연산 가능
Hash 한 객체의 이름 붙은 칸들 상품의 이름·상태·센터 코드 필드별 조회가 가능해도 전체 조회는 크기에 비례
List 앞뒤로 넣고 빼는 줄 간단한 처리 목록 신뢰성 있는 작업 처리에는 ACK·재처리 설계 필요
Set 중복 없는 이름표 모음 오늘 스캔한 상품 ID 정렬된 순서가 없음
Sorted Set 점수 붙은 이름표 입장 시간순 대기열 같은 점수의 정렬 기준과 동시성 고려
Stream ID 붙은 이벤트 기록 작업 이벤트 소비 ACK·보존·재처리·멱등 처리 필요

이 표는 선택을 돕는 독자적인 업무 예시이며, 지원 명령과 버전별 확장은 공식 자료구조 안내에서 확인합니다. 자료형 이름과 메모리 안의 구현은 다릅니다. 예를 들어 같은 Hash라도 원소 개수와 크기에 따라 압축된 표현이나 해시 테이블 표현을 사용할 수 있습니다. 03편에서 이 차이를 다룹니다.

명령 시간 복잡도도 익혀야 합니다. O(1)은 데이터 전체 개수와 무관한 작업량이라는 뜻이지, 네트워크·큰 응답·메모리 압력까지 항상 일정하다는 뜻이 아닙니다. O(N)은 살펴봐야 할 원소가 늘수록 일이 늘어난다는 뜻입니다. 작은 개발 데이터에서 빠른 전체 조회 명령이 운영의 거대한 키에서는 이벤트 루프를 오래 점유할 수 있습니다.

다음 예시는 이미 만든 폐기 가능한 로컬 학습 Redis에서만 실행하세요. 운영 주소를 복사해 쓰지 마세요. 설명용 포트 16379를 사용하며, 서버를 이 포트에 직접 준비하지 않았다면 명령을 실행하지 않습니다.

redis-cli -h 127.0.0.1 -p 16379 SET study:goods:123:name '배추' EX 60
redis-cli -h 127.0.0.1 -p 16379 GET study:goods:123:name
redis-cli -h 127.0.0.1 -p 16379 HSET study:goods:123 status AVAILABLE center IC
redis-cli -h 127.0.0.1 -p 16379 HGET study:goods:123 status
redis-cli -h 127.0.0.1 -p 16379 SADD study:scanned:today 123 123 124
redis-cli -h 127.0.0.1 -p 16379 SCARD study:scanned:today

마지막 Set의 크기는 다른 작업이 없고 새 키였다면 2가 예상됩니다. 같은 값 123이 두 번 입력되어도 하나의 원소이기 때문입니다. 반복 실행 전에 상태가 남아 있다는 점도 실습 결과의 일부입니다. 테스트를 재현할 때는 새 키 접두사를 쓰거나 자신이 만든 키만 정리합니다.

5. TTL과 eviction: 시간이 끝난 것과 자리가 부족한 것

TTL(time to live)은 키가 유효하게 남아 있을 시간입니다. SET ... EX 60은 값 저장과 만료 설정을 하나의 명령으로 요청합니다. 값 저장 뒤 별도 EXPIRE를 보내는 사이 애플리케이션이 죽으면 만료 없는 키가 남을 수 있으므로, 처음부터 TTL이 필요한 String에는 한 명령을 쓰는 편이 낫습니다. 일반 SET으로 값을 덮어쓰면 기존 TTL이 사라질 수 있으므로, 의도한 옵션을 명시해야 합니다. SET 명령

만료(expiration)와 퇴거(eviction)는 이유가 다릅니다. 만료는 약속한 시간이 끝난 것이고, 퇴거는 메모리 한도에 맞추기 위해 정책에 따라 키를 내보내는 것입니다. TTL이 10분 남아 있어도 퇴거 대상이 될 수 있습니다. noeviction은 데이터가 무한히 들어간다는 뜻이 아니라, 한도에 도달하면 메모리가 필요한 쓰기가 오류로 실패할 수 있다는 뜻입니다. 퇴거 정책

redis-cli -h 127.0.0.1 -p 16379 SET study:ttl value EX 60
redis-cli -h 127.0.0.1 -p 16379 TTL study:ttl
redis-cli -h 127.0.0.1 -p 16379 SET study:ttl changed
redis-cli -h 127.0.0.1 -p 16379 TTL study:ttl

TTL 조회에서 -1은 키에 만료가 없음을, -2는 키가 없음을 뜻합니다. 첫 TTL은 명령 사이 시간이 흐르므로 정확히 60이라고 고정하지 않습니다. 타이머 테스트는 오차 범위와 마감 시간을 두고, CI가 바쁠 때 몇 밀리초 지연됐다고 실패하지 않도록 설계합니다. EXPIRE 설명

상품 캐시 10만 개가 모두 같은 순간에 만들어져 5분 뒤 동시에 만료되는 상황을 생각해 봅시다. 값이 없어지는 것 자체보다 그 직후 DB로 향하는 재조회가 문제입니다. TTL에 작은 무작위 차이(jitter)를 주면 재생성 시간이 분산됩니다. 단, 오래된 데이터를 얼마나 허용하는지 먼저 정해야 하며, jitter는 정합성을 보장하는 장치가 아닙니다.

6. Cache-aside와 오래된 값이 되살아나는 경주

Cache-aside는 애플리케이션이 캐시를 직접 확인하고 채우는 패턴입니다. 조회 시 캐시에 값이 있으면 반환하고(hit), 없으면(miss) DB를 조회한 뒤 캐시에 저장합니다. 단순해 보이지만 DB와 Redis는 서로 다른 시스템이므로 한쪽 성공이 다른 쪽 성공을 보장하지 않습니다.

일단 캐시에 값을 넣는 위치를 다음과 같이 그릴 수 있습니다. 아래 Java는 개념을 보이는 골격이며, 실제 DB·Redis 연결 코드가 아닙니다. 문자열을 사용해 직렬화 문제를 일부러 숨기지 않고 분리했습니다.

import java.time.Duration;
import java.util.Optional;

public final class GoodsQuery {
    interface Cache {
        Optional<String> get(String key);
        void put(String key, String value, Duration ttl);
    }
    interface Repository { Optional<String> findName(long goodsId); }
    private final Cache cache;
    private final Repository db;
    public GoodsQuery(Cache cache, Repository db) {
        this.cache = cache;
        this.db = db;
    }
    public Optional<String> name(long id) {
        String key = "goods:name:" + id;
        Optional<String> hit = cache.get(key);
        if (hit.isPresent()) return hit;
        Optional<String> value = db.findName(id);
        value.ifPresent(v -> cache.put(key, v, Duration.ofSeconds(60)));
        return value;
    }
}

이 코드가 프로덕션 완성본이 아닌 이유를 찾아봅시다. Redis 장애가 예외로 나오면 DB 조회까지 도달하지 않습니다. 반대로 예외를 모두 무시하고 DB로 우회하면 DB가 과부하될 수 있습니다. 존재하지 않는 ID는 매번 DB에 갑니다. 동일 키의 동시 miss는 여러 DB 조회를 일으킵니다. DB를 읽은 후 값을 캐시에 넣기 전 다른 요청이 데이터를 변경할 수 있습니다.

가장 중요한 경쟁 상황을 시간순으로 봅시다.

  1. 조회 요청 A가 캐시 miss를 만나 DB의 옛 이름 “배추”를 읽습니다.
  2. 수정 요청 B가 DB 이름을 “알배기배추”로 커밋합니다.
  3. B가 Redis의 상품 캐시를 삭제합니다.
  4. 늦어진 A가 예전에 읽었던 “배추”를 Redis에 저장합니다.
  5. 다음 사용자는 다시 옛 이름을 받습니다.

따라서 “DB 커밋 후 캐시 삭제”는 유용한 기본 전략이지 모든 경주를 없애는 증명이 아닙니다. TTL로 오래됨의 시간을 제한하고, 데이터 버전을 비교하거나, 갱신과 캐시 채우기를 같은 일관성 규칙 아래 묶거나, 필요한 경우 캐시를 사용하지 않는 선택까지 검토합니다. 버전 비교도 버전 정보와 값의 갱신이 원자적으로 이루어지고 모든 writer가 같은 규칙을 따를 때 의미가 있습니다.

“삭제를 두 번 하면 완벽하다”는 주장도 조심해야 합니다. 두 번째 삭제 이후까지 A가 지연되면 비슷한 문제가 남을 수 있습니다. 지연 삭제는 특정 지연 분포에서 위험을 낮추는 운영 기법일 수 있지만, 시간 가정 없이 정확성을 증명하지 못합니다. 주문·재고 확정의 최종 판단은 캐시 조회 결과만으로 내려서는 안 됩니다.

7. Stampede, penetration, hot key를 다른 문제로 보기

Stampede는 인기 키가 사라진 순간 여러 요청이 동시에 원본을 읽어 캐시를 채우는 현상입니다. Penetration은 존재하지 않는 데이터 요청이 캐시를 통과해 계속 원본까지 가는 상황입니다. Hot key는 한 키에 요청이 집중되는 현상입니다. 셋을 모두 “Redis 증설”로 해결할 수는 없습니다.

예를 들어 상품 A를 초당 2,000번 조회하고 DB 조회가 30ms라고 가정합시다. 캐시가 비어 있는 30ms 동안 평균 약 60개의 요청이 들어올 수 있습니다. 이 수치는 설명용 가정이며 실제 시스템의 도착 분포와 동시성에 따라 달라집니다. 같은 조회를 한 작업으로 합치거나(single-flight), 갱신 중 허용 가능한 옛 값을 제공하거나(stale-while-revalidate), TTL을 분산시키는 방식을 고려합니다.

단일 JVM 안의 single-flight는 다른 서버 인스턴스의 조회를 합쳐주지 않습니다. 분산락을 추가하면 전역 중복을 줄일 수 있지만, 락 대기·만료·장애·소유권 관리라는 새 문제가 생깁니다. 또 트래픽이 없는 키에 복잡한 락까지 넣는 것은 비용 대비 효과가 작을 수 있습니다. 어떤 키가 뜨거운지 관측하고, 원본 저장소가 버틸 수 있는 부하 예산을 먼저 정하세요.

존재하지 않는 상품을 짧게 음수 캐싱(없다는 결과를 보관)하면 반복 DB 조회를 줄일 수 있습니다. 그러나 조금 뒤 실제 상품이 생성되었는데도 없다는 응답이 남을 수 있으므로 짧은 TTL과 생성 시 무효화가 필요합니다. Bloom filter는 “없음”을 빠르게 걸러낼 수 있는 후보이지 사용자 인증이나 정확한 재고 판단을 대신하는 도구는 아닙니다. 필터 갱신 누락과 삭제·재생성 정책도 설계해야 합니다.

8. 원자성과 트랜잭션, 롤백은 같은 단어가 아니다

원자성이라는 말을 들으면 먼저 “무엇을 기준으로 하나인가?”를 물어야 합니다. 하나의 INCR는 중간 값을 다른 요청에 노출하지 않고 증가시킵니다. 하지만 GET으로 값을 읽고 Java에서 1을 더한 뒤 SET으로 쓰는 두 명령은 그 사이 다른 요청이 끼어들 수 있습니다. Redis가 명령을 순차 처리해도 애플리케이션의 여러 명령 묶음까지 저절로 하나가 되지는 않습니다.

MULTI/EXEC는 명령들을 모아 실행하며, 실행 중 다른 클라이언트 명령이 끼어들지 않는 범위를 제공합니다. 그러나 실행 단계에서 어떤 명령이 잘못된 자료형 오류를 낸다고 앞서 성공한 명령을 되돌리지 않습니다. WATCH는 읽은 키가 바뀌었는지 확인하는 낙관적 동시성 제어에 사용합니다. 충돌 후 재시도는 애플리케이션이 횟수와 시간 한도를 정해야 합니다. 트랜잭션 공식 문서

아래는 빈 로컬 학습 인스턴스에서 “실행 오류가 모든 변경을 취소하지 않는다”를 관찰하는 예입니다. 각 줄을 같은 redis-cli 세션에 입력해야 합니다.

SET study:counter 0
SET study:not-a-list hello
MULTI
INCR study:counter
LPUSH study:not-a-list x
INCR study:counter
EXEC
GET study:counter

EXEC 결과 배열에는 성공 결과와 WRONGTYPE 오류가 함께 나올 수 있습니다. 다른 변경이 없다면 counter는 2가 예상됩니다. “요청 하나가 실패했다”와 “모든 데이터 변경이 취소됐다”는 다릅니다. 큐에 넣는 단계의 문법 오류와 실행 단계의 자료형 오류도 구별해야 합니다.

Lua로 조건 확인과 변경을 한 번에 실행할 수도 있습니다. 하지만 스크립트 역시 외부 DB의 트랜잭션이 아니고 실행 오류 때 모든 이전 쓰기를 자동 롤백하지 않습니다. 키의 자료형·필수 인자·허용 범위를 먼저 확인하고 실제 쓰기는 뒤에 배치하는 설계가 중요합니다. Cluster에서 함께 처리할 키의 슬롯 제약도 17편에서 배웁니다.

9. 파이프라인은 단체 배송이지 단체 트랜잭션이 아니다

한 사람에게 편지를 보내고 답장을 받아야 다음 편지를 보내는 방식은 왕복 시간이 큽니다. 파이프라이닝은 답장을 매번 기다리지 않고 여러 명령을 보내 왕복 비용을 줄이는 방식입니다. 명령 처리 자체를 무료로 만들거나 원자성을 추가하지는 않습니다. 많은 요청과 응답을 쌓아두면 클라이언트와 서버 메모리도 사용하므로 배치를 무제한 키우지 않습니다. 파이프라이닝 설명

가령 네트워크 왕복이 1ms이고 명령 작업이 0.05ms라는 가정을 두면, 단건 100회는 대략 105ms 규모로 생각할 수 있습니다. 한 번에 묶으면 왕복 횟수는 줄지만 실제 소요 시간은 버퍼·패킷·스케줄링·응답 크기에도 좌우됩니다. 이 계산은 병목을 이해하는 모형이지 보장된 성능 수치가 아닙니다.

서버가 일부 명령을 처리한 뒤 연결이 끊기면 어느 명령까지 처리되었는지 모를 수 있습니다. 파이프라인 전체를 그대로 다시 보내면 INCR가 중복될 수 있습니다. “더 빠르게 보내기”와 “실패를 정확히 처리하기”는 각각 설계해야 합니다. 23편에서는 처리량만 높게 보이는 벤치마크 대신 지연 분포와 실제 요청 패턴을 함께 측정합니다.

10. 타임아웃이 의미하는 것은 실패가 아니라 결과 불확실일 수 있다

요청을 보냈는데 제한 시간 안에 응답이 안 왔습니다. 가능한 원인은 여러 가지입니다. 서버에 도착하지 않았을 수도 있고, 서버 큐에서 기다릴 수도 있고, 실행은 끝났지만 응답만 늦었을 수도 있습니다. 그래서 “타임아웃이면 무조건 다시 실행”은 쓰기 연산에서 위험합니다.

입고 수량 3을 더하는 요청이 실행된 뒤 응답만 유실되었다면, 재시도로 3을 다시 더하면 실제 입고 3개가 6개가 됩니다. 요청마다 안정적인 업무 ID를 만들고, 이미 처리했는지 판단하는 결과와 변경을 같은 보호 범위에서 기록하는 멱등 설계가 필요합니다. Redis에서 중복 방지 키만 먼저 저장하고 DB 변경 전에 죽으면, 재시도가 막혀 실제 업무는 수행되지 않는 반대 문제가 생깁니다.

외부 DB의 확정 작업이라면 DB 고유 제약·업무 상태 전이·트랜잭션·Outbox와 연결하는 편이 자연스러울 수 있습니다. Redis는 조회 가속이나 중복 요청의 부하 완화에 활용하되 정확성의 마지막 근거가 무엇인지 분명히 합니다. 네트워크가 있는 시스템에서는 실패 응답 하나에 최종 업무 결과를 모두 담을 수 없을 때가 있습니다. 이때 조회 가능한 처리 ID와 대조 절차가 중요합니다.

11. 분산락이 재고 정합성을 대신해 주지는 않는다

분산락은 여러 프로세스가 같은 작업을 동시에 하지 않도록 조율하는 수단입니다. 흔한 기본은 소유자별 고유 토큰을 값으로 넣고 NX와 만료를 함께 설정하는 것입니다. 해제할 때 단순 DEL 대신 현재 값이 자기 토큰인지 확인해야, 만료 후 다른 사람이 얻은 락을 지우지 않습니다. 분산락 공식 패턴

그러나 안전한 해제만으로 모든 문제가 끝나지는 않습니다. 작업자 A가 락을 얻고 오랫동안 멈췄습니다. TTL이 끝나 B가 락을 얻어 작업합니다. A가 깨어나 자신이 여전히 소유자라고 생각하며 DB를 변경하면 둘이 동시에 일할 수 있습니다. 락 연장도 프로세스 정지와 네트워크 분할이라는 가정을 지워주지는 않습니다.

이 상황에서 저장 대상이 단조 증가하는 권한 번호(fencing token)를 검사해 오래된 작업자의 쓰기를 거절하도록 만들 수 있습니다. 하지만 토큰을 발급하기만 하고 DB가 비교하지 않으면 아무 효과가 없습니다. 토큰 생성 자체의 장애 후 단조성도 요구 조건입니다. “Redisson을 썼다”라는 라이브러리 선택과 “실패한 소유자의 늦은 쓰기가 막힌다”라는 정확성 증명은 다른 일입니다.

실무 질문으로 바꾸면 더 쉽습니다. “락을 잡은 다음 JVM이 40초 멈추고 락 TTL은 30초라면 어떤 일이 생기는가?”에 답할 수 있어야 합니다. 30초와 40초는 사고를 설명하는 가정이며 적정 TTL 권고가 아닙니다. 업무 처리 시간의 분포, 정지 시간, 장애 시 복구 정책을 함께 고려하세요.

12. Spring 개발자가 먼저 확인할 연결 경계

Spring의 @Transactional을 메서드에 붙였다고 MySQL과 Redis가 하나의 원자적 커밋으로 묶이지는 않습니다. 어떤 transaction manager가 선택되는지, RedisTemplate의 트랜잭션 참여 설정이 무엇인지, 명령이 같은 연결에서 실행되는지 확인해야 합니다. Spring Data Redis는 같은 연결의 연속 작업을 위해 SessionCallback을 제공합니다. Spring 트랜잭션 안내

실제 서비스를 설계할 때 다음 질문을 코드 옆에 붙여두면 좋습니다.

  • 연결 타임아웃과 명령 타임아웃은 각각 얼마이며 HTTP 요청의 전체 예산 안에 들어가는가?
  • Redis 오류 시 어떤 기능은 우회하고 어떤 기능은 실패시키는가?
  • 재시도 대상 명령은 멱등한가? 요청 ID를 계속 유지하는가?
  • Sentinel/Cluster 전환 후 새 토폴로지를 어떻게 발견하는가?
  • 직렬화 형식이 변경되면 기존 캐시를 읽을 수 있는가? 키에 버전 접두사가 필요한가?
  • TTL과 최대 값 크기, hot key 지표를 어떤 대시보드에서 확인하는가?

예를 들어 JSON 필드 이름을 바꾼 새 배포와 이전 배포가 동시에 실행되면 둘이 같은 키를 서로 다른 형식으로 읽을 수 있습니다. 블루그린 배포에서는 서버 수만 두 배가 되는 것이 아니라 캐시를 읽고 쓰는 코드 버전도 둘이 될 수 있습니다. 키 버전을 나누면 호환성 위험은 낮아지지만 캐시 적중률 하락과 일시적 메모리 중복이라는 비용이 생깁니다.

13. 실습 기록을 남기는 방법

실습 결과를 “잘 됨” 한 줄로 남기면 나중에 무엇을 검증했는지 알 수 없습니다. 다음 항목을 같이 적으세요.

  1. Redis 서버 버전, 클라이언트 버전, Java 버전과 실행 OS.
  2. 단일 노드인지, replica가 있는지, Sentinel/Cluster인지.
  3. 변경한 설정과 데이터 크기, 요청 수, 동시 연결 수.
  4. 명령을 보낸 시각과 오류를 관측한 시각, 서버 로그와 지표.
  5. 예상 결과와 실제 결과, 재현하지 못한 조건.
  6. 만든 키·프로세스·파일을 어떻게 안전하게 정리했는지.

이 시리즈의 학습 코드는 운영 서버를 향하도록 작성되지 않았습니다. 직접 재현할 때도 먼저 주소와 포트를 출력하고, 폐기 가능한 인스턴스인지 확인하세요. 장애 실험·강제 종료·ACL 변경·디스크 복구는 개인 학습 인스턴스에서 수행합니다. 백업을 “만들어 봤다”와 “다른 인스턴스에 복원해 업무 데이터를 대조했다”는 다른 검증입니다.

14. 접었다 펼치는 기초 면접 문답

Q1. Redis가 빠르다는 말만으로 선택하면 왜 부족한가요?

속도는 요구사항 중 하나일 뿐입니다. 데이터의 최종 근거, 손실 허용 범위, 오래된 조회 허용 시간, 장애 시 우회 정책을 먼저 정해야 합니다. 예를 들어 상품 설명 캐시는 DB에서 복원할 수 있지만 Redis에만 있는 입고 작업 상태는 같은 방식으로 버릴 수 없습니다. 답변할 때는 “조회 가속 목적이며 원본은 MySQL, Redis 장애 때는 DB 부하 한도 안에서만 우회”처럼 실패 정책까지 붙이면 설계가 구체적입니다.

Q2. TTL이 있으니 메모리 부족과 오래된 값 문제는 모두 해결되나요?

아닙니다. TTL은 키의 유효 시간을 제한하지만 입력 속도와 값 크기가 충분히 크면 만료되기 전에 메모리 한도에 닿을 수 있습니다. 또한 TTL 동안에는 오래된 값이 남을 수 있고, 잘못된 값으로 갱신되면 그 시점부터 다시 TTL이 시작될 수 있습니다. 메모리 정책과 갱신 정합성 정책을 따로 설계해야 합니다. 무조건 짧게 줄이면 원본 조회 부하가 늘어나는 점도 함께 설명해야 합니다.

Q3. DB 수정 후 캐시 삭제를 하면 항상 최신 데이터가 보이나요?

아닙니다. DB 수정 전 값을 읽은 느린 조회가 캐시 삭제 뒤 옛 값을 다시 넣는 경주가 가능합니다. 먼저 시간순으로 A의 조회, B의 커밋, B의 삭제, A의 저장을 그려 설명하세요. 요구되는 최신성에 따라 TTL, 버전 검사, 갱신 규칙, 원본 직접 조회 등을 선택합니다. 단순히 “삭제를 한 번 더 한다”는 방법만으로 무한한 지연과 모든 실패를 해결했다고 말해서는 안 됩니다.

Q4. Redis는 단일 스레드라서 GET 후 SET도 안전하지 않나요?

개별 명령의 실행 순서와 애플리케이션의 여러 명령을 하나로 묶는 것은 다릅니다. A가 GET한 뒤 B가 GET·SET을 끝내고 A가 옛 값에 기반한 SET을 하면 갱신이 사라질 수 있습니다. 숫자 증가라면 INCR, 조건에 따른 변경이라면 적절한 Lua나 WATCH 기반 재시도를 검토합니다. Redis 프로세스 전체에 스레드가 하나뿐이라는 뜻으로 단순화하지 않는 것도 중요합니다.

Q5. MULTI/EXEC는 MySQL 트랜잭션과 무엇이 다른가요?

Redis는 묶인 명령의 실행 중 다른 명령이 끼어들지 않는 성질을 제공하지만 실행 중 오류가 발생했다고 이미 수행된 변경을 모두 롤백하지 않습니다. 오류가 명령을 큐에 넣는 시점인지 실행하는 시점인지도 구분해야 합니다. MySQL과 Redis를 하나의 트랜잭션처럼 사용하려면 두 시스템 사이 커밋 경계를 별도로 설계해야 하며, Spring 애너테이션 이름이 같다는 이유로 분산 원자성이 생기지 않습니다.

Q6. 파이프라인을 쓰면 명령 전체가 원자적인가요?

아닙니다. 파이프라인은 응답을 매번 기다리는 비용을 줄이는 전송 방식입니다. 원자적 조건 확인·갱신과는 목적이 다릅니다. 배치 크기가 지나치게 크면 버퍼 메모리와 지연에 부담을 줄 수 있고, 연결 중단 뒤 부분 성공을 다루는 문제도 남습니다. 성능 개선을 설명할 때는 왕복 감소와 실행 보장을 분리하는 것이 핵심입니다.

Q7. INCR가 타임아웃이면 재시도하면 되나요?

서버가 이미 증가시켰지만 응답이 유실되었을 수 있어 단순 재시도는 중복을 만들 수 있습니다. 먼저 결과 불확실 상태를 인정해야 합니다. 업무 ID로 중복을 판단하고 결과를 조회할 수 있게 하거나, 최종 저장소의 멱등 제약을 사용합니다. 단순한 통계 카운터라면 일부 오차를 허용할 수 있지만 입고 확정 수량에는 같은 판단을 적용하면 안 됩니다.

Q8. 분산락을 쓰면 재고가 절대 틀리지 않는다고 할 수 있나요?

그렇게 단정할 수 없습니다. 락 만료 후 이전 소유자가 재개하거나 장애 전환 중 락 정보가 사라지는 조건을 따져야 합니다. 안전한 토큰 비교 해제, 필요 시 저장 대상의 fencing 검사, DB 제약과 업무 멱등성이 각각 어떤 실패를 막는지 구분합니다. 락을 업무 정확성의 유일한 장벽으로 쓰기 전에 프로세스 정지와 네트워크 분할의 시간순 시나리오를 검증해야 합니다.

Q9. Sentinel과 Cluster 중 어느 것이 더 좋은가요?

문제가 다릅니다. Sentinel은 일반적으로 한 primary와 replica 집합의 장애 감시·전환과 위치 발견에 사용합니다. Cluster는 여러 primary에 키를 분할하며 슬롯과 리다이렉션을 다룹니다. 데이터와 부하가 한 primary에 들어가는지, 다중 키 연산이 필요한지, 운영 복잡성을 감당할 수 있는지부터 봅니다. 노드 수가 많다는 사실 자체가 더 강한 일관성이나 무손실을 뜻하지 않습니다.

Q10. 이 30편만 읽으면 Redis 전체를 공부한 건가요?

아닙니다. 제공 자료는 운영 문서 중심이며 이 안내에서 개발 기본기를 보충합니다. 검색·벡터·모듈·제품별 관리형 기능 전체를 포괄하지 않습니다. 목표는 Java/Spring 백엔드 개발자가 설정, 실패 보장, 관측, 복구와 코드의 경계를 설명할 수 있게 되는 것입니다. 부족한 범위를 숨기기보다 자신의 서비스에 필요한 기능을 공식 문서와 실행 버전에 맞춰 추가하는 것이 좋습니다.
