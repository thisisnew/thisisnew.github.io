Processor API와 Serde 심화

도트 게임 속 스테이지를 진행하듯, 쉬운 비유부터 기술적인 흐름과 장애 대응을 함께 익혀봅시다. 비유의 한계를 기억하고 실제 용어를 직접 설명해 보세요.

1. Processor API

처음 듣는 사람을 위한 비유

기성 공구 대신 맞춤형 공구

정확한 개념과 내부 동작

Processor API는 DSL에서 표현하기 어려운 레코드 단위 처리와 State Store 접근을 구성하는 저수준 API다.

2. Serde

3. State Store

처음 듣는 사람을 위한 비유

실습과 점검

테스트 토픽과 격리된 Kafka 클러스터에서 각각의 이벤트 Key, Partition, Offset, 처리 성공 여부를 기록하며 결과를 추적하세요. 상태를 사용하는 기능은 앱 재시작 시 복구 시간도 측정합니다. 운영 클러스터의 오프셋을 임의로 수정하거나 Topic을 삭제해서는 안 됩니다.

더 깊게 배우기 1. Serde의 정확한 역할

Kafka는 메시지의 비즈니스 Java 객체 타입을 아는 시스템이 아니에요. Producer가 StringSerializer로 보낸 값과 Consumer가 JsonDeserializer로 복원하려는 값이 일치하지 않으면 문제가 생깁니다. Streams에서 Serde는 Serializer와 Deserializer의 쌍으로 이해할 수 있어요. 기본 Serde와 특정 연산에서 명시하는 Consumed/Produced/Grouped Serde를 구분해야 합니다.

더 깊게 배우기 2. Processor API를 쓰는 시점

DSL filter, mapValues, aggregate만으로 표현하기 어려운 복잡한 레코드 처리·사용자 정의 상태 전이가 필요할 때 Processor API를 검토합니다. 대신 State Store 접근, Processor 생명주기, 전달 동작을 직접 이해해야 하므로 코드와 테스트가 복잡해질 수 있어요.

더 깊게 배우기 3. Stream Time과 Wall Clock Time

Stream Time은 처리한 레코드 타임스탬프 진행과 관련돼요. 이벤트가 한동안 들어오지 않으면 Stream Time이 멈출 수 있습니다. Wall Clock Time은 실제 경과하는 시간에 기반한 실행 방식입니다. 일정 주기로 하는 작업을 Stream Time 기반으로 예약했는데 새 메시지가 없으면 기대한 시각에 실행되지 않을 수 있습니다.

더 깊게 배우기 4. State Store와 실패 복구

로컬 상태 저장소를 직접 사용하는 Processor라면 상태가 어디에 기록되고 재시작 시 어떻게 복원되는지 알아야 합니다. Changelog가 없는 로컬 저장소가 지워지면 데이터 복구가 불가능할 수도 있습니다. State Store를 설계할 때 로그 기록 정책을 명시하세요.

더 깊게 배우기 5. 테스트해야 할 예외 상황

정상 레코드만 테스트하면 부족합니다. null Key와 null Value, 역직렬화 실패, 이벤트 역순, 이전 State가 없는 상황, 프로세스 재시작, 동일 이벤트 재전송 등을 테스트하세요. 특히 상태 전이 로직은 중복 레코드를 받아도 일관된 결과를 내는지 확인해야 합니다.
