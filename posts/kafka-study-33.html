KAFKA STUDY 33/35 · OFFICIAL SOURCE 33

Processor API, Serde

쉬운 비유에서 실제 Streams 내부 동작·운영 장애·질문 풀이로 이어지는 학습 해설입니다. 개념 이해 후 공식문서의 전체 세부 항목을 반드시 확인하세요.

1. Processor API

쉽게 이해하기

기본 도구 대신 직접 만든 공구로 처리합니다.

실제 동작의 핵심

레코드마다 정밀한 로직과 상태 저장소 접근을 구현합니다.

각 레코드가 어느 파티션에서 읽혔고, 어떤 순서로 변환되고, 상태가 어디에 저장되며, 프로세스 중단 시 어떻게 복구되는지를 순서대로 생각해야 합니다. 단순히 함수 이름을 암기하는 것보다 입력 이벤트와 출력 이벤트를 구체적으로 상상하는 것이 중요합니다.

운영에서 주의할 점

레코드마다 정밀한 로직과 상태 저장소 접근을 구현합니다. 장애 복구와 파티션 재배치 때 동일 이벤트의 중복 처리나 상태 복원 지연에 주의해야 합니다. 외부 데이터베이스까지 포함하는 경우 Kafka의 내부 처리 보장이 외부 트랜잭션을 대체하지 않습니다.

Q. Processor API이 필요한 이유와 내부 동작을 설명해 보세요.

기본 도구 대신 직접 만든 공구로 처리합니다. 실제 Streams에서는 레코드마다 정밀한 로직과 상태 저장소 접근을 구현합니다.

정상 동작 시 입력·출력·상태가 무엇인지 먼저 확인한 뒤, 재시작 직후의 동작까지 설명해 보세요.

Q. Processor API 관련 장애가 난다면 무엇을 살펴야 할까요?

Kafka 소비 지연, Streams Task 상태, State Store 복구 진행, 내부 토픽과 ACL을 점검합니다. 오류 메시지와 설정 변경 이력을 기록해 원인에 따른 복구를 결정하세요.

2. Serde

쉽게 이해하기

컴퓨터가 바이트와 객체를 서로 번역합니다.

실제 동작의 핵심

Serializer와 Deserializer가 키와 값 타입에 부합해야 합니다.

각 레코드가 어느 파티션에서 읽혔고, 어떤 순서로 변환되고, 상태가 어디에 저장되며, 프로세스 중단 시 어떻게 복구되는지를 순서대로 생각해야 합니다. 단순히 함수 이름을 암기하는 것보다 입력 이벤트와 출력 이벤트를 구체적으로 상상하는 것이 중요합니다.

컴퓨터가 바이트와 객체를 서로 번역합니다. 실제 Streams에서는 Serializer와 Deserializer가 키와 값 타입에 부합해야 합니다.

3. State Store

쉽게 이해하기

중간 처리 기록을 보관하는 공책입니다.

로컬 상태, Changelog 복구 및 재할당 비용을 관리합니다.

각 레코드가 어느 파티션에서 읽혔고, 어떤 순서로 변환되고, 상태가 어디에 저장되며, 프로세스 중단 시 어떻게 복구되는지를 순서대로 생각해야 합니다. 단순히 함수 이름을 암기하는 것보다 입력 이벤트와 출력 이벤트를 구체적으로 상상하는 것이 중요합니다.

복습 과제

Kafka Streams Topology를 직접 한 줄 흐름으로 표현해 보세요. Source → filter/mapValues → groupByKey → aggregate → Sink 구성에서 상태 저장과 재파티셔닝이 필요한 지점을 찾아보세요.
