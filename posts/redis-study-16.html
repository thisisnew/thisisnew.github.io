1. Cluster의 설계 목표를 보장과 구분한다

Redis Cluster는 높은 성능과 수평 확장, 실용적인 쓰기 안전성, 일부 장애에서의 가용성을 함께 추구한다. 이를 위해 일반 요청 경로에 중앙 프록시를 두지 않고 클라이언트가 담당 노드에 직접 접속하며, 복제는 비동기로 수행하고 충돌 데이터의 일반적인 병합은 하지 않는다. “확장을 목표로 한다”와 “서버 N개면 모든 업무 처리량이 정확히 N배”는 다른 문장이다. workload와 핫키, 네트워크, 클라이언트 연결 수가 실제 결과를 결정한다.

복잡한 자료구조를 자동 병합하지 않는 이유도 업무 의미와 비용에 있다. 서로 다른 primary에서 변경된 배송 이벤트 목록 두 개를 단순 합치면 중복과 순서 문제가 생길 수 있고, 정렬 집합의 점수 충돌도 의미에 따라 다르게 처리해야 한다. Redis Cluster는 이런 충돌 해결을 일반적으로 대신 수행하는 시스템이 아니다. 이 설명을 모든 Redis 제품이나 별도의 CRDT 시스템으로 일반화하지 않고, 이 장의 대상인 Redis Open Source Cluster로 한정한다.

2. 키 → 슬롯 → 노드, 두 단계의 간접 참조

키를 바로 서버 수로 나눈다면 서버 수가 바뀔 때 많은 키의 계산 결과가 달라질 수 있다. Cluster는 고정된 16,384 슬롯을 중간에 두고 키는 슬롯에, 슬롯은 현재 primary에 매핑한다. 서버가 추가되어도 같은 키의 슬롯 번호는 변하지 않는다. 바뀌는 것은 그 슬롯을 맡는 node ID다. 이 구분이 리샤딩과 클라이언트 슬롯 캐시의 기초다.

shipment:{S300}:status ─┐
                        ├─ 태그 S300의 CRC16 → 슬롯 s → primary P
shipment:{S300}:events ─┘                         └→ replica P1

리샤딩 후: 같은 슬롯 s → primary Q
키 문자열과 슬롯 번호가 같아도 담당 노드는 바뀔 수 있다.

CRC16은 데이터를 정해진 16비트 값으로 계산하는 함수이며 여기서는 암호학적 보안 기능이 아니다. Redis의 구체적인 CRC16 변형과 입력 바이트 규칙을 따라야 같은 슬롯을 계산한다. Java에서 임의의 String.hashCode()나 다른 CRC 라이브러리 기본값을 쓰면 Redis와 다른 결과를 만들 수 있다. 실무에서는 검증된 Cluster 클라이언트에 슬롯 계산을 맡기고 CLUSTER KEYSLOT을 테스트 oracle로 사용한다.

3. 해시 태그는 중괄호 규칙을 정확히 읽어야 한다

키에 첫 {가 있고 그 오른쪽에 }가 있으며 둘 사이가 비어 있지 않으면 그 사이의 바이트를 해시한다. 첫 후보가 빈 태그이면 뒤에서 새로운 태그를 찾는 방식이 아니라 전체 키를 해시한다. 중괄호를 사람이 의미 단위로 해석한 결과와 Redis가 바이트로 읽는 결과가 다를 수 있다.

키 해시 입력 이유
shipment:{S300}:status S300 첫 중괄호 쌍 사이가 비어 있지 않음
shipment:{S300}:events S300 같은 태그이므로 같은 슬롯
foo{}{bar} 전체 키 첫 쌍이 비어 있음
foo{{bar}}zap {bar 첫 여는 괄호와 그 뒤 첫 닫는 괄호 사이
foo{bar}{zap} bar 첫 태그 사용
foo{bar 전체 키 닫는 괄호가 없음

사용자 입력을 키에 그대로 넣으면 예상하지 못한 중괄호가 태그 해석에 영향을 줄 수 있다. 배송 ID의 문자 집합과 정규화 규칙을 정하고, 다른 언어의 서비스가 동일한 인코딩으로 키를 만드는지 테스트한다. 한글을 포함한 키라면 문자열의 시각적 모양뿐 아니라 실제 바이트 인코딩도 중요하다. 키 생성 코드를 공통 라이브러리로 관리하고 대표 입력의 KEYSLOT 결과를 회귀 테스트에 포함할 수 있다.

4. 태그의 크기는 업무 원자성의 크기다

배송 하나의 상태와 이벤트를 함께 변경해야 한다면 shipment ID가 좋은 후보가 될 수 있다. 창고 전체를 태그로 묶으면 같은 창고의 작업을 함께 다룰 수 있지만 대형 창고 하나가 슬롯 하나에 집중된다. 고객 전체를 태그로 묶는 설계도 대형 고객의 트래픽과 데이터가 한 primary를 압박할 수 있다. 반대로 키마다 다른 태그를 쓰면 분산은 쉬워지지만 함께 변경해야 하는 키가 cross-slot이 된다.

따라서 “태그를 붙여 CROSSSLOT을 없애자”라는 처방 전에 어떤 업무 변경이 반드시 원자적이어야 하는지 정의한다. 여러 배송 건의 전체 배치를 하나의 Redis 트랜잭션으로 묶으려는 요구가 실제로 필요한가? 원장에서 배치 상태를 확정하고 Redis 조회 모델을 순차 갱신해도 되는가? 원자성 범위를 줄이면 확장성 선택지가 늘어난다. 같은 슬롯에 둔다고 SQL처럼 실행 오류가 자동 롤백되는 것은 아니며, Lua와 트랜잭션 내부 검증 순서는 별도 문제다.

5. 노드 ID와 주소는 같은 정체성이 아니다

Cluster 노드는 고유 ID로 식별되며 주소와 포트는 그 노드에 도달하기 위한 위치 정보다. 프로세스를 재시작해도 보존된 클러스터 상태 파일에 따라 정체성을 유지할 수 있다. 반대로 같은 IP·포트에서 완전히 새로운 빈 상태로 시작하면 이전 노드와 동일하다고 가정할 수 없다. 그래서 nodes.conf를 함부로 삭제하거나 여러 노드에 복제하면 안 된다.

CLUSTER NODES에는 node ID, 주소, 역할 플래그, replica의 부모 ID, 최근 통신 정보, configuration epoch, 링크 상태, 슬롯 범위 등이 나타난다. 주소 하나만 보고 토폴로지를 그리지 말고 ID와 부모 관계를 함께 읽는다. 출력의 connected는 그 관찰 노드의 링크 상태에 관한 정보이며 애플리케이션 사용자의 네트워크 경로와 동일하지 않다. 멤버십이 정상이어도 클라이언트 접근이 막힌 경우가 있다.

6. cluster bus와 handshake는 발견과 합의의 기반이다

노드들은 cluster bus의 이진 프로토콜로 서로 상태를 전파하고 장애 탐지·구성 변경 정보를 주고받는다. gossip은 자신이 알고 있는 다른 노드의 상태 일부를 이웃에게 전파해 전체 인식이 퍼지도록 하는 방식이다. 모든 요청마다 모든 노드에 값을 저장하는 동기 복제와 다르다. CLUSTER MEET 같은 handshake 경로는 노드가 서로를 알고 구성원 정보를 받아들이게 하는 절차다. 빈 노드를 알렸다고 자동으로 슬롯까지 맡는 것은 아니다.

노드 수가 늘면 클라이언트 연결과 노드 사이의 통신 부담도 늘어난다. 16,384 슬롯이라는 수를 그대로 권장 primary 수로 읽으면 안 된다. 공식 명세의 확장 목표와 실제 운영의 권장 규모는 workload와 배치에 따라 검토한다. 작은 테스트에서 명령 지연이 낮았다고 대규모 전체 연결 토폴로지의 비용을 무시해서는 안 된다.

7. 패턴 검색과 DB 제약도 모델에 들어간다

Cluster는 기본적으로 DB 0을 사용하며 standalone처럼 여러 논리 DB를 SELECT로 나누어 쓰는 모델을 지원하지 않는다. 테넌트 분리는 키 네임스페이스와 ACL, 필요하면 별도 인스턴스 같은 다른 경계로 설계한다. SCAN을 한 노드에서 실행했다고 전체 Cluster를 검색한 것이 아니다. 일부 버전의 단일 슬롯을 추론할 수 있는 glob 패턴 최적화도 전역 검색이나 일반 성능 보장을 뜻하지 않는다. 운영 버전에서 지원 조건을 확인하고 전체 순회는 각 primary와 변경 중 중복·누락 가능성을 고려한다.

실습 공통 토대: 여섯 노드의 격리된 작은 Cluster

이 절은 13~16장을 독립적으로 읽는 독자를 위한 실습 토대다. 아래 명령은 교재 작성 중 실제 실행한 결과가 아니며 이후 설명은 예상 관찰이다. 이미 사용 중인 포트와 충돌하지 않는 로컬 일회용 환경에서만 수행한다. 동일 호스트의 여섯 프로세스는 클러스터 프로토콜 학습에는 도움이 되지만 호스트 장애를 견디는 배치가 아니다. 운영에서는 primary와 그 replica를 서로 다른 장애 도메인에 배치하고, 인증·TLS·방화벽·백업·여유 메모리·복제 지연 정책을 별도로 설계해야 한다.

redis-server --version
redis-cli --version
LAB=$(mktemp -d /tmp/redis-cluster-study.XXXXXX)
printf '%s\n' "$LAB"
for p in 7000 7001 7002 7003 7004 7005; do
  mkdir -p "$LAB/$p"
  cat > "$LAB/$p/redis.conf" <<EOF
port $p
bind 127.0.0.1
protected-mode yes
dir $LAB/$p
pidfile $LAB/$p/redis.pid
logfile $LAB/$p/redis.log
daemonize yes
cluster-enabled yes
cluster-config-file nodes.conf
cluster-node-timeout 5000
save ""
appendonly no
EOF
  redis-server "$LAB/$p/redis.conf"
done
redis-cli --cluster create   127.0.0.1:7000 127.0.0.1:7001 127.0.0.1:7002   127.0.0.1:7003 127.0.0.1:7004 127.0.0.1:7005   --cluster-replicas 1

생성 도구가 제시하는 primary/replica 관계와 슬롯 범위를 읽고, 오직 이번에 만든 빈 노드 여섯 개가 맞을 때만 확인 질문에 동의한다. 포트 순서만 보고 특정 replica의 부모를 단정하지 않는다. 도구가 실제 제안하고 생성한 관계를 기록한다. 데이터 포트 70007005 외에 기본 cluster bus 포트 1700017005도 노드 사이에서 필요하다. loopback 실습에서는 동일 호스트로 접근하지만 컨테이너나 VM을 섞으면 광고한 주소가 각 클라이언트와 다른 노드에서 실제로 도달 가능한지 확인해야 한다.

nodes.conf는 사용자가 수동 편집하는 일반 설정 템플릿이 아니라 Redis가 자신의 노드 ID, 다른 노드, 슬롯 배치 같은 상태를 기록하는 파일이다. 이 예제는 각 프로세스의 dir가 다르므로 파일명이 같아도 서로 다른 파일을 사용한다. 여러 노드가 하나의 nodes.conf를 공유하게 해서는 안 된다. save ""와 appendonly no는 실습용으로 영속성을 끈 설정이므로 재시작 복구 실험이나 운영 내구성의 근거로 사용할 수 없다. 재시작 후 데이터가 보이지 않는 것을 Cluster의 슬롯 계산 오류로 오인하지 않는다.

최초 정상 상태를 확인하는 네 가지 관점

redis-cli -p 7000 CLUSTER INFO
redis-cli -p 7000 CLUSTER NODES
redis-cli --cluster check 127.0.0.1:7000
redis-cli -p 7000 CLUSTER KEYSLOT 'shipment:{S100}:status'
redis-cli -p 7000 CLUSTER KEYSLOT 'shipment:{S100}:events'
redis-cli -c -p 7000 SET 'shipment:{S100}:status' READY
redis-cli -c -p 7001 GET 'shipment:{S100}:status'

첫 관점은 전체 상태다. 안정 상태에서는 cluster_state:ok와 전체 슬롯 할당을 기대한다. 둘째는 노드 관계다. CLUSTER NODES의 node ID, 역할, replica의 부모 ID, 링크 상태, 슬롯 범위를 읽는다. 셋째는 슬롯 일관성이다. 검사 도구가 모든 슬롯의 커버리지와 배치를 어떻게 보고하는지 확인한다. 넷째는 애플리케이션 경로다. -c를 붙인 redis-cli가 다른 primary로의 리다이렉션을 처리하며 쓰기와 읽기를 수행하는지 본다. 노드 상태가 정상이더라도 애플리케이션의 DNS, 자격 증명, 라우팅 정보가 잘못되면 요청은 실패한다.

위 두 키는 중괄호 안의 S100이 같으므로 동일 슬롯이 예상된다. 어떤 숫자가 나오는지 암기하지 말고 실제 CLUSTER KEYSLOT으로 확인한다. 동일 슬롯이라고 두 키의 값이 반드시 같다는 의미는 아니며, 동일 primary에 있다고 반드시 동일 슬롯인 것도 아니다. 하나의 primary가 수천 슬롯을 맡을 수 있기 때문이다. 다중 키 명령의 가능 여부는 서버 주소가 아니라 슬롯 번호로 판단한다.

실행 버전과 설정 파일 실험 재현과 버전별 차이 확인 latest 태그를 버전으로 기록하지 않는다
primary ID와 슬롯 범위 장애가 영향을 주는 데이터 범위 파악 포트는 역할과 함께 바뀔 수 있다
replica의 부모 ID와 복제 상태 승격 가능성과 최신성 평가 링크 연결과 데이터 완전성은 다르다
요청 ID·시작·종료 시각 업무 성공과 서버 성공을 구분 timeout은 미실행의 증명이 아니다
변경 전후의 노드 출력 역할 전환·슬롯 이전 검증 한 노드의 순간 관찰을 전체 진실로 취급하지 않는다

장애 실습에서 DEBUG SEGFAULT를 사용할 필요는 없다. 이 명령은 의도적으로 프로세스를 충돌시키며 운영 환경에서는 금지해야 한다. 명확히 식별한 일회용 인스턴스의 정상 종료, 또는 격리된 컨테이너의 정지부터 시작하면 된다. 정상 종료 실험은 전원 장애·커널 정지·부분 네트워크 분할과 동일하지 않다. 그 차이를 실험 보고서에 적어야 결과를 과장하지 않는다. 실제 네트워크 분할 실험은 host 방화벽을 즉흥적으로 바꾸기보다 별도의 네트워크 namespace나 전용 컨테이너 네트워크를 준비한 뒤 수행한다.

정리와 증거 보존

# 이번 실습에서 직접 생성했고 다른 서비스가 아닌 것을 먼저 확인한다.
for p in 7000 7001 7002 7003 7004 7005; do
  redis-cli -h 127.0.0.1 -p "$p" SHUTDOWN NOSAVE
done
# $LAB의 로그와 설정은 분석이 끝날 때까지 보존한다.

추가한 7006, 7007 같은 노드가 있다면 해당 실습의 정확한 목록을 별도로 종료한다. 노드 제거 명령을 실행했다고 프로세스까지 종료되는 것은 아니다. 반대로 프로세스를 종료했다고 나머지 노드들이 그 노드를 잊은 것도 아니다. 멤버십 변경, 프로세스 생명주기, 데이터 보존은 서로 다른 작업이라는 점을 마지막까지 구분한다.

키 설계 워크숍: 창고·배송·고객 중 무엇을 태그로 할까

배송 S400은 창고 W8에서 출고되고 고객 C9에 속한다고 하자. 키를 warehouse:{W8}:shipment:S400으로 만들면 같은 창고의 배송이 같은 슬롯으로 모인다. shipment:{S400}:status와 shipment:{S400}:events로 만들면 배송 한 건의 관련 데이터가 같은 슬롯으로 모인다. customer:{C9}:shipment:S400이라면 고객 단위로 모인다. 셋 다 문법적으로 가능하지만 원자성 범위와 부하 집중 지점이 다르다.

태그 후보 편해지는 작업 위험 선택 전 질문
창고 ID 창고 안 여러 키의 함께 변경 대형 창고 집중 모든 배송의 동시 원자 변경이 정말 필요한가?
배송 ID 배송 한 건의 상태·이벤트 처리 창고 전체 집계는 분산 업무 경계를 한 건으로 줄일 수 있는가?
고객 ID 고객 단위 자료의 함께 처리 대형 고객 집중 고객별 데이터와 요청 편차는 어느 정도인가?
무조건 공통 상수 모든 키가 같은 슬롯 샤딩 효과 상실 사실상 단일 shard를 원하는 것 아닌가?

정답은 태그 문법에서 나오지 않는다. 어떤 상태 전이가 같은 순간 적용되어야 하는지 업무 모델에서 나온다. 창고 전체의 집계는 비동기 조회 모델로 만들고 실제 출고의 원자성은 배송 한 건으로 제한할 수 있다면 배송 ID 태그가 유리할 수 있다. 반대로 창고 재고의 원자적 예약이 핵심이면 재고 품목 단위 같은 다른 모델이 필요하다. Redis 키를 먼저 정하고 업무 트랜잭션을 억지로 끼워 맞추지 않는다.

Java 키 생성기에서 검증할 것

// 키 규칙을 보여 주는 개념 예제. 실제 프로젝트에서 별도 테스트한다.
static String shipmentKey(String shipmentId, String field) {
    if (!shipmentId.matches("[A-Za-z0-9_-]+")) {
        throw new IllegalArgumentException("unsupported shipment ID");
    }
    if (!field.equals("status") && !field.equals("events")) {
        throw new IllegalArgumentException("unsupported field");
    }
    return "shipment:{" + shipmentId + "}:" + field;
}

이 예제는 사용자 입력의 중괄호가 태그 경계를 바꾸지 못하도록 문자 집합을 제한한다. 실제 ID에 다른 문자가 필요하면 무조건 거부하기보다 명확한 인코딩·정규화 규칙을 정하고 역변환 가능성까지 검토한다. Java 문자열이 같아 보여도 다른 서비스가 다른 바이트 인코딩이나 정규화를 쓰면 키가 달라질 수 있다. Redis serializer가 문자열을 어떻게 전송하는지도 포함한다. 키 prefix를 환경별로 추가할 때 태그 부분은 의도한 대로 유지되는지 확인한다.

서버를 기준으로 한 회귀 테스트

CLUSTER KEYSLOT은 실제 서버의 슬롯 계산을 확인하는 좋은 기준이다. 대표 배송 ID마다 status와 events가 같은 슬롯인지 검사하고, 빈 ID·중괄호 입력·매우 긴 ID·한글 ID 정책 같은 경계를 테스트한다. 서로 다른 배송이 반드시 다른 슬롯이어야 한다는 잘못된 테스트는 만들지 않는다. 유한한 슬롯 공간에서는 충돌이 가능하기 때문이다.

redis-cli -p 7000 CLUSTER KEYSLOT 'shipment:{S400}:status'
redis-cli -p 7000 CLUSTER KEYSLOT 'shipment:{S400}:events'
redis-cli -p 7000 CLUSTER KEYSLOT 'foo{}{bar}'
redis-cli -p 7000 CLUSTER KEYSLOT 'foo{{bar}}zap'

이 명령은 값을 만들거나 이동시키지 않는 계산 조회다. 앞의 두 결과가 같다는 사실은 같은 슬롯 조건을 확인하지만 뒤의 두 결과 숫자 자체를 암기할 필요는 없다. 어떤 바이트 범위를 해시했는지 설명할 수 있어야 한다. 클라이언트 업그레이드나 serializer 변경 뒤 같은 테스트를 반복하면 키 규칙의 호환성을 지킬 수 있다.

슬롯 재배치와 클라이언트 캐시의 수명

클라이언트는 보통 슬롯→노드 맵을 보관한다. 키→슬롯 계산은 같아도 운영자가 슬롯을 옮기거나 replica가 승격되면 두 번째 매핑이 바뀐다. 캐시 갱신은 성능 최적화이지 데이터를 복제하는 동작이 아니다. 오래된 맵을 사용한 요청이 MOVED를 만나면 새 담당 정보를 반영하고, ASK는 이동 중 예외 요청으로 처리한다. 모든 오류에서 전체 맵을 무제한 재조회하면 장애 순간 메타데이터 요청이 폭증할 수 있으므로 클라이언트의 갱신 정책을 이해해야 한다.

주소가 바뀌는 환경에서는 광고 주소와 DNS, TLS 인증서 이름도 맞아야 한다. seed 노드만 정상 인증되고 리다이렉션된 노드의 인증서나 hostname이 맞지 않으면 데이터 경로가 실패한다. 슬롯 모델이 올바르다는 사실만으로 네트워크 모델까지 검증된 것은 아니다. 개발 환경의 loopback 실습과 운영의 여러 호스트 배치는 이 점에서 크게 다르다.

전역 검색을 설계 요구로 드러내기

“고객 C9의 모든 배송 키를 찾자”는 요구를 SCAN customer:* 한 번으로 해결하려 하면 Cluster 전체 검색 범위를 놓칠 수 있다. 각 primary의 키 공간을 순회하거나 별도의 인덱스 자료구조·원장 조회를 사용해야 한다. SCAN은 전체 순회 중 데이터 변경이 있으면 중복 같은 특성을 고려해야 하며, 한 순간의 전역 스냅샷을 제공하는 일반 쿼리 엔진이 아니다. 정기 정산이나 정합성 감사의 근거로 사용할 때는 이 한계를 명시한다.

일부 버전의 단일 슬롯 glob 패턴 최적화는 패턴이 특정 태그를 확실히 가리킬 때 검색 범위를 좁히는 데 도움이 된다. 그러나 패턴의 wildcard 위치와 지원 버전 조건을 확인해야 하고 일반적인 KEYS *를 운영에서 안전한 명령으로 바꾸지 않는다. 전역 조회가 업무의 중심이라면 Redis Cluster를 모든 검색 요구의 유일한 저장소로 쓰는 것이 맞는지부터 검토한다.

면접 질문과 깊이 있는 답변

답을 펼치기 전에 원리, 장애 반례, 운영 확인 방법의 세 순서로 말해 보자. 짧은 정의만 외우기보다 어떤 조건에서 그 설명이 깨지는지를 덧붙이는 것이 중요하다.

서버를 추가하면 키의 슬롯 번호도 바뀌나요?

같은 키 바이트와 태그 규칙이라면 슬롯 번호는 변하지 않습니다. 키→슬롯 매핑은 고정이고 슬롯→담당 노드 매핑이 바뀝니다. 이 간접 참조 덕분에 서버 수 변화와 키 해시 계산을 분리할 수 있습니다. 리샤딩은 두 번째 매핑과 실제 키 위치를 옮기는 작업입니다.

CRC16 대신 Java hashCode를 써도 되나요?

안 됩니다. Redis가 정의한 CRC16 변형과 입력 바이트 규칙에 맞아야 합니다. 임의 해시 함수는 다른 슬롯을 계산합니다. 검증된 클라이언트를 사용하고 대표 키에 대해 서버의 CLUSTER KEYSLOT과 일치하는지 테스트하는 것이 안전합니다.

foo{}{bar}는 bar를 태그로 쓰나요?

아닙니다. 첫 여는 괄호와 그 뒤 첫 닫는 괄호 사이가 비어 있으므로 전체 키를 해시합니다. 뒤의 유효해 보이는 태그로 계속 탐색하는 규칙이 아닙니다. 키 생성기에서 중괄호가 포함된 사용자 입력을 허용할 때 이런 경계를 테스트해야 합니다.

모든 키에 같은 태그를 붙이면 편하지 않나요?

다중 키 연산의 슬롯 조건은 쉽게 맞출 수 있지만 모두 한 슬롯으로 몰려 샤딩 이점을 크게 잃습니다. 원자적으로 묶어야 하는 가장 작은 업무 단위를 선택해야 합니다. 고객·창고 단위 태그는 대형 고객이나 센터의 핫스폿 위험을 평가해야 합니다.

다른 태그는 항상 다른 슬롯인가요?

아닙니다. 슬롯 수가 유한하므로 서로 다른 태그가 같은 슬롯으로 해시될 수 있습니다. 같은 태그는 같은 슬롯을 보장하지만 역은 성립하지 않습니다. cross-slot 실패 시험에서는 실제 KEYSLOT 결과가 다른 키를 선택해야 합니다.

node ID와 IP 주소가 왜 다른가요?

ID는 Cluster 구성원의 정체성이고 주소는 현재 도달 위치입니다. 같은 주소에서 새 상태로 시작한 프로세스를 이전 노드와 동일하게 취급하면 안 됩니다. 상태 파일을 보존하고 운영 기록에는 ID·주소·역할을 함께 남겨야 역할 전환과 재합류를 정확히 추적할 수 있습니다.

Cluster에서 DB 1을 테넌트별로 쓰면 되나요?

Cluster는 DB 0 모델을 사용하며 standalone의 여러 논리 DB 선택 방식과 다릅니다. 키 네임스페이스·ACL·별도 인스턴스 등으로 격리 요구를 설계해야 합니다. 이름 접두사만 붙이는 것과 보안·성능 격리는 별개라는 점도 함께 검토합니다.

gossip은 모든 쓰기의 합의 프로토콜인가요?

아닙니다. 노드 상태와 구성 정보를 전파하는 메커니즘을 데이터 쓰기별 동기 합의와 혼동하면 안 됩니다. 일반 쓰기는 해당 primary에서 처리되고 replica에 비동기 복제됩니다. 따라서 구성 전파가 잘된다고 승인 쓰기의 무손실이나 강한 일관성이 자동 보장되지 않습니다.
