Cluster 장애 전환과 노드 변경

자동·수동 전환의 차이와 노드 추가·제거·업그레이드 순서를 데이터 보존 관점에서 익힌다.

첨부 Redis 학습 자료의 주제를 쉬운 설명과 공식 문서 근거로 재구성했습니다. 명령·설정의 버전 조건은 본문을 확인하세요. 장애 시나리오와 수치는 별도 표시가 없으면 학습용 가정이며, 코드가 실려 있다는 사실만으로 실행 검증을 의미하지 않습니다. 검증 범위와 남은 한계

1. 노드 작업은 데이터·역할·멤버십 세 가지 변화다

노드를 추가한다는 말에는 빈 프로세스를 실행하는 일, Cluster 구성원으로 알려지는 일, 슬롯을 받거나 다른 primary를 복제하는 일이 섞여 있다. 노드를 제거한다는 말에도 슬롯을 비우는 일, 다른 노드가 그 멤버를 잊는 일, 프로세스를 종료하는 일이 섞여 있다. 이들을 하나의 동작이라고 생각하면 빈 노드를 추가한 뒤 부하가 분산되지 않는 이유를 이해하지 못하거나, 데이터가 있는 primary를 먼저 종료하는 사고를 만들 수 있다.

물류센터 폐쇄를 생각하면 쉽다. 건물 전원을 끄기 전에 담당 구역과 장부를 다른 센터로 넘기고, 배차 시스템의 주소록을 갱신하고, 실제 배송 요청이 새 센터로 가는지 확인해야 한다. 비유의 한계는 Redis가 업무 데이터의 올바른 병합을 대신 결정하지 않는다는 점이다. 운영자는 데이터셋과 슬롯 소유권을 확인하는 정확한 절차를 따라야 한다.

2. 자동 전환 실험은 한 primary부터 시작한다

공통 실습에서 CLUSTER NODES로 현재 primary와 해당 replica를 확인한다. 종료할 노드는 실제 primary인지, 다른 살아 있는 노드에서 그 replica가 알려져 있는지 검사한다. 일회용 환경의 그 primary 하나를 SHUTDOWN NOSAVE로 종료하고 다른 primary에서 상태를 관찰한다. 이는 정상 종료 실험이며 전원 장애와 같다고 주장하지 않는다. timeout과 선출 지연 동안 일부 요청이 실패할 수 있다.

예상 결과는 적격 replica가 새 primary가 되어 기존 슬롯을 담당하는 것이다. 원래 primary를 다시 시작하면 더 최신 구성에 따라 replica로 합류할 수 있다. 같은 포트가 다시 응답한다고 그 포트가 여전히 쓰기 담당이라는 뜻은 아니다. ROLE, INFO replication, CLUSTER NODES를 함께 확인한다. 유실이 관찰되지 않은 한 번의 실험은 무손실 보장이 아니며, 복제 지연과 장애 타이밍이 다르면 승인된 쓰기도 없어질 수 있다.

3. 정상 수동 전환과 FORCE·TAKEOVER를 구분한다

계획된 유지보수에서는 primary를 일부러 충돌시키기보다 그 replica에서 CLUSTER FAILOVER를 실행하는 방법을 검토한다. 정상 수동 전환은 기존 primary와 협력하여 클라이언트 처리와 복제 offset을 맞추고, replica가 그 지점까지 처리한 뒤 전환을 진행한다. 그래서 갑작스러운 장애에서의 승격보다 데이터 전달 측면에서 안전한 절차다. 그러나 모든 외부 업무가 무중단·무손실이라는 일반 보장으로 확대하지 않는다. 재연결과 다른 동시 장애는 여전히 검증해야 한다.

# 예시: 7004가 교체 대상 primary의 replica임을 실제로 확인한 경우에만 실행
redis-cli -p 7004 ROLE
redis-cli -p 7004 CLUSTER FAILOVER
# 이후 다른 노드에서도 새 역할과 슬롯 범위를 확인
redis-cli -p 7000 CLUSTER NODES

FORCE는 기존 primary와의 정상 협력 없이 전환을 시도하는 경로이고, TAKEOVER는 합의 안전장치까지 우회할 수 있는 더 위험한 경로다. 이름만 보고 “더 확실한 전환”이라고 선택하지 않는다. 네트워크 분할 복구 등 특수 작업에서 정확한 데이터 손실 가능성과 권위 있는 쪽을 결정한 뒤에만 검토한다. 이 교재의 기본 실습에서는 두 옵션을 실행하지 않는다. 새로 추가한 replica라면 충분한 primary들이 그 replica를 알고 있어야 선출될 수 있으므로 발견 직후 즉시 전환부터 시도하지 않는다.

4. 새 primary를 추가하려면 빈 노드와 슬롯 이전이 필요하다

7006에 공통 설정과 같은 방식으로 새 디렉터리·별도 nodes.conf를 가진 빈 노드를 실행했다고 하자. 그 노드를 기존 Cluster에 추가한다. 주소는 모두 로컬 테스트 예시다.

redis-cli --cluster add-node 127.0.0.1:7006 127.0.0.1:7000
redis-cli -p 7000 CLUSTER NODES
redis-cli --cluster reshard 127.0.0.1:7000

추가만으로 기존 데이터가 자동으로 충분히 재배치되는 것은 아니다. 새 node ID를 확인하고 리샤딩으로 일부 슬롯을 넘긴다. 새 primary가 실제 트래픽을 받으면 그에 대응하는 replica도 마련해야 장애 내성을 유지할 수 있다. 슬롯의 개수뿐 아니라 데이터 크기와 요청 부하를 봐야 한다. 기존 세 primary에 replica가 하나씩 있다는 사실이 새 primary의 보호를 자동으로 의미하지 않는다.

5. 새 replica는 누구의 복사본인지 지정한다

별도로 실행한 빈 7007을 replica로 추가할 때는 목표 primary ID를 확인한 뒤 해당 ID를 지정한다. 아래의 TARGET_PRIMARY_ID는 반드시 실제 조회한 값으로 채워야 하며 문자 그대로 실행할 값이 아니다.

# TARGET_PRIMARY_ID에 실제 대상 primary의 node ID를 넣은 뒤 실행
redis-cli --cluster add-node 127.0.0.1:7007 127.0.0.1:7000   --cluster-slave --cluster-master-id "$TARGET_PRIMARY_ID"

CLI 옵션에 과거 용어가 남아 있어도 역할은 replica다. 명령이 수락된 뒤에도 초기 동기화가 완료되어 실제 대기 복사본 역할을 하는지 확인해야 한다. 복제 도중 메모리·네트워크·디스크 부담이 커질 수 있으므로 애플리케이션 지연을 함께 관찰한다. 새 replica의 복제 진행도가 충분하지 않은 상태에서 기존 replica를 제거하면 잠시 보호 수준이 떨어진다.

6. primary 제거는 슬롯을 비우는 것부터다

제거할 primary가 담당하는 모든 슬롯을 다른 primary로 옮기고, 남은 데이터와 소유권 상태를 검사한 뒤 멤버십에서 제거한다. redis-cli --cluster del-node 접속주소 제거할ID는 정확한 ID를 대상으로 해야 한다. 슬롯을 가진 노드를 먼저 종료해서 장애 전환에 의존하는 것은 계획된 축소 절차가 아니다. replica를 제거할 때도 그 primary에 남은 보호 수와 장애 도메인을 확인한다.

replica migration은 어떤 primary에 여분 replica가 있고 다른 primary가 복제본 없이 고립되었을 때 복제 배치를 개선할 수 있는 기능이다. 관련 barrier와 migration 설정에 따라 동작하며 사용자가 모든 상황에서 원하는 위치로 즉시 옮겨 주는 보장은 없다. 데이터 슬롯 이동인 리샤딩과 replica의 소속 이동을 구분한다. replica migration은 없어진 데이터 자체를 만들어 내지 못한다.

7. 롤링 업그레이드는 한 번에 한 위험만 늘린다

운영 버전의 업그레이드 호환성과 릴리스 노트를 먼저 확인한다. 백업 복구 검증 없이 버전만 바꾸지 않는다. replica 하나를 업그레이드하고 정상 복제와 지연을 확인한 뒤 계획된 수동 전환으로 그 노드를 primary로 만들고, 이전 primary를 replica 상태에서 업그레이드하는 흐름을 검토한다. 모든 replica나 모든 primary를 동시에 재시작하지 않는다. 단계마다 멈출 수 있는 기준과 원래 버전으로 돌아갈 수 있는 데이터 형식·설정 호환성을 확인한다.

실습 공통 토대: 여섯 노드의 격리된 작은 Cluster

이 절은 13~16장을 독립적으로 읽는 독자를 위한 실습 토대다. 아래 명령은 교재 작성 중 실제 실행한 결과가 아니며 이후 설명은 예상 관찰이다. 이미 사용 중인 포트와 충돌하지 않는 로컬 일회용 환경에서만 수행한다. 동일 호스트의 여섯 프로세스는 클러스터 프로토콜 학습에는 도움이 되지만 호스트 장애를 견디는 배치가 아니다. 운영에서는 primary와 그 replica를 서로 다른 장애 도메인에 배치하고, 인증·TLS·방화벽·백업·여유 메모리·복제 지연 정책을 별도로 설계해야 한다.

redis-server --version
redis-cli --version
LAB=$(mktemp -d /tmp/redis-cluster-study.XXXXXX)
printf '%s\n' "$LAB"
for p in 7000 7001 7002 7003 7004 7005; do
  mkdir -p "$LAB/$p"
  cat > "$LAB/$p/redis.conf" <<EOF
port $p
bind 127.0.0.1
protected-mode yes
dir $LAB/$p
pidfile $LAB/$p/redis.pid
logfile $LAB/$p/redis.log
daemonize yes
cluster-enabled yes
cluster-config-file nodes.conf
cluster-node-timeout 5000
save ""
appendonly no
EOF
  redis-server "$LAB/$p/redis.conf"
done
redis-cli --cluster create   127.0.0.1:7000 127.0.0.1:7001 127.0.0.1:7002   127.0.0.1:7003 127.0.0.1:7004 127.0.0.1:7005   --cluster-replicas 1

생성 도구가 제시하는 primary/replica 관계와 슬롯 범위를 읽고, 오직 이번에 만든 빈 노드 여섯 개가 맞을 때만 확인 질문에 동의한다. 포트 순서만 보고 특정 replica의 부모를 단정하지 않는다. 도구가 실제 제안하고 생성한 관계를 기록한다. 데이터 포트 70007005 외에 기본 cluster bus 포트 1700017005도 노드 사이에서 필요하다. loopback 실습에서는 동일 호스트로 접근하지만 컨테이너나 VM을 섞으면 광고한 주소가 각 클라이언트와 다른 노드에서 실제로 도달 가능한지 확인해야 한다.

nodes.conf는 사용자가 수동 편집하는 일반 설정 템플릿이 아니라 Redis가 자신의 노드 ID, 다른 노드, 슬롯 배치 같은 상태를 기록하는 파일이다. 이 예제는 각 프로세스의 dir가 다르므로 파일명이 같아도 서로 다른 파일을 사용한다. 여러 노드가 하나의 nodes.conf를 공유하게 해서는 안 된다. save ""와 appendonly no는 실습용으로 영속성을 끈 설정이므로 재시작 복구 실험이나 운영 내구성의 근거로 사용할 수 없다. 재시작 후 데이터가 보이지 않는 것을 Cluster의 슬롯 계산 오류로 오인하지 않는다.

최초 정상 상태를 확인하는 네 가지 관점

redis-cli -p 7000 CLUSTER INFO
redis-cli -p 7000 CLUSTER NODES
redis-cli --cluster check 127.0.0.1:7000
redis-cli -p 7000 CLUSTER KEYSLOT 'shipment:{S100}:status'
redis-cli -p 7000 CLUSTER KEYSLOT 'shipment:{S100}:events'
redis-cli -c -p 7000 SET 'shipment:{S100}:status' READY
redis-cli -c -p 7001 GET 'shipment:{S100}:status'

첫 관점은 전체 상태다. 안정 상태에서는 cluster_state:ok와 전체 슬롯 할당을 기대한다. 둘째는 노드 관계다. CLUSTER NODES의 node ID, 역할, replica의 부모 ID, 링크 상태, 슬롯 범위를 읽는다. 셋째는 슬롯 일관성이다. 검사 도구가 모든 슬롯의 커버리지와 배치를 어떻게 보고하는지 확인한다. 넷째는 애플리케이션 경로다. -c를 붙인 redis-cli가 다른 primary로의 리다이렉션을 처리하며 쓰기와 읽기를 수행하는지 본다. 노드 상태가 정상이더라도 애플리케이션의 DNS, 자격 증명, 라우팅 정보가 잘못되면 요청은 실패한다.

위 두 키는 중괄호 안의 S100이 같으므로 동일 슬롯이 예상된다. 어떤 숫자가 나오는지 암기하지 말고 실제 CLUSTER KEYSLOT으로 확인한다. 동일 슬롯이라고 두 키의 값이 반드시 같다는 의미는 아니며, 동일 primary에 있다고 반드시 동일 슬롯인 것도 아니다. 하나의 primary가 수천 슬롯을 맡을 수 있기 때문이다. 다중 키 명령의 가능 여부는 서버 주소가 아니라 슬롯 번호로 판단한다.

장애를 넣기 전에 작성할 기록표

기록 항목 기록하는 이유 해석할 때의 주의
실행 버전과 설정 파일 실험 재현과 버전별 차이 확인 latest 태그를 버전으로 기록하지 않는다
primary ID와 슬롯 범위 장애가 영향을 주는 데이터 범위 파악 포트는 역할과 함께 바뀔 수 있다
replica의 부모 ID와 복제 상태 승격 가능성과 최신성 평가 링크 연결과 데이터 완전성은 다르다
요청 ID·시작·종료 시각 업무 성공과 서버 성공을 구분 timeout은 미실행의 증명이 아니다
변경 전후의 노드 출력 역할 전환·슬롯 이전 검증 한 노드의 순간 관찰을 전체 진실로 취급하지 않는다

장애 실습에서 DEBUG SEGFAULT를 사용할 필요는 없다. 이 명령은 의도적으로 프로세스를 충돌시키며 운영 환경에서는 금지해야 한다. 명확히 식별한 일회용 인스턴스의 정상 종료, 또는 격리된 컨테이너의 정지부터 시작하면 된다. 정상 종료 실험은 전원 장애·커널 정지·부분 네트워크 분할과 동일하지 않다. 그 차이를 실험 보고서에 적어야 결과를 과장하지 않는다. 실제 네트워크 분할 실험은 host 방화벽을 즉흥적으로 바꾸기보다 별도의 네트워크 namespace나 전용 컨테이너 네트워크를 준비한 뒤 수행한다.

정리와 증거 보존

# 이번 실습에서 직접 생성했고 다른 서비스가 아닌 것을 먼저 확인한다.
for p in 7000 7001 7002 7003 7004 7005; do
  redis-cli -h 127.0.0.1 -p "$p" SHUTDOWN NOSAVE
done
# $LAB의 로그와 설정은 분석이 끝날 때까지 보존한다.

추가한 7006, 7007 같은 노드가 있다면 해당 실습의 정확한 목록을 별도로 종료한다. 노드 제거 명령을 실행했다고 프로세스까지 종료되는 것은 아니다. 반대로 프로세스를 종료했다고 나머지 노드들이 그 노드를 잊은 것도 아니다. 멤버십 변경, 프로세스 생명주기, 데이터 보존은 서로 다른 작업이라는 점을 마지막까지 구분한다.

유지보수 런북: 한 primary를 교체하고 보호 수준을 회복하기

실제 노드 ID와 역할을 확인하여 P가 primary, R이 그 replica인 상태를 가정한다. 목표는 P의 유지보수이며, 첫 단계에서 확인할 것은 “R 프로세스가 떠 있다”가 아니라 “R이 P의 복제 스트림을 정상적으로 따라가며 승격 가능한 상태이고, 다른 primary들이 R을 알고 있다”는 사실이다. 신규 replica의 초기 동기화가 끝나지 않았다면 작업을 시작하지 않는다.

단계 실행 목적 통과 증거 통과하지 못하면
준비 현재 관계와 복구 경로 확보 백업·노드 ID·복제 상태 기록 작업 보류, 원인 조사
replica 점검 새 담당자 자격 확인 정상 복제·충분한 여유·구성원 인식 동기화·인증·자원 문제 해결
정상 수동 전환 요청 R을 primary로 변경 ROLE·NODES에서 새 역할 확인 로그 확인, 무작정 FORCE 금지
앱 경로 확인 고객 요청 정상화 실제 읽기·쓰기와 지연 지표 클라이언트 라우팅·ACL 점검
이전 P 유지보수 이제 replica인 노드 작업 새 버전 기동·복제 재연결 호환성·설정·로그 검토
보호 수준 회복 다음 장애 대비 원하는 replica 수·지연 회복 다음 노드 작업 시작 금지

CLUSTER FAILOVER의 OK는 요청을 수락했다는 뜻이지 전환이 이미 완료되었다는 증거가 아니다. 이후 비동기로 진행되는 상태를 확인해야 한다. replica 로그에 수동 전환 timeout이 나타났다면 실패 원인을 분석한다. 반복 호출을 자동 재시도 루프에 넣기보다 현재 어떤 역할이 되었는지부터 확인해야 의도하지 않은 연속 변경을 피할 수 있다.

FORCE를 선택하기 전에 답할 세 질문

첫째, 기존 primary는 정말 도달 불가능한가, 아니면 이 운영 단말에서만 접근하지 못하는가? 둘째, 승격할 replica가 어느 시점까지 데이터를 받았는가? 셋째, 과반 primary들이 그 전환을 승인할 수 있는가? FORCE는 정상 primary와의 협력 절차를 생략하지만 과반 승인 조건까지 자동으로 없애는 옵션은 아니다. TAKEOVER는 이보다 더 나아가 합의 승인을 우회하므로 별도 재해복구 의사결정과 데이터 손실 평가가 필요하다.

두 운영자가 서로 다른 쪽에서 동시에 강제 복구를 진행하면 충돌을 더 키울 수 있다. incident commander나 단일 작업자를 정하고, 사용한 node ID·명령·시각·응답을 기록한다. 주소가 같은지보다 어떤 정체성의 노드를 바꿨는지가 중요하다. 하나의 공식 작업 기록이 있어야 뒤늦게 합류한 운영자가 이미 수행한 전환을 다시 시도하지 않는다.

노드 축소에서 놓치기 쉬운 빈 공간

새 primary를 추가할 때는 먼저 빈 노드가 생기고 나중에 슬롯을 받는다. 제거할 때는 먼저 슬롯이 없어지고 나중에 멤버십에서 빠진다. 이 대칭을 기억하면 순서가 선명해진다. 제거 대상의 슬롯을 옮겼더라도 replica 관계가 어떻게 바뀌었는지 확인해야 한다. 특정 primary를 따라가던 replica가 의도하지 않은 보호 배치로 남을 수 있다. 전체 노드 수가 줄어든 만큼 감당할 수 있는 장애 조합도 다시 계산한다.

단순히 del-node가 성공했다는 이유로 서버 비용을 즉시 없애지 않는다. 다른 노드가 제거 사실을 반영했는지, 애플리케이션의 토폴로지 캐시에 오래된 주소가 남지 않았는지, 해당 프로세스가 실제 종료되었는지 확인한다. 필요한 로그와 설정은 보존하고 비밀 값이 담긴 디스크 정리는 조직 절차에 따른다. 데이터 삭제와 멤버십 변경은 별개의 행위다.

replica migration을 오해하지 않기

P1에 replica가 둘, P2에는 하나도 없다면 일부 조건에서 replica가 P2로 소속을 옮겨 다음 장애에 대한 내성을 개선할 수 있다. 그러나 그 replica가 P2의 전체 데이터를 받는 데 시간과 자원이 필요하다. 이동했다는 구성 정보만 보고 즉시 완전한 보호가 생겼다고 판단하지 않는다. 복제 초기 동기화와 지연이 정상화된 뒤 보호 수준을 보고한다.

운영 목표가 각 shard에 독립 장애 도메인의 replica 하나 이상이라면 자동 migration 이후 배치가 그 목표를 만족하는지도 확인한다. 네트워크상 가까운 서버가 선택되었다고 물리 장애 도메인까지 항상 원하는 대로 배치되는 것은 아니다. 자동화 기능과 조직의 배치 정책을 연결하는 검증이 필요하다. 이 검증 없이 “migration이 있으니 replica 설계는 필요 없다”고 말하면 안 된다.

업그레이드 완료는 버전 문자열 이상의 의미다

버전이 바뀌었다는 사실 외에도 기존 명령·스크립트·직렬화·ACL·TLS·관찰 도구가 동작하는지 확인한다. 영속성 파일 형식이나 설정 차이 때문에 이전 버전으로 바로 돌아갈 수 없는 경우가 있으므로 롤백 가능성을 사전에 검토한다. 이 장은 특정 최신 버전을 추천하지 않으며 실제 목표 버전의 공식 업그레이드 문서와 릴리스 노트를 작업 계획에 연결해야 한다.

한 shard의 전환과 replica 복구가 끝나면 다음 shard로 넘어간다. 장애가 발생하면 어디에서 멈췄는지를 표에 표시하고 남은 노드를 한꺼번에 재시작하지 않는다. 계획 작업의 목표는 최단 명령 수가 아니라 각 단계에서 현재 권위 데이터와 남은 장애 내성을 설명할 수 있는 상태를 유지하는 것이다.

면접 질문과 깊이 있는 답변

답을 펼치기 전에 원리, 장애 반례, 운영 확인 방법의 세 순서로 말해 보자. 짧은 정의만 외우기보다 어떤 조건에서 그 설명이 깨지는지를 덧붙이는 것이 중요하다.

정상 CLUSTER FAILOVER는 어디에서 실행하나요?

교체하려는 primary의 replica에서 실행합니다. 실제 부모 관계를 확인한 뒤 수행해야 합니다. 정상 경로는 기존 primary와 협력하여 복제 offset을 맞춘 뒤 전환하므로 계획 유지보수에 유용합니다. 강제 옵션을 기본 절차처럼 사용하지 않습니다.

FORCE와 TAKEOVER는 더 안전한 옵션인가요?

아닙니다. 정상 협력이나 합의 안전장치를 우회하는 특수 경로입니다. 데이터가 덜 최신인 노드를 승격하거나 충돌 구성을 만드는 위험을 검토해야 합니다. 네트워크 분할 복구 같은 명확한 상황에서 권위 있는 데이터와 손실 허용 범위를 결정한 뒤에만 고려합니다.

새 replica를 추가하자마자 승격하면 되나요?

먼저 다른 primary들이 그 replica를 알고 있는지와 실제 복제 상태를 확인해야 합니다. 초기 동기화가 끝나지 않았거나 선출에 필요한 인식이 전파되지 않았다면 전환이 실패할 수 있습니다. 명령 수락과 보호 수준 확보는 같은 시점이 아닙니다.

새 primary에 데이터가 없는 것은 오류인가요?

슬롯을 아직 받지 않았다면 정상일 수 있습니다. 빈 노드 추가와 슬롯 재배치는 별도 단계입니다. node ID를 확인하고 원하는 슬롯을 리샤딩한 뒤 부하와 데이터량을 관찰합니다. 새 primary용 replica가 준비되었는지도 함께 확인합니다.

primary를 지우려면 프로세스부터 종료하나요?

계획된 제거에서는 담당 슬롯을 다른 primary로 옮기고 최종 소유권과 데이터 상태를 확인한 뒤 멤버십에서 제거하고 프로세스를 종료합니다. 먼저 종료하면 불필요한 장애 전환과 보호 수준 저하를 만들 수 있습니다. 작업 순서를 데이터·멤버십·프로세스로 나누어 관리합니다.

replica migration과 리샤딩의 차이는요?

리샤딩은 슬롯 소유권과 키를 다른 primary로 옮기는 일입니다. replica migration은 복제본이 부족한 primary를 보호하도록 replica의 소속을 바꾸는 기능입니다. 후자가 없어져 버린 데이터를 복원하거나 primary의 슬롯 부하를 균등하게 나누는 것은 아닙니다.

업그레이드는 왜 replica부터 검토하나요?

primary의 직접 서비스 경로를 유지하면서 새 버전의 기동·복제·지연을 먼저 검증할 수 있기 때문입니다. 이후 정상 수동 전환과 이전 primary 업그레이드를 단계적으로 진행할 수 있습니다. 다만 버전 호환·데이터 형식·롤백 가능성은 해당 릴리스 문서로 먼저 확인해야 합니다.

재시작한 원래 primary가 다시 primary인가요?

그렇다고 가정하면 안 됩니다. 장애 전환 뒤에는 새 구성에 따라 replica로 합류할 수 있습니다. 포트가 다시 열렸다는 사실보다 node ID·ROLE·부모 관계·슬롯 소유권을 확인합니다. 클라이언트도 이전 주소를 영구 쓰기 대상으로 고정해서는 안 됩니다.
