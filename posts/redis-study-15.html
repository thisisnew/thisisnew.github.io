실행 검증 기록: 로컬 Cluster 통합 시험은 Redis 7.2.5의 임시 여섯 노드에서 단일 슬롯 이전 중 ASK·TRYAGAIN·동일 연결의 ASKING 범위, 이전 뒤 표본 값·자료형·양수 TTL 및 정상 수동 전환을 검사한다. 자동 장애 전환·네트워크 분할·FORCE·TAKEOVER·노드 추가/제거·버전 업그레이드·Spring 재연결·운영 부하는 이 시험에 포함하지 않는다. Java 예제 실행 기록은 교육 모델의 본문 일치·컴파일·독립 main 검사를 별도로 기록한다. 아래의 수동 실습 명령 전체를 실행했다는 뜻은 아니며 실제 통과 여부와 검사 시각은 각 기록에서 확인한다.

입문 해설. 담당자 교체·담당 구역 이전·구성원 삭제를 구분하기

물류센터 A의 장비를 점검하려고 한다고 하자. 같은 장부를 따라 적던 대기 담당자 A1에게 업무를 넘기면 담당 구역은 그대로이고 담당 프로세스의 역할만 바뀐다. 이것이 장애 전환을 이해하는 출발점이다. 반대로 A가 맡던 일부 배송 구역을 전혀 다른 센터 B로 넘기면 슬롯과 데이터를 옮기는 리샤딩이다. 마지막으로 A라는 센터를 주소록에서 빼는 것은 멤버십 제거다. 세 작업은 영향을 주는 상태가 다르므로 명령도 검사도 다르다.

서버를 추가할 때도 세 단계를 구분한다. 프로세스를 실행했다는 사실은 Redis가 응답한다는 뜻이다. Cluster에 알려졌다는 사실은 구성원으로 인식된다는 뜻이다. 실제 슬롯을 받거나 replica로 동기화되었다는 사실은 데이터 역할을 수행한다는 뜻이다. 새 primary가 슬롯 0개를 가지고 있다면 메모리가 충분해도 기존 데이터의 저장 부하가 자동으로 나뉘지는 않는다. 새 replica가 목록에 나타났더라도 전체 동기화가 끝나기 전에는 기대한 대기 사본이 완성되지 않았을 수 있다.

이 장에서 계속 던질 질문은 “현재 누가 쓰기를 받고, 어떤 데이터를 가지고, 다음 장애 때 누가 대신할 수 있는가?”다. 이 세 질문에 답할 수 있으면 정상 수동 전환·자동 장애 전환·노드 축소·롤링 유지보수의 차이를 더 쉽게 이해할 수 있다. 명령 이름을 외우는 것보다 각 단계 뒤에 이 세 질문의 답이 어떻게 바뀌는지 적어 보는 것이 중요하다. 다음 작업을 시작할 조건도 같은 질문으로 정한다.

1. 노드 작업은 데이터·역할·멤버십 세 가지 변화다

노드를 추가한다는 말에는 빈 프로세스를 실행하는 일, Cluster 구성원으로 알려지는 일, 슬롯을 받거나 다른 primary를 복제하는 일이 섞여 있다. 노드를 제거한다는 말에도 슬롯을 비우는 일, 다른 노드가 그 멤버를 잊는 일, 프로세스를 종료하는 일이 섞여 있다. 이들을 하나의 동작이라고 생각하면 빈 노드를 추가한 뒤 부하가 분산되지 않는 이유를 이해하지 못하거나, 데이터가 있는 primary를 먼저 종료하는 사고를 만들 수 있다.

물류센터 폐쇄를 생각하면 쉽다. 건물 전원을 끄기 전에 담당 구역과 장부를 다른 센터로 넘기고, 배차 시스템의 주소록을 갱신하고, 실제 배송 요청이 새 센터로 가는지 확인해야 한다. 비유의 한계는 Redis가 업무 데이터의 올바른 병합을 대신 결정하지 않는다는 점이다. 운영자는 데이터셋과 슬롯 소유권을 확인하는 정확한 절차를 따라야 한다.

2. 자동 전환 실험은 한 primary부터 시작한다

공통 실습에서 CLUSTER NODES로 현재 primary와 해당 replica를 확인한다. 종료할 노드는 실제 primary인지, 다른 살아 있는 노드에서 그 replica가 알려져 있는지 검사한다. 일회용 환경의 그 primary 하나를 SHUTDOWN NOSAVE로 종료하고 다른 primary에서 상태를 관찰한다. 이는 정상 종료 실험이며 전원 장애와 같다고 주장하지 않는다. timeout과 선출 지연 동안 일부 요청이 실패할 수 있다.

예상 결과는 적격 replica가 새 primary가 되어 기존 슬롯을 담당하는 것이다. 원래 primary를 다시 시작하면 더 최신 구성에 따라 replica로 합류할 수 있다. 같은 포트가 다시 응답한다고 그 포트가 여전히 쓰기 담당이라는 뜻은 아니다. ROLE, INFO replication, CLUSTER NODES를 함께 확인한다. 유실이 관찰되지 않은 한 번의 실험은 무손실 보장이 아니며, 복제 지연과 장애 타이밍이 다르면 승인된 쓰기도 없어질 수 있다.

3. 정상 수동 전환과 FORCE·TAKEOVER를 구분한다

계획된 유지보수에서는 primary를 일부러 충돌시키기보다 그 replica에서 CLUSTER FAILOVER를 실행하는 방법을 검토한다. 정상 수동 전환은 기존 primary와 협력하여 클라이언트 처리와 복제 offset을 맞추고, replica가 그 지점까지 처리한 뒤 전환을 진행한다. 그래서 갑작스러운 장애에서의 승격보다 데이터 전달 측면에서 안전한 절차다. 그러나 모든 외부 업무가 무중단·무손실이라는 일반 보장으로 확대하지 않는다. 재연결과 다른 동시 장애는 여전히 검증해야 한다.

# 예시: 7004가 교체 대상 primary의 replica임을 실제로 확인한 경우에만 실행
redis-cli -p 7004 ROLE
redis-cli -p 7004 CLUSTER FAILOVER
# 이후 다른 노드에서도 새 역할과 슬롯 범위를 확인
redis-cli -p 7000 CLUSTER NODES

FORCE는 기존 primary와의 정상 협력 없이 전환을 시도하는 경로이고, TAKEOVER는 합의 안전장치까지 우회할 수 있는 더 위험한 경로다. 이름만 보고 “더 확실한 전환”이라고 선택하지 않는다. 네트워크 분할 복구 등 특수 작업에서 정확한 데이터 손실 가능성과 권위 있는 쪽을 결정한 뒤에만 검토한다. 이 교재의 기본 실습에서는 두 옵션을 실행하지 않는다. 새로 추가한 replica라면 충분한 primary들이 그 replica를 알고 있어야 선출될 수 있으므로 발견 직후 즉시 전환부터 시도하지 않는다.

4. 새 primary를 추가하려면 빈 노드와 슬롯 이전이 필요하다

7006에 공통 설정과 같은 방식으로 새 디렉터리·별도 nodes.conf를 가진 빈 노드를 실행했다고 하자. 그 노드를 기존 Cluster에 추가한다. 주소는 모두 로컬 테스트 예시다.

redis-cli --cluster add-node 127.0.0.1:7006 127.0.0.1:7000
redis-cli -p 7000 CLUSTER NODES
redis-cli --cluster reshard 127.0.0.1:7000

추가만으로 기존 데이터가 자동으로 충분히 재배치되는 것은 아니다. 새 node ID를 확인하고 리샤딩으로 일부 슬롯을 넘긴다. 새 primary가 실제 트래픽을 받으면 그에 대응하는 replica도 마련해야 장애 내성을 유지할 수 있다. 슬롯의 개수뿐 아니라 데이터 크기와 요청 부하를 봐야 한다. 기존 세 primary에 replica가 하나씩 있다는 사실이 새 primary의 보호를 자동으로 의미하지 않는다.

5. 새 replica는 누구의 복사본인지 지정한다

별도로 실행한 빈 7007을 replica로 추가할 때는 목표 primary ID를 확인한 뒤 해당 ID를 지정한다. 아래의 TARGET_PRIMARY_ID는 반드시 실제 조회한 값으로 채워야 하며 문자 그대로 실행할 값이 아니다.

# TARGET_PRIMARY_ID에 실제 대상 primary의 node ID를 넣은 뒤 실행
redis-cli --cluster add-node 127.0.0.1:7007 127.0.0.1:7000   --cluster-slave --cluster-master-id "$TARGET_PRIMARY_ID"

CLI 옵션에 과거 용어가 남아 있어도 역할은 replica다. 명령이 수락된 뒤에도 초기 동기화가 완료되어 실제 대기 복사본 역할을 하는지 확인해야 한다. 복제 도중 메모리·네트워크·디스크 부담이 커질 수 있으므로 애플리케이션 지연을 함께 관찰한다. 새 replica의 복제 진행도가 충분하지 않은 상태에서 기존 replica를 제거하면 잠시 보호 수준이 떨어진다.

6. primary 제거는 슬롯을 비우는 것부터다

제거할 primary가 담당하는 모든 슬롯을 다른 primary로 옮기고, 남은 데이터와 소유권 상태를 검사한 뒤 멤버십에서 제거한다. redis-cli --cluster del-node 접속주소 제거할ID는 정확한 ID를 대상으로 해야 한다. 슬롯을 가진 노드를 먼저 종료해서 장애 전환에 의존하는 것은 계획된 축소 절차가 아니다. replica를 제거할 때도 그 primary에 남은 보호 수와 장애 도메인을 확인한다.

replica migration은 어떤 primary에 여분 replica가 있고 다른 primary가 복제본 없이 고립되었을 때 복제 배치를 개선할 수 있는 기능이다. 관련 barrier와 migration 설정에 따라 동작하며 사용자가 모든 상황에서 원하는 위치로 즉시 옮겨 주는 보장은 없다. 데이터 슬롯 이동인 리샤딩과 replica의 소속 이동을 구분한다. replica migration은 없어진 데이터 자체를 만들어 내지 못한다.

7. 롤링 업그레이드는 한 번에 한 위험만 늘린다

운영 버전의 업그레이드 호환성과 릴리스 노트를 먼저 확인한다. 백업 복구 검증 없이 버전만 바꾸지 않는다. replica 하나를 업그레이드하고 정상 복제와 지연을 확인한 뒤 계획된 수동 전환으로 그 노드를 primary로 만들고, 이전 primary를 replica 상태에서 업그레이드하는 흐름을 검토한다. 모든 replica나 모든 primary를 동시에 재시작하지 않는다. 단계마다 멈출 수 있는 기준과 원래 버전으로 돌아갈 수 있는 데이터 형식·설정 호환성을 확인한다.

실습 공통 토대: 여섯 노드의 격리된 작은 Cluster

이 절은 13~16장을 독립적으로 읽는 독자를 위한 실습 토대다. 아래 명령은 교재 작성 중 실제 실행한 결과가 아니며 이후 설명은 예상 관찰이다. 이미 사용 중인 포트와 충돌하지 않는 로컬 일회용 환경에서만 수행한다. 동일 호스트의 여섯 프로세스는 클러스터 프로토콜 학습에는 도움이 되지만 호스트 장애를 견디는 배치가 아니다. 운영에서는 primary와 그 replica를 서로 다른 장애 도메인에 배치하고, 인증·TLS·방화벽·백업·여유 메모리·복제 지연 정책을 별도로 설계해야 한다.

redis-server --version
redis-cli --version
LAB=$(mktemp -d /tmp/redis-cluster-study.XXXXXX)
printf '%s\n' "$LAB"
for p in 7000 7001 7002 7003 7004 7005; do
  mkdir -p "$LAB/$p"
  cat > "$LAB/$p/redis.conf" <<EOF
port $p
bind 127.0.0.1
protected-mode yes
dir $LAB/$p
pidfile $LAB/$p/redis.pid
logfile $LAB/$p/redis.log
daemonize yes
cluster-enabled yes
cluster-config-file nodes.conf
cluster-node-timeout 5000
save ""
appendonly no
EOF
  redis-server "$LAB/$p/redis.conf"
done
redis-cli --cluster create   127.0.0.1:7000 127.0.0.1:7001 127.0.0.1:7002   127.0.0.1:7003 127.0.0.1:7004 127.0.0.1:7005   --cluster-replicas 1

생성 도구가 제시하는 primary/replica 관계와 슬롯 범위를 읽고, 오직 이번에 만든 빈 노드 여섯 개가 맞을 때만 확인 질문에 동의한다. 포트 순서만 보고 특정 replica의 부모를 단정하지 않는다. 도구가 실제 제안하고 생성한 관계를 기록한다. 데이터 포트 70007005 외에 기본 cluster bus 포트 1700017005도 노드 사이에서 필요하다. loopback 실습에서는 동일 호스트로 접근하지만 컨테이너나 VM을 섞으면 광고한 주소가 각 클라이언트와 다른 노드에서 실제로 도달 가능한지 확인해야 한다.

nodes.conf는 사용자가 수동 편집하는 일반 설정 템플릿이 아니라 Redis가 자신의 노드 ID, 다른 노드, 슬롯 배치 같은 상태를 기록하는 파일이다. 이 예제는 각 프로세스의 dir가 다르므로 파일명이 같아도 서로 다른 파일을 사용한다. 여러 노드가 하나의 nodes.conf를 공유하게 해서는 안 된다. save ""와 appendonly no는 실습용으로 영속성을 끈 설정이므로 재시작 복구 실험이나 운영 내구성의 근거로 사용할 수 없다. 재시작 후 데이터가 보이지 않는 것을 Cluster의 슬롯 계산 오류로 오인하지 않는다.

최초 정상 상태를 확인하는 네 가지 관점

redis-cli -p 7000 CLUSTER INFO
redis-cli -p 7000 CLUSTER NODES
redis-cli --cluster check 127.0.0.1:7000
redis-cli -p 7000 CLUSTER KEYSLOT 'shipment:{S100}:status'
redis-cli -p 7000 CLUSTER KEYSLOT 'shipment:{S100}:events'
redis-cli -c -p 7000 SET 'shipment:{S100}:status' READY
redis-cli -c -p 7001 GET 'shipment:{S100}:status'

첫 관점은 전체 상태다. 안정 상태에서는 cluster_state:ok와 전체 슬롯 할당을 기대한다. 둘째는 노드 관계다. CLUSTER NODES의 node ID, 역할, replica의 부모 ID, 링크 상태, 슬롯 범위를 읽는다. 셋째는 슬롯 일관성이다. 검사 도구가 모든 슬롯의 커버리지와 배치를 어떻게 보고하는지 확인한다. 넷째는 애플리케이션 경로다. -c를 붙인 redis-cli가 다른 primary로의 리다이렉션을 처리하며 쓰기와 읽기를 수행하는지 본다. 노드 상태가 정상이더라도 애플리케이션의 DNS, 자격 증명, 라우팅 정보가 잘못되면 요청은 실패한다.

위 두 키는 중괄호 안의 S100이 같으므로 동일 슬롯이 예상된다. 어떤 숫자가 나오는지 암기하지 말고 실제 CLUSTER KEYSLOT으로 확인한다. 동일 슬롯이라고 두 키의 값이 반드시 같다는 의미는 아니며, 동일 primary에 있다고 반드시 동일 슬롯인 것도 아니다. 하나의 primary가 수천 슬롯을 맡을 수 있기 때문이다. 다중 키 명령의 가능 여부는 서버 주소가 아니라 슬롯 번호로 판단한다.

기록 항목 기록하는 이유 해석할 때의 주의

장애 실습에서 DEBUG SEGFAULT를 사용할 필요는 없다. 이 명령은 의도적으로 프로세스를 충돌시키며 운영 환경에서는 금지해야 한다. 명확히 식별한 일회용 인스턴스의 정상 종료, 또는 격리된 컨테이너의 정지부터 시작하면 된다. 정상 종료 실험은 전원 장애·커널 정지·부분 네트워크 분할과 동일하지 않다. 그 차이를 실험 보고서에 적어야 결과를 과장하지 않는다. 실제 네트워크 분할 실험은 host 방화벽을 즉흥적으로 바꾸기보다 별도의 네트워크 namespace나 전용 컨테이너 네트워크를 준비한 뒤 수행한다.

정리와 증거 보존

# 이번 실습에서 직접 생성했고 다른 서비스가 아닌 것을 먼저 확인한다.
for p in 7000 7001 7002 7003 7004 7005; do
  redis-cli -h 127.0.0.1 -p "$p" SHUTDOWN NOSAVE
done
# $LAB의 로그와 설정은 분석이 끝날 때까지 보존한다.

추가한 7006, 7007 같은 노드가 있다면 해당 실습의 정확한 목록을 별도로 종료한다. 노드 제거 명령을 실행했다고 프로세스까지 종료되는 것은 아니다. 반대로 프로세스를 종료했다고 나머지 노드들이 그 노드를 잊은 것도 아니다. 멤버십 변경, 프로세스 생명주기, 데이터 보존은 서로 다른 작업이라는 점을 마지막까지 구분한다.

유지보수 런북: 한 primary를 교체하고 보호 수준을 회복하기

실제 노드 ID와 역할을 확인하여 P가 primary, R이 그 replica인 상태를 가정한다. 목표는 P의 유지보수이며, 첫 단계에서 확인할 것은 “R 프로세스가 떠 있다”가 아니라 “R이 P의 복제 스트림을 정상적으로 따라가며 승격 가능한 상태이고, 다른 primary들이 R을 알고 있다”는 사실이다. 신규 replica의 초기 동기화가 끝나지 않았다면 작업을 시작하지 않는다.

단계 실행 목적 통과 증거 통과하지 못하면
준비 현재 관계와 복구 경로 확보 백업·노드 ID·복제 상태 기록 작업 보류, 원인 조사
replica 점검 새 담당자 자격 확인 정상 복제·충분한 여유·구성원 인식 동기화·인증·자원 문제 해결
정상 수동 전환 요청 R을 primary로 변경 ROLE·NODES에서 새 역할 확인 로그 확인, 무작정 FORCE 금지
앱 경로 확인 고객 요청 정상화 실제 읽기·쓰기와 지연 지표 클라이언트 라우팅·ACL 점검
이전 P 유지보수 이제 replica인 노드 작업 새 버전 기동·복제 재연결 호환성·설정·로그 검토
보호 수준 회복 다음 장애 대비 원하는 replica 수·지연 회복 다음 노드 작업 시작 금지

CLUSTER FAILOVER의 OK는 요청을 수락했다는 뜻이지 전환이 이미 완료되었다는 증거가 아니다. 이후 비동기로 진행되는 상태를 확인해야 한다. replica 로그에 수동 전환 timeout이 나타났다면 실패 원인을 분석한다. 반복 호출을 자동 재시도 루프에 넣기보다 현재 어떤 역할이 되었는지부터 확인해야 의도하지 않은 연속 변경을 피할 수 있다.

FORCE를 선택하기 전에 답할 세 질문

첫째, 기존 primary는 정말 도달 불가능한가, 아니면 이 운영 단말에서만 접근하지 못하는가? 둘째, 승격할 replica가 어느 시점까지 데이터를 받았는가? 셋째, 과반 primary들이 그 전환을 승인할 수 있는가? FORCE는 정상 primary와의 협력 절차를 생략하지만 과반 승인 조건까지 자동으로 없애는 옵션은 아니다. TAKEOVER는 이보다 더 나아가 합의 승인을 우회하므로 별도 재해복구 의사결정과 데이터 손실 평가가 필요하다.

두 운영자가 서로 다른 쪽에서 동시에 강제 복구를 진행하면 충돌을 더 키울 수 있다. incident commander나 단일 작업자를 정하고, 사용한 node ID·명령·시각·응답을 기록한다. 주소가 같은지보다 어떤 정체성의 노드를 바꿨는지가 중요하다. 하나의 공식 작업 기록이 있어야 뒤늦게 합류한 운영자가 이미 수행한 전환을 다시 시도하지 않는다.

노드 축소에서 놓치기 쉬운 빈 공간

새 primary를 추가할 때는 먼저 빈 노드가 생기고 나중에 슬롯을 받는다. 제거할 때는 먼저 슬롯이 없어지고 나중에 멤버십에서 빠진다. 이 대칭을 기억하면 순서가 선명해진다. 제거 대상의 슬롯을 옮겼더라도 replica 관계가 어떻게 바뀌었는지 확인해야 한다. 특정 primary를 따라가던 replica가 의도하지 않은 보호 배치로 남을 수 있다. 전체 노드 수가 줄어든 만큼 감당할 수 있는 장애 조합도 다시 계산한다.

단순히 del-node가 성공했다는 이유로 서버 비용을 즉시 없애지 않는다. 다른 노드가 제거 사실을 반영했는지, 애플리케이션의 토폴로지 캐시에 오래된 주소가 남지 않았는지, 해당 프로세스가 실제 종료되었는지 확인한다. 필요한 로그와 설정은 보존하고 비밀 값이 담긴 디스크 정리는 조직 절차에 따른다. 데이터 삭제와 멤버십 변경은 별개의 행위다.

replica migration을 오해하지 않기

P1에 replica가 둘, P2에는 하나도 없다면 일부 조건에서 replica가 P2로 소속을 옮겨 다음 장애에 대한 내성을 개선할 수 있다. 그러나 그 replica가 P2의 전체 데이터를 받는 데 시간과 자원이 필요하다. 이동했다는 구성 정보만 보고 즉시 완전한 보호가 생겼다고 판단하지 않는다. 복제 초기 동기화와 지연이 정상화된 뒤 보호 수준을 보고한다.

운영 목표가 각 shard에 독립 장애 도메인의 replica 하나 이상이라면 자동 migration 이후 배치가 그 목표를 만족하는지도 확인한다. 네트워크상 가까운 서버가 선택되었다고 물리 장애 도메인까지 항상 원하는 대로 배치되는 것은 아니다. 자동화 기능과 조직의 배치 정책을 연결하는 검증이 필요하다. 이 검증 없이 “migration이 있으니 replica 설계는 필요 없다”고 말하면 안 된다.

업그레이드 완료는 버전 문자열 이상의 의미다

버전이 바뀌었다는 사실 외에도 기존 명령·스크립트·직렬화·ACL·TLS·관찰 도구가 동작하는지 확인한다. 영속성 파일 형식이나 설정 차이 때문에 이전 버전으로 바로 돌아갈 수 없는 경우가 있으므로 롤백 가능성을 사전에 검토한다. 이 장은 특정 최신 버전을 추천하지 않으며 실제 목표 버전의 공식 업그레이드 문서와 릴리스 노트를 작업 계획에 연결해야 한다.

한 shard의 전환과 replica 복구가 끝나면 다음 shard로 넘어간다. 장애가 발생하면 어디에서 멈췄는지를 표에 표시하고 남은 노드를 한꺼번에 재시작하지 않는다. 계획 작업의 목표는 최단 명령 수가 아니라 각 단계에서 현재 권위 데이터와 남은 장애 내성을 설명할 수 있는 상태를 유지하는 것이다.

관찰 도구 해설. ROLE·복제 정보·Cluster 정보는 같은 보고서가 아니다

ROLE은 접속한 Redis가 지금 어떤 복제 역할을 수행하는지 보는 데 도움이 된다. INFO replication은 복제 링크와 동기화 상태 등 더 상세한 정보를 제공한다. CLUSTER NODES는 접속한 노드가 알고 있는 Cluster 정체성·부모·슬롯·링크 상태를 보여 준다. 이 출력들은 서로 관련되지만 관찰 대상과 시점이 다르다. 하나가 정상이라고 다른 모든 층까지 정상이라는 결론을 내리지 않는다.

예를 들어 R의 ROLE이 master로 바뀌었더라도 다른 노드의 슬롯 인식이 아직 수렴 중일 수 있다. 반대로 여러 노드가 R을 새 primary로 알고 있어도 앱이 오래된 연결이나 잘못된 주소를 사용해 실패할 수 있다. 또한 새 primary가 쓰기를 받아도 이를 따라가는 건강한 replica가 없다면 다음 장애 대비는 약해져 있다. “전환 완료”라는 말을 한 가지 성공 조건으로 뭉치지 말고 관찰 항목을 나눠야 한다.

관찰 알려 주는 것 이것만으로 모르는 것
PING 해당 접속 경로에서 응답함 역할·슬롯·복제 최신성
ROLE 그 노드의 현재 복제 역할 모든 노드의 구성 수렴·앱 성공
INFO replication 복제 링크·동기화 관찰 업무 데이터 전부의 정확성
CLUSTER NODES 그 노드가 아는 구성과 슬롯 모든 다른 노드가 같은 시점의 인식을 가짐
앱의 테스트 쓰기·읽기 해당 업무 경로의 실제 처리 다른 모든 슬롯·다음 장애 대비

로그를 남길 때는 포트만 쓰지 말고 node ID와 시각을 같이 적는다. 같은 주소에서 프로세스를 재설치하고 상태 파일을 새로 만들었다면 예전 노드와 다른 정체성이 될 수 있다. 주소가 다시 열렸다고 이전 담당자가 그대로 돌아왔다고 판단하면 안 된다. 반대로 역할이 바뀌어도 node ID는 같은 프로세스 정체성을 이어갈 수 있다. 주소·정체성·역할의 세 단어를 구분하면 노드 교체 기록이 명확해진다.

정상 수동 전환의 내부 순서. 복제 스트림의 같은 줄까지 맞추기

계획된 유지보수에서 정상 CLUSTER FAILOVER를 replica R에 요청하는 이유는 R을 다음 쓰기 담당자로 만들기 위해서다. R은 기존 primary P와 협력해 전환 절차를 진행한다. 핵심은 P가 전환 과정에서 쓰기 처리를 조정하고 자신이 도달한 복제 스트림 위치를 알리며, R이 그 위치까지 처리했는지를 확인한 뒤 승격을 시작한다는 점이다. 장부 비유로 현재 담당자가 새 쓰기를 잠시 조정하고 “이 줄까지는 넘겨야 한다”고 기준선을 알려 주는 것이다.

replication offset은 임의의 주문 버전 번호와 같은 것이 아니다. 복제 스트림에서 어디까지 처리했는지 나타내는 위치다. 서로 관계없는 복제 이력의 숫자만 가져와 대소를 비교해 최신 데이터를 확정해서는 안 된다. 정상 수동 전환에서는 현재 primary와 그 replica라는 관계 안에서 정해진 기준 위치를 맞추는 맥락이 중요하다. 숫자 하나보다 어느 primary의 어떤 이력을 따라가고 있는지 함께 확인한다.

기준 위치를 맞췄다고 바로 모든 앱 요청이 끝난 것은 아니다. 선출 승인과 역할 변경, 슬롯 담당 정보 전파, 클라이언트 경로 갱신이 뒤따른다. 명령 응답의 OK는 시작 요청을 수락했다는 의미이고, 결과는 별도 관찰로 확인해야 한다. 기존 연결에서 실행 중인 요청이나 응답 유실, 다른 shard의 동시 문제까지 자동으로 해결하는 업무 트랜잭션도 아니다. 전환 도중 오류·timeout이 났다면 먼저 실제 역할과 요청 결과를 조회한다.

자동 전환과 강제 옵션. 줄이는 대기 조건과 사라지는 보장을 따로 보기

자동 장애 전환은 P가 정상적으로 협력할 수 없는 상황에서 다른 노드의 장애 인식과 승격 후보·승인 절차를 통해 진행된다. 따라서 정상 수동 전환과 같은 복제 기준선 맞추기를 항상 기대할 수 없다. R이 살아 있다는 사실 외에 후보가 유효한지, 필요한 primary들이 서로 통신하고 승인할 수 있는지, Cluster 상태가 전환을 허용하는지를 확인해야 한다. 자동 전환 실패를 곧바로 “replica가 없어서” 한 가지 원인으로 축소하지 않는다.

FORCE는 정상 primary와 기준 위치를 맞추는 협력 단계를 생략하는 경로다. 하지만 필요한 다른 primary들의 승인까지 전부 없애는 선택으로 이해하면 안 된다. TAKEOVER는 합의 승인을 거치지 않고 새 구성 epoch를 만들어 슬롯을 주장하는 경로다. 이것은 “FORCE도 실패했으니 한 단계 더 강하게 누르는 버튼”이라는 사용 순서가 아니다. 각 옵션이 어떤 전제를 제거하는지 알고, 네트워크 분할과 데이터 권위를 통제하는 별도 복구 계획에서 판단해야 한다.

경로 기존 primary의 정상 협력 승인 절차의 의미 주요 판단
정상 수동 전환 사용함 정상 선출·전환 경로 유지 계획 작업에 필요한 복제·연결 상태
FORCE 생략함 다른 primary 승인까지 자동 제거하지 않음 후보 데이터와 손실 범위
TAKEOVER 생략함 합의 없이 슬롯 권위를 주장 중복 권위 방지·재해복구 결정

두 쪽이 서로를 보지 못하는데 양쪽 운영자가 각각 TAKEOVER를 실행하면, 같은 업무 범위에 대해 서로 다른 권위를 주장하는 구성을 만들 수 있다. 이를 안전하게 복구하려면 어떤 데이터셋을 최종 기준으로 삼을지와 반대쪽 쓰기를 어떻게 막을지부터 결정해야 한다. 이 교재는 FORCE와 TAKEOVER를 기본 자동 재시도 경로로 제공하지 않으며, 자체 통합 시험에서도 실행하지 않는다. 실제로 시험하지 않은 경로를 성공한 일반 경로와 같은 수준의 증거로 표시하지 않는다.

Java 예제. 작업을 시작해도 되는 조건을 한 번 더 묻기

아래 모델은 팀이 정한 유지보수 시작 조건을 검사한다. Redis 내부 선출 알고리즘이나 모든 승격 적격성을 구현한 코드는 아니다. backupRecoveryChecked는 백업 파일의 존재만이 아니라 팀이 요구한 복구 확인이 끝났다는 외부 입력이고, replica 상태·장애 도메인·앱 오류 예산 역시 다른 관찰에서 채워야 한다. 교육용 모델이 모르는 상태를 true로 가정해서는 안 된다.

import java.util.ArrayList;
import java.util.List;

public final class ClusterMaintenanceGateLesson {
    record Evidence(boolean backupRecoveryChecked, boolean expectedParent,
                    boolean replicaLinkUp, boolean initialSyncFinished,
                    boolean independentFailureDomain, boolean applicationHealthy) {}

    static List<String> blockers(Evidence e) {
        List<String> result = new ArrayList<>();
        if (!e.backupRecoveryChecked()) result.add("recovery evidence missing");
        if (!e.expectedParent()) result.add("unexpected replica parent");
        if (!e.replicaLinkUp()) result.add("replication link down");
        if (!e.initialSyncFinished()) result.add("initial sync in progress");
        if (!e.independentFailureDomain()) result.add("shared failure domain");
        if (!e.applicationHealthy()) result.add("application already unhealthy");
        return List.copyOf(result);
    }

    public static void main(String[] args) {
        Evidence ready = new Evidence(true, true, true, true, true, true);
        if (!blockers(ready).isEmpty()) throw new AssertionError("ready");
        Evidence syncing = new Evidence(true, true, true, false, true, true);
        if (!blockers(syncing).equals(List.of("initial sync in progress"))) {
            throw new AssertionError("a connected replica may still be syncing");
        }
        Evidence risky = new Evidence(true, true, false, false, false, true);
        if (blockers(risky).size() != 3) throw new AssertionError("independent reasons");
        System.out.println("ready blockers=" + blockers(ready));
        System.out.println("syncing blockers=" + blockers(syncing));
    }
}

여러 조건을 한 개의 healthy=true로 압축하면 나중에 원인을 설명하기 어렵다. 링크가 연결되었어도 초기 동기화가 끝나지 않았을 수 있고, 복제가 정상이어도 같은 호스트에 배치되어 함께 실패할 수 있다. 기존 앱이 이미 오류 예산을 소모하고 있다면 기술적으로 전환 가능해도 계획 작업을 미루는 팀 정책을 둘 수 있다. 시작 조건은 Redis가 명령을 받아들이는 최소 조건보다 넓은 운영 판단이다.

조건이 모두 통과해도 안전이 영구 보장되는 것은 아니다. 관찰 이후 상태가 바뀔 수 있으므로 실행 직전에 부모·역할을 다시 읽고, 실행 중에도 중단 기준을 본다. 이 모델은 미리 관찰한 불리한 증거를 숨기지 않도록 돕는 도구다. 자동화한다면 실패한 조건과 관찰 시각을 로그에 남기고, 과거의 통과 결과를 오래 재사용하지 않는다. 실제 전환의 권한·버전 호환·승인 조건까지 대신 계산하는 도구로 쓰지 않는다.

Java 예제. 서비스 복구와 replica 보호 회복을 분리하기

아래는 한 shard에 대해 팀이 관찰한 네 가지 조건으로 다음 작업 여부를 결정하는 모델이다. 새 primary가 되어 슬롯 인식이 수렴하고 앱의 테스트 요청이 성공했다면 서비스는 회복했다고 기록할 수 있다. 그러나 건강하고 독립적인 replica가 아직 없으면 다음 계획 작업을 진행하지 않는 정책을 둔다. 다른 모든 슬롯의 상태나 실제 지연을 측정하는 코드는 아니며, 입력은 별도 확인이 필요하다.

public final class ClusterProtectionRecoveryLesson {
    record Observation(boolean expectedPrimary, boolean slotViewsConverged,
                       boolean applicationProbePassed, boolean replicaProtected) {}

    static boolean serviceRestored(Observation e) {
        return e.expectedPrimary() && e.slotViewsConverged()
                && e.applicationProbePassed();
    }

    static boolean nextMaintenanceAllowed(Observation e) {
        return serviceRestored(e) && e.replicaProtected();
    }

    public static void main(String[] args) {
        Observation roleOnly = new Observation(true, false, false, false);
        Observation serving = new Observation(true, true, true, false);
        Observation protectedAgain = new Observation(true, true, true, true);
        if (serviceRestored(roleOnly)) throw new AssertionError("role alone");
        if (!serviceRestored(serving)) throw new AssertionError("service probe");
        if (nextMaintenanceAllowed(serving)) {
            throw new AssertionError("serving is not replica protection");
        }
        if (!nextMaintenanceAllowed(protectedAgain)) {
            throw new AssertionError("all evidence present");
        }
        System.out.println("service restored before the next maintenance is allowed");
    }
}

이 차이는 실제 작업 순서를 바꾼다. 새 primary R이 정상 응답하기 시작했다고 바로 다른 replica를 재시작하면, 아직 보호되지 않은 shard가 늘어날 수 있다. 한 shard의 전환·앱 확인·복제 보호 회복을 마친 뒤 다음 shard로 넘어가면 동시에 유지보수로 늘어나는 위험을 줄일 수 있다. 그 순서가 모든 장애를 방지하는 것은 아니지만 적어도 무엇을 잃어버린 채 다음 단계를 시작하는지 드러내 준다.

보고서에는 요청 수락 시각, 새 역할 관찰 시각, 앱 첫 정상 요청 시각, replica 링크와 정책 회복 시각을 따로 남긴다. 시간을 분리하면 서버 전환이 느렸는지, 클라이언트가 옛 경로에 머물렀는지, 데이터 동기화가 오래 걸렸는지 찾기 쉽다. 하나의 “복구 10초” 숫자만 남기면 실제 병목을 파악하기 어렵다. 예제의 조건은 이런 관찰 설계를 코드로 작게 표현한 것이다.

노드 추가 워크숍. 새 primary를 넣으면 언제 용량이 늘어나는가

P4라는 새 빈 primary를 기존 Cluster에 넣었다고 하자. 멤버십에는 P4가 보이지만 슬롯이 아직 없다면 기존 P1·P2·P3의 데이터는 그대로다. 이때 전체 메모리 대시보드에서 사용률 평균이 낮아져도 가장 가득 찬 shard의 문제가 해결된 것은 아니다. P4가 실제 슬롯과 키를 받아야 데이터 부하를 나눌 수 있다. 평균만 보면 새 빈 서버가 위험한 기존 서버의 수치를 희석할 수 있다.

슬롯을 옮길 때는 source·target 모두에 여유가 필요하다. 목적지의 키 데이터 외에 복제·네트워크·일시 작업 비용도 관찰한다. 새 primary에 replica를 준비하는 시점은 팀의 위험 허용 정책에 따라 계획하되, 데이터를 받은 뒤 보호 사본이 없는 기간을 숨기지 않는다. 기존 shard마다 replica가 하나씩 있다는 사실은 새 shard의 보호를 의미하지 않는다. 슬롯을 추가로 맡는 쓰기 담당자가 생기면 그 데이터의 다음 장애 후보도 다시 그려야 한다.

새 primary가 슬롯을 가지기 시작하면 Cluster의 투표권 집합과 과반 계산에 미치는 영향도 확인해야 한다. 단순히 전체 프로세스 수를 하나 늘리는 산술이 아니다. 어떤 primary가 슬롯을 맡고 있으며 서로 어떤 구성으로 인식하는지를 봐야 한다. 변경 중에는 한 노드의 출력이 다른 노드와 다를 수 있으므로 여러 관찰과 도구 검사를 묶는다. 이 장의 Java 유지보수 모델은 이런 동적 선출 멤버십 계산을 구현하지 않는다.

새 replica를 넣는 경우에는 target primary ID를 먼저 확정한다. 포트를 보고 임의로 부모를 추정하지 않는다. 목록에 추가되었다는 결과와 복제가 정상화되었다는 결과를 나누어 기록한다. 초기 동기화가 길어질 때 원본 primary의 지연·메모리·네트워크도 함께 증가할 수 있다. 복사본을 추가하는 작업은 읽기 경로에만 영향을 주는 무비용 작업이 아니므로 사용자 지연을 보면서 속도와 작업 창을 정한다.

노드 축소 워크숍. 빈 슬롯 수와 빈 데이터 수가 무엇을 뜻하는가

primary를 제거하기 전 담당 슬롯을 다른 primary로 이전한다. 이때 슬롯 0개라는 상태, 남은 키가 없는 상태, 구성원에서 사라진 상태, 프로세스가 종료된 상태는 서로 다른 증거다. 슬롯을 옮겼어도 열린 이전 상태가 남거나 다른 노드의 소유권 인식이 수렴하지 않았을 수 있다. 제거 도구의 최종 점검과 여러 노드의 구성·실제 키 검사를 통해 단계별 상태를 확인한다.

제거 대상에 replica가 연결되어 있다면 그 replica를 앞으로 누구의 보호로 사용할지도 정한다. 주소록에서 primary를 없앴다고 모든 데이터 복사본과 연결이 의도한 방식으로 자동 정리되는 것은 아니다. 필요한 재배치 후 초기 동기화와 실제 장애 도메인을 다시 확인한다. replica migration은 일부 상황에서 보호 배치를 개선할 수 있지만 운영자가 기대한 위치와 시간에 정확히 끝나는 전체 배치 관리 시스템으로 보면 안 된다.

축소 후 용량은 평균 외에 최악 shard를 기준으로 계산한다. P1·P2·P3·P4 중 P4를 빼면 남은 서버의 슬롯과 부하가 늘어난다. 단순 메모리 합계가 충분해도 특정 핫키나 태그를 작은 단위로 나눌 수 없으면 한 primary가 먼저 병목이 된다. 축소 계획에는 데이터 크기·명령 비용·요청 편중·복제 보호를 포함한다. “평균 사용률이 40%니까 절반을 빼도 된다” 같은 계산은 분포를 무시한다.

프로세스를 종료하기 전 필요한 로그와 node ID·슬롯 이전 계획을 보존한다. 이후 문제가 생겼을 때 구성 변경과 실제 트래픽 변화를 연결할 근거가 된다. 영속 데이터와 비밀 값이 있는 디스크의 정리는 조직의 데이터 처리 절차에 따른다. 이 교재의 일회용 로컬 환경은 테스트 전용 데이터만 사용하고 임시 프로세스와 경로를 정리한다. 그 간단한 종료 절차를 운영 데이터 삭제 절차로 일반화하지 않는다.

롤링 유지보수 사례. 다음 노드를 시작하지 않을 조건부터 정하기

세 shard의 버전을 순차로 변경하는 가상 작업을 보자. 목표 버전의 호환성을 검토하고 복구 시험을 마친 뒤 A1 replica부터 작업한다. 새 버전으로 기동해 정상 동기화·지연·앱 호환을 확인하고, 정상 수동 전환으로 A1을 primary로 만든다. 이후 이전 A가 replica가 된 상태에서 작업하고 복제 보호를 회복한다. 이 흐름은 버전 호환을 검증한 경우의 계획 예시이며 모든 버전 쌍에 그대로 적용되는 업그레이드 지침은 아니다.

작업 상황 다음 행동을 정할 기준
replica가 기동했지만 동기화 진행 중 전환을 시작하지 않고 원인·진행 상태 확인
전환 요청은 OK이나 역할이 바뀌지 않음 반복 호출보다 로그·현재 역할·timeout 확인
역할은 바뀌었지만 앱 쓰기 실패 주소·토폴로지·ACL·연결·업무 예외 확인
앱은 정상이나 replica 보호가 미회복 다음 shard 작업 보류
새 버전에서 기존 데이터 해석 문제 더 확산하지 않고 호환·복구 계획에 따라 판단

롤백은 버전 문자열을 예전 것으로 바꾸는 행위와 같지 않다. 새 버전이 영속성 파일이나 설정을 바꿨다면 이전 버전이 그것을 읽을 수 있는지 확인해야 한다. 최신 데이터가 어느 노드에 있고 어떤 백업 시점으로 복구할 것인지도 별도다. 전환을 반대로 수행하는 역할 롤백과 바이너리 다운그레이드, 데이터 복원은 다른 절차다. 계획 단계에서 이를 구분해야 문제 발생 시 더 큰 데이터 손실을 피할 수 있다.

작업자가 둘 이상이면 한 가지 진행 기록을 기준으로 삼는다. “7001 작업 완료”보다 “node ID R이 primary가 되었고 앱 시험 통과, 이전 P는 replica 동기화 완료”처럼 결과 상태를 적는다. 작업 직후 새로 합류한 사람이 같은 전환을 다시 실행하지 않도록 시각·명령·확인 결과·다음 허용 단계를 남긴다. 자동화도 동일하게 현재 상태를 확인한 뒤 다음 단계를 선택해야 하며, 명령을 정해진 횟수 반복하는 것으로 대체할 수 없다.

추가 면접 문답. 역할 변경과 작업 완료의 차이

CLUSTER FAILOVER가 OK인데 앱은 계속 실패합니다. 무엇부터 보나요?

OK는 요청 수락이므로 먼저 실제 역할 변경이 완료됐는지 확인합니다. 대상 replica의 ROLE, 여러 노드의 슬롯 소유권, 관련 로그를 봅니다. 그다음 앱이 새 담당 노드에 직접 접근·인증할 수 있는지, 오래된 경로를 사용하지 않는지 확인합니다. 마지막으로 요청별 결과와 오류 종류를 봐야 합니다. timeout은 명령 미실행 증거가 아니므로 비멱등 쓰기를 무조건 다시 보내지 않습니다. 역할 완료·구성 수렴·앱 정상화를 구분해서 기록하면 지연 구간을 찾기 쉽습니다.

정상 전환이 안 되면 FORCE, 그래도 안 되면 TAKEOVER 순서인가요?

그런 단계형 재시도 절차로 사용하면 위험합니다. FORCE는 기존 primary와의 정상 협력 없이 승격을 시도하고, TAKEOVER는 합의 승인까지 우회해 슬롯을 주장하는 경로입니다. 실패 원인이 네트워크 경로·후보 데이터·승인 집합 중 무엇인지 먼저 알아야 합니다. 특히 분할 양쪽에서 강제 권위를 만들면 충돌을 키울 수 있습니다. 재해복구 계획 안에서 권위 데이터와 손실 허용 범위, 반대쪽 쓰기 통제를 결정한 뒤 검토할 옵션입니다.

새 primary가 응답하니 다음 서버를 재시작해도 되나요?

서비스 정상화와 다음 장애 대비 회복을 분리해야 합니다. 새 primary의 역할·슬롯 수렴·앱 요청 성공을 확인하고, 이어서 건강한 replica가 원하는 장애 도메인에 있으며 동기화와 지연이 정책을 만족하는지 봅니다. 보호 수준이 회복되기 전에 다음 노드를 중단하면 동시에 취약한 범위가 늘어납니다. 계획 작업은 명령 수가 적은 것보다 각 단계에서 남은 데이터 사본과 권위를 설명할 수 있는 것이 중요합니다.

노드를 추가했는데 평균 메모리만 낮아지고 기존 서버는 그대로입니다. 왜 그런가요?

빈 primary의 멤버십 추가와 슬롯·키 이전은 별개이기 때문입니다. 새 노드가 슬롯을 받지 않았다면 실제 데이터는 기존 primary들에 남습니다. 평균 사용률은 빈 서버가 추가되어 낮아질 수 있으므로 가장 가득 찬 shard의 실제 사용량과 소유 슬롯·키 분포를 확인해야 합니다. 리샤딩으로 부하를 나눈 뒤에도 핫키 하나는 자동 분할되지 않으며, 새 shard에 대한 replica 보호도 별도로 준비해야 합니다.

면접 질문과 깊이 있는 답변

답을 펼치기 전에 원리, 장애 반례, 운영 확인 방법의 세 순서로 말해 보자. 짧은 정의만 외우기보다 어떤 조건에서 그 설명이 깨지는지를 덧붙이는 것이 중요하다.

정상 CLUSTER FAILOVER는 어디에서 실행하나요?

교체하려는 primary의 replica에서 실행합니다. 실제 부모 관계를 확인한 뒤 수행해야 합니다. 정상 경로는 기존 primary와 협력하여 복제 offset을 맞춘 뒤 전환하므로 계획 유지보수에 유용합니다. 강제 옵션을 기본 절차처럼 사용하지 않습니다.

FORCE와 TAKEOVER는 더 안전한 옵션인가요?

아닙니다. 정상 협력이나 합의 안전장치를 우회하는 특수 경로입니다. 데이터가 덜 최신인 노드를 승격하거나 충돌 구성을 만드는 위험을 검토해야 합니다. 네트워크 분할 복구 같은 명확한 상황에서 권위 있는 데이터와 손실 허용 범위를 결정한 뒤에만 고려합니다.

새 replica를 추가하자마자 승격하면 되나요?

먼저 다른 primary들이 그 replica를 알고 있는지와 실제 복제 상태를 확인해야 합니다. 초기 동기화가 끝나지 않았거나 선출에 필요한 인식이 전파되지 않았다면 전환이 실패할 수 있습니다. 명령 수락과 보호 수준 확보는 같은 시점이 아닙니다.

새 primary에 데이터가 없는 것은 오류인가요?

슬롯을 아직 받지 않았다면 정상일 수 있습니다. 빈 노드 추가와 슬롯 재배치는 별도 단계입니다. node ID를 확인하고 원하는 슬롯을 리샤딩한 뒤 부하와 데이터량을 관찰합니다. 새 primary용 replica가 준비되었는지도 함께 확인합니다.

primary를 지우려면 프로세스부터 종료하나요?

계획된 제거에서는 담당 슬롯을 다른 primary로 옮기고 최종 소유권과 데이터 상태를 확인한 뒤 멤버십에서 제거하고 프로세스를 종료합니다. 먼저 종료하면 불필요한 장애 전환과 보호 수준 저하를 만들 수 있습니다. 작업 순서를 데이터·멤버십·프로세스로 나누어 관리합니다.

replica migration과 리샤딩의 차이는요?

리샤딩은 슬롯 소유권과 키를 다른 primary로 옮기는 일입니다. replica migration은 복제본이 부족한 primary를 보호하도록 replica의 소속을 바꾸는 기능입니다. 후자가 없어져 버린 데이터를 복원하거나 primary의 슬롯 부하를 균등하게 나누는 것은 아닙니다.

업그레이드는 왜 replica부터 검토하나요?

primary의 직접 서비스 경로를 유지하면서 새 버전의 기동·복제·지연을 먼저 검증할 수 있기 때문입니다. 이후 정상 수동 전환과 이전 primary 업그레이드를 단계적으로 진행할 수 있습니다. 다만 버전 호환·데이터 형식·롤백 가능성은 해당 릴리스 문서로 먼저 확인해야 합니다.

재시작한 원래 primary가 다시 primary인가요?

그렇다고 가정하면 안 됩니다. 장애 전환 뒤에는 새 구성에 따라 replica로 합류할 수 있습니다. 포트가 다시 열렸다는 사실보다 node ID·ROLE·부모 관계·슬롯 소유권을 확인합니다. 클라이언트도 이전 주소를 영구 쓰기 대상으로 고정해서는 안 됩니다.
