실습과 점검

테스트 토픽과 격리된 Kafka 클러스터에서 각각의 이벤트 Key, Partition, Offset, 처리 성공 여부를 기록하며 결과를 추적하세요. 상태를 사용하는 기능은 앱 재시작 시 복구 시간도 측정합니다. 운영 클러스터의 오프셋을 임의로 수정하거나 Topic을 삭제해서는 안 됩니다.

더 깊게 배우기 1. 실제로 실행하는 첫 Topology

Kafka Streams는 Java 라이브러리입니다. StreamsBuilder builder=new StreamsBuilder(); KStream<String,String> stream=builder.stream("orders"); stream.filter((key,value)->value!=null).to("valid-orders"); 같은 단계로 입력과 출력을 연결할 수 있어요. 실행하려면 application.id, bootstrap.servers, Serde 설정이 필요합니다. 처리할 Topic이 없거나 ACL이 맞지 않으면 코드가 컴파일돼도 시작이 실패할 수 있습니다.

더 깊게 배우기 2. Start, Close, 상태 전환

KafkaStreams 인스턴스는 start()로 작동하고 close()로 종료합니다. 상태에는 CREATED, REBALANCING, RUNNING, PENDING_SHUTDOWN 등 단계가 있어요. 서버가 살아 있다고 Stream 처리가 정상이라고 단정할 수 없습니다. 종료 훅을 등록하고, 배포 시 Task 할당·복원 진행을 확인하세요.

더 깊게 배우기 3. 직렬화와 기본 Serde

문자열 JSON을 StringSerde로 읽을지, Avro·Protobuf 등 다른 형식으로 읽을지는 Producer가 보낸 실제 바이트에 달려 있습니다. KStream 타입 파라미터를 <String,String>으로 선언했다고 브로커의 레코드가 자동 변환되는 건 아니에요. Serde 오류는 정상 메시지 한 건 때문에 스트림 전체 처리에 영향을 줄 수 있습니다.

더 깊게 배우기 4. application.id를 바꿀 때의 위험

새 배포 버전에서 application.id를 바꾸면 서로 다른 Streams 애플리케이션으로 인식되어 입력 소비 위치나 내부 토픽·상태가 달라질 수 있습니다. 기존 데이터 재처리나 상태 초기화 의도가 없다면 무심코 바꾸지 마세요. Blue-Green 구성에서도 데이터 중복 생산 가능성에 대비해야 합니다.

같은 코드를 인스턴스 두 개로 실행하고 Kafka Topic의 파티션 수를 바꿔가며 Task 할당을 관찰해 보세요. 한 인스턴스를 종료했을 때 Lag과 상태 복구가 어떻게 변하는지 확인하면 Task, Thread, Rebalance의 관계가 드러납니다. 테스트 토픽에서만 실습하세요.
