트랜잭션과 MVCC: 같은 데이터를 다르게 보는 이유

읽는 방법

비유로 개념을 잡고 SQL을 실행하기 전 결과를 예상해 보세요. 이번 개정에서는 단계별 동작 추적에 더해, 전편에 네 가지 확장 수업과 심층 면접 답변을 추가했습니다. 본문의 수치 예시는 설명용이고, 실행 환경에 따라 달라지는 값은 따로 표시했습니다. 기준은 MySQL 8.0·InnoDB, 재현용 서버는 8.0.36입니다. 처음 시작한다면 1편의 서버 준비만 먼저 진행하면 됩니다.

전체 학습 지도·검증 범위

1. 트랜잭션은 ‘함께 성공해야 하는 일’의 경계다

출고를 처리하며 재고를 1 줄이고 출고 이력을 남긴다고 합시다. 재고만 줄고 이력이 없으면 나중에 원인을 추적할 수 없습니다. 이력만 남고 재고가 그대로여도 잘못입니다. 두 변경을 함께 확정하거나 취소하는 경계가 트랜잭션입니다. 그러나 트랜잭션을 썼다고 업무 규칙이 저절로 맞아지는 것은 아닙니다. ‘재고는 음수가 될 수 없다’는 조건을 SQL·제약조건·동시성 제어로 실제 구현해야 합니다.

ACID에서 원자성은 부분 완료를 남기지 않는 성질, 일관성은 제약과 올바른 업무 로직에 따라 유효한 상태를 유지하는 성질, 격리성은 동시에 수행되는 작업이 서로 보이는 방식, 지속성은 확정한 변경을 장애 이후 보존하는 성질입니다. 여기서 격리 수준은 ‘다른 사람의 작업을 어느 시점 기준으로 볼 것인가’를 조정합니다.

2. 잠그지 않고 과거를 읽는 방법: MVCC

공동 편집 문서를 보면서 다른 사람이 수정 중이어도 내가 읽던 판본을 계속 볼 수 있다고 생각해 보세요. 매번 원본 편집을 막지 않아도 읽기가 가능합니다. MVCC(Multi-Version Concurrency Control)는 여러 버전 정보를 사용해 이런 동작을 구현합니다. 단, InnoDB가 SELECT마다 테이블 전체를 복사하는 것은 아닙니다.

InnoDB의 클러스터드 인덱스 레코드에는 마지막 변경 트랜잭션 정보와 undo를 가리키는 정보가 있습니다. 읽는 트랜잭션은 read view라는 가시성 기준으로 현재 버전을 볼 수 있는지 판단합니다. 볼 수 없으면 undo를 따라 이전 상태를 구성합니다. ‘트랜잭션 번호가 나보다 작으면 보인다’만으로 설명하면 부족합니다. read view를 만들 당시 아직 실행 중이던 트랜잭션인지 등도 영향을 줍니다.

이것은 낡은 데이터만 읽는 장치가 아닙니다. 일관된 기준으로 읽기 위한 장치입니다. 자기 트랜잭션이 직접 변경한 내용은 읽을 수 있으므로 단순한 ‘과거 사진’ 비유에도 한계가 있습니다. 같은 트랜잭션 안의 자기 변경과 다른 트랜잭션의 변경을 구분해야 합니다.

3. RC와 RR은 언제 사진을 찍는가가 다르다

격리 수준일반적인 비잠금 SELECT주의할 점
READ UNCOMMITTED다른 작업의 미확정 변경을 볼 수 있다.업무 정합성이 필요한 조회에 부적합할 수 있다.
READ COMMITTED각 일관된 읽기마다 새로운 스냅샷같은 트랜잭션의 두 조회 결과가 달라질 수 있다.
REPEATABLE READ일반적으로 첫 일관된 읽기가 만든 스냅샷을 재사용BEGIN 시점과 첫 조회 시점은 다를 수 있다.
SERIALIZABLE더 강한 격리를 위해 읽기도 잠금 영향을 받을 수 있다.autocommit·명시적 트랜잭션에 따라 세부 동작을 구분한다.

이 표는 일반 SELECT의 출발점입니다. SELECT ... FOR UPDATE와 UPDATE는 같은 과거 스냅샷을 그대로 고치는 작업이 아닙니다. 잠금을 획득하며 최신 상태를 대상으로 처리합니다. 그래서 RR에서도 일반 SELECT 결과와 잠금 읽기 결과가 다를 수 있습니다. “RR이면 모든 SQL이 무조건 같은 값을 본다”는 표현은 틀립니다.

4. 두 세션으로 직접 확인하는 실습

1편 서버에 터미널 두 개를 열고 각각 docker exec -it mysql-school mysql -uroot -p로 접속합니다. 두 창 모두 USE mysql_school을 실행합니다. 준비 SQL은 한 창에서 한 번만 실행합니다.

CREATE DATABASE IF NOT EXISTS mysql_school;
USE mysql_school;
DROP TABLE IF EXISTS mvcc_demo;
CREATE TABLE mvcc_demo(id INT PRIMARY KEY, qty INT NOT NULL)
  ENGINE=InnoDB;
INSERT INTO mvcc_demo VALUES(1,10);
순서세션 A세션 B
1SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;
2START TRANSACTION;
3SELECT qty FROM mvcc_demo WHERE id=1; → 10
4UPDATE mvcc_demo SET qty=20 WHERE id=1; → autocommit=1로 확정
5SELECT qty FROM mvcc_demo WHERE id=1; → 10
6SELECT qty FROM mvcc_demo WHERE id=1 FOR UPDATE; → 20
7ROLLBACK;

A의 첫 조회가 만든 관점에서는 B의 나중 변경이 보이지 않습니다. 그러나 잠금 읽기는 20을 대상으로 합니다. 이 차이를 직접 보는 것이 실습의 목표입니다. B의 autocommit이 0이라면 COMMIT해야 위 결과가 됩니다. 확인하지 않고 진행하면 A의 잠금 읽기가 기다릴 수 있습니다.

이제 트랜잭션이 모두 끝난 상태에서 값을 10으로 되돌리고, A의 격리 수준을 READ COMMITTED로 바꿔 반복합니다. 순서 5의 일반 SELECT는 20을 봅니다. 다른 조건은 그대로 두고 격리 수준 하나만 바꿔야 무엇이 결과를 바꾸었는지 알 수 있습니다.

5. 스냅샷이 있어도 재고 초과 판매는 생길 수 있다

A와 B가 수량 1을 읽고 각각 “구매 가능”을 판단했습니다. 두 작업이 애플리케이션에서 1-1을 계산한 뒤 UPDATE로 0을 저장하면 수량은 0이지만 주문은 두 개일 수 있습니다. 일반 SELECT의 일관성과 업무의 원자적 판단은 다른 문제입니다.

UPDATE mvcc_demo
SET qty = qty - 1
WHERE id = 1 AND qty >= 1;
SELECT ROW_COUNT();

영향받은 행이 1이면 이 문장은 수량을 실제로 차감했습니다. 0이면 조건을 만족하는 행이 없었습니다. 존재하지 않는 상품과 부족한 재고를 구분해야 한다면 추가 설계가 필요합니다. 차감 성공과 주문 저장은 하나의 트랜잭션으로 묶고, 요청 재시도에 대비한 고유 요청 ID도 고려해야 합니다. 이 SQL 한 줄이 결제까지 포함한 모든 분산 트랜잭션을 해결하지는 않습니다.

6. 오래 열린 읽기 트랜잭션도 비용이 있다

사용자가 보고서를 연 뒤 점심을 먹으러 갔는데 DB 트랜잭션이 계속 열려 있다고 합시다. 그 스냅샷이 과거 버전을 필요로 할 수 있어 undo 정리를 지연시킵니다. 읽기만 하니 아무 영향이 없다고 볼 수 없습니다. undo 보존·purge 지연·버전 탐색 비용이 늘 수 있습니다. DB 트랜잭션 안에서 HTTP 호출이나 사용자 입력을 기다리지 않는 이유 중 하나입니다.

진단할 때는 오래 열린 트랜잭션과 실제 실행 중인 SQL을 구분합니다. 세션이 Sleep이어도 트랜잭션은 열려 있을 수 있습니다. information_schema.innodb_trx의 시작 시각, 연결 식별자, 상태를 확인합니다. history list length는 단순히 “undo 바이트 수”가 아니므로 크기 단위를 혼동하지 않습니다.

7. DDL까지 ROLLBACK으로 되돌릴 수 있다고 믿지 않기

MySQL의 많은 DDL은 암묵적 커밋을 일으킵니다. UPDATE 후 ALTER TABLE을 실행한 다음 ROLLBACK해도 UPDATE가 이미 확정되었을 수 있습니다. 8.0의 atomic DDL은 장애 중 DDL 내부 변경을 일관되게 처리하는 성질이지, 사용자가 일반 트랜잭션처럼 모든 DDL을 자유롭게 롤백할 수 있다는 뜻이 아닙니다. 업무 DML과 스키마 변경은 별도 절차로 관리합니다.

read view는 데이터 복사본이 아니라 ‘누구의 변경을 볼 것인가’라는 기준이다

사진 비유는 이해하기 쉽지만 실제로 테이블 전체의 사진 파일을 만드는 것은 아닙니다. read view는 생성 시점의 활성 트랜잭션과 트랜잭션 ID 경계 같은 정보를 이용해 버전의 가시성을 판단합니다. 현재 레코드를 읽어도 되는지 검사하고, 안 된다면 undo로 과거 버전을 구성합니다. 같은 원본 장부를 읽으면서 각 독자가 볼 수 있는 수정 이력의 경계가 다른 셈입니다.

숫자로 따라가 봅시다. 트랜잭션 100은 이미 커밋했고, 101은 수정 중이며, 102는 커밋했습니다. 이때 A가 read view를 만들었다고 가정합니다. A는 100·102의 커밋된 변경을 볼 수 있지만 당시 활성 상태였던 101의 변경은 볼 수 없습니다. 나중에 101이 커밋해도 RR의 같은 read view에서는 여전히 그 변경을 제외합니다. 그래서 단순히 “내 번호보다 작은 변경은 전부 보인다”는 규칙으로 설명할 수 없습니다.

실제 구현은 효율적인 판정을 위해 여러 경계와 활성 ID 집합을 사용합니다. 위 번호는 원리 설명용이며 트랜잭션 ID를 실제 커밋 시각의 일련번호로 읽으면 안 됩니다. 먼저 시작한 트랜잭션이 나중에 커밋할 수 있기 때문입니다. 순서가 중요한 것은 시작·변경·커밋·read view 생성 중 어느 사건인지입니다.

현재 값 7에서 과거 값 10으로 되돌아 읽는 과정

수량 10을 B가 9로, C가 7로 변경했다고 합시다. A의 스냅샷에서 두 변경이 모두 보이지 않는다면 A는 현재 값 7을 그대로 반환하지 않습니다. 레코드의 변경 트랜잭션 정보를 확인하고 undo를 따라 9에 해당하는 버전을 구성한 뒤, 여전히 안 보이면 더 이전의 10을 구성합니다.

검사할 버전A의 관점다음 행동
현재 값 7, C의 변경스냅샷 이후 변경이전 버전 구성
이전 값 9, B의 변경역시 보이지 않음더 이전 버전 구성
이전 값 10볼 수 있는 커밋 버전10 반환

버전마다 전체 행의 완전한 복사본을 무조건 따로 저장한다는 뜻은 아닙니다. 이전 상태를 재구성할 정보가 있다는 뜻입니다. 버전 연결이 길어지면 과거를 찾는 비용이 생길 수 있고, 오래된 스냅샷이 있으면 필요한 undo를 정리하지 못할 수 있습니다. “잠금을 잡지 않는 읽기는 공짜”가 아닌 이유입니다.

RR의 사진은 언제 찍힐까? BEGIN과 첫 SELECT를 분리하기

다음은 앞의 mvcc_demo를 사용한 추가 관찰입니다. 두 세션의 이전 트랜잭션을 모두 종료하고 B를 autocommit=1로 둔 뒤 수량을 10으로 맞춥니다. A가 BEGIN만 하고 데이터를 읽지 않은 사이 B가 20으로 커밋하면, A의 첫 일반 SELECT는 통상 20을 봅니다. 아직 일관된 읽기의 read view가 없었기 때문입니다.

순서A: RRB: autocommit
1START TRANSACTION
2아직 SELECT 없음qty를 20으로 UPDATE
3첫 일반 SELECT → 20
4qty를 30으로 UPDATE
5일반 SELECT → 20
6ROLLBACK

반대로 RR에서 START TRANSACTION WITH CONSISTENT SNAPSHOT을 사용하면 시작 시 일관된 읽기의 관점을 요청합니다. 이 옵션의 효과는 격리 수준과 함께 이해해야 합니다. BEGIN이라는 이름만으로 “항상 시작 시점의 사진”이라고 외우지 않는 것이 핵심입니다.

조회와 갱신을 섞었을 때 보이는 값이 달라지는 이유

A가 일반 SELECT로 10을 읽었습니다. B가 20으로 커밋합니다. 이후 A가 UPDATE ... SET qty=qty-1을 하면 오래된 사진 속 10이 아니라 갱신 시점의 대상 행에 대해 경쟁을 제어하며 처리하므로 19가 될 수 있습니다. A가 자기가 변경한 값을 읽으면 19를 봅니다. RR이 모든 문장을 과거 사진으로 고정하는 규칙이 아니라는 뜻입니다.

이때 애플리케이션이 처음 읽은 10으로 계산해 SET qty=9를 보내면 의미가 다릅니다. DB가 보호하는 것은 보낸 UPDATE 자체의 실행이지, 앱에서 오래전에 읽은 값으로 한 판단의 유효성까지가 아닙니다. 조건부 갱신, 버전 열을 이용한 낙관적 잠금, 명시적 잠금 읽기 중 업무에 맞는 방식을 선택해야 합니다.

버전 방식은 예를 들어 id=1, version=3인 행을 읽었다면 UPDATE 조건에 version=3을 넣고 성공 시 version을 4로 올리는 형태입니다. 누군가 먼저 변경하면 조건을 만족하지 않아 0행이 갱신됩니다. 이때 동일한 오래된 값을 무한 재전송하는 것이 아니라 새 데이터를 읽고 업무 판단을 다시 해야 합니다.

여러 행을 가로지르는 규칙은 더 조심해야 합니다. “창고에 근무자 최소 한 명 유지”를 두 사람이 각자 읽고 자기 행만 비활성화하면 서로 다른 행을 갱신하므로 단순한 동일 행 경쟁이 없습니다. RR 스냅샷만으로 모든 업무 불변식이 보호된다고 믿지 말고 공통으로 잠글 대상, 제약 모델, 직렬화 방식 등을 설계해야 합니다.

오래된 읽기 트랜잭션을 찾는 질문

느린 보고서 때문에 undo가 늘었다면 먼저 “누가 언제부터 어떤 스냅샷을 유지하는가”를 봅니다. SQL이 실행 중이지 않은 Sleep 세션도 트랜잭션을 열어 둔 채 남을 수 있습니다. 긴 트랜잭션을 종료할 때는 그 업무와 롤백 비용을 확인해야 하며, 단순히 오래됐다는 이유만으로 운영 연결을 일괄 종료하지 않습니다.

보고서를 페이지 단위로 나눠 각 페이지를 새 트랜잭션에서 읽으면 오래된 관점을 유지하는 비용은 줄 수 있습니다. 대신 전체 보고서가 하나의 시점이라는 성질은 사라질 수 있습니다. 성능 개선에는 종종 결과 의미의 변화가 따라옵니다. 어떤 일관성이 필요한지 먼저 정한 뒤 읽기 범위와 트랜잭션 길이를 선택하세요.

확장 수업 ① — ACID를 입고 확정 한 건에 대입하기

입고 확정은 상태를 COMPLETED로 바꾸고 재고를 늘리는 두 작업이라고 합시다. 둘 중 하나만 남으면 업무가 어긋납니다. 원자성은 이 작업을 하나의 트랜잭션으로 묶었을 때 함께 확정하거나 취소할 수 있게 하는 성질입니다. 지속성은 성공적으로 커밋한 내용을 요구한 장애 범위에서 보존하는 성질입니다. 격리성은 다른 트랜잭션과 동시에 실행될 때 무엇을 관찰하고 어떻게 경쟁하는지를 정합니다.

일관성은 DB가 모든 업무 의미를 알아서 추론한다는 뜻이 아닙니다. 기본 키·외래 키·CHECK 같은 제약은 선언된 규칙을 검사하지만 “이미 확정한 입고를 두 번 더하지 않는다”는 규칙은 고유 키, 상태 조건, 잠금과 트랜잭션 설계 등으로 표현해야 합니다. 잘못된 수량을 정상적으로 두 번 더하는 SQL도 원자적으로 커밋될 수 있습니다.

따라서 “@Transactional이 있으니 안전하다”는 답변은 부족합니다. 무엇을 하나의 트랜잭션으로 묶었는지, 동시에 같은 입고를 처리하면 어느 조건이 두 번째 실행을 막는지, 실패와 재시도를 어떻게 구분하는지까지 설명해야 합니다.

확장 수업 ② — 잠금이 있는데도 갱신 유실이 생기는 이유

순서AB저장된 qty
1SELECT → 1010
2SELECT → 1010
3앱에서 10−1 계산, SET qty=9 후 커밋9
4앱에서 10−1 계산, SET qty=9 후 커밋9

두 UPDATE는 각각 행 잠금을 잡아 안전하게 실행될 수 있습니다. 하지만 DB가 받은 두 번째 명령은 “현재 값에서 1을 빼라”가 아니라 “9를 저장하라”입니다. DB는 애플리케이션이 오래된 10을 사용해 계산했다는 의도를 알 수 없습니다. 결과는 차감 두 번인데 최종 수량 9입니다. 문장 실행의 상호 배제와 읽은 값의 유효성 검사는 다른 문제입니다.

SET qty=qty-1 WHERE qty>=1은 갱신 대상의 현재 값을 사용해 조건 검사와 변경을 수행합니다. 버전 방식이라면 WHERE id=1 AND version=3으로 읽을 당시 상태가 유지되는지를 검사하고, 성공한 변경에서 version을 증가시킵니다. 여러 문장의 판단이 꼭 필요하면 SELECT FOR UPDATE로 읽기부터 보호할 수 있습니다. 세 방식은 취향이 아니라 보호하려는 업무 범위가 달라서 선택합니다.

확장 수업 ③ — 서로 다른 행을 바꾸는 경쟁도 있다

창고 당직자 A·B 중 적어도 한 명이 남아야 한다고 합시다. 둘 다 현재 당직 중입니다. 두 트랜잭션이 같은 스냅샷을 읽고 “나 말고 한 명이 남으니 퇴근 가능”이라고 판단한 뒤 자기 행만 OFF로 바꾸면, 서로 다른 행을 갱신하여 두 작업이 모두 성공할 수 있습니다. 최종적으로 당직자가 0명이 됩니다.

이것은 하나의 수량 행에서 일어나는 갱신 유실과 다릅니다. 각 행의 버전을 각각 검사하는 것만으로는 여러 행에 걸친 규칙을 보호하지 못할 수 있습니다. 예를 들어 창고별 공통 제어 행을 먼저 FOR UPDATE로 잠그고 그 잠금 안에서 당직자 집합을 다시 확인·변경하면 같은 창고의 판단을 직렬화할 수 있습니다. 모든 관련 변경 경로가 같은 규칙을 따라야 한다는 조건이 붙습니다.

더 강한 격리 수준이나 제약 모델 변경도 후보지만, 각 방식의 잠금 범위와 재시도 비용을 확인해야 합니다. 스냅샷은 읽는 집합을 일관되게 보여 주는 장치이지, 임의의 업무 규칙이 미래의 모든 변경 뒤에도 참이도록 보장하는 장치는 아닙니다.

확장 수업 ④ — 낙관적 잠금의 성공과 실패를 직접 보기

다음 실습은 앞 테이블과 별개입니다. 두 사용자가 모두 version=0을 읽었다고 가정하고, 먼저 처리한 명령과 뒤늦게 도착한 명령을 순서대로 실행합니다. 동시에 실행하지 않아도 “오래된 버전을 사용한 변경 거절”이라는 핵심을 관찰할 수 있습니다.

CREATE DATABASE IF NOT EXISTS mysql_school;
USE mysql_school;
DROP TABLE IF EXISTS version_case;
CREATE TABLE version_case (
 id INT PRIMARY KEY, qty INT NOT NULL, version INT NOT NULL
) ENGINE=InnoDB;
INSERT INTO version_case VALUES (1,10,0);
UPDATE version_case SET qty=qty-1, version=version+1
WHERE id=1 AND version=0 AND qty>=1;
SELECT ROW_COUNT() AS first_success; -- 1
UPDATE version_case SET qty=qty-1, version=version+1
WHERE id=1 AND version=0 AND qty>=1;
SELECT ROW_COUNT() AS stale_success; -- 0
SELECT * FROM version_case; -- id=1, qty=9, version=1

두 번째가 실패한 이유는 qty 부족이 아니라 version 불일치입니다. 실패 뒤 재시도하려면 최신 값을 읽고 업무 판단을 다시 해야 합니다. 충돌이 매우 잦다면 재시도 비용이 커질 수 있으므로 낙관적 잠금이 모든 상황에서 효율적인 것은 아닙니다. 실제 여러 세션 경쟁은 앞의 조건부 재고 차감 실습과 함께 비교해 보세요.

8. 상세 면접 Q&A

RR 스냅샷은 BEGIN 순간에 생기나요?

일반적으로 첫 일관된 읽기 시점에 만들어집니다. START TRANSACTION WITH CONSISTENT SNAPSHOT 같은 명시적인 방식과 구분해야 합니다. 실험에서 BEGIN만 해 놓고 다른 세션이 변경한 뒤 처음 SELECT하면 예상보다 최신 값을 볼 수 있는 이유입니다.

MVCC는 읽기·쓰기가 절대 서로 막지 않는다는 뜻인가요?

아닙니다. 일반 일관된 읽기는 행 잠금을 피할 수 있지만 잠금 읽기·쓰기·메타데이터 잠금 등은 별개입니다. DDL이 얽힌 상황도 있습니다. “MVCC니까 SELECT는 무조건 안 기다린다”라고 일반화하지 않습니다.

RR이면 재고 경쟁 문제가 해결되나요?

아닙니다. 읽고 판단하고 쓰는 업무 전체의 경쟁을 따로 제어해야 합니다. 조건부 UPDATE, SELECT FOR UPDATE, 버전 열을 사용하는 낙관적 잠금 등의 방법이 있습니다. 격리 수준 이름만으로 업무 불변식이 자동 보장된다고 생각하면 안 됩니다.

RC는 무조건 RR보다 빠른가요?

아닙니다. 잠금 범위와 스냅샷 갱신 특성이 다르지만 실제 성능은 쿼리·인덱스·경쟁 형태에 달려 있습니다. RC에서도 외래 키와 중복 키 검사 등의 잠금이 있고 데드락이 사라지지 않습니다. 필요한 읽기 일관성부터 결정하고 측정합니다.

읽기 전용 트랜잭션을 오래 유지하면 왜 문제인가요?

과거 버전을 계속 필요로 할 수 있어 purge가 정리할 수 없는 정보가 늘어납니다. 쓰기를 하지 않는다는 사실이 자원 보존 비용까지 없애 주지는 않습니다. 트랜잭션 경계를 짧게 하고 대량 보고서의 일관성 요구와 처리 방식을 함께 설계합니다.

Atomic DDL은 DDL ROLLBACK 지원인가요?

아닙니다. 장애 시 DDL 관련 내부 변경의 원자성과 사용자 트랜잭션에서의 취소 가능성은 다른 개념입니다. 많은 DDL은 암묵적 커밋 경계입니다. 마이그레이션의 복구는 역방향 변경이나 백업 복원 등을 별도 준비해야 합니다.

꼬리 질문: read view를 만든 뒤 다른 트랜잭션이 커밋하면 보이나요?

답변: RR에서 같은 일관된 읽기 관점을 재사용한다면 당시 활성 상태였던 다른 트랜잭션의 나중 커밋은 그 관점에서 보이지 않습니다. RC에서는 다음 일관된 읽기가 새 관점을 만들므로 달라질 수 있습니다.

구분: 현재 커밋됐다는 사실과 내 read view에서 볼 수 있다는 사실은 다릅니다. 잠금 읽기와 자기 트랜잭션의 변경은 별도 규칙입니다.

꼬리 질문: RR이면 팬텀 리드는 완전히 없어지나요?

답변: InnoDB의 일반 일관된 읽기는 같은 스냅샷으로 집합을 보고, 범위 잠금 읽기는 필요 시 next-key 잠금으로 삽입을 제어합니다. 두 메커니즘을 나누어 설명해야 합니다.

주의: 일반 SELECT와 UPDATE·잠금 읽기를 섞는 상황까지 “어떤 문장도 새로운 행을 보지 않는다”라고 확장하면 틀립니다. SQL 종류, 격리 수준, 인덱스와 실제 잠금 범위를 함께 설명합니다.

꼬리 질문: 조건부 UPDATE가 0행이면 무조건 품절인가요?

답변: 아닙니다. 해당 id가 없거나 수량 조건을 만족하지 않는 등 여러 이유가 있습니다. 조건과 갱신 형태에 따라 영향 행 수의 의미도 구분해야 합니다.

설계: 재고 차감 예시는 성공하면 실제 수량이 바뀌므로 성공 여부를 판정하기 좋습니다. 요청량 검증, 존재하지 않는 상품 처리, 주문 저장의 원자성, 요청 멱등성을 별도로 설계합니다.

꼬리 질문: 낮은 격리 수준이면 항상 더 빠른가요?

답변: 항상은 아닙니다. RC가 일부 갭 잠금과 과거 버전 유지 부담을 줄일 수 있지만 전체 성능은 쿼리·경쟁·읽기 형태에 달려 있습니다.

판단: 격리 수준 변경은 같은 트랜잭션의 반복 조회 의미도 바꿉니다. 성능 실험과 함께 업무가 의존하는 정합성 가정을 검증해야 합니다. 모든 장애를 격리 수준 하나로 해결하려 하지 않습니다.

심층 면접: RR인데 두 번의 SELECT 사이에 자기 UPDATE를 넣으면 왜 같은 값이 안 나오나요?

답변: RR의 일반 일관된 읽기는 같은 read view를 재사용하지만 자기 트랜잭션이 변경한 내용은 볼 수 있습니다. UPDATE는 과거 사진 속 값을 기계적으로 수정하는 작업과도 다릅니다.

예시: A가 10을 읽은 뒤 B가 20으로 커밋하고, A가 qty=qty-1로 갱신하면 대상의 현재 값을 기준으로 19를 만들 수 있습니다. 이후 A는 자기 변경인 19를 봅니다. 처음 읽은 10과 다르다고 RR 자체가 동작하지 않은 것은 아닙니다.

주의: 순수한 반복 스냅샷 조회와 갱신·잠금 읽기를 섞은 흐름을 구분하고, 실제 업무가 어떤 값을 기준으로 판단해야 하는지를 먼저 정하겠습니다.

심층 면접: 모든 테이블에 version 열을 넣으면 동시성 문제를 해결할 수 있나요?

답변: 각 행의 오래된 상태를 바탕으로 한 갱신은 검출할 수 있지만 여러 행에 걸친 모든 불변식까지 자동으로 보호하지는 못합니다. 또한 모든 쓰기 경로가 version 조건과 증가를 지켜야 합니다.

반례: 두 당직자가 서로 다른 행을 수정하면 각자의 version 검사는 모두 성공할 수 있어도 “최소 한 명 당직” 규칙은 깨질 수 있습니다. 공통 제어 행 잠금, 제약으로 표현 가능한 모델, 적절한 직렬화가 필요합니다.

운영: 충돌 시 무제한 재시도하지 않고 새 상태로 재판단하며 횟수와 지연을 제한합니다. 재시도 중 발생하는 외부 효과의 중복도 별도로 관리하겠습니다.
