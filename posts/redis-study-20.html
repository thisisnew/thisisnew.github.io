“Redis는 빠른데 왜 API는 느리지?”

상품 조회 API가 400ms 걸린다. 추적 시스템에서 Redis 호출 구간이 길게 보이지만 SLOWLOG에는 아무것도 없다. 누군가는 네트워크 문제라고 하고, 다른 사람은 Redis가 아닌 것 같다고 말한다. 둘 다 아직 증거가 부족하다. SLOWLOG는 모든 종류의 지연을 재는 도구가 아니기 때문이다.

이 장에서는 제공된 원문 20장의 latency baseline, network communication, mostly single-threaded command execution과 slow commands를 바탕으로 측정의 경계를 세운다. 오래된 원문에 등장하는 특정 VM, CPU, 과거 측정값은 오늘의 보편적인 성능 보장으로 재사용하지 않는다. 우리는 현재 서비스의 실제 경로를 측정하고 병목을 좁히는 방법을 배운다.

핵심 문장은 다음과 같다. 느린 요청과 느린 명령은 같은 말이 아니다. 요청이 서버에 도착하기 전에 기다릴 수 있고, 빠른 명령이 앞의 느린 명령 때문에 기다릴 수 있으며, Redis가 이미 응답한 뒤 JVM이 처리하지 못할 수도 있다.

1. 식당의 조리 시간과 손님의 체류 시간

식당에서 요리를 만드는 데 2분이 걸렸어도 손님은 30분을 기다렸을 수 있다. 입장 줄, 주문 접수, 앞선 주문, 서빙과 결제 시간이 있기 때문이다. SLOWLOG는 주로 “해당 요리를 만드는 실행 구간”에 가깝고 애플리케이션 timer는 주문 전후의 더 넓은 구간을 잴 수 있다.

비유의 한계도 있다. Redis의 여러 단계는 서로 겹칠 수 있고, 네트워크 패킷과 이벤트 루프의 실행은 사람처럼 명확한 순서의 창구로 보이지 않을 수 있다. 아래 합은 실용적인 분해 모델이지 각 도구가 자동으로 정확한 값을 하나씩 제공한다는 뜻은 아니다.

HTTP 전체 시간에는 그 밖에 인증, 업무 계산, DB 조회, 템플릿 렌더링 등이 더 들어간다. Reactive API에서 메서드가 Mono를 반환하는 데 걸린 시간만 재면 실제 네트워크 작업을 전혀 재지 않을 수 있다. 무엇을 시작 시점과 끝 시점으로 삼았는지 먼저 써야 한다.

2. SLOWLOG가 실제로 재는 것

SLOWLOG는 Redis 서버가 명령을 실행하는 데 걸린 시간이 설정된 기준을 넘으면 기록하는 기능이다. 클라이언트와 통신하는 네트워크 I/O 시간은 포함하지 않는다. 또한 다른 명령 뒤에서 실행 차례를 기다린 시간을 해당 명령의 실행 시간과 동일시하면 안 된다. 따라서 slowlog에 빠른 GET만 있거나 기록이 없더라도 GET의 end-to-end 응답은 느릴 수 있다. 공식 SLOWLOG 정의

설정 slowlog-log-slower-than은 마이크로초 단위다. 10,000은 10초가 아니라 10ms다. slowlog-max-len은 보관할 항목 수와 관련된다. 기록은 유한하므로 사고가 지난 뒤 조회했을 때 이미 오래된 항목이 밀려났을 수 있다. 임계값이 너무 높거나 수집이 늦은 경우 “없다”는 결과의 의미는 더욱 제한된다.

SLOWLOG는 느린 명령의 인수 일부를 보여 줄 수 있으므로 민감 정보 취급도 중요하다. 값, 고객 식별자, 토큰이 로그 수집 시스템으로 전달되는지 확인한다. 로그를 외부 티켓에 붙일 때 비밀번호만 지우면 끝이 아닐 수 있다. 성능 조사라는 이유로 데이터 접근 범위를 무제한으로 넓히지 않는다.

3. 아주 빠른 GET이 느리게 보이는 대기열

가정상 어떤 명령 하나가 서버의 명령 실행 경로를 80ms 동안 점유한다. 그 직후 도착한 GET 자체는 20µs 만에 끝날 수 있어도 앞의 작업을 기다려 약 80ms의 지연을 겪는다. GET의 slowlog 실행 시간은 80ms가 아니다. 긴 명령이 기록될 수 있고, 뒤따른 빠른 명령들은 사용자 입장에서는 함께 느려진다.

이것이 head-of-line blocking, 즉 줄 맨 앞의 작업이 뒤의 작업들을 막는 현상이다. 느린 명령을 실행한 고객과 기다리는 고객이 다를 수 있다. 관리자가 실행한 전체 키 조회 한 번 때문에 정상적인 결제 캐시 GET이 느려질 수도 있다. Redis가 여러 클라이언트 연결을 동시에 관리한다는 말과 여러 일반 명령의 데이터 조작을 독립적으로 병렬 실행한다는 말은 다르다.

대기열은 이용률이 높을수록 비선형적으로 나빠질 수 있다. CPU 사용률이 50%에서 60%로 늘었다고 지연도 정확히 20% 증가하는 식은 아니다. 긴 작업의 분포, 도착의 burst, 연결별 버퍼와 네트워크까지 영향을 준다. 이 장에서는 특정 큐 모델을 실제 Redis에 그대로 대입하지 않지만, 평균 처리 시간이 짧아도 긴 꼬리가 전체 tail latency를 흔들 수 있다는 관점은 반드시 가져간다.

4. 평균, p50, p95, p99는 서로 다른 질문이다

p99가 100ms라는 말은 측정한 요청의 약 99%가 그 값 이하라는 뜻이다. 모든 요청이 100ms를 넘지 않는다는 뜻도, 평균이 100ms라는 뜻도 아니다. p50은 가운데 요청, p95와 p99는 더 느린 쪽의 경계다. 최댓값은 측정 구간 길이와 극단적인 사건에 크게 영향을 받는다.

가정으로 요청 1,000개 중 990개가 1ms이고 10개가 201ms라면 평균은 3ms다. “평균 3ms”는 대부분이 빠르다는 사실과 일부가 201ms를 기다렸다는 사실을 모두 숨긴다. 이 분포의 p99 값을 말할 때는 도구의 percentile 정의와 보간 방식도 확인해야 한다. 경계에 정확히 걸린 예시이므로 숫자를 억지로 한 값으로 단정하기보다 느린 요청 비율과 값의 분포를 함께 기록한다.

에러와 timeout을 제외하고 성공 요청만 percentile에 넣으면 장애 때 지연이 좋아 보일 수도 있다. 느린 요청들이 성공 집계에서 빠졌기 때문이다. 따라서 요청 수, 성공률, timeout 수, 재시도 수와 latency histogram을 함께 본다. 여러 인스턴스의 p99를 산술평균하여 서비스 전체 p99라고 부르면 안 된다. 가능하면 bucket 또는 원시 분포를 집계한다.

--latency는 애플리케이션과 같은 네트워크 구간에서 실행하면 유용하다. Redis 서버 바로 옆에서 빠르게 나온 PING으로 멀리 떨어진 앱의 경로까지 정상이라고 주장할 수는 없다. TLS, 프록시, NAT, 가용 영역, DNS와 실제 연결 재사용 조건이 다를 수 있다.

--intrinsic-latency는 Redis에 요청을 보내지 않는다. Redis가 실행되는 서버 환경에서 도구 프로세스가 CPU를 받지 못하는 간격을 측정한다. 서버가 잠깐 스케줄되지 않는 환경적 지연을 찾는 데 쓰지만, 모든 Redis 요청의 최소 지연이 항상 그 최댓값보다 크다는 뜻은 아니다. 관측된 스케줄링 공백은 해당 측정 구간의 환경적 tail 위험을 알려 주는 증거다.

이 테스트는 한 CPU 코어를 강하게 사용할 수 있다. 운영 부하가 높은 서버에서 아무 때나 실행하면 측정 자체가 경쟁을 만든다. 승인된 시간과 환경에서 실행하거나 복제한 실험 환경에서 먼저 영향도를 확인한다. 원문의 오래된 환경별 결과를 현재 인스턴스 성능으로 가져오는 대신 직접 통제된 측정 기록을 남긴다.

6. 네트워크 왕복이 지배하는 경우

가정으로 RTT가 1ms이고 명령 자체가 충분히 짧으며 클라이언트가 한 요청의 응답을 받은 뒤 다음 요청을 보낸다고 하자. 하나의 연결에서 순차적으로 100번 호출하면 왕복만 대략 100ms가 된다. Redis 명령 실행을 20µs에서 10µs로 최적화해도 전체의 주요 비용은 여전히 왕복이다. 이는 예제 가정이지 실제 Redis의 처리량 수치가 아니다.

해결 후보는 명령 수를 줄이는 집계 연산, pipeline, 연결 재사용이다. MGET으로 묶을 때 Cluster에서는 키들이 같은 슬롯이어야 하는 제약을 확인한다. 일부 클라이언트가 여러 노드에 나누어 요청한 뒤 결과를 합쳐 주더라도 그것이 서버의 단일 원자적 MGET과 같은 의미라고 가정하지 않는다.

Pipeline은 앞의 응답을 기다리지 않고 여러 요청을 보내 왕복 대기를 겹친다. 하지만 명령들이 하나의 트랜잭션이 되거나 앞선 결과를 뒤 명령의 입력으로 즉시 사용할 수 있게 되는 것은 아니다. 큰 pipeline은 서버·클라이언트 버퍼, 한 번에 처리할 응답, 다른 요청의 지연을 늘릴 수 있다. batch를 제한하고 실제 업무에서 가능한 크기로 실험한다.

연결을 요청마다 새로 만들면 TCP 연결, TLS handshake, 인증, 토폴로지 조회 등의 비용이 추가될 수 있다. 다만 “무조건 거대한 connection pool”이 정답도 아니다. Lettuce 같은 클라이언트는 비동기 공유 연결 모델을 사용하며 blocking 명령이나 transaction에는 별도 고려가 필요하다. 연결 전략은 드라이버의 실제 동작과 명령 사용 패턴을 기준으로 정한다.

7. 시간 복잡도는 시작점이지 성능 결과표가 아니다

O(N)은 입력 규모 N에 따라 작업량이 대략 어떻게 늘어나는지 설명한다. N이 키 개수인지, Hash field 수인지, 반환 원소 수인지, 검사하는 원소 수인지 명령마다 다르다. 명령 문서의 complexity를 볼 때 그 N의 정의를 읽어야 한다.

O(1)도 “값이 아무리 커도 네트워크까지 같은 시간”이라는 뜻은 아니다. 큰 문자열 GET은 키 조회 자체가 빠르더라도 바이트 전송, 메모리 복사, 클라이언트 파싱에 시간이 든다. 가정으로 1MiB 값을 100회 읽으면 값 payload만 100MiB다. 프로토콜과 네트워크 오버헤드는 별도이며, 작은 값을 읽는 벤치마크와 비교할 수 없다.

O(N) 명령이 무조건 금지인 것도 아니다. 원소가 최대 20개인 작은 집합을 다루는 연산과 수백만 개를 다루는 연산은 실제 비용이 다르다. 중요한 것은 입력 크기의 상한을 모델에 두는 것이다. “사용자가 계속 추가할 수 있다”면 시간이 지나면서 상한 없는 큰 키가 생길 수 있으므로 저장 시 cardinality 제한, 시간 버킷 분리, 페이지 접근을 고려한다.

KEYS pattern은 전체 keyspace를 훑으므로 운영 요청 경로에 넣기 위험하다. SCAN은 커서를 이용해 여러 번에 나누지만 전체 탐색 비용이 사라지는 것은 아니다. COUNT는 정확한 페이지 크기 약속이 아니라 힌트이고 중복 반환 가능성, 실행 중 키 변경에 대한 의미를 이해해야 한다. 관리 검색을 SCAN으로 바꾸었다고 바로 무제한 호출을 허용해서는 안 된다. SCAN의 보장과 COUNT 의미

8. 큰 응답과 큰 키는 다른 문제를 동시에 만든다

큰 Hash 하나의 모든 field를 HGETALL로 가져오는 설계는 서버 탐색, 응답 생성, 네트워크 전송, JVM 객체 생성 모두에 비용을 만든다. slowlog가 보여 주는 시간은 그 중 서버 실행의 일부 경계다. 서버 실행이 빨라도 앱의 JSON 역직렬화와 GC 때문에 지연이 커질 수 있다.

큰 키를 삭제할 때는 자료구조 해제 비용도 생각한다. DEL로 복잡한 큰 자료구조를 제거하면 실행 경로에 비용이 집중될 수 있고, UNLINK는 키를 논리적으로 분리한 후 메모리 해제를 비동기로 넘기는 선택지다. 그러나 UNLINK도 모든 종류의 메모리 압박을 즉시 해결하거나 부하를 0으로 만들지는 않는다. 배경 작업 처리량과 실제 RSS 회수는 별도다. UNLINK의 비동기 해제

큰 Lua 스크립트를 “네트워크 왕복을 줄이는 최적화”로 넣었다가 명령 실행 경로를 오래 독점할 수도 있다. 원자성이 필요한 최소 작업만 묶고, 입력 원소 수를 제한한다. 스크립트 timeout이 관계형 DB처럼 자동 롤백이나 강제 종료를 항상 제공한다고 가정하지 않는다. 이미 쓰기를 한 스크립트의 중단 제약은 별도로 알아야 한다.

9. Java에서 timer를 두 개 두는 이유

다음 코드는 동기 호출의 왕복 경계와 파싱 경계를 분리하는 개념 예시다. recordNanos는 실제 사용하는 메트릭 라이브러리로 연결하고 단위를 명시해야 한다. 전체 key를 metric label로 넣지 않는다.

String loadDocument(long id) {
    long redisStarted = System.nanoTime();
    String json;
    try {
        json = redis.opsForValue().get("document:" + id);
    } finally {
        metrics.recordNanos("redis.lookup", System.nanoTime() - redisStarted);
    }
    if (json == null) return null;

    long parseStarted = System.nanoTime();
    try {
        return decodeAndRender(json); // 예시: 실제 업무 파싱/변환
    } finally {
        metrics.recordNanos("document.decode", System.nanoTime() - parseStarted);
    }
}

System.nanoTime()은 경과 시간 측정에 적합하다. 서로 다른 머신의 nanoTime 값을 빼서 네트워크 지연을 계산하면 안 된다. 사건의 시각을 연결할 때는 별도의 wall clock timestamp와 시계 동기화 상태를 기록한다. 메트릭은 성공과 실패를 구분하되 개인정보나 무한 종류의 exception message를 태그로 사용하지 않는다.

위 첫 timer에는 StringRedisTemplate과 드라이버가 수행한 문자열 변환이 일부 포함될 수 있다. 따라서 “첫 timer는 순수 Redis 서버 시간”이라고 이름 붙이지 않는다. 이 두 timer의 목적은 완벽한 내부 프로파일링이 아니라 사용자 호출의 어떤 큰 구간에서 시간이 증가했는지 구별하는 것이다.

Reactive 코드에서는 구독 시점부터 terminal signal까지 측정해야 한다. 이벤트 루프에서 Thread.sleep, 큰 JSON 변환, 동기 DB 호출을 실행하면 Redis 응답 수신 처리가 지연될 수 있다. 호출 구간이 느리다고 Redis 서버부터 늘리기 전에 스레드 덤프, GC pause와 event-loop blocking 여부를 함께 확인한다.

10. Pipeline 예제를 해석할 때의 계약

여러 독립적인 카운터를 읽는 작업은 순차 왕복을 줄일 수 있다. Spring Data Redis의 pipeline API 형태를 사용한 다음 예시는 작은 고정 개수의 UTF-8 키를 조회하는 구조다. 사용 중인 버전의 반환값 직렬화 설정을 확인해야 하며, 동일 Cluster 슬롯 키만 사용해 노드 분산 의미를 피한다. 아래는 공식 pipeline callback 계약에 맞춰 callback이 null을 반환하는 형태다. Spring Data Redis pipeline 문서

List<Object> values = redis.executePipelined(
    (RedisCallback<Object>) connection -> {
        connection.stringCommands().get(
            "metric:{shop:7}:view".getBytes(StandardCharsets.UTF_8));
        connection.stringCommands().get(
            "metric:{shop:7}:click".getBytes(StandardCharsets.UTF_8));
        return null; // pipeline callback 자체 결과가 아니라 명령 결과를 수집
    });

이 코드는 두 카운터가 정확히 같은 시점의 스냅샷이라는 보장을 의도하지 않는다. 다른 명령이 끼어들 수 있으며 pipeline은 transaction이 아니다. 원자적인 다중 읽기가 요구되고 명령이 지원하면 MGET 같은 집계 명령을 고려한다. 자료형이 String이 아니라면 get 대신 적합한 명령으로 바꾼다.

성능 비교는 순차 2회와 pipeline 2회의 전체 시간을 같은 환경에서 반복해 측정한다. warm-up, 연결 재사용, payload, GC, 동시 요청 수를 맞춰야 한다. 단 한 번의 호출이 빨라졌다고 처리량과 p99가 모두 개선되었다고 주장하지 않는다. pipeline 크기를 늘릴수록 batch를 채우는 시간이 사용자 지연으로 들어갈 수 있다는 점도 잊지 않는다.

11. 안전한 격리 실습: 측정 경계 확인

다음 명령은 실행하지 않은 절차다. localhost의 폐기용 단일 Redis를 사용하고 운영과 데이터를 공유하지 않는다. 예시는 포트 6389가 오직 이 실습용임을 먼저 확인한다. ACL과 인증 설정이 있으면 안전한 방식으로 자격 증명을 제공한다. 모든 키는 lab:latency: 접두사를 쓴다.

redis-cli -p 6389 INFO server
redis-cli -p 6389 CONFIG GET slowlog-log-slower-than
redis-cli -p 6389 CONFIG GET slowlog-max-len
redis-cli -p 6389 SLOWLOG LEN
redis-cli -p 6389 SLOWLOG GET 10
redis-cli -p 6389 SET lab:latency:small hello
redis-cli -p 6389 GET lab:latency:small

예상 결과는 작은 GET/SET이 정상 동작하지만 기존 threshold에 따라 SLOWLOG에 기록되지 않을 수도 있다는 것이다. 이를 “명령이 실행되지 않았다”라고 읽으면 안 된다. 조회 결과의 시간 단위와 항목 수를 먼저 이해한다.

실습 환경에서만 원래 설정을 적어 둔 다음 threshold를 0으로 바꾸면 모든 명령을 기록하는 조건을 관찰할 수 있다. 0이 latency monitor에서는 비활성 의미인 것과 혼동하지 않는다. 실습이 끝나면 반드시 기록해 둔 원래 값으로 복원한다. 실습 전후 SLOWLOG를 임의로 RESET하면 기존 증거를 지울 수 있으므로 새로 만든 전용 인스턴스가 아니라면 하지 않는다.

# 전용 실습 서버에서만. 원래 값을 먼저 별도 기록한다.
redis-cli -p 6389 CONFIG SET slowlog-log-slower-than 0
redis-cli -p 6389 GET lab:latency:small
redis-cli -p 6389 SLOWLOG GET 10
# 종료 시: CONFIG SET slowlog-log-slower-than <기록한_원래값>

다른 터미널에서 redis-cli -p 6389 --latency를 실행하여 PING 왕복을 관찰하고, 충분한 짧은 관찰 뒤 Ctrl-C로 끝낸다. 앱 timer와 CLI 왕복, SLOWLOG 실행 시간은 값이 다를 수 있으며 그것이 정상이다. 정확한 수치는 이 문서에서 예측하지 않는다. 의도적으로 큰 KEYS나 DEBUG SLEEP을 운영 서버에 보내 느린 상황을 만들지 않는다.

12. 진단을 좁히는 의사결정 흐름

첫째, 실제 사용자 영향과 측정 경계를 확인한다. 어느 API, 어느 앱 인스턴스, 어느 Redis 노드, 어떤 시간대에 p99와 오류율이 변했는지 본다. “Redis가 느리다”보다 “상품 상세 API의 Redis 전체 호출 p99가 특정 노드 접근에서 상승했다”가 훨씬 유용하다.

둘째, 동일 시간대 SLOWLOG와 명령 종류·입력 크기를 본다. 긴 명령이 있으면 그 명령을 호출한 업무와 N의 크기를 확인한다. 다만 기록이 없다고 서버를 제외하지 않는다. 내부 이벤트, 대기열, 네트워크와 클라이언트 경로는 남아 있다.

셋째, CLI 왕복을 앱 가까운 위치에서 비교한다. 모든 클라이언트 경로가 동시에 느리면 서버나 공통 네트워크를, 특정 앱만 느리면 GC·연결·스레드·로컬 네트워크를 먼저 의심할 수 있다. 이는 가설 우선순위이지 증명은 아니다. 둘 이상의 원인이 겹칠 수도 있다.

넷째, INFO commandstats, CPU, 네트워크 바이트, 응답 크기, 연결 수와 대기 상태를 같은 시간 축에 놓는다. CPU 평균이 낮아도 짧은 순간의 단일 실행 경로 포화가 평균에 묻힐 수 있다. 메모리와 persistence 이벤트가 의심되면 다음 장의 fork·swap·disk 분석으로 넘어간다.

마지막으로 변경은 한 번에 한 가지 가설을 겨냥한다. 명령을 바꾸면서 VM을 키우고 timeout도 늘리면 무엇이 원인이었는지 알기 어렵다. 개선 전후 요청 조건, 성공률, p99와 자원 사용을 함께 비교하고 기능 의미가 바뀌지 않았는지 확인한다.

13. 실제 장애처럼 읽는 가상 사건

교육용 사례다. 14:00에 운영 검색 화면을 배포했다. 14:03부터 결제 API p99가 상승했다. 서버 CPU는 분 단위 평균으로 45%였고 결제의 GET은 SLOWLOG에 없었다. 초기 대응으로 Redis timeout을 1초에서 3초로 늘렸더니 timeout 수는 줄었지만 웹 요청이 더 오래 쌓였다.

조사 결과 검색 화면이 주기적으로 큰 keyspace를 KEYS로 조회했고 그 실행이 SLOWLOG에 남았다. 결제 GET 자체는 짧았지만 그 뒤에서 기다렸다. 올바른 개선은 timeout 확대가 아니라 관리 검색의 별도 인덱스·증분 조회·호출 제한을 설계하고, 운영 명령을 애플리케이션 ACL과 역할로 제한하는 것이다. SCAN으로 단순 치환하더라도 반복 횟수와 총 부하는 제한해야 한다.

다른 사례에서는 SLOWLOG도 CLI도 정상이지만 특정 JVM의 Redis timer만 늘었다. 그 JVM은 큰 값을 역직렬화한 후 메모리 압박으로 GC pause가 길어졌다. 이 경우 Redis CPU를 늘리는 것은 핵심을 놓친다. payload를 줄이거나 필요한 field만 읽고, 직렬화 및 객체 생성을 최적화해야 한다. 같은 증상 이름이라도 측정 경계를 나누면 다른 해결책으로 이어진다.

면접과 설계 리뷰 Q&A

Q1. SLOWLOG가 비어 있는데 Redis 요청이 느릴 수 있는가?

그렇다. 네트워크, 클라이언트 대기, 앞선 명령 뒤의 대기, 응답 파싱과 GC 등이 전체 시간을 늘릴 수 있다. 또한 threshold가 높거나 오래된 기록이 밀려났을 수 있다. SLOWLOG가 없다는 것은 그 관측 조건에서 긴 서버 실행 기록을 못 봤다는 뜻이지 Redis 관련 경로가 모두 정상이라는 뜻이 아니다.

Q2. GET은 O(1)인데 큰 값은 왜 느린가?

복잡도 설명의 대상과 전체 요청의 비용 범위가 다르기 때문이다. 키를 찾는 일이 빠르더라도 큰 값을 메모리에서 읽어 응답하고 네트워크로 보내며 JVM에서 파싱하는 바이트 비용은 남는다. key cardinality뿐 아니라 value 크기, 응답 바이트와 역직렬화 비용을 함께 봐야 한다.

Q3. 평균 지연만 알면 용량 계획을 할 수 있는가?

평균은 긴 꼬리를 숨길 수 있어 부족하다. p95·p99, 오류와 timeout, 부하 수준에 따른 변화가 필요하다. 특히 실패 요청을 제외한 평균은 장애 때 더 좋아 보일 수도 있다. 지연 분포와 성공 처리량을 함께 측정하고 사용자 SLO를 만족하는 부하 구간을 찾는 것이 용량 계획의 출발점이다.

Q4. SCAN은 KEYS의 완전한 무비용 대체인가?

아니다. 한 번의 긴 작업을 커서 기반 여러 호출로 나누지만 전체 순회 비용은 남는다. COUNT는 엄격한 결과 개수 제한이 아니며 중복과 실행 중 변경 의미도 고려해야 한다. 업무 조회가 자주 필요하면 순회 자체보다 해당 조회를 위한 작은 인덱스나 다른 저장소가 맞는지 먼저 검토한다.

Q5. pipeline을 쓰면 원자성과 처리량이 모두 좋아지는가?

왕복 대기를 줄여 처리량 개선을 기대할 수 있지만 원자성은 제공하지 않는다. 큰 batch는 버퍼와 대기 시간을 늘릴 수도 있다. 실제 업무에서 가능한 batch 크기, 응답 크기, 실패 때 결과 해석을 정하고 측정해야 한다. 여러 노드에 분산되는 Cluster pipeline이면 결과 취합과 부분 실패 의미도 확인한다.

Q6. intrinsic latency를 앱 서버에서 재면 되는가?

Redis 실행 환경의 스케줄링 공백을 보려면 Redis 서버 환경에서 측정해야 한다. 이 모드는 Redis에 접속하지 않으므로 앱 서버에서 실행하면 앱 서버의 환경을 측정한 것이다. 또한 CPU 집약적일 수 있어 실행 자체가 다른 부하에 영향을 주지 않도록 통제한다. 측정 최댓값을 모든 요청의 고정 최소 지연으로 해석하지 않는다.

Q7. Redis가 single-threaded이면 CPU 여러 개는 쓸모없는가?

일반 명령 실행의 직렬 경로가 중요한 것은 맞지만 Redis에는 I/O와 배경 작업, persistence 자식 프로세스 등 다른 실행 활동이 있다. 모든 작업을 하나의 코어에 억지로 묶으면 오히려 경쟁이 생길 수 있다. 실제 버전과 설정의 스레딩 모델을 확인하고 명령 실행 병목과 전체 호스트 자원 사용을 구별해야 한다.

Q8. timeout을 늘리는 것이 성능 문제의 해결책인가?

일시적 변동을 허용하는 정책 변경일 수는 있지만 서버가 처리하는 일을 줄이거나 대기 원인을 제거하지 않는다. 더 오래 기다리는 요청이 쌓여 thread·queue·메모리를 더 쓰게 될 수도 있다. 상위 deadline과 오류 정책에 맞게 조정하되, 명령 비용·왕복·클라이언트 정체라는 근본 원인은 따로 해결해야 한다.

정리

성능 분석의 첫 기술은 빠른 명령을 외우는 것이 아니라 어느 시계가 어느 구간을 재는지 명확히 말하는 것이다. SLOWLOG, PING 왕복, 앱 timer와 intrinsic latency는 서로 경쟁하는 정답이 아니라 서로 다른 관측창이다. 입력 크기를 제한하고 왕복을 줄이며 긴 명령이 다른 요청을 막는 경로를 찾아야 한다.

  • 제공된 원문 20장: latency baseline, communication, command execution과 slow commands를 재구성했다.
  • 공식 지연 진단 문서: 측정 도구와 환경 지연의 교차 확인.
  • SLOWLOG: 서버 실행과 통신 I/O의 경계.
