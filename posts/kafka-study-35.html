Streams 운영·보안·리밸런스

도트 게임 속 스테이지를 진행하듯, 쉬운 비유부터 기술적인 흐름과 장애 대응을 함께 익혀봅시다. 비유의 한계를 기억하고 실제 용어를 직접 설명해 보세요.

2. 내부 토픽 권한

작업 장부를 쓸 수 있는 열쇠

Stateful Topology는 내부 Changelog/Repartition 토픽에 대한 생성·읽기·쓰기 권한이 필요할 수 있다.

실습과 점검

테스트 토픽과 격리된 Kafka 클러스터에서 각각의 이벤트 Key, Partition, Offset, 처리 성공 여부를 기록하며 결과를 추적하세요. 상태를 사용하는 기능은 앱 재시작 시 복구 시간도 측정합니다. 운영 클러스터의 오프셋을 임의로 수정하거나 Topic을 삭제해서는 안 됩니다.

더 깊게 배우기 1. Streams Rebalance는 무엇을 이동시킬까?

Consumer Group의 파티션 배정과 연결돼 Streams Task가 재할당되면, Stateful Task는 State Store 복원이 필요할 수 있습니다. 이 과정에서 애플리케이션이 RUNNING으로 돌아오기까지 시간이 걸릴 수 있어요. 단순 Consumer보다 State Store가 큰 시스템은 배포 시간을 길게 잡아야 할 수도 있습니다.

더 깊게 배우기 2. 내부 Topic과 ACL

Streams의 내부 Changelog/Repartition Topic을 만들고 읽고 쓰려면 필요한 권한이 있어야 합니다. 원본 Topic에 Read 권한만 주었다고 Streams 전체가 동작하는 것은 아닐 수 있습니다. application.id에 따라 내부 Topic 이름이 구성되므로 ACL 네이밍과 배포 정책을 같이 설계하세요.

더 깊게 배우기 3. Standby Task와 복구

Standby Task는 활성 Task의 상태 정보를 따라 유지하여 장애 시 복원 부담을 줄이는 데 도움이 될 수 있습니다. 하지만 복제 비용과 추가 리소스가 필요하고, Standby 수를 늘린다고 장애 복구가 항상 즉시 끝나는 것은 아닙니다. 클러스터 용량과 목표 RTO를 기준으로 선택합니다.

더 깊게 배우기 4. Exactly-once의 실제 보장 범위

Streams의 exactly_once_v2를 사용해도 MySQL이나 외부 REST API 갱신이 같은 Kafka 트랜잭션 안에 자동으로 들어가지 않아요. 예를 들어 Kafka 이벤트를 소비해서 결제 API에 요청했다면, 재시도 시 외부 결제가 중복될 수 있습니다. 외부 시스템의 Idempotency-Key와 업무 상태 전이 설계가 필요합니다.

더 깊게 배우기 5. 운영 Runbook

재배포 후 Lag이 늘면 ① Task가 REBALANCING인지 ② State Store가 RESTORING인지 ③ 내부 Topic 권한이 정상인지 ④ 디스크 여유가 있는지 ⑤ Broker ISR과 요청 지연이 정상인지 순서대로 확인해요. CPU 증설이나 컨슈머 수 증가부터 시도하면 근본 원인을 놓칠 수 있습니다.
