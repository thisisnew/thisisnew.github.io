개정 심화: 내부 원리와 설계 판단

실제로 저장되고 이동하는 것은 무엇인가?

Connect REST는 설정과 상태·재시작을 관리합니다. Connector 상태만 보고 Task 실패를 놓치지 않도록 /connectors/{name}/status의 task별 상태와 trace를 확인합니다. errors.tolerance=all은 지원되는 변환·변환기 등 오류 처리 범위에서 레코드를 건너뛸 수 있게 하지만 모든 Connector put 예외를 자동 복구하지 않습니다. Sink DLQ는 실패 데이터 보관 경로이지 최종 업무 처리 성공의 증거가 아닙니다.

설정을 선택할 때 따져야 할 경계

DLQ에는 원본 데이터·개인정보와 오류 문맥이 들어갈 수 있어 ACL·보존·재처리 도구를 설계합니다. 오류 허용을 켰으면 성공 처리량과 건너뛴 수·DLQ 수를 따로 봅니다. plugin upgrade는 모든 Worker 배포·Task 이동·직렬화 호환성을 시험하고 REST 인터페이스는 외부 공개 관리 API로 방치하지 않습니다.

가상 장애 사례: 증상에서 실패 구간으로

알람을 끄려고 errors.tolerance=all을 켜면 빨간 불은 줄어도 업무 누락이 늘 수 있습니다. DLQ에 쌓인 데이터를 누가 언제 어떤 버전으로 재처리할지 소유자를 정해야 합니다. 원인을 고치지 않고 restart만 반복하면 원본 로그 보존이 끝나 복구 범위를 잃을 수도 있습니다.

이 주장을 반례로 검증해 보세요

검증할 주장: “errors.tolerance=all이면 모든 Task 오류가 DLQ로 간다”

반박과 확인할 증거: 지원되는 변환·처리 단계와 Connector별 예외를 구분해야 합니다. 외부 Sink 영구 장애까지 전부 건너뛴다고 가정하면 안 됩니다.

단계별 해설: Connector와 Task 상태를 같이 읽기

상황과 비유

REST status에 Connector RUNNING, Task 0 FAILED, Task 1 RUNNING이 보인다고 합시다. 전체 연결이 정상이라는 결론도, 모든 파티션이 멈췄다는 결론도 아직 근거가 부족합니다.

시간순으로 내부 동작 따라가기

Task 0이 맡은 입력과 실패 trace를 확인하고 Task 1의 처리율도 따로 봅니다. 자격 오류라면 설정을 수정하고, 잘못된 레코드라면 지원되는 오류 처리 범위와 격리 정책을 확인합니다. 재시작은 실패 원인을 고친 뒤 적용해야 하며 같은 입력에서 반복 실패한다면 재시작 횟수만 늘어납니다.

직접 확인할 실습과 판단 기준

상태 조회와 실제 데이터 도착 검증을 묶으세요. 장애 직전 마지막 성공 eventId, 커밋, DLQ 수, 외부 결과를 저장합니다. 오류 허용 설정은 모든 외부 부작용·Task 예외를 자동 복구하는 만능 스위치가 아니므로 적용되는 처리 단계도 문서에서 확인합니다.

Java 21과 Spring 코드로 연결하기

Connect 실습은 Worker를 띄운 뒤 세 가지를 따로 확인합니다. REST로 Connector·Task 상태를 읽고, Kafka에서 실제 eventId를 읽고, 외부 원본·대상 시스템의 행을 대조합니다. Worker가 RUNNING인 것과 전체 데이터가 도착했다는 것은 다른 주장입니다. 학습에 쓰는 FileStream은 Connect 흐름을 관찰하는 예시이며 운영 CDC 성능·내구성 보증으로 확장하지 않습니다.

SourceTask가 원본 100번 행까지 읽고 Kafka 전송 전에 죽는 경우와, Kafka 성공 뒤 source offset 저장 전에 죽는 경우를 구분합니다. 전자는 다시 읽을 수 있어야 하고 후자는 중복 전송이 생길 수 있습니다. exactly-once source 지원은 Worker·Connector·외부 원본의 조건을 함께 확인합니다. SinkTask는 외부 시스템에서 완료되지 않은 레코드의 Kafka offset을 안전한 진행으로 보고하지 않아야 합니다.

외부 Sink에서 batch 100건 중 50건만 저장하고 timeout이 났다면 어떤 50건인지 아는지, 대상이 원자 batch를 제공하는지, eventId 기준 upsert가 가능한지 조사합니다. flush와 preCommit을 연결하지 않고 비동기 put 접수만 성공으로 보고하면 재시작에서 유실될 수 있습니다. 예외를 무조건 RetriableException으로 바꿔도 영구 오류는 사라지지 않으며 원본 보존 기간만 소모할 수 있습니다.

아래 Java Consumer는 Kafka 쪽 실제 레코드를 대조하는 관찰 도구로 사용할 수 있습니다. 별도 그룹에서 읽어야 실제 Sink 그룹의 offset에 영향을 주지 않습니다. 아래 Spring 예제는 Connector 코드가 아니라 같은 토픽을 읽는 애플리케이션 예시입니다. 프레임워크가 다르면 ack/flush의 의미도 다르므로 메서드 이름이 비슷하다는 이유로 같은 복구 경계라고 단정하지 않습니다.

package study;

import java.time.Duration;
import java.util.*;
import java.util.concurrent.TimeUnit;
import org.apache.kafka.clients.admin.*;
import org.apache.kafka.clients.consumer.*;
import org.apache.kafka.clients.producer.*;
import org.apache.kafka.common.TopicPartition;
import org.apache.kafka.common.serialization.*;

/** Finite lab: unique topic, explicit offsets, bounded waits. Java 21. */
public final class Lab {
    public static String bootstrap() {
        return System.getenv().getOrDefault("KAFKA_BOOTSTRAP", "localhost:9092");
    }
    public static Properties producerProperties() {
        Properties p = new Properties();
        p.put("bootstrap.servers", bootstrap());
        p.put("key.serializer", StringSerializer.class.getName());
        p.put("value.serializer", StringSerializer.class.getName());
        p.put("acks", "all");
        p.put("enable.idempotence", true);
        p.put("linger.ms", 5);
        p.put("request.timeout.ms", 10000);
        p.put("delivery.timeout.ms", 30000);
        return p;
    }
    public static Properties consumerProperties(String group) {
        Properties p = new Properties();
        p.put("bootstrap.servers", bootstrap());
        p.put("group.id", group);
        p.put("key.deserializer", StringDeserializer.class.getName());
        p.put("value.deserializer", StringDeserializer.class.getName());
        p.put("enable.auto.commit", false);
        p.put("auto.offset.reset", "earliest");
        p.put("max.poll.records", 10);
        return p;
    }
    public static void main(String[] args) throws Exception {
        String topic = "study.java." + UUID.randomUUID();
        String group = topic + ".group";
        try (Admin admin = Admin.create(Map.of("bootstrap.servers", bootstrap()))) {
            admin.createTopics(List.of(new NewTopic(topic, 1, (short) 1)))
                 .all().get(30, TimeUnit.SECONDS);
            try {
                try (KafkaProducer<String, String> producer = new KafkaProducer<>(producerProperties())) {
                    List<java.util.concurrent.Future<RecordMetadata>> sends = new ArrayList<>();
                    for (int i = 0; i < 10; i++) {
                        sends.add(producer.send(new ProducerRecord<>(topic, "order-A", "evt-" + i)));
                    }
                    for (var send : sends) {
                        var m = send.get(30, TimeUnit.SECONDS);
                        System.out.printf("sent partition=%d offset=%d%n", m.partition(), m.offset());
                    }
                }
                Set<String> seen = new HashSet<>();
                try (KafkaConsumer<String, String> c = new KafkaConsumer<>(consumerProperties(group))) {
                    c.subscribe(List.of(topic));
                    long deadline = System.nanoTime() + Duration.ofSeconds(40).toNanos();
                    while (seen.size() < 10 && System.nanoTime() < deadline) {
                        ConsumerRecords<String, String> batch = c.poll(Duration.ofMillis(500));
                        Map<TopicPartition, OffsetAndMetadata> done = new HashMap<>();
                        for (var r : batch) {
                            // In-memory observation only: not durable business deduplication.
                            seen.add(r.value());
                            System.out.printf("read %s-%d@%d value=%s%n", r.topic(), r.partition(), r.offset(), r.value());
                            done.put(new TopicPartition(r.topic(), r.partition()), new OffsetAndMetadata(r.offset() + 1));
                        }
                        if (!done.isEmpty()) c.commitSync(done);
                        for (var tp : c.assignment()) {
                            System.out.printf("position=%d committed=%s%n", c.position(tp), c.committed(Set.of(tp)).get(tp));
                        }
                    }
                }
                if (seen.size() != 10) throw new IllegalStateException("Expected 10 unique events, got " + seen.size());
                System.out.println("PASS: ten events observed and explicit next offsets committed");
            } finally {
                admin.deleteTopics(List.of(topic)).all().get(30, TimeUnit.SECONDS);
            }
        }
    }
}

import org.springframework.kafka.core.DefaultKafkaConsumerFactory;
import org.springframework.kafka.listener.ContainerProperties;
import org.springframework.kafka.listener.CommonContainerStoppingErrorHandler;
import org.springframework.kafka.support.Acknowledgment;

/** Plain Spring configuration; Boot is intentionally not needed for this lab. */
@Configuration
@EnableKafka
public class SpringConsumer {
    @Bean
    ConcurrentKafkaListenerContainerFactory<String, String> kafkaListenerContainerFactory() {
        var f = new ConcurrentKafkaListenerContainerFactory<String, String>();
        Map<String, Object> props = new java.util.HashMap<>();
        Lab.consumerProperties("study.spring").forEach((k, v) -> props.put(k.toString(), v));
        f.setConsumerFactory(new DefaultKafkaConsumerFactory<>(props));
        f.getContainerProperties().setAckMode(ContainerProperties.AckMode.MANUAL_IMMEDIATE);
        // Educational fail-stop: do not silently recover/discard after retries.
        f.setCommonErrorHandler(new CommonContainerStoppingErrorHandler());
        return f;
    }
    @KafkaListener(topics = "study.spring.input", groupId = "study.spring")
    public void listen(ConsumerRecord<String, String> record, Acknowledgment ack) {
        if (record.value() == null) throw new IllegalArgumentException("Null payload in this lab");
        System.out.printf("processed %s-%d@%d value=%s%n", record.topic(), record.partition(), record.offset(), record.value());
        // Replace with a durable transactional service before using for real work.
        ack.acknowledge();
    }
    public static void main(String[] args) {
        var ctx = new AnnotationConfigApplicationContext(SpringConsumer.class);
        ctx.registerShutdownHook();
    }
}

코드 읽기 과제: 메서드 호출이 성공한 사실과 영속 저장이 성공한 사실이 어디에서 갈라지는지 표시하세요. listen의 stdout을 실제 DB 서비스로 바꾼다면 DB 예외를 삼키지 말고, DB 트랜잭션이 반환된 뒤 ack 경계를 정합니다. 별도 비동기 큐에 넣고 즉시 ack하는 변경은 다른 전달 모델이므로 그대로 안전하다고 판단하지 않습니다.

DLQ를 운영 가능한 작업 목록으로 만들기

DLQ에 레코드가 쌓였다는 알람만 있으면 다음 행동이 정해지지 않습니다. eventId, 원래 Topic/Partition/Offset, 실패 단계, 오류 분류, 최초·최근 실패 시각, 시도 횟수, 재처리 코드 버전을 연결할 수 있어야 합니다. 실제 payload에는 개인정보가 있을 수 있어 DLQ를 누구나 읽는 공용 토픽으로 만들지 않습니다.

재처리는 원인 수정 후 작은 샘플부터 진행합니다. 스키마 오류를 고쳤는지, 외부 Sink 자격이 회복됐는지, 같은 이벤트가 이미 일부 반영됐는지 확인합니다. 전체 DLQ를 원본 토픽에 다시 밀어 넣으면 순서 역전과 중복이 생길 수 있습니다. 원본 key와 eventId를 유지하고 정상 처리 결과와 대조할 수 있어야 합니다.

Task를 restart하는 것은 진행 상태와 데이터를 자동 초기화하는 명령이 아닙니다. 같은 오류를 다시 만나면 다시 실패할 수 있습니다. 설정 변경이 Task 재구성·리밸런스를 유발하는지도 확인합니다. 운영 API의 restart·pause·resume·stop의 정확한 지원과 효과를 버전에 맞춰 읽고 사용합니다.

완료 기준은 DLQ가 비었다는 하나의 수치보다 최종 대상에 필요한 데이터가 존재하고 중복 부작용이 없다는 대조입니다. 복구 작업 중 발생한 새 실패가 별도로 구분되는지도 중요합니다. DLQ 보존이 끝나기 전에 처리할 담당자·기한·오류 분류별 runbook을 정해야 데이터 보관이 실제 복구로 이어집니다.

코드로 계산하는 안전한 커밋 경계와 offset 공백

다음 계산기는 한 파티션에서 실제 전달된 순서 목록을 사용합니다. offset이 100,102,105라면 101·103·104가 없다는 이유만으로 실패라고 판단하지 않습니다. 로그 정리·제어 레코드 등으로 offset 공백이 가능하기 때문입니다. 반대로 실제 전달된 102가 실패했는데 105가 성공했다면 106으로 뛰어넘으면 안 됩니다. 이 계산은 한 배치의 의미를 보여 주는 예제이며 리밸런스·이전 in-flight batch·동시 작업을 관리하는 운영 commit manager가 아닙니다.

package study;
import java.util.*;

/** One partition, one delivered batch in log order. A teaching calculation,
 * not a rebalance-aware concurrent commit manager. */
public final class CommitBoundary {
    public static OptionalLong next(List<Long> delivered, Set<Long> successful) {
        if (delivered.isEmpty()) return OptionalLong.empty();
        long previous = -1;
        for (long offset : delivered) {
            if (offset < 0 || offset <= previous)
                throw new IllegalArgumentException("Offsets must be strictly increasing");
            previous = offset;
        }
        for (long offset : delivered) {
            if (!successful.contains(offset)) return OptionalLong.of(offset);
        }
        return OptionalLong.of(Math.addExact(delivered.getLast(), 1));
    }
}
package study;
import static org.junit.jupiter.api.Assertions.*;
import java.util.*;
import org.junit.jupiter.api.Test;
class CommitBoundaryTest {
    @Test void doesNotSkipEarlierFailureWhenLaterRecordCompletes() {
        assertEquals(101, CommitBoundary.next(List.of(100L,101L,102L), Set.of(100L,102L)).orElseThrow());
    }
    @Test void offsetGapsDoNotMeanMissingBusinessRecords() {
        assertEquals(106, CommitBoundary.next(List.of(100L,102L,105L), Set.of(100L,102L,105L)).orElseThrow());
    }
    @Test void noCompletionMeansNoForwardProgress() {
        assertEquals(100, CommitBoundary.next(List.of(100L,101L), Set.of()).orElseThrow());
        assertTrue(CommitBoundary.next(List.of(), Set.of()).isEmpty());
    }
    @Test void rejectsWrongOrderRatherThanInventingSafeBoundary() {
        assertThrows(IllegalArgumentException.class, () -> CommitBoundary.next(List.of(2L,1L), Set.of(1L,2L)));
    }
}

실험에서 100과 102가 먼저 성공하고 101이 실패한 경우를 설명하세요. 가장 큰 성공 offset은 102이지만 안전하게 건너뛸 수 있는 경계는 101입니다. 반면 실제 전달 목록 자체가 100,102,105이고 모두 성공했다면 다음 경계는 106입니다. 숫자의 연속성과 실제 전달된 업무의 연속 성공을 구분해야 합니다. 파티션마다 독립적으로 계산하고, 재할당 후 이전 소유자의 완료 통지를 그대로 적용하지 않도록 소유권 경계를 별도로 관리합니다.

실무 연결: 발행 결과 관찰과 DB 멱등 경계

같은 이벤트를 다시 받았을 때 재고가 두 번 증가하지 않도록 DB 유일 키와 업무 변경을 같은 로컬 트랜잭션에 넣는 예제입니다. 이 코드는 MySQL 전용 오류 1062를 중복 키로 분류하며 다른 SQL 오류까지 중복이라고 삼키지 않습니다. Kafka offset은 이 DB 트랜잭션에 참여하지 않습니다. DB commit 후 listener에서 ack하며, commit 직후 프로세스가 죽으면 재수신에서 marker가 중복 증가를 막는 구조입니다. DB commit 결과가 네트워크 장애로 불명인 경우에도 실패를 노출하고 안정적인 eventId로 재시도해야 합니다.

package study;
import javax.sql.DataSource;
import java.sql.*;

/** MySQL-specific duplicate-key classification; not a generic SQL dialect adapter.
 * The event marker and inventory update share ONE local DB transaction.
 * Kafka offsets are deliberately outside this JDBC transaction. */
public final class DedupJdbc {
    public static boolean apply(DataSource ds, String consumer, String eventId,
                                String sku, long inboundQuantity) throws SQLException {
        if (consumer == null || eventId == null || sku == null || inboundQuantity < 0)
            throw new IllegalArgumentException("Invalid inbound event");
        try (Connection c = ds.getConnection()) {
            c.setAutoCommit(false);
            try {
                try (PreparedStatement marker = c.prepareStatement(
                        "INSERT INTO processed_event(consumer_name,event_id) VALUES (?,?)")) {
                    marker.setString(1, consumer);
                    marker.setString(2, eventId);
                    try {
                        marker.executeUpdate();
                    } catch (SQLException duplicate) {
                        if (duplicate.getErrorCode() != 1062) throw duplicate;
                        c.rollback();
                        return false; // Marker already exists: no inventory change.
                    }
                }
                try (PreparedStatement update = c.prepareStatement(
                        "UPDATE stock SET qty = qty + ? WHERE sku = ?")) {
                    update.setLong(1, inboundQuantity);
                    update.setString(2, sku);
                    if (update.executeUpdate() != 1)
                        throw new SQLException("Stock row missing or unexpected update count");
                }
                c.commit();
                return true;
            } catch (SQLException | RuntimeException failure) {
                try { c.rollback(); } catch (SQLException rollback) { failure.addSuppressed(rollback); }
                throw failure;
            }
        }
    }
}

사고 실험은 세 단계로 나눕니다. 첫 호출로 SKU-A가 0에서 10으로 바뀌고 marker가 생기는지 확인합니다. 같은 consumer_name과 eventId로 다시 호출하면 false가 반환되고 재고가 10에 남아야 합니다. 다른 eventId에 재고 행이 없는 sku를 넣으면 UPDATE 실패로 marker도 롤백되어야 합니다. 이 예제의 DB 동작은 별도 MySQL 통합 시험 대상이며 컴파일 성공만으로 DB 동시성과 장애 복구를 검증했다고 보고하지 않습니다.

운영 적용에는 연결풀 상태 복구, 서비스의 트랜잭션 매니저, DB 격리 수준, 재시도, 이벤트 검증, 삭제·보존 정책, consumer_name의 안정성을 추가로 검토합니다. Spring의 관리 트랜잭션 안에서 이 메서드가 임의로 별도 connection을 만들도록 섞어 쓰지 말고, 같은 트랜잭션 경계로 맞춰 이식해야 합니다. 서로 다른 eventId로 같은 업무가 두 번 발행되는 문제에는 업무 키·상태 전이 조건도 필요합니다.

독립 학습용 공통 원리: 이 편만 읽어도 필요한 배경

다음 여덟 절은 각 포스팅을 독립적으로 읽을 수 있도록 공유하는 배경 교재입니다. 여러 편을 순서대로 읽는다면 이미 이해한 절은 건너뛰고 이번 편 고유 실험과 Q&A에 집중하세요. 공유 배경의 분량을 주제별 신규 설명 분량으로 집계하지 않습니다.

로그·상태·진행 위치를 서로 다른 장부로 구분하기

입고 이벤트 한 건을 추적할 때 장부를 세 개로 나눠 생각해 봅시다. 첫째는 Kafka에 실제로 들어 있는 레코드 로그, 둘째는 Consumer 그룹이 어디부터 다시 시작할지 저장한 진행 위치, 셋째는 MySQL의 실제 입고 결과입니다. 세 장부가 같은 시스템에 저장된다고 가정하면 거의 모든 정합성 설명이 틀어집니다. Kafka가 레코드를 오래 보관해도 Consumer가 앞서 커밋했다면 업무 누락이 생길 수 있고, DB가 성공해도 커밋이 실패하면 재처리가 생길 수 있습니다.

일반 Kafka Consumer에서 offset 104까지 성공했다면 다음 복구 위치는 105입니다. offset은 파티션마다 독립이므로 P0의 105와 P1의 105는 서로 다른 위치입니다. 로그 정리와 트랜잭션 제어 레코드 등의 영향 때문에 offset 차이를 곧바로 업무 건수로 바꾸면 안 됩니다. 키가 같은 레코드도 서로 다른 offset을 얻을 수 있습니다. eventId는 업무 이벤트의 정체성, offset은 특정 로그의 위치라는 차이를 기억하세요.

처리 순서를 시간선에 놓으면 문제가 단순해집니다. t1에서 poll이 100~109를 반환하고, t2에서 DB에 100~104를 반영하고, t3에서 프로세스가 죽었다고 해봅시다. 커밋이 100에 남아 있으면 재시작 후 앞 다섯 건이 다시 올 수 있습니다. 커밋을 110으로 미리 옮겼다면 뒤 다섯 건을 건너뛸 수 있습니다. 안전한 진전은 파티션별 연속 성공 경계를 기록하는 것입니다. 단순히 완료된 레코드 중 가장 큰 offset을 커밋하는 것은 병렬 처리에서 안전하지 않습니다.

Kafka 트랜잭션으로 Kafka 입력 offset과 Kafka 출력을 묶을 수 있어도 별도 DB의 성공이 자동으로 포함되는 것은 아닙니다. 업무 결과에 고유 eventId를 기록하고 같은 트랜잭션에서 재고 변경과 함께 확정하는 방식이 필요할 수 있습니다. 이 원리는 Producer·Connect·Streams·DR에서도 반복됩니다. 단, 각 도구의 진행 위치 저장 방식과 트랜잭션 범위는 다르므로 같은 단어를 그대로 옮겨 붙이면 안 됩니다.

재시도를 세 가지 결과로 나누면 중복이 이해된다

네트워크 요청 결과를 성공·실패 두 가지로만 나누면 어려운 장애가 설명되지 않습니다. 결과는 성공 확인, 미적용이 확인된 실패, 적용 여부를 알 수 없는 결과로 나눠 봅니다. 서버가 레코드를 저장한 뒤 응답이 끊겼다면 클라이언트는 타임아웃을 보지만 서버에는 기록이 남을 수 있습니다. 그래서 타임아웃을 무조건 미기록으로 해석한 재시도는 중복을 만듭니다.

재시도하려면 무엇이 같은 요청인지 먼저 정해야 합니다. 클라이언트 라이브러리가 같은 전송을 재시도하는 것과, 사용자가 버튼을 다시 눌러 새 이벤트를 만드는 것은 다릅니다. Producer idempotence는 프로토콜의 Producer 식별·epoch·sequence를 사용해 전송 재시도 문제를 다룹니다. 새 프로세스가 새 eventId로 같은 주문 완료를 발행하는 문제까지 자동 해결하지 않습니다. 업무 멱등 키를 안정적으로 유지해야 하는 이유입니다.

Consumer 쪽에서는 eventId를 저장한 뒤 이미 처리됐는지 확인하고 업무 작업을 수행하는 경계가 중요합니다. 단순 SELECT 후 INSERT는 동시 실행 경쟁에 약합니다. DB의 UNIQUE 제약을 최종 방어선으로 쓰고, 중복 감지 기록과 업무 갱신을 같은 DB 트랜잭션에 넣습니다. 중복 표식만 먼저 별도 트랜잭션으로 커밋하면 업무 실패 뒤 재수신을 잘못 건너뛸 수 있습니다. 반대로 업무만 먼저 커밋하면 표식 기록 전 장애에서 중복을 막지 못합니다.

재시도 간격에는 backoff와 jitter를 사용해 여러 인스턴스가 동시에 외부 DB를 두드리지 않게 합니다. 최대 횟수만 정하는 것으로는 충분하지 않습니다. 총 경과 시간, 업무 마감, 보존 기간, 영구 오류의 격리와 소유자까지 정해야 합니다. DLQ는 처리 실패를 보관하는 경로이며 성공으로 바꾸는 마법이 아닙니다. DLQ 건수와 재처리 결과를 정상 처리 결과와 별도로 대조합니다.

복제·가시성·물리 저장의 보장은 같은 말이 아니다

Replica는 파티션의 사본입니다. replication factor가 3이면 보통 세 브로커에 해당 파티션 사본을 둡니다. Leader가 쓰기와 일반 읽기 요청을 담당하고 follower는 로그를 복제합니다. ISR은 현재 동기 상태로 간주되는 복제본 집합이며 RF 숫자와 항상 같지는 않습니다. 장애·지연으로 ISR에서 빠진 사본이 존재할 수 있습니다.

acks=all은 현재 ISR과 연관된 복제 확인이고 min.insync.replicas는 그 모드에서 쓰기를 허용하는 최소 ISR 수입니다. RF=3, minISR=2에서 한 사본이 이탈해 ISR=2가 되면 설정 조건 안에서 쓰기를 계속할 수 있습니다. ISR=1이 되면 쓰기 가용성을 제한하여 내구성 조건을 지키는 선택입니다. minISR=2가 언제나 정확히 두 대 응답만 기다린다는 뜻은 아닙니다. 요청 도중 ISR이 바뀌거나 응답이 유실되면 실패 응답과 실제 로그 상태를 별도로 살펴야 합니다.

복제 확인과 fsync는 다른 층입니다. Kafka는 파일시스템 로그와 OS 페이지 캐시를 활용하며 매 레코드마다 모든 디스크를 물리적으로 flush한다는 의미로 acks를 설명하면 안 됩니다. 모든 복제본이 같은 전원·스토리지 장애 도메인에 있으면 복제 수만으로 충분한 내결함성을 얻지 못합니다. 랙·가용영역 배치와 장애 모델을 함께 써야 합니다.

Consumer가 볼 수 있는 위치도 로그 끝과 구별합니다. High watermark는 복제에 따른 커밋 경계와 관련되고, read_committed에서는 미완료 트랜잭션의 영향을 받는 last stable offset이 중요합니다. 아직 완료되지 않은 트랜잭션 때문에 뒤 데이터의 가시성이 지연될 수 있습니다. 모니터링 도구가 어느 경계를 조회하는지에 따라 lag 해석도 달라집니다. ELR을 사용하는 4.3 구성에서는 ISR 밖이라도 안전하게 리더 후보가 되는 경우를 공식 ELR 문서와 함께 확인해야 하므로 과거의 ISR 설명을 무조건적인 전체 규칙으로 외우지 않습니다.

DB 정합성: Outbox와 소비 멱등성은 서로 다른 실패를 다룬다

DB 저장과 Kafka 발행을 차례로 호출하는 코드를 생각해 봅시다. DB가 먼저 성공하면 발행 전 장애에서 이벤트가 빠집니다. Kafka를 먼저 성공시키면 뒤 DB 롤백에서 실제로 없는 사실이 발행될 수 있습니다. @Transactional이 붙었다는 사실만으로 두 자원이 하나의 분산 트랜잭션이 되는 것은 아닙니다. 어떤 트랜잭션 매니저가 어느 자원을 관리하는지 확인해야 합니다.

Outbox는 업무 행과 발행할 이벤트 행을 같은 DB 트랜잭션에서 저장합니다. 별도 발행기가 미발행 행을 읽어 Kafka에 보내고 전송 완료를 표시합니다. 이때 Kafka 성공 뒤 DB의 완료 표시 전에 발행기가 죽으면 같은 Outbox가 다시 전송될 수 있습니다. 따라서 Outbox는 발행 의도 누락을 줄이는 설계이지 모든 중복을 없애는 장치가 아닙니다. Consumer의 eventId 기반 멱등성과 함께 사용합니다.

발행기를 여러 개 운영하면 같은 Outbox 행을 누가 맡는지 잠금·상태·lease 같은 소유권 전략이 필요합니다. offset이나 auto increment id가 항상 DB 커밋 순서를 대변한다고 가정하면 늦게 커밋된 행을 건너뛸 수 있으므로 조회 경계와 재스캔 정책을 검토합니다. DB 락을 잡은 채 외부 Kafka 응답을 오래 기다리면 잠금과 커넥션풀 정체를 키울 수 있습니다. 처리량과 정합성 모두를 보며 설계해야 합니다.

소비 멱등성에는 eventId만이 아니라 업무 규칙도 있습니다. 서로 다른 eventId로 같은 주문 완료가 두 번 만들어진다면 이벤트 중복 키만으로 막을 수 없습니다. 주문 상태 전이, 업무 명령 id, 버전 비교 같은 도메인 조건을 함께 사용합니다. 재고를 무조건 더하는 연산과 특정 버전의 상태로 갱신하는 연산은 중복에 대한 성질이 다릅니다. 어떤 중복을 막는지 문장으로 먼저 정의한 뒤 코드를 작성하세요.

배치·병렬성·역압력을 분리해서 계산하기

배치란 여러 작업을 묶어 고정 비용을 나누는 것이고 병렬성은 여러 작업을 동시에 진행하는 것입니다. JDBC batch를 쓰는 Consumer가 하나일 수도 있고, 여러 Consumer가 건별 SQL을 보낼 수도 있습니다. Producer의 네트워크 배치, Consumer poll의 레코드 묶음, Spring batch listener, DB bulk insert는 서로 다른 네 단계입니다. 하나를 켰다고 나머지도 자동으로 묶이지 않습니다.

일반 Consumer Group에서 한 토픽 파티션은 같은 시점에 한 멤버가 담당하므로 파티션 3개에 멤버 10개를 붙여도 그 토픽을 10개가 동시에 분할 소비하지 않습니다. 여러 토픽을 구독하면 전체 배정 가능 파티션을 봐야 합니다. 한 파티션의 특정 키에 일이 집중되면 전체 평균 CPU가 낮아도 그 키의 진행이 막힐 수 있습니다. 처리 순서를 유지해야 하는 단위와 확장 단위를 함께 정합니다.

DB bulk로 처리할 때는 배치 전체 롤백이 가능한지, 일부 성공을 반환하는지, 실패 레코드를 어떻게 찾는지 검증합니다. 100개 중 50개 성공 후 실패했는데 전체를 재시도하면 앞 50개가 중복될 수 있습니다. 외부 시스템이 원자적 batch를 제공하지 않으면 멱등 키와 안전한 연속 성공 경계를 관리해야 합니다. 가장 큰 offset 한 개만 커밋해서는 안 되는 이유가 여기에도 있습니다.

역압력은 처리 가능한 속도에 맞춰 유입·소비를 조절하는 전략입니다. 큐가 무제한이면 순간적인 처리량은 좋아 보여도 메모리와 업무 지연이 계속 증가합니다. pause/resume, 제한된 작업 큐, DB 커넥션 수, 외부 API rate limit을 함께 설계합니다. pause 중에도 그룹 생존·poll 요구 조건을 지켜야 하며 Consumer 객체를 여러 작업 스레드에서 임의 호출하면 안 됩니다. 속도가 빨라졌는지 최종 업무 완료율과 가장 오래된 대기 이벤트의 나이로 판단합니다.

시간·보존·재처리 가능 기간을 함께 보기

레코드의 event timestamp, Broker 도착 시각, Consumer 처리 시각, DB 반영 시각은 서로 다를 수 있습니다. 이벤트 시간 기반 통계를 처리 시각으로 계산하면 장애 후 재처리한 과거 이벤트가 오늘 실적으로 잡힐 수 있습니다. 반대로 잘못된 미래 timestamp는 윈도우 진행이나 유효성 검사에 영향을 줄 수 있습니다. 시간의 출처·단위·타임존을 스키마와 함께 정합니다.

retention은 Consumer가 읽었는지와 무관한 로그 보관 정책입니다. 그룹이 오래 멈추면 커밋 위치가 이미 정리된 구간을 가리킬 수 있습니다. 이때 auto.offset.reset의 선택에 따라 뒤에서 재개하거나 오류를 노출할 수 있지만 사라진 이벤트를 되살려 주지는 않습니다. 업무 복구 목표가 14일인데 로그는 7일만 보관한다면 별도 아카이브·원본 재추출 전략이 필요합니다.

compaction은 시간순 사건 이력을 전부 보존하는 것과 다릅니다. 키별 최신 상태를 재구성하는 데 유용하지만 중간 변경 내역이 정리될 수 있습니다. null value tombstone은 삭제를 뜻하고, 삭제 표식을 뒤늦게 읽는 복구 Consumer가 놓치지 않도록 관련 보존·복구 기간을 함께 검토합니다. 키가 없는 이벤트에 compaction을 무심코 적용하는 것도 올바른 상태 모델이 아닙니다.

재처리 전에 출력 부작용을 확인합니다. 통계 테이블을 새로 만드는 작업과 실제 고객에게 알림을 다시 보내는 작업은 위험이 다릅니다. 별도 그룹·출력 토픽·shadow 테이블로 먼저 재생하고 eventId 집합과 결과 합계를 비교하는 방법이 유용합니다. 검증된 결과를 서비스에 반영하는 단계와 원본을 읽는 단계를 분리하면 재처리 오류가 실제 업무를 다시 오염시키는 위험을 줄일 수 있습니다.

장애 조사에서 계층별 증거를 모으는 방법

장애를 "Kafka가 느리다"로 시작하면 원인이 너무 넓습니다. 먼저 최초 이상 시각, 영향을 받은 토픽·파티션·그룹·인스턴스, 사용자 증상을 적습니다. 그다음 앱의 입력·처리·DB·커밋 구간 시간을 나눕니다. Producer Future 대기와 DB 커넥션 대기를 같은 한 개의 응답 시간으로만 남기면 어느 쪽이 막혔는지 알기 어렵습니다.

네트워크 계층에서는 bootstrap뿐 아니라 메타데이터가 알려 준 모든 주소에 대한 DNS·포트·TLS를 확인합니다. 인증 계층에서는 메커니즘과 principal을, 인가 계층에서는 Topic·Group·TransactionalId 등 자원을 구분합니다. 데이터 계층에서는 직렬화·스키마와 키·offset·timestamp를 봅니다. 처리 계층에서는 외부 API·DB 잠금·커넥션풀·스레드 큐를 봅니다. 서로 다른 계층의 오류를 무조건 같은 재시도 분기로 보내지 않습니다.

모니터링에는 Kafka lag와 최종 업무 지연을 같이 둡니다. 생성률이 5000/s이고 처리율이 4000/s면 backlog는 초당 약 1000 증가합니다. 처리율을 7000/s로 높이면 순감소는 2000/s입니다. 60만 backlog를 없애는 데 약 300초라는 계산은 입력률·처리율이 일정하고 파티션 편중이 없다는 가정입니다. 가정과 실제를 비교하면 증설이 효과를 냈는지 빨리 판단할 수 있습니다.

복구 종료 기준도 미리 정합니다. 프로세스 재시작 성공은 첫 단계입니다. 할당 안정, ISR 회복, lag/age 감소, 오류율 회복, DB eventId·합계 대조까지 끝나야 업무 복구로 판단할 수 있습니다. 재처리를 했다면 중복 알림·재고 이중 증가가 없는지 별도로 확인합니다. 로그에 비밀번호·토큰·원본 개인정보를 남기지 않으면서도 eventId·파티션·offset·traceId를 연결할 수 있도록 설계하세요.

실험에서 주장할 수 있는 범위를 정하기

실습이 통과했다고 운영 안전성이 모두 입증되는 것은 아닙니다. 단일 브로커에서 Producer·Consumer가 동작한 것은 기본 연결과 코드 경로를 확인한 것입니다. RF=3의 내구성·브로커 장애·네트워크 분리·가용영역 장애를 검증한 것이 아닙니다. TopologyTestDriver는 계산 의미를 빠르게 검증하지만 실제 분산 리밸런스나 ACL·EOS 장애 복구를 대신하지 않습니다.

실험 전에 가설과 관측값을 씁니다. 예를 들어 "ack 생략만으로 position이 멈추지 않는다"는 가설이라면 listener 호출 offset, position, committed를 같은 시간축에 기록합니다. 재시작 뒤 재수신 여부만 보면 프레임워크의 오류 처리·커밋 타이밍에 따른 다른 원인이 섞일 수 있습니다. 실험 변수 하나를 바꾸고 다른 조건을 유지해야 인과를 설명하기 쉽습니다.

성능 실험은 레코드 수뿐 아니라 평균·최대 바이트, 키 분포, 압축률, RF/minISR/acks, 브로커 수, Consumer 수, DB 처리 조건을 적습니다. 평균 latency가 줄어도 p99가 나빠질 수 있으며, Kafka 전송량이 늘어도 최종 DB 처리율이 그대로면 전체 업무는 빨라지지 않았습니다. 비용·오류율·복구 시간을 같이 기록해야 운영 선택이 됩니다.

마지막으로 결과를 세 칸으로 나눠 보고합니다. "실행해 관측한 사실", "공식문서가 정의한 동작", "아직 시험하지 않은 가정"입니다. 예제 코드가 보인다는 이유로 실제 실행까지 완료했다고 쓰지 않습니다. 실패 실험은 정확한 환경과 복구·정리 절차를 포함해 다시 수행할 수 있게 보관합니다. 이 구분은 면접에서도 자신의 경험과 이론을 정직하고 설득력 있게 설명하는 데 도움이 됩니다.

심화 면접 Q&A: 답변·경계·꼬리 질문

답을 접고 먼저 소리 내어 설명해 보세요. “항상”, “무조건”이라는 말을 썼다면 그 주장이 깨지는 반례를 같이 말해 봅니다. 첫 질문들은 이번 편 고유 쟁점이고 이어지는 질문들은 분산 처리의 공통 실패 경계를 확인합니다.

Connector RUNNING이면 데이터도 정상인가요?

답변: Task 실패, 입력 없음, 외부 시스템 대기, 처리 정체를 별도로 확인해야 합니다.

꼬리 질문과 해설: 최근 성공 시각·입출력 건수·DLQ·Task 상태를 함께 관찰합니다.

DLQ로 보내면 데이터 유실이 해결됐나요?

답변: 데이터 보관과 업무 반영 완료는 다릅니다. 재처리·대조가 필요합니다.

꼬리 질문과 해설: DLQ 보존 만료와 접근 권한까지 운영 책임으로 정해야 합니다.

“errors.tolerance=all이면 모든 Task 오류가 DLQ로 간다”라는 주장에 동의하나요?

답변: 지원되는 변환·처리 단계와 Connector별 예외를 구분해야 합니다. 외부 Sink 영구 장애까지 전부 건너뛴다고 가정하면 안 됩니다.

꼬리 질문과 해설: 이번 편 실습에서 이 주장을 가르는 관측값을 하나 선택하고, 정상·실패에서 각각 어떤 값이 나올지 예측하세요.

처리 성공과 커밋 성공 사이에 죽으면 어떤 일이 생기나요?

답변: DB 성공 후 offset 커밋 전에 죽으면 같은 레코드를 다시 받을 수 있습니다. 소비 멱등성이 필요한 구간입니다. 커밋부터 한 뒤 DB가 실패하면 반대로 누락 위험을 만듭니다. 두 순서를 시간선으로 그려 어느 결과가 영속 저장됐는지 구분합니다.

꼬리 질문과 해설: 한 DB 트랜잭션 안에서 eventId 처리 표식과 업무 변경을 함께 확정하는지, 커밋 실패 후 재수신에도 결과가 유지되는지 시험하세요.

한 파티션에서 병렬 처리한 가장 큰 offset을 커밋해도 되나요?

답변: 완료된 최대 offset과 연속 완료 경계는 다릅니다. 100이 실패하고 101이 성공했는데 102를 커밋하면 재시작에서 100을 건너뛸 수 있습니다. 파티션별 빈틈 없는 성공 경계가 필요합니다.

꼬리 질문과 해설: 멀티스레드 큐의 완료 추적, 리밸런스 시 in-flight 처리, 중복 실행 방어를 함께 설계해야 합니다.

새 그룹에 earliest를 주면 얼마나 오래된 데이터까지 읽나요?

답변: 현재 보존되어 있는 가장 이른 유효 위치부터입니다. 이미 retention이나 compaction으로 제거된 사건을 되살리지 않습니다. 기존 그룹에 유효한 커밋이 있다면 auto.offset.reset이 매번 그 커밋을 무시하지도 않습니다.

꼬리 질문과 해설: 원본 재추출·아카이브가 필요한 재해 복구 기간과 Kafka 보존 기간을 비교해 보세요.

같은 키면 모든 환경에서 영구적으로 같은 파티션인가요?

답변: 같은 파티셔닝 조건과 파티션 수에서 매핑됩니다. 파티션 수·파티셔너·직렬화된 키 바이트를 바꾸면 새 레코드의 위치가 달라질 수 있습니다. 서로 다른 언어 클라이언트의 기본 파티셔너도 확인해야 합니다.

꼬리 질문과 해설: 기존 파티션의 미처리 이벤트와 새 파티션 이벤트가 동시에 처리될 때 업무 순서가 어떻게 되는지 검증하세요.

한 번의 send나 poll이 한 번의 네트워크 왕복인가요?

답변: 클라이언트는 버퍼·배치·메타데이터 조회·재시도를 수행합니다. send는 비동기 전송 결과를 반환할 수 있고 poll은 내부에 이미 가져온 데이터를 돌려줄 수 있습니다. 메서드 호출 수로 요청 수를 단순 계산하면 안 됩니다.

꼬리 질문과 해설: 프로듀서 request rate·batch size와 Consumer fetch 지표를 함께 계측하여 실제 왕복을 확인하세요.

Timeout이 나면 무조건 같은 일을 다시 실행하면 되나요?

답변: 서버 적용 후 응답만 유실됐을 가능성이 있습니다. 일시 장애 재시도와 업무 부작용의 안전한 재실행은 별개입니다. 안정적인 eventId·멱등 키·사후 조회를 사용해 결과 불명 상태를 처리해야 합니다.

꼬리 질문과 해설: 알림·결제·재고 증가처럼 되돌리기 어려운 외부 부작용에 어떤 대조·보상 경로가 있는지 답해 보세요.

Kafka가 복제하면 별도 장애 복구 설계가 필요 없나요?

답변: 복제본 수와 장애 도메인, 쓰기 확인 조건, 보존 정책, 클라이언트 진행 위치를 함께 봐야 합니다. 같은 지역 전체가 장애 나거나 애플리케이션이 잘못 커밋한 문제는 복제만으로 해결되지 않습니다.

꼬리 질문과 해설: 데이터 손실 허용 범위 RPO와 서비스 재개 시간 RTO를 정하고 실제 장애 실험으로 측정해야 합니다.

오류를 catch하고 로그만 남기면 안전한가요?

답변: 프레임워크가 정상 완료로 해석하여 뒤 offset으로 진행할 수 있습니다. 오류를 삼키는 행위가 처리 정책을 바꿀 수 있으므로 재시도·정지·격리 중 어떤 경로인지 명시해야 합니다.

꼬리 질문과 해설: 격리를 성공으로 셀지, 업무 미완료로 셀지 정하고 DLQ 수와 최종 업무 성공 수를 따로 계측하세요.

성능을 높이려면 concurrency부터 올리면 되나요?

답변: 파티션 수·키 편중·외부 DB 풀·잠금·API 제한이 상한을 만들 수 있습니다. 병목이 DB라면 Consumer 증설이 더 많은 대기와 재시도를 만들 수 있습니다.

꼬리 질문과 해설: 증설 전후 최종 업무 완료율과 p99·오류율이 어떻게 변해야 가설이 맞는지 먼저 정하세요.

정확히 한 번 처리는 어떤 경계를 말해야 하나요?

답변: Kafka 내부의 입력 offset·출력·상태를 묶는 보장과 외부 DB·HTTP 부작용은 구분해야 합니다. 동일한 업무 이벤트를 별도 레코드로 두 번 생성하는 것은 프로토콜 재시도 중복과도 다릅니다.

꼬리 질문과 해설: 면접에서는 도구 이름만 말하지 말고 원자적으로 묶이는 자원과 남은 실패 구간을 함께 설명하세요.

가상 장애 시나리오와 실제 운영 경험을 어떻게 구별해 답하나요?

답변: 실제로 측정한 값·환경·내가 실행한 조치와 공식문서를 통해 이해한 설계를 구분합니다. 이 교재의 장애 예시는 재현을 위한 가상 사례이며 특정 기업의 실사례로 주장하지 않습니다.

꼬리 질문과 해설: 직접 실험했다면 버전, 입력 데이터, 실패 주입 지점, 관측값, 복구 결과를 남기면 근거 있는 경험으로 설명할 수 있습니다.

공식 기본값과 예제 설정이 다르면 무엇을 믿어야 하나요?

답변: 기본값은 해당 버전·컴포넌트 공식 설정표에서 확인하고 예제는 학습 의도로 명시한 override로 읽습니다. 브로커 4.3과 오래된 Java 클라이언트·Spring 기본값이 같다고 가정하면 안 됩니다.

꼬리 질문과 해설: 운영 적용 전 실제 dependency tree, effective config, 토픽 override를 확인하고 지원 조합에서 회귀 시험하세요.
