Connect 운영 REST와 실패 복구

도트 게임 속 스테이지를 진행하듯, 쉬운 비유부터 기술적인 흐름과 장애 대응을 함께 익혀봅시다. 비유의 한계를 기억하고 실제 용어를 직접 설명해 보세요.

1. Connector 상태

2. REST API

처음 듣는 사람을 위한 비유

운송 상황을 조회하는 관리 전화

정확한 개념과 내부 동작

Connect REST API는 Connector 생성·설정 조회·상태 조회 및 일부 운영 동작을 제공한다.

실무에서 생기는 문제

실습과 점검

테스트 토픽과 격리된 Kafka 클러스터에서 각각의 이벤트 Key, Partition, Offset, 처리 성공 여부를 기록하며 결과를 추적하세요. 상태를 사용하는 기능은 앱 재시작 시 복구 시간도 측정합니다. 운영 클러스터의 오프셋을 임의로 수정하거나 Topic을 삭제해서는 안 됩니다.

상세 학습 1. RUNNING 표시가 왜 충분하지 않을까?

Connect에는 Connector와 Task 각각의 상태가 있습니다.

Connector가 RUNNING이지만 일부 Task가 FAILED라면 전체 데이터 흐름을 신뢰할 수 없습니다.

REST의 `/connectors/{name}/status` 응답에서 Connector와 각 Task 상태를 따로 확인해야 합니다.

상세 학습 2. Task 실패에서 가장 먼저 볼 것

FAILED Task의 trace에 실제 예외가 남을 수 있어요. 인증 실패라면 외부 DB 권한을, 역직렬화 예외라면 Converter와 스키마를, Timeout이라면 외부 API·DB 응답 지연을 확인하세요. 원인을 해결하지 않고 Task만 재시작하는 방식은 같은 장애를 반복할 수 있습니다.

상세 학습 3. DLQ를 쓸 때 놓치는 위험

Sink 처리에서 특정 레코드를 DLQ에 격리할 수 있습니다.

하지만 원본 업무 이벤트를 DLQ로 보냈다는 것은 정상 업무 처리에 성공했다는 뜻이 아닙니다.

DLQ 건수, 원본 Topic/Partition/Offset, 오류 사유, 재처리 절차를 함께 운영해야 합니다.

상세 학습 4. Worker Rolling 배포

Worker가 세 대라면 한 대씩 종료하고 새 버전으로 기동할 수 있습니다.

하지만 Task 재할당과 재시작이 발생하면서 Source·Sink 처리에 지연이 생길 수 있습니다.

배포 중 Connector와 Task 상태, 오류율, Consumer Lag, 외부 DB 요청량이 함께 안정적인지 확인해야 합니다.

상세 학습 5. Connect REST 보호

Connect REST API는 관리 작업을 수행할 수 있어 외부 노출에 각별히 주의해야 합니다.

브로커 SASL 인증을 사용한다고 REST API의 접근 제어까지 자동으로 완성되는 것은 아닙니다.

사설 네트워크 제한, 인증·인가, 변경 감사 기록과 최소 권한을 별도로 고려해야 합니다.
