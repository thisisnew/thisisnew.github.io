시작 질문: String 다섯 개와 Hash 하나는 같은가

사용자 42의 이름, 지역, 등급을 Redis에 저장한다고 하자. user:42:name, user:42:region, user:42:tier 세 키로 나눌 수도 있고, user:42라는 Hash 하나의 세 필드로 묶을 수도 있다. 애플리케이션에서 보이는 정보는 비슷하지만 Redis 내부에서 필요한 사전 항목, 키 이름, 객체, 메모리 할당 횟수는 같지 않다. 이 차이를 이해하면 메모리를 줄일 수 있다. 그러나 너무 크게 묶으면 읽기 지연, 만료 단위, 샤딩, 장애 영향이 나빠질 수 있다.

이 장은 제공된 03장의 원리를 현대적인 확인 절차와 연결한다. 원문에는 과거 zipmap/ziplist 설정명과 “Hash 필드에는 만료를 걸 수 없다”는 역사적 설명이 있다. 이를 현재의 절대 명제로 외우면 안 된다. Redis 7.0 계열 이후의 Hash 압축 인코딩 설명에서는 listpack이 등장하며, 필드 만료는 Redis 7.4부터 HEXPIRE 등 별도 명령으로 제공된다. 구체적 지원 여부는 실행 서버의 COMMAND INFO HEXPIRE, 해당 버전 문서, 클라이언트 API로 확인한다. 공식 메모리 최적화, HEXPIRE, Redis 7.4 명령 기준

1. 논리 자료형과 물리 인코딩

논리 자료형은 사용자가 명령을 통해 보는 규칙이다. String은 바이트 문자열, Hash는 필드와 값의 집합, Set은 중복 없는 원소 집합, Sorted Set은 점수에 따라 정렬되는 원소 집합이다. 물리 인코딩은 그 규칙을 메모리에서 구현하는 실제 표현이다. 같은 Hash라도 작은 경우에는 조밀한 표현, 커지면 해시 테이블 기반 표현을 사용할 수 있다.

이를 도서관에 비유해 보자. “책을 제목으로 찾을 수 있다”는 것은 제공 기능이다. 책이 다섯 권이면 한 줄로 놓고 훑어도 빠르다. 수백만 권이면 색인이 필요하다. 기능은 같아도 내부 보관 방식은 달라진다. 비유의 한계는 Redis가 임의의 취향으로 서가를 고르지 않는다는 점이다. 자료형, 원소 수, 길이, 값의 형태, 설정, 버전이 정한 조건에 따라 인코딩이 결정된다.

TYPE key는 논리 자료형을 알려 준다. OBJECT ENCODING key는 현재 내부 표현을 알려 준다. MEMORY USAGE key는 해당 키의 메모리 비용을 관찰하는 도구다. 내부 인코딩 이름은 애플리케이션의 영구 계약이 아니다. 코드가 “반드시 listpack이어야 한다”는 전제로 동작하면 서버 업그레이드나 데이터 성장에 취약해진다. 애플리케이션의 정합성은 논리 명령의 의미에 기대고, 인코딩은 성능 진단에 사용한다. OBJECT ENCODING

2. 작은 자료구조에서 선형 탐색이 유리할 수 있는 이유

해시 테이블은 평균적으로 빠른 조회를 제공하지만 무료가 아니다. 버킷 배열, 엔트리, 포인터, 키와 값의 분리된 할당 등에 비용이 든다. 작은 필드 다섯 개를 저장하는데 이런 관리 구조를 넉넉히 만드는 것이 아까울 수 있다. 조밀한 인코딩은 필드와 값을 가까이 붙여 저장해 부가 비용을 줄인다.

CPU는 메모리를 한 바이트씩 무작위로 가져오는 단순 기계가 아니다. 캐시 라인 단위로 가까운 데이터를 함께 가져온다. 서로 가까이 있는 짧은 데이터들을 순서대로 읽으면, 포인터를 따라 여러 위치를 방문하는 것보다 실제 시간이 짧을 수 있다. 이것을 캐시 지역성의 이익이라고 이해하면 된다.

여기서 빅오 표기만으로 결론을 내리면 곤란하다. O(N)은 원소 수가 증가할 때 비용이 어떻게 커지는지 설명한다. N이 항상 아주 작도록 제한되면 선형 탐색의 실제 비용도 작을 수 있다. 반대로 임계값을 크게 늘려 N이 수만이 되면 “작은 자료구조 최적화”라는 전제가 깨진다. 연속 메모리에 중간 삽입이나 확장이 필요하면 데이터를 이동하거나 다시 할당하는 비용도 생길 수 있다.

따라서 “listpack이 해시 테이블보다 무조건 빠르다”도, “O(N)이니까 반드시 느리다”도 아니다. 자료 크기와 접근 패턴에 따라 CPU와 메모리를 교환하는 설계다. 이 원리는 Redis 외에도 작은 배열 기반 맵, 인라인 저장, 구조체 압축에서 반복된다.

3. 임계값과 인코딩 전환

공식 문서는 Hash, Sorted Set, Set 등의 작은 자료구조에 대해 원소 수와 값 길이를 기준으로 특수 인코딩을 선택하는 설정을 설명한다. 예를 들어 설치 버전이 지원한다면 hash-max-listpack-entries, hash-max-listpack-value를 조회할 수 있다. 과거 ziplist 이름이 남은 문서를 그대로 복사하지 말고 실행 중인 서버의 값을 읽는다.

CONFIG GET hash-max-listpack-entries
CONFIG GET hash-max-listpack-value

중요한 점은 원소 개수만 세면 안 된다는 것이다. 필드가 두 개뿐이어도 하나의 길이가 임계값을 넘으면 다른 표현으로 바뀔 수 있다. 길이는 사용자에게 보이는 글자 수가 아니라 인코딩된 바이트 수와 관련된다. 한글 세 글자와 ASCII 세 글자는 UTF-8에서 같은 바이트 크기가 아니다. Java의 String.length()도 UTF-8 바이트 길이와 같지 않다.

한 번 임계값을 넘어 전환된 키를 다시 줄였을 때 원래 인코딩으로 즉시 돌아올 것이라고 가정해서도 안 된다. 전환 방향과 재압축 여부는 자료형·버전·작업 경로에 따라 다를 수 있다. 중요한 것은 프로그램이 자동 복귀를 기대하지 않고 실제 OBJECT ENCODING으로 확인하는 것이다.

전환은 서비스 요청 경로의 비용이 될 수 있다. 평소에는 짧은 필드를 저장하다가 특정 사용자에게 매우 긴 소개 글을 넣는 순간 자료구조가 커질 수 있다. 메모리 그래프가 계단처럼 증가하면 “누수”만 의심하지 말고 데이터 분포와 인코딩 경계를 조사한다. 임계값을 올려 전환을 피하는 것은 다른 요청의 탐색과 이동 비용을 키우는 선택이므로, p95/p99와 최대 객체 크기를 함께 시험한다.

4. 모델 A: 속성별 String

SET user:42:name "Mina"
SET user:42:region "Seoul"
SET user:42:tier "silver"

이 모델은 각 속성에 독립된 TTL, 접근 제어 패턴, 개별 삭제와 교체 단위를 적용하기 쉽다. 필요한 항목만 직관적으로 읽고 쓸 수 있다. 그러나 사용자 ID와 접두사가 여러 키에 반복되고, 각 키마다 최상위 사전과 관리 비용이 생긴다. 원격 호출을 세 번 하면 네트워크 왕복도 세 번 발생할 수 있다. 파이프라이닝이나 적절한 다중 키 명령으로 왕복을 줄일 수 있지만, 메모리 표현 자체가 자동으로 합쳐지지는 않는다.

운영에서는 키 패턴을 기준으로 관측하기 쉬운 장점도 있다. 다만 속성이 매우 많으면 키 수가 급격히 늘고 SCAN 기반 관리 작업의 총 비용도 커진다. 이 모델이 나쁘다는 뜻이 아니라, 독립 수명과 관리 단위라는 기능에 비용을 지불하는 것이다.

5. 모델 B: 사용자별 Hash

HSET user:42 name "Mina" region "Seoul" tier "silver"
HGET user:42 name
HMGET user:42 name tier

사용자라는 객체의 속성들을 한 키 아래에 묶는다. 작은 Hash가 조밀한 인코딩을 유지하면 관리 비용을 줄일 수 있다. 일부 속성만 바꿀 때 JSON 전체를 읽고 수정하고 다시 저장할 필요도 없다. 한 명의 사용자라는 자연스러운 경계가 있으므로 무한히 커지는 전역 Hash보다 크기를 예측하기 쉽다.

단점도 분명하다. 키 단위 TTL은 사용자 객체 전체에 적용된다. 지원 버전에서 필드별 만료를 사용할 수 있어도 클라이언트 지원, 만료 메타데이터 비용, 명령 의미를 따로 확인해야 한다. 키 단위 eviction, Cluster에서의 키 배치, 큰 Hash 응답 비용은 여전히 남는다. 필드 TTL이 생겼다고 Hash가 독립 키의 모든 기능과 운영 경계를 그대로 대체하는 것은 아니다.

또한 HGETALL은 모든 필드와 값을 반환한다. 지금은 다섯 필드라 괜찮아도 미래에 수만 필드가 되면 응답 크기가 커진다. 필요한 필드가 정해져 있으면 HMGET을 고려하고, 전체 순회가 필요하면 데이터 규모와 일관성 요구에 맞는 순회 전략을 택한다. “Hash를 썼으니 최적화가 끝났다”가 아니라 요청당 처리량까지 계산한다.

6. 모델 C: 작은 객체 여러 개를 버킷 Hash에 묶기

원문은 숫자 ID를 접두사와 끝자리로 나누어 여러 객체를 한 Hash에 담는 아이디어를 소개한다. 예를 들어 ID 1234를 버킷 object:12, 필드 34로 표현한다. 균등한 숫자 ID와 작은 값이라면 최상위 키 수를 줄일 수 있다. 다만 이는 단순한 저장 형식 변경이 아니라 애플리케이션의 주소 지정 규칙 변경이다.

원래 주소: object:1234
새 주소:   key=object:12, field=34

주소 변환은 모든 읽기와 쓰기에서 같은 규칙을 써야 한다. 음수, 앞자리 0, 문자열 ID, ID 범위 변경도 정의해야 한다. “끝 두 글자를 자른다”는 구현이 숫자 나눗셈과 항상 같은 의미는 아니다. 여러 언어 서비스가 공유한다면 테스트 벡터를 만들어 동일 입력이 동일 키와 필드로 변환되는지 검증한다.

버킷을 너무 크게 만들면 hot key가 된다. 특정 버킷에 요청이 집중되면 Cluster의 여러 노드가 있어도 그 키의 작업은 하나의 배치 경계에 집중된다. 독립 객체들이 eviction이나 키 삭제의 운명을 공유할 수도 있다. 관측과 이관도 복잡해진다. 따라서 수십만 독립 키를 하나의 거대한 Hash로 바꾸는 것은 메모리 절약보다 큰 운영 비용을 만들 수 있다.

원문의 과거 측정값을 “우리 서비스도 몇 배 절약된다”는 약속으로 쓰지 않는다. Redis 버전, 값 길이, allocator, 실제 분포가 다르면 비율은 달라진다. 자연스러운 객체 경계의 Hash부터 검토하고, 인위적인 버킷화는 비용 절약이 실제로 필요한 경우에만 비교 실험으로 선택한다.

7. bitmap: 참/거짓을 한 비트로 표현하기

사용자별 출석 여부를 문자열 true로 저장하는 대신 비트 하나로 나타낼 수 있다. bitmap은 별도 논리 자료형이라기보다 String의 비트를 다루는 방식이다. SETBIT attendance:day:2026-10-21 42 1은 해당 비트 위치를 1로 만든다. GETBIT은 그 위치의 값을 읽고, BITCOUNT는 설정된 비트 수를 셀 수 있다.

밀집된 ID 0부터 9,999,999까지 천만 명을 나타내면 순수 비트 수는 천만 비트이고, 8로 나누면 약 125만 바이트다. 여기에 키와 문자열 관리 비용이 더해진다. 이 계산은 저장 구조를 선택하기 전 가능한 절감 폭을 감 잡는 데 도움이 된다.

하지만 희소한 ID에는 주의한다. 사용자 한 명의 ID가 10억이라고 그 위치를 바로 설정하면 그 위치까지 표현할 문자열 공간이 필요해질 수 있다. 실제 사용자가 두 명뿐이어도 최대 offset이 크면 메모리가 커진다. 큰 offset을 처음 확장하는 명령은 할당과 초기화 비용도 유발할 수 있다. 반드시 ID 범위와 밀도를 검토하고, 날짜나 범위별로 나누는 전략과 최대 크기를 정한다.

bitmap은 사용자의 이름이나 여러 속성을 저장하지 않는다. 무엇이 1인지의 의미와 ID 매핑은 애플리케이션이 유지해야 한다. 사용자 ID를 재사용하면 옛 비트가 다른 사용자의 기록처럼 보일 수 있다. 압축은 의미를 없애는 마법이 아니라 표현 규칙을 더 엄격하게 만드는 선택이다.

8. Java 직렬화가 메모리 최적화를 무효화하는 경우

Redis가 작은 값에 최적화되어 있어도 클라이언트가 메타데이터가 많은 직렬화 형식으로 저장하면 바이트가 커진다. 같은 42를 UTF-8 문자열로 저장하는 것과 클래스 정보를 포함한 직렬화 결과로 저장하는 것은 다르다. 읽는 쪽의 serializer가 쓰는 쪽과 다르면 redis-cli에서 보이는 키와 애플리케이션이 찾는 키가 달라 보일 수도 있다.

String text = "서울";
int codeUnits = text.length();
int utf8Bytes = text.getBytes(StandardCharsets.UTF_8).length;
// 두 값은 같은 개념이 아니다. 저장 비용은 실제 전송 바이트와 연관된다.

Map<String, String> fields = Map.of(
    "name", "Mina",
    "region", "Seoul",
    "tier", "silver"
);
redisTemplate.opsForHash().putAll("lab:user:42", fields);

이 코드는 문자열 기반 템플릿 구성을 전제로 한 개념 예시다. 실제 Spring Data Redis 설정에서는 키, 값, Hash 필드, Hash 값의 직렬화기를 구별한다. 프레임워크 기본값을 추측하지 말고 구성과 저장된 바이트를 확인한다. 운영 중 serializer를 바꾸면 과거 데이터와 새 데이터가 섞일 수 있으므로 새 접두사, 읽기 호환, 백필, 전환 기간을 포함한 마이그레이션 계획이 필요하다.

JSON은 디버깅과 언어 간 호환에 유리할 수 있지만 필드 이름과 문법 바이트가 반복된다. 압축은 크기를 줄여도 CPU와 작은 부분 갱신을 어렵게 한다. 직렬화 선택은 메모리 숫자뿐 아니라 호환성, 관측성, 배포 순서까지 함께 비교해야 한다.

9. 격리 실습 A: 작은 Hash의 인코딩 경계를 직접 보기

포트 16381의 일회용 인스턴스를 만든다. 운영 서버의 임계값을 바꾸지 않는다. 아래 설정명은 listpack 지원 버전을 전제로 하므로 먼저 버전을 확인한다. 해당 설정이 없으면 자신의 버전 문서를 따라 실습을 조정하고, 모르는 설정을 억지로 적용하지 않는다.

LAB=$(mktemp -d /tmp/redis-encoding-lab.XXXXXX)
redis-server --bind 127.0.0.1 --port 16381 --protected-mode yes \
  --daemonize no --dir "$LAB" --save "" --appendonly no \
  --maxmemory 64mb --maxmemory-policy noeviction

다른 터미널에서 다음을 실행한다.

redis-cli -h 127.0.0.1 -p 16381 INFO server
redis-cli -h 127.0.0.1 -p 16381 CONFIG GET hash-max-listpack-entries
redis-cli -h 127.0.0.1 -p 16381 CONFIG GET hash-max-listpack-value
redis-cli -h 127.0.0.1 -p 16381 CONFIG SET hash-max-listpack-entries 4
redis-cli -h 127.0.0.1 -p 16381 CONFIG SET hash-max-listpack-value 16
redis-cli -h 127.0.0.1 -p 16381 HSET lab:small a 1 b 2 c 3
redis-cli -h 127.0.0.1 -p 16381 TYPE lab:small
redis-cli -h 127.0.0.1 -p 16381 OBJECT ENCODING lab:small
redis-cli -h 127.0.0.1 -p 16381 MEMORY USAGE lab:small
redis-cli -h 127.0.0.1 -p 16381 HSET lab:small d 4 e 5
redis-cli -h 127.0.0.1 -p 16381 OBJECT ENCODING lab:small
redis-cli -h 127.0.0.1 -p 16381 MEMORY USAGE lab:small

예상 관찰은 논리 자료형은 계속 Hash지만 임계값을 넘긴 뒤 내부 표현과 메모리 비용이 달라질 수 있다는 것이다. listpack 경로를 사용하는 해당 버전에서는 처음 listpack, 이후 hashtable과 같은 변화가 관찰될 수 있다. 실제 이름과 바이트 수를 기록하고 버전과 함께 해석한다. 응답을 그대로 교재의 고정 성능 보장으로 받아들이지 않는다.

이번에는 필드 수 대신 값 길이를 바꾼다.

redis-cli -h 127.0.0.1 -p 16381 HSET lab:long a short
redis-cli -h 127.0.0.1 -p 16381 OBJECT ENCODING lab:long
redis-cli -h 127.0.0.1 -p 16381 HSET lab:long b 12345678901234567
redis-cli -h 127.0.0.1 -p 16381 OBJECT ENCODING lab:long

왜 17자 ASCII를 사용했는가? 이 실습에서 길이 임계값을 16으로 설정했으므로 경계 넘김을 명확히 하려는 것이다. 원소 수와 길이 중 어느 조건이 원인인지 분리했다. 이런 식으로 한 변수씩 바꾸어야 관찰 결과를 설명할 수 있다.

10. 격리 실습 B: 표현의 비용과 기능을 함께 비교

같은 전용 인스턴스에서 다음 데이터를 만든다. 앞 실습의 작은 임계값이 남아 있으므로 비교 전에 원래 조회해 둔 값으로 복원하거나 새 인스턴스를 사용한다. 다른 설정이 섞이면 공정한 비교가 아니다.

SET lab:string:user:1:name Mina
SET lab:string:user:1:region Seoul
SET lab:string:user:1:tier silver
HSET lab:hash:user:1 name Mina region Seoul tier silver
MEMORY USAGE lab:string:user:1:name
MEMORY USAGE lab:string:user:1:region
MEMORY USAGE lab:string:user:1:tier
MEMORY USAGE lab:hash:user:1
SETBIT lab:attendance 42 1
SETBIT lab:attendance 100 1
BITCOUNT lab:attendance
STRLEN lab:attendance

위 Redis 명령은 반드시 redis-cli -h 127.0.0.1 -p 16381로 접속한 실습 세션에 입력한다. String 세 개의 비용 합과 Hash 하나를 비교하되, 이 작은 표본만으로 서비스 전체 절감률을 확정하지 않는다. 전체 사용량에는 사전 용량 확장과 고정 비용이 있고, MEMORY USAGE의 중첩 자료구조 추정은 샘플링 설정의 영향을 받을 수 있다.

bitmap 예시는 아주 작은 offset만 사용해 안전하게 구조를 관찰한다. BITCOUNT는 두 비트가 켜진 상황에서 2를 기대하고, STRLEN은 가장 큰 offset까지 담는 바이트 길이를 보여 준다. 실제 사용자 ID를 무작위로 거대한 offset에 대입하는 실험은 하지 않는다.

비교표에는 메모리 외에도 호출 수, 읽는 바이트, TTL 단위, 최대 객체 크기, Cluster 배치 단위, 장애 시 영향 범위를 적는다. 메모리 20%를 아끼지만 한 키가 수백 MiB가 되어 전송과 이관이 어려워진다면 성공이라고 부르기 어렵다. 실습 종료는 자신이 만든 인스턴스에만 SHUTDOWN NOSAVE를 보낸다.

11. 운영 사고: 어느 날 특정 사용자만 느려졌다

대부분의 사용자 Hash는 필드 10개와 짧은 값으로 이루어져 있었다. 그런데 일부 사용자에게 “최근 활동 전체”를 필드로 계속 추가했다. 사용자별 크기 상한이 없어서 몇 개의 Hash만 거대해졌다고 하자. 이 경우 평균 키 크기와 평균 요청 지연은 괜찮아도 특정 사용자 요청에서 큰 응답과 긴 처리 시간이 생길 수 있다.

진단 순서는 느린 명령과 키 유형, 필드 수, 반환 크기, 인코딩, 메모리 비용을 함께 보는 것이다. 운영에서 모든 키에 비싼 전체 조회를 반복하면 진단이 새로운 부하가 된다. 승인된 샘플링과 낮은 빈도의 관측으로 접근한다. 사용자 개인정보를 그대로 로그에 출력하지 않고 키 식별자와 크기 메타데이터만으로 조사할 수 있는지도 검토한다.

해결은 listpack 임계값을 올리는 것이 아니라 데이터 경계를 다시 잡는 것일 수 있다. 사용자 기본 프로필과 활동 이력을 나누고, 이력에 개수와 기간 상한을 두며, 페이지 단위 읽기를 설계한다. 자료형 최적화는 업무 모델을 대신하지 않는다. “항상 추가만 하는 필드”가 등장했다면 이미 무한 성장 구조인지 질문해야 한다.

면접 질문과 상세 답변

1. Redis Hash와 해시 테이블은 같은 말인가요?

아니다. Redis Hash는 필드와 값을 제공하는 논리 자료형이고, 해시 테이블은 가능한 내부 구현 중 하나다. 작은 Hash는 조밀한 인코딩을 사용할 수 있다. 사용자는 HGET/HSET 의미를 기준으로 코드를 작성하고, 성능 분석에서 OBJECT ENCODING을 확인한다. 논리 인터페이스와 내부 표현을 분리하면 인코딩 변경이 왜 애플리케이션 기능을 바꾸지 않으면서 메모리와 지연을 바꿀 수 있는지 설명할 수 있다.

2. 작은 Hash가 여러 String 키보다 메모리를 덜 쓰는 이유는요?

최상위 키마다 필요한 이름, 사전 항목, 객체 관리 비용을 여러 필드가 공유할 수 있고, 작은 자료구조에서 조밀한 표현을 사용할 수 있기 때문이다. 필드와 값을 가까이 담아 포인터와 개별 할당 비용을 줄일 수도 있다. 다만 값 길이가 크거나 필드 수가 임계값을 넘으면 이익이 달라진다. 정확한 절감률은 실제 버전과 데이터 분포로 측정해야 하며 과거 벤치마크 비율을 그대로 약속해서는 안 된다.

3. 선형 탐색을 쓰는 구조가 왜 빠를 수 있나요?

원소 수가 작게 제한되어 있으면 실제 비교 횟수가 적고, 연속된 메모리를 읽는 지역성 덕분에 CPU 캐시를 잘 활용할 수 있다. 반면 해시 테이블은 평균 O(1)이라도 해시 계산과 포인터 접근 등의 상수 비용이 있다. 그러나 임계값을 크게 올리면 선형 탐색과 데이터 이동 비용이 커진다. 빅오와 실제 규모, 캐시 지역성을 함께 설명해야 한다.

4. listpack 임계값을 크게 올리면 언제나 좋은가요?

아니다. 메모리 이익을 얻는 대신 조회, 삽입, 확장, 전환 비용과 지연 꼬리가 커질 수 있다. 특히 큰 객체가 특정 요청에서 갑자기 일반 인코딩으로 변환되는 경우를 시험해야 한다. 평균 처리량만 비교하지 말고 p99, 최대 명령 시간, 객체 크기 분포를 확인한다. 운영 전체 설정을 바꾸기 전에 격리 환경에서 실제 자료 분포로 비교하는 것이 순서다.

5. Hash 필드에는 TTL을 줄 수 없다는 설명은 맞나요?

모든 버전에 통하는 설명은 아니다. 과거에는 키 단위 만료 중심으로 설명했지만 지원 버전에는 HEXPIRE 같은 필드 만료 명령이 있다. 실행 서버와 클라이언트 라이브러리의 지원 여부를 확인해야 한다. 필드 만료가 있어도 키 단위 eviction, 샤딩 위치, 큰 Hash의 응답 비용은 별개다. 새 기능 하나가 독립 키와 Hash의 모든 차이를 없애지는 않는다.

6. 사용자별 boolean에 bitmap을 쓰면 어떤 위험이 있나요?

ID가 밀집되어 있고 최대 범위가 예측 가능하면 효율적이지만, 희소한 큰 ID를 offset으로 쓰면 큰 문자열을 확장해야 할 수 있다. ID 재사용과 매핑 변경도 과거 비트의 의미를 바꿀 수 있다. 날짜나 ID 구간별 분할, 최대 offset 검증, 보존 기간을 설계해야 한다. 비트 하나의 비용만 보지 말고 가장 큰 주소와 의미 매핑의 수명을 함께 본다.

7. 메모리 최적화를 위해 모든 데이터를 하나의 Hash에 넣으면 안 되나요?

한 키에 부하와 수명이 모여 hot key와 big key를 만들 수 있다. Cluster에서도 한 키 내부의 필드를 자동으로 여러 슬롯에 분산하지 않는다. 전체 조회, 이관, 삭제, eviction의 영향 범위도 커진다. 자연스러운 업무 객체 경계나 제한된 버킷을 사용하고 최대 크기를 명시해야 한다. 메모리 절감보다 가용성과 예측 가능한 지연이 더 중요한 경우가 많다.

8. Java에서 보이는 문자열 길이로 Redis 메모리를 계산해도 되나요?

정확하지 않다. Java String 길이, UTF-8 전송 바이트, serializer가 추가한 메타데이터, Redis 내부 관리 비용이 서로 다르다. 실제 serializer를 사용한 바이트 크기와 MEMORY USAGE, 전체 INFO memory를 함께 측정한다. 직렬화 변경은 기존 데이터 호환성 문제를 만들 수 있으므로 새 접두사나 단계적 읽기 전환 같은 마이그레이션 전략이 필요하다.

공식 자료와 한 문장 정리

  • Memory optimization: 작은 자료구조 최적화의 원리와 버전별 설정.
  • OBJECT ENCODING: 내부 표현 관찰.
  • MEMORY USAGE: 키 비용과 샘플링 의미.
  • HEXPIRE: 지원 버전의 필드 만료.
  • SETBIT: bitmap의 offset과 할당 비용.

좋은 모델은 가장 적은 바이트만 쓰는 모델이 아니라, 수명·조회·증가 상한·분산 경계를 유지하면서 필요한 만큼만 쓰는 모델이다.
