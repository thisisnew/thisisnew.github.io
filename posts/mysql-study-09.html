옵티마이저: 통계·조인 순서·힌트가 계획을 만드는 과정

읽는 방법

비유로 개념을 잡고 SQL을 실행하기 전 결과를 예상해 보세요. 이번 개정에서는 단계별 동작 추적·비교표·꼬리 질문을 전편에 추가했습니다. 본문의 수치 예시는 설명용이고, 실행 환경에 따라 달라지는 값은 따로 표시했습니다. 기준은 MySQL 8.0·InnoDB, 재현용 서버는 8.0.36입니다. 처음 시작한다면 1편의 서버 준비만 먼저 진행하면 됩니다.

전체 학습 지도·검증 범위

1. SQL은 목적지, 실행 계획은 경로다

‘창고 3의 미완료 주문을 찾아라’는 무엇을 원하는지 설명하지만, 어떤 자료를 먼저 읽을지는 모두 지정하지 않습니다. 내비게이션이 목적지를 받아 여러 길을 비교하듯 옵티마이저는 가능한 실행 방법을 비교합니다. 가장 적은 비용이 예상되는 경로를 고르지만 미래의 실제 실행시간을 정확히 아는 것은 아닙니다. 통계와 비용 모델로 추정합니다.

통계가 어긋나면 좋은 기능을 가진 옵티마이저도 나쁜 결정을 할 수 있습니다. 도로에 차가 거의 없다고 알고 있는데 실제로는 출퇴근 정체라면 경로 선택이 틀어지는 것과 같습니다. 데이터 분포·파라미터·테이블 크기·사용 가능한 인덱스를 함께 보아야 합니다.

2. 비용은 초 단위 시간이 아니다

EXPLAIN에 표시되는 cost는 모델상의 비교 값입니다. cost=100이 100ms라는 뜻이 아닙니다. 페이지 읽기, 행 평가, 인덱스 접근 등 예상 작업량을 반영하며 실제 장비와 캐시·동시 부하에서는 오차가 생깁니다. 추정 rows도 실제 행 수와 다를 수 있습니다. 옵티마이저를 평가할 때는 추정과 실제가 어느 단계에서 벌어졌는지 찾습니다.

통계의 카디널리티는 구분되는 값의 개수 추정과 관련됩니다. 예를 들어 상태가 두 종류라고 해서 두 상태가 50%씩 있다는 뜻은 아닙니다. DONE 99.9%, WAITING 0.1%일 수 있습니다. 또 창고와 상태가 강하게 연관되면 열 하나씩의 분포만으로 조합의 선택도를 정확히 알기 어렵습니다. 히스토그램이 모든 열 간 상관관계를 해결한다고 생각하면 안 됩니다.

3. 조인 순서가 반복 횟수를 바꾼다

창고 테이블 100행과 주문 테이블 1천만 행을 조인한다고 합시다. 대상 창고가 1개뿐이라면 창고를 먼저 한 행으로 줄인 뒤 그 창고의 주문을 찾는 경로가 유리할 수 있습니다. 반대로 매우 희귀한 주문 조건으로 5건만 남는다면 주문부터 시작하는 것이 유리할 수 있습니다. 원래 테이블이 작은 쪽이 무조건 먼저라는 규칙은 없습니다. 조건을 적용한 뒤의 크기와 다음 단계의 접근 비용이 중요합니다.

Nested loop는 바깥 결과 한 행마다 안쪽을 찾는 구조입니다. 바깥이 10행이고 안쪽 인덱스 조회가 한 번에 3행이면 작은 작업일 수 있습니다. 바깥이 100만 행이고 매번 안쪽 전체를 스캔하면 폭발적으로 커집니다. 코드의 이중 for문을 떠올리되 안쪽에서 전체 순회하는지 인덱스로 좁히는지 구분하세요.

Hash join은 한 입력으로 해시 구조를 만들고 다른 입력을 대조하는 방식입니다. 적절한 동등 조인에서 인덱스 없이도 반복 전체 스캔을 줄일 수 있습니다. 메모리 사용과 디스크 spill 비용이 있고 언제나 더 빠른 것은 아닙니다. MySQL 8.0.18에 도입되었고 8.0.20 전후로 지원 경로가 확장되었으므로 오래된 ‘MySQL은 nested loop만 있다’는 설명을 그대로 쓰면 안 됩니다.

4. 실습: 조건을 바꾸며 조인의 입력 크기 보기

CREATE DATABASE IF NOT EXISTS mysql_school;
USE mysql_school;
DROP TABLE IF EXISTS join_order_demo;
DROP TABLE IF EXISTS join_wh_demo;
CREATE TABLE join_wh_demo (
 id INT PRIMARY KEY, name VARCHAR(30) NOT NULL
) ENGINE=InnoDB;
CREATE TABLE join_order_demo (
 id INT PRIMARY KEY, warehouse_id INT NOT NULL,
 status VARCHAR(16) NOT NULL,
 KEY ix_ws(warehouse_id,status)
) ENGINE=InnoDB;
INSERT INTO join_wh_demo VALUES(0,'서울'),(1,'부산'),(2,'대전');
INSERT INTO join_order_demo
WITH RECURSIVE seq AS (
 SELECT 1 n UNION ALL SELECT n+1 FROM seq WHERE n<1000
)
SELECT n,MOD(n,3),IF(MOD(n,100)=0,'WAITING','DONE') FROM seq;
ANALYZE TABLE join_wh_demo, join_order_demo;
EXPLAIN ANALYZE
SELECT w.name,o.id FROM join_wh_demo w
JOIN join_order_demo o ON o.warehouse_id=w.id
WHERE w.id=1 AND o.status='WAITING';

WAITING은 id가 100의 배수인 10행입니다. 그중 warehouse_id=1인 것은 100,400,700,1000으로 네 행입니다. 결과 개수는 4로 검증할 수 있지만 실행 계획의 시간·비용·표현은 버전과 환경에 따라 달라집니다. 이제 w.id 조건을 제거하거나 status를 DONE으로 바꾸고 읽은 행 수와 loops를 비교합니다. 이것이 대표 파라미터가 중요한 이유입니다.

5. 통계 갱신과 히스토그램을 구분하기

ANALYZE TABLE join_order_demo;
ANALYZE TABLE join_order_demo
  UPDATE HISTOGRAM ON status WITH 16 BUCKETS;
SELECT SCHEMA_NAME,TABLE_NAME,COLUMN_NAME,HISTOGRAM
FROM information_schema.COLUMN_STATISTICS
WHERE SCHEMA_NAME='mysql_school'
  AND TABLE_NAME='join_order_demo';
-- 실습 후 히스토그램만 제거
ANALYZE TABLE join_order_demo DROP HISTOGRAM ON status;

일반 ANALYZE TABLE과 히스토그램 생성은 같은 명령 이름을 공유하지만 작업이 다릅니다. 히스토그램은 값 분포를 버킷으로 표현합니다. 인덱스가 아니므로 그것만으로 행을 찾아가는 새 경로가 생기지는 않습니다. 추정에 도움을 주는 정보입니다. 인덱스 통계 등 다른 추정 경로가 우선 사용되어 계획이 그대로일 수도 있습니다.

대량 적재나 삭제 후 계획이 바뀌었다면 통계가 원인 후보입니다. 하지만 운영에서 모든 테이블에 ANALYZE를 일괄 실행하기 전에 비용과 잠금 영향, 대상 버전, 변경될 계획을 확인합니다. 통계를 최신으로 만드는 것이 언제나 모든 쿼리를 더 빠르게 한다는 보장도 없습니다.

6. 서브쿼리·CTE는 ‘임시 테이블을 꼭 만든다’는 뜻이 아니다

CTE는 WITH로 이름을 붙인 쿼리 표현입니다. 읽기 좋게 작성할 수 있지만 문법만으로 실행 방식이 고정되지 않습니다. 옵티마이저는 조건에 따라 바깥 쿼리에 합치거나(materialization 없이 merge), 중간 결과를 물질화할 수 있습니다. 서브쿼리도 semijoin 등으로 바뀔 수 있습니다. ‘WITH는 항상 빠르다’나 ‘서브쿼리는 무조건 느리다’는 규칙을 버리고 실제 계획을 봅니다.

예를 들어 주문이 하나라도 있는 창고를 찾는 질문은 주문의 모든 행을 반환하는 조인과 의미가 다릅니다. EXISTS로 존재 여부를 표현하면 최적화 기회도 달라질 수 있습니다. 먼저 동일한 결과를 요구하는 SQL끼리 비교해야 합니다. 중복 행을 없애는 비용이나 NULL 의미가 바뀌었다면 같은 문제를 비교한 것이 아닙니다.

7. 힌트는 임시 통제 수단이지 이유를 대신하지 않는다

EXPLAIN
SELECT /*+ JOIN_ORDER(w,o) */ w.name,o.id
FROM join_wh_demo w
JOIN join_order_demo o ON o.warehouse_id=w.id
WHERE o.status='WAITING';
SHOW WARNINGS;

힌트는 인식되지 않거나 적용할 수 없으면 무시될 수 있습니다. SQL이 성공했다고 힌트가 반영된 것은 아닙니다. 바로 SHOW WARNINGS와 계획을 확인합니다. 적용되더라도 데이터가 늘거나 분포가 바뀌면 과거의 좋은 선택이 나쁜 선택이 될 수 있습니다. 힌트를 넣을 때는 이유·대표 파라미터·성능 증거·재검토 조건을 남깁니다.

옵티마이저는 내비게이션처럼 예상 비용으로 경로를 고른다

목적지까지 가는 길이 세 개라면 가장 짧은 거리만으로 고르지 않습니다. 도로 폭, 신호, 예상 정체를 함께 봅니다. DB도 인덱스가 있다는 이유만으로 선택하지 않습니다. 후보 행 수, 본문 접근, 정렬, 조인 반복, 중간 결과 같은 비용을 추정해 비교합니다. 실제 실행 전에 판단하므로 예상과 실제가 다를 수 있습니다.

비용 값은 일반적으로 밀리초를 그대로 의미하지 않습니다. 옵티마이저 내부 모델로 경로를 비교하기 위한 단위입니다. cost=100이 cost=50보다 정확히 두 배 오래 걸린다는 뜻은 아닙니다. 서버의 캐시 상태와 동시 부하까지 완벽히 반영한 예언도 아닙니다. 계획의 이유를 설명할 단서로 사용하고 실측으로 확인합니다.

카디널리티와 선택도: 종류 수와 남는 비율을 구분하기

상태 값이 WAITING·DONE 두 종류라면 카디널리티는 낮습니다. 하지만 WAITING이 100만 행 중 1,000개라면 그 조건은 전체의 0.1%만 남깁니다. DONE은 99.9%를 남깁니다. 값 종류가 두 개라는 사실만으로 각 값이 절반씩 있다고 판단하면 큰 오차가 생깁니다.

인덱스 통계는 데이터를 매번 전부 세지 않고 표본을 사용해 추정할 수 있습니다. 표본과 실제 분포가 다르면 추정이 틀릴 수 있습니다. 히스토그램은 열 값의 분포를 더 자세히 표현할 수 있지만 새 검색 경로를 만드는 인덱스는 아닙니다. 또한 단일 열 히스토그램이 여러 열의 상관관계를 완벽히 알려 주는 것도 아닙니다.

예를 들어 창고=0이 20%, WAITING이 10%라면 두 조건을 독립이라고 가정할 때 2%를 예상할 수 있습니다. 하지만 WAITING이 전부 창고 0에 있으면 실제로는 10%입니다. “각 열의 통계를 다 가지고 있으니 조합도 정확하다”는 생각이 틀리는 사례입니다. 앞의 복합 인덱스 실습이 이 편향을 의도적으로 포함한 이유입니다.

조인 순서를 숫자로 바꾸면 작은 실수가 크게 보인다

입고 요청 100만 건과 창고 10개가 있다고 합시다. 요청 테이블에서 조건으로 20건을 먼저 줄이고 각 요청의 창고 PK를 찾으면 약 20번의 작은 조회로 창고 정보를 붙일 수 있습니다. 반대로 창고 10개를 먼저 읽는다고 항상 더 싼 것은 아닙니다. 각 창고의 많은 요청을 읽은 뒤 상태를 걸러야 한다면 총 후보가 매우 클 수 있습니다.

중첩 루프 조인의 개념은 바깥 결과 한 건마다 안쪽을 조회하는 것입니다. 바깥이 20행이고 안쪽 조회가 평균 0.05ms라면 안쪽 작업만 단순 계산으로 약 1ms입니다. 바깥이 실제 200,000행이라면 같은 작은 조회가 누적되어 약 10초가 됩니다. 이 수치는 설명용이며 실제 시간은 캐시·겹치는 작업·계측 방식에 따라 달라집니다.

따라서 안쪽 한 번이 빠르다는 말만으로 좋은 조인이라고 평가할 수 없습니다. 바깥 입력 수와 안쪽 반복 수를 함께 봅니다. 추정상 20행이었던 바깥이 실제 200,000행이면 원인은 안쪽 인덱스보다 앞단의 추정·필터·조인 순서일 수 있습니다.

Hash join은 어느 일을 바꾸는가?

두 목록에서 같은 주문 번호를 연결한다고 합시다. 한쪽 목록으로 주문 번호→행 정보를 찾을 해시 테이블을 만들고 다른 목록을 순회하며 대응 항목을 찾는 방식이 hash join의 출발점입니다. 매번 긴 목록을 다시 훑는 일을 줄일 수 있지만 해시 구조를 만들고 메모리에 보관하는 비용이 생깁니다.

입력이 크고 메모리가 부족하면 디스크로 나눠 처리하는 spill 비용이 생길 수 있습니다. 반대로 바깥이 몇 행뿐이고 안쪽 PK 조회가 매우 빠르면 중첩 루프가 유리할 수 있습니다. MySQL 8.0의 hash join 지원과 적용 범위는 마이너 버전별 변화가 있으므로 5.7의 실행 방식에 그대로 적용하지 않습니다. 이 시리즈는 8.0.36 재현 환경을 기준으로 봅니다.

EXISTS·JOIN·LEFT JOIN은 결과 의미부터 확인하기

“입고 요청이 있는 창고 목록”을 구하는 경우 창고 하나에 요청이 100개여도 창고를 한 번만 원할 수 있습니다. 일반 JOIN은 요청마다 창고 행을 반복해서 반환할 수 있습니다. EXISTS는 존재 여부를 표현하므로 같은 결과 문제인지부터 확인해야 합니다. JOIN 뒤 DISTINCT로 중복을 없애는 방식과 비교할 때도 중복 제거 비용이 포함됩니다.

LEFT JOIN에서는 일치하지 않는 행을 NULL로 확장해 남깁니다. 그런데 오른쪽 테이블의 조건을 WHERE에 잘못 두면 NULL 확장 행이 탈락해 의도한 외부 조인 의미가 사라질 수 있습니다. 옵티마이저가 순서를 바꾸는 것도 SQL의 의미를 유지할 수 있는 범위에서 일어납니다. 빠른 계획을 얻기 위해 결과 의미를 바꾸면 안 됩니다.

CTE를 합치거나 물질화하는 두 가지 방법

CTE를 작업에 붙인 이름표라고 생각해 보세요. 옵티마이저가 바깥 쿼리와 합칠 수 있다면 이름표의 내용을 펼쳐 하나의 계획으로 처리할 수 있습니다. 반대로 중간 결과를 만들어 두고 읽는 물질화 경로를 선택할 수도 있습니다. 물질화는 중간 저장 비용이 있지만 같은 결과를 재사용하거나 크기를 줄여 유리할 수 있습니다.

집계·DISTINCT·LIMIT 등 특정 구성은 merge 가능성에 영향을 줍니다. 그래서 WITH로 바꿨다는 사실만으로 “메모리 임시 테이블 생성”이나 “무조건 빨라짐”을 예측하지 않습니다. 계획에서 물질화 노드와 입력·출력 크기, 반복을 확인합니다. 이름이 더 읽기 좋아졌다는 코드 품질 개선과 실행 비용 개선은 각각 평가합니다.

계획이 나빠졌을 때 증거를 모으는 순서

  1. 같은 SQL인지, 바인딩 타입과 파라미터가 같은지 확인합니다.
  2. 변경 전후 테이블 행 수와 값 분포, 인덱스 정의를 비교합니다.
  3. 추정 행과 실제 행이 처음 크게 벌어지는 노드를 찾습니다.
  4. 통계 갱신·인덱스 설계·조건 표현 중 그 오차와 작업량에 직접 관련된 것을 하나씩 검토합니다.
  5. 힌트를 사용한다면 적용 여부와 대표 파라미터별 회귀를 확인합니다.

한 파라미터를 빠르게 만든 힌트가 다른 파라미터에는 손해일 수 있습니다. 월초에 10건, 월말에 100만 건이 나오는 조회라면 모두 확인해야 합니다. SQL 튜닝은 하나의 스크린샷에 좋은 계획을 만드는 일이 아니라 실제 입력 범위에서 결과와 비용을 관리하는 일입니다.

8. 상세 면접 Q&A

옵티마이저가 고른 계획이면 항상 최선인가요?

추정 정보와 비용 모델 안에서 선택한 계획입니다. 실제 캐시·상관관계·분포·동시 부하를 완벽히 알지 못합니다. 추정 rows와 실제 rows가 벌어진 지점을 확인해 통계, 쿼리 형태, 인덱스, 제한적으로 힌트를 검토합니다.

작은 테이블부터 조인하면 되나요?

원본 행 수만 보면 안 됩니다. 필터 적용 후 남는 행과 안쪽 접근 비용이 중요합니다. 큰 테이블에서 유니크 조건으로 한 행만 남는다면 그쪽이 좋은 시작점일 수 있습니다. 외부 조인 등의 의미 제약도 조인 순서를 제한합니다.

히스토그램을 만들면 인덱스가 없어도 빨라지나요?

히스토그램은 탐색 자료구조가 아니라 분포 추정 정보입니다. 더 나은 조인 순서나 접근 경로를 고르게 도울 수 있지만 직접 행의 위치를 알려 주지 않습니다. 계획이 바뀌지 않거나 실제 비용이 달라지지 않을 수도 있습니다.

Hash join이 nested loop보다 무조건 좋은가요?

아닙니다. 작은 바깥 입력과 좋은 안쪽 인덱스가 있으면 nested loop가 효율적일 수 있습니다. Hash join은 해시 생성·메모리·spill 비용이 있습니다. 실제 입력 크기와 조인 조건을 보고 판단합니다.

CTE는 임시 테이블인가요?

SQL 표현 방식이며 실행 시 merge 또는 materialize될 수 있습니다. 재귀 CTE 등 별도의 제약도 있습니다. 문법을 실행 자료구조와 동일시하지 말고 EXPLAIN에서 파생 결과와 물질화 여부를 확인합니다.

힌트를 넣었는데 변화가 없다면요?

인식·적용 여부를 SHOW WARNINGS와 계획으로 확인합니다. 원래 같은 경로를 선택했거나 다른 제약 때문에 적용하지 못했을 수 있습니다. 결과가 같다는 것만으로 힌트가 동작했다고 판단하지 않습니다.

꼬리 질문: 옵티마이저 cost는 실제 실행시간인가요?

답변: 아닙니다. 비용 모델의 비교용 추정값입니다. 같은 버전·환경의 후보 계획을 이해하는 단서이지 절대 밀리초가 아닙니다.

검증: EXPLAIN ANALYZE의 실측과 반복 횟수, 실제 입력 규모를 확인합니다. 비용 값이 줄었다는 것만으로 운영 지연 개선을 보고하지 않습니다.

꼬리 질문: 히스토그램으로 모든 추정 오차를 고칠 수 있나요?

답변: 아닙니다. 단일 열 분포, 표본 한계, 열 간 상관관계, 다른 추정 경로의 우선 사용 등 제약이 있습니다.

판단: 통계가 바뀌었는지뿐 아니라 계획의 어느 추정이 달라졌는지 확인합니다. 새 인덱스가 필요한 문제와 통계 정보가 부족한 문제를 분리합니다.

꼬리 질문: SQL에 먼저 쓴 테이블이 조인의 바깥쪽인가요?

답변: 반드시 그렇지 않습니다. 옵티마이저가 의미를 유지하는 범위에서 조인 순서를 선택할 수 있습니다. 외부 조인 등에는 제약이 있습니다.

확인: SQL 텍스트 순서가 아니라 실행 계획의 실제 입력 순서와 loops를 봅니다. 텍스트 순서만 바꿔 성능이 개선됐다고 결론내리지 않습니다.

꼬리 질문: 통계를 갱신했는데도 계획이 그대로면 실패인가요?

답변: 아닙니다. 새 추정에서도 같은 계획이 최선일 수 있고, 다른 통계가 사용되었거나 실제 문제의 원인이 통계가 아닐 수 있습니다.

다음 행동: 추정값 변화와 실제 작업량을 비교합니다. 계획 이름을 바꾸는 것이 목표가 아니라 불필요한 일을 줄이는 것이 목표입니다.
