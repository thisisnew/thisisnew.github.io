실행 계획 해독: EXPLAIN ANALYZE로 느린 이유 찾기

읽는 방법

비유로 개념을 잡고 SQL을 실행하기 전 결과를 예상해 보세요. 이번 개정에서는 단계별 동작 추적에 더해, 전편에 네 가지 확장 수업과 심층 면접 답변을 추가했습니다. 본문의 수치 예시는 설명용이고, 실행 환경에 따라 달라지는 값은 따로 표시했습니다. 기준은 MySQL 8.0·InnoDB, 재현용 서버는 8.0.36입니다. 처음 시작한다면 1편의 서버 준비만 먼저 진행하면 됩니다.

전체 학습 지도·검증 범위

1. 실행 계획은 성적표가 아니라 작업 설명서다

EXPLAIN에서 ALL이 나오면 나쁘고 ref가 나오면 좋다고 외우기 쉽습니다. 그러나 3행 테이블을 전부 읽는 것은 저렴하고, 인덱스로 500만 행을 찾아 본문까지 접근하는 것은 비쌀 수 있습니다. 실행 계획은 ‘어떻게 일할 것인가’를 보여 줍니다. 좋고 나쁨은 실제 작업량과 업무의 지연 목표를 대입해 판단합니다.

기본 EXPLAIN은 계획과 추정을 보여 줍니다. EXPLAIN ANALYZE는 쿼리를 실제 실행해 추정과 실측을 함께 보여 줍니다. 8.0.18부터 도입되었고 8.0에서는 TREE 출력입니다. 운영에서 무거운 SELECT에 붙이면 실제 부하가 발생합니다. 문장 종류에 따른 지원 범위도 있으므로 학습에서는 작은 SELECT만 사용합니다.

2. 먼저 읽을 여섯 열

열읽는 질문주의
table어느 입력을 처리하나?실제 테이블 외 파생·물질화 결과도 가능
type어떤 접근 방식인가?속도 순위표로만 외우지 않기
key실제로 선택한 인덱스는?possible_keys는 후보일 뿐
rows몇 행을 검사할 것으로 예상하나?InnoDB에서는 추정값
filtered그중 조건 통과 비율은?낮은 값은 많은 후보가 탈락한다는 뜻
Extra필터·정렬·커버링 같은 추가 작업은?문구 하나로 전체 성능 판단 금지

예를 들어 rows=10000, filtered=2이면 다음 단계로 10000×0.02=200행이 넘어갈 것으로 추정한다는 의미입니다. 이것은 실제 200행이라는 보장이 아닙니다. 조인에서 앞 단계의 추정 오차가 뒤의 반복 횟수 오차로 커질 수 있습니다.

3. 접근 유형을 실제 행동으로 번역하기

const는 유니크한 상수 조건 등으로 한 행을 고정하는 접근입니다. eq_ref는 이전 조합마다 유니크한 한 행을 찾는 조인 접근입니다. ref는 같은 키의 여러 후보를 찾을 수 있습니다. range는 인덱스 범위를, index는 인덱스 전체를, ALL은 전체 테이블을 스캔하는 의미로 이해하면 출발하기 좋습니다. 세부 조건과 다른 유형은 공식 정의로 확인합니다.

index는 이름이 좋아 보여도 전체 인덱스 스캔일 수 있습니다. 다만 좁은 커버링 인덱스를 전부 읽는 것이 넓은 테이블을 읽는 것보다 저렴할 수 있습니다. Using filesort는 인덱스 순서만으로 해결되지 않는 정렬을 뜻하며 반드시 디스크 파일을 썼다는 뜻은 아닙니다. Using temporary 역시 항상 디스크 임시 테이블을 뜻하지 않습니다.

4. 실습: 읽는 양을 줄이는 전후 비교

CREATE DATABASE IF NOT EXISTS mysql_school;
USE mysql_school;
DROP TABLE IF EXISTS plan_demo;
CREATE TABLE plan_demo(
 id INT PRIMARY KEY, warehouse_id INT NOT NULL,
 expected_date DATE NOT NULL, memo VARCHAR(200) NOT NULL
) ENGINE=InnoDB;
INSERT INTO plan_demo
WITH RECURSIVE seq AS (
 SELECT 1 n UNION ALL SELECT n+1 FROM seq WHERE n<1000
)
SELECT n,MOD(n,10),
 DATE_ADD('2026-01-01',INTERVAL MOD(n,30) DAY),REPEAT('p',150)
FROM seq;
EXPLAIN ANALYZE
SELECT id,expected_date FROM plan_demo
WHERE warehouse_id=1
ORDER BY expected_date,id LIMIT 10;
CREATE INDEX ix_wdi ON plan_demo(warehouse_id,expected_date,id);
ANALYZE TABLE plan_demo;
EXPLAIN ANALYZE
SELECT id,expected_date FROM plan_demo
WHERE warehouse_id=1
ORDER BY expected_date,id LIMIT 10;

변경 전에는 창고 열에 인덱스가 없으므로 후보를 찾고 정렬하는 작업이 필요할 수 있습니다. 변경 후에는 창고를 고정한 인덱스 구간에서 날짜·id 순으로 읽고 10건을 얻는 경로가 가능합니다. 실제 계획이 이 경로를 택했는지 확인합니다. 결과가 빠르다는 것만 보지 말고 스캔 행·정렬 노드·LIMIT에서 읽기가 멈추는 위치를 봅니다.

학습 데이터가 작아 시간 차이는 거의 없을 수 있습니다. 그런 경우 ‘몇 배 빨라졌다’는 숫자를 꾸며내지 않습니다. 접근 경로와 작업량 변화를 먼저 설명하고, 성능 주장을 하려면 더 큰 대표 데이터·반복 측정·동시 부하를 사용합니다.

5. actual time, rows, loops를 함께 읽기

설명을 위해 만들어 낸 가상 노드가 actual time=0.02..0.08 rows=3 loops=100이라고 합시다. 첫 숫자는 첫 행까지, 둘째는 해당 반복의 완료까지 걸린 시간이며 단위는 ms입니다. 여러 반복이 있으면 시간과 행 수는 반복당 평균으로 해석합니다. 대략 3×100=300행을 반환한 노드로 이해할 수 있습니다. 반올림 때문에 곱셈이 정확한 총계와 다를 수 있습니다.

부모 노드 시간은 자식 실행 시간을 포함합니다. 모든 노드의 시간을 더하면 중복 계산합니다. 바깥 입력이 100배 늘어 안쪽 loops가 늘었는지, 각 반복이 느려졌는지 구분하세요. 조인의 문제는 한 번의 조회가 느린 것이 아니라 작은 조회를 너무 많이 반복하는 것일 수 있습니다.

6. 목록 쿼리와 COUNT 쿼리는 왜 다른 인덱스를 고를까?

WHERE가 같아도 SELECT 열, ORDER BY, LIMIT, 집계가 다르면 해야 할 일이 다릅니다. 목록은 앞의 20건만 정렬 순서대로 얻으면 끝날 수 있습니다. COUNT는 조건에 맞는 전체 행을 세야 합니다. 목록이 본문 열을 여러 개 요구하지만 COUNT는 좁은 인덱스만 읽을 수 있는 경우도 있습니다.

EXPLAIN FORMAT=JSON
SELECT id,expected_date FROM plan_demo
WHERE warehouse_id=1 ORDER BY expected_date,id LIMIT 10;
EXPLAIN FORMAT=JSON
SELECT COUNT(*) FROM plan_demo WHERE warehouse_id=1;

두 쿼리가 같은 인덱스를 쓰더라도 작업량은 다를 수 있고, 서로 다른 인덱스를 쓰는 것도 오류가 아닙니다. ‘WHERE를 복사했으니 계획도 같아야 한다’고 보지 말고 결과를 만들기 위한 전체 요구를 비교합니다.

7. 느린 SQL 진단 기록을 남기는 법

  1. 정확한 SQL, 바인딩 타입과 대표 파라미터, 버전을 기록합니다.
  2. 현재 인덱스와 테이블 크기, 값의 편향을 확인합니다.
  3. EXPLAIN으로 위험한 읽기량을 먼저 추정합니다.
  4. 작은 검증 환경에서 EXPLAIN ANALYZE로 오차와 실제 병목을 찾습니다.
  5. 한 번에 한 변화만 적용하고 결과 동일성을 확인합니다.
  6. 읽기 지연뿐 아니라 쓰기 비용·인덱스 크기·계획 안정성을 비교합니다.

DB 실행은 50ms인데 서비스가 2초라면 풀 대기·네트워크·ORM 객체 매핑·N+1도 봐야 합니다. EXPLAIN ANALYZE는 클라이언트가 전체 결과를 수신하고 화면을 렌더링하는 시간의 대체 측정이 아닙니다. 반대로 대량 결과 전송 때문에 느린 API는 반환 열·행을 줄이는 것이 핵심일 수 있습니다.

실행 계획을 읽기 전에 SQL의 약속을 적기

택배 작업 설명서를 보기 전에 무엇을 몇 개 어느 순서로 보내야 하는지 알아야 합니다. SQL도 반환 열, 필터, 중복 허용 여부, 정렬, LIMIT이 무엇인지 먼저 적습니다. 목록 10개와 전체 COUNT는 필요한 일이 다릅니다. 같은 WHERE를 갖는다는 이유로 같은 계획을 기대하지 않습니다.

예를 들어 “1번 창고의 요청 중 날짜가 빠른 10개, 날짜가 같으면 id 순”이라는 요구라면 날짜·id 순서를 만족하는 조기 종료가 큰 이점입니다. 반면 “1번 창고 요청 총 건수”는 모든 일치 행을 세어야 합니다. 이 요구를 머리에 둬야 LIMIT 아래의 노드가 적게 읽는지, 정렬 때문에 많이 읽는지 판단할 수 있습니다.

가상의 TREE 결과를 한 줄씩 읽어 보기

아래는 실제 서버 출력이 아니라 해석 연습을 위한 가상 계획입니다. 숫자와 줄 모양은 설명용이며 실행 환경의 성능 결과로 사용하지 않습니다.

Limit: 10 rows (actual time=1.20..1.21 rows=10 loops=1)
  Sort: expected_date, id (actual time=1.19..1.20 rows=10 loops=1)
    Filter: warehouse_id = 1 (actual time=0.02..0.90 rows=100 loops=1)
      Table scan on plan_demo (actual time=0.01..0.70 rows=1000 loops=1)

아래쪽 스캔은 1,000행을 읽어 위로 전달했습니다. 필터는 그중 100행을 남겼습니다. 정렬은 필요한 순서를 만들고 위쪽 LIMIT은 10행을 반환합니다. 정렬 노드의 출력이 10행이어도 입력이 100행이었다는 사실은 사라지지 않습니다. Top-N 정렬 최적화가 있어도 어떤 행이 상위 10개인지 결정하려면 후보를 봐야 할 수 있습니다.

이제 적절한 인덱스로 같은 창고의 날짜·id 순서가 확보되면 10행을 얻는 데 필요한 범위만 읽고 멈출 가능성이 생깁니다. 개선은 단지 “ALL이 ref로 바뀜”이 아니라 후보 스캔과 정렬 작업을 줄이는 것입니다. 다만 실제 계획이 그렇게 선택했는지 확인해야 하며 필터가 추가되면 10개를 얻으려고 더 많은 후보를 읽을 수 있습니다.

rows×loops를 계산하되 무엇의 행 수인지 구분하기

가상 안쪽 노드가 rows=2 loops=500이라면 반복당 평균 2행을 반환하고 500번 실행했으므로 대략 1,000행이 상위로 전달된 것으로 읽을 수 있습니다. 이것은 그 노드 아래에서 검사한 모든 행의 총수가 항상 1,000이라는 뜻은 아닙니다. 필터 전 입력은 더 클 수 있습니다.

예를 들어 인덱스 탐색 노드가 반복당 100행을 제공하고 필터가 2행만 남긴다면, 필터 출력은 1,000행이어도 아래쪽 후보는 약 50,000행입니다. 높은 필터 탈락률이 어디에서 발생하는지 봐야 합니다. 최상단 결과가 10행이라는 정보만으로 전체 일을 평가하면 이 차이를 놓칩니다.

실측 행 수가 반복당 평균으로 표시되고 반올림될 수 있어 곱한 값은 근사치일 수 있습니다. 또한 실행되지 않은 노드는 never executed로 나타날 수 있습니다. 한 노드의 숫자만 떼어 절대 처리량으로 발표하지 않습니다.

시간을 더하면 왜 틀릴까?

부모가 자식에게 일을 시키고 결과를 받는 동안의 시간은 부모 시간에 포함됩니다. 택배 전체 배송시간에 창고 작업시간을 다시 더하면 중복 계산하는 것과 같습니다. 가상 계획의 루트 1.21ms에 스캔 0.70ms, 필터 0.90ms, 정렬 1.20ms를 더해 4.01ms라고 하면 안 됩니다.

loops가 여러 번이면 표시된 시간도 반복당 평균으로 해석합니다. 반복 한 번의 비용이 작아도 반복 수가 크면 누적 부담이 큽니다. 노드별 차이로 자신의 비용을 거칠게 추정할 때도 자식 실행 방식과 반복 수를 고려해야 하므로 무조건 뺄셈으로 정확한 CPU 시간을 얻는다고 보지 않습니다.

EXPLAIN ANALYZE에는 계측 오버헤드가 있고 일반 SELECT처럼 전체 결과를 애플리케이션에 전달해 객체로 만드는 경로와 다릅니다. 그래서 서버 계획 분석과 실제 API 지연 측정은 서로 보완 관계입니다. 어느 하나가 다른 측정을 완전히 대체하지 않습니다.

possible_keys·key·key_len을 오해하지 않기

possible_keys는 후보이고 key는 선택된 인덱스입니다. 후보가 여러 개라고 모두 동시에 사용했다는 뜻이 아닙니다. key_len은 사용된 키 길이에 대한 정보이며 자료형·문자셋·NULL 허용 등과 함께 해석해야 합니다. 숫자 하나만 보고 인덱스의 모든 후행 열이 쓸모없다고 결론내리지 않습니다.

특히 복합 인덱스는 범위를 정하는 열, 인덱스에서 필터링하는 열, 결과를 커버하는 열이 다를 수 있습니다. 어느 열까지 검색 경계를 만드는지 보려면 JSON 출력의 used_key_parts와 조건 위치 등도 함께 봅니다. 필드 하나에 모든 정보를 압축해서 해석하려 하지 않는 것이 정확합니다.

보이는 표현의미곧바로 단정하면 안 되는 것
Using index커버링 접근 관련 표시읽는 양이 반드시 작음
Using index condition인덱스 조건 푸시다운모든 열이 커버됨
Using filesort인덱스 순서 외 추가 정렬반드시 디스크 파일 사용
Using temporary중간 임시 결과 사용항상 나쁜 계획·항상 디스크

실험은 빨라졌는지보다 같은 결과인지부터

목록 SQL의 튜닝이라면 행의 집합뿐 아니라 순서도 확인합니다. 날짜가 같은 행의 순서를 안정시키려면 id 같은 유일한 기준이 필요합니다. JOIN을 EXISTS로 바꾸면 중복 수가 달라질 수 있고 LEFT JOIN 조건 이동은 NULL 행을 없앨 수 있습니다. COUNT(column)과 COUNT(*)도 NULL 처리 의미가 다릅니다.

성능 비교는 동일 데이터, 동일 파라미터, 같은 반환량을 기본으로 합니다. 찬 캐시와 따뜻한 캐시를 섞어 “10배 개선”이라고 하지 않습니다. 작은 학습 테이블에서는 시간보다 읽기 경로 변화를 중심으로 보고, 실제 효과는 대표 데이터와 동시 부하에서 p50·p95·p99 같은 분포로 확인합니다.

진단 사례: 반환 20행인데 API가 3초

가상의 사례입니다. 목록 SQL은 20ms이지만 목록의 각 행마다 상품 조회가 한 번씩 발생하고, 총 COUNT가 2초 걸리며, 연결 대기가 500ms 발생한다고 합시다. 목록 SQL의 인덱스만 개선하면 전체 문제의 대부분이 남습니다. 먼저 요청에서 실행되는 SQL의 개수와 각 누적 시간을 확인해야 합니다.

그다음 COUNT의 필요성·빈도·결과 정확도 요구를 따져 별도 최적화하고, N+1을 줄이며, 연결 점유 시간을 확인합니다. “가장 눈에 띄는 SQL”과 “전체 지연을 가장 많이 만드는 일”은 다를 수 있습니다. 실행 계획을 실제 요청 흐름에 연결하는 것이 실무 튜닝의 마지막 단계입니다.

확장 수업 ① — 실행 계획을 작업자들의 요청 관계로 읽기

TREE 계획에서 부모 연산자는 자식에게 필요한 행을 요청합니다. LIMIT은 아래 연산자가 낸 결과 중 필요한 수만 받고 멈출 수 있습니다. 하지만 아래에 정렬이 있으면 정렬은 올바른 앞 10개를 결정하기 위해 훨씬 많은 후보를 읽어야 할 수 있습니다. 따라서 맨 위 rows=10과 맨 아래가 수행한 작업량은 다릅니다.

필터 작업자를 떠올려 봅시다. 창고 직원이 상자 1,000개를 건네주면 필터 담당이 100개를 통과시키고, 정렬 담당이 그중 먼저 보낼 10개를 정합니다. 최종 배송이 10개여도 창고 직원이 꺼낸 상자는 1,000개입니다. 튜닝은 배송 수를 보는 데서 끝나지 않고 어느 단계에서 불필요한 상자가 많이 생겼는지를 찾는 일입니다.

정렬 순서와 조건에 맞는 인덱스가 있다면 처음부터 필요한 순서로 후보를 읽어 조기 종료할 수 있습니다. 그래도 인덱스에서 충족되지 않는 추가 필터가 있다면 결과 10개를 얻기 위해 더 많은 후보를 검사할 수 있습니다. LIMIT이 있다는 사실 자체가 읽기 상한 10을 보장하지는 않습니다.

확장 수업 ② — rows=4, loops=250을 어떻게 읽을까?

어떤 내부 조회가 actual time=0.01..0.04 rows=4 loops=250이라고 나왔다고 합시다. 수치는 설명용입니다. 여러 번 실행된 연산자의 actual time과 rows는 반복당 평균으로 해석하며, loops는 실행 횟수입니다. 평균 4행을 250회 내보냈다면 이 연산자가 내보낸 행은 약 1,000개입니다. 표시 반올림 때문에 곱이 정확한 정수 총계와 다를 수 있습니다.

표시의미이것과는 다름
0.01첫 행까지의 평균 시간, ms전체 API 최초 응답 시간
0.04해당 반복에서 모든 행을 내는 평균 시간, ms자식 비용을 제외한 순수 CPU 시간
rows=4반복당 평균 출력 행무조건 디스크에서 읽은 4페이지
loops=250연산자가 실행된 횟수SQL 요청 250개

0.04×250은 그 연산자가 여러 번 수행한 시간 규모를 이해하는 데 도움이 됩니다. 그러나 모든 노드의 이 값을 더해 전체 시간을 만들면 중복 계산합니다. 부모 시간은 자식 처리 시간을 포함하기 때문입니다. 먼저 최상위 실행 시간과 지연이 큰 경로를 보고, 각 연산자의 반복 증가와 자식 관계를 해석합니다.

행 수도 마찬가지입니다. 부모 필터의 100행과 자식 스캔의 1,000행을 합쳐 “1,100행을 디스크에서 읽었다”고 말하면 틀립니다. 같은 데이터가 연산자를 거치며 다른 단계의 출력으로 집계된 것입니다. 각 숫자가 어느 단계의 어떤 단위인지 붙여서 설명하는 습관이 필요합니다.

확장 수업 ③ — 튜닝 전후를 공정하게 비교하는 기록지

before 120ms, after 12ms를 봤다고 곧바로 90% 개선이라고 발표하지 마세요. 앞 실행이 페이지를 메모리에 올렸다면 뒤 실행은 그 혜택을 받았을 수 있습니다. 데이터가 달라졌거나 같은 조건처럼 보여도 날짜 범위가 다르면 작업량도 달라집니다. 실험은 결과 일치와 측정 조건을 먼저 확인합니다.

기록할 항목왜 필요한가
서버 버전·테이블 정의·인덱스기능과 후보 계획의 조건 고정
데이터 수·분포·바인딩 값작은 창고와 큰 창고의 편차 확인
반환 행·중복·정렬틀린 결과가 빨라진 것을 배제
반복 실행·워밍업 조건한 번의 우연과 캐시 효과 분리
추정 행·실제 행·loops시간 변화의 원인을 작업량으로 설명
동시 부하·쓰기 비용단독 SELECT 개선의 운영 효과 확인

실행 계획이 같아도 부하와 캐시 상태 때문에 지연은 달라질 수 있습니다. 반대로 계획이 달라도 작은 데이터에서는 시간 차이가 측정 오차 수준일 수 있습니다. 학습용 1,000행에서 인덱스 원리를 확인하는 것과 운영 처리량을 예측하는 일은 구분해야 합니다.

확장 수업 ④ — 사례를 보고 다음 실험 하나를 선택하기

사례 A: 예상 10행, 실제 100만 행이 필터에 들어갑니다. 통계·값 분포·조건이 인덱스로 좁혀지는지를 먼저 조사할 근거가 됩니다. 사례 B: 1행 PK 조회 자체는 빠르지만 loops가 10만입니다. 반복을 만드는 조인 입력이나 애플리케이션의 N+1 호출 구조를 살펴봅니다. DB 내부 loops와 앱이 보낸 SQL 횟수는 구분해야 합니다.

사례 C: SQL 실행은 수십 ms인데 API가 2초입니다. EXPLAIN만 더 들여다보기보다 연결 풀·네트워크·직렬화·외부 호출을 측정합니다. 사례 D: 많은 행을 정렬하지만 업무가 실제로 전체 정렬을 요구합니다. filesort 표기 자체를 없애는 것보다 필요한 결과량과 메모리·디스크 비용을 검토합니다.

다음 실험은 하나의 가설을 확인하도록 정합니다. “상태 조건이 너무 늦게 적용되어 원본 행 조회가 많다”는 가설이라면 후보 인덱스에서 필터 위치와 실제 행 수가 바뀌는지 봅니다. 이유 없이 인덱스 여러 개와 서버 설정을 동시에 바꾸면 무엇이 효과를 냈는지 알기 어렵습니다.

8. 상세 면접 Q&A

EXPLAIN의 rows는 실제 읽은 행 수인가요?

InnoDB에서는 추정입니다. 실측은 EXPLAIN ANALYZE의 실제 행 수와 반복 횟수 등을 확인합니다. 추정과 실제가 크게 다르면 통계·분포·상관관계·조건 해석을 원인 후보로 봅니다. 추정값을 운영 처리량처럼 보고하면 안 됩니다.

Using filesort면 반드시 튜닝해야 하나요?

정렬이 있다는 사실을 나타낼 뿐입니다. 수십 행 정렬은 저렴할 수 있고 인덱스를 억지로 쓰는 경로가 더 비쌀 수도 있습니다. 정렬 입력 크기·메모리·디스크 spill·실제 시간을 보고 판단합니다.

actual time을 전부 더하면 전체 시간이 되나요?

아닙니다. 부모가 자식 시간을 포함하므로 중복됩니다. 노드별 반복과 입력·출력 행 수를 보고 시간을 설명해야 합니다. 루트 시간도 애플리케이션 전체 응답시간과는 다릅니다.

COUNT와 목록의 WHERE가 같은데 계획이 다른 이유는?

필요한 열, 정렬, 조기 종료, 집계 요구가 다르기 때문입니다. 목록은 LIMIT으로 일찍 멈추고 COUNT는 전체 후보를 처리할 수 있습니다. 반환 목적이 다른 두 SQL에 같은 인덱스를 강제할 이유는 없습니다.

튜닝 전후 결과가 같은지 왜 확인하나요?

빠르게 틀린 결과를 내는 것은 개선이 아닙니다. 조인 중복·NULL·날짜 경계·정렬 동률·페이지 경계가 바뀔 수 있습니다. 대표 데이터와 경계값에서 행 집합과 필요한 순서를 검증한 뒤 성능을 비교합니다.

한 번 실행한 시간으로 개선율을 발표해도 되나요?

캐시·초기화·동시 부하·측정 오차가 섞입니다. 조건을 통제해 반복하고 분포와 실제 읽기량을 함께 기록합니다. 작은 실습에서 0.1ms 차이를 운영의 10배 개선처럼 해석하지 않습니다.

꼬리 질문: LIMIT 10이면 DB도 10행만 읽나요?

답변: 아닙니다. 조건과 정렬을 만족하는 10행을 찾기 위해 많은 후보를 읽을 수 있습니다.

확인: LIMIT 아래의 스캔·필터·정렬 입력을 봅니다. 인덱스 순서가 맞으면 일찍 멈출 수 있지만 추가 조건에서 많이 탈락하면 더 많은 행이 필요합니다.

꼬리 질문: filtered가 낮으면 항상 나쁜가요?

답변: 후보 중 남는 비율의 추정입니다. 낮은 비율은 많은 후보가 탈락할 수 있다는 신호이지만 절대량을 함께 봐야 합니다.

예: 10행 중 1행과 1억 행 중 1천만 행은 같은 10%여도 비용이 다릅니다. 더 좁힐 인덱스와 그 유지 비용을 비교합니다.

꼬리 질문: EXPLAIN ANALYZE를 운영에서 마음껏 실행해도 되나요?

답변: 쿼리를 실제 실행하므로 부하가 발생합니다. 큰 SELECT는 일반 실행과 마찬가지로 자원을 사용할 수 있습니다.

절차: 먼저 EXPLAIN으로 계획을 확인하고 대표 검증 환경에서 실측합니다. 운영 실측이 필요하면 실행시간·자원·취소 절차와 읽기 대상의 영향을 고려합니다.

꼬리 질문: 전체 스캔보다 인덱스 스캔이 항상 낫나요?

답변: 아닙니다. 비커버링 인덱스로 대부분의 행을 찾아 본문까지 접근하면 전체 스캔보다 비쌀 수 있습니다.

판단: 접근 유형의 이름보다 읽는 페이지·후보 수·본문 접근·정렬·실측 시간을 비교합니다. 작은 테이블의 ALL은 정상적이고 합리적인 선택일 수 있습니다.

심층 면접: EXPLAIN ANALYZE 결과가 실제 API 지연과 다르면 어느 쪽이 틀린가요?

답변: 측정 범위가 다를 수 있으므로 바로 어느 쪽이 틀렸다고 하지 않습니다. EXPLAIN ANALYZE는 쿼리를 실제 실행해 연산자 정보를 계측하지만 앱의 연결 대기, 일반 결과 전송·변환, 외부 호출까지 동일하게 측정하는 것은 아닙니다.

검증: 같은 SQL·입력·서버인지 확인하고, API 추적에서 DB 연결 대여와 SQL 실행 구간을 분리합니다. 계측 자체의 부하, 캐시·동시 부하 차이도 고려합니다.

주의: EXPLAIN ANALYZE는 단순 예상 출력이 아니라 실제 실행입니다. 운영에서 무거운 문장을 반복 실행하는 진단은 별도 부하가 됩니다.

심층 면접: key_len이 길어졌으면 튜닝에 성공한 건가요?

답변: 아닙니다. key_len은 선택한 키의 사용 길이를 해석하는 단서이지 성능 점수는 아닙니다. 데이터 타입, 인코딩, NULL 허용 여부와 사용한 키 부분의 영향을 이해해야 합니다.

구분: 더 많은 키 부분이 사용되어도 실제 범위가 넓거나 원본 행 조회·정렬·반복이 많으면 느릴 수 있습니다. 또한 key_len만으로 모든 조건이 범위 축소에 쓰였는지와 정렬이 해결되었는지를 판정할 수 없습니다.

확인: 실제 읽기 경로와 조건 위치, 행·loops·응답 지연을 확인하고 동일한 결과가 나오는지 검증한 후 개선을 판단하겠습니다.
