처음부터 이해하는 MySQL: 서버·연결·SQL의 여행

읽는 방법

비유로 개념을 잡고 SQL을 실행하기 전 결과를 예상해 보세요. 이번 개정에서는 단계별 동작 추적에 더해, 전편에 네 가지 확장 수업과 심층 면접 답변을 추가했습니다. 본문의 수치 예시는 설명용이고, 실행 환경에 따라 달라지는 값은 따로 표시했습니다. 기준은 MySQL 8.0·InnoDB, 재현용 서버는 8.0.36입니다. 처음 시작한다면 1편의 서버 준비만 먼저 진행하면 됩니다.

전체 학습 지도·검증 범위

1. 데이터베이스는 거대한 엑셀이 아니라, 함께 쓰는 장부다

물류센터에서 사과 재고를 10개라고 적은 장부를 두 직원이 동시에 고친다고 생각해 봅시다. 한 사람은 3개를 출고하고 다른 사람은 4개를 출고합니다. 둘 다 먼저 10을 읽고 각각 7과 6을 적으면 마지막 숫자는 6이 될 수 있습니다. 실제 재고는 3인데 장부가 틀린 것입니다. 파일에 숫자를 저장하는 것만으로는 이 문제를 해결할 수 없습니다. 누가 어떤 값을 읽어도 되는지, 누가 먼저 고칠지, 중간에 전원이 꺼지면 무엇을 복원할지까지 정해야 합니다.

MySQL은 여러 프로그램이 데이터를 공유하도록 관리하는 서버이고, InnoDB는 그 안에서 행을 저장하고 트랜잭션·잠금·복구를 담당하는 저장 엔진입니다. 음식점에 비유하면 MySQL 서버 계층은 주문을 이해하고 순서를 계획하는 홀, InnoDB는 실제 재료와 조리 과정을 관리하는 주방입니다. 단, 한 SQL의 작업이 한 번만 주방에 전달되는 것은 아닙니다. 여러 행을 읽는 동안 서버와 엔진이 반복해서 협력합니다.

커넥션 풀은 연결을 재사용하는 애플리케이션 쪽 장치입니다. 풀 크기가 10이라고 해서 MySQL 전체가 SQL 10개만 처리하는 것은 아닙니다. 서버가 3대이고 각 서버의 풀이 10이면 최대 30개 연결을 사용할 수 있습니다. 풀을 기다리는 요청은 아직 DB에 SQL을 보내지도 못했을 수 있습니다. 따라서 API가 3초 걸렸다고 SQL도 3초 걸렸다고 판단하면 안 됩니다.

3. 로컬에 안전하게 실습 서버 만들기

이 시리즈는 MySQL 8.0.36을 재현용 기준으로 사용합니다. 최신 운영 버전 추천이라는 뜻은 아닙니다. Docker가 설치된 Mac·Linux에서 아래 명령을 실행합니다. Apple Silicon에서는 ARM64 이미지 제공 여부를 먼저 확인하고, 사용할 수 없다면 실습에 한해 --platform linux/amd64를 추가할 수 있습니다. 에뮬레이션 결과로 성능을 비교하지는 마세요.

docker run --name mysql-school \
  -e MYSQL_ROOT_PASSWORD=LocalStudyOnly_83 \
  -p 127.0.0.1:3307:3306 \
  -d mysql:8.0.36

docker logs mysql-school
# ready for connections가 나타난 뒤 접속
# 아래 비밀번호는 로컬 학습 전용입니다.
docker exec -it mysql-school mysql -uroot -p

3307:3306은 내 컴퓨터의 3307번 문으로 들어온 요청을 컨테이너의 3306번 문으로 연결한다는 뜻입니다. 앞에 붙은 127.0.0.1은 로컬에서만 접근하도록 하는 바인딩입니다. 컨테이너 안에서 docker exec로 실행한 클라이언트는 이 포트 전달을 거치지 않습니다. 첫 접속이 실패하면 비밀번호를 바꾸기 전에 로그에서 서버 초기화 완료 여부를 확인합니다.

SELECT VERSION(), CONNECTION_ID(), @@autocommit,
       @@transaction_isolation, @@innodb_page_size;
CREATE DATABASE mysql_school CHARACTER SET utf8mb4;
USE mysql_school;
CREATE TABLE stock (
  sku BIGINT PRIMARY KEY,
  qty INT NOT NULL,
  CHECK (qty >= 0)
) ENGINE=InnoDB;
INSERT INTO stock VALUES (101, 10), (102, 20);
SELECT * FROM stock ORDER BY sku;

성공하면 101의 수량은 10, 102의 수량은 20입니다. CHECK는 8.0.16부터 실제 제약을 검사합니다. 5.7에서 같은 문장이 허용되었다고 같은 보장이 있는 것이 아닙니다. 실습을 다시 할 때는 이미 테이블이 존재한다는 오류가 정상입니다. 기존 학습 데이터를 지워도 괜찮다면 DROP TABLE stock; 후 생성부터 반복합니다. 다른 편은 각자 별도의 테이블명을 사용합니다.

4. SELECT 한 줄이 결과가 되기까지

  1. 연결과 인증: 서버는 어떤 계정인지 확인하고 요청을 받을 세션을 유지합니다.
  2. 문장 분석과 이름 해석: SQL 문법, 테이블·열 이름, 필요한 권한 등을 확인합니다. 단계의 세부 배치는 문장과 구현에 따라 달라질 수 있습니다.
  3. 최적화: 가능한 접근 방법을 비교합니다. 모든 행을 읽을지, 인덱스로 후보를 찾을지, 조인을 어떤 순서로 할지 결정합니다.
  4. 실행: 실행기가 계획에 따라 InnoDB에 레코드를 요청합니다. InnoDB는 페이지와 인덱스, 읽기 가시성 규칙을 사용합니다.
  5. 결과 전달: 필터·집계·정렬 등 필요한 작업을 수행하고 클라이언트에 결과를 보냅니다.

SELECT qty FROM stock WHERE sku=101에서 sku는 기본 키입니다. 원하는 행 하나로 찾아갈 수 있는 경로가 있습니다. 반면 인덱스 없는 qty 조건은 여러 행을 검사해야 할 수 있습니다. 결과가 한 행이라는 사실과 읽은 행이 한 개라는 사실은 다릅니다. 창고에서 빨간 상자 한 개를 찾았더라도 찾기 위해 선반 천 개를 열었을 수 있는 것과 같습니다.

MySQL 8.0에는 과거의 Query Cache가 없습니다. 같은 SELECT가 두 번째에 빨라지는 것은 버퍼 풀·운영체제 캐시·실행 환경 등의 영향일 수 있습니다. “결과 전체가 MySQL Query Cache에 저장되었다”고 설명하면 버전상 잘못된 설명입니다. 데이터 페이지 재사용과 SQL 결과 재사용은 별개입니다.

5. 설정은 파일, 전역값, 세션값이 다를 수 있다

SELECT @@GLOBAL.autocommit, @@SESSION.autocommit;
SET SESSION autocommit = 0;
UPDATE stock SET qty = qty - 1 WHERE sku = 101;
ROLLBACK;
SELECT qty FROM stock WHERE sku = 101;
SET SESSION autocommit = 1;
SHOW VARIABLES LIKE 'max_connections';

ROLLBACK 뒤 수량은 다시 10입니다. 세션 설정은 그 연결에만 적용됩니다. 전역 변수를 바꿔도 이미 연결된 세션의 대응 세션값이 자동으로 모두 바뀌는 것은 아닙니다. 또한 런타임 변경이 재시작 뒤 유지된다는 보장도 없습니다. 지원되는 변수에 대한 SET PERSIST와 설정 파일은 별도 관리 대상입니다. 실습에서 전역 설정을 무작정 바꾸지 않는 이유입니다.

한 요청을 현미경으로 보기: 재고 조회 API의 7개 시간

브라우저에서 재고 조회 버튼을 누르면 곧바로 디스크가 움직일 것 같지만, 그 사이에는 여러 대기와 계산이 있습니다. 식당에서 음식을 받는 시간도 입장 대기, 주문, 조리, 서빙으로 나뉘듯이 API 시간도 나누어야 합니다. 아래 수치는 실제 측정값이 아닌 계산 연습용 가정입니다.

합계는 370ms입니다. SQL의 20ms를 10ms로 줄여도 전체는 360ms입니다. 반면 풀 대기의 원인을 해결해 300ms를 30ms로 줄이면 전체는 100ms가 됩니다. 이것이 “느린 SQL부터 고친다”보다 “시간이 사라지는 구간부터 찾는다”가 정확한 이유입니다. 실제로는 일부 단계가 겹치거나 추가 호출이 있으므로 위 표를 그대로 더하기보다 분산 추적 구간을 사용합니다.

행·열·키를 처음 만나는 사람을 위한 장부 읽기

stock(sku, qty)에서 행 하나는 특정 상품의 재고 기록이고, 열은 그 기록의 속성입니다. sku=101은 행을 찾을 식별자, qty=10은 현재 수량입니다. PRIMARY KEY는 중복과 NULL을 허용하지 않는 식별 규칙이며 InnoDB에서는 저장 구조의 기준이기도 합니다. “101번째 줄”을 뜻하지 않습니다. 중간 행을 삭제해도 다른 행의 상품 코드가 줄 번호처럼 당겨지지 않습니다.

데이터 타입은 저장 칸의 크기와 비교 규칙을 정합니다. INT는 정수 계산에, VARCHAR는 문자열에 맞습니다. 상품 코드에 앞자리 0이 의미 있다면 숫자로 바꾸면서 그 정보가 사라질 수 있습니다. NOT NULL은 값이 반드시 있어야 한다는 뜻이고, 0과 NULL은 다릅니다. 0은 수량을 알고 있고 없다는 뜻, NULL은 수량이 없거나 모른다는 의미를 모델링할 수 있습니다. 업무상 재고를 항상 알아야 한다면 NOT NULL이 자연스럽습니다.

SQL은 대체로 “어떤 결과가 필요한지”를 선언합니다. WHERE sku=101은 찾을 대상을, SELECT qty는 반환할 정보를 지정합니다. 개발자가 직접 for문으로 행을 순회하지 않아도 옵티마이저와 실행기가 접근 경로를 결정합니다. 이 분리 덕분에 SQL이 같아도 통계나 인덱스 변화로 실행 방법은 달라질 수 있습니다.

서버와 엔진의 경계를 따라 SELECT와 UPDATE 비교하기

SELECT를 수행할 때 서버 계층은 SQL을 이해하고 접근 경로를 정합니다. InnoDB는 그 경로를 따라 인덱스 레코드를 찾고 읽기 관점에 맞는 버전을 제공합니다. 서버는 필요하면 추가 필터, 정렬, 집계를 수행합니다. 인덱스를 선택했다고 결과가 이미 완성된 것이 아닙니다. 창고 위치 목록을 얻은 뒤 물품 상태를 확인하고 묶음을 만드는 작업이 남는 것과 같습니다.

UPDATE는 여기에 경쟁 제어와 복구 기록이 더해집니다. 같은 상품을 다른 트랜잭션이 수정 중이면 기다릴 수 있고, 변경 전 상태를 되돌릴 undo와 변경을 복구할 redo가 필요합니다. autocommit=1이라면 문장이 끝날 때 확정 과정까지 포함합니다. SELECT가 1ms라고 같은 조건의 UPDATE도 1ms일 것이라 예상할 수 없는 이유입니다. 뒤의 3~6편이 각각 페이지, 로그, 읽기 관점, 잠금을 담당합니다.

풀 10개로 요청 100개를 처리한다는 말의 실제 의미

모든 요청이 동시에 연결을 필요로 하고 각 요청이 100ms 동안 연결을 독점한다고 가정합시다. 최대 10개가 먼저 연결을 받고 나머지는 풀에서 기다립니다. 완벽하게 균일하고 추가 병목이 없다면 100ms마다 10개씩 끝나므로 마지막 묶음은 약 1초에 끝납니다. 이때 MySQL에 연결 100개가 생기는 것이 아닙니다. 아직 연결을 못 빌린 요청은 애플리케이션에 있습니다.

하지만 풀을 100개로 늘렸을 때 각 작업이 잠금 경쟁으로 2초가 되면 처리량이 악화될 수도 있습니다. 연결 개수는 일할 수 있는 입장권 개수이며 CPU 코어 수나 디스크 처리 능력 자체는 아닙니다. 특히 트랜잭션을 열고 외부 HTTP 응답을 기다리면 DB가 별일을 하지 않아도 연결을 오래 점유합니다. 먼저 연결 보유 시간을 줄일 수 있는지 확인해야 합니다.

평균 동시 점유 수는 안정적인 상황에서 대략 “초당 처리 건수 × 평균 점유 시간(초)”로 생각할 수 있습니다. 초당 100건, 평균 0.05초라면 평균 5개입니다. 이는 풀을 정확히 5로 정하라는 공식이 아닙니다. 순간 폭주와 긴 꼬리 지연, 다른 트랜잭션을 포함해 여유와 제한을 실험해야 한다는 출발점입니다.

실습 결과가 다를 때: 두 창을 실제 두 세션으로 만들기

DataGrip의 콘솔 탭 두 개가 반드시 서로 다른 연결을 뜻한다고 가정하지 마세요. 각 창에서 SELECT CONNECTION_ID();를 실행해 값이 다른지 확인합니다. A에서 autocommit을 0으로 바꿔도 B의 값이 그대로라면 세션 설정의 범위를 직접 관찰한 것입니다. 이때 A의 변경이 보이지 않는다고 무조건 캐시 문제로 판단하면 안 됩니다. 미커밋 상태인지, B의 기존 스냅샷인지 먼저 확인합니다.

아래 진단 SQL은 데이터를 변경하지 않습니다. 결과를 복사해 “어느 서버의 어느 세션에서 무엇을 실행했는가”부터 기록하세요. 운영에서 비슷한 이름의 개발·검증·운영 스키마를 혼동하는 문제도 같은 원리로 줄일 수 있습니다.

SELECT @@hostname AS server_name, @@port AS server_port,
       CONNECTION_ID() AS session_id, DATABASE() AS current_schema,
       @@SESSION.autocommit AS autocommit_mode,
       @@SESSION.transaction_isolation AS isolation_level;
SHOW CREATE TABLE mysql_school.stock;

마지막으로 자가 설명을 해 보세요. “재고 조회가 느리다”는 말만 들었을 때 왜 인덱스를 바로 추가하면 안 되는지, 연결과 트랜잭션은 왜 다른지, 한 행을 반환해도 많은 행을 읽을 수 있는 이유를 각각 한 문장으로 말할 수 있으면 다음 편으로 넘어갈 준비가 된 것입니다.

확장 수업 ① — 도서관 비유를 실제 서버 구조로 번역하기

도서관에서 “김 작가의 책을 찾아 주세요”라고 말하면 접수 직원이 요청을 확인하고, 검색 시스템이 서가 위치를 찾고, 담당 직원이 책을 가져옵니다. MySQL에서도 역할이 나뉩니다. 클라이언트는 요청자, MySQL 서버 계층은 SQL의 의미와 실행 방법을 다루는 접수·검색 담당, InnoDB는 실제 데이터를 저장하고 읽으며 동시 접근을 제어하는 담당이라고 생각하면 됩니다.

이 비유에서 중요한 것은 역할의 경계가 별도 서버의 경계는 아니라는 점입니다. MySQL과 InnoDB를 설치하면 두 컴퓨터가 서로 네트워크로 이야기하는 것이 아닙니다. 일반적인 구성에서 InnoDB는 mysqld 프로세스 안에서 동작하는 스토리지 엔진입니다. 애플리케이션 서버와 DB 서버 사이에는 네트워크가 있지만, MySQL 서버 계층과 InnoDB 사이의 호출은 그와 다른 경계입니다.

SQL의 문법이 틀리면 책을 꺼내러 갈 필요도 없습니다. 권한이 없으면 허용되지 않은 요청입니다. 실행 계획이 나쁘면 너무 많은 서가를 돌아다닐 수 있습니다. 필요한 페이지가 메모리에 없으면 디스크에서 가져와야 합니다. 다른 작업이 대상 행을 수정 중이면 기다릴 수 있습니다. “DB가 느리다”는 말 한마디 안에 서로 다른 문제가 들어 있으므로, 먼저 어느 경계에서 시간이 쓰이는지 나눠야 합니다.

확장 수업 ② — 요청·연결·트랜잭션의 수명이 다른 이유

입고 API 요청 하나가 도착했다고 합시다. 애플리케이션은 풀에서 연결을 빌리고, 트랜잭션을 시작하고, 입고 상태를 조회하고, 수량을 갱신한 뒤 커밋합니다. 마지막에는 연결을 풀에 돌려줍니다. API 요청은 끝났지만 물리 연결은 다음 요청을 위해 살아 있을 수 있습니다. 반대로 요청 처리 중 외부 API를 먼저 호출한다면 DB 연결을 아직 빌리지 않았을 수도 있습니다.

단위무엇을 묶는가관찰할 질문
HTTP 요청사용자의 한 번의 호출전체 응답은 몇 ms인가?
연결 대여풀이 연결을 빌려준 구간빌리기까지 얼마나 기다렸나?
DB 트랜잭션함께 확정·취소할 DB 작업커밋까지 무엇을 기다렸나?
SQL 문장서버에 보낸 개별 명령실행·잠금·결과 전송 비용은?

연결을 빌린 뒤 외부 배송 API를 2초 기다리는 동안 SQL이 하나도 실행되지 않더라도 풀의 연결은 사용 중입니다. 풀에 10개가 있고 같은 요청 10개가 이 상태라면 11번째 요청은 DB CPU가 낮아도 연결을 못 빌립니다. 따라서 CPU 사용률만으로 “DB 여유가 있으니 문제없다”고 판단하면 원인을 놓칩니다. 느린 외부 호출을 트랜잭션에서 분리할 수 있는지 먼저 검토하되, 분리 후 필요한 원자성은 Outbox 같은 별도 업무 설계로 보완해야 합니다.

확장 수업 ③ — 연결 수를 숫자로 추정해 보기

설명용으로 초당 200개 요청이 오고, 각 요청이 연결을 평균 0.05초 점유한다고 합시다. 안정 상태에서 평균 동시 점유량은 대략 200 × 0.05 = 10개입니다. 이 계산은 처리량과 평균 체류 시간의 관계를 사용한 것이며, “풀을 정확히 10개로 정하면 된다”는 처방이 아닙니다. 도착 간격의 변동, 긴 요청, DB 처리 한계와 목표 지연을 함께 봐야 합니다.

SQL은 그대로인데 트랜잭션 안에서 0.5초짜리 외부 호출이 추가되면 점유 시간은 0.55초, 같은 처리량을 가정한 평균 점유량은 110개가 됩니다. 이때 풀을 무작정 110개로 키우면 DB까지 더 많은 동시 작업이 밀려갈 수 있습니다. 대여 대기 시간, 실제 SQL 시간, 연결 점유 시간을 따로 측정해야 하는 이유입니다.

서버가 세 대이고 각 풀의 최대 크기가 20이면 이 애플리케이션이 만들 수 있는 연결은 최대 60개입니다. 배포 중 서버가 잠시 여섯 대가 되면 최대 120개가 될 수 있습니다. 여기에 배치·운영 도구·다른 서비스 연결을 더합니다. max_connections는 한 애플리케이션의 풀 크기가 아니라 서버 전체가 수용하는 연결 한도입니다.

확장 수업 ④ — “쿼리는 빠른데 API는 느리다”를 분해하기

가상의 측정 결과가 연결 대기 700ms, SQL 20ms, 결과 변환 15ms, 외부 호출 250ms라면 SQL에 인덱스를 추가해 20ms를 5ms로 줄여도 전체 개선은 15ms뿐입니다. 중첩 구간을 중복 합산하지 않도록 추적 도구의 시간 경계를 확인하고, 긴 구간부터 조사합니다. 결과 10만 행을 보내는 쿼리는 서버의 첫 행 생성은 빨라도 전체 전송과 앱 객체 생성이 오래 걸릴 수 있습니다.

또한 같은 SQL 문자열이 같은 작업량을 뜻하지 않습니다. 창고 A에는 주문 100개, 창고 B에는 100만 개가 있을 수 있습니다. 진단 기록에 SQL뿐 아니라 바인딩 값의 특성, 반환 행 수, 접속 서버, 세션 설정을 남기세요. 비밀번호나 고객 개인정보를 그대로 기록할 필요는 없습니다. 문제를 재현할 수 있는 범위와 분포를 남기는 것이 목적입니다.

7. 상세 면접 Q&A

MySQL과 InnoDB는 같은 것인가요?

MySQL은 서버 전체이고 InnoDB는 저장 엔진입니다. SQL 분석·실행 계획과 실제 레코드 저장·잠금·복구는 서로 다른 책임입니다. 같은 MySQL 서버라도 테이블 엔진이 다르면 트랜잭션 성질이 달라질 수 있습니다. 따라서 “MySQL은 행 잠금”보다 “이 테이블은 InnoDB이고 해당 SQL은 이런 인덱스 레코드를 잠근다”가 정확합니다.

커넥션 풀을 10에서 100으로 키우면 10배 빨라지나요?

아닙니다. 연결 대기를 줄일 수 있지만 CPU·I/O·잠금 경쟁이 병목이면 DB에 동시에 밀어 넣는 작업만 증가합니다. 평균 처리시간이 늘어나 전체 대기열이 악화될 수도 있습니다. 풀 사용률, 대기시간, DB 활성 세션과 자원 사용률을 함께 본 뒤 부하 실험으로 결정합니다.

autocommit이 켜져 있으면 트랜잭션이 없나요?

아닙니다. InnoDB의 개별 문장도 트랜잭션으로 처리됩니다. 기본적으로 한 문장이 성공하면 자동 확정하는 것입니다. START TRANSACTION을 쓰면 여러 문장을 묶어 명시적으로 COMMIT 또는 ROLLBACK할 수 있습니다. “자동 확정”과 “원자성 없음”을 혼동하면 안 됩니다.

같은 쿼리가 두 번째에 빠른 이유를 어떻게 증명하나요?

버퍼 풀의 물리 읽기 증가량, 실행 계획, 실제 실행시간을 함께 비교합니다. 단순히 두 번째 실행이 빠르다는 사실만으로 캐시 종류까지 확정할 수 없습니다. MySQL 8.0에서 제거된 Query Cache를 원인으로 들면 안 되고, 동시 부하와 클라이언트 초기화 비용도 분리해야 합니다.

설정을 바꿨는데 서비스가 그대로라면요?

현재 세션값과 전역값, 실제 접속 서버를 확인합니다. 커넥션 풀이 오래된 세션을 재사용하거나 다른 인스턴스에 접속했을 수 있습니다. 설정이 동적으로 변경 가능한지, 새 연결에만 적용되는지, 재시작 후에도 유지되는지도 따로 확인합니다.

이 편을 이해했는지 스스로 어떻게 확인하나요?

“클라이언트 연결 → 서버의 문장 처리 → InnoDB의 데이터 접근 → 결과 전송”을 자기 말로 설명하고, 접속 실패와 SQL 실행 지연을 구분해 보세요. 또 세션 두 개를 열어 CONNECTION_ID가 다르고 설정이 독립적인지 확인하면 추상적인 용어가 실제 동작으로 연결됩니다.

꼬리 질문: DB 연결 하나에 트랜잭션도 하나인가요?

답변: 일반적인 MySQL 클라이언트 세션에서는 그 세션이 현재 수행하는 트랜잭션 상태를 가집니다. 하나의 연결을 오래 유지하며 여러 트랜잭션을 순서대로 처리할 수 있으므로 연결 수명과 트랜잭션 수명은 다릅니다.

이유: 커넥션 풀은 연결을 반납받아 다른 요청에 재사용합니다. 이전 요청이 트랜잭션이나 세션 상태를 잘못 남기면 다음 사용에 영향을 줄 수 있어 드라이버·풀·프레임워크의 정리 규칙이 중요합니다. 물리 연결 하나에서 독립 트랜잭션 여러 개를 아무렇게나 동시에 실행할 수 있다고 설명하면 안 됩니다.

꼬리 질문: SELECT 1이 빠르면 DB는 정상인가요?

답변: 연결과 간단한 문장 처리는 확인하지만 업무 테이블의 I/O·인덱스·잠금까지 확인하지는 못합니다.

진단: 실제 업무 쿼리의 지연, 활성 세션, 잠금 대기, 스토리지 지연을 함께 봅니다. 안내 데스크가 전화에 즉시 응답한다고 창고의 출고가 정상이라는 증거는 아닌 것과 같습니다. 헬스체크와 업무 성능 검증을 구분합니다.

꼬리 질문: 프리페어드 스테이트먼트는 결과 캐시인가요?

답변: 아닙니다. SQL과 파라미터를 분리해 실행하는 방식이며 같은 결과를 저장해 돌려주는 기능이 아닙니다.

적용: Java에서 PreparedStatement에 타입이 맞는 값을 바인딩하면 문자열 연결로 SQL을 조립하는 위험을 줄일 수 있습니다. 서버 측 준비 문장 사용 여부와 재사용 동작은 드라이버 설정에 따라 달라지므로, 성능 이득이나 최적화 생략을 항상 보장한다고 말하지 않습니다.

꼬리 질문: 에러가 났는데 일부 데이터는 왜 남았나요?

답변: 여러 문장이 하나의 트랜잭션으로 묶였는지부터 확인합니다. autocommit 상태에서 첫 UPDATE가 성공하고 다음 INSERT가 실패하면 첫 문장은 이미 확정되었을 수 있습니다.

해결: 함께 성공해야 할 DML을 명시적 트랜잭션으로 묶고 실패 시 롤백합니다. 모든 예외가 자동으로 전체 업무를 되돌린다고 가정하지 말고 프레임워크의 예외별 롤백 규칙도 확인합니다. DDL의 암묵적 커밋은 별도 문제입니다.

심층 면접: DB CPU는 10%인데 커넥션 풀 타임아웃이 납니다. 어떻게 접근하나요?

답변: 먼저 연결 생성 실패인지, 이미 만들어진 연결을 빌리는 대기 시간 초과인지 구분하겠습니다. 풀의 사용 중·유휴·대기 연결 수와 연결 점유 시간을 확인하고, DB의 실행 중 SQL·잠금 대기·열린 트랜잭션을 연결합니다.

이유와 예시: 외부 HTTP 호출을 기다리며 연결을 계속 점유하면 DB CPU가 낮아도 풀이 고갈됩니다. 반대로 잠금 때문에 UPDATE가 기다리는 상황도 CPU가 낮게 보일 수 있습니다. 전자는 트랜잭션 경계, 후자는 차단 트랜잭션과 접근 순서를 조사해야 합니다.

꼬리 질문: 풀 증설은 순간 대기를 줄일 수 있지만 DB 동시 부하를 늘립니다. 원인을 확인한 후 연결 점유 시간 단축과 부하 시험을 함께 검토하겠습니다.

심층 면접: MySQL의 한 연결을 여러 요청이 동시에 공유해도 되나요?

답변: 일반적인 JDBC 사용에서는 풀에서 빌린 연결을 한 작업 흐름이 사용하고 반환하도록 설계합니다. 한 세션에는 현재 트랜잭션과 세션 설정이 연결되어 있으므로 임의의 두 요청이 같은 연결에서 명령을 섞으면 업무 경계가 깨질 수 있습니다.

예시: 요청 A가 UPDATE한 뒤 요청 B가 같은 연결에서 COMMIT하면 A가 의도한 시점과 다른 확정이 일어날 수 있습니다. 자바 스레드가 다르다는 사실만으로 DB 트랜잭션이 분리되지는 않습니다.

주의: 연결 풀의 재사용과 동시 공유는 다릅니다. 반환 뒤 재대여는 일반적인 동작이며, 풀과 프레임워크가 세션 상태를 어떻게 복구하는지도 확인해야 합니다.
