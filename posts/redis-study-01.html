제공된 학습 자료의 01장과 Redis 공식 설정 문서를 출발점으로 삼았다. 제공 자료는 특정 시점의 문서 스냅샷이며, 그 안의 배포 파일 구성과 버전 예시는 지금 실행할 바이너리의 기능을 보장하지 않는다. 실습에서는 먼저 redis-server --version과 INFO server를 확인하고 설치한 버전에 동봉된 설정 예시를 기준으로 삼는다. 관리형 서비스는 CONFIG를 제한하고 별도의 파라미터 관리 화면을 제공할 수 있다. 공식 설정 문서

1. 프로세스, 설정 파일, 데이터 파일은 서로 다르다

프로세스는 실행 중인 프로그램이다. Redis 서버 프로세스는 네트워크 요청을 받아 메모리의 데이터를 읽고 바꾼다. redis.conf는 그 프로세스를 어떤 주소와 포트로 열고, 메모리를 얼마나 쓰며, 영속성을 어떻게 유지할지 적은 설명서다. dump.rdb와 AOF 파일은 실제 데이터 복원에 쓰이는 파일이다. 설정 파일을 백업했다고 데이터가 백업되는 것도 아니고, 데이터 파일을 복구했다고 보안 설정까지 복구되는 것도 아니다.

식당에 비유하면 프로세스는 영업 중인 주방, 데이터는 식재료와 주문 상태, 설정은 영업 매뉴얼이다. 매니저가 현장에서 “오늘부터 주문 마감은 9시”라고 말했다고 인쇄된 매뉴얼이 자동으로 고쳐지지 않는다. 다음 교대조가 옛 매뉴얼을 보면 다시 10시에 마감한다. 런타임 설정과 파일 설정의 차이가 이와 같다. 비유의 한계도 있다. Redis는 사람이 눈치껏 두 지시를 조정하지 않는다. 지원되는 설정을 파싱하고 정해진 순서로 적용할 뿐이며, 잘못된 설정은 시작 실패나 명령 오류를 일으킬 수 있다.

운영할 때는 최소 네 가지 상태를 구별한다.

상태 어디서 확인하는가 무엇을 말해 주는가
원하는 상태 Git, 배포 템플릿, 승인된 변경 기록 조직이 의도한 설정
디스크 상태 실제 마운트된 설정 파일 다음 기동 때 읽을 후보
기동 입력 서비스 관리자, 컨테이너 command/args 파일 외에 덮어쓰는 인자
현재 상태 CONFIG GET, INFO 지금 프로세스가 적용한 설정

이 네 줄을 하나로 생각하면 “파일은 바꿨는데 왜 적용되지 않았지?”라는 장애가 반복된다. 파일 수정은 이미 실행 중인 서버에 자동으로 전달되지 않는다. 반대로 CONFIG SET은 실행 중인 서버에 적용되지만 파일까지 고치는 명령은 아니다.

2. redis.conf의 문법을 읽는 법

기본 문법은 설정이름 인자1 인자2 ...다. 설정값 중 공백이 필요한 경우 인용부호를 사용한다. 다음은 운영 권장값 묶음이 아니라 설정의 종류를 읽기 위한 예시다.

bind 127.0.0.1
port 16379
protected-mode yes
daemonize no
maxmemory 128mb
maxmemory-policy noeviction
appendonly no
save ""

bind는 소켓을 열 로컬 네트워크 주소다. port는 그 주소에서 사용할 TCP 포트다. 127.0.0.1은 같은 호스트 안에서만 접근하는 루프백 주소다. protected-mode는 안전장치이지 방화벽이나 ACL을 대신하는 완전한 보안 경계가 아니다. daemonize no는 서버가 스스로 백그라운드로 분리되지 않게 한다. 컨테이너나 서비스 관리자가 수명을 관리하면 일반적으로 이 방식이 관찰하기 쉽다.

maxmemory는 Redis가 축출 여부를 판단하는 메모리 한도이고, 프로세스 전체의 RSS나 컨테이너 한도와 같은 숫자가 아니다. noeviction은 메모리가 부족할 때 기존 키를 임의로 내보내지 않는 정책이다. 이때 메모리를 늘리는 쓰기가 오류를 받을 수 있다. appendonly no, save ""는 이 예시에서 지속 저장을 사용하지 않는다는 뜻이다. 따라서 여기 적힌 구성을 업무 데이터에 복사해서는 안 된다. 실습을 빨리 초기화하기 위한 의도적 선택이다.

설정 파일 안에는 include로 다른 파일을 포함할 수도 있다. 여기서 중요한 질문은 “설정이 어디에 적혀 있는가?”만이 아니다. “동일 항목을 다른 파일이나 명령행에서 다시 지정하는가?”도 물어야 한다. 환경별 파일을 겹치는 방식은 편하지만, 파일을 읽는 순서와 기동 인자를 함께 검토하지 않으면 눈에 보이는 값과 적용값이 달라진다. 비밀값은 저장소에 평문으로 커밋하지 않고, 승인된 비밀 관리 수단과 파일 권한 정책으로 전달한다.

3. 파일과 명령행 인자는 어떻게 만나는가

다음 두 명령은 서로 다른 의도를 드러낸다.

redis-server /tmp/example/redis.conf
redis-server /tmp/example/redis.conf --port 16380

첫 번째는 지정한 파일을 읽는다. 두 번째는 파일과 명령행 인자를 함께 사용한다. Redis는 명령행 옵션을 설정 지시문과 같은 형태로 해석한다. 따라서 실행 관리자에 적힌 --port나 --maxmemory를 모른 채 파일만 고치면 변경이 반영되지 않는 것처럼 보일 수 있다. 운영에서는 어떤 파일을 읽었는지, 누가 명령행 인자를 만들었는지, 최종 실행 명령이 무엇인지까지 추적해야 한다.

컨테이너 이미지 속 기본 설정 파일과 볼륨으로 마운트한 설정 파일도 구분한다. 호스트의 파일을 고쳤는데 컨테이너가 다른 경로를 읽는 경우, 파일 내용은 완벽해도 결과는 변하지 않는다. 파일 경로가 맞더라도 읽기 전용 볼륨이면 런타임 설정을 파일로 다시 기록하는 명령은 실패할 수 있다. 이 실패를 Redis 데이터 손상이라고 진단하면 엉뚱한 곳을 수리하게 된다.

좋은 배포 기록에는 다음이 남는다.

  1. Redis 바이너리 또는 이미지의 정확한 버전과 식별자.
  2. 최상위 설정 파일 경로와 포함 파일 목록.
  3. 서비스 관리자가 전달한 인자.
  4. 비밀값을 제외한 설정 변경 내역.
  5. 재시작 후 확인할 핵심 CONFIG GET 목록.
  6. 이상 징후가 생겼을 때 사용할 이전 구성과 롤백 조건.

4. CONFIG GET, SET, REWRITE의 역할

CONFIG GET은 현재 적용된 값을 읽는다. 예를 들어 CONFIG GET maxmemory는 “지금 메모리에 올라온 한도”를 확인한다. 파일의 숫자를 보여 주는 명령이 아니다. 반환되는 단위 표현이 입력과 다를 수 있다. 사람이 128mb라고 입력했어도 결과는 바이트 수로 보일 수 있으므로 숫자가 다르다는 이유만으로 오류라고 판단하지 않는다.

CONFIG SET은 동적 변경이 지원되는 항목을 바꾼다. 모든 설정을 동적으로 바꿀 수 있는 것은 아니다. 명령의 성공 응답은 그 설정 변경을 받아들였다는 뜻이지, 데이터 이동이나 파일 생성 같은 후속 작업까지 끝났다는 뜻은 아니다. 특히 AOF 활성화와 같이 백그라운드 작업이 수반될 수 있는 변경은 관련 INFO 상태를 별도로 확인한다.

CONFIG REWRITE는 현재 설정을 기동 설정 파일에 반영하는 기능이다. 하지만 “Git에 저장한다”, “모든 노드의 설정을 맞춘다”, “배포 시스템의 원본 템플릿도 수정한다”라는 뜻은 아니다. 설정 파일 없이 기동했거나 파일을 쓸 수 없는 환경에는 그대로 적용할 수 없다. 운영의 설정 소유자가 GitOps나 관리형 서비스라면 그 제어면을 통해 영속화하는 것이 맞다. 즉 REWRITE의 사용 가능 여부보다 누가 설정의 원본을 소유하는가가 먼저다.

변경 절차를 짧게 쓰면 다음과 같다.

현재값 기록 → 영향과 되돌릴 값 결정 → 런타임 적용
→ 현재값/서비스 상태 확인 → 원본 구성 반영 → 재기동 검증

이때 “되돌릴 값”은 추측한 기본값이 아니라 변경 직전에 읽은 실제 값이다. 기본값은 버전과 배포판마다 다를 수 있고, 원래 의도적으로 조정된 상태일 수도 있다.

5. 캐시 정책: TTL과 eviction을 섞어 생각하지 않기

TTL은 Time To Live, 즉 키가 얼마나 오래 유효한지를 나타내는 수명이다. 만료는 시간이 지났기 때문에 데이터를 더 이상 유효하게 취급하지 않는 것이다. eviction은 메모리 압력 때문에 어떤 키를 내보낼지 결정하는 정책이다. allkeys-lru를 사용한다고 상품 가격이 10분 후 자동으로 갱신되는 것은 아니다. 메모리가 넉넉하고 키가 자주 쓰이면 오래 남을 수 있다.

상품 가격 캐시가 5분 이내로 신선해야 한다면 TTL 또는 명시적 무효화 전략이 필요하다. 메모리 초과 때 오래 안 쓰인 키를 내보내고 싶다면 eviction 정책이 필요하다. 하나는 업무상 유효기간, 다른 하나는 자원 관리 규칙이다. 둘을 함께 사용해도 모순되지 않는다. 근사 LRU는 모든 접근의 완전한 순위를 유지하는 이상적 LRU와 동일한 구현도 아니다.

반대로 로그인 세션, 재고 카운터, 중복 처리 방지 키를 일반 캐시와 같은 인스턴스에 넣고 allkeys-lru를 켜면 중요한 상태가 메모리 부족 때 사라질 수 있다. 애플리케이션에서 TTL을 길게 준다고 eviction으로부터 보호되는 것도 아니다. 데이터의 재생성 가능성과 유실 영향을 기준으로 인스턴스 또는 정책 경계를 설계한다.

6. 격리 실습: 재시작 전후의 설정 차이

이 실습은 자신이 만든 일회용 로컬 인스턴스에만 적용한다. redis-server와 redis-cli가 설치되어 있어야 한다. 포트 16379가 사용 중이면 빈 포트로 바꾸고 명령 전체에 동일하게 반영한다. 아래 결과 설명은 실행 결과를 주장하는 것이 아니라 확인할 관찰 기준이다.

LAB=$(mktemp -d /tmp/redis-config-lab.XXXXXX)
cat > "$LAB/redis.conf" <<EOFCONF
bind 127.0.0.1
port 16379
protected-mode yes
daemonize no
dir $LAB
save ""
appendonly no
maxmemory 128mb
maxmemory-policy noeviction
EOFCONF
redis-server --version
redis-server "$LAB/redis.conf"

마지막 명령은 터미널을 점유한다. 두 번째 터미널을 열어 다음을 실행한다. LAB 경로는 첫 번째 터미널의 값이므로 필요한 경우 출력해서 기록한다.

redis-cli -h 127.0.0.1 -p 16379 PING
redis-cli -h 127.0.0.1 -p 16379 CONFIG GET maxmemory
redis-cli -h 127.0.0.1 -p 16379 CONFIG SET maxmemory 96mb
redis-cli -h 127.0.0.1 -p 16379 CONFIG GET maxmemory

예상 관찰은 최초 값이 128 MiB에 대응하고, 변경 뒤에는 96 MiB에 대응하는 바이트 수가 나타나는 것이다. 파일을 열어 보면 128mb가 남아 있어야 한다. 이것이 런타임과 파일이 분리된다는 증거다. 설정 파일을 확인할 때 비밀이 포함된 운영 파일 전체를 채팅이나 로그에 출력하지 않는다. 이 실습 파일에는 비밀이 없으므로 읽어도 된다.

이제 실습 인스턴스에만 종료 명령을 보내고 같은 파일로 다시 실행한다.

redis-cli -h 127.0.0.1 -p 16379 SHUTDOWN NOSAVE
# 첫 번째 터미널에서 동일한 LAB 값을 가진 상태로 실행
redis-server "$LAB/redis.conf"

재기동 후 CONFIG GET maxmemory가 다시 128 MiB를 나타내면 의도한 차이를 관찰한 것이다. 이번에는 96 MiB로 바꾼 후 CONFIG REWRITE를 실행한다. 쓰기 가능한 파일로 시작했다면 파일과 다음 기동값이 함께 달라지는지 확인한다. 실패하면 오류 메시지, 파일 권한, 실제 기동 파일을 살펴본다. 실패를 숨기고 다음 단계로 넘어가지 않는다.

이 실습은 데이터 내구성 실험이 아니다. 지속 저장을 껐으므로 종료 때 데이터가 사라지는 것은 설정의 결과다. 실습이 끝나면 자신이 만든 프로세스만 종료하고 임시 경로를 기록한다. 시스템의 다른 Redis를 중지하거나 데이터를 삭제하는 정리 명령은 필요하지 않다.

7. Spring 애플리케이션 설정과 서버 설정의 경계

Java 개발자는 application.yml에 Redis 호스트와 포트를 적으면 Redis 설정까지 끝났다고 느끼기 쉽다. 그러나 연결 설정은 클라이언트가 누구에게 어떻게 요청할지를 결정하고, redis.conf는 서버가 어떻게 동작할지를 결정한다. 클라이언트의 타임아웃을 길게 바꾸어도 서버의 maxmemory가 늘어나지 않는다. 커넥션 풀 크기를 늘려도 서버의 비싼 명령이 빨라지는 것은 아니다.

// 개념 예시: StringRedisTemplate을 주입받은 서비스 메서드
public void cacheDisplayName(String userId, String displayName) {
    String key = "profile:name:" + userId;
    redisTemplate.opsForValue().set(key, displayName, Duration.ofMinutes(5));
}

여기서 TTL을 명령과 함께 전달하는 이유는 값 저장과 수명 설정 사이에 프로세스가 죽어 “만료 없는 캐시”를 남기는 일을 피하기 위해서다. 코드의 Duration은 애플리케이션의 신선도 요구다. 서버의 eviction 정책은 별도로 결정한다. 코드 예시는 프레임워크 버전별 연결 구성 전체를 대신하지 않으며, 실제 의존성 버전의 API와 직렬화 설정을 확인해야 한다.

애플리케이션 계정에 CONFIG SET 권한을 주는 방식으로 서버 정책을 자동 수정하게 만들지 않는다. 서비스가 배포될 때마다 서버 전체 정책이 바뀌면 여러 애플리케이션이 함께 사용하는 데이터에 영향을 줄 수 있다. 애플리케이션에는 필요한 데이터 명령만 허용하고, 운영 설정 변경은 별도 관리자 경로로 분리하는 것이 책임 경계를 선명하게 한다.

8. 운영 사고를 설정 경로로 역추적하기

사례 A: 재시작 이후 갑자기 OOM 오류가 늘었다. 먼저 서버가 정말 메모리를 다 쓴 것인지, Redis의 noeviction 쓰기 거절인지, OS가 프로세스를 종료한 것인지 구분한다. 그 다음 재시작 전후의 maxmemory, 정책, 이미지 버전, 기동 인자를 비교한다. 어제 긴급하게 늘린 한도가 파일에 남지 않아 이전 값으로 돌아갔을 수 있다. 해결은 현재값을 다시 키우는 것에서 끝나지 않는다. 왜 원본 구성이 갱신되지 않았는지를 수정해야 한다.

사례 B: CONFIG REWRITE가 성공했는데 다음 배포에서 되돌아갔다. 컨테이너 내부 파일만 수정됐고, 다음 컨테이너는 Git의 옛 설정으로 생성되었을 수 있다. 이때 Redis 명령이 실패한 것이 아니라 구성 관리 경로가 두 개가 된 것이다. 원본 템플릿을 수정하고 재배포 후 현재값을 검증한다.

사례 C: 접속이 안 되어 bind를 모든 인터페이스로 바꿨다. 연결 문제를 해결하면서 노출 범위를 넓힌 위험한 대응이다. 먼저 주소, 포트, 방화벽, 컨테이너 네트워크, 인증, TLS 요구를 나누어 확인한다. 루프백 제한 해제는 보안 설계 변경이며 별도 검토가 필요하다. “접속된다”와 “안전하게 접속된다”는 같은 합격 기준이 아니다.

9. 변경 검토표와 스스로 설명할 문제

설정 변경 요청에는 적어도 목적, 대상 인스턴스, 기존값, 새 값, 서비스 영향, 확인 지표, 롤백값, 영속화 경로를 적는다. 이 중 하나가 비어 있으면 팀원은 명령 한 줄은 알지만 의도와 위험은 알 수 없다. 특히 메모리 한도를 낮추는 변경은 그 순간의 사용량에 따라 eviction이나 쓰기 오류를 유발할 수 있으므로 단순히 숫자만 작게 쓰는 작업이 아니다.

연습 문제를 하나 생각해 보자. 파일에는 2 GiB, 기동 인자에는 3 GiB, 어제 CONFIG SET으로는 4 GiB를 적용했다. 지금 CONFIG GET이 4 GiB라고 해서 내일도 4 GiB라고 말할 수 있는가? 정답은 아니다. 기동 경로와 구성 영속화 여부를 조사해야 한다. 이 질문에 “재시작해 보면 되죠”라고만 답하면 운영 검증 순서가 거꾸로다. 먼저 문서와 실행 경로로 예상값을 만든 다음 안전한 환경에서 재시작해 예상과 비교해야 한다.

10. 재시작 검증을 자동화할 때의 합격 기준

테스트 환경에서 재시작 검증을 자동화한다면 응답 가능 여부와 설정 일치를 분리해 검사한다. PING이 성공해도 다른 포트의 옛 프로세스에 연결했을 수 있고, 설정은 예상과 달라도 서버 자체는 정상 응답할 수 있다. 먼저 대상 주소와 프로세스 식별 정보를 확인하고, 다음으로 핵심 설정의 현재값을 읽고, 마지막으로 작은 테스트 키의 저장·만료 동작을 확인한다. 데이터 검증은 업무 키가 아닌 전용 접두사를 사용한다.

예를 들어 배포 계약을 “루프백 실습 주소, 포트 16379, noeviction, 128 MiB”로 정했다면 각 항목을 별도 assertion으로 다룬다. 실패 시 전체 CONFIG 출력을 무조건 첨부하지 말고 필요한 항목과 비밀을 제거한 오류만 남긴다. 테스트가 원본 설정 파일을 수정했다면 종료 시 복구하거나 일회용 디렉터리를 사용한다. 테스트의 목적은 서버가 어떻게든 시작하게 만드는 것이 아니라, 의도한 구성으로 시작했음을 증명하는 것이다.

면접 질문과 상세 답변

1. redis.conf를 수정했는데 실행 중인 Redis에 반영되지 않는 이유는 무엇인가요?

설정 파일은 일반적으로 기동 시 읽는 입력이다. 이미 실행 중인 프로세스가 파일 변경을 계속 감시해서 자동 반영하는 것은 아니다. 동적 변경이 지원되는 항목은 관리 권한으로 CONFIG SET을 사용할 수 있고, 지원되지 않는 항목은 계획된 재시작이 필요할 수 있다. 답변에서 중요한 것은 “재시작하세요”보다 먼저 실제 기동 파일, 명령행 덮어쓰기, 현재 CONFIG GET 값을 확인한다는 순서다. 잘못된 파일을 고쳤다면 재시작해도 결과는 바뀌지 않는다.

2. CONFIG SET과 CONFIG REWRITE의 차이를 설명해 주세요.

CONFIG SET은 현재 프로세스의 지원되는 설정을 변경한다. CONFIG REWRITE는 현재 설정을 기동 설정 파일에 기록하는 별도의 작업이다. SET 성공은 재시작 후 유지 보장이 아니며, REWRITE 성공도 Git이나 배포 템플릿 갱신을 의미하지 않는다. 읽기 전용 설정 파일이나 관리형 서비스에서는 직접 기록 방식이 맞지 않을 수 있다. 따라서 설정의 권위 있는 원본이 어디인지 확인한 뒤 해당 경로로 변경을 보존해야 한다.

3. allkeys-lru를 쓰면 TTL은 필요 없나요?

메모리 관리만 목표라면 모든 키에 TTL이 반드시 필요한 것은 아니지만, 데이터 신선도를 보장하려면 별도 수명 또는 무효화 정책이 필요하다. LRU 계열 eviction은 메모리가 압박받을 때의 선택 규칙이다. 공간이 충분하면 오래된 값도 남을 수 있고, 자주 읽는 오래된 값은 계속 유지될 수 있다. 가격이나 권한처럼 시간에 민감한 데이터는 eviction을 만료 정책으로 착각하면 안 된다.

4. maxmemory를 서버 RAM과 똑같이 잡아도 되나요?

안전하지 않다. Redis 데이터 외에도 allocator 여유 공간, 클라이언트 및 복제 버퍼, 영속성 작업 중 copy-on-write, 운영체제와 다른 프로세스의 메모리가 필요하다. 컨테이너에서는 호스트 RAM보다 cgroup 한도가 먼저 제약할 수도 있다. maxmemory는 Redis의 메모리 정책 판단 기준이지 OS에 대한 총량 예약이나 RSS 상한이 아니다. 다음 장에서 이 차이를 수치로 나누어 다룬다.

5. 설정 파일을 Git으로 관리하면 비밀번호도 넣어야 하나요?

아니다. 구성의 재현성과 비밀의 노출은 별개다. 일반 정책과 템플릿은 버전 관리하되 인증 비밀은 승인된 비밀 관리 시스템, 접근 제한된 파일, 플랫폼의 비밀 주입 기능 등으로 전달한다. 설정 비교나 장애 로그를 만들 때도 민감 항목을 가려야 한다. “Git에서 빼기”만으로 충분한 것은 아니며 셸 기록, 프로세스 인자, 로그, 백업 파일의 노출 경로까지 고려한다.

6. CONFIG GET 값과 파일 값 중 어느 것이 정답인가요?

서로 다른 질문의 정답이다. 현재 동작을 알고 싶으면 런타임 값이 직접적인 증거다. 다음 시작의 의도를 알고 싶으면 파일과 기동 인자를 함께 봐야 한다. 조직이 승인한 상태를 알고 싶으면 배포 원본을 봐야 한다. 세 값이 다를 때는 어느 하나를 무조건 정답이라 하지 말고 drift, 즉 의도와 실제 사이의 차이를 발견한 것으로 다룬다.

7. noeviction이면 데이터가 절대 사라지지 않나요?

아니다. 이 정책은 메모리 압력 때문에 키를 자동 축출하지 않는다는 의미다. TTL 만료, 애플리케이션의 삭제나 덮어쓰기, 장애 후 복구 시점 차이, 영속성 설정 오류는 별개의 경로다. 또한 공간이 부족하면 일부 쓰기가 실패할 수 있으므로 애플리케이션은 오류 처리와 재시도 정책을 가져야 한다. 내구성, 만료, 축출, 접근 통제는 다른 축의 보장이다.

8. 운영 설정을 안전하게 바꿨다는 증거는 무엇인가요?

명령의 OK 응답 하나로 충분하지 않다. 변경 전후의 현재값, 예상한 서비스 지표, 오류율과 지연, 필요한 백그라운드 작업의 완료 상태, 원본 구성 반영, 재기동 후 일치 검증이 증거가 된다. 변경의 범위에 맞춰 확인해야 하며, 모든 변경에 무조건 재시작을 요구하는 것은 아니다. 다만 재시작 내구성이 목표라면 실제 재기동 검증이나 검증된 배포 테스트가 필요하다.

정리와 공식 자료

설정 운영의 핵심은 숫자를 많이 외우는 것이 아니라 현재값·다음 기동값·승인된 원본값을 구별하는 습관이다. 다음 장에서는 그중 가장 자주 오해하는 메모리 한도를 OS 관점으로 확장한다.

  • Redis configuration: 설정 파일과 동적 변경의 공식 설명.
  • CONFIG GET, CONFIG SET: 실행 버전의 지원 여부와 동적 설정 확인.
  • CONFIG REWRITE: 파일 반영의 범위와 제약.
  • Key eviction: 메모리 정책과 만료의 차이.
