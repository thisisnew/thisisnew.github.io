저장 완료의 비밀: redo·undo·커밋·장애 복구

읽는 방법

비유로 개념을 잡고 SQL을 실행하기 전 결과를 예상해 보세요. 이번 개정에서는 단계별 동작 추적에 더해, 전편에 네 가지 확장 수업과 심층 면접 답변을 추가했습니다. 본문의 수치 예시는 설명용이고, 실행 환경에 따라 달라지는 값은 따로 표시했습니다. 기준은 MySQL 8.0·InnoDB, 재현용 서버는 8.0.36입니다. 처음 시작한다면 1편의 서버 준비만 먼저 진행하면 됩니다.

전체 학습 지도·검증 범위

1. ‘저장 완료’ 버튼을 누른 직후 전원이 꺼진다면

재고를 10에서 9로 바꾼 뒤 성공 응답을 받았습니다. 그런데 DB 서버 전원이 꺼졌습니다. 다시 켰을 때 재고는 9여야 할까요? 업무가 기대하는 답은 그렇습니다. 하지만 메모리는 전원이 꺼지면 사라집니다. 따라서 메모리에서 값을 바꾼 것만으로는 성공을 약속할 수 없습니다. 복구에 충분한 정보를 안정적인 저장소에 남기는 과정이 필요합니다.

회의 중 큰 원본 문서 전체를 매번 출력하는 대신 변경 지시를 작은 장부에 순서대로 기록한다고 생각해 보세요. 원본 출력이 늦어져도 장부를 적용하면 다시 만들 수 있습니다. 이것이 redo를 이해하는 출발점입니다. 다만 실제 redo는 SQL 문장을 그대로 저장한 일기장이 아니라 InnoDB 내부 변경을 재현하는 정보입니다.

2. redo, undo, binlog는 목적부터 다르다

기록주된 질문역할
Redo데이터 파일에 덜 반영된 변경을 어떻게 복구하나?InnoDB crash recovery
Undo변경 전 상태가 필요하면 어떻게 하나?롤백, 일관된 읽기의 과거 버전 구성
Binary log서버의 변경 이벤트를 다른 서버나 복구 작업에 어떻게 전달하나?복제와 시점 복구의 기반

‘redo는 커밋한 트랜잭션만 담는다’는 설명은 틀립니다. 커밋 전에 발생한 변경의 redo도 기록될 수 있습니다. crash recovery는 먼저 redo로 페이지 상태를 복원하고, 확정되지 않은 트랜잭션의 변경은 undo 등을 사용해 취소하는 작업을 포함합니다. redo와 undo는 서로 경쟁하는 선택지가 아니라 서로 다른 방향의 복구 재료입니다.

3. UPDATE부터 COMMIT까지, 무엇이 언제 안전해지나

단순화한 개념 흐름은 다음과 같습니다. 행을 찾아 필요한 잠금을 획득하고, 이전 상태를 되돌릴 정보와 변경을 재현할 정보를 만들며, 버퍼 풀의 페이지를 변경합니다. 실제 구현은 여러 내부 작업과 로그 레코드가 엮이므로 이 순서를 모든 함수의 정확한 호출 순서로 외우지는 마세요. 핵심 제약은 데이터 페이지를 내보내기 전에 복구에 필요한 redo가 먼저 보존되어야 한다는 WAL(Write-Ahead Logging) 원칙입니다.

COMMIT은 트랜잭션의 확정 경계입니다. 기본적인 내구성 설정에서는 커밋에 필요한 redo를 안정적인 저장장치로 flush하는 과정이 중요합니다. binlog가 활성화되면 엔진의 확정과 binlog의 기록이 어긋나지 않도록 조정하는 과정도 필요합니다. 그렇지 않으면 원본 DB에는 반영되었는데 복제에 전달할 이벤트가 없는 문제가 생길 수 있습니다.

그렇다고 커밋마다 디스크 동기화가 정확히 한 번씩 발생한다고 단정할 수는 없습니다. 여러 트랜잭션의 로그 flush를 묶는 group commit이 있습니다. ‘개별 트랜잭션이 기다리는 내구성 조건’과 ‘실제 저장장치 호출 횟수’는 다릅니다.

4. 내구성 설정을 읽는 법

SELECT @@innodb_flush_log_at_trx_commit, @@sync_binlog,
       @@log_bin;
SHOW VARIABLES LIKE 'innodb_redo_log_capacity';
SHOW GLOBAL STATUS LIKE 'Innodb_log_waits';

innodb_flush_log_at_trx_commit=1은 각 커밋에서 redo write·flush를 요구하는 정책입니다. 2는 커밋마다 파일에 write하지만 flush는 보통 주기적으로 수행합니다. 0은 write와 flush가 주기적입니다. 운영체제 캐시에 write했다는 것과 전원 장애에도 살아남을 저장소에 flush했다는 것은 다릅니다. 주기적 작업은 정확한 시계처럼 보장되지 않으므로 “최대 정확히 1초만 잃는다”고 약속하면 안 됩니다.

sync_binlog=1은 binlog의 동기화 정책에 해당합니다. redo 설정만 강하게 하고 binlog 쪽은 약하게 두면 두 기록의 장애 특성이 달라집니다. 실제 보장은 디스크·파일시스템·가상화 계층이 동기화 요청을 올바르게 지키는지에도 달려 있습니다. 속도 개선을 위해 값을 바꾸려면 어떤 장애에서 어떤 데이터를 잃을 수 있는지 먼저 합의해야 합니다.

5. 체크포인트와 doublewrite가 추가로 필요한 이유

로그를 영원히 보관할 수는 없습니다. 변경된 페이지를 데이터 파일에 충분히 반영하면 그 이전 redo 일부를 재사용할 수 있습니다. 어디까지의 복구 부담을 데이터 파일이 맡을 수 있는지 진전시키는 경계가 체크포인트와 연결됩니다. redo 공간을 늘리면 쓰기 폭주를 흡수할 여유가 생길 수 있지만, 지속적인 디스크 쓰기 능력 자체가 늘어나는 것은 아닙니다. 8.0.30부터 redo 용량 관리는 innodb_redo_log_capacity 중심으로 바뀌었습니다.

또 다른 문제는 페이지를 쓰다 전원이 꺼져 앞 절반만 새 데이터가 되는 torn page입니다. redo가 있다고 손상된 기본 페이지를 항상 그대로 고칠 수 있는 것은 아닙니다. doublewrite는 페이지를 원래 위치에 쓰기 전 별도 영역에 기록하는 방식으로 복구에 사용할 온전한 페이지를 확보합니다. 이름에 write가 두 번 들어가지만 저장장치 비용이 무조건 정확히 두 배라는 뜻은 아닙니다. 배치와 순차 I/O 특성이 다릅니다.

6. 실습: 확정·취소·재접속을 구분하기

CREATE DATABASE IF NOT EXISTS mysql_school;
USE mysql_school;
DROP TABLE IF EXISTS durability_demo;
CREATE TABLE durability_demo(id INT PRIMARY KEY, qty INT NOT NULL)
  ENGINE=InnoDB;
INSERT INTO durability_demo VALUES(1,10);
START TRANSACTION;
UPDATE durability_demo SET qty=9 WHERE id=1;
ROLLBACK;
SELECT qty FROM durability_demo; -- 10
START TRANSACTION;
UPDATE durability_demo SET qty=8 WHERE id=1;
COMMIT;
SELECT qty FROM durability_demo; -- 8

같은 로컬 서버를 docker restart mysql-school로 재시작하고 다시 조회하면 8이 유지되어야 합니다. 이것은 정상 재시작의 보존 실습이지 전원 장애 내구성 증명이 아닙니다. 컨테이너 kill도 호스트 OS 전원 차단과 같지 않습니다. OS 캐시가 살아 있을 수 있기 때문입니다. ‘강제 종료했는데 안 잃었으니 설정 2도 완전히 안전하다’는 결론을 내리면 안 됩니다.

7. 장애 시나리오: 커밋은 됐는데 응답을 못 받았다

클라이언트가 COMMIT을 보냈고 서버는 성공적으로 확정했습니다. 그 직후 네트워크가 끊기면 클라이언트는 오류만 봅니다. 이때 재시도하면 중복 출고가 생길 수 있습니다. DB의 원자성이 ‘클라이언트가 결과를 반드시 안다’는 보장까지 주는 것은 아닙니다.

업무 요청에 고유한 요청 ID를 붙이고 UNIQUE 제약으로 중복 처리를 막는 방법을 생각해 볼 수 있습니다. 예를 들어 출고 요청 ID가 이미 처리되었다면 저장된 결과를 조회합니다. 단순히 모든 SQL 오류를 실패로 보고 같은 재고 차감을 반복하는 것은 위험합니다. 커밋 결과 불명확성과 확실한 롤백을 구분해야 합니다.

세 장소를 구분해야 ‘저장했다’는 말을 이해할 수 있다

변경 기록이 놓일 수 있는 장소를 메모리의 로그 버퍼, 운영체제의 파일 캐시, 전원 장애 후에도 남는 저장장치로 나누어 봅시다. 편지를 책상 위에 쓴 상태, 우체통에 넣은 상태, 수신처의 금고에 들어간 상태가 다른 것과 같습니다. 프로그램의 write 호출 성공이 마지막 단계까지 자동 보장하는 것은 아닙니다.

장애사라질 수 있는 것관찰의 한계
클라이언트 종료클라이언트가 아는 결과서버에서 커밋했는지 별도 확인
mysqld 프로세스 비정상 종료프로세스 메모리운영체제 캐시는 살아 있을 수 있음
호스트 전원 차단프로세스·OS의 휘발성 상태장치의 flush 보장도 중요
디스크 자체 손실같은 디스크의 데이터와 로그로컬 redo만으로 해결 불가

이 표 때문에 정상 재시작 실습과 장애 복구 시험은 별개입니다. docker restart는 정상 종료 기회를 줄 수 있고, kill은 호스트 전원을 끄지 않습니다. 한 종류의 장애에서 성공했다고 모든 장애에 대한 보장을 검증했다고 쓰면 안 됩니다.

커밋 시 모든 페이지를 쓰지 않는 이유: 랜덤 작업을 작은 순차 기록으로 바꾸기

한 트랜잭션이 서로 떨어진 데이터 페이지 100개를 조금씩 고친다고 가정해 보겠습니다. 매번 그 페이지를 전부 안정적으로 저장하고 응답한다면 많은 I/O를 기다릴 수 있습니다. 대신 변경을 복구할 로그를 먼저 안정화하고 페이지 기록을 뒤로 미루면 커밋의 대기 경로를 줄일 수 있습니다. 로그는 변경을 모아 기록하기 유리하고 여러 트랜잭션의 flush를 묶을 여지도 있습니다.

이것은 디스크 쓰기를 없앤 것이 아닙니다. 페이지는 나중에 써야 합니다. 단지 “응답 전에 반드시 해야 하는 일”과 “복구 정보를 확보했으니 나중에 해도 되는 일”을 분리합니다. 같은 페이지를 짧은 시간에 여러 번 수정했다면 최종 상태를 모아 내보내는 이득도 가능합니다. 그 대가로 로그 공간, 체크포인트, 복구 절차가 필요해집니다.

LSN과 체크포인트: 어디까지 장부를 다시 읽어야 할까?

LSN(Log Sequence Number)은 redo 스트림 안에서의 위치를 나타내는 값입니다. 트랜잭션 개수나 행 개수와 같은 단위가 아닙니다. 변경 기록이 추가되면 앞으로 이동하며, 페이지에 반영된 변경과 복구 경계를 연결하는 데 사용됩니다. 체크포인트는 앞쪽 로그를 재사용할 수 있도록 데이터 파일의 반영 진도를 관리합니다.

설명을 위해 현재 로그 위치가 900MB 지점이고 체크포인트가 600MB 지점이라고 해 봅시다. 두 위치 사이에는 약 300MB의 거리, 즉 아직 복구 관점에서 고려해야 할 로그 구간이 있습니다. 이것은 더티 데이터가 정확히 300MB라는 뜻이 아닙니다. 동일 페이지가 여러 번 바뀌어 로그가 계속 쌓일 수 있기 때문입니다.

쓰기 생성 속도가 지속적으로 flush 진도를 앞서면 간격이 커집니다. 로그 용량을 늘리면 일시적인 폭주를 더 오래 흡수할 수 있지만 영원히 미룰 수는 없습니다. 결국 데이터를 내보내는 속도가 따라가야 합니다. 체크포인트는 모든 작업을 멈추고 전체 버퍼 풀을 한 번에 저장하는 버튼처럼 이해하지 않습니다. 실제로는 실행 중 페이지를 점진적으로 flush하며 복구 경계를 전진시킵니다.

redo와 undo가 함께 필요한 장면을 시간순으로 따라가기

상품 수량이 10인 행을 T1이 9로 바꾼 뒤 커밋하지 않았고, T2는 다른 행을 변경해 커밋했다고 합시다. 백그라운드 기록과 로그 flush는 트랜잭션 하나만을 위해 움직이지 않습니다. 장애 시점의 파일에는 일부 변경이 반영되고 일부는 빠질 수 있으며 미커밋 변경도 포함될 수 있습니다.

  1. 복구는 유효한 로그를 이용해 데이터 페이지가 필요한 상태까지 도달하도록 redo를 적용합니다.
  2. 트랜잭션의 확정 상태를 판별해 미완료 변경을 롤백할 필요가 있습니다.
  3. T1의 미확정 변경은 undo를 사용해 되돌려야 하므로 수량 9를 최종 결과로 남겨서는 안 됩니다.
  4. T2의 확정 변경은 내구성 조건이 충족된 범위에서 유지되어야 합니다.

이 과정은 이해를 위한 개념 순서입니다. 실제 복구는 병렬 작업이나 백그라운드 롤백이 섞일 수 있습니다. 중요한 것은 “redo를 재생하면 커밋된 행만 복구된다”가 아니라 “페이지 복원과 트랜잭션 확정 판정이 함께 필요하다”입니다. undo 자체의 변경도 복구 가능하게 관리되어야 하므로 undo는 단순한 애플리케이션 메모리 목록이 아닙니다.

binlog와 엔진의 확정을 맞추는 내부 2단계 커밋

binlog가 켜진 서버는 엔진의 데이터와 복제용 변경 기록이 서로 모순되지 않게 조정해야 합니다. 엔진만 커밋하고 binlog를 잃으면 복제본은 그 변경을 모를 수 있습니다. 반대로 binlog에는 성공한 변경처럼 남았는데 엔진은 취소했다면 역시 문제가 됩니다.

개념적으로 엔진의 준비(prepare), binlog 기록·동기화, 엔진 확정(commit)을 연결하는 내부 2단계 커밋을 생각할 수 있습니다. 중간에 장애가 나면 로그와 준비된 트랜잭션 정보를 함께 사용해 결론을 맞춥니다. 실제 단계의 그룹화와 동기화는 설정·구현에 영향을 받습니다. 이것은 외부 결제 API까지 자동으로 원자적으로 묶는 분산 트랜잭션 기능이라는 뜻이 아닙니다.

따라서 innodb_flush_log_at_trx_commit=1만 보고 복제·시점 복구까지 같은 내구성을 얻었다고 판단하지 않습니다. sync_binlog, 로그 보존, 백업, 저장장치 보장까지 살펴야 합니다. 설정은 숫자보다 어떤 장애에서 어떤 기록을 잃을 수 있는지로 설명하는 것이 좋습니다.

성공 여부를 모를 때 중복 차감을 막는 업무 설계

요청 ID가 R-100인 출고 처리에서 재고 차감과 처리 결과 저장을 같은 트랜잭션으로 묶고, 요청 ID에 UNIQUE 제약을 둔다고 합시다. 응답이 끊긴 클라이언트는 R-100으로 재요청합니다. 서버는 동일 ID의 처리 결과가 있는지 확인해 새 차감 없이 기존 결과를 돌려줄 수 있습니다. 다른 내용으로 같은 ID를 재사용하면 충돌로 처리해야 하므로 요청의 핵심 내용도 확인해야 합니다.

사전 SELECT만으로 중복을 막는 것은 부족합니다. 두 요청이 동시에 “없다”고 읽을 수 있어 최종 경쟁은 UNIQUE 제약과 트랜잭션으로 제어해야 합니다. 이미 커밋된 요청과 아직 처리 중인 요청도 구분해야 합니다. 이 설계는 DB 로그가 해결하지 못하는 “클라이언트의 결과 불확실성”을 업무 식별자로 다루는 방법입니다.

확장 수업 ① — 세 가지 기록을 하나의 재고 변경에 대입하기

수량을 10에서 9로 바꾸는 일을 생각해 봅시다. 데이터 페이지에는 조회할 현재 상태가 반영됩니다. undo에는 취소하거나 이전 버전을 구성하는 데 필요한 정보가, redo에는 장애 후 페이지 변경을 재현하는 데 필요한 정보가 기록됩니다. binlog가 활성화되어 있다면 복제와 시점 복구에 사용할 변경 이벤트도 별도 경로로 기록됩니다.

비유하면 현재 재고 장부, 이전 상태를 복원할 수정 이력, 시스템을 복구할 작업 기록, 다른 창고에 전달할 변경 내역입니다. 하지만 각 로그가 문자열 “10을 9로 바꿨다”를 동일하게 한 줄씩 보관하는 것은 아닙니다. redo는 엔진의 페이지 변경과 관련된 내부 기록이고, binlog는 설정과 형식에 따라 문장이나 행 변경 이벤트 등을 다룹니다. 목적이 다른 기록을 서로 대신 사용할 수 있다고 생각하면 복구 설계가 틀어집니다.

undo도 메모리에만 잠깐 남는 취소 버튼이 아닙니다. undo 페이지의 변경 역시 복구 체계의 보호를 받습니다. 커밋된 UPDATE라도 오래된 read view가 이전 버전을 필요로 하면 관련 undo를 즉시 버릴 수 없습니다. “커밋했으니 로그를 모두 지운다”는 모델 대신, 로그마다 언제 필요 없어지는지가 다르다는 모델을 가져야 합니다.

확장 수업 ② — 전원이 꺼지는 위치에 따라 무엇이 달라질까?

다음 표는 정상 동작하는 저장장치, redo 내구성 설정, InnoDB 복구를 전제로 한 개념 설명입니다. 실제 전원 차단 시험 결과가 아닙니다. 쓰기 캐시의 내구성 보장과 binlog 설정까지 맞아야 전체 요구를 만족할 수 있습니다.

장애 시점생각할 문제복구 관점
갱신했지만 커밋 결정 전일부 변경이 디스크에 먼저 갔을 수도 있음복구 후 미완료 트랜잭션을 취소할 수 있어야 함
필요한 커밋 기록이 안전하게 저장됨데이터 페이지는 아직 오래된 상태일 수 있음redo를 사용해 필요한 변경을 복구
커밋 완료 뒤 응답 전달 중서버는 완료, 클라이언트는 결과 불명재요청 전에 업무 식별자로 결과 확인
페이지 쓰기 중 일부만 기록됨페이지 자체가 불완전해질 수 있음doublewrite 등 페이지 복구 보호와 redo가 함께 필요

WAL의 뜻은 대응하는 데이터 페이지를 내보내기 전에 필요한 로그가 먼저 안전해야 한다는 순서입니다. 모든 데이터 페이지를 커밋 때까지 메모리에 붙잡아 두라는 뜻이 아닙니다. 커밋 전 데이터 페이지가 플러시되는 경우도 처리해야 하므로 미완료 변경을 취소할 수 있는 undo가 중요합니다.

실제 복구의 세부 단계는 내부 구현에 따르지만, 학습에서는 “페이지 상태를 복구할 정보”와 “업무 트랜잭션의 완료 여부”라는 두 질문을 분리하면 이해가 쉽습니다. redo를 적용했다는 사실만으로 모든 트랜잭션이 커밋되었다고 볼 수 없습니다.

확장 수업 ③ — 로그를 크게 해도 쓰기가 계속 빨라지지 않는 이유

redo는 무한한 기록 보관소가 아닙니다. 재사용할 공간을 확보하려면 이전 변경을 복구하는 데 필요한 범위를 줄여야 하고, 그 과정에 더티 페이지 플러시와 체크포인트 진행이 관련됩니다. 로그 생성 속도가 디스크가 받아내는 페이지 처리 속도를 장기간 초과하면, 큰 로그는 여유 시간을 늘릴 뿐 근본적인 처리량 부족을 없애지 못합니다.

설명용으로 처리되지 않은 작업이 초당 100MB씩 순증한다고 합시다. 추가 여유가 10GB라면 약 100초 정도의 완충량이라는 계산이 가능합니다. 실제 redo 공간의 사용 가능량과 체크포인트 정책은 이 단순 계산보다 복잡하므로 운영 설정값을 이 식 하나로 정하면 안 됩니다. 중요한 관계는 유입과 처리의 차이가 계속 양수이면 유한한 완충 공간은 결국 찬다는 것입니다.

로그 버퍼 부족, redo 공간 압박, 커밋 시 저장장치 동기화 지연은 별개 문제입니다. Innodb_log_waits 하나를 보고 redo 파일 크기만 늘리는 식으로 대응하지 말고 지표의 의미, 시간대의 쓰기량, 저장장치 지연과 트랜잭션 크기를 함께 확인하세요. MySQL 8.0에서도 세부 버전에 따라 redo 용량 설정 방식이 달라집니다.

확장 수업 ④ — 재고 차감의 ‘응답 유실’을 업무 수준에서 복구하기

요청 R-123이 재고를 차감하고 커밋했는데 응답이 유실되었습니다. 클라이언트가 같은 요청을 다시 보내면 단순 UPDATE는 다시 차감할 수 있습니다. 이를 막으려면 요청 식별자를 UNIQUE 제약으로 보호하고, 처리 기록과 재고 차감을 같은 트랜잭션에서 확정하는 구조를 생각할 수 있습니다.

  1. 입력값과 요청 ID를 검증합니다. 같은 요청 ID에 서로 다른 수량이 오면 동일 요청으로 무조건 받아들이지 않습니다.
  2. 처리 기록의 고유 키를 확보합니다. 이미 완료된 요청이면 저장된 결과를 반환하는 경로로 갑니다.
  3. 수량 조건을 포함한 원자적 UPDATE를 하고 영향 행 수를 검사합니다.
  4. 업무 결과와 처리 기록을 함께 커밋한 뒤 응답합니다.

동시에 같은 요청이 들어오면 고유 키 경쟁으로 대기하거나 중복 키 오류가 날 수 있습니다. 어떤 오류나 조회 결과를 완료·진행 중·실패로 해석할지까지 설계해야 합니다. RR 트랜잭션의 오래된 스냅샷으로 재확인하면 최신 처리 기록이 보이지 않을 수도 있으므로 재조회 시점과 트랜잭션 경계를 명확히 합니다. DB 로그가 보장하는 내구성과 API가 요구하는 멱등성은 서로 보완하는 장치입니다.

8. 상세 면접 Q&A

COMMIT 후 데이터 페이지가 아직 더티여도 괜찮나요?

복구에 필요한 로그가 내구성 조건을 충족했다면 가능합니다. crash 후 redo를 적용해 데이터 파일에 없던 변경을 재현할 수 있습니다. 커밋은 모든 데이터 페이지를 즉시 flush하는 명령이 아닙니다. 로그와 페이지를 분리해야 쓰기 성능과 복구가 함께 성립합니다.

Redo가 있는데 undo가 왜 필요한가요?

Redo는 변경을 재현하고 undo는 이전 상태를 구성합니다. 장애 복구 과정에서 아직 확정되지 않은 변경이 redo로 다시 나타날 수 있으므로 이를 취소할 정보가 필요합니다. 실행 중인 일반 SELECT가 과거 버전을 읽는 데도 undo가 사용됩니다.

Redo를 크게 하면 쓰기가 영원히 빨라지나요?

아닙니다. 일시적인 쓰기 증가를 흡수하고 체크포인트 압박을 완화할 수 있지만, 장기적으로 생성되는 더티 페이지를 저장장치가 처리해야 합니다. 버퍼 크기는 지속 처리량을 대체하지 못합니다. 복구 시간과 디스크 공간도 함께 고려합니다.

Binlog는 백업인가요?

완전한 기준 백업을 대체하지 않습니다. 기준 백업 이후의 이벤트를 적용해 특정 시점으로 복구하는 데 사용합니다. 기준 데이터, 필요한 로그 범위, 위치나 GTID, 복구 절차가 함께 있어야 합니다. 로그가 남아 있다는 사실만으로 복구 가능성을 확정하지 않습니다.

Doublewrite를 끄면 성능이 좋아지나요?

일부 비용은 줄 수 있지만 부분 페이지 쓰기에서의 복구 보호를 잃을 수 있습니다. 저장장치의 원자적 쓰기 지원 등 구체적인 전제 없이 끄는 것은 성능 튜닝으로 권할 수 없습니다. 먼저 실제 병목이 이 경로인지 측정해야 합니다.

커밋 응답이 끊기면 롤백된 것으로 처리하나요?

확정 여부를 모를 수 있습니다. 서버는 이미 확정했는데 응답만 유실되었을 수 있기 때문입니다. 요청 식별자·중복 방지 제약·결과 조회를 결합해 재시도 가능하게 설계합니다. 이 문제는 트랜잭션 격리 수준을 높이는 것만으로 해결되지 않습니다.

꼬리 질문: WAL이 있으니 데이터 페이지는 커밋 뒤에만 쓰나요?

답변: 아닙니다. WAL은 관련 로그가 데이터 페이지보다 먼저 안정화되어야 한다는 제약이지, 모든 페이지 쓰기를 커밋 이후로 제한하는 규칙이 아닙니다.

이유: 버퍼 풀 관리상 미커밋 변경이 있는 페이지도 기록될 수 있습니다. 장애 후 그 변경을 취소하기 위해 undo와 트랜잭션 상태 관리가 필요합니다. 커밋과 페이지 flush를 일대일로 묶으면 이 동작을 설명할 수 없습니다.

꼬리 질문: 로그 버퍼와 redo 파일 용량은 어떻게 다르나요?

답변: 로그 버퍼는 메모리의 기록 공간이고 redo 파일 용량은 디스크에서 로그를 유지·재사용할 수 있는 공간입니다.

판단: 큰 트랜잭션의 로그 버퍼 압박과 체크포인트가 못 따라가는 로그 용량 압박은 서로 다릅니다. 로그 버퍼만 키워도 지속적인 디스크 병목이 해결되지 않고, redo 용량만 키워도 커밋마다 필요한 flush 지연이 사라지지는 않습니다.

꼬리 질문: doublewrite와 redo는 같은 내용을 두 번 보관하나요?

답변: 목적과 기록 형태가 다릅니다. doublewrite는 부분 페이지 쓰기에서 사용할 온전한 페이지를 확보하고, redo는 필요한 변경을 재현하는 로그입니다.

비유: 찢어진 장부의 바탕을 복구할 복사본과 그 이후 수정 내역을 적은 메모를 함께 갖는 것입니다. redo가 있다는 이유만으로 torn page 보호를 불필요하다고 판단할 수 없습니다.

꼬리 질문: 커밋 지연이 높으면 인덱스를 추가해야 하나요?

답변: 로그 동기화나 저장장치 지연이 병목이면 인덱스 추가가 직접 해법이 아닐 수 있습니다. 오히려 유지해야 할 인덱스가 늘어 로그와 쓰기량이 증가할 수 있습니다.

진단: 문장의 행 탐색 시간, 잠금 대기, 커밋 단계 지연을 나누고 동기화 정책·스토리지 지연·동시 커밋 부하를 봅니다. 데이터 손실 조건을 바꾸는 설정 완화는 단순 성능 숫자만으로 결정하지 않습니다.

심층 면접: redo와 binlog가 둘 다 필요한데 한쪽만 기록되면 어떻게 되나요?

답변: 엔진의 변경 상태와 복제·복구용 변경 이력이 불일치할 수 있으므로 두 기록의 커밋 결정을 조정해야 합니다. MySQL은 binlog를 사용하는 트랜잭션의 내부 커밋 과정에서 엔진 준비 상태와 binlog 기록 등을 연결합니다.

구분: 이를 외부 서비스 여러 개를 묶는 분산 트랜잭션이 자동으로 해결되었다는 뜻으로 받아들이면 안 됩니다. 또 논리적인 조정 절차와 실제 전원 장애 시 내구성은 별개 축이므로 innodb_flush_log_at_trx_commit, sync_binlog 및 저장장치 보장을 함께 봅니다.

예시: API가 성공을 받은 데이터와 장애 후 복구된 데이터·복제 이력의 일치를 요구한다면 기본값을 추측하지 않고 실제 설정과 장애 범위를 기록하겠습니다.

심층 면접: COMMIT에 타임아웃이 났으니 같은 트랜잭션을 다시 실행하면 되나요?

답변: 곧바로 실행하지 않습니다. 응답을 못 받았다는 사실만으로 서버가 롤백했다고 판단할 수 없기 때문입니다. 서버가 이미 커밋한 뒤 네트워크만 끊겼을 수 있습니다.

업무 대응: 요청 식별자로 처리 결과를 조회하고, 같은 요청의 재전송이 중복 효과를 만들지 않도록 고유 제약과 처리 기록을 설계합니다. 같은 ID에 다른 입력이 붙는 경우도 거부해야 합니다.

한계: 외부 결제나 메시지 발송까지 포함하면 DB 트랜잭션 하나만으로 모든 효과가 원자적으로 묶이지 않습니다. 외부 시스템의 멱등키와 Outbox 등 별도 전달·재시도 설계를 연결하겠습니다.
