javap로 바이트코드 읽기: 객체·배열·호출·예외 실습

javac -g와 javap -c -v -p로 실제 class 파일을 읽고, new·dup·invoke·배열 명령을 해석한다

기준: Java SE 21 사양과 HotSpot JDK 21. 첨부 자료의 JVMS 23·JDK 17 발췌는 이 기준으로 대조했습니다. 설명 속 장애 상황은 학습용 가상 사례입니다. 예제는 외부 라이브러리 없이 실행할 수 있습니다.

1. javap는 역컴파일러와 무엇이 다른가

완성된 기계의 부품 목록과 조립 지시를 보는 것이 javap에 가깝습니다. 사람이 썼던 Java 문장을 완전히 복원하는 도구는 아닙니다. javap -c는 메서드의 JVM 명령을, -v는 상수 풀과 Code 속성 등 자세한 정보를, -p는 private 멤버까지 보여 줍니다. -l은 줄 번호·지역변수 표를 요청합니다.

javac -g는 디버그 정보를 생성합니다. 변수명과 줄 번호를 더 잘 연결할 수 있지만 실행의 논리적 결과가 달라지는 것은 아닙니다. 주석이나 개발자의 원래 의도까지 class 파일에 보존하는 옵션은 아닙니다. 근거: javap

2. 한 파일에서 여러 종류를 관찰하기

// file: Lesson06.java
public class Lesson06 {
    static final class Box {
        private final int value;
        Box(int value) { this.value = value; }
        int read() { return value; }
    }
    static int first(int[] values) {
        return values[0];
    }
    public static void main(String[] args) {
        Box box = new Box(7);
        int[] values = {box.read(), 9};
        System.out.println(first(values));
        try {
            first(new int[0]);
        } catch (ArrayIndexOutOfBoundsException e) {
            System.out.println("empty");
        }
    }
}

javac --release 21 -g Lesson06.java
java Lesson06
javap -c -v -p Lesson06
javap -c -v -p 'Lesson06$Box'

출력은 7, empty입니다. 중첩 클래스가 별도 class 파일로 생성된 점을 확인하세요. 셸에서 $를 변수 확장으로 오해하지 않도록 작은따옴표를 붙였습니다. 외부 클래스만 열고 Box 생성자 코드가 없다고 판단하면 잘못된 파일을 보고 있는 것입니다.

3. new·dup·invokespecial을 함께 읽기

new Box(7)에서는 보통 new, dup, 숫자 상수 적재, invokespecial ... <init>가 보입니다. new는 객체를 위한 공간을 할당하고 아직 생성자 초기화가 끝나지 않은 참조를 만듭니다. dup는 그 참조를 복제합니다. 생성자 호출에 참조 하나가 소비되어도 생성된 객체를 이어서 저장할 참조가 필요하기 때문입니다.

생성자의 이름은 class 파일에서 <init>입니다. 생성자 호출은 일반적인 가상 메서드 디스패치와 다르게 다루므로 invokespecial을 사용합니다. “new 명령 하나가 객체 할당과 Java 생성자 본문 실행 전체를 끝낸다”라고 외우지 마세요. 검증 규칙은 초기화되지 않은 참조의 사용도 제한합니다.

4. 호출 명령을 목적별로 구분하기

명령 대표 상황 읽을 때 확인할 것
invokestatic static 메서드 수신 객체 없이 인자 전달
invokevirtual 일반 클래스 인스턴스 메서드 실제 수신 객체와 디스패치
invokeinterface 인터페이스를 통한 호출 인터페이스 메서드 참조
invokespecial 생성자, super 호출 등 특별 취급 생성·상위 호출의 의미
invokedynamic 런타임에 연결되는 호출 지점 부트스트랩 메서드·호출 지점

Java 소스의 모든 메서드 호출이 invokevirtual은 아닙니다. Java 21의 문자열 연결에는 invokedynamic이 보일 수 있습니다. 람다도 관련 메커니즘을 사용하지만 “invokedynamic은 람다 전용”이라고 할 수 없습니다. class 파일의 BootstrapMethods 속성을 함께 보아야 연결 방식을 추적할 수 있습니다.

이 표는 명령의 일반적 용도를 이해하기 위한 것입니다. 정확한 대상 선택과 접근 규칙은 각 명령과 JVMS 해석·메서드 선택 절을 확인해야 합니다. JIT는 해당 의미를 유지하면서 호출을 인라이닝할 수도 있습니다.

5. 배열 초기화를 명령으로 따라가기

int[] values = {box.read(), 9}는 배열을 만들고 각 원소를 채우는 동작입니다. newarray int는 기본형 int 배열을 만들고, iastore는 인덱스 위치에 int를 저장합니다. 배열 참조·인덱스·값이 필요하므로 단순히 값 하나만 스택에 있으면 되는 명령이 아닙니다.

first에는 보통 aload_0, iconst_0, iaload, ireturn이 있습니다. 배열 참조를 올리고 인덱스 0을 올린 뒤 원소를 읽습니다. 참조가 null이면 NullPointerException, 길이가 0이면 범위 오류가 발생합니다. 참조 배열은 anewarray, aaload, aastore 등 다른 명령을 사용합니다. 배열 자체도 객체이며 length는 별도 arraylength 명령으로 읽습니다.

6. 예외 표와 줄 번호를 읽는 순서

메서드의 Exception table은 보호되는 바이트코드 범위, 처리할 예외 타입, 이동할 핸들러 위치를 보여 줍니다. 범위의 끝은 포함하지 않는 규칙입니다. 예제에서 빈 배열 접근이 난 명령 위치가 어느 보호 범위에 속하는지 확인하세요.

LineNumberTable은 바이트코드 위치를 소스 줄과 연결합니다. 소스 한 줄에 여러 명령이 대응할 수 있고, 최적화·컴파일 방식에 따라 단순 일대일 관계가 아닙니다. StackMapTable은 검증용 타입 상태이고, 예외 표는 제어 흐름의 핸들러 정보이며, 둘은 서로 다른 역할입니다.

7. 장애 사례: 내가 보는 코드와 배포된 코드가 다르다

개발자 화면에서는 메서드가 있는데 서버는 NoSuchMethodError를 낸다고 가정합니다. 소스만 다시 읽으면 빌드 결과에 다른 버전의 라이브러리가 들어갔다는 사실을 놓칠 수 있습니다. 실제 배포된 JAR의 대상 class를 javap로 확인하고 메서드 descriptor를 비교하세요.

다른 classpath의 같은 이름 클래스를 보고 있지 않은지도 확인합니다. 필요하면 javap -classpath에 배포 JAR 경로를 명시하고 로드 로그로 실제 출처를 확인합니다. javap는 조사용 도구이지 실행 중인 JVM의 모든 JIT 기계 코드를 보여 주는 도구는 아닙니다. 바이트코드가 같아도 실행 프로파일에 따라 JIT 결과가 달라질 수 있습니다.

더 깊이: switch와 finally도 명령 목록으로 읽기

정수 switch에는 tableswitch나 lookupswitch가 나타날 수 있습니다. 전자는 인덱스 범위에 대응하는 점프 표, 후자는 키와 대상의 대응 목록을 생각하면 이해하기 쉽습니다. 키의 분포와 컴파일러 선택 등에 따라 결과가 다르며 소스에 switch가 있다는 사실만으로 항상 같은 명령이라고 단정하지 않습니다. 문자열 switch는 추가 비교 과정이 생길 수 있습니다.

finally는 JVM의 'finally 명령 하나'로 전부 실행되는 기능이 아닙니다. javac는 정상 경로와 예외 경로에 필요한 정리 동작과 예외 처리 표를 구성합니다. try-with-resources에서는 닫는 중 예외가 발생했을 때 원래 예외와 suppressed 예외를 다루는 코드도 생길 수 있습니다. 명령이 길어졌다고 자동으로 나쁜 코드가 된다는 뜻은 아닙니다.

javap로 읽을 때는 첫째 메서드 descriptor, 둘째 정상 경로의 입력과 결과, 셋째 분기 대상, 넷째 예외 표, 다섯째 상수 풀 순서로 좁혀 보세요. 처음부터 verbose 출력의 모든 #번호를 외우려 하면 실제 제어 흐름을 놓치기 쉽습니다.

심화 Q. 소스 한 줄에서 예외가 났다면 명령도 한 개만 조사하면 되나요?

한 줄에 객체 생성·메서드 호출·배열 접근 등이 함께 있을 수 있습니다. LineNumberTable은 명령과 소스의 대략적 연결을 제공하므로 같은 줄에 여러 실패 지점이 있을 수 있습니다.

긴 표현식을 나누어 재현하거나 예외 메시지·호출 스택·바이트코드 범위를 함께 확인해야 합니다. 줄 번호 하나를 실제 CPU 명령 하나로 해석하지 않습니다.

차근차근 이해하기: javap 출력에서 길을 잃지 않는 순서

javap 출력 전체를 처음부터 암기하려 하지 마세요. 먼저 메서드 이름과 descriptor, 다음 Code의 명령 목록, 그다음 명령이 참조하는 상수 풀 항목, 마지막으로 예외 표와 디버그 정보를 읽으면 됩니다. descriptor는 메서드가 어떤 타입의 인자를 받고 무엇을 돌려주는지를 JVM 형식으로 적은 문자열입니다. ()V는 인자 없음과 void 반환, (I)I는 int 하나를 받아 int를 반환한다는 뜻입니다.

명령 앞의 0:, 1:, 4: 같은 숫자는 Java 소스 줄 번호가 아니라 메서드 Code 내부의 바이트 오프셋입니다. 명령 길이가 모두 같지 않으므로 숫자가 한 칸씩 증가하지 않을 수 있습니다. #7, #12 같은 표기는 별도로 상수 풀의 항목 번호입니다. 오프셋과 상수 풀 번호를 같은 주소라고 해석하면 호출 대상을 잘못 찾게 됩니다.

new와 dup를 손으로 따라가기

new Box(7)의 대표적인 명령 흐름을 단순화해 보겠습니다. 실제 상수 풀 번호와 오프셋은 빌드에 따라 달라집니다.

사건 개념적 피연산자 스택 설명
new Box [u] 아직 생성자 호출이 끝나지 않은 객체의 참조
dup [u, u] 같은 참조 값을 하나 더 준비
정수 7 적재 [u, u, 7] 생성자 인자 준비
invokespecial Box.<init> [box] 수신 참조와 인자가 소비되고 생성자 정상 완료
astore [] 남겨 둔 참조를 지역변수에 저장

여기서 u는 설명을 위한 기호이며 Java 변수 이름이 아닙니다. 중요한 점은 생성자가 객체를 반환해서 스택에 box가 생긴 것이 아니라는 것입니다. 생성자의 JVM descriptor 반환 타입은 void입니다. 미리 복제해 둔 참조가 생성자 정상 완료 후 사용할 수 있는 참조로 남습니다. 생성자에서 예외가 발생하면 이 정상 완료 경로로 이어지지 않습니다.

예외 표는 명령 목록 옆의 별도 길 안내다

예외 표에는 보호 범위의 시작과 끝, 핸들러 위치, 처리할 예외 타입이 기록됩니다. 범위의 끝 오프셋은 포함하지 않습니다. 특정 명령이 예외를 던졌을 때 그 명령 위치가 보호 범위에 속하고 타입이 맞아야 해당 핸들러가 후보가 됩니다. catch가 있으니 메서드 어느 줄에서 난 모든 예외를 잡는다는 뜻은 아닙니다.

예제의 배열 인덱스를 바꾸어 정상 읽기와 범위 초과를 비교하면 좋습니다. 배열 읽기 명령 자체에는 참조와 인덱스를 소비해 원소를 얻는 의미가 있습니다. 예외 처리는 별도 표가 그 명령의 실패 경로를 연결합니다. 소스의 try-catch 블록 모양만 보지 않고 어느 명령이 어떤 범위에 들어가는지를 확인하는 것이 핵심입니다.

실제 배포본을 조사하는 실무 순서

실행 프로세스가 어떤 JAR과 클래스 경로를 사용하는지 먼저 확보합니다. 다음으로 그 산출물 안의 정확한 클래스에 javap를 적용합니다. 개발 PC에서 다시 빌드한 다른 파일을 보면 장애 시점과 다른 코드를 조사할 수 있습니다. 메서드 이름이 같아도 인자 타입과 반환 타입을 포함한 descriptor, 클래스 로더, 라이브러리 버전을 함께 비교해야 합니다.

바이트코드는 프로그램의 중간 표현입니다. “이 명령이 있으므로 CPU가 매번 이 비용을 지불한다”라는 결론은 아직 이릅니다. 실제 실행에는 인라이닝과 여러 최적화가 개입할 수 있습니다. javap는 배포 코드의 구조와 의미를 확인하는 도구로, 프로파일링은 실제 시간의 사용처를 관찰하는 도구로 연결해서 쓰세요.

확인 문제. LineNumberTable의 같은 줄에 명령이 여러 개면 어느 명령에서 실패했나요?

판단: 소스 줄 번호만으로는 하나로 좁혀지지 않을 수 있습니다. 한 줄 안에 객체 생성, 메서드 호출, 배열 접근이 함께 있을 수 있기 때문입니다.

조사: 예외 타입과 메시지, 해당 줄에 대응하는 명령 범위, 입력값을 함께 봅니다. 복잡한 한 줄을 여러 문장으로 나누어 재현하면 관찰 지점을 만들기 쉽습니다. 다만 재빌드본과 실제 장애 산출물의 차이도 기록해야 합니다.

꼬리질문: 디버그 정보를 넣으면 변수 값을 알 수 있나요? LocalVariableTable은 이름과 범위 같은 정보를 제공할 수 있지만 당시 실행값을 저장한 기록은 아닙니다. 과거 값을 보려면 당시의 로그나 녹화·덤프 등 별도 증거가 필요합니다.

8. 상세 면접 Q&A

Q1. -c와 -v의 차이는 무엇인가요?

-c는 메서드 바이트코드를 해석해 보여 줍니다. -v는 상수 풀, 클래스 버전, 속성 등 더 자세한 출력을 제공합니다. 먼저 -c로 흐름을 잡고 #번호나 descriptor의 의미가 필요할 때 -v로 넓히면 읽기 쉽습니다.

구체적으로: -c는 실행 명령을 중심으로 보고, -v는 descriptor·상수 풀·속성 등 문맥을 더 제공합니다. 처음에는 관심 메서드 하나를 고른 뒤 필요할 때 주변 정보를 확장하는 편이 좋습니다.

꼬리질문까지: 디버그 정보가 없으면 -v를 써도 원래 변수 이름이 마법처럼 복원되지는 않습니다.

Q2. new 뒤에 왜 dup가 나오나요?

생성자 호출에 사용할 참조와 호출 뒤 사용할 참조를 확보하는 전형적인 패턴입니다. 생성자 호출은 반환 타입이 void이므로 생성자가 객체 참조를 결과로 돌려주는 것으로 이해하면 안 됩니다. new가 만든 참조를 유지하는 흐름을 스택으로 추적해야 합니다.

구체적으로: 생성자 호출은 수신 객체 참조와 인자를 소비하고 void로 완료됩니다. 호출 뒤 참조를 저장할 수 있도록 같은 참조를 앞서 하나 남겨 두는 전형적인 패턴입니다.

꼬리질문까지: 생성자가 객체를 반환한다는 설명과 구분하고, 생성자가 예외로 종료되면 정상 저장 경로가 실행되지 않는 점도 확인하세요.

Q3. 배열 접근은 단순 메모리 읽기인가요?

Java 의미에서는 null·범위·타입 규칙을 만족해야 합니다. JVM은 최적화로 검사가 불필요하다고 증명하면 제거할 수 있지만 결과와 예외 의미는 지켜야 합니다. JIT가 검사 명령을 줄였다고 언어 규칙이 사라지는 것은 아닙니다.

구체적으로: 배열 참조가 null인지, 인덱스가 범위 안인지 같은 언어 의미가 필요합니다. 명령 하나라고 해서 아무 검사도 없는 임의 주소 접근과 같은 것은 아닙니다.

꼬리질문까지: 최적화가 일부 검사를 없앨 수 있어도 프로그램이 관찰하는 예외 의미를 함부로 바꿀 수는 없습니다.

Q4. javap로 원래 변수명을 항상 알 수 있나요?

지역변수 디버그 정보가 존재해야 더 많은 이름을 볼 수 있습니다. 인덱스만 남아 있는 class에서 원래 이름·주석·소스 표현을 완전히 복구하는 것은 보장되지 않습니다. -g를 사용한 학습용 결과와 배포 결과를 구분합니다.

구체적으로: LocalVariableTable 같은 속성이 있어야 이름과 유효 범위에 대한 단서를 얻을 수 있습니다. 난독화나 컴파일 옵션에 따라 원래 이름을 얻기 어려울 수 있습니다.

꼬리질문까지: 디버그 이름과 실행 당시 값은 다릅니다. javap는 과거 메모리 상태를 재생하는 도구가 아닙니다.

Q5. invokevirtual이 보이면 실제 CPU도 매번 가상 호출하나요?

명령은 가상 호출의 의미를 표현하지만 JIT는 실제 타입 프로파일을 활용해 호출을 인라이닝하거나 직접적인 경로로 최적화할 수 있습니다. 의미와 최적화 구현이 다릅니다. 타입이 달라져 가정이 깨지면 다른 경로나 역최적화가 필요할 수 있습니다.

구체적으로: 프로파일상 수신 타입이 하나라면 JIT가 인라인하거나 호출 대상을 특화할 수 있습니다. 바이트코드는 가능한 의미를, 기계 코드는 해당 실행의 구현을 보여 줍니다.

꼬리질문까지: 성능 병목을 논할 때에는 javap와 프로파일링·컴파일 정보를 연결해야 합니다.

Q6. NoSuchMethodError를 javap로 어떻게 조사하나요?

호출하는 쪽의 상수 풀에 기록된 메서드 이름·descriptor와, 실행 시 로드되는 대상 클래스의 메서드 목록을 비교합니다. 컴파일 때 기대한 버전과 실행 때의 버전이 다르면 불일치가 드러날 수 있습니다. 실제 로드 경로를 함께 확인해야 다른 파일을 검사하는 실수를 피할 수 있습니다.

구체적으로: 메서드 이름뿐 아니라 호출자 상수 풀의 소유 타입과 descriptor를 실제 라이브러리의 선언과 비교합니다. 인자가 같아 보여도 반환 타입 등 바이너리 계약이 달라졌을 수 있습니다.

꼬리질문까지: 개발 PC의 소스 대신 장애 배포 산출물을 조사하고 어떤 로더가 로드했는지도 확인하세요.

먼저 비유로 이해하기

건물 설계도는 javap가 읽는 바이트코드이고 현장의 실제 공사 동선은 JIT가 최적화한 기계어에 가깝다. 설계도를 읽었다고 시공 순서까지 확정할 수는 없다.

구현 내부에서는 정확히 무엇이 일어날까?

javap -c는 클래스 파일에 담긴 바이트코드를 보여준다. JVM이 JIT로 생성한 최종 기계어를 그대로 보여주는 도구는 아니다. 컴파일 옵션·타깃 JDK·합성 메서드·람다 변환 등에 따라 같은 의도라도 바이트코드는 달라질 수 있다.

여기서 중요한 구분은 Java/JVM 사양이 보장하는 의미와 HotSpot JDK 21의 실제 구현 선택이다. 성능과 관측 결과는 JDK 빌드·옵션·실행 환경에 따라 달라질 수 있으므로 명령 출력 자체를 모든 JVM의 불변 법칙으로 일반화하지 않는다.

직접 확인하는 터미널 실험

javap -c -p -v Main

예제 실행 시에는 본문에서 제공한 Java 파일을 먼저 컴파일하고, 가능하면 Java 21의 동일한 런타임에서 실행한다. 결과를 기록할 때는 관측값과 그 값으로부터 내린 추론을 따로 적어 보자.

현업에서 따라가는 진단 순서

  1. 증상을 시간·환경·재현 입력과 함께 기록한다.
  2. 해당 현상이 사양 위반인지, JVM 구현·옵션의 선택인지 먼저 나눈다.
  3. 관련 로그·바이트코드·프로세스 상태를 수집해 반례가 없는지 검토한다.
  4. 문제를 일으킨 조건 하나씩만 변경한 뒤 같은 명령으로 다시 측정한다.

추가 심화 면접 Q&A

invokevirtual과 invokestatic은 무엇이 다른가요?

invokevirtual은 수신 객체를 기준으로 가상 메서드 디스패치를 수행한다. invokestatic은 클래스의 정적 메서드를 호출한다. invokespecial·invokeinterface·invokedynamic도 서로 다른 연결 규칙이 있다.

추가 질문이 나오면 먼저 정확한 용어를 정의하고, 성립 조건과 예외, 실제 진단 방법을 차례로 설명하면 좋다.
