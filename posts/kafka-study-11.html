Kafka 4.3 업그레이드와 KRaft를 안전하게 이해하기

Kafka는 최신 버전으로 올린다고 끝나는 도구가 아닙니다. 실행 바이너리, 클러스터 메타데이터, 브로커 가용성, 클라이언트 호환성을 구분해야 합니다. 쉬운 비유로 시작해 실제 운영 절차까지 공부해 봅니다.

1. 업그레이드가 왜 위험할까?

먼저 쉬운 비유로

학교 운동장을 공사할 때 학생을 모두 내보내지 않고 한 구역씩 공사한다고 상상해 봅시다. 다만 공사 중 구역 사이 이동 통로가 막히면 학교 운영은 멈춥니다.

Kafka가 실제로 하는 일

Kafka Broker를 순서대로 업그레이드하는 동안 오래된 Broker와 새로운 Broker가 공존할 수 있습니다. 이때 클라이언트 API 버전, Broker 설정, 메타데이터 버전, 리더 이동, ISR 상태를 함께 고려해야 합니다.

실무에서 반드시 확인할 점

운영에서는 소프트웨어 파일만 바꾼다고 끝나지 않습니다. 데이터 복제 상태와 메타데이터 버전, 클러스터 기능이 어떻게 활성화되는지를 알아야 합니다.

2. Kafka 4.3은 ZooKeeper 모드를 지원할까?

먼저 쉬운 비유로

운영 일지를 보관하던 장소가 바뀌었는데 옛날 창고만 사용하려 하면 새 시설에 들어갈 수 없습니다.

Kafka가 실제로 하는 일

Kafka 4.3은 KRaft 전용입니다. 공식 4.3 업그레이드 안내는 ZooKeeper 모드 클러스터라면 **4.3 업그레이드 전에 KRaft로 마이그레이션**하라고 명시합니다. KRaft 상태라 해도 너무 오래된 버전에서는 먼저 3.9.x로 이동하는 경로가 권장될 수 있습니다.

실무에서 반드시 확인할 점

'Kafka는 ZooKeeper가 필요하다'는 옛 자료를 현재 버전의 진실로 외우지 마세요. KRaft에선 Controller Quorum이 메타데이터 합의를 담당합니다.

3. 3.3.x~4.2.0에서 4.3.0으로 업그레이드

먼저 쉬운 비유로

교실을 한 번에 비우지 않고 A반부터 공사합니다. A반이 정상인지 확인한 뒤 B반으로 옮겨 갑니다.

Kafka가 실제로 하는 일

공식문서는 해당 버전 범위의 KRaft 모드 서버에 대해 Broker를 한 대씩 종료→새 바이너리 적용→재시작하는 롤링 절차를 설명합니다. 모든 Broker를 교체한 뒤에는 동작과 성능을 검증하고 feature version을 갱신하는 순서를 제시합니다.

실무에서 반드시 확인할 점

일괄 재시작하면 ISR 과반이나 가용한 Replica 수가 급격히 줄 수 있습니다. 브로커별 리더·팔로워 상태를 확인하면서 진행하세요.

4. metadata.version은 실행 버전과 무엇이 다를까?

먼저 쉬운 비유로

휴대폰 운영체제를 업데이트했다고 모든 새로운 기능을 그 즉시 켜는 것은 아닙니다. 업데이트 후 기능 활성화 단계를 나눌 수 있습니다.

Kafka가 실제로 하는 일

Broker가 실행 중인 Kafka 바이너리 버전과 클러스터의 메타데이터 기능 버전은 별도의 개념입니다. 롤링 업그레이드 동안 호환성을 유지하다 모든 노드가 안전하게 올라온 뒤 feature를 최종화하는 방식입니다.

실무에서 반드시 확인할 점

공식문서는 4.3의 메타데이터 변경 때문에 클러스터 metadata downgrade가 지원되지 않는다고 명시합니다. 업그레이드 전 '언제 되돌릴 수 없는가'를 명확히 해야 합니다.

5. 공식 업그레이드 명령을 읽어보자

먼저 쉬운 비유로

운영 담당자가 모든 교실을 점검하고 마지막으로 새 규칙을 확정한다고 생각해요.

Kafka가 실제로 하는 일

공식 4.3.0 안내에는 `bin/kafka-features.sh --bootstrap-server localhost:9092 upgrade --release-version 4.3` 형식의 명령이 제시됩니다. 이는 Broker를 모두 교체하고 호환성과 성능을 검증한 뒤 수행하는 최종화 단계이지, 처음부터 무턱대고 실행할 명령이 아닙니다.

실무에서 반드시 확인할 점

localhost는 예시입니다. 실제 운영 클러스터의 부트스트랩 주소, 현재 feature 상태, 다운그레이드 제약과 변경 승인을 검증해야 합니다.

6. 4.3.1은 왜 주목해야 할까?

먼저 쉬운 비유로

교과서가 새 판으로 바뀌면 새로 추가된 내용뿐 아니라 인쇄 오류가 고쳐지기도 합니다.

Kafka가 실제로 하는 일

제공된 02번 PDF의 4.3.1 변경 목록에는 Kafka Streams의 RocksDB 컬럼 패밀리 핸들과 옵션 해제 관련 native memory leak 수정 및 재시작 시 stale offset으로 인해 OffsetOutOfRangeException이 발생할 수 있는 문제의 수정이 언급됩니다. Admin 파티션 리더 API가 종료된 리더 캐시 때문에 대기하는 문제 등도 언급됩니다.

실무에서 반드시 확인할 점

버전 숫자가 조금 올랐다고 무조건 위험이 적거나 많다고 할 수 없습니다. 해당 버전의 실제 변경 항목과 서비스 사용 기능을 매핑해야 합니다.

7. Kafka 클라이언트까지 동시에 바꿔야 할까?

먼저 쉬운 비유로

학교 건물을 새로 지어도 학생들 모두 새 가방을 같은 날 구입할 필요는 없는 경우가 있습니다.

Kafka가 실제로 하는 일

브로커와 Java 클라이언트는 프로토콜을 통해 통신하며 버전 조합별 지원 범위를 확인해야 합니다. 새 Kafka Broker와 기존 Spring Kafka 클라이언트가 공존할 수 있는지 실제 버전 지원표와 회귀 테스트로 검증합니다.

실무에서 반드시 확인할 점

Java 21/Spring Boot 서비스를 운영한다면 Spring Kafka의 kafka-clients 전이 의존 버전과 Broker 버전을 구분하고, 빌드 파일에서 실제 해결된 의존성 버전을 확인하세요.

8. 브로커를 한 대 종료하면 무슨 일이 일어날까?

먼저 쉬운 비유로

같은 서류의 사본을 세 사무실에 보관한다면 한 사무실이 쉬는 동안 다른 사무실이 서류를 제공할 수 있습니다.

Kafka가 실제로 하는 일

9. 리밸런스와 리더 선출을 구별하자

먼저 쉬운 비유로

학생 모둠 구성원을 다시 나누는 일과 학교 반장을 새로 뽑는 일은 다릅니다.

변경 전에 클러스터 메타데이터와 구성을 백업하고, 업그레이드 완료 기준 및 진행 중단 조건을 명시하세요.

11. 업그레이드 중 장애가 발생하면?

먼저 쉬운 비유로

공사 중 다른 구역의 전기가 끊어지면 다음 공사를 즉시 진행하지 않고 먼저 피해를 확인합니다.

Kafka가 실제로 하는 일

Broker 재시작 실패나 ISR 급감이 발생했다면 다음 Broker 종료를 중지합니다. 관련 Broker 로그와 controller 상태, 리더 선출 결과, 디스크·네트워크·인증 연결을 확인합니다. 아직 feature 최종화 전인지 여부에 따라 롤백 가능한 범위가 달라집니다.

실무에서 반드시 확인할 점

메타데이터 버전까지 최종화한 후에는 이전 바이너리로 단순 다운그레이드가 불가능할 수 있습니다. 그래서 최종화는 제일 마지막에 수행해야 합니다.

면접 질문 10개 — 눌러서 정답 보기

Q1. ZooKeeper 모드에서 곧바로 Kafka 4.3으로 올려도 되나요?

안 됩니다. Kafka 4.3은 KRaft 전용이므로 ZooKeeper 모드 클러스터는 먼저 공식 지원 경로를 따라 KRaft로 마이그레이션해야 합니다.

Q2. Kafka Broker 바이너리를 전부 4.3으로 바꾸면 끝인가요?

아닙니다. 혼합 버전 구간과 안정성을 검증하고 feature/metadata 버전 최종화를 별도 단계로 고려해야 합니다.

Q3. 왜 모든 Broker를 동시에 재시작하면 위험한가요?

다수의 리더와 복제본이 동시에 사라져 쓰기·읽기 가용성이 크게 흔들릴 수 있습니다. 순차 롤링과 ISR 확인이 중요합니다.

Q4. metadata.version을 바로 4.3으로 올려도 되나요?

모든 Broker 업그레이드·검증이 끝난 뒤 공식 절차에 따라 진행해야 합니다. 4.3 메타데이터 변경 이후 다운그레이드 제약에 유의하세요.

Q5. 4.3.1 변경에서 Streams 운영자가 신경 쓸 부분은?

RocksDB 컬럼 패밀리 관련 native memory leak 수정과 재시작의 OffsetOutOfRangeException 관련 수정이 원문에 나옵니다. 해당 기능과 인프라 사용 여부를 대조해야 합니다.

Q6. Consumer Rebalance와 Partition Leader Election은 같은가요?

아닙니다. 전자는 소비자 그룹의 파티션 담당 변경이고 후자는 브로커 복제본 중 리더 선택입니다.

Q7. RF=3이면 Broker 한 대 종료가 무조건 안전한가요?

아닙니다. ISR 상태, minISR, Leader 분포 및 클러스터 부하에 따라 Producer 쓰기 실패나 지연이 발생할 수 있습니다.

Q8. 업그레이드의 '중단 조건'은 무엇으로 정하나요?

ISR 지속 감소, Offline Partition 발생, 응답 오류 급증, Consumer 처리가 복구 불가능한 수준으로 지연되는 상황처럼 서비스 SLO와 데이터 안전에 연결되는 지표를 사전에 정합니다.

Q9. Java 클라이언트 버전도 Broker와 항상 같아야 하나요?

반드시 같을 필요는 없지만 실제 지원 범위와 Spring Kafka 의존성 버전 호환성을 검증해야 합니다.

Q10. feature 최종화 후 문제가 생기면 이전 버전으로 되돌리면 되나요?

버전·메타데이터 변경에 따라 다운그레이드가 불가능할 수 있습니다. 4.3 공식 안내는 메타데이터 변경에 따른 다운그레이드 미지원 조건을 명시합니다.
