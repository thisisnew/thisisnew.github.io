실습과 점검

테스트 토픽과 격리된 Kafka 클러스터에서 각각의 이벤트 Key, Partition, Offset, 처리 성공 여부를 기록하며 결과를 추적하세요. 상태를 사용하는 기능은 앱 재시작 시 복구 시간도 측정합니다. 운영 클러스터의 오프셋을 임의로 수정하거나 Topic을 삭제해서는 안 됩니다.

심화 강의 1. Streams DSL은 무엇을 줄여줄까?

물류센터에 입고 이벤트가 들어오면 여러 단계를 거쳐 처리한다고 상상해 봅시다. 잘못된 이벤트를 제거하고(filter), 필요한 값으로 변환하고(mapValues), 상품별로 모아(groupByKey), 합계를 구하고(aggregate), 결과를 다른 Topic에 쓰는(to) 흐름입니다.

Kafka Streams DSL은 이를 Java 메서드 체인으로 표현하도록 도와줍니다. 다만 코드가 짧아졌다고 내부 작업이 공짜가 된 것은 아닙니다. 상태 저장소, 내부 Changelog Topic, 재파티셔닝 Topic, 직렬화·역직렬화, 리밸런스 등이 필요할 수 있어요.

어떤 연산이 단순한 무상태 Stateless 연산이고 어떤 연산이 상태를 저장하는 Stateful 연산인지 구분하면 코드를 읽을 때 병목과 복구 비용을 예측할 수 있습니다.

심화 강의 2. KStream과 KTable의 결정적 차이

KStream은 지나가는 사건들의 기록입니다. 같은 주문 ID로 CREATED, PAID, SHIPPED 레코드가 오면 세 사건을 각각 관찰하는 데 적합합니다. KTable은 키를 기준으로 현재 상태를 표현합니다. 주문 ID의 최신 상태를 기억하는 표라고 생각할 수 있어요.

예를 들어 KStream에서 count() 집계를 수행하면 결과는 시간이 지나며 갱신되는 KTable 형태가 됩니다. 즉 '지금 상품 A의 이벤트를 몇 건 보았는가'라는 상태를 표현할 수 있습니다.

물론 KTable도 내부적으로는 Kafka 로그를 통해 갱신을 전달받으며 초기 데이터 로딩과 상태 복구에 주의해야 합니다. 이벤트 이력이 필요한 감사 용도와 최종 상태가 필요한 캐시 재구축은 서로 다른 요구사항입니다.

심화 강의 3. filter, mapValues, selectKey가 실제로 바꾸는 것

filter는 레코드를 버리거나 통과시키는 연산입니다. mapValues는 키는 그대로 둔 채 값만 변환하는 편리한 연산입니다. selectKey는 레코드의 키를 바꾸기 때문에 그 후 집계나 조인에서 재파티셔닝이 필요할 수 있어요.

예를 들어 주문 ID를 키로 입력받다가 상품 ID를 키로 집계하고 싶다고 해봅시다. selectKey로 상품 ID로 바꾼 뒤 groupByKey를 사용하면 상품별 집계를 만들 수 있습니다. 하지만 처음 Producer가 주문 ID 기준으로 토픽 파티션에 보낸 데이터는 상품 ID별로 분포되지 않았을 수 있어요.

이때 Streams가 내부 repartition Topic을 사용하여 새 키에 맞게 데이터를 다시 나누는 일이 생길 수 있습니다. 내부 토픽은 네트워크·디스크·복제 비용을 만들어 내며 권한이 부족하면 애플리케이션 오류가 발생할 수 있어요.

심화 강의 4. Count 실습 — 코드와 상태 변화

StreamsBuilder builder = new StreamsBuilder();
KStream<String, String> events = builder.stream("order-events");

KTable<String, Long> counts = events .filter((key, value) -> key != null && value != null) .groupByKey() .count(Materialized.as("order-counts"));

counts.toStream().to("order-count-updates", Produced.with(Serdes.String(), Serdes.Long()));

Properties props = new Properties(); props.put(StreamsConfig.APPLICATION_ID_CONFIG, "order-counter"); props.put(StreamsConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092"); props.put(StreamsConfig.DEFAULT_KEY_SERDE_CLASS_CONFIG, Serdes.StringSerde.class); props.put(StreamsConfig.DEFAULT_VALUE_SERDE_CLASS_CONFIG, Serdes.StringSerde.class);

KafkaStreams streams = new KafkaStreams(builder.build(), props); streams.start(); ~~~

위 예제에서 key=A인 이벤트를 세 번 받으면 A의 Count는 1→2→3으로 변합니다. count가 리턴하는 것은 KTable이며, toStream으로 변경 결과를 이벤트처럼 전달할 수 있어요. 이 코드는 학습용이고 운영에서는 종료 훅, 예외 처리, 보안 설정과 상태 복구 정책이 추가로 필요합니다.

질문: 앱을 두 대로 늘리고 Kafka 파티션이 하나라면 Count가 두 배 빨라질까요? 보통 그렇지 않습니다. 해당 파티션을 처리하는 Task 수와 상태 저장소 배치가 병렬성을 제한합니다.

심화 강의 5. 윈도우 집계: 늦게 도착한 이벤트는?

10시부터 10시 5분까지 일어난 주문을 집계한다고 해봅시다. 주문이 실제 발생한 시각과 Kafka에 도착한 시각은 다를 수 있어요. 네트워크 지연으로 10시 3분 이벤트가 10시 7분에 들어올 수 있습니다.

Streams의 Window 집계는 시간 구간을 정의하며 이벤트에 기록된 Timestamp와 Timestamp Extractor 정책이 어느 구간에 들어갈지 영향을 줍니다. grace는 늦게 도착하는 레코드를 얼마나 받아들일지와 관련된 개념입니다. 단순히 Broker 수신 시각으로 시간을 자르기만 한다면 실제 비즈니스 발생 시각과 집계가 달라질 수 있겠지요.

실무에서 '어제 집계가 오늘 갑자기 바뀌었다'는 문제가 있다면 Window 정책, 이벤트 시각, 늦게 도착한 이벤트, 집계 출력 설정을 같이 확인하세요.

심화 강의 6. Join: 왜 키와 파티션이 중요한가?

주문 이벤트와 회원 등급 데이터를 연결하려면 같은 회원 ID를 기준으로 찾아야 합니다. KStream-KTable Join은 이벤트를 현재 테이블 상태와 연결하는 대표적인 패턴입니다. KStream-KStream Join은 시간 창과 각 스트림의 도착 시각 관계를 고려해야 하는 경우가 많습니다.

Join 전에 양쪽의 키와 파티션 분포를 맞춰야 할 수 있습니다. 조인 키가 서로 다르거나 직렬화 방식이 일치하지 않으면 예상대로 결합되지 않습니다. Repartition이 발생하면 내부 토픽 비용도 고려해야 합니다.

중요한 질문: 'Join은 Kafka 토픽에 JOIN SQL을 직접 실행하는 건가요?' → 아닙니다. Streams 라이브러리의 토폴로지 연산이며 상태 저장과 시간 모델에 따라 동작합니다.

심화 강의 7. 장애·리밸런스·상태 복구

상태 저장 집계에서 특정 Task가 죽으면 다른 인스턴스가 Task를 인수받아야 할 수 있습니다. 이때 Changelog Topic을 통해 State Store를 복구하는 데 시간이 걸릴 수 있어요. 초기 처리량만 보고 용량을 산정하면 장애 중 회복 시간이 너무 길어질 수 있습니다.

내부 토픽 ACL, state.dir의 디스크 여유, RocksDB 상태 저장소의 사용량, Consumer Lag과 Streams Task 상태를 함께 살펴보세요. 또 Kafka Streams의 exactly-once는 외부 MySQL 업데이트를 자동으로 원자화하지 않습니다.

운영 연습: 일부러 테스트 앱을 중지하고 다시 실행한 뒤 Count 결과가 올바르게 복원되는지 검증해 보세요. 프로덕션에서 실습용 상태 초기화 명령을 실행하지는 마세요.
