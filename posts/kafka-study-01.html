1. Kafka 없이 서비스를 만든다면 어떤 일이 생길까?

온라인 쇼핑몰을 상상해 보겠습니다. 사용자가 주문 버튼을 누르면 주문 서비스는 주문을 저장합니다. 그런데 주문 후 해야 할 일이 많아요.

① 재고를 차감해야 합니다. ② 결제 내역을 기록해야 합니다. ③ 고객에게 알림을 보내야 합니다. ④ 배송 요청을 만들어야 합니다. ⑤ 추천 서비스에도 구매 기록을 전달해야 합니다.

Kafka가 없다면 주문 서비스가 다른 서비스들의 HTTP API를 일일이 호출할 수 있습니다. 서비스가 다섯 개면 다섯 곳에 네트워크로 요청해야 하고, 알림 서비스가 갑자기 느려졌을 때 주문 요청까지 느려지게 만들 위험이 있습니다. 물론 비동기 작업 큐나 다른 메시지 시스템으로도 해결할 수 있습니다. Kafka만 유일한 해결책은 아닙니다.

Kafka를 도입하면 주문 서비스는 '주문 완료'라는 사건을 Kafka에 발행하고, 재고·배송·알림 등 소비자들이 자신에게 필요한 사건을 읽는 구조를 만들 수 있습니다. 주문 서비스는 누가 읽는지 몰라도 되고, 새로운 소비자를 추가할 때 주문 서비스의 코드를 반드시 수정할 필요도 없습니다.

중요한 단서: 'Kafka에 발행했다'와 '다른 서비스의 업무가 성공적으로 끝났다'는 서로 다른 사실입니다. Kafka는 전달과 저장을 도와줄 뿐, 다른 서비스의 DB 처리 성공까지 자동 보증하지 않습니다.

2. 이벤트(Event)와 이벤트 스트리밍(Event Streaming)

'사건'은 무언가가 일어났다는 사실입니다. 예를 들어 '2026년 10월 19일 13시에 주문 A-123이 생성됨', '상품 B가 물류센터에 입고됨', '차량 C가 출발함'이 모두 이벤트입니다. 이벤트는 명령과 다릅니다. '배송을 시작해!'는 명령(Command)에 가깝고, '배송이 시작되었다'는 과거에 발생한 사실(Event)입니다. 실제 토픽에서는 명령형 메시지도 사용할 수 있지만 두 의미를 구분하면 설계가 명확해집니다.

이벤트 스트리밍을 아주 쉽게 생각하면 '시간순으로 계속 흘러오는 사건 기록을 다루는 것'입니다. 휴대폰에서 위치 이벤트가 매초 올라오는 경우, 결제 이벤트가 초당 수천 건 발생하는 경우, 창고 PDA가 입고 스캔 결과를 보내는 경우를 떠올려 보세요.

Apache Kafka 공식 소개는 이벤트 스트리밍을 크게 사건의 지속적인 수집, 나중에도 다시 볼 수 있는 저장, 현재와 과거 이벤트의 처리 및 전송으로 설명합니다. Kafka는 (1) 이벤트 발행·구독 (2) 내구성 있는 이벤트 저장 (3) 이벤트 처리 기능을 결합합니다.

스트리밍이라고 무조건 '실시간으로 즉시 완료'를 의미하지는 않습니다. Kafka에 사건을 기록한 직후 소비자가 바쁘다면 몇 분 뒤에 읽을 수도 있습니다. 이 지연을 감시하는 지표 중 하나가 Consumer Lag입니다.

3. Producer, Broker, Consumer — 유치원 게시판

선생님(Producer)이 공지를 작성해 유치원 게시판(Broker가 보관하는 Topic)에 붙입니다. 아이(Consumer)는 게시판을 보며 공지를 읽습니다. 선생님이 아이가 공지를 끝까지 읽을 때까지 옆에서 기다릴 필요는 없습니다.

이 비유를 실제 시스템과 정확히 연결해 봅시다.

Producer(생산자): Kafka에 레코드를 쓰는 클라이언트 프로그램입니다. 주문 서비스의 KafkaTemplate, Java KafkaProducer 등이 여기에 해당합니다.

Broker(브로커): Kafka 서버 프로세스입니다. 파티션 데이터를 보관하고 Producer의 전송 요청 및 Consumer의 읽기 요청을 처리합니다.

Cluster(클러스터): 여러 브로커가 함께 구성하는 Kafka 시스템입니다. 한 브로커만으로 개발용 환경을 만들 수도 있지만, 운영 내결함성을 위해 여러 브로커와 복제를 설계합니다.

Consumer(소비자): Topic에서 레코드를 읽는 클라이언트 프로그램입니다. 서버가 모든 메시지를 푸시해서 처리시키는 것으로 오해하기 쉬운데, 일반적인 Kafka Consumer는 poll/fetch 방식으로 데이터를 가져옵니다.

Topic(토픽): 비슷한 종류의 이벤트에 붙이는 논리적 이름입니다. 예를 들면 orders.paid입니다. Topic은 파일 한 개가 아니라 하나 이상의 Partition으로 구성됩니다.

핵심: Producer와 Consumer는 서로의 IP를 직접 호출하지 않습니다. 양쪽 모두 Kafka와 통신합니다. 하지만 실제 시스템은 토픽 스키마와 의미에 의존할 수 있으므로 '아무 의존도 없다'는 뜻은 아닙니다.

4. 하나의 이벤트(Record) 안에는 무엇이 들어갈까?

주문 완료 이벤트 하나를 예로 들어볼게요.

{
  "eventId": "evt-9081",
  "orderId": "A-123",
  "status": "PAID",
  "amount": 23000
}

Kafka 레코드의 주요 요소는 Key, Value, Timestamp, Headers입니다.

- Key: 주문 ID A-123처럼 파티션을 결정하는 데 사용할 수 있는 식별자입니다. 키가 항상 있어야 하는 것은 아니며, Key 자체가 데이터베이스의 Primary Key와 완전히 같지도 않습니다.
- Value: 위 JSON처럼 소비자가 실제 사용할 데이터입니다. Kafka 내부에는 보통 직렬화한 바이트로 저장됩니다.
- Timestamp: 레코드와 관련된 시각입니다. 프로듀서 생성 시각을 쓰거나 토픽 설정에 따라 브로커 기록 시각을 사용할 수 있습니다.
- Headers: eventType, traceId 같은 부가 정보에 쓰기 좋습니다.

Kafka는 JSON만 받는 시스템이 아닙니다. String, JSON, Avro, Protobuf 같은 표현을 사용할 수 있으며 Producer의 Serializer와 Consumer의 Deserializer가 맞아야 합니다. 서로 약속한 구조가 달라지면 역직렬화 오류나 필드 누락이 발생할 수 있습니다.

메시지 스키마를 바꿀 때는 '새 Producer가 보내는 형식을 오래된 Consumer도 이해하는가?'를 생각해야 합니다. Kafka는 전달 기반이지 임의의 JSON 스키마 호환성을 보장해 주는 도구가 아닙니다.

5. Topic과 Partition — 서랍을 여러 개 두는 이유

큰 책장에 책을 한 줄로만 꽂으면 관리가 어려울 수 있습니다. 책장을 세 칸으로 나눠 분담하면 각각 따로 읽거나 관리할 수 있습니다. Kafka에서 Topic은 책장, Partition은 책장의 칸에 비유할 수 있습니다.

예를 들어 orders 토픽이 3개 파티션으로 구성됩니다.

orders
  ├─ Partition 0 : [offset 0] [offset 1] [offset 2]
  ├─ Partition 1 : [offset 0] [offset 1]
  └─ Partition 2 : [offset 0] [offset 1] [offset 2]

세 가지 사실을 정확히 기억하세요.

첫째, 레코드는 Topic에 들어가되 실제 저장 위치는 그 안의 특정 Partition입니다.

둘째, 각 Partition은 자신만의 순서를 갖습니다. P0의 offset 2와 P1의 offset 2는 전혀 다른 위치입니다. Topic 전체에 걸쳐 완벽한 단일 순서가 보장되는 것은 아닙니다.

셋째, 파티션은 병렬 처리의 단위입니다. 파티션을 여러 개 두면 서로 다른 브로커와 소비자에 일을 분산할 수 있습니다. 그러나 파티션이 많아질수록 파일, 메타데이터, 복제, 리밸런스 등 관리 비용도 발생합니다.

왜 Key가 중요할까? 예를 들어 같은 주문 A-123의 '결제됨 → 포장됨 → 배송됨' 이벤트가 모두 한 파티션에 기록되면 그 파티션 안에서 기록 순서를 따라 읽을 수 있습니다. 일반적인 Key 기반 파티셔닝에서는 동일 키가 같은 파티션으로 매핑됩니다. 다만 파티션 수나 파티셔너가 바뀌면 매핑이 달라질 수 있으므로 영구적인 보증이라고 오해해서는 안 됩니다.

6. Offset과 Consumer의 책갈피는 무엇이 다를까?

10페이지까지 읽은 어린이가 책갈피를 꽂아둔다고 생각해 봅시다. Kafka의 Offset은 파티션 로그에서 레코드의 위치를 나타내는 번호입니다. Committed Offset은 소비자 그룹이 재시작할 때 어디서부터 다시 읽을지 기록하는 진행 위치입니다.

예를 들어 Partition 0에는 offset 0, 1, 2, 3, 4, 5가 있습니다. 소비자가 offset 4의 레코드까지 처리했다면 일반적으로 '다음에는 offset 5부터 처리'하겠다는 위치를 커밋합니다. 이는 '마지막 처리 레코드가 4이므로 커밋 값도 4'라는 뜻이 아닙니다.

여기서 가장 흔한 착각은 poll로 읽어온 것과 업무 처리를 끝낸 것을 같은 것으로 생각하는 것입니다. poll은 가져오는 과정이고, DB 업데이트는 별개의 작업입니다. 읽은 메시지의 처리에 실패했는데 지나치게 일찍 커밋하면 작업이 누락될 수 있습니다. 반대로 DB 업데이트는 성공했지만 커밋 전 장애가 나면 같은 메시지를 다시 처리할 수 있습니다.

소비자의 position은 다음에 가져올 위치, committed offset은 그룹의 재시작 기준입니다. 둘이 항상 같은 값은 아닙니다. 컨슈머 Lag이 클러스터·도구에서 어느 위치 기준으로 계산되는지도 확인해야 합니다.

7. Consumer Group — 같은 토픽을 두 팀이 읽는다면?

유치원 공지를 '청소팀'과 '급식팀'이 각각 확인해야 한다고 해봅시다. 청소팀 안에서는 구성원이 업무를 분담하고, 급식팀 안에서도 별도로 분담합니다. 청소팀이 읽었다고 급식팀에서 해당 공지가 사라지지는 않습니다.

Kafka의 Consumer Group은 group.id로 구분합니다. 서로 다른 그룹은 같은 토픽을 독립적으로 읽을 수 있습니다.

~~~text
orders Topic: P0 P1 P2

shipping-group : C1←P0,P1 / C2←P2
notification-group : N1←P0,P1,P2
~~~

같은 그룹 안에서 일반적인 구독 모델에서는 한 파티션이 동시에 한 소비자에게 할당됩니다. 그래서 파티션이 3개인데 Consumer가 10개라면 같은 시점에 10개 모두가 그 토픽 파티션을 맡아 일할 수는 없습니다. 대개 3개까지만 할당받고 나머지는 대기합니다. 실제 그룹이 여러 토픽을 구독한다면 전체 파티션 수를 함께 계산해야 합니다.

컨슈머가 죽거나 새로 추가되면 파티션 배정을 조정합니다. 이를 Rebalance(리밸런스)라고 합니다. 이는 복제본 Leader를 다시 뽑는 과정과는 다른 개념입니다. Rebalance 중에는 처리 지연이나 중복 실행 가능성에 주의해야 합니다.

8. Broker가 여러 대일 때 복제와 Leader는?

중요한 공지를 게시판 하나에만 붙여두면 건물이 정전되었을 때 볼 수 없겠지요. Kafka는 Replication(복제)으로 파티션의 여러 사본을 브로커에 배치할 수 있습니다.

Broker A : orders-P0 (Leader)
Broker B : orders-P0 (Follower)
Broker C : orders-P0 (Follower)

RF(Replication Factor)=3이라는 표현은 파티션 복제본 수를 3개로 구성한다는 뜻입니다. Leader는 일반적으로 그 파티션의 클라이언트 읽기·쓰기 요청을 담당하고, Follower는 Leader의 로그를 따라갑니다. ISR(In-Sync Replicas)은 일정 기준으로 Leader와 동기화된 복제본 집합입니다.

Producer의 acks는 쓰기 성공 응답을 언제 돌려받을지 결정합니다. acks=0은 브로커 응답을 기다리지 않으며 acks=1은 Leader 확인을, acks=all은 동기화 복제 조건에 따른 확인을 기다립니다. min.insync.replicas는 acks=all에서 필요한 최소 ISR 수와 연결됩니다.

핵심 오해 바로잡기: RF=3이면 모든 장애에서 데이터 유실이 절대 없다는 뜻이 아닙니다. Producer 설정, ISR 감소, 실패한 재시도, 리더 선출 정책, 저장 장치와 운영 실수까지 고려해야 합니다. 상세한 복제 알고리즘은 다음 편(핵심 설계)에서 깊게 다룹니다.

9. 데이터를 읽어도 지워지지 않는 이유: Retention

일반적인 작업 대기열에서는 일을 꺼내 처리하면 메시지가 사라진다고 생각하기 쉽습니다. Kafka의 로그는 보통 읽었다는 이유만으로 제거되지 않습니다.

토픽의 보관 정책(retention)이 지난 레코드 제거를 결정합니다. 예를 들어 일주일 동안 보관하도록 설정된 토픽에서 알림 서비스가 오늘 새벽 이벤트를 이미 읽었더라도, 다른 서비스가 오후에 독립적인 그룹으로 그 이벤트를 읽을 수 있습니다. 단 데이터가 계속 영원히 남는 것은 아닙니다. 시간·크기 제한, 로그 압축, 저장 공간 정책에 영향을 받습니다.

운영 환경의 retention.ms, retention.bytes, cleanup.policy가 중요한 이유가 이것입니다. 데이터 재처리 가능성은 보존 기간이 남아 있고, 필요한 로그가 실제로 존재한다는 조건에서만 유효합니다. 보존된 기록이 사라진 뒤에는 오프셋만 바꾼다고 과거 메시지를 되살릴 수 없습니다.

Kafka를 '무제한 메시지 백업 저장소'로 이해하면 안 됩니다. DB 백업·아카이빙과 역할을 구별해야 합니다.

10. 공식문서의 다섯 가지 주요 API

Apache Kafka에는 대표적으로 다섯 가지 주요 API 계열이 있습니다. 혼동하기 쉬우므로 실제 역할로 연결해 봅시다.

1. Producer API — 이벤트를 토픽에 발행합니다. 예: 주문 서비스가 주문 완료 이벤트 전송.
2. Consumer API — 토픽을 구독하고 이벤트를 가져와 처리합니다. 예: 배송 서비스가 주문 완료 이벤트 읽음.
3. Admin API — 토픽 생성·조회, 설정 관리 등 관리 작업을 수행합니다.
4. Kafka Streams API — 이벤트를 실시간 변환·집계·조인하는 스트림 처리 애플리케이션을 만듭니다.
5. Kafka Connect API — 데이터베이스나 외부 저장소와 Kafka 사이에 데이터를 지속적으로 수집·전달하는 커넥터를 운영합니다.

중요한 구분: Spring Kafka의 @KafkaListener를 쓴다고 Kafka Streams를 사용 중인 것은 아닙니다. Kafka Streams는 별도의 스트림 처리 라이브러리이며, 상태 저장 처리와 내부 토픽, 리밸런스 등 추가 개념이 따라옵니다. Kafka Connect는 주로 데이터 통합을 위한 실행 프레임워크입니다. 현재는 이름과 역할만 구분하고, 다음 문서들에서 하나씩 깊게 공부하면 됩니다.

11. 로컬 실습 1: 토픽 만들고 콘솔로 전송하기

개념을 읽는 것만으로 부족하므로 직접 이벤트를 보내 봅시다. 개발 PC에 Docker가 설치되어 있다고 가정합니다. 아래 예시는 Kafka 4.3 개발용 단일 노드 실행 예입니다. 이미지 버전과 실행 명령은 플랫폼에 따라 달라질 수 있으므로 Apache Kafka Quickstart와 대조하세요.

docker run -d --name kafka -p 9092:9092 apache/kafka:4.3.0

명령이 성공한 후 브로커가 기동할 때까지 기다립니다. Kafka CLI 스크립트는 컨테이너 내부 배포판에 포함된 것을 사용합니다.

~~~bash
# 토픽 만들기
docker exec kafka /opt/kafka/bin/kafka-topics.sh \
--bootstrap-server localhost:9092 --create \
--topic hello-kafka --partitions 1 --replication-factor 1

# 토픽 상세 정보 확인
docker exec kafka /opt/kafka/bin/kafka-topics.sh \
--bootstrap-server localhost:9092 --describe --topic hello-kafka
~~~

다음 명령을 별도 터미널에서 실행합니다. 시작 후 내용을 한 줄씩 입력하고 Enter를 누르면 레코드가 전송됩니다.

docker exec -it kafka /opt/kafka/bin/kafka-console-producer.sh \
  --bootstrap-server localhost:9092 --topic hello-kafka

입력 예: hello kafka, order A-123 paid. 또 다른 터미널에서 읽어 봅니다.

docker exec -it kafka /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server localhost:9092 --topic hello-kafka --from-beginning

이제 Producer → Broker → Consumer 흐름을 손으로 확인한 것입니다. RF=1은 개발용이며 브로커 고장에 대한 내결함성을 제공하지 않습니다.

12. 로컬 실습 2: 왜 Consumer Group이 중요한지 확인

이제 '같은 그룹'과 '서로 다른 그룹'의 차이를 직접 관찰합니다. 먼저 Consumer를 실행할 때 각 터미널에 동일한 그룹 이름 team-a를 부여해 보세요.

docker exec -it kafka /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server localhost:9092 --topic hello-kafka --group team-a

두 번째 터미널에서도 동일한 명령을 실행하면 어떻게 될까요? hello-kafka 토픽의 파티션은 하나뿐이므로 같은 그룹 안에서 일반적인 할당 방식으로는 동시에 한 소비자만 해당 파티션을 담당할 수 있습니다. 이 예제에서는 다른 소비자가 대기하는 모습을 확인할 수 있습니다. 두 Consumer의 실제 상태는 배정·재조정 시점에 따라 달라질 수 있습니다.

이번에는 다른 그룹인 team-b를 실행합니다.

docker exec -it kafka /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server localhost:9092 --topic hello-kafka --group team-b --from-beginning

team-a와 team-b는 독립적인 진행 위치를 가질 수 있습니다. 다만 --from-beginning은 해당 그룹에 저장된 Offset이 없을 때의 시작 위치 설정과 관계되므로, 그룹에 이전에 커밋된 위치가 있다면 그 위치가 사용될 수 있습니다.

그룹 상태와 Lag을 보려면 다음 명령을 실행하세요.

docker exec kafka /opt/kafka/bin/kafka-consumer-groups.sh \
  --bootstrap-server localhost:9092 --describe --group team-a

이때 CURRENT-OFFSET, LOG-END-OFFSET, LAG를 봅니다. 숫자만 외우지 말고 '읽기 위치보다 뒤에 얼마나 많은 데이터가 있는가?'를 생각하는 것이 중요합니다.

13. Java 21 / Spring Boot로 생산자 만들기

실습을 Java 코드로 연결해 보겠습니다. Spring Boot에서는 spring-kafka 의존성을 사용합니다. 다음은 핵심 흐름을 보여주는 예시이며 보안·재시도·메트릭·에러 복구 정책까지 포함한 완전한 운영 코드가 아닙니다.

implementation 'org.springframework.kafka:spring-kafka'
spring:
  kafka:
    bootstrap-servers: localhost:9092
    producer:
      key-serializer: org.apache.kafka.common.serialization.StringSerializer
      value-serializer: org.apache.kafka.common.serialization.StringSerializer
    consumer:
      key-deserializer: org.apache.kafka.common.serialization.StringDeserializer
      value-deserializer: org.apache.kafka.common.serialization.StringDeserializer

~~~java
@Service
@RequiredArgsConstructor
public class OrderEventPublisher {
private final KafkaTemplate<String, String> kafkaTemplate;

public CompletableFuture<SendResult<String, String>> publish(
String orderId, String json) {
return kafkaTemplate.send("orders", orderId, json);
}
}
~~~

호출하는 쪽에서는 반환된 Future의 성공과 실패를 관찰해야 합니다.

publisher.publish(orderId, json).whenComplete((result, error) -> {
    if (error != null) {
        log.error("Kafka publish failed. orderId={}", orderId, error);
        // 운영 정책에 따라 Outbox 재처리 등 설계
        return;
    }
    log.info("Sent to partition={}, offset={}",
            result.getRecordMetadata().partition(),
            result.getRecordMetadata().offset());
});

아주 중요: publish() 메서드가 반환되었다고 Kafka 전송이 성공한 것이 아닙니다. 비동기 Future 완료를 확인해야 합니다. 또한 DB 트랜잭션 안에서 send()를 호출했다고 데이터베이스 저장과 Kafka 발행이 자동으로 단일 원자 트랜잭션이 되지도 않습니다.

14. Spring Kafka Consumer와 중복 처리의 첫걸음

소비자 코드를 붙여 봅시다.

~~~java
@Component
@RequiredArgsConstructor
public class ShippingConsumer {
private final ShippingService shippingService;

@KafkaListener(topics = "orders", groupId = "shipping-service")
public void consume(String payload) {
shippingService.handleOrderEvent(payload);
}
}
~~~

이 코드는 핵심 흐름만 보여줍니다. 실무에서는 eventId 또는 주문 ID를 파싱하고, 이 이벤트가 이미 처리되었는지 확인해야 합니다. 예를 들어 데이터베이스에 processed_event(event_id)를 UNIQUE 제약조건과 함께 저장하고, 배송 생성과 같은 로컬 트랜잭션 안에서 중복 처리를 관리할 수 있습니다. 두 Consumer가 동시에 같은 이벤트를 처리하는 경쟁 조건까지 고려하려면 단순 exists() 검사만으로는 부족합니다. 유니크 제약조건 또는 원자적인 DB 처리가 안전장치가 되어야 합니다.

실패가 발생했을 때 무조건 catch(Exception e) { log.error(...); }로 삼키면 프레임워크가 메시지를 정상 처리했다고 판단하는 경우가 생깁니다. 컨테이너의 AckMode와 ErrorHandler 설정에 따라 재시도·커밋 결과가 달라집니다. 어떤 실패는 다시 시도할지, 어떤 실패는 DLQ로 격리할지 업무 요구에 맞춰 정해야 합니다.

15. 장애 시나리오: 정말 어디에서 실패할까?

상황 A: 주문 DB에는 저장됐지만 Kafka 발행 전에 서버가 죽음. DB에는 주문이 존재하지만 다른 서비스는 이벤트를 받지 못할 수 있습니다. 이를 '이중 쓰기(Dual Write)' 문제라고 부릅니다. 대표적인 완화책은 비즈니스 테이블과 Outbox 테이블을 하나의 DB 트랜잭션에 함께 기록하고, 별도 발행기가 Outbox 레코드를 Kafka로 전송하는 방법입니다.

상황 B: Kafka에 이벤트가 저장됐지만 Producer가 성공 응답을 받기 전 연결이 끊김. 애플리케이션은 전송 실패라고 생각할 수 있지만 실제로는 기록됐을 수 있습니다. 재시도와 Producer 멱등성 설정의 역할을 이해해야 합니다. 비즈니스 이벤트 ID를 두고 중복 가능성을 관리하는 편이 좋습니다.

상황 C: Consumer가 배송 DB에 저장했지만 Offset 커밋 전에 죽음. 재시작하면 같은 이벤트가 다시 전달될 수 있습니다. 이를 고려하지 않으면 배송 요청이 중복 생성될 수 있습니다. DB의 유니크 키와 중복 이벤트 처리 정책이 필요합니다.

상황 D: Consumer Lag이 갑자기 3만 증가함. 무조건 Consumer 인스턴스를 늘리는 것이 정답일까요? 파티션 수가 적으면 Consumer를 늘려도 동시 처리량이 늘지 않습니다. DB 락·외부 API 지연·Listener 오류·리밸런스 반복인지부터 확인합니다.

상황 E: 브로커 한 대가 죽음. 복제본이 있다면 다른 Broker가 역할을 이어받을 수 있지만, 실제 가용성은 RF, ISR, 설정과 장애 상황에 따라 달라집니다. Producer와 Consumer의 재연결·메타데이터 갱신에도 시간이 필요할 수 있습니다.

16. 자주 헷갈리는 오해 10개

① Kafka는 DB를 대체한다? → 아닙니다. 이벤트 로그와 업무 데이터 저장에는 서로 다른 요구가 있습니다.
② Consumer가 읽으면 메시지는 사라진다? → 일반적인 Kafka 로그에서는 아닙니다. 보관 정책이 제거를 결정합니다.
③ Topic에 순서가 하나만 존재한다? → 아닙니다. 기본적인 순서 보장은 파티션 내부입니다.
④ Offset은 토픽 전체의 전역 번호다? → 아닙니다. 파티션마다 따로 있습니다.
⑤ Consumer Group이 다르면 서로 같은 데이터를 못 읽는다? → 아닙니다. 서로 독립적으로 읽을 수 있습니다.
⑥ 파티션이 3개인데 Consumer를 20개 추가하면 20개가 다 일한다? → 일반적인 그룹 소비에서는 동시에 할당받는 소비자 수에 한계가 있습니다.
⑦ Producer의 send가 반환되면 무조건 발행 성공이다? → 비동기 결과를 확인해야 합니다.
⑧ acks=all과 RF=3이면 어떤 장애에서도 절대 유실이 없다? → 절대 보장이 아닙니다.
⑨ Offset Commit에 성공하면 비즈니스 DB도 성공한 것이다? → 별개입니다.
⑩ Kafka exactly-once를 쓰면 외부 MySQL도 자동으로 한 번만 갱신된다? → 아닙니다. DB 등 외부 시스템의 멱등 처리는 별도로 설계해야 합니다.

17. 면접 질문: 답변과 꼬리 질문까지

Q1. Kafka를 한 문장으로 정의해 보세요.
A. 여러 애플리케이션이 이벤트를 발행·구독하고 내구성 있게 저장하며 재처리할 수 있도록 지원하는 분산 이벤트 스트리밍 플랫폼입니다.
꼬리질문: 그렇다면 단순 HTTP 호출 대신 Kafka를 쓸 이유는? → 생산자와 소비자의 결합을 줄이고 버퍼링·독립 처리·재처리에 유리하지만 시스템 복잡성이 증가합니다.

Q2. Kafka의 Topic과 Partition 차이는?
A. Topic은 이벤트를 묶는 논리적 이름이고 Partition은 실제 저장·순서·병렬 처리의 단위입니다.
꼬리질문: 왜 Topic 전체 순서가 어려운가? → 서로 다른 파티션이 독립적으로 기록·읽히기 때문입니다.

Q3. 같은 주문 ID의 이벤트 순서를 지키려면?
A. 동일한 Key를 사용해 동일 파티션에 보내는 전략을 검토합니다.
꼬리질문: 토픽 파티션 수를 늘리면? → Key의 매핑이 달라질 수 있으므로 변경 계획이 필요합니다.

Q4. Consumer Group이란?
A. 같은 그룹의 Consumer들이 토픽 파티션을 분담하는 단위입니다.
꼬리질문: 두 서비스가 같은 주문 이벤트를 모두 읽으려면? → 서로 다른 group.id를 사용하도록 구성합니다.

Q5. Offset과 Commit의 차이는?
A. Offset은 파티션 내 레코드 위치이고 Commit은 소비자가 재시작할 진행 위치를 기록하는 동작입니다.
꼬리질문: DB 반영 후 Commit 전에 죽으면? → 이미 반영한 이벤트가 다시 전달될 수 있으므로 멱등 처리가 필요합니다.

Q6. Kafka에 데이터를 저장하면 절대 사라지지 않나요?
A. 아닙니다. 로그 보관 정책에 따라 제거될 수 있고, 복제·장애 상황에 따라 유실 가능성도 고려해야 합니다.
꼬리질문: 과거 메시지를 다시 읽는 조건은? → 해당 레코드가 보존돼 있어야 하고 소비자 읽기 위치를 적절히 설정해야 합니다.

Q7. Producer, Consumer 장애를 하나씩 설명해 보세요.
A. 발행 성공 여부가 불확실할 때 중복 발행 가능성이 있고, DB 처리 성공 후 Commit 전 장애 시 중복 소비 가능성이 있습니다. 각각 Producer 멱등성·이벤트 ID 기반 Consumer 멱등 처리를 설계합니다.

Q8. Kafka Streams와 Consumer API는 같은 것인가요?
A. 아닙니다. Streams는 Consumer·Producer 기반의 고수준 스트림 처리 라이브러리이며 변환·상태 집계·조인 같은 기능을 제공합니다.

Q9. Broker 한 대만 운영하면 안 되나요?
A. 개발용으로는 가능하지만 브로커 단일 장애에 취약합니다. 운영에서는 복제와 장애 시 처리량까지 설계합니다.

Q10. Kafka를 도입해도 해결되지 않는 문제는?
A. DB와 Kafka 이중 쓰기, 비즈니스 트랜잭션의 정합성, 중복 메시지의 업무 처리, 스키마 호환성, Consumer 병목 등은 별도 설계가 필요합니다.

19. Kafka와 HTTP는 언제 선택할까?

HTTP를 사용하면 주문 서비스가 재고 서비스에 직접 요청하고 결과를 바로 알 수 있습니다. 예를 들어 '지금 재고가 있는가?' 같은 즉시 질의는 동기 API가 자연스럽습니다. Kafka는 '주문이 생성되었다'라는 사실을 다른 여러 서비스가 각자 처리해야 할 때 유리합니다. 둘 중 하나를 무조건 선택해야 하는 것은 아닙니다.

동기 HTTP에서는 호출자가 응답을 기다립니다. 수신 서버가 느려지면 호출자도 타임아웃과 재시도를 관리해야 합니다. Kafka에서는 Producer가 브로커에 기록한 후 Consumer가 나중에 처리할 수 있으므로 시간적 결합이 줄어듭니다. 단 Consumer가 실제로 처리했는지 알아야 할 때는 별도 상태 조회, 보상 처리 또는 응답 이벤트 설계가 필요합니다.

Kafka를 사용한다고 주문-재고 사이의 업무 순서를 자연스럽게 보장하는 것은 아닙니다. 서로 다른 토픽이나 파티션을 사용하면 도착 순서가 바뀔 수 있습니다. 최종 상태가 일관되어야 하는 업무는 이벤트 순서, 버전, 멱등성, 실패 복구 정책을 명확히 해야 합니다.

면접에서 '모든 서비스 호출을 Kafka로 바꾸겠습니다'라고 답하지 마세요. 즉시 응답이 필요한 조회는 HTTP/gRPC, 비동기 이벤트 팬아웃과 재처리가 중요한 곳은 Kafka처럼 요구사항별로 선택하는 이유를 설명하세요.

20. Partition 수를 잘못 정하면?

책장 서랍이 한 개라면 도서관 사서 열 명을 고용해도 같은 서랍은 한 번에 한 사서만 담당할 수 있습니다. 일반적인 Consumer Group에서는 각 파티션이 특정 시점에 하나의 소비자에게 할당되므로 파티션 수는 병렬 처리 한계와 관련 있습니다.

예를 들어 3개 파티션의 토픽을 소비하는 그룹에 Consumer 인스턴스가 5개 있다면, 보통 최대 3개가 파티션을 맡고 나머지는 해당 토픽에서 유휴 상태일 수 있습니다. 단 소비자가 여러 토픽을 동시에 구독한다면 토픽 전체의 할당 가능한 파티션 수를 함께 봐야 합니다.

파티션을 지나치게 늘리면 각 파티션 로그 파일과 인덱스, 컨트롤러 메타데이터, 복제 트래픽 및 리밸런싱 부담이 커집니다. '언제나 파티션이 많을수록 빠르다'는 잘못된 결론입니다. 메시지 크기, 키 분포, 소비자 DB 작업 시간, 브로커 디스크·네트워크 처리량을 근거로 결정해야 합니다.

파티션을 늘리면 기존 Key와 파티션의 해시 매핑이 달라질 수 있습니다. 따라서 주문 ID 같은 키의 시간순 처리 요구가 있다면 파티션 수 변경이 기존과 미래 이벤트의 배치에 미치는 영향을 확인해야 합니다.

21. Poll, 처리, Commit을 시간순으로 추적하기

메시지 10개가 있는 P0를 생각해 봅시다. Consumer는 poll 호출로 여러 레코드를 가져오고, 애플리케이션이 DB에 저장하고, 성공한 뒤 다음 시작 위치를 Commit합니다. 이 순서에서 '가져왔다'와 '저장했다'와 '커밋했다'는 서로 다른 순간입니다.

시각 T1: poll이 offset 0~9를 반환. T2: offset 0~4의 DB 처리는 성공. T3: 프로세스 종료. 이때 커밋이 이전 offset 0으로 남아 있었다면 재시작 시 앞서 처리한 0~4도 다시 전달될 수 있습니다. 반대로 처리 전에 다음 위치 10을 커밋했다면 나머지 5~9를 건너뛸 위험이 있습니다.

그래서 'at-least-once' 처리는 일반적으로 재전달을 허용하고 비즈니스 쪽에서 중복을 안전하게 처리하도록 설계합니다. 'at-most-once'는 중복을 줄일 수 있지만 실패 시 누락을 허용할 수 있습니다. Exactly-once는 어떤 경계에서 보장하는지 정확히 설명해야 합니다.

Spring Kafka에서 AckMode.MANUAL과 MANUAL_IMMEDIATE도 구분할 필요가 있습니다. acknowledge()의 실제 Commit 시점, consumer 스레드 호출 여부 및 컨테이너 설정에 따라 달라집니다. 설정 이름만 보고 모든 실패에서 즉시 재전달된다고 가정하지 마세요.

22. Consumer Lag 수치 읽기

한 파티션의 최신 로그 끝 위치가 12이고 Consumer Group의 커밋 위치가 7이라고 가정하면, 보통 표시되는 커밋 기반 Lag은 12 - 7 = 5입니다. 이는 완료했다고 저장된 위치가 로그 끝보다 다섯 레코드 뒤처져 있다는 뜻입니다.

그런데 Consumer가 poll로 offset 7~11을 가져와 DB에 비동기로 처리 중이라면 어떨까요? 커밋 기반 Lag은 아직 5일 수 있습니다. 반대로 작업이 제대로 끝나기 전에 오프셋만 일찍 커밋하면 Lag이 0처럼 보여도 실제 비즈니스 처리는 안 끝났을 수 있습니다.

따라서 Lag 자체만으로 시스템의 건강도를 판단하지 말고 처리 성공률, 처리 시간, 실패·재시도, 레코드 유입량과 파티션별 분포를 함께 확인하세요. 브로커의 로그 끝 오프셋과 소비자 커밋 값을 구분하고, 조회 도구가 어느 정의를 사용하는지도 확인해야 합니다.

운영 질문: Lag이 3만이라고 해서 소비자가 3만 초 늦었다는 뜻인가요? 아닙니다. 기본 Lag은 레코드 수 차이이며 시간 지연으로 환산하려면 별도 측정이 필요합니다.

23. 실제 배송 이벤트의 데이터 정합성

주문 완료 이벤트에는 eventId=E100과 orderId=O10이 있다고 해 봅시다. 배송 Consumer가 이벤트를 수신한 뒤 배송 요청 테이블에 insert하고, 처리 이벤트 ID를 별도 테이블에 기록한다고 합시다.

두 DB 쓰기를 하나의 로컬 트랜잭션으로 묶고 eventId에 UNIQUE 제약조건을 걸면, 동일 이벤트를 재전달받더라도 중복 배송 요청을 방지하는 데 도움이 됩니다. '처리했는지 SELECT로 확인 후 INSERT'만 하면 동시에 들어온 두 처리 스레드가 둘 다 미처리라고 판단할 수 있어 경쟁 조건이 남습니다.

단 배송 요청을 외부 택배사 API로 보내는 일까지 MySQL 트랜잭션 안에 원자적으로 포함할 수는 없습니다. 외부 API의 idempotency key 지원, 재시도 가능한 상태 모델, Outbox, 보상 처리 등을 조합해야 합니다.

실무 질문: Kafka 메시지를 정확히 한 번 소비했더라도 API 호출의 네트워크 응답이 유실되면 택배 요청이 중복될 가능성이 있나요? 있습니다. 시스템의 경계를 나누어 설계해야 합니다.

24. Retry와 DLQ를 언제 사용할까?

외부 서비스가 2초 동안 응답하지 않는 일시 오류와, 필수 필드가 없는 잘못된 이벤트는 같은 방식으로 처리하면 안 됩니다. 전자는 재시도하면 성공할 수 있지만 후자는 같은 내용을 100번 재전송해도 실패할 수 있습니다.

일시 오류에는 재시도 횟수 제한과 지수 백오프, 지터 등을 설정할 수 있습니다. 영구 오류에는 Dead Letter Topic(DLT 또는 DLQ)에 원본 이벤트와 오류 사유를 따로 기록하고 운영자가 나중에 원인을 분석·복구하는 전략을 사용할 수 있습니다.

주의할 점은 실패 메시지를 건너뛰는 순간에도 업무적 정합성이 필요한지 여부입니다. 같은 주문의 PAID가 실패했는데 다음 SHIPPED 이벤트를 계속 처리하면 순서 제약을 깨뜨릴 수 있습니다. 이 경우 파티션 일시 중단, 순서 보존 재시도 토픽 설계, 이벤트 상태 머신 등 추가 대안이 필요합니다.

Spring Kafka의 DefaultErrorHandler와 DeadLetterPublishingRecoverer는 이런 정책을 구현하는 데 도움이 되지만, 기본값과 옵션은 실제 Spring Kafka 버전에 따라 확인해야 합니다.

25. 멱등 Producer가 해결하는 것과 못 하는 것

Producer가 레코드를 보내자 브로커는 성공적으로 저장했지만 응답이 네트워크에서 사라졌다고 해 봅시다. Producer는 전송 결과가 불확실해 재시도할 수 있습니다.

enable.idempotence는 같은 Producer 세션에서 특정 파티션에 재전송하는 경우 중복 로그 추가를 피하기 위한 메커니즘입니다. 브로커는 Producer ID와 시퀀스 번호 등을 이용해 중복을 판단합니다. 이를 사용할 때 acks, retries, max.in.flight.requests.per.connection 등 관련 설정 조건도 중요합니다.

그러나 사용자가 결제 버튼을 두 번 눌러 애플리케이션이 서로 별개의 이벤트를 만든 경우, Producer 멱등성만으로 업무 중복이 제거되지 않습니다. Producer가 재시작해서 새로운 세션에서 같은 업무 이벤트를 발행하는 문제도 외부 eventId 기반 멱등 처리로 다루는 것이 안전합니다.

면접에서는 'Kafka Producer의 멱등성'과 '업무 요청의 멱등성'을 분리해서 답해야 합니다. 기술적 중복 기록 제한과 비즈니스 중복 처리 방지는 다른 층위입니다.

26. Kafka 설정을 처음 볼 때 읽는 순서

설정을 인터넷 블로그에서 아무거나 복사하기 전에 어떤 목적의 설정인지 분류해 봅시다. producer 설정은 전송의 성능·안전성·재시도, consumer 설정은 읽기·그룹·커밋·오류 처리, broker/topic 설정은 저장·복제·보존 정책과 연결됩니다.

Producer: acks, enable.idempotence, retries, delivery.timeout.ms, linger.ms, batch.size, compression.type. Consumer: group.id, enable.auto.commit, auto.offset.reset, max.poll.records, max.poll.interval.ms, session.timeout.ms. Topic/Broker: partitions, replication.factor, min.insync.replicas, retention.ms, cleanup.policy.

예를 들어 enable.auto.commit=true라면 자동 커밋이 어떤 기준으로 일어나는지 알아야 합니다. auto.offset.reset=earliest를 설정한다고 이미 커밋된 그룹의 위치가 항상 처음으로 돌아가는 것은 아닙니다. 옵션은 '언제 적용되는가'를 꼭 함께 읽어야 합니다.

각 설정의 기본값과 지원 여부는 Kafka 4.3 및 Spring Kafka 실제 클라이언트 버전의 공식문서를 기준으로 확인하세요. 기본값을 확인하지 않은 채 운영 환경에 고정하면 업그레이드 시 의도치 않은 차이가 날 수 있습니다.

27. 학습용 실험: 일부러 실패를 만들어 보기

테스트 1: Consumer Group을 두 개 띄워 서로 다른 그룹이 같은 기록을 읽는지 확인합니다. 테스트 2: 하나의 파티션에 같은 그룹 Consumer를 두 개 띄워 파티션 할당 상태를 확인합니다. 테스트 3: Consumer를 종료 후 재시작해서 커밋된 위치 이후 데이터를 읽는지 확인합니다.

테스트 4: Listener에서 특정 eventId일 때 일부러 예외를 발생시키고 로그 및 재시도 동작을 관찰합니다. 테스트 5: DB 저장 성공 직후 커밋 전 프로세스를 종료하는 환경을 만들어 중복 처리를 확인합니다. 테스트 6: Producer send의 Future가 완료되기 전 애플리케이션이 종료되는 상황을 실험해 봅니다.

실험할 때는 메시지 Key, Topic, Partition, Offset, Consumer Group, Commit 여부를 표로 기록해 두세요. 그래야 '왜 두 번 처리됐나?' 같은 문제가 느낌이 아니라 사실에 근거해 설명됩니다.

절대 운영 Kafka에 이런 실험을 그대로 수행하지 마세요. 로컬 또는 완전히 격리된 테스트 클러스터에서 재현해야 합니다.

먼저 질문을 읽고 30초 동안 입으로 답해 보세요. 답을 생각한 뒤 질문 행을 누르면 정답과 해설이 펼쳐집니다. 정답 문장을 외우기보다는 정확한 이유를 설명할 수 있어야 합니다.

Q01 Kafka와 RabbitMQ 중 Kafka가 항상 더 좋은가요? 답변 보기 ▾

정답과 상세 해설

아닙니다. 여러 소비자가 독립적으로 읽고, 장기간 이벤트를 재처리해야 하며 큰 스트림 처리량이 중요한 환경에서는 Kafka가 잘 맞을 수 있습니다. 세밀한 작업 큐·라우팅·개별 작업 ACK 모델이 중요한 경우 다른 메시징 시스템이 더 단순할 수 있습니다. 무엇보다 운영팀의 경험과 장애 복구 요구사항을 함께 보아야 합니다.

한 단계 더 생각하기

'Kafka가 더 빠르다'처럼 근거 없는 절대 평가보다 처리량, 전달 보장, 소비 모델, 보존 기간, 운영 부담을 비교하세요.

Q02 Consumer 두 개가 같은 group.id인데 왜 하나는 쉬고 있나요? 답변 보기 ▾

정답과 상세 해설

구독한 토픽의 파티션이 하나라면 일반적인 Consumer Group 모델에서는 한 파티션이 동시에 하나의 Consumer에게만 할당됩니다. 나머지는 유휴 상태일 수 있습니다.

한 단계 더 생각하기

그룹에서 여러 토픽을 구독한다면 토픽별 파티션 수를 합해 확인해야 합니다.

Q03 Topic과 Partition의 차이를 5살에게 설명하면? 답변 보기 ▾

정답과 상세 해설

Topic은 '주문 알림 게시판'이라는 이름이고, Partition은 그 게시판을 여러 칸으로 나눈 것입니다. 각각의 칸에는 자기 번호 순서로 공지가 붙습니다.

한 단계 더 생각하기

순서 보장은 토픽 전체가 아니라 파티션별이라는 점까지 말하면 더 정확합니다.

Q04 Offset 10을 Commit하면 Offset 10을 처리한 것인가요? 답변 보기 ▾

정답과 상세 해설

반드시 그렇지 않습니다. 일반적인 커밋 의미는 '다음에 읽을 위치가 10'이라는 뜻입니다. 보통 Offset 9까지 성공적으로 처리했다는 의도로 10을 Commit합니다.

한 단계 더 생각하기

position과 committed offset을 분리하세요. 프레임워크의 특정 커밋 동작도 확인해야 합니다.

Q05 Consumer가 poll로 읽은 순간 Broker에서 기록이 사라지나요? 답변 보기 ▾

정답과 상세 해설

아닙니다. 일반적으로 데이터는 토픽의 보존 정책에 따라 로그에 남습니다. 다른 그룹이나 읽기 위치를 조정한 그룹이 보존된 기록을 다시 읽을 수 있습니다.

한 단계 더 생각하기

보존 기간이 지난 기록을 Offset Reset만으로 되살릴 수는 없습니다.

Q06 Producer send() 메서드가 성공적으로 반환하면 전송 완료인가요? 답변 보기 ▾

정답과 상세 해설

Spring Kafka의 KafkaTemplate.send는 비동기 Future를 반환합니다. 메서드가 반환되었다고 성공 ACK까지 받았다는 뜻은 아닙니다. 완료 콜백이나 Future 결과를 확인해야 합니다.

한 단계 더 생각하기

HTTP 요청 성공과 Kafka 발행 성공, Consumer 업무 성공은 세 개의 별도 사건입니다.

Q07 RF=3인데 브로커 하나가 죽으면 어떻게 되나요? 답변 보기 ▾

정답과 상세 해설

해당 파티션의 ISR에 적합한 다른 복제본이 있고 컨트롤러가 리더를 선출할 수 있다면 계속 서비스할 수 있습니다. 하지만 현재 ISR 수, acks, min.insync.replicas, 브로커 상태에 따라 쓰기가 실패하거나 지연될 수 있습니다.

한 단계 더 생각하기

'RF=3이라 문제없다'고 단언하지 마세요. 리더/ISR/재복제 상태를 확인해야 합니다.

Q08 acks=all이면 중복 처리도 막아 주나요? 답변 보기 ▾

정답과 상세 해설

acks는 Producer가 성공 응답을 언제 받을지와 관련 있습니다. Consumer의 DB 중복 처리까지 막아주지는 않습니다. Producer 멱등성 및 Consumer의 비즈니스 멱등성은 각각 별도로 생각해야 합니다.

한 단계 더 생각하기

acks, Producer idempotence, Consumer idempotence의 책임 경계를 구분하세요.

Q09 같은 Key인데 이벤트 순서가 달라질 수 있나요? 답변 보기 ▾

정답과 상세 해설

일반적인 Key 기반 라우팅에서 같은 Key는 같은 파티션으로 가며 파티션 로그 안의 순서는 정해집니다. 그러나 애플리케이션에서 여러 스레드가 이벤트를 생성하는 순서, 재시도 정책, 파티션 수 변경 또는 별도 토픽 사용에 따라 비즈니스 이벤트의 의도한 순서가 깨질 수 있습니다.

한 단계 더 생각하기

파티션 로그 순서와 실제 발생 시각의 인과관계는 같은 뜻이 아닙니다.

Q10 Consumer Lag이 0이면 DB 반영도 완료인가요? 답변 보기 ▾

정답과 상세 해설

꼭 그렇지 않습니다. 오프셋을 업무 완료보다 먼저 커밋하거나, Consumer가 메시지를 비동기 작업 큐에 넘긴 뒤 즉시 커밋하면 Lag이 0이어도 후속 처리 작업은 남아 있을 수 있습니다.

한 단계 더 생각하기

최종 업무 처리 성공률과 처리 소요 시간을 별도 메트릭으로 측정하세요.

Q11 Consumer Lag이 크면 Consumer 인스턴스부터 늘리면 되나요? 답변 보기 ▾

정답과 상세 해설

먼저 Lag이 어느 토픽·파티션에서 증가하는지 확인합니다. 파티션 수가 적으면 Consumer 수를 늘려도 동시 처리량은 늘지 않을 수 있습니다. DB 락, 외부 API, 직렬화, 리밸런스, 특정 핫키 문제 등 원인을 먼저 찾아야 합니다.

한 단계 더 생각하기

토픽 전체 Lag 합계와 파티션별 최대 Lag을 함께 확인하세요.

Q12 Consumer Group이 다른 두 서비스는 이벤트를 각각 받을 수 있나요? 답변 보기 ▾

정답과 상세 해설

네. 같은 토픽을 구독해도 서로 다른 group.id를 사용하면 독립적인 소비 위치를 가집니다. 단 해당 이벤트가 보존 중이어야 하고, 각 그룹의 시작 오프셋·커밋 상태에 따라 실제로 읽는 범위는 다릅니다.

한 단계 더 생각하기

새 그룹을 earliest로 시작할지 latest로 시작할지 운영 요구에 맞춰 결정합니다.

Q13 Offset을 Commit하지 않으면 메시지가 바로 반복되나요? 답변 보기 ▾

정답과 상세 해설

아닙니다. Consumer는 메모리의 현재 position을 따라 다음 poll에서 앞으로 진행할 수 있습니다. Commit은 재시작과 파티션 재할당 시 사용할 복구 위치입니다. seek, 리밸런스, 재시작 등의 상황에서 같은 메시지를 다시 가져올 수 있습니다.

한 단계 더 생각하기

poll position, committed offset, 처리 완료를 각각 따로 기록해서 관찰하세요.

Q14 @KafkaListener에서 예외를 잡고 끝내면 안전한가요? 답변 보기 ▾

정답과 상세 해설

아닙니다. 예외를 삼키면 컨테이너는 메서드가 정상 종료됐다고 판단할 수 있어 실패 레코드에 대한 재시도나 적절한 커밋 처리가 기대와 달라집니다. ErrorHandler와 AckMode를 설계해야 합니다.

한 단계 더 생각하기

예외를 삼키는 목적이 있다면 DLQ 기록, 상태 저장 등 명확한 복구 방법이 있어야 합니다.

Q15 DB에 주문 저장 후 Kafka 발행 전 죽으면 어떻게 하죠? 답변 보기 ▾

정답과 상세 해설

주문은 DB에 있지만 후속 Consumer가 이벤트를 모를 수 있습니다. 대표적인 해법은 주문 데이터와 Outbox 레코드를 한 DB 트랜잭션에 기록하고, 별도 발행기가 Outbox를 Kafka에 보내는 Transactional Outbox 패턴입니다.

한 단계 더 생각하기

Outbox도 중복 발행 가능성을 남기므로 Consumer 멱등 처리가 중요합니다.

Q16 Kafka Exactly-once면 MySQL까지 자동으로 정확히 한 번인가요? 답변 보기 ▾

정답과 상세 해설

아닙니다. Kafka 트랜잭션·처리 보장은 Kafka 내부의 기록과 관련된 경계를 가집니다. 외부 DB 업데이트는 별도의 트랜잭션이며, 이를 자동으로 원자적으로 묶어주는 것은 아닙니다.

한 단계 더 생각하기

어떤 시스템들 사이에서 정확히 한 번이라고 주장하는지 반드시 경계를 특정하세요.

Q17 메시지 순서가 중요한데 Partition을 여러 개 써도 되나요? 답변 보기 ▾

정답과 상세 해설

업무 키별 순서만 중요하다면 같은 업무 Key가 같은 파티션에 들어가도록 라우팅하고 해당 Key 처리의 멱등·직렬성을 관리할 수 있습니다. 전체 토픽의 전역 순서가 반드시 필요하다면 하나의 파티션 또는 별도 순서 설계가 필요합니다.

한 단계 더 생각하기

키 편중으로 특정 파티션만 바쁜 핫 파티션 현상도 고려해야 합니다.

Q18 retention.ms를 늘리면 무조건 좋은가요? 답변 보기 ▾

정답과 상세 해설

오래된 이벤트를 더 오래 재처리할 수 있지만 브로커 디스크 사용량과 비용이 증가합니다. 로그 압축 및 세그먼트 삭제 정책과 함께 설계해야 합니다. 필요한 기간이 길면 별도 아카이브 저장 전략을 고려할 수 있습니다.

한 단계 더 생각하기

consumer가 오래 중단될 수 있는 최대 기간과 보관 기간의 관계를 생각해 보세요.

Q19 Rebalance가 일어나면 메시지가 사라지나요? 답변 보기 ▾

정답과 상세 해설

일반적인 리밸런스는 파티션 할당 주체를 바꾸는 과정이지 토픽 로그를 삭제하는 작업이 아닙니다. 다만 이전 담당 Consumer가 처리한 내용과 커밋 시점이 어긋나면 중복 처리나 누락 위험이 있습니다.

한 단계 더 생각하기

리밸런스 전후 커밋과 배정 상태, graceful shutdown을 점검해야 합니다.

Q20 Kafka를 도입하면 서버가 없어도 되나요? 답변 보기 ▾

정답과 상세 해설

아닙니다. Kafka 자체는 Broker 및 관리 구성요소가 필요하며 애플리케이션 Producer·Consumer도 실행되어야 합니다. 관리형 Kafka를 쓰면 브로커 운영 부담이 줄어들 뿐, 용량·보안·모니터링·비즈니스 장애 대응 책임이 완전히 사라지지는 않습니다.

한 단계 더 생각하기

정적 블로그의 '서버리스 호스팅'과 Kafka 운영 모델을 혼동하지 마세요.

연습 과제: 실제로 설명할 수 있나요?

각 질문의 답변을 보지 않고 직접 대답하거나, Kafka 로컬 환경에서 재현해 보세요. 로그·브로커 설정·파티션 할당·오프셋을 함께 기록하면 이해가 훨씬 빨라집니다.

실습 1. 같은 그룹의 Consumer를 5개 띄우고 토픽 파티션은 3개만 두면 어떻게 될까요?

일반적인 Consumer Group에서 최대 3개 Consumer가 파티션을 맡을 수 있습니다. 나머지는 해당 토픽의 파티션 할당을 받지 못할 수 있습니다. consumer-groups.sh --describe를 사용해서 실제 할당 결과를 확인하세요.

실습 2. DB는 성공하고 Commit은 실패하면 어떻게 될까요?

이미 DB에 저장한 레코드를 재시작 뒤 다시 받을 수 있습니다. eventId UNIQUE 제약조건 등을 이용해 비즈니스 중복을 막고, 커밋 전후의 실패를 로그로 비교하세요.

실습 3. Lag이 0인데 배송 작업이 남아 있다면?

Kafka 메시지를 가져온 뒤 비동기 작업 큐에 전달하고 너무 일찍 Commit했을 수 있습니다. Consumer Lag과 별개로 최종 업무 완료 카운터와 작업 대기량을 계측하세요.
