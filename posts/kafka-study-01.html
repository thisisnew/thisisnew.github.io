Kafka 완전 입문: 왜 쓰고, 어떻게 동작할까?

이번 글은 Apache Kafka 4.3의 Getting Started를 바탕으로 작성했습니다. Kafka를 처음 배우는 사람도 이해하도록 아주 쉬운 비유에서 시작하지만, Producer·Consumer 내부 흐름, Java/Spring 사용법, 운영 장애 및 면접 질문까지 이어집니다. 이 페이지 하나로 첫 입문 과정을 공부하는 것이 목표입니다.

1. Kafka가 왜 필요할까? — 배경부터

어린이집에 친구가 100명 있고 선생님 한 명이 "오늘은 운동장에서 놀아요!"를 알린다고 상상해 봅시다. 선생님이 100명에게 한 명씩 전화하면 느리고 힘들겠지요. 반면 운동장 게시판에 공지를 붙여두면 친구들은 각자 원하는 시간에 공지를 확인할 수 있습니다. Kafka는 여러 프로그램이 사건을 주고받을 수 있도록 만든 분산형 이벤트 스트리밍 플랫폼입니다. 주문 서비스가 주문 완료 사실을 발행하면 재고 서비스, 배송 서비스, 알림 서비스가 이 사건을 자기 속도로 읽을 수 있습니다.

중요한 건 Kafka가 단순히 한쪽에서 보낸 메시지를 다른 쪽으로 전달하고 버리는 도구가 아니라는 점입니다. 이벤트를 로그에 일정 기간 보관하고, 서로 다른 소비자 그룹이 독립적으로 읽고, 필요하면 앞서 처리한 이벤트를 다시 읽을 수 있습니다. 이 특성 덕분에 서비스들이 서로 직접 통신해야 하는 횟수를 줄이고, 일시적으로 소비자가 중단되어도 나중에 밀린 이벤트를 처리하는 구조를 만들 수 있습니다.

2. 이벤트 스트리밍이란?

이벤트(Event)는 '무슨 일이 일어났다'는 사실을 나타냅니다. '주문번호 A-100을 결제했다', '상품 X가 입고됐다', '택배가 배송 완료됐다'가 예시입니다. 이벤트 스트리밍은 이런 사건들을 계속 받아서 저장하고 다른 프로그램에 전달하고 분석하는 방식입니다.

여기서 스트리밍은 꼭 영상처럼 끊임없이 화면이 움직인다는 뜻이 아닙니다. 이벤트가 발생할 때마다 새 기록이 이어서 들어오는 흐름을 다룬다는 뜻입니다. 1초에 1건일 수도 있고 10만 건일 수도 있습니다. Kafka는 이벤트를 ① 생산·구독하고 ② 일정 기간 안전하게 저장하며 ③ 실시간 또는 나중에 처리하는 기능을 결합합니다.

Kafka의 장점은 이벤트의 생산자와 소비자의 처리 속도를 어느 정도 분리할 수 있다는 것입니다. 그러나 무한히 쌓아둘 수 있는 마법 상자는 아닙니다. 저장 공간, 보존 정책, 복제, 파티션 처리량을 설계해야 합니다.

3. 등장인물: Producer, Broker, Topic, Consumer

Producer(생산자)는 사건을 보내는 프로그램입니다. Java 애플리케이션에서 KafkaTemplate로 메시지를 보낸다면 그 애플리케이션이 Producer 역할을 하는 것이지요. Broker(브로커)는 메시지를 저장하고 요청에 응답하는 Kafka 서버입니다. 여러 Broker가 모여 Cluster를 만들 수 있습니다.

Topic(토픽)은 이벤트 종류에 붙이는 이름입니다. 예를 들어 orders, inbound-completed 같은 이름을 사용합니다. Topic 내부는 하나 이상의 Partition(파티션)으로 나뉩니다. Partition은 기록이 순서대로 쌓이는 독립적인 로그입니다. 하나의 Topic이 세 개 파티션으로 나뉘었다면 Topic 전체의 유일한 순서보다는 각 파티션 내부의 순서가 보장된다고 생각해야 합니다.

Consumer(소비자)는 Topic의 기록을 읽는 애플리케이션입니다. 같은 Group ID를 가진 소비자들은 일반적인 Consumer Group 모델에서 파티션을 나눠 맡습니다. 서로 다른 Group ID를 사용하면 각 그룹이 같은 이벤트를 독립적으로 읽을 수 있습니다. 그러므로 주문 완료 이벤트를 배송 팀과 알림 팀이 둘 다 읽고 싶을 때, 반드시 메시지를 두 번 생산할 필요는 없습니다.

4. Record는 무엇으로 이뤄질까?

Kafka의 Record 또는 Event에는 대표적으로 Key, Value, Timestamp, Headers가 있습니다. Value는 실제로 전달할 내용입니다. 예를 들어 {"orderId":"A-100","status":"PAID"} 같은 JSON을 넣을 수 있습니다. Key는 메시지의 파티션 선택 등에 영향을 줄 수 있는 값입니다. 같은 주문번호에 관한 이벤트의 순서를 지키고 싶다면 orderId를 Key로 지정하는 설계가 흔합니다.

Timestamp는 이벤트에 연결된 시각입니다. Topic 설정에 따라 생산자가 기록한 시각 또는 브로커가 받은 시각을 활용할 수 있습니다. Headers는 추적 ID, 이벤트 타입 등 부가 메타데이터에 적합합니다. Key와 Value는 결국 바이트로 직렬화되어 전달되므로 StringSerializer나 JSON/Avro/Protobuf 등 직렬화 방식을 생산자와 소비자가 합의해야 합니다.

초보자가 자주 헷갈리는 포인트는 Key가 데이터베이스의 PK와 똑같은 개념은 아니라는 점입니다. Kafka가 같은 Key의 Record를 자동으로 덮어쓰지 않습니다. 로그에는 여러 번 기록될 수 있으며, 토픽의 로그 압축 정책 등과 결합되면 나중에 키 기준 정리가 일어날 수 있습니다.

5. Partition, Offset, 복제를 그림 없이 이해하기

학교 게시판에 공지가 너무 많아져서 1반, 2반, 3반 게시판으로 나눴다고 생각하세요. 이 게시판 한 장이 Partition에 해당합니다. 각 게시판에서는 공지가 0, 1, 2, 3... 순서로 붙습니다. 이 번호가 Offset입니다. 중요한 점: Partition 0의 Offset 3과 Partition 1의 Offset 3은 서로 다른 레코드입니다. Offset은 Topic 전체가 아니라 파티션별 위치입니다.

브로커 한 대가 고장 나면 기록이 사라질 위험이 있습니다. 이를 줄이기 위해 파티션의 사본을 다른 브로커에 유지하는 복제(Replication)를 구성합니다. 복제 계수 RF=3이면 일반적으로 파티션의 복제본 3개가 서로 다른 브로커에 배치됩니다. 이때 하나의 복제본이 Leader 역할을 맡으며 다른 복제본들은 데이터를 따라 복제합니다. 다만 RF=3이라고 어떤 장애 상황에서도 절대 데이터가 유실되지 않는다는 뜻은 아닙니다. Producer 확인 설정, 동기 복제본(ISR), 장애 전환 정책이 함께 중요합니다.

오프셋은 데이터의 위치 번호, Commit은 소비자가 '재시작하면 여기부터 처리할게'라고 그룹의 진행 위치를 기록하는 행동입니다. 아직 첫 장에서는 두 개를 구분해 기억하면 충분합니다.

6. 메시지를 보내고 읽는 실제 흐름

① 사용자가 주문을 완료합니다. ② 주문 서비스가 DB에 주문 정보를 저장합니다. ③ 주문 완료 이벤트를 Kafka의 orders Topic에 발행합니다. ④ Producer는 해당 레코드가 어느 파티션으로 갈지 정하고 해당 파티션의 Leader Broker에 전송합니다. ⑤ Kafka는 레코드를 파티션 로그에 기록하고 설정에 따른 성공·실패 응답을 돌려줍니다. ⑥ 배송 서비스 Consumer가 poll로 레코드를 가져옵니다. ⑦ 배송 서비스는 배송 요청 업무를 처리합니다. ⑧ 처리 완료 후 적절한 시점에 Offset을 Commit합니다.

이 설명만 보면 단순하지만 현실에서는 어느 단계에서도 장애가 날 수 있습니다. Kafka에는 기록했는데 Producer가 응답을 못 받으면 재시도할 수 있고, 배송 DB에 저장했지만 Offset Commit 전에 죽으면 동일 이벤트가 다시 전달될 수 있습니다. 그러므로 Consumer 코드는 중복 실행되더라도 결과가 잘못되지 않도록 멱등성(Idempotency)을 설계하는 것이 중요합니다.

특히 DB 저장과 Kafka 발행은 서로 다른 시스템 작업입니다. 둘 사이에 원자적인 단일 트랜잭션이 자동으로 생기는 것은 아닙니다. 중요한 경우에는 Transactional Outbox 패턴 등을 고려해야 합니다.

7. 직접 실습: 로컬 Kafka 시작

실습을 위해 Java와 운영 환경을 먼저 복잡하게 준비할 필요는 없습니다. Docker를 설치했다면 로컬 Kafka 이미지를 이용하는 방법이 편합니다. 다음은 단일 노드 개발용 예시이며 운영용 고가용성 설정이 아닙니다. 명령어는 사용하는 Kafka 버전과 이미지 배포 정책을 확인한 뒤 실행하세요.

Docker 예시:

docker run -d --name kafka -p 9092:9092 apache/kafka:4.3.0

Kafka 배포판의 bin 디렉터리에 포함된 CLI를 사용한다고 가정하면 토픽을 생성합니다.

bin/kafka-topics.sh --bootstrap-server localhost:9092 --create --topic hello-kafka --partitions 1 --replication-factor 1

생산자 콘솔을 실행합니다.

bin/kafka-console-producer.sh --bootstrap-server localhost:9092 --topic hello-kafka

여기에 hello, kafka!를 입력하고 Enter를 누릅니다. 다른 터미널에서 소비자를 실행합니다.

bin/kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic hello-kafka --from-beginning

메시지가 보이면 '생산 → 브로커 저장 → 소비' 과정을 직접 확인한 것입니다. --from-beginning은 해당 소비자가 시작할 읽기 위치를 초기화할 때 유용하지만, 기존 그룹에 이미 저장된 Offset이 있으면 그 그룹의 진행 위치가 우선할 수 있습니다. 운영에서 무작정 실행해 과거 데이터를 재처리하지 않도록 주의하세요.

8. Java / Spring Boot 개발자는 어떻게 사용할까?

Spring Boot 프로젝트에서는 spring-kafka 의존성을 추가한 뒤 KafkaTemplate와 @KafkaListener를 사용하는 경우가 많습니다. 아래 코드는 동작 구조를 간략하게 보여주는 개념 예시입니다. 실제 운영 코드는 토픽·보안·직렬화·재시도·멱등 처리를 추가해야 합니다.

Producer 예시:

@Service
@RequiredArgsConstructor
class OrderEventPublisher {
    private final KafkaTemplate<String, String> kafkaTemplate;
    public void publish(String orderId, String payload) {
        kafkaTemplate.send("orders", orderId, payload)
            .whenComplete((result, ex) -> {
                if (ex != null) {
                    // 실패 로깅 및 재시도/Outbox 복구 전략 적용
                }
            });
    }
}

Consumer 예시:

@Component
class OrderEventConsumer {
    @KafkaListener(topics = "orders", groupId = "shipping-service")
    public void onMessage(String payload) {
        // 이벤트 파싱, 중복 처리 방지, 비즈니스 트랜잭션 수행
    }
}

KafkaTemplate.send(...)는 비동기입니다. Java 메서드가 반환됐다는 사실과 Kafka 발행이 성공했다는 사실은 다릅니다. @KafkaListener의 Offset 커밋 동작은 컨테이너 설정과 처리 성공/실패에 영향을 받습니다. Kafka Listener에서 예외를 무조건 삼키면 실패한 이벤트가 정상 처리된 것으로 간주될 수 있으므로 예외 처리 정책을 명시해야 합니다.

9. 운영에서 자주 만나는 다섯 가지 문제

첫째, Producer가 메시지를 보냈는데 Consumer가 못 받았다고 합니다. 다른 토픽을 구독하고 있는지, Group ID가 무엇인지, Consumer의 현재 Offset이 어디인지 확인합니다. 둘째, Producer 전송은 성공인데 업무 데이터가 반영되지 않습니다. Consumer Listener 오류와 DLQ/재시도 정책, DB 트랜잭션 결과를 확인해야 합니다.

셋째, Consumer Lag이 계속 증가합니다. 생산 속도와 소비 속도 차이, 파티션 수, 처리 중 외부 API와 DB 병목, Consumer 리밸런스 여부를 살핍니다. 넷째, 동일한 주문이 두 번 처리됐습니다. Kafka의 일반적인 at-least-once 재전달 가능성을 이해하고, 주문번호와 이벤트 ID로 중복 처리를 막는 방식을 설계합니다. 다섯째, Broker 한 대가 장애가 났습니다. 파티션 복제 계수, ISR과 Leader 변화, 최소 동기 복제 설정이 정상인지 먼저 확인합니다.

운영 면접에서 'Kafka를 도입하면 데이터 유실이 없나요?'라는 질문에 무조건 그렇다고 말하면 위험합니다. 어디에 실패 가능성이 있고 어떤 설정과 구조로 완화했는지 설명하는 편이 정확합니다.

10. 면접 질문 8개와 꼬리 질문

Q1. Kafka는 무엇인가요? — 이벤트를 저장하고 여러 소비자에게 전달·재처리할 수 있는 분산 이벤트 스트리밍 플랫폼입니다.
Q2. Producer와 Consumer는 무엇이 다른가요? — 전자는 이벤트를 발행하고 후자는 구독해 읽습니다.
Q3. Topic과 Partition은 어떻게 다르나요? — Topic은 논리적인 이벤트 분류, Partition은 독립적인 순서와 저장·병렬성의 단위입니다.
Q4. Offset은 무엇인가요? — 파티션 로그 내 레코드의 위치입니다.
Q5. Consumer Group이 필요한 이유는? — 같은 그룹 내에서 파티션을 분담하여 병렬 소비하기 위해서입니다. 다른 그룹은 같은 이벤트를 독립적으로 읽을 수 있습니다.
Q6. Consumer가 실패했다 재시작하면? — 커밋된 Offset과 재할당 결과에 따라 다시 읽으며, 이미 처리한 메시지가 중복 전달될 수 있습니다.
Q7. Kafka에 메시지가 기록되면 바로 삭제되나요? — 일반적인 로그에서는 Consumer가 읽었다는 이유로 바로 삭제되지 않고 토픽 보관 정책에 따릅니다.
Q8. Kafka를 쓰면 데이터 정합성이 자동으로 해결되나요? — 아닙니다. DB와 Kafka 사이의 이중 쓰기, 중복 수신, 스키마 변경, 멱등 처리와 장애 대응을 설계해야 합니다.

꼬리 질문 연습: 파티션이 한 개인 토픽에서 Consumer Group에 멤버 5개를 띄우면 실제 처리에는 몇 개가 참여할까요? 같은 주문 ID의 이벤트 순서를 유지하려면 Producer에서 어떤 값을 Key로 삼을까요? Offset을 처리 전에 커밋하는 것과 처리 후에 커밋하는 것은 각각 어떤 문제가 있을까요?

11. 이 글을 다 읽은 뒤 점검하기

다음 다섯 가지를 빈 종이에 그려 보세요. (1) Producer → Broker → Consumer 흐름, (2) Topic 안에 3개 Partition이 있는 그림, (3) Partition마다 독립적인 Offset 번호, (4) Consumer Group 두 개가 같은 Topic을 따로 읽는 모습, (5) DB 저장과 Kafka 발행 사이에 장애가 날 수 있는 지점. 이 다섯 개를 자신의 말로 설명할 수 있다면 1편의 목표를 달성한 것입니다.

다음 글에서는 Kafka의 핵심 설계인 Partition, Replication, Leader/Follower, ISR, acks를 더 깊이 다룹니다. 특히 '왜 파티션은 처리량을 높여주지만 순서 보장 범위를 제한하는가'를 실제 예시와 함께 살펴봅니다.
