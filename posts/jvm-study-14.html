1. 처음부터 모든 길을 고속도로로 만들지 않는다

처음 가는 길은 지도를 보고 이동하지만 매일 반복하는 길은 익숙한 경로로 빠르게 움직입니다. HotSpot도 처음에는 실행 정보를 모으고, 자주 실행되는 부분에 최적화 비용을 집중할 수 있습니다. 실행 중 번역하는 컴파일이 **JIT(Just-In-Time)**입니다.

이 비유에서 익숙한 길이 영원히 같다는 보장은 없습니다. 새로운 구현 타입이 들어오거나 실행 패턴이 바뀌면 기존 최적화 가정이 깨질 수 있습니다. JVM은 최적화를 취소·교체하면서도 프로그램 의미를 유지해야 합니다. 이 적응형 특성을 이해해야 배포 직후와 안정 상태 성능 차이를 설명할 수 있습니다.

2. C1·C2와 Tiered Compilation

실행 형태 대표 역할 비용·조건
Interpreter 바이트코드 해석, 프로파일 수집 낮은 준비 비용, 반복 해석 비용
C1 빠른 컴파일과 프로파일링 단계 기동·중간 성능 개선
C2 더 강한 최적화 분석·컴파일 시간과 메모리 필요
OSR 실행 중인 긴 루프를 컴파일 코드로 전환 메서드 진입만 기다리지 않음

일반적인 HotSpot 계층형 컴파일은 0~4 수준으로 설명합니다. 0은 인터프리터, 중간 수준은 C1의 프로파일링 강도 차이, 4는 C2와 관련됩니다. 모든 메서드가 0→1→2→3→4를 빠짐없이 정확히 순서대로 거치는 것은 아닙니다. 호출·루프 빈도, 프로파일 상태, 큐와 자원 등에 따라 경로가 달라집니다.

OSR(On-Stack Replacement)은 메서드가 한 번 호출되어 오래 도는 경우에도 루프 내부에서 최적화된 실행으로 넘어갈 수 있게 합니다. “JIT는 메서드 호출 횟수만 센다”는 설명이 불완전한 이유입니다. 구현 근거: 계층형 컴파일

3. 인라이닝은 호출 비용만 줄이는 것이 아니다

작은 메서드를 호출하는 대신 그 동작을 호출자의 최적화 범위에 넣는 것이 인라이닝입니다. 호출 경계가 없어지면 상수 전파·불필요 분기 제거·탈출 분석 등을 더 넓게 수행할 수 있습니다. 결과적으로 객체 할당까지 사라질 수 있습니다.

반면 모든 메서드를 무한히 인라이닝하면 코드 크기가 커지고 컴파일 비용과 명령 캐시 부담이 생깁니다. 메서드 크기, 호출 빈도, 타입 프로파일 등 판단 요소가 있습니다. “private면 무조건 인라이닝”이나 “메서드가 한 줄이면 반드시 인라이닝” 같은 규칙은 보장이 아닙니다.

4. 추측 최적화와 Deoptimization

인터페이스 호출이 지금까지 한 구현체로만 들어왔다면 JIT는 그 패턴을 활용할 수 있습니다. 하지만 나중에 다른 타입이 들어올 수 있으므로 가드와 대체 경로, 필요 시 **역최적화(Deoptimization)**가 필요합니다. 더 이상 유효하지 않은 코드에서 안전한 실행 상태로 되돌아가고 재컴파일할 수 있습니다.

따라서 실행 중 인터페이스를 쓰면 항상 느리다거나 final을 붙이면 항상 빨라진다고 단정할 수 없습니다. 실제 타입 분포와 인라이닝 결과가 중요합니다. 구현을 두 개에서 여러 개로 바꿨을 때 프로파일이 달라져 성능이 변할 수 있지만, 그 크기는 측정해야 합니다.

5. JIT를 관찰하는 실행 예제

// file: Lesson14.java
public class Lesson14 {
    interface Price { int apply(int value); }
    static final class PlusOne implements Price {
        public int apply(int value) { return value + 1; }
    }
    static final class PlusTwo implements Price {
        public int apply(int value) { return value + 2; }
    }
    static volatile long sink;
    static long run(Price price, int n) {
        long sum = 0;
        for (int i = 0; i < n; i++) sum += price.apply(i);
        return sum;
    }
    public static void main(String[] args) {
        for (int i = 0; i < 40; i++) sink = run(new PlusOne(), 100_000);
        System.out.println(run(new PlusOne(), 100));
        System.out.println(run(new PlusTwo(), 100));
    }
}

javac --release 21 -g Lesson14.java
java -XX:+PrintCompilation Lesson14
java -XX:+UnlockDiagnosticVMOptions -XX:+PrintInlining Lesson14
java -Xint Lesson14

논리적 결과는 5050과 5150입니다. PrintCompilation 로그에는 다른 표준 라이브러리 메서드도 섞입니다. % 같은 표식은 OSR 컴파일을 읽는 단서가 될 수 있습니다. 로그 형식과 발생 시점은 버전·환경에 따라 달라집니다. 결과가 “not entrant”로 바뀌는 상태도 정상적인 코드 교체의 일부일 수 있습니다.

-Xint는 해석 실행을 관찰하기 위한 로컬 비교 옵션입니다. 이 짧은 실험을 Stopwatch로 재서 운영 환경에서 몇 배 빠르다고 발표하는 용도로 쓰지 않습니다. 원하는 메서드가 실제 컴파일되었는지와 프로그램 의미가 유지되는지를 관찰하는 것이 목표입니다.

6. Code Cache와 Compiler Control

JIT가 생성한 기계 코드는 Code Cache에 저장됩니다. Heap과 별도 예산을 사용하며 컴파일 코드와 VM 코드 등 수명이 다른 항목을 관리합니다. 계층형 컴파일과 분할된 Code Cache는 코드 종류별 관리를 돕습니다. 메서드를 바꾸지 않아도 JVM이 실행 중 여러 버전의 코드를 만들고 교체할 수 있습니다.

Compiler Control은 특정 메서드의 컴파일·인라이닝 등에 대한 진단·제어를 제공하는 HotSpot 기능입니다. 일반 서비스의 첫 성능 해결책으로 지시문을 무작정 추가하지 마세요. 프로파일에서 확인한 경로를 제한된 실험으로 검증할 때 사용하며, VM 버전과 사용한 지시문을 기록합니다. 공식 근거: Compiler Control

Code Cache 부족이 보이면 공간만 늘리기 전에 코드 생성량, 동적 클래스, 배포·플러그인 수명과 실제 컴파일 상태를 확인합니다. jcmd PID Compiler.codecache와 JFR 등이 조사에 도움이 됩니다.

7. 손으로 잰 벤치마크가 거짓말하는 다섯 이유

첫째, 결과를 사용하지 않으면 dead code elimination으로 계산이 사라질 수 있습니다. 둘째, 입력을 상수로 고정하면 constant folding으로 미리 계산될 수 있습니다. 셋째, 워밍업 전후 실행 형태가 다릅니다. 넷째, 같은 프로세스에서 실험 순서가 프로파일과 캐시에 영향을 줄 수 있습니다. 다섯째, GC·OS·타이머·백그라운드 작업이 짧은 측정을 흔듭니다.

JMH는 워밍업·측정 반복·fork·결과 소비 등 JVM 벤치마크를 위한 도구를 제공합니다. 그렇다고 JMH 사용만으로 잘못된 입력 모델과 비대표 부하가 자동 교정되지는 않습니다. 실제 서비스 처리량·지연은 DB·네트워크·락을 포함한 대표 부하에서 별도로 검증해야 합니다. 공식 프로젝트

8. 장애 사례: 배포 직후 CPU가 높고 곧 안정됨

클래스 로딩과 초기화, 캐시 적재, 커넥션 생성, JIT 컴파일이 기동 근처에 몰릴 수 있습니다. Compiler Thread가 CPU를 쓴다고 무조건 오류는 아닙니다. 그러나 작은 CPU 제한 아래 반복 재시작이 발생하면 워밍업을 끝내지 못하는 악순환이 생길 수 있습니다.

JFR에서 실행 표본·컴파일·할당·GC를 나눠 보고 readiness와 트래픽 유입 시점을 비교합니다. 무조건 대기 시간을 길게 고정하기보다 실제 준비 조건과 대표 경로 예열을 검증합니다. 스케일아웃 직후 p99와 CPU를 안정 상태와 따로 측정하면 이 효과를 놓치지 않을 수 있습니다.

더 깊이: 워밍업을 측정 설계에 반영하기

워밍업 전 결과와 안정 상태 결과는 서로 다른 질문에 답합니다. 단발성 명령 도구나 짧은 배치에서는 기동·초기 실행 비용이 중요할 수 있고, 장시간 서버에서는 안정 상태 처리량이 중요할 수 있습니다. 무조건 워밍업을 길게 해 기동 비용을 지우는 것도 목적에 따라 잘못된 측정입니다.

JMH에서 warmup·measurement·fork를 정할 때는 어떤 상태를 측정하는지 먼저 적습니다. 입력을 한 값으로 고정하지 않고 실제 범위에 맞추며 결과를 소비하고, 실험 대상 밖에서 데이터를 준비할지 여부도 의도해야 합니다. 측정 구간 안에서 매번 데이터를 만들면 자료구조 연산과 할당 비용이 섞일 수 있습니다.

성능 차이가 보여도 '왜'는 별도 증거가 필요합니다. 컴파일 로그·인라이닝·할당·GC·CPU 표본을 통해 가설을 확인하세요. 결과를 소비하는 코드와 volatile 접근 같은 측정 장치 자체가 성능을 지배하는지도 점검합니다. 수치 하나보다 실험 조건과 재현 가능성이 더 중요한 경우가 많습니다.

심화 Q. 운영 서버를 오래 켜면 언제나 더 빨라지나요?

워밍업과 캐시 적재로 좋아질 수 있지만 누수·커진 live set·Code Cache·프로파일 변화·외부 자원 상태 때문에 나빠질 수도 있습니다. 시간 경과 자체를 성능 향상의 보장으로 보지 않습니다.

기동 직후와 안정 구간, 장기 실행 구간을 따로 관측하고 각각 어떤 비용이 변하는지 확인해야 합니다.

차근차근 이해하기: 자주 쓰는 길에서 얻은 정보로 최적화한다

인터프리터는 바이트코드의 의미를 수행하고, JIT는 선택된 코드를 기계 코드로 컴파일합니다. Tiered Compilation은 빠르게 컴파일하는 단계와 더 많은 정보를 이용해 최적화하는 단계를 연결합니다. 초반에는 실행 정보를 모으고, 반복되는 경로를 더 적극적으로 최적화할 수 있습니다. 다만 모든 메서드가 반드시 같은 단계를 같은 순서와 횟수로 거치는 고정 수업 과정은 아닙니다.

여기서 프로파일은 “이 호출 지점에 주로 어떤 타입이 왔는가”, “어떤 분기가 자주 선택되었는가” 같은 실행 관찰 정보입니다. 소스의 타입 선언만으로 확정할 수 없는 정보가 최적화에 도움이 됩니다. 하지만 관찰한 과거가 미래를 항상 보장하지 않으므로, 최적화에 사용한 가정이 깨졌을 때 올바른 실행으로 돌아갈 장치가 필요합니다.

인터페이스 호출에서 무슨 추측을 할 수 있을까

기존 Price 예제에서 한 호출 지점에 오랫동안 PlusOne만 전달되었다고 가정합시다. JIT는 실제 타입이 거의 하나라는 정보를 이용해 호출을 인라인하는 등 최적화할 수 있습니다. 나중에 PlusTwo가 들어오면 다른 경로를 사용하거나 재컴파일·역최적화가 관련될 수 있습니다. 어떤 일이 실제로 발생했는지는 로그로 확인해야 합니다. 코드에 구현체가 두 개 있다는 사실만으로 역최적화가 반드시 발생했다고 말할 수는 없습니다.

관찰 또는 변화 가능한 최적화 관점 해석의 한계
한 타입이 반복 등장 호출 대상 특화와 인라이닝에 유리할 수 있음 모든 호출이 무조건 인라인되지는 않음
인라이닝 후 값이 상수로 보임 계산 단순화와 불필요한 코드 제거 가능 소스 줄 수만큼 기계 명령이 남는 것은 아님
새로운 타입이 등장 기존 가정의 재검토가 필요할 수 있음 반드시 오류나 성능 장애라는 뜻은 아님
긴 루프가 계속 실행 OSR을 통한 실행 코드 전환 가능 메서드 재호출만이 최적화 진입점은 아님

인라이닝이 다음 최적화의 문을 여는 이유

메서드 A가 B를 호출할 때 B의 내용을 A 안에서 볼 수 있게 되면, B의 인자로 전달한 값이 사실은 상수라는 것을 알 수 있습니다. 상수 조건의 분기를 줄이고 사용하지 않는 계산을 없앨 수 있습니다. 따라서 인라이닝의 효과는 호출·반환 비용을 아끼는 것보다 넓습니다.

반대로 너무 많이 펼치면 코드 크기가 커지고 명령 캐시와 컴파일 비용에 영향을 줄 수 있습니다. 그래서 “짧은 메서드는 모두 인라인”, “소스에서 직접 펼치면 항상 더 빠름” 같은 규칙은 적절하지 않습니다. 가독성을 해치며 수동으로 펼치기 전에 실제 병목과 컴파일 결과를 확인해야 합니다.

간단한 시간 측정이 틀리는 장면을 만들어 보자

계산 함수를 백만 번 호출하고 결과를 전혀 쓰지 않는 측정을 상상해 봅시다. 관찰 가능한 효과가 없다면 최적화가 일부 계산을 제거할 수 있습니다. 같은 상수 입력만 계속 주면 상수 전파의 영향을 크게 받을 수도 있습니다. 반대로 매번 println을 넣으면 계산보다 출력과 동기화 비용을 더 많이 측정할 수 있습니다.

그래서 측정에는 입력 분포, 결과 소비, 워밍업, 여러 독립 실행, 측정 시간과 오차를 고려해야 합니다. JMH는 이런 실수를 줄이는 장치를 제공하지만 벤치마크가 실제 업무를 대표하는지까지 대신 판단하지는 않습니다. 작은 순수 계산의 결과를 DB 호출이 포함된 전체 요청 성능으로 곧바로 확장하면 안 됩니다.

새 프로세스와 같은 프로세스를 나누어 비교하기

배포 직후 지연이 관심사라면 시작부터의 지연을 측정해야 합니다. 안정 상태 처리량이 관심사라면 워밍업 이후를 따로 측정해야 합니다. 두 값을 평균 하나로 섞으면 기동 문제와 정상 처리 성능을 모두 흐릴 수 있습니다. 같은 프로세스 내 반복과 새 프로세스 반복을 구분해서 기록하는 이유입니다.

확인 문제. JIT 로그에 컴파일 기록이 있으면 그 메서드가 병목이라는 뜻인가요?

판단: 컴파일 기록은 해당 컴파일 활동의 증거이지 메서드가 전체 시간을 가장 많이 소비한다는 증거가 아닙니다. 호출 빈도가 높아도 실행 비용은 작을 수 있습니다.

연결: 프로파일링에서 시간이 많이 쓰인 경로를 찾고, 그 경로의 인라이닝·컴파일 상태를 보조 자료로 조사합니다. 대기 시간이 대부분인 서비스라면 계산 최적화보다 외부 호출과 락의 영향을 먼저 확인할 수도 있습니다.

꼬리질문: 역최적화 횟수를 0으로 만들면 좋나요? 항상 그렇지는 않습니다. 적응적 최적화 과정에서 정상적으로 발생할 수 있으므로 반복 빈도, CPU 비용, 지연과의 상관관계를 확인해야 합니다.

심화 실험실: 같은 인터페이스 호출이 실행 중 달라지는 이유

대부분 같은 손님이 온다는 관측은 영구적인 약속이 아니다

매일 같은 배송사가 오는 창구라면 자주 쓰는 처리 절차를 빠르게 만들 수 있습니다. 하지만 새 배송사가 오면 기존 가정이 여전히 맞는지 확인해야 합니다. JIT의 프로파일 기반 최적화도 실제 관측한 타입과 실행 빈도를 활용할 수 있지만, 관측을 Java 언어의 영구 보장으로 바꾸지는 못합니다.

// file: Deep14.java
public class Deep14 {
    interface Fee { int apply(int quantity); }
    static class Normal implements Fee {
        public int apply(int quantity) { return quantity + 1; }
    }
    static class Express implements Fee {
        public int apply(int quantity) { return quantity + 10; }
    }
    static volatile long sink;
    static long batch(Fee fee) {
        long sum = 0;
        for (int i = 0; i < 100; i++) sum += fee.apply(i);
        return sum;
    }
    public static void main(String[] args) {
        Fee normal = new Normal();
        for (int i = 0; i < 30_000; i++) sink = batch(normal);
        System.out.println(batch(normal));
        System.out.println(batch(new Express()));
    }
}

javac --release 21 Deep14.java
java -XX:+UnlockDiagnosticVMOptions -XX:+PrintCompilation -XX:+PrintInlining Deep14

업무 결과는 5050, 5950입니다. 로그에는 JDK 내부 컴파일 기록도 섞입니다. 자신의 클래스와 batch·apply를 찾아 인라이닝 판단을 읽습니다. 로그 순서와 최적화 결정, deoptimization 발생 여부는 실행 환경에 따라 달라집니다. 이 예제가 반드시 특정 컴파일 단계나 deoptimization 한 번을 재현한다고 주장하지 않습니다.

가능한 최적화와 반드시 지켜야 할 의미

Normal만 관측된 호출 지점은 타입 검사와 함께 빠른 경로로 최적화될 수 있습니다. Express가 나중에 들어왔을 때 JVM은 새 타입에 맞는 올바른 결과를 내야 합니다. 검사 실패 후 다른 경로로 가거나, 기존 코드의 가정을 무효화하고 재컴파일하는 등 구현에 따라 대응할 수 있습니다. “인터페이스는 언제나 느리다”도, “한 번 인라인되면 이후 타입 변화는 무시한다”도 정확하지 않습니다.

개념 해결하는 문제 흔한 혼동
인라이닝 호출 경계를 없애 더 넓은 최적화 소스를 사람이 복사한 것과 동일하다고 생각
OSR 오래 도는 메서드의 실행 중 루프를 최적화 코드로 전환 다음 메서드 호출까지 무조건 기다린다고 생각
Deoptimization 기존 최적화 가정으로 실행하기 어려운 상태 복원 업무 예외 또는 JVM 장애라고 단정
Code cache 컴파일한 네이티브 코드 보관 Java 객체 Heap과 동일하게 취급

volatile sink가 있어도 벤치마크는 아니다

예제의 sink는 결과가 전혀 사용되지 않는 실험보다 관측을 분명하게 만들지만, 그 자체로 정밀 성능 측정이 되지는 않습니다. volatile 쓰기 비용이 추가되고, 루프 패턴이 실제 요청과 다르며, 입력 타입 분포도 인위적입니다. 이 코드는 컴파일 동작 관찰용입니다. 성능 비교는 JMH 같은 도구로 warm-up, 측정 반복, 별도 프로세스 fork, 결과 소비를 설계해야 합니다.

또한 작은 메서드만 빠르게 만든 결과가 서비스 처리량 개선으로 바로 이어지는 것은 아닙니다. 대부분의 시간이 DB 대기라면 계산 메서드의 20% 개선은 전체 응답에서 매우 작을 수 있습니다. 전체 시간 중 그 코드가 차지하는 비중을 먼저 프로파일링하는 것이 우선입니다.

새 인스턴스가 느릴 때 확인할 순서

배포 직후 CPU가 높다는 이유만으로 JIT를 끄지 않습니다. 클래스 로딩과 초기화, JIT 컴파일, 캐시 구축, 트래픽 집중을 분리합니다. compiler thread 활동과 코드 캐시 상태, 애플리케이션 CPU 스택을 확인하고 이전 인스턴스와 동일한 트래픽·자원 조건에서 비교합니다. 워밍업 트래픽도 실제 유형을 반영하지 않으면 다른 타입 분포로 준비되어 효과가 제한될 수 있습니다.

심화 면접. JIT가 이미 인터페이스 구현체를 인라인했는데 다른 구현체가 들어오면 오답이 나오나요?

답변: 올바른 JVM 구현은 Java의 의미를 유지해야 합니다. 관측한 타입을 전제로 최적화했다면 그 전제가 유효한지 검사하거나 관련 의존성을 관리하고, 달라질 때 올바른 실행 경로로 복귀해야 합니다.

주의: 모든 경우가 반드시 deoptimization 하나로만 처리되는 것은 아닙니다. 타입 검사와 느린 경로, 여러 타입의 인라이닝 등 실제 컴파일 결과에 따라 다릅니다.

실무: 타입 분포가 다른 마이크로벤치마크 하나로 운영 성능을 단정하지 않고 실제 호출 지점의 프로파일과 워밍업 이후 성능을 확인하겠습니다.

추가 근거: HotSpot 성능 개선과 계층형 컴파일, OpenJDK JMH.

9. 상세 면접 Q&A

Q1. JIT는 정확히 몇 번 호출하면 시작하나요?

단일 고정 횟수로 모든 메서드를 설명할 수 없습니다. 호출과 루프 빈도, 계층형 정책, 프로파일·컴파일 큐·자원 조건 등이 영향을 줍니다. 임계값 하나를 언어의 보장값처럼 외우지 말고 실제 로그로 확인합니다.

구체적으로: 컴파일 결정은 호출 횟수뿐 아니라 루프 실행과 단계별 정책, 실행 프로파일, 컴파일 자원 등의 영향을 받습니다. 숫자 하나를 모든 메서드의 보장으로 제시하지 않습니다.

꼬리질문까지: 정확한 실행에서는 PrintCompilation 등으로 실제 컴파일 시점을 관찰하고 관련 옵션을 기록합니다.

Q2. 인라이닝하면 스택 트레이스가 전부 사라지나요?

실제 호출 경계가 최적화되어도 JVM은 Java의 예외·디버깅·역최적화 등에 필요한 정보를 유지해야 합니다. 소스의 논리적 호출과 실제 기계 프레임을 구분합니다. 인라이닝을 단순한 텍스트 복붙으로만 이해하면 이 부분을 설명하기 어렵습니다.

구체적으로: 실제 호출 경계가 없어져도 JVM은 논리적 호출 의미와 디버깅·예외 등에 필요한 정보를 유지할 수 있습니다. 소스 메서드와 물리 프레임을 구분해야 합니다.

꼬리질문까지: 인라이닝 여부를 스택 트레이스의 한 줄만으로 단정하기보다 컴파일 정보를 함께 확인하세요.

Q3. Deoptimization은 JVM 오류인가요?

추측 최적화 가정이 바뀔 때 안전한 실행 상태로 돌아가는 정상 메커니즘일 수 있습니다. 잦은 역최적화가 성능에 영향을 줄 수는 있으므로 원인을 관측해야 하지만 발생 사실만으로 버그라고 하지 않습니다.

구체적으로: 실행 중 새로운 타입이나 조건이 나타나 최적화 가정이 맞지 않으면 더 일반적인 실행으로 돌아가는 것이 정확성을 지키는 정상 장치일 수 있습니다.

꼬리질문까지: 빈번한 반복으로 비용이 커지는지 확인한 뒤 성능 문제로 판단하며 횟수 0을 무조건 목표로 삼지 않습니다.

Q4. 반환값을 출력하면 마이크로벤치마크 문제가 모두 해결되나요?

계산 제거 일부를 막는 데 도움이 될 수 있어도 상수 전파·프로파일 오염·워밍업·측정 오버헤드 등은 남습니다. 출력 자체가 병목이 될 수도 있습니다. JMH의 결과 소비·상태·fork·측정 구조를 목적에 맞게 사용합니다.

구체적으로: 출력은 계산 제거를 막는 데 영향을 줄 수 있지만 출력 자체 비용이 측정을 지배할 수 있습니다. 입력 상수화·워밍업·독립 실행 부족도 그대로 남습니다.

꼬리질문까지: JMH를 사용하더라도 실제 업무를 대표하는 입력과 측정 목표는 직접 설계해야 합니다.

Q5. Code Cache는 Xmx 안에 포함되나요?

일반 Java Heap과 별도입니다. 따라서 Xmx만으로 전체 JVM 메모리 예산을 설명할 수 없습니다. 컴파일 코드와 Metaspace·스레드·버퍼 등 다른 영역까지 고려해야 합니다.

구체적으로: 컴파일된 기계 코드를 보관하는 Code Cache는 Java Heap 한도와 별도인 Native 메모리 사용 범주입니다. Xmx만으로 JVM 프로세스 예산을 설명할 수 없는 이유입니다.

꼬리질문까지: 코드 캐시가 커 보이면 정상적인 컴파일 성장인지 한도와 사용 추세를 비교해 판단합니다.

Q6. OSR이 왜 필요한가요?

메서드가 한 번만 호출되어도 내부 루프가 매우 오래 실행될 수 있습니다. 다음 메서드 호출만 기다리면 현재 긴 실행을 최적화하지 못합니다. OSR은 실행 중인 루프에서 컴파일된 경로로 전환하는 데 쓰입니다.

구체적으로: 한 번 호출된 메서드 안의 긴 루프는 메서드 재진입을 기다리지 않고 최적화된 코드로 전환할 필요가 있을 수 있습니다. OSR이 이러한 실행 중 전환을 지원합니다.

꼬리질문까지: 호출 횟수만 세어 뜨거운 코드 여부를 판단하면 긴 루프의 최적화를 설명하기 어렵습니다.

동네 지리에 익숙해진 배달기사가 자주 가는 길을 최적화하지만, 공사로 길이 바뀌면 새 경로로 돌아가는 것과 비슷하다.

HotSpot JDK 21과 JVM 사양을 구별하며 깊게 보기

JIT는 실행 중 얻은 타입과 분기 빈도 정보를 바탕으로 인라이닝과 추측 최적화를 적용할 수 있다. 추측이 틀리면 deoptimization이 일어나 인터프리터 또는 덜 최적화된 코드로 돌아갈 수 있다. 따라서 단순 반복 측정으로 JIT 성능을 단정하기 어렵다.

직접 실험하기

java -XX:+PrintCompilation Main

Java 21에서 본문 실습 파일을 컴파일한 다음 실행하고, 관측값이 일정하지 않은 경우 JVM 옵션과 실행 환경을 기록한다.

운영 관점의 검증 순서

  1. 재현 입력과 실행 환경을 기록한다.
  2. 현상이 JVM 사양이 보장하는 규칙인지 HotSpot의 최적화·휴리스틱인지 구분한다.
  3. 명령 출력·바이트코드·로그를 비교하고 하나의 조건씩 바꿔 반증한다.

추가 심화 면접 Q&A

인라이닝하면 Java 클래스 파일이 바뀌나요?

아니다. JIT가 만든 기계어에 호출 경계를 합치는 최적화이며 원본 소스와 클래스 파일은 그대로다. 어떤 호출이 인라인되는지는 실행 프로파일·코드 크기·컴파일러 판단 등에 달려 있다.
