B-tree와 InnoDB 인덱스: 기본 키가 저장 구조를 바꾼다

읽는 방법

비유로 개념을 잡고 SQL을 실행하기 전 결과를 예상해 보세요. 이번 개정에서는 단계별 동작 추적·비교표·꼬리 질문을 전편에 추가했습니다. 본문의 수치 예시는 설명용이고, 실행 환경에 따라 달라지는 값은 따로 표시했습니다. 기준은 MySQL 8.0·InnoDB, 재현용 서버는 8.0.36입니다. 처음 시작한다면 1편의 서버 준비만 먼저 진행하면 됩니다.

전체 학습 지도·검증 범위

1. 인덱스는 빨리 찾는 대신 따로 관리해야 하는 자료다

창고에 상품이 백만 개 있는데 상품 코드 순으로 위치를 적은 목록이 없다면 원하는 상품을 찾으려고 선반을 전부 확인해야 합니다. 인덱스는 검색에 유리한 순서로 정보를 정리한 별도의 자료구조입니다. 다만 상품을 추가하거나 검색 기준을 바꾸면 목록도 고쳐야 합니다. 인덱스를 무조건 많이 만드는 것이 정답이 아닌 이유입니다.

DB 인덱스를 이해할 때 ‘비교 횟수’만 세면 부족합니다. 저장장치에서 페이지를 몇 번 가져오는지, 메모리에 얼마나 남는지, 넓은 범위를 얼마나 연속적으로 읽는지가 중요합니다. 한 번에 분기 두 개만 확인하는 이진 트리보다 한 페이지에 많은 분기 정보를 담는 B-tree 계열이 저장장치에 잘 맞는 이유입니다.

2. B+tree: 위에서는 방향을, 아래에서는 데이터를 찾는다

InnoDB의 일반적인 인덱스는 B+tree 형태로 이해할 수 있습니다. 공식 문서는 보통 B-tree라는 표현을 사용합니다. 루트 페이지에서 범위를 고르고, 내부 페이지를 거쳐 리프 페이지에 도착합니다. 리프는 키 순서의 순회를 지원합니다. ‘50번부터 80번까지’를 찾을 때 시작점을 찾은 뒤 다음 항목들을 읽기 좋습니다.

설명을 위한 가정으로 한 내부 페이지가 200개 하위 페이지를 가리키고 리프 하나에 100행이 있다고 해 봅시다. 루트 → 내부 → 리프의 세 단계면 200×200×100=400만 행을 표현할 수 있습니다. 이것은 실제 용량 보장이 아닙니다. 키 길이·페이지 빈 공간·행 크기에 따라 달라집니다. 핵심은 분기 수가 많아 높이가 낮아질 수 있다는 점입니다.

상위 페이지는 반복해서 방문하므로 버퍼 풀에 남기 쉽습니다. 따라서 트리 높이가 3이라고 매번 디스크 I/O를 3번 수행하는 것은 아닙니다. 논리적 페이지 방문과 물리 읽기를 구분해야 합니다. 반대로 범위 검색으로 수십만 행을 읽으면 시작점 탐색이 빨라도 전체 조회는 느릴 수 있습니다.

3. InnoDB의 테이블은 기본 키 인덱스 리프에 행을 저장한다

클러스터드 인덱스는 행 데이터를 리프에 저장하는 특별한 인덱스입니다. PRIMARY KEY가 있으면 그것을 사용합니다. 없으면 모든 열이 NOT NULL인 적절한 UNIQUE 인덱스를 선택하고, 그것도 없으면 숨겨진 행 식별자로 구성합니다. 그러므로 “PK를 선언하지 않았으니 클러스터드 인덱스가 없다”는 설명은 틀립니다.

기본 키 순서로 정리되어 있다는 말은 파일의 모든 바이트가 영원히 연속된 물리 주소에 있다는 뜻이 아닙니다. 페이지 분할·할당·재사용이 있습니다. 또한 ORDER BY 없는 SELECT 결과 순서를 보장하지 않습니다. 정렬된 출력이 필요하면 SQL에 정렬 조건을 명시해야 합니다.

4. 보조 인덱스의 주소는 디스크 위치가 아니라 기본 키다

상품 이름 인덱스에서 ‘사과’를 찾으면 무엇을 얻을까요? InnoDB 보조 인덱스 레코드는 인덱스 열과 기본 키 값을 포함합니다. 다른 열까지 필요하면 이 기본 키로 클러스터드 인덱스를 다시 찾아갑니다. 이를 흔히 테이블 접근 또는 bookmark lookup이라고 부릅니다. 상품명 색인에서 상품 번호를 얻고, 번호로 본문 장부를 찾는 구조입니다.

조회가능한 경로읽기 비용
PK로 qty 조회클러스터드 인덱스 → 행추가 보조 인덱스 탐색 불필요
sku로 qty 조회sku 보조 인덱스 → PK → 행후보마다 본문 접근이 필요할 수 있음
sku로 id·sku 조회보조 인덱스가 필요한 열을 포함커버링 경로가 가능

커버링 인덱스는 SQL이 필요한 열을 해당 인덱스에서 얻을 수 있다는 의미입니다. MVCC 가시성 확인 등으로 클러스터드 접근이 필요한 상황도 있으므로 “실행 중 어떤 상황에서도 본문에 절대 접근하지 않는다”까지 확대하지 않습니다.

5. 실습: 같은 조건에서 SELECT 열만 바꿔 보기

CREATE DATABASE IF NOT EXISTS mysql_school;
USE mysql_school;
DROP TABLE IF EXISTS index_demo;
CREATE TABLE index_demo (
  id BIGINT PRIMARY KEY,
  sku VARCHAR(30) NOT NULL,
  qty INT NOT NULL,
  memo VARCHAR(200),
  KEY ix_sku(sku)
) ENGINE=InnoDB;
INSERT INTO index_demo VALUES
 (1,'APPLE',10,'A구역'),(2,'BANANA',20,'B구역'),
 (3,'APPLE',30,'C구역');
EXPLAIN SELECT id, sku FROM index_demo WHERE sku='APPLE';
EXPLAIN SELECT id, sku, memo FROM index_demo WHERE sku='APPLE';
SHOW INDEX FROM index_demo;

첫 SQL은 ix_sku가 id와 sku를 담으므로 커버링이 가능합니다. 두 번째는 memo가 필요해 본문을 찾아야 할 수 있습니다. 3행짜리 테이블에서는 옵티마이저가 전체 스캔을 고르는 것도 합리적입니다. 이때 학습 목적으로 FROM index_demo FORCE INDEX(ix_sku)를 사용해 경로 차이를 볼 수 있지만, 실제 운영에서 강제가 빠르다는 증거가 되지는 않습니다.

결과의 두 행은 id가 1과 3입니다. 출력 순서를 확인하려면 ORDER BY id를 붙입니다. 실행 계획의 Extra에서 Using index가 보인다면 단순히 ‘인덱스를 사용했다’보다 구체적으로 커버링 접근 의미를 생각해야 합니다. 실제 어떤 인덱스를 골랐는지는 key 열을 확인합니다.

6. 키가 길어지면 왜 다른 인덱스도 커질까?

기본 키가 모든 보조 인덱스 레코드에 포함되기 때문입니다. 설명용으로 8바이트 키 대신 36바이트 문자열 키를 쓰고 보조 인덱스가 5개, 행이 1천만 개라면 단순 키 차이만 28×5×1천만=14억 바이트입니다. 실제 저장량은 인코딩·압축·레코드 오버헤드·페이지 활용률에 따라 다르지만, 기본 키 결정이 다른 인덱스에 반복 전파된다는 사실을 보여 줍니다.

순차 증가 키는 새 삽입이 비슷한 리프 끝으로 모여 페이지 지역성을 얻기 쉽습니다. 무작위 키는 여러 페이지를 건드려 캐시와 분할 비용이 커질 수 있습니다. 그렇다고 AUTO_INCREMENT가 모든 상황의 정답은 아닙니다. 분산 ID 생성·외부 노출·업무 키 변경 가능성·쓰기 집중도까지 보고 결정합니다. ID 순서가 커밋 순서와 같다는 보장도 없습니다.

7. 페이지 분할과 인덱스의 쓰기 비용

한 리프 페이지가 꽉 찼는데 중간 키를 삽입해야 하면 레코드를 나누고 상위 경계를 갱신하는 작업이 필요할 수 있습니다. 이것이 페이지 분할입니다. INSERT 한 줄이 논리적으로 한 행을 추가해도 여러 페이지 변경과 redo를 만들 수 있습니다. 보조 인덱스가 10개면 각 인덱스 유지 작업도 고려해야 합니다.

가상의 장애 상황으로 검색 성능 개선을 위해 인덱스를 여러 개 추가한 후 야간 대량 적재가 느려졌다고 합시다. SELECT 성능만 보지 말고 쓰기 TPS, redo 생성량, 디스크 I/O, 버퍼 풀 압박, 인덱스 크기를 함께 봅니다. 실제 사용되지 않는 인덱스를 제거할 때도 UNIQUE 제약이나 외래 키 지원 역할이 있는지 먼저 확인합니다.

왜 이진 트리보다 한 페이지에 많은 길을 담을까?

백만 권의 책이 있는 도서관에서 안내판 하나가 왼쪽·오른쪽 두 방향만 알려 준다면 많은 안내판을 거쳐야 합니다. 반면 안내판 하나가 200개의 구역을 가리키면 몇 번의 선택으로 원하는 서가에 갈 수 있습니다. 디스크 기반 인덱스에서는 비교 연산 몇 번보다 새 페이지를 가져오는 비용이 중요하기 때문에 높은 분기 수와 낮은 높이가 유리합니다.

단순한 설명용 모델에서 내부 페이지 하나가 200개를 가리키고 리프에 100행씩 들어간다고 합시다. 루트가 바로 리프를 가리키면 약 2만 행, 중간 층이 하나 더 있으면 약 400만 행, 하나 더 있으면 약 8억 행을 담는 구조를 상상할 수 있습니다. 실제 페이지는 헤더·키·포인터·빈 공간을 포함하고 가득 차 있지도 않으므로 용량 예측 공식으로 사용하면 안 됩니다. 구조가 커져도 높이가 천천히 증가한다는 점이 핵심입니다.

페이지 안에서도 원하는 레코드를 찾는 작업이 있습니다. “트리 높이가 3이니 비교 세 번”은 아닙니다. 반대로 루트와 내부 페이지가 메모리에 있으면 “높이가 3이니 디스크 읽기 세 번”도 아닙니다. CPU 비교 횟수, 논리 페이지 방문, 물리 읽기를 분리해 설명하면 B-tree의 장점을 과장하지 않을 수 있습니다.

기본 키 조회와 보조 인덱스 조회를 실제 목록으로 따라가기

앞의 index_demo에 있는 세 행을 기준으로 생각해 봅시다. 클러스터드 인덱스의 리프에는 id=1·2·3에 해당하는 행 데이터가 있습니다. 보조 인덱스 ix_sku에는 개념적으로 (APPLE,1), (APPLE,3), (BANANA,2)가 sku와 PK 순서로 정리됩니다. 물리 바이트 배치를 정확히 표현한 표가 아니라 검색 경로를 설명하기 위한 목록입니다.

요청첫 탐색추가 작업
id=3의 memoPK 트리에서 3같은 리프의 행에서 memo 읽기
sku=APPLE의 idix_sku에서 APPLE 구간인덱스에 있는 1·3 반환 가능
sku=APPLE의 memoix_sku에서 1·3 획득PK 트리로 각각 찾아 memo 읽기

APPLE이 2행이면 추가 접근이 작지만 50만 행이면 이야기가 달라집니다. 보조 인덱스로 찾는 일이 빨라도 그 뒤 넓게 흩어진 본문을 많이 읽어야 할 수 있습니다. 그래서 선택도가 낮고 많은 열을 반환하는 쿼리에서는 테이블 스캔이 더 합리적일 수 있습니다. 인덱스 사용 여부를 합격·불합격처럼 보면 이 선택을 이해하기 어렵습니다.

커버링은 이 추가 본문 접근을 줄일 기회입니다. 다만 MVCC 가시성 확인 때문에 클러스터드 레코드 확인이 필요한 경우가 있어 “아무 상황에서도 추가 접근이 0”이라고 약속하지 않습니다. 또한 앱이 실제로 필요하지 않은 memo까지 SELECT *로 가져오면 원래 가능했던 좁은 커버링 경로를 잃을 수 있습니다.

범위 조회는 한 번 찾아간 뒤 옆으로 걷는 일이다

id가 1000 이상 2000 미만인 행을 읽는다고 합시다. 먼저 트리에서 시작 지점 1000을 찾고 이후 키 순서로 리프 레코드를 순회합니다. 모든 id마다 루트부터 처음 검색하는 것과는 다릅니다. 이것이 정렬과 범위 조회에 B-tree 계열이 잘 맞는 이유입니다.

하지만 시작점 탐색이 빠르다고 범위 전체가 공짜는 아닙니다. 결과가 100만 행이면 그 행을 검사하고 필요 시 본문 접근·전송·객체 생성까지 해야 합니다. “O(log N)”은 주로 탐색 시작 비용을 설명할 때 유용하며 결과 k개를 읽는 비용을 빼면 안 됩니다. 범위 비용을 생각할 때는 시작점과 읽을 결과·후보량을 함께 봅니다.

INSERT 한 줄이 여러 페이지를 고치는 과정

새 행을 추가하면 클러스터드 인덱스의 적절한 리프에 넣고, 각 보조 인덱스에도 대응 항목을 넣어야 합니다. 해당 페이지에 충분한 공간이 없다면 분할이 필요할 수 있습니다. 분할은 레코드를 여러 페이지로 나누고 상위에서 올바른 범위를 가리키게 만드는 작업입니다. 모든 INSERT가 분할을 일으키는 것은 아니지만 분할이 생기면 한 행 이상의 저장 작업이 발생합니다.

기본 키를 바꾸는 UPDATE는 특히 주의합니다. 기본 키가 행의 저장 기준이면서 보조 인덱스가 행을 찾는 키이기 때문입니다. 업무상 자주 바뀌는 이름이나 상태를 기본 키로 선택하면 수정의 영향이 커집니다. 안정적인 대리 키와 별도의 업무 UNIQUE 제약을 조합하는 설계를 자주 사용하는 배경입니다.

순차 키도 마법은 아닙니다. 끝부분 접근이 모여 지역성이 좋아질 수 있지만 높은 동시 쓰기에서는 같은 영역에 집중될 수 있습니다. 무작위 키가 불리하다는 설명을 “모든 시스템에서 AUTO_INCREMENT만 사용”이라는 규칙으로 바꾸지 말고 분산 생성 요구와 실제 쓰기 부하를 함께 봐야 합니다.

기본 키 길이가 메모리까지 영향을 주는 계산

기본 키가 8바이트에서 36바이트로 늘고 보조 인덱스가 5개, 행이 1천만 개라고 합시다. 단순한 추가 키 바이트는 28×5×10,000,000=1,400,000,000바이트입니다. 약 1.4GB이며 GiB로는 약 1.30입니다. 문자열 인코딩과 가변 길이 관리, 페이지 오버헤드를 제외한 설명용 계산입니다.

추가 공간은 디스크 요금만의 문제가 아닙니다. 한 페이지에 들어가는 인덱스 레코드 수가 줄면 같은 후보 수를 읽는 데 더 많은 페이지가 필요할 수 있습니다. 작업 집합이 커져 버퍼 풀 미스가 늘 수 있고 백업·복제·인덱스 생성에도 영향을 줍니다. 기본 키의 결정은 해당 열 하나가 아니라 테이블 전체의 접근 비용에 전파됩니다.

인덱스를 제거하기 전에 확인할 세 가지 역할

인덱스는 검색 가속, 데이터 제약, 외래 키 지원처럼 여러 역할을 가질 수 있습니다. 최근 통계에서 사용 횟수가 낮다고 바로 삭제하면 월말 배치나 유일성 보장이 사라질 수 있습니다. 관찰 기간이 충분한지, UNIQUE가 업무 중복을 막는지, 다른 쿼리의 정렬·커버링을 담당하는지 확인합니다.

MySQL 8.0의 invisible index는 지원되는 인덱스를 옵티마이저의 일반 선택에서 숨겨 계획 영향을 살펴보는 데 사용할 수 있습니다. 하지만 유지 비용이 없어지는 것은 아닙니다. 숨긴 동안에도 인덱스는 갱신되므로 쓰기 비용 절감 실험과 삭제 결과를 동일하게 보지 않습니다. 실제 삭제는 복원 비용까지 포함해 결정합니다.

8. 상세 면접 Q&A

해시가 O(1)이면 B-tree보다 항상 좋은가요?

평균 동등 검색 복잡도만으로 DB 인덱스를 결정하지 않습니다. 범위·정렬·접두 조건·디스크 페이지 접근·갱신 비용이 중요합니다. B-tree 계열은 여러 검색 형태를 지원하며 높이를 낮게 유지합니다. ‘빠른 알고리즘 하나’로 모든 접근을 대체할 수 없습니다.

InnoDB 보조 인덱스는 행의 디스크 주소를 저장하나요?

일반적으로 기본 키 값을 포함하고 그것으로 클러스터드 인덱스를 탐색합니다. 물리 주소를 직접 따라가는 구조로 외우면 기본 키 길이가 보조 인덱스 크기에 미치는 영향과 두 단계 조회를 설명하기 어렵습니다.

기본 키가 없으면 무슨 일이 생기나요?

적절한 NOT NULL UNIQUE 키를 사용하거나 숨겨진 행 식별자 기반 클러스터드 인덱스를 만듭니다. 따라서 기본 키를 생략한다고 인덱스 유지 비용이 없어지지 않습니다. 명시적이고 안정적인 짧은 키를 설계하는 것이 일반적으로 이해와 운영에 유리합니다.

커버링 인덱스에 모든 열을 넣으면 되나요?

폭이 커져 페이지당 레코드 수가 줄고 저장·캐시·쓰기 비용이 증가합니다. 자주 실행되는 중요 조회의 반환 열을 줄이고, 필요한 경우만 커버링을 설계합니다. 큰 TEXT 같은 열까지 무작정 넣는 방식은 범용 해결책이 아닙니다.

AUTO_INCREMENT에 빈 번호가 있으면 유실인가요?

그렇지 않습니다. 롤백·실패한 삽입 등으로 간격이 생길 수 있습니다. 자동 증가 번호는 모든 번호의 연속 사용이나 커밋 순서를 보장하는 회계 번호가 아닙니다. 업무상 연속 번호가 필요하면 요구사항을 별도로 설계해야 합니다.

클러스터드 인덱스가 있으니 ORDER BY를 생략해도 되나요?

안 됩니다. 옵티마이저가 보조 인덱스나 다른 경로를 선택할 수 있고 SQL 결과 순서는 ORDER BY로 명시해야 합니다. 지금 관찰한 출력 순서와 계약으로 보장되는 순서를 구분합니다.

꼬리 질문: PK가 바뀌면 왜 보조 인덱스도 영향을 받나요?

답변: 보조 인덱스 레코드가 행을 찾을 기본 키를 포함하기 때문입니다. PK는 테이블 내부의 주소 역할도 합니다.

설계: 자주 바뀌는 업무 값은 별도 열과 UNIQUE 제약으로 두고 안정적인 식별자를 PK로 두는 방식을 검토합니다. 단, 대리 키만 추가해 놓고 필요한 업무 유일성을 빼먹으면 중복 데이터가 생길 수 있습니다.

꼬리 질문: 조회 결과가 한 행인데 전체 스캔이 가능할까요?

답변: 가능합니다. 인덱스 없는 조건을 만족하는 한 행을 찾기 위해 모든 후보를 검사할 수 있습니다.

확인: 반환 행 수보다 실제 읽은 후보와 실행 계획을 봅니다. 창고에서 불량품 한 개를 발견했다는 사실은 검사한 상자가 한 개였다는 뜻이 아닙니다.

꼬리 질문: UNIQUE 인덱스와 PRIMARY KEY는 같은가요?

답변: 둘 다 유일성 관련 역할이 있지만 PRIMARY KEY는 NULL을 허용하지 않고 테이블당 하나이며 InnoDB의 클러스터드 인덱스 기준이 됩니다. 일반 UNIQUE 인덱스는 별도로 여러 개 둘 수 있습니다.

주의: nullable UNIQUE 열의 NULL 처리도 PK와 다릅니다. 업무상 값이 반드시 있어야 한다면 NOT NULL까지 함께 설계합니다.

꼬리 질문: invisible index로 쓰기 부하도 줄일 수 있나요?

답변: 숨기는 것만으로 유지 비용은 없어지지 않습니다. 옵티마이저가 일반적으로 그 인덱스를 고르지 않게 하면서 인덱스 자체는 유지합니다.

활용: 삭제 전 읽기 계획의 영향을 살피는 단계로 유용할 수 있으나 삭제에 따른 디스크·쓰기 절감까지 검증한 것은 아닙니다. 테스트 목적을 구분해야 합니다.
