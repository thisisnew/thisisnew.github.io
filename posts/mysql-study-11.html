데이터 압축: 공간 절감과 CPU·쓰기 비용의 교환

읽는 방법

비유로 개념을 잡고 SQL을 실행하기 전 결과를 예상해 보세요. 이번 개정에서는 단계별 동작 추적에 더해, 전편에 네 가지 확장 수업과 심층 면접 답변을 추가했습니다. 본문의 수치 예시는 설명용이고, 실행 환경에 따라 달라지는 값은 따로 표시했습니다. 기준은 MySQL 8.0·InnoDB, 재현용 서버는 8.0.36입니다. 처음 시작한다면 1편의 서버 준비만 먼저 진행하면 됩니다.

전체 학습 지도·검증 범위

1. 압축은 공간을 CPU와 바꾸는 선택이다

옷을 압축팩에 넣으면 보관 공간이 줄지만 꺼낼 때 펼쳐야 합니다. 데이터 압축도 저장·전송할 양을 줄이는 대신 압축과 해제 연산이 필요합니다. 디스크 읽기가 병목인 업무에서는 유리할 수 있고 CPU가 이미 꽉 찬 업무에서는 불리할 수 있습니다. 압축률만 측정해서 도입하면 실제 응답시간이 악화될 수 있습니다.

예를 들어 가상의 문서 데이터가 원래 100GiB이고 압축 후 40GiB라면 60% 공간을 줄인 것입니다. 그러나 조회가 20ms에서 35ms로 느려졌다면 서비스 목표에 맞지 않을 수 있습니다. 반대로 네트워크·스토리지 비용이 큰 보관용 데이터에서는 가치가 있을 수 있습니다. 저장 크기, 읽기·쓰기 지연, CPU, 메모리, 백업·복구 비용을 함께 비교합니다.

2. 테이블 압축과 페이지 압축은 다른 기능이다

구분대표 설정핵심 특징
InnoDB 테이블 압축ROW_FORMAT=COMPRESSED, KEY_BLOCK_SIZE압축된 B-tree 페이지를 관리하며 재압축·분할 비용을 고려한다.
InnoDB 페이지 압축COMPRESSION='zlib' 등페이지를 기록할 때 압축하고 파일시스템의 공간 반환 기능을 활용한다.
앱에서 값 압축애플리케이션 코드DB가 압축된 값 내부를 일반 SQL로 검색하기 어려워질 수 있다.

같은 ‘압축’이라는 이름 때문에 설정을 섞지 마세요. 테이블 압축은 압축 목표 페이지 크기와 인덱스 내부 관리가 중요합니다. 페이지 압축은 sparse file·hole punching 같은 파일시스템 기능의 지원과 할당 단위가 중요합니다. Docker에서 동작했다고 모든 운영 스토리지에서 같은 공간 절감이 생긴다고 보장할 수 없습니다.

3. 반복 데이터는 잘 줄고 무작위 데이터는 잘 안 줄어든다

‘서울센터 입고완료’라는 문장이 만 번 반복되면 반복 패턴으로 표현하기 쉽습니다. 반면 이미 압축된 이미지나 무작위에 가까운 암호문은 추가 압축 이득이 작을 수 있습니다. 따라서 테스트 데이터를 전부 같은 문자로 채우면 압축률이 지나치게 좋게 나옵니다. 실제 열 값의 분포와 길이, 이미 압축된 데이터 비율을 반영해야 합니다.

테이블 압축은 행 본문뿐 아니라 인덱스 페이지에도 관련됩니다. 인덱스가 전체 공간의 큰 부분을 차지한다면 본문 크기만 보고 예상하면 틀릴 수 있습니다. 또 긴 VARCHAR·TEXT 값은 행 형식과 크기에 따라 외부 페이지에 저장될 수 있어 단순히 ‘행마다 압축팩 하나’로 이해하면 한계가 있습니다.

4. 압축된 페이지를 수정하면 무엇이 어려울까?

이미 꽉 찬 압축팩에 두꺼운 옷을 추가하면 다시 포장하거나 팩을 나누어야 합니다. 압축 페이지도 변경 후 목표 크기에 들어가지 않으면 재압축·페이지 분할 같은 작업이 필요할 수 있습니다. InnoDB는 작은 변경을 효율적으로 다루기 위한 관리 기법을 사용하지만 업데이트 비용이 사라지는 것은 아닙니다.

압축된 페이지와 해제된 형태가 버퍼 풀에서 함께 관리되는 상황도 있습니다. 따라서 디스크가 절반으로 줄었다고 메모리도 자동으로 절반이면 된다고 계산하지 않습니다. 읽기 중심인지 쓰기 중심인지, 자주 쓰는 페이지인지에 따라 실제 이득이 달라집니다. 공식 모니터링 테이블의 압축 시도·성공·해제 카운터를 관찰하는 이유입니다.

5. 실습 A: 같은 내용을 다른 저장 형태로 만들기

기준 환경은 1편의 MySQL 8.0.36, 기본 16KiB 페이지, file-per-table입니다. 학습용 테이블만 생성합니다. 압축이 지원되지 않는 환경에서는 경고나 오류를 기록하고 전제를 확인합니다.

CREATE DATABASE IF NOT EXISTS mysql_school;
USE mysql_school;
SELECT @@innodb_page_size, @@innodb_file_per_table;
DROP TABLE IF EXISTS compress_plain;
DROP TABLE IF EXISTS compress_zip;
CREATE TABLE compress_plain (
 id INT PRIMARY KEY, payload VARCHAR(1000) NOT NULL
) ENGINE=InnoDB ROW_FORMAT=DYNAMIC;
CREATE TABLE compress_zip (
 id INT PRIMARY KEY, payload VARCHAR(1000) NOT NULL
) ENGINE=InnoDB ROW_FORMAT=COMPRESSED KEY_BLOCK_SIZE=8;
SHOW WARNINGS;
INSERT INTO compress_plain
WITH RECURSIVE seq AS (
 SELECT 1 n UNION ALL SELECT n+1 FROM seq WHERE n<1000
)
SELECT n,REPEAT(CONCAT('warehouse-',MOD(n,10),';'),60) FROM seq;
INSERT INTO compress_zip SELECT * FROM compress_plain;
ANALYZE TABLE compress_plain,compress_zip;
SELECT COUNT(*),SUM(LENGTH(payload)) FROM compress_plain;
SELECT COUNT(*),SUM(LENGTH(payload)) FROM compress_zip;
SELECT TABLE_NAME,ROW_FORMAT,DATA_LENGTH,INDEX_LENGTH
FROM information_schema.TABLES
WHERE TABLE_SCHEMA='mysql_school'
  AND TABLE_NAME IN ('compress_plain','compress_zip');

두 테이블의 행 수와 payload 바이트 합계가 같아야 합니다. 이 자료의 한 문자열은 12바이트 패턴을 60번 반복하므로 각 행 720바이트, 전체 합계 720000입니다. 이것은 학습용으로 잘 압축되는 데이터입니다. 실제 공간 비율은 할당 단위와 통계 갱신, 데이터 크기에 따라 달라지므로 특정 숫자를 정답으로 요구하지 않습니다.

6. 실습 B: 페이지 압축의 ‘겉보기 크기’와 ‘할당 크기’

DROP TABLE IF EXISTS compress_page;
CREATE TABLE compress_page (
 id INT PRIMARY KEY, payload VARCHAR(1000) NOT NULL
) ENGINE=InnoDB ROW_FORMAT=DYNAMIC COMPRESSION='zlib';
SHOW WARNINGS;
INSERT INTO compress_page SELECT * FROM compress_plain;
SELECT NAME,FILE_SIZE,ALLOCATED_SIZE,FS_BLOCK_SIZE
FROM information_schema.INNODB_TABLESPACES
WHERE NAME='mysql_school/compress_page';

FILE_SIZE는 파일의 논리적 크기, ALLOCATED_SIZE는 실제 할당된 공간과 연결됩니다. sparse file은 중간 일부 공간을 실제로 할당하지 않을 수 있어 두 값이 다를 수 있습니다. 페이지가 아직 flush되지 않았거나 파일시스템이 지원하지 않으면 기대한 차이가 없을 수 있습니다. CREATE TABLE 성공 하나만으로 공간 절감이 검증되었다고 기록하지 않습니다.

COMPRESSION 설정 변경은 기존 모든 페이지를 즉시 다시 쓰는 명령이 아닙니다. 이후 기록되는 페이지부터 달라질 수 있습니다. 전체 재작성에는 테이블 rebuild 같은 작업이 필요하며 큰 테이블에서는 공간·I/O·잠금 영향을 계획해야 합니다. 이 글은 운영 테이블에 OPTIMIZE를 일괄 실행하도록 권하지 않습니다.

7. 장애 시나리오: 용량은 줄었는데 야간 적재가 느리다

가정: 문서 이력 테이블에 압축을 적용한 뒤 저장공간은 줄었지만 배치 시간이 늘었습니다. 먼저 같은 입력량에서 CPU와 압축·해제 활동, redo·디스크 쓰기량, 페이지 분할 관련 현상을 비교합니다. 압축 전후 인덱스와 쿼리 계획도 동일한지 확인합니다. 데이터 크기만 줄어든 것이 성능 개선 증거는 아닙니다.

자주 수정되는 현재 상태와 거의 바뀌지 않는 오래된 이력을 다른 테이블로 분리하면 서로 다른 저장 전략을 적용할 수 있습니다. 단, 업무 조회와 보존 정책이 복잡해지는 비용도 있습니다. 보관용 데이터라는 이유만으로 암호화·백업·복원 검증을 생략하지 않습니다.

압축을 이해하기 위한 세 가지 크기

문서에 쓰인 글자 수, 파일의 길이, 디스크에 실제 할당된 공간은 같지 않을 수 있습니다. SQL의 LENGTH(payload)는 값의 바이트 길이이고, 테이블·인덱스는 관리 정보와 빈 공간도 포함합니다. 파일시스템은 일정한 블록 단위로 공간을 할당하며 sparse file은 논리 파일 중 일부를 실제로 할당하지 않을 수 있습니다.

관찰 대상무엇을 설명하나?그 값만으로 모르는 것
SUM(LENGTH(payload))저장한 값의 바이트 합계인덱스·페이지·파일 실제 사용량
DATA_LENGTH·INDEX_LENGTH테이블·인덱스 공간 관련 통계정확한 행별 압축률·하위 장치 할당량
FILE_SIZE파일의 논리 길이hole이 실제 차지하지 않는 공간
ALLOCATED_SIZE파일에 할당된 공간스토리지 하위 중복제거 등 모든 계층의 비용

앞 실습에서 논리 payload 합계가 같아야 하는 이유는 압축이 내용을 바꾸는 기능이 아니기 때문입니다. 반면 데이터가 같아도 물리 공간은 달라질 수 있습니다. “행 수와 값이 동일한지”를 먼저 검증하고 “공간이 얼마나 줄었는지”를 별도로 측정합니다.

테이블 압축: 정해진 크기의 압축 페이지에 맞추기

ROW_FORMAT=COMPRESSED와 KEY_BLOCK_SIZE를 사용하는 방식은 압축된 페이지 크기를 목표로 삼습니다. 원래 데이터가 압축 후 목표 크기에 들어가야 하므로 수정 후 더 이상 맞지 않으면 재압축이나 분할이 필요할 수 있습니다. 작은 상자에 물건을 넣는 것과 같아 상자를 줄일수록 공간 이득은 기대할 수 있지만 포장 실패와 재배치 비용도 고려해야 합니다.

InnoDB는 압축 페이지의 작은 변경을 기록하는 modification log 같은 기법으로 매 변경마다 전체를 다시 압축하는 비용을 줄입니다. 이 공간이 부족하거나 페이지를 재구성해야 하면 재압축을 시도할 수 있습니다. 따라서 “UPDATE마다 모든 테이블을 다시 압축한다”도 틀리고, “압축은 읽기 때만 CPU를 쓴다”도 틀립니다.

버퍼 풀에서 압축된 형태와 해제된 형태를 함께 관리할 수 있어 메모리 이득은 단순한 디스크 압축률과 다릅니다. 자주 접근하는 페이지는 해제된 상태가 유리할 수 있고, 메모리 압력에 따라 유지 전략이 달라집니다. 저장공간만 반으로 줄었다고 버퍼 풀 설정도 반으로 줄이는 것은 근거가 부족합니다.

페이지 압축: 남은 부분을 파일시스템에 돌려주기

페이지 압축은 페이지를 파일에 기록할 때 압축하고, 파일시스템이 지원하면 남은 부분의 물리 할당을 해제하는 hole punching을 활용합니다. 책의 페이지 번호는 그대로 두면서 빈 영역에 실제 종이를 쓰지 않는 형태로 상상할 수 있습니다. 논리적 파일 길이와 실제 사용 공간이 달라지는 배경입니다.

기본 페이지가 16KiB, 파일시스템 블록이 4KiB라고 가정해 봅시다. 압축 결과가 약 10KiB라면 관리 오버헤드와 정렬을 감안해 대략 12KiB 단위가 필요할 수 있어 한 블록을 줄일 여지가 있습니다. 14KiB라면 16KiB 할당이 필요해 절감이 없을 수 있습니다. 이 숫자는 블록 단위 효과를 보여 주는 단순 예시이며 실제 헤더와 저장 구현에 따라 달라집니다.

따라서 압축 알고리즘이 몇 바이트를 줄였다는 사실과 파일시스템 공간이 줄었다는 사실은 다릅니다. 지원하지 않는 파일시스템, flush 전 상태, 작은 테이블의 할당 오버헤드 때문에 이득이 보이지 않을 수도 있습니다. CREATE TABLE이 성공하고 SHOW WARNINGS에 문제가 없는지 확인하는 것은 시작이며 공간 절감의 결론은 별도 측정입니다.

압축률이 좋은 데이터가 성능 테스트에는 나쁠 수 있다

모든 행을 'aaaa...'로 채우면 알고리즘이 반복을 매우 잘 줄입니다. 하지만 실제 입고 이력에는 시간, 코드, UUID, 자유 텍스트, 이미 압축된 JSON 외부 객체 등이 섞일 수 있습니다. 반복도와 수정 패턴이 다르면 CPU와 재압축 비용도 달라집니다. 기능 실습용 데이터와 운영 예측용 데이터는 목적이 다릅니다.

대표 데이터를 만들 때는 짧은 값·긴 값의 비율, NULL 빈도, 비슷한 접두사, 이미 압축된 데이터 비율, 갱신되는 열과 주기를 고려합니다. 특히 INSERT만 빠른지 보고 UPDATE가 많은 현재 상태 테이블에 적용하면 실패할 수 있습니다. 기존 작은 값을 큰 값으로 바꾸는 경우도 포함해야 합니다.

도입 실험을 네 칸으로 나누기

실험관찰왜 필요한가?
읽기 중심·찬 캐시I/O·지연·CPU디스크 절감과 해제 비용 비교
읽기 중심·따뜻한 캐시CPU·메모리·지연I/O 이득이 작은 상태의 비용 확인

결과가 “공간 40% 절감, p99 15% 악화”라면 좋은지 나쁜지는 업무 목표에 달려 있습니다. 온라인 API가 아니라 주로 보관하는 이력이라면 허용할 수도 있습니다. 반대로 100ms 응답 목표를 넘으면 공간 절감보다 지연이 중요한 제약일 수 있습니다. 수치를 실제로 측정하기 전에는 이 비율을 성능 주장으로 사용하지 않습니다.

압축과 암호화는 적용 위치가 중요하다

일반적으로 반복 패턴을 가진 평문은 압축하기 쉽고 강하게 암호화된 값은 무작위에 가까워 추가 압축 이득이 작습니다. 애플리케이션이 값을 먼저 암호화해 DB에 넣었다면 DB 페이지 압축의 기대가 달라질 수 있습니다. 반면 DB의 저장 암호화와 압축은 지원되는 내부 처리 순서에 따라 함께 동작할 수 있어 제품·옵션의 조합을 확인해야 합니다.

압축은 기밀성을 제공하지 않습니다. 압축된 파일을 열어 풀면 원문이 나옵니다. 공간 절감과 정보 보호를 같은 문제로 취급하지 마세요. 다음 편에서는 저장 파일, 네트워크, SQL 권한, 백업의 보호 경계를 각각 나눠 봅니다.

확장 수업 ① — 파일 크기와 실제 할당 공간은 왜 다를까?

노트에 100쪽까지 페이지 번호가 적혀 있다고 해서 모든 쪽을 실제 종이로 채워 둘 필요가 없는 특별한 파일을 상상해 봅시다. sparse file은 논리적으로 긴 파일 안의 일부 구간에 실제 디스크 블록을 배정하지 않을 수 있습니다. 페이지 압축은 파일시스템의 hole punching 지원 등을 활용해 압축 뒤 남는 공간의 할당을 회수할 수 있습니다.

그래서 파일의 논리 크기와 실제 할당 크기가 다를 수 있습니다. ls에서 보이는 길이만 보고 “압축이 전혀 안 됐다”고 판단하지 않습니다. 반대로 SQL의 DATA_LENGTH 하나만으로 운영 볼륨의 실제 절감률을 확정하지도 않습니다. 어떤 수치가 페이지 할당, 추정 통계, 파일 길이, 파일시스템 할당을 나타내는지 구분합니다.

복사·백업·스토리지 계층이 sparse 특성을 어떻게 다루는지도 중요합니다. 원본에서는 빈 구간이 적은 공간만 차지해도 다른 방식으로 복사하면 공간이 다시 커질 수 있습니다. “DB에서 압축 켰음”에서 끝내지 않고 백업 생성과 복원 뒤 실제 할당량까지 확인해야 하는 이유입니다.

확장 수업 ② — 1KB를 더 줄여도 공간 절약이 0일 수 있다

설명용으로 논리 페이지가 16KiB이고 파일시스템 할당 블록이 4KiB라고 합시다. 압축 결과가 약 9KiB면 보관에 약 12KiB 단위가 필요하다고 생각할 수 있습니다. 약 8KiB면 8KiB에 들어갈 수 있습니다. 실제 페이지 헤더와 구현 세부를 제외한 교육용 계산이지만, 블록 경계를 넘는지가 공간 절감에 중요하다는 점을 보여 줍니다.

압축 결과 크기 가정4KiB 단위 반올림 예시16KiB 대비 절감 예시
13KiB16KiB0KiB
9KiB12KiB4KiB
8KiB8KiB8KiB

실제 절감량을 이 표대로 보장하는 것은 아닙니다. 페이지 압축의 요구 조건과 파일시스템 블록 크기를 확인하고 충분한 데이터가 기록·플러시된 상태에서 측정해야 합니다. INSERT 직후 아직 데이터가 메모리에 있는 작은 실습으로 최종 파일 절감량을 평가하면 결론이 흔들립니다.

이 계산은 ROW_FORMAT=COMPRESSED의 모든 동작을 설명하는 표도 아닙니다. 테이블 압축의 목표 압축 페이지 크기와 페이지 압축의 파일시스템 공간 회수는 서로 다른 메커니즘입니다. 같은 “압축”이라는 단어보다 어떤 기능을 사용했는지를 먼저 밝히세요.

확장 수업 ③ — 잘 압축되던 페이지가 UPDATE 후 어려워지는 이유

반복되는 짧은 문자열로 채운 페이지는 작은 크기로 줄어들기 쉽습니다. 이후 값들을 서로 다른 긴 문자열로 바꾸면 같은 논리 페이지에 있는 정보량이 커져 목표 압축 크기를 맞추기 어려워질 수 있습니다. 테이블 압축에서는 페이지 내 변경 기록, 재압축, 필요 시 페이지 분할 같은 처리가 관련됩니다. “처음 INSERT 때 잘 압축됐으니 이후 쓰기 비용도 같다”고 볼 수 없습니다.

압축 해제한 페이지를 사용해 읽고 수정해야 하는 상황도 있어 CPU 비용과 메모리 사용 양상이 달라집니다. 압축된 표현과 비압축 표현을 함께 유지할 수 있는 버퍼 풀 동작도 고려해야 합니다. 디스크 파일이 절반으로 줄었다고 버퍼 풀 사용량도 반드시 절반이라고 말할 수 없습니다.

데이터 특성이 중요합니다. 이미 압축된 이미지나 암호문처럼 반복 패턴이 적은 데이터는 추가 압축의 이득이 작을 수 있습니다. 이런 데이터를 반복 문자로 만든 실험의 결과에 대입하면 안 됩니다. 크기 분포뿐 아니라 값의 실제 성질과 수정 비율을 대표하도록 테스트 데이터를 준비합니다.

확장 수업 ④ — 압축 도입을 결정하는 작은 실험 설계

먼저 무압축·테이블 압축·페이지 압축을 구분한 후보를 만듭니다. 같은 논리 데이터를 적재하고 COUNT뿐 아니라 내용도 비교합니다. COUNT와 SUM(LENGTH)가 같다는 것은 일부 성질이 같다는 증거일 뿐 모든 바이트가 같다는 증명은 아닙니다. 정확한 검증이 필요하면 기본 키별 실제 값 비교나 적절한 체크섬 검증을 추가합니다.

읽기 중심·갱신 중심 실험을 나누고 단독 실행뿐 아니라 대표 동시성도 적용합니다. 평균 지연만 보지 말고 느린 꼬리 구간과 CPU, 저장장치 읽기·쓰기, 실제 할당 공간을 함께 측정합니다. 파일 크기 40% 절감이 있어도 갱신 p99가 목표를 넘으면 해당 업무에는 적합하지 않을 수 있습니다. 반대로 저장장치 읽기가 병목인 보관용 테이블에서는 CPU 증가를 감수할 가치가 있을 수 있습니다.

마지막으로 도입 작업 자체를 평가합니다. 기존 테이블의 형식 변경은 재구성·추가 디스크 공간·잠금 및 로그 부담을 만들 수 있습니다. 되돌리는 작업도 자원을 필요로 합니다. 작은 테이블에서 실험하고, 대표 크기로 확대하고, 복원까지 확인한 뒤 운영 변경 계획을 정하는 순서가 합리적입니다.

8. 상세 면접 Q&A

압축하면 무조건 I/O가 줄고 빨라지나요?

공간과 I/O 감소 가능성은 있지만 압축·해제 CPU 비용과 재압축·분할 비용이 있습니다. 저장장치가 병목인지 CPU가 병목인지에 따라 결과가 다릅니다. 대표 읽기·쓰기 부하와 p95/p99를 함께 측정합니다.

ROW_FORMAT=COMPRESSED와 COMPRESSION은 같은 옵션인가요?

서로 다른 압축 방식에 해당합니다. 전자는 테이블 압축과 목표 페이지 크기, 후자는 페이지 기록과 파일시스템 공간 절감이 핵심입니다. 지원 제약과 모니터링 방법도 구분해서 사용해야 합니다.

파일 크기가 그대로면 압축이 실패한 건가요?

페이지 압축에서는 논리 파일 크기와 실제 할당 공간이 다를 수 있습니다. ALLOCATED_SIZE나 적절한 파일시스템 도구로 확인합니다. 아직 flush되지 않았거나 지원 조건이 맞지 않는 경우도 있으므로 설정 성공과 공간 절감 결과를 나눠 봅니다.

반복 문자로 압축 테스트하면 충분한가요?

기능 이해에는 좋지만 운영 압축률 예측에는 부적절합니다. 반복도가 높아 지나치게 좋은 결과를 만듭니다. 실제 길이·분포·이미 압축된 값 비율과 업데이트 패턴을 반영해야 합니다.

압축 설정을 켜면 기존 데이터도 즉시 모두 줄어드나요?

페이지 압축 옵션 변경은 기존 페이지 전체를 즉시 재작성하지 않습니다. 새로 기록되는 페이지와 기존 페이지가 섞일 수 있습니다. 완전한 전환은 rebuild와 그 운영 비용을 별도 검토해야 합니다.

디스크 50% 절감이면 메모리도 50% 줄여도 되나요?

자동으로 그렇지 않습니다. 압축·해제 형태 관리와 실제 작업 집합, 연결 메모리, 다른 엔진 구조의 사용량이 다릅니다. 버퍼 풀과 전체 프로세스 메모리를 실제 부하로 측정해야 합니다.

꼬리 질문: KEY_BLOCK_SIZE를 줄일수록 무조건 좋은가요?

답변: 작은 목표 크기는 공간 절감 기회를 주지만 데이터가 맞지 않을 때 재압축·분할 비용이 커질 수 있습니다.

검증: 압축 성공률과 읽기·쓰기 지연, 페이지 관리 비용을 함께 봅니다. 값 길이와 분포가 바뀌면 결과가 달라지므로 실제 업데이트 패턴으로 비교해야 합니다.

꼬리 질문: 압축 카운터의 누적값만 비교하면 되나요?

답변: 실험 시간과 작업량이 다르면 누적값 비교는 의미가 약합니다. 같은 구간의 증가량을 요청 수나 처리 데이터량과 함께 봐야 합니다.

예: 압축 시도가 많아졌다는 것은 쓰기가 많아진 결과일 수도 있습니다. 성공·실패·해제 횟수와 지연을 함께 비교해 원인과 부하 증가를 구분합니다.

꼬리 질문: 데이터 파일을 복사하면 sparse 특성이 유지되나요?

답변: 복사 도구와 목적지 파일시스템에 따라 달라질 수 있습니다. 논리 내용이 같아도 hole이 일반 블록으로 채워져 공간이 커질 수 있습니다.

운영: 실제 백업·복원 경로에서 할당 공간과 복원 시간을 확인합니다. 원본 서버에서의 절감률만으로 전체 저장 비용을 계산하지 않습니다.

꼬리 질문: 압축을 끄는 일은 즉시 끝나나요?

답변: 방식과 변경 명령에 따라 기존 페이지 재작성이나 테이블 재구성이 필요할 수 있습니다. 옵션 변경과 기존 데이터의 완전한 전환은 다릅니다.

계획: 되돌리기에도 임시 공간·I/O·잠금·시간이 필요할 수 있으므로 도입 전에 전환·복귀 절차를 검증합니다. 작은 테이블의 빠른 ALTER를 운영 규모에 그대로 적용하지 않습니다.

심층 면접: 압축률이 50%면 읽기 성능도 두 배 좋아지나요?

답변: 아닙니다. 읽기 성능은 줄어드는 I/O와 추가되는 압축 해제 CPU 비용, 버퍼 풀 상태, 실제 접근 패턴의 합으로 결정됩니다. 이미 메모리에 있는 데이터를 읽는 작업은 디스크 절감의 이득이 작을 수 있습니다.

예시: 저장장치 대기가 큰 순차 조회와 CPU가 포화된 짧은 조회는 같은 압축률이어도 결과가 다릅니다. 갱신 작업에는 재압축 등의 비용도 생깁니다.

판단: 공간 절감률·처리량·평균 및 꼬리 지연·CPU를 같은 데이터로 측정하고, 목표에 맞는지를 보겠습니다.

심층 면접: 페이지 압축을 켰는데 디스크 사용량이 줄지 않았습니다. 실패인가요?

답변: 즉시 실패라고 단정하지 않습니다. 기능과 파일시스템 요구 조건, 압축 효과가 블록 할당을 줄일 만큼 충분한지, 페이지가 실제로 기록되었는지, 무엇의 크기를 측정했는지를 확인합니다.

구분: 논리 파일 크기와 실제 할당 크기는 다를 수 있습니다. 데이터가 압축에 불리하거나 블록 경계를 넘지 못하면 압축 계산을 했어도 할당 공간 절감이 작을 수 있습니다.

검증: 대표 데이터와 충분한 기록량으로 실제 할당을 비교하고, 백업·복사·복원 과정에서 sparse 특성이 유지되는지도 확인하겠습니다.
