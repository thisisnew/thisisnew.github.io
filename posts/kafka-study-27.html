Connect User Guide: 실제 연결 흐름

도트 게임 속 스테이지를 진행하듯, 쉬운 비유부터 기술적인 흐름과 장애 대응을 함께 익혀봅시다. 비유의 한계를 기억하고 실제 용어를 직접 설명해 보세요.

1. Source Connector

처음 듣는 사람을 위한 비유

외부 창고에서 메시지를 가져오는 차량

정확한 개념과 내부 동작

Source Connector는 외부 소스에서 데이터와 소스 진행 위치를 가져와 Kafka 레코드로 전환한다.

실무에서 생기는 문제

CDC 도입 시 원본 DB 접근 권한, 초기 스냅샷 및 변경 로그 보관 정책을 확인한다.

2. Sink Connector

처음 듣는 사람을 위한 비유

Kafka에서 외부 창고로 나르는 차량

정확한 개념과 내부 동작

Sink Connector는 Kafka 토픽에서 읽은 데이터를 외부 저장소로 전달한다.

실무에서 생기는 문제

외부 DB 삽입 실패 후 재시도 시 중복 갱신 가능성에 대비한다.

3. Worker와 Task

운송회사와 실제 운전기사

실습과 점검

테스트 토픽과 격리된 Kafka 클러스터에서 각각의 이벤트 Key, Partition, Offset, 처리 성공 여부를 기록하며 결과를 추적하세요. 상태를 사용하는 기능은 앱 재시작 시 복구 시간도 측정합니다. 운영 클러스터의 오프셋을 임의로 수정하거나 Topic을 삭제해서는 안 됩니다.

상세 학습 1. Source와 Sink는 정반대 방향이다

Source Connector는 MySQL CDC나 파일 변경처럼 외부 시스템에서 읽은 이벤트를 Kafka에 쓰는 도구예요. Sink Connector는 Kafka에 저장된 레코드를 Elasticsearch, S3, DB 같은 외부 목적지에 써요. 둘 다 같은 'Connect' 안에 있지만 Offset을 관리하는 방식과 장애가 생기는 위치는 다릅니다.

Source는 외부 데이터 소스에서 어디까지 읽었는지를 저장하고, Sink는 Kafka 토픽의 어디까지 처리했는지를 관리합니다.

상세 학습 2. Worker·Connector·Task를 구분하기

학교에서 배송 회사는 전체 조직, 배달 노선은 Connector, 실제로 물건을 나르는 직원은 Task, 직원들이 일하는 사무실은 Worker로 생각할 수 있어요. Connector 객체는 설정과 Task 분할을 담당하고, Worker 프로세스가 Task를 실행합니다.

`tasks.max=8`을 설정해도 데이터 소스가 실제로 두 구간으로밖에 분할되지 않는다면 무조건 Task 여덟 개가 돌아가지 않습니다.

상세 학습 3. 분산 모드와 세 가지 내부 토픽

Distributed Mode에서는 Worker들이 공통 group.id와 내부 토픽을 바탕으로 협력합니다.

`config.storage.topic`은 설정, `offset.storage.topic`은 Source 측 진행 위치, `status.storage.topic`은 Connector·Task 상태를 기록합니다.

내부 토픽의 복제계수와 ACL이 잘못돼도 앱 자체를 정상으로 운영할 수 없어요. 단일 노드 개발 모드와 다중 Worker 운영 모드는 복구 특성이 다르니 나누어 생각하세요.

상세 학습 4. JSON Converter와 SMT

Converter는 Connect 데이터 모델을 Kafka 레코드 바이트 형식으로 바꿔요. JSON Converter의 `schemas.enable` 여부에 따라 출력 레코드 형식이 달라질 수 있습니다.

SMT(Single Message Transform)는 필드 제거·추가 등 레코드 단위의 단순 변환을 도와줍니다.

단순한 데이터 구조 변경과 복잡한 업무 트랜잭션을 혼동하지 마세요.

상세 학습 5. 실습: Worker REST API 이용하기

다음은 Connect Worker를 이미 실행했다고 가정한 예시예요. `curl http://localhost:8083/connectors`는 Connector 목록을 확인하고, `curl http://localhost:8083/connectors/your-connector/status`는 Connector와 Task 상태를 확인합니다.

설정을 수정하기 전에 먼저 응답에서 개별 Task의 FAILED 상태와 trace를 확인하세요. 인증되지 않은 Connect REST API를 인터넷에 직접 노출해서는 안 됩니다.

상세 학습 6. DB CDC 도입 시 미리 검증하기

MySQL의 변경 로그를 Kafka로 전달하는 Connector를 사용한다면 먼저 초기 스냅샷과 이후 변경 로그를 어떤 순서로 수집하는지 확인해야 해요. DB 계정 권한, Binlog 보관 기간, 스키마 변경, 원본 테이블의 대용량 스냅샷 시간, 중복 수집 가능성을 검증하지 않고 바로 운영에 도입하면 위험합니다.

수신 Consumer의 멱등 처리와 변경 이벤트의 순서·타임스탬프 의미도 함께 살펴야 합니다.
