08. KRaft, Tiered Storage, Transaction

교실 반장을 어떻게 뽑을까?

Apache Kafka 4.3 공식 문서의 학습 순서를 토대로 쉽게 풀어쓴 글입니다. 비유는 이해를 돕기 위한 것으로 실제 시스템 동작과 구분해 읽으세요.

이번 글의 목표

교실 반장을 어떻게 뽑을까? 개념을 설명하고, 내부 흐름·운영 시 주의점·면접 질문까지 연결합니다.

1. 먼저, 아주 쉬운 비유

교실의 규칙과 구성원을 관리하는 대표가 필요하듯 Kafka 클러스터도 메타데이터를 일관되게 관리해야 해요. KRaft는 Kafka 자체의 Raft 기반 합의 구조를 사용합니다.

2. 정확한 개념과 용어

KRaft의 Controller Quorum은 메타데이터를 관리하며 브로커는 실제 데이터 저장과 제공을 담당합니다. Controller와 Broker 역할을 개발 환경에서 합칠 수 있지만 운영 환경에서는 장애 도메인과 용량을 고려합니다.

3. 백엔드 실무 예시

Tiered Storage는 오래된 로그를 원격 저장 계층으로 확장하는 접근입니다. Consumer Rebalance Protocol은 그룹 멤버 간 파티션 할당을 조정합니다. Transaction은 여러 파티션 기록과 Consumer Offset Commit을 연계할 수 있으나 외부 MySQL 트랜잭션까지 자동 원자화하지 않습니다.

4. 안에서는 어떤 일이 일어날까?

Kafka 트랜잭션 처리의 대표 흐름: beginTransaction() → 메시지 전송 → 필요 시 sendOffsetsToTransaction(...) → commitTransaction(). read_committed 소비자는 커밋되지 않은 트랜잭션 레코드를 노출하지 않도록 처리합니다.

5. 장애가 나면 무엇을 볼까?

브로커 다운 이후 ISR·리더 선출 상태와 컨트롤러 쿼럼 건강도를 분리해서 확인하세요. KRaft와 데이터 파티션 복제를 하나의 개념으로 혼동하면 장애 분석이 틀어질 수 있습니다.

6. 면접 꼬리 질문

Q. Kafka exactly-once라면 DB 업데이트도 정확히 한 번인가요? A. 아닙니다. 외부 DB까지 포함하면 별도 멱등성·트랜잭션 경계 설계가 필요합니다.
