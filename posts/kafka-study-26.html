실습과 점검

테스트 토픽과 격리된 Kafka 클러스터에서 각각의 이벤트 Key, Partition, Offset, 처리 성공 여부를 기록하며 결과를 추적하세요. 상태를 사용하는 기능은 앱 재시작 시 복구 시간도 측정합니다. 운영 클러스터의 오프셋을 임의로 수정하거나 Topic을 삭제해서는 안 됩니다.

심화 강의 1. 인증(Authentication)과 인가(Authorization)를 흐름으로 이해하기

학교 정문에서 학생증을 확인했다고 학교의 모든 문을 열 수 있는 건 아닙니다. Kafka도 마찬가지예요. 클라이언트는 먼저 Broker에 네트워크로 접속합니다. TLS 인증서나 SASL 등의 방식으로 누구인지 확인할 수 있어요. 그다음 Producer가 Topic에 쓰려고 하면 '이 사람이 이 Topic에 Write 작업을 할 권한이 있는가?'를 검사합니다.

따라서 인증 성공과 메시지 발행 성공은 다른 단계예요. 인증은 성공했지만 ACL 때문에 TopicAuthorizationException이 발생할 수 있습니다. Group에 참여하거나 Offset을 Commit하는 Consumer는 Topic 외에도 Group 관련 권한을 필요로 합니다.

실무 진단에서는 DNS → TCP 연결 → TLS Handshake → SASL Authentication → Kafka Authorization → 요청 결과 순서로 끊어서 봅니다. 이 순서로 보면 'Kafka에 접속이 안 된다' 같은 넓은 증상을 더 작은 원인으로 나눌 수 있어요.

심화 강의 2. ACL을 구성하는 네 가지 조각

ACL은 단순히 Topic 이름만 등록하는 목록이 아닙니다. 보통 Principal(누가), Resource Pattern(무엇에), Operation(어떤 작업을), Permission(허용 또는 거부)을 조합해서 이해할 수 있어요.

예를 들어 User:shipping-service라는 Principal에게 Topic:orders-paid의 READ와 Group:shipping-group의 READ를 허용한다고 합시다. 여기서 토픽과 그룹은 서로 다른 Resource입니다. Topic을 읽을 수 있다고 Group에 참여할 권한까지 자동으로 부여되지는 않습니다.

리소스 이름 매칭에는 특정 이름만 적용하는 Literal 패턴과 접두사로 매칭하는 Prefixed 패턴이 있습니다. 예를 들어 orders-로 시작하는 모든 Topic에 접근을 허용하면 나중에 생긴 orders-admin 같은 토픽까지 범위에 포함될 수 있어요. 편리하지만 권한 범위가 넓어질 위험이 있습니다.

Kafka ACL은 Broker의 authorizer 설정과 실제 인증된 Principal 매핑에도 영향을 받습니다. 단순 ACL 명령만 추가했다고 모든 연결에서 동일한 Principal로 식별된다고 단정하지 마세요.

심화 강의 3. 로컬에서 ACL 명령어 살펴보기

다음 예제는 ACL 명령 구조를 이해하기 위한 예시입니다. Kafka Broker에 authorizer가 활성화돼 있고 관리자가 ACL을 변경할 권한이 있어야 작동합니다. 실제 운영 환경에 복사해서 실행하지 마세요.

# shipping-service가 orders-paid 토픽을 읽도록 허용
bin/kafka-acls.sh --bootstrap-server localhost:9092 \
  --add --allow-principal User:shipping-service \
  --operation Read --topic orders-paid

# Consumer Group 접근 허용 bin/kafka-acls.sh --bootstrap-server localhost:9092 \ --add --allow-principal User:shipping-service \ --operation Read --group shipping-group

# ACL 조회 bin/kafka-acls.sh --bootstrap-server localhost:9092 --list ~~~

실제 Consumer는 사용 API와 그룹 프로토콜에 따라 추가 권한이 요구될 수 있습니다. 테스트에서는 앱 구동부터 poll, commit, 재시작까지 전체 흐름을 확인해야 해요. 또한 현재 로그인한 관리자가 ACL을 수정할 권한을 갖는지도 중요합니다.

심화 강의 4. Spring Boot Consumer에서 권한 오류를 발견했다면

예를 들어 @KafkaListener(topics="orders-paid", groupId="shipping-group")가 시작하자마자 실패했다고 합시다. 단순히 Kafka가 다운됐다고 결론 내리면 안 됩니다. 다음처럼 나눠 확인하세요.

첫째, bootstrap.servers와 advertised.listeners를 통해 실제 Broker에 접근할 수 있는가. 둘째, security.protocol이 SASL_SSL 등 브로커 리스너 설정과 일치하는가. 셋째, SASL 메커니즘과 자격 증명이 올바른가. 넷째, 인증된 Principal이 어떤 이름으로 보이는가. 다섯째, Topic READ와 Group READ가 허용돼 있는가.

Producer가 쓰기에 성공하는데 같은 사용자로 Consumer가 읽기에 실패할 수 있어요. Kafka Operation이 Write와 Read로 구분되기 때문입니다. 반대로 개발자가 ACL 범위를 광범위한 와일드카드로 풀어 증상만 숨기면 운영 환경의 보안 위험이 커져요.

심화 강의 5. ACL 설계 시 흔한 사고 5가지

① 모든 서비스에 관리자 권한을 줘서 개발은 편하지만 계정 유출의 피해가 커집니다. ② Topic에만 권한을 주고 Group을 빠뜨려 Consumer 실행에 실패합니다. ③ Prefix 패턴을 넓게 잡아 의도하지 않은 새 Topic까지 접근을 허용합니다. ④ SASL username과 Kafka Principal 이름이 동일하다고 가정했는데 매핑 규칙으로 달라졌습니다. ⑤ Secret을 application.yml과 Git 저장소에 평문으로 올립니다.

좋은 운영 방식은 서비스별 Principal 분리, 최소 권한, 인증정보의 중앙 관리, 정기 권한 검토와 감사 기록입니다. 새 서비스가 추가되면 토픽 읽기·쓰기·관리 요청 중 실제 필요한 작업만 체크리스트로 검토하세요.

마지막으로 'ACL을 바꾸면 Kafka 메시지 저장 내용도 바뀌나요?'라는 질문에는 아니라고 답해야 합니다. ACL은 접근 제어 정책이고, 로그 데이터나 Offset 값을 직접 변경하는 기능이 아니에요.

심화 강의 6. 면접 질문 — 기본에서 꼬리질문까지

Q. SASL에 로그인됐는데 Producer가 TopicAuthorizationException을 받았어요. 이유는? → 인증과 인가는 다른 절차입니다. Topic Write ACL을 확인해야 합니다.

Q. Consumer는 READ 권한 하나면 충분한가요? → Topic뿐 아니라 Group을 대상으로 한 필요한 권한도 확인해야 합니다.

Q. 클러스터 관리자가 모든 서비스에 와일드카드 ACL을 주면 안 되나요? → 편하지만 피해 범위가 커지므로 최소 권한 원칙에 위배됩니다.

Q. Kafka ACL과 네트워크 보안그룹은 같은 역할인가요? → 아닙니다. 보안그룹은 네트워크 접근 범위를 제어하고 ACL은 Kafka 내부 Resource 작업 권한을 제어합니다.

Q. ACL로 이미 기록된 이벤트를 삭제할 수 있나요? → ACL 자체는 삭제 기능이 아닙니다. 삭제를 허용할지 거부할지에 관련된 접근 제어입니다.
