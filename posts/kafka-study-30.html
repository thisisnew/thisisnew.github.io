Streams 아키텍처: KStream·KTable

도트 게임 속 스테이지를 진행하듯, 쉬운 비유부터 기술적인 흐름과 장애 대응을 함께 익혀봅시다. 비유의 한계를 기억하고 실제 용어를 직접 설명해 보세요.

1. KStream

처음 듣는 사람을 위한 비유

매분 들어오는 새 주문표

정확한 개념과 내부 동작

KStream은 이벤트가 흘러오는 기록의 스트림으로, 동일 Key에 여러 레코드가 도착해도 개별 이벤트로 처리한다.

실무에서 생기는 문제

주문 완료 이벤트를 실시간 필터링·변환할 때 적합하다.

정답: KStream은 이벤트가 흘러오는 기록의 스트림으로, 동일 Key에 여러 레코드가 도착해도 개별 이벤트로 처리한다. 주문 완료 이벤트를 실시간 필터링·변환할 때 적합하다.

2. KTable

처음 듣는 사람을 위한 비유

주문번호별 현재 상태표

정확한 개념과 내부 동작

KTable은 Key별 상태 변경을 표현하는 추상화로 동일 Key의 새 값이 현재 상태를 갱신하는 의미를 갖는다.

실무에서 생기는 문제

이력 감사 로그와 현재 상태 뷰를 구별한다.

🎯 연습 문제: KTable을(를) 설명해 보세요.

정답: KTable은 Key별 상태 변경을 표현하는 추상화로 동일 Key의 새 값이 현재 상태를 갱신하는 의미를 갖는다. 이력 감사 로그와 현재 상태 뷰를 구별한다.

3. State Store

처음 듣는 사람을 위한 비유

집계한 숫자를 적는 지역 장부

정확한 개념과 내부 동작

Stateful 집계는 로컬 State Store를 사용하고 복구에 Changelog 토픽이 활용될 수 있다.

실무에서 생기는 문제

인스턴스 이동 후 상태 재구축 시간과 디스크 사용량을 고려한다.

🎯 연습 문제: State Store을(를) 설명해 보세요.

정답: Stateful 집계는 로컬 State Store를 사용하고 복구에 Changelog 토픽이 활용될 수 있다. 인스턴스 이동 후 상태 재구축 시간과 디스크 사용량을 고려한다.

4. Task와 Partition

처음 듣는 사람을 위한 비유

컨베이어 하나마다 작업 담당

정확한 개념과 내부 동작

실습과 점검

테스트 토픽과 격리된 Kafka 클러스터에서 각각의 이벤트 Key, Partition, Offset, 처리 성공 여부를 기록하며 결과를 추적하세요. 상태를 사용하는 기능은 앱 재시작 시 복구 시간도 측정합니다. 운영 클러스터의 오프셋을 임의로 수정하거나 Topic을 삭제해서는 안 됩니다.

더 깊게 배우기 1. KStream vs KTable를 배송 이벤트로 배우기

KStream은 배송 상태가 바뀌는 사건 각각을 기록합니다. 주문 A가 CREATED→PACKED→SHIPPED로 바뀌면 세 가지 이벤트가 모두 의미 있어요. KTable은 A 주문의 현재 상태를 키 기준으로 바라보는 모델입니다. 그래서 감사 추적에는 이벤트 흐름이, 현재 상태 조회에는 테이블 표현이 유용할 수 있습니다. Kafka Topic의 cleanup.policy와 KTable의 상태 복원 동작은 구분해서 공부해야 합니다.

더 깊게 배우기 2. Topology와 Processor Node

StreamsBuilder로 입력 토픽을 읽고 filter→mapValues→to를 선언하면 논리적인 처리 Topology가 만들어집니다. Processor Node들은 연결된 그래프를 이루고 레코드가 노드를 따라 전달됩니다. `Topology.describe()`를 통해 구조를 확인할 수 있어요. 코드가 한 줄이라도 stateful 작업은 내부 저장소와 토픽을 만들 수 있습니다.

더 깊게 배우기 3. Partition·Task·Thread·Instance 차이

입력 토픽이 세 파티션이면 Task 단위 병렬 처리의 기본 상한이 결정됩니다. 프로세스 하나에서 Stream Thread를 늘리거나 애플리케이션 인스턴스를 더 띄우면 할당이 바뀌지만 Task 수를 넘는 실행 병렬성이 무한정 생기지는 않습니다. 하나의 Task는 할당받은 파티션의 처리와 로컬 상태를 관리하므로 이동할 때 상태 복원이 중요합니다.

더 깊게 배우기 4. State Store와 Changelog

상품별 총 입고 수량을 집계한다면 스트림 앱은 상품 ID별 현재 합계를 기억해야 합니다. Local State Store가 그 역할을 할 수 있고, Changelog Topic은 저장된 상태를 복구하기 위한 기록으로 활용됩니다. 브로커에 원본 이벤트가 있다고 해서 모든 상태 저장소가 언제나 즉시 복원되는 것은 아닙니다.
