Kafka의 여섯 가지 API를 처음부터 이해하기

공식 Kafka 4.3 문서는 Producer, Consumer, Share Consumer, Streams, Connect, Admin 여섯 종류를 소개합니다. 쉽지만 정확하게 구분해 봅시다.

1. Kafka API가 여섯 개라는 사실부터

아주 쉬운 비유

레스토랑을 운영하려면 요리 주문을 넣는 사람, 주문표를 읽는 사람, 여러 직원이 나눠 처리하는 사람, 요리를 가공하는 사람, 재료를 운반하는 사람, 매장을 관리하는 사람이 필요합니다. Kafka의 API도 각각 맡은 역할이 다릅니다.

실제 Kafka에서는?

공식 Kafka 4.3의 03번 PDF에는 Producer, Consumer, Share Consumer, Streams, Connect, Admin까지 정확히 **여섯 종류**가 나옵니다. 기존 글이 Share Consumer를 빠뜨린 것은 잘못이었어요. Producer/Consumer/Admin/Share Consumer는 kafka-clients 라이브러리 영역이고 Streams에는 kafka-streams가, Connect에는 Connect 관련 실행 프레임워크와 API가 사용됩니다.

실무에서 중요한 점

'Kafka는 다섯 API'라는 옛 설명을 그대로 외우지 마세요. 버전이 바뀌면 API 범위가 변할 수 있으므로 원문을 확인합니다.

2. Producer API — 주문표를 작성하는 직원

아주 쉬운 비유

주문을 완료한 손님이 카운터에 주문표를 놓습니다. 식당 직원이 나중에 주문표를 읽더라도 주문표 자체는 먼저 전달할 수 있습니다.

실제 Kafka에서는?

KafkaProducer는 ProducerRecord에 Topic, 선택적인 Partition/Key, Value, Header 등을 담아 전송합니다. 보통 Key가 있으면 파티셔너가 Partition을 정하며 특정 Partition을 명시할 수도 있습니다. send()는 비동기로 동작하며 반환 Future의 완료를 확인해야 전송 결과를 제대로 압니다.

실무에서 중요한 점

kafka-clients를 사용한 Java 예제를 직접 실행할 때는 키·값 Serializer를 맞추고, close() 또는 flush()를 통해 종료를 관리하세요.

3. Consumer API — 주문표를 읽는 직원

아주 쉬운 비유

직원들은 주문표를 여러 개 읽고 일을 나눠 수행합니다. 어느 직원까지 읽었는지 기록하는 책갈피가 중요합니다.

실제 Kafka에서는?

KafkaConsumer는 subscribe 후 poll로 기록을 가져옵니다. 동일 Group ID의 일반 Consumer들은 파티션을 나눠 담당하고, 읽기 위치(position)와 Commit 위치는 다를 수 있습니다. KafkaConsumer 인스턴스는 일반적으로 스레드 안전하지 않습니다.

실무에서 중요한 점

Consumer를 두 개 띄웠는데 토픽 Partition이 하나이면 같은 그룹에서 보통 하나만 해당 Partition을 담당합니다. Consumer 숫자만 늘리는 것이 답은 아닙니다.

4. Share Consumer API — 같은 일감을 협력해서 맡기

아주 쉬운 비유

기존 작업 방식에서는 서랍 하나를 한 직원이 맡습니다. 그런데 처리 시간이 긴 개별 주문표를 여러 직원이 협력해서 가져갈 수 있다면 다른 방식의 분업이 가능합니다.

실제 Kafka에서는?

Kafka 4.3 문서는 Share Consumer를 여섯 가지 핵심 API 중 하나로 소개합니다. Share Group의 소비자는 전통적인 Consumer Group과 달리 파티션에 대해 협력해 레코드를 처리할 수 있도록 설계되었습니다. 전통적 Consumer의 파티션 독점 할당 및 오프셋 커밋 모델과 처리·확인 모델이 다르기 때문에 기존 코드를 설정 하나만 바꿔 그대로 대체한다고 가정하면 안 됩니다.

실무에서 중요한 점

작업 큐 성격의 처리량 확대를 고민할 때 유용하지만 사용 중인 Broker·Client의 기능 지원 및 처리 보장, 개별 레코드 확인 방식을 검증해야 합니다.

5. Streams API — 기록을 계속 가공하는 조리대

아주 쉬운 비유

과일이 컨베이어 벨트로 오면 흠집 난 과일을 빼고 색깔별로 묶어 개수를 셉니다. 이벤트가 흘러오는 동안 계속 가공하는 일입니다.

실제 Kafka에서는?

Kafka Streams는 Source Topic에서 읽은 이벤트를 filter, mapValues, groupByKey, count, join 등의 토폴로지 연산을 거쳐 다른 Topic으로 출력할 수 있는 Java 라이브러리입니다. Stateful 연산에는 State Store 및 Changelog가 활용될 수 있습니다.

실무에서 중요한 점

KafkaTemplate와 @KafkaListener만 쓰는 일반 Spring 애플리케이션을 Kafka Streams 애플리케이션과 혼동하지 마세요. 상태 복원과 내부 토픽 운영 책임이 달라집니다.

6. Connect API — 다른 시스템과 오가는 운송 수단

아주 쉬운 비유

학교 게시판의 내용을 창고 장부나 다른 마을의 게시판에도 옮겨야 할 때 배달 시스템을 만들 수 있습니다.

실제 Kafka에서는?

Source Connector는 외부 시스템에서 Kafka로 데이터를 유입시키고 Sink Connector는 Kafka에서 외부 시스템으로 보냅니다. Connector는 설정과 작업 분할 단위이며 Task가 실제 작업을 수행합니다. Kafka Connect Worker가 실행과 오류·상태 관리를 맡습니다.

실무에서 중요한 점

CDC 같은 데이터 연계가 목적이라면 Connect를 검토할 수 있지만 커넥터 종류, 외부 시스템 제약, 스키마 변경, 권한, 재시도 및 DLQ를 확인해야 합니다.

7. Admin API — 관리자가 게시판을 운영하기

아주 쉬운 비유

게시판을 설치할지, 몇 칸으로 만들지, 낡은 게시판을 어떻게 바꿀지 관리자만 처리할 수 있는 일이 있습니다.

실제 Kafka에서는?

AdminClient는 토픽 목록·설정·컨슈머 그룹 등의 Kafka 객체를 관리하고 조회합니다. 애플리케이션 코드로 관리 작업을 자동화할 수 있지만 관리자 권한을 일반 Producer나 Consumer 계정에 무제한 부여해서는 안 됩니다.

실무에서 중요한 점

자동화 스크립트는 토픽 삭제나 설정 변경 실패 때 변경 범위와 롤백 정책이 명확해야 합니다.

8. 어떤 API를 선택할까? 실무 시나리오

아주 쉬운 비유

입고 확정 이벤트를 보낼까? Producer. 입고 완료를 배송 시스템에 반영할까? Consumer. 처리량이 중요한 개별 작업을 다수가 가져가야 할까? Share Consumer의 적합성을 검토. 입고 수량을 실시간 집계할까? Streams. DB 변경을 Kafka로 수집할까? Connect. 토픽 생성과 설정 자동화일까? Admin.

실제 Kafka에서는?

실무에서 여러 API를 함께 사용할 수 있습니다. 예를 들어 Connect가 DB CDC를 수집하고 Streams가 이벤트를 집계하고 일반 Consumer가 결과를 업무 DB에 반영하는 구조도 가능합니다. 다만 이벤트의 업무 정합성까지 Kafka가 자동 해결하지는 않습니다.

실무에서 중요한 점

도구를 먼저 정하지 말고 처리 목적, 전달 보장, 재처리 요구, 순서, 운영 복잡성이라는 요구사항을 먼저 적으세요.

9. 실습: Java 클라이언트의 최소 흐름

아주 쉬운 비유

처음에는 한 Topic으로 전송하고 다른 Group에서 읽는 것만 확인합니다.

실제 Kafka에서는?

Gradle 의존성 예: implementation 'org.apache.kafka:kafka-clients:4.3.1'. 실제 코드에서는 KafkaProducer<String,String>에 bootstrap.servers, key.serializer, value.serializer를 지정하고 ProducerRecord<>("orders",orderId,json)를 send한 뒤 Future를 확인합니다. 면접 질문 8개 — 눌러서 답 보기

Q1. Kafka 4.3의 핵심 API는 몇 개이며 무엇인가요?

여섯 개입니다. Producer, Consumer, Share Consumer, Streams, Connect, Admin API입니다. 오래된 다섯 개 소개에서 Share Consumer가 빠지는 경우가 있습니다.

Q2. Producer.send()의 반환을 받았으면 Kafka 기록도 성공인가요?

아니요. send()는 비동기이므로 Future 완료 결과와 실패 예외를 확인해야 합니다.

Q3. Consumer API와 Share Consumer API는 똑같은 그룹 모델인가요?

아닙니다. 전통적인 Consumer Group은 파티션 할당과 오프셋 중심으로 분담하지만, Share Group은 레코드 단위의 협력적 처리를 위한 모델이며 확인 방식과 제한 사항을 별도로 공부해야 합니다.

Q4. Kafka Streams와 Kafka Connect를 언제 구분하나요?

Streams는 Kafka 이벤트를 변환·집계·조인하는 애플리케이션 라이브러리, Connect는 외부 시스템과 Kafka 사이 데이터를 지속적으로 이동하는 프레임워크입니다.

Q5. @KafkaListener를 사용하면 Kafka Streams API를 사용하고 있나요?

아니요. 일반적으로 Spring Kafka의 Consumer API 기반 Listener입니다. Streams Topology와 State Store를 운영하는 것과 다릅니다.

Q6. AdminClient는 어디에 사용하나요?

토픽·설정·그룹 같은 Kafka 객체 관리와 조회입니다. 변경 및 삭제 기능에는 최소 권한과 보호 절차가 필요합니다.

Q7. Consumer가 두 개인데 파티션 하나를 동시에 나눠 처리하나요?

기존 일반 Consumer Group에서는 대개 한 파티션이 한 소비자에게 할당됩니다. 이 상황의 병렬성 제한을 Share Consumer와 혼동하지 않아야 합니다.

Q8. MySQL 업데이트와 Kafka Produce를 한 줄 코드로 실행하면 원자적인가요?

아니요. DB와 Kafka는 다른 시스템이므로 둘을 자동으로 묶는 단일 트랜잭션은 아닙니다. Outbox, 중복 방지 등 추가 설계가 필요합니다.

오늘의 복습

자기 말로 여섯 API의 책임을 하나씩 말하고, 물류 입고 시스템에서 각각 언제 쓸지 상황을 만들어 보세요. Share Consumer와 일반 Consumer의 구분을 특히 점검하세요.
