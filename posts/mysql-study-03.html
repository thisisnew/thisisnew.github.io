페이지와 버퍼 풀: 메모리·디스크·캐시의 실제 역할

읽는 방법

비유로 개념을 잡고 SQL을 실행하기 전 결과를 예상해 보세요. 이번 개정에서는 단계별 동작 추적에 더해, 전편에 네 가지 확장 수업과 심층 면접 답변을 추가했습니다. 본문의 수치 예시는 설명용이고, 실행 환경에 따라 달라지는 값은 따로 표시했습니다. 기준은 MySQL 8.0·InnoDB, 재현용 서버는 8.0.36입니다. 처음 시작한다면 1편의 서버 준비만 먼저 진행하면 됩니다.

전체 학습 지도·검증 범위

1. 메모리는 작업대, 디스크는 창고다

작업자가 볼트 하나를 사용할 때마다 먼 창고까지 다녀오면 느립니다. 자주 쓰는 상자를 작업대 위에 두면 이동이 줄어듭니다. InnoDB의 버퍼 풀(buffer pool)은 이런 작업대입니다. 디스크의 데이터·인덱스 페이지를 메모리에 올려 재사용합니다. 여기서 중요한 말은 ‘행’이 아니라 ‘페이지’입니다. 사과 한 개가 필요해도 운송 상자째 가져오는 것처럼, DB는 저장과 읽기를 페이지 단위로 관리합니다.

기본 InnoDB 페이지 크기는 16KiB입니다. 모든 환경에서 무조건 16KiB라는 뜻은 아니므로 SELECT @@innodb_page_size로 확인합니다. 16KiB는 16,384바이트입니다. 한 행이 100바이트라고 해서 정확히 163행이 들어가지는 않습니다. 페이지 헤더, 레코드 관리 정보, 빈 공간이 있고 긴 값은 외부 페이지를 사용할 수도 있습니다. ‘페이지 크기 ÷ 행 크기’는 이해를 돕는 상한 추정일 뿐 실제 저장량 공식이 아닙니다.

2. SELECT 한 번이 디스크 읽기 한 번은 아니다

고객 번호로 한 행을 찾는다고 생각해 봅시다. 인덱스의 상위 페이지에서 방향을 찾고 하위 페이지로 내려갑니다. 필요한 페이지가 버퍼 풀에 있으면 메모리에서 읽습니다. 없으면 저장장치에서 읽어 올립니다. 따라서 여러 페이지를 논리적으로 방문해도 물리 디스크 읽기는 0일 수 있습니다. 반대로 한 SQL이 수십만 페이지를 읽을 수도 있습니다.

관찰뜻잘못된 해석
논리 읽기버퍼 풀에서 페이지를 요청하는 작업디스크를 반드시 읽었다
물리 읽기캐시에 없어 저장장치에서 가져오는 작업SQL 개수와 같다
캐시 적중률요청 중 메모리에서 해결한 비율높으면 모든 쿼리가 빠르다
작업 집합최근 업무가 반복적으로 사용하는 데이터 범위DB 전체 용량과 항상 같다

가상의 수치로 1분 동안 논리 읽기 1,000,000회, 물리 읽기 2,000회가 늘었다면 단순 근사 적중률은 99.8%입니다. 그래도 물리 읽기 2,000회가 특정 API에 몰렸거나 메모리에서 100만 번 비교하느라 CPU가 바쁘면 느릴 수 있습니다. 비율은 절대량·지연시간과 함께 읽어야 합니다.

3. 깨끗한 페이지와 더티 페이지

작업대의 재고 장부를 고쳤는데 창고의 보관본은 아직 바꾸지 않았다고 생각해 보세요. 메모리 페이지와 디스크 페이지의 내용이 달라진 상태가 더티 페이지(dirty page)입니다. 더티는 오류나 오염이라는 뜻이 아닙니다. 변경 내용을 언젠가 디스크의 데이터 파일에 기록해야 한다는 표시입니다.

COMMIT할 때마다 변경된 모든 데이터 페이지를 즉시 디스크에 쓰면 랜덤 I/O가 많아집니다. InnoDB는 복구에 필요한 로그와 데이터 페이지 쓰기를 구분합니다. 로그가 내구성 조건을 만족하면 업무를 확정하고 데이터 페이지는 이후 flush할 수 있습니다. 이때 해당 페이지 변경을 복구할 redo가 먼저 안전하게 기록되어야 합니다. 그래서 버퍼 풀과 redo는 한 묶음으로 이해해야 합니다.

깨끗한 페이지는 필요하면 버리고 디스크에서 다시 읽을 수 있습니다. 더티 페이지는 변경을 보존하지 않은 채 버릴 수 없습니다. 쓰기량이 많아 flush가 따라가지 못하면 빈 페이지 확보나 체크포인트 진행에 압박이 생깁니다. 메모리를 늘렸는데 잠깐 좋아졌다가 다시 느려지는 경우, 지속적인 쓰기 처리량 한계를 메모리로 가린 것일 수 있습니다.

4. 한 번 읽은 대용량 보고서가 왜 다른 조회를 느리게 할까?

작업대가 꽉 찼는데 한 번만 볼 상자를 수천 개 가져오면 자주 쓰던 상자가 밀려납니다. 이것이 캐시 오염입니다. InnoDB는 LRU 목록을 young·old 부분으로 나누는 방식으로 대규모 스캔의 영향을 줄입니다. 새로 읽은 페이지를 곧바로 가장 뜨거운 데이터로 취급하지 않는 정책입니다. 하지만 ‘보호 장치가 있으니 전체 테이블 스캔은 무해하다’는 뜻은 아닙니다.

Read-ahead는 앞으로 필요할 가능성이 있는 페이지를 미리 가져오는 기능입니다. 순차 접근에서는 이득일 수 있지만 미리 읽은 페이지를 사용하지 않으면 불필요한 I/O가 됩니다. Adaptive Hash Index는 반복되는 접근 패턴에 대해 InnoDB가 내부적으로 만드는 보조 구조입니다. 사용자가 CREATE INDEX로 만드는 일반 해시 인덱스가 아니며, 모든 업무에 도움이 되는 것도 아닙니다.

Change buffer는 버퍼 풀에 없는 특정 보조 인덱스 페이지의 변경을 나중에 병합하도록 완충하는 장치입니다. 모든 INSERT·모든 인덱스에 무조건 적용되지 않습니다. 기본 키 변경 경로와 같은 것으로 설명하면 안 됩니다. 버퍼 풀, 로그 버퍼, change buffer는 모두 ‘버퍼’라는 이름이 있지만 저장하는 내용과 해결하는 문제가 다릅니다.

5. 실습: 캐시 지표를 SQL 개수와 분리해 보기

1편의 서버에 root로 접속한 뒤 아래를 실행합니다. 이미 데이터베이스가 있다면 그대로 사용합니다. 1,000행의 작은 자료라 캐시 압박을 만드는 벤치마크가 아니라 관찰 방법을 익히는 실습입니다.

CREATE DATABASE IF NOT EXISTS mysql_school;
USE mysql_school;
DROP TABLE IF EXISTS buffer_demo;
CREATE TABLE buffer_demo (
  id INT PRIMARY KEY, payload VARCHAR(200) NOT NULL
) ENGINE=InnoDB;
INSERT INTO buffer_demo
WITH RECURSIVE seq AS (
  SELECT 1 AS n UNION ALL SELECT n+1 FROM seq WHERE n<1000
)
SELECT n, REPEAT('x', 180) FROM seq;
SHOW GLOBAL STATUS WHERE Variable_name IN (
  'Innodb_buffer_pool_read_requests', 'Innodb_buffer_pool_reads',
  'Innodb_buffer_pool_pages_dirty', 'Innodb_buffer_pool_wait_free');
SELECT SUM(LENGTH(payload)) FROM buffer_demo;
SELECT SUM(LENGTH(payload)) FROM buffer_demo;
SHOW GLOBAL STATUS WHERE Variable_name IN (
  'Innodb_buffer_pool_read_requests', 'Innodb_buffer_pool_reads',
  'Innodb_buffer_pool_pages_dirty', 'Innodb_buffer_pool_wait_free');

SUM 결과는 두 번 모두 180000입니다. 여기서 고정적으로 검증할 값은 합계이고, 읽기 카운터 증가량은 환경에 따라 달라집니다. 방금 INSERT하면서 페이지가 이미 메모리에 있을 수 있으므로 첫 SELECT조차 물리 읽기가 없을 수 있습니다. 이것은 실습 실패가 아닙니다. ‘첫 SQL은 언제나 디스크를 읽는다’는 가정이 틀렸다는 관찰입니다.

전역 상태값은 다른 세션 작업도 포함합니다. 앞뒤 차이를 기록하고, 비교 실험에서는 동시 작업과 데이터 크기를 통제하세요. FLUSH TABLES가 버퍼 풀 전체를 비워 준다고 생각하지 마세요. 운영 서버에서 캐시를 비우거나 재시작해 실험하는 것도 피해야 합니다.

6. 장애 시나리오와 진단 순서

가정: 야간 보고서가 시작된 뒤 주문 조회의 p99가 상승했습니다. 평균은 비슷하지만 느린 요청이 늘었습니다. 우선 보고서 시간과 물리 읽기량·디스크 지연·CPU·버퍼 풀 관련 대기를 나란히 봅니다. 실행 계획에서 보고서가 읽은 범위와 반환량을 확인합니다. 보고서 중단 후 지연이 줄더라도 곧바로 원인을 확정하지 말고 동일 조건의 재현으로 확인합니다.

개선 후보는 보고서의 인덱스·기간 필터·사전 집계·실행 시간 분리입니다. 읽기 복제본으로 옮길 때는 복제 지연과 일관성 요구도 고려합니다. 버퍼 풀을 늘리는 것은 OS와 다른 메모리 소비를 포함해 여유가 있을 때만 후보가 됩니다. 서버 RAM 32GiB라고 버퍼 풀을 32GiB로 설정하면 연결 버퍼와 OS가 사용할 공간이 없어집니다.

페이지 하나를 읽는다는 것은 상자 하나를 꺼내는 일이다

디스크는 요청한 열의 몇 바이트만 항상 따로 가져오는 장치로 이해하면 안 됩니다. InnoDB는 페이지 단위로 데이터를 관리합니다. 기본 16KiB 페이지에 여러 레코드와 관리 정보가 들어갑니다. 도서관에서 문장 하나를 읽으려고 책 한 권을 책상으로 가져오는 모습과 비슷합니다. 같은 책의 다음 문장은 책상 위에서 읽을 수 있으므로 두 번째 접근에는 서가를 다시 방문하지 않을 수 있습니다.

기본 키로 한 행을 찾더라도 트리 탐색에 필요한 여러 페이지에 접근할 수 있습니다. 페이지가 버퍼 풀에 있으면 메모리에서, 없으면 저장소에서 읽어 적재합니다. 그러므로 SQL 한 번, 행 한 개, 페이지 한 개, 디스크 읽기 한 번은 서로 다른 단위입니다. 이 단위들을 섞으면 캐시 적중률이나 처리량을 잘못 해석하게 됩니다.

단위의미예시
SQL클라이언트가 보낸 문장상품 1개 조회
행논리적인 레코드sku 101의 재고
페이지 접근인덱스·데이터 관리 단위 방문루트·내부·리프 탐색
물리 읽기버퍼 풀에 없어 저장소에서 가져오기리프 페이지 적재

캐시 미스에서 빈자리가 없으면 무슨 일이 벌어질까?

버퍼 풀에 요청한 페이지가 없으면 새 페이지를 놓을 자리가 필요합니다. 빈자리가 있으면 곧바로 활용할 수 있지만 꽉 차 있다면 다른 페이지를 내보내야 합니다. 깨끗한 페이지는 디스크와 내용이 같아 비교적 간단히 버릴 수 있습니다. 반면 더티 페이지는 메모리에서 바뀐 내용이 아직 데이터 파일에 반영되지 않은 상태입니다. 그 내용을 보존하지 않고 버릴 수는 없습니다.

따라서 백그라운드 flush는 단지 언젠가 저장할 일을 미리 하는 것만이 아닙니다. 나중에 읽기 요청이 들어왔을 때 사용할 깨끗한 공간을 확보하는 데도 중요합니다. 쓰기가 몰려 flush가 따라가지 못하면 새 페이지를 요구하는 읽기까지 대기의 영향을 받을 수 있습니다. “우리 SQL은 SELECT인데 왜 쓰기 폭주 때 느려지는가?”를 설명하는 한 가지 경로입니다.

실제 InnoDB는 빈 페이지 관리, 교체 순서, 더티 페이지 flush 관리를 각각 위한 자료구조를 사용합니다. LRU 목록은 재사용·교체 관점, flush 목록은 변경된 페이지를 내보낼 관점입니다. 하나의 줄에서 모든 문제를 해결하는 것이 아닙니다. 이 차이를 이해하면 더티 비율이 낮아도 읽기가 많을 수 있고, 적중률이 높아도 flush 병목이 생길 수 있음을 설명할 수 있습니다.

한 번 보는 보고서가 인기 상품 페이지를 몰아내지 않도록

가장 단순한 LRU는 최근 사용한 것을 앞에 두고 오래 안 쓴 것을 뒤에서 버립니다. 그런데 백만 페이지를 한 번씩 읽는 보고서가 실행되면 이 페이지들이 모두 “최근 사용”으로 취급되어 자주 보는 상품 페이지를 밀어낼 수 있습니다. 보고서가 끝나면 평소 조회가 다시 디스크를 읽어야 합니다. 이를 캐시 오염으로 생각할 수 있습니다.

InnoDB는 버퍼 풀 LRU를 young/new와 old 부분으로 나누고 새로 읽은 페이지를 중간 지점에 넣는 방식을 사용합니다. 반복 사용 여부와 시간 조건에 따라 더 오래 보호할지 판단합니다. 기본 old 영역 비율과 승격 지연은 설정에 영향을 받습니다. 이름과 기본 숫자를 암기하기보다 “한 번 스친 데이터와 재사용되는 데이터를 구분한다”는 목적을 먼저 이해하세요.

이 장치가 대형 스캔의 영향을 완전히 제거하는 것은 아닙니다. 스캔 자체가 I/O·CPU를 사용하고 작업 집합이 너무 크면 여전히 경쟁합니다. read-ahead도 연속 접근을 예상해 페이지를 미리 읽어 지연을 줄일 수 있지만, 사용되지 않은 선행 읽기는 공간과 I/O를 낭비할 수 있습니다. 미리 읽기가 많다는 것과 유용한 미리 읽기가 많다는 것은 다릅니다.

적중률 99.9%를 숫자로 다시 읽기

관찰 구간에 논리 읽기 요청이 1,000,000번, 버퍼 풀에서 해결하지 못한 읽기가 1,000번이라면 단순 계산 적중률은 99.9%입니다. 같은 비율이라도 초당 논리 요청 10,000번과 1,000,000번에서는 미스의 절대량이 100배 다릅니다. 높은 비율만 보고 스토리지 부담이 작다고 단정할 수 없습니다.

또한 서버 시작 이후 누적 카운터는 방금 발생한 장애를 가릴 수 있습니다. 한 달 동안 잘 동작하다 최근 5분에 물리 읽기가 급증해도 전체 적중률은 높게 남을 수 있습니다. 그래서 일정 간격의 차이, 즉 Δ값으로 비교합니다. 분모가 0인 구간에서는 비율을 계산하지 말고 요청이 없었다고 기록합니다.

설명용 계산: 60초 동안 read_requests가 600,000 증가하고 reads가 3,000 증가했다면 단순 미스 비율은 0.5%, 초당 물리 읽기 카운터 증가는 50입니다. 이것만으로 디스크 IOPS 전체를 50이라고 단정할 수는 없습니다. 쓰기와 다른 I/O 경로가 있으므로 운영체제·스토리지 지표도 함께 봐야 합니다.

버퍼 풀 크기를 결정하는 질문은 ‘전체 DB 크기’만이 아니다

DB가 1TiB여도 매일 반복해서 읽는 데이터가 20GiB라면 전체를 메모리에 올릴 필요가 없을 수 있습니다. 반복 접근하는 데이터와 인덱스의 집합을 작업 집합이라고 부릅니다. 반대로 테이블이 작더라도 불필요하게 많은 인덱스와 긴 키가 있으면 실제 캐시해야 하는 양이 커집니다. 7~8편의 인덱스 설계가 메모리 문제와 연결되는 지점입니다.

버퍼 풀 외에도 연결별 버퍼, 정렬·조인 작업 공간, Performance Schema, 엔진 메타데이터, 운영체제 메모리가 필요합니다. 모든 연결이 모든 버퍼를 최대치로 동시에 할당하는 것은 아니지만, 동시 무거운 쿼리가 늘면 메모리 압력이 커질 수 있습니다. 고정 비율 하나를 복사하기보다 전체 RSS, 여유 메모리, swap, 동시 작업 수를 보고 여유를 남겨야 합니다.

앞 실습의 SUM은 CPU가 메모리의 1,000행을 검사하는 일도 포함합니다. 물리 읽기가 0인데 시간이 든다면 이상한 것이 아닙니다. “캐시에 있으니 SQL 작업도 없어졌다”는 생각을 버리면 읽을 행 수를 줄이는 튜닝과 캐시 증설의 차이를 이해할 수 있습니다.

확장 수업 ① — 한 상품을 읽는데 왜 페이지를 가져올까?

창고에서 나사 하나가 필요해도 나사 상자를 작업대에 가져오는 편이 효율적일 수 있습니다. 저장장치와 메모리 사이에서도 아주 작은 열 값 하나씩 관리하기보다 일정한 크기의 페이지로 데이터를 다룹니다. 기본 16KiB 페이지를 사용하는 InnoDB를 생각하되, 모든 서버가 이 크기라고 가정하지 말고 @@innodb_page_size로 확인하세요.

상품 id=100의 수량만 읽어도 그 레코드가 있는 인덱스 페이지를 접근합니다. 다음 요청이 같은 페이지에 있는 id=101을 읽는다면 페이지를 재사용할 수 있습니다. 반대로 서로 멀리 흩어진 상품 100개를 읽으면 결과는 작아도 여러 페이지가 필요할 수 있습니다. 반환 데이터 크기와 내부에서 다룬 페이지 양은 다른 지표입니다.

B-tree를 찾는 과정의 루트·중간·리프도 페이지입니다. 트리 높이가 3이라고 매번 물리 읽기 3번이 생기는 것은 아닙니다. 상위 페이지가 이미 버퍼 풀에 있다면 그 접근은 메모리에서 해결됩니다. 보조 인덱스로 기본 키를 찾은 뒤 원본 행을 읽으면 두 구조를 오가므로 접근량이 늘 수 있고, 커버링 설계는 이 일부를 줄일 수 있습니다.

확장 수업 ② — 캐시 공간의 상태를 네 장면으로 나누기

필요한 페이지버퍼 풀 상황개념적인 처리
이미 있음접근 가능메모리의 페이지 이용
없음사용 가능한 빈 공간 있음읽어서 적재
없음깨끗한 교체 후보 있음후보를 내보내고 새 페이지 적재
없음즉시 재사용할 공간 확보가 어려움필요한 플러시와 공간 확보를 기다릴 수 있음

이 표는 원리 설명입니다. 실제 구현은 백그라운드 작업으로 미리 빈 공간을 확보하고, 사용 중인 페이지를 마음대로 내보내지 않는 등 더 복잡합니다. 핵심은 “메모리가 가득 참” 자체가 곧 장애는 아니라는 점입니다. 캐시는 활용하려고 채우는 공간입니다. 문제는 필요한 페이지가 자주 없고 새 페이지를 받아들일 때 비용이 커지는 경우입니다.

더티 페이지는 디스크의 대응 상태와 달라진 페이지입니다. 이 단위는 트랜잭션과 일대일이 아닙니다. 한 페이지 안에 서로 다른 트랜잭션이 수정한 여러 행이 있을 수 있습니다. 따라서 페이지를 디스크에 쓰는 것과 어떤 트랜잭션을 커밋하는 것을 같은 사건으로 설명하면 안 됩니다. WAL·redo·undo가 이 독립성을 뒷받침하며 4편에서 이어집니다.

확장 수업 ③ — 누적 카운터를 초당 변화량으로 바꾸기

서버가 시작된 뒤 누적된 물리 읽기가 100만이라고 해도 지금 느린지 알 수 없습니다. 100일 동안 생긴 100만과 10초 동안 늘어난 100만은 완전히 다른 상황입니다. 같은 서버에서 t0·t1의 값을 읽고 차이를 시간으로 나눕니다. 중간에 서버가 재시작되거나 카운터가 초기화되었다면 그대로 계산하면 안 됩니다.

관측 항목t010초 뒤 t1해석
read_requests5,000,0006,000,000논리 읽기 증가 1,000,000
reads20,00021,000버퍼 풀에서 해결되지 않은 읽기 증가 1,000
구간 적중률 추정1 − 1,000 / 1,000,00099.9%

이 예시에서는 해당 reads 증가율이 초당 100입니다. 이것을 전체 디스크 IOPS와 같다고 두면 안 됩니다. 쓰기·로그·읽기 선행 작업과 운영체제·장치 계층이 별도로 존재하기 때문입니다. 또한 전역 카운터에는 다른 연결의 작업도 섞입니다. 특정 SQL 한 개의 읽기 비용이라고 단정하려면 격리된 실험이나 추가 관측이 필요합니다.

비율이 같아도 전체 논리 읽기가 100배 늘면 미스의 절대량도 100배 늘 수 있습니다. 반대로 적중률을 조금 올려도 CPU가 이미 병목이면 지연이 크게 줄지 않을 수 있습니다. 적중률, 물리 읽기 증가율, 저장장치 지연, 쿼리 지연을 같은 시간 구간으로 맞춰 보세요.

확장 수업 ④ — 1TB DB를 64GB 메모리로 운영할 수 있을까?

총 데이터 크기보다 자주 반복해서 접근하는 작업 집합이 중요합니다. 1TB 중 최근 입고 데이터 20GB에 요청 대부분이 집중된다면 상당한 읽기를 캐시로 처리할 수 있습니다. 반대로 50GB 테이블이어도 매번 전체를 무작위로 접근하고 다른 인덱스도 함께 읽으면 32GB 버퍼 풀에 필요한 페이지가 충분히 남지 못할 수 있습니다.

버퍼 풀을 늘리면 다른 메모리를 쓸 여유는 줄어듭니다. 서버는 연결, 정렬, 조인, 임시 테이블, Performance Schema 등에도 메모리를 사용합니다. 메모리가 부족해 운영체제 스왑이나 프로세스 종료가 발생하면 캐시를 늘린 취지가 사라집니다. 고정 비율 하나를 외우기보다 실제 동시 작업량과 메모리 사용을 관찰해야 합니다.

실습의 작은 테이블은 방금 INSERT한 페이지가 메모리에 있을 가능성이 높습니다. 두 번째 SELECT가 빠르다는 관찰만으로 “첫 번째는 디스크, 두 번째는 메모리”라고 쓰지 마세요. 첫 번째도 이미 메모리였을 수 있습니다. 운영 DB의 캐시를 비워 증명하려 하지 말고, 별도의 실험 환경에서 데이터 크기와 워밍업 조건을 명시합니다.

7. 상세 면접 Q&A

버퍼 풀은 SQL 결과 캐시인가요?

아닙니다. 데이터·인덱스 페이지를 저장합니다. 같은 페이지를 읽더라도 필터·조인·집계를 다시 수행할 수 있습니다. 결과 캐시와 페이지 캐시를 구분해야 “디스크 읽기는 없는데 CPU가 높다”는 상황도 설명할 수 있습니다.

더티 페이지가 많으면 데이터가 위험한가요?

더티 자체는 정상적인 쓰기 동작입니다. 내구성은 redo flush 정책과 저장장치 보장 등을 함께 보아야 합니다. 다만 flush가 따라가지 못해 체크포인트와 빈 페이지 확보가 막히는지 확인해야 합니다. 비율 하나로 안전성이나 성능을 단정하지 않습니다.

적중률 99.9%인데 왜 느리죠?

전체 요청이 많으면 0.1%도 큰 I/O일 수 있고, 특정 쿼리가 대부분의 miss를 만들 수 있습니다. 캐시에 있는 데이터를 너무 많이 읽거나 잠금을 기다리는 문제도 가능합니다. 쿼리별 실제 읽기량과 CPU·잠금 대기·스토리지 지연을 함께 봅니다.

메모리 증설과 인덱스 추가 중 무엇이 먼저인가요?

원인에 따라 다릅니다. 불필요한 백만 행 스캔은 인덱스로 읽을 양을 줄이는 것이 근본 개선일 수 있습니다. 적절한 계획인데 실제 작업 집합이 메모리보다 큰 경우는 증설이 후보입니다. 쓰기 비용과 운영 비용까지 비교합니다.

Adaptive Hash Index가 있으면 B-tree가 필요 없나요?

필요합니다. AHI는 관찰된 접근에 대한 내부 가속 구조이고 원래 인덱스를 대체하지 않습니다. 해시로 유리한 조회와 범위 순회는 다른 문제입니다. 경쟁 비용이 커지는 워크로드도 있어 실제 부하에서 평가해야 합니다.

작은 실습에서 디스크 읽기가 0이면 무엇을 배울 수 있나요?

데이터를 삽입한 과정 자체가 페이지를 메모리에 올렸을 수 있다는 점입니다. 실험 시작 전 상태가 결과를 결정합니다. ‘원하는 결과가 안 나오니 틀렸다’가 아니라 페이지가 언제 적재되었는지 설명할 수 있어야 합니다.

꼬리 질문: 버퍼 풀 적중과 운영체제 캐시 적중은 같은가요?

답변: 다릅니다. 버퍼 풀은 InnoDB가 관리하는 페이지 캐시이고 운영체제 캐시는 파일 I/O 계층의 캐시입니다. I/O 설정에 따라 OS 캐시를 우회하는 경로도 있습니다.

관찰: 버퍼 풀 미스가 발생했다고 반드시 회전 디스크의 실제 읽기 지연이 그대로 발생하는 것도 아닙니다. 하위 캐시와 저장장치가 개입할 수 있습니다. 어떤 계층의 hit·read를 측정했는지 명시합니다.

꼬리 질문: 더티 페이지는 커밋한 데이터인가요?

답변: 더티 여부와 커밋 여부는 같은 기준이 아닙니다. 더티는 메모리 페이지와 데이터 파일의 차이이고 커밋은 트랜잭션의 확정 상태입니다.

원리: 페이지에는 여러 트랜잭션의 변경이 섞일 수 있습니다. 커밋된 변경이 더티 상태로 남을 수 있고, 미커밋 변경도 WAL 조건을 지키며 데이터 파일에 기록될 수 있습니다. 그래서 redo와 undo를 모두 포함한 복구 체계가 필요합니다.

꼬리 질문: change buffer는 모든 INSERT를 빨리 하나요?

답변: 아닙니다. 대상이 되는 보조 인덱스 페이지와 연산에 제한이 있으며 유일성 검사가 필요한 인덱스 등은 같은 방식으로 다루지 않습니다.

비용: 나중에 페이지를 읽거나 백그라운드에서 병합해야 하므로 일을 완전히 없애는 것이 아니라 시점을 조정합니다. 이미 페이지가 메모리에 있는 워크로드와 차갑고 큰 보조 인덱스에서는 이득이 다를 수 있습니다.

꼬리 질문: 재시작 후 왜 조회가 느려질 수 있나요?

답변: 이전에 메모리에 있던 작업 집합을 다시 읽어야 하는 cold cache 상태가 원인 후보입니다. 버퍼 풀 dump/load 설정에 따라 이전에 사용한 페이지 정보를 활용해 적재할 수 있습니다.

주의: 이것은 메모리의 모든 내용을 그대로 영구 저장한다는 뜻도, 모든 쿼리 결과를 복원한다는 뜻도 아닙니다. 서버 기동과 서비스의 정상 지연 회복을 별도로 관찰해야 합니다.

심층 면접: 버퍼 풀 적중률 99.9%인데 디스크 병목이라는 주장이 가능한가요?

답변: 가능합니다. 높은 비율이 낮은 절대 I/O를 뜻하지 않고, 이 읽기 적중률은 redo·binlog 기록이나 더티 페이지 쓰기까지 대표하지 않습니다. 먼저 같은 시간 구간의 카운터 차이와 장치 읽기·쓰기 지연을 비교하겠습니다.

예시: 초당 논리 읽기 100만 회 중 0.1%가 캐시 밖 읽기를 필요로 하면 초당 1,000회입니다. 여기에 쓰기 부하도 존재할 수 있습니다. 이 숫자는 설명용이며 MySQL 카운터와 장치 IOPS를 일대일로 등치하지 않습니다.

대응: 읽는 페이지 수가 문제인지, 캐시 크기가 문제인지, 플러시·로그 쓰기가 문제인지 구분한 후 쿼리·인덱스·메모리·저장장치를 검토하겠습니다.

심층 면접: 버퍼 풀이 꽉 찼으니 즉시 늘려야 하나요?

답변: 아닙니다. 캐시가 공간을 활용하는 것은 자연스럽습니다. 빈 공간의 비율보다 필요한 페이지의 미스, 교체 비용, 플러시 대기와 지연 변화를 확인해야 합니다.

이유: 오래 사용하지 않는 깨끗한 페이지를 교체하는 상황과, 더티 페이지를 충분히 처리하지 못해 공간 확보를 기다리는 상황은 다릅니다. 같은 사용률이라도 결과가 다릅니다.

검증: 버퍼 풀 증가 실험에서는 읽기 미스 감소뿐 아니라 전체 메모리 여유·스왑·응답 지연도 봅니다. 필요한 열과 범위를 줄여 작업 집합 자체를 줄이는 방법도 함께 비교하겠습니다.
