1. 같은 파일도 사용하는 방식이 다르다

택배 보관소에서 송장 번호로 상자 전체를 받아 오는 방식은 객체 스토리지에 가깝습니다. 빈 창고 바닥을 받아 사용자가 선반과 통로를 만드는 방식은 블록 스토리지에 가깝습니다. 여러 사람이 같은 폴더와 파일 이름을 보며 작업하는 공유 사무실은 파일 스토리지에 가깝습니다. 사진 파일 하나를 저장하더라도 프로그램이 HTTP API를 쓰는지, 로컬 디스크를 요구하는지, 공유 파일 경로와 잠금을 요구하는지에 따라 선택이 달라집니다.

방식 대표 서비스 접근 단위 적합한 예
객체 S3 key로 식별하는 객체와 메타데이터 검수 이미지·로그·백업·데이터 레이크
블록 EBS 블록 장치를 OS가 파일시스템 등으로 사용 EC2의 디스크·DB 저장 장치
파일 EFS, FSx 디렉터리·파일·프로토콜 공유 업로드 폴더·기존 NFS/SMB 앱

비유의 한계도 있습니다. S3는 일반 목적 버킷에서 폴더처럼 보이는 prefix를 제공하지만 일반적인 POSIX 파일시스템과 동일한 수정·잠금 계약이 아닙니다. 마운트 도구가 있다고 모든 로컬 파일 동작이 같은 의미가 되지는 않습니다.

2. S3: 저장 성공, 읽기, 복제는 다른 약속이다

S3 일반 목적 버킷에는 key로 객체를 저장합니다. PUT이 성공한 뒤 해당 객체를 GET하거나 목록을 조회하는 동작에는 강한 일관성 보장이 있습니다. 예전 설명처럼 “방금 올렸으니 한동안 안 보일 수 있다”를 기본 모델로 외우면 안 됩니다. 다만 여러 객체를 한 번에 바꾸는 관계형 트랜잭션이나 다른 리전으로의 복제 완료까지 같은 보장이 되는 것은 아닙니다.

일관성은 지금 어떤 값을 읽는가, 내구성은 데이터가 사라지지 않도록 얼마나 보호하는가, 가용성은 지금 접근할 수 있는가라는 서로 다른 질문입니다. 저장 데이터가 남아 있어도 권한 오류나 서비스 장애 때문에 접근하지 못할 수 있습니다. 강하게 일관된 삭제도 잘못된 삭제라면 업무에는 재앙입니다. 그래서 Versioning·Object Lock·백업·접근 제어를 별도로 설계합니다.

Versioning은 같은 key의 이전 버전을 보존하는 데 도움이 됩니다. 일반적인 삭제는 delete marker를 만들 수 있지만, 버전 자체를 영구 삭제하는 권한까지 열려 있으면 모든 실수를 막지는 못합니다. Object Lock은 보존 정책에 따른 변경·삭제 제한을 제공하며 모드와 권한의 차이를 확인해야 합니다. 복제는 오류나 삭제 정책까지 전파할 수 있으므로 백업과 동일한 의미가 아닙니다.

3. 스토리지 클래스는 복구 시간을 먼저 물어야 한다

자주 읽는 원본에는 Standard, 접근이 드문 데이터에는 IA 계열, 접근 패턴을 예측하기 어려운 데이터에는 Intelligent-Tiering을 검토합니다. Glacier라는 이름만 보고 모두 몇 시간 기다린다고 외우면 틀립니다. Instant Retrieval은 즉시 접근용이고 Flexible Retrieval·Deep Archive는 복원 절차와 대기 시간을 고려하는 아카이브 선택지입니다. 저장료 외에 요청료·검색료·최소 보관 기간·객체 크기 조건을 확인해야 합니다.

One Zone 계열은 다중 AZ 저장 클래스와 장애 범위가 다릅니다. 재생성 가능한 썸네일과 유일한 원본 검수 사진은 같은 기준으로 고르지 않습니다. S3 Express One Zone은 directory bucket과 낮은 지연이라는 특성이 있지만 한 AZ라는 범위를 감수해야 합니다. 이 편의 기본 설명은 일반 목적 버킷이며 다른 버킷 유형의 모든 제한을 동일하게 적용하지 않습니다.

Lifecycle은 시간이 지난 데이터를 다른 클래스로 이동하거나 만료시키는 규칙입니다. “보관 비용을 줄이자”는 규칙이 법적 보존·고객 조회·백업 요구와 충돌하지 않는지 확인합니다. 미완료 multipart upload 조각도 과금 대상이 될 수 있어 정리 정책을 고려합니다.

4. EBS: 용량과 성능을 분리해서 보기

EBS 볼륨은 AZ 범위의 블록 스토리지입니다. 인스턴스에 연결한 뒤 OS가 파일시스템이나 DB 저장 공간으로 사용합니다. 인스턴스를 종료할 때 볼륨이 남는지는 delete-on-termination 등의 설정과 볼륨 역할에 따라 달라집니다. “EC2 디스크는 전부 영구적이다”와 “전부 사라진다”는 둘 다 틀린 일반화입니다.

IOPS는 초당 I/O 횟수이고 처리량은 초당 전송 바이트입니다. 16KiB 요청을 초당 10,000번 처리하면 대략 156MiB/s입니다. 작은 랜덤 읽기와 큰 순차 읽기는 같은 처리량이어도 필요한 IOPS가 다릅니다. 볼륨 성능뿐 아니라 인스턴스 EBS 대역폭과 큐 깊이도 병목이 될 수 있습니다. gp3와 io 계열 등을 비교할 때 데이터 크기만 보지 말고 지연 요구·지속 부하를 함께 봅니다.

스냅샷은 특정 시점의 블록 데이터 복구 수단입니다. 애플리케이션 일관성을 확보하려면 버퍼·트랜잭션·여러 볼륨의 정합성을 고려해야 합니다. 실행 중 스냅샷이 성공했다고 업무 트랜잭션까지 항상 원하는 시점으로 맞춰진다고 가정하지 않습니다. 볼륨 축소는 단순한 크기 설정 변경과 다르므로 더 작은 새 볼륨으로 데이터를 이전하는 절차 등이 필요할 수 있습니다.

5. EFS와 FSx: 파일 프로토콜과 애플리케이션 호환성

EFS는 NFS 기반 공유 파일 접근에 적합합니다. 여러 컴퓨팅 인스턴스가 같은 파일 경로를 사용할 수 있지만 애플리케이션의 동시 쓰기와 파일 잠금 문제를 자동 해결하지는 않습니다. EFS의 Regional과 One Zone 선택지는 장애 범위가 다르므로 “EFS는 전부 다중 AZ”로 단정하지 않습니다. mount target·보안 그룹·DNS·POSIX 권한을 함께 맞춰야 실제 파일을 읽을 수 있습니다.

FSx for Windows File Server는 SMB와 Windows 통합, FSx for Lustre는 HPC 등 병렬 파일 처리, FSx for NetApp ONTAP은 ONTAP 기능과 관련 프로토콜, FSx for OpenZFS는 ZFS 기반 기능과 NFS 워크로드라는 관점으로 구분합니다. 기존 프로그램이 SMB와 디렉터리 서비스에 의존한다면 S3 API로 바꾸는 비용을 먼저 계산해야 합니다.

Amazon File Cache는 S3나 NFS 원본의 데이터를 AWS에서 파일 형태로 빠르게 처리하도록 제공하는 임시 고성능 캐시입니다. 원본 데이터 저장소를 대체하는 유일한 영구 보관소로 취급하지 않습니다. 변경 데이터를 원본 저장소로 내보내는 절차와 AZ 범위를 확인해야 합니다. File Cache 동작과 범위 Storage Gateway는 온프레미스 애플리케이션이 파일·볼륨·테이프 인터페이스를 통해 클라우드 저장소를 활용하도록 연결하는 계층입니다. DataSync는 데이터를 이동하는 도구라는 점에서 지속적인 저장 인터페이스와 역할이 다릅니다.

6. Backup과 Disaster Recovery는 복구 목표에서 만난다

AWS Backup은 여러 지원 리소스의 백업 정책·보존·복구 지점을 관리하는 데 사용합니다. AWS Elastic Disaster Recovery는 서버 기반 워크로드의 복제와 복구 실행이라는 목적을 가집니다. 제품을 켜는 것만으로 원하는 RTO/RPO가 충족되는 것은 아닙니다. 복구 후 네트워크·키·접속 권한·애플리케이션 검증까지 완료하는 시간을 재야 합니다.

가상 사고: 운영자가 원본 사진 버킷에 잘못된 만료 정책을 적용했습니다. 복제 버킷에도 관련 삭제가 전파되는 구성이라면 단순 복제만으로는 충분하지 않습니다. 별도 권한 경계의 백업, 적절한 보존 잠금, 삭제 작업에 대한 통제와 복구 훈련을 설계합니다. 암호화 키를 잃으면 백업 파일이 남아도 읽을 수 없다는 점도 확인합니다.

7. 설계 연습: 데이터 네 가지를 분류하기

원본 사진은 재생성 불가, 썸네일은 재생성 가능, 분석 임시 파일은 작업 종료 후 불필요, DB 파일은 낮은 지연의 블록 접근이 필요하다고 가정합니다. 각각에 보관 기간·읽기 빈도·복구 시간·허용 손실을 써 보세요. 원본과 썸네일을 같은 class·보존 정책으로 묶으면 비용이나 보호 수준 중 하나가 어긋납니다. 선택 이유를 저장 방식부터 설명할 수 있으면 제품 목록을 외운 것보다 깊게 이해한 것입니다.

8. 상세 면접 Q&A

Q. S3가 강한 일관성을 제공하면 DB 대신 쓰면 되나요?

단일 객체와 목록의 일관성은 관계형 조인·제약조건·여러 행의 트랜잭션과 다릅니다. 사진 저장에는 적합하지만 주문 수량과 재고를 함께 변경하는 업무를 동일한 방식으로 처리할 수 있다는 뜻은 아닙니다. 접근 패턴과 원자성 범위를 기준으로 선택합니다.

Q. EBS를 여러 서버가 공유하면 EFS와 같나요?

일부 EBS 구성은 Multi-Attach를 지원하지만 일반 파일시스템을 여러 서버에서 마음대로 동시에 쓰면 정합성이 깨질 수 있습니다. 지원 볼륨·인스턴스·AZ 조건과 클러스터 파일시스템 등 애플리케이션 조정이 필요합니다. 공유 파일 서비스를 원한다면 EFS/FSx의 프로토콜과 성능을 먼저 검토합니다.

Q. 백업 성공 지표만 보면 충분한가요?

아닙니다. 복구가 가능한 권한과 키가 있는지, 실제 데이터가 일관적인지, 복원과 업무 검증이 목표 시간 안에 끝나는지 확인해야 합니다. 백업 성공은 복구 가능성을 위한 필요조건 중 하나입니다. 다른 계정·리전에서 복구하는 훈련은 숨어 있는 의존성을 드러냅니다.

Q. 가장 저렴한 아카이브를 선택하면 비용이 최소인가요?

저장 단가만 낮을 수 있습니다. 자주 복원하거나 최소 보관 기간 전에 삭제하면 검색·요청·조기 삭제 비용 등이 커질 수 있습니다. 고객이 기다릴 수 있는 시간과 실제 접근 기록으로 전체 비용을 계산해야 합니다.

깊이 읽기: 바이트가 저장되는 방식이 애플리케이션을 바꾼다

블록·파일·객체를 책장에 비유해 구분하기

블록 스토리지는 번호가 붙은 빈 종이를 제공하는 것에 가깝습니다. OS와 파일 시스템이 그 위에 파일 이름·디렉터리·접근 규칙을 만듭니다. 파일 스토리지는 이미 정리된 공동 책장에 가깝습니다. 여러 사용자가 파일 경로와 파일 프로토콜로 접근합니다. 객체 스토리지는 보관 번호로 완성된 꾸러미를 맡기고 가져오는 창고에 가깝습니다. 객체 key는 디렉터리처럼 보일 수 있지만 같은 파일 시스템 의미를 전부 제공하는 것은 아닙니다.

그래서 “여러 서버가 함께 쓰니까 EBS를 여러 대에 붙이자”는 결론은 위험합니다. 지원되는 일부 볼륨의 Multi-Attach 기능과 애플리케이션이 동시 쓰기를 안전하게 조정하는 것은 다른 문제입니다. 여러 컴퓨터가 같은 종이를 동시에 수정할 수 있다고 해서 서로의 기록이 자동 보호되지 않습니다. 공유 파일 시스템을 기대한다면 EFS·FSx 등 요구 프로토콜에 맞는 후보부터 검토합니다.

S3 업로드를 요청·객체·업무 상태로 나누기

큰 사진 묶음이나 동영상을 multipart upload로 보낸다고 합시다. 업로드를 시작하면 upload ID를 얻고, 여러 part를 전송한 다음 완료 요청으로 객체를 조립합니다. 일부 part 전송에 실패하면 실패한 부분을 다시 보내는 방식으로 전체 재전송을 줄일 수 있습니다. 아직 완료하지 않은 part는 완성된 객체와 같지 않습니다. 중단된 업로드의 정리 정책이 없으면 보관 비용이 남을 수 있습니다.

ETag를 항상 파일 전체의 MD5라고 생각하면 무결성 검증을 잘못할 수 있습니다. multipart와 암호화 방식 등에 따라 의미가 다릅니다. 지원되는 checksum 기능으로 어떤 알고리즘과 범위의 값을 검증하는지 명시해야 합니다. 이는 “데이터가 그대로 전달됐는가”의 검증이며, “이 사진이 올바른 입고 건의 사진인가”는 별도 업무 검증입니다.

저장 완료 후에도 DB 메타데이터 저장이 실패할 수 있습니다. 이를 피하려고 거대한 분산 트랜잭션을 가정하기보다 업로드 상태를 준비 → 업로드 확인 → 업무 연결 완료처럼 관리할 수 있습니다. 일정 시간이 지나도 연결되지 않은 객체는 정리 후보가 됩니다. 정리할 때는 업로드 중인 객체와 이미 업무에서 참조하는 객체를 구별해야 합니다. 실제 삭제는 보존 요구와 재처리 절차를 포함해 설계합니다.

강한 일관성이 해결하지 않는 것

S3의 성공한 객체 쓰기 후 읽기·목록 일관성 보장은 오래된 정보만 보일 걱정을 줄여 줍니다. 하지만 두 객체를 하나의 거래처럼 동시에 바꾸거나, S3와 DB를 한 트랜잭션으로 묶어 주지는 않습니다. 두 사용자가 같은 key에 다른 내용을 쓰는 업무 충돌도 여전히 설계해야 합니다. 버전 관리, 조건부 요청, 변경되지 않는 고유 key 같은 방법을 요구에 맞게 선택합니다.

CDN을 앞에 두면 원본 S3의 최신성과 사용자에게 제공되는 캐시의 최신성을 또 나누어야 합니다. 원본은 새 데이터인데 캐시는 TTL 동안 이전 응답을 줄 수 있습니다. 변경 불가능한 파일 이름에 버전을 포함하면 캐시 관리가 쉬워질 수 있지만 참조하는 HTML이나 DB 값 갱신까지 고려해야 합니다. “저장소가 강한 일관성”이라는 한 문장으로 전체 응답 경로의 최신성을 설명하지 않습니다.

IOPS와 처리량을 숫자로 이해하기

IOPS는 1초에 처리하는 I/O 작업 수이고 처리량은 1초에 옮기는 데이터 양입니다. 같은 1,000 IOPS라도 작업 크기가 4 KiB이면 약 3.9 MiB/s, 256 KiB이면 250 MiB/s입니다. 단순한 산술 관계일 뿐 실제 볼륨 성능은 볼륨·인스턴스 한도, I/O 모양, 큐 깊이 등에 제한됩니다. 작은 랜덤 읽기가 많은 DB와 큰 순차 파일을 옮기는 작업의 요구가 다른 이유입니다.

큐 깊이를 늘리면 장치가 병렬로 일을 받아 처리량이 좋아질 수 있지만, 포화 이후에는 대기 시간만 늘 수 있습니다. 크기만 큰 볼륨을 구매했다고 I/O 지연이 해결된다고 단정하지 않습니다. 볼륨 유형·설정 성능, EC2의 EBS 대역폭, 애플리케이션의 I/O 패턴을 함께 확인합니다.

더 깊은 면접 Q&A: 저장·복제·복구의 차이

Q. S3 버전 관리를 켜면 백업은 필요 없나요?

답변: 이전 버전을 남겨 실수로 덮어쓰거나 삭제한 상황의 복구에 도움을 줄 수 있지만, 필요한 보존 기간과 권한 격리·다른 계정이나 리전의 재해 대응까지 자동 충족하지는 않습니다. 버전을 영구 삭제할 권한을 가진 주체나 잘못된 수명주기 정책도 검토해야 합니다.

꼬리 질문: 복구할 버전을 식별하고 애플리케이션 참조와 함께 되돌릴 수 있는지 시험합니다. 데이터가 남아 있다는 사실과 업무 전체를 복구할 수 있다는 사실은 다릅니다.

Q. 백업 스냅샷이 있으면 DB 파일의 일관성도 보장되나요?

답변: 블록을 저장했다는 사실만으로 애플리케이션의 여러 쓰기가 같은 업무 시점에 맞춰졌다고 단정할 수 없습니다. 엔진과 백업 방식에 따른 일관성 보장, 여러 볼륨 사이의 정합성, 복구 시 로그 재생 등을 확인합니다.

연습: 복원한 DB가 시작되는지만 보지 말고 마지막 완료 주문, 미완료 거래, 첨부 파일 참조까지 확인합니다. 복구 시험은 인프라가 부팅되었다는 증거보다 한 단계 더 나아가야 합니다.

Q. 가장 저렴한 아카이브 클래스로 모두 옮기면 안 되나요?

답변: 보관 단가 외에 검색 시간, 검색 비용, 최소 보관 기간, 최소 과금 크기, 전환 요청 비용을 고려해야 합니다. 자주 꺼내는 작은 파일에는 저장 단가 절약보다 다른 비용이 클 수 있습니다.

답변 순서: 접근 빈도와 복구 시간 요구 → 객체 크기와 보관 기간 → 저장·요청·검색의 총비용 순으로 비교합니다. 모든 아카이브 클래스가 같은 접근 지연을 갖는다고 묶지 않습니다.

Q. 파일 업로드 후 응답이 끊겼다면 다시 올려야 하나요?

답변: 클라이언트가 응답을 못 봤다고 서버 저장이 실패한 것은 아닙니다. 요청 ID·고유 객체 key·checksum·업로드 상태 조회를 통해 결과를 확인하는 흐름이 필요합니다. 무조건 새 key로 재전송하면 중복 파일이 생길 수 있습니다.

업무 연결: 파일 중복과 업무 중복은 별개입니다. 같은 사진이 두 개 저장되어도 입고 완료가 두 번 처리되지 않도록 업무 멱등성을 추가합니다. 네트워크의 불확실성을 사용자 상태 모델로 흡수하는 설계입니다.

직접 풀어 보기: 저장소를 하나로 통일하면 쉬울까

입고 사진 원본, 여러 Linux 서버가 동시에 사용하는 공유 파일 경로, 재생성 가능한 변환 임시 파일, 관계형 DB의 디스크를 모두 같은 저장소로 통일하려 합니다. 운영 대상을 줄이는 장점이 있더라도 어떤 조건을 먼저 확인해야 할까요?

해설 펼치기 — 판단 과정과 조건을 바꾼 경우

접근 방식: 사진은 객체 key로 저장·조회할 수 있지만 공유 파일 프로그램은 파일 시스템의 경로·권한·동시 접근 의미를 기대할 수 있습니다. DB 디스크는 해당 엔진이 요구하는 블록·파일 동작과 내구성을 만족해야 합니다.

손실 허용: 원본 사진은 복구할 수 있어야 하고 임시 변환 파일은 다시 만들 수 있을 수 있습니다. 그러나 재생성이 비싸거나 오래 걸리면 임시라고 무조건 버려도 되는 것은 아닙니다.

성능·수명: 작은 랜덤 I/O, 큰 순차 전송, 자주 열고 닫는 작은 파일은 요구가 다릅니다. 같은 GB 수라도 비용과 처리 지연은 다르게 나타납니다.

결론: 저장소의 수를 최소화하는 것보다 데이터별 계약을 만족하는 구성이 우선입니다. 서로 다른 저장 방식을 쓰더라도 소유자·보존·복구 기준을 통일하면 운영의 일관성을 높일 수 있습니다.
