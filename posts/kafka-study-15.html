Kafka Streams 설정과 상태 저장을 처음부터 이해하기

Streams를 단순 Consumer라고 생각하지 않고 내부 Task, State Store, 처리 보장까지 운영자의 관점에서 배웁니다.

1. Streams 설정은 왜 별도일까?

쉬운 비유

일반 Consumer는 전달된 편지를 읽고 각자 할 일을 합니다. Streams는 흐르는 편지를 계속 분류·계산해 다른 곳에 보내는 공장이에요.

실제 내부 동작

Kafka Streams 애플리케이션은 입력 토픽을 읽는 것뿐 아니라 처리 Topology, 상태 저장소, 내부 토픽, Task 배정을 관리합니다. 따라서 일반 KafkaConsumer와 다른 설정을 필요로 합니다.

실무에서 생길 수 있는 문제

Streams를 @KafkaListener로만 생각하면 Changelog, State Store 복구 및 Task 재배치 운영을 놓칠 수 있습니다.

2. application.id는 왜 중요할까?

쉬운 비유

두 팀이 같은 이름표를 쓰면 서로의 작업 장부가 뒤섞일 수 있습니다.

실제 내부 동작

application.id는 Streams 앱을 식별하며 Consumer Group과 내부 토픽 네이밍 등에 영향을 줍니다. 동일 토폴로지의 여러 인스턴스는 동일 application.id로 협력할 수 있습니다. 서로 독립적인 애플리케이션은 고유 ID를 사용해야 합니다.

실무에서 생길 수 있는 문제

새 버전을 테스트하려고 application.id를 바꿀 때는 새 그룹과 새로운 내부 상태 자원이 생길 수 있으므로 의도된 데이터 재처리 여부를 확인합니다.

3. bootstrap.servers

쉬운 비유

처음 가야 할 공장 정문 주소를 알려줍니다.

실제 내부 동작

Kafka Streams도 Broker 메타데이터를 가져오기 위한 bootstrap.servers가 필요합니다. 초기 목록 전체에 모든 Broker를 넣을 필요는 없지만 여러 접근 가능한 Broker를 기재하는 것이 회복에 유리합니다.

실무에서 생길 수 있는 문제

Docker 환경에서 광고 주소가 잘못되면 초기 연결 이후 데이터 조회·기록이 실패할 수 있습니다.

4. num.stream.threads와 병렬 처리

쉬운 비유

공장에 직원이 네 명이어도 운반 벨트가 한 개면 네 명 모두가 독립적으로 같은 벨트를 맡는 것은 아닙니다.

실제 내부 동작

7. processing.guarantee와 exactly_once_v2

쉬운 비유

공장 직원이 계산 결과를 두 번 적거나 일부만 적는 사고를 줄이고 싶습니다.

실제 내부 동작

Kafka Streams의 processing.guarantee 설정은 처리 보장 수준을 정합니다. exactly_once_v2는 Kafka 내부에서 입력 오프셋과 출력 레코드 등을 트랜잭션으로 관리하는 처리에 사용됩니다. 외부 REST 호출이나 MySQL 업데이트까지 자동 원자화하지는 않습니다.

Java Kafka Streams 최소 예제

StreamsBuilder builder = new StreamsBuilder();
KStream<String, String> events = builder.stream("orders");
events.filter((key, value) -> value != null)
      .mapValues(String::toUpperCase)
      .to("orders-normalized");

Properties props = new Properties();
props.put(StreamsConfig.APPLICATION_ID_CONFIG, "orders-transformer");
props.put(StreamsConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092");
props.put(StreamsConfig.DEFAULT_KEY_SERDE_CLASS_CONFIG, Serdes.StringSerde.class);
props.put(StreamsConfig.DEFAULT_VALUE_SERDE_CLASS_CONFIG, Serdes.StringSerde.class);

KafkaStreams app = new KafkaStreams(builder.build(), props);
Runtime.getRuntime().addShutdownHook(new Thread(app::close));
app.start();

이 예제는 String 값의 단순 변환입니다. 실제 집계 시에는 상태 저장소, 내부 토픽, Serde, 오류 및 상태 복원 설정이 추가됩니다.

면접 질문 10개 — 펼쳐서 정답 확인

Q1. Streams 인스턴스 5개와 토픽 파티션 2개면 모두 동일하게 일하나요?

파티션과 Task 수가 병렬성을 제한하므로 모든 인스턴스가 동일량의 입력 처리를 담당한다고 가정하면 안 됩니다.

Q2. application.id를 변경하면 무엇이 달라지나요?

Streams 앱이 별도 논리적 식별자로 취급되며 Group 및 내부 자원과 상태가 달라질 수 있습니다.

Q3. state.dir만 있으면 장애 뒤 영구 복구가 되나요?

아닙니다. 로컬 상태와 Changelog의 보존, 데이터 유효성, 재처리 정책을 함께 고려해야 합니다.

Q4. num.standby.replicas는 Producer RF와 같은 뜻인가요?

아닙니다. 전자는 Streams Task의 예비 상태 복제 운영이고 후자는 Kafka Topic Partition Replica 수입니다.

Q5. Exactly-once-v2가 MySQL 갱신을 포함하나요?

아닙니다. Kafka Streams의 Kafka 기록·오프셋 트랜잭션 경계와 외부 DB 트랜잭션은 분리되어 있습니다.

Q6. Serde를 잘못 지정하면 어떤 오류가 나나요?

키 또는 값의 데이터 형식을 복원하지 못해 역직렬화 예외가 발생할 수 있습니다.

Q7. 내부 토픽 생성이 실패하면?

Streams 애플리케이션 기동이나 상태 복구에 실패할 수 있습니다. ACL, 브로커 수, replication factor 등 설정을 확인합니다.

Q8. num.stream.threads를 무조건 높일까요?

아닙니다. 토픽 Partition과 Task 수, 처리 노드 CPU·메모리·State Store IO가 실제 병렬 처리량의 한계입니다.

Q9. commit.interval.ms를 낮추면 항상 좋나요?

처리·커밋 비용이 증가할 수 있으므로 지연과 처리량 간 트레이드오프를 측정해야 합니다.

Q10. Lag은 낮은데 집계가 늦다면?

State Store 복구, downstream sink 지연, 토폴로지 처리 병목 및 커밋·캐시 동작을 따로 확인해야 합니다.
