1. 모든 상자에 같은 자물쇠를 달면 충분할까

홍보 전단과 고객 주소 명단은 둘 다 파일이지만 노출의 피해는 다릅니다. 데이터 분류는 무엇을 얼마나 보호하고 얼마나 오래 보관할지 정하는 출발점입니다. 보안 장비를 먼저 사기보다 데이터가 어디서 생겨 어디로 이동하고 누가 읽으며 언제 삭제되는지 그려야 합니다. SEC 7~9는 데이터 분류·저장·전송 보호, SEC 10은 사고 대응, SEC 11은 개발 과정의 보안을 다룹니다.

2. SEC 7: 분류와 수명주기

공개·내부·기밀·민감 같은 분류 체계를 업무와 연결합니다. 실제 등급 이름보다 소유자·허용 사용자·보관 기간·복구 요구·삭제 기준이 명확한지가 중요합니다. 개인 정보가 로그·백업·분석 복사본에도 남을 수 있으므로 원본 DB만 조사해서는 부족합니다. Macie 같은 자동 발견 도구는 지원 범위에서 도움이 되지만 모든 데이터의 의미와 규정을 자동으로 확정하지는 못합니다.

SEC07-BP01~04는 분류 체계, 민감도별 통제, 발견 자동화, 수명주기 관리를 포함합니다. 보존 기간이 끝난 데이터는 원본뿐 아니라 복사본·캐시·export·백업 정책까지 검토해야 합니다. 반대로 복구와 감사에 필요한 데이터를 비용 절감만 보고 삭제하면 안 됩니다. 데이터 소유자와 보존 책임을 정하고 예외를 기록합니다.

3. SEC 8: 저장 암호화와 접근 제어

암호화는 데이터가 저장 매체나 백업으로 노출될 때 읽기 위험을 줄이지만, 정상 권한으로 복호화하는 공격자를 막는 만능 통제는 아닙니다. KMS key policy·IAM·grant·서비스 통합을 통해 누가 어떤 맥락에서 키를 사용하는지 제한합니다. 데이터 접근 권한과 키 사용 권한을 구분하면 사고 조사와 역할 분리가 쉬워집니다.

envelope encryption에서는 데이터 키로 본문을 암호화하고 KMS key로 데이터 키를 보호합니다. key rotation은 키 재료 변경을 관리하는 과정이고 기존 암호문 전체를 자동으로 다시 쓰는 것과 다릅니다. 키를 비활성화하거나 삭제하면 업무와 복구가 영향을 받습니다. 백업 복사 시 대상 계정·리전의 키와 복호화 권한까지 확인해야 합니다.

SEC08-BP01~04는 키 관리, 저장 암호화, 자동 검증·수정, 접근 제어입니다. 기본 암호화 설정이 있어도 예전 객체·다른 저장소·export 파일의 보호 상태가 같다고 단정하지 않습니다. 통제를 코드로 배포하고 실제 리소스와 데이터에 적용되었는지 증거를 수집합니다.

4. SEC 9: TLS는 어디에서 끝나는가

사용자와 ALB 사이가 HTTPS라도 ALB와 앱 사이가 HTTP이면 그 구간은 다른 보호 조건입니다. TLS 종료 지점을 표시하고 각 구간에 필요한 암호화와 인증을 설계합니다. 인증서 검증을 끄면 암호화는 되어도 상대가 올바른 서버인지 확인하지 못할 수 있습니다. 인증서 이름·체인·만료·회전을 관리해야 합니다.

mTLS는 양쪽 인증서를 검증하는 방식으로 서비스 신원 확인에 활용할 수 있지만, 인증된 주체가 어떤 업무를 할 수 있는지는 별도의 인가입니다. private network나 Direct Connect를 사용한다고 자동으로 모든 데이터가 종단 간 암호화되는 것은 아닙니다. SEC09-BP01~03은 키·인증서 관리, 전송 암호화, 통신 상대 인증을 구분합니다.

5. SEC 10: 사고 중에 도구부터 설치하지 않기

사고 대응은 준비→탐지와 분석→격리→근절→복구→학습의 흐름으로 생각할 수 있습니다. 연락할 사람과 외부 지원, 의사결정 권한, 증거 취급, 커뮤니케이션 계획을 미리 정합니다. 사고 중 필요한 role·포렌식 도구·격리 환경을 사전 준비하지 않으면 가장 급할 때 권한 요청과 설치에 시간을 씁니다.

로그·디스크 스냅샷·메모리 등 증거의 필요성과 휘발성을 이해합니다. 무조건 재부팅하거나 종료하면 증거를 잃을 수 있고, 아무 조치 없이 보존만 하면 공격이 계속될 수 있습니다. 사고 유형별 플레이북에서 격리와 업무 영향·증거 보존의 순서를 정합니다. 증거 수집 시각·주체·해시·보관 위치·접근 이력을 남겨 신뢰성을 확보합니다.

SEC10-BP01~08은 연락망, 대응 계획, 포렌식, 플레이북 개발·검증, 사전 권한, 사전 도구, 시뮬레이션, 사고 학습을 포함합니다. 게임데이는 통제된 환경에서 역할과 절차를 연습하는 활동입니다. 성공 기준은 “훈련을 했다”가 아니라 발견·판단·격리·복구 시간이 목표에 맞고 누락된 권한과 절차를 수정했는지입니다.

6. SEC 11: 개발 수명주기에 보안을 넣기

개발자 교육은 추상적인 규정 전달보다 실제 코드의 인증 우회·입력 처리·secret 노출 사례와 연결합니다. 코드 검토는 업무 권한과 데이터 흐름을 확인하고, SAST·SCA·secret scanning·동적 테스트 등 자동 검사를 파이프라인에 배치합니다. 각 도구는 발견 가능한 문제가 다르고 오탐·누락이 있어 사람의 검토와 상호 보완해야 합니다.

의존성과 패키지를 승인된 출처로 관리하고 버전과 빌드 결과를 추적합니다. CI가 배포 role을 얻는 경로와 서명 키, 외부 PR이 접근 가능한 secret도 점검합니다. 애플리케이션 소스는 안전해도 파이프라인이 침해되면 악성 결과물이 배포될 수 있습니다. 프로그래밍 방식의 배포는 재현성을 높이지만 배포 권한을 좁히고 변경 이력을 남겨야 합니다.

SEC11-BP01~08은 교육, 자동 테스트, 침투 테스트, 코드 검토, 의존성 중앙화, 자동 배포, 파이프라인 보안 검토, 워크로드 팀의 보안 책임을 포함합니다. 침투 테스트는 허용된 범위와 정책에 따라 수행하고 자동 검사 결과만으로 모든 비즈니스 로직 취약점이 제거되었다고 주장하지 않습니다.

7. 가상 사고: 운영 secret이 빌드 로그에 노출

먼저 노출된 secret을 실제 사용하는 시스템과 유효 기간·권한 범위를 파악합니다. 필요한 교체·폐기와 접근 기록 조사를 진행하고, 로그 접근자와 보관·복사 범위를 확인합니다. 로그 한 줄을 지우는 것으로 끝내지 않습니다. 캐시·아티팩트·외부 로그 수집기에 남아 있을 수 있고 이미 사용되었을 수 있기 때문입니다. 빌드 단계에서 운영 secret이 정말 필요했는지와 최소 권한·마스킹·검출을 개선합니다.

연습으로 데이터 한 종류를 골라 생성·저장·전송·분석·백업·삭제 단계를 그립니다. 각 단계에 소유자·암호화·키·권한·로그·보존 기간을 적으면 빠진 복사본과 신뢰 경계가 드러납니다. 실제 운영 사고를 만들 필요 없이 문서와 비운영 시나리오로도 먼저 검증할 수 있습니다.

8. 상세 면접 Q&A

Q. HTTPS를 쓰면 데이터 보호가 끝났나요?

전송 구간의 암호화와 서버 인증을 제공하지만 저장 데이터·로그·권한·키 관리·업무 인가는 별도입니다. TLS가 종료되는 지점 이후 통신도 확인해야 합니다. 인증서 검증을 끄거나 잘못된 신뢰 체인을 쓰면 기대한 보호가 성립하지 않을 수 있습니다.

Q. KMS 키를 교체하면 기존 데이터를 모두 재암호화하나요?

키 재료 회전과 기존 데이터 재암호화는 다른 작업입니다. 서비스와 키 유형의 회전 동작을 확인해야 하며, 필요한 데이터 재암호화는 별도 절차일 수 있습니다. 기존 데이터 복호화를 위해 어떤 키 재료가 유지되는지도 이해해야 합니다.

Q. 사고가 나면 서버부터 종료해야 하나요?

피해 확산과 증거 보존·업무 영향의 균형을 판단해야 합니다. 종료로 휘발성 증거를 잃을 수 있으므로 가능한 격리와 수집 절차를 미리 준비합니다. 정답은 모든 사고에 같은 단일 조치가 아니라 유형별 검증된 플레이북입니다.

Q. 보안 팀이 있으니 개발 팀은 기능만 만들면 되나요?

업무 권한·데이터 의미·코드 흐름을 가장 잘 아는 팀이 보안 책임을 공유해야 합니다. 보안 팀은 기준과 전문 지원을 제공하고, 개발 팀은 설계·검토·수정·운영에 통합합니다. 출시 직전에 검사만 추가하면 구조적 문제를 고치는 비용이 커집니다.

깊이 읽기: 데이터의 복사본과 평문이 생기는 모든 위치

원본만 보호하면 충분하지 않은 이유

고객 주소가 암호화된 DB에 저장되어 있어도 CSV 다운로드, 개발용 덤프, 오류 로그, 백업, 분석용 S3에 복사될 수 있습니다. 보안은 원본 한 곳의 설정이 아니라 데이터 수명주기의 문제입니다. 수집 목적, 저장 위치, 복사 경로, 처리 주체, 보존 기간, 삭제 방법을 연결해 봅니다.

종이 문서를 금고에 보관하면서 복사본을 회의실에 두고 오는 상황에 비유할 수 있습니다. 금고의 자물쇠가 강해도 복사본이 노출되면 정보는 유출됩니다. 따라서 데이터 분류는 “민감”이라는 라벨을 붙이는 데서 끝나지 않고 로그 마스킹, 다운로드 제한, 테스트 데이터 생성, 보존·폐기 규칙으로 이어져야 합니다.

암호화의 경계 네 곳

저장 암호화는 디스크나 저장 매체에 남은 데이터를 보호합니다. 전송 암호화는 네트워크 구간을 보호합니다. 애플리케이션이 처리하는 동안의 평문은 접근 권한과 프로세스 격리·코드 안전성의 영향을 받습니다. 결과를 사용자에게 제공한 뒤에는 다운로드·브라우저·외부 시스템의 보관도 고려해야 합니다. 한 종류의 암호화가 네 경계를 모두 해결하지 않습니다.

브라우저→ALB→앱→DB에서 TLS가 어느 구간에 적용되고 어디서 종료되는지 표시해 보세요. 인증서 검증을 끄면 암호화된 연결이라도 원하는 상대와 통신한다는 보장이 약해질 수 있습니다. 내부 구간이므로 검증을 생략한다는 결론은 위협 모델과 요구를 확인한 뒤 판단해야 합니다.

데이터 삭제와 키 삭제는 같은 작업이 아니다

데이터를 삭제해도 버전·백업·분석 복사본이 남을 수 있습니다. 키를 삭제하면 관련 암호문을 읽기 어렵게 만들 수 있지만 어떤 데이터와 복사본이 그 키에 의존하는지, 다른 키나 평문 복사본이 없는지 확인해야 합니다. 또한 법적·업무 보존 요구와 복구 필요를 함께 검토해야 합니다. 여기서는 법률적 결론을 내리지 않고 기술적 수명주기 통제의 필요를 설명합니다.

키 비활성화·삭제 권한이 데이터 삭제 권한만큼 중요할 수 있는 이유도 여기에 있습니다. 백업 데이터가 완벽해도 복호화에 필요한 키와 권한을 잃으면 복구에 실패할 수 있습니다. 백업 정책과 키 관리 정책을 서로 다른 팀이 따로 설계했다면 실제 복원 시험에서 연결을 확인해야 합니다.

빌드 파이프라인도 데이터와 권한의 통로다

개발자는 코드를 검토해도 CI 로그나 컨테이너 이미지에 secret이 들어가는 것을 놓칠 수 있습니다. 빌드 인수·환경 변수·테스트 출력·의존성 다운로드·배포 권한을 살펴봅니다. 생성된 이미지의 출처와 변경 이력을 추적하고 동일 배포물을 여러 환경으로 승격하면 “검증한 것과 배포한 것이 같은가”를 확인하기 쉬워집니다.

의존성 취약점 검사와 secret 탐지, 코드 리뷰는 서로 대체하지 않습니다. 라이브러리가 안전해도 사용자 권한 검사가 빠진 업무 API는 취약할 수 있습니다. 반대로 업무 로직이 맞아도 오래된 의존성이나 과도한 배포 권한이 위험을 만듭니다. 보안 검사를 개발 마지막 날의 행사로 두기보다 변경 과정에 작은 확인 단계로 넣습니다.

유출 사고를 시간 순서로 다루기

  1. 어떤 정보·자격증명이 어느 경로로 노출됐는지 범위를 확인합니다.
  2. 추가 노출을 제한하되 필요한 증거와 기록을 보호합니다.
  3. 자격증명은 회전·철회하고 이미 생성된 세션이나 추가 권한을 조사합니다.
  4. 영향받은 데이터·다운로드·외부 전달을 추적합니다.
  5. 원인을 수정하고 정상 업무·권한·보호 기능을 검증합니다.
  6. 재발 방지 작업을 담당자와 완료 기준까지 기록합니다.

이 순서는 일반적인 사고 모델입니다. 실제 사고에서는 확산 속도와 조직 절차에 따라 조치를 병행하거나 우선순위를 바꿉니다. “Git에서 secret 한 줄 삭제”는 노출 이력과 복사본을 지우지 못하므로 대응 완료가 아닙니다.

더 깊은 면접 Q&A: 암호화 다음에 물어야 할 것

Q. 운영 DB를 마스킹해서 개발에 복사하면 안전한가요?

답변: 직접 식별자뿐 아니라 조합으로 개인을 추정할 수 있는 필드, 자유 텍스트, 첨부 파일, 로그와 연관 키를 확인해야 합니다. 마스킹 후에도 개발 목적에 필요한 최소 데이터만 제공하는 방향이 좋습니다.

대안: 가능한 경우 합성 데이터나 제한된 샘플로 테스트합니다. 원본을 내려받는 순간부터 새 복사본의 접근·보존·삭제 책임이 생깁니다.

Q. 키 회전 후 옛 백업은 새 키로 자동 재암호화되나요?

답변: 키 재료 회전과 기존 암호문의 재작성은 다른 작업입니다. 서비스의 회전 방식과 기존 데이터 복호화 동작을 확인해야 하며 “회전했으니 모든 백업이 새 암호문”이라고 설명하면 안 됩니다.

복구 연결: 백업을 실제로 복원할 계정과 role이 키를 사용할 수 있는지, 키가 사용 가능한 상태인지 확인합니다. 데이터 보관 기간보다 키 사용 가능 기간이 짧으면 복구 계획이 깨질 수 있습니다.

Q. Secret이 로그에 노출되면 로그를 지우는 게 먼저인가요?

답변: 노출 확산 제한과 증거 보존, 자격증명 무효화·회전을 함께 판단합니다. 삭제만 하면 이미 복사한 사람이 계속 사용할 수 있고 조사 흔적도 잃을 수 있습니다. 조직의 사고 대응 절차에 따라 접근을 제한하고 필요한 기록을 보호합니다.

후속: 같은 값이 이미지·아티팩트·채팅·다른 로그에도 남았는지 확인합니다. 재발 방지는 출력 코드 제거와 secret 탐지·권한 최소화까지 포함합니다.

Q. TLS를 쓰는데 왜 서명 URL의 노출을 조심해야 하나요?

답변: 전송 구간 암호화와 URL 자체가 주는 접근 권한은 다른 문제입니다. 유효한 서명 URL을 가진 사람이 허용된 동작을 할 수 있는 조건이라면 로그·공유·브라우저 기록으로 유출되는 경로를 고려해야 합니다.

설계: 필요한 객체·작업·유효기간을 제한하고 URL 발급 자체에도 사용자 권한을 확인합니다. URL을 만들 수 있다는 사실이 요청자가 그 객체를 볼 자격이 있다는 뜻은 아닙니다.

직접 풀어 보기: 백업은 있는데 복호화할 수 없다

재해 복구 계정에 데이터 백업을 보관했습니다. 복원 작업은 시작되지만 암호화 키 사용 권한 문제로 읽기가 실패합니다. 원본 데이터가 있다는 사실만으로 복구 준비가 끝나지 않은 이유를 설명해 보세요.

해설 펼치기 — 판단 과정과 조건을 바꾼 경우

복구 의존성: 암호문, 필요한 키, 그 키를 사용할 권한, 서비스·리전 지원 조건이 모두 맞아야 합니다. 백업 파일 하나만 독립적으로 존재한다고 앱이 데이터를 읽을 수 있는 것은 아닙니다.

권한 모델: 실제 복구 role과 계정에서 키 접근이 허용되는지, key policy와 관련 제한·상태를 확인합니다. 운영 role에서 성공한 시험은 재해 복구 role의 권한을 증명하지 못합니다.

훈련: 평소와 동일한 관리자 자격증명 대신 실제 비상 절차의 신원과 경로를 사용해 복원합니다. 문서에 빠진 접근 단계와 담당자 의존성을 발견하는 것이 목적입니다.

예방: 키 수명주기와 데이터 보존 기간을 연결하고 삭제·비활성화의 영향을 검토합니다. 암호화를 약하게 만드는 우회보다 정상적인 복구 경로가 작동하도록 설계해야 합니다.
