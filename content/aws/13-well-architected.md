## 1. 건물을 검사할 때 출입문만 보지 않는다

튼튼한 건물이라도 비상구가 없거나 유지비를 감당할 수 없으면 좋은 건물이라고 하기 어렵습니다. 시스템도 보안만 강하고 복구가 불가능하거나, 빠르지만 비용이 무제한이면 문제가 됩니다. Well-Architected는 하나의 정답 구조를 강요하기보다 **설계에서 빠뜨린 질문을 찾는 프레임워크**입니다. 여섯 원칙은 서로 연결되지만 같은 목표가 아닙니다.

워크로드는 비즈니스 가치를 제공하는 구성 요소의 묶음입니다. 입고 검수 API·DB·큐·운영 절차까지 하나의 워크로드로 볼 수 있습니다. 컴포넌트 하나의 성능이 아니라 사용자가 끝까지 업무를 마치는 경험을 평가합니다. 공개된 일반 설계 원칙은 용량 추측을 줄이고, 실제에 가까운 규모로 시험하고, 자동화하고, 실험과 측정으로 구조를 계속 개선하라는 방향입니다.

## 2. 여섯 원칙을 증거와 연결하기

| 원칙 | 핵심 질문 | 좋은 증거 |
|---|---|---|
| 운영 우수성 | 변경하고 관찰하고 학습할 수 있는가 | 런북·배포 기록·SLO·사후 분석 |
| 보안 | 신원·데이터·시스템을 보호하는가 | 최소 권한·로그·위협 모델·대응 훈련 |
| 신뢰성 | 고장과 변화 속에서 업무를 유지·복구하는가 | 장애 테스트·복구 시간·백업 복원 |
| 성능 효율 | 필요한 성능에 적합한 자원을 쓰는가 | 부하 모델·p99·병목 분석 |
| 비용 최적화 | 필요한 성과를 합리적 비용으로 얻는가 | 단위 원가·활용률·수명주기 |
| 지속 가능성 | 필요한 성과 대비 자원 사용과 환경 영향을 줄이는가 | 사용량·데이터 이동·유휴 제거 지표 |

“Multi-AZ를 사용한다”는 설정 사실은 신뢰성 증거의 일부입니다. 실제로 한 AZ가 없어도 주문을 처리했는지, 복구가 얼마나 걸렸는지는 별도의 증거입니다. 검토 표에 체크한 것과 검증된 것은 다릅니다.

## 3. 운영 우수성: 조직·준비·운영·개선

조직 단계에서는 비즈니스 우선순위와 소유자를 정합니다. 준비 단계에서는 관찰성·배포·운영 준비도를 확인합니다. 운영 단계에서는 정상 상태를 지표로 정의하고 사건에 대응합니다. 개선 단계에서는 실패와 성공을 다음 작업에 반영합니다. 작은 변경·자동화·자주 검증하는 배포는 문제의 영향과 되돌림 비용을 줄입니다.

런북은 알려진 작업을 수행하는 절차, 플레이북은 아직 원인을 모르는 문제를 조사하는 절차에 가깝습니다. “서비스가 느리면 재시작”만 적은 문서는 조사도 복구도 불충분합니다. 조건·영향·확인 항목·조치·성공 기준·중단 조건을 적고 실제로 수행할 수 있어야 합니다. 운영 책임을 특정 퇴사자나 베테랑의 기억에만 두지 않는 것도 아키텍처 품질입니다.

## 4. 보안과 신뢰성: 서로 도와주기도 충돌하기도 한다

보안은 강한 신원 기반·추적 가능성·다층 방어·자동화·데이터 보호·사고 준비를 포함합니다. 신뢰성은 할당량·네트워크·분산 상호작용·변경·백업·장애 격리·DR을 포함합니다. 백업을 별도 계정에 보관하면 침해와 실수의 영향 범위를 줄이면서 복구 능력을 높일 수 있습니다.

그러나 모든 보안 제한이 복구에 자동으로 유리한 것은 아닙니다. 긴급 상황에 필요한 role이나 키 권한을 전혀 준비하지 않으면 복구가 지연됩니다. 반대로 긴급 계정을 상시 무제한으로 열어 두면 침해 위험이 커집니다. 사전 정의된 break-glass 절차와 승인·감사·사후 회수·정기 테스트로 두 요구를 맞춥니다.

## 5. 성능 효율과 비용: 측정 없이는 둘 다 어렵다

적절한 컴퓨팅·저장소·DB·네트워크 선택을 실제 부하로 검증합니다. 처리량이 높아져도 p99가 나빠지면 사용자 경험은 악화될 수 있습니다. 서버를 늘리는 것보다 N+1 조회 제거가 더 좋은 결과를 만들 수 있고, 너무 공격적인 자원 축소는 장애 여유를 없앨 수 있습니다.

비용 원칙은 클라우드 재무 관리, 지출 인식, 자원 선택, 수요와 공급, 지속 개선으로 나뉩니다. 구매 할인만의 문제가 아닙니다. 원가를 업무 성과와 연결하고 소유자가 없는 자원을 정리해야 합니다. 큰 약정을 사기 전에 구조와 수요를 최적화하는 순서가 중요한 이유입니다.

## 6. 지속 가능성: 전력량을 추측해 단정하지 않기

지속 가능성은 같은 업무 결과를 위해 필요한 자원과 낭비를 줄이는 관점입니다. 리전 선택, 수요에 맞춘 용량, 효율적인 소프트웨어, 데이터 수명주기, 적절한 하드웨어·관리형 서비스, 개발 프로세스를 함께 봅니다. 유휴 개발 환경과 무의미한 로그를 줄이는 일은 비용과 자원 사용을 동시에 개선할 수 있습니다.

하지만 “비용이 30% 줄었으니 탄소도 정확히 30% 감소했다”는 결론은 근거가 부족합니다. 가격과 에너지·배출은 동일한 측정치가 아닙니다. 거래당 CPU 시간·저장량·전송량 등 관찰 가능한 지표를 먼저 사용하고 환경 영향 추정에는 가정과 한계를 표시합니다. 데이터 보존을 줄일 때도 규정·복구 요구를 먼저 만족해야 합니다. 필요한 원본을 삭제해 다시 만드는 작업이 더 비싸고 위험할 수 있습니다.

## 7. 검토는 감사 점수보다 개선 대화

원문은 잘잘못을 따지는 형식보다 구체적인 위험과 개선을 찾는 대화를 강조합니다. 설계 초기에 되돌리기 어려운 선택을 먼저 검토합니다. 예를 들어 전 조직의 겹치는 IP 대역이나 고객 데이터의 지역 이동은 나중에 바꾸기 어렵습니다. 인스턴스 크기처럼 상대적으로 쉽게 되돌릴 수 있는 선택은 작은 실험으로 빠르게 배울 수 있습니다.

검토 결과에는 위험, 근거, 영향, 개선안, 담당자, 기한을 남깁니다. “보안 개선” 같은 모호한 작업 대신 “운영 role의 미사용 S3 삭제 권한을 검토하고 테스트 후 제거”처럼 실행 가능하게 만듭니다. 시스템이 변하면 검토도 갱신해야 하며 일회성 인증서처럼 취급하지 않습니다.

## 8. 통합 사고 실험: 입고 사진 분석 서비스

사진을 S3에 두고 SQS로 분석을 전달하는 구성에서 여섯 질문을 던져 보세요. 운영: 큐 대기 시간과 실패 작업을 볼 수 있는가? 보안: 앱은 자기 prefix만 쓰고 분석기는 필요한 객체만 읽는가? 신뢰성: DB 커밋 후 메시지 삭제 전 장애에 멱등한가? 성능: 큰 사진이 소비자 메모리를 압박하지 않는가? 비용: 썸네일 재생성·수명주기를 고려했는가? 지속 가능성: 같은 사진을 불필요하게 여러 번 분석하거나 전송하지 않는가?

하나의 아키텍처에서도 답은 여섯 방향으로 다릅니다. 캐시는 성능·비용·자원 사용을 개선할 수 있지만 오래된 값과 무효화 복잡성을 늘립니다. 트레이드오프는 결함을 숨기는 말이 아니라, 무엇을 얻고 어떤 위험을 받아들이는지 명시하는 작업입니다.

## 깊이 읽기: 여섯 원칙을 하나의 설계 회의에 적용하기

### 원칙은 서비스 목록이 아니라 질문의 방향이다

같은 입고 사진 분석 시스템을 여섯 방향에서 검토해 봅시다. 운영 우수성은 문제가 생겼을 때 누가 무엇을 보고 조치하는지 묻습니다. 보안은 누가 사진을 보고 바꿀 수 있는지 묻습니다. 신뢰성은 일부 장애에도 업무가 계속되거나 복구되는지 묻습니다. 성능 효율은 요구 지연과 처리량을 어떤 자원으로 만족할지 묻습니다. 비용 최적화는 같은 가치를 더 적은 총비용으로 제공할지 묻습니다. 지속 가능성은 불필요한 자원과 작업을 줄이는 방향을 검토합니다.

건물의 소방·동선·전기·운영비 검사를 각각 하는 것과 비슷합니다. 하나를 잘했다고 나머지가 자동으로 좋아지지 않습니다. 예를 들어 모든 데이터를 영구 보관하면 조사에는 도움이 될 수 있지만 비용·개인정보·자원 사용 부담이 커집니다. 요구와 보존 근거를 확인한 뒤 기간과 계층을 정해야 합니다.

### 설계 선택 하나에 붙는 여섯 질문

사진 분석을 비동기 큐로 바꾸는 선택을 봅시다. 운영 측면에서는 메시지 나이와 DLQ를 감시해야 합니다. 보안 측면에서는 발행자와 소비자의 큐 권한을 나눕니다. 신뢰성 측면에서는 중복 처리와 재시도를 설계합니다. 성능 측면에서는 접수 지연과 최종 완료 시간을 따로 측정합니다. 비용 측면에서는 배치 처리와 실행 시간·요청 비용을 비교합니다. 지속 가능성 측면에서는 중복 분석과 불필요한 polling을 줄일 수 있는지 봅니다.

따라서 “SQS를 도입했으니 신뢰성 원칙 충족”처럼 제품 도입을 완료 조건으로 쓰면 안 됩니다. 실제 실패 시 어떻게 동작하는지와 운영 증거가 있어야 합니다. 원칙은 체크박스보다 설계의 빠진 질문을 드러내는 도구입니다.

### 정량 목표를 먼저 합의하기

가상 요구로 접수 API는 p95 300ms 이내, 분석 결과는 5분 이내, 장애 시 최대 30분 내 복구, 손실 허용 범위는 업무별 별도 정의라고 적을 수 있습니다. 이 수치는 예시이며 권장 기본값이 아닙니다. “빠르게”, “안전하게”, “저렴하게”라는 말만으로는 상충하는 선택을 평가하기 어렵습니다.

RTO와 RPO는 담당 엔지니어가 임의로 정하는 인프라 숫자가 아닙니다. 업무 중단과 데이터 손실의 영향을 사업 담당자와 합의해야 합니다. 모든 데이터를 같은 중요도로 다루면 지나치게 비싸지거나 핵심 데이터를 충분히 보호하지 못할 수 있습니다. 원본 사진·재생성 가능한 썸네일·검수 완료 기록은 복구 우선순위가 다릅니다.

### 위험을 개선 작업으로 바꾸기

| 발견한 위험 | 막연한 할 일 | 실행 가능한 개선 작업 |
|---|---|---|
| 백업 복원 미검증 | 백업 강화 | 격리 환경에서 복원 후 핵심 조회 검증, 시간 기록 |
| 장애 알림 주인 없음 | 모니터링 개선 | 알람별 담당자·첫 조치·에스컬레이션 지정 |
| secret이 설정 파일에 있음 | 보안 강화 | 저장 경로 이전, 회전 검증, 노출 이력 조사 |
| 피크 때 큐가 밀림 | 서버 확장 | 입력·처리율 측정, 완료 시간 목표로 용량 산정 |
| 비용 증가 이유 모름 | 비용 절감 | 비용 배분 기준과 성공 업무당 비용 계산 |

개선 작업에는 담당자, 완료 기준, 확인 증거와 검토 날짜를 둡니다. 모든 위험을 한 번에 제거하기보다 발생 가능성과 피해, 개선 비용, 의존성을 고려해 순서를 정합니다. 높은 위험을 그대로 두어야 한다면 이유와 임시 통제, 다시 볼 시점을 기록합니다.

### 지속 가능성을 과장 없이 말하기

서버를 줄였다고 곧바로 특정 탄소 배출량을 줄였다고 계산할 수는 없습니다. 전력·장비·서비스 배분·리전 등 필요한 정보와 추정 범위를 확인해야 합니다. 이 연재에서는 측정 근거 없는 탄소 수치를 제시하지 않습니다. 대신 중복 처리 제거, 불필요한 데이터 이동·보존 감소, 수요에 맞춘 용량 같은 직접 통제 가능한 작업을 검토합니다.

더 오래 실행되는 작은 서버가 더 짧게 끝나는 큰 서버보다 항상 효율적인 것도 아닙니다. 전체 작업량·자원 사용 시간·품질을 비교해야 합니다. 비용 감소와 자원 효율 개선이 같은 방향일 수 있지만 항상 완전히 같은 지표는 아닙니다.

## 더 깊은 면접 Q&A: 좋은 설계에 정답 하나가 없는 이유

<details><summary>Q. Well-Architected 검토를 통과하면 장애가 안 나나요?</summary><p><strong>답변:</strong> 위험을 식별하고 개선하는 체계이지 장애가 없다는 보증이 아닙니다. 실제 트래픽·배포·조직·의존성이 바뀌면 과거 검토의 가정도 달라집니다. 반복 검토와 실험, 사고 후 학습이 필요합니다.</p><p><strong>증거:</strong> “다중 AZ 사용”이라는 답보다 한 AZ 손실 시 남는 용량과 실제 복구 시험 결과가 더 구체적입니다. 구성 여부와 요구 충족 여부를 나눕니다.</p></details>
<details><summary>Q. 비용과 신뢰성이 충돌하면 무엇을 우선하나요?</summary><p><strong>답변:</strong> 먼저 반드시 지켜야 할 업무 목표를 정하고 그 범위 안에서 비용을 줄입니다. 중요한 거래 기록의 복구 목표를 깨면서 비용을 낮추는 것은 같은 서비스를 더 효율적으로 운영한 것이 아닙니다.</p><p><strong>대안:</strong> 모든 기능에 최고 가용성을 적용하는 대신 중요 기능과 지연 가능한 기능을 분리합니다. 핵심은 남기고 비핵심 작업을 늦추는 방식으로 같은 예산 안에서 요구를 맞출 수 있습니다.</p></details>
<details><summary>Q. 관리형 서비스를 쓰는 것이 항상 운영 우수성에 유리한가요?</summary><p><strong>답변:</strong> 반복적인 인프라 운영을 줄이는 장점이 있지만 팀의 관측·장애 대응·비용 관리와 기능 제약 이해가 필요합니다. 관리형 경계 밖의 앱과 데이터 문제는 그대로 남습니다.</p><p><strong>판단:</strong> 직접 운영할 이유가 무엇인지와 맡겼을 때 잃는 제어·얻는 효율을 구체적으로 비교합니다. 익숙하다는 이유만으로 직접 운영하거나 유행한다는 이유만으로 이전하지 않습니다.</p></details>
<details><summary>Q. 아키텍처 리뷰에서 가장 먼저 가져갈 자료는 무엇인가요?</summary><p><strong>답변:</strong> 업무 목표, 데이터 흐름과 소유자, 핵심 의존성, 정상·피크 트래픽, 장애·복구 목표, 현재 지표가 필요합니다. 서비스 아이콘만 있는 그림은 왜 그런 선택을 했는지 보여주지 못합니다.</p><p><strong>실무 팁:</strong> 중요한 선택마다 가정·대안·선택 이유·재검토 조건을 남깁니다. 나중에 트래픽이 바뀌었을 때 과거 결정을 비난하기보다 어떤 가정이 달라졌는지 확인할 수 있습니다.</p></details>

## 직접 풀어 보기: 리뷰 결과를 실행 가능한 작업으로 만들기

설계 리뷰에서 “보안 강화, 가용성 개선, 비용 최적화가 필요하다”는 결론이 나왔습니다. 이대로는 다음 회의에서도 같은 이야기를 반복할 가능성이 큽니다. 입고 서비스의 실제 작업 세 개로 바꾸어 보세요.

<details><summary>해설 펼치기 — 판단 과정과 조건을 바꾼 경우</summary><p><strong>보안:</strong> 운영 사진 접근 role의 자원 범위를 확인하고 다른 업무 prefix 읽기가 거부되는 테스트를 추가합니다. 담당자·검토 기한·정상 및 거부 테스트 결과를 완료 증거로 둡니다.</p><p><strong>신뢰성:</strong> 지정한 백업에서 격리 환경으로 복원하고 핵심 주문·사진 참조를 검증하며 실제 복구 시간을 기록합니다. 백업 존재가 아니라 업무 복원 성공을 완료 기준으로 정합니다.</p><p><strong>비용:</strong> 성공한 고유 사진 처리 건수를 분모로 단위 비용을 계산하고 상위 사용량 항목 하나의 개선 실험을 수행합니다. 지연·오류 목표를 유지하는지 함께 봅니다.</p><p><strong>우선순위:</strong> 세 작업을 무조건 동시에 진행하지 않고 피해·발생 가능성·의존성·비용으로 순서를 합의합니다. 추상적인 원칙을 측정 가능한 작업으로 바꾸는 것이 리뷰의 실질적인 결과입니다.</p></details>
