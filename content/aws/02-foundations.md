## 1. 서버를 산다는 것과 빌린다는 것

물류센터를 직접 지으면 건물·전력·보안·장비를 먼저 마련해야 합니다. 임대한 센터를 쓰면 시작이 빠르지만 상품 배치와 출입 권한까지 임대인이 정해 주지는 않습니다. 클라우드는 컴퓨팅·스토리지·네트워크 자원을 API로 요청해 사용하는 방식입니다. 핵심은 남의 컴퓨터라는 사실보다 **필요할 때 프로비저닝하고 사용량에 맞춰 바꿀 수 있는 운영 방식**입니다.

고정 투자에서 사용 기반 지출로 이동하고, 공급자의 규모의 경제를 활용하며, 용량을 미리 과하게 추정하는 부담을 줄일 수 있습니다. 실험 환경을 빠르게 만들고 여러 지역으로 확장하기도 쉽습니다. 다만 켜 둔 자원·복제·데이터 전송·라이선스는 계속 비용을 만들 수 있습니다. 클라우드로 옮기기만 하면 저렴해진다는 보장은 없습니다.

## 2. 계정, 리전, AZ, 엣지는 서로 다른 경계

| 개념 | 쉬운 비유 | 실제 의미 |
|---|---|---|
| AWS 계정 | 회사별 장부와 출입증 체계 | 리소스 소유·권한·청구의 주요 경계 |
| 리전 | 서로 떨어진 도시의 사업장 | 지리적으로 구분된 서비스 운영 영역 |
| AZ | 한 도시 안의 독립 시설군 | 하나 이상의 데이터센터로 구성되는 장애 격리 영역 |
| 엣지 위치 | 고객 가까운 배송 거점 | 캐시·네트워크 접점을 제공하는 위치 |
| VPC | 설계한 사설 도로망 | 리전 범위의 논리적 네트워크 |
| 서브넷 | 특정 구역의 주소 블록 | 한 AZ에 속하는 IP 범위 |

AZ 하나가 곧 서버실 건물 하나라고 단정하면 안 됩니다. 중요한 것은 AWS가 전력·네트워크 등 장애 영향을 줄이도록 분리한 영역이라는 점입니다. 리전은 멀리 떨어져 있어 더 큰 범위의 장애 격리에 도움이 되지만 지연·복제 비용·일관성 문제가 커집니다. 엣지가 있다고 DB 전체가 모든 엣지로 자동 복제되는 것도 아닙니다.

## 3. 요청의 경로로 범위를 이해하기

서울 사용자가 DNS로 주소를 찾고 CloudFront에서 캐시된 이미지를 받으면 오리진까지 가지 않을 수 있습니다. 캐시가 없거나 동적 요청이면 지정한 오리진으로 전달됩니다. ALB가 서로 다른 AZ의 애플리케이션으로 요청을 분산하더라도, 세션이 한 서버 메모리에만 있으면 다른 서버가 같은 사용자의 상태를 모릅니다. 인프라를 여러 AZ에 놓는 것과 애플리케이션이 장애를 견디는 것은 별도 작업입니다.

멀티 리전도 “복사 버튼 하나”의 문제가 아닙니다. 애플리케이션 코드·설정·비밀·키·데이터·DNS·외부 허용 목록·서비스 할당량을 함께 준비해야 합니다. 복제 중인 데이터가 몇 초 뒤처질 수 있다면 장애 직전 쓰기를 잃을 수 있습니다. 이런 문제를 수치로 표현하는 도구가 RPO와 RTO이며 18편에서 자세히 다룹니다.

## 4. 확장성·탄력성·고가용성을 분리하기

확장성은 더 큰 부하를 처리하도록 용량을 늘릴 수 있는 성질입니다. 수직 확장은 더 큰 서버, 수평 확장은 더 많은 서버를 쓰는 방식입니다. 탄력성은 수요에 맞춰 늘렸다 줄이는 성질입니다. 고가용성은 장애가 있어도 서비스를 제공하는 성질입니다. 서버 100대가 있어도 단일 전원 장애에 모두 멈춘다면 고가용성이라고 보기 어렵습니다.

예를 들어 한 대가 안정적으로 초당 200건을 처리하고 평상시 부하가 초당 600건이면 단순 계산상 세 대가 필요합니다. 그러나 세 대 중 한 대가 죽으면 남은 용량은 400건입니다. 장애 시에도 600건을 유지하려면 여유 용량이나 빠른 확장·트래픽 제한이 필요합니다. 이 숫자는 AWS 성능 보장이 아니라 설계 계산 예시이며 실제 처리량은 부하 테스트로 정해야 합니다.

## 5. 공동 책임 모델: 관리형이어도 내 일이 남는다

AWS는 클라우드 자체의 물리 시설과 기반 인프라를 보호합니다. 고객은 자신이 선택한 서비스 수준에 따라 데이터·신원·권한·설정·애플리케이션을 책임집니다. EC2에서는 게스트 OS 패치와 애플리케이션 관리 책임이 큽니다. RDS에서는 기반 DB 운영의 많은 부분이 관리형이 되지만, 스키마·쿼리·DB 계정·접근 경로·백업 요구는 고객이 설계합니다. Lambda에서도 코드 취약점과 과도한 role 권한이 사라지지 않습니다.

IaaS는 가상 인프라, PaaS는 애플리케이션 실행 플랫폼, SaaS는 완성된 소프트웨어를 제공하는 방향으로 추상화 수준이 높아지는 분류입니다. 실제 AWS 서비스는 이 교과서 분류에 딱 하나씩 들어맞지 않을 수 있습니다. 따라서 분류 이름보다 “누가 무엇을 패치하고 복구하는가”를 묻는 것이 정확합니다. 퍼블릭 클라우드, 온프레미스, 하이브리드는 배포 위치와 연결 모델을 설명하며 위 책임 수준 분류와 다른 축입니다.

## 6. 가상 장애 사례와 설계 연습

두 애플리케이션 서버를 만들었는데 같은 AZ에 배치했습니다. AZ 장애로 둘 다 접근 불가가 되었습니다. 해결책은 단순히 세 번째 서버를 같은 AZ에 더 만드는 것이 아니라 장애 영역을 분리하는 것입니다. 이어 DB·NAT·파일 공유도 같은 장애 영역에 묶이지 않았는지 확인해야 합니다. Multi-AZ로 바꾼 후에는 한 AZ를 잃은 상태의 처리 용량까지 확인합니다.

직접 종이에 계정·리전·AZ를 큰 원부터 그리고 각 리소스를 넣어 보세요. VPC는 리전 범위, 서브넷과 EBS 볼륨은 AZ 범위라는 차이를 표시합니다. 서비스별 정확한 범위는 문서로 확인해야 하며 “관리형은 전부 리전 전체에 자동 복제된다”라고 일반화하면 안 됩니다.

## 깊이 읽기: 클라우드의 경계를 실제 주소와 장애로 이해하기

### 계정·리전·AZ·서브넷을 차례로 놓기

계정은 권한과 자원 소유를 나누는 기본 경계입니다. 리전은 지리적으로 구분된 서비스 제공 영역이고, AZ는 리전 안에서 장애 격리를 위해 나눈 위치 단위입니다. VPC는 내가 정의하는 가상 네트워크입니다. 하나의 VPC 안에 여러 AZ의 서브넷을 만들 수 있지만 하나의 서브넷은 하나의 AZ에 속합니다. 이 관계를 알면 “서브넷 두 개니까 AZ 장애에 안전하다”는 말이 왜 불충분한지 이해할 수 있습니다. 두 서브넷이 같은 AZ라면 같은 장애 범위에 묶일 수 있습니다.

학교에 비유하면 계정은 운영 주체, 리전은 도시, AZ는 서로 떨어진 교사동, VPC는 학교가 관리하는 통신 구역에 가깝습니다. 다만 실제 AWS의 경계는 물리 건물 도면 그대로가 아닙니다. 서비스별 복제 범위와 고객이 선택할 수 있는 설정은 공식 문서로 확인해야 합니다. “관리형”이라는 말만으로 모든 데이터가 다른 리전에 복제된다고 추론할 수 없습니다.

### 정상 요청이 성공하려면 몇 가지 조건이 동시에 필요할까

사용자가 도메인으로 API를 호출하면 DNS에서 주소를 찾고, 네트워크 연결을 만들고, 필요하면 TLS로 서버 인증과 암호화를 수행합니다. 로드 밸런서는 준비된 애플리케이션으로 요청을 전달합니다. 애플리케이션은 사용자 권한을 확인하고 DB에서 데이터를 읽거나 씁니다. 응답이 돌아오는 경로도 동작해야 사용자는 성공을 봅니다.

따라서 “EC2는 running인데 서비스가 안 된다”는 상황은 이상하지 않습니다. OS는 살아 있지만 프로그램이 시작 중일 수 있고, 프로그램은 정상이어도 DB 연결이 막혔을 수 있습니다. 헬스 체크가 단순히 프로세스 존재만 확인한다면 업무 실패를 놓칠 수도 있습니다. 반대로 모든 외부 의존성을 헬스 체크에 무조건 넣으면 일시적인 DB 문제로 정상 앱까지 한꺼번에 제외할 수 있습니다. 생존 여부와 실제 요청을 받을 준비 상태를 구분하는 이유입니다.

### 관리 영역과 실제 처리 영역

설정을 바꾸고 자원을 만드는 작업은 제어 영역(control plane)의 성격을 가집니다. 이미 구성된 자원으로 요청을 처리하는 작업은 데이터 영역(data plane)의 성격입니다. 예를 들어 서버 생성과 기존 서버가 웹 요청을 처리하는 것은 서로 다른 종류의 일입니다. 정확한 경계는 서비스별로 다르지만 이 구분은 복구 설계에 중요합니다.

장애가 난 뒤에만 인스턴스 생성·권한 생성·네트워크 변경을 시작한다면 그 관리 작업이 지연될 때 복구도 늦어집니다. 이미 준비한 용량으로 먼저 처리하고 이후 관리 기능으로 복구하는 설계는 의존성을 줄일 수 있습니다. 다만 미리 준비한 용량에는 비용이 듭니다. 가용성 설계가 비용 설계와 만나는 구체적인 지점입니다.

### 두 대와 두 배의 차이

가상 시스템의 서버 한 대가 안전하게 초당 100건을 처리한다고 합시다. 평소 초당 150건이 들어오고 두 AZ에 한 대씩 두면 합계 200건이므로 정상 상황에서는 여유가 있습니다. 하지만 한 AZ를 잃으면 100건만 처리할 수 있어 초당 50건이 밀립니다. 서버를 두 장소에 두었다는 사실만으로 장애 시 성능까지 보장하지는 못합니다.

세 대를 두면 항상 해결될까요? 두 대가 한 AZ, 한 대가 다른 AZ에 있다면 두 대가 있는 AZ를 잃는 경우를 다시 계산해야 합니다. 중요한 것은 총 대수보다 **어떤 장애 후에 얼마가 남는가**입니다. 이를 DB·NAT·캐시·외부 API까지 확장해서 계산합니다. 여기의 처리량은 설명용 가정이며 실제 용량은 부하 시험으로 구해야 합니다.

### 공동 책임을 업무 목록으로 바꾸기

| 선택 | AWS가 줄여 주는 부담의 예 | 고객에게 남는 일의 예 |
|---|---|---|
| EC2 | 물리 서버·가상화 기반 운영 | OS 패치, 앱 배포, 접근 권한, 데이터 보호 |
| 관리형 DB | 선택한 서비스 범위의 DB 운영 자동화 | 스키마·쿼리·사용자 권한·복구 요구 검증 |
| S3 | 객체 저장 인프라 운영 | 버킷 정책, 데이터 분류, 보존·삭제 정책 |
| Lambda | 실행 서버 용량 운영 | 코드, 의존성, 실행 권한, 중복 처리·timeout 설계 |

이 표는 세부 계약 전체가 아니라 책임을 생각하는 출발점입니다. 관리형 서비스에서도 사용자가 잘못된 데이터를 삭제하거나 과도한 권한을 부여하면 서비스가 업무 의도를 대신 판단하지 않습니다. 인프라 책임이 줄어든 만큼 데이터와 애플리케이션 계약을 더 명확히 해야 합니다.

## 더 깊은 면접 Q&A: 경계를 바꾸면 무엇이 달라지나

<details><summary>Q. 서버 두 대를 쓰는데 왜 단일 장애점이 남나요?</summary><p><strong>답변:</strong> 두 서버가 같은 DB·같은 AZ·같은 네트워크 출구·같은 외부 API에 의존하면 공통 의존성이 실패할 때 함께 멈출 수 있습니다. 서버만 두 대라는 설명 대신 의존성 그래프에서 어느 지점을 지우면 모든 요청 경로가 끊기는지 봅니다.</p><p><strong>꼬리 질문:</strong> 공통 지점을 모두 복제하는 것이 정답은 아닙니다. 중요도와 복구 목표에 따라 중복 구성, 임시 기능 제한, 대기열 보관 같은 대응을 선택합니다. 업무가 어느 수준으로 계속되어야 하는지 먼저 합의합니다.</p></details>
<details><summary>Q. 리전을 두 개 쓰면 가용성이 무조건 좋아지나요?</summary><p><strong>답변:</strong> 한 리전의 장애를 피할 선택지가 늘지만 데이터 복제·쓰기 충돌·DNS 전환·운영 복잡도도 늘어납니다. 두 리전이 하나의 인증 시스템이나 배포 실수에 함께 영향받으면 기대한 격리가 되지 않습니다.</p><p><strong>확인할 것:</strong> 어느 리전이 쓰기 권한을 갖는지, 복제 지연 중 무엇을 보여줄지, 전환과 원복을 어떻게 검증할지 설명해야 합니다. 복구 훈련 없이 지도 위에 리전 두 개만 표시하는 것은 가용성의 증거가 아닙니다.</p></details>
<details><summary>Q. Auto Scaling이 있으면 여유 용량이 필요 없나요?</summary><p><strong>답변:</strong> 확장 감지, 자원 준비, 프로그램 초기화, 트래픽 편입에 시간이 필요합니다. 그동안 기존 용량이 버티거나 큐가 부하를 흡수해야 합니다. 계정 할당량과 해당 위치의 실제 용량도 제한이 될 수 있습니다.</p><p><strong>예:</strong> 행사 시작 시각을 안다면 미리 용량을 준비할 수 있습니다. 갑작스러운 burst에는 최소 여유 용량과 유입 제한을 함께 고려합니다. 자동 확장은 반응 과정이지 무한한 자원이 즉시 생기는 약속이 아닙니다.</p></details>
<details><summary>Q. 인터넷으로 접속할 수 없는 서버라면 안전한 서버인가요?</summary><p><strong>답변:</strong> 공개 공격 표면이 줄어드는 것이지 모든 위험이 사라지지는 않습니다. 내부 서비스의 취약점, 탈취된 IAM 권한, 과도한 출구 통신, 잘못된 데이터 접근은 여전히 문제가 됩니다.</p><p><strong>설계 연결:</strong> 사설 네트워크, 최소 권한, 패치, 비밀정보 관리, 로그와 탐지를 서로 다른 방어 층으로 둡니다. “내부니까 신뢰한다”는 가정은 한 곳이 침해되었을 때 전체 피해 범위를 키웁니다.</p></details>

## 직접 풀어 보기: 한 AZ를 잃은 뒤의 용량

각 서버가 안전하게 초당 80건을 처리한다고 가정합니다. 두 AZ에 각각 두 대씩 있고 정상 유입은 초당 240건입니다. 총용량은 320건/초이므로 충분하다는 주장이 맞을까요? 장애 순간 자동 확장은 아직 완료되지 않았다고 가정합니다.

<details><summary>해설 펼치기 — 판단 과정과 조건을 바꾼 경우</summary><p><strong>정상 상황:</strong> 네 대의 합계는 320건/초로 입력 240건/초보다 큽니다. 단순 모델에서는 정상 부하를 처리합니다. 하지만 이것은 AZ 장애 후의 검증이 아닙니다.</p><p><strong>장애 상황:</strong> 한 AZ를 잃으면 두 대, 즉 160건/초만 남습니다. 입력이 유지되면 초당 80건의 부족이 생기고 1분에 4,800건이 추가 대기하거나 실패할 수 있습니다. 큐가 있으면 기다릴 수는 있지만 즉시 완료되지는 않습니다.</p><p><strong>대안 비교:</strong> 남은 AZ에 미리 여유를 두거나, 빠르게 확장할 수 있는 준비와 대기 허용을 조합하거나, 비핵심 입력을 제한할 수 있습니다. 어느 선택이 맞는지는 완료 시간·비용·거절 가능성에 달렸습니다.</p><p><strong>추가 확인:</strong> 앱 용량이 남아도 DB·캐시·네트워크 출구가 장애 AZ에만 있으면 전체 경로가 끊깁니다. 서버 계산을 끝낸 뒤 같은 질문을 모든 필수 의존성에 반복해야 합니다.</p></details>
