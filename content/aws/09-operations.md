## 1. 계기판, 출입 기록, 설비 장부

자동차 계기판은 현재 속도와 온도를 보여 줍니다. 출입 기록은 누가 차고에 들어왔는지 알려 주고, 정비 장부는 부품이 어떻게 바뀌었는지 남깁니다. CloudWatch는 지표·로그·알람 등 관찰성, CloudTrail은 API 활동과 감사, Config는 리소스 구성과 규정 준수 평가라는 출발점으로 구분할 수 있습니다. 실제 기능은 일부 겹치지만 장애 조사에서 던지는 질문이 다릅니다.

## 2. 지표·로그·추적을 한 요청으로 묶기

지표는 시간에 따른 숫자입니다. 초당 요청 수·오류율·p99 지연·큐 대기 시간 같은 값을 집계해 이상을 빨리 찾습니다. 로그는 사건의 구체적 맥락입니다. 어떤 주문과 오류 코드가 실패했는지 확인합니다. trace는 여러 서비스에 걸친 요청 구간을 연결합니다. 전체 2초 중 DB 1.8초, 외부 API 0.1초였다는 식으로 시간을 나눕니다.

평균 지연이 낮아도 일부 요청이 매우 느릴 수 있습니다. 창고 A는 정상인데 창고 B만 실패하면 전체 평균 오류율은 낮게 보일 수 있습니다. 업무적으로 중요한 차원으로 지표를 나누되 주문 ID처럼 무한히 증가하는 값을 지표 차원으로 넣으면 cardinality와 비용이 커집니다. 개별 ID는 로그·trace에 두고 지표는 제한된 차원으로 설계합니다.

## 3. CloudWatch 알람은 평가 규칙이다

알람은 지표 한 번을 보는 버튼이 아니라 기간·평가 횟수·임계값·누락 데이터 처리로 상태를 판단합니다. “5분 평균 CPU 80%”는 10초 동안의 심한 지연을 놓칠 수 있습니다. 반대로 단일 순간 값만 보면 잡음에 자주 울립니다. 요청량이 적어 데이터가 없는 시간과 수집 장애로 데이터가 없는 시간을 구분해야 합니다.

EC2 기본 지표만으로 애플리케이션의 메모리·디스크 내부 사용량·업무 성공률이 모두 보이는 것은 아닙니다. 에이전트나 사용자 지표·로그 계측이 필요할 수 있습니다. 알람에는 담당자·영향·확인 명령·안전한 조치·복구 기준을 연결합니다. 자동 대응은 오탐 때도 안전하고 반복 실행 가능해야 합니다. 알람을 많이 만드는 것보다 행동 가능한 알람을 만드는 것이 중요합니다.

## 4. CloudTrail과 Config로 변경을 추적하기

장애 시작 직전에 보안 그룹이 바뀌었다면 CloudTrail로 누가 어떤 API를 호출했는지 찾고 Config로 이전과 현재 설정을 비교할 수 있습니다. CloudTrail의 관리 이벤트와 데이터 이벤트는 범위와 수집 설정이 다릅니다. 기본 이벤트 이력만 켜 두었다고 모든 S3 객체 읽기나 모든 애플리케이션 행동이 기록된다고 가정하지 않습니다. 장기 보관·조직 통합·데이터 이벤트는 요구에 맞게 구성해야 합니다.

Config rule이 비준수라고 평가했다고 자동으로 리소스가 수정되는 것은 아닙니다. 별도의 remediation을 연결하고 그 조치의 위험을 검토합니다. 예를 들어 공개 보안 그룹을 자동 제거할 때 정상 서비스 입구를 차단할 수 있으므로 소유자·예외·되돌리기 경로가 필요합니다. 규정 준수 평가와 실제 보안 사고 탐지는 다른 질문입니다.

## 5. CloudFormation과 Systems Manager

CloudFormation은 원하는 리소스 구성을 코드로 정의하고 stack 단위로 생성·변경합니다. 사람이 콘솔에서 수정한 상태가 코드와 어긋나는 drift를 확인하고, 변경 내용을 검토한 뒤 배포합니다. stack rollback이 발생해도 이미 외부로 보낸 메일이나 애플리케이션이 변경한 데이터까지 되돌려 준다는 뜻은 아닙니다.

Systems Manager는 인벤토리·명령 실행·패치·자동화·세션 관리 등의 운영 작업에 활용합니다. SSH 키와 공개 포트를 줄이는 데 도움을 줄 수 있지만 agent·IAM·서비스 endpoint 연결이 필요합니다. “SSM이 있으니 네트워크가 필요 없다”는 오해는 피합니다. Launch Wizard는 지원 워크로드 배포 안내, Service Catalog는 승인된 제품 배포, License Manager는 라이선스 관리라는 위치로 구분합니다.

## 6. Organizations와 Control Tower

Organizations는 계정 묶음과 OU·정책·통합 청구의 기반입니다. 개발·운영·로그 보관을 계정으로 분리하면 실수의 영향과 권한 경계를 줄일 수 있습니다. SCP는 멤버 계정 권한의 상한을 제한하는 가드레일이며 IAM Allow를 대신하지 않습니다. 관리 계정과 서비스 연결 role 등에는 별도의 적용 범위가 있으므로 “조직 안의 모든 주체에 같은 방식으로 적용된다”고 단정하지 않습니다.

Control Tower는 멀티계정 환경의 landing zone과 통제를 구성·운영하는 데 도움을 줍니다. Organizations와 경쟁하는 완전히 다른 계정 체계라기보다 관련 서비스를 조합하는 관리 계층으로 이해합니다. AWS Health는 AWS 서비스 이벤트와 계정 영향, Trusted Advisor는 모범 사례 관점의 점검, Compute Optimizer는 사용 지표에 기반한 자원 권장이라는 서로 다른 역할입니다.

## 7. 나머지 운영 도구와 제품 상태

Managed Service for Prometheus는 메트릭 수집·조회 생태계, Managed Grafana는 대시보드와 시각화라는 관계로 봅니다. Amazon Q Developer in chat applications는 채팅 환경의 운영 상호작용, User Notifications는 알림 관리, Console Mobile Application은 모바일 관리 접근, Well-Architected Tool은 설계 검토 기록을 지원합니다. AWS Auto Scaling이라는 여러 자원 확장 관리와 EC2 Auto Scaling Group의 구체적인 인스턴스 관리를 구분하세요.

원문의 OpsWorks는 2024-05-01, Proton은 2026-10-07 지원 종료가 공지되어 있습니다. 따라서 이 둘은 과거 구성 관리·템플릿 기반 배포의 사례로 설명하며 현재 신규 도입 대상으로 추천하지 않습니다. [OpsWorks 종료 목록](https://docs.aws.amazon.com/general/latest/gr/full_shutdown_services.html) · [Proton 종료 공지](https://docs.aws.amazon.com/proton/latest/userguide/proton-end-of-support.html) 도구 이름을 외우는 것보다 승인된 변경을 재현하고 되돌릴 수 있는지가 중요합니다.

## 8. 가상 장애 조사 순서

10:02부터 오류가 늘었다고 가정합니다. CloudWatch에서 어느 endpoint·AZ·버전의 오류인지 좁히고, trace로 DB 접속 단계가 실패하는지 확인합니다. 로그에서는 AccessDenied인지 timeout인지 구분합니다. CloudTrail에서 10:00의 정책 변경을 찾고 Config의 차이를 확인합니다. 원인을 확인하기 전 모든 인스턴스를 재시작하면 증거를 잃거나 문제를 확산할 수 있습니다. 변경과 증상은 상관관계이며 최종 원인은 재현·되돌림·설정 검증으로 확인합니다.

실습으로 가상의 장애 타임라인을 작성해 보세요. 시각, 사용자 영향, 관찰한 증거, 가설, 실행한 조치, 결과를 열로 분리하면 추측을 사실처럼 기록하는 실수를 줄일 수 있습니다.

## 깊이 읽기: 알람이 울린 뒤 사람이 실제로 움직일 수 있게 만들기

### 지표·로그·추적은 세 종류의 질문에 답한다

식당의 평균 대기 시간이 늘었다는 계기판은 지표입니다. 어느 손님이 무엇을 주문했고 어떤 오류가 났는지 적은 기록은 로그입니다. 주문 접수부터 조리·포장·배달까지 걸린 시간을 연결한 것은 분산 추적에 가깝습니다. 지표로 이상을 찾고 추적으로 느린 구간을 좁힌 다음 로그로 상세 원인을 확인하면 서로 보완됩니다.

입고 API의 p99가 높아졌다고 합시다. 평균 CPU는 정상입니다. trace를 보니 전체 3초 중 2.7초가 외부 상품 API 대기였습니다. 같은 trace ID로 로그를 찾으면 재시도 두 번과 연결 timeout을 확인할 수 있습니다. 이때 API 서버를 늘리는 것보다 외부 의존성의 제한·timeout·재시도를 조정하는 것이 먼저일 수 있습니다. 관측성은 자료를 많이 저장하는 일보다 질문에 맞는 증거를 연결하는 일입니다.

### 평균에 숨는 사용자와 지표 집계의 함정

100건 중 99건이 10ms, 1건이 10초라고 가정하면 평균은 약 110ms입니다. 평균만 보면 괜찮아 보이지만 한 사용자는 10초를 기다렸습니다. p95·p99 같은 분위수와 오류율·처리량을 함께 보는 이유입니다. 단, 각 서버의 p99를 단순 평균하여 전체 서비스의 p99라고 부르면 정확하지 않습니다. 분포를 어떻게 집계했는지 확인해야 합니다.

비율도 분모가 중요합니다. 1분 동안 요청 1건 중 1건 실패는 100%이고, 100만 건 중 100건 실패는 0.01%입니다. 비율만 보면 첫 상황이 더 심각해 보이지만 업무 영향은 다릅니다. 낮은 트래픽의 비율 변동과 실제 실패 수를 함께 고려하고, 무응답·트래픽 소실도 별도로 감지합니다.

### 알람의 기간과 누락 데이터

“최근 세 구간 중 두 구간이 임계값을 넘으면 알림” 같은 M-out-of-N 설정은 순간 튐에 모두 반응하지 않게 도와줍니다. 대신 감지 시간이 늘 수 있습니다. 한 구간이 1분인지 5분인지에 따라 같은 숫자라도 대응 시점이 달라집니다. 사용한 통계가 Average인지 Maximum인지도 의미를 바꿉니다.

누락 데이터를 정상으로 취급하면 수집기가 죽었을 때 서비스도 정상으로 보일 수 있습니다. 반대로 이벤트가 있을 때만 값을 내는 지표의 누락을 모두 장애로 보면 불필요한 알람이 생깁니다. 지표가 “아무 일도 없으면 0을 보냄”인지 “문제 때만 값을 보냄”인지 먼저 정합니다. 알람을 만든 뒤 실제 실패와 수집 중단을 각각 가정해 상태 전이를 확인해야 합니다.

### 변경 기록과 현재 설정을 연결하기

CloudTrail로 누가 어떤 관리 API를 호출했는지 추적하고 Config로 지원되는 자원의 구성 상태와 변경을 검토할 수 있습니다. 둘 다 모든 애플리케이션 업무 로그를 자동 대체하지는 않습니다. S3 객체 접근 같은 data event는 필요한 기록 범위와 비용을 별도로 설계해야 할 수 있습니다. “CloudTrail을 켰다”는 말 대신 어떤 이벤트를 어느 계정·리전에서 얼마나 보관하는지 명시합니다.

IaC도 현재 상태가 코드와 영원히 같음을 보장하지 않습니다. 콘솔에서 긴급 변경을 했다면 코드로 반영하거나 의도된 상태로 되돌려야 합니다. Drift 탐지는 지원 범위 내 차이를 찾는 도구이며 모든 업무 의미를 판단하지 않습니다. 배포 실패 시 rollback이 데이터 변경까지 완벽히 되돌리는지도 별도로 검토합니다.

## 더 깊은 면접 Q&A: 관측과 자동화의 한계

<details><summary>Q. 로그를 전부 저장하면 장애 분석이 쉬워지나요?</summary><p><strong>답변:</strong> 관련 요청을 연결할 식별자와 구조가 없으면 양만 늘 수 있습니다. 개인정보·secret 유출, 저장·검색 비용, 중요한 로그가 묻히는 문제도 생깁니다. 요청 ID, 업무 ID, 오류 유형, 처리 단계와 시간을 구조화하고 필요한 수준을 선택합니다.</p><p><strong>꼬리 질문:</strong> 성공 로그를 줄이더라도 정상 흐름의 기준을 잃지 않도록 지표나 표본 추적을 남깁니다. 보관 기간과 접근 권한도 데이터의 성질에 맞춰 정합니다.</p></details>
<details><summary>Q. CPU 알람과 사용자 오류율 알람 중 무엇이 중요한가요?</summary><p><strong>답변:</strong> 사용자 영향과 직접 연결되는 오류율·지연은 서비스 상태 판단에 중요하고 CPU는 원인 조사와 용량 예측에 도움이 됩니다. CPU가 높아도 요구를 만족할 수 있고 CPU가 낮아도 외부 대기로 서비스가 실패할 수 있습니다.</p><p><strong>설계:</strong> 사용자 영향 알람에서 대응을 시작하고 자원 지표로 원인을 좁히는 구성을 고려합니다. 특정 자원이 포화되기 전에 예방해야 한다면 자원 임계값 알람도 별도로 둡니다.</p></details>
<details><summary>Q. 자동 복구는 언제 실행하면 되나요?</summary><p><strong>답변:</strong> 증상이 명확하고 조치가 제한적이며 반복 실행해도 안전하고 결과를 검증할 수 있을 때 적합합니다. 원인이 불명확한 모든 장애에 전체 재시작을 연결하면 증거를 지우거나 부하를 더 키울 수 있습니다.</p><p><strong>안전장치:</strong> 적용 대상·최대 횟수·대기 시간·실패 시 중단·사람에게 넘기는 조건을 정합니다. 자동화의 성공 로그보다 실제 업무가 회복됐는지 확인하는 단계가 필요합니다.</p></details>
<details><summary>Q. 배포 직후 오류가 늘면 무조건 롤백하나요?</summary><p><strong>답변:</strong> 변경과 오류의 상관을 확인하고 롤백이 안전한지 판단합니다. 데이터 스키마나 메시지 형식이 호환되지 않게 바뀌었다면 코드만 과거로 돌리는 것이 더 위험할 수 있습니다.</p><p><strong>예방:</strong> 이전·새 버전이 공존할 수 있는 변경 순서를 준비하고 작은 범위부터 배포합니다. 롤백 가능성은 사고 때 만드는 기능이 아니라 배포 설계의 일부입니다.</p></details>

## 직접 풀어 보기: 알람은 조용한데 주문이 들어오지 않는다

서버 CPU와 오류 로그는 모두 정상처럼 보입니다. 그런데 15분 동안 성공 주문이 0건입니다. 정상적으로 트래픽이 없는 시간인지 요청 경로가 끊긴 것인지 구분하려면 무엇을 봐야 할까요?

<details><summary>해설 펼치기 — 판단 과정과 조건을 바꾼 경우</summary><p><strong>분모 확인:</strong> 요청이 아예 도착하지 않으면 오류율도 0처럼 보일 수 있습니다. 외부 진입점의 요청 수, DNS·인증·프런트엔드 오류, 앱 도달 수와 업무 완료 수를 순서대로 비교합니다.</p><p><strong>관측 경로 확인:</strong> 지표 수집 자체가 중단되지 않았는지도 봅니다. 누락 데이터를 정상으로 처리하는 설정이면 수집기 장애를 숨길 수 있습니다. 마지막 수집 시각과 다른 독립 신호를 대조합니다.</p><p><strong>기준선:</strong> 같은 요일·시간의 평소 트래픽과 예정된 작업을 확인합니다. 모든 무트래픽을 장애로 알리면 피로가 커지므로 업무 시간과 최소 기대 요청량을 고려합니다.</p><p><strong>개선:</strong> 자원 상태 알람 외에 핵심 사용자 경로의 synthetic check 또는 업무 완료 지표를 검토합니다. 실제 거래를 만드는 검사라면 테스트 데이터와 부수 효과를 안전하게 분리해야 합니다.</p></details>
