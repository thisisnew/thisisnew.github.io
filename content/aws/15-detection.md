## 1. CCTV를 설치한 것과 사건을 찾는 것은 다르다

센터에 CCTV가 있어도 저장 장치가 꺼져 있거나 녹화 영상을 아무도 확인하지 않으면 도움이 되지 않습니다. 보안 로그도 생성·수집·보존·검색·분석·대응이 이어져야 합니다. 원문의 SEC 4는 이벤트를 어떻게 찾고 조사할지, SEC 5는 네트워크를 어떻게 보호할지, SEC 6은 실행 환경을 어떻게 보호할지 묻습니다.

탐지 결과는 사실의 단서이지 모든 경우에 확정된 침해 판정은 아닙니다. “이상한 위치에서 로그인”이라는 결과에 계정 소유자·배포 일정·허용된 VPN·접근한 데이터 정보를 더해 판단합니다. 오탐을 줄이겠다고 로그를 꺼 버리는 대신 규칙과 맥락을 개선합니다.

## 2. SEC 4: 생성→중앙화→상관분석→조치

CloudTrail·VPC Flow Logs·DNS 로그·WAF 로그·앱 인증 로그 등은 서로 다른 층의 사건을 보여 줍니다. Flow Logs는 트래픽 메타데이터이지 모든 패킷 본문의 녹화가 아닙니다. 애플리케이션은 로그인 결과·권한 거부·중요 데이터 변경 같은 업무 이벤트를 별도로 남겨야 합니다. 비밀번호·토큰·개인정보를 그대로 로깅하면 보안 로그가 새로운 유출원이 됩니다.

중앙 로그 계정과 표준 형식은 여러 계정의 사건을 같은 시간축에서 찾게 합니다. 시간 동기화·주체 ID·요청 ID·리소스 ARN·보존 기간·접근 권한이 중요합니다. 업무 계정이 침해되어도 중앙 로그를 마음대로 지우지 못하도록 권한 경계를 설계합니다. 수집 파이프라인 자체가 중단되었음을 알 수 있는 지표도 필요합니다.

보안 결과는 위협·취약점·구성 위반 등 종류가 다릅니다. GuardDuty의 의심 활동, Inspector의 취약점, Config의 비준수 상태를 같은 의미로 취급하지 않습니다. Security Hub 등의 결과를 자산 중요도·공개 여부·데이터 민감도와 연결해 우선순위를 정합니다. 인터넷에 공개된 운영 서버의 악용 가능한 취약점은 고립된 테스트 자원의 낮은 영향 문제보다 먼저 처리할 수 있습니다.

SEC04-BP01~04는 로깅, 표준 위치에 수집, 알림의 맥락 보강, 비준수 조치 시작을 포함합니다. 자동 수정은 검증된 조건에서만 실행하고 예외·실패·되돌림을 기록합니다. 잘못된 자동 방화벽 변경이 서비스 전체를 끊는다면 방어가 새 장애 원인이 됩니다.

## 3. SEC 5: 네트워크 계층과 트래픽 흐름

외부 진입 계층·앱 계층·데이터 계층을 구분하고 필요한 흐름만 허용합니다. 보안 그룹은 앱 role이 할 수 있는 AWS API 권한과 다르며, 사설 IP는 사용자 인증이 아닙니다. “같은 VPC라서 신뢰”하는 대신 출발·도착·프로토콜·포트·목적을 정의합니다. outbound도 관리하지 않으면 침해된 서버가 데이터를 외부로 보내는 길이 열릴 수 있습니다.

검사 기반 보호에는 WAF·Network Firewall·지원되는 네트워크 어플라이언스 등이 있습니다. 라우팅이 검사 경로를 지나야 규칙이 적용됩니다. 장비를 배치했지만 return path가 다른 비대칭 경로라면 상태 추적과 통신에 문제가 생길 수 있습니다. TLS로 암호화된 통신에서 무엇을 관찰할 수 있는지, 검사하려면 어떤 추가 신뢰와 비용이 필요한지도 따져야 합니다.

SEC05-BP01~04는 네트워크 계층 생성, 흐름 제어, 검사 보호, 자동화를 다룹니다. IaC로 기준 구성을 배포하고 drift를 확인하면 사람마다 다른 방화벽 규칙이 쌓이는 문제를 줄일 수 있습니다. 중앙 방화벽도 모든 워크로드가 의존하는 단일 장애점이 되지 않도록 용량·AZ·경로를 설계합니다.

## 4. SEC 6: 이미지·패치·접근·무결성

실행 서버에 SSH로 들어가 수동 수정하면 어떤 상태가 정답인지 알기 어려워집니다. 검증된 이미지에서 배포하고 변경을 파이프라인에 남기는 방식은 재현과 복구를 쉽게 만듭니다. 이미지 강화는 불필요한 패키지·서비스·권한을 줄이고 기본 설정을 맞추는 작업입니다. Image Builder·ECR 스캔·Inspector 등은 각자의 지원 범위에서 활용할 수 있습니다.

취약점 관리는 발견→우선순위→수정→배포→재검증의 순환입니다. 심각도 점수만으로 끝내지 말고 실제 노출·악용 가능성·데이터 영향·보완 통제를 함께 봅니다. 오래된 취약 이미지가 다시 배포되지 않도록 이미지 사용 정책과 수명주기도 관리합니다. 패치가 새 장애를 만들 가능성은 테스트와 점진 배포로 줄입니다.

소프트웨어 무결성은 내가 검증한 빌드가 실제 배포되었는지 확인하는 문제입니다. 태그 이름만 같다고 이미지 내용이 같지는 않을 수 있습니다. digest 고정·서명·검증·의존성 출처 관리를 검토합니다. 서명된 악성 코드도 가능하므로 서명은 출처와 변조 여부의 증거이지 코드가 안전하다는 절대 보장이 아닙니다.

SEC06-BP01~05는 취약점 관리, 강화 이미지, 수동 접근 감소, 무결성 검증, 보호 자동화를 묶습니다. Session Manager 같은 접근 방식으로 공개 SSH와 개인 키 관리를 줄일 수 있지만 세션 권한·기록·네트워크 연결·긴급 접근을 함께 설계해야 합니다.

## 5. 가상 공격 경로를 끊어 보기

취약한 웹 앱이 원격 코드 실행에 노출되었다고 가정합시다. 1단계는 코드·의존성 패치와 WAF 보완 통제로 진입 위험을 줄이는 것입니다. 2단계는 앱 role의 권한을 좁혀 접근 가능한 데이터를 제한하는 것입니다. 3단계는 outbound·네트워크 분리로 옆 시스템 이동을 제한합니다. 4단계는 위협 탐지와 로그로 발견하고 격리합니다. 하나의 통제가 실패해도 다음 계층이 피해를 줄이는 구조입니다.

격리 전에 증거를 보존해야 하는 경우가 있습니다. 인스턴스를 즉시 종료하면 휘발성 증거가 사라질 수 있습니다. 반대로 계속 열어 두면 피해가 확대됩니다. 사전 플레이북에서 격리·증거·업무 지속의 우선순위를 정하고 사고 대응 팀과 합의해야 합니다.

## 6. 검증 연습과 운영 증거

비운영 환경에서 공개 포트 변경 같은 통제된 이벤트를 계획하고, 변경 로그가 생성되는지, 중앙 계정에 도착하는지, 경보가 담당자에게 전달되는지, 조치가 기록되는지 확인하는 훈련을 설계해 보세요. 실제 공격을 만들어 운영망에 실행하는 것이 목적이 아닙니다. 한 단계라도 끊기면 “보안 도구가 켜져 있다”는 상태와 실제 탐지 능력의 차이가 드러납니다.

| 검증 대상 | 질문 | 증거 |
|---|---|---|
| 로그 | 필요한 사건을 기록하는가 | 샘플 이벤트·도착 시간 |
| 경보 | 올바른 팀이 행동하는가 | 수신·확인·조치 기록 |
| 네트워크 | 허용·차단 경로가 의도와 같은가 | 연결 테스트·flow 기록 |
| 이미지 | 검증한 결과물만 배포되는가 | digest·서명·배포 이력 |
| 패치 | 수정이 실제 실행 자원에 반영됐나 | 배포 후 재스캔 |

## 깊이 읽기: 탐지 신호를 사건으로, 사건을 제한된 조치로 바꾸기

### 침입 한 번을 여러 층에서 관찰하기

공격자가 취약한 웹 기능을 이용해 서버에서 명령을 실행했다고 가정합니다. 웹 요청 계층에는 비정상 경로·페이로드가 남을 수 있고, 호스트에는 예상하지 않은 프로세스가 나타날 수 있으며, 네트워크에는 평소와 다른 목적지 통신이 보일 수 있습니다. 탈취한 role로 API를 호출하면 CloudTrail 등의 감사 흔적이 관련될 수 있습니다. 하나의 도구가 모든 단서를 완벽하게 보여준다고 가정하지 않습니다.

성의 정문, 복도, 금고에 각각 다른 센서를 두는 비유가 맞습니다. 정문 센서가 조용해도 이미 안에 들어온 사람이 금고를 열 수 있습니다. 그래서 WAF·네트워크 제어·호스트 관리·IAM 최소 권한·로그 분석이 함께 필요합니다. 방어 층이 많다는 사실보다 각 층이 독립적인 위험을 줄이는지 봅니다.

### Finding은 판정의 시작이다

탐지 결과에는 자원, 시간, 계정, 유형과 심각도 같은 정보가 들어갑니다. 이것을 업무 맥락과 연결해야 합니다. 야간 대량 S3 조회가 예정된 백업 작업인지 탈취된 계정의 반출인지 판단하려면 담당자·변경 일정·평소 사용 패턴을 확인합니다. 심각도가 높다는 이유만으로 운영 DB를 즉시 끄는 자동화는 더 큰 장애를 만들 수 있습니다.

기본 흐름은 수집 → 중복 묶기 → 맥락 추가 → 우선순위 → 제한된 완화 → 증거 보존 → 확인과 종료입니다. Findings가 많아지면 같은 원인의 중복 경보를 묶고 영향 범위로 우선순위를 정합니다. 경보 수를 줄이기 위해 광범위하게 무시 규칙을 만들면 새 공격도 숨길 수 있으므로 예외의 이유와 만료를 관리합니다.

### 로그를 중앙화하는 이유와 보호해야 할 것

침해된 서버의 로컬 로그만 믿으면 공격자가 지우거나 서버 종료로 사라질 수 있습니다. 다른 보안 경계로 로그를 전달하면 증거 보존에 도움이 됩니다. 중앙화된 저장소도 읽기·쓰기·삭제 권한, 보존 정책, 암호화 키, 시간 정합성을 보호해야 합니다. 모든 운영자가 모든 보안 로그를 삭제할 수 있으면 중앙화의 이점이 줄어듭니다.

시간대와 시계 차이는 사건 순서를 헷갈리게 합니다. 애플리케이션 로그와 AWS 감사 기록을 비교할 때 UTC·현지 시간, event time·수집 시간을 구분합니다. 동일 요청 ID나 principal·resource·IP 같은 연결 단서도 남깁니다. 수집에 실패했을 때 그 실패 자체를 알 수 있어야 “로그가 없으니 사건도 없다”는 오판을 줄입니다.

### 패치와 이미지 갱신의 실제 수명주기

취약점 목록을 받는 것만으로 취약점이 제거되지는 않습니다. 영향받는 버전 확인, 악용 가능성과 노출 범위 판단, 수정 이미지 생성, 테스트, 점진 배포, 이전 버전 제거까지 이어져야 합니다. 실행 중인 컨테이너를 수동으로 고쳐도 다음 배포가 옛 이미지에서 시작하면 취약점이 되살아납니다. 이미지와 배포 명세를 함께 갱신하는 이유입니다.

긴급 패치를 바로 적용하기 어려우면 임시 네트워크 제한·기능 비활성화 같은 완화를 검토할 수 있습니다. 단, 임시 조치를 영구 해결로 착각하지 않도록 담당자와 만료일을 둡니다. 취약점의 점수만이 아니라 인터넷 노출, 실제 사용 기능, 데이터 민감도, 대체 통제를 함께 보아야 합니다.

### 격리할 때도 증거와 업무를 고려하기

격리는 공격 확산을 줄이는 목적입니다. 하지만 프로세스 종료·디스크 삭제·인스턴스 교체는 휘발성 증거를 잃게 할 수 있습니다. 반대로 증거 수집을 기다리는 동안 피해가 커질 수도 있습니다. 사전에 사고 유형별 우선순위와 승인·실행 절차를 정해야 합니다. 아래 항목은 개념적 검토표이며 실제 환경에서는 조직의 대응 절차를 따릅니다.

| 질문 | 판단 목적 |
|---|---|
| 공격이 진행 중인가? | 확산 차단의 긴급성 |
| 어느 계정·role·자원이 영향받았나? | 조치 범위 제한 |
| 로그와 스냅샷을 어디에 보관할까? | 증거 보호 |
| 격리 후 업무가 어디로 이동하나? | 서비스 연속성 |
| 원본으로 재배포해도 원인이 남나? | 재침해 방지 |

## 더 깊은 면접 Q&A: 탐지 도구를 켠 뒤 해야 할 일

<details><summary>Q. GuardDuty를 켜면 공격을 자동 차단하나요?</summary><p><strong>답변:</strong> 탐지 결과를 얻는 것과 차단 조치를 실행하는 것은 별도 흐름입니다. 필요한 자동화·알림·운영 절차를 구성하고 탐지 유형별 오탐과 영향 범위를 평가합니다. 서비스 기능을 포괄적인 예방 방화벽처럼 설명하면 안 됩니다.</p><p><strong>꼬리 질문:</strong> 자동 차단은 복구 가능한 제한 조치부터 시작할 수 있습니다. 조치 성공 후에도 공격자의 다른 권한이나 자원 변경이 남았는지 조사해야 합니다.</p></details>
<details><summary>Q. VPC Flow Logs로 요청 본문까지 볼 수 있나요?</summary><p><strong>답변:</strong> 네트워크 흐름의 메타데이터를 보는 도구이며 애플리케이션 요청 본문을 그대로 복원하는 로그로 취급하면 안 됩니다. HTTP 경로·상태·업무 오류는 해당 계층의 로그나 추적을 함께 사용합니다.</p><p><strong>조사:</strong> 허용·거부, 출발지·목적지·포트와 시간으로 통신 여부를 좁힌 뒤 LB와 앱 기록을 연결합니다. 한 로그 소스에 모든 진단 정보를 기대하지 않습니다.</p></details>
<details><summary>Q. 보안 그룹에서 차단하면 침해 대응은 끝난 건가요?</summary><p><strong>답변:</strong> 통신 경로 일부를 제한한 것입니다. 이미 탈취된 자격증명, 수정된 정책, 다른 자원에 심어진 변경, 반출된 데이터는 남을 수 있습니다. 네트워크 격리와 identity 대응·데이터 영향 조사를 함께 수행합니다.</p><p><strong>복구:</strong> 신뢰할 수 있는 배포물에서 재구성하고 원인이 된 취약점이나 권한을 수정합니다. 단순 재시작으로 공격 전 상태가 자동 복원된다고 가정하지 않습니다.</p></details>
<details><summary>Q. 탐지 규칙이 너무 많이 울리면 임계값만 높이면 되나요?</summary><p><strong>답변:</strong> 정상 활동과 실제 위험을 구분할 맥락이 부족한지 먼저 봅니다. 자원 중요도·업무 시간·승인된 작업·주체를 반영하고 중복 경보를 묶을 수 있습니다. 임계값 상승만으로 조용하게 만들면 작은 유출을 놓칠 수 있습니다.</p><p><strong>검증:</strong> 규칙 변경 전후에 놓친 사건과 대응 가능한 경보 비율을 확인합니다. 알람이 적다는 사실보다 중요한 사건을 제때 처리하는지가 목표입니다.</p></details>

## 직접 풀어 보기: 야간 대량 다운로드 경보

새벽에 특정 role이 평소보다 많은 S3 객체를 읽었다는 경보가 발생했습니다. 예정된 백업인지 정보 반출인지 아직 모릅니다. 탐지 결과만 보고 모든 운영 접근을 막는 대신 어떤 확인과 조치를 연결할까요?

<details><summary>해설 펼치기 — 판단 과정과 조건을 바꾼 경우</summary><p><strong>맥락:</strong> role의 소유자, 예정된 작업, 사용 위치와 시간, 읽은 객체 범위, 최근 권한 변경을 확인합니다. 정상 백업과 다른 목적지·데이터 범위가 있는지 비교합니다.</p><p><strong>피해 제한:</strong> 실제 유출 가능성과 진행 여부에 따라 해당 주체·세션·자원 범위에 제한된 대응을 검토합니다. 광범위한 차단은 정상 복구나 업무도 막을 수 있으므로 영향과 긴급성을 함께 판단합니다.</p><p><strong>증거:</strong> 관련 로그와 정책 변경 이력을 별도 보호하고, 경보의 시간과 실제 이벤트 시간을 맞춥니다. 조사 중 원본 기록을 임의로 지우지 않습니다.</p><p><strong>종료:</strong> 정상 작업이면 이유와 예외 범위를 기록하고, 비정상이면 자격증명·추가 권한·데이터 영향까지 조사합니다. 경보를 닫는 것과 사고를 해결하는 것은 다른 상태입니다.</p></details>
