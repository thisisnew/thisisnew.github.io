## 1. 이사는 트럭을 부르는 것으로 끝나지 않는다

물류센터를 이전할 때 선반만 옮기면 운영할 수 있을까요? 재고 장부·전력·통신·거래처 주소·업무 시간·출입 권한도 바꿔야 합니다. 클라우드 마이그레이션도 파일 복사만의 문제가 아닙니다. **어떤 단위로 옮길지, 이전 중 변경은 어떻게 따라잡을지, 언제 새 시스템으로 전환할지, 실패하면 어떻게 돌아갈지**를 정해야 합니다.

서버 전체를 옮기는 것과 DB의 테이블 데이터를 옮기는 것, 공유 폴더를 복사하는 것은 다른 작업입니다. 도구를 고르기 전에 이전 단위를 정해야 합니다.

## 2. 도구를 이전 단위로 비교하기

| 이전 대상 | 도구의 출발점 | 남는 책임 |
|---|---|---|
| 서버·애플리케이션 실행 환경 | MGN 계열 애플리케이션 마이그레이션 | 앱 검증·네트워크·라이선스·전환 |
| DB 데이터와 변경분 | DMS | 스키마·엔진 차이·데이터 검증 |
| 파일·객체 데이터 이동 | DataSync | 권한·메타데이터·일관성·성능 |
| SFTP/FTPS/FTP 등 기존 전송 인터페이스 | Transfer Family | 사용자·키·접근 정책·워크플로 |
| 지속적인 온프레미스 저장 인터페이스 | Storage Gateway | 캐시·연결·복구 설계 |
| 네트워크가 어려운 대량 반출입 | 과거 Snow 계열의 목적 | 현재 지원·대체 수단 확인 필수 |

Discovery 도구는 서버와 의존성을 파악하는 데, Migration Hub는 이전 진행 추적에 활용하는 맥락입니다. Application Discovery Service와 Migration Hub는 현재 신규 고객을 받지 않는 유지보수 목록에 포함됩니다. Mainframe Modernization은 메인프레임 이전·현대화라는 별도 분야이며 Managed Runtime Environment와 Self-Managed Experience에도 현재 이용 제한이 안내됩니다. 특정 기능의 종료를 DMS나 DataSync 전체 종료로 오해하지 않아야 합니다. [현재 유지보수 목록](https://docs.aws.amazon.com/general/latest/gr/maintenance_services.html)

## 3. DMS: 전체 복사 후 변경분을 따라가기

업무 DB는 복사하는 동안에도 바뀝니다. 전체 적재만 하면 복사를 시작한 뒤의 수정이 빠질 수 있습니다. DMS의 full load와 CDC(Change Data Capture)는 초기 데이터를 옮기고 원본 변경 로그를 따라가는 접근입니다. 원본 엔진의 로그 설정·보존·권한과 지원 데이터 유형을 확인해야 합니다. CDC 지연이 계속 늘면 전환 시점에 따라잡지 못할 수 있습니다.

DMS는 DB 엔진을 마법처럼 완벽히 번역하는 도구가 아닙니다. 테이블 스키마·인덱스·제약조건·저장 프로시저·함수·트리거 등은 별도 변환과 검증이 필요할 수 있습니다. 동일 엔진 이전과 이기종 엔진 이전의 위험이 다른 이유입니다. 문자열 정렬·시간대·정밀도·자동 증가·SQL 문법 차이도 업무 결과를 바꿀 수 있습니다.

복제 지연이 0이라고 모든 업무 정합성이 증명된 것은 아닙니다. 행 수와 체크섬, 핵심 업무 집계, 외래 관계, 샘플 조회, 애플리케이션 시나리오를 검증해야 합니다. 데이터를 읽을 수 있다는 것과 업무가 정상이라는 것은 다릅니다.

## 4. 전환 시점과 쓰기 주체

안전한 전환 예시는 다음과 같습니다. 먼저 새 환경을 준비하고 초기 적재와 CDC를 수행합니다. 전환 창에서 원본 쓰기를 통제하고 마지막 변경분을 따라잡습니다. 대상의 정합성을 확인한 뒤 앱 연결을 변경합니다. 새 환경의 읽기·쓰기·외부 연동을 검증하고 관찰 기간을 둡니다. 이 과정의 시간은 실제 데이터와 트래픽으로 측정해야 합니다.

되돌리기는 특히 어렵습니다. 대상 DB에서 새 주문이 발생한 뒤 원본으로 접속만 돌리면 새 주문이 사라집니다. 역방향 변경 동기화·쓰기 중단·데이터 병합 등 전략을 미리 정해야 합니다. 양쪽에 동시에 쓴다고 항상 안전하지도 않습니다. 한쪽만 성공하는 dual-write 문제와 충돌 해결이 남습니다. cutover의 기술적 DNS 변경보다 **어느 저장소가 진실의 원본인가**라는 규칙이 중요합니다.

## 5. DataSync와 Transfer Family

DataSync는 지원 위치 사이의 데이터 전송을 자동화하며 전송·검증·메타데이터 처리 조건을 제공합니다. 수천만 개의 작은 파일은 총 바이트가 같아도 목록 조회·메타데이터·요청 수 때문에 큰 파일 몇 개와 성능이 다릅니다. 네트워크 대역폭뿐 아니라 원본 저장소의 읽기 성능과 대상 요청 제한도 병목이 됩니다.

Transfer Family는 거래처가 기존 SFTP 같은 프로토콜을 유지하면서 AWS 저장소로 파일을 전송하는 요구에 적합한 출발점입니다. 인증 방식·사용자 홈 디렉터리·권한·파일 처리 흐름을 설계합니다. 지속적인 파일 전송 접점과 일회성 대규모 데이터 이동 작업은 다른 문제이므로 제품을 혼동하지 않습니다.

## 6. 시간 계산과 병목

10TB를 초당 100MB의 유효 속도로 옮긴다는 단순 십진 계산에서는 약 100,000초, 약 27.8시간입니다. 실제로는 프로토콜 오버헤드·파일 탐색·재시도·원본 변경·검증 시간이 더해집니다. 1Gbps 회선이 항상 초당 125MB의 애플리케이션 데이터 전송을 보장하는 것도 아닙니다. 초기 복사 기간이 길수록 변경 로그 보존과 CDC 따라잡기 요구가 커집니다.

이전 계획에는 발견→준비→복제→검증→전환→안정화→폐기의 단계가 필요합니다. 원본 환경은 되돌림과 보존 조건을 확인한 뒤 폐기해야 비용이 이중으로 계속 발생하는 문제를 막을 수 있습니다.

## 7. 원문 보정: Snow는 역사적 목적과 현재 상태를 분리

Snowball은 대용량 데이터를 장치에 담아 옮기거나 연결이 어려운 곳에서 처리하는 목적의 서비스였습니다. 그러나 현재 공식 공지는 신규 고객 제한과 함께 2026-12-31 상용 리전의 Snowball 장치 지원 종료를 안내합니다. GovCloud·ADC의 일부 활성 작업에는 예외가 명시되어 있습니다. 따라서 2026-10-20 기준 새 이전 계획에서 일반적으로 주문 가능한 현행 해법처럼 제시하지 않습니다. DataSync·전용 연결·파트너 전송 등 현재 가능한 대안을 데이터량과 일정으로 검토합니다. 시험 자료의 과거 목록과 실제 조달 가능성은 별개입니다.

## 8. 가상 장애와 점검표

원본 로그 보존이 하루인데 전체 적재가 이틀 걸렸습니다. CDC가 필요한 변경 로그를 더 이상 읽을 수 없다면 이전을 다시 준비해야 할 수 있습니다. 원본 로그 설정과 용량, 복제 지연, 재시작 가능 지점을 사전에 점검해야 합니다. 또 대상 DB 성능이 낮으면 CDC 적용이 밀리므로 “네트워크만 빠르면 된다”는 판단도 틀립니다.

실습으로 이전 대상 하나를 정하고 데이터 크기·변경률·허용 중단·검증 쿼리·쓰기 전환 시점·되돌림 조건을 한 페이지에 작성하세요. 도구 이름 없이 이 계획을 설명할 수 있어야 도구가 맞는지 판단할 수 있습니다.

## 깊이 읽기: 데이터 복사 완료와 서비스 이전 완료 사이

### 이삿짐을 옮기는 동안 가게가 계속 영업한다면

정지한 DB를 한 번 복사하는 것과 계속 쓰이는 DB를 옮기는 것은 다른 문제입니다. Full load는 기존 데이터를 옮기고 CDC는 그 사이와 이후의 변경을 따라가는 역할을 합니다. 원본에서 초당 만들어지는 변경량보다 대상에 적용하는 속도가 낮으면 지연은 줄지 않습니다. “복제가 실행 중”이라는 상태만 보고 전환할 수 없다는 뜻입니다.

또한 엔진마다 로그 설정·권한·보존·지원 데이터 타입·DDL 처리 등 전제가 다릅니다. CDC가 읽어야 할 로그가 너무 일찍 지워지면 이어 따라가기 어려울 수 있습니다. 이전 기간 중 긴 트랜잭션이나 대규모 변경이 영향을 주는지도 확인합니다. 도구가 데이터를 운반해도 원본과 대상의 모든 기능 의미가 동일해지는 것은 아닙니다.

### 전환을 다섯 단계로 설계하기

첫째, 새 대상 환경을 준비하고 연결·권한·용량을 검증합니다. 둘째, 전체 복사와 변경분 추적을 수행합니다. 셋째, 행 수와 값뿐 아니라 업무 핵심 합계·상태·시간대·문자열 정렬·숫자 정밀도까지 비교합니다. 넷째, 정해진 절차로 기존 쓰기를 멈추거나 통제하고 마지막 변경이 반영됐는지 확인합니다. 다섯째, 새 대상에 연결한 앱에서 실제 업무 흐름을 검증하고 모니터링을 강화합니다.

“DNS만 바꾸면 끝”이라고 말하면 연결 풀에 남은 기존 연결, 배치·소비자·관리 스크립트의 별도 접속 주소를 놓칠 수 있습니다. 이전 대상은 웹 API만이 아닙니다. 누가 어느 DB에 쓰는지 목록을 만들어 모든 writer의 전환을 관리해야 합니다.

### 롤백이 어려워지는 정확한 시점

새 대상이 쓰기를 받기 전이라면 원본으로 되돌아가는 것이 비교적 단순할 수 있습니다. 새 대상에서 새 주문이 발생한 뒤에는 원본에 그 주문이 없을 수 있습니다. 연결 주소만 과거로 되돌리면 최신 데이터를 잃거나 사용자별로 다른 상태를 보여줄 수 있습니다. 그래서 전환 후 원복 조건에는 새 변경분을 어떻게 반영할지 또는 어떤 시점부터 원복 대신 앞으로 수정할지 포함해야 합니다.

양방향 복제를 설정하면 자동 해결된다고 단정하지 않습니다. 충돌, 순환 복제, 키 충돌, 스키마 호환, 쓰기 주체 규칙을 추가로 설계해야 합니다. 이전을 시작하기 전에 “되돌릴 수 있는 마지막 단계”를 문서로 명확히 해 두면 사고 때 잘못된 결정을 줄일 수 있습니다.

### 대역폭 계산과 실제 소요 시간

가상으로 1 TB를 1 Gbit/s로 보낸다면 바이트를 비트로 바꾸어 `8×10^12 / 10^9 = 8,000초`, 약 2.2시간이 순수 전송의 이론값입니다. TB를 십진 단위로 놓은 계산이며 TiB라면 값이 달라집니다. 실제로는 프로토콜 오버헤드, 암호화, 읽기·쓰기 성능, 파일 수, 재전송, 원본 부하 제한이 더해집니다. 이론 시간만으로 중단 창을 정하면 위험합니다.

작은 파일 백만 개는 같은 총바이트의 큰 파일 하나보다 파일 열기·메타데이터·요청 처리 비용이 클 수 있습니다. DataSync 같은 도구를 검토할 때도 데이터 양만 보지 말고 파일 수·변경률·권한 정보·검증 요구를 함께 봅니다. 네트워크 증설만으로 원본 디스크가 느린 문제를 해결할 수는 없습니다.

| 운반 | 행 수·checksum·복제 지연 | 삭제·갱신 누락, 지원하지 않는 타입 |
| 실행 | 앱 조회·저장·트랜잭션·배치 | 드라이버, SQL 차이, 시간대, 권한 |
| 업무 | 주문 총액·재고 불변식·중복 여부 | 집계 일치가 개별 오류를 숨김 |

DMS의 validation 기능은 유용하지만 지원 범위와 엔진·대상 제약을 확인해야 합니다. 모든 검증을 제품 상태 표시 하나로 대신하지 않고 업무가 의존하는 규칙을 별도 검사합니다.

## 더 깊은 면접 Q&A: 이전 작업의 종료 조건

<details><summary>Q. 원본과 대상의 행 수가 같으면 데이터 이전 성공인가요?</summary><p><strong>답변:</strong> 서로 다른 행이 누락·중복되어도 개수는 같을 수 있습니다. 값 변환, 소수 정밀도, NULL, 시간대, 문자 인코딩도 확인해야 합니다. 변경이 계속되는 동안 비교했다면 같은 시점을 비교했는지도 중요합니다.</p><p><strong>검증:</strong> 키별 표본·범위별 checksum·업무 합계를 함께 사용하고 핵심 데이터는 더 엄격히 확인합니다. 검사 자체가 원본 서비스에 주는 부하도 관리합니다.</p></details>
<details><summary>Q. CDC lag가 0이면 바로 전환해도 되나요?</summary><p><strong>답변:</strong> 그 지표의 의미와 측정 시점을 확인하고 모든 writer의 통제, 대상의 애플리케이션 호환성과 용량 검증이 끝났는지 봅니다. 단일 시점의 지연 0은 전체 이전 절차 완료를 뜻하지 않습니다.</p><p><strong>꼬리 질문:</strong> 전환 순간 새로 유입되는 쓰기를 어느 시스템이 받는지 명확해야 합니다. 마지막 변경 확인과 접속 전환 사이에 생기는 틈까지 절차로 다룹니다.</p></details>
<details><summary>Q. 서버를 그대로 복제해 옮기면 애플리케이션 수정은 필요 없나요?</summary><p><strong>답변:</strong> 코드 변경을 줄일 수 있지만 IP·DNS·외부 방화벽·인증서·파일 경로·라이선스·시간 동기화·운영 도구 같은 환경 의존성이 남습니다. OS가 부팅되는 것과 업무가 정상 동작하는 것은 다릅니다.</p><p><strong>예:</strong> 애플리케이션은 새 DB를 보는데 야간 배치는 옛 DB를 계속 수정할 수 있습니다. 의존성 목록과 실제 통신 관찰을 통해 숨은 연결을 찾아야 합니다.</p></details>
<details><summary>Q. 마이그레이션 중 성능까지 동시에 개선하는 것이 효율적이지 않나요?</summary><p><strong>답변:</strong> 필요할 수 있지만 플랫폼 변경·스키마 변경·코드 변경을 동시에 하면 문제 원인을 분리하기 어렵습니다. 변경을 분리할 수 있는지, 각각의 검증과 원복 기준이 있는지 판단합니다.</p><p><strong>현실적 선택:</strong> 동일 동작으로 먼저 이전한 뒤 개선하거나, 반드시 필요한 변경만 분리된 실험으로 검증합니다. 일정 단축보다 문제가 생겼을 때 어디서부터 틀렸는지 확인할 수 있는 구조가 중요합니다.</p></details>

## 직접 풀어 보기: 새 DB로 옮긴 뒤 다시 돌아갈 수 있을까

새 DB로 전환한 뒤 20분 동안 주문을 받았습니다. 성능 문제가 발견되어 운영자가 예전 접속 주소로 즉시 되돌리려 합니다. 왜 위험하며 어떤 판단이 필요한가요?

<details><summary>해설 펼치기 — 판단 과정과 조건을 바꾼 경우</summary><p><strong>데이터 기준:</strong> 새 DB에만 존재하는 20분간의 주문이 있을 수 있습니다. 예전 주소로 돌리면 사용자는 그 주문을 찾지 못하거나 다시 생성할 수 있습니다. 연결 원복과 데이터 원복은 다릅니다.</p><p><strong>쓰기 통제:</strong> 현재 writer를 명확히 하고 추가 쓰기를 어떻게 통제할지 결정합니다. 원본과 새 대상 양쪽에서 쓰기가 이어지면 충돌과 조정 범위가 커집니다.</p><p><strong>대안:</strong> 새 환경에서 성능 문제를 완화하며 앞으로 수정할지, 변경분을 검증해 예전 환경으로 옮긴 뒤 원복할지 사전 계획과 실제 영향으로 판단합니다. 어떤 경로든 손실·중복과 시간을 검증해야 합니다.</p><p><strong>예방:</strong> 이전 계획에 원복 가능 시점과 새 쓰기 이후의 절차를 별도로 적습니다. 전환 리허설은 성공 전환뿐 아니라 이 실패 상황까지 포함해야 합니다.</p></details>
