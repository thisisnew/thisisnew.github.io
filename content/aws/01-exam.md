## 1. 시험은 제품 이름 퀴즈가 아니다

건축사에게 “콘크리트가 무엇인가”만 묻지 않고, 지진과 예산을 고려해 건물을 설계하라고 하듯 SAA는 요구사항을 AWS 구성으로 바꾸는 능력을 평가합니다. “주문이 늘어도 유실되면 안 된다. 작업 완료까지 몇 분은 기다릴 수 있다. 운영 인력은 적다”라는 조건을 읽으면 비동기 큐, 내구성, 관리형 서비스가 중요한 후보가 됩니다. 반대로 응답이 100ms 안에 필요하다면 큐에 맡기기만 해서는 요구를 만족하지 않습니다.

원문 시험 가이드는 최소 1년 정도의 AWS 설계 실무 경험을 목표 응시자 설명에 제시합니다. 이는 응시 자격 제한을 뜻하지 않으며, 경험 없이도 암기만으로 충분하다는 뜻도 아닙니다. 각 서비스의 정상 동작뿐 아니라 실패와 비용을 함께 이해해야 합니다.

## 2. 채점 구조를 오해하지 않기

가이드에는 채점 대상 50문항과 비채점 15문항이 설명되어 있습니다. 비채점 문항은 시험 중 구별되지 않습니다. 객관식은 한 개의 답을 고르는 형식과 여러 답을 고르는 형식이 있으며, 미응답은 오답으로 취급되고 추측 자체에 별도 감점은 없습니다. 점수는 100~1,000의 환산 척도이고 합격 기준은 720입니다. **720점을 72% 정답과 동일시하면 안 됩니다.** 난이도 차이를 조정하는 척도이기 때문입니다. 영역별 모두 합격점을 받아야 하는 방식이 아니라 전체 점수로 판정하는 보상적 채점 방식입니다.

이 정보를 이용해 시험 중 비채점 문제를 추정하려고 시간을 쓰지 마세요. 불확실한 문제에는 현재 가장 타당한 답을 선택하고 재검토 표시를 하는 편이 낫습니다. 공식 가이드의 영역 비중은 학습 시간 배분의 출발점이지 개별 시험에 등장할 서비스 횟수 예측표가 아닙니다.

## 3. 네 영역을 업무 질문으로 번역하기

| 영역 | 비중 | 실제로 답해야 하는 질문 |
|---|---:|---|

보안은 네트워크 방화벽 하나로 끝나지 않습니다. 신원·권한·애플리케이션 보호·데이터 보호가 함께 필요합니다. 복원력도 서버 두 대로 끝나지 않습니다. 두 서버가 같은 단일 DB와 같은 AZ에 의존하면 공통 장애 지점이 남습니다. 고성능은 무조건 큰 인스턴스가 아니라 올바른 데이터 모델과 캐시·분산 전략을 포함합니다. 비용은 인스턴스 단가 외에 전송·요청·라이선스·운영 노동을 포함합니다.

## 5. 한 문제를 끝까지 해석하는 사고 실험

가상 문제: “검수 이미지 업로드 후 분석을 실행한다. 업로드는 빠르게 끝나야 하고, 분석 서버 장애 중에도 작업을 보존해야 한다. 분석 결과는 수 분 뒤 나와도 된다.” 먼저 즉시 응답이 필요한 것은 업로드 접수이지 분석 완료가 아니라는 점을 분리합니다. 다음으로 이미지 본문과 작업 메시지를 구분합니다. S3에 이미지를 두고 메시지에는 객체 키와 작업 ID를 넣는 방식이 자연스럽습니다. 분석 소비자는 실패하면 재시도하고, 같은 ID가 다시 들어와도 중복 결과를 만들지 않아야 합니다.

여기서 SNS만 연결하고 끝내면 소비자의 장애 기간과 재시도 계약을 확인하지 않은 설계가 됩니다. 각 분석 서비스가 자기 큐를 가지면 독립적인 backlog와 재처리가 쉬워집니다. 그러나 “정확히 한 번만 분석 비용을 내야 한다”는 추가 조건이 붙으면 큐의 중복 방지 기능만으로는 부족하고 작업 상태 저장과 멱등 처리가 필요합니다. 한 단어의 조건 변경이 답을 바꿉니다.

## 6. 출제 범위 목록은 어떻게 읽는가

가이드는 분석, 통합, 비용, 컴퓨팅, 컨테이너, DB, 개발 도구, 웹·모바일, ML, 관리·거버넌스, 미디어, 이전, 네트워크, 보안, 서버리스, 스토리지를 열거합니다. 목록에 있다고 모든 제품의 모든 API를 외울 필요는 없습니다. 예를 들어 Textract는 문서에서 텍스트를 추출하는 목적, Transcribe는 음성을 텍스트로 바꾸는 목적, Translate는 언어 변환이라는 대표 역할부터 구분합니다. X-Ray는 요청 추적, Amplify는 웹·모바일 개발 지원, Device Farm은 장치 테스트라는 연결 고리를 잡습니다.

원문은 범위가 비포괄적이고 변경될 수 있다고 명시합니다. 시험 범위에 예전 제품이 등장한다고 신규 운영 환경에서 무조건 도입할 수 있는 것은 아닙니다. 서비스 종료·신규 고객 제한과 시험 가이드상의 명칭은 별도로 확인합니다. AR/VR·게임·양자·위성 등의 범위 밖 목록도 개별 서비스 기준으로 읽어야지, 비슷한 이름만으로 다른 서비스를 제외하면 안 됩니다.

## 깊이 읽기: 문제의 문장을 아키텍처 제약으로 번역하기

### 정답을 고르기 전, 네 가지 문장으로 다시 쓰기

시험 문제는 긴 이야기 속에 필수 조건과 배경 설명을 섞어 놓습니다. 밑줄을 많이 긋기보다 요구를 네 칸으로 분리해 보세요. 첫째는 데이터와 작업의 성질입니다. 사진인지, 거래 기록인지, 오래 실행되는 계산인지 식별합니다. 둘째는 반드시 지켜야 할 조건입니다. 데이터 손실 허용 범위, 중단 시간, 프로토콜 호환성 같은 조건입니다. 셋째는 최적화 목표입니다. 비용 최소화인지 운영 부담 최소화인지 읽습니다. 넷째는 변경할 수 없는 제약입니다. 기존 애플리케이션을 바꾸지 못한다면 서비스 선택 폭이 크게 줄어듭니다.

비유하면 이삿짐센터를 고르는 일입니다. 가장 싼 업체를 묻는데 깨지기 쉬운 냉장 제품을 상온으로 보내는 답은 비용이 싸도 탈락입니다. 먼저 필수 조건을 만족하는 후보를 남기고, 그 안에서 가장 유리한 선택을 해야 합니다. “가장 비용 효율적”이라는 문구가 신뢰성이나 보안 요구를 무시하라는 뜻은 아닙니다.

### 직접 만든 연습 문제 1: 파일 공유

여러 Linux 서버가 같은 디렉터리 경로에서 파일을 읽고 수정합니다. 기존 프로그램은 POSIX 파일 접근 방식을 사용하며 애플리케이션 변경은 최소화해야 합니다. 이때 “파일이니까 S3”로 바로 답하면 안 됩니다. S3는 객체 API로 접근하는 저장소입니다. 애플리케이션이 기대하는 파일 잠금·디렉터리·파일 시스템 동작을 같은 방식으로 제공한다고 가정할 수 없습니다. 공유 파일 시스템 후보를 먼저 검토합니다.

반대로 정적 이미지가 HTTP로 배포되고 수정할 때 새 객체로 교체한다면 객체 스토리지와 CDN 조합이 자연스러울 수 있습니다. 데이터의 확장자가 같아도 **접근 계약**이 다르면 정답이 달라집니다. 여기서 외워야 할 것은 “이미지=S3”가 아니라 “어떤 API와 공유 의미가 필요한가”입니다.

### 직접 만든 연습 문제 2: 장애와 읽기 부하

DB 장애 시 자동 복구가 필요하며 읽기 요청도 증가했다고 합시다. 전통적인 RDS Multi-AZ DB instance의 standby를 읽기 서버로 쓰겠다는 선택은 맞지 않습니다. 이 배포 형태의 standby는 읽기 부하 분산용이 아닙니다. 읽기 복제본이나 읽기 가능한 standby를 가진 다른 배포 형태를 구분해야 합니다.

여기서 “Multi-AZ면 읽을 수 없다”로 역암기해도 틀립니다. Multi-AZ DB cluster는 읽기 가능한 replica를 갖습니다. 문제에 나온 **정확한 배포 형태**를 먼저 확인해야 합니다. 또한 읽기 서버가 생겨도 최신 쓰기 결과를 즉시 읽어야 하는 요청은 복제 지연 영향을 따져야 합니다. 기능의 존재와 업무 요구 충족은 한 단계 더 떨어져 있습니다.

### 직접 만든 연습 문제 3: 갑자기 몰리는 주문

가상 조건으로 API는 초당 1,000건을 접수할 수 있지만 후속 처리 시스템은 초당 200건만 처리할 수 있다고 합시다. 잠깐 몰린 요청을 나중에 처리해도 된다면 큐가 후보입니다. 하지만 초당 1,000건이 계속 들어오면 초당 800건씩 대기가 증가합니다. 큐를 도입했다는 이유만으로 문제 해결이라고 말하면 안 됩니다.

선택지를 판단할 때는 “요청을 잃지 않고 받아둘 수 있는가”와 “약속한 시간 안에 끝낼 수 있는가”를 분리합니다. 처리량을 늘리거나 입력을 제한하거나 완료 기한을 조정해야 할 수 있습니다. 동기 응답이 필수라면 큐만 추가하는 선택은 원래 요구와 다를 수 있습니다. 이 연습의 수치는 계산용 가정이며 실제 시험 문항을 재현한 것이 아닙니다.

| 시간 | 백업이 있으니 즉시 복구 가능 | 복원·검증·전환에 얼마가 필요한가? |
| 상태 | 서버만 늘리면 세션도 자동 공유 | 다음 요청에 필요한 상태는 어디에 있는가? |
| 접근 방식 | 객체 저장소를 파일 시스템처럼 취급 | 애플리케이션이 기대하는 API는 무엇인가? |
| 권한 | 암호화하면 읽기 권한은 불필요 | 누가 어떤 API와 키를 사용할 수 있는가? |
| 경제성 | 모든 부하를 장기 약정 | 확실히 지속되는 사용량은 얼마인가? |

오답을 기록할 때 정답 서비스, 결정 문구, 탈락 이유, 조건을 바꾸면 정답이 바뀌는 경우를 각각 한 줄로 남깁니다. 예를 들어 “재처리 가능한 배치라 Spot 후보, 중단 불가 단일 작업이면 다른 용량 필요”라고 적습니다. 같은 문제를 다시 맞히는 것보다 조건 변화에 따라 판단을 바꾸는 능력이 중요합니다.

## 더 깊은 면접 Q&A: 선택 이유를 끝까지 설명하기

<details><summary>Q. 운영 부담을 줄이라는 요구에 무조건 서버리스를 고르면 되나요?</summary><p><strong>답변:</strong> 서버 운영 책임을 줄일 수 있는 것은 맞지만 실행 시간, 네트워크, 동시성, 연결 방식, 기존 코드의 제약을 먼저 확인합니다. 맞지 않는 애플리케이션을 억지로 분리하면 장애 분석과 배포 복잡도가 오히려 커질 수 있습니다.</p><p><strong>꼬리 질문:</strong> 비교할 때 서버 관리 시간뿐 아니라 재시도 설계, 관측성, 테스트, 팀 학습 비용까지 포함합니다. 문제에서 요구한 운영 최소화가 어떤 범위인지 문맥으로 판단합니다.</p></details>
<details><summary>Q. 읽기 복제본을 만들면 DB 성능 문제를 해결할 수 있나요?</summary><p><strong>답변:</strong> 읽기가 병목이며 요청을 적절히 분산할 수 있을 때 도움이 됩니다. 쓰기 락 경합이나 잘못된 쿼리, 연결 폭증이 원인이라면 복제본만 추가해도 문제가 남습니다. 복제 지연을 허용하지 못하는 읽기는 별도로 취급해야 합니다.</p><p><strong>답변 순서:</strong> 병목 측정 → 읽기·쓰기 분리 가능성 → 일관성 요구 → 복제 지연 및 장애 시 연결 전환을 설명합니다. “서버 한 대 추가”보다 이 판단 과정이 핵심입니다.</p></details>
<details><summary>Q. 정답 후보가 둘 다 요구를 만족하면 무엇으로 구분하나요?</summary><p><strong>답변:</strong> 문제의 최적화 목표를 다시 봅니다. 운영 부담 최소화와 월 비용 최소화는 같은 기준이 아닙니다. 기존 환경 변경 최소화, 복구 목표, 관리형 기능 제공 여부도 비교합니다. 필수 조건과 선호 조건을 섞지 않으면 후보를 좁히기 쉽습니다.</p><p><strong>실무와 차이:</strong> 시험은 주어진 조건으로 최선의 후보를 고르지만 실무에서는 빠진 조건을 질문하고 작은 실험으로 검증합니다. 시험 문제에 없는 업무 제약을 임의로 추가해 오답을 만들지 않습니다.</p></details>
<details><summary>Q. 모르는 서비스가 나왔을 때 무엇을 추론할 수 있나요?</summary><p><strong>답변:</strong> 이름만으로 기능을 발명하지 않고, 알고 있는 선택지에서 요구와 명백히 충돌하는 것을 제거합니다. 저장·전송·처리·탐지처럼 역할의 범주와 관리 책임을 비교할 수 있습니다. 다만 지원 프로토콜이나 배포 범위 같은 제품 사실은 추측으로 확정하면 안 됩니다.</p><p><strong>학습 방법:</strong> 틀린 뒤 공식 문서에서 서비스 정의와 제한을 확인하고, 기존 비교표에 한 행을 추가합니다. 제품 전체 문서를 처음부터 외우려 하기보다 판단에 필요한 차이를 채웁니다.</p></details>

## 직접 풀어 보기: 가장 저렴하다는 문장에 함정이 있다

가상의 선택지 A는 월비용 100, 복구 10분이고 B는 월비용 60, 복구 3시간입니다. 업무는 최대 30분만 중단될 수 있습니다. “가장 저렴한 설계”를 고르라는 요구에 무엇을 답해야 할까요? 실제 상품 가격·성능을 나타내는 수치가 아닙니다.

<details><summary>해설 펼치기 — 판단 과정과 조건을 바꾼 경우</summary><p><strong>먼저 제약 검사:</strong> B는 비용이 낮지만 중단 허용 조건을 만족하지 못하므로 비교 후보에서 제외합니다. 주어진 두 후보 중에서는 A가 요구를 만족합니다. 비용 최소화는 필수 조건을 만족하는 집합 안에서 수행합니다.</p><p><strong>확인할 가정:</strong> 복구 시간이 백업 복원만 뜻하는지 업무 검증까지 포함하는지 확인합니다. A의 10분이 반복 시험의 결과인지 단순 예상인지도 중요합니다. 실무라면 숫자의 근거를 질문해야 합니다.</p><p><strong>조건 변경:</strong> 업무가 다음 날까지 복구되어도 된다면 B가 후보가 됩니다. 반대로 데이터 손실을 허용하지 않는 조건을 추가하면 두 후보의 RPO도 확인해야 하므로 주어진 정보만으로 최종 결론을 내리기 어렵습니다.</p><p><strong>학습 포인트:</strong> 좋은 오답 노트는 “A 정답”에서 끝나지 않습니다. 어떤 문구가 B를 탈락시켰는지와 어떤 조건에서 B가 다시 후보가 되는지 적습니다. 조건을 바꿔 답도 바꿀 수 있으면 암기를 넘어선 이해입니다.</p></details>
