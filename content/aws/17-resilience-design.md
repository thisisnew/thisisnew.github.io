## 1. 창구를 늘려도 뒷문이 하나면 막힌다

입고 접수 창구를 열 개로 늘렸지만 검수대가 하나라면 접수 속도만 빨라지고 대기열은 계속 길어집니다. 분산 시스템도 한 단계의 확장이 다음 단계의 용량 부족을 드러낼 수 있습니다. 신뢰성은 고장 난 서버를 바꾸는 것뿐 아니라 **의존성의 속도 차이와 실패를 어떻게 제한하는지**의 문제입니다. REL 1~5는 기본 제약부터 서비스 간 상호작용까지 다룹니다.

## 2. REL 1: 할당량과 실제 용량을 분리

서비스 할당량은 API 요청률·자원 개수·동시 실행 수처럼 계정·리전·서비스별로 적용되는 제한입니다. 일부는 상향할 수 있지만 일부는 구조적 제한입니다. 할당량을 올렸다고 물리 용량이나 애플리케이션 처리량이 보장되는 것은 아닙니다. 반대로 CPU가 남아도 API throttling 때문에 확장 작업이 실패할 수 있습니다.

원문의 REL01-BP01~06은 제한 파악, 계정·리전별 관리, 고정 제한을 수용하는 구조, 모니터링, 자동 관리, 장애 조치 여유를 강조합니다. DR 리전의 할당량은 평소 트래픽이 적다고 무시하면 안 됩니다. 장애 때 처음 대량 생성하려다 quota에 막히면 복구 목표를 놓칩니다. API 조회를 과도하게 반복하는 모니터링 자체가 제한을 소진할 수도 있습니다.

용량 예시: AZ 두 곳이 각각 100건/초를 처리하고 총 유입이 160건/초라면 평소 총 용량 200으로 충분합니다. 한 AZ를 잃으면 100만 남아 60건/초가 밀립니다. 장애 후 자동 확장에만 의존할지, 정상 상태부터 각 AZ가 더 큰 부하를 감당할지 정해야 합니다. 이 계산은 제품 수치가 아니라 장애 용량 모델입니다.

## 3. REL 2: 네트워크를 처음부터 연결 가능한 모양으로

공개 endpoint의 가용성, 온프레미스 연결의 이중화, 충분한 서브넷 IP, 허브 구조, 겹치지 않는 주소가 핵심입니다. 컨테이너나 서버를 늘릴 CPU가 있어도 서브넷 IP가 부족하면 배치하지 못할 수 있습니다. blue-green 배포 때 두 환경이 겹치는 기간과 장애 조치 때 추가 자원을 생성하는 기간까지 주소를 계산해야 합니다.

VPC가 늘 때 모든 VPC를 서로 연결하면 연결 관리가 복잡해집니다. Transit Gateway 같은 hub-and-spoke 구조를 검토하되 허브의 경로·비용·장애 범위도 평가합니다. 두 데이터센터와 클라우드가 같은 CIDR을 쓰면 이후 통합이 어려워집니다. REL02-BP01~05는 회선 하나의 속도보다 전체 연결의 복원력과 확장성을 묻습니다. VPN·Direct Connect의 서로 다른 경로가 실제로 같은 장비나 장소를 공유하는지도 확인해야 합니다.

## 4. REL 3: 서비스 경계는 비즈니스 의미로

서비스를 작게 나누는 것 자체가 목적은 아닙니다. 주문·재고·검수처럼 책임과 변경 이유가 다른 영역을 경계로 검토합니다. 하나의 사용자 요청이 열 개 서비스의 동기 성공을 모두 요구하면 작은 서비스들이 하나의 거대한 장애 경로가 될 수 있습니다. 경계를 나눌 때 데이터 소유권·API 계약·실패 의미·버전 호환을 함께 정합니다.

REL03-BP01~03은 분할 방식 선택, 업무 도메인 중심 구성, API별 계약을 다룹니다. 계약에는 입력 형식뿐 아니라 중복 요청·오류·timeout·재시도 가능 여부·일관성도 포함됩니다. 재고 차감 API의 응답을 잃었을 때 “실패했으니 다시 호출”해도 되는지를 문서화하지 않았다면 계약이 불완전합니다.

## 5. REL 4: 느슨한 결합과 일정한 작업, 멱등성

동기 호출은 호출자가 상대의 즉시 성공에 묶입니다. 비동기 큐는 생산과 소비 속도를 분리하지만 결과 지연·중복·보존·재처리 책임을 추가합니다. 큐를 넣었다는 이유로 업무의 hard dependency가 없어지는 것은 아닙니다. 사용자가 즉시 검수 확정 결과를 요구하면 비동기 접수만으로 같은 경험을 제공할 수 없습니다.

“일정한 작업”은 장애 상태에서 갑자기 평소보다 훨씬 무거운 일을 수행하지 않도록 설계하는 관점입니다. 정상 때는 작은 증분 갱신을 하다가 장애 때 전체 캐시 재구축을 동시에 시작하면 복구 경로가 더 큰 부하를 만들 수 있습니다. 큰 일괄 작업을 작은 조각으로 분산하고 주기 작업 시작 시각에 지터를 두는 방식이 도움이 됩니다.

멱등성은 같은 논리 요청을 반복해도 추가 부수 효과가 생기지 않는 성질입니다. 요청 ID를 저장하는 것만으로 충분하지 않고 업무 변경과 기록의 원자성·중복 보존 기간·같은 ID에 다른 본문이 들어왔을 때의 처리까지 정해야 합니다. 최초 처리 중인 요청과 완료된 요청도 구분해야 합니다. REL04-BP01~04는 분산 시스템의 일관성·실패 모델 이해, 느슨한 결합, 일정한 작업, 변경 작업의 멱등성을 묶습니다.

## 6. REL 5: 재시도는 부하를 복제한다

A→B→C 세 계층이 각각 최초 호출 포함 3번 시도하면 가장 아래 호출은 최악의 단순 모델에서 3×3×3=27번까지 늘 수 있습니다. 장애가 원래 과부하 때문이라면 재시도가 복구를 방해합니다. 재시도할 오류와 하지 않을 오류를 구분하고, 전체 deadline·최대 횟수·지수 backoff·jitter를 설정합니다. 가능하면 한 계층이 재시도 책임을 갖도록 정리합니다.

connection timeout은 연결 수립, read/request timeout은 응답 대기, 전체 deadline은 사용자 요청의 총 예산입니다. 각 하위 호출 timeout을 전체 예산보다 길게 잡으면 사용자에게 이미 실패를 돌려준 뒤에도 자원이 계속 묶일 수 있습니다. timeout은 상대 작업을 확실히 취소했다는 뜻이 아닙니다. 상대는 이미 DB 커밋을 했을 수 있으므로 재시도에는 멱등성이 필요합니다.

빠른 실패와 제한된 큐는 과부하를 숨기지 않게 합니다. 무한 큐는 오류 대신 대기 시간을 무한히 늘려 결국 메모리와 timeout을 소모합니다. 요청 제한은 입구에서 허용량을 정하고, bulkhead는 기능별 자원 풀을 분리하며, circuit breaker는 실패 중인 의존성 호출을 잠시 차단하고 회복을 시험합니다. 이 셋은 같은 기능이 아닙니다.

## 7. 단계적 성능 저하와 비상 레버

추천 서비스가 죽었을 때 주문까지 실패시키지 않고 추천 없이 주문을 받는 것은 graceful degradation입니다. 하지만 재고 검증이나 결제 승인처럼 필수 안전 조건을 생략하면 안 됩니다. 어떤 의존성을 hard에서 soft로 바꿀 수 있는지 업무 의미로 결정합니다. 오래된 캐시 값을 허용할 수 있는 데이터와 절대 허용하지 않는 데이터를 구분해야 합니다.

REL05-BP01~07은 성능 저하, throttling, 재시도 제어, 빠른 실패·큐 제한, timeout, stateless, 비상 레버입니다. 비상 레버는 분석·이미지 고해상도 처리처럼 선택 기능을 끄거나 유입을 제한하는 사전 준비된 수단입니다. 장애 중 처음 코드를 수정해 배포하는 방식보다 통제된 설정으로 동작하게 할 수 있습니다. 레버가 오래 켜진 채 방치되지 않도록 소유자·로그·해제 조건도 필요합니다.

## 8. 통합 가상 장애: 외부 택배 API 지연

외부 API가 100ms에서 10초로 느려졌습니다. 앱의 스레드가 대기하며 풀이 고갈되고, 재시도가 추가 요청을 만들었습니다. 결국 택배 조회와 무관한 검수 등록도 실패했습니다. 원인은 외부 지연이지만 피해 확산 원인은 공유 풀·긴 timeout·중첩 재시도입니다.

대응 설계는 택배 호출 전용 풀과 동시성 한도, 전체 시간 예산에 맞는 timeout, 제한된 재시도, circuit breaker, 허용 가능한 캐시 응답, 중요 기능의 자원 보호입니다. 큐를 넣는다면 최대 대기 시간과 만료·취소를 정의합니다. 복구 후에는 갑자기 쌓인 backlog가 외부 API를 다시 압도하지 않도록 배출 속도를 제한합니다.

## 9. 계산 연습

초당 500건, 평균 응답 0.2초면 안정 상태에서 동시 진행량은 약 100입니다. 평균이 2초로 늘면 약 1,000입니다. 부하가 늘지 않아도 지연만으로 자원 사용량이 열 배가 될 수 있습니다. Little의 법칙은 안정적인 평균 관계의 근사 도구이며 burst와 꼬리 지연·대기열 한계까지 대신하지는 않습니다. 정상·지연·단절·복구 네 상태를 따로 부하 시험하는 이유입니다.

## 깊이 읽기: 실패가 옆 서비스로 번지는 과정을 끊기

### 느린 의존성 하나가 서버 전체를 멈추는 과정

외부 배송 API가 0.1초에서 5초로 느려졌다고 합시다. 초당 100건을 처리하는 앱의 평균 진행 중 요청은 단순 근사로 10개에서 500개가 됩니다. 스레드·연결·메모리를 오래 붙잡으면서 다른 정상 API도 기다리기 시작할 수 있습니다. CPU는 낮은데 서비스 전체가 느려지는 이유입니다. 대기 시간이 자원 점유 시간을 늘리는 연결을 이해해야 합니다.

식당에서 한 손님의 결제가 멈췄다고 모든 직원이 그 손님만 기다리는 상황과 비슷합니다. 업무별 자원을 나누는 bulkhead는 결제 대기 때문에 조리와 포장이 모두 멈추지 않게 하는 방법입니다. 다만 풀을 분리하면 유휴 자원을 다른 업무가 쓰기 어려운 비용이 생길 수 있습니다. 격리 단위는 업무 중요도와 장애 전파 위험에 맞춥니다.

### Timeout은 상대 작업 취소 확인서가 아니다

호출자가 기다리기를 중단했다고 상대 서버가 실행을 멈췄다는 뜻은 아닙니다. 주문 생성 요청이 timeout 났지만 상대 DB에는 이미 저장됐을 수 있습니다. 곧바로 새 주문 ID로 재시도하면 중복 주문이 생깁니다. 요청의 업무 ID를 유지하고 결과 조회·멱등 처리 계약을 마련해야 합니다.

Connect timeout, read timeout, 전체 deadline은 목적이 다릅니다. 전체 사용자 응답 예산 안에 여러 하위 호출과 재시도를 넣어야 합니다. 남은 시간이 100ms인데 최대 2초짜리 재시도를 시작하면 사용자는 이미 떠났는데 서버만 일을 계속할 수 있습니다. 가능하면 남은 시간 예산을 전달하고 불필요한 작업을 중단하는 흐름을 검토합니다.

### 재시도가 곱셈으로 불어나는 이유

A가 B를 호출하고 B가 C를 호출한다고 합시다. 각 단계에서 최초 시도 포함 세 번씩 호출하면 최악의 경우 C는 원래 요청 하나 때문에 아홉 번 호출될 수 있습니다. 단계가 더 많으면 더 커집니다. 각 팀이 자기 서비스만 보고 “재시도 세 번이면 안전”이라고 정하면 시스템 전체 부하를 증폭할 수 있습니다.

재시도는 일시적 실패에 효과가 있지만 권한 오류·잘못된 입력처럼 반복해도 달라지지 않는 실패에는 보통 도움이 되지 않습니다. 재시도 횟수·전체 시간·백오프·지터·재시도할 오류를 정하고 가능한 한 책임을 한 계층에 모읍니다. 지터는 모두 같은 순간에 다시 몰리는 현상을 줄이는 도구이지 의존성의 처리 능력을 늘리는 기능이 아닙니다.

### Rate limit·backpressure·load shedding을 분리하기

Rate limit은 정해진 기간에 허용할 요청량을 제한합니다. Backpressure는 뒤쪽 처리 능력에 맞춰 앞쪽 생산·전달 속도를 조절하는 흐름입니다. Load shedding은 감당할 수 없는 부하 일부를 거절해 나머지의 정상 처리를 보호합니다. Circuit breaker는 실패하는 의존성 호출을 잠시 줄이고 회복을 확인하는 상태 기반 패턴입니다. 서로 연관되지만 같은 이름이 아닙니다.

쿠폰 조회와 결제 완료 처리의 중요도가 같지 않다면 우선순위를 분리할 수 있습니다. 하지만 일부 요청을 버릴 때 무엇이 안전하게 재시도되는지, 사용자에게 어떤 상태를 보여줄지 정의해야 합니다. 무조건 200을 응답하고 내부에서 버리는 방식은 가용성처럼 보이는 데이터 손실을 만들 수 있습니다.

### 할당량과 네트워크 주소도 용량이다

CPU·메모리 외에도 연결 수, IP 주소, 서비스 API 한도, 실행 동시성, 계정 할당량이 확장을 막을 수 있습니다. 허용된 할당량이 높아도 원하는 위치에 실제 자원이 즉시 확보되는지는 또 다른 문제입니다. 재해 때 새 자원을 만들 계획이라면 평소에 경로·이미지·권한·주소·할당량을 점검해야 합니다.

| 장애 유발 조건 | 전파 경로 | 끊을 수 있는 지점 |
|---|---|---|
| 외부 API 지연 | 대기 요청 증가·풀 고갈 | timeout·격리·동시성 제한 |
| 반복 실패 | 재시도 폭증 | 재시도 예산·백오프·지터 |
| 입력 급증 | 큐 증가·완료 지연 | 유입 제한·확장·업무 우선순위 |
| 인기 키 집중 | 특정 저장 경로 포화 | 키 설계·캐시·조건부 처리 |

## 더 깊은 면접 Q&A: 실패해도 업무를 잃지 않기

<details><summary>Q. Circuit breaker를 열면 가용성을 낮추는 것 아닌가요?</summary><p><strong>답변:</strong> 이미 실패하거나 매우 느린 의존성에 계속 요청을 보내 전체 자원을 소모하는 대신 제한된 실패를 빠르게 반환해 다른 기능을 보호할 수 있습니다. 성공을 만들어 내는 장치가 아니라 전파를 줄이고 회복 기회를 주는 장치입니다.</p><p><strong>주의:</strong> 대체 응답의 의미와 회복 확인 호출을 설계합니다. 오래된 데이터를 제공해도 되는 기능과 거래 승인을 임의로 성공 처리하면 안 되는 기능을 구분합니다.</p></details>
<details><summary>Q. 재시도 횟수는 보통 몇 번이 적당한가요?</summary><p><strong>답변:</strong> 모든 시스템에 통하는 횟수는 없습니다. 전체 deadline, 실패 유형, 상대 지연 분포, 부수 효과의 멱등성, 다른 계층의 재시도를 포함해 정합니다. 횟수뿐 아니라 최대 누적 대기 시간과 총 요청량을 제한합니다.</p><p><strong>예:</strong> 사용자가 1초 안에 결과를 원하면 긴 백오프 세 번은 맞지 않을 수 있습니다. 비동기 작업은 더 오래 재시도할 수 있지만 최종 실패 상태와 운영 처리 경로가 있어야 합니다.</p></details>
<details><summary>Q. 멱등 키는 UUID만 붙이면 끝인가요?</summary><p><strong>답변:</strong> 같은 업무 재시도에서 같은 키를 재사용해야 하고, 키의 범위·보존 기간·다른 요청 본문으로 재사용될 때의 처리도 정해야 합니다. 매번 새 UUID를 만들면 중복 업무를 같은 것으로 인식하지 못합니다.</p><p><strong>저장:</strong> 키 확인과 업무 변경이 경쟁하지 않도록 원자적으로 보호합니다. 완료 결과를 다시 돌려줄지, 진행 중이면 어떤 상태를 줄지도 API 계약에 포함합니다.</p></details>
<details><summary>Q. 큐에 무한히 쌓아 두면 요청을 거절하지 않아도 되나요?</summary><p><strong>답변:</strong> 저장 용량뿐 아니라 완료 기한과 보존 기간이 있습니다. 유입이 처리보다 계속 많으면 대기 시간이 끝없이 증가하고 이미 의미가 없어진 작업까지 처리할 수 있습니다.</p><p><strong>대응:</strong> 가장 오래된 메시지 나이, 예상 완료 시간, 처리 여력을 보고 유입 제한이나 기능 축소를 판단합니다. 요청을 받아 놓고 약속한 시간에 못 끝내는 것도 사용자 관점의 실패입니다.</p></details>

## 직접 풀어 보기: 재시도 세 겹의 총호출 수

A→B→C→D로 순차 호출하며 각 계층이 최초 시도 포함 최대 세 번 호출합니다. D가 계속 실패하고 모든 상위 계층이 자기 하위 호출을 끝까지 재시도한다면 D는 원래 요청 하나로 최대 몇 번 호출될까요?

<details><summary>해설 펼치기 — 판단 과정과 조건을 바꾼 경우</summary><p><strong>계산:</strong> A가 B를 세 번, 각 B가 C를 세 번, 각 C가 D를 세 번 호출하므로 단순 최악 모델에서 3×3×3=27회입니다. 최초 시도 외에 세 번 재시도라는 조건이었다면 각 배수가 네 번으로 달라집니다. 용어부터 정확히 정의해야 합니다.</p><p><strong>영향:</strong> D가 과부하로 실패했다면 호출을 27배 늘리는 것이 회복을 방해할 수 있습니다. 재시도는 무료 신뢰성이 아니라 추가 부하를 쓰는 선택입니다.</p><p><strong>개선:</strong> 책임 계층과 전체 deadline, retry budget, 재시도할 오류, 백오프·지터를 정합니다. 멱등하지 않은 부수 효과는 키나 결과 확인 절차로 보호합니다.</p><p><strong>한계:</strong> 이것은 모든 시도가 실제 도달하는 단순 상한 예제입니다. Timeout·circuit breaker·부분 성공 등 실제 동작에 따라 다르므로 trace와 호출 수로 검증해야 합니다.</p></details>
