## 1. 접수 창구와 방송실은 다르다

입고 검수 결과가 나오면 재고 반영·문자 알림·통계 집계가 필요하다고 가정합시다. 접수 직원이 세 작업을 모두 끝낼 때까지 기다리면 가장 느린 작업 때문에 전체 응답이 늦어집니다. 해야 할 일을 접수함에 넣고 담당 작업자가 꺼내 처리하면 속도를 분리할 수 있습니다. 이것이 큐의 비유입니다. 반면 결과가 나왔다는 사실을 여러 부서에 알려 각자 행동하게 하는 것은 방송에 가깝습니다.

SQS는 작업을 보관하고 소비자가 가져가는 큐, SNS는 구독자에게 메시지를 배포하는 pub/sub, EventBridge는 이벤트의 내용과 규칙에 따라 대상으로 전달하는 이벤트 버스, Step Functions는 여러 단계의 상태와 순서를 관리하는 워크플로입니다. 이들은 함께 사용할 수도 있습니다.

## 2. SQS에서 메시지는 받는 순간 사라지지 않는다

기본 흐름은 전송 → 수신 → 일정 시간 숨김 → 업무 처리 → 삭제입니다. visibility timeout은 다른 소비자가 같은 작업을 곧바로 집어 가지 않도록 일시적으로 숨기는 기간입니다. 처리 완료 전에 소비자가 죽으면 삭제되지 않은 메시지는 다시 보일 수 있습니다. timeout이 너무 짧으면 아직 처리 중인데 다시 전달될 수 있고, 너무 길면 실패한 작업의 재시작이 늦어집니다.

Standard 큐는 적어도 한 번 전달 모델이므로 중복을 전제로 설계합니다. visibility timeout도 완벽한 분산 락으로 취급하면 안 됩니다. long polling은 메시지를 기다리며 불필요한 빈 응답을 줄이는 방식이고, 메시지 보존 기간은 큐에 얼마나 오래 남길지 결정합니다. visibility timeout·retention·애플리케이션 timeout은 서로 다른 시계입니다.

처리 실패를 무한 반복하는 poison message는 DLQ로 분리할 수 있습니다. DLQ는 자동으로 문제를 해결하는 곳이 아닙니다. 실패 이유·메시지 나이·재처리 권한·수정 후 redrive 절차를 정해야 합니다. 정상 메시지까지 너무 빨리 DLQ로 보내지 않도록 일시 장애와 영구 오류를 구분합니다.

## 3. 가장 중요한 실패 구간: DB 커밋과 메시지 삭제 사이

소비자가 재고를 10개 늘리고 DB 커밋에 성공했습니다. 그런데 SQS 삭제 전에 프로세스가 죽었습니다. 재전달된 메시지를 그대로 실행하면 재고가 20개 늘어납니다. 큐가 고장 난 것이 아니라 외부 DB 변경과 큐 삭제가 하나의 원자적 트랜잭션이 아니기 때문에 생기는 정상적인 실패 가능성입니다.

해결 방법 중 하나는 업무 이벤트 ID를 unique key로 저장하고, **처리 기록과 업무 변경을 같은 DB 트랜잭션 안에서** 수행하는 것입니다. 첫 처리에서 기록과 재고 변경을 커밋하고, 재전달에서는 이미 처리된 ID임을 확인한 뒤 성공으로 마무리합니다. 처리 기록만 먼저 저장한 뒤 업무 처리를 별도 트랜잭션으로 하면 중간 실패 때 영구 누락될 수 있습니다. 외부 결제·메일처럼 DB 트랜잭션에 묶이지 않는 부수 효과는 제공자의 멱등키나 별도 상태 전이까지 필요합니다.

생산자 쪽에도 DB 커밋과 메시지 전송 사이 간격이 있습니다. 주문은 저장됐지만 이벤트 전송이 실패할 수 있습니다. outbox는 업무 데이터와 발행할 이벤트를 같은 DB 트랜잭션에 저장하고 별도 전달자가 재시도하는 패턴입니다. 전달 중복은 여전히 가능하므로 소비자 멱등성과 함께 사용합니다.

## 4. FIFO: 순서를 어느 범위에서 지킬 것인가

FIFO 큐는 message group 안에서 순서를 다루고 전송 중복 제거 기능을 제공합니다. 모든 업무를 단일 group에 넣으면 순서 경계가 커져 병렬성이 제한됩니다. 주문별 순서가 필요하면 orderId를 group 기준으로 검토하고, 서로 다른 주문은 독립적으로 처리할 수 있게 합니다. 다만 한 주문의 느린 메시지가 뒤의 같은 group을 막을 수 있습니다.

전송 중복 제거와 업무 부수 효과의 정확히 한 번 실행은 다릅니다. 소비자가 DB 커밋 후 삭제 전에 죽는 문제는 FIFO라는 이름만으로 사라지지 않습니다. 순서가 중요한 업무를 DLQ로 옮기면 뒤 메시지 처리와 상태 전이에도 영향을 줄 수 있으므로 재처리 순서를 설계해야 합니다.

## 5. SNS·EventBridge·Step Functions 비교

| 요구 | 출발 후보 | 확인할 점 |
|---|---|---|
| 작업을 모아 소비자 속도로 처리 | SQS | backlog·중복·재처리 |
| 같은 알림을 여러 구독자에 배포 | SNS | 구독 형태·필터·전달 실패 |
| 이벤트 내용으로 여러 대상에 라우팅 | EventBridge | 규칙·스키마·권한·대상 재시도 |
| 승인→처리→보상 같은 다단계 흐름 | Step Functions | 상태·Retry/Catch·실행 모델 |

SNS 뒤에 부서별 SQS를 놓으면 각 부서는 자기 속도로 소비할 수 있습니다. 하나의 큐를 세 부서가 경쟁해서 읽으면 모든 부서가 모든 이벤트를 받는 구조가 아닙니다. EventBridge의 규칙과 archive/replay 같은 기능도 전달 보장을 이해하고 사용해야 하며, 외부 시스템의 원자성을 대신하지 않습니다.

Step Functions의 Standard와 Express는 실행 시간·기록·처리 보장·비용 특성이 다릅니다. 워크플로가 정확히 한 번 상태를 진행한다는 설명을 외부 API의 영구 부수 효과가 절대 중복되지 않는다는 뜻으로 확대하면 안 됩니다. Retry를 켜는 순간 호출 대상의 멱등성이 중요해집니다. 결제 성공 후 재고 실패라면 기술적 rollback이 아니라 취소·환불 같은 보상 업무를 설계할 수 있습니다.

## 6. 원문에 포함된 통합 서비스의 역할

Amazon MQ는 ActiveMQ/RabbitMQ 등 기존 메시징 프로토콜·API와의 호환성이 중요한 이전에서 검토합니다. SQS가 관리형이라는 이유만으로 기존 JMS 코드를 무수정 이전할 수 있는 것은 아닙니다. MWAA는 Apache Airflow 기반 DAG와 데이터 파이프라인 스케줄링 운영, AppFlow는 SaaS와 AWS 사이 데이터 흐름, B2B Data Interchange는 EDI 문서를 구조화된 데이터로 변환하는 역할입니다. SWF는 작업 조정의 다른 서비스 모델이며 Step Functions와 이름만 다른 동일 제품으로 보지 않습니다.

첨부 PDF 본문은 Step Functions부터 Amazon MQ까지 발췌되고 SNS/SQS는 목록에 등장합니다. 이 편의 SQS/SNS 상세 원리는 해당 개발자 문서로 보완했습니다. 발췌가 짧다는 이유로 큐의 핵심 실패 구간을 생략하지 않습니다.

## 7. 사고 실험과 관찰 지표

처리 시간이 40초인 작업의 visibility timeout이 30초라면 30초 후 다른 소비자가 같은 작업을 받을 수 있습니다. 업무 시간을 줄이거나 적절한 timeout과 연장 heartbeat를 설계하되, 중복 방지는 별도로 둡니다. 유입 100건/초, 총 처리 80건/초라면 backlog는 초당 20건씩 늘어납니다. 큐가 있다는 것은 시간을 벌었다는 뜻이지 무한한 용량 문제가 해결됐다는 뜻이 아닙니다. 대기 건수·최고 대기 시간·실패율·DLQ·소비자 처리량을 함께 봅니다.

## 깊이 읽기: 메시지 한 건의 수명과 중복이 만들어지는 순간

### 접수·수신·처리 완료를 각각 다른 사건으로 보기

택배 접수증을 받았다는 것은 물건을 배달했다는 뜻이 아닙니다. 마찬가지로 producer의 전송 성공은 큐 접수를 뜻하고 consumer의 수신 성공은 업무 완료를 뜻하지 않습니다. SQS 메시지를 받으면 일정 시간 다른 수신에서 보이지 않도록 하는 visibility timeout이 적용됩니다. 소비자가 업무를 끝낸 뒤 메시지를 삭제해야 그 메시지의 일반적인 처리 수명이 끝납니다.

소비자가 죽거나 삭제하지 못하면 visibility 시간이 지난 뒤 다시 처리될 수 있습니다. 따라서 메시지를 받자마자 삭제하면 처리 중 장애에서 업무를 잃을 수 있고, 처리 뒤 삭제하면 중복을 고려해야 합니다. 이 두 선택의 차이가 at-most-once와 at-least-once를 이해하는 출발점입니다. Standard queue는 중복과 최선 노력 순서 보장을 전제로 설계해야 합니다.

### DB 커밋 전후를 시간표로 써 보기

| 시각 | 사건 | 이때 죽으면 남는 것 |
|---|---|---|
| T1 | 메시지 수신 | 원본 메시지는 재등장 가능 |
| T2 | DB 트랜잭션 시작 | 미커밋 변경은 완료로 취급하지 않음 |
| T3 | 업무 갱신과 처리 기록 커밋 | 업무는 완료됐으나 큐는 남을 수 있음 |
| T4 | 메시지 삭제 | 정상 처리 종료 |

가장 헷갈리는 구간은 T3와 T4 사이입니다. 다음 소비자는 같은 메시지를 받더라도 이미 완료된 업무임을 식별해야 합니다. 업무 ID에 unique 제약을 둔 처리 기록과 실제 변경을 같은 DB 트랜잭션에 넣는 방식이 한 예입니다. “처리 여부 확인 → 업무 변경”을 아무 보호 없이 분리하면 두 소비자가 동시에 확인하고 둘 다 변경할 수 있으므로 원자성이 중요합니다.

외부 API 호출은 로컬 DB 트랜잭션으로 되돌릴 수 없습니다. 외부 시스템의 idempotency key를 사용하거나 요청 결과를 조회해 조정할 수 있어야 합니다. 처리 기록을 먼저 완료로 저장해 놓고 외부 호출이 실패하면 작업을 놓칠 수 있고, 외부 호출 뒤 저장이 실패하면 재호출 위험이 있습니다. 정확히 한 번의 업무 효과는 큐 설정 하나보다 넓은 설계입니다.

### Outbox는 발행의 누락을 줄이되 중복은 남긴다

주문 상태와 “이벤트를 보내야 한다”는 outbox 행을 같은 DB 거래로 저장합니다. 별도의 publisher가 outbox를 읽어 큐로 보내고 발행 상태를 갱신합니다. 이렇게 하면 주문은 저장됐는데 이벤트를 보낼 기록이 없는 문제를 줄일 수 있습니다. 하지만 큐 전송 성공 후 outbox 완료 표시 전에 장애가 나면 같은 이벤트를 다시 발행할 수 있습니다. 그래서 소비자의 멱등성이 계속 필요합니다.

Outbox의 운영도 설계해야 합니다. 오래된 미발행 행, 반복 실패 행, 테이블 보존 기간, 여러 publisher의 작업 분배, 이벤트 버전 호환성을 관찰합니다. “비동기니까 언젠가 되겠지”가 아니라 가장 오래된 미발행 시간과 재시도 종료 후 처리 절차를 정합니다. 이벤트 ID와 업무 ID를 함께 남기면 중복 발행과 중복 업무를 구별하기 쉽습니다.

### FIFO의 순서는 전체가 아니라 그룹 단위로 생각하기

한 주문의 상태 변경은 순서가 중요하지만 서로 다른 주문까지 모두 한 줄로 처리할 필요는 없을 수 있습니다. MessageGroupId를 업무 단위에 맞추면 같은 그룹의 순서를 유지하면서 다른 그룹을 병렬로 처리하는 방향을 검토할 수 있습니다. 모든 메시지를 한 그룹으로 몰면 처리 병렬성이 제한되고 한 문제 메시지의 영향이 커질 수 있습니다.

중복 제거 기능이 있다고 외부 DB 변경이 영원히 정확히 한 번이라는 뜻은 아닙니다. 서비스의 중복 제거 범위·시간과 애플리케이션의 업무 ID 수명은 다를 수 있습니다. DLQ로 문제 메시지를 빼는 선택도 후속 메시지와의 순서 의미를 바꿀 수 있습니다. 주문 취소가 승인보다 먼저 적용되면 안 되는 업무라면 상태 전이 규칙으로 방어해야 합니다.

### Lambda 배치 처리의 실패 범위

큐에서 받은 배치 중 한 건만 실패해도 설정과 응답 방식에 따라 성공한 항목까지 다시 처리될 수 있습니다. 지원되는 partial batch response를 사용하면 실패한 항목을 구분해 재처리 범위를 줄일 수 있습니다. 그러나 FIFO의 순서, 함수의 예외 처리, item ID 매핑을 맞춰야 하며 멱등성을 제거하는 기능은 아닙니다. 배치 크기를 늘리면 호출 비용을 줄일 수 있지만 실패 시 영향과 처리 시간도 달라집니다.

## 더 깊은 면접 Q&A: 재시도할수록 안전해지는가

<details><summary>Q. Visibility timeout을 아주 길게 두면 중복이 없어지나요?</summary><p><strong>답변:</strong> 중복 가능성을 모두 없애지 못하고 소비자 장애 후 재처리가 시작되는 시간을 늦출 수 있습니다. 정상 처리 시간 분포와 긴 작업의 연장 방식, 장애 감지 목표를 함께 봅니다. 너무 짧으면 작업 중 재등장하고 너무 길면 실패 회복이 늦습니다.</p><p><strong>꼬리 질문:</strong> 연장 heartbeat가 멈췄을 때 기존 작업이 완전히 멈췄는지도 보장되지 않을 수 있습니다. visibility를 완벽한 분산 락처럼 믿지 말고 저장 단계의 멱등성과 조건부 갱신으로 업무를 보호합니다.</p></details>
<details><summary>Q. DLQ로 간 메시지는 삭제해도 되나요?</summary><p><strong>답변:</strong> DLQ는 처리 불가 원인을 조사하고 복구하기 위한 격리 지점입니다. 원인 확인 없이 삭제하면 업무를 잃을 수 있습니다. 스키마 오류, 권한 오류, 외부 장애, 잘못된 데이터처럼 유형을 나누고 재처리 또는 수동 보정 기준을 정합니다.</p><p><strong>재처리 조건:</strong> 원인을 해결했는지, 원래 메시지의 업무가 이미 일부 완료됐는지, 새 코드가 옛 스키마를 이해하는지 확인합니다. 수천 건을 한 번에 재주입해 같은 장애를 다시 만들지 않도록 속도도 제한합니다.</p></details>
<details><summary>Q. 소비자를 두 배 늘리면 처리량도 두 배인가요?</summary><p><strong>답변:</strong> 독립적인 작업이고 DB·외부 API·키 분포에 여유가 있을 때 근접할 수 있지만 일반적으로 보장되지 않습니다. 같은 주문 그룹의 순차 처리, DB 락, 외부 API 한도는 병렬성을 제한합니다.</p><p><strong>측정:</strong> 입력량, 성공 처리량, 실패율, 메시지 나이, 의존성 지연을 함께 봅니다. 큐 길이가 줄어도 실패를 DLQ로 빠르게 보내고 있다면 정상적인 용량 개선이라고 말할 수 없습니다.</p></details>
<details><summary>Q. SNS로 여러 시스템에 보냈으면 모두 처리한 것을 알 수 있나요?</summary><p><strong>답변:</strong> 발행과 각 구독자의 업무 완료는 별개입니다. 필요하다면 구독자별 큐와 처리 결과 이벤트, 업무 상태 저장소를 둡니다. 모든 후속 작업의 완료 조건이 중요하면 워크플로 관리나 명시적 조정 로직을 검토합니다.</p><p><strong>예:</strong> 주문 후 이메일 실패가 주문 취소 사유인지, 정산 실패는 반드시 재처리해야 하는지 업무별로 다릅니다. 메시징 서비스가 그 사업 규칙을 대신 결정하지 않습니다.</p></details>

## 직접 풀어 보기: 열 건 중 한 건만 실패했다

소비자가 메시지 열 건을 배치로 받아 아홉 건의 DB 변경을 완료하고 한 건에서 실패했습니다. 전체 배치를 다시 받으면 어떤 문제가 생길까요? 부분 실패 응답을 지원하는 경우와 그렇지 않은 경우를 각각 생각해 보세요.

<details><summary>해설 펼치기 — 판단 과정과 조건을 바꾼 경우</summary><p><strong>중복 효과:</strong> 아홉 건이 다시 실행될 수 있으므로 이미 완료한 업무를 식별해야 합니다. 메시지 ID만으로 충분한지, 발행 재시도에서 다른 ID로 같은 업무가 오는지도 봅니다. 업무 키 기준의 중복 방어가 중요할 수 있습니다.</p><p><strong>부분 실패:</strong> 지원되는 설정과 응답 규격으로 실패 항목만 알리면 재처리 범위를 줄일 수 있습니다. 실패 항목 ID를 잘못 매핑하면 누락이나 불필요한 반복이 생길 수 있으므로 테스트해야 합니다.</p><p><strong>순서:</strong> 같은 순서 그룹의 앞 항목이 실패했는데 뒤 항목을 계속 처리해도 되는지 확인합니다. 일반 Standard 배치와 FIFO 업무의 순서 계약을 같은 방식으로 취급하지 않습니다.</p><p><strong>최종 실패:</strong> 계속 실패하는 항목은 원인을 고치고 재처리할 별도 경로가 필요합니다. DLQ 이동은 업무 성공이 아니므로 사용자 상태와 운영 알림에도 반영합니다.</p></details>
