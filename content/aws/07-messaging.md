## 1. 접수 창구와 방송실은 다르다

입고 검수 결과가 나오면 재고 반영·문자 알림·통계 집계가 필요하다고 가정합시다. 접수 직원이 세 작업을 모두 끝낼 때까지 기다리면 가장 느린 작업 때문에 전체 응답이 늦어집니다. 해야 할 일을 접수함에 넣고 담당 작업자가 꺼내 처리하면 속도를 분리할 수 있습니다. 이것이 큐의 비유입니다. 반면 결과가 나왔다는 사실을 여러 부서에 알려 각자 행동하게 하는 것은 방송에 가깝습니다.

SQS는 작업을 보관하고 소비자가 가져가는 큐, SNS는 구독자에게 메시지를 배포하는 pub/sub, EventBridge는 이벤트의 내용과 규칙에 따라 대상으로 전달하는 이벤트 버스, Step Functions는 여러 단계의 상태와 순서를 관리하는 워크플로입니다. 이들은 함께 사용할 수도 있습니다.

## 2. SQS에서 메시지는 받는 순간 사라지지 않는다

기본 흐름은 전송 → 수신 → 일정 시간 숨김 → 업무 처리 → 삭제입니다. visibility timeout은 다른 소비자가 같은 작업을 곧바로 집어 가지 않도록 일시적으로 숨기는 기간입니다. 처리 완료 전에 소비자가 죽으면 삭제되지 않은 메시지는 다시 보일 수 있습니다. timeout이 너무 짧으면 아직 처리 중인데 다시 전달될 수 있고, 너무 길면 실패한 작업의 재시작이 늦어집니다.

Standard 큐는 적어도 한 번 전달 모델이므로 중복을 전제로 설계합니다. visibility timeout도 완벽한 분산 락으로 취급하면 안 됩니다. long polling은 메시지를 기다리며 불필요한 빈 응답을 줄이는 방식이고, 메시지 보존 기간은 큐에 얼마나 오래 남길지 결정합니다. visibility timeout·retention·애플리케이션 timeout은 서로 다른 시계입니다.

처리 실패를 무한 반복하는 poison message는 DLQ로 분리할 수 있습니다. DLQ는 자동으로 문제를 해결하는 곳이 아닙니다. 실패 이유·메시지 나이·재처리 권한·수정 후 redrive 절차를 정해야 합니다. 정상 메시지까지 너무 빨리 DLQ로 보내지 않도록 일시 장애와 영구 오류를 구분합니다.

## 3. 가장 중요한 실패 구간: DB 커밋과 메시지 삭제 사이

소비자가 재고를 10개 늘리고 DB 커밋에 성공했습니다. 그런데 SQS 삭제 전에 프로세스가 죽었습니다. 재전달된 메시지를 그대로 실행하면 재고가 20개 늘어납니다. 큐가 고장 난 것이 아니라 외부 DB 변경과 큐 삭제가 하나의 원자적 트랜잭션이 아니기 때문에 생기는 정상적인 실패 가능성입니다.

해결 방법 중 하나는 업무 이벤트 ID를 unique key로 저장하고, **처리 기록과 업무 변경을 같은 DB 트랜잭션 안에서** 수행하는 것입니다. 첫 처리에서 기록과 재고 변경을 커밋하고, 재전달에서는 이미 처리된 ID임을 확인한 뒤 성공으로 마무리합니다. 처리 기록만 먼저 저장한 뒤 업무 처리를 별도 트랜잭션으로 하면 중간 실패 때 영구 누락될 수 있습니다. 외부 결제·메일처럼 DB 트랜잭션에 묶이지 않는 부수 효과는 제공자의 멱등키나 별도 상태 전이까지 필요합니다.

생산자 쪽에도 DB 커밋과 메시지 전송 사이 간격이 있습니다. 주문은 저장됐지만 이벤트 전송이 실패할 수 있습니다. outbox는 업무 데이터와 발행할 이벤트를 같은 DB 트랜잭션에 저장하고 별도 전달자가 재시도하는 패턴입니다. 전달 중복은 여전히 가능하므로 소비자 멱등성과 함께 사용합니다.

## 4. FIFO: 순서를 어느 범위에서 지킬 것인가

FIFO 큐는 message group 안에서 순서를 다루고 전송 중복 제거 기능을 제공합니다. 모든 업무를 단일 group에 넣으면 순서 경계가 커져 병렬성이 제한됩니다. 주문별 순서가 필요하면 orderId를 group 기준으로 검토하고, 서로 다른 주문은 독립적으로 처리할 수 있게 합니다. 다만 한 주문의 느린 메시지가 뒤의 같은 group을 막을 수 있습니다.

전송 중복 제거와 업무 부수 효과의 정확히 한 번 실행은 다릅니다. 소비자가 DB 커밋 후 삭제 전에 죽는 문제는 FIFO라는 이름만으로 사라지지 않습니다. 순서가 중요한 업무를 DLQ로 옮기면 뒤 메시지 처리와 상태 전이에도 영향을 줄 수 있으므로 재처리 순서를 설계해야 합니다.

## 5. SNS·EventBridge·Step Functions 비교

| 요구 | 출발 후보 | 확인할 점 |
|---|---|---|
| 작업을 모아 소비자 속도로 처리 | SQS | backlog·중복·재처리 |
| 같은 알림을 여러 구독자에 배포 | SNS | 구독 형태·필터·전달 실패 |
| 이벤트 내용으로 여러 대상에 라우팅 | EventBridge | 규칙·스키마·권한·대상 재시도 |
| 승인→처리→보상 같은 다단계 흐름 | Step Functions | 상태·Retry/Catch·실행 모델 |

SNS 뒤에 부서별 SQS를 놓으면 각 부서는 자기 속도로 소비할 수 있습니다. 하나의 큐를 세 부서가 경쟁해서 읽으면 모든 부서가 모든 이벤트를 받는 구조가 아닙니다. EventBridge의 규칙과 archive/replay 같은 기능도 전달 보장을 이해하고 사용해야 하며, 외부 시스템의 원자성을 대신하지 않습니다.

Step Functions의 Standard와 Express는 실행 시간·기록·처리 보장·비용 특성이 다릅니다. 워크플로가 정확히 한 번 상태를 진행한다는 설명을 외부 API의 영구 부수 효과가 절대 중복되지 않는다는 뜻으로 확대하면 안 됩니다. Retry를 켜는 순간 호출 대상의 멱등성이 중요해집니다. 결제 성공 후 재고 실패라면 기술적 rollback이 아니라 취소·환불 같은 보상 업무를 설계할 수 있습니다.

## 6. 원문에 포함된 통합 서비스의 역할

Amazon MQ는 ActiveMQ/RabbitMQ 등 기존 메시징 프로토콜·API와의 호환성이 중요한 이전에서 검토합니다. SQS가 관리형이라는 이유만으로 기존 JMS 코드를 무수정 이전할 수 있는 것은 아닙니다. MWAA는 Apache Airflow 기반 DAG와 데이터 파이프라인 스케줄링 운영, AppFlow는 SaaS와 AWS 사이 데이터 흐름, B2B Data Interchange는 EDI 문서를 구조화된 데이터로 변환하는 역할입니다. SWF는 작업 조정의 다른 서비스 모델이며 Step Functions와 이름만 다른 동일 제품으로 보지 않습니다.

첨부 PDF 본문은 Step Functions부터 Amazon MQ까지 발췌되고 SNS/SQS는 목록에 등장합니다. 이 편의 SQS/SNS 상세 원리는 해당 개발자 문서로 보완했습니다. 발췌가 짧다는 이유로 큐의 핵심 실패 구간을 생략하지 않습니다.

## 7. 사고 실험과 관찰 지표

처리 시간이 40초인 작업의 visibility timeout이 30초라면 30초 후 다른 소비자가 같은 작업을 받을 수 있습니다. 업무 시간을 줄이거나 적절한 timeout과 연장 heartbeat를 설계하되, 중복 방지는 별도로 둡니다. 유입 100건/초, 총 처리 80건/초라면 backlog는 초당 20건씩 늘어납니다. 큐가 있다는 것은 시간을 벌었다는 뜻이지 무한한 용량 문제가 해결됐다는 뜻이 아닙니다. 대기 건수·최고 대기 시간·실패율·DLQ·소비자 처리량을 함께 봅니다.
