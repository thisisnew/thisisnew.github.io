## 1. 실행할 곳과 관리할 사람을 함께 고른다

식당을 운영한다고 생각해 봅시다. 주방 전체를 빌려 직접 관리하는 방식은 EC2에 가깝습니다. 조리 도구와 재료를 정해진 포장 단위로 배치하는 것이 컨테이너라면, 여러 조리대를 배치하고 고장 난 조리대를 교체하는 관리자는 ECS나 Kubernetes입니다. 주문마다 작은 조리 작업을 맡기는 방식은 Lambda에 가깝습니다. 다만 비유와 달리 Lambda도 실제 서버 위에서 실행되고, 컨테이너가 반드시 서버리스인 것도 아닙니다.

핵심 질문은 세 가지입니다. **무엇을 실행하는가, 얼마나 오래 실행하는가, 운영체제와 실행 용량을 누가 관리하는가?** 이 질문에 답한 뒤 서비스 이름을 선택해야 합니다.

## 2. EC2의 내부 흐름: 이미지에서 요청 처리까지

EC2는 가상 서버 인스턴스입니다. AMI는 시작에 필요한 OS와 소프트웨어 구성을 담는 이미지이고, instance type은 CPU·메모리·네트워크 등의 자원 형태를 정합니다. 시작 템플릿에는 이미지, 유형, 보안 그룹, IAM instance profile 등의 시작 설정을 담을 수 있습니다. 인스턴스가 켜졌다고 서비스가 준비된 것은 아닙니다. OS 부팅, 설정 로딩, Java 프로세스 시작, DB 연결, 캐시 준비를 거쳐야 실제 트래픽을 받을 수 있습니다.

일반 목적·컴퓨팅 최적화·메모리 최적화·스토리지 최적화·가속 컴퓨팅은 병목이 다른 작업을 위한 선택지입니다. Java 서비스가 느릴 때 CPU가 낮다고 더 작은 인스턴스로 바꾸면 안 됩니다. DB 대기·메모리 부족·디스크 지연일 수 있기 때문입니다. burstable 인스턴스는 CPU 크레딧 조건도 확인합니다. 지속적인 고부하와 짧은 순간 부하는 같은 평균 CPU라도 비용과 성능이 다를 수 있습니다.

EBS는 인스턴스와 생명주기가 분리될 수 있는 블록 스토리지입니다. instance store는 호스트에 연결된 임시 저장 성격이 강하므로 유일한 원본 데이터 저장소로 쓰면 위험합니다. 재부팅·중지·종료·호스트 장애는 서로 다른 사건이며, 어떤 저장 데이터가 남는지는 저장 방식과 삭제 설정에 따라 판단합니다.

## 3. Auto Scaling은 “CPU가 높으면 복제”보다 넓다

Auto Scaling Group은 최소·희망·최대 용량과 건강 상태를 바탕으로 인스턴스 수를 유지합니다. 건강하지 않은 인스턴스를 교체하는 일과 부하에 맞춰 수를 바꾸는 일은 별개입니다. target tracking은 지표를 목표 수준에 가깝게 유지하려는 정책이고, scheduled scaling은 예상 가능한 시간에 용량을 준비합니다. 애플리케이션 준비 시간과 instance warmup을 고려하지 않으면 새 서버가 충분히 처리하기 전에 또 확장하거나 너무 빨리 축소할 수 있습니다.

큐 소비자는 CPU보다 **인스턴스당 backlog**와 가장 오래된 메시지의 나이가 더 직접적인 지표일 수 있습니다. 가령 1건 처리에 0.2초가 걸리고 한 소비자가 순차 처리하면 초당 약 5건입니다. 1분 안에 대기 작업 3,000건을 처리하려면 신규 유입이 없다는 단순 가정에서 10개 소비자의 처리량이 필요합니다. 실제로는 유입·병렬성·외부 API 제한·DB 용량을 포함해야 합니다.

축소할 때는 새 요청을 막고 진행 중 요청을 마무리해야 합니다. LB의 deregistration delay, 애플리케이션 graceful shutdown, 큐 visibility timeout을 따로 설정하면 종료 중 중복 처리나 요청 실패가 생길 수 있습니다. 단순히 프로세스를 즉시 죽이는 배포는 자동 확장과 잘 맞지 않습니다.

## 4. Lambda: 함수가 실행되는 단위를 이해하기

Lambda는 이벤트를 받아 함수를 실행합니다. 실행 환경 준비가 필요할 때 초기화 지연이 발생할 수 있고, 재사용되는 환경에서는 초기화 비용을 줄일 수 있습니다. 그러나 환경 재사용을 영속 상태 보장으로 생각하면 안 됩니다. 임시 파일과 메모리 캐시는 최적화 수단일 뿐, 업무 원본은 외부 저장소에 둡니다.

동시성은 동시에 진행 중인 호출 수입니다. 안정 상태의 근사로 `동시성 ≈ 초당 호출 수 × 평균 실행 시간(초)`를 사용할 수 있습니다. 초당 100회 호출되고 평균 0.5초가 걸리면 약 50개가 동시에 실행됩니다. 실행 시간이 DB 지연으로 5초가 되면 같은 유입에도 약 500개가 필요합니다. Lambda를 무작정 늘리면 DB 연결이 먼저 한계에 닿을 수 있습니다. reserved concurrency는 함수의 동시성 한계를 정하고 다른 함수와 자원을 나누는 데 쓰이며, provisioned concurrency는 준비된 실행 환경으로 초기화 지연을 줄이는 목적입니다.

호출 방식마다 재시도와 오류 처리 계약이 다릅니다. 동기 호출 실패는 호출자가 처리하고, 비동기 호출과 큐 이벤트 소스는 각자의 재시도 동작을 가집니다. “Lambda가 알아서 정확히 한 번 실행한다”는 가정은 금물입니다. 장시간 상주 연결·특정 OS 제어·실행 시간 제한을 넘는 작업은 다른 실행 환경을 검토합니다.

## 5. ECR·ECS·EKS·Fargate는 대체어가 아니다

| 요소 | 책임 | 오해하기 쉬운 점 |
|---|---|---|
| ECR | 컨테이너 이미지 보관·배포 | 이미지를 저장해도 실행되지는 않음 |
| ECS | task·service 단위 배치와 유지 | EC2 또는 Fargate 등의 실행 용량과 결합 |
| EKS | 관리형 Kubernetes 제어 영역 | 워커·애드온·네트워크·앱 운영이 모두 없어지지 않음 |
| Fargate | 컨테이너 실행용 서버 용량 관리 | 컨테이너 이미지·권한·앱 자원 설정은 고객 책임 |
| EC2 | 가상 서버 용량 | 컨테이너 없이도, 컨테이너 호스트로도 사용 가능 |

ECS의 task definition은 이미지·자원·포트·role 등의 실행 명세이고, service는 원하는 task 수를 유지하는 역할을 합니다. task role은 애플리케이션이 AWS API를 호출하는 권한, execution role은 이미지 가져오기나 로그 전달 등 실행 지원 작업의 권한이라는 구분이 중요합니다. EKS를 선택하는 이유는 Kubernetes 생태계·표준 도구·팀 경험과 연결해야 합니다. 단지 컨테이너를 쓴다는 이유만으로 EKS가 필수는 아닙니다.

## 6. 원문에 나오는 다른 컴퓨팅 서비스의 위치

Batch는 대량 작업의 대기열·스케줄링·실행 용량을 조정합니다. Elastic Beanstalk는 애플리케이션 배포와 기반 리소스 구성을 추상화하고, Lightsail은 단순한 묶음형 환경을 제공합니다. Image Builder는 이미지 제작·검증 파이프라인을 관리하고, Amazon Linux는 실행 OS 선택지입니다. Serverless Application Repository는 재사용할 서버리스 애플리케이션 배포물을 찾는 곳이지 별도의 실행 서버가 아닙니다.

Outposts는 온프레미스로 AWS 인프라와 서비스를 확장하는 하이브리드 방식이고, Wavelength는 통신망 엣지 가까운 실행 요구와 연결됩니다. App2Container는 기존 애플리케이션의 컨테이너화 지원, ROSA는 관리형 OpenShift, VMware Cloud on AWS는 VMware 기반 이전과 운영 연속성이라는 맥락에서 이해합니다. App Runner는 소스나 이미지에서 웹 애플리케이션을 배포하는 추상화를 제공하지만, 현재 공식 문서는 신규 고객을 받지 않으며 기존 고객만 계속 사용할 수 있다고 안내합니다. 새 구축에는 이 제한을 반영해야 합니다. [App Runner 상태 공지](https://docs.aws.amazon.com/apprunner/latest/dg/apprunner-availability-change.html) 핵심은 제품 이름을 암기하기보다 “배포 추상화·이미지 제작·배치·하이브리드”라는 역할을 분리하는 것입니다.

## 7. 가상 장애: 확장했더니 DB가 먼저 죽었다

이미지 처리 Lambda가 빨리 늘어나며 각 실행이 새 DB 연결을 만들었습니다. 함수의 CPU는 여유가 있지만 DB 연결 수가 한계에 도달해 timeout이 증가했습니다. timeout 때문에 재시도가 늘어 동시성이 더 커졌습니다. 해결은 Lambda 용량 확대 하나가 아닙니다. 동시성 제한, 큐로 유입 완충, 짧은 트랜잭션, 연결 재사용 또는 적절한 프록시, 멱등 처리를 함께 설계합니다. DB가 견딜 처리량을 넘지 않도록 전체 경로의 예산을 정합니다.

실습 대신 먼저 초당 유입 200건, 처리 시간 0.1초·1초·3초를 표로 계산해 보세요. 필요한 동시성은 20·200·600으로 바뀝니다. 평균만으로는 꼬리 지연과 burst를 담지 못하므로 실제 배포 전에는 p95/p99와 throttling도 관찰해야 합니다.

## 깊이 읽기: 컴퓨팅 용량이 생기고 사라지는 전체 과정

### 서버 한 대가 서비스에 참여하기까지

식당에서 새 요리사를 채용했다고 즉시 주문을 받을 수는 없습니다. 출근하고 도구 위치를 익히고 재료를 준비해야 합니다. EC2도 인스턴스 시작, OS 부팅, 프로세스 실행, 설정·비밀정보 조회, DB 연결 준비, 헬스 체크 통과를 거칩니다. 각각 다른 시계이므로 인스턴스의 running 상태를 애플리케이션 ready와 동일시하면 안 됩니다.

배포 이미지에 소프트웨어를 미리 포함하면 시작 시 설치하는 작업을 줄일 수 있습니다. 그러나 비밀정보를 이미지에 굽는 것은 별개의 보안 문제입니다. 코드는 고정된 배포물로 만들고 환경별 설정과 권한은 실행 시 공급하는 식으로 나눕니다. 시작 과정이 오래 걸린다면 CPU만 늘릴 것이 아니라 외부 저장소 다운로드·DNS·비밀정보 조회·DB 연결에서 어느 단계가 늦는지 측정합니다.

### 확장 지표에는 어떤 성질이 필요할까

용량을 두 배로 늘렸을 때 지표가 줄어드는 관계가 있어야 목표 추적에 유리합니다. 예를 들어 균등 분산되는 부하에서 인스턴스당 처리 요청이나 backlog는 용량과 연결됩니다. 전체 큐 길이만 보면 소비자가 늘어도 입력 증가 때문에 길이가 바로 줄지 않을 수 있습니다. 입력률과 평균 작업 시간, 소비자당 병렬 처리 수를 함께 봅니다.

가상 예로 초당 120건이 들어오고 작업 하나가 평균 0.5초라면 필요한 처리 중 동시성은 평균 약 60입니다. 소비자 한 대가 10개씩 병렬 처리한다면 이론적으로 여섯 대가 입력을 따라갑니다. 하지만 여섯 대가 최대치를 꽉 채우면 이미 쌓인 작업을 줄일 여유가 없습니다. backlog 1,200건을 60초에 줄이려면 신규 입력 외에 초당 20건을 추가 처리해야 하므로 총 140건/초가 필요합니다. 실패·긴 작업·DB 제한을 제외한 단순 계산이므로 실제 안전 용량은 시험으로 정합니다.

### Lambda 동시성과 DB 연결 수를 분리하기

함수 동시성 100이 DB 연결 정확히 100개를 의미하지는 않습니다. 실행 환경마다 연결 풀을 만들고 풀의 최대 크기를 10으로 두면 잠재적인 연결 요구는 훨씬 커집니다. 반대로 연결을 늦게 생성하거나 재사용하면 실제 수는 적을 수 있습니다. 따라서 함수 수, 환경당 풀 크기, 연결 수명, DB 최대 연결, 다른 서비스의 연결 사용량을 모두 봅니다.

Reserved concurrency는 해당 함수가 사용할 수 있는 동시성에 상한을 만들고 계정의 동시성을 예약하는 기능입니다. 실행 환경을 미리 초기화하는 기능과는 다릅니다. Provisioned concurrency는 초기화된 환경을 준비해 초기 지연을 줄이는 목적입니다. 준비된 동시성보다 많은 호출이 들어올 때의 처리와 함수 상한은 따로 검토합니다. 이 차이를 구분해야 “DB 보호”와 “cold start 완화”를 다른 설정으로 해결할 수 있습니다.

### 컨테이너 재시작이 데이터 복구는 아니다

컨테이너 이미지는 실행할 프로그램과 의존성을 묶은 배포 단위입니다. 실행 중인 컨테이너의 로컬 변경이 다음 컨테이너에 자동 보존되는 것은 아닙니다. 이미지 처리 중간 파일이라면 다시 만들 수 있지만 유일한 원본이라면 외부의 적절한 저장소에 보관해야 합니다. ECS service가 task 수를 복구해도 애플리케이션의 미완료 업무까지 이해하는 것은 아닙니다.

예를 들어 소비자가 결제 승인 후 종료되면 새 task가 만들어져도 그 결제가 이미 승인됐는지 스스로 알 수 없습니다. 외부 결제 ID나 업무 멱등 키로 상태를 확인해야 합니다. 실행 복구와 업무 복구의 차이는 EC2·ECS·EKS·Lambda 모두에 적용됩니다. 오케스트레이터를 바꿔도 업무 상태 모델은 사라지지 않습니다.

### 종료 순서도 정상 흐름으로 설계하기

1. 새 요청이나 새 작업 수신을 중단합니다. 단순히 프로세스를 먼저 죽이지 않습니다.
2. 이미 시작한 작업의 완료 가능 시간을 판단합니다. 제한 시간 안에 끝낼 수 없는 작업은 안전하게 재처리할 수 있어야 합니다.
3. 완료한 업무의 저장과 메시지 확인 처리를 구분합니다. DB 커밋 후 확인 실패는 중복 가능성이 남습니다.
4. 연결과 자원을 정리하고 종료합니다. 배포 중 이전 버전과 새 버전이 함께 실행되는 시간도 호환성 범위에 포함합니다.

<details><summary>Q. 서버를 늘렸는데 응답이 더 느려질 수도 있나요?</summary><p><strong>답변:</strong> 가능합니다. 각 서버가 DB 연결 풀이나 외부 API 동시성을 갖기 때문에 서버 증가가 공통 의존성 부하를 늘립니다. DB가 포화되면 응답이 늦고 재시도가 늘어 전체 시스템이 악화될 수 있습니다.</p><p><strong>대응:</strong> 앱 대수만이 아니라 전체 연결·동시 요청 예산을 정합니다. 병목이 DB라면 쿼리·트랜잭션·캐시·읽기 분산을 검토하고, 무작정 입력 처리 능력을 늘리지 않습니다. 확장 전후의 성공 처리량과 p99를 함께 비교합니다.</p></details>
<details><summary>Q. CPU 20%인데 큐가 계속 쌓이면 어떻게 조사하나요?</summary><p><strong>답변:</strong> CPU를 쓰는 계산보다 DB 락, 네트워크 응답, 연결 풀 획득, 외부 API 제한에 기다리는 시간일 수 있습니다. 작업 한 건의 시간을 단계별로 나누고 실제 실행 중 동시성·대기 수를 확인합니다.</p><p><strong>꼬리 질문:</strong> 스레드를 늘리면 기다리는 작업만 늘 수도 있습니다. 의존성이 감당할 범위 안에서 병렬성을 실험하고, 처리량이 늘지 않는데 대기 시간만 커지는 지점을 피합니다.</p></details>
<details><summary>Q. Provisioned concurrency를 켜면 모든 Lambda 지연이 사라지나요?</summary><p><strong>답변:</strong> 초기화 지연을 줄이기 위한 준비이지 DB 쿼리나 외부 API 시간을 없애는 설정이 아닙니다. 준비 용량을 넘는 호출, 배포·버전 설정, 호출 경로도 확인해야 합니다. 지연 원인이 어디인지 먼저 측정합니다.</p><p><strong>실무 판단:</strong> 간헐적인 관리 작업은 비용 대비 효과가 낮을 수 있고, 엄격한 응답 목표를 가진 API는 가치가 클 수 있습니다. 동일한 트래픽 조건에서 지연 분포와 총비용을 비교해야 합니다.</p></details>
<details><summary>Q. Spot에 체크포인트를 저장하면 충분한가요?</summary><p><strong>답변:</strong> 저장한 체크포인트를 새 실행이 찾아 이어서 처리할 수 있어야 하고 중간 산출물의 일관성도 맞아야 합니다. 작업 소유권, 중복 실행, 재시작 위치, 최종 결과의 원자적 공개를 함께 설계합니다.</p><p><strong>예:</strong> 파일 100개 중 60개를 처리했다면 파일별 완료 기록으로 나머지를 재처리할 수 있습니다. 그러나 완료 표시 전에 외부 시스템에 결과를 보냈다면 같은 파일을 다시 보내도 업무 효과가 중복되지 않도록 별도 키가 필요합니다.</p></details>

## 직접 풀어 보기: 밀린 작업을 언제 따라잡을까

큐에 6,000건이 쌓였고 초당 100건이 계속 들어옵니다. 확장 후 소비자 전체는 초당 150건을 성공 처리합니다. 모든 작업의 처리량이 일정하다는 가정에서 backlog를 없애는 데 얼마나 걸릴까요? 초당 150건이 단순 수신 건수가 아니라 성공 완료 건수라는 점을 주의하세요.

<details><summary>해설 펼치기 — 판단 과정과 조건을 바꾼 경우</summary><p><strong>순처리량:</strong> 새 입력 100건을 제외하면 기존 대기를 줄이는 속도는 초당 50건입니다. 따라서 6,000÷50=120초가 필요합니다. 6,000÷150=40초라고 계산하면 새 유입을 무시한 것입니다.</p><p><strong>현실의 변수:</strong> 긴 작업·실패 재시도·특정 키의 순서 제약·DB 제한 때문에 실제 속도는 달라집니다. CPU보다 성공 처리량과 가장 오래된 메시지 나이를 함께 봅니다.</p><p><strong>축소 조건:</strong> backlog가 0이 되자마자 용량을 너무 줄이면 다시 쌓일 수 있습니다. 지속 입력을 감당하는 용량과 피크 여유, 안정화 시간을 고려합니다. 작업 중인 소비자가 축소될 때의 종료 절차도 필요합니다.</p><p><strong>조건 변경:</strong> 입력이 초당 170건으로 늘면 확장된 150건/초로도 따라잡을 수 없습니다. 대기열은 완충 장치이므로 처리 확장·입력 제한·업무 조정 중 추가 선택이 필요합니다.</p></details>
