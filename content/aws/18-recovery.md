## 1. 소화기를 샀다는 것과 대피할 수 있다는 것

소화기를 비치했어도 위치를 모르거나 문이 잠겨 있으면 위기에서 쓸 수 없습니다. 백업·DR도 같습니다. 백업 파일이 있다는 사실, 복구 절차가 있다는 사실, 목표 시간 안에 실제 복구했다는 사실은 서로 다른 단계입니다. 이 편은 원문에서 가장 긴 REL 6~13을 관찰→변경→보호→복구→시험의 흐름으로 연결합니다.

## 2. REL 6: 모니터링은 수집부터 행동까지

모든 주요 구성 요소에서 지표와 로그를 만들고, 업무 성공률·지연·처리량으로 집계하며, 담당자에게 알리고, 검증된 조치를 자동화합니다. 로그 분석과 end-to-end trace로 원인을 좁히고 수집 범위를 정기적으로 검토합니다. REL06-BP01~07의 핵심은 “메트릭을 보낸다”에서 끝나지 않는 피드백 루프입니다.

서버가 살아 있는지와 사용자가 업무를 완료하는지는 다릅니다. 검수 확정 API는 200을 반환하지만 후속 재고 반영이 계속 실패할 수 있습니다. 이때 HTTP 성공률만으로 신뢰성을 설명하면 안 됩니다. 비동기 완료 지연·실패 작업 수·업무 정합성 지표를 추가합니다. 모든 알람에는 행동과 소유자가 있어야 하며, 알람이 너무 많아 무시되는 상태도 신뢰성 문제입니다.

## 3. REL 7: 수요 변화와 장애를 구분해 용량 준비

자동 자원 확보, 장애 시 대체, 부하 증가 시 확장, 부하 테스트가 REL07-BP01~04입니다. 평균 CPU 하나로는 DB 대기나 큐 지연을 설명할 수 없습니다. 확장 지표가 실제 병목을 반영하는지 확인합니다. 새 인스턴스의 초기화·JIT warmup·캐시 채움·건강 확인 시간이 확장 지연에 포함됩니다.

시험은 일정한 부하뿐 아니라 급격한 burst와 일부 자원 상실을 포함해야 합니다. 3개 AZ에서 각각 50% 사용하던 구성도 한 AZ 상실 뒤 남은 두 AZ의 부하가 어떻게 변하는지 계산합니다. 균등 분산과 선형 성능이라는 단순 가정에서는 각 AZ 부하가 75%로 올라갑니다. 실제로는 hot key와 공통 DB 병목 때문에 단순 계산보다 나쁠 수 있습니다.

## 4. REL 8: 변경은 복구 가능한 작은 단위로

런북, 기능 테스트, 복원력 테스트, 불변 인프라, 자동 배포가 핵심입니다. 기존 서버에 손으로 패키지를 바꾸는 대신 검증한 새 이미지로 교체하면 이전 상태를 재현하기 쉽습니다. canary는 일부 트래픽에서 결과를 관찰하고, blue-green은 두 환경을 준비해 전환할 수 있지만 자원·IP·DB 연결이 일시적으로 두 배 가까이 필요할 수 있습니다.

애플리케이션 rollback과 DB schema rollback은 같은 문제가 아닙니다. 새 코드가 컬럼을 삭제하거나 데이터를 변환하면 옛 코드를 되돌려도 동작하지 않을 수 있습니다. expand-and-contract 방식으로 새·옛 코드가 공존할 수 있는 기간을 만들고 데이터 변경의 되돌림 가능성을 별도로 검증합니다. 배포 성공 지표에는 시작 여부뿐 아니라 오류율·지연·업무 결과가 포함되어야 합니다.

## 5. REL 9: 무엇을 백업하고 무엇을 재생성할까

백업 대상 식별, 보호와 암호화, 자동 백업, 정기 복원이 REL09-BP01~04입니다. 원본 주문·검수 결과는 재생성하기 어렵지만 썸네일·캐시는 원본에서 다시 만들 수 있습니다. 데이터뿐 아니라 설정·IaC·비밀 접근·인증서·외부 연동 정보를 복구 계획에 포함합니다. 백업이 다른 계정에 있어도 키 권한이나 조직 정책이 막으면 읽지 못할 수 있습니다.

복제는 가용성과 낮은 RPO에 도움이 되지만 논리 오류도 빠르게 전파할 수 있습니다. 잘못된 삭제를 복제한 두 사본은 올바른 과거 시점의 백업을 대신하지 못합니다. point-in-time restore가 지원되더라도 보존 범위·복구 소요·업무 검증을 확인해야 합니다. 정기 복원에서 행 수뿐 아니라 핵심 업무 시나리오를 실행합니다.

## 6. REL 10: 장애 격리와 셀

여러 위치 배치, 단일 위치 구성 요소의 자동 복구, bulkhead가 REL10-BP01~03입니다. 한 고객이나 창고의 폭주가 전체를 막지 않도록 자원 풀·큐·데이터 경계를 나눌 수 있습니다. 셀 구조는 일정 크기의 독립 처리 단위를 반복하고 고객을 셀에 배치해 영향 범위를 제한하는 접근입니다. 공유 인증·라우팅·데이터 계층이 모든 셀의 단일 장애점으로 남지 않는지 확인해야 합니다.

격리를 지나치게 세분화하면 운영·비용·데이터 이동이 복잡해집니다. 최소 격리 단위는 고객 영향과 팀 운영 능력으로 정합니다. 여러 AZ 배치도 모든 서버가 같은 단일 외부 API에 의존하면 그 의존성의 장애는 공유합니다.

## 7. REL 11: 복구 때 새 관리 작업에 덜 의존하기

control plane은 자원을 생성·설정하는 관리 기능, data plane은 이미 구성된 서비스가 실제 요청을 처리하는 기능으로 생각할 수 있습니다. 장애 때마다 새 리소스 생성 API가 성공해야만 복구할 수 있다면 관리 영역 장애에도 영향을 받습니다. **정적 안정성(static stability)**은 이미 준비된 용량과 구성으로 장애 상태에서도 서비스할 수 있게 하는 설계 관점입니다.

이것은 Auto Scaling을 금지한다는 뜻이 아닙니다. 갑작스러운 장애 직후의 필수 기능을 신규 생성에 전적으로 의존하지 않도록 준비하고, 이후 확장을 추가 수단으로 사용한다는 뜻입니다. 정상 때와 장애 때 완전히 다른 무거운 처리 경로를 요구하는 bimodal behavior를 줄입니다. REL11-BP01~07은 감지·정상 대상으로 전환·모든 계층 자동 복구·데이터 영역 활용·정적 안정성·알림·가용성 목표 설계를 포함합니다.

## 8. REL 12: 시험과 사후 분석

원인을 모르는 장애에는 조사 플레이북, 반복 작업에는 런북을 활용합니다. 사고 후에는 누가 실수했는지만 묻지 않고 어떤 조건과 통제가 결과를 만들었는지 분석합니다. 탐지 지연·권한 누락·문서 오류·자동화 위험을 개선 과제로 연결합니다. 잘못된 변경을 막을 검증이 없었다면 개인 주의력만 강조해서는 재발을 줄이기 어렵습니다.

성능·확장 시험, 카오스 엔지니어링, 게임데이는 서로 연결되지만 무작정 장애를 만드는 활동이 아닙니다. 정상 상태 가설, 제한된 영향 범위, 중단 조건, 되돌림, 관찰 지표를 정합니다. AWS FIS 같은 도구를 사용하더라도 안전한 실험 설계가 선행되어야 합니다. REL12-BP01~05는 조사·사후 학습·확장 시험·복원력 실험·정기 훈련을 다룹니다.

## 9. REL 13: RTO와 RPO를 시계 두 개로 보기

RTO는 허용하는 복구 시간 목표, RPO는 허용하는 데이터 손실의 시간 범위 목표입니다. 10:00에 장애가 났고 09:55까지 복구 가능한 데이터가 있다면 잠재적 손실 구간은 5분입니다. 서비스를 10:20에 정상 업무까지 검증해 재개했다면 실제 복구 시간은 20분입니다. 목표와 관찰 결과를 구분해야 합니다. 복구 서버를 켠 시점이 아니라 사용자가 정상 업무를 할 수 있는 시점을 기준으로 정합니다.

| 전략 | 평소 준비 | 일반적 경향 | 확인할 함정 |
|---|---|---|---|
| 백업과 복원 | 복구 데이터·절차 | 비용 낮음, 복구 작업 많음 | 데이터 복원·인프라 생성 시간 |
| Pilot light | 핵심 데이터·최소 기반 | 나머지를 장애 시 확장 | 관리 API·용량 확보 의존 |
| Warm standby | 축소된 전체 환경 | 확장 후 전환 | 축소 환경의 실제 준비 상태 |
| Multi-site active-active | 여러 곳이 실제 처리 | 빠른 전환 가능, 복잡도·비용 큼 | 쓰기 충돌·공통 의존·정합성 |

이 표의 경향은 보장된 분 단위 수치가 아닙니다. 데이터 규모·복제·애플리케이션 시작·DNS·수동 승인·외부 시스템에 따라 달라집니다. REL13-BP01~05는 목표 정의, 전략, 실제 테스트, DR 환경 drift 관리, 자동 복구입니다. DR 리전의 코드는 최신인데 secret이나 방화벽이 옛날 설정이면 실제 복구는 실패할 수 있습니다.

## 10. 가상 DR 실패와 연습

분기별 백업은 성공했지만 복구 훈련에서 KMS 권한이 없어 데이터가 열리지 않았습니다. 권한을 고친 뒤에는 외부 거래처가 DR 리전 IP를 허용하지 않아 통신이 막혔습니다. 이 사례가 보여 주는 것은 DB 백업과 전체 업무 복구의 차이입니다. 복구 계획에는 데이터·키·신원·네트워크·DNS·할당량·외부 의존·업무 검증을 포함해야 합니다.

RTO 30분을 가정하고 탐지 3분, 판단 4분, 전환 8분, 데이터 확인 10분, 업무 검증 5분을 배분해 보세요. 합이 이미 30분이면 예상 밖 지연 여유가 없습니다. 병렬 가능한 단계와 사전 자동화 가능한 단계를 찾아야 합니다. 실제 시험에서는 각 단계의 측정값과 실패 원인을 남깁니다.

## 11. 상세 면접 Q&A

<details><summary>Q. 백업과 replica 중 어느 것이 더 중요하나요?</summary><p>해결하는 실패가 다릅니다. replica는 일부 인프라 장애와 읽기 확장에 도움이 되지만 잘못된 변경을 함께 반영할 수 있습니다. 백업은 과거 상태 복구에 필요하지만 복원 시간이 듭니다. 업무의 RTO/RPO와 논리 오류 시나리오에 맞춰 둘을 조합합니다.</p></details>
<details><summary>Q. active-active면 RPO가 항상 0인가요?</summary><p>그렇지 않습니다. 각 지역의 쓰기와 복제·충돌 해결·일관성 모델에 따라 다릅니다. 두 곳이 요청을 받는다는 사실만으로 데이터가 동시에 원자적으로 커밋되는 것은 아닙니다. 지원하는 데이터베이스 모드와 네트워크 분할 시 동작을 확인해야 합니다.</p></details>
<details><summary>Q. 정적 안정성이면 용량을 낭비하는 것 아닌가요?</summary><p>장애 직후에도 목표 서비스를 유지하기 위해 여유 용량을 사는 선택입니다. 중단 손실과 신규 자원 확보 실패 위험을 비용과 비교합니다. 모든 기능에 같은 수준을 적용할 필요는 없고 필수 경로에 집중할 수 있습니다.</p></details>
<details><summary>Q. 배포 rollback을 자동화하면 안전한가요?</summary><p>코드와 데이터가 이전 버전과 호환되어야 합니다. schema 삭제·데이터 변환·외부 부수 효과는 바이너리를 되돌린다고 복구되지 않습니다. 호환 기간과 데이터 복구 전략을 포함한 배포 설계가 필요합니다.</p></details>
<details><summary>Q. 복구 테스트에서 가장 많이 빠지는 것은 무엇인가요?</summary><p>키와 권한, 외부 허용 목록, DNS 캐시, 서비스 할당량, 운영자 접근, 복구 후 업무 검증처럼 데이터 바깥의 의존성입니다. 실제에 가까운 별도 환경에서 전체 흐름을 수행해야 문서상 성공과 운영 가능성의 차이를 발견할 수 있습니다.</p></details>
