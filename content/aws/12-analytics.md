## 1. 컨베이어와 분석실은 같은 장비가 아니다

창고 센서가 온도를 계속 보내고, 하루 뒤 관리자가 시간대별 평균을 본다고 해 봅시다. 데이터를 받는 통로, 잠깐 보관하는 공간, 계산하는 작업자, 결과를 조회하는 분석실이 필요합니다. Kinesis나 MSK가 데이터를 운반·보관하는 역할을 맡는다고 Athena의 SQL 분석까지 같은 서비스가 처리하는 것은 아닙니다. 분석 시스템을 **수집→저장→가공→조회→공유**로 나누면 긴 제품 목록이 정리됩니다.

## 2. 스트림과 큐의 차이부터

큐에서는 작업 완료 후 메시지를 제거하는 소비 모델을 많이 사용합니다. 로그 기반 스트림은 보존된 레코드를 소비 위치에 따라 읽고 여러 소비자가 독립적으로 다시 처리하는 모델이 중요합니다. 어느 쪽이 더 좋다는 뜻이 아니라 작업 분배와 기록 재생의 요구가 다르다는 뜻입니다.

Kinesis Data Streams는 partition key와 shard 기반의 스트림 처리 개념을 제공합니다. 같은 키의 부하가 집중되면 전체 용량이 남아도 hot shard 문제가 생길 수 있습니다. 소비자는 자신의 처리 위치와 지연을 관리하고, 보존 기간 안에서 재처리를 계획합니다. 전역 순서와 키·shard 안의 순서는 다르므로 “스트림이면 모든 사건이 한 줄로 정렬된다”고 가정하지 않습니다.

MSK는 Apache Kafka의 관리형 운영 선택지입니다. 브로커 운영의 일부가 관리형이 되어도 partition key·consumer group·offset·retention·중복 처리·스키마 호환성은 애플리케이션 책임으로 남습니다. Kafka를 쓴 경험과 생태계가 중요한 요구라면 MSK를, 다른 관리형 스트림 선택이 운영 요구에 더 맞으면 해당 서비스를 비교합니다.

## 3. Firehose와 Flink: 전달과 계산

Data Firehose는 스트리밍 데이터를 지원 목적지에 전달하는 관리형 수집·전달 서비스입니다. 버퍼링과 변환 옵션을 이용할 수 있지만 모든 이벤트를 즉시 단건으로 전달하는 초저지연 경로로 일반화하지 않습니다. 버퍼 크기·시간·목적지·오류 레코드 처리에 따라 지연과 비용이 달라집니다. “S3로 안정적으로 적재하고 나중에 분석”하는 요구와 잘 연결됩니다.

Managed Service for Apache Flink는 상태를 가진 스트림 계산에 사용합니다. 최근 5분의 창고별 평균 온도처럼 시간 창과 상태가 필요할 때 중요합니다. 이벤트가 발생한 시간(event time)과 시스템이 처리한 시간(processing time)은 다릅니다. 늦게 온 데이터까지 어떻게 집계할지 watermark·허용 지연·상태 복구 전략을 정해야 합니다. checkpoint가 있어도 외부 sink의 보장과 함께 검토해야 end-to-end 결과를 설명할 수 있습니다.

## 4. S3·Glue·Lake Formation: 데이터와 설명서와 출입 통제

S3는 데이터 레이크의 객체 저장소로 사용할 수 있습니다. Glue Data Catalog는 테이블·스키마·위치 같은 메타데이터를 관리하는 역할이며 데이터 본문을 자동으로 모두 복사해 보관하는 DB가 아닙니다. crawler는 데이터를 관찰해 메타데이터를 추론하는 데 도움을 주지만 모든 의미적 타입과 변경을 완벽히 판단하지는 않습니다. 스키마 변화가 소비 쿼리를 깨뜨리지 않도록 계약을 관리합니다.

Glue ETL은 데이터를 추출·변환·적재하는 작업을 지원합니다. CSV 로그를 날짜·창고 기준으로 정리하고 Parquet 같은 열 지향 파일로 변환하면 분석 스캔을 줄일 수 있습니다. Lake Formation은 데이터 레이크 권한과 거버넌스에 관련됩니다. IAM·S3·KMS와의 관계를 함께 이해해야 “카탈로그에서 보이니 데이터도 읽힌다”는 오해를 피할 수 있습니다.

## 5. Athena와 Redshift

Athena는 S3 등의 지원 데이터 소스에 SQL로 분석하는 서버리스 쿼리 서비스입니다. S3에 JSON을 쌓아 두었다고 자동으로 최적의 분석 구조가 되는 것은 아닙니다. 날짜 파티션을 만들고 쿼리에 해당 조건을 넣으며 필요한 열만 읽도록 포맷을 개선하면 읽는 데이터량을 줄일 수 있습니다. 작은 파일이 지나치게 많으면 파일 목록·계획·요청 오버헤드가 커질 수 있어 파일 크기도 관리합니다.

Redshift는 데이터 웨어하우스 분석 목적의 선택지입니다. 대규모 분석과 반복적인 BI 질의, 분산 처리·열 저장·데이터 배치와 최적화라는 관점을 가집니다. Serverless 선택지에서도 비용·용량·쿼리 패턴 검토가 없어지는 것은 아닙니다. Athena와 Redshift를 “작으면 Athena, 크면 Redshift”로만 구분하지 말고 반복성·동시성·지연·운영·데이터 모델을 비교하세요.

| 요구 | 출발 후보 | 검증할 병목 |
|---|---|---|
| S3 로그를 가끔 SQL로 탐색 | Athena | 스캔량·파티션·파일 수 |
| 반복적인 대규모 BI | Redshift | 분산·정렬·동시 쿼리 |
| 검색과 로그 탐색 | OpenSearch | 색인·샤드·메모리·보존 |
| Spark/Hadoop 생태계 처리 | EMR | 작업 자원·shuffle·스토리지 |
| 지속적인 상태 기반 스트림 집계 | Flink | 상태 크기·지연·checkpoint |

## 6. 원문의 나머지 분석 서비스

Kinesis Video Streams는 영상 스트림이라는 별도 입력 특성을 다룹니다. OpenSearch Serverless는 운영 용량 관리의 추상화가 다르지만 인덱스와 접근 정책·비용을 이해해야 합니다. Amazon Quick 계열은 분석·시각화와 사용자 소비 맥락, DataZone은 데이터 발견·공유·거버넌스, Clean Rooms는 여러 주체의 제한된 협업 분석이라는 목적입니다.

Data Exchange는 외부 데이터 구독과 공유, Entity Resolution은 서로 다른 기록이 같은 실체인지 연결하는 작업입니다. CloudSearch는 현재 신규 고객을 받지 않는 유지보수 단계입니다. Data Pipeline은 원문에서 데이터 이동·처리 의존성을 정의하는 오케스트레이션 서비스로 소개되며, 실제 신규 구성에서는 현재 이용 조건과 Glue·Step Functions·MWAA 같은 대안의 적합성을 확인합니다. [CloudSearch 상태](https://docs.aws.amazon.com/general/latest/gr/maintenance_services.html) FinSpace는 공식 문서상 2026-10-07 지원 종료가 안내되어 있으므로 이 연재의 작성일에는 신규 시스템 추천으로 다루지 않습니다. 제품 소개를 보존하는 것과 오늘 도입할 도구를 추천하는 것은 분리해야 합니다.

## 7. 가상 장애: 분석 비용이 갑자기 열 배

원본 JSON을 날짜 구분 없이 저장하고 `SELECT *`로 전체 기간을 매번 읽었습니다. 데이터가 늘면서 스캔량과 시간이 함께 커졌습니다. 먼저 쿼리의 필터와 실제 스캔량을 확인합니다. 필요한 열만 읽도록 열 지향 포맷을 검토하고, 날짜 파티션과 적절한 파일 크기를 설계합니다. 파티션을 만들기만 하고 쿼리가 그 조건을 사용하지 않으면 기대한 pruning 효과가 없을 수 있습니다.

실습으로 총 1TB 중 하루치 10GB만 필요한 상황을 계산해 보세요. 날짜로 읽는 범위를 줄이고 열 선택으로 추가 절감할 수 있지만, 압축률·파일 통계·실제 쿼리 엔진 동작에 따라 결과가 달라집니다. 임의 수치를 제품 성능 보장처럼 쓰지 말고 실제 scanned bytes로 검증합니다.

## 깊이 읽기: 업무 데이터가 분석 결과가 되기까지

### 처리할 일과 이미 일어난 사실

큐에 넣은 “이 사진을 분석하라”는 작업 요청과 스트림에 남긴 “입고 검수가 완료됐다”는 사건은 의미가 다릅니다. 작업 큐에서는 누군가 일을 끝내는 것이 중요하고, 사건 스트림에서는 여러 소비자가 각자의 목적으로 같은 사실을 읽고 재처리하는 것이 중요할 수 있습니다. 서비스 선택 전 메시지가 명령인지 사실인지부터 구분하면 보존·재생·구독 구조가 명확해집니다.

실시간 대시보드와 일별 정산도 요구가 다릅니다. 대시보드는 몇 초 늦은 근사값을 허용할 수 있지만 정산은 늦게 들어온 취소까지 반영해야 할 수 있습니다. 같은 스트림을 써도 소비자의 상태와 완료 기준은 다르게 설계합니다. “실시간”이라는 말 대신 허용 지연과 수정 가능 기간을 숫자로 정의합니다.

### 이벤트 시간과 처리 시간

PDA가 10시 00분에 검수한 사건을 통신 장애로 10시 05분에 보냈다고 합시다. 이벤트 시간은 10시 00분, 시스템이 받은 시간은 10시 05분입니다. 처리 시간을 기준으로 집계하면 실제 작업 시간대와 달라집니다. 이벤트 시간으로 집계하려면 늦게 도착하는 데이터와 기기 시계 오차를 다뤄야 합니다.

Window는 일정 구간의 사건을 모아 계산하는 단위입니다. Watermark는 이벤트 시간이 어느 정도 진행됐다고 판단하는 기준으로 이해할 수 있지만 모든 미래 지연 데이터가 절대 오지 않는다는 보장은 아닙니다. 허용 지연을 넘긴 사건을 버릴지, 별도 경로에 저장할지, 기존 결과를 수정할지 정합니다. 상태 저장과 checkpoint가 있어도 외부 sink에 결과를 쓰는 계약까지 맞아야 원하는 중복·복구 의미를 얻습니다.

### S3 데이터 레이크의 세 요소

원본 파일은 데이터이고, 테이블의 열·타입·위치 설명은 메타데이터이며, 누가 어떤 데이터를 볼 수 있는지는 접근 제어입니다. Glue Data Catalog에 테이블을 등록했다고 데이터가 DB 엔진 내부로 모두 옮겨진 것은 아닙니다. Athena 같은 엔진은 메타데이터를 참고해 S3 데이터를 읽습니다. 실제 S3·KMS 접근과 Lake Formation 등 적용된 권한 체계도 맞아야 합니다.

Crawler가 구조를 발견해 준다고 잘못된 원본 의미를 정정해 주지는 않습니다. 숫자 코드와 문자열 코드, 타임존이 없는 시각, 필드 의미 변경은 데이터 계약으로 관리해야 합니다. 같은 이름의 열이 어느 날부터 다른 단위를 뜻하면 쿼리는 성공해도 결과는 틀릴 수 있습니다. 데이터 품질은 문법 오류보다 넓습니다.

### 열 기반 파일과 partition pruning

행 기반 표현은 한 주문의 모든 열을 가까이 두는 그림이고, 열 기반 파일은 같은 열의 값을 모아 읽기 쉽게 정리하는 그림입니다. 분석에서 수십 개 열 중 금액과 날짜만 필요하다면 Parquet·ORC 같은 형식이 불필요한 읽기를 줄이는 데 도움이 됩니다. 압축과 통계 정보, 실제 쿼리·데이터 타입에 따라 효과가 달라집니다.

날짜별로 partition을 나누고 쿼리가 해당 partition 조건을 사용하면 읽을 범위를 줄일 수 있습니다. 365일 데이터에서 하루만 읽는다면 큰 차이가 날 수 있지만, 실제 스캔 감소가 정확히 365배라고 보장할 수는 없습니다. 크기 분포·열 선택·파일 구성·실행 계획이 영향을 줍니다. 모든 사용자 ID처럼 너무 세밀한 단위로 나누면 작은 파일과 메타데이터 작업이 늘어 역효과가 날 수 있습니다.

### 작은 파일이 많으면 왜 불리할까

상자 하나를 열 때마다 운송장 확인과 포장 해체 시간이 든다고 생각해 보세요. 데이터가 작아도 파일마다 목록 확인·요청·메타데이터·읽기 준비 비용이 발생할 수 있습니다. 적절한 크기로 묶는 compaction은 이를 줄이지만 작업 비용과 데이터 신선도 지연을 가져옵니다. “파일은 클수록 좋다”도 아닙니다. 병렬 읽기와 압축 형식, partition 요구를 함께 고려합니다.

## 더 깊은 면접 Q&A: 빠른 집계보다 올바른 집계

<details><summary>Q. 스트림 처리에서 exactly-once라고 하면 집계 결과는 절대 중복되지 않나요?</summary><p><strong>답변:</strong> 어떤 범위에서 제공하는 보장인지 확인해야 합니다. 처리 엔진의 상태와 checkpoint가 일관되어도 외부 DB·API에 쓰는 효과가 같은 계약에 참여하지 않으면 중복될 수 있습니다.</p><p><strong>설계:</strong> 이벤트 ID, sink의 트랜잭션·멱등 쓰기 지원, 장애 후 재생 범위를 확인합니다. 내부 처리 보장과 업무 전체 보장을 같은 말로 사용하지 않습니다.</p></details>
<details><summary>Q. Athena 쿼리에 LIMIT을 붙이면 스캔 비용이 항상 작아지나요?</summary><p><strong>답변:</strong> 반환 행 수를 제한하는 것과 읽어야 할 데이터를 줄이는 것은 별개입니다. 쿼리 형태와 엔진 동작에 따라 다르므로 LIMIT만으로 스캔량 감소를 보장해서는 안 됩니다. partition 조건, 필요한 열 선택, 파일 형식과 실제 scanned bytes를 확인합니다.</p><p><strong>연습:</strong> 같은 결과를 만드는 두 쿼리의 실행 계획·스캔량·시간을 비교합니다. 결과 행 수가 같다는 사실만으로 비용이 같거나 적다고 판단하지 않습니다.</p></details>
<details><summary>Q. 늦게 도착한 데이터를 무시하면 안 되나요?</summary><p><strong>답변:</strong> 업무가 허용하면 가능하지만 손실 범위와 영향이 명확해야 합니다. 실시간 모니터링의 임시 숫자와 정산·감사 기록은 허용 기준이 다릅니다. 원본을 남기고 최종 집계에서 보정하는 방법도 있습니다.</p><p><strong>꼬리 질문:</strong> 수정된 결과를 이미 소비한 다른 시스템에 어떻게 알릴지도 필요합니다. 한 번 만든 대시보드 숫자를 바꾸는 것과 이미 지급한 금액을 정정하는 것은 난도가 다릅니다.</p></details>
<details><summary>Q. S3에 모든 원본을 모으면 데이터 레이크가 완성되나요?</summary><p><strong>답변:</strong> 저장 기반은 생기지만 카탈로그·소유자·스키마·품질·보존·접근 권한이 없으면 필요한 데이터를 찾거나 신뢰하기 어렵습니다. 민감정보가 무작정 복제되는 위험도 생깁니다.</p><p><strong>완료 기준:</strong> 특정 분석 질문에 대해 어떤 원본과 변환을 거쳤는지 추적할 수 있고, 권한 있는 사용자가 재현 가능한 결과를 얻어야 합니다. 저장량 자체가 분석 플랫폼의 성숙도를 뜻하지는 않습니다.</p></details>

## 직접 풀어 보기: 어제 집계가 오늘 바뀌었다

어제 23시 58분에 발생한 검수 사건이 기기 통신 장애로 오늘 00시 07분에 도착했습니다. 일별 검수량 보고서에 어느 날짜로 넣어야 할까요? 실시간 화면과 최종 정산 보고서의 목적이 다르다고 가정합니다.

<details><summary>해설 펼치기 — 판단 과정과 조건을 바꾼 경우</summary><p><strong>시간 정의:</strong> 실제 업무 시점을 기준으로 집계한다면 어제에 속합니다. 수집된 시점을 기준으로 시스템 처리량을 보고 싶다면 오늘에 속할 수 있습니다. 먼저 보고서의 질문을 정의해야 합니다.</p><p><strong>지연 처리:</strong> 어제 결과를 이미 확정했다면 수정 가능한 기간과 재집계 절차를 정합니다. 실시간 화면은 임시값임을 표현하고 최종 보고서는 늦은 사건을 반영하는 방식도 가능합니다.</p><p><strong>정합성:</strong> 같은 사건이 재전송되었는지 식별할 event ID가 필요할 수 있습니다. 시간만으로 중복을 판단하면 같은 시각에 발생한 다른 사건을 잃을 수 있습니다. 원본 보관과 변환 이력을 연결합니다.</p><p><strong>추가 조건:</strong> 기기 시계가 틀렸을 수 있으므로 이벤트 시간의 신뢰성도 평가합니다. 모든 날짜 오류를 스트림 엔진의 watermark 설정만으로 해결할 수는 없습니다.</p></details>
