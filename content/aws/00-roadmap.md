## 1. AWS를 처음 만나면 왜 이름부터 막힐까

물류센터를 처음 방문했다고 생각해 봅시다. 냉장창고, 검수대, 컨베이어, 출입증 발급실 이름을 외운다고 입고 시스템을 설계할 수 있는 것은 아닙니다. 상품이 언제 도착하고, 누가 검사하며, 불량이면 어디로 보내고, 정전이 나면 무엇을 지킬지 알아야 시설을 배치할 수 있습니다. AWS도 같습니다. EC2는 프로그램을 실행할 곳, S3는 파일을 보관할 곳, SQS는 나중에 처리할 일을 맡기는 곳입니다. 각각의 기능보다 **요청이 들어와서 데이터가 남기까지의 흐름**을 먼저 이해해야 이름이 기억됩니다.

이 연재는 첨부 공부팩의 23개 PDF를 로드맵·CORE·DEEP DIVE 순서로 대응시킵니다. 원문을 그대로 복사한 번역본이 아니라, 개념과 설계 질문을 한국어로 재구성한 학습 해설입니다. 원문의 참고 링크·반복 설명·제품 홍보 문구까지 문장 단위로 옮긴 것은 아닙니다. 공개되지 않은 AWS 내부 구현은 추측으로 채우지 않고, 문서에서 보장하는 동작과 일반적인 분산 시스템 원리를 구분합니다.

## 2. 먼저 완성할 한 장의 그림

사용자가 검수 사진을 올린다고 해 봅시다. DNS는 서비스 주소를 찾고, 로드 밸런서는 살아 있는 애플리케이션으로 요청을 보냅니다. 애플리케이션은 사용자의 권한을 확인한 뒤 사진을 S3에 저장하고, 사진의 주소와 검수 결과는 관계형 DB에 기록합니다. 후속 알림은 큐로 넘깁니다. 운영자는 지표와 로그로 성공 여부를 확인하고, 장애가 나면 복구 계획에 따라 서비스를 되살립니다.

| 질문 | 주로 만나는 서비스·개념 | 반드시 연결할 조건 |
|---|---|---|
| 코드는 어디서 실행하나 | EC2, Lambda, ECS/EKS, Fargate | 실행 시간, 상태, 운영 책임 |
| 사진·파일은 어디에 남기나 | S3, EBS, EFS, FSx | 객체·블록·파일 접근 방식 |
| 요청은 어떤 길로 가나 | VPC, ALB/NLB, Route 53, CloudFront | 경로·접근 제어·캐시 |
| 업무 상태는 어떻게 보존하나 | RDS/Aurora, DynamoDB | 트랜잭션·조회 패턴·복제 |
| 느린 일을 어떻게 분리하나 | SQS, SNS, EventBridge | 재시도·중복·독립 소비 |
| 누가 무엇을 할 수 있나 | IAM, KMS, Secrets Manager | 인증·인가·키 관리 |
| 고장과 낭비를 어떻게 발견하나 | CloudWatch, CloudTrail, Config, 비용 도구 | 지표·감사·구성·귀속 |

이 흐름은 유일한 정답 아키텍처가 아닙니다. 사진 업로드는 사전 서명 URL로 S3에 직접 보낼 수도 있고, 업무 성격에 따라 DB나 실행 환경도 달라집니다. 학습의 목적은 구성을 외우는 것이 아니라 **바꿨을 때 생기는 책임과 손해를 설명하는 것**입니다.

## 3. 권장 학습 순서와 완료 기준

첫 회전은 01~13편입니다. 서비스마다 “무엇을 해결하는가, 비슷한 대안과 어떻게 다른가, 장애가 나면 무엇이 남는가”를 설명해 보세요. 02편에서 계정·리전·AZ를 구분한 뒤 03~09편의 구성 요소를 연결합니다. 10~12편은 비용·이전·분석이라는 목적에 맞춰 앞의 지식을 다시 사용합니다. 13편은 설계를 여섯 관점에서 검토하는 방법입니다.

두 번째 회전은 비교 중심입니다. EC2와 Lambda, EBS와 EFS, Multi-AZ와 Read Replica를 비교하면서 반드시 전제를 붙입니다. 예를 들어 “Multi-AZ는 읽기 확장용이 아니다”라는 문장을 모든 RDS 배포 형태에 적용하면 틀립니다. 전통적인 Multi-AZ DB 인스턴스의 standby와 읽기를 지원하는 Multi-AZ DB 클러스터는 다릅니다.

세 번째 회전은 14~22편의 심화입니다. 보안은 SEC 1~11, 신뢰성은 REL 1~13, 성능은 PERF 1~4, 비용은 COST 1~11의 설계 질문을 따라갑니다. 단순 제품 소개보다 팀이 무엇을 결정하고 어떻게 검증할지가 중요해집니다. 이 공부팩의 성능 심화 발췌는 PERF 1~4이며, 프레임워크 전체와 발췌 범위가 같지는 않습니다.

기간은 사람마다 다릅니다. 원래 로드맵의 CORE 7~10일, 비교 4~5일, 선택 심화 3~7일은 계획 예시이지 합격 보장이 아닙니다. 하루 공부 시간을 먼저 정하고, 설명하지 못한 비교 쌍을 다음 학습 대상으로 삼는 편이 낫습니다.

## 4. 글 한 편을 공부하는 실제 방법

1. **상황부터 읽습니다.** “원본 사진은 잃으면 안 되고, 썸네일은 재생성 가능하다”처럼 제약을 적습니다.
2. **비유를 자신의 말로 바꿉니다.** 비유의 어느 부분이 실제 시스템과 다른지도 말합니다.
3. **정상 흐름을 그립니다.** 요청·저장·응답·후속 처리 순서를 써 봅니다.
4. **한 곳을 고장 냅니다.** DB는 저장했는데 응답이 사라지면 재시도가 어떤 결과를 만드는지 묻습니다.
5. **접힌 Q&A를 먼저 스스로 답합니다.** 정답을 외우기보다 선택 이유와 대안이 탈락한 조건을 비교합니다.
6. **증거를 남깁니다.** 읽은 문서, 설정, 예상 결과, 관찰 결과를 분리합니다. 이 연재의 사고 실험은 AWS 계정에서 실행한 테스트 결과가 아닙니다.

## 5. 시험 문제를 실무 판단으로 바꾸기

“최소 운영 부담”은 직접 브로커를 설치하는 것보다 관리형 큐가 유리할 수 있다는 신호입니다. 그러나 기존 JMS 호환 코드가 중요하면 Amazon MQ를 검토해야 합니다. “가장 저렴한 저장소”도 복구 시간이 몇 시간이어도 되는지, 매일 읽는지에 따라 달라집니다. 정답을 바꾸는 단어는 서비스 이름보다 **지연 시간, 데이터 손실, 호환성, 운영 부담, 비용**에 숨어 있습니다.

실무에서는 시험보다 미확정 조건이 많습니다. 그럴 때 질문을 생략하지 마세요. “몇 초 내 복구가 필요한가”, “마지막 몇 분의 데이터 손실을 허용하는가”, “중복 알림은 허용되는가”라는 질문이 아키텍처의 출발점입니다.

## 깊이 읽기: 서비스 이름을 외우기 전에 요청 하나를 끝까지 따라가기

### 처음 보는 용어를 생활 속 동작으로 바꾸기

서버는 요청을 받아 일을 하는 컴퓨터이고, 애플리케이션은 그 위에서 실행되는 프로그램입니다. 데이터베이스는 프로그램이 꺼져도 남겨야 하는 업무 기록을 관리합니다. 네트워크는 이들이 대화할 길입니다. 권한은 그 길로 도착한 상대에게 어떤 일을 허용할지 정하는 규칙입니다. 따라서 “네트워크 연결 성공”과 “데이터 조회 허용”은 같은 사건이 아닙니다. 창고 문 앞까지 도착했다고 재고 장부를 읽을 권리가 생기지는 않습니다.

| 용어 | 쉬운 뜻 | 반드시 함께 물을 질문 |
|---|---|---|
| 엔드포인트 | 요청을 보낼 주소 | 그 주소 뒤의 서버가 바뀌면 어떻게 연결할까? |
| 지연 시간 | 요청부터 결과까지 걸린 시간 | 실제 작업 시간인가, 줄 서서 기다린 시간인가? |
| 처리량 | 단위 시간에 끝낸 작업 수 | 입력 수보다 적으면 대기는 얼마나 쌓일까? |
| 가용성 | 필요할 때 사용할 수 있는 정도 | 서버가 켜져 있어도 주문이 실패하면 정상인가? |
| 내구성 | 저장한 데이터가 손실되지 않는 성질 | 남아 있는 데이터에 지금 접근할 수 있는가? |
| 일관성 | 읽고 쓰는 결과 사이의 보장 | 방금 저장한 결과를 어떤 경로로 읽는가? |

### 입고 사진 한 장으로 전 과목 연결하기

물류센터 작업자가 PDA로 상품 사진을 등록한다고 가정합니다. PDA가 API를 호출하면 서버는 먼저 사용자를 인증하고 해당 입고 건을 수정할 권한을 확인합니다. 파일을 저장할 위치와 업무 기록은 분리할 수 있습니다. 사진 원본은 S3에, 입고 번호·파일 키·처리 상태는 관계형 DB에 둡니다. S3의 key는 물체에 붙인 보관 번호이고 DB 행은 그 보관 번호를 적은 장부에 해당합니다.

사진 분석이 오래 걸리면 API 요청 안에서 끝까지 기다리지 않고 작업을 큐에 넣습니다. 응답의 의미도 바뀝니다. “분석 완료”가 아니라 “분석 요청 접수”입니다. 소비자가 작업을 받고 사진을 읽어 분석한 뒤 DB 상태를 완료로 바꿉니다. 사용자는 상태 조회 API로 결과를 확인합니다. 이 과정에서 큐는 원본 사진도 DB 트랜잭션도 대신하지 않습니다. 서비스를 하나 추가할 때마다 맡은 책임을 한 문장으로 적어야 구성이 이해됩니다.

여기서 어려운 부분은 서비스 이름보다 실패의 경계입니다. 사진은 저장됐지만 DB 저장이 실패할 수 있습니다. DB에는 접수됐지만 큐 발행이 실패할 수도 있습니다. 분석은 끝났는데 큐 메시지 삭제가 실패하면 같은 작업이 다시 올 수 있습니다. 그래서 임시 업로드 정리, outbox, 멱등 키, 상태 전이 같은 애플리케이션 설계가 등장합니다. AWS 공부와 기존 Java/Spring 경험은 이 지점에서 연결됩니다.

### 같은 그림을 다섯 번 다른 질문으로 읽기

첫 번째에는 정상 흐름만 설명합니다. 두 번째에는 각 상자 하나를 지워 봅니다. API 한 대가 죽으면 다른 인스턴스가 처리할 수 있는지, DB가 잠시 연결되지 않으면 재시도하는지 확인합니다. 세 번째에는 트래픽을 열 배로 늘립니다. 서버가 자동 확장되어도 DB 연결 수나 외부 분석 API 한도는 그대로일 수 있습니다. 네 번째에는 권한 하나가 잘못되었다고 가정합니다. S3 파일을 읽을 권한과 KMS 복호화 권한, 네트워크 경로를 나누어 찾습니다. 마지막에는 한 달 비용을 나눕니다. 저장한 바이트, 요청 수, 실행 시간, 네트워크 전송량이 각각 과금의 출발점이 됩니다.

이렇게 공부하면 서비스별 장점 목록이 하나의 시스템 설명으로 바뀝니다. CORE에서는 각 부품을 식별하고, DEEP DIVE에서는 부품 사이의 실패와 통제 방법을 설명하는 것을 목표로 삼습니다. 모든 세부 항목을 한 번에 외우기보다 한 시스템에 질문을 추가하는 방식이 덜 어렵습니다.

### 스스로 이해했는지 확인하는 네 단계

1. 책을 보지 않고 정상 흐름을 6문장으로 설명합니다. 막히는 용어는 별도 목록에 적습니다.
2. “왜 이 서비스를 쓰는가” 다음에 “무엇은 해결하지 못하는가”를 붙입니다. 예를 들어 큐는 순간 부하를 완충하지만 처리 능력 부족을 영구 해결하지 않습니다.
3. 숫자를 넣습니다. 초당 20개 유입에 초당 15개 처리라면 10분 동안 3,000개가 추가로 쌓입니다. 단, 입력·처리가 일정하고 실패가 없다는 가정을 밝힙니다.
4. 조건을 하나 바꾸고 결론도 바꿉니다. 분석 결과가 즉시 필요하다면 비동기 접수만으로 요구를 만족하지 못합니다. 서비스 이름을 유지하려고 요구를 억지로 바꾸지 않습니다.

## 더 깊은 면접 Q&A: 학습한 내용을 설계 언어로 말하기

<details><summary>Q. 서비스는 많이 아는데 아키텍처를 그리지 못한다면 무엇부터 해야 하나요?</summary><p><strong>답변:</strong> 사용자 행동 하나, 저장할 원본 하나, 성공 응답의 의미 하나부터 정합니다. “사진 분석을 요청하고 최종 결과를 조회한다”처럼 업무 문장으로 시작한 뒤 동기 작업과 비동기 작업을 나눕니다. 그 다음 실행 환경·저장소·통신 경로를 선택합니다.</p><p><strong>꼬리 질문 — 서비스를 최소화하면 항상 좋은가요?</strong> 운영할 대상이 적어지는 장점은 있지만, 긴 작업을 API 안에 모두 넣으면 timeout과 확장이 어려워질 수 있습니다. 개수 자체보다 각 구성 요소가 해결하는 요구가 명확한지 봅니다.</p></details>
<details><summary>Q. 고가용성과 데이터 내구성이 왜 별개의 개념인가요?</summary><p><strong>답변:</strong> 안전한 금고에 문서가 남아 있지만 금고 문이 고장 나 열 수 없는 상황을 생각하면 됩니다. 문서 손실은 없지만 사용할 수 없습니다. 반대로 서비스는 계속 응답해도 잘못된 삭제가 복제되었다면 원본을 잃을 수 있습니다.</p><p><strong>설계 연결:</strong> 장애 조치로 접근 경로를 복원하는 계획과, 백업에서 이전 데이터를 복구하는 계획을 따로 준비합니다. 복제본 수만 세고 백업 복원 시험을 생략하면 두 목표 중 하나를 놓칩니다.</p></details>
<details><summary>Q. CORE를 읽고 바로 DEEP DIVE를 읽어야 하나요?</summary><p><strong>답변:</strong> 기본 서비스의 역할과 요청 경로를 설명할 수 있다면 보안·복구·성능·비용 중 막힌 주제로 넘어가도 됩니다. CORE의 모든 제품 이름을 완벽히 외우는 것이 선행 조건은 아닙니다. 대신 신뢰성 심화를 읽다가 RDS 장애 조치를 이해하지 못하면 DB 편으로 되돌아갑니다.</p><p><strong>완료 기준:</strong> 단순히 읽은 페이지 수가 아니라 선택 이유, 제외한 대안, 실패 지점, 확인할 지표까지 말할 수 있어야 합니다. 학습 순서는 일방통행보다 왕복하는 구조가 자연스럽습니다.</p></details>
<details><summary>Q. 실습 없이 글만 읽어도 실무를 이해했다고 할 수 있나요?</summary><p><strong>답변:</strong> 동작 모델과 설계 판단은 배울 수 있지만 실제 계정의 권한, 한도, 지연, 장애 복구 시간까지 검증한 것은 아닙니다. 이 연재의 계산과 장애 상황은 설명을 위한 가정입니다. 운영 적용 전에는 작은 검증 환경에서 정상 처리와 실패 처리를 모두 관찰해야 합니다.</p><p><strong>연습:</strong> 실행하지 않은 상태에서도 예상 결과를 먼저 써 보세요. 실습 결과가 예상과 다를 때 그 차이를 설명하는 과정이 단순히 콘솔 화면을 따라 누르는 것보다 깊은 학습입니다.</p></details>

## 직접 풀어 보기: 입고 사진 서비스의 성공은 언제인가

PDA는 사진 업로드 뒤 1초 안에 응답을 받아야 합니다. 사진 분석은 평균 20초가 걸리고 결과는 5분 안에 나오면 됩니다. 분석 결과를 저장한 직후 소비자가 종료될 수 있습니다. API가 무엇을 응답해야 하는지, 원본과 작업 상태를 어디에 둘지, 중복 처리를 어떻게 설명할지 먼저 적어 보세요. 수치는 학습용 가정입니다.

<details><summary>해설 펼치기 — 판단 과정과 조건을 바꾼 경우</summary><p><strong>1단계 — 성공의 뜻:</strong> 1초 안에 분석 완료를 약속하면 20초 작업과 충돌합니다. 업로드 또는 요청 접수 성공을 반환하고 작업 ID와 상태 조회 방법을 제공합니다. 최종 성공은 분석 결과가 확정된 시점으로 따로 정의합니다.</p><p><strong>2단계 — 책임 분리:</strong> 원본 사진 저장, 업무 상태 저장, 작업 전달, 분석 실행을 나눕니다. 각 요소를 S3·DB·큐·실행 환경 후보와 연결할 수 있지만 이름을 정하기 전에 보존과 일관성 요구를 먼저 적습니다.</p><p><strong>3단계 — 실패의 틈:</strong> 상태 저장과 작업 발행 사이의 누락, 결과 저장과 큐 확인 사이의 중복을 표시합니다. Outbox와 멱등 처리가 왜 필요한지 이 두 틈으로 설명할 수 있어야 합니다.</p><p><strong>조건 변경:</strong> 사용자가 결과를 즉시 받아야 한다면 비동기 접수만으로 해결하지 못합니다. 분석 시간을 줄이거나 요구를 재협의해야 합니다. AWS 서비스 이름을 바꾸는 것만으로 물리적인 처리 시간이 사라지지 않습니다.</p></details>
