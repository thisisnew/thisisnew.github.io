## 1. 출입증을 발급하는 회사의 운영 규칙

물류센터 출입증을 만들 때 이름만 적으면 충분하지 않습니다. 누구의 승인을 받는지, 어느 구역에 언제까지 들어갈 수 있는지, 퇴사하면 어떻게 회수하는지, 출입 시스템이 고장 나면 누가 긴급 접근할지를 정해야 합니다. IAM도 정책 JSON 한 장보다 넓은 운영 문제입니다. 원문의 SEC 1은 안전한 운영 기반, SEC 2는 인증, SEC 3은 권한 관리를 묻습니다.

이 편에서 인증은 신원 확인, 권한은 행동 허용, 가드레일은 넘을 수 없는 정책 경계, federation은 외부 신원을 연결하는 방식입니다. 임시 자격 증명도 만료되기 전 탈취되면 악용될 수 있으므로 “임시니까 아무 데나 보관해도 된다”는 뜻은 아닙니다.

## 2. SEC 1: 계정·루트·통제 목표·위협 모델

개발과 운영을 계정으로 나누면 실험 중 삭제나 과도한 권한의 피해 범위를 줄일 수 있습니다. 계정 분리는 네트워크 분리와 같은 말이 아니며 계정 간 role·리소스 공유·중앙 로그 경로를 다시 설계해야 합니다. 로그 보관 계정은 업무 계정 관리자에게 무제한 삭제 권한을 주지 않는 식으로 독립성을 확보할 수 있습니다.

루트 사용자는 일상 업무에 사용하지 않고 강한 인증과 복구 절차를 적용합니다. 루트 이메일·연락처·결제 정보·MFA·긴급 접근 책임자를 관리하는 일도 보안입니다. 조직의 중앙 루트 접근 기능을 사용하는 경우와 개별 계정 자격 증명을 유지하는 경우는 조건이 다르므로 현재 구성에 맞게 절차를 문서화합니다.

통제 목표는 “보안을 강화한다”보다 구체적이어야 합니다. 예를 들어 “고객 주소는 승인된 서비스만 읽으며 모든 관리 변경을 추적한다”를 목표로 정하면 최소 권한·로그·암호화·검토 지표를 연결할 수 있습니다. 위협 모델은 자산·데이터 흐름·신뢰 경계·공격자 능력을 정리하고 가능한 악용 경로를 찾는 작업입니다. 앱 서버가 침해되었을 때 모든 버킷을 삭제할 수 있는가라는 질문은 정책의 피해 범위를 드러냅니다.

원문의 SEC01-BP01~08은 계정 분리, 루트 보호, 목표 정의, 최신 위협 파악, 보안 관리 범위 축소, 표준 제어 자동화, 위협 모델, 새 기능 평가를 묶습니다. 관리형 서비스로 OS 관리 범위를 줄일 수 있지만 데이터·role·앱 취약점 책임은 남습니다. 새 보안 기능도 도입 자체를 성과로 삼지 말고 기존 위험이 실제로 줄었는지 확인합니다.

## 3. SEC 2: 사람과 시스템의 인증을 다르게 설계

직원은 중앙 IdP와 IAM Identity Center 등의 연동으로 로그인하고, 그룹·속성에 따라 필요한 역할을 맡도록 설계할 수 있습니다. 입사·이동·퇴사 과정이 신원 수명주기와 연결되어야 합니다. 여러 계정마다 개인 user를 따로 만들면 회수 누락과 장기 키 관리가 어려워집니다.

시스템은 실행 환경에 부여된 role이나 지원되는 workload identity로 임시 자격 증명을 얻도록 합니다. STS 자격 증명에는 만료가 있으므로 SDK의 자격 증명 제공 체인을 활용하고 직접 장기 저장하는 방식을 피합니다. DB·외부 API secret은 승인된 저장소에서 가져오며 로그·빌드 결과물·환경 덤프에 노출되지 않게 합니다. 회전은 secret 값만 바꾸는 작업이 아니라 사용하는 시스템의 전환까지 포함합니다.

SEC02-BP01~06은 강한 로그인, 임시 자격 증명, secret 보호, 중앙 IdP, 정기 감사·교체, 그룹·속성 사용을 다룹니다. ABAC는 태그·속성에 따라 권한을 정할 수 있지만 사용자가 자신에게 유리한 태그를 마음대로 바꿀 수 있으면 권한 상승 경로가 생깁니다. 속성의 생성·수정 권한까지 통제해야 합니다.

## 4. SEC 3: 정책 평가를 실제 요청으로 따라가기

앱 role이 `s3:GetObject`를 호출한다고 가정합시다. 먼저 실제 호출 주체와 세션을 확인합니다. 다음으로 대상 object ARN과 적용되는 identity policy·resource policy·조건을 봅니다. 명시적 Deny, permissions boundary, session policy, SCP/RCP 등 적용 가능한 제한을 확인합니다. SSE-KMS라면 KMS 권한도 별도의 경계입니다. cross-account 요청은 양쪽 신뢰와 허용 구성이 필요하며 일부 리소스 정책의 주체 유형에 따른 예외를 확인해야 합니다.

최소 권한은 처음에 작게 부여하고 관찰과 검토를 통해 계속 좁히는 과정입니다. 실제 사용 기록만 보고 바로 제거하면 월말·장애 복구처럼 드물지만 필수인 작업을 놓칠 수 있습니다. 반대로 “언젠가 필요할 수도 있다”는 이유로 모든 권한을 남겨 두면 최소 권한이 아닙니다. 업무 소유자와 사용 주기를 확인하고 테스트·되돌림 계획을 붙입니다.

아래는 특정 prefix 읽기만 설명하는 정책 조각입니다. 독립적으로 모든 접근을 보장하는 완성 정책이 아니며 버킷 이름은 예시입니다.

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": "s3:GetObject",
    "Resource": "arn:aws:s3:::example-inspection-bucket/results/*"
  }]
}
```

목록 조회에는 버킷 ARN과 `s3:ListBucket`이 별도로 필요할 수 있습니다. 객체 ARN에 ListBucket을 붙이거나 버킷 ARN만으로 GetObject를 허용하면 원하는 정책이 되지 않습니다. Policy Simulator와 Access Analyzer, 실제 비운영 환경 테스트를 함께 활용하되 도구가 모든 외부 조건을 대신 검증한다고 가정하지 않습니다.

## 5. 긴급 접근·외부 공유·confused deputy

긴급 접근은 장애 중에 새로 만들기보다 미리 준비하고 정기적으로 시험합니다. 승인·시간 제한·강한 인증·감사·사후 회수를 정합니다. 중앙 IdP가 고장 난 시나리오도 포함해야 합니다. 누구나 알고 있는 무제한 비밀번호를 문서에 적어 두는 방식은 긴급 접근 계획이 아닙니다.

외부 업체에 접근을 줄 때는 장기 키 공유보다 제한된 cross-account role을 검토합니다. 제3자 서비스가 여러 고객을 대신해 행동할 때 다른 고객의 권한으로 오인해 접근하는 confused deputy 위험을 줄이기 위해 external ID 같은 조건을 사용할 수 있습니다. external ID는 비밀번호가 아니라 어떤 고객의 위임인지 구별하는 조건이며, 신뢰 정책의 principal 제한과 함께 설계합니다. AWS 서비스 위임에서는 source ARN·source account 같은 지원 조건도 검토합니다.

SEC03-BP01~09의 흐름은 요구 정의→최소 권한→긴급 접근→지속 축소→조직 가드레일→수명주기→공개·계정 간 접근 분석→조직 공유→제3자 공유입니다. 각각의 소유자와 검증 결과를 남겨야 정책이 시간이 지나며 넓어지는 것을 막을 수 있습니다.

## 6. 가상 사고와 확인 연습

퇴사자가 쓰던 access key가 CI 설정에 남아 있었습니다. 키는 살아 있고 권한은 여러 버킷 삭제까지 가능했습니다. 대응은 키 비활성화만이 아닙니다. 사용 로그와 영향 범위 조사, 필요한 서비스의 대체 신원 배포, 관련 secret 회전, 권한 축소, 퇴사 절차 개선이 이어집니다. 로그에 없다고 미사용을 단정하지 말고 수집 범위도 확인합니다.

학습 연습으로 직원·배포 파이프라인·EC2 앱·외부 파트너 네 주체에 대해 신원 출처, 자격 증명 만료, 허용 작업, 리소스 범위, 회수 담당자를 표로 작성하세요. “관리자” 한 단어로 채워지는 칸이 많으면 권한 요구가 아직 충분히 분해되지 않은 것입니다.

## 7. 상세 면접 Q&A

<details><summary>Q. SCP에서 Allow를 주면 사용자가 바로 실행할 수 있나요?</summary><p>아닙니다. SCP는 적용 대상의 최대 권한 범위를 제한하며 그 자체로 사용자의 실행 권한을 부여하지 않습니다. IAM 등 실제 허용과 다른 제한을 함께 평가해야 합니다. 관리 계정과 일부 서비스 주체의 적용 범위도 구분합니다.</p></details>
<details><summary>Q. role을 사용해도 키 탈취 위험이 있나요?</summary><p>임시 자격 증명도 유효 기간과 권한 범위 안에서 악용될 수 있습니다. 만료는 노출 기간을 줄이고 자동 교체를 쉽게 만들지만 과도한 권한·로그 노출·취약한 앱을 해결하지는 않습니다. 최소 권한과 네트워크·탐지 통제를 함께 적용합니다.</p></details>
<details><summary>Q. 최소 권한을 처음부터 완벽히 정할 수 있나요?</summary><p>업무 시나리오를 기준으로 작게 시작하고 비운영 테스트와 사용 기록·Access Analyzer 결과를 통해 개선합니다. 드문 복구 작업도 요구에 포함합니다. 상시 관리자 권한으로 운영한 뒤 언젠가 줄이겠다는 계획보다 권한 요청과 검토 절차를 만드는 것이 중요합니다.</p></details>
<details><summary>Q. ABAC가 RBAC보다 무조건 좋은가요?</summary><p>ABAC는 많은 리소스를 속성으로 관리할 때 유연하지만 속성의 정확성과 변경 권한이 핵심입니다. RBAC는 역할이 명확한 조직에서 이해와 감사가 쉬울 수 있습니다. 조직 규모·태그 거버넌스·예외 요구를 고려해 선택하거나 결합합니다.</p></details>
