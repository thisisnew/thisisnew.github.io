처음 읽는다면 아래 용어의 뜻만 확인한 뒤 본문으로 넘어가세요. 먼저 예제의 결과를 예상하고, 실행 과정을 따라간 다음, 면접 답변을 펼쳐 자신의 설명과 비교하면 좋습니다.

| 용어 | 이 글에서의 뜻 |
|---|---|
| Region | G1이 Heap을 나눈 고정 크기 구역 |
| 대피 | 생존 객체를 다른 공간으로 옮기는 처리 |
| 마킹 | 생존 객체를 추적해 표시하는 처리 |
| Mixed | Young과 선택된 Old Region을 함께 수집하는 단계 |

## 1. G1은 창고를 작은 구역으로 나누어 청소한다

거대한 창고를 한 번에 비우는 대신 같은 크기의 구역으로 나누고, 청소 효과가 큰 구역부터 정리한다고 생각해 봅시다. G1은 Heap을 같은 크기의 **Region**들로 나누고 일부 Region을 골라 살아 있는 객체를 다른 공간으로 옮깁니다. 선택한 수집 대상 집합이 **Collection Set(CSet)**입니다.

Young·Old는 여전히 존재합니다. 단지 각 세대가 반드시 하나의 연속된 덩어리인 것은 아닙니다. Eden·Survivor·Old 역할의 Region이 여러 위치에 있을 수 있습니다. Region의 역할도 수집·재사용에 따라 달라집니다. G1은 여러 하드웨어 구성에서 기본 수집기로 선택되지만 실제 환경의 선택은 로그로 확인하는 것이 정확합니다.

## 2. 전체 사이클을 사건 순서로 읽기

| 사건 | 애플리케이션과 관계 | 핵심 작업 |
|---|---|---|
| Normal Young | STW | Young 생존 객체를 Survivor·Old로 대피 |
| Concurrent Start | Young STW에 결합 | 전역 동시 마킹 시작을 준비 |
| Concurrent Mark | 애플리케이션과 동시 진행 | Old Region 생존 정보 조사 |
| Remark | STW | 마킹 관련 미완료 작업 마무리 |
| Cleanup | 짧은 STW 단계 등 | Region 정보와 회수 후보 정리 |
| Prepare Mixed·Mixed | STW | Young과 선택된 Old Region 대피 |
| Full GC | STW | 필요 시 전체 Heap 정리·압축의 복구 경로 |

이 표는 주요 흐름을 이해하기 위한 것입니다. 모든 실행에서 모든 단계가 반드시 같은 횟수·순서로 로그에 나타나는 것은 아닙니다. 조건에 따라 마킹을 중단하거나 Mixed 단계로 가지 않을 수 있습니다. Young 수집도 동시 마킹 중에 발생할 수 있습니다.

**Mixed GC는 Full GC가 아닙니다.** Young에 더해 일부 Old Region을 선택해 점진적으로 정리하는 것이 Mixed입니다. Old 전체를 매번 한 번에 수집하는 모델과 다릅니다. 반대로 G1이라고 Full GC가 존재하지 않는 것도 아닙니다.

## 3. 참조를 놓치지 않는 두 종류의 장치

첫째, CSet 밖의 객체가 CSet 안을 참조할 수 있습니다. 객체를 옮기면 이 참조도 갱신해야 하므로 외부에서 들어오는 참조 정보를 좁혀 찾는 **Remembered Set**이 필요합니다. 카드 단위의 근사 위치를 활용해 메모리·갱신 비용을 줄입니다. 모든 외부 객체를 매번 처음부터 전부 스캔하는 비용을 피하려는 것입니다.

둘째, 동시 마킹 중 애플리케이션이 참조 그래프를 바꾸면 조사하던 연결이 사라질 수 있습니다. G1은 **SATB(Snapshot-At-The-Beginning)** 계열 알고리즘을 사용합니다. 시작 시점에 살아 있던 객체를 보수적으로 보존하도록 참조 변경을 기록하는 방식입니다. 실제 Heap 전체를 파일이나 별도 복사본으로 스냅샷 찍는 것은 아닙니다.

SATB 때문에 마킹 중 도달 불가능해진 객체가 이번 회수에서 바로 없어지지 않을 수 있습니다. 이는 항상 누수를 뜻하지 않으며 다음 사이클에서 회수될 수 있습니다. SATB 관련 pre-write barrier와 Region 간 참조 추적의 역할을 같은 한 문장으로 뭉개지 마세요. 둘은 각각 동시 마킹 정확성과 부분 수집의 외부 참조 탐색이라는 문제를 다룹니다.

## 4. Pause 목표는 상한 보증이 아니다

`-XX:MaxGCPauseMillis=200`은 모든 정지가 반드시 200ms 이내라는 계약이 아닙니다. G1은 이전 관측으로 비용을 예측하고 Young 크기와 수집할 작업량을 조절해 목표를 맞추려고 합니다. 실시간 수집기의 확정적 deadline과 다릅니다.

목표를 작게 하면 한 번의 수집량이 줄어들거나 수집 빈도·동시 작업 비용이 커질 수 있습니다. 응답 지연뿐 아니라 처리량과 CPU, 여유 Heap도 같이 평가해야 합니다. Young 크기를 `-Xmn` 등으로 고정하면 G1의 적응형 정책을 제약할 수 있으므로 숫자 튜닝을 출발점으로 삼지 않습니다. [공식 근거: G1 튜닝](https://docs.oracle.com/en/java/javase/21/gctuning/garbage-first-garbage-collector-tuning.html)

## 5. IHOP와 대피 여유 공간

동시 마킹은 시간이 걸립니다. Old가 완전히 찬 뒤 시작하면 마킹과 Mixed 수집이 끝나기 전에 공간이 부족할 수 있습니다. **IHOP(Initiating Heap Occupancy Percent)**와 적응형 예측은 마킹 시작 시점을 정하는 데 관련됩니다. 실제 할당·승격 속도와 마킹 소요 시간에 여유를 두는 것이 중요합니다.

대피하려면 살아 있는 객체를 복사할 목적지 공간도 필요합니다. 빈 공간이 너무 적으면 **evacuation failure**가 발생할 수 있습니다. 모든 대피 실패가 즉시 Full GC 한 번으로 직결되는 단순 규칙은 아니지만, 여유 공간이 계속 부족하면 Full GC 등 더 비싼 복구 경로가 필요할 수 있습니다.

그래서 “Heap을 꽉 채워야 효율적”이라는 생각은 위험합니다. 큰 live set, 높은 할당·승격, 부족한 CPU가 겹치면 동시 작업이 따라가지 못할 수 있습니다. 원인을 제거하지 않고 Pause 목표만 줄여도 해결되지 않습니다.

## 6. Humongous 객체가 별도 취급되는 이유

G1의 Humongous 경계는 Region 절반 크기와 연결됩니다. Oracle 가이드는 절반 이상으로 설명하지만, [HotSpot 21u의 실제 판정](https://github.com/openjdk/jdk21u/blob/master/src/hotspot/share/gc/g1/g1CollectedHeap.hpp)은 임계값을 엄격히 초과하는 비교(`>`)입니다. 배열의 데이터 길이만이 아니라 헤더·정렬을 포함한 객체 할당 크기가 관련됩니다. 이 예제는 경계에 딱 맞는 값을 쓰지 않습니다. Humongous 객체는 연속된 여러 Region을 사용해 Old 쪽에 배치되며 마지막 Region의 남는 공간을 다른 일반 객체에 쓰지 못하는 비용이 생길 수 있습니다.

전체 빈 공간의 합이 충분해도 필요한 연속 Region이 부족하면 문제가 생길 수 있습니다. 대형 byte 배열, 대량 엑셀 전체 적재, 큰 JSON 중간 버퍼가 이런 경로와 연결됩니다. “G1은 객체를 잘 옮기니 단편화 문제는 절대 없다”는 결론은 틀립니다. 데이터 스트리밍·청크 처리·중간 복사 제거를 먼저 검토할 수 있습니다.

## 7. Region 크기를 고정한 로컬 실습

```java
// file: Lesson13.java
public class Lesson13 {
    static volatile byte[] sink;
    public static void main(String[] args) {
        byte[][] retained = new byte[8][];
        for (int i = 0; i < 240; i++) {
            byte[] data = new byte[700 * 1024];
            data[0] = (byte) i;
            retained[i % retained.length] = data;
            sink = data;
        }
        System.out.println("retained=" + retained.length);
        System.out.println("last=" + sink[0]);
    }
}
```

```sh
javac --release 21 -g Lesson13.java
java -Xms32m -Xmx32m -XX:+UseG1GC -XX:G1HeapRegionSize=1m -Xlog:gc*,gc+humongous=debug:file=gc13.log:time,uptime,level,tags Lesson13
```

1MiB Region을 명시하고 700KiB 배열을 만들어 Humongous 경로를 관찰합니다. 출력은 `retained=8`, `last=-17`입니다. 마지막 값은 byte가 부호 있는 8비트이므로 239를 변환한 결과입니다. Region 고정은 경로를 재현하기 위한 실습 설정이며 운영 튜닝 추천이 아닙니다.

로그의 `Humongous regions` 변화를 먼저 보고 GC 원인과 전체 흐름을 연결하세요. 이 작은 실습에서 Mixed와 Full GC가 반드시 모두 나타나지는 않습니다. Full GC를 관찰하지 못했다고 기능이 없다는 뜻은 아닙니다. 더 많은 객체를 영구 보관하는 변형은 OOM을 유발할 수 있어 기본 실습에 넣지 않았습니다.

## 8. 장애 사례: 큰 엑셀 내보내기가 p99를 끌어올림

전체 데이터를 한 번에 조회한 뒤 거대한 문자열과 byte 배열을 여러 번 복사한다고 가정합니다. Humongous Region 증가와 동시 마킹 시작, 정지 시간이 요청 시간과 겹칠 수 있습니다. 먼저 JFR 할당 위치와 GC 로그를 요청 시각에 맞춰 보고 큰 객체를 만드는 경로를 찾습니다.

해결 후보는 페이지·청크 단위 처리, 스트리밍 출력, 중간 표현의 중복 제거, 해당 작업의 동시 실행 제한입니다. 효과는 대표 부하에서 검증합니다. Region 크기만 늘리면 분류 경계는 바뀌어도 live set과 총 할당량 문제는 남을 수 있습니다.

## 더 깊이: 한 줄의 GC 로그에서 주장할 수 있는 범위

다음은 형식을 설명하기 위해 만든 가상 로그 요약입니다. 실제 실행 결과를 복사한 것이 아닙니다.

```text
GC(17) Pause Young (Mixed) ... 180M->120M(256M) 24.0ms
```

이 요약에서 Mixed는 Young과 일부 Old를 수집한 유형이고, 180M→120M은 표시된 Heap 점유 변화, 256M은 로그 맥락의 Heap 용량, 24ms는 해당 정지의 시간으로 읽을 수 있습니다. 하지만 이 한 줄만으로 '전체 Old의 60MiB를 회수했다'고 말할 수는 없습니다. Young 변화와 기타 작업이 포함되므로 Region별·단계별 정보를 더 봐야 합니다.

또한 서비스 응답이 200ms였다면 나머지 176ms를 자동으로 DB 시간이라고 계산할 수 없습니다. 요청과 정지가 겹친 실제 시점, CPU 스케줄링, 다른 처리·대기를 확인해야 합니다. 서로 범위가 다른 시간 지표를 단순 차감하면 원인 분석이 틀어질 수 있습니다.

## 차근차근 이해하기: Region의 역할과 객체의 위치를 구분하자

G1은 Heap을 같은 크기의 Region으로 나누고 각 Region에 Eden, Survivor, Old 등의 역할을 부여합니다. 이는 Young과 Old가 각각 항상 하나의 큰 연속 구간이어야 한다는 생각에서 벗어나게 해 줍니다. Region의 역할은 고정된 방 이름처럼 영원히 유지되는 것이 아니라 수집과 재사용 과정에서 달라질 수 있습니다.

**대피(evacuation)**는 선택한 Region의 살아 있는 객체를 다른 공간으로 옮기는 작업입니다. 버릴 상자만 하나씩 치우는 대신 필요한 상자를 다른 방으로 옮기고 원래 방을 통째로 비우는 방식으로 생각하면 됩니다. 이때 옮길 목적지가 필요하므로 Heap을 극단적으로 꽉 채우면 수집에도 어려움이 생길 수 있습니다.

### Young 수집에서 Mixed 수집까지 한 사이클 따라가기

| 사건 | 무엇을 알아내거나 수행하는가 | 초보자가 놓치기 쉬운 점 |
|---|---|---|
| Young 수집 | 선택된 Young Region의 생존 객체를 이동 | Heap 전체의 모든 쓰레기를 처리하는 것은 아님 |
| Concurrent Start | 마킹 시작에 필요한 일을 Young 정지와 함께 수행 | 이후 동시 단계가 있다고 이 정지가 없어지지는 않음 |
| 동시 마킹 | 애플리케이션과 함께 진행하며 생존 정보를 수집 | 실행 중 참조 변경을 고려하는 장치가 필요 |
| Remark·정리 단계 | 마킹 완료와 회수 후보 판단에 필요한 처리 | 전체 사이클이 하나의 무정지 작업은 아님 |
| Mixed 수집 | Young과 선택된 Old Region을 함께 수집 | 모든 Old를 한꺼번에 치우는 Full GC와 다름 |

실제 로그에는 더 세부적인 단계가 나오고 적응 정책에 따라 다음 행동이 결정됩니다. 이 표는 읽기 위한 흐름이지 모든 실행에서 동일 횟수와 간격으로 반복되는 고정 시간표가 아닙니다.

### SATB와 remembered set을 서로 다른 질문으로 이해하자

SATB는 동시 마킹 도중 애플리케이션이 참조를 바꾸더라도 시작 시점의 생존성 추적에 필요한 정보를 놓치지 않기 위한 방식입니다. 기존 참조가 덮어써지는 순간에 필요한 정보를 기록하는 장벽이 관련됩니다. Heap 전체를 한 번 더 복사한 사진 파일을 만드는 것은 아닙니다.

Remembered set은 특정 Region을 수집할 때 **바깥에서 이 Region으로 들어오는 참조를 어디서 찾을지**에 관계됩니다. 관련 쓰기 장벽과 카드 추적이 이 정보를 관리하는 데 사용됩니다. SATB가 마킹 중 참조 변화의 의미를 보존하는 문제라면, remembered set은 부분 수집에서 경계를 넘어오는 참조를 찾는 문제입니다. 둘 다 참조를 다룬다는 공통점 때문에 하나로 외우지 마세요.

### 정지 목표를 낮추면 어떤 교환이 생길까

학습용으로 정지 목표를 200ms에서 50ms로 낮췄다고 가정해 봅시다. G1은 예측 모델을 이용해 한 번의 수집에 넣을 작업량 등을 조절하려 하지만, 매번 50ms 안에 끝난다는 보장은 없습니다. 더 작은 수집을 자주 하거나 추가 CPU 비용을 쓰는 방향의 교환이 있을 수 있습니다. 정지 한 번이 짧아졌더라도 전체 처리량과 CPU 여유가 악화될 수 있습니다.

그래서 비교표에는 최대 정지 하나만 적지 말고 정지 횟수, 총 정지 시간, 응답 지연 분포, 처리량, CPU 사용량을 함께 적습니다. 동일한 요청 부하와 충분한 관찰 구간이 필요합니다. “설정을 낮췄다”는 변경 사실과 “사용자가 더 빨라졌다고 느낀다”는 서비스 결과는 구분해서 검증합니다.

### Humongous 실습은 경계값보다 원리를 먼저 보자

1MiB Region에서 700KiB byte 배열을 만드는 기존 예제는 헤더와 정렬을 고려해도 절반 기준에서 충분히 떨어진 사례입니다. 정확히 경계에 걸친 길이로 실험하면 배열 길이만으로 전체 객체 크기를 판단하는 실수를 하기 쉽습니다. 먼저 명확한 사례로 Humongous 로그를 확인한 뒤, 경계값은 해당 HotSpot 구현과 객체 배치를 따로 확인하는 순서가 좋습니다.

<details class="question"><summary>확인 문제. GC 후 빈 공간이 충분한데 왜 큰 객체 할당이 어려울 수 있나요?</summary><div class="answer"><p><strong>판단:</strong> 총 빈 용량과 필요한 형태의 빈 공간은 다릅니다. G1의 Humongous 객체는 연속된 Region 공간이 필요하므로 작은 빈 구간이 흩어져 있으면 총량만으로 설명할 수 없습니다.</p><p><strong>조사:</strong> 객체 크기와 Region 크기, Humongous Region 변화, 수집 시점의 여유를 함께 확인합니다. 대용량 응답 전체를 한 배열로 만드는지, 동시에 몇 요청이 같은 작업을 수행하는지도 봅니다.</p><p><strong>꼬리질문:</strong> Region을 크게 하면 되나요? 경계가 바뀔 수 있지만 Region 개수와 수집 선택의 세밀함 등 다른 조건도 달라집니다. 데이터 스트리밍·분할과 동시성 제한으로 큰 객체 자체를 줄이는 방법도 함께 비교해야 합니다.</p></div></details>

## 심화 실험실: G1 로그를 보고 바꿀 설정을 결정하기 전에

### 청소 시간은 쓰레기 양 하나로 결정되지 않는다

창고 한 구역의 대부분이 빈 상자여도 아직 쓰는 상자를 옮기고, 다른 구역에서 가리키는 재고표를 확인해야 합니다. G1의 정지 비용도 단순히 “회수할 쓰레기 바이트 수”만으로 정해지지 않습니다. 살아 있는 객체를 대피시키는 비용, 들어오는 참조를 찾는 비용, 병렬 작업과 CPU 자원 등의 영향을 받습니다.

Old 객체가 Young 객체를 가리킨다면 Young 구역만 보고는 그 객체가 살아 있음을 알 수 없습니다. remembered set과 관련 장치는 구역 밖에서 들어오는 참조를 찾는 비용을 줄이는 데 쓰입니다. SATB는 동시 마킹 도중 참조 그래프가 바뀌어도 마킹 시작 시점의 생존 판단을 보수적으로 유지하기 위한 장치입니다. 두 장치가 모두 write barrier와 관련될 수 있어도 답하는 질문은 다릅니다.

### Old 쪽 컨테이너에 새 참조를 계속 저장하는 형태

```java
// file: Deep13.java
public class Deep13 {
    static final byte[][] cache = new byte[512][];
    static volatile int sink;
    public static void main(String[] args) {
        for (int round = 0; round < 120; round++) {
            for (int i = 0; i < cache.length; i++) {
                byte[] value = new byte[8 * 1024];
                value[0] = (byte) round;
                cache[i] = value;
                sink = value[0];
            }
        }
        System.out.println("slots=" + cache.length);
        System.out.println("last=" + cache[511][0]);
    }
}
```

```sh
javac --release 21 Deep13.java
java -Xms64m -Xmx64m -XX:+UseG1GC \
  -Xlog:gc*,gc+phases=debug:file=g1-deep.log:uptime,level,tags Deep13
```

출력은 `slots=512`, `last=119`입니다. 오래 유지되는 cache 컨테이너에 새 배열 참조를 반복 저장합니다. 컨테이너가 Old에 도달한 이후에는 Old→Young 참조가 생길 수 있습니다. 이 프로그램만으로 특정 시점의 승격이나 remembered set 비용 증가를 확정하지는 않습니다. GC 로그의 단계별 시간과 실제 부하를 확인하는 출발점입니다.

### 가상 로그 관측에서 가설 만들기

| 관측 | 가능한 해석 | 다음 증거 |
|---|---|---|
| Object Copy 계열 시간이 큼 | 생존 객체 대피 비용이 큼 | 수집 후 생존량, 요청·캐시 수명 |
| 참조 스캔 관련 시간이 큼 | 구역 밖 참조 조사 비용 영향 | 단계 로그, 업데이트 패턴과 수집 범위 |
| 동시 마킹 중 Old 점유 빠르게 증가 | 마킹 완료 전 여유 소진 위험 | 할당·승격 속도, CPU 제한 |
| Humongous region 증가 | 큰 객체가 구역을 연속 점유 | 큰 배열·문자열·직렬화 payload |
| Evacuation failure 또는 to-space 부족 | 옮길 공간 확보 실패 | 생존량과 대피 여유, Heap 점유 |

단계 이름은 JVM 버전과 로깅 수준에 따라 다를 수 있습니다. 한 번의 긴 pause만 보고 설정을 결정하지 말고 반복 패턴과 서비스 지연의 겹침을 확인하세요. `MaxGCPauseMillis`는 목표이며 외부 SLO를 보장하는 상한선이 아닙니다. 목표를 낮추면 수집 작업이 작게 나뉘며 빈도와 처리량에 영향을 줄 수 있습니다.

### Humongous를 이해하는 계산

Region이 1 MiB라면 객체 크기가 그 절반을 초과할 때 humongous로 다룹니다. 중요한 것은 배열 payload뿐 아니라 헤더 등을 포함한 객체 크기입니다. 따라서 `new byte[512 * 1024]`처럼 payload를 정확히 절반으로 맞춰도 전체 객체는 경계를 넘을 수 있습니다. 경계 실험에서는 헤더를 무시한 길이만으로 분류를 예언하지 않습니다.

큰 객체는 필요한 연속 Region 확보와 끝부분 낭비에 영향을 줄 수 있습니다. 하지만 Region을 크게 바꾸면 항상 해결되는 것은 아닙니다. 작은 수집 단위의 장점과 객체 분류가 함께 바뀝니다. 먼저 대형 엑셀·JSON·압축 결과를 한 배열에 모두 쌓는 구현인지, 스트리밍과 청크 처리로 최대 동시 보유량을 낮출 수 있는지 검토합니다.

### 변경 하나에 검증 지표 하나만 붙이지 않기

Heap을 늘리거나 pause 목표를 바꾼 뒤 pause만 짧아졌다고 성공으로 보지 않습니다. 같은 부하에서 처리량, p95·p99, CPU, GC 빈도와 총 정지 시간, 최대 생존량을 함께 봅니다. 평균 지연은 좋아졌지만 처리량이 떨어졌다면 용량 한계에서 다시 큐가 쌓일 수 있습니다. 애플리케이션 목표에 맞는 비교가 필요합니다.

<details class="question"><summary>심화 면접. G1 pause 목표를 200 ms에서 20 ms로 낮추면 p99가 20 ms 이하가 되나요?</summary><div class="answer"><p><strong>답변:</strong> 아닙니다. G1의 pause 목표는 수집 작업을 선택하는 휴리스틱의 목표이며 모든 정지의 상한 보장도, 요청 전체 지연의 보장도 아닙니다.</p><p><strong>이유:</strong> 요청에는 DB·네트워크·큐·락 대기 시간이 있고 GC도 생존량, CPU와 여유 공간의 제약을 받습니다. 목표를 줄이며 수집 빈도와 처리량이 달라질 수 있습니다.</p><p><strong>검증:</strong> 같은 부하에서 단계별 GC 시간과 서비스 지연을 연결하고, 총 정지 시간·처리량·CPU를 함께 비교하겠습니다. 수치 하나를 낮추는 것보다 목표 SLO를 만족하는지 확인하겠습니다.</p></div></details>

## 9. 상세 면접 Q&A

<details class="question"><summary>Q1. Mixed GC는 왜 Full GC가 아닌가요?</summary><div class="answer"><p>Mixed는 Young과 선택된 일부 Old Region을 함께 대피하는 점진적 수집입니다. 전체 Heap 정리의 복구 경로인 Full GC와 대상·비용이 다릅니다. Old가 포함되었다는 이유만으로 둘을 같은 이름으로 부르면 로그 진단이 틀어집니다.</p><p><strong>구체적으로:</strong> Mixed는 Young에 더해 일부 Old Region을 선택해 대피시키는 수집입니다. 모든 Heap을 한 번에 처리하는 의미로 이해하면 로그의 작업 범위를 과대 해석합니다.</p><p><strong>꼬리질문까지:</strong> Mixed 횟수가 늘어난 이유를 보려면 후보 Region과 생존량, 전체 사이클을 함께 확인합니다.</p></div></details>
<details class="question"><summary>Q2. G1에서 Concurrent와 STW가 동시에 설명되는 이유는 무엇인가요?</summary><div class="answer"><p>사이클의 단계별 실행 방식이 다릅니다. 전역 마킹의 큰 부분은 애플리케이션과 동시 진행하지만 대피·Remark 같은 정지 단계가 있습니다. 수집기의 한 단어 이름보다 어떤 단계가 어느 시간에 실행되는지 보는 것이 중요합니다.</p><p><strong>구체적으로:</strong> 동시 마킹 동안 애플리케이션이 실행될 수 있어도 대피 등 특정 단계에는 정지가 필요합니다. 수집기의 이름보다 단계별 실행 관계를 봐야 합니다.</p><p><strong>꼬리질문까지:</strong> Concurrent라는 단어를 모든 정지가 없다는 뜻으로 설명하지 않습니다.</p></div></details>
<details class="question"><summary>Q3. MaxGCPauseMillis를 10으로 하면 모든 정지가 10ms 아래인가요?</summary><div class="answer"><p>목표일 뿐 확정 상한이 아닙니다. live set, 참조 탐색, CPU, 공간 부족 등 때문에 초과할 수 있습니다. 지나치게 낮은 목표는 빈도와 처리량 비용을 늘릴 수 있어 지연 분포와 전체 처리량을 함께 측정해야 합니다.</p><p><strong>구체적으로:</strong> 목표는 예측과 작업 선택에 쓰이지만 작업량과 자원 조건 때문에 초과할 수 있습니다. 목표를 낮추면 더 잦은 수집이나 처리량 변화가 생길 수 있습니다.</p><p><strong>꼬리질문까지:</strong> 설정 전후의 p99·처리량·총 GC 시간까지 비교해야 원하는 교환인지 판단할 수 있습니다.</p></div></details>
<details class="question"><summary>Q4. SATB는 Heap 전체를 복사해 두나요?</summary><div class="answer"><p>물리적 전체 복사본을 만드는 뜻이 아닙니다. 참조 변경을 기록하며 시작 시점의 생존 객체를 놓치지 않는 추적 규칙입니다. 그 때문에 마킹 도중 죽은 객체가 보수적으로 다음 회수까지 남을 수 있습니다.</p><p><strong>구체적으로:</strong> 참조 변경 중 필요한 이전 값 정보를 장벽으로 기록해 마킹의 일관성을 돕습니다. Heap의 모든 바이트를 복제한 물리 스냅샷과는 다릅니다.</p><p><strong>꼬리질문까지:</strong> 동시 마킹 이후에 죽은 일부 객체가 다음 사이클까지 남을 수 있는 이유도 시작 시점 기준의 보수적인 생존 판단과 연결됩니다.</p></div></details>
<details class="question"><summary>Q5. 빈 Heap이 있는데도 Humongous 할당이 어려울 수 있나요?</summary><div class="answer"><p>필요한 연속 Region의 확보와 마지막 Region의 낭비를 고려해야 합니다. 빈 공간의 총합만으로 큰 연속 할당 가능성을 판정할 수 없습니다. 큰 객체 생성 경로와 live set, Region 분포를 함께 봅니다.</p><p><strong>구체적으로:</strong> Humongous 객체에 필요한 연속 Region이 부족하면 흩어진 빈 공간의 총량만으로 해결되지 않을 수 있습니다. 배열 길이 외에 헤더와 정렬도 크기에 영향을 줍니다.</p><p><strong>꼬리질문까지:</strong> 전체 데이터를 한 번에 만드는 방식을 분할·스트리밍으로 바꾸는 대안과 Region 조정을 비교합니다.</p></div></details>
<details class="question"><summary>Q6. G1 튜닝의 첫 행동은 무엇인가요?</summary><div class="answer"><p>JDK·수집기·Heap·CPU 제한과 대표 부하를 확인하고 GC 로그·할당·live set을 수집합니다. 누수·대형 객체·외부 대기로 인한 생존량 문제부터 구분합니다. 기본 적응형 정책을 출발점으로 한 번에 하나의 변경을 검증해야 합니다.</p><p><strong>구체적으로:</strong> 현재 JDK와 수집기, Heap 한도, GC 로그, 요청 부하를 먼저 기록합니다. 바꾸려는 목표가 지연인지 처리량인지도 정해야 합니다.</p><p><strong>꼬리질문까지:</strong> 여러 옵션을 한꺼번에 바꾸면 효과의 원인을 구분하기 어려우므로 하나의 가설에 맞춰 비교하세요.</p></div></details>
