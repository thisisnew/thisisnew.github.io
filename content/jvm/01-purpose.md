## 시작 전에: 이 편에서 쓰는 말

처음 읽는다면 아래 용어의 뜻만 확인한 뒤 본문으로 넘어가세요. 먼저 예제의 결과를 예상하고, 실행 과정을 따라간 다음, 면접 답변을 펼쳐 자신의 설명과 비교하면 좋습니다.

| 용어 | 이 글에서의 뜻 |
|---|---|
| 소스 | 사람이 작성하는 Java 코드 |
| 바이트코드 | JVM 명령으로 표현된 실행 코드 |
| 기계 코드 | 특정 CPU가 실행하는 명령 |
| 런타임 | 프로그램 실행에 필요한 환경 |

## 1. CPU는 Java 문장을 읽지 못한다

`System.out.println(3)`은 사람이 읽기 좋은 표기입니다. CPU가 실제로 수행하는 것은 자신이 이해하는 기계 명령입니다. ARM CPU와 x86 CPU는 사용하는 명령 체계가 다르고, macOS와 Linux는 실행 파일 형식과 운영체제 기능 호출 방식도 다릅니다. Java 소스를 각 환경의 실행 파일로만 미리 바꾸면 환경별 결과물을 관리해야 합니다.

Java는 그 사이에 공통 실행 형식인 **class 파일**과 **JVM(Java Virtual Machine)**을 둡니다. 개발 도구가 소스를 class 파일로 만들고, 각 환경의 JVM이 그 형식에 정의된 동작을 수행합니다. JVMS가 정의하는 JVM은 추상적인 실행 기계입니다. 구현체가 바뀌어도 규정된 프로그램 의미는 유지되어야 합니다. [공식 근거: JVMS §1.2, §2.1](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-1.html#jvms-1.2)

## 2. 공통 악보와 악기라는 비유

같은 악보를 바이올린과 피아노로 연주할 수 있습니다. 악보에는 어떤 음을 어떤 순서로 낼지가 적혀 있고, 각 악기는 자기 구조로 소리를 만듭니다. class 파일은 악보, 각 OS·CPU의 JVM은 연주 장치에 가깝습니다. 같은 class 파일을 옮겨도 Linux용 JVM 실행 파일을 macOS에서 그대로 실행하는 것은 별개 문제입니다.

다만 비유에는 한계가 있습니다. Java 프로그램은 운영체제 파일 경로, 외부 라이브러리, 네이티브 코드, 문자 인코딩, 시간대에 의존할 수 있습니다. 같은 악보라도 “이 장소의 특정 음향 장비를 사용하라”라는 조건이 붙으면 어느 공연장에서나 똑같이 연주할 수 없듯이, 이식성에는 환경 조건이 있습니다.

## 3. Java를 설치한다는 말의 정확한 의미

| 이름 | 하는 일 | 확인할 예 |
|---|---|---|
| Java 언어 | 소스 문법·타입·표현식·메모리 모델의 의미 | class, interface, synchronized |
| JVMS | class 형식과 가상 기계 동작의 약속 | iadd, 프레임, 클래스 로딩 |
| JVM 구현 | 약속을 실제 OS·CPU에서 수행 | HotSpot |
| Java 표준 라이브러리 | 프로그램이 호출하는 공통 기능 | String, List, java.io |
| JRE라는 개념 | JVM과 라이브러리 등 실행에 필요한 환경 | 프로그램 실행에 필요한 구성 |
| JDK | 실행 환경과 개발·진단 도구 | java, javac, javap, jcmd |

JDK는 개발 키트입니다. `javac`는 컴파일러이고 `java`는 Java 프로그램을 시작하는 런처입니다. HotSpot은 OpenJDK와 여러 JDK 배포판에서 사용하는 JVM 구현입니다. “Java 21”은 언어·플랫폼 버전을 가리키며, “HotSpot 21”이라는 말로 전체 플랫폼과 구현을 완전히 같은 개념으로 취급해서는 안 됩니다.

과거에는 JDK 안에 별도 `jre` 디렉터리가 있는 그림이 널리 쓰였습니다. 현대 JDK는 모듈 구조를 사용하므로 그 디렉터리 그림을 JDK 21의 실제 배포 구조라고 외우지 마세요. 별도 JRE 상품 제공 여부는 배포판마다 다르며, `jlink`로 필요한 모듈을 담은 런타임 이미지를 만들 수도 있습니다. [공식 근거: jlink](https://docs.oracle.com/en/java/javase/21/docs/specs/man/jlink.html)

## 4. JVM은 단순 번역기보다 많은 일을 한다

첫째, class 바이트를 읽고 형식과 타입 사용을 검증합니다. 둘째, 클래스와 메서드가 참조하는 다른 요소들을 연결하고 초기화합니다. 셋째, 스레드가 메서드를 호출할 실행 상태와 객체를 담을 메모리를 관리합니다. 넷째, 더 이상 도달할 수 없는 객체의 공간을 GC로 회수합니다.

HotSpot은 실행 중 자주 쓰이는 코드에 JIT 최적화도 적용합니다. 이때 바이트코드 한 줄이 항상 기계 명령 한 줄에 대응하는 것은 아닙니다. 메서드 호출이 인라이닝되어 사라지거나 계산이 합쳐져도, 관측 가능한 Java 프로그램의 의미는 보존해야 합니다. JVMS는 모든 구현에 특정 JIT나 GC 알고리즘을 강제하지 않습니다. [공식 근거: 공개 설계와 구현 자유](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-2.html#jvms-2.13)

## 5. 첫 번째 실습: 실행 환경을 눈으로 확인하기

아래 코드를 `Lesson01.java`에 저장합니다. 환경 값을 출력한 뒤 같은 컴파일 결과가 JVM에서 실행되는지 확인합니다. 외부 라이브러리는 필요 없습니다.

```java
// file: Lesson01.java
public class Lesson01 {
    public static void main(String[] args) {
        System.out.println("java=" + System.getProperty("java.version"));
        System.out.println("vm=" + System.getProperty("java.vm.name"));
        System.out.println("os=" + System.getProperty("os.name"));
        System.out.println("arch=" + System.getProperty("os.arch"));
        System.out.println("sum=" + (20 + 22));
    }
}
```

```sh
javac --release 21 Lesson01.java
java Lesson01
javap -verbose Lesson01
```

`sum=42`는 환경과 무관한 논리적 결과입니다. `os`와 `arch`는 머신에 따라 달라집니다. `javap`에서 major version 65를 확인하세요. ARM64 Mac과 x86 Linux에서 동일 class 파일을 실행할 수 있지만, 양쪽 모두 그 버전을 지원하는 JVM과 필요한 라이브러리를 갖추어야 합니다.

`java -version`과 `javac -version`도 각각 확인하세요. PATH가 섞이면 컴파일은 21로 하고 실행은 17로 하는 상황이 생길 수 있습니다. 실행 중인 서비스의 JVM은 내 터미널의 JVM과 다를 수 있으므로 컨테이너 이미지와 프로세스 명령행도 확인해야 합니다.

## 6. 이식성이 깨지는 네 가지 경계

**버전:** JDK 21로 만든 일반 class 파일은 Java 17 JVM이 읽을 수 없습니다. 반대로 최신 JVM이 오래된 class 파일을 지원하는 경우가 많지만, 제거된 API나 달라진 실행 환경까지 자동 복구하지는 않습니다.

**네이티브 의존성:** JNI로 연결하는 `.so`나 `.dylib`는 OS와 CPU에 맞아야 합니다. Java 코드가 이식 가능해도 연결된 네이티브 라이브러리가 x86 전용이면 ARM 실행이 막힐 수 있습니다.

**환경 의존성:** 절대 경로, 기본 시간대, 파일 권한, 외부 시스템 응답은 JVM이 같아도 달라집니다. 입고 마감 시각을 서버 기본 시간대에 맡긴 코드는 배포 환경에서 다른 날짜를 만들 수 있습니다.

**메모리·CPU 예산:** 프로그램의 의미가 같다는 것은 같은 지연 시간과 처리량을 보장한다는 뜻이 아닙니다. JVM이 정상 실행되어도 작은 컨테이너 메모리 한도를 초과하면 OS가 종료할 수 있습니다. 이 경계는 16편에서 진단합니다.

## 7. 장애 사례: 배포하자마자 UnsupportedClassVersionError

가정: 개발자는 JDK 21로 컴파일했고 서버 이미지는 Java 17입니다. 애플리케이션이 요청을 받기 전에 실패합니다. 이 에러는 “GC가 부족하다”나 “Spring Bean 설정이 틀렸다”로 접근할 문제가 아닙니다. 실행 JVM이 해당 클래스 파일 버전을 지원하는지부터 확인해야 합니다.

확인 순서는 빌드 로그의 JDK 버전, 실제 컨테이너의 `java -version`, 문제가 된 class의 `javap -v` 출력입니다. 해결은 실행 환경을 의도한 JDK로 맞추거나, 소스와 모든 의존성이 지원하는 낮은 타깃으로 다시 빌드하는 것입니다. `--release 17`을 붙였다고 Java 21 전용 API와 21 전용 라이브러리가 갑자기 17과 호환되지는 않습니다. 공식 도구의 `--release` 범위를 확인하고 의존성도 함께 검사합니다.

## 더 깊이: JVM과 Docker는 어떤 경계를 추상화하는가

둘 다 가상화라는 단어와 연결되지만 추상화 대상이 다릅니다. JVM은 class 형식과 명령·메모리·객체·예외의 실행 의미를 제공합니다. Docker 컨테이너는 운영체제의 프로세스 격리와 자원 제한을 활용하는 실행 환경입니다. Linux 컨테이너 안에서도 Java 프로그램에는 JVM과 표준 라이브러리가 필요합니다. 반대로 JVM을 쓴다고 파일·네트워크·프로세스 권한이 컨테이너처럼 자동 격리되는 것은 아닙니다.

Spring도 별도 층입니다. Spring은 JVM 위에서 실행되는 라이브러리·프레임워크이며 객체를 만들고 연결하고 요청을 처리하는 규칙을 제공합니다. Spring Bean을 GC가 아니라 Spring이 만들었다고 해서 Heap 밖의 특별한 메모리에 존재하는 것은 아닙니다. Bean 객체 역시 Java 객체이고, 컨테이너의 참조가 수명에 영향을 줄 수 있습니다.

따라서 장애 질문을 계층별로 나누세요. class 버전 오류는 컴파일·JVM 버전, Bean 생성 실패는 애플리케이션 구성과 초기화, 파일 권한 오류는 OS·컨테이너 환경, 메모리 제한 종료는 프로세스 전체 자원이라는 단서입니다. 같은 'Java 서비스 시작 실패'라도 처음 실패한 계층이 다릅니다.

## 차근차근 이해하기: 파일·프로세스·실행 환경은 서로 다르다

처음에는 `.java`, `.class`, `java`가 비슷한 이름이라 혼동하기 쉽습니다. `.java`는 사람이 편집하는 **소스 파일**, `.class`는 컴파일러가 만든 **클래스 파일**, `java`는 JVM을 시작하고 프로그램을 실행하도록 하는 **명령**입니다. 같은 폴더에 이들이 함께 보이더라도 역할은 다릅니다. 클래스 파일은 디스크에 저장된 데이터이므로 그 자체가 CPU나 메모리를 계속 사용하는 것은 아닙니다. 실행 명령을 내려 프로세스가 만들어져야 실행 상태가 생깁니다.

프로세스는 운영체제가 관리하는 실행 중인 프로그램 단위라고 생각하면 됩니다. 같은 `Lesson01.class`를 두 터미널에서 실행하면 일반적으로 별개의 Java 프로세스 두 개가 생깁니다. 두 프로세스가 같은 클래스 파일을 읽어도 Java의 static 변수와 Heap이 자동으로 공유되는 것은 아닙니다. 배포 서버를 두 대로 늘렸는데 `static int requestCount`가 전체 요청 수를 세지 못하는 이유도 여기서 출발합니다.

| 눈으로 확인할 대상 | 파일인가, 실행 상태인가 | 처음 확인할 질문 |
|---|---|---|
| Lesson01.java | 소스 파일 | 어떤 코드를 작성했는가? |
| Lesson01.class | 바이너리 파일 | 어떤 Java 버전을 대상으로 만들었는가? |
| java 실행 파일 | OS가 시작할 수 있는 프로그램 | 어느 JDK 경로의 실행 파일인가? |
| 실행 중인 JVM | 프로세스 내부 실행 환경 | 어떤 옵션과 라이브러리로 실행 중인가? |
| 프로그램 출력 | 실행 결과 | 코드와 환경 중 무엇의 영향을 받았는가? |

### 같은 덧셈이 여러 환경에서 실행되는 과정을 따라가자

`20 + 22`를 계산하는 메서드를 만들었다고 합시다. javac는 결과를 JVM이 이해하는 형식으로 표현합니다. 특히 20 + 22처럼 상수만의 식은 컴파일 시 42로 접힐 수 있어 실행 시 덧셈 명령이 남는다고 단정하지 않습니다. Linux x86용 HotSpot은 x86에서 실행될 수 있는 방식으로, Linux ARM용 HotSpot은 ARM에서 실행될 수 있는 방식으로 그 의미를 수행합니다. 프로그램은 42를 얻어야 하지만, 내부에서 사용하는 기계 명령이나 컴파일 시점, 실행 시간까지 같아야 하는 것은 아닙니다.

이 점을 택배 배송에 비유하면 **배송 약속**과 **운송 수단**의 차이입니다. “주소 A로 상자 하나를 보낸다”는 약속은 같아도 지역에 따라 트럭이나 배를 쓸 수 있습니다. JVM 사양은 약속을 규정하고 HotSpot은 구체적인 운송 체계를 구현합니다. 따라서 성능을 설명할 때는 “JVM은 반드시 이렇게 한다”와 “이 버전의 HotSpot은 이렇게 구현한다”를 구분해야 합니다.

```sh
java -cp . Lesson01
```

첫 두 명령의 버전을 함께 확인하세요. PATH 설정에 따라 실행기와 컴파일러가 서로 다른 설치 경로를 가리킬 수 있습니다. `--release 21`은 소스 문법, 생성할 클래스 파일 버전, 사용 가능한 표준 API의 범위를 Java 21 대상으로 맞추는 데 쓰입니다. 그러나 외부 의존 라이브러리까지 자동으로 Java 21 호환으로 다시 만들어 주지는 않습니다.

`-cp .`의 점은 현재 디렉터리를 클래스 검색 경로에 넣겠다는 뜻입니다. 실행할 때는 `Lesson01.class`가 아니라 클래스 이름 `Lesson01`을 전달합니다. 패키지가 있다면 그 이름까지 포함한 클래스 이름과 올바른 검색 루트가 필요합니다. “파일이 있는데 실행이 안 된다”는 상황에서는 파일 존재 여부 다음으로 **클래스 이름과 검색 경로의 관계**를 확인해야 합니다.

<details class="question"><summary>확인 문제. 개발 PC에서 실행된 class 파일이면 서버에서도 실행된다고 확정할 수 있나요?</summary><div class="answer"><p><strong>판단:</strong> 아직 확정할 수 없습니다. 서버 JVM이 클래스 파일 버전을 지원해야 하고, 필요한 표준 API와 외부 의존성, 네이티브 라이브러리 및 운영 환경도 맞아야 합니다.</p><p><strong>추적 예:</strong> 개발 PC에서는 JDK 21로 실행하고 서버에서는 JDK 17로 실행하면 Java 21 클래스 파일을 읽는 단계에서 실패할 수 있습니다. 양쪽 모두 21이어도 특정 OS용 네이티브 라이브러리만 포함했다면 다른 OS에서 실패할 수 있습니다.</p><p><strong>꼬리질문:</strong> Docker를 쓰면 전부 해결될까요? 이미지로 사용자 공간과 실행 환경을 고정하는 데 도움이 되지만 CPU 아키텍처, 호스트 자원 제한, 외부 설정과 서비스 의존성까지 사라지는 것은 아닙니다. 배포 산출물과 실제 실행 조건을 함께 검증해야 합니다.</p></div></details>

## 심화 실험실: 빌드 성공과 배포 성공 사이의 세 가지 계약

### 계약을 나누면 에러를 읽을 수 있다

식당에 레시피를 전달한다고 생각해 보겠습니다. 레시피의 언어를 읽을 수 있어야 하고, 필요한 조리 도구가 있어야 하며, 실제 주방에서 재료를 구할 수 있어야 합니다. Java 배포에서도 **class 형식**, **API와 의존성**, **실행 환경**이라는 서로 다른 조건을 만족해야 합니다. 첫 조건만 맞았다고 나머지가 자동으로 맞지는 않습니다.

`--release 17`은 “17에서도 읽을 class 파일을 만든다”보다 넓은 기능입니다. Java 17의 언어 규칙과 표준 API 범위를 대상으로 컴파일하도록 돕습니다. 반면 `-source 17 -target 17`만 설정하면 컴파일러가 현재 JDK의 더 새로운 표준 API를 보고 컴파일할 여지가 있습니다. 그러면 파일 버전은 오래되었는데 실행 중 필요한 메서드는 없는 모순이 생길 수 있습니다. 빌드 성공은 컴파일 당시 참조한 세계에서의 성공입니다.

### 실제 API를 사용해 경계 확인하기

```java
// file: Deep01.java
import java.util.List;
public class Deep01 {
    public static void main(String[] args) {
        List<String> warehouses = List.of("GIMPO", "PYEONGTAEK");
        System.out.println(warehouses.getFirst());
    }
}
```

JDK 21의 `List.getFirst()`를 사용하는 예제입니다. JDK 21로 다음 명령을 실행하면 첫 번째 컴파일과 실행은 성공하고 `GIMPO`가 출력됩니다. 마지막 컴파일은 의도적으로 실패해야 합니다.

```sh
javac --release 21 Deep01.java
java Deep01
javac --release 17 Deep01.java
```

마지막 실패는 JVM 실행 에러가 아닙니다. **컴파일 단계에서 Java 17 API에 없는 메서드를 걸러 낸 것**입니다. 이것이 실제 서버까지 가기 전에 잡고 싶은 실패입니다. 의존 JAR이 이미 Java 21로 빌드되어 있다면 내 코드의 release 설정만 내려도 그 JAR이 재컴파일되지는 않습니다. 직접 작성한 코드와 가져온 바이너리의 타깃을 함께 관리해야 합니다.

| 상황 | 실패하는 경계 | 가장 먼저 볼 증거 |
|---|---|---|
| class 버전 65를 Java 17에서 실행 | 파일 형식 지원 | 실제 PID의 JVM 버전, class major version |
| 호출자가 기대한 메서드가 배포 JAR에 없음 | 바이너리 연결 | 호출 descriptor, 실제 로드한 JAR |
| ARM 서버가 x86 네이티브 라이브러리 로드 | 네이티브 실행 환경 | OS·아키텍처·라이브러리 파일 |
| 서울 기준 날짜를 UTC 기본값으로 계산 | 애플리케이션 환경 가정 | 명시한 ZoneId와 컨테이너 설정 |

### 운영에서 쓸 수 있는 배포 체크의 이유

빌드 JDK, 실행 JDK, 의존성 잠금 정보, 이미지 식별자를 한 묶음으로 남깁니다. “둘 다 Java 21”이라는 기록만으로는 패치·배포판·옵션 차이를 재현하기 어렵습니다. 특히 Blue-green 배포에서 새 서버만 실패한다면 소스 차이뿐 아니라 실제 런타임과 JAR 구성 차이도 비교해야 합니다. 여기서 JVM 학습은 추상적인 용어 암기를 넘어 장애 조사 범위를 줄이는 도구가 됩니다.

<details class="question"><summary>심화 면접. --release를 쓰면 하위 Java 버전 호환성이 완전히 보장되나요?</summary><div class="answer"><p><strong>답변:</strong> 자신의 소스를 대상 언어·class 형식·표준 API 범위에 맞춰 컴파일하는 데 도움이 되지만, 모든 외부 JAR과 네이티브 코드, 리플렉션으로 접근하는 API, 운영 환경까지 검증하지는 않습니다.</p><p><strong>이유:</strong> 컴파일러가 직접 타입 검사하는 참조와 실행 중 동적으로 찾아가는 참조의 범위가 다르기 때문입니다. 문자열로 적은 클래스 이름을 컴파일러가 실행 환경에서 실제로 찾아보는 것은 아닙니다.</p><p><strong>실무 답변:</strong> release 설정에 더해 실제 배포 런타임에서 기동과 핵심 요청 경로를 실행하고, 의존성 버전 및 이미지 식별자를 고정하겠습니다. 오류를 발견하면 class 버전·API 연결·환경 의존성 중 어디서 실패했는지 나누겠습니다.</p></div></details>

추가 근거: [javac의 --release 및 교차 컴파일](https://docs.oracle.com/en/java/javase/21/docs/specs/man/javac.html), [List.getFirst API](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/List.html#getFirst()).

## 8. 상세 면접 Q&A

<details class="question"><summary>Q1. JVM이 있는데 왜 운영체제별 JDK를 받아야 하나요?</summary><div class="answer"><p>공통인 것은 class 파일의 형식과 실행 의미입니다. 그 약속을 구현하는 JVM 자체는 네이티브 프로그램이므로 OS와 CPU에 맞게 만들어져야 합니다. Linux x86 JDK와 macOS ARM JDK는 같은 플랫폼 규칙을 다른 기계에서 구현합니다.</p><p>따라서 배포 대상을 확인할 때 Java 버전뿐 아니라 OS·아키텍처·네이티브 라이브러리 지원도 봅니다. class 파일의 이식성과 JVM 실행 파일의 이식성은 구분해서 답해야 합니다.</p><p><strong>구체적으로:</strong> class 파일은 공통 형식이지만 JVM 실행 파일은 OS의 실행 형식과 CPU 명령에 맞아야 합니다. 같은 악보를 읽더라도 악기는 각자 실제로 소리를 낼 수 있는 구조여야 하는 것과 같습니다.</p><p><strong>꼬리질문까지:</strong> 컨테이너 이미지의 CPU 아키텍처까지 확인해야 하는 이유도 같은 경계에서 설명할 수 있습니다.</p></div></details>
<details class="question"><summary>Q2. JDK·JRE·JVM의 포함 관계만 외우면 충분한가요?</summary><div class="answer"><p>개념적 역할을 이해하는 데는 도움이 되지만, 과거 디렉터리 구조를 현대 JDK에 그대로 대입하면 틀립니다. JVM은 실행 엔진의 구현이고 실행에는 라이브러리 등이 추가로 필요하며 JDK에는 개발 도구가 포함됩니다. 현대 JDK에서는 모듈과 jlink를 함께 설명하는 것이 정확합니다.</p><p><strong>구체적으로:</strong> 개발 PC에는 javac가 필요하지만 배포 환경은 실행에 필요한 모듈과 도구를 어떻게 제공할지가 중요합니다. 실제 배포판의 구성은 단순한 포함 관계 그림만으로 결정되지 않습니다.</p><p><strong>꼬리질문까지:</strong> jlink로 만든 런타임은 필요한 모듈에 맞게 구성할 수 있지만, 서비스에 필요한 모듈과 진단 도구가 포함됐는지 검증해야 합니다.</p></div></details>
<details class="question"><summary>Q3. JVM은 반드시 인터프리터와 JIT를 모두 가져야 하나요?</summary><div class="answer"><p>JVMS는 특정 실행 최적화 방식을 강제하지 않습니다. HotSpot은 보통 인터프리터와 계층형 JIT를 사용하지만, 그것을 모든 JVM의 사양상 의무라고 말하면 안 됩니다. 구현은 최적화 방식이 달라도 명세된 동작을 지켜야 합니다.</p><p><strong>구체적으로:</strong> JVMS는 프로그램의 관찰 가능한 동작을 규정하고 실행 전략에는 구현의 선택 여지를 둡니다. HotSpot의 인터프리터·JIT 구조를 다른 모든 JVM의 의무로 설명하면 사양과 구현을 섞게 됩니다.</p><p><strong>꼬리질문까지:</strong> 성능 질문에서는 JVM 구현체·버전·옵션을 먼저 고정하고, 언어 의미 질문에서는 사양의 보장을 먼저 설명하세요.</p></div></details>
<details class="question"><summary>Q4. Java의 플랫폼 독립성은 성능도 동일하다는 뜻인가요?</summary><div class="answer"><p>아닙니다. 의미와 형식의 이식성이 핵심입니다. CPU, 메모리, 운영체제 스케줄링, GC 선택, JIT 프로파일이 다르면 실행 시간은 달라집니다. 특정 머신에서 얻은 초당 처리량을 다른 환경의 보장값으로 제시할 수 없습니다.</p><p><strong>구체적으로:</strong> 같은 결과 42가 나와도 CPU 명령, 코어 수, 메모리 대역폭, JIT 결정은 다를 수 있습니다. 파일 읽기나 외부 호출은 OS와 주변 환경의 차이도 받습니다.</p><p><strong>꼬리질문까지:</strong> 서버 이전 전후 성능은 같은 입력·부하·자원 제한으로 비교해야 하며, class 파일이 같다는 사실만으로 성능 회귀를 배제할 수 없습니다.</p></div></details>
<details class="question"><summary>Q5. Kotlin도 JVM에서 동작하는 이유는 무엇인가요?</summary><div class="answer"><p>JVM은 Java 소스만 읽도록 정의된 것이 아니라 class 파일 형식과 명령 실행을 규정합니다. Kotlin의 JVM 타깃 컴파일러가 이를 만족하는 결과를 생성하면 실행할 수 있습니다. 다만 언어별 런타임 라이브러리와 타깃 버전 등 추가 조건이 필요합니다.</p><p><strong>구체적으로:</strong> JVM은 원래 소스가 어느 언어였는지보다 class 파일 형식과 실행 규칙을 충족하는지가 중요합니다. 다른 언어의 컴파일러도 그 형식에 맞는 코드를 만들 수 있습니다.</p><p><strong>꼬리질문까지:</strong> 언어별 런타임 라이브러리와 생성 코드의 특성은 별도로 필요할 수 있습니다. JVM 위에서 동작한다는 것이 모든 의존성이 같다는 뜻은 아닙니다.</p></div></details>
<details class="question"><summary>Q6. 실제 서비스 JVM을 확인하려면 무엇부터 보나요?</summary><div class="answer"><p>실행 중인 프로세스와 컨테이너를 기준으로 버전, VM 이름, 명령행, 옵션을 확인합니다. 로컬 터미널의 java 명령만으로 서버 환경을 추정하지 않습니다. jcmd의 VM.version과 VM.command_line은 연결 권한과 도구 호환성이 확보된 환경에서 유용합니다.</p><p><strong>구체적으로:</strong> 터미널의 java -version과 서비스 프로세스의 JVM이 다를 수 있습니다. 서비스 실행 경로·이미지·시작 옵션을 먼저 확인하고 실제 PID에 대한 VM.version과 command_line으로 연결합니다.</p><p><strong>꼬리질문까지:</strong> 같은 Java 21이어도 배포판·패치 버전과 옵션이 다를 수 있으므로 재현 보고서에는 구체적인 빌드까지 남깁니다.</p></div></details>
