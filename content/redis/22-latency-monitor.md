## 이 장에서 해결할 질문

사용자가 “결제 화면이 가끔 멈춘다”고 말했다. 애플리케이션 로그에는 Redis 호출이 80ms 걸렸다고 적혀 있다. Redis는 메모리 데이터베이스이고 평소 GET은 매우 빠르다고 배웠다. 그렇다면 Redis가 80ms 동안 GET을 실행한 것일까? 아직 그렇게 말할 수 없다. 애플리케이션이 측정한 구간에는 연결을 기다린 시간, 네트워크 왕복, 서버에서 차례를 기다린 시간, 명령 실행, 응답 수신, 자바 객체로 변환하는 시간이 섞여 있기 때문이다. 이 장의 목표는 도구 이름을 많이 외우는 것이 아니라, 서로 다른 시계가 가리키는 시간을 올바르게 연결하는 것이다.

먼저 결론을 기억하자. **LATENCY는 Redis 내부의 특정 작업 경로에서 발생한 지연 이벤트를 관찰하는 장치이며, 모든 사용자 요청의 종단 간 지연을 기록하는 APM이 아니다.** 이 차이를 이해하면 “LATENCY가 비어 있으니 Redis는 무죄”나 “fork 이벤트가 있으니 모든 timeout은 fork 때문”이라는 성급한 판단을 피할 수 있다. 도구는 증거를 제공한다. 인과관계는 시간 범위, 요청 경로, 재현 결과, 다른 지표를 함께 검토하여 만들어야 한다.

학습 순서는 다음과 같다. 첫째, 요청 하나가 거치는 대기 구간을 나눈다. 둘째, Redis가 기록하는 이벤트와 그 보존 방식을 익힌다. 셋째, 서비스의 지연 예산에서 관찰 임계값을 도출한다. 넷째, 실제 설정을 변경하기 전에 읽기 중심으로 증거를 수집한다. 마지막으로 가상 장애 사례를 통해 어떤 가설을 유지하고 어떤 가설을 버릴지 결정한다. 운영 중인 서버에 부하를 만들거나 설정을 바꾸는 일은 이 글을 읽었다는 이유만으로 허용되지 않는다.

## 1. 식당의 주문 시간과 조리 시간은 다르다

Redis 호출을 식당 주문에 비유해 보자. 손님은 입구에서 자리 배정을 기다리고, 주문을 전달하고, 주방에서 조리 순서를 기다리고, 요리가 완성된 뒤 직원이 가져다주기를 기다린다. 손님의 체감 시간은 입구부터 식탁까지다. 요리사가 스톱워치로 잰 시간은 실제 조리 시작부터 끝까지다. 두 값이 다르다는 사실은 어느 쪽 시계가 틀렸다는 뜻이 아니다. **측정 경계가 다르다는 뜻**이다.

여기에 Redis를 대응시키면 연결 풀 대기는 자리 배정, 네트워크 전송은 주문 전달, 서버 실행 대기는 주방의 주문 줄, 명령 실행은 조리, 응답 수신과 역직렬화는 음식 운반과 그릇 정리에 가깝다. 이 비유에도 한계가 있다. Redis는 여러 작업을 이벤트 루프로 처리하고, 네트워크 버퍼와 OS 스케줄러가 개입하며, 일부 백그라운드 작업도 존재한다. 따라서 “Redis는 직원 한 명인 식당이다”라는 설명만으로 모든 실행을 단순화하면 안 된다. 여기서는 대기와 실행을 구분하기 위한 비유로만 사용한다.

```text
사용자 요청 시작
  → 애플리케이션 작업 큐
  → 연결 획득 또는 연결 준비
  → 요청 인코딩 / 소켓 쓰기
  → 네트워크 / 서버 소켓 버퍼
  → Redis에서 실행 차례 대기
  → 명령 실행
  → 응답 전송 / 수신
  → 역직렬화 / 후속 콜백
  → 사용자 응답 완료
```

이 경로에서 한 곳만 느려져도 전체 호출은 느려진다. 서버 명령 실행이 0.1ms였더라도 연결 풀에서 50ms 기다렸다면 사용자는 느리다고 느낀다. 반대로 평균 연결 획득이 빠르더라도 어떤 큰 작업이 실행 경로를 오래 점유하면 뒤에 도착한 작은 GET도 기다릴 수 있다. 작은 명령이 오래 걸린다는 보고를 받았을 때 작은 명령 자체만 분석하면 앞서 실행된 큰 작업을 놓칠 수 있다.

## 2. 지연 시간은 하나의 숫자가 아니라 측정 계약이다

운영 문서에 “Redis latency 5ms”라고 쓰려면 최소한 어디서 어디까지 잰 것인지, 성공한 요청만인지, timeout도 포함했는지, 어떤 분위수인지, 어느 시간 구간인지 밝혀야 한다. 평균 5ms와 p99 5ms는 전혀 다른 주장이다. p99는 관측 집합에서 약 99%가 그 값 이하였다는 뜻이지, 다음 요청이 반드시 그 시간 안에 끝난다는 보장은 아니다. 짧은 구간에 표본이 적으면 꼬리 지연의 추정도 흔들린다.

예를 들어 1분 동안 완료한 요청 100개만 모으고, 2초에서 timeout 난 요청 20개를 버렸다고 하자. 성공 요청 p99가 낮아도 사용자 경험이 좋았다고 결론 내릴 수 없다. 실패한 요청은 실패율로 남기고, timeout 경계에서 관측이 잘렸다는 사실도 기록해야 한다. 이 문제는 Redis 모니터 기능의 결함이 아니라 애플리케이션 측정 설계의 문제다. 서버 이벤트만 추가해도 사라지지 않는다.

각 계층은 서로 다른 시간 단위를 쓰기도 한다. LATENCY 이벤트의 지연 값은 밀리초 단위다. SLOWLOG의 명령 실행 시간은 마이크로초 단위다. Java의 `System.nanoTime()` 차이는 나노초 단위다. 대시보드에 값을 합치기 전에 단위를 정규화하고, 원본 단위를 메타데이터로 보존해야 한다. 숫자 1000을 밀리초와 마이크로초 사이에서 잘못 옮기면 심각도가 천 배 달라진다. 그래프 모양이 그럴듯하다고 단위 검증을 생략하지 않는다.

## 3. LATENCY 모니터 내부의 사고방식

입력 자료의 공식 설명은 모니터를 네 부분으로 나눈다. 지연에 민감한 내부 경로의 측정 지점, 이벤트별 시간 기록, 기록을 조회하는 명령, 사람이 읽을 수 있는 분석이다. 애플리케이션 요청마다 추적 ID를 붙여 전 과정을 저장하는 방식과 다르다. 이름 붙은 내부 작업이 설정된 기준을 넘었는지 관찰하고, 해당 이벤트의 시계열에 표본을 남기는 방식이다.

예를 들어 `command`는 일반적인 명령 실행 경로의 지연을, `fast-command`는 빠른 복잡도 범주에 속하는 명령 경로의 지연을 살펴보는 이름이다. `fork`는 자식 프로세스를 만들 때의 시스템 호출 구간을 관찰한다. 만료 처리, 메모리 회수, AOF 관련 작업도 별도 이벤트로 나타날 수 있다. 이벤트의 정확한 목록과 구현 경로는 실행 버전에 따라 확인한다. 최신 문서에 나온 이름을 오래된 서버에서 반드시 찾을 수 있다고 가정하지 않는다.

중요한 것은 이벤트 이름이 곧 장애 원인 전체를 뜻하지 않는다는 점이다. `fork`가 오래 걸렸다면 자식 생성 과정의 지연이라는 범위까지는 좁혀진다. 그러나 왜 오래 걸렸는지는 메모리 규모, OS 상태, 페이지 테이블 처리, 호스트 경쟁 같은 추가 가설이 필요하다. `aof-write`가 보이면 파일 쓰기 경로의 관찰이라는 근거가 생기지만, 저장 장치 자체의 문제인지 다른 I/O와의 경쟁인지까지 하나의 이름으로 확정할 수 없다.

공식 모니터 문서의 기록 구조에서 특히 기억할 내용은 이벤트별 기록이 제한되어 있고 같은 초의 여러 지연이 하나로 합쳐질 수 있다는 사실이다. 입력 원문은 이벤트 시계열에 160개 요소가 있으며, 같은 이벤트가 같은 초에 여러 번 관측되면 최댓값을 남긴다고 설명한다. 따라서 이 데이터는 모든 요청의 원시 로그가 아니다. 이 의미를 확인할 때는 [Redis latency monitoring 공식 문서](https://redis.io/docs/latest/operate/oss_and_stack/management/optimization/latency-monitor/)와 실제 서버 버전을 함께 본다.

## 4. 기록이 압축되면 어떤 질문에 답할 수 없을까

같은 초에 2ms 지연이 100번, 40ms 지연이 한 번 있었다고 가정하자. 기록에는 그 초를 대표하는 큰 값만 남을 수 있다. 이를 보고 “그 초에 느린 요청이 딱 한 번 있었다”고 말하면 틀린다. 반대로 그 표본을 요청 개수 101개로 확장하여 분포를 계산할 수도 없다. 원래 발생 횟수가 사라졌기 때문이다. 압축된 이벤트 기록은 느린 순간이 있었는지 찾는 데 유용하지만, 사용자 요청 지연 분포의 대체재가 아니다.

“160개 요소”를 “항상 최근 160초”라고 읽는 것도 잘못이다. 이벤트가 계속 발생한다면 초 단위 병합 때문에 그 정도 이상의 시간 폭이 확보될 수 있지만, 이벤트가 드문 서버에서는 더 오래된 시각이 남는다. 반대로 장기 장애 보고서를 만들기 위해 하루 뒤에 접속했을 때 원하는 순간의 기록이 여전히 존재한다고 보장할 수 없다. 필요한 관찰 기간은 외부 수집 시스템의 보존 정책으로 설계한다.

이 제한은 도구 선택을 바꾼다. 지난 30일간 사용자 p99 추세가 필요하면 애플리케이션 히스토그램과 장기 메트릭 저장소를 쓴다. 특정 시각에 서버 내부에서 어떤 느린 경로가 있었는지 알고 싶으면 LATENCY를 본다. 비싼 명령의 일부 인자와 실행 시간이 필요하면 접근 권한과 민감 정보 정책을 확인한 뒤 SLOWLOG를 검토한다. 질문이 다르면 필요한 증거도 다르다. 한 도구에서 모든 답을 얻으려 하지 않는다.

## 5. 임계값은 경보 기준과 동일하지 않다

임계값을 정할 때 “우리는 사용자 p99가 100ms 이하면 되니까 Redis 모니터도 100ms면 된다”고 바로 결정하지 않는다. 사용자 요청은 인증, DB, 외부 API, 응답 직렬화 등 여러 구간을 포함한다. Redis 한 구간이 80ms를 사용하면 아직 100ms를 넘지 않았더라도 전체 예산을 거의 소진했을 수 있다. 내부 관찰 기준은 서비스 전체 SLO를 계층별 지연 예산으로 나누어 생각해야 한다.

다만 너무 낮게 잡으면 일상적인 작은 변동까지 기록되어 사건 구분이 어려워진다. 목표는 데이터가 많아지는 것이 아니라 의사결정에 도움이 되는 데이터가 생기는 것이다. 처음에는 정상 시간대의 애플리케이션 분포, 요청량, 명령 구성, 서버 자원을 함께 조사한다. 그다음 “이 정도 내부 멈춤이면 사용자의 꼬리 지연을 설명하는 데 중요하다”는 기준을 세우고, 승인된 환경에서 관찰한다. 임계값의 변경 이유와 적용 시간을 반드시 적는다.

기본값과 실제 설정을 혼동하지 말자. 입력 원문은 기본 임계값 0에서 모니터가 꺼져 있다고 설명한다. 그래서 데이터가 없다는 사실만으로 이벤트가 없었다고 결론 낼 수 없다. 모니터가 켜져 있었는지, 해당 시간에 임계값이 얼마였는지부터 확인해야 한다. “없음”은 관측 결과일 수도 있고, 관측하지 않은 상태일 수도 있다. 이 구분을 못 하면 장애 회고에서 빈 그래프를 무죄 증거로 제출하게 된다.

## 6. 읽기 중심의 첫 조사

아래 명령은 사용 중인 제품·권한·버전에서 지원되는지 먼저 확인한다. 변수는 이미 승인된 **읽기 대상**의 접속 설정이라고 가정한다. 비밀번호를 명령 줄에 직접 적거나 터미널 기록에 남기지 않는다. Redis CLI의 인증 방법은 조직의 비밀 관리 방식에 맞춘다. 관리형 서비스에서는 CONFIG 일부가 제한될 수 있고, 그 제한을 우회하기 위해 권한을 늘리지 않는다.

```text
INFO server
INFO clients
INFO stats
INFO memory
INFO persistence
INFO commandstats
CONFIG GET latency-monitor-threshold
LATENCY LATEST
LATENCY HISTORY command
LATENCY HISTORY fork
LATENCY DOCTOR
SLOWLOG LEN
SLOWLOG GET 10
```

이 목록을 무조건 매초 반복하는 스크립트로 바꾸지 않는다. 사건 초기에는 한 번 읽고 필요한 섹션을 좁힌다. 장기 수집 주기는 운영 메트릭 체계에서 부하와 보존 목적을 검토해 정한다. `INFO`도 서버에 요청을 보내는 명령이며, 대규모 자동화에서 수집기 수와 빈도가 과도하면 관측 자체가 자원을 소비한다. 특히 전체 명령 스트림을 보는 MONITOR를 평상시 성능 측정의 기본 도구로 붙이지 않는다.

SLOWLOG에는 명령 인자 등 민감할 수 있는 정보가 포함될 수 있다. 키 이름에 사용자 식별자가 들어간다면 스크린샷이나 회고 문서에 그대로 옮기는 것도 데이터 노출이다. 필요한 범위만 수집하고 비식별화한다. 관찰 권한이 있다고 해서 원시 데이터를 외부 채널에 공유할 권한까지 생기는 것은 아니다. 진단 정확성과 정보 보호는 별개의 체크리스트가 아니라 같은 운영 작업의 일부다.

## 7. SLOWLOG, LATENCY, INFO를 서로 번역하기

SLOWLOG는 느린 명령 실행을 찾는 데 적합하다. 다만 클라이언트와의 네트워크 통신까지 모두 포함한 사용자 체감 시간을 기록하지 않는다. 따라서 애플리케이션에서 느린 GET을 보았는데 SLOWLOG에 GET이 없다는 현상은 모순이 아니다. 앞선 다른 명령 때문에 실행 차례를 기다렸거나, 네트워크가 느리거나, 애플리케이션 내부에서 기다렸을 가능성이 남는다. 범위는 [SLOWLOG GET 공식 설명](https://redis.io/docs/latest/commands/slowlog-get/)에서 확인한다.

LATENCY는 명령 외의 내부 이벤트를 조사할 때 도움이 된다. SLOWLOG에서 특정 명령을 찾지 못했지만 같은 시각에 `fork`나 AOF 관련 이벤트가 있었다면 추가 조사 방향을 정할 수 있다. 반대로 LATENCY가 비어 있어도 낮은 임계값으로 활성화되어 있었는지 먼저 확인해야 한다. 기록이 없다는 사실은 항상 설정 정보와 한 묶음으로 해석한다.

INFO는 순간 상태와 누적 카운터를 제공한다. 누적 값은 단순히 크다고 나쁜 것이 아니다. 서버가 오래 실행되면 정상적인 값도 커진다. 두 시점 차이를 관찰 시간으로 나누어 변화율을 보되, 재시작이나 카운터 초기화가 있었다면 이전 값과 그대로 빼지 않는다. 전체 CPU 평균만 보고 단일 실행 경로의 포화를 놓치지 않으며, 메모리 크기만 보고 페이지 폴트나 호스트 메모리 압박을 배제하지 않는다.

세 도구의 결과를 하나의 타임라인에 배치하면 질문이 구체화된다. “Redis가 느렸다”에서 “14:03:10 부근에 애플리케이션 p99가 상승했고, 같은 초에 fork 이벤트가 있었으며, persistence 상태에 백그라운드 저장 시작이 보인다. SLOWLOG에는 대형 명령이 없다”로 바뀐다. 이는 조사 가치가 높은 가설이다. 그래도 최종 문장은 “fork가 원인으로 확정되었다”가 아니라 “fork 경로와 지연 상승의 시간적 연관이 관찰되어 다음 확인을 수행한다”여야 한다.

## 8. 벽시계와 단조 시계를 함께 쓰는 Java 관찰 예제

Java에서 짧은 경과 시간은 `System.nanoTime()`의 차이로 잰다. 벽시계는 다른 시스템 로그와 시간대를 맞추기 위해 따로 남긴다. `nanoTime()`의 절댓값을 UTC 시각으로 바꾸려 하지 않는다. 서로 다른 JVM의 값을 직접 빼는 것도 안 된다. 경과 측정과 사건 시각은 목적이 다르기 때문에 둘 다 필요하다.

```java
import java.time.Instant;
import java.util.concurrent.Callable;

public final class ObservedCall {
    public record Observation(Instant startedAt, long elapsedNanos,
                              boolean success, String operation) {}
    public interface Sink { void record(Observation observation); }

    public static <T> T measure(String operation, Callable<T> call,
                                Sink sink) throws Exception {
        Instant startedAt = Instant.now();
        long started = System.nanoTime();
        boolean success = false;
        try {
            T value = call.call();
            success = true;
            return value;
        } finally {
            long elapsed = System.nanoTime() - started;
            // Sink는 빠르고 비차단이어야 하며 업무 예외를 가리지 않아야 한다.
            sink.record(new Observation(startedAt, elapsed, success, operation));
        }
    }
}
```

이 코드는 측정 경계 설명용이지 완성된 모니터링 SDK가 아니다. 실제 구현에서는 sink가 예외를 던져 원래 업무 예외를 덮지 않도록 처리하고, 비동기 전송 버퍼의 상한과 버림 정책도 정해야 한다. 매 요청마다 동기 파일 쓰기를 한다면 관측 코드 자체가 지연을 만든다. 원시 Redis 키나 사용자 ID를 메트릭 태그에 넣으면 서로 다른 태그 값의 수인 cardinality가 폭증할 수 있으므로 `GET_PRODUCT_CACHE`처럼 제한된 작업 이름을 사용한다.

또 하나의 함정이 있다. 비동기 Redis 클라이언트에서 `call.call()`이 Future를 즉시 반환하면 이 코드가 재는 것은 요청 완료 시간이 아니라 Future를 만든 시간이다. 그런 API에서는 completion callback에 종료 시간을 기록해야 한다. 그리고 callback이 어느 executor에서 실행되는지도 확인한다. callback 대기가 길면 네트워크 응답 이후의 지연까지 포함될 수 있다. 이는 틀린 측정이 아니라 포함 범위를 명시해야 하는 측정이다.

이 Java 코드 조각은 본 장에서 Redis 성능 실측을 위해 실행한 코드가 아니다. 저장소의 독립 실습은 GET/SET·TTL·INCR·pipeline 응답 순서·MULTI/Lua 오류 동작을 실제로 검증했지만 지연 분포, APM 계측, LATENCY 이벤트 생성은 검증 범위가 아니다. 실행 증거는 `learning/redis/lab-checks.json`의 구체적인 항목만 근거로 사용한다.

## 9. 가상 사례 A: 평균은 정상인데 p99만 상승한다

다음 수치는 설명을 위해 구성한 가상 관측이며 실제 측정 결과가 아니다. 정상 구간에서 애플리케이션 Redis 호출 p50은 1ms, p99는 4ms였고, 특정 1분에 p50은 1ms 그대로지만 p99가 60ms로 올랐다고 하자. 평균만 보면 작은 변화로 보일 수 있다. 일부 요청이 긴 대기를 겪었기 때문이다. 여기서 “모든 요청이 느려졌다”라고 말하면 조사 범위를 잘못 잡게 된다.

먼저 어떤 애플리케이션 인스턴스에서 발생했는지 나눈다. 모든 인스턴스가 같은 시각에 느렸다면 공통 서버나 공유 네트워크가 후보가 된다. 한 JVM에서만 발생했다면 GC 정지, CPU 제한, 작업 큐, 연결 관리 같은 로컬 요인이 더 우선일 수 있다. 그렇다고 하나의 인스턴스라는 이유만으로 Redis를 완전히 배제하지는 않는다. 그 인스턴스만 특정 큰 키나 다른 노드에 접근했을 수 있기 때문이다.

다음에는 사건 창을 넓혀 본다. 애플리케이션 로그의 초 단위 시각과 서버 이벤트의 초 단위 기록은 경계에서 어긋날 수 있다. 정확히 같은 초만 대조하지 않고 시계 동기 상태와 수집 지연을 고려한 앞뒤 구간을 살펴본다. 단, 창을 너무 넓혀 아무 이벤트나 갖다 붙이면 상관관계가 인과관계처럼 보인다. 창을 넓힌 이유와 최대 허용 오차를 조사 기록에 적는다.

만약 해당 구간에 `fork` 이벤트가 있고 백그라운드 저장이 시작되었다면 메모리 및 OS 상태를 추가 확인한다. 운영에서 곧바로 BGSAVE를 반복하여 재현하지 않는다. 비운영 복제 환경에서 비슷한 데이터 규모와 자원 조건을 준비하고, 실험을 승인받은 뒤 제한된 횟수로 비교한다. 재현되지 않았다고 원래 가설이 반드시 틀린 것도 아니다. 입력 데이터와 호스트 상태가 달랐을 수 있으므로 실험 차이를 기록한다.

## 10. 가상 사례 B: LATENCY가 비어 있고 연결 대기가 길다

두 번째 역시 가상 사례다. Redis 서버의 내부 이벤트는 비어 있고, 작은 PING도 빠르지만 애플리케이션 전체 호출이 200ms까지 늘어난다고 하자. 애플리케이션 계측을 나누자 연결 획득에서 대부분의 시간을 보낸다. 이때 서버 메모리를 늘리거나 LATENCY 임계값을 더 낮추는 것은 첫 번째 해결책이 아니다. 실제로 시간을 소비한 구간이 클라이언트 쪽이기 때문이다.

그렇다고 연결 수를 무작정 늘리는 것도 위험하다. 연결이 부족한 이유가 느린 후속 처리, 누수, 잘못된 풀 사용, blocking 작업 공유, 재시도 폭증 중 무엇인지 살펴야 한다. 원인을 모르고 풀 상한만 키우면 서버에 동시 요청이 더 쌓여 대기 위치가 클라이언트에서 서버로 옮겨질 수 있다. 지연이 사라진 것이 아니라 큐가 이동한 것일 수 있다.

관찰 계획은 구체적으로 쓴다. 연결 획득 대기 분포, 활성 연결 수, 대기자 수, timeout 수, 명령 종류별 호출량, 애플리케이션 스레드 상태를 같은 시간 창으로 모은다. 운영의 연결 풀 변경은 변경 전후 사용자 지연과 오류율을 함께 보고 판단한다. Redis 내부 메트릭이 안정적이었다는 사실은 이 가설을 뒷받침하지만, 다른 워크로드와 서버 상태가 같은지도 비교해야 한다.

## 11. 안전한 실습 설계: 이벤트를 억지로 만들지 않기

지연 모니터를 공부한다며 운영에 긴 Lua 루프, DEBUG SLEEP, 대형 KEYS를 실행하면 안 된다. 학습 목표는 다른 사용자 요청을 멈추는 것이 아니다. 이 저장소의 `scripts/check-redis-lab.py`는 무작위 포트와 비밀번호를 쓰는 별도 Redis 프로세스를 만들고 끝나면 자신이 생성한 프로세스만 종료한다. 기본 의미 검증은 이 실행기로 재현할 수 있다. 하지만 이 실행기는 LATENCY 이벤트를 일부러 생성하는 부하 도구가 아니다.

모니터 자체를 연습하려면 직접 관리하는 폐기 가능한 별도 인스턴스를 준비하고, 설정 파일에 낮은 관찰 임계값을 넣은 뒤 소규모 정상 명령만 실행한다. 이벤트가 안 생겨도 실습 실패가 아니다. 시스템이 해당 기준을 넘는 느린 작업을 관측하지 않았을 수 있다. 빈 결과를 확인하고 “모니터 활성화됨, 임계값 확인됨, 이 실행에서는 이벤트 없음”이라고 기록하는 것도 올바른 관측이다.

```text
# 아래는 전용 일회성 인스턴스의 설정 예시이며 운영 변경 명령이 아니다.
bind 127.0.0.1
protected-mode yes
latency-monitor-threshold 1
save ""
appendonly no

# 별도로 임의 포트, 비밀번호, 임시 dir, 메모리 상한을 지정한다.
# 실행 후 조회 예시:
LATENCY LATEST
LATENCY HISTORY command
LATENCY DOCTOR
```

실습의 종료 조건도 미리 정한다. 요청 수와 시간을 제한하고, 오류율이나 메모리 사용이 상한을 넘으면 중단한다. 프로세스 정리는 실제로 생성한 PID만 대상으로 한다. 다른 서버에 연결해 SHUTDOWN이나 FLUSHALL을 보내는 정리법을 쓰지 않는다. 남긴 로그에는 접속 비밀번호를 포함하지 않는다. 결과가 비어 있을 때 지연 이벤트가 나올 때까지 무제한 부하를 올리는 것도 금지한다.

## 12. 사고 대응 메모를 쓰는 순서

좋은 사고 기록은 처음부터 정답을 아는 사람처럼 쓰지 않는다. 관측 사실, 가설, 조치, 결과를 분리한다. “14:05 UTC에 API p99 증가”는 관측이다. “동시에 시작한 저장 작업 때문에 서버가 멈췄을 수 있음”은 가설이다. “비운영에서 같은 데이터 규모로 제한된 비교 실험”은 조치 계획이다. “재현 시 같은 이벤트가 관측되고 지연 창이 겹침”은 추가 결과다. 이 네 범주를 섞지 않으면 뒤늦게 가설이 바뀌어도 기록이 유용하다.

또한 증거를 없애는 명령을 서두르지 않는다. LATENCY RESET이나 SLOWLOG RESET은 조사 기록을 지우는 동작이다. 대시보드를 깔끔하게 만들기 위해 먼저 초기화하면 사건 당시 흔적을 잃을 수 있다. 필요한 자료를 보존하고 접근 제한을 적용한 뒤, 명확한 목적이 있을 때 승인된 환경에서 초기화한다. 서비스 복구를 위한 재시작이 불가피하다면 재시작 전후의 PID, uptime, 설정 변경 시각을 함께 남긴다.

원인 수정 후에는 “이제 빨라 보인다”로 끝내지 않는다. 동일한 업무량과 요청 구성을 가능한 한 맞추고, 성공률·p50·p95·p99·timeout·서버 이벤트를 비교한다. 재시도 수가 줄어 부하가 줄었는지, 단순히 트래픽이 적어진 것인지 구별한다. 더 빠르게 만든 변경이 내구성이나 데이터 정확성을 약화시키지 않았는지도 검토한다. 지연 개선은 다른 품질 속성과 교환한 결과일 수 있다.

## 13. 실무 진단 표

| 관측 | 우선 세울 가설 | 다음에 확인할 것 | 성급한 결론 |
|---|---|---|---|
| 한 JVM만 느림 | 로컬 큐·GC·연결 관리 | 동일 요청의 다른 JVM 비교 | Redis는 절대로 관련 없다 |
| 모든 앱이 같은 순간 느림 | 공통 서버·네트워크·공유 의존성 | 시간 동기와 서버 이벤트 | 곧바로 Redis 재시작 |
| SLOWLOG에 큰 명령 | 명령 자체의 비용 | 입력 크기·빈도·동시 워크로드 | 모든 timeout이 그 명령 탓 |
| LATENCY fork 발생 | 자식 생성 지연 | persistence와 OS 메모리 상태 | 저장 기능 영구 비활성화 |
| LATENCY 결과 없음 | 비활성·임계값·범위 차이 | 실제 설정과 관찰 기간 | 서버 지연이 없었다 |
| 연결 대기만 큼 | 클라이언트 큐 포화 | 풀 대기·누수·재시도 | 무조건 연결 상한 확대 |

이 표는 자동 판단 규칙이 아니다. 실제 사건에서는 여러 조건이 함께 나타난다. 예를 들어 서버 지연이 먼저 발생하고, 애플리케이션 재시도가 늘어나며, 그 결과 연결 풀이 포화될 수 있다. 마지막에 보이는 병목만 제거하면 최초 원인이 남는다. 시간 순서를 복원하여 선행 원인과 증폭 요인을 구분하는 것이 시니어 수준의 진단이다.

## 14. 면접과 복습: 이유까지 설명하기

<details>
<summary>Q1. 애플리케이션 Redis 호출이 50ms인데 SLOWLOG가 비어 있으면 무엇을 말할 수 있나요?</summary>

명령 실행 시간이 SLOWLOG 기준을 넘지 않았을 가능성을 말할 수 있을 뿐, 전체 Redis 경로가 빨랐다고 확정할 수 없습니다. 연결 대기, 서버에서 실행 차례 대기, 네트워크, 응답 처리 등이 애플리케이션 측정에는 포함될 수 있습니다. 실제 SLOWLOG 설정과 기록 보존 상태도 확인해야 합니다. 답변에서는 먼저 측정 시작·끝 지점을 물은 뒤, 애플리케이션 구간별 시간과 서버 이벤트를 같은 사건 창에 놓겠다고 설명하는 것이 좋습니다.
</details>

<details>
<summary>Q2. LATENCY의 표본으로 사용자 요청 p99를 계산해도 되나요?</summary>

안 됩니다. 임계값을 넘은 특정 내부 이벤트만 기록하고, 같은 초의 여러 이벤트가 최댓값으로 합쳐질 수 있으므로 전체 요청 모집단과 발생 횟수가 보존되지 않습니다. p99에는 어떤 요청 집합을 대상으로 했는지가 중요합니다. 사용자 요청 또는 클라이언트 호출의 히스토그램을 별도로 수집하고, LATENCY는 꼬리 지연이 나타난 시점의 서버 내부 단서를 찾는 보조 자료로 사용합니다.
</details>

<details>
<summary>Q3. 임계값은 서비스 SLO와 똑같이 두면 되나요?</summary>

항상 그렇지는 않습니다. 서비스 SLO는 여러 의존성과 애플리케이션 처리의 합에 적용될 수 있습니다. Redis 내부 지연 하나가 전체 예산에 도달하기 전에도 서비스는 위험해질 수 있습니다. 정상 분포와 계층별 예산을 보고, 조사에 의미 있는 내부 지연을 포착하도록 관찰 기준을 정합니다. 관찰 임계값과 사용자에게 경보를 울리는 조건도 서로 다른 목적이므로 별도로 설계합니다.
</details>

<details>
<summary>Q4. fork 이벤트와 API 지연이 동시에 나타났다면 원인을 확정할 수 있나요?</summary>

시간적 연관은 강한 단서지만 충분한 인과 증명은 아닙니다. 같은 시간의 백업, 호스트 경쟁, 메모리 압박 등 공통 원인이 두 현상을 만들 수도 있습니다. 시계 오차를 확인하고 persistence 상태와 OS 지표를 대조한 뒤, 안전한 별도 환경에서 데이터 규모와 조건을 맞춘 비교를 고려합니다. 보고서에는 확정 사실과 가설을 구분하여 기록해야 합니다.
</details>

<details>
<summary>Q5. latency-monitor-threshold가 0이면 아주 작은 지연까지 기록하나요?</summary>

입력 원문에서 0은 모니터 비활성 상태를 뜻합니다. 단순히 숫자가 작으니 더 민감하다고 해석하면 안 됩니다. 실제 서버의 설정값과 해당 버전 문서를 확인한 뒤 의미를 판단해야 합니다. 빈 결과를 만났을 때는 관찰이 활성화되어 있었는지부터 검증하고, 관찰하지 않은 구간을 정상 구간이라고 보고하지 않습니다.
</details>

<details>
<summary>Q6. Java에서 currentTimeMillis의 차이만 재면 충분한가요?</summary>

경과 시간 측정에는 단조 시간 기준인 nanoTime 차이가 더 적합합니다. 벽시계는 동기화나 보정의 영향을 받을 수 있고, 서로 다른 시스템의 로그를 맞추는 용도로 따로 보존합니다. 비동기 API라면 메서드가 Future를 반환한 시점이 아니라 작업 완료 지점을 측정해야 합니다. 측정 코드 자체의 로그·메트릭 전송 비용도 별도로 고려합니다.
</details>

<details>
<summary>Q7. 장애가 끝나면 LATENCY RESET을 먼저 실행해도 되나요?</summary>

증거 보존 전에 초기화하면 안 됩니다. 제한된 메모리 기록은 이미 손실되기 쉬우므로 필요한 이벤트, 설정, 서버 uptime, 시각 정보를 먼저 안전하게 보존합니다. 초기화는 별도 비교 실험처럼 목적이 명확하고 권한이 있는 경우에만 수행합니다. 키나 명령 인자에 민감 정보가 포함될 수 있으므로 자료 공유 범위도 함께 관리합니다.
</details>

<details>
<summary>Q8. 운영에서 DEBUG SLEEP으로 모니터를 확인하는 것은 좋은 실습인가요?</summary>

아닙니다. 의도적으로 서버 처리 경로를 막아 다른 요청에 영향을 줄 수 있고, 실제 고객 장애를 만들 수 있습니다. 폐기 가능한 독립 인스턴스에서 설정과 조회를 익히며, 이벤트가 없으면 그대로 기록하면 됩니다. 실습이 유효하려면 반드시 느린 사건을 만들어야 한다는 생각을 버려야 합니다. 부하 재현은 별도의 승인·상한·중단 조건을 가진 실험으로 다룹니다.
</details>

<details>
<summary>Q9. 해결 후 p99가 낮아졌다면 변경이 성공한 것 아닌가요?</summary>

요청량, 요청 구성, 실패율, timeout 처리 방식이 같았는지 확인해야 합니다. 느린 요청을 일찍 실패시켜 성공 요청 p99만 낮아진 것일 수 있고, 트래픽이 줄어든 결과일 수도 있습니다. 지연과 성공률을 함께 보고 내구성·정확성·자원 비용이 악화되지 않았는지 검토해야 합니다. 변경 효과는 조건과 관측 기간을 포함하여 설명합니다.
</details>

## 15. 직접 답해 보는 과제

첫 번째 과제는 사용 중인 애플리케이션 Redis 호출의 측정 경계를 그림으로 그리는 것이다. 연결 대기가 포함되는지, 비동기 완료가 포함되는지, 역직렬화가 포함되는지를 각각 표시한다. 실제 구현을 확인하지 못했다면 추정이라고 적는다. 두 번째 과제는 LATENCY가 비어 있는 경우 가능한 설명을 세 가지 이상 쓰는 것이다. 활성화 여부, 임계값, 관찰 범위와 보존 기간을 반드시 포함한다.

세 번째 과제는 가상 장애 메모를 작성하는 것이다. “10:00에 p99 증가, 한 JVM만 영향, 연결 대기 증가, 서버 이벤트 없음”이라는 가상의 조건에서 조사 순서를 다섯 단계로 적어 본다. 운영 변경을 첫 단계로 넣지 말고 읽기와 가설 분리부터 시작한다. 마지막에는 어떤 추가 증거가 생기면 현재 가설을 버릴지 써 본다. 자신의 가설을 반증할 조건을 말할 수 있어야 진단이 아니라 추측만 하고 있는 상태를 벗어날 수 있다.

## 공식 출처와 검증 범위

주요 원문은 제공된 22장과 [Redis latency monitoring](https://redis.io/docs/latest/operate/oss_and_stack/management/optimization/latency-monitor/)이며 2026-10-21에 공식 페이지 접근을 확인했다. 보조 참조는 [LATENCY LATEST](https://redis.io/docs/latest/commands/latency-latest/), [LATENCY HISTORY](https://redis.io/docs/latest/commands/latency-history/), [SLOWLOG](https://redis.io/docs/latest/commands/slowlog/), [INFO](https://redis.io/docs/latest/commands/info/)다. 최신 문서의 기능을 모든 구버전에 그대로 적용하지 않는다.

이 장의 숫자와 장애 시나리오는 이해를 위한 구성 예시다. 실제 LATENCY 부하 실험, AOF 지연 재현, 운영 환경 분석을 수행했다고 주장하지 않는다. 저장소의 Java 21·Redis 7.2.5 실습 결과는 기본 명령 의미와 오류 처리에 한정되며 성능 인증이 아니다. 다음 장에서는 이 구분을 유지한 채 처리량과 벤치마크 결과를 읽는 방법을 배운다.
