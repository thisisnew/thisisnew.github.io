## 1. 메모리에 있다는 것과 사라져도 된다는 것은 다르다

Redis는 요청을 빠르게 처리하기 위해 데이터를 메모리에 둔다. 하지만 모든 Redis 데이터가 지워져도 되는 임시 정보는 아니다. 어떤 서비스는 MySQL에서 다시 읽을 수 있는 상품 정보를 저장하고, 어떤 서비스는 로그인 세션이나 아직 처리하지 않은 작업 상태를 저장한다. 같은 `SET` 명령이라도 데이터가 사라졌을 때의 사업 영향은 다르다.

**영속성, persistence**는 프로세스가 사라진 후에도 상태를 복원할 수 있도록 내구성 있는 저장 장치에 기록하는 성질이다. **복제, replication**는 다른 Redis 인스턴스에 상태를 전달하는 것이고, **백업**은 실수나 장애로부터 돌아갈 별도 복구 지점을 보관하는 것이다. 셋은 서로 보완하지만 대체 관계가 아니다. 잘못된 쓰기는 복제본에도 전달되고, 같은 디스크가 망가지면 로컬 영속성 파일도 함께 사라질 수 있다.

이 장은 제공된 04장의 RDB 설명을 중심으로 원리를 풀어 쓴다. 공식 문서의 RDB/AOF 비교를 참고하되 “절대로 유실되지 않는다”, “부모는 아무 비용도 없다”처럼 읽히는 단순화는 장애 유형과 구현 경계로 다시 나눈다. 설치한 버전과 저장 장치 조건에 따라 세부 동작을 확인해야 한다. [Redis persistence](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/)

## 기초 보충. 성공 응답과 복구 가능한 기록을 분리해서 보기

사용자가 입고 확정 버튼을 눌렀고 화면에 성공이 표시되었다. 이때 무엇이 성공했는지 구체적으로 물어야 한다. HTTP 요청을 처리한 것인지, Redis 메모리의 값을 바꾼 것인지, MySQL 트랜잭션을 커밋한 것인지, 디스크에 복구 가능한 기록을 남긴 것인지가 다를 수 있다. 화면의 한 단어로 여러 시스템의 보장을 모두 표현할 수는 없다.

Redis의 SET 성공은 해당 명령의 의미에 따른 저장이 수행되었다는 응답이다. 하지만 어떤 영속성 정책과 복제 구성이 있는지 모른 채 “그러므로 전원이 끊겨도 반드시 남는다”라고 이어 말할 수는 없다. 내구성은 실패 종류에 대한 계약이다. 프로세스만 종료되는 경우, OS가 재시작되는 경우, 디스크가 사라지는 경우, 호스트가 모두 소실되는 경우의 복구 경로가 다르다.

노트 필기를 비유로 생각해 보자. 머릿속으로 계산을 끝낸 것은 메모리의 변경에 가깝다. 종이에 적은 것은 별도 기록을 남긴 것에 가깝다. 그 종이를 다른 건물에도 복사해 둔 것은 다른 장애 범위에 대비하는 행동이다. 계산을 끝냈다는 사실만으로 종이가 생기지는 않고, 종이가 있다는 사실만으로 건물 전체가 사라졌을 때도 복구되는 것은 아니다. Redis의 세부 구현은 이 비유보다 복잡하지만 보장의 층을 나누는 데 도움이 된다.

RDB를 사용할 때는 현재 메모리와 마지막 성공 스냅샷이 서로 다른 상태일 수 있음을 기본 전제로 둔다. 이것이 오류가 아니라 기능의 성질이다. 100이라는 값이 저장된 스냅샷을 만든 뒤 현재 메모리를 90으로 바꿨다면, 스냅샷 파일은 여전히 과거의 100을 표현할 수 있다. 어떤 파일에서 복원하는지 명시하지 않고 “복구하면 무슨 값이 나옵니까?”라고 물으면 답이 모호해진다.

따라서 설계 문서에는 성공 응답 뒤에 남을 수 있는 손실 범위를 적는다. 데이터가 원본 DB에서 다시 만들어지는 캐시라면 손실 자체보다 재생성 부하가 중요할 수 있다. Redis가 유일한 상태를 가진다면 손실이 업무 결과를 뒤집을 수 있다. 똑같은 RDB 설정이 한 서비스에는 충분하고 다른 서비스에는 부족한 이유는 기술의 차이가 아니라 데이터 역할과 요구의 차이다.


## 2. 무엇을 잃어도 되는지 먼저 정하기

RPO는 Recovery Point Objective, 복구 시 허용하는 데이터 손실 시간 범위다. 예를 들어 “최대 5분 전 상태로 돌아가도 된다”는 요구다. RTO는 Recovery Time Objective, 복구해서 서비스를 다시 제공하기까지 허용하는 시간이다. “파일이 있다”는 것은 두 목표 중 어느 것도 자동으로 만족하지 않는다.

상품 상세 캐시를 잃으면 원본 DB에서 다시 만들 수 있다. 하지만 빈 캐시 상태에서 모든 요청이 DB로 몰리면 DB가 버티지 못할 수 있다. 따라서 캐시의 RPO가 사실상 느슨해도 RTO와 재가열 부하는 중요하다. 반대로 재고 감소를 Redis만에 기록한다면 최근 몇 분의 손실이 초과 판매로 이어질 수 있어 더 엄격한 요구가 필요하다.

질문을 다음 순서로 만든다.

1. Redis 외부에 권위 있는 원본이 있는가?
2. 이 데이터가 없어지면 단순히 느려지는가, 업무 상태가 틀어지는가?
3. 어느 시점까지 되돌아갈 수 있는가?
4. 복원 후 빠진 작업을 다른 로그나 DB로 재구성할 수 있는가?
5. 복구 중 읽기와 쓰기를 어디로 보낼 것인가?
6. 누가 복구 완료를 승인할 것인가?

영속성은 서버 옵션 고르기 전에 이 질문의 답으로 시작한다. `appendonly yes`를 켰다는 이유만으로 주문 처리 설계가 완성되지는 않는다.

## 3. RDB의 핵심은 특정 시점의 상태

RDB는 Redis 데이터셋의 특정 시점 상태를 파일로 표현하는 방식이다. 사진에 비유하면 이해하기 쉽다. 12시 사진에는 12시 당시의 책상이 담긴다. 12시 1분에 새로 올려놓은 책은 그 사진에 없다. 파일 쓰기가 12시 2분에 끝났다고 사진이 12시 2분의 모든 변화를 포함하는 것도 아니다.

이 비유에서 주의할 부분은 실제 Redis 스냅샷이 카메라처럼 순간적으로 디스크에 완성되지 않는다는 것이다. fork와 COW를 이용해 기준 시점의 메모리 모습을 유지하면서 자식이 파일을 만든다. 부모는 그 이후에도 요청을 처리한다. 파일 생성 완료 시각과 포함된 데이터의 경계 시각을 구분해야 한다.

간단한 시간표를 보자.

```text
12:00:00  balance=100, 스냅샷 기준 상태 형성
12:00:05  클라이언트가 balance=90으로 변경, 성공 응답
12:00:20  스냅샷 파일 생성 완료
12:00:30  서버와 메모리 상실
복구 결과: 이 스냅샷만 사용한다면 balance=100
```

위 표는 이해를 위한 논리 예시이며 실제 실행 측정이 아니다. “BGSAVE가 12시 20초에 성공했으니 12시 5초의 쓰기도 들어 있겠지”라는 추측이 왜 틀릴 수 있는지 보여 준다.

## 4. SAVE와 BGSAVE의 차이

`SAVE`는 동기적으로 RDB를 저장하는 명령이다. 큰 데이터셋에서 클라이언트 처리에 긴 영향을 줄 수 있으므로 일상적인 운영 백업 명령처럼 무심코 사용하지 않는다. `BGSAVE`는 백그라운드 저장을 요청한다. 일반적인 경로에서 부모가 자식을 만들고, 자식이 스냅샷 파일을 작성한다.

BGSAVE의 즉시 응답은 “작업을 시작했거나 요청을 처리했다”는 의미이지 파일 생성 완료 증명은 아니다. 실행 중인 다른 백그라운드 작업과 상태에 따라 오류나 예약 경로가 있을 수 있으므로 응답을 읽고 `INFO persistence`와 로그를 확인한다. 단순히 명령 한 줄이 오류 없이 반환됐다는 이유로 그 다음 줄에서 새 백업을 업로드하면 이전 파일을 복사할 수 있다.

관찰할 필드는 다음과 같다. 지원 여부와 세부 정의는 실행 버전의 문서를 따른다.

| 지표 | 읽는 질문 |
|---|---|
| `rdb_bgsave_in_progress` | 지금 저장 중인가? |
| `rdb_last_bgsave_status` | 마지막 백그라운드 저장이 성공했나? |
| `rdb_last_save_time` | 마지막 저장 완료 시각이 언제인가? |
| `rdb_changes_since_last_save` | 마지막 저장 이후 변경이 얼마나 누적되었나? |
| `rdb_last_bgsave_time_sec` | 마지막 저장에 얼마나 걸렸나? |
| COW 관련 필드 | 저장 중 메모리 추가 비용은 어땠나? |

`LASTSAVE`도 마지막 성공 저장의 시각을 확인하는 데 쓸 수 있다. 초 단위 시간 비교만으로 너무 빠른 연속 작업을 식별하기 어려울 수 있으므로 작업 로그와 파일 상태를 함께 사용한다. [BGSAVE](https://redis.io/docs/latest/commands/bgsave/), [SAVE](https://redis.io/docs/latest/commands/save/), [INFO](https://redis.io/docs/latest/commands/info/)

## 5. 내부 흐름: fork에서 최종 파일 교체까지

일반적인 RDB 저장 흐름을 단계로 나누면 다음과 같다.

1. 부모가 저장 조건과 현재 백그라운드 작업 상태를 확인한다.
2. fork로 자식 프로세스를 만든다. 이 순간의 관리 비용은 부모 요청 지연에 영향을 줄 수 있다.
3. 자식은 기준 상태의 데이터를 읽어 임시 RDB 파일을 쓴다.
4. 부모는 계속 쓰기를 처리한다. 공유 페이지가 수정되면 COW 비용이 발생할 수 있다.
5. 파일 생성이 성공하면 최종 파일 이름으로 교체하는 절차를 거친다.
6. 부모는 자식 종료 상태를 수집하고 저장 성공/실패 지표를 갱신한다.

완성된 RDB는 저장 중에 계속 덧붙이는 로그와 다르다. 다음 저장은 임시 파일을 만든 뒤 최종 이름을 원자적으로 교체하는 방식을 사용한다. 덕분에 실행 중인 서버의 **완성된** RDB를 복사하는 백업 패턴이 가능하다. 다만 파일 이름이 존재한다고 방금 요청한 저장의 결과라고 단정하면 안 된다. 이전 성공본일 수 있기 때문이다.

“원자적”은 관찰자에게 교체 전후의 경계가 명확하다는 뜻으로 이해하자. 이것이 전원 손실, 저장 장치 고장, 파일 시스템 손상, 다른 지역의 재해까지 모두 해결한다는 뜻은 아니다. 파일의 전송과 보관, 복원 가능성은 다음 단계의 검증 대상이다.

## 6. 저장 조건은 고정 간격 타이머와 다르다

설정 파일의 `save` 지시문은 시간과 변경 횟수 조건으로 저장을 요청하는 규칙을 표현한다. 예를 들어 다음은 개념 설명용이다.

```conf
save 300 100
```

이를 단순히 “정확히 5분마다 무조건 저장”이라고 읽으면 틀리다. 시간 경과와 최소 변경 조건이 함께 관련된다. 여러 save 규칙을 둘 수도 있다. 실제 실행에는 백그라운드 작업 상태와 자원 상황도 영향을 준다. 따라서 요구 RPO를 “save에 적은 초”와 동일시하면 안 된다.

예를 들어 5분 간격의 저장 목표라도 작업이 2분 걸리고 이전 작업이 실패했다면 최신 성공 스냅샷은 훨씬 오래되었을 수 있다. RPO 경보는 설정 문자열이 아니라 **마지막 검증된 복구 지점의 나이**를 기준으로 설계해야 한다. 파일이 새로 생성되었는지, 원격 백업까지 전달되었는지도 요구 수준에 따라 구분한다.

저장 빈도를 높이면 손실 창을 줄일 수 있지만 fork 빈도, 디스크 쓰기, COW, 작업 간 충돌 비용이 커질 수 있다. RDB만으로 아주 짧은 손실 창을 달성하려다 서버 지연과 가용성을 망칠 수 있다. 이때는 AOF와의 조합, 복제, 외부 원본 로그 등 전체 구조를 검토한다.

## 7. RDB, AOF, 복제, 백업의 역할 비교

| 장치 | 주로 해결하는 문제 | 해결하지 못하는 대표 문제 |
|---|---|---|
| RDB | 특정 시점 상태 복원, 이동 가능한 스냅샷 | 스냅샷 이후의 최근 쓰기 손실 |
| AOF | 변경 기록 기반 재구성, 정책에 따른 더 짧은 손실 창 | 모든 장애에서 절대 무손실, 영구 감사 이력 |
| 복제 | 다른 인스턴스로 상태 전달, 읽기 확장·장애 대응 기반 | 오삭제에서 과거로 복구 |
| 외부 백업 | 로컬 손실·잘못된 변경에서 독립 복구 | 즉시 자동 장애 전환 |

RDB와 AOF를 모두 활성화하면 일반적인 재시작 복원에서 AOF를 우선 사용하는 경로를 이해해야 한다. RDB를 새로 복사해 놓고 기존 AOF를 그대로 둔 채 시작하면 기대와 다른 데이터가 로드될 수 있다. 실제 복구 절차에서는 어떤 파일을 선택하게 할지 명시하고 새 격리 디렉터리에서 검증한다. 설정과 로드 경로가 복구 결과의 일부다.

RDB는 비교적 조밀한 상태 표현이라 이송과 백업에 유용하다. AOF는 연속 변경과 재작성이라는 다른 비용을 가진다. “RDB는 느슨하고 AOF는 완벽하다”처럼 이분법으로 외우지 말고, 실패 종류·복구 시간·파일 크기·운영 복잡도를 함께 비교한다.

## 8. 격리 실습: 사진 이후의 변경은 복원되지 않는다

이 실습은 실제 장애를 일으키지 않고 RDB의 시점 경계를 관찰한다. 원본 실습 서버와 복원 서버를 서로 다른 포트와 디렉터리로 만든다. 운영 데이터 파일을 가져오지 않는다. `redis-server`, `redis-cli`가 설치되어 있고 16382와 16383이 비어 있어야 한다.

첫 터미널에서 원본을 실행한다.

```bash
SRC=$(mktemp -d /tmp/redis-rdb-source.XXXXXX)
echo "$SRC"
redis-server --bind 127.0.0.1 --port 16382 --protected-mode yes \
  --daemonize no --dir "$SRC" --dbfilename dump.rdb \
  --save "" --appendonly no --maxmemory 64mb
```

다른 터미널에서 데이터를 만들고 저장을 요청한다.

```bash
redis-cli -h 127.0.0.1 -p 16382 SET lab:balance 100
redis-cli -h 127.0.0.1 -p 16382 SET lab:snapshot-marker before
redis-cli -h 127.0.0.1 -p 16382 BGSAVE
redis-cli -h 127.0.0.1 -p 16382 INFO persistence
```

저장 진행 상태가 0이고 마지막 저장 상태가 `ok`인지, 로그와 `dump.rdb`가 완료된 작업을 나타내는지 확인한다. 상태가 아직 진행 중이면 잠시 후 다시 확인한다. 이 장은 무조건 1초면 끝난다는 가정을 하지 않는다. 파일이 존재하지 않거나 실패했다면 권한, 경로, 디스크 여유와 로그를 조사하고 이후 단계로 넘어가지 않는다.

완료를 확인한 후 값을 바꾼다.

```bash
redis-cli -h 127.0.0.1 -p 16382 SET lab:balance 90
redis-cli -h 127.0.0.1 -p 16382 SET lab:after-snapshot yes
redis-cli -h 127.0.0.1 -p 16382 GET lab:balance
```

이제 **완성된 파일**을 새 경로로 복사한다. `SRC`는 첫 터미널에 출력한 실제 경로로 설정한다. 복원 경로를 원본 경로와 같게 지정하면 안 된다.

```bash
# SRC=/tmp/redis-rdb-source.실제로출력된접미사
RESTORE=$(mktemp -d /tmp/redis-rdb-restore.XXXXXX)
cp "$SRC/dump.rdb" "$RESTORE/dump.rdb"
redis-check-rdb "$RESTORE/dump.rdb"
redis-server --bind 127.0.0.1 --port 16383 --protected-mode yes \
  --daemonize no --dir "$RESTORE" --dbfilename dump.rdb \
  --save "" --appendonly no --maxmemory 64mb
```

복원 서버가 시작되면 별도 터미널에서 확인한다.

```bash
redis-cli -h 127.0.0.1 -p 16383 GET lab:balance
redis-cli -h 127.0.0.1 -p 16383 GET lab:snapshot-marker
redis-cli -h 127.0.0.1 -p 16383 GET lab:after-snapshot
```

예상 결과는 잔액 100, marker `before`, 스냅샷 이후 키의 부재다. 원본 서버의 잔액은 90이므로 **원본의 현재 상태와 복구 지점의 상태가 다르다**는 사실을 직접 비교할 수 있다. 이는 RDB 버그가 아니라 의도한 시점 복원이다. 실습을 반복하면서 덮어쓰거나 다른 저장이 수행되었다면 결과가 달라질 수 있으므로 단계와 파일 생성 시각을 기록한다.

종료할 때는 두 실습 포트에만 `SHUTDOWN NOSAVE`를 보낸다. 업무 프로세스를 강제 종료하거나 파일을 삭제하는 명령은 필요하지 않다. 위 결과는 예상 관찰이며 이 문서의 작성 환경에서 실행해 얻은 측정값이라고 주장하지 않는다.

## 9. 복원 검증에서 키 개수만 세면 놓치는 것

원본과 복원본이 모두 1,000개 키라고 하자. 키 수가 같아도 값이 다를 수 있고, 자료형이 바뀌었을 수 있으며, TTL이 잘못되었을 수 있다. 따라서 `DBSIZE`는 출발점일 뿐 데이터 정합성의 완전한 증명이 아니다.

검증 대상을 업무 의미로 나눈다. 카운터라면 음수가 되면 안 되는지, Hash라면 필수 필드가 있는지, 목록이라면 처리 순서가 의미에 맞는지, 캐시라면 원본에서 재생성 가능한지 확인한다. 예시용 marker 키에 백업 배치 ID를 저장하는 방식도 복구 지점을 식별하는 데 도움이 된다. 단, marker를 저장한 시점과 실제 스냅샷에 포함되는 시점이 맞는지 설계해야 한다.

TTL은 특히 주의한다. 만료 정보는 단순히 “복원하면 저장 당시 남은 시간이 다시 시작”하는 식으로 생각하면 안 된다. 시간은 백업 동안에도 흐른다. 복원 시점에 이미 만료된 데이터가 보이지 않는 것은 자연스러울 수 있다. 짧은 TTL 데이터만으로 키 수를 비교하면 정상 복원을 손상으로 오진할 수 있다. 시스템 시계와 시간 동기화도 데이터 의미에 영향을 준다. [EXPIRE](https://redis.io/docs/latest/commands/expire/)

## 10. 장애 사례: 디스크가 가득 차서 쓰기가 막혔다

RDB 저장에 실패하고 `stop-writes-on-bgsave-error` 관련 정책에 따라 쓰기가 거절되는 상황을 생각해 보자. 애플리케이션은 “Redis 쓰기 오류”만 보지만 근본 원인은 디스크 공간, 권한, 읽기 전용 파일 시스템, fork 실패 등일 수 있다. 우선 `INFO persistence`와 로그에서 실패 종류를 확인한다.

잘못된 대응은 오류를 없애려고 즉시 안전장치를 끄는 것이다. 그러면 현재 서비스는 다시 쓰기를 받지만, 성공 응답을 받은 데이터가 저장되지 않는 상태가 길어질 수 있다. 업무의 손실 허용 범위와 별도 복구 경로를 검토하지 않은 채 이를 수행하면 가용성을 회복하면서 내구성을 포기한 셈이다.

안전한 절차는 최근 검증 백업의 위치와 나이 확인, 디스크/권한/메모리 원인 확인, 쓰기 차단의 업무 영향 평가, 용량 확보나 경로 수정, 새 저장 성공 확인, 원격 백업과 복원 검증 순서로 구성한다. 여유 공간 확보를 위해 어떤 파일이든 지우는 행동은 특히 위험하다. AOF 세트나 유일한 정상 RDB를 삭제하면 복구 가능성 자체를 잃는다.

## 11. Java 서비스와 복구된 과거 상태의 충돌

가령 주문 서비스가 MySQL에 주문 500번을 확정하고 Redis에 `order:500:status=confirmed`를 기록했다고 하자. Redis를 그 이전 RDB로 복원하면 키가 없거나 과거 상태일 수 있다. 이것이 단순 캐시라면 MySQL을 조회해 재생성하면 된다. Redis를 권위 있는 상태로 취급해 주문을 취소하면 논리가 뒤집힌다.

```java
// 캐시가 권위 있는 원본이 아닌 경우의 의사 코드
String cached = cache.get(orderId);
if (cached != null) {
    return decode(cached);
}
Order order = orderRepository.findRequired(orderId);
cache.putWithTtl(orderId, encode(order));
return order;
```

이 코드는 읽기 흐름을 설명하는 의사 코드이며 분산 트랜잭션을 해결하지 않는다. DB 변경과 캐시 무효화 사이의 경쟁, 복원 후 오래된 값이 남는 경우, 캐시 재가열 폭주를 별도로 다뤄야 한다. 중요한 것은 데이터의 권위를 명확히 하고, Redis 복구가 외부 DB의 시간을 되돌리지는 않는다는 사실이다.

복구 직후에는 오래된 중복 방지 키가 없을 수 있다. 타임아웃 후 재시도된 요청이 다시 실행될 수 있으므로 업무상 중복 실행을 막아야 하는 상태를 어디에 영속적으로 둘지 설계한다. 스냅샷의 기능과 결제·주문 시스템의 보장은 같은 층위가 아니다.

## 12. 영속성 선택을 문장으로 적는 연습

좋은 설계 문서는 “RDB 사용”으로 끝나지 않는다. 예를 들어 “상품 캐시는 원본 DB에서 복구 가능하며 RDB는 초기 재가열 시간을 줄이는 보조 수단이다. 스냅샷이 오래되면 해당 캐시를 신뢰하지 않고 제한된 속도로 재생성한다. 원본 DB 보호를 위해 동시 재가열 수를 제한한다”처럼 실패 후 행동을 설명한다.

반대로 “업무 큐 상태가 유일한 원본이며 최근 1분의 손실도 허용되지 않는다”면 RDB 단독 전략은 요구를 만족시키기 어렵다. AOF 정책, 복제, 디스크와 노드 장애 모델, 애플리케이션 재처리와 멱등성까지 확장해야 한다. 이름이 같은 Redis여도 데이터 역할에 따라 선택이 달라져야 한다.

백업 주기와 저장 주기도 다르다. RDB가 매시간 만들어져도 원격 복사가 하루 한 번이면 데이터센터 상실 시 사용할 원격 지점은 하루 전일 수 있다. RPO는 장애 범위별로 정의해야 한다. 프로세스 재시작 RPO와 리전 전체 상실 RPO를 같은 수치로 말하려면 각각의 경로가 그 수치를 만족한다는 근거가 필요하다.

## 요구사항 보충. RPO와 RTO를 입고 업무로 번역하기

RPO를 처음 들으면 복구 시스템의 전문용어처럼 느껴진다. 쉽게는 “얼마나 최근까지의 일을 잃어도 되는가?”라는 질문이다. RTO는 “얼마나 오래 서비스를 못 써도 되는가?”라는 질문이다. 둘은 독립적이다. 오래된 백업을 아주 빨리 띄우면 복구 시간은 짧아도 데이터 손실이 클 수 있다. 최신 데이터를 모두 복원하더라도 몇 시간이 걸리면 업무가 오래 멈출 수 있다.

입고 현장에서 상품명 조회 캐시를 잃는 상황을 생각해 보자. 이름은 DB에 있으므로 Redis 데이터 손실이 직접 수량 오류를 만들지는 않을 수 있다. 그러나 모든 PDA가 동시에 DB를 조회하면서 화면이 느려지면 업무가 멈춘다. 이 경우 영속성 파일을 활용한 재가열, 요청 제한, 필요한 상품부터 채우는 순서가 RTO에 영향을 준다. “캐시니까 손실 허용”이라는 한 문장으로 끝낼 수 없는 이유다.

반대로 입고 확정 수량을 Redis에만 저장하는 가정을 해 보자. 5분 전으로 돌아가면 그 5분 동안 확정된 수량을 잃을 수 있다. 작업자는 이미 물건을 다음 구역으로 옮겼는데 시스템은 처리하지 않은 것으로 보게 된다. 이런 업무에서는 누락을 찾아 다시 구성할 수 있는 독립적인 이력과 중복 처리 방지가 필요하다. RDB 주기를 줄이는 것만으로 전체 업무 복구가 해결되지는 않는다.

복구 목표는 장애 종류별로 적는 편이 좋다. 프로세스 장애라면 로컬 파일이 남아 있을 수 있다. 호스트 장애라면 다른 노드나 원격 백업이 필요할 수 있다. 리전 장애라면 같은 리전의 복제본과 파일이 모두 영향을 받을 수 있다. **어느 장애에서 어느 사본을 사용할지**를 먼저 정한 뒤 그 사본의 최신성과 복원 시간을 측정한다.

| 질문 | 단순 답변 | 더 구체적인 답변의 형태 |
|---|---|---|
| 어느 데이터를 잃을 수 있나? | 캐시니까 괜찮다 | 상품 설명은 DB 재생성 가능, 대기 순번은 별도 계약 필요 |
| 어디까지 돌아갈 수 있나? | 5분 백업이다 | 해당 장애에서 접근 가능한 검증 사본의 기준 시점 확인 |
| 언제 서비스가 돌아오나? | Redis를 띄우면 된다 | 다운로드·로드·검증·전환·재가열까지 포함 |
| 누락을 어떻게 찾나? | 키 개수를 센다 | 업무 이력과 요청 ID, 상태 불변식을 대조 |

RPO와 RTO의 숫자는 운영팀만의 관심사가 아니다. API의 재시도 방식, 사용자에게 보여 줄 상태, 작업자의 재처리 절차가 그 숫자와 연결된다. 복구 후에도 사람이 이미 수행한 물리 작업은 되돌아가지 않는다. 물류처럼 시스템 상태와 현장 상태가 함께 움직이는 도메인에서는 이 차이를 특히 중요하게 다루어야 한다.


## 시간선 보충. 스냅샷의 시작·완료·복사·검증은 네 사건이다

RDB를 사진에 비유할 때 가장 흔한 오해는 사진 인화가 끝난 시각을 촬영 시각으로 생각하는 것이다. 스냅샷 기준 상태가 만들어지는 시점과 파일 작성 완료는 구별해야 한다. 또 파일이 완성된 것과 원격 위치로 전달된 것도 다른 사건이다. 마지막으로 그 사본을 실제로 읽어 복원할 수 있다고 확인한 시점도 다르다.

아래 시간은 설명용 가정이다. 12시 정각에 스냅샷의 기준 상태가 형성되고, 파일 작성에 40초가 걸렸다고 하자. 원격 복사는 12시 1분에 끝났고 격리 복원 검사는 12시 3분에 끝났다. 12시 4분에 원본 호스트가 사라졌다면 원격에서 사용할 수 있는 이 파일은 12시 3분의 업무 상태가 아니라 기준 시점의 상태를 표현한다.

| 사건 | 가상 시각 | 무엇을 확인하는가 | 이 시각으로 알 수 없는 것 |
|---|---|---|---|
| 기준 상태 형성 | 12:00:00 | 어떤 데이터 시점을 담는가 | 파일이 이미 완성됐는가 |
| 저장 완료 | 12:00:40 | 새 파일이 성공적으로 만들어졌는가 | 원격 보관이 끝났는가 |
| 원격 복사 완료 | 12:01:00 | 다른 위치에서 파일에 접근 가능한가 | 실제로 로드 가능한가 |
| 복원 검사 완료 | 12:03:00 | 정한 검사가 통과했는가 | 12:03의 최신 쓰기가 포함됐는가 |
| 원본 호스트 상실 | 12:04:00 | 사용할 복구 경로는 무엇인가 | 최근 4분의 일이 자동으로 복원되는가 |

저장 완료 시각과 기준 시점이 다르므로 “마지막 저장이 10초 전이니까 최대 10초만 잃는다”는 계산은 조건을 빠뜨릴 수 있다. 작업이 오래 걸렸다면 기준 상태는 더 오래전일 수 있다. 원격 백업을 기준으로 하는 장애에서는 원격 전송과 보존 상태까지 봐야 한다. 같은 파일을 다루어도 어떤 시계를 보고 있는지 명확해야 한다.

그렇다고 모든 운영 시스템에서 스냅샷의 정확한 내부 기준 시각을 하나의 지표로 쉽게 얻을 수 있다는 뜻은 아니다. 작업 시작·종료 로그, 애플리케이션 marker, 백업 메타데이터를 함께 설계해야 할 수 있다. 근사치로 판단한다면 그 오차를 여유에 포함한다. 관측할 수 없는 것을 정확히 안다고 가정하기보다 불확실성을 문서에 남기는 편이 안전하다.

백업 파일 이름에 시각을 넣는 것만으로도 충분하지 않다. 이름을 붙인 시각과 데이터 기준 시각이 다를 수 있기 때문이다. 파일 이름은 식별자이고 파일 안의 데이터 경계와 메타데이터는 별도 증거다. 날짜가 최신이라는 이유로 복구 대상 파일을 고르는 실수를 피해야 한다.


## 내부 원리 보충. 자식이 파일을 쓰는 동안 부모는 무엇을 하는가

부모 Redis는 클라이언트 명령을 처리하는 프로세스다. 백그라운드 저장 경로에서는 자식 프로세스가 기준 상태를 읽어 파일을 만든다. 이 분리는 파일 전체를 쓰는 동안 부모가 모든 요청을 완전히 멈추는 방식을 피하는 데 도움이 된다. 하지만 자식이 있다는 이유로 부모의 비용이 0이 되는 것은 아니다.

우선 fork를 만드는 순간의 작업이 있다. 메모리 본문을 모두 즉시 복사하지 않아도 프로세스와 주소 공간 관리에 비용이 든다. 그 다음 부모가 공유 페이지를 변경하면서 COW가 발생할 수 있다. 부모와 자식이 같은 호스트의 CPU, 메모리, 저장 장치 등 자원을 사용한다는 점도 남는다. “백그라운드”는 사용자 요청과 완전히 무관하다는 뜻이 아니다.

같은 사무실의 직원 두 명을 생각해 보자. 한 직원이 주문을 받고 다른 직원이 장부 사본을 만든다면 역할은 나뉜다. 그러나 같은 복사기와 책상을 사용하면 서로 영향을 줄 수 있다. 실제 컴퓨터에서는 그 영향이 스케줄링, 메모리 대역폭, 페이지 관리, I/O 경쟁 같은 형태로 나타난다. 기능상 분리와 자원상 독립을 혼동하지 않는 것이 중요하다.

저장 중에 부모가 새 키를 추가하거나 기존 값을 바꿀 수 있다. 자식은 기준 시점의 상태를 계속 읽어야 하므로 현재 메모리의 모든 최신 변경을 따라가며 사진을 바꾸는 모델이 아니다. 이 성질 덕분에 일관된 시점의 파일을 만들 수 있지만, 바로 그 때문에 완료 직전의 최신 쓰기는 해당 파일에 포함되지 않을 수 있다. 장점과 한계가 같은 원리에서 나온다.

작업이 실패하면 부모는 실패 상태를 관측하고 관련 지표를 갱신한다. 예전의 정상 RDB가 남아 있을 수도 있다. 따라서 “dump.rdb가 있으니 이번 저장이 성공했다”는 판단은 틀릴 수 있다. 파일 존재, 이번 작업의 완료, 선택한 파일의 세대는 서로 다른 확인 항목이다.


## 파일 보충. 원자적 교체와 완전한 안전은 같은 말이 아니다

새 RDB를 쓰는 동안 기존 정상 파일을 계속 제자리에서 조금씩 덮어쓴다면, 중간 실패 때 기존 파일과 새 파일 모두 불완전해질 위험이 있다. 임시 파일에 새 결과를 만들고 성공 후 최종 이름으로 교체하는 방식은 이런 종류의 중간 상태 노출을 줄인다. 책의 새 판을 완성한 뒤 표지를 바꾸는 것과, 독자가 읽고 있는 책의 페이지를 한 장씩 갈아 끼우는 것의 차이로 생각할 수 있다.

여기서 원자적 교체는 파일 이름을 통해 관찰하는 교체 경계에 대한 설명이다. 어떤 파일 시스템과 저장 장치에서도 전원 손실에 대한 모든 보장이 자동으로 같아진다는 뜻은 아니다. 원자성과 내구성을 나누어 읽어야 한다. 교체 중간의 섞인 파일을 보지 않는 것과 교체 후 파일이 하드웨어 장애를 견디는 것은 다른 질문이다.

백업 도구는 완성된 파일을 복사해야 한다. 임시 파일을 발견했다고 최신 결과로 선택하면 아직 작성 중일 수 있다. 최종 파일도 이전 작업의 정상 결과일 수 있으므로 원하는 작업과 연결해야 한다. 백업의 최신성은 파일이 정상적으로 열리는지만으로 판정되지 않는다.

복사한 파일의 해시를 비교하면 전송 전후 바이트가 같은지 확인하는 데 도움이 된다. 하지만 같은 바이트가 업무상 올바른 시점이라는 뜻은 아니다. 이미 잘못된 데이터가 들어 있는 파일을 정확히 복사할 수도 있다. **전송 무결성, 파일 형식 유효성, 업무 데이터 정합성**은 각각 다른 검사다.

| 검사 | 확인하는 것 | 통과해도 남는 문제 |
|---|---|---|
| 파일 크기·존재 | 파일이 생성됐는지 | 최신 세대인지 모름 |
| 체크섬 대조 | 복사 중 바이트 변화가 없는지 | 원본부터 잘못됐을 수 있음 |
| redis-check-rdb | 파일 구조 관련 유효성 | 업무 값이 맞는지 모름 |
| 격리 로드 | 해당 환경에서 로드 가능한지 | 실제 서비스 계약 전체는 별도 |
| 업무 샘플 대조 | 정한 데이터 규칙이 맞는지 | 검사하지 않은 모든 키까지 증명하지 않음 |

검사를 여러 개 하는 이유는 같은 확인을 반복하기 위해서가 아니다. 서로 다른 실패를 구별하기 위해서다. 이 표를 이해하면 “체크섬 맞으니까 복구 완료” 같은 성급한 결론을 피할 수 있다.


## 실습 해설. 원본 서버와 복원 서버를 분리하는 이유

앞의 실습은 원본 Redis와 복원 Redis를 서로 다른 포트와 디렉터리로 실행한다. 이것은 단순한 편의가 아니다. 복원 실험 중 원본 파일을 덮어쓰거나 원본 데이터를 바꿔 버리면, 무엇이 원래 상태였는지 비교할 기준을 잃는다. 원본과 실험 대상을 분리하면 실패해도 관찰할 기준이 남는다.

원본에 balance=100을 저장한 뒤 BGSAVE 완료를 확인한다. 그 다음 원본을 90으로 바꾼다. 파일을 복원한 서버에서는 100이 보이고 원본에서는 90이 보일 것으로 예상한다. 두 서버가 다른 값을 보이는 것은 실습의 성공 조건이다. 둘이 항상 같아야 한다고 생각하면 스냅샷의 목적을 잘못 이해한 것이다.

`lab:snapshot-marker=before`는 복구 지점을 식별하기 위한 작은 표식이다. 표식도 일반 키이므로 언제 썼는지 중요하다. 스냅샷 이후에 쓴 표식은 그 스냅샷에 포함될 것이라고 기대할 수 없다. 실제 백업 배치에서는 표식과 작업 메타데이터를 어떤 순서로 기록하는지 정의해야 한다. 표식만 있으면 모든 시점 문제가 해결된다고 생각하지 않는다.

`lab:after-snapshot`이 복원 서버에 없다는 사실도 중요한 결과다. 파일을 만든 뒤의 변경을 해당 스냅샷이 포함하지 않는다는 것을 값 변경과 새 키 추가 두 관점에서 확인한다. 정상 경로를 관찰하는 데 굳이 서버를 강제 종료할 필요가 없다. 별도 인스턴스에 파일을 로드하는 것만으로도 시점 경계를 이해할 수 있다.

`SHUTDOWN NOSAVE`를 사용하는 것은 실습 종료 시 새 저장으로 관찰한 파일을 다시 바꾸지 않으려는 의도다. 이 명령을 운영 종료의 일반 권장 방식으로 복사하면 안 된다. 실습에서는 영속성을 꺼 둔 작은 별도 인스턴스와 복사한 파일만 다룬다. 명령의 안전성은 문자열 자체가 아니라 대상과 목적, 현재 상태에 달려 있다.

실습이 예상과 다르면 다음 순서로 확인한다. 복원 서버가 정말 16383인지, 원본과 다른 디렉터리인지, 복사한 파일이 완료된 파일인지, AOF를 함께 읽고 있지 않은지, 이후에 다른 저장을 수행하지 않았는지 살핀다. “Redis가 이상하다”보다 먼저 **어떤 입력으로 어떤 서버를 시작했는지**를 확인하는 01편의 원칙이 적용된다.


## Java 사고 실험. 복구 지점과 현재 상태를 별도 객체로 다루기

아래 예제는 RDB 파일 파서를 구현하지 않는다. Java Map의 복사본으로 **현재 상태와 스냅샷 상태가 다른 객체라는 개념**을 보여 준다. 실제 Redis의 fork, COW, 디스크 기록이나 성능을 재현하는 코드는 아니다. Java 21에서 독립 실행할 수 있다.

```java
import java.time.Duration;
import java.time.Instant;
import java.util.HashMap;
import java.util.Map;

public final class RedisSnapshotLesson {
    record Snapshot(Instant capturedAt, Map<String, String> values) {
        Snapshot {
            values = Map.copyOf(values);
        }
    }

    static Snapshot capture(Instant at, Map<String, String> live) {
        return new Snapshot(at, live);
    }

    static Map<String, String> restore(Snapshot snapshot) {
        return new HashMap<>(snapshot.values());
    }

    public static void main(String[] args) {
        Map<String, String> live = new HashMap<>();
        live.put("lab:balance", "100");
        Instant captured = Instant.parse("2026-10-22T03:00:00Z");
        Snapshot snapshot = capture(captured, live);

        live.put("lab:balance", "90");
        live.put("lab:after", "yes");
        Instant failure = captured.plusSeconds(30);
        Map<String, String> restored = restore(snapshot);

        if (!"90".equals(live.get("lab:balance"))) {
            throw new AssertionError("live state must change");
        }
        if (!"100".equals(restored.get("lab:balance"))) {
            throw new AssertionError("snapshot boundary was lost");
        }
        if (restored.containsKey("lab:after")) {
            throw new AssertionError("post-snapshot write must be absent");
        }
        System.out.println("live=" + live.get("lab:balance"));
        System.out.println("restored=" + restored.get("lab:balance"));
        System.out.println("point age seconds="
                + Duration.between(snapshot.capturedAt(), failure).toSeconds());
    }
}
```

Snapshot 생성자에서 `Map.copyOf`를 사용한다. 원본 Map의 참조만 보관했다면 원본을 바꿀 때 스냅샷이 바라보는 내용도 바뀌어 이 사고 실험의 목적을 달성하지 못한다. 여기서는 key와 value가 불변 문자열이므로 이 예제의 상태 분리에 충분하다. 값이 변경 가능한 복잡한 객체라면 Map의 얕은 복사만으로 내부 객체까지 독립된 스냅샷이 되는 것은 아니다.

`restore`는 스냅샷에서 새 Map을 만든다. 복구된 데이터를 이후에 변경해도 스냅샷 자체를 바꾸지 않으려는 의도다. 실제 복구에서도 보존해야 할 백업 원본과 새 서비스가 쓸 데이터 경로를 분리한다. 물론 이 Java 모델의 객체 복사는 Redis RDB의 파일 로드와 구현 방식이 다르다. 비유 코드의 한계를 함께 읽어야 한다.

출력의 30초는 이 가상 시나리오에서 기준 시점과 장애 시점 사이의 시간이다. 그 30초 동안 실제 업무가 얼마나 발생했는지는 별도다. 손실 시간을 업무 손실 건수로 바꾸려면 그 구간의 이벤트와 요청을 알아야 한다. 30초라는 숫자가 작아 보여도 피크 시간의 입고 확정이 몰렸다면 영향은 클 수 있다.

이 모델은 TTL을 구현하지 않는다. 만료가 포함된 실제 복구에서는 시계와 만료 시각이 추가된다. 예제에 없는 기능까지 테스트했다고 주장하지 않는 것이 중요하다. 코드의 목적은 “사진이 현재 상태를 계속 따라가는 것이 아니다”라는 한 관계를 분명하게 만드는 것이다.


## 복구 검증 보충. TTL은 백업 중에도 시간이 흐른다

캐시에 10분 TTL을 주고 저장했다고 하자. 스냅샷 파일을 몇 시간 보관한 뒤 복원하면 그 값에 다시 10분의 유효기간이 생길까? 그렇게 생각하면 안 된다. 만료는 시간과 관련된 데이터이므로 복원 시점까지 흐른 시간도 의미에 영향을 준다. RDB가 과거 상태를 표현하더라도 세상의 시계가 과거로 되돌아가는 것은 아니다.

이 차이를 모르고 키 수를 비교하면 정상 복구를 실패라고 판단할 수 있다. 원본 스냅샷을 만들 때 1,000개 키 중 900개가 짧은 TTL의 캐시였다면, 나중에 복원할 때 그 키들이 보이지 않을 수 있다. 이 경우 먼저 만료 정책과 복원 시각을 확인해야 한다. 키 수가 줄었다는 사실만으로 파일 손상을 확정하지 않는다.

반대 방향의 위험도 있다. 만료가 없던 오래된 캐시를 복원하면 그 값은 현재 DB보다 뒤처져 있을 수 있다. 단순히 키가 존재한다는 이유로 최신 정보처럼 반환하면 사용자가 오래된 데이터를 보게 된다. 복구 시 캐시 세대를 바꾸거나, 업무 버전을 확인하거나, 원본으로 다시 채우는 정책이 필요할 수 있다. 어떤 선택이 적절한지는 재생성 비용과 신선도 요구에 달려 있다.

시스템 시계도 중요하다. 시간에 기반한 데이터는 서버 시계가 크게 어긋나면 해석이 달라질 수 있다. 복구 환경의 시간 동기화는 운영 편의가 아니라 데이터 의미의 일부가 될 수 있다. 그렇다고 시간을 마음대로 과거로 돌려 만료 키를 되살리는 식의 운영 절차를 제안하는 것은 아니다. 복구는 업무의 현재 시점에서 어떤 데이터를 사용해도 되는지 판단하는 과정이다.

복원 검증용 데이터는 목적별로 나누자. 파일의 시점 경계를 확인하는 marker에는 충분히 긴 수명이나 명시적 비만료 조건을 사용하고, TTL 동작 검사는 별도 키와 시간 범위로 확인한다. 모든 검사를 몇 초짜리 키 하나로 해결하려 하면 느린 CI나 복구 준비 시간 때문에 결과를 해석하기 어려워진다.


## 장애 대응 보충. 저장 실패 때 무작정 재시작하면 왜 위험한가

저장 실패가 발생한 상태에서 메모리에는 최신 데이터가 남아 있을 수 있다. 이때 원인을 확인하지 않고 프로세스를 재시작하면, 메모리의 최신 상태를 잃고 더 오래된 파일로 돌아갈 수 있다. 재시작은 오류 메시지를 지우는 버튼이 아니라 데이터 상태를 바꾸는 사건이다. 어떤 데이터를 보존할 수 있는지 확인한 뒤 선택해야 한다.

디스크가 가득 찼다면 먼저 어떤 파일이 필요한지 구별한다. 오래된 로그와 현재 복구에 필요한 파일은 같지 않다. 유일한 정상 RDB나 AOF의 필요한 세트를 삭제해서 공간을 확보하면 저장 오류는 줄어도 복구 수단이 사라질 수 있다. 공간 확보는 파일 역할과 보관 정책을 아는 상태에서 수행한다.

권한 오류라면 파일 경로와 실행 계정, 마운트 상태를 확인한다. 메모리 관련 fork 실패라면 OS와 컨테이너 제한, overcommit 정책과 실제 피크를 확인한다. 서로 다른 원인에 같은 “재시작” 조치를 적용하는 것은 진단이 아니다. 복구 목표를 지키기 위한 안정화와 원인 규명을 나누고, 각각 어떤 증거를 남길지 정해야 한다.

안전장치를 끄는 선택은 서비스가 쓰기를 다시 받는 대신 내구성 위험을 더 받아들이는 결정일 수 있다. 그 자체를 언제나 금지하거나 언제나 허용하는 단순 규칙으로 설명하지 않는다. 데이터 역할, 손실 허용 범위, 대체 기록, 장애 시간과 승인된 운영 정책에 따라 판단한다. 중요한 것은 위험을 숨기지 않고 변경의 의미를 분명하게 하는 것이다.

원인을 고친 뒤에는 새 저장 성공을 확인한다. 그 다음 원하는 위치의 백업과 격리 복원이 가능한지 확인한다. 오류가 사라졌다는 사실만으로 실패 기간 동안의 복구 지점 공백이 자동으로 메워진 것은 아니다. 현재 상태의 새로운 정상 사본을 확보했는지까지 이어서 점검해야 한다.


## 설계 연습. 복구된 Redis와 살아 있는 MySQL의 시간이 다를 때

가상의 주문 500번이 MySQL에서는 확정 상태이고 Redis의 오래된 스냅샷에서는 대기 상태라고 하자. 복구된 Redis가 먼저 응답한다고 그 값을 최종 진실로 취급하면 이미 확정한 주문을 다시 처리할 수 있다. 데이터의 권위가 MySQL에 있다면 Redis는 그 기준에 맞춰 재생성하거나 무효화해야 한다. 응답 속도가 데이터의 권위를 결정하지 않는다.

중복 방지 키도 같은 문제를 가진다. Redis 스냅샷 이후에 처리한 요청의 ID가 복구본에는 없을 수 있다. 클라이언트가 재시도하면 새 요청처럼 보일 수 있다. 업무상 두 번 실행하면 안 되는 변경을 Redis의 짧은 기억에만 의존했는지 검토해야 한다. DB 고유 제약이나 영속적인 업무 이력과 연결하는 이유가 여기서 나온다.

반대로 오래된 락이나 진행 상태가 남아 있으면 이미 끝난 작업을 아직 실행 중이라고 볼 수 있다. TTL과 소유권, 최종 업무 상태 대조가 필요하다. 단순히 “키가 있으면 처리 중”이라는 조건이 복구 뒤에도 유효한지 질문해야 한다. 복구는 저장된 바이트를 읽는 기술 작업인 동시에 애플리케이션 상태 머신을 현재 현실과 맞추는 작업이다.

설계 검토에서는 데이터별로 복구 후 행동을 한 줄씩 적어 보자. 상품 이름 캐시는 원본 조회로 갱신한다. 작업 확정은 DB 이력으로 판정한다. 임시 대기열은 약속한 재입장 정책을 따른다. 인증 세션은 보안 요구에 따라 재로그인을 요구할 수 있다. 이 예시는 가능한 정책의 형태를 보여 주며 실제 서비스의 정답은 아니다. 중요한 것은 모든 키를 같은 방식으로 처리하지 않는 것이다.


## 면접 질문과 상세 답변

<details><summary>1. RDB와 AOF를 가장 간단하게 구분하면 무엇인가요?</summary>

RDB는 특정 시점의 상태 표현이고 AOF는 상태를 재구성하는 기록 계열이다. RDB 이후의 쓰기는 해당 스냅샷만으로 복원할 수 없고, AOF도 fsync 정책과 저장 장치·장애 유형에 따라 손실 경계가 있다. RDB는 이동과 보관에 유용한 조밀한 복구 지점이며, AOF는 더 짧은 손실 창을 목표로 할 수 있다. 어느 쪽이 무조건 좋다는 대신 RPO, RTO, 처리 부하와 운영 복잡도로 선택한다.

</details>

<details><summary>2. BGSAVE가 백그라운드라면 서비스 지연이 전혀 없나요?</summary>

아니다. 자식이 파일을 쓰는 동안 부모가 요청을 계속 처리할 수 있지만 fork 순간의 비용, COW, 메모리 대역폭과 디스크 경합이 남는다. 데이터셋과 환경에 따라 p99가 튈 수 있다. 저장 전후 요청 지연, latest_fork_usec, COW, 저장 시간과 시스템 메모리를 함께 측정한다. “백그라운드”는 비용이 없다는 뜻이 아니라 일부 작업의 실행 주체가 분리된다는 뜻이다.

</details>

<details><summary>3. BGSAVE가 성공 응답을 주면 바로 파일을 백업해도 되나요?</summary>

응답과 완료를 구분해야 한다. 명령은 백그라운드 작업 시작을 알릴 수 있으며, 파일은 아직 생성 중일 수 있다. 진행 상태가 끝났고 마지막 작업이 성공했는지, 로그와 파일 시각이 원하는 작업과 맞는지 확인한다. 기존 dump.rdb가 있으면 너무 일찍 복사해도 파일 자체는 정상이라 실수를 발견하기 어렵다. 백업의 최신성까지 검증해야 한다.

</details>

<details><summary>4. save 300 100이면 RPO가 300초인가요?</summary>

그렇게 단정할 수 없다. 시간과 변경 조건, 작업 시작 지연, 저장 소요 시간, 실패, 외부 백업 전송 시점이 모두 영향을 준다. 최근 성공 스냅샷이 실제로 언제의 상태인지와 그 파일이 어디에 보관되어 있는지를 기준으로 RPO를 평가한다. 설정값은 계획이고, 검증된 복구 지점의 나이는 증거다. 특히 리전 장애와 단일 프로세스 장애의 복구 경로를 분리해야 한다.

</details>

<details><summary>5. 실행 중인 Redis의 dump.rdb를 복사해도 되나요?</summary>

완성된 RDB는 이후 제자리에서 계속 수정되는 방식이 아니라 다음 저장 결과로 교체되는 구조이므로 공식 문서가 온라인 복사를 설명한다. 다만 임시 파일을 복사하지 말고, 원하는 저장의 성공과 경로를 확인해야 한다. 복사 가능성과 복구 가능성은 별개이므로 전송 검증과 격리 복원을 수행한다. 파일 복사 성공만으로 업무 정합성이 검증된 것은 아니다.

</details>

<details><summary>6. RDB가 있으면 백업은 별도로 필요 없나요?</summary>

로컬 RDB 하나는 같은 디스크 고장, 호스트 상실, 오삭제, 잘못된 데이터의 새 스냅샷으로부터 충분히 보호하지 못한다. 백업은 독립 위치와 여러 시점의 보존, 접근 통제, 복원 훈련을 포함한다. 현재 파일을 계속 덮어쓰는 영속성과 과거의 정상 지점을 유지하는 백업은 목적이 다르다. 복제본 역시 잘못된 변경을 따라가므로 백업을 대신하지 않는다.

</details>

<details><summary>7. 캐시라면 영속성을 모두 꺼도 괜찮나요?</summary>

원본에서 재생성 가능하고 유실이 업무 정합성에 영향을 주지 않는다면 가능한 선택이다. 그러나 빈 캐시에서 원본 DB로 몰리는 부하와 재가열 시간은 검증해야 한다. 복제 구성에서 영속성 없는 primary가 빈 상태로 자동 재시작하면 복제본이 그 빈 상태를 따라갈 위험도 있다. 따라서 “캐시니까 상관없다”가 아니라 재시작·장애 전환·원본 보호까지 포함한 계획이 있어야 한다.

</details>

<details><summary>8. 복구 후 키 개수가 같으면 데이터가 정상인가요?</summary>

충분하지 않다. 값, 자료형, 필수 필드, TTL, 업무 불변식이 다를 수 있다. 시간 경과에 따라 정상적으로 만료된 키도 있으므로 수가 다르다고 곧바로 손상이라고 할 수도 없다. 대표 샘플과 업무별 불변식, 복구 지점 marker, 애플리케이션 읽기 검증을 결합한다. 복원 성공은 프로세스가 시작되었다는 사실보다 넓은 개념이다.

</details>

## 추가 면접 문답: 복구를 시간과 증거로 설명하기

<details><summary>9. 스냅샷 파일이 방금 완성됐는데 왜 몇 분 전 값으로 복원되나요?</summary>

파일 완성 시각과 데이터 기준 시점이 다르기 때문이다. 백그라운드 저장 동안 부모는 새 요청을 처리할 수 있고 자식은 기준 시점의 상태를 파일로 만든다. 저장이 오래 걸렸다면 완료 직전의 쓰기가 그 스냅샷에 들어 있다고 기대할 수 없다.

면접에서는 시작·완료·복사·검증 시각을 나누어 설명한다. 마지막 저장 완료가 최근이라는 사실은 중요한 증거지만 복구 지점의 최신성을 전부 설명하지 않는다. 장애 범위에 따라 접근 가능한 사본과 그 기준 시점을 확인해야 한다.

</details>

<details><summary>10. 체크섬이 같으면 복원 테스트는 생략해도 되나요?</summary>

체크섬은 전송 전후 바이트의 일치를 확인하는 데 도움이 되지만, 해당 파일이 필요한 버전에서 로드되는지나 업무 값이 올바른지는 확인하지 못한다. 잘못된 시점의 정상 파일도 정확히 복사할 수 있다. 무결성과 적합성을 구별해야 한다.

파일 형식 검사, 격리 인스턴스 로드, 대표 데이터와 업무 규칙 대조를 목적에 맞게 추가한다. 모든 키를 완벽하게 검사했다고 과장하지 말고 어떤 범위를 확인했는지 기록한다. 복원 훈련은 실제 RTO를 측정하는 데도 필요하다.

</details>

<details><summary>11. RDB 복원 후 키 수가 줄었으면 데이터 손상인가요?</summary>

그럴 수도 있지만 키 수만으로 확정할 수 없다. 스냅샷에 있던 만료 정보와 복원 시점 사이에 시간이 흘러 일부 키가 유효하지 않을 수 있다. 먼저 TTL을 가진 키의 비율과 수명, 복원 환경의 시계를 확인한다.

반대로 키 수가 같다고 정상도 아니다. 값이나 자료형, 필수 필드가 달라질 수 있다. 개수는 빠른 이상 징후 지표이고, 정합성 판단에는 기준 시점과 업무 의미가 필요하다. “같으면 성공, 다르면 손상”이라는 이분법을 피한다.

</details>

<details><summary>12. 캐시를 RDB에서 복원하면 DB 부하 문제도 해결되나요?</summary>

완화될 수 있지만 자동 해결은 아니다. 복원한 값이 오래됐거나 만료되어 재조회가 많을 수 있고, 평소 인기 키가 스냅샷에 충분히 포함되어 있지 않을 수도 있다. 클라이언트가 동시에 다시 연결하면서 순간 부하가 생길 수도 있다.

복원 후 유효한 hit 비율, DB 조회량, 재가열 속도를 함께 본다. 필요한 데이터부터 제한된 동시성으로 채우고 원본 보호 정책을 유지한다. 복구 프로세스가 시작된 것과 사용자가 안정적인 응답을 받는 것은 다른 완료 기준이다.

</details>

<details><summary>13. 영속성 실패 중에는 재시작이 가장 빠른 해결 아닌가요?</summary>

메모리에만 있는 최신 상태를 잃을 수 있으므로 먼저 복구 가능한 지점과 실패 원인을 확인해야 한다. 디스크 공간이나 권한 문제라면 재시작 후에도 같은 문제가 남을 수 있고, 로드 과정에서 시간이 더 걸릴 수 있다. 현재 상태와 파일 상태를 구별하지 않은 재시작은 위험하다.

서비스 안정화가 급하더라도 어떤 데이터를 지킬지, 어떤 실패를 받아들일지, 어떤 증거로 조치 성공을 판단할지 정한다. 재시작이 적절한 경우도 있지만 모든 저장 오류의 공통 처방은 아니다.

</details>
