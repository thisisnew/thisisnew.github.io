## 1. 실습 목표는 성공 메시지가 아니라 불변식 확인이다

**불변식**은 과정이 바뀌어도 유지되어야 하는 조건이다. Cluster 실습에서는 모든 필요한 슬롯이 담당자를 갖고, 각 노드가 같은 최종 소유권을 이해하고, 테스트 키가 이동 전후에 올바르게 읽히는지를 확인한다. 생성 도구가 성공을 출력했다는 사실은 시작점이지 애플리케이션 검증의 끝이 아니다. 명령을 실행하기 전에 테스트 키 목록과 예상 값을 파일이나 노트에 기록하면 사후 비교가 쉬워진다.

공통 실습 토대의 여섯 노드는 빈 데이터와 서로 다른 설정 상태 파일로 시작한다. 기존 운영 데이터를 가진 노드에 `--cluster create`를 적용하는 것은 이 절의 범위가 아니다. 기존 데이터 마이그레이션은 키 스키마, DB 0 사용, cross-slot 명령, TTL, 복구 경로를 포함한 별도 계획이 필요하다. 안전한 실습은 새로 만든 디렉터리와 주소만 대상으로 한다.

## 2. CLI의 일반 모드와 Cluster 모드를 비교한다

```bash
redis-cli -p 7000 CLUSTER KEYSLOT 'shipment:{S200}:status'
redis-cli -p 7000 SET 'shipment:{S200}:status' PACKED
redis-cli -c -p 7000 SET 'shipment:{S200}:status' PACKED
redis-cli -c -p 7002 GET 'shipment:{S200}:status'
```

키의 슬롯이 7000 담당 범위가 아니라면 일반 모드의 `SET`은 `MOVED`를 반환할 수 있다. 이것은 반드시 서버 장애가 아니라 올바른 서버로 가라는 정상 프로토콜이다. `-c` 모드에서는 리다이렉션을 따라가 성공할 것으로 기대한다. 우연히 키가 7000의 슬롯이면 일반 모드도 성공하므로 오류가 안 나왔다고 Cluster 라우팅이 불필요하다고 결론 내리지 않는다. `CLUSTER NODES`의 슬롯 범위와 `KEYSLOT` 결과로 이유를 설명한다.

다음으로 같은 태그의 두 키를 쓰고 다중 키 조회를 비교한다. 서로 다른 태그가 항상 서로 다른 슬롯이라는 보장은 없으므로 실험에서는 실제 슬롯 번호를 확인한다. 해시 충돌이 있기 때문이다. 같은 태그는 같은 슬롯을 보장하지만 다른 태그가 다른 슬롯을 보장하지는 않는다.

```bash
redis-cli -c -p 7000 MSET   'shipment:{S200}:status' PACKED   'shipment:{S200}:carrier' demo-carrier
redis-cli -c -p 7001 MGET   'shipment:{S200}:status' 'shipment:{S200}:carrier'
```

## 3. 리샤딩은 슬롯 소유권과 그 안의 키를 함께 옮긴다

**리샤딩**은 담당 슬롯을 다른 primary로 재배치하는 작업이다. 새 서버를 추가하는 것과 같은 말이 아니다. 기존 세 primary 사이에서도 슬롯을 옮길 수 있고, 새 primary가 들어와도 슬롯을 받기 전에는 일반 키 저장 부하를 맡지 않을 수 있다. 물류 비유로 새 센터 건물을 열었다고 바로 담당 우편 구역이 배정되는 것은 아니다.

실습에서는 먼저 7000~7005의 node ID와 슬롯 범위를 기록하고, 두 primary를 source와 target으로 선택한다. 포트 문자열 대신 도구가 요구하는 정확한 node ID를 사용한다. 처음에는 작은 슬롯 수만 옮겨 지연과 로그를 관찰한다. 한 슬롯에 큰 키가 있다면 슬롯 개수가 적어도 작업 비용이 클 수 있다.

```bash
redis-cli -p 7000 CLUSTER NODES
redis-cli --cluster reshard 127.0.0.1:7000
```

대화형 질문에서 이동할 슬롯 수, 대상 node ID, 출발 node ID를 지정하고 계획을 읽는다. 이 교재는 환경마다 다른 ID를 가짜로 채워 넣지 않는다. 계획에 나타나는 출발지·목적지·슬롯이 방금 확인한 것과 일치할 때만 동의한다. 자동화하려면 먼저 같은 버전의 `redis-cli --cluster help`로 옵션을 확인하고 비대화형 실행 전 계획 검증 절차를 둔다.

## 4. 이동 중에는 왜 ASK가 필요한가

출발 노드가 슬롯을 **MIGRATING**, 목적지 노드가 **IMPORTING** 상태로 이해하는 과도기가 있다. 출발 노드에 아직 있는 키는 그곳에서 처리할 수 있고, 이미 옮겨진 키에 대한 요청은 목적지로 안내해야 한다. 이때 임시 리다이렉션 `ASK`는 다음 요청에 대한 예외적 경로를 안내한다. 클라이언트는 목적지 연결에서 `ASKING`을 보낸 뒤 해당 명령을 수행하는 절차를 따른다. 반면 `MOVED`는 슬롯 담당자 변경을 반영하도록 하는 정보다.

리샤딩 도구는 키 이전과 최종 슬롯 소유권 갱신을 조정한다. 사용자가 운영 환경에서 낮은 수준의 `CLUSTER SETSLOT`과 `MIGRATE`를 무작정 섞어 실행하는 것은 위험하다. 도중 실패로 두 노드의 인식이 다르면 증거를 확보하고 상태를 진단해야 한다. `--cluster fix`도 이름이 친절하다고 무조건 무해한 조회 명령이 아니다. 복구 계획과 백업 없이 자동 수정을 실행하지 않는다.

## 5. 이동 전후 테스트를 업무 단위로 설계한다

테스트 키의 값만 비교하지 말고 TTL이 있는 키의 잔여 수명, 자료형, 큰 컬렉션의 원소 수, 애플리케이션 요청의 오류와 지연을 함께 본다. 일부 샘플이 같다고 모든 데이터가 검증된 것은 아니므로 샘플링 범위를 명시한다. `DBSIZE`는 접속한 노드의 키 수를 나타내며 전체 Cluster의 데이터량이라고 단정하지 않는다. TTL로 키가 만료되는 동안은 단순 합계 비교도 조심해야 한다.

리샤딩 중 같은 슬롯의 다중 키가 일시적으로 서로 다른 쪽에 존재하면 일부 다중 키 연산이 `TRYAGAIN` 같은 재시도 가능한 상태를 만날 수 있다. 정상상태에서 같은 슬롯이라는 설계가 이동 중 모든 순간 무오류를 보장하지는 않는다. 짧은 재시도·backoff·전체 요청 deadline을 두고 재실행의 업무 효과를 검토한다. `MOVED`·`ASK`·timeout·`TRYAGAIN`을 같은 종류의 실패로 뭉뚱그리지 않는다.

```bash
redis-cli --cluster check 127.0.0.1:7000
redis-cli -p 7000 CLUSTER NODES
redis-cli -p 7001 CLUSTER NODES
redis-cli -c -p 7002 GET 'shipment:{S200}:status'
```

최종적으로 이동 중 슬롯 표시가 남지 않는지, 소유권 인식이 수렴했는지, 애플리케이션이 새 경로로 요청하는지 확인한다. “다운타임 없이 이동 가능”이라는 설계 특성을 “지연 증가·재시도·업무 오류가 절대 없다”는 약속으로 확대하지 않는다. 데이터 크기와 네트워크 상황에 맞는 작업 속도를 정하고 관측 지표가 허용 범위를 넘으면 다음 배치를 멈추는 기준을 준비한다.

## 실습 공통 토대: 여섯 노드의 격리된 작은 Cluster

이 절은 13~16장을 독립적으로 읽는 독자를 위한 실습 토대다. 아래 명령은 교재 작성 중 실제 실행한 결과가 아니며 이후 설명은 예상 관찰이다. 이미 사용 중인 포트와 충돌하지 않는 로컬 일회용 환경에서만 수행한다. 동일 호스트의 여섯 프로세스는 클러스터 프로토콜 학습에는 도움이 되지만 호스트 장애를 견디는 배치가 아니다. 운영에서는 primary와 그 replica를 서로 다른 장애 도메인에 배치하고, 인증·TLS·방화벽·백업·여유 메모리·복제 지연 정책을 별도로 설계해야 한다.

```bash
redis-server --version
redis-cli --version
LAB=$(mktemp -d /tmp/redis-cluster-study.XXXXXX)
printf '%s\n' "$LAB"
for p in 7000 7001 7002 7003 7004 7005; do
  mkdir -p "$LAB/$p"
  cat > "$LAB/$p/redis.conf" <<EOF
port $p
bind 127.0.0.1
protected-mode yes
dir $LAB/$p
pidfile $LAB/$p/redis.pid
logfile $LAB/$p/redis.log
daemonize yes
cluster-enabled yes
cluster-config-file nodes.conf
cluster-node-timeout 5000
save ""
appendonly no
EOF
  redis-server "$LAB/$p/redis.conf"
done
redis-cli --cluster create   127.0.0.1:7000 127.0.0.1:7001 127.0.0.1:7002   127.0.0.1:7003 127.0.0.1:7004 127.0.0.1:7005   --cluster-replicas 1
```

생성 도구가 제시하는 primary/replica 관계와 슬롯 범위를 읽고, 오직 이번에 만든 빈 노드 여섯 개가 맞을 때만 확인 질문에 동의한다. 포트 순서만 보고 특정 replica의 부모를 단정하지 않는다. 도구가 실제 제안하고 생성한 관계를 기록한다. 데이터 포트 7000~7005 외에 기본 cluster bus 포트 17000~17005도 노드 사이에서 필요하다. loopback 실습에서는 동일 호스트로 접근하지만 컨테이너나 VM을 섞으면 광고한 주소가 각 클라이언트와 다른 노드에서 실제로 도달 가능한지 확인해야 한다.

`nodes.conf`는 사용자가 수동 편집하는 일반 설정 템플릿이 아니라 Redis가 자신의 노드 ID, 다른 노드, 슬롯 배치 같은 상태를 기록하는 파일이다. 이 예제는 각 프로세스의 `dir`가 다르므로 파일명이 같아도 서로 다른 파일을 사용한다. 여러 노드가 하나의 `nodes.conf`를 공유하게 해서는 안 된다. `save ""`와 `appendonly no`는 실습용으로 영속성을 끈 설정이므로 재시작 복구 실험이나 운영 내구성의 근거로 사용할 수 없다. 재시작 후 데이터가 보이지 않는 것을 Cluster의 슬롯 계산 오류로 오인하지 않는다.

### 최초 정상 상태를 확인하는 네 가지 관점

```bash
redis-cli -p 7000 CLUSTER INFO
redis-cli -p 7000 CLUSTER NODES
redis-cli --cluster check 127.0.0.1:7000
redis-cli -p 7000 CLUSTER KEYSLOT 'shipment:{S100}:status'
redis-cli -p 7000 CLUSTER KEYSLOT 'shipment:{S100}:events'
redis-cli -c -p 7000 SET 'shipment:{S100}:status' READY
redis-cli -c -p 7001 GET 'shipment:{S100}:status'
```

첫 관점은 **전체 상태**다. 안정 상태에서는 `cluster_state:ok`와 전체 슬롯 할당을 기대한다. 둘째는 **노드 관계**다. `CLUSTER NODES`의 node ID, 역할, replica의 부모 ID, 링크 상태, 슬롯 범위를 읽는다. 셋째는 **슬롯 일관성**이다. 검사 도구가 모든 슬롯의 커버리지와 배치를 어떻게 보고하는지 확인한다. 넷째는 **애플리케이션 경로**다. `-c`를 붙인 redis-cli가 다른 primary로의 리다이렉션을 처리하며 쓰기와 읽기를 수행하는지 본다. 노드 상태가 정상이더라도 애플리케이션의 DNS, 자격 증명, 라우팅 정보가 잘못되면 요청은 실패한다.

위 두 키는 중괄호 안의 `S100`이 같으므로 동일 슬롯이 예상된다. 어떤 숫자가 나오는지 암기하지 말고 실제 `CLUSTER KEYSLOT`으로 확인한다. 동일 슬롯이라고 두 키의 값이 반드시 같다는 의미는 아니며, 동일 primary에 있다고 반드시 동일 슬롯인 것도 아니다. 하나의 primary가 수천 슬롯을 맡을 수 있기 때문이다. 다중 키 명령의 가능 여부는 서버 주소가 아니라 슬롯 번호로 판단한다.

### 장애를 넣기 전에 작성할 기록표

| 기록 항목 | 기록하는 이유 | 해석할 때의 주의 |
|---|---|---|
| 실행 버전과 설정 파일 | 실험 재현과 버전별 차이 확인 | `latest` 태그를 버전으로 기록하지 않는다 |
| primary ID와 슬롯 범위 | 장애가 영향을 주는 데이터 범위 파악 | 포트는 역할과 함께 바뀔 수 있다 |
| replica의 부모 ID와 복제 상태 | 승격 가능성과 최신성 평가 | 링크 연결과 데이터 완전성은 다르다 |
| 요청 ID·시작·종료 시각 | 업무 성공과 서버 성공을 구분 | timeout은 미실행의 증명이 아니다 |
| 변경 전후의 노드 출력 | 역할 전환·슬롯 이전 검증 | 한 노드의 순간 관찰을 전체 진실로 취급하지 않는다 |

장애 실습에서 `DEBUG SEGFAULT`를 사용할 필요는 없다. 이 명령은 의도적으로 프로세스를 충돌시키며 운영 환경에서는 금지해야 한다. 명확히 식별한 일회용 인스턴스의 정상 종료, 또는 격리된 컨테이너의 정지부터 시작하면 된다. 정상 종료 실험은 전원 장애·커널 정지·부분 네트워크 분할과 동일하지 않다. 그 차이를 실험 보고서에 적어야 결과를 과장하지 않는다. 실제 네트워크 분할 실험은 host 방화벽을 즉흥적으로 바꾸기보다 별도의 네트워크 namespace나 전용 컨테이너 네트워크를 준비한 뒤 수행한다.

### 정리와 증거 보존

```bash
# 이번 실습에서 직접 생성했고 다른 서비스가 아닌 것을 먼저 확인한다.
for p in 7000 7001 7002 7003 7004 7005; do
  redis-cli -h 127.0.0.1 -p "$p" SHUTDOWN NOSAVE
done
# $LAB의 로그와 설정은 분석이 끝날 때까지 보존한다.
```

추가한 7006, 7007 같은 노드가 있다면 해당 실습의 정확한 목록을 별도로 종료한다. 노드 제거 명령을 실행했다고 프로세스까지 종료되는 것은 아니다. 반대로 프로세스를 종료했다고 나머지 노드들이 그 노드를 잊은 것도 아니다. **멤버십 변경**, **프로세스 생명주기**, **데이터 보존**은 서로 다른 작업이라는 점을 마지막까지 구분한다.


## 리샤딩 관찰 노트: 같은 키를 세 시점에서 비교하기

이동 대상으로 선택한 슬롯 s에 `shipment:{S200}:status`와 `shipment:{S200}:carrier`가 있다고 가정하자. 실제 슬롯 번호와 source·target node ID는 `KEYSLOT`과 `CLUSTER NODES`로 확인하여 기록한다. 예제 이름을 썼다고 자동으로 사용자가 선택한 이동 슬롯에 포함되는 것은 아니므로 계획에 해당 슬롯이 들어 있는지 먼저 확인해야 한다.

| 시점 | 슬롯 소유권 인식 | 키의 실제 위치 | 읽기 요청에서 기대하는 해석 |
|---|---|---|---|
| 이동 전 | source 소유 | source | source가 정상 처리 |
| 이동 중 | 기존 소유권과 importing/migrating 상태 | 키별로 source 또는 target | ASK·일시 재시도 처리 가능 |
| 이동 후 | target 소유로 수렴 | target | 오래된 맵에는 MOVED, 갱신 후 직접 요청 |

이 표의 핵심은 슬롯 소유권과 키의 물리적 위치가 과도기에 같은 문장으로 설명되지 않는다는 것이다. 두 키가 모두 source에 있거나 모두 target에 있으면 다중 키 요청이 가능한 경로가 있을 수 있지만, 서로 나뉘면 바로 같은 노드에서 처리할 수 없다. 그래서 같은 슬롯 설계가 맞더라도 리샤딩 도중의 오류 처리를 시험해야 한다. “해시 태그를 붙였으니 이제 어떤 운영 변화도 안전하다”는 결론은 과장이다.

### 작은 부하 생성기의 요구사항

실험 부하 프로그램은 단순 초당 명령 수보다 요청별 결과를 보존해야 한다. 각 쓰기에 고유 ID와 예상 값을 붙이고, 성공 응답을 받은 요청과 결과 미상 요청을 별도 집합으로 기록한다. 읽기 검증은 TTL 만료와 실제 값 불일치를 구분한다. 모든 요청을 무조건 재시도해 최종 값만 맞추면 이동 중 오류와 불확실성의 증거가 지워질 수 있다.

```java
// 실제 클라이언트 API가 아니라 실험 기록 구조의 예시다.
record OperationTrace(
    String requestId,
    String key,
    String expectedValue,
    long startedNanos,
    long elapsedNanos,
    String outcome,       // ACK, TIMEOUT, MOVED, ASK, TRYAGAIN 등
    int attempts
) {}
```

저수준 MOVED나 ASK는 정상 지원 클라이언트 내부에서 처리되어 애플리케이션 예외로 노출되지 않을 수 있다. 이 경우 클라이언트 진단 지표나 debug 로그를 제한적으로 사용해 경로를 관찰하되 운영 트래픽의 민감한 키·값이 노출되지 않게 한다. 애플리케이션 결과에서는 전체 경과 시간과 재시도 횟수를 관찰한다. 평균은 정상 요청에 가려질 수 있으므로 높은 백분위 지연과 최대 지연도 함께 본다.

### 중단 기준과 되돌리기를 구분한다

이동 중 지연이 허용 범위를 넘었다면 먼저 다음 배치의 시작을 멈추는 것이 안전한 선택일 수 있다. 이미 진행한 키 이전을 모두 즉시 반대 방향으로 되돌리는 것은 또 하나의 리샤딩이며 부하와 오류를 늘릴 수 있다. “중단”과 “롤백”을 같은 작업으로 부르지 않는다. 현재 진행 중인 슬롯의 상태와 도구가 어디까지 완료했는지 확인한 뒤 다음 행동을 결정한다.

목적지 메모리가 부족하거나 인증 오류가 난 경우에는 키 위치와 열린 슬롯 상태를 기록한다. source와 target 모두에서 관련 슬롯의 상태를 확인하고, 다른 primary들의 최종 인식과 비교한다. 데이터를 보존해야 하는 환경에서 상태 파일을 지우거나 강제 fix를 반복해 문제를 숨기지 않는다. 리샤딩 명령의 로그·실패 시점·이동 계획이 있어야 재개와 복구를 구분할 수 있다.

### 최종 검증을 네 묶음으로 나눈다

첫째, `--cluster check`와 여러 노드의 `CLUSTER NODES`로 슬롯 커버리지와 소유권 수렴을 검사한다. 둘째, 미리 기록한 테스트 키의 자료형·값·원소 수를 비교한다. 셋째, TTL이 있는 키는 경과 시간을 고려해 남은 수명을 확인한다. 넷째, 애플리케이션이 새 노드에 직접 접근하여 성공하는지 확인한다. 이 네 묶음은 서로 대체되지 않는다. 값이 맞아도 라우팅이 비효율적일 수 있고, 라우팅이 맞아도 일부 테스트 데이터가 누락되었을 수 있다.

대량 운영 데이터 전체를 검증하지 않았다면 보고서에는 “선정한 N개 키와 슬롯 커버리지를 검증”했다고 적는다. 표본 검사 결과를 전체 무결성 증명으로 확대하지 않는다. 실험에서 TTL을 쓰지 않았다면 만료 동작은 미검증이라고 남긴다. 테스트가 자세할수록 검증하지 않은 범위도 명확히 표시해야 다음 실험을 설계할 수 있다.

### 온라인 이전의 사용자 경험

배송 조회 API가 리샤딩 중 몇 번의 짧은 재시도를 하더라도 사용자는 deadline 안에 정상 응답을 받을 수 있다. 반대로 전체 timeout이 너무 짧으면 Cluster가 정상적으로 ASK를 처리하는 동안에도 고객 오류가 늘 수 있다. timeout을 무조건 늘리는 것도 해결책은 아니다. 동시 요청이 오래 쌓여 애플리케이션 메모리와 원장 fallback을 압박할 수 있다. 이동 배치 크기, 재시도 정책, 동시성 제한, 고객 응답 계약을 함께 조정한다.

## 면접 질문과 깊이 있는 답변

답을 펼치기 전에 원리, 장애 반례, 운영 확인 방법의 세 순서로 말해 보자. 짧은 정의만 외우기보다 어떤 조건에서 그 설명이 깨지는지를 덧붙이는 것이 중요하다.

<details><summary>새 Cluster 생성 전에 노드가 비어 있어야 하는 이유는요?</summary>

기존 데이터와 슬롯 소유권을 임의로 섞지 않기 위해서입니다. 이 실습은 새 디렉터리의 빈 노드에서 토폴로지를 만드는 절차이며 기존 운영 데이터 이관 절차가 아닙니다. 기존 데이터는 DB·키 스키마·TTL·cross-slot 명령과 복구 경로를 따로 설계해야 합니다.

</details>

<details><summary>redis-cli의 -c는 무엇을 바꾸나요?</summary>

Cluster 리다이렉션을 처리하도록 합니다. 일반 연결에서 MOVED를 받는 것은 담당 노드가 다른 정상 상황일 수 있습니다. -c로 성공했다면 이동한 경로까지 관찰하고, 우연히 seed가 그 키의 담당자라 일반 모드도 성공한 경우와 구분합니다.

</details>

<details><summary>리샤딩과 노드 추가는 같은 작업인가요?</summary>

아닙니다. 노드 추가는 멤버십을 늘리는 작업이고 리샤딩은 슬롯과 그 데이터를 재배치하는 작업입니다. 새 primary가 슬롯을 받지 않으면 기존 데이터 부하가 자동으로 분산되었다고 볼 수 없습니다. 반대로 기존 primary 사이에서도 리샤딩할 수 있습니다.

</details>

<details><summary>ASK와 MOVED는 왜 다르게 처리하나요?</summary>

ASK는 이동 중 해당 요청에 대한 임시 안내이고 MOVED는 슬롯 담당자 정보 변경을 알립니다. ASK에서는 목적지 연결에서 ASKING 후 요청하는 절차가 필요하며 이를 곧바로 영구 슬롯 맵 변경과 동일시하면 잘못된 라우팅을 만들 수 있습니다. 검증된 클라이언트에 맡기는 편이 좋습니다.

</details>

<details><summary>같은 슬롯 다중 키 연산도 리샤딩 중 실패하나요?</summary>

키가 출발지와 목적지에 나뉘어 있는 과도기에는 일부 다중 키 연산이 재시도 필요 상태를 만날 수 있습니다. 정상상태의 동일 슬롯 조건은 모든 이동 중 순간의 무오류를 약속하지 않습니다. 전체 deadline과 backoff를 두고 재실행 효과가 안전한지 확인합니다.

</details>

<details><summary>슬롯 열 개만 옮기면 가벼운 작업인가요?</summary>

슬롯 수만으로 비용을 알 수 없습니다. 큰 키나 많은 키가 들어 있으면 네트워크·메모리·이벤트 루프 지연이 커질 수 있습니다. 이동 전 데이터 크기와 부하를 조사하고 작은 배치부터 지연을 관찰합니다. 허용 범위를 넘으면 다음 배치를 멈추는 기준을 둡니다.

</details>

<details><summary>DBSIZE 합계로 완전한 검증이 되나요?</summary>

노드별 키 수는 유용하지만 값과 TTL의 정확성까지 증명하지 않습니다. 만료가 진행되면 키 수는 자연스럽게 변하고 이동 중 중복 관찰도 주의해야 합니다. 테스트 키 목록의 값·자료형·TTL과 최종 슬롯 소유권, 애플리케이션 경로를 함께 확인합니다.

</details>

<details><summary>cluster fix를 바로 실행해도 되나요?</summary>

수정 명령은 읽기 전용 진단이 아닙니다. 열린 슬롯이나 인식 불일치의 원인과 데이터 위치를 먼저 기록하고 백업·복구 계획을 확보해야 합니다. 이름만 믿고 자동 수정을 실행하면 원래 상태와 조사 증거를 잃을 수 있으므로 승인된 절차로 다룹니다.

</details>
