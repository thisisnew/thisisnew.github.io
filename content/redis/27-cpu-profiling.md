## 1. CPU가 바쁘다는 말과 요청이 느리다는 말

음식점에서 음식이 늦게 나왔다고 하자. 요리사가 계속 칼질하느라 바쁜 것일 수도 있지만, 재료 배달을 기다리거나 주문서가 카운터에 쌓인 것일 수도 있다. 요리사의 손만 촬영해서는 모든 지연을 설명할 수 없다. CPU 프로파일링도 비슷하다. 프로그램이 CPU에서 실행 중인 순간을 관찰하는 도구는 “실제로 무엇을 계산했는가”를 잘 보여 주지만, 실행되지 못하고 기다린 모든 시간을 직접 보여 주지는 않는다.

**on-CPU**는 CPU에서 실행 중인 상태이고, **off-CPU**는 디스크·네트워크·락·스케줄링 등을 기다리며 실행하지 않는 상태를 가리킨다. CPU 프로파일을 읽기 전에 어느 문제를 조사하는지 정해야 한다. Redis 응답이 100ms 걸렸다고 CPU 계산이 100ms였다는 뜻은 아니다.

```text
애플리케이션 관측 지연
  = 클라이언트 대기 + 전송 + 서버 대기 + 명령 실행
  + 응답 전송 + 클라이언트 처리
```

이 식은 원인을 나누기 위한 개념식이다. 실제 비동기 시스템에서는 구간이 겹칠 수 있고 측정 경계도 도구마다 다르다. 중요한 점은 하나의 서버 CPU 프로파일로 전체 식을 설명하려 하지 않는 것이다.

## 2. 먼저 CPU 병목인지 확인한다

Redis 프로세스 CPU가 높다는 사실만으로 업무 명령 실행이 병목이라고 결론 내리지 않는다. TLS, 응답 복사, 메모리 할당·해제, 백그라운드 작업, 네트워크 처리에도 CPU가 사용된다. 반대로 전체 호스트 CPU가 낮아도 명령을 주로 처리하는 한 스레드는 포화될 수 있다.

8개 논리 CPU가 있는 머신에서 한 스레드가 한 코어를 거의 다 쓰면 호스트 전체 평균은 대략 12.5%처럼 보일 수 있다. 모니터링 도구마다 100%의 기준이 한 코어인지 전체 머신인지 다르므로 대시보드 단위를 확인한다. 컨테이너에서는 허용 CPU quota, 즉 사용할 수 있는 CPU 시간 한도 때문에 호스트가 한가해도 해당 컨테이너가 제한될 수 있다.

| 관찰 | 가능한 해석 | 다음 증거 |
|---|---|---|
| 주 실행 스레드 CPU가 높고 지연 증가 | 명령 또는 직렬 처리 구간 포화 | 함수 스택, 명령별 통계 |
| CPU 낮고 지연 높음 | 네트워크·디스크·큐·스케줄링 대기 | RTT, 저장장치, cgroup 지표 |
| 시스템 CPU 비중이 큼 | 시스템 호출·네트워크 커널 처리 | 커널 스택, 패킷·연결 수 |
| 클라이언트 CPU만 높음 | 직렬화·역직렬화·GC 비용 | JVM 프로파일 |
| fork 시점에 지연 집중 | 프로세스 복제·페이지 처리 영향 | latest_fork_usec, 메모리 지표 |

Redis 공식 프로파일링 가이드도 CPU 병목 여부를 먼저 확인하고, 심볼과 스택 추적에 필요한 빌드 조건을 준비하는 흐름을 설명한다. [Redis CPU profiling](https://redis.io/docs/latest/operate/oss_and_stack/management/optimization/cpu-profiling/)

## 3. 프로파일링이 실제로 수집하는 것

### 3.1 표본: 매 순간이 아니라 일정한 간격의 사진

샘플링 프로파일러는 일정 빈도로 실행 위치와 호출 스택을 기록한다. 99Hz면 대략 초당 99번의 표본을 목표로 한다. 모든 함수 호출을 기록하는 것은 아니다. 따라서 표본 수가 적으면 짧게 실행되는 함수가 빠질 수 있고, 우연한 흔들림도 커진다.

함수 A가 전체 표본의 40%에서 보였다고 해서 A가 정확히 전체 요청 시간의 40%를 차지했다고 단정하지 않는다. 어떤 이벤트를 샘플링했는지, 스레드와 프로세스 범위가 무엇인지, 표본이 유실되었는지를 함께 봐야 한다. 비율은 조사 방향을 잡는 증거이지 절대적인 진실의 소수점 표기가 아니다.

### 3.2 호출 스택: 누가 누구를 불렀는가

함수는 다른 함수를 호출한다. 예를 들어 명령 처리 함수가 키 조회를 하고, 키 조회가 해시 계산과 문자열 비교를 호출할 수 있다. 호출 스택은 지금 실행하는 함수와 그 함수를 부른 경로를 보여 준다. 단순히 `memcpy`가 많이 보이는 것보다 어떤 명령 경로에서 큰 복사가 생겼는지 확인하는 것이 중요하다.

- **self 비용:** 함수 자신의 코드에서 소비한 비용.
- **inclusive 비용:** 그 함수와 아래에서 호출한 함수들의 비용을 합친 관점.

상위 명령 처리 함수의 inclusive 비중이 크다고 그 함수 자체의 몇 줄을 최적화하면 빨라진다는 뜻은 아니다. 실제 비용이 하위의 암호화나 메모리 복사에 있을 수 있다. 보고서의 self와 children 열을 혼동하지 않는다.

### 3.3 심볼과 프레임 포인터

심볼은 기계어 주소를 함수 이름이나 소스 위치와 연결하는 정보다. 심볼이 없으면 보고서에 주소나 `[unknown]`이 많이 나타날 수 있다. 프레임 포인터는 호출 스택을 거슬러 올라갈 때 도움이 되는 구조다. 최적화된 빌드에서 생략되기도 하므로 DWARF 기반 언와인딩 같은 다른 방법이 필요할 수 있다.

프로파일이 깨졌을 때 “Redis가 이상하다”보다 심볼, 정확한 바이너리, 디버그 정보, 언와인딩 방식을 먼저 확인한다. 성능 측정을 위해 완전히 다른 디버그 빌드로 바꾸면 실제 운영 성능과 달라질 수 있다. 가능하면 운영과 같은 최적화 빌드에 대응되는 심볼을 사용하고, 빌드 변경의 영향을 기록한다.

## 4. perf와 eBPF를 만능 도구로 오해하지 않기

Linux의 perf는 CPU 이벤트와 스택을 관찰하는 도구다. eBPF 기반 도구는 커널의 제한된 실행 환경을 이용해 이벤트를 관찰할 수 있다. 둘 다 권한·커널 설정·컨테이너 제약에 영향을 받는다. 명령이 실패했다고 보안 설정을 전역으로 느슨하게 바꾸는 것은 올바른 첫 대응이 아니다.

프로파일링 권한은 운영 정책으로 승인받아야 한다. 개발 격리 환경에서 먼저 도구를 검증하고, 운영에서는 대상 PID, 수집 시간, 빈도, 저장 위치, 보관 기간을 정한다. 스택·프로세스 경로·주소가 내부 정보를 포함할 수 있고, 다른 종류의 추적은 인자나 데이터까지 노출할 수 있으므로 결과물도 제한적으로 공유한다.

호출 횟수를 세는 도구와 시간 비율을 추정하는 도구도 구분한다. 함수가 백만 번 호출되었어도 매우 짧으면 총 비용은 작을 수 있다. 반대로 몇 번 호출되지 않는 큰 작업이 긴 정지를 만들 수 있다. “가장 자주 호출되는 함수가 가장 느린 함수”라는 가정은 성립하지 않는다.

## 5. 플레임 그래프는 시간 순서 그래프가 아니다

플레임 그래프는 수집된 호출 스택을 합쳐 시각화한 그림이다. 보통 아래가 호출자, 위가 호출된 함수다. 사각형의 너비는 해당 스택이 차지하는 표본 수나 집계 가중치를 나타낸다. x축의 왼쪽에서 오른쪽으로 시간이 흐르는 것으로 읽으면 안 된다. 도구에 따라 시간 순서형 flame chart도 있지만 일반적인 flame graph와 구분해야 한다.

색은 대개 함수 구분을 돕기 위한 것이며 “빨간색이 가장 느리다”는 규칙이 아니다. 높은 탑은 호출 깊이가 깊다는 뜻이지 반드시 비용이 크다는 뜻이 아니다. 가장 넓은 구간의 호출 경로를 찾아 어떤 작업에서 비용이 발생했는지 해석한다.

```text
잘못된 해석: 오른쪽의 빨간 탑이 마지막에 발생한 긴 장애다.
올바른 질문: 넓은 스택이 어떤 요청 경로에서 반복되었고,
             같은 조건의 비교 실험에서 그 비중과 총 CPU가 줄었는가?
```

프로파일 A에서 함수 X가 30%, B에서 20%가 되었다고 최적화가 성공했다고 단정할 수도 없다. 전체 CPU 시간이 두 배가 되었다면 X의 절대 비용은 오히려 늘었을 수 있다. 비율과 함께 처리량, 요청당 CPU 시간, 지연 분포를 비교해야 한다.

## 6. 안전한 로컬 실습: 작은 부하와 짧은 수집

아래 절차는 Linux 개발 머신의 **예상 관찰 실습**이다. 실제 측정 결과를 제시하는 것이 아니다. Redis와 perf, redis-benchmark가 설치되어 있고 현재 사용자에게 자기 프로세스의 프로파일 권한이 있다고 가정한다. 운영 PID를 선택하지 않는다.

```bash
umask 077
LAB=$(mktemp -d)
redis-server --bind 127.0.0.1 --port 16379 --dir "$LAB" \
  --save '' --appendonly no >"$LAB/redis.log" 2>&1 &
REDIS_PID=$!
printf '대상 Redis PID=%s, 자료 경로=%s\n' "$REDIS_PID" "$LAB"
```

먼저 프로세스가 정상 시작했고 포트가 그 프로세스의 것인지 확인한다. 기존 서버가 같은 포트를 사용하면 시작한 프로세스가 종료될 수 있다. `$!`는 바로 앞에서 시작한 백그라운드 프로세스의 PID이므로, 다음 단계 전에 실행 파일과 로그를 확인해야 한다.

```bash
ps -p "$REDIS_PID" -o pid,comm,args
redis-cli -h 127.0.0.1 -p 16379 PING
```

별도 터미널에서 작은 실습 부하를 보낸다.

```bash
redis-benchmark -h 127.0.0.1 -p 16379 \
  -t set,get -n 200000 -c 8 -d 128 -r 10000 -q
```

처리 속도에 따라 부하가 금방 끝날 수 있다. 수집 시간과 부하 시간이 겹치는지 확인하고, 부족하면 실습 머신의 자원 여유 안에서 요청 수를 조절한다. 무한 반복이나 매우 큰 값을 사용하지 않는다. benchmark는 인증과 TLS, 실제 키 분포를 생략한 단순 부하이므로 운영 처리량 예측값으로 사용하지 않는다.

대상 PID를 재확인한 뒤 짧게 수집한다.

```bash
perf record -F 99 -g -p "$REDIS_PID" \
  -o "$LAB/redis.perf.data" -- sleep 10
perf report -i "$LAB/redis.perf.data"
```

기대하는 것은 특정 성능 수치가 아니라 “명령 처리·메모리·네트워크 등 어떤 함수 경로가 표본에 나타나는가”다. `[unknown]`이 많으면 심볼과 스택 추적 조건을 확인한다. 권한 오류가 나면 이 실습은 그 지점에서 멈추고 허용된 환경을 준비한다. 전역 커널 보안 설정을 임의로 변경하지 않는다.

수집 후 실습 프로세스만 종료한다.

```bash
kill -TERM "$REDIS_PID"
wait "$REDIS_PID"
```

`wait`는 같은 셸에서 시작한 자식 프로세스에 적용한다. 종료 로그를 확인하고 필요한 보고서를 정리한 뒤 임시 디렉터리를 삭제한다. `pgrep redis-server` 결과 전체에 시그널을 보내는 식으로 다른 인스턴스를 건드리지 않는다.

## 7. 두 번째 실험: 값 크기를 바꾸면 무엇이 달라질까?

첫 실험은 작은 값이었다. 다음 실험에서는 요청 수와 동시성 조건을 기록하고 값 크기를 조금 키운다. 예를 들어 128바이트와 4KiB를 비교할 수 있다. 단, 요청 수가 같으면 총 전송 바이트는 크게 달라진다. “SET/GET 횟수”만 같다고 같은 부하가 아니다.

가설은 다음처럼 구체적으로 쓴다.

> 값이 커지면 명령 파싱·키 조회의 고정 비용보다 메모리 복사와 전송 비용의 비중이 커질 수 있다. CPU만이 아니라 초당 바이트와 클라이언트 처리 비용도 함께 증가할 것이다.

관찰은 가설과 다를 수 있다. 네트워크가 먼저 포화되거나 클라이언트가 부하를 충분히 만들지 못하면 서버 CPU는 오히려 덜 바쁠 수 있다. 이 경우 실험 실패가 아니라 병목 위치가 바뀐 증거다. 프로파일의 모양만 비교하지 말고 아래 표를 채운다.

| 조건 | 작은 값 | 큰 값 |
|---|---|---|
| 서버 버전·빌드 | 기록 | 동일 여부 |
| 요청 수·동시 연결 수 | 기록 | 동일 여부 |
| 값 크기·키 분포 | 기록 | 변경 내용 |
| 서버 CPU 초 | 측정 | 측정 |
| 처리량 | 측정 | 측정 |
| p50/p95/p99 지연 | 측정 | 측정 |
| 전송 바이트 | 측정 | 측정 |
| 클라이언트 CPU | 측정 | 측정 |
| 주요 스택 | 관찰 | 관찰 |

p99는 요청 100개 중 대략 99개가 그 값 이하였다는 지연 분포 지표다. 표본 수가 적거나 요청 발생 방식이 다르면 비교가 불안정하다. 평균 하나로 긴 꼬리 지연을 숨기지 않는다.

## 8. Java/Spring에서 서버 프로파일과 연결하기

서비스에서 Redis 호출이 느리다고 서버부터 재설정하지 않는다. Java에서 다음 구간을 분리한다.

```text
요청 수신
  → 업무 로직
  → 키/값 직렬화
  → 연결 또는 비동기 큐 대기
  → Redis 왕복
  → 응답 역직렬화
  → 후속 업무 로직
```

```java
long started = System.nanoTime();
try {
    return redis.opsForValue().get(key);
} finally {
    long elapsedNanos = System.nanoTime() - started;
    // 예: 메트릭 시스템에 latency를 기록한다.
    // 실제 key, 값, 비밀번호는 태그나 로그로 넣지 않는다.
    redisReadTimer.record(elapsedNanos, java.util.concurrent.TimeUnit.NANOSECONDS);
}
```

이 시간은 서버의 명령 실행 시간만이 아니라 클라이언트 측 호출 전체를 포함한다. 서버 SLOWLOG가 짧은데 이 시간이 길다면 네트워크, 클라이언트 스레드, 직렬화, 큐 대기를 살펴본다. 키 전체를 메트릭 태그로 넣으면 고유 값이 너무 많아지는 high cardinality 문제와 데이터 노출이 생길 수 있다. 명령 종류·서비스 역할처럼 제한된 태그를 사용한다.

JVM에서는 GC, 즉 쓰지 않는 객체를 정리하는 작업이 지연에 영향을 줄 수 있다. 큰 Redis 응답을 역직렬화해 수많은 객체를 만들면 Redis 서버가 빨라도 애플리케이션이 느릴 수 있다. 서버 perf와 Java Flight Recorder 같은 JVM 관찰 자료의 시간대를 맞추면 책임 구간을 좁힐 수 있다. Java 코드의 동기 호출을 Netty 이벤트 루프 안에서 블로킹하는 실수도 확인한다.

## 9. 흔한 스택을 운영 가설로 바꾸기

### 9.1 메모리 복사가 넓게 보인다

큰 값과 큰 응답, 파이프라인 배치 크기, 직렬화 결과를 확인한다. 압축이 도움이 될 수도 있지만 압축 자체가 CPU를 사용하고 작은 값에는 이득이 없을 수 있다. “memcpy를 없애자”보다 필요한 데이터 양을 줄일 수 있는지부터 질문한다.

### 9.2 암호화 함수가 넓게 보인다

TLS가 실제 CPU 비용을 차지한다는 단서다. 연결 재사용, 핸드셰이크 빈도, 서버·클라이언트 CPU와 암호화 라이브러리 조건을 확인한다. 무조건 TLS를 끄는 것이 아니라 안전성을 유지하면서 요청당 비용을 줄일 방법을 비교한다.

### 9.3 메모리 해제 함수가 넓게 보인다

큰 자료구조 삭제와 만료 작업을 확인한다. 비동기 해제 옵션이나 UNLINK가 적절할 수 있지만 모든 삭제 비용이 사라지는 것은 아니다. 백그라운드 해제 큐와 메모리 회수 지연, CPU 이동을 함께 관찰한다. 비용을 다른 스레드로 옮긴 것과 총 비용을 줄인 것은 다르다.

### 9.4 키 조회 경로가 넓게 보인다

조회 자체가 많은 워크로드에서는 자연스러운 결과일 수 있다. 넓게 보인다고 버그는 아니다. 요청 수를 줄일 수 있는 캐싱, 적절한 배치, 자료구조 선택을 검토하되 데이터 일관성과 지연 요구를 함께 고려한다. 측정에서 흔한 함수가 애플리케이션 설계 변경의 힌트를 주는 것이다.

## 10. 최적화 결과를 판정하는 방법

최적화 전후에 같은 조건을 만들고, 한 번에 하나의 변수를 바꾸고, 여러 번 반복한다. warm-up, 즉 코드·메모리·연결이 초기 상태에서 안정 상태로 가는 시간을 분리한다. 실험 중 다른 작업이나 백그라운드 저장이 겹쳤는지도 기록한다.

개선 판정은 “그래프가 예쁘다”가 아니라 서비스 목표와 연결한다. 처리량을 늘리면서 p99가 악화되었다면 목적에 따라 실패일 수 있다. CPU가 줄었지만 메모리 사용이 크게 늘면 비용과 장애 위험을 다시 계산해야 한다. 최대 처리량보다 목표 부하에서 지연 예산을 지키는지가 더 중요한 서비스도 많다.

프로파일링 자체의 오버헤드도 확인한다. 낮은 빈도의 짧은 수집으로 시작해 자료가 충분한지 보고 조절한다. 높은 빈도가 항상 더 좋은 답을 주는 것은 아니다. 수집 도구 때문에 스케줄링과 캐시 상태가 바뀌면 측정 대상도 달라진다.

### 하드웨어 카운터는 마지막 판결문이 아니다

CPU는 명령어 수, 사이클 수, 캐시 미스 같은 하드웨어 이벤트를 셀 수 있다. IPC는 사이클당 실행한 명령어 수라는 비율이다. 같은 프로그램에서 메모리 대기가 늘면 IPC가 달라질 수 있지만 높은 IPC가 곧 업무 처리량이 높다는 뜻은 아니다. 불필요한 계산을 빠르게 많이 수행하는 프로그램도 높은 값을 보일 수 있다.

CPU 모델마다 지원 이벤트 이름과 의미가 다르고, 동시에 셀 수 있는 이벤트 수에도 제한이 있다. 도구가 이벤트를 번갈아 측정하는 multiplexing을 사용했다면 실제 측정 비율과 추정값을 확인한다. 오래된 문서의 특정 제조사 이벤트 목록을 다른 서버에 복사해서 오류가 나거나 의미가 달라지는 경우가 있다.

따라서 하드웨어 카운터는 함수 프로파일과 업무 지표를 보완하는 근거로 사용한다. “캐시 미스가 높으므로 해시 테이블을 바꾼다”보다, 동일 요청에서 어떤 메모리 접근 패턴이 발생하고 변경 후 요청당 비용이 감소했는지 검증한다. 성능 진단은 이름이 어려운 지표를 많이 모으는 대회가 아니라 가설을 반증할 수 있는 증거를 모으는 과정이다.

## 11. 면접 질문과 상세 답변

<details><summary>Q1. Redis가 느린데 CPU가 낮으면 perf부터 보면 되나요?</summary>

볼 수는 있지만 on-CPU 프로파일만으로 대기 원인을 설명하기는 어렵다. 네트워크 RTT, 클라이언트 큐, 디스크, cgroup 제한, 스케줄링 지연을 먼저 함께 확인한다. CPU를 쓰지 않는 시간이 긴 문제에서 함수 실행 비율만 보면 잘못된 최적화 대상을 고를 수 있다.

문제를 “서버 계산이 느림”으로 먼저 단정하지 않고 전체 요청 경로를 나누어 측정한다. 서버 SLOWLOG와 애플리케이션 지연의 차이는 어느 구간을 더 살펴볼지 알려 주는 좋은 단서다.

</details>

<details><summary>Q2. 호스트 CPU 15%인데 Redis가 CPU 병목일 수 있나요?</summary>

가능하다. 많은 코어의 평균이 낮아도 주요 명령 실행 스레드 하나가 포화될 수 있다. 프로세스·스레드별 사용률과 도구의 백분율 기준을 확인해야 한다. 컨테이너 CPU quota와 throttling도 호스트 평균으로는 보이지 않을 수 있다.

Redis의 I/O 스레드나 백그라운드 스레드가 있다는 사실이 모든 명령의 병렬 실행을 뜻하지 않는다. 직렬 구간의 처리 한계와 전체 프로세스의 자원 사용을 구분하는 것이 중요하다.

</details>

<details><summary>Q3. 플레임 그래프에서 너비와 높이는 무엇인가요?</summary>

일반적인 샘플링 플레임 그래프의 너비는 해당 스택에 집계된 표본의 비중이고, 높이는 호출 깊이다. x축은 보통 시간 순서가 아니다. 색도 일반적으로 비용의 절대 등급을 나타내지 않는다.

따라서 넓은 구간의 호출 경로를 보고 왜 그 작업이 반복되는지 조사한다. 높은 탑이나 붉은색만 보고 병목이라고 판단하지 않는다. 시간 순서가 필요한 경우에는 타임라인 형태의 다른 시각화가 필요하다.

</details>

<details><summary>Q4. self와 inclusive 비용을 구분해야 하는 이유는 무엇인가요?</summary>

상위 함수의 inclusive 비용에는 그 함수가 부른 하위 함수의 비용이 포함된다. 명령 처리 함수가 크게 보여도 실제 계산은 암호화나 메모리 복사에서 일어날 수 있다. self 비용은 함수 자체에서 소비한 부분을 보는 데 도움이 된다.

최적화할 때는 넓은 상위 함수 이름만 보는 것이 아니라 하위 스택으로 내려가 실제 작업을 찾아야 한다. 그렇지 않으면 거의 비용이 없는 분기 코드를 바꾸며 중요한 데이터 복사량은 그대로 두게 된다.

</details>

<details><summary>Q5. 함수 호출 횟수가 가장 많으면 그 함수가 병목인가요?</summary>

반드시 그렇지 않다. 총 비용은 호출 횟수와 한 번의 비용 모두에 영향을 받는다. 매우 짧은 함수가 자주 호출되는 것보다 드문 큰 자료구조 처리 한 번이 더 긴 지연을 만들 수 있다. 호출 횟수 추적과 CPU 샘플링은 서로 다른 질문에 답한다.

빈도가 문제인지 한 번의 작업 크기가 문제인지 구분하고, 요청 분포와 지연 꼬리도 함께 본다. 비용을 줄이는 방법도 호출을 줄일지, 각 호출을 가볍게 할지에 따라 달라진다.

</details>

<details><summary>Q6. 프로파일에서 unknown이 많으면 어떻게 하나요?</summary>

정확한 실행 바이너리와 대응되는 심볼이 있는지, 프레임 포인터 또는 DWARF 언와인딩이 가능한지 확인한다. 컨테이너 안의 경로와 호스트의 심볼 경로 차이도 원인이 될 수 있다. 자료 수집 권한과 유실 여부도 함께 점검한다.

다른 빌드의 심볼을 억지로 맞추면 잘못된 함수 이름으로 해석될 수 있다. 성능이 다른 디버그 빌드로 교체했다면 그 차이도 명시한다. 측정의 신뢰성을 확보한 뒤 최적화 결론을 내려야 한다.

</details>

<details><summary>Q7. 어떤 함수의 비중이 30%에서 20%로 줄면 성공인가요?</summary>

비율만으로는 판단할 수 없다. 전체 CPU 시간이 커졌다면 절대 비용은 늘었을 수 있고, 처리량이 줄어 같은 작업을 덜 했을 수도 있다. 요청당 CPU, 총 처리량, 지연 분포를 같은 조건에서 비교해야 한다.

최적화의 성공 기준은 서비스 목표다. p99 지연 예산을 지키는 것이 목표라면 평균 CPU 감소만으로 충분하지 않다. 다른 자원 비용과 오류율도 함께 확인한다.

</details>

<details><summary>Q8. Java 애플리케이션 지연과 Redis SLOWLOG가 다른 이유는 무엇인가요?</summary>

측정 범위가 다르다. 애플리케이션 호출 시간에는 직렬화, 연결·큐 대기, 네트워크, 응답 처리 등이 포함된다. SLOWLOG의 명령 실행 시간은 그 전체와 같지 않다. Redis 서버가 짧게 실행해도 JVM GC나 큰 응답 역직렬화 때문에 호출 시간이 길 수 있다.

서버와 클라이언트의 시간대를 맞추고 각 구간을 계측한다. 키나 값을 메트릭 태그에 넣는 대신 제한된 명령·서비스 태그를 사용해 정보 유출과 과도한 메트릭 개수를 피한다.

</details>
