실습을 먼저 따라 하려면 아래의 **실습 공통 토대**에서 격리된 환경을 준비하고 정상 상태를 확인한 뒤, 이 장의 개별 실험으로 돌아온다. 코드와 출력 설명은 별도 언급이 없는 한 실행 결과가 아니라 예제와 예상 관찰이다.



## 1. 복제와 샤딩을 다른 축으로 그린다

하나의 물류센터가 모든 송장을 보관하면 특정 시간에 조회가 몰리거나 메모리가 부족해질 수 있다. 같은 장부의 복사본을 만드는 복제는 장애 대비와 일부 읽기 분산에 도움이 되지만 원본 데이터의 저장 범위를 나누지는 않는다. **샤딩**은 전체 키 공간을 여러 primary에 나누어 저장하는 방식이다. Redis Cluster는 샤딩과 각 shard의 복제를 함께 제공한다. Sentinel은 비샤딩 복제 그룹의 primary 교체를 돕는 별도 구조이며 Cluster를 운용하기 위해 Sentinel을 덧붙이는 구조가 아니다.

물류 비유로 슬롯은 우편 분류 구역 번호, primary는 그 구역을 담당하는 센터, replica는 해당 센터 장부의 대기 복사본이다. 센터를 추가한다고 구역 번호 체계 자체를 새로 만들 필요는 없다. 기존 구역 일부의 담당 센터를 바꾸면 된다. 다만 슬롯은 실제 지리나 고객 규모를 이해하지 못한다. 같은 슬롯의 어떤 키 하나가 매우 크거나 뜨거워도 그 업무를 자동으로 여러 primary에 쪼개 주지 않는다.

## 2. 16,384 슬롯은 서버 수가 아니다

Redis Cluster의 키 공간은 0부터 16383까지의 16,384 슬롯으로 나뉜다. 기본 계산은 `CRC16(key) mod 16384`다. 안정 상태에서 각 슬롯은 하나의 primary가 담당하며 그 primary의 replica들이 해당 데이터를 복제한다. 세 primary라면 슬롯을 대략 나누어 맡지만, 범위가 정확히 같아야만 정상인 것은 아니다. 중요한 것은 필요한 슬롯이 빠짐없이 올바른 소유자에게 할당되는지와 부하가 적절한지다.

슬롯이 균등해도 메모리와 CPU는 균등하지 않을 수 있다. 1KB 문자열 수천 개와 수백 MB의 대형 자료구조 하나는 비용이 다르다. 모든 배송 조회가 특정 대형 고객의 한 키에 몰리면 그 키를 담당한 primary가 병목이 된다. 노드를 늘리면 모든 요청이 선형으로 빨라진다는 보장은 없다. 키 크기, 요청 빈도, 명령 복잡도, 네트워크 대역폭, 복제 비용을 함께 측정한다.

## 3. 클라이언트가 분산 경로를 이해해야 한다

Cluster 노드는 일반적으로 잘못 도착한 요청을 대신 전달하는 프록시가 아니다. 클라이언트에 올바른 노드로 가라는 `MOVED` 또는 이동 중 임시 경로를 알리는 `ASK` 응답을 보낸다. Cluster 지원 클라이언트는 슬롯 맵을 보관해 평소에는 곧바로 해당 primary로 요청하고, 토폴로지 변경 때 정보를 갱신한다. 단일 Redis용 커넥션에 서버 주소 하나만 주고 리다이렉션을 전혀 처리하지 않으면 정상적인 Cluster도 오류처럼 보인다.

노드에는 클라이언트 명령용 포트와 노드 사이의 cluster bus 포트가 있다. 기본적으로 bus 포트는 데이터 포트에 10000을 더하지만 설정으로 달라질 수 있다. 클라이언트는 bus에 일반 명령을 보내지 않는다. 노드 사이에서는 장애 탐지와 구성 전파뿐 아니라 마이그레이션에 필요한 데이터 포트 접근도 필요하다. 방화벽 표에는 누가 어느 포트로 접속하는지 방향까지 적는다. 외부에서 seed 하나만 접속 가능하고 리다이렉션된 주소는 접근 불가능한 배치는 실패한다.

## 4. 다중 키 작업은 같은 슬롯 안에서 설계한다

`shipment:{S100}:status`와 `shipment:{S100}:events`는 해시 태그 `S100`을 공유한다. 그러면 키 이름 전체 대신 태그로 슬롯을 계산하므로 같은 슬롯에 모인다. 같은 shipment의 관련 키를 함께 변경해야 한다면 유용하다. 그러나 모든 키에 `{logistics}`를 붙이면 사실상 한 슬롯으로 몰려 샤딩의 이점이 사라진다. 원자적 변경이 꼭 필요한 가장 작은 업무 단위를 선택한다.

같은 슬롯이라는 조건은 다중 키 명령·트랜잭션·스크립트를 그 노드에서 수행할 수 있도록 하는 배치 조건이다. 그것만으로 오류 발생 시 이전 변경이 자동 롤백되는 것은 아니다. Redis 트랜잭션과 Lua 스크립트는 명령 실행의 원자적 구간을 제공하지만, 실행 도중 발생한 오류를 SQL 트랜잭션처럼 일반적으로 되돌리지 않는다. 검증을 먼저 수행하고 변경을 뒤에 배치해야 한다. cross-slot의 여러 주문을 한 번에 수정하는 요구라면 업무 트랜잭션 경계를 원장에 두거나 보상 가능한 절차로 나누는 설계가 필요하다.

## 5. 가용성은 실패한 노드 수만으로 계산되지 않는다

세 primary A·B·C와 각각의 replica A1·B1·C1이 있다고 하자. A만 멈추고 A1이 살아 있으며 충분한 primary들이 서로 통신할 수 있으면 A1의 승격으로 복구할 수 있다. A와 A1이 함께 사라지면 그 shard의 데이터를 맡을 후보가 없어진다. 총 여섯 개 중 네 개가 살아 있다는 숫자만으로 서비스가 가능하다고 결론 낼 수 없다. 어떤 역할과 데이터 범위가 남았는지가 중요하다.

`cluster-require-full-coverage`는 슬롯 커버리지 상실이 전체 요청 처리에 어떤 영향을 주는지와 관계가 있다. 이를 완화하는 설정이 손실된 슬롯의 데이터를 재생성하는 것은 아니다. 또한 다수 primary와의 통신 조건 같은 다른 가용성 조건도 남는다. 장애 때 읽기 허용 관련 옵션도 버전에 따라 존재하므로 “어떤 장애에도 읽기는 된다”는 식의 약속을 하지 않는다. 서비스가 부분 데이터를 안전하게 다룰 수 있는지 먼저 결정한 뒤 설정을 검토한다.

## 6. 승인된 쓰기도 유실될 수 있는 타임라인

클라이언트가 primary B에 출고 상태를 쓰고 성공 응답을 받았다. B가 그 변경을 B1에 전달하기 전에 B가 사라지면, B1이 승격되어도 그 변경은 없다. 이것이 비동기 복제의 유실 창이다. 평상시 유실 창이 짧아 실습에서 관찰하기 어려워도 보장이 강화되는 것은 아니다. 소수 네트워크 분할에서는 이전 primary가 쓰기 거부 상태에 들어가기 전까지 받아들인 변경이 새 구성에 남지 않을 수 있다.

Cluster는 다수 primary와 통신하지 못하는 쪽에서 계속 무기한 쓰기를 받는 모델을 목표로 하지 않는다. `cluster-node-timeout`과 장애 탐지·선출 절차가 진행되며 쓰기 거부와 역할 변경이 일어난다. 그러나 이 값을 “유실 데이터가 정확히 몇 초 이하다”는 계약처럼 쓰면 안 된다. 이벤트 순서·복제 지연·재연결·후보 상태를 포함한 전체 장애 모델이 필요하다.

## 실습 공통 토대: 여섯 노드의 격리된 작은 Cluster

이 절은 13~16장을 독립적으로 읽는 독자를 위한 실습 토대다. 아래 명령은 교재 작성 중 실제 실행한 결과가 아니며 이후 설명은 예상 관찰이다. 이미 사용 중인 포트와 충돌하지 않는 로컬 일회용 환경에서만 수행한다. 동일 호스트의 여섯 프로세스는 클러스터 프로토콜 학습에는 도움이 되지만 호스트 장애를 견디는 배치가 아니다. 운영에서는 primary와 그 replica를 서로 다른 장애 도메인에 배치하고, 인증·TLS·방화벽·백업·여유 메모리·복제 지연 정책을 별도로 설계해야 한다.

```bash
redis-server --version
redis-cli --version
LAB=$(mktemp -d /tmp/redis-cluster-study.XXXXXX)
printf '%s\n' "$LAB"
for p in 7000 7001 7002 7003 7004 7005; do
  mkdir -p "$LAB/$p"
  cat > "$LAB/$p/redis.conf" <<EOF
port $p
bind 127.0.0.1
protected-mode yes
dir $LAB/$p
pidfile $LAB/$p/redis.pid
logfile $LAB/$p/redis.log
daemonize yes
cluster-enabled yes
cluster-config-file nodes.conf
cluster-node-timeout 5000
save ""
appendonly no
EOF
  redis-server "$LAB/$p/redis.conf"
done
redis-cli --cluster create   127.0.0.1:7000 127.0.0.1:7001 127.0.0.1:7002   127.0.0.1:7003 127.0.0.1:7004 127.0.0.1:7005   --cluster-replicas 1
```

생성 도구가 제시하는 primary/replica 관계와 슬롯 범위를 읽고, 오직 이번에 만든 빈 노드 여섯 개가 맞을 때만 확인 질문에 동의한다. 포트 순서만 보고 특정 replica의 부모를 단정하지 않는다. 도구가 실제 제안하고 생성한 관계를 기록한다. 데이터 포트 7000~7005 외에 기본 cluster bus 포트 17000~17005도 노드 사이에서 필요하다. loopback 실습에서는 동일 호스트로 접근하지만 컨테이너나 VM을 섞으면 광고한 주소가 각 클라이언트와 다른 노드에서 실제로 도달 가능한지 확인해야 한다.

`nodes.conf`는 사용자가 수동 편집하는 일반 설정 템플릿이 아니라 Redis가 자신의 노드 ID, 다른 노드, 슬롯 배치 같은 상태를 기록하는 파일이다. 이 예제는 각 프로세스의 `dir`가 다르므로 파일명이 같아도 서로 다른 파일을 사용한다. 여러 노드가 하나의 `nodes.conf`를 공유하게 해서는 안 된다. `save ""`와 `appendonly no`는 실습용으로 영속성을 끈 설정이므로 재시작 복구 실험이나 운영 내구성의 근거로 사용할 수 없다. 재시작 후 데이터가 보이지 않는 것을 Cluster의 슬롯 계산 오류로 오인하지 않는다.

### 최초 정상 상태를 확인하는 네 가지 관점

```bash
redis-cli -p 7000 CLUSTER INFO
redis-cli -p 7000 CLUSTER NODES
redis-cli --cluster check 127.0.0.1:7000
redis-cli -p 7000 CLUSTER KEYSLOT 'shipment:{S100}:status'
redis-cli -p 7000 CLUSTER KEYSLOT 'shipment:{S100}:events'
redis-cli -c -p 7000 SET 'shipment:{S100}:status' READY
redis-cli -c -p 7001 GET 'shipment:{S100}:status'
```

첫 관점은 **전체 상태**다. 안정 상태에서는 `cluster_state:ok`와 전체 슬롯 할당을 기대한다. 둘째는 **노드 관계**다. `CLUSTER NODES`의 node ID, 역할, replica의 부모 ID, 링크 상태, 슬롯 범위를 읽는다. 셋째는 **슬롯 일관성**이다. 검사 도구가 모든 슬롯의 커버리지와 배치를 어떻게 보고하는지 확인한다. 넷째는 **애플리케이션 경로**다. `-c`를 붙인 redis-cli가 다른 primary로의 리다이렉션을 처리하며 쓰기와 읽기를 수행하는지 본다. 노드 상태가 정상이더라도 애플리케이션의 DNS, 자격 증명, 라우팅 정보가 잘못되면 요청은 실패한다.

위 두 키는 중괄호 안의 `S100`이 같으므로 동일 슬롯이 예상된다. 어떤 숫자가 나오는지 암기하지 말고 실제 `CLUSTER KEYSLOT`으로 확인한다. 동일 슬롯이라고 두 키의 값이 반드시 같다는 의미는 아니며, 동일 primary에 있다고 반드시 동일 슬롯인 것도 아니다. 하나의 primary가 수천 슬롯을 맡을 수 있기 때문이다. 다중 키 명령의 가능 여부는 서버 주소가 아니라 슬롯 번호로 판단한다.

### 장애를 넣기 전에 작성할 기록표

| 기록 항목 | 기록하는 이유 | 해석할 때의 주의 |
|---|---|---|
| 실행 버전과 설정 파일 | 실험 재현과 버전별 차이 확인 | `latest` 태그를 버전으로 기록하지 않는다 |
| primary ID와 슬롯 범위 | 장애가 영향을 주는 데이터 범위 파악 | 포트는 역할과 함께 바뀔 수 있다 |
| replica의 부모 ID와 복제 상태 | 승격 가능성과 최신성 평가 | 링크 연결과 데이터 완전성은 다르다 |
| 요청 ID·시작·종료 시각 | 업무 성공과 서버 성공을 구분 | timeout은 미실행의 증명이 아니다 |
| 변경 전후의 노드 출력 | 역할 전환·슬롯 이전 검증 | 한 노드의 순간 관찰을 전체 진실로 취급하지 않는다 |

장애 실습에서 `DEBUG SEGFAULT`를 사용할 필요는 없다. 이 명령은 의도적으로 프로세스를 충돌시키며 운영 환경에서는 금지해야 한다. 명확히 식별한 일회용 인스턴스의 정상 종료, 또는 격리된 컨테이너의 정지부터 시작하면 된다. 정상 종료 실험은 전원 장애·커널 정지·부분 네트워크 분할과 동일하지 않다. 그 차이를 실험 보고서에 적어야 결과를 과장하지 않는다. 실제 네트워크 분할 실험은 host 방화벽을 즉흥적으로 바꾸기보다 별도의 네트워크 namespace나 전용 컨테이너 네트워크를 준비한 뒤 수행한다.

### 정리와 증거 보존

```bash
# 이번 실습에서 직접 생성했고 다른 서비스가 아닌 것을 먼저 확인한다.
for p in 7000 7001 7002 7003 7004 7005; do
  redis-cli -h 127.0.0.1 -p "$p" SHUTDOWN NOSAVE
done
# $LAB의 로그와 설정은 분석이 끝날 때까지 보존한다.
```

추가한 7006, 7007 같은 노드가 있다면 해당 실습의 정확한 목록을 별도로 종료한다. 노드 제거 명령을 실행했다고 프로세스까지 종료되는 것은 아니다. 반대로 프로세스를 종료했다고 나머지 노드들이 그 노드를 잊은 것도 아니다. **멤버십 변경**, **프로세스 생명주기**, **데이터 보존**은 서로 다른 작업이라는 점을 마지막까지 구분한다.


## 용량 설계 사례: 여섯 창고의 배송 조회를 나누기

배송 데이터 600GB가 있고 primary 세 개에 단순히 200GB씩 나누면 된다고 생각해 보자. 실제 필요 메모리에는 자료구조 오버헤드, allocator 단편화, 복제 버퍼, 클라이언트 버퍼, 영속성 작업의 여유가 들어간다. replica는 같은 shard의 데이터를 추가로 보관한다. 세 primary와 세 replica를 쓴다고 600GB를 여섯으로 나누어 한 노드당 100GB만 필요하다고 계산하면 틀린다. 역할을 먼저 그린 뒤 실제 자료형과 사용량으로 용량을 산정해야 한다.

| shard | 데이터 비중 | 요청 비중 | 위험과 대응 방향 |
|---|---:|---:|---|
| A | 33% | 10% | 메모리 중심 관찰 |
| B | 34% | 75% | 핫키·고비용 명령·클라이언트 집중 조사 |
| C | 33% | 15% | 상대적으로 여유가 있어도 B의 단일 핫키를 자동 분담하지 못함 |

이 표는 가상 workload다. 슬롯 개수와 메모리가 균등해도 요청이 균등하지 않음을 보여 준다. B의 많은 슬롯에 부하가 골고루 분산되어 있다면 일부 슬롯을 옮겨 완화할 수 있다. 반대로 한 대형 고객의 태그 하나가 대부분의 요청을 차지한다면 그 슬롯을 옮겨도 병목은 다른 노드로 이동할 뿐이다. 키 모델을 더 작은 업무 단위로 나눌 수 있는지, 읽기 캐시나 읽기 복제본을 사용할 때 오래된 값이 허용되는지 검토해야 한다.

### Spring 클라이언트의 연결 수를 계산하는 습관

애플리케이션 인스턴스가 30개이고 각 인스턴스의 Cluster 클라이언트가 여러 노드에 연결을 만든다면, 단일 Redis 때 생각한 pool 크기를 그대로 모든 노드에 적용할 경우 연결 수가 크게 늘 수 있다. 실제 연결 생성·공유 방식은 클라이언트와 버전마다 다르므로 “pool 10이니까 전체 연결 10”이라고 단정하지 않는다. 토폴로지 갱신용 연결, Pub/Sub 연결, blocking 명령용 연결이 별도일 수 있다.

Spring에서 Cluster 모드를 활성화했다고 애플리케이션의 모든 Redis 사용이 자동으로 Cluster 안전해지는 것은 아니다. 한 repository는 지원 client를 사용하지만 다른 유틸리티는 직접 host:port를 고정할 수 있고, Lua 스크립트의 키가 서로 다른 슬롯에 걸칠 수 있다. 통합 테스트에는 키 직렬화 결과, 다중 키 연산, 리다이렉션, 전환 뒤 재연결을 포함한다. 문자열 키를 예상했는데 serializer가 바이너리 prefix를 붙이면 슬롯 계산과 태그가 달라질 수 있으므로 실제 전송 바이트를 기준으로 검사한다.

### 데이터 손실 범위를 shard별로 설명한다

A primary만 실패하고 A1이 승격되었다고 하자. 비동기 복제 때문에 A의 마지막 쓰기 일부가 없을 수 있지만, 이를 곧바로 B와 C의 모든 쓰기가 같은 방식으로 유실되었다고 확대하지 않는다. 실제 영향 범위는 실패·전환한 shard와 전역 가용성 정책, 클라이언트 재시도에 따라 다르다. 클러스터 전체 요청이 잠시 실패한 현상과 실제 데이터 유실 범위는 구분해야 한다.

배송 S10의 예약 키가 A에, S20의 예약 키가 B에 있는데 애플리케이션이 두 키를 차례로 변경한다고 하자. 첫 변경은 성공하고 두 번째에서 timeout이 나면 업무는 부분 완료 상태일 수 있다. `-c`나 Cluster 라우팅은 이 부분 완료를 자동 롤백하지 않는다. 출고 배치의 최종 상태는 원장 트랜잭션에서 관리하고 Redis의 개별 조회 모델을 재생성하는 설계, 또는 명확한 보상 작업과 상태 머신을 사용하는 설계를 검토한다.

### 같은 슬롯으로 묶은 재고 예약도 조건이 있다

한 배송의 `reservation:{S10}:quantity`와 `reservation:{S10}:request-id`를 같은 슬롯에 두면 한 스크립트에서 함께 다루기 쉬워진다. 그러나 스크립트가 수량부터 감소시키고 뒤에서 자료형 오류를 만나면 이전 변경을 일반적으로 자동 롤백하지 않는다. 인자 형식, 기존 키 자료형, 유효 범위, 중복 요청 여부를 먼저 확인하고 변경을 마지막 구간에 배치한다. 외부 택배사 API 호출은 Redis 스크립트의 원자적 구간에 포함되지 않는다.

금전이나 재고에 영향을 주는 요청의 최종 멱등성 근거를 TTL이 짧은 Redis 키 하나에만 두면, 그 키가 만료되거나 전환 중 유실될 때 같은 요청이 다시 처리될 수 있다. Redis의 빠른 중복 방지 캐시와 영속 원장의 unique 제약을 함께 사용하는 등 업무 손실 기준에 맞는 계층을 둔다. “분산 락을 잡았으니 정확히 한 번”이라는 결론도 같은 이유로 별도 검증이 필요하다.

### 부분 장애 정책을 서비스 계약으로 바꾼다

일부 슬롯이 없을 때 나머지 슬롯의 조회를 계속 제공할지 전체 기능을 막을지 업무별로 정한다. 배송 조회는 존재하는 shard의 정보를 보여 주되 unavailable과 not-found를 구분할 수 있다. 반면 여러 shard의 재고 합계로 출고 여부를 판단하는 기능은 일부 결과만으로 승인을 내려서는 안 된다. `cluster-require-full-coverage`를 변경하기 전에 이런 응답 의미가 정의되어 있어야 한다. 설정은 업무 정책의 구현 수단이지 정책의 대체물이 아니다.

## 면접 질문과 깊이 있는 답변

답을 펼치기 전에 원리, 장애 반례, 운영 확인 방법의 세 순서로 말해 보자. 짧은 정의만 외우기보다 어떤 조건에서 그 설명이 깨지는지를 덧붙이는 것이 중요하다.

<details><summary>Sentinel 대신 Cluster를 쓰는 이유는 무엇인가요?</summary>

데이터를 여러 primary로 나누어 저장하는 샤딩이 필요할 때 Cluster를 검토합니다. Sentinel은 비샤딩 복제 그룹의 고가용성을 조정합니다. 둘 다 복제를 사용할 수 있지만 용량 분산과 장애 전환은 다른 요구입니다. 단순히 서버 수가 많다는 이유로 Cluster가 정답인 것은 아닙니다.

</details>

<details><summary>슬롯이 균등하면 부하도 균등한가요?</summary>

아닙니다. 슬롯마다 키 수·값 크기·조회 빈도·명령 비용이 다릅니다. 한 핫키는 기본적으로 한 primary의 처리 경로에 남습니다. 노드별 메모리와 CPU뿐 아니라 키별 접근 패턴을 분석하고 필요하면 업무 모델이나 읽기 전략을 바꿔야 합니다.

</details>

<details><summary>같은 primary의 두 키는 MGET할 수 있나요?</summary>

동일 primary라는 사실만으로 충분하지 않습니다. 서버가 여러 슬롯을 맡을 수 있으므로 두 키가 동일 슬롯인지 확인해야 합니다. Cluster의 다중 키 연산 조건은 슬롯 기준입니다. 같은 해시 태그는 같은 슬롯을 보장하는 편리한 방법이지만 태그가 너무 크면 핫스폿을 만들 수 있습니다.

</details>

<details><summary>Cluster가 CROSSSLOT 트랜잭션을 자동 분산 실행하나요?</summary>

일반적인 cross-slot 다중 키 트랜잭션을 자동으로 조정하는 구조가 아닙니다. 원자적으로 다룰 키를 같은 슬롯에 두거나 업무 경계를 원장·사가·보상 절차 등으로 재설계해야 합니다. 클라이언트가 여러 노드에 명령을 나누어 보내는 것은 전역 원자성과 다릅니다.

</details>

<details><summary>같은 슬롯 Lua는 실패하면 모두 롤백되나요?</summary>

아닙니다. 실행 중 다른 명령이 끼어들지 않는 원자성과 오류 때 이전 변경을 되돌리는 롤백은 다른 성질입니다. 실행 오류 이전의 변경이 남을 수 있으므로 필요한 자료형·인자·업무 조건을 먼저 검증하고 그 뒤 변경하도록 설계합니다.

</details>

<details><summary>여섯 노드 중 네 개가 살아 있으면 항상 가용한가요?</summary>

남은 노드의 역할과 담당 데이터가 중요합니다. 같은 shard의 primary와 유일한 replica가 함께 사라지면 해당 슬롯을 복구할 후보가 없습니다. 과반 primary 통신과 커버리지 정책도 확인해야 합니다. 단순 생존 노드 수를 데이터 가용성으로 바꿔 계산하면 안 됩니다.

</details>

<details><summary>성공 응답을 받은 쓰기도 왜 없어질 수 있나요?</summary>

primary의 적용·응답과 replica 전달 사이에는 비동기 복제 구간이 있습니다. 그 구간에 primary가 실패하고 해당 쓰기 없는 replica가 승격되면 승인된 값이 새 데이터셋에 없습니다. 한 번의 실험에서 유실이 없었다는 관찰은 모든 장애에 대한 보장이 아닙니다.

</details>

<details><summary>seed 노드 하나만 네트워크로 열어 두면 되나요?</summary>

안 됩니다. 클라이언트는 리다이렉션을 따라 실제 슬롯 담당 노드에 직접 접속해야 합니다. 여러 seed는 발견 가능성을 높이지만 모든 잠재적 담당 노드의 접근성을 대체하지 않습니다. 데이터 포트와 cluster bus 포트를 역할별로 검토해야 합니다.

</details>
