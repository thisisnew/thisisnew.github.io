## 1. 암호화된 전화의 상대가 사기꾼이라면

누군가와 암호화된 전화로 대화한다고 하자. 옆 사람이 대화를 엿듣지 못해도, 전화를 받은 사람이 내가 찾던 은행 직원인지 확인하지 않았다면 비밀번호를 안전하게 전달한 것이 아니다. 공격자와 아주 안전한 통신로를 만든 셈이다. TLS도 마찬가지다. TLS를 “데이터를 알아볼 수 없게 바꾸는 기술”로만 이해하면 인증서 검증을 끄는 위험한 해결책을 선택하기 쉽다.

Redis 통신을 보호하려면 다음 세 가지를 구분해야 한다.

- **기밀성:** 제삼자가 명령과 응답을 읽기 어렵게 한다.
- **무결성:** 전달 중 데이터가 변조되었는지 탐지한다.
- **상대 인증:** 접속한 서버가 의도한 서버인지 확인한다.

TLS는 저장된 RDB나 AOF 파일을 암호화하는 기능이 아니다. 서버 프로세스 안에서는 명령과 값이 처리되므로 메모리 덤프, 애플리케이션 로그, 백업의 접근 제어는 별도로 필요하다. “전송 중 보호”라는 경계를 정확히 기억해야 한다.

## 2. 인증서, 공개키, 개인키, CA를 한 번에 이해하기

### 2.1 인증서는 비밀 파일이 아니다

인증서는 어떤 이름에 어떤 공개키가 연결되는지와 발급자·유효 기간 같은 정보를 담고 서명된 문서다. 공개키는 공개해도 되는 키이고, 개인키는 서버만 보호해야 하는 비밀이다. 인증서 파일을 공격자가 읽었다고 곧바로 서버로 위장할 수 있는 것은 아니지만 개인키가 유출되면 훨씬 심각하다.

CA는 Certificate Authority, 즉 인증서 발급 기관이다. 클라이언트는 신뢰하는 CA 목록을 가지고 서버가 제시한 인증서의 서명 연결을 확인한다. 회사 내부 CA를 쓰면 그 CA를 클라이언트의 신뢰 저장소에 적절히 배포해야 한다. 아무 인증서나 신뢰하도록 만드는 것은 CA 배포 문제를 해결하는 것이 아니라 검증을 없애는 것이다.

### 2.2 이름 검사와 체인 검사는 별개다

“신뢰하는 CA가 발급했다”는 사실만으로 “이 서버가 내가 요청한 서버다”가 성립하지 않는다. 같은 CA가 여러 서버의 인증서를 발급할 수 있기 때문이다. 클라이언트는 접속 대상 DNS 이름이 인증서의 SAN, Subject Alternative Name에 들어 있는지도 확인해야 한다.

예를 들어 인증서가 `redis.internal.example`에 유효하다면 `10.0.1.15`라는 IP로 연결할 때는 IP SAN이 별도로 없어서 검증에 실패할 수 있다. 이때 올바른 DNS 이름으로 접속하거나 실제 접속 방식에 맞는 인증서를 발급해야지 호스트 이름 검증을 끄면 안 된다. SAN과 서버 이름 검증은 TLS 클라이언트의 동작이므로 사용 라이브러리의 옵션을 확인한다.

### 2.3 SNI는 검증과 다르다

SNI는 클라이언트가 TLS 연결 초기에 접속하려는 서버 이름을 알려 주는 기능이다. 여러 서비스를 한 주소에서 제공하는 서버가 알맞은 인증서를 선택하는 데 사용할 수 있다. **SNI를 보냈다고 호스트 이름 검증을 수행한 것은 아니다.** 어떤 CLI의 `--sni` 옵션을 보았다고 이름 검증까지 보장한다고 추정하지 않는다.

이 구분은 진단 도구에서도 중요하다. 테스트가 “암호화 연결 성공”, “인증서 체인 성공”, “이름 검증 성공” 중 무엇을 확인했는지 명시해야 한다. TLS 소켓이 열렸다는 메시지 하나로 세 가지를 모두 입증할 수 없다.

## 3. Redis의 TLS 포트와 평문 포트

Redis Open Source는 6부터 선택적으로 빌드되는 TLS 지원을 제공한다. 패키지와 컨테이너 이미지가 TLS 지원으로 빌드되었는지 확인해야 한다. 서버 설정에서 `tls-port`를 지정했다고 평문 `port`가 자동으로 꺼지는 것은 아니다. 평문 수신을 없애려면 `port 0`처럼 명시한다. [Redis TLS 공식 문서](https://redis.io/docs/latest/operate/oss_and_stack/management/security/encryption/)

```conf
bind 127.0.0.1
port 0
tls-port 16379
tls-cert-file /절대경로/lab/server.crt
tls-key-file /절대경로/lab/server.key
tls-ca-cert-file /절대경로/lab/ca.crt
```

이 설정만으로 운영 배포가 완성되지는 않는다. 인증서 체인, 개인키 권한, 클라이언트 인증 정책, ACL, 네트워크 접근 제한, 재발급 및 교체 절차가 필요하다. 위 경로는 예시이며 실제 파일을 준비한 후 사용해야 한다.

서버가 TLS를 지원하지 않는 빌드라면 설정 파싱 또는 시작 단계에서 실패할 수 있다. 서버 버전 숫자만 보고 지원된다고 추정하지 않는다. 배포 이미지의 빌드 옵션과 실제 시작 로그가 증거다. TLS 기능 추가를 위해 운영 서버에서 즉흥적으로 재컴파일하는 대신 검증된 배포 아티팩트를 준비한다.

## 4. 서버 인증, mTLS, Redis ACL은 세 개의 문이다

일반적인 서버 인증 TLS에서 클라이언트는 서버 인증서를 검증한다. mTLS, mutual TLS는 서버도 클라이언트 인증서를 검증하는 상호 인증이다. Redis의 기본 TLS 구성에서는 클라이언트 인증서가 요구되므로, 인증서 없이 연결하려 하면 Redis AUTH에 도달하기 전에 실패할 수 있다. 구성에 따라 `tls-auth-clients no`로 클라이언트 인증서 요구를 해제할 수 있지만 서버 인증 검증을 해제하라는 의미가 아니다.

mTLS 인증서는 네트워크 연결 주체를 확인하는 데 쓰이고, Redis ACL은 연결이 사용할 명령과 키를 제한한다. 일반적인 Redis Open Source 구성에서 **클라이언트 인증서의 이름이 자동으로 특정 ACL 사용자로 매핑된다고 가정하지 않는다.** ACL 인증이 필요한 구성이라면 TLS 연결 후 사용자 이름과 비밀번호 인증도 수행한다.

```text
TCP 연결
   ↓
TLS: 서버 인증서 검증, 필요하면 클라이언트 인증서 검증
   ↓
Redis AUTH: ACL 사용자 인증
   ↓
ACL: 명령·키·채널 권한 검사
   ↓
업무 명령 실행
```

한 단계의 성공은 다음 단계의 성공을 뜻하지 않는다. 인증서가 유효해도 ACL 비밀번호가 틀릴 수 있고, AUTH가 성공해도 특정 SET은 거부될 수 있다. 따라서 오류를 어느 단계에서 발생했는지 분류하는 것이 첫 진단이다.

## 5. 애플리케이션 연결만 암호화하면 충분할까?

Redis는 애플리케이션 외에도 복제, 클러스터 노드 통신, Sentinel, 운영 도구와 통신한다. “서비스에서 TLS를 켰다”는 표현은 보통 이 중 한 경로만 설명한다. 실제 연결 목록을 작성해야 한다.

| 연결 | 누가 클라이언트 역할인가? | 별도 확인 사항 |
|---|---|---|
| 앱 → Redis | Java 애플리케이션 | 신뢰 저장소, 이름 검증, ACL |
| replica → primary | replica | TLS 복제 설정, 인증서와 복제 계정 |
| 클러스터 노드 간 | 각 Redis 노드 | 클러스터 버스 TLS와 알려 주는 주소 |
| Sentinel → Redis | Sentinel | 모니터링·장애 조치 연결의 TLS |
| 앱 → Sentinel | 애플리케이션 | Sentinel 자체 연결 설정 |
| 관리자 CLI → Redis | 운영 도구 | CA, 클라이언트 인증서, 비밀 입력 |

복제의 송신 연결에는 `tls-replication yes`, 클러스터에는 `tls-cluster yes`처럼 별도 설정이 관여한다. Sentinel은 Redis 네트워킹 설정과 연동되는 부분이 있으므로 해당 버전 문서를 따라 실제 연결을 시험한다. 이 설정들이 서버 간 계정 인증이나 외부 방화벽까지 자동으로 해결하는 것은 아니다.

클러스터에서는 처음 접속한 seed 주소만 검증해서는 안 된다. MOVED나 토폴로지 조회로 전달받은 노드 주소로도 연결한다. 그 주소들이 클라이언트에서 해석 가능하고 인증서 SAN과 일치해야 한다. 초기 접속은 성공하지만 특정 슬롯 접근 때만 TLS 오류가 나는 원인이 될 수 있다.

Sentinel 환경도 마찬가지다. 최초 primary는 정상인데 승격된 replica의 인증서 이름이나 신뢰 체인이 다르면 장애 조치 시점에 실패한다. TLS 시험에 failover 경로를 포함해야 하는 이유다.

## 6. 안전한 로컬 실습: 정상 검증과 실패 검증을 함께 하기

다음은 **실행 결과가 아닌 재현 절차와 예상 관찰**이다. 개발용 Linux/macOS 환경, TLS 지원 Redis, OpenSSL 1.1.1 이상 계열을 가정한다. 임시 CA는 오직 이 실습에서만 사용하며 시스템 전체 신뢰 저장소에 설치하지 않는다. 생성한 개인키를 Git에 추가하지 않는다.

### 6.1 격리된 인증서 만들기

```bash
umask 077
LAB=$(mktemp -d)
printf '실습 경로: %s\n' "$LAB"
cd "$LAB"

openssl req -x509 -newkey rsa:2048 -nodes \
  -keyout ca.key -out ca.crt -days 2 \
  -subj '/CN=Redis Lesson CA'

openssl req -new -newkey rsa:2048 -nodes \
  -keyout server.key -out server.csr \
  -subj '/CN=localhost'

cat > server.ext <<'EXT'
basicConstraints=critical,CA:FALSE
keyUsage=critical,digitalSignature,keyEncipherment
extendedKeyUsage=serverAuth
subjectAltName=DNS:localhost,IP:127.0.0.1
EXT

openssl x509 -req -in server.csr \
  -CA ca.crt -CAkey ca.key -CAcreateserial \
  -out server.crt -days 2 -sha256 -extfile server.ext
```

`umask 077`은 이후 생성하는 파일에 다른 사용자의 접근 권한을 기본적으로 주지 않도록 한다. `-nodes`는 이 실습에서 개인키 파일 자체를 비밀번호로 암호화하지 않는 선택이다. 운영 개인키 관리 정책으로 일반화하면 안 된다. 운영에서는 비밀 마운트와 파일 권한, 키 보호 요구에 맞는 배포 방법을 사용한다.

SAN에 `localhost`와 `127.0.0.1`을 넣은 것은 두 접속 이름 모두를 실습하기 위해서다. 실제 서비스에서는 실제 접속 DNS 이름을 기준으로 발급하고, 불필요하게 넓은 이름이나 와일드카드를 넣지 않는다.

### 6.2 TLS만 받는 실습 서버 시작

```bash
cat > redis.conf <<CONF
bind 127.0.0.1
port 0
dir $LAB
tls-port 16379
tls-cert-file $LAB/server.crt
tls-key-file $LAB/server.key
tls-ca-cert-file $LAB/ca.crt
tls-auth-clients no
save ""
appendonly no
user default off
user lesson on nopass ~lesson:* -@all +ping +get +set
CONF
redis-server "$LAB/redis.conf"
```

이 실습은 서버 인증의 원리를 분리해 보기 위해 클라이언트 인증서를 요구하지 않는다. ACL 사용자도 `nopass`로 두었으므로 운영 보안 구성 예제가 아니다. 오직 루프백에서만 접근할 수 있게 유지한다. 인증서와 ACL 비밀번호를 동시에 추가하면 처음 학습하는 사람이 실패 단계를 구분하기 어려워 여기서는 범위를 나눈 것이다.

다른 터미널에서 실습 경로를 정확히 지정하고 인증서 체인과 이름을 검사한다.

```bash
openssl s_client -connect 127.0.0.1:16379 \
  -servername localhost \
  -CAfile /실습/절대경로/ca.crt \
  -verify_hostname localhost -verify_return_error </dev/null
```

예상 관찰은 인증서 검증 성공이다. 종료 코드와 출력의 검증 결과를 확인한다. 같은 명령에서 `-verify_hostname wrong.example`로 바꾸면 이름 불일치 실패가 예상된다. 서버가 실제로 그 이름을 가진 것이 아니므로 실패하는 것이 올바른 안전 동작이다. 검증 옵션의 의미는 [OpenSSL s_client 문서](https://docs.openssl.org/3.0/man1/openssl-s_client/)를 참고한다.

### 6.3 Redis 명령 계층 확인

```bash
redis-cli --tls -h localhost -p 16379 \
  --cacert /실습/절대경로/ca.crt
```

CLI 안에서 아래를 입력한다.

```text
AUTH lesson unused
PING
SET lesson:tls enabled
GET lesson:tls
```

예상값은 인증 성공, PONG, SET 성공, `enabled` 조회다. 단, 이 CLI 호출의 CA 검증만으로 모든 버전의 CLI가 호스트 이름 검증까지 수행한다고 주장하지 않는다. 위 OpenSSL 검증과 운영 Java 클라이언트의 이름 검증 테스트를 따로 둔 이유다.

평문 `redis-cli -p 16379 PING`은 정상적인 PONG을 얻지 못해야 한다. 정확한 오류 메시지는 버전에 따라 다르다. 이때 보호 기능을 끄지 말고 TLS와 평문 프로토콜이 다른 것을 확인한다. 서버 터미널에서 Ctrl-C로 종료한 뒤, 종료를 확인하고 실습 디렉터리의 인증서와 개인키를 삭제한다. 삭제 전에 경로가 실습 임시 디렉터리인지 반드시 확인한다.

## 7. Java/Spring에서 신뢰 저장소를 이해하기

Java TLS 설정에는 보통 두 종류의 저장소가 등장한다.

- **trust store:** 상대의 인증서를 검증하기 위해 신뢰할 CA를 저장한다.
- **key store:** 자기 인증서와 개인키를 저장한다. mTLS에서 클라이언트 신원을 제시할 때 필요하다.

서버 CA를 key store에 넣고 끝내거나, 클라이언트 개인키를 trust store로 생각하면 개념이 섞인다. Spring Boot와 Lettuce의 세부 설정 API는 버전별로 달라질 수 있지만 역할은 같다. `ssl.enabled=true` 하나가 사설 CA 설치, mTLS 인증서 배포, 호스트 이름 정책까지 자동으로 만들어 주는 것은 아니다.

```yaml
# Spring Boot 3 계열의 연결 설정 모양을 보여 주는 예시
spring:
  data:
    redis:
      host: redis.internal.example
      port: 6379
      username: ${REDIS_USERNAME}
      password: ${REDIS_PASSWORD}
      ssl:
        enabled: true
      connect-timeout: 2s
      timeout: 1s
```

이 설정에는 신뢰 CA를 제공하는 구성이 생략되어 있다. 조직의 JVM trust store나 해당 버전의 SSL bundle/클라이언트 SSL 옵션으로 CA를 제공해야 한다. 실제 프로젝트에서 사용하는 Spring Boot·Spring Data Redis·Lettuce 버전을 함께 고정하고 공식 설정 문서로 완성한다. 복사해서 바로 운영 적용할 수 있는 완결 설정이라고 오해하면 안 된다.

테스트에서는 성공만 확인하지 않는다. 신뢰하지 않는 CA, 만료된 인증서, 이름이 다른 인증서, mTLS에서 클라이언트 인증서 누락이 각각 실패하는지 확인한다. 인증서 오류가 날 때 `trustAll`, `disablePeerVerification` 같은 우회 옵션을 넣는 것은 장애를 해결하는 것이 아니라 공격도 허용하는 동작이다.

## 8. 인증서 교체와 성능을 운영 절차로 만들기

인증서에는 만료일이 있다. 만료 당일 알림은 이미 늦다. 발급·검증·배포·재연결에 필요한 시간보다 충분히 일찍 알리고, 서버 인증서뿐 아니라 중간 CA와 클라이언트 인증서의 만료도 추적한다. 파일 교체 후 기존 TLS 연결이 살아 있다고 새 연결도 정상이라고 단정하지 않는다.

CA를 바꾸는 경우에는 신뢰 전환 순서가 중요하다. 일반적으로 새 CA를 클라이언트가 먼저 신뢰하도록 준비하고, 서버 인증서를 교체하고, 모든 새 연결이 정상임을 확인한 후 오래된 CA를 제거하는 전환 창을 설계한다. mTLS라면 서버의 클라이언트 CA 신뢰도 함께 고려한다. 정확한 reload 지원 범위는 사용하는 Redis와 클라이언트 버전으로 확인한다.

TLS 비용은 새 연결을 만드는 핸드셰이크 비용과 지속 연결에서 데이터를 암호화하는 비용으로 나누어 생각한다. 매 요청마다 연결하면 핸드셰이크가 과도해질 수 있다. 연결 재사용, 적절한 파이프라이닝, 응답 크기 조절을 먼저 검토한다. TLS를 끄는 것을 첫 성능 해결책으로 삼지 않는다.

Redis 8.0부터 TLS에서 I/O threading을 지원한다는 버전 경계가 공식 문서에 명시되어 있다. 따라서 오래된 “TLS에서는 I/O 스레드를 사용할 수 없다”는 설명을 모든 버전에 적용하면 안 된다. 또한 I/O 스레드 지원은 모든 명령이 병렬 실행된다는 뜻이 아니다. 성능 비교는 같은 서버·클라이언트 버전, CPU, 연결 수, 값 크기, TLS 설정으로 수행해야 한다.

### 오류를 계층으로 분류하는 간단한 연습

연결 거부는 주소·포트·방화벽·프로세스 상태부터 확인한다. 신뢰할 수 없는 발급자 오류는 CA 배포와 중간 인증서 체인을 확인한다. 이름 불일치는 실제 접속 주소와 SAN을 비교한다. 클라이언트 인증서 요청 실패는 mTLS 정책과 인증서 용도를 확인한다. TLS 이후 NOAUTH나 WRONGPASS가 나타나면 Redis 사용자 인증을 조사한다.

오류 이름을 정확히 기록하면 무작정 인증서를 재발급하거나 비밀번호를 바꾸는 일을 줄일 수 있다. 반면 오류 로그에 개인키 내용이나 비밀번호를 추가하는 디버깅은 하지 않는다. 공개 가능한 인증서 메타데이터와 비밀 자료를 구분하고, 필요한 범위의 로그만 제한적으로 공유한다.

## 9. 면접 질문과 상세 답변

<details><summary>Q1. TLS를 켜면 중간자 공격이 완전히 해결되나요?</summary>

암호화만 활성화하고 상대 인증을 검증하지 않으면 충분하지 않다. 클라이언트는 신뢰 체인, 유효 기간, 접속 이름 등 서버 인증서의 유효성을 확인해야 한다. 공격자의 인증서를 무조건 신뢰하면 공격자와 암호화 연결을 만들 수 있다.

따라서 “TLS 연결 성공”과 “의도한 서버임을 확인”을 구분한다. 운영 테스트에는 잘못된 CA와 잘못된 이름을 가진 서버가 반드시 거부되는 음성 테스트를 포함한다. 안전한 실패도 기능의 일부다.

</details>

<details><summary>Q2. CA 검증과 호스트 이름 검증이 왜 둘 다 필요한가요?</summary>

CA 검증은 신뢰하는 발급자가 인증서를 승인했는지를 확인한다. 이름 검증은 그 인증서가 지금 접속하려는 대상에 발급되었는지를 확인한다. 같은 CA가 발급한 다른 서비스의 인증서를 받아들이면 대상 위장 위험이 남는다.

IP로 접속할 때 DNS SAN만 있는 인증서가 실패하는 것도 이 구분으로 설명할 수 있다. 실제 접속 이름에 맞는 인증서를 사용해야 하며, 이름 검증을 끄는 것으로 해결해서는 안 된다.

</details>

<details><summary>Q3. mTLS가 있으면 Redis AUTH와 ACL은 필요 없나요?</summary>

일반적인 Redis Open Source 구성에서는 별개의 계층이다. mTLS는 클라이언트 인증서로 연결 주체를 검증하고, AUTH는 Redis 사용자로 인증하며, ACL은 명령·키·채널 권한을 제한한다. 인증서 이름이 자동으로 ACL 사용자와 매핑된다고 가정하면 안 된다.

조직이 별도 프록시나 관리형 인증 통합을 사용한다면 그 제품의 정책을 확인해야 한다. 어느 계층이 신원 매핑을 책임지는지 명확해야 과도한 권한이나 인증 우회를 피할 수 있다.

</details>

<details><summary>Q4. tls-port를 설정하면 평문 접속이 자동으로 차단되나요?</summary>

아니다. 평문 포트와 TLS 포트는 함께 열릴 수 있다. 평문 수신을 사용하지 않으려면 port를 0으로 두는 등 명시적으로 비활성화하고 실제 수신 소켓과 접속 시험으로 확인해야 한다. 방화벽에서만 막았다고 서버 설정까지 닫힌 것은 아니다.

전환 기간에 두 포트를 잠시 사용하는 경우에도 종료 조건과 책임자를 정한다. 임시 평문 포트가 남는 것이 흔한 구성 드리프트다. 모든 클라이언트 전환 확인 후 제거한다.

</details>

<details><summary>Q5. SNI를 지정하면 호스트 이름도 검증되나요?</summary>

SNI는 서버에 원하는 이름을 알려 주는 기능이고, 호스트 이름 검증은 서버가 제시한 인증서가 그 이름에 유효한지 확인하는 기능이다. 서로 관련 있지만 동일하지 않다. 클라이언트 옵션에서 별도로 설정될 수도 있다.

CLI나 라이브러리 문서를 읽을 때 “서버 이름 전송”과 “인증서 대상 이름 검증”을 구분한다. 실제 운영 클라이언트에 잘못된 이름의 인증서를 제시했을 때 연결이 거부되는지 검증하면 오해를 줄일 수 있다.

</details>

<details><summary>Q6. TLS 적용 후 처리량이 떨어지면 무엇부터 확인하나요?</summary>

연결을 매 요청마다 만들고 있는지, 핸드셰이크가 반복되는지, 서버와 클라이언트 중 어디의 CPU가 포화되는지 확인한다. 값 크기와 네트워크 대역폭, 파이프라인 깊이도 중요하다. 암호화 비용이라고 추측만 하지 말고 프로파일과 지표로 확인한다.

버전도 중요하다. TLS와 I/O threading의 지원 범위가 바뀌었으므로 오래된 벤치마크를 그대로 적용하지 않는다. 보안 기능을 끄기 전에 연결 재사용과 워크로드 조절로 줄일 수 있는 비용을 찾는다.

</details>

<details><summary>Q7. 평상시 정상인데 failover 후 TLS 오류가 발생하는 이유는 무엇일까요?</summary>

새 primary의 주소가 인증서 SAN과 다르거나, 인증서 체인이 클라이언트 신뢰 저장소에 없거나, 해당 노드의 mTLS 정책이 다를 수 있다. Sentinel이나 클러스터가 알려 주는 주소와 인증서 이름이 일치하는지도 확인한다.

초기 seed 연결만 시험하면 이런 문제를 놓친다. 모든 장애 조치 후보와 토폴로지에서 전달되는 주소로 새 연결을 시험해야 한다. 인증서·비밀·ACL의 배포 일관성을 함께 검증하는 것이 중요하다.

</details>

<details><summary>Q8. TLS는 RDB와 AOF 파일도 보호하나요?</summary>

TLS는 통신 구간을 보호한다. 디스크에 저장된 파일, 백업 사본, 메모리 덤프, 애플리케이션 로그의 접근 제어와 암호화는 별도 문제다. TLS를 켰다고 개인정보가 모든 위치에서 암호화되었다고 설명하면 잘못이다.

데이터가 지나가는 경로와 저장되는 위치를 따로 목록화한다. 각 위치의 접근 권한, 암호화, 보존 기간, 삭제 정책을 검토해야 전체 데이터 보호 설계가 된다. 전송 보안은 그중 중요한 한 부분이다.

</details>

- [OpenSSL s_client](https://docs.openssl.org/3.0/man1/openssl-s_client/): 인증서 검증과 이름 검증 옵션. 설치된 OpenSSL 버전의 문서도 확인한다.
- [Redis 보안 모델](https://redis.io/docs/latest/operate/oss_and_stack/management/security/): TLS 외에 필요한 네트워크·접근 통제.
