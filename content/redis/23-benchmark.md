## 이 장에서 해결할 질문

어떤 글에서 “Redis는 초당 백만 요청을 처리한다”는 숫자를 보았다고 하자. 그렇다면 우리 서비스에서 초당 주문 백만 건을 받아도 될까? 아니다. 명령 하나와 주문 하나가 같은 작업인지부터 확인해야 한다. 그 숫자가 GET인지 SET인지, 작은 값인지 큰 값인지, pipeline을 썼는지, 같은 컴퓨터에서 접속했는지, 영속성은 켰는지, 실패한 요청은 얼마나 있었는지 알지 못하면 우리 서비스의 용량으로 바꿀 수 없다.

성능 수치는 제품에 붙는 영구적인 등급표가 아니다. **특정 환경에서 특정 입력과 특정 측정 방식으로 얻은 관측 결과**다. 실험 조건을 지우면 숫자는 남지만 의미는 사라진다. 이 장에서는 최고 기록을 만드는 법보다, 의사결정에 사용할 수 있는 성능 증거를 만드는 법을 배운다. 장비 구매, 연결 풀 조정, pipeline 도입, 캐시 구조 변경처럼 실제 결정을 내릴 때 중요한 것은 재현 가능한 조건과 사용자 지연이다.

제공된 공식 원문은 redis-benchmark의 사용법과 함정을 설명한다. 아래 해설은 그 내용을 바탕으로 학습용 사고 실험과 안전한 실험 계획을 더한 것이다. 본 장의 숫자 표는 모두 가상 예시이며, 이 저장소에서 실제로 Redis 처리량이나 p99를 측정했다는 의미가 아니다. 실제로 실행한 Java 실습은 기본 명령과 오류 의미 검증이고 성능 테스트가 아니다. 이 경계를 끝까지 유지하는 것이 이 장의 첫 번째 실무 원칙이다.

## 1. 고속도로 통행량과 자동차 한 대의 이동 시간

처리량을 고속도로 톨게이트를 통과하는 자동차 수에 비유해 보자. 초당 100대가 지나간다는 것은 통행량이다. 자동차 한 대가 입구에서 출구까지 2분 걸린다는 것은 지연 시간이다. 통행량이 많다고 각 자동차가 빠르게 도착한다고 보장하지 않는다. 오히려 진입 차량을 계속 늘리면 도로 안에 줄이 생겨 개별 이동 시간이 길어질 수 있다.

Redis에서도 초당 완료 명령 수와 명령 하나의 지연은 다른 지표다. 연결 수를 늘리면 동시에 진행 중인 요청이 증가하여 서버가 더 바쁘게 일할 수 있다. 어느 지점까지는 처리량이 증가하지만, 자원 한계에 가까워지면 대기열이 늘고 꼬리 지연이 악화될 수 있다. 최고 처리량만 보고 운영 부하를 그 수준에 맞추면 작은 변동에도 지연이 급격히 늘어날 수 있다.

이 비유의 한계도 있다. Redis 명령은 길이가 모두 같은 자동차가 아니다. 작은 GET, 큰 응답을 만드는 조회, 자료구조를 순회하는 명령, Lua 스크립트는 요구하는 CPU와 메모리·네트워크 비용이 다르다. 큰 화물차와 자전거를 같은 한 대로 세는 것처럼, 명령 수만 세면 서로 다른 일을 같은 단위로 취급하게 된다. 그래서 명령 혼합과 데이터 크기를 기록해야 한다.

## 2. 가장 먼저 단위를 정의한다

`ops/s`, `requests/s`, `TPS`, `QPS`를 문맥 없이 섞어 쓰지 않는다. 이 실험에서 operation이 Redis 명령 하나인지, pipeline 한 묶음인지, 사용자 업무 하나인지 명시한다. 예를 들어 주문 처리 한 번에 재고 조회, 조건 검사, 예약 기록, 세션 조회 등 여러 명령을 수행한다면 Redis 명령 처리량을 주문 TPS로 그대로 나눌 수 없다. 캐시 적중과 재시도에 따라 업무당 명령 수가 달라질 수도 있다.

가상의 예를 들자. 정상 주문 한 건에 평균 4개 Redis 명령을 보낸다고 해도 명령 처리량을 단순히 4로 나눈 수치는 매우 거친 산술 상한일 뿐이다. 모든 명령 비용이 같지 않고, DB와 외부 결제 API가 함께 작동하며, 실제 요청은 균등하게 도착하지 않기 때문이다. 재시도가 늘면 성공 주문 한 건당 명령 수가 더 많아진다. 성능 계획에서는 정상 경로와 실패·재시도 경로를 나누어야 한다.

latency 역시 정의가 필요하다. 명령을 보내기 전부터 응답을 받을 때까지인지, 큐에서 기다린 시간까지인지, pipeline 전체 완료 시간인지, 개별 응답 시간인지 구분한다. 여러 명령을 한 번에 보낸 경우 하나의 묶음 완료 시간을 각 명령의 지연처럼 해석하지 않는다. 도구의 출력 항목과 버전별 측정 방식을 확인한 뒤 보고서에 측정 경계를 적는다.

## 3. 실험 질문이 먼저이고 도구는 나중이다

좋은 벤치마크는 “얼마나 빠른가?” 대신 좁은 질문으로 시작한다. 예를 들어 “동일한 상품 조회에서 연결 수 8과 32를 비교하면 p99와 처리량이 어떻게 달라지는가?”, “평균 1KiB 값이 8KiB로 커질 때 네트워크가 먼저 한계에 도달하는가?”, “우리 업무에서 실제로 묶을 수 있는 8개 요청에 pipeline을 적용하면 종단 간 지연이 줄어드는가?”가 좋은 질문이다.

질문이 정해지면 독립 변수와 고정 조건을 나눈다. 연결 수를 바꾸는 실험이라면 Redis 버전, 서버 설정, 데이터 크기, 요청 수, 클라이언트 배치, pipeline 길이를 가능한 한 고정한다. 동시에 서버 버전도 올리고 pipeline도 늘리면 결과가 좋아져도 어느 변경이 원인인지 알기 어렵다. 여러 변수를 탐색해야 할 때도 각 실행의 조합을 표로 남겨 해석 가능성을 유지한다.

종료 조건도 질문의 일부다. 실험당 최대 시간, 총 요청 수, 최대 메모리, 허용 오류, 중단할 지연 기준을 미리 정한다. 목표 수치를 얻을 때까지 무제한으로 부하를 올리면 비교 실험이 아니라 위험한 탐색이 된다. 운영과 자원을 공유하는 환경이라면 영향 범위를 승인받아야 한다. 새로운 Redis 프로세스라고 해도 같은 호스트 CPU·디스크를 쓰면 다른 작업에 영향을 줄 수 있다.

## 4. redis-benchmark를 어떻게 읽을까

redis-benchmark는 지정한 동시 연결과 요청 수로 Redis 명령을 실행하는 도구다. 전체 기본 테스트를 한꺼번에 실행하는 대신 `-t`로 필요한 명령만 고르는 것이 질문을 좁히는 데 도움이 된다. `-n`은 총 요청 수, `-c`는 병렬 연결 수, `-d`는 값 크기, `-P`는 pipeline 길이, `-r`은 랜덤 키 공간 설정에 관련된다. 정확한 옵션과 동작은 사용하는 도구의 `--help`와 버전 출력으로 확인한다.

기본값에 기대지 않는 습관이 중요하다. 다른 사람이 결과를 재현할 때 도구 버전이나 설정이 다르면 기본값도 해석이 달라질 수 있다. 핵심 조건을 명령 줄 또는 실험 설정 파일에 명시한다. `-q`처럼 요약 출력만 보면 편하지만 지연 분포나 오류 정보가 빠질 수 있으므로 원본 출력을 함께 보존한다. 숫자 한 줄만 슬랙에 붙이는 것으로 실험 기록을 대신하지 않는다.

공식 원문의 예제 중에는 데이터를 비우는 명령이 포함되어 있지만, 이 장에서는 기존 서버를 지우는 방식을 실습 준비로 사용하지 않는다. 전용 폐기 인스턴스를 새로 만들고 다른 데이터와 연결되지 않았음을 확인한다. DB 번호를 바꾸는 것만으로는 CPU·메모리·영속성·명령 실행 자원이 분리되지 않는다. “테스트용 DB 15니까 안전하다”는 주장은 성립하지 않는다.

도구 설명과 주요 옵션의 출처는 [Redis benchmark 공식 문서](https://redis.io/docs/latest/operate/oss_and_stack/management/optimization/benchmarks/)다. 문서 속 예전 하드웨어 결과를 최신 환경의 성능 약속으로 읽지 않는다. 그 결과는 당시 버전과 조건에서의 예시이며, 우리 시스템의 성능은 별도 조건으로 검증해야 한다.

## 5. 동기 요청 하나가 낮은 처리량을 보이는 이유

클라이언트 하나가 GET을 보내고 응답을 받은 다음 다음 GET을 보내는 경우를 생각하자. 한 번의 왕복에 걸리는 시간이 크면 서버가 명령을 매우 빨리 처리해도 클라이언트는 다음 요청을 보내기 전에 기다린다. 그동안 서버는 이 클라이언트로부터 할 일을 받지 못한다. 이 실험의 낮은 초당 명령 수를 서버의 최대 성능이라고 부르면 안 된다.

단순한 사고 실험에서 한 연결이 매 요청마다 1ms를 기다리고 다른 비용이 없다고 가정하면 초당 약 1,000번의 왕복만 가능하다. 이것은 실제 Redis 측정치가 아니라 시간의 역수로 계산한 교육용 예다. 실제로는 인코딩, OS 스케줄링, 서버 처리, 응답 크기, 클라이언트 구현이 더해진다. 따라서 이 산술은 병목을 이해하는 힌트이지 용량 산정 공식이 아니다.

여러 연결을 쓰면 한 연결이 응답을 기다리는 동안 다른 연결이 일을 제공할 수 있다. pipeline은 한 연결에서 여러 요청을 응답 대기 없이 연속으로 보내 왕복 대기의 영향을 줄인다. 두 방법은 모두 동시 진행량을 늘리지만 동일한 기법은 아니다. 연결 수는 소켓과 연결 관리 자원을 늘리고, pipeline은 한 연결의 미완료 요청과 응답 버퍼를 늘린다. 목표는 무조건 크게 만드는 것이 아니라 업무 특성에 맞는 수준을 찾는 것이다.

## 6. Pipeline은 묶음 배송이지 트랜잭션이 아니다

우체국에 편지를 한 통씩 보내고 도착 확인을 기다리는 대신 여러 통을 한 번에 맡기면 왕복 횟수가 줄어든다. 이것이 pipeline의 직관이다. 하지만 편지들을 한 번에 맡겼다고 모두 하나의 원자적 업무가 되는 것은 아니다. Redis pipeline도 전송 방식의 최적화이며 MULTI/EXEC이나 Lua의 실행 의미와 구분해야 한다. 성능이 좋아졌다는 이유로 원자성이 추가되었다고 설명하면 정확성 사고로 이어진다.

pipeline 길이를 늘리면 서버와 클라이언트가 버퍼링해야 하는 데이터가 커질 수 있다. 큰 응답을 많이 묶으면 네트워크와 메모리 압력이 올라간다. 앞선 응답을 기다리는 구조에서는 묶음 안의 느린 작업이 뒤의 완료 관찰을 지연시킬 수도 있다. 따라서 pipeline 크기와 값 크기는 함께 고려해야 한다. 작은 GET 16개와 큰 결과를 반환하는 명령 16개는 같은 부하가 아니다.

업무에서 실제로 묶을 수 있는 요청인지도 중요하다. 두 번째 명령의 입력이 첫 번째 응답에 의존한다면 단순히 모든 명령을 먼저 보낼 수 없다. 벤치마크에서는 독립적인 GET을 수백 개 묶어 높은 수치를 만들 수 있어도 실제 주문 경로에서는 그 구조를 적용하지 못할 수 있다. 보고서에는 “이 pipeline 크기가 실제 서비스의 어느 구간에서 가능한가?”라는 설명을 넣는다.

공식 [pipelining 설명](https://redis.io/docs/latest/develop/using-commands/pipelining/)은 왕복 비용과 요청 묶음의 효과를 다룬다. 이 저장소의 Java 실습은 세 명령을 먼저 보내고 응답을 순서대로 읽는 동작을 실제 확인했다. 하지만 처리량 증가율이나 최적 pipeline 크기를 측정한 것은 아니다. 의미 검증과 성능 검증을 구별하는 연습으로 이 사례를 기억하자.

## 7. 데이터 크기와 키 분포가 바뀌면 실험도 바뀐다

3바이트 값을 반복 조회한 결과와 수십 KiB JSON을 조회한 결과를 같은 GET이라는 이름만으로 비교하지 않는다. 응답 크기는 전송량과 클라이언트 역직렬화 비용에 영향을 준다. 값이 커지면 서버 CPU가 여유로워도 네트워크 대역폭이나 클라이언트 CPU가 병목이 될 수 있다. 키 이름 길이, 값 크기 분포, 자료구조의 요소 수를 기록해야 한다.

한 키만 반복 접근하는 워크로드와 넓은 키 공간에 접근하는 워크로드도 다르다. 실제 서비스에서는 일부 인기 상품에 요청이 집중되는 hot-key 분포가 나타날 수 있다. 균등 랜덤만 사용하면 집중된 키의 효과를 놓친다. 반대로 단일 키만 사용하면 전체 메모리 배치와 데이터 다양성의 영향을 충분히 보지 못할 수 있다. 벤치마크를 하나로 끝내지 말고 질문에 맞는 분포를 선택한다.

GET 테스트 전에 데이터가 존재하는지도 확인한다. 없는 키에 대한 응답은 실제 값이 있는 GET과 반환량이 다르다. 모든 요청이 miss인데 캐시 적중 성능으로 보고하면 실험 계약이 깨진다. SET으로 준비한 키 범위와 GET이 선택하는 범위가 같은지 확인하고, 대표 표본의 존재·값 크기를 점검한다. 랜덤하게 N번 SET했다고 N개의 서로 다른 키가 만들어진다고 보장할 수 없다는 점도 기억한다.

TTL과 삭제 패턴도 장기 워크로드에서는 중요하다. 짧은 벤치마크는 만료, 메모리 회수, 단편화, 데이터 크기 변화가 충분히 나타나기 전에 끝날 수 있다. 그렇다고 학습 실습을 무작정 오래 돌리지는 않는다. 짧은 탐색 실험과 승인된 장시간 안정성 실험을 분리하고, 어떤 현상을 어느 실험에서 확인할 것인지 계획한다.

## 8. 내구성 조건을 같게 맞추지 않으면 공정한 비교가 아니다

메모리에 기록하고 응답한 구성과 영속성 요구를 더 강하게 둔 구성을 같은 처리량 숫자로 비교하면 기능 차이를 성능 차이로 오해할 수 있다. Redis의 RDB, AOF, fsync 정책과 복제 조건은 지연과 자원 사용에 영향을 줄 수 있다. 어떤 데이터를 잃어도 되는 캐시와 주문 원장을 같은 요구 조건으로 취급할 수 없다.

예를 들어 AOF를 끈 테스트 결과를 보고 AOF가 필요한 운영 시스템의 용량을 결정하면 안 된다. 반대로 빠른 수치를 얻기 위해 영속성을 끄고 “최적화 성공”이라고 보고하면 서비스 요구사항을 바꾼 것이다. 성능 변경 제안은 지연·처리량뿐 아니라 장애 시 손실 허용 범위와 복구 요구에 어떤 영향을 주는지도 포함해야 한다.

다른 데이터베이스와 비교할 때도 동일한 업무 의미를 맞춰야 한다. 응답을 언제 확정하는지, 오류가 어떻게 전달되는지, 트랜잭션 범위가 무엇인지, 내구성이 어느 수준인지가 다르면 단순 ops/s 비교는 제한적이다. 비교가 불가능하다는 뜻은 아니다. 비교한 기능 범위와 보장 수준의 차이를 정직하게 적어야 한다는 뜻이다.

## 9. 부하 생성기 자신도 병목이 된다

서버 CPU가 낮고 처리량이 더 이상 늘지 않는다고 해서 Redis가 비효율적이라고 바로 결론 내리지 않는다. 클라이언트 프로세스가 CPU 한 코어를 다 쓰거나, 네트워크 인터페이스가 포화되거나, TLS 처리와 응답 파싱이 병목일 수 있다. 이때 서버 사양을 올려도 결과가 거의 바뀌지 않을 수 있다. 부하 생성기의 자원 사용도 서버와 함께 수집해야 한다.

같은 컴퓨터에서 서버와 클라이언트를 실행하면 편리하지만 자원을 서로 경쟁한다. loopback 네트워크는 실제 배포의 네트워크 경로와 다르고, 부하 생성기가 서버 CPU 시간을 빼앗을 수 있다. 반대로 별도 호스트를 쓰면 실제 네트워크 지연과 대역폭이 개입한다. 어느 방식이 무조건 옳은 것이 아니라 실험 질문에 맞는 배치를 선택하고 그 한계를 써야 한다.

가상 머신과 컨테이너에서는 할당된 CPU 수뿐 아니라 제한과 스케줄링도 중요하다. 호스트 전체 CPU 사용률이 낮아도 컨테이너의 CPU quota에 걸릴 수 있다. 자원 사용률을 어느 범위에서 읽었는지 명확히 한다. CPU 코어 수를 많이 줬다고 Redis 명령 실행 경로가 그만큼 선형 확장된다고 가정하지 않는다. 현대 Redis의 여러 작업 스레드와 주요 명령 실행 특성을 구분해서 이해해야 한다.

## 10. 닫힌 부하 모델과 열린 도착 모델

응답을 받은 뒤 다음 요청을 보내는 부하 생성 방식은 시스템이 느려지면 요청을 보내는 속도도 자연스럽게 줄어든다. 손님이 한 명씩 계산을 마친 뒤 다음 손님이 입장하는 구조와 비슷하다. 이런 방식은 일정한 동시 진행량에서의 동작을 보는 데 유용하지만, 실제 외부 요청이 계속 도착하는 서비스의 대기열 폭증을 충분히 재현하지 못할 수 있다.

반면 도착률을 정해 계속 요청을 생성하는 모델에서는 처리 속도가 도착 속도를 따라가지 못하면 대기열이 늘어난다. 이때 큐의 크기와 실패 정책을 정하지 않으면 부하 생성기 자체가 메모리를 소모하거나 결과를 왜곡할 수 있다. 생성 예정 시각부터 지연을 계산하는지 실제 전송 시각부터 계산하는지도 해석에 중요하다. 전송하기 전 기다린 시간을 빼 버리면 사용자가 경험할 대기를 과소평가할 수 있다.

이 장은 redis-benchmark 하나가 모든 부하 모델을 제공한다고 주장하지 않는다. 도구마다 제공하는 부하 모델과 지연 측정 정의를 확인해야 한다. 단순 동시 연결 실험은 빠른 기준선 탐색에 적합하고, 실제 서비스의 도착 패턴·재시도·큐 정책을 검증하려면 애플리케이션 수준의 별도 실험이 필요할 수 있다. 실험 도구의 한계를 알리는 것은 결과의 가치를 낮추는 것이 아니라 적용 가능한 범위를 명확히 하는 일이다.

## 11. 가상 결과 표를 읽는 연습

아래는 **실제 실행 결과가 아닌 교육용 가상 숫자**다. 단위와 관계를 읽는 연습을 위해 구성했으며 Redis 7.2.5의 성능을 주장하지 않는다. 값 크기와 명령 혼합이 같고 오류는 별도 집계되었다고 가정한다.

| 실험 | 연결 수 | pipeline 길이 | 완료 명령/s | p99 | 실패율 |
|---|---:|---:|---:|---:|---:|
| A | 1 | 1 | 2,000 | 0.8ms | 0% |
| B | 8 | 1 | 12,000 | 1.4ms | 0% |
| C | 32 | 1 | 20,000 | 5ms | 0% |
| D | 64 | 1 | 21,000 | 18ms | 0.2% |
| E | 8 | 8 | 30,000 | 4ms | 0% |

D는 C보다 처리량이 조금 높지만 p99와 실패율이 악화되었다. 사용자 SLO가 p99 10ms라면 D를 더 좋은 구성이라고 고를 수 없다. E는 높은 처리량을 보이지만 실제 업무에서 8개 독립 명령을 묶을 수 있는지 확인해야 한다. A는 서버 한계라기보다 한 연결의 대기 구조를 반영할 수 있다. 이처럼 순위는 하나의 숫자가 아니라 목적과 제약으로 정한다.

여기서 추가로 물어야 할 질문은 “p99가 어떤 요청 단위인가?”, “실패율의 분모에 timeout이 포함되는가?”, “얼마나 오래 측정했는가?”, “반복 실행의 편차는 얼마인가?”다. 표가 깔끔하다고 실험이 충분한 것은 아니다. 이 정보가 없다면 구성 선택을 잠정 결론으로 남기고 필요한 측정을 추가한다.

## 12. 재현 가능한 실험 기록 양식

실험마다 다음 항목을 기록하면 나중에 결과를 비교하기 쉬워진다. 모든 항목을 대외 공개할 필요는 없지만 내부 증거에는 남겨야 한다. 비밀번호나 고객 데이터는 절대 포함하지 않는다. 서버 버전과 클라이언트 도구 버전은 서로 다를 수 있으므로 각각 기록한다.

```text
실험 질문:
실험 ID와 UTC 시작/종료 시각:
서버 버전 / 빌드 / allocator:
클라이언트 도구 버전 / 실행 명령:
서버와 클라이언트 배치 / 네트워크 경로:
CPU·메모리 제한 / 다른 작업 존재 여부:
영속성 / 복제 / TLS / 인증 조건:
명령 혼합 / 키 수 / 값 크기 분포 / hit 비율:
연결 수 / pipeline 길이 / 총 요청 수:
워밍업 방식 / 본 측정 구간 / 반복 횟수:
완료 수 / 오류 수 / timeout 수 / 지연 정의:
p50 / p95 / p99 / 최대값 / 처리량:
서버와 클라이언트 CPU·메모리·네트워크:
중단 조건 도달 여부 / 알려진 한계:
원본 로그 위치 / 분석 코드 버전:
```

“실험 ID”는 단순한 장식이 아니다. 다른 파일에 저장된 서버 메트릭, 클라이언트 출력, 설정 스냅샷을 연결하는 키다. 나중에 결과가 예상과 다르면 어떤 구성으로 실행했는지 되짚을 수 있어야 한다. 이름에 날짜만 넣는 대신 변수 조합과 실행 순서를 구별할 수 있게 관리한다. 테스트 간 데이터 준비 상태가 달라졌다면 그 사실도 기록한다.

## 13. 안전한 소규모 실습 계획

아래는 실행 계획 예시이며 본 장에서 수행한 성능 측정이 아니다. 먼저 전용 폐기 서버를 준비한다. localhost에만 바인딩하고 임의 포트·비밀번호·임시 데이터 디렉터리·메모리 상한을 지정한다. 기존 Redis 주소를 기본값으로 삼지 않는다. 포트가 비어 있었다는 확인만으로 인스턴스 소유권을 확정하지 말고, 자신이 만든 프로세스와 인증 설정을 확인한다.

첫 번째 실험은 작게 시작한다. 총 요청 5,000개, 연결 수 1, pipeline 1처럼 상한을 분명히 둔다. 그다음 연결 수만 바꾸어 비교한다. 별도 실험에서 pipeline 길이를 바꾼다. 무한 반복 옵션은 사용하지 않는다. 소규모 실험은 정밀한 p99 추정이나 운영 용량 인증에 부족하지만 도구 출력과 변수의 관계를 배우는 데 적합하다.

```bash
# 직접 준비한 전용 일회성 인스턴스에만 적용하는 형태 예시다.
# LAB_PORT가 비어 있으면 중단하며 기본 포트로 자동 연결하지 않는다.
: "${LAB_PORT:?전용 실습 포트를 먼저 지정하세요}"

# 인증은 사용하는 도구 버전의 지원 방식과 비밀 관리 정책을 확인한다.
# 아래 예시는 인증 인자를 생략한 명령 형태 설명이다.
redis-benchmark -h 127.0.0.1 -p "$LAB_PORT" \
  -n 5000 -c 1 -P 1 -d 128 -t set,get

redis-benchmark -h 127.0.0.1 -p "$LAB_PORT" \
  -n 5000 -c 8 -P 1 -d 128 -t set,get
```

이 명령을 복사하기 전에 대상 확인과 인증 구성을 완료해야 한다. localhost라는 사실만으로 실습 대상임이 보장되지는 않는다. 로컬 개발자가 쓰는 Redis도 있을 수 있다. 예시 명령은 키를 쓰므로 읽기 전용 진단이 아니다. 기존 DB를 선택해 실행하지 말고 새 서버에만 연결한다. 실험을 끝낸 뒤 자신의 프로세스를 종료하고 임시 파일을 지운다. 결과를 정리한다며 FLUSHALL을 호출하는 방식을 쓰지 않는다.

GET 데이터 준비 상태도 점검한다. 사용한 도구 버전에서 SET과 GET 테스트가 어떤 키를 생성하고 선택하는지 확인하며, 랜덤 키 공간을 도입하면 실제 적중률을 별도로 검증한다. 첫 실습은 작은 키 공간과 값 크기로 도구 사용법을 확인하는 단계다. 운영의 JSON 분포와 명령 혼합을 흉내 내는 단계는 다른 실험으로 분리한다.

## 14. Java로 측정할 때의 흔한 함정

Java에서 Redis 호출을 for문으로 반복하고 총 시간을 나누면 간단한 측정이 나온다. 그러나 그 숫자는 JIT 워밍업, 객체 할당, GC, 연결 생성, 인코딩, 동기 대기, 로그 출력 비용의 영향을 받는다. 이런 비용은 애플리케이션 종단 간 성능을 보는 데는 오히려 필요한 요소일 수 있다. 문제는 측정 범위를 서버 자체 성능이라고 잘못 이름 붙이는 것이다.

다음 코드는 외부 Redis 클라이언트 라이브러리를 지정하지 않는 설명용 뼈대다. `operation`에 무엇을 넣느냐에 따라 의미가 달라진다. 실제 네트워크 코드를 연결하지 않았고, 본 장의 성능 결과로 사용하지 않았다. 샘플마다 객체를 대량 생성하거나 콘솔을 출력하지 않도록 의도했지만, 정밀 벤치마크 도구를 대체하는 구현은 아니다.

```java
import java.util.Arrays;

public final class SmallMeasurement {
    @FunctionalInterface
    public interface Operation { void run() throws Exception; }

    public record Result(int completed, long elapsedNanos,
                         long p50Nanos, long p99Nanos) {}

    public static Result run(Operation operation, int count) throws Exception {
        if (count < 100 || count > 10_000) {
            throw new IllegalArgumentException("bounded sample count required");
        }
        long[] samples = new long[count];
        long totalStart = System.nanoTime();
        for (int i = 0; i < count; i++) {
            long start = System.nanoTime();
            operation.run(); // 여기서는 동기 완료까지 기다린다고 가정한다.
            samples[i] = System.nanoTime() - start;
        }
        long elapsed = System.nanoTime() - totalStart;
        Arrays.sort(samples);
        int p50 = (int) Math.ceil(count * 0.50) - 1;
        int p99 = (int) Math.ceil(count * 0.99) - 1;
        return new Result(count, elapsed, samples[p50], samples[p99]);
    }
}
```

이 예제는 예외가 나면 즉시 실패하여 성공 결과를 반환하지 않는다. 오류를 무시하고 `count` 전체를 성공 처리량의 분모에 넣는 실수를 피하기 위한 선택이다. 실제 실험에서는 성공·오류·timeout을 각각 집계하고 전체 완료의 정의를 정한다. 비동기 API를 넣으면 메서드 호출 시간이 아니라 완료 시점까지 기다리거나 completion callback에서 측정해야 한다. Future를 반환하는 시간만 재면 Redis 왕복을 거의 포함하지 않을 수 있다.

배열 정렬로 구한 분위수는 유한 표본의 간단한 추정이다. p99가 그럴듯하게 나왔다고 작은 표본에서 극단 지연을 안정적으로 파악한 것은 아니다. 또한 여기서 계산한 총 시간에는 루프와 측정 호출의 비용이 포함된다. 이 특성을 설명하지 않고 마이크로초 숫자 몇 자리까지 보고하면 정밀도와 정확도를 혼동하게 된다. 더 정교한 측정은 검증된 히스토그램과 부하 생성 도구를 검토하되, 도구가 무엇을 측정하는지 먼저 이해한다.

## 15. 워밍업과 반복 실행을 왜 구분할까

처음 몇 번의 요청에는 연결 수립, 클래스 초기화, 코드 최적화, 데이터 준비 등 정상 상태와 다른 비용이 섞일 수 있다. 지속 부하 성능이 질문이라면 워밍업 구간을 본 측정과 분리하는 것이 도움이 된다. 그러나 첫 요청 지연이 중요한 서버리스나 재연결 시나리오라면 그 비용을 버리면 안 된다. 워밍업 여부는 관례가 아니라 실험 질문으로 결정한다.

실행을 한 번만 하면 우연한 호스트 경쟁이나 백그라운드 작업의 영향을 구별하기 어렵다. 반복 실행에서 중앙 경향과 변동 폭을 보고, 이상치가 나온 실행을 이유 없이 삭제하지 않는다. 왜 달랐는지 원본 메트릭을 확인하고, 분석에서 제외했다면 근거를 남긴다. 좋은 결과만 골라 보고하면 가장 필요한 운영 변동성을 감춘다.

실험 순서도 영향을 줄 수 있다. A를 항상 먼저, B를 항상 나중에 실행하면 데이터 준비나 호스트 상태 변화가 B에 유리하거나 불리할 수 있다. 반복 순서를 바꾸거나 동일한 초기 상태를 다시 준비하여 편향을 줄인다. 그렇다고 모든 실험에서 운영체제 캐시를 강제로 지우거나 시스템 전역 설정을 바꾸는 것은 아니다. 그런 조치는 영향 범위와 목적이 명확할 때만 별도로 승인받는다.

## 16. 평균보다 꼬리를 보되 최대값만 숭배하지 않는다

평균은 전체 비용의 요약으로 유용하지만 일부 느린 요청을 가릴 수 있다. p95와 p99는 꼬리 부분을 보는 데 도움이 되며, timeout과 실패율을 함께 봐야 한다. 최대값은 가장 느린 관측 하나를 알려 주지만 표본 수와 실행 길이에 민감하다. 10초 실험의 최대값과 10시간 실험의 최대값을 같은 조건의 숫자처럼 비교하면 안 된다.

여러 인스턴스의 p99를 단순 평균하여 전체 p99라고 부르는 것도 피한다. 각 인스턴스의 요청 수와 분포가 다를 수 있기 때문이다. 가능한 경우 같은 정의의 히스토그램을 집계하고 전체 분포에서 분위수를 계산한다. 원시 표본을 모두 저장할 필요는 없지만 집계 방식과 히스토그램 버킷의 한계는 알아야 한다.

지연 개선의 성공 조건은 업무로 돌아가야 한다. 사용자가 기다릴 수 있는 시간, 실패 허용 수준, 비용 제약, 장애 시 여유를 반영하여 운영 지점을 정한다. 실험에서 최대 처리량을 찾았더라도 그 값 그대로 평상시 목표 부하로 삼지 않는다. 장애 시 트래픽 이동, 백그라운드 작업, 재시도 급증 같은 상황을 위한 여유는 별도 검증 대상으로 둔다. 특정 비율 하나를 모든 시스템에 적용하는 만능 공식은 없다.

## 17. 잘못된 보고서를 고쳐 쓰기

나쁜 문장은 “Redis는 초당 30만 건을 처리하므로 주문 30만 TPS가 가능하다”다. 명령과 업무 단위를 혼동했고 조건이 빠졌다. 더 나은 문장은 “전용 환경에서 작은 값의 GET을 지정 연결 수와 pipeline 조건으로 실행했을 때 완료 명령 처리량을 관측했다. 주문 경로, 영속성 조건, 네트워크 배치가 달라 운영 주문 용량으로 직접 환산할 수 없다”다. 숫자보다 제한을 길게 쓰는 것이 답답해 보여도 의사결정에는 더 정직하다.

또 다른 나쁜 문장은 “pipeline 적용 후 열 배 빨라졌다”다. 처리량인지 지연인지부터 불명확하다. 더 나은 문장은 “독립 요청을 묶을 수 있는 구간에서 pipeline 길이를 변경한 실험의 완료 명령/s가 증가했으며, p99와 메모리 사용도 함께 변했다. 의존적인 명령 구간에는 같은 개선을 적용할 수 없다”다. 무엇이 좋아지고 무엇이 바뀌었는지 각각 쓴다.

마지막으로 “오류는 조금 있었지만 최고 TPS는 높았다”는 문장도 수정해야 한다. 실패한 요청을 빠르게 거절하면 처리 속도가 높아 보일 수 있다. 성공 처리량과 오류 처리량을 나누고, 요구 성공률을 만족하는 범위에서 성능을 평가한다. 성능은 정확성과 가용성을 유지하면서 제공하는 능력이지 실패 응답을 많이 만드는 능력이 아니다.

## 18. 면접과 복습: 조건을 붙여 답하기

<details>
<summary>Q1. redis-benchmark의 TPS를 운영 용량으로 바로 써도 되나요?</summary>

안 됩니다. 명령 종류, 데이터 크기와 분포, 연결 수, pipeline, 네트워크, 영속성, 클라이언트 구현이 운영과 같은지 확인해야 합니다. 업무 한 건이 여러 Redis 명령과 다른 의존성을 포함한다면 단위도 다릅니다. 벤치마크는 특정 조건의 기준선을 제공하며, 운영 용량은 실제 업무 혼합과 SLO·실패율·장애 여유를 포함한 추가 검증으로 정합니다.
</details>

<details>
<summary>Q2. 단일 동기 연결에서 처리량이 낮으면 서버가 느린 것인가요?</summary>

그렇게 단정할 수 없습니다. 응답을 기다린 뒤 다음 명령을 보내는 구조에서는 네트워크 왕복과 클라이언트 대기가 처리량을 제한할 수 있습니다. 서버가 명령을 처리한 뒤 유휴 상태일 수도 있습니다. 연결 수나 pipeline을 통제하여 변화시키고 서버와 클라이언트 자원 사용을 함께 관찰해야 합니다. 단일 연결 실험은 그 애플리케이션 호출 구조의 성능으로는 의미가 있지만 서버 최대치와는 다릅니다.
</details>

<details>
<summary>Q3. Pipeline 길이를 크게 할수록 항상 좋은가요?</summary>

아닙니다. 왕복 비용을 줄일 수 있지만 미완료 요청과 응답 버퍼가 커지고, 큰 응답에서는 메모리와 네트워크 압력이 늘 수 있습니다. 업무 명령 사이에 의존성이 있으면 임의로 묶을 수도 없습니다. 실제로 가능한 묶음 크기를 기준으로 처리량뿐 아니라 꼬리 지연과 자원 사용을 비교합니다. pipeline은 원자성을 제공하는 기능이 아니라 전송 방식의 최적화라는 점도 분리해서 설명합니다.
</details>

<details>
<summary>Q4. GET 테스트 전에 왜 데이터를 확인하나요?</summary>

없는 키를 조회하면 실제 값이 있는 조회와 응답 크기가 다릅니다. 준비한 키 공간과 조회 범위가 어긋나면 의도치 않게 miss 성능을 측정할 수 있습니다. 랜덤 SET 횟수와 실제 고유 키 수가 같다고 보장할 수도 없습니다. 대표 표본과 적중률을 검증하고, 보고서에 hit와 miss의 구성 비율을 명시해야 합니다.
</details>

<details>
<summary>Q5. 서버 CPU가 낮은데 처리량이 늘지 않으면 무엇을 보나요?</summary>

부하 생성기의 CPU, 네트워크 대역폭, 클라이언트 파싱, TLS 처리, 연결 구조, 컨테이너 제한을 확인합니다. 서버의 평균 CPU만으로 개별 실행 경로의 포화를 배제할 수도 없습니다. 먼저 실제 병목 위치를 찾은 뒤 자원을 늘려야 합니다. 서버 증설은 클라이언트 병목을 해결하지 못할 수 있으며, 같은 호스트 실험이라면 둘 사이의 자원 경쟁도 검토합니다.
</details>

<details>
<summary>Q6. AOF를 끄고 얻은 좋은 결과를 왜 따로 표시해야 하나요?</summary>

영속성 조건은 서비스가 제공하는 보장의 일부이기 때문입니다. AOF가 필요한 운영과 꺼진 실험은 다른 조건의 시스템입니다. 성능이 높아졌더라도 데이터 손실과 복구 요구를 바꾸었다면 단순 최적화가 아닙니다. 비교에서는 영속성·복제·응답 확정 조건을 맞추거나 차이를 명시해야 하며, 높은 수치를 얻기 위해 요구사항을 몰래 낮추면 안 됩니다.
</details>

<details>
<summary>Q7. 평균 지연과 최대 TPS만 있으면 충분한가요?</summary>

평균은 일부 느린 요청을 가릴 수 있고 최대 TPS는 지연과 오류율이 나쁜 포화 지점에서 나온 값일 수 있습니다. p95·p99·timeout·성공률과 자원 사용을 함께 봐야 합니다. 어떤 요청이 지연 계산에 포함되는지도 중요합니다. 실패한 요청을 제외하여 성공 지연만 좋아 보이는 결과를 사용자 경험 개선으로 해석하지 않습니다.
</details>

<details>
<summary>Q8. 왜 같은 실험을 반복하고 원본 로그를 보존하나요?</summary>

호스트 경쟁, 워밍업, 백그라운드 작업, 데이터 상태가 결과를 흔들 수 있기 때문입니다. 반복 실행의 변동 폭은 운영 안정성을 판단하는 자료가 됩니다. 원본 로그와 설정을 보존하면 이상 결과의 원인을 조사하고 다른 사람이 같은 조건을 재현할 수 있습니다. 좋은 숫자만 골라 남기거나 불리한 실행을 이유 없이 제거하면 실험의 신뢰성이 사라집니다.
</details>

<details>
<summary>Q9. Java Future를 반환하는 메서드 주변에 타이머를 두면 Redis 지연인가요?</summary>

대개는 Future를 생성하고 반환하기까지의 시간일 뿐 실제 Redis 작업 완료 시간을 포함하지 않을 수 있습니다. 원하는 측정 경계가 종단 간 완료라면 completion 시점까지 측정해야 합니다. callback executor 대기나 역직렬화가 포함되는지도 확인합니다. 동기·비동기라는 API 모양만으로 단위를 정하지 말고 실제 시작과 끝 사건을 정의해야 합니다.
</details>

<details>
<summary>Q10. 실습용 DB 번호만 바꾸면 운영 서버에서 benchmark를 해도 안전한가요?</summary>

아닙니다. 논리 DB 번호는 CPU, 메모리, 네트워크, 영속성 작업을 물리적으로 분리하지 않습니다. 별도 DB의 부하도 같은 서버의 다른 요청에 영향을 줄 수 있습니다. 전용 폐기 인스턴스를 사용하고 호스트 자원 공유까지 검토해야 합니다. 쓰기 테스트의 대상과 종료 조건을 확인하지 않은 채 기존 서버에 실행하는 것은 안전한 학습 방법이 아닙니다.
</details>

## 19. 직접 설계해 보는 과제

상품 캐시 조회의 값 크기가 256바이트에서 4KiB로 늘어났다는 가상의 상황을 생각하자. 변경 전후 비교 실험을 설계하되, 연결 수와 pipeline을 동시에 바꾸지 않는다. GET 적중률, 네트워크 배치, 클라이언트 역직렬화 범위를 명시하고 어떤 지표가 병목 위치를 알려 줄지 적는다. 숫자를 예측하는 것보다 측정 계약을 분명하게 만드는 것이 목표다.

두 번째 과제는 가상 표의 C와 D 중 운영 구성을 고르는 것이다. 사용자 SLO, 실패 허용 수준, 비용과 장애 여유를 먼저 정의한 뒤 이유를 쓴다. 처리량이 더 높은 D를 무조건 선택하지 말고, C도 실제 운영에 충분한 여유가 있는지 질문한다. 마지막에는 추가로 필요한 증거를 세 가지 적는다. 좋은 성능 판단은 숫자를 고르는 능력보다 아직 모르는 것을 명확히 말하는 능력에 가깝다.

## 공식 출처와 검증 범위

주요 원문은 제공된 23장과 [Redis benchmark 공식 문서](https://redis.io/docs/latest/operate/oss_and_stack/management/optimization/benchmarks/)이며 2026-10-21에 공식 페이지 접근을 확인했다. pipeline 의미는 [Redis pipelining](https://redis.io/docs/latest/develop/using-commands/pipelining/), 서버 관찰 항목은 [INFO](https://redis.io/docs/latest/commands/info/)를 참고한다. 문서 속 과거 장비의 수치를 현재 버전의 성능 보장으로 재사용하지 않는다.

저장소에서 실제로 실행한 실습은 Redis 7.2.5와 Java 21.0.12.1에서 기본 명령, pipeline 응답 순서, MULTI/Lua의 오류 의미를 확인한 것이다. `learning/redis/lab-checks.json`에는 성능과 부하가 미검증 범위로 표시되어 있다. 본 장의 Java 계측 뼈대, benchmark 명령, 가상 처리량 표는 설계·해석 교육을 위한 자료이며 실측 결과가 아니다. 다음 장의 보안 설정 역시 성능과 분리된 기능이 아니라 실제 운영 조건의 일부라는 점을 연결해서 생각하자.
