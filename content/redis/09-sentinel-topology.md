## 처음 만나는 개념. 저장 담당자와 담당자를 교체하는 관리자는 다르다

작은 물류센터에서 한 직원이 입고 장부를 맡고, 다른 직원이 복사본을 따라 적는다고 생각해 보자. 첫 직원이 자리를 비우면 복사본을 가진 직원이 다음 일을 이어받을 수 있다. 하지만 **누가 결근을 판단하고, 누가 대체 담당자를 정하고, 다른 작업자에게 새 담당자를 알려 줄지**는 아직 정해지지 않았다. 데이터 복제와 자동 장애 전환 사이에 남아 있는 일이 바로 이것이다.

Redis의 replica는 데이터를 따라오는 역할이다. Sentinel은 데이터 노드의 상태를 관찰하고 필요할 때 역할 변경을 조정한다. replica를 추가하면 데이터의 복사본이 생기지만 판단자와 주소 안내가 자동으로 완성되는 것은 아니다. Sentinel을 추가하면 감시와 전환 경로를 만들 수 있지만 데이터 복사본을 대신 저장하는 것은 아니다. 두 구성 요소가 협력한다고 이해하면 쉽다.

또한 서버라는 말부터 구분해야 한다. 물리 컴퓨터나 VM 한 대 안에 Redis 프로세스와 Sentinel 프로세스를 함께 실행할 수 있다. 이때 프로세스는 둘이지만 호스트 장애는 함께 겪을 수 있다. 숫자를 셀 때 프로세스 수와 독립적으로 남을 수 있는 위치의 수를 따로 적는다. 이 구분이 세 대 배치의 이유를 이해하는 시작이다.

자동 장애 전환에는 애플리케이션도 참여한다. 새 담당자를 정했는데 작업자들이 계속 예전 창구로 가면 업무는 회복되지 않는다. 클라이언트가 새 주소를 발견하고 연결을 교체할 수 있어야 한다. Sentinel 배치는 Redis 노드와 감시자만의 그림이 아니라 실제 요청을 보내는 애플리케이션까지 포함한 그림이다.

이 장을 읽을 때는 네 질문을 기억하자. 누가 데이터를 보관하는가? 누가 장애를 판단하는가? 누가 새 쓰기 담당자가 되는가? 애플리케이션은 그 사실을 어떻게 아는가? 이 네 가지를 한 서버의 기능처럼 섞지 않으면 다음 장의 전환 절차를 훨씬 쉽게 따라갈 수 있다.


## 1. Sentinel을 설치하기 전에 해결할 문제부터 정한다

한 대의 Redis에 배송 조회 캐시를 저장하면 구조는 단순하다. 그러나 서버가 멈출 때마다 사람이 대기 서버의 역할을 바꾸고 애플리케이션 주소까지 수정해야 한다면 장애 시간이 길어진다. Sentinel이 해결하는 중심 문제는 **복제 그룹의 현재 primary를 감시하고 교체하는 일**이다. 메모리 용량을 여러 primary로 나누는 샤딩은 하지 않는다. replica를 추가해도 전체 데이터셋의 복사본이 늘어날 뿐 기본적인 쓰기 저장 용량이 합산되지 않는다.

Sentinel의 네 역할을 각각 문장으로 표현하자. 감시는 주기적으로 상태를 확인하는 일이다. 알림은 이상과 역할 변경을 외부 운영 도구에 알리는 일이다. 자동 장애 전환은 적절한 replica를 primary로 승격하고 나머지 복제 관계를 바꾸는 일이다. 구성 제공은 클라이언트에게 논리 서비스 이름에 대응하는 현재 primary 주소를 알려 주는 일이다. Sentinel은 일반 명령을 전달해 주는 프록시가 아니므로 클라이언트는 Sentinel에서 주소를 알아낸 다음 데이터 Redis에 직접 접속한다.

## 2. 프로세스 수보다 독립 장애 도메인이 먼저다

**장애 도메인**은 하나의 원인으로 함께 고장 날 수 있는 범위다. 같은 물리 서버의 서로 다른 컨테이너, 같은 전원 장치에 연결된 서버, 같은 가용 영역의 VM은 서로 다른 수준의 공통 장애를 공유한다. “Sentinel 세 개를 실행했다”는 사실만으로 세 개의 독립 판단 지점을 확보한 것이 아니다. 세 프로세스가 같은 VM에 있다면 VM 정지 한 번으로 전부 사라진다.

권장 출발점은 서로 독립적으로 실패한다고 볼 수 있는 세 위치의 Sentinel 세 개다. 데이터 Redis와 같은 호스트에 둘 수 있지만, 그러면 그 호스트 실패로 데이터 노드와 감시자 하나가 함께 사라진다는 것을 도식에 표시한다. 애플리케이션 서버에 두면 클라이언트와 비슷한 네트워크 관점을 얻을 수 있지만 애플리케이션 배포나 autoscaling으로 감시자 수가 바뀌지 않도록 수명주기를 관리해야 한다.

| 장애 도메인 | 실행 역할 | 상실 시 함께 영향받는 것 |
|---|---|---|
| A | primary와 S1 | 원본 데이터 노드·감시자 하나 |
| B | replica R1과 S2 | 데이터 후보·감시자 하나 |
| C | replica R2와 S3 | 데이터 후보·감시자 하나 |

이 배치에서 A가 사라지면 B와 C의 Sentinel 두 개가 남아 과반 승인을 구성할 수 있고, 살아 있는 replica를 후보로 삼을 수 있다. 그러나 B와 C가 같은 물리 네트워크 장비에 연결되어 그 장비가 함께 고장 나면 기대한 독립성은 깨진다. 비용표에는 서버 개수만 넣지 말고 장애 도메인, 네트워크 경로, 운영 권한, 업그레이드 시점을 함께 적는다.

## 3. 두 Sentinel에서 quorum을 1로 낮추면 왜 충분하지 않을까

**quorum**은 primary가 장애라고 판단하는 데 필요한 감시자 동의 수다. **과반수 승인**은 실제 장애 전환을 수행할 Sentinel을 선출하고 허가하는 조건이다. 감시자가 두 개면 과반수는 두 개다. quorum을 1로 내려도 하나가 사라진 상황에서 남은 하나만으로 과반 승인을 받을 수 없다. 서로 상대방을 못 보는 대칭적인 상황에서 양쪽이 각자 새로운 primary를 만들도록 허용하면 안전한 단일 구성을 정하기 어려워진다.

세 개와 quorum 2를 구성하면 한 감시자의 장애를 견딜 수 있다. 다섯 개와 quorum 2라면 두 개의 장애 판단으로 전환 시도를 시작할 수 있어도 승인에는 최소 세 개가 필요하다. quorum을 과반수보다 높이면 그보다 더 많은 동의가 필요하므로 민감도가 낮아지고 더 많은 장애를 참는 것이 아니라 전환 조건이 더 엄격해진다. 숫자를 줄이면 가용성이 무조건 좋아진다는 식의 튜닝은 금물이다.

## 4. 네트워크와 설정 파일도 배치의 일부다

Sentinel 기본 포트는 26379이며 데이터 Redis 기본 포트 6379와 다르다. Sentinel끼리 통신해야 하고 Sentinel은 모든 데이터 인스턴스를 감시·제어할 수 있어야 한다. 클라이언트도 여러 Sentinel과 모든 잠재적 primary에 도달할 수 있어야 한다. 6379만 열고 26379를 막으면 평소 조회는 가능해도 자동 장애 전환에 필요한 통신이 실패할 수 있다.

Sentinel 설정 파일은 현재 구성과 epoch 같은 상태를 저장하기 때문에 쓰기 가능해야 한다. 읽기 전용으로 마운트한 초기 템플릿을 그대로 런타임 파일로 사용하면 시작 또는 상태 보존에 문제가 생긴다. 템플릿과 Sentinel이 갱신하는 실제 파일의 책임을 나누고, 재배포 때 오래된 템플릿으로 현재 토폴로지를 덮어쓰지 않도록 한다. 각 Sentinel의 파일과 정체성도 따로 유지한다.

NAT는 주소를 바꾸는 네트워크 변환이다. 컨테이너 내부에서 6379로 듣는 서버를 외부에는 16379로 노출했다면 Redis와 Sentinel이 서로에게 알려 주는 주소가 실제 접근 주소와 다를 수 있다. 단순히 최초 접속이 성공했다는 것만으로 자동 발견이 맞다고 볼 수 없다. `sentinel announce-ip`, `sentinel announce-port`나 replica의 광고 주소 설정을 검토하되 실제 버전의 옵션과 DNS 지원을 확인한다. DNS 이름을 쓴다면 이름 해석 지연과 장애도 의존성이다.

## 5. 설계 검토를 통과시키는 질문

설계도에서 A 한 칸을 지워 보자. 남은 Sentinel이 승인 가능한가? 최신 데이터를 가진 승격 후보가 있는가? 애플리케이션이 그 후보에 직접 접속 가능한가? 그 후보에 쓰기 권한과 영속성 설정이 준비되어 있는가? 이전 primary가 돌아왔을 때 어떤 복제 관계가 되는가? 다섯 질문 중 하나라도 답이 없으면 “세 대니까 HA”라는 결론을 내려서는 안 된다. 이 사고 실험은 프로세스 종료 실습보다 먼저 수행할 수 있고, 비용을 들이지 않고도 공통 장애 지점을 발견하게 해 준다.

## 실습 공통 토대: 감시망과 데이터망을 따로 확인하기

이 절은 09~12장을 각각 독립적으로 읽어도 실습 전제를 놓치지 않도록 제공하는 복습이다. Sentinel은 데이터를 저장하는 Redis의 다른 이름이 아니다. 데이터 Redis는 주문 상태를 읽고 쓰는 **데이터 평면**이고, Sentinel은 현재 쓰기를 받을 주 서버를 알려 주고 장애 전환을 조정하는 **제어 평면**이다. 운영자는 두 평면의 정상 여부를 각각 확인해야 한다. 감시가 정상이어도 Redis의 디스크가 가득 찰 수 있고, 데이터 읽기가 정상이어도 Sentinel 사이의 연결이 끊어져 다음 장애를 처리하지 못할 수 있다.

물류센터에 비유하면 Redis primary는 출고 장부를 수정하는 현재 담당자, replica는 그 장부를 받아 적는 대기 담당자, Sentinel은 담당자 교체를 결정하는 관리위원이다. 장부 복사는 비동기다. 원 담당자가 출고 승인 도장을 찍은 순간 대기 담당자가 마지막 줄까지 받아 적었다는 뜻은 아니다. 관리위원 세 명이 교체에 동의해도 복사되지 않은 장부 한 줄을 복원할 수는 없다. 이 비유의 한계도 분명하다. Redis는 사람처럼 빠진 주문의 의미를 추론하거나 장부 두 권을 자동 병합하지 않는다. 어느 서버를 기준으로 삼을지 결정하고 나면 이전 서버는 새 기준의 데이터를 복제하게 된다.

### 격리된 실습 환경 만들기

아래는 로컬의 일회용 테스트 환경을 만드는 예제다. 이 교재에서 실행한 결과가 아니며 명령 뒤의 관찰 설명은 **예상되는 관찰**이다. 이미 같은 포트를 쓰는 서비스가 있으면 중단하고 빈 포트로 바꾼다. 인증을 생략하는 이유는 오직 loopback 실습의 복잡도를 낮추기 위해서다. 공유 호스트, 외부 공개 VM, 운영 서버에서는 그대로 사용하지 않는다. 방화벽으로 외부 접근을 차단하고 로컬 사용자에게도 민감한 데이터가 없는 환경을 쓴다. 운영 도입에는 인증, TLS, 비밀 관리, 독립 장애 도메인 배치가 추가로 필요하다.

```bash
# 필요한 프로그램이 설치되어 있는지와 실제 버전을 먼저 기록한다.
redis-server --version
redis-cli --version
LAB=$(mktemp -d /tmp/redis-sentinel-study.XXXXXX)
printf '%s\n' "$LAB"

for p in 6379 6380 6381; do
  mkdir -p "$LAB/$p"
  cat > "$LAB/$p/redis.conf" <<EOF
port $p
bind 127.0.0.1
protected-mode yes
dir $LAB/$p
pidfile $LAB/$p/redis.pid
logfile $LAB/$p/redis.log
daemonize yes
save ""
appendonly no
EOF
  if [ "$p" != 6379 ]; then
    printf 'replicaof 127.0.0.1 6379\n' >> "$LAB/$p/redis.conf"
  fi
  redis-server "$LAB/$p/redis.conf"
done

for p in 26379 26380 26381; do
  mkdir -p "$LAB/$p"
  cat > "$LAB/$p/sentinel.conf" <<EOF
port $p
bind 127.0.0.1
protected-mode yes
dir $LAB/$p
pidfile $LAB/$p/sentinel.pid
logfile $LAB/$p/sentinel.log
daemonize yes
sentinel monitor logistics-main 127.0.0.1 6379 2
sentinel down-after-milliseconds logistics-main 5000
sentinel failover-timeout logistics-main 60000
sentinel parallel-syncs logistics-main 1
EOF
  redis-server "$LAB/$p/sentinel.conf" --sentinel
done
```

여기서 `save ""`와 `appendonly no`는 실습을 단순화하기 위한 **영속성 비활성화**다. 재시작하면 데이터가 남는다고 기대하지 않는다. 운영에 이 설정을 복사해서는 안 된다. 세 Redis와 세 Sentinel이 한 컴퓨터에서 실행되므로 프로토콜은 관찰할 수 있지만 실제 고가용성은 제공하지 않는다. 컴퓨터 하나가 멈추면 여섯 프로세스가 동시에 사라진다. `daemonize`를 지원하지 않는 배포 환경이라면 각 프로세스를 별도 터미널에서 foreground로 시작하고 종료할 대상을 직접 추적한다.

```bash
redis-cli -p 26379 SENTINEL GET-MASTER-ADDR-BY-NAME logistics-main
```

처음에는 6379가 master이고 다른 두 인스턴스가 그 서버를 복제하는 관계가 예상된다. 일부 출력 필드에는 호환성 때문에 과거 용어 `slave`가 남아 있다. 단어보다 역할과 연결 대상 주소를 읽는다. `master_link_status:up`은 복제 링크가 연결되었다는 뜻이지 데이터 유실 가능성이 없다는 증명은 아니다. `SENTINEL SENTINELS`는 요청받은 Sentinel 자신을 제외한 다른 감시자를 보여 주므로 정상적인 세 감시자 구성에서 목록의 두 항목을 보고 한 대가 사라졌다고 오해하지 않는다.

`CKQUORUM`은 현재 관점에서 장애 판단 정족수와 장애 전환 승인을 받을 수 있는지 검사하는 운영 진단이다. 이 결과가 정상이라고 미래의 복제 지연, 데이터 노드 장애, 클라이언트의 재연결 실패까지 검증되지는 않는다. 따라서 관찰 기록에는 Sentinel 응답만 쓰지 말고 Redis 역할, replica 연결, 애플리케이션 성공률을 함께 적는다. 서로 다른 Sentinel에 같은 조회를 반복해 인식이 일치하는지도 비교한다. 발견 정보가 전파되는 동안 짧은 차이가 있을 수 있으므로 한 번의 서로 다른 응답만으로 영구 분할을 선언하지 않는다.

### 실습을 마친 뒤의 정리

실습 전 포트가 비어 있었고 이 절에서만 생성한 인스턴스라는 것을 확인한 뒤, 테스트 데이터가 필요 없을 때만 각 포트를 종료한다. `killall redis-server`처럼 호스트의 모든 Redis를 종료하는 명령은 쓰지 않는다. 아래 종료 명령도 운영 포트에 그대로 실행하면 장애를 만들므로 현재 실습 대상임을 다시 확인한다.

```bash
# 일회용 실습 인스턴스만 대상으로 한다.
for p in 26379 26380 26381 6379 6380 6381; do
  redis-cli -h 127.0.0.1 -p "$p" SHUTDOWN NOSAVE
done
# 로그 분석이 끝날 때까지 $LAB 디렉터리는 보존한다.
```

종료 도중 연결이 닫혔다는 메시지는 종료 요청이 수락된 상황에서도 보일 수 있다. 프로세스와 포트 상태로 후속 확인한다. 로그에는 실제 주소와 운영 정보가 남으므로 공유 전에 확인한다. 이 실습의 목적은 명령을 외우는 것이 아니라, **설정 → 발견 → 판단 → 승인 → 승격 → 재연결**을 서로 다른 증거로 확인하는 습관을 만드는 것이다.


## 설계 워크숍: 배송 조회 서비스의 장애 행렬

서울 센터에 primary와 S1, 부산 센터에 R1과 S2, 별도 운영 구역에 R2와 S3를 배치한다고 가정하자. 여기서 지명은 네트워크 지연과 장애 도메인을 설명하기 위한 가상 이름이며 실제 권장 리전 조합이 아니다. 세 위치를 멀리 떨어뜨리면 공통 전원 장애 위험은 줄어들 수 있지만 복제 지연과 감시 오탐 위험이 커질 수 있다. **거리의 독립성**과 **통신의 안정성**을 함께 계산해야 한다.

| 고장 가정 | 남은 감시자 | 남은 승격 후보 | 우선 확인할 것 |
|---|---|---|---|
| primary 프로세스만 종료 | S1·S2·S3 | R1·R2 | replica 최신성, 전환·재연결 시간 |
| 서울 호스트 전체 종료 | S2·S3 | R1·R2 | 두 감시자 상호 통신과 후보 접근 |
| 서울-부산 경로만 단절 | 경로에 따라 관점이 다름 | 단순 개수로 판단 불가 | 모든 쌍의 실제 통신과 클라이언트 위치 |
| 부산과 운영 구역의 공통 회선 장애 | S1만 고립되지 않고 남을 수도 있음 | primary만 정상일 수 있음 | 과반 승인 불가와 기존 서비스 상태 구분 |
| 애플리케이션의 Sentinel 접근만 차단 | 감시자 자체는 정상 | 후보는 정상 | 기존 연결 유지와 새 발견 실패 구분 |

첫 줄과 둘째 줄의 차이를 설명할 수 있어야 한다. primary 프로세스만 죽는 시험에서는 같은 호스트의 S1이 살아 있다. 이 시험만 성공했다고 서울 호스트 전체 장애를 검증한 것이 아니다. 셋째 줄은 더 까다롭다. S3가 양쪽과 통신할 수 있는지, 어느 방향으로 패킷이 통과하는지에 따라 결과가 달라진다. “망이 끊겼다”는 말보다 출발지·목적지·포트·방향을 기록하는 편이 정확하다.

### Spring 애플리케이션의 연결 설정 검토표

Spring 애플리케이션이 필요한 논리 정보는 `logistics-main`이라는 primary 그룹 이름, 여러 Sentinel의 접근 주소, Sentinel 인증 정보, 데이터 Redis 인증 정보다. 연결 팩토리가 Sentinel 모드로 초기화되는지 확인하고 단일 호스트 설정이 우연히 우선 적용되지 않는지도 검사한다. 프레임워크 버전에 따라 설정 속성의 접두사와 username 지원이 달라질 수 있으므로 이 장은 특정 Spring Boot 버전의 YAML을 보편적인 정답으로 제시하지 않는다.

예를 들어 배포 설정에 Sentinel 목록을 넣었지만 직접 만든 `RedisConnectionFactory` bean이 6379를 고정해서 사용한다면, 설정 파일을 읽는 사람은 HA라고 생각해도 실제 애플리케이션은 단일 주소로 동작할 수 있다. 테스트에서는 단순 `PING` 대신 **현재 연결 대상이 전환 후 바뀌는지** 확인한다. 자격 증명은 별도로 마스킹하고 서버 주소와 연결 모드만 진단한다. 개발 환경에서 성공한 주소가 운영 컨테이너 내부에서도 해석되는지 검사한다.

### 메모리와 유지보수도 실패 행렬에 넣는다

R1이 승격되면 primary의 쓰기 부하와 복제 송신을 감당해야 한다. 평소 읽기만 담당하던 작은 서버를 저비용 replica로 두었다가 승격 직후 CPU나 메모리가 포화되면 전환은 성공했지만 서비스는 여전히 실패한다. 모든 승격 후보에 실제 primary 부하를 감당할 여유를 두거나 승격 가능성을 의도적으로 제한하고 그 결과 남는 후보 수를 계산한다. replica-priority를 바꾸는 일은 단순 선호도 지정이 아니라 실패 행렬을 바꾸는 작업이다.

Sentinel이 세 개라도 유지보수로 하나를 내린 동안 다른 하나가 실패하면 과반이 사라진다. 따라서 감시자 업그레이드는 한 번에 하나씩 수행하고 재합류·발견을 확인한 뒤 다음 인스턴스로 넘어간다. 데이터 노드 유지보수와 감시자 유지보수를 같은 시간에 겹치지 않는 것이 안전한 출발점이다. 자동 배포 시스템이 모든 replica와 Sentinel을 같은 업데이트 그룹에 넣지 않았는지 확인한다.

### 설계 승인 기준을 문장으로 쓴다

좋은 기준은 “Sentinel 세 대 구축 완료”가 아니라 “임의의 한 장애 도메인을 잃어도 남은 감시자가 승인 가능하며, 적격 replica에 애플리케이션이 재연결하여 정해진 시간 안에 배송 조회를 회복한다”다. 여기에 데이터 조건을 붙인다. 배송 상태는 원장의 이벤트로 재구성 가능한 캐시이며, 전환 후 마지막 갱신이 빠졌으면 원장을 읽어 보완한다. Redis가 유일한 출고 원장이라면 같은 배치라도 손실 허용 기준이 달라져 추가 설계가 필요하다.

마지막으로 설계 문서에 아직 시험하지 않은 고장을 명시한다. 프로세스 종료는 시험했지만 호스트 정지, 비대칭 분할, DNS 장애, 자격 증명 회전은 미시험이라고 쓰는 것이 정확하다. 미시험 항목을 숨기지 않아야 다음 검증의 우선순위를 정할 수 있다. 고가용성은 제품 이름이 아니라 구체적인 장애 모델에 대해 확보한 증거의 집합이다.

## 요청 경로 해설. 애플리케이션은 Sentinel을 거쳐 데이터를 읽는가

Sentinel의 주소 안내를 택시 안내소에 비유해 보자. 안내소는 지금 어느 승강장으로 가야 하는지 알려 준다. 승객의 모든 이동을 안내소 건물 안으로 통과시키는 것은 아니다. 일반적인 Sentinel 사용에서도 클라이언트는 Sentinel에 현재 primary를 묻고, 얻은 데이터 노드에 직접 연결해 GET이나 SET을 보낸다.

따라서 네트워크 경로가 두 종류다. 하나는 서비스 발견을 위한 경로이고 다른 하나는 실제 데이터를 읽고 쓰는 경로다. 애플리케이션이 Sentinel에 연결됐다는 사실은 새 primary의 데이터 포트에도 접근할 수 있다는 뜻이 아니다. 반대로 Redis 데이터 연결이 잘되더라도 Sentinel 주소 발견 경로가 막혀 있으면 장애 전환 뒤 새 주소를 찾지 못할 수 있다.

| 요청의 목적 | 출발점 | 도착점 | 확인하는 사실 |
|---|---|---|---|
| 현재 쓰기 담당자 찾기 | 애플리케이션 클라이언트 | Sentinel | 논리 이름에 대응하는 주소 |
| 상품 정보 읽기·변경 | 애플리케이션 클라이언트 | 데이터 Redis | 해당 데이터 명령의 결과 |
| 상태 감시·역할 제어 | Sentinel | 데이터 Redis | 역할과 상태, 전환 결과 |
| 감시자 간 협력 | Sentinel | 다른 Sentinel | 판단과 전환 수행 권한 |
| 데이터 따라오기 | replica | 현재 primary | 기준 상태와 변경 스트림 |

이 표에서 연결 하나를 지웠을 때 무엇이 깨지는지 생각해 보자. 데이터 경로만 남으면 현재 연결은 잠시 동작해도 주소 변경에 취약할 수 있다. 감시 경로만 남으면 Sentinel은 새 primary를 안내할 수 있어도 애플리케이션은 그곳에 접속하지 못할 수 있다. 이런 식으로 경로를 목적별로 읽으면 방화벽 규칙을 검토할 때도 질문이 구체적이 된다.

Sentinel이 일반 데이터 프록시가 아니라는 점은 용량 산정에도 영향을 준다. 데이터 트래픽이 많다고 그 모든 바이트가 Sentinel을 통과하는 것은 아니다. 그렇다고 감시자의 자원과 네트워크가 중요하지 않다는 뜻도 아니다. 감시자가 과부하로 멈추면 판단의 품질과 전환 시간이 영향을 받을 수 있다. 역할과 비용을 구분해서 측정한다.


## 서비스 이름 해설. logistics-main은 IP 주소도 Redis 키도 아니다

Sentinel은 감시하는 primary 그룹을 논리적인 이름으로 식별한다. 예를 들어 `logistics-main`이라고 정하면 클라이언트는 그 이름의 현재 primary 주소를 질의한다. 장애 전환 뒤 주소가 바뀌어도 이름은 같은 서비스를 가리킬 수 있다. 이름과 위치를 분리하는 것이다.

이름을 사내 담당 업무명으로 생각하면 쉽다. “입고 담당자”라는 역할은 유지되지만 오늘 앉아 있는 사람이 바뀔 수 있다. 클라이언트에 오래된 IP만 고정하면 역할이 바뀌어도 예전 사람을 찾아가게 된다. Sentinel 지원 클라이언트는 논리 이름과 감시자 목록을 바탕으로 현재 위치를 알아내는 경로를 사용한다.

이 이름은 Redis 안의 key-value 데이터와 별도다. `SET logistics-main ...`을 실행한다고 Sentinel 감시 그룹이 생성되지 않는다. DNS 이름을 자동으로 만드는 것도 아니다. 같은 문자열을 여러 시스템에서 쓸 수 있지만 어떤 주체가 해석하는 이름인지 구별해야 한다. 클라이언트 설정과 Sentinel 설정의 그룹 이름이 서로 다르면 정상 네트워크에서도 발견이 실패할 수 있다.

운영 문서에는 논리 이름, 초기 데이터 주소, Sentinel 목록, 애플리케이션이 쓰는 이름을 함께 기록한다. 개발·검증·운영 환경의 이름과 주소를 혼동하지 않도록 해야 한다. 이름이 사람이 읽기 좋다고 대상 확인을 생략할 수 있는 것은 아니다. 실제로 발견한 주소와 ROLE을 확인하는 절차가 필요하다.


## 배치 사고 실험. 세 프로세스를 한 호스트에 두면 몇 번의 장애를 견디는가

감시자 S1·S2·S3를 한 VM에 띄웠다고 하자. 프로세스 하나만 종료되는 사고에서는 나머지가 남을 수 있다. VM 자체가 멈추면 세 감시자가 함께 사라진다. “한 장애를 견딘다”는 말에서 그 장애의 단위가 무엇인지 적지 않으면 서로 다른 설계를 같은 것으로 보게 된다.

반대로 각 감시자를 다른 호스트에 두었다고 모든 공통 장애가 제거되는 것도 아니다. 같은 가용 영역, 네트워크 장비, 전원, 운영 계정과 일괄 배포가 공통 원인이 될 수 있다. 독립성은 전부 있거나 전부 없는 이분법보다 **어떤 사고에 대해 독립적인가**라는 질문으로 다루는 편이 정확하다.

| 배치 | 프로세스 하나 종료 | 호스트 하나 상실 | 추가로 남는 공통 원인 |
|---|---|---|---|
| 한 호스트에 S1·S2·S3 | 일부 생존 가능 | 전부 상실 가능 | 호스트·전원·OS |
| 세 호스트에 하나씩 | 다른 감시자 유지 가능 | 두 감시자 유지 가능 | 같은 영역·망·배포 |
| 독립 영역에 분산 | 조건에 따라 일부 생존 | 조건에 따라 일부 생존 | 영역 간 통신·공통 권한 |

세 개의 감시자가 있는 이유도 “무조건 세 개가 가장 빠르다”가 아니다. 안정된 세 구성원 가운데 두 개는 과반수다. 한 감시자가 사라져도 나머지 두 개가 서로 통신하면 과반 조건을 구성할 수 있다. 감시자가 두 개면 과반은 두 개이므로 한 개 상실 뒤 남은 하나가 충분하지 않다. quorum 값을 낮추어도 과반 승인이라는 다른 조건은 남는다.

다만 두 감시자가 남았다는 사실만으로 데이터 서비스가 회복되지는 않는다. 살아 있는 적격 replica가 있어야 하고 제어·데이터 네트워크와 권한, 클라이언트 연결도 필요하다. 숫자 계산은 전환의 필요한 조건 일부를 검토하는 것이지 서비스 복구의 충분조건 전체가 아니다.


## Java 배치 모델. 호스트 하나씩 지워 보며 남는 조건 계산하기

아래는 배치 검토용 사고 실험이다. 알려진 감시자 집합이 고정되어 있고 살아 있는 호스트들끼리 통신할 수 있다고 가정한다. Redis Sentinel의 실제 멤버십 발견이나 선출 알고리즘은 구현하지 않는다. Java 21에서 실행해 **프로세스 배치와 단일 호스트 상실의 관계**를 확인한다.

```java
import java.util.List;
import java.util.Set;

public final class SentinelPlacementLesson {
    record Host(String name, int sentinels, int promotionCandidates) {
        Host {
            if (sentinels < 0 || promotionCandidates < 0) {
                throw new IllegalArgumentException("negative process count");
            }
        }
    }
    record Remaining(int sentinels, int requiredMajority, int candidates) {
        boolean prerequisitesRemain() {
            return sentinels >= requiredMajority && candidates > 0;
        }
    }

    static Remaining afterLoss(List<Host> hosts, Set<String> failedHosts) {
        int known = hosts.stream().mapToInt(Host::sentinels).sum();
        if (known == 0) throw new IllegalArgumentException("no known Sentinels");
        int liveSentinels = hosts.stream().filter(h -> !failedHosts.contains(h.name()))
                .mapToInt(Host::sentinels).sum();
        int liveCandidates = hosts.stream().filter(h -> !failedHosts.contains(h.name()))
                .mapToInt(Host::promotionCandidates).sum();
        return new Remaining(liveSentinels, known / 2 + 1, liveCandidates);
    }

    public static void main(String[] args) {
        List<Host> spread = List.of(new Host("A", 1, 0),
                new Host("B", 1, 1), new Host("C", 1, 1));
        for (String lost : List.of("A", "B", "C")) {
            Remaining remaining = afterLoss(spread, Set.of(lost));
            if (!remaining.prerequisitesRemain()) throw new AssertionError(lost);
            System.out.println("lost " + lost + ": " + remaining);
        }
        List<Host> concentrated = List.of(new Host("A", 3, 0),
                new Host("B", 0, 1), new Host("C", 0, 1));
        if (afterLoss(concentrated, Set.of("A")).prerequisitesRemain()) {
            throw new AssertionError("one host must not count as three domains");
        }
        if (afterLoss(spread, Set.of("B", "C")).prerequisitesRemain()) {
            throw new AssertionError("no majority and no promotion candidates");
        }
        System.out.println("correlated loss cases detected");
    }
}
```

`known / 2 + 1`은 이 모델의 고정된 알려진 감시자 수에 대한 엄격한 과반 계산이다. 호스트가 사라졌다고 분모를 즉시 남은 감시자 수로 줄이지 않는다. 그렇게 줄이면 고립된 한 감시자도 자기 자신 기준으로 과반이라고 주장하는 잘못된 사고 모델을 만들 수 있다. 실제 멤버십과 발견 규칙은 더 복잡하므로 이 산술을 그대로 제품 구현이라고 부르지 않는다.

promotionCandidates는 살아 있는 적격 후보가 있다고 가정한 수다. 실제 적격성에는 연결 이력과 우선순위, 복제 진행 상태 등이 들어간다. 또한 이 함수는 클라이언트 접근성과 인증, 디스크와 자원을 검사하지 않는다. 그래서 메서드 이름도 `serviceRecovered`가 아니라 `prerequisitesRemain`이다. 남은 조건 일부와 전체 복구 완료를 이름부터 구분한다.

이런 작은 모델은 설계 검토에서 유용하다. 그림의 상자 하나를 지우는 일을 반복 가능한 입력으로 만들 수 있기 때문이다. 그러나 코드가 통과했다는 이유로 실제 네트워크 분할이나 failover가 검증됐다고 주장하면 안 된다. 다음 단계는 격리 환경에서 가정을 실제 관측으로 확인하는 것이다.


## Spring 연결 예제. Sentinel 목록과 데이터 연결 설정을 한 곳에 모으기

다음은 Spring Data Redis 3.2.0 API를 사용하는 로컬 학습용 설정 클래스다. 예제 포트에 실제로 격리된 Sentinel과 Redis를 준비한 프로젝트에 넣어야 한다. 여기서는 인증 없는 루프백 실습 환경을 전제로 연결 구조만 보여 준다. 운영 계정과 TLS, 재연결 정책은 사용 버전과 환경에 맞게 별도로 구성한다.

```java
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.data.redis.connection.RedisSentinelConfiguration;
import org.springframework.data.redis.connection.lettuce.LettuceConnectionFactory;
import org.springframework.data.redis.core.StringRedisTemplate;

@Configuration
public class SentinelClientConfiguration {
    @Bean
    public LettuceConnectionFactory redisConnectionFactory() {
        RedisSentinelConfiguration sentinel = new RedisSentinelConfiguration()
                .master("logistics-main")
                .sentinel("127.0.0.1", 26379)
                .sentinel("127.0.0.1", 26380)
                .sentinel("127.0.0.1", 26381);
        return new LettuceConnectionFactory(sentinel);
    }

    @Bean
    public StringRedisTemplate redisTemplate(LettuceConnectionFactory factory) {
        return new StringRedisTemplate(factory);
    }
}
```

여기서 세 sentinel 주소는 클라이언트가 서비스 발견에 사용할 초기 감시자 목록이다. GET과 SET이 이 세 포트로 번갈아 가며 보내진다는 뜻은 아니다. master에 지정한 문자열은 감시 그룹의 논리 이름이다. 이 문자열을 현재 primary의 IP 주소처럼 바꾸면 안 된다. 데이터 노드 주소가 바뀌어도 같은 그룹을 찾는 의도를 표현한다.

127.0.0.1은 각 프로세스의 네트워크 환경에서 자기 자신을 가리킨다. Java가 컨테이너 안에 있다면 호스트에서 띄운 Sentinel의 루프백과 같다고 가정하면 안 된다. 이 예제를 복사했는데 연결이 안 되면 먼저 실제 실행 위치와 포트, 네트워크 경로를 확인한다. 인증 오류와 연결 실패를 한 문제로 묶지 않는다.

클래스의 컴파일은 API 형태를 확인하는 증거다. Spring 컨텍스트가 실제로 시작되고 연결이 생성되며 장애 전환 뒤 새 primary에 요청하는지는 별도 통합 시험이다. 이 예제에는 main이 없고, 단독 javac 명령으로 모든 의존성 없이 실행하는 프로그램도 아니다. 코드가 맡는 책임과 필요한 실행 환경을 함께 읽는다.

실제 프로젝트에서는 자동 구성과 직접 등록한 빈이 어떻게 함께 동작하는지 확인한다. 동일한 연결 팩토리를 여러 경로로 정의하거나 기존 Redis 설정을 일부만 덮어쓰면 의도와 다른 빈이 사용될 수 있다. 설정 파일의 숫자만 바꾸기보다 최종 주입된 연결 구성과 실제 대상 주소를 관측하는 것이 중요하다.


## 구성 파일 보충. 초기 템플릿과 살아 있는 Sentinel 상태를 구별하기

일반적인 애플리케이션 설정 파일은 배포 시스템이 만들고 프로그램은 읽기만 하는 방식으로 관리할 수 있다. Sentinel의 런타임 설정 파일은 현재 알게 된 구성과 정체성, epoch 같은 상태를 유지하는 데 쓰이는 부분이 있다. 그래서 읽기 전용 초기 템플릿을 그대로 런타임 파일로 사용하면 문제가 생길 수 있다.

문제는 파일을 쓰기 가능하게 만드는 한 줄로 끝나지 않는다. 누가 초기 내용을 공급하고, 각 Sentinel이 어디에 자기 상태를 보관하고, 컨테이너가 재생성될 때 그 상태를 어떻게 유지할지 정해야 한다. 세 Sentinel이 같은 파일을 공유하며 서로 덮어쓰는 방식도 각자의 정체성과 상태를 다루는 올바른 모델이 아니다.

구성 원본과 런타임 상태의 책임을 나누어 생각하자. 배포 템플릿에는 의도한 초기 정책과 서비스 정보를 담을 수 있다. 실행 중인 Sentinel은 발견하고 채택한 상태를 자기 파일에 갱신한다. 다음 배포에서 오래된 템플릿으로 최신 상태를 무조건 교체하면 재시작의 의미가 달라질 수 있다. 실제 운영 플랫폼의 지속 저장과 초기화 절차를 검토해야 한다.

파일 검토 시 비밀이 들어 있다면 전체를 로그로 출력하지 않는다. 이 장의 핵심은 정보를 많이 수집하는 것이 아니라 필요한 값의 출처와 적용 경로를 구별하는 것이다. 다음 인증 장에서 다섯 연결의 계정을 분리하고 역할 변경 뒤에도 필요한 권한이 남는지 확인한다.


## 배치 검토 워크숍. 서버 한 칸을 지운 뒤 네 가지 경로를 따라가기

설계도를 그렸다면 가장 비싼 장애 실험부터 할 필요는 없다. 먼저 primary가 있는 상자를 지워 보자. 남은 감시자들이 서로 통신하며 필요한 판단과 승인을 할 수 있는가? 살아 있는 replica 중 후보가 있는가? Sentinel이 그 후보를 제어할 수 있는가? 애플리케이션이 새 주소로 직접 연결할 수 있는가? 각 질문의 증거를 선과 표로 표시한다.

다음에는 replica가 있는 상자를 지운다. primary가 살아 있어도 최소 replica 쓰기 조건이 깨지는지 확인한다. 장애 전환이 필요 없는 사고인데도 쓰기 가용성이 영향을 받을 수 있다. 감시자의 과반수만 계산한 설계표에는 이 문제가 보이지 않는다. 데이터 복제의 보호 조건과 제어 계층의 승인 조건을 함께 보아야 한다.

세 번째는 애플리케이션과 Sentinel 사이의 선을 지워 본다. 기존 데이터 연결은 유지될 수 있지만 새 주소 발견이 필요한 순간 문제가 생길 수 있다. 네 번째는 애플리케이션과 잠재적 새 primary 사이의 선을 지운다. 감시망이 완벽하게 새 담당자를 정해도 사용자는 여전히 실패를 볼 수 있다. 이 두 사례가 감시망과 데이터망을 나누는 이유다.

실제 검토표에는 비용과 운영 조건도 적는다. 감시자와 데이터 노드가 같은 호스트에 있으면 그 호스트의 점검과 과부하를 함께 겪는다. 자동 확장되는 애플리케이션 프로세스와 수명을 공유하면 감시자 구성도 의도치 않게 변할 수 있다. 배치의 독립성은 하드웨어 위치뿐 아니라 배포와 종료 방식에도 달려 있다.


## 면접 질문과 깊이 있는 답변

답을 펼치기 전에 원리, 장애 반례, 운영 확인 방법의 세 순서로 말해 보자. 짧은 정의만 외우기보다 어떤 조건에서 그 설명이 깨지는지를 덧붙이는 것이 중요하다.

<details><summary>Sentinel과 replica는 어떻게 다른가요?</summary>

replica는 데이터의 복사본을 유지하는 데이터 노드이고 Sentinel은 감시·전환·주소 발견을 담당하는 제어 프로세스입니다. Sentinel을 세 개 추가해도 데이터 복사본이 세 개 늘지 않습니다. 설계도에는 두 종류를 별도 기호로 그리고 각 장애 때 무엇이 남는지 확인해야 합니다.

</details>

<details><summary>왜 Sentinel 두 개에 quorum 1이면 부족한가요?</summary>

quorum은 장애 판단 조건이고 실제 전환에는 감시자 과반 승인이 필요합니다. 두 개의 과반은 두 개이므로 한 감시자가 사라지면 승인할 수 없습니다. 특히 primary와 감시자를 같은 호스트에 둔 두 호스트 구성에서 그 호스트 장애는 데이터 서버와 표 한 개를 동시에 없앱니다.

</details>

<details><summary>Sentinel 세 개를 한 호스트에서 실행하면 HA인가요?</summary>

프로토콜 학습은 가능하지만 호스트 장애 내성은 없습니다. 프로세스 단위 고장만 분리되었을 뿐 전원·커널·네트워크 인터페이스를 공유합니다. 독립 장애 도메인의 범위를 명시하고, 한 도메인이 사라졌을 때 과반 감시자와 적격 replica가 남는지 검토해야 합니다.

</details>

<details><summary>Sentinel은 애플리케이션 요청을 프록시하나요?</summary>

일반 데이터 명령의 프록시가 아닙니다. 클라이언트는 Sentinel에 논리 이름의 현재 primary 주소를 물은 다음 Redis 데이터 포트로 직접 접속합니다. 따라서 모든 잠재적 primary 주소에 클라이언트가 접근 가능해야 하고, 지원 클라이언트의 발견·재연결 동작도 테스트해야 합니다.

</details>

<details><summary>컨테이너에서 최초 연결만 성공하면 충분한가요?</summary>

아닙니다. 자동 발견으로 알려지는 주소가 내부 전용 IP나 다른 포트일 수 있습니다. Sentinel 상호 통신, replica 발견, 클라이언트가 받는 새 primary 주소를 각각 확인해야 합니다. NAT·포트 매핑·DNS 설정을 바꿨다면 실제 전환 뒤 접근 경로까지 검증합니다.

</details>

<details><summary>Sentinel 설정 파일은 왜 쓰기 가능해야 하나요?</summary>

단순한 시작 템플릿이 아니라 발견된 노드와 현재 구성·epoch 같은 상태를 저장하는 파일이기 때문입니다. 읽기 전용 마운트나 재배포 때 오래된 파일로 덮어쓰기하는 정책은 문제가 됩니다. 템플릿 배포와 런타임 상태 보존의 책임을 분리해야 합니다.

</details>

<details><summary>Sentinel이 있으면 성공한 쓰기가 모두 보존되나요?</summary>

아닙니다. 데이터 복제는 비동기이므로 승인 후 replica에 전달되기 전에 primary가 실패하면 새 primary에 그 쓰기가 없을 수 있습니다. Sentinel은 전환을 조정할 뿐 복제되지 않은 값을 복원하지 못합니다. 원장·백업·재처리와 허용 손실 범위를 별도로 설계합니다.

</details>

<details><summary>배치 검토에서 가장 먼저 그릴 것은 무엇인가요?</summary>

서버 개수보다 장애 도메인과 통신 경로입니다. 한 도메인을 지웠을 때 남은 감시자 승인 수, 승격 후보, 애플리케이션 접근 경로를 계산합니다. 그다음 실제 장애 시험으로 감지·전환·재연결·업무 대조 시간을 나누어 검증하면 설계와 운영이 연결됩니다.

</details>


## 운영 수명 보충. 배포가 감시자를 한꺼번에 지우지 않는지 확인하기

장애 도메인을 물리 위치만으로 보면 소프트웨어 배포가 만드는 공통 실패를 놓칠 수 있다. 서로 다른 세 호스트에 감시자가 있어도 같은 배포 작업이 세 프로세스를 동시에 재시작하면 잠시 판단 주체가 모두 사라질 수 있다. 자동 확장으로 애플리케이션 인스턴스와 함께 감시자가 제거되는 구조라면 알려진 구성과 실제 실행 수의 관계도 달라진다.

따라서 정상 운영 절차도 배치 그림에 넣는다. 감시자 점검을 순차로 하는지, 재시작 뒤 현재 그룹과 다른 감시자들을 정상적으로 인식했는지, 다음 대상을 내려도 필요한 조건이 남는지 확인한다. 새 프로세스의 포트가 열렸다는 사실과 감시 집합에 필요한 상태가 준비됐다는 사실은 다르다.

변경을 되돌릴 때도 현재 primary 주소와 저장된 상태를 먼저 확인한다. 오래된 설정 템플릿을 무조건 복사하면 실제로 채택한 구성과 다른 입력으로 감시자를 시작할 수 있다. 재현 가능한 초기 구성과 실행 중 상태 보존을 함께 설계해야 한다. 이 항목들은 비용표의 서버 수에는 잘 보이지 않지만 실제 가용성에 영향을 준다.

## 추가 면접 문답: 배치의 필요조건을 정확히 설명하기

<details><summary>Sentinel 세 대가 있으면 Redis 서버 한 대만 있어도 자동 복구되나요?</summary>

감시자 세 대와 데이터 복사본은 다른 자원이다. primary가 사라졌을 때 승격할 적격 replica가 없다면 Sentinel의 판단이 가능해도 대체 데이터를 가진 서버를 새 primary로 만들 수 없다. 감시자가 Redis 데이터셋을 대신 저장하는 것은 아니다.

답변에서는 감시자 수, 데이터 노드 수, 장애 도메인, 클라이언트 경로를 각각 말한다. 어떤 상실 뒤 어떤 후보가 남는지 구체적으로 설명해야 한다. 프로세스 숫자 하나만으로 전체 복구 가능성을 선언하지 않는다.

</details>

<details><summary>Sentinel은 정상인데 애플리케이션만 장애가 날 수 있나요?</summary>

가능하다. Sentinel이 새 primary를 정확히 안내해도 애플리케이션이 그 주소의 데이터 포트에 접근하지 못하거나 인증이 맞지 않을 수 있다. 클라이언트가 이전 주소와 연결을 계속 사용해도 문제가 생긴다. 서버의 역할 변경과 사용자 요청의 회복은 다른 단계다.

실제 애플리케이션 위치에서 서비스 발견과 새 데이터 연결을 모두 검사한다. 현재 연결 한 개가 살아 있다는 사실만으로 전환 후 접근성을 증명하지 않는다. 오류 주소와 역할, 발견 및 재연결 시각을 연결해 조사한다.

</details>

<details><summary>다른 VM 세 대면 장애 도메인이 완전히 독립적인가요?</summary>

어떤 사고에 대한 독립성인지 확인해야 한다. 같은 물리 호스트나 영역, 네트워크 장비, 전원, 일괄 배포를 공유할 수 있다. VM 식별자가 다르다는 사실만으로 모든 공통 원인이 제거되는 것은 아니다.

배치 검토에서는 대비할 장애의 단위를 먼저 정하고 그 원인으로 함께 사라질 구성 요소를 묶는다. 한 상자를 지운 뒤 남은 감시자와 데이터 후보, 네트워크와 권한이 필요한 조건을 만족하는지 확인한다.

</details>

<details><summary>Sentinel 연결 주소를 세 개 넣으면 데이터 읽기도 세 곳으로 분산되나요?</summary>

그 목록은 보통 발견에 사용할 감시자들의 주소다. 일반 데이터 명령은 발견한 Redis 노드로 직접 전송된다. Sentinel을 데이터 프록시나 읽기 분산 노드로 생각하면 포트와 연결 경로를 잘못 설계할 수 있다.

replica 읽기를 사용할지는 클라이언트의 별도 라우팅과 일관성 정책이다. 오래된 값을 허용하는 업무인지 판단해야 하며, Sentinel 목록의 개수로 결정되지 않는다.

</details>
