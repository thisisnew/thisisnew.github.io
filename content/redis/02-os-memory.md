## 출발점: 8 GiB 데이터가 왜 8 GiB 서버에 들어가지 않을까

문자열을 전부 더했더니 8 GiB였다. 그렇다면 RAM 8 GiB인 서버를 주문하면 될까? 아니다. 데이터를 찾는 사전 구조, 키 이름, 객체 정보, 메모리 할당기의 여유 공간, 클라이언트 응답, 복제 데이터, 운영체제까지 공간을 쓴다. 스냅샷을 만드는 동안에는 평소보다 더 많은 메모리가 필요할 수도 있다. 이 장의 목표는 “RAM을 넉넉하게”라는 조언을 **측정 가능한 항목과 실패 경로**로 바꾸는 것이다.

제공된 02장에는 Linux 설정, swap, 복제, 오래된 클라우드 인스턴스 예시가 함께 있다. 여기서는 오래된 인스턴스명이나 비율을 현재 권장값으로 복사하지 않는다. 공식 운영 문서의 원리를 참고하되, 커널·컨테이너·Redis 버전·서비스 SLO에 맞추어 검증한다. SLO는 사용자가 경험할 서비스 수준의 목표이며, 예를 들어 “99% 요청이 20ms 이내” 같은 기준이다. [공식 운영 가이드](https://redis.io/docs/latest/operate/oss_and_stack/management/admin/)

## 기초 보충 A. RAM, 가상 메모리, 디스크를 먼저 구별하기

메모리를 처음 공부할 때는 RAM을 아주 빠른 작업대, 디스크를 오래 보관하는 창고로 생각해 보자. Redis는 데이터를 주로 RAM에서 다루므로 디스크에서 매번 값을 찾는 비용을 줄인다. 그러나 작업대가 빠르다고 크기가 무한하지는 않다. 작업대가 꽉 찼을 때 무엇을 버릴지, 창고로 옮길지, 새 주문을 거절할지 정해야 한다. Redis의 eviction, OS의 swap, 쓰기 오류는 각각 다른 주체가 내리는 다른 결정이다.

여기에 **가상 메모리**가 등장한다. 프로세스는 물리 RAM의 위치를 직접 번호로 기억하며 사용하는 대신, OS가 제공하는 자기만의 주소 공간을 사용한다. 가상 주소는 큰 건물의 방 번호표처럼 생각할 수 있다. 번호가 있다고 모든 방에 물건이 들어 있는 것은 아니다. 주소 공간의 크기와 현재 물리 RAM을 차지하는 양은 같지 않다. 따라서 프로세스의 가상 메모리가 크게 보인다는 이유만으로 그만큼 RAM을 실제 점유한다고 해석하면 안 된다.

OS는 주소 공간을 일정한 크기의 **페이지** 단위로 관리한다. 이 장의 계산 예시에서는 작은 페이지를 4 KiB로 가정하지만, 실제 페이지 크기와 큰 페이지 사용 여부는 시스템에 따라 확인해야 한다. 하나의 Redis 키가 한 페이지를 독점하는 것은 아니다. 여러 작은 값과 관리 정보가 같은 페이지에 들어갈 수 있고, 큰 값은 여러 페이지에 걸칠 수 있다. 이 사실이 뒤에서 COW 비용을 이해하는 열쇠다.

페이지 테이블은 가상 주소가 어느 물리 페이지에 대응하는지 관리하는 정보다. 책 목차가 본문 그 자체는 아니지만 공간을 차지하듯이, 페이지 테이블도 데이터 값은 아니지만 자원과 관리 비용이 필요하다. fork가 데이터 본문 전체를 즉시 복사하지 않아도 작업 시간이 0이 아닌 이유를 여기서 이해할 수 있다. 메모리 내용의 복사와 메모리 주소 관계의 복사는 같은 작업이 아니다.

**상주한다**는 표현은 페이지가 현재 RAM에 올라와 있다는 뜻으로 이해하면 된다. RSS는 그런 관점에서 프로세스를 본다. 다만 공유 페이지가 있으면 프로세스별 RSS를 단순히 모두 더했을 때 같은 물리 페이지를 여러 번 셀 수 있다. 부모와 자식이 같은 페이지를 공유하는 동안 각자의 지표가 커 보인다고 실제 사용 RAM이 무조건 두 배인 것은 아니다. 메모리 대시보드에서 측정 범위를 먼저 읽어야 하는 이유다.

Redis가 파일을 쓰는 과정에도 OS가 관여한다. 데이터가 파일로 기록되는 동안 파일 캐시와 I/O 버퍼 등 다른 비용이 관찰될 수 있다. 컨테이너의 메모리 사용량은 Redis의 `used_memory`와 동일한 항목만 합산한 값이 아니다. 같은 숫자 이름처럼 보여도 측정 대상이 다르므로, “Redis는 3 GiB라는데 컨테이너는 왜 4 GiB죠?”라는 질문은 자연스러운 출발점이다. 둘 중 하나가 반드시 틀린 것이 아니다.

## 1. 메모리라는 단어를 다섯 칸으로 나누기

첫째, **논리 데이터 크기**는 애플리케이션이 저장한 내용의 크기다. 값이 `hello`면 내용은 5바이트지만 키 이름과 관리 구조는 포함하지 않은 숫자다. 둘째, **Redis가 할당한 메모리**는 데이터와 내부 관리 구조를 위해 할당기에서 받은 공간이다. `INFO memory`의 `used_memory`는 이런 관점의 중요한 지표다. 셋째, **RSS**는 Resident Set Size, 프로세스와 관련해 실제 RAM에 상주하는 페이지의 크기다. `used_memory_rss`를 보면 할당량과 상주량이 다를 수 있음을 알 수 있다.

넷째, **시스템 또는 cgroup 사용량**은 OS가 제한을 적용하는 범위의 소비다. 컨테이너에서는 Redis 프로세스뿐 아니라 그 그룹에 속한 다른 작업과 메모리 계산 규칙도 중요하다. 다섯째, **maxmemory 판단에 쓰이는 메모리**는 Redis의 축출 정책과 관련된 계산이다. 특정 복제/AOF 버퍼는 축출 피드백 루프를 피하기 위해 이 판단에서 제외되는 부분이 있다. `mem_not_counted_for_evict` 같은 지표를 함께 보는 이유다. 정확한 필드 정의는 해당 버전의 `INFO` 문서를 확인한다. [INFO 메모리 필드](https://redis.io/docs/latest/commands/info/)

식당 비유를 다시 써 보자. 음식 자체의 부피가 논리 데이터, 용기와 선반까지 포함한 공간이 할당량, 건물이 실제로 점유한 면적이 RSS에 가깝다. 매니저가 “식재료 창고는 50㎡까지만”이라고 정했다고 복도와 조리실이 사라지지 않는다. 비유의 한계는 OS가 고정된 방 단위로만 움직이지 않는다는 데 있다. 실제 메모리는 페이지와 가상 주소, 공유 페이지, 파일 캐시 등의 규칙으로 계산된다. 그래서 서로 다른 지표를 단순 합산하면 공유 영역을 이중 계산할 수도 있다.

## 기초 보충 B. 데이터를 넣기 전부터 메모리가 쓰이는 이유

빈 Redis에 `DBSIZE`를 보내면 키가 0개일 수 있다. 그렇다고 메모리 사용량이 0일 수는 없다. 프로그램 코드, 서버 상태, 자료구조의 초기 공간, 연결을 처리하는 정보 등은 서버가 살아 있는 것만으로 필요하다. 식당에 손님이 없어도 냉장고와 조리대가 공간을 차지하는 것과 같다. 이 기본 비용을 무시하면 작은 표본으로 전체 용량을 잘못 계산하게 된다.

키 한 개를 추가할 때도 값의 내용만 들어가는 것이 아니다. `goods:1001:name`이라는 이름 자체를 기억해야 하고, 이름으로 값을 찾기 위한 사전 항목이 필요하며, 값이 어떤 형태인지 다루는 관리 정보도 필요하다. 만료가 있으면 만료 시각을 관리하는 비용이 생길 수 있다. 내부 표현은 버전에 따라 달라질 수 있지만, **내용 바이트와 저장 비용이 같지 않다**는 원리는 변하지 않는다.

짧은 값에서는 이런 관리 비용의 비중이 특히 커진다. 값이 5바이트인데 키 이름과 관리 구조가 그보다 큰 상황은 이상하지 않다. 반대로 값이 수백 KiB라면 관리비의 상대 비중은 작아질 수 있지만, 한 번 읽을 때 전송량과 클라이언트 힙 부담이 커진다. 그래서 “작은 키를 합치면 좋다”와 “큰 키를 피하라”는 조언이 모순되지 않는다. 무엇을 공유하고 어느 정도까지 묶을지 균형을 잡는 문제다.

간단한 용량 추정은 다음처럼 시작할 수 있다. 먼저 대표 키를 적은 수만 넣어 표현과 평균 크기를 관찰한다. 다음으로 충분히 큰 표본을 넣기 전후의 전체 사용량 차이를 비교한다. 마지막으로 실제 분포의 긴 꼬리, 즉 일부 매우 큰 값과 많은 필드를 가진 객체를 포함한다. 가장 평범한 사용자 한 명의 키만 측정해서 전체 사용자 수를 곱하면 오래된 계정이나 활동량이 큰 사용자의 비용을 놓칠 수 있다.

| 측정 방식 | 얻기 쉬운 정보 | 놓치기 쉬운 정보 |
|---|---|---|
| 값의 UTF-8 바이트 계산 | 전송할 내용의 크기 | 키와 서버 내부 관리 비용 |
| MEMORY USAGE로 샘플 확인 | 해당 키의 메모리 추정 | 전체 사전의 성장과 연결 비용 |
| 적재 전후 INFO 차이 | 표본 집합의 전체 증가 | 장기 churn과 백그라운드 피크 |
| 실제 부하를 둔 장시간 관찰 | 삭제·재삽입·버퍼·작업 피크 | 재현하지 않은 장애 조건 |

측정값을 늘리는 목적은 복잡한 표를 만들기 위해서가 아니다. 각 측정법이 다른 질문에 답하기 때문이다. 모델 선택에는 키별 비용이 유용하고, 컨테이너 limit 결정에는 실제 범위의 피크가 중요하다. 어떤 결정을 내릴지 먼저 정하면 필요한 지표를 고를 수 있다.

## 2. allocator와 단편화: 지웠는데 RSS가 그대로인 이유

메모리 할당기는 요청받은 바이트 수마다 정확히 같은 크기의 독립 공간을 만드는 단순한 도구가 아니다. 여러 크기 등급과 페이지 단위의 관리 전략을 사용한다. 33바이트를 요청해도 실제 슬롯은 더 클 수 있다. 같은 페이지에 살아 있는 작은 객체가 남아 있으면 다른 객체를 지워도 페이지 전체를 OS에 반환하기 어렵다.

이를 단편화라고 부른다. 내부 단편화는 요청한 크기와 실제 할당 단위 사이의 낭비, 외부 단편화는 사용 중인 조각 사이의 빈 공간 때문에 큰 영역을 효율적으로 활용하기 어려운 상태로 이해하면 된다. Redis에서 지표의 세부 정의는 allocator에 따라 다르므로 용어를 교과서 정의와 기계적으로 일치시키기보다 `allocator_allocated`, `allocator_active`, `allocator_resident` 등의 관계로 읽는다.

`mem_fragmentation_ratio`가 1보다 크다고 즉시 장애는 아니다. 작은 데이터셋에서는 프로세스의 고정 비용이 상대적으로 커져 비율이 높아질 수 있다. 비율 2.0이어도 낭비가 수 MiB면 긴급하지 않을 수 있고, 비율 1.2라도 전체가 수백 GiB라면 큰 비용이다. **비율과 절대 바이트를 함께 확인**한다. 반대로 RSS가 할당량보다 작다면 swap이나 측정 시점 같은 요인을 검토한다. 한 숫자만으로 “메모리 누수”를 확정하지 않는다.

활성 조각 모음이나 allocator 반환 관련 기능은 버전과 빌드 조건에 따라 다르고 CPU 비용도 생긴다. 먼저 증가 원인이 실제 키 증가인지, 응답 버퍼인지, 복제 지연인지, 삭제 후 페이지 잔류인지 구분한다. 원인도 모른 채 조각 모음 설정을 켜면 지연만 늘리고 원래 문제는 남길 수 있다.

## 내부 원리 보충 A. 지운 공간을 왜 즉시 OS에 돌려주지 않을까

메모리 할당기는 매번 OS에 아주 작은 공간을 요청하는 대신 큰 영역을 받아 작은 슬롯으로 나누어 재사용할 수 있다. 예를 들어 여러 크기의 보관함이 있는 창고를 생각해 보자. 33칸짜리 물건이 들어왔는데 준비된 보관함이 48칸 크기라면 남는 공간이 생긴다. 이 예시의 숫자는 특정 allocator의 실제 크기 등급을 의미하지 않는다. 요청 크기와 확보 크기가 다를 수 있다는 원리를 설명하는 가정이다.

물건 몇 개를 버렸어도 같은 선반에 다른 물건이 남아 있으면 선반 전체를 건물 밖으로 내보낼 수 없다. 대신 빈 칸에 다음 물건을 넣는다. Redis에서 키를 지운 뒤 RSS가 즉시 줄지 않아도, 그 공간을 같은 프로세스의 다음 할당에 재사용할 수 있다. 따라서 RSS가 그대로라는 사실만으로 메모리가 영원히 손실됐거나 누수됐다고 단정하지 않는다.

메모리 누수는 더 좁은 개념이다. 프로그램이 더 이상 필요하지 않은 메모리를 적절히 해제하지 못해 사용량이 계속 증가하는 경우 등을 말한다. 업무상 필요하다고 계속 쌓는 키가 늘어나는 것은 용량 또는 보존 정책의 문제일 수 있고, 해제된 공간을 allocator가 보유하는 것은 재사용 정책일 수 있다. 증상이 “메모리가 많다”로 같아 보여도 고쳐야 할 곳은 다르다.

다음 가상 관찰을 비교해 보자. 첫 서비스는 키 수가 매일 늘고 used_memory도 비슷한 기울기로 증가한다. 두 번째 서비스는 키 수와 used_memory가 안정적인데 특정 대량 삭제 후 RSS가 높은 수준에 남는다. 세 번째 서비스는 키 수가 그대로인데 느린 클라이언트가 늘 때 메모리가 증가한다. 첫 번째는 수명과 저장량, 두 번째는 allocator와 페이지 반환, 세 번째는 클라이언트 버퍼가 조사 후보다. 이 후보는 확정 원인이 아니라 다음에 확인할 방향이다.

그래서 운영 대시보드에는 메모리 총량 하나만 두지 않는다. 키 수, 만료와 eviction의 변화, 클라이언트 수, 버퍼 관련 항목, 영속성 작업 상태, RSS를 시간축으로 연결한다. 모든 지표를 높은 빈도로 수집할 필요는 없지만, 사고가 난 뒤 서로 다른 시각의 스크린샷을 맞추는 방식으로는 인과관계를 찾기 어렵다. 같은 시간대의 변화가 중요하다.

단편화 비율을 볼 때도 분모를 이해하자. 아주 작은 데이터셋에서 고정 비용이 몇 MiB만 추가돼도 비율은 크게 보일 수 있다. 큰 데이터셋에서는 작은 비율 차이가 수 GiB가 된다. 따라서 경보를 “비율이 1.5를 넘으면 무조건 심각”처럼 단일 기준으로 정하기보다 절대 증가량, 한도까지의 여유, 지속 시간, 서비스 지연을 함께 고려한다. 이 장은 보편적인 경보 임계값을 제시하지 않는다.

## 3. fork는 전체 데이터를 즉시 복사하는가

`fork()`는 Unix 계열 OS가 부모 프로세스를 바탕으로 자식 프로세스를 만드는 기능이다. Redis는 RDB 저장이나 AOF 재작성에서 자식에게 무거운 파일 생성을 맡기는 경로를 사용한다. 부모는 요청을 계속 처리하고 자식은 일정 시점의 데이터를 읽는다.

여기서 **copy-on-write, COW**가 중요하다. 처음에는 부모와 자식이 같은 물리 페이지를 공유할 수 있다. 부모가 특정 페이지를 변경하려고 하면 이전 내용을 자식이 계속 볼 수 있도록 별도 페이지가 필요해진다. 즉 실제 추가 복사는 “쓰기 때문에 공유를 유지할 수 없게 된 페이지”를 중심으로 발생한다. `fork`를 불렀다는 이유만으로 모든 데이터가 즉시 두 벌이 되는 것도 아니고, “공유하니까 추가 RAM은 거의 필요 없다”도 아니다.

작은 사고 실험을 해 보자. 스냅샷에 40초가 걸리고 그동안 전체 데이터의 넓은 범위가 갱신된다면 많은 페이지가 복사될 수 있다. 반대로 한 카운터만 계속 바꾸면 변경 횟수는 많아도 영향을 받는 페이지 범위가 상대적으로 좁을 수 있다. 하지만 키 하나와 페이지 하나는 같은 단위가 아니다. allocator 배치, 메타데이터 갱신, 해시 테이블 변화에 따라 추가 페이지가 수정되므로 “초당 쓰기 개수 × 값 크기”만으로 COW를 정확히 계산할 수 없다.

`fork` 자체에도 비용이 있다. 데이터 내용을 전부 복사하지 않아도 페이지 테이블 등 프로세스 메모리 관리 정보를 다루어야 한다. 큰 주소 공간과 가상화 환경에서 이 단계의 일시 정지가 p99 지연에 영향을 줄 수 있다. 그래서 `latest_fork_usec`, 저장 시간, COW 관련 `INFO persistence` 필드를 함께 기록한다. 필드 존재 여부는 버전에 따라 다르며, 단위가 마이크로초인지 바이트인지 반드시 확인한다.

## 내부 원리 보충 B. COW를 네 장의 종이로 이해하기

이제 부모 Redis와 저장용 자식 프로세스가 있다고 하자. 설명을 위해 데이터가 물리 페이지 P0, P1, P2, P3 네 장에 들어 있다고 가정한다. fork 직후에는 부모와 자식이 같은 네 장을 바라볼 수 있다. 자식은 저장 시점의 내용을 파일로 만들고, 부모는 새 요청을 처리한다. 서로 다른 시점의 데이터를 봐야 한다는 요구 때문에 쓰기 시 분리가 필요해진다.

부모가 P1의 내용을 변경하려고 하면, 자식이 보던 예전 P1을 보존하면서 부모가 새 내용을 가질 수 있는 별도 페이지가 필요하다. 설명상 새 페이지를 P1-new라고 부르자. 이제 자식은 예전 P1을 읽고 부모는 변경된 P1-new를 사용한다. 핵심은 **수정한 값만큼의 바이트가 아니라 페이지 단위의 추가 비용이 생길 수 있다는 것**이다.

| 시간 | 부모 작업 | 자식이 유지하는 시점 | 추가 공간을 이해하는 관점 |
|---|---|---|---|
| T0 | fork 전 일반 처리 | 자식 없음 | 원래 페이지들 |
| T1 | fork 직후 | T1 시점의 데이터 | 초기 공유가 가능 |
| T2 | P1에 속한 값 변경 | 예전 P1이 필요 | 변경 페이지 분리 가능 |
| T3 | 같은 새 P1을 다시 변경 | 여전히 예전 P1 | 같은 이유로 매번 전체 페이지가 무한 증가하는 것은 아님 |
| T4 | P2에 속한 값 변경 | 예전 P2도 필요 | 다른 페이지까지 분리 범위 확대 |
| T5 | 자식 저장 완료·종료 | 더 이상 이전 시점 불필요 | 공유와 할당 상태가 다시 달라짐 |

“쓰기 요청이 100만 번이면 페이지도 100만 개 복사되나요?”라는 질문이 여기서 나온다. 단순히 그렇지는 않다. 같은 좁은 영역을 반복 갱신하는 패턴과 넓게 퍼진 키들을 갱신하는 패턴은 다르다. 다만 Redis의 명령은 값 본문만 바꾸는 것이 아니라 객체 정보나 사전 관리 구조도 바꿀 수 있으므로, 애플리케이션의 키 주소만으로 물리 페이지 접근을 정확히 예측할 수는 없다.

반대로 “값은 8바이트 카운터니까 COW도 8바이트겠죠?”도 틀리다. 변경이 필요한 페이지와 관리 정보가 비용의 단위에 영향을 준다. 작은 값의 잦은 갱신이 넓은 데이터셋에 퍼져 있으면 상당한 메모리 피크를 만들 수 있다. 따라서 쓰기 RPS와 평균 값 크기만으로 저장 중 추가 RAM을 확정하는 공식은 만들기 어렵다.

자식 작업의 시간도 중요하다. 같은 쓰기 패턴이라도 저장이 5초 안에 끝나는 경우와 60초 동안 계속되는 경우는 겹치는 변경 범위가 다를 수 있다. 디스크가 느려지거나 저장할 데이터가 많아지면 자식이 살아 있는 시간이 길어지고 그동안 변경되는 페이지가 늘 수 있다. 여기서 디스크 지연이 메모리 문제로 이어지는 연결고리를 볼 수 있다. “메모리 장애니까 디스크는 상관없다”는 분류가 위험한 이유다.

자식이 종료되면 반드시 RSS가 즉시 처음 값으로 돌아온다는 보장도 없다. OS와 allocator가 메모리를 계산하고 반환하는 방식, 부모가 그동안 실제로 추가한 데이터, 버퍼 상태가 함께 작용한다. 실험에서는 시작 전, 작업 중 최고점, 종료 직후, 안정화 이후를 나누어 기록한다. 최고점만 보고 영구 누수를 주장하거나 종료 직후만 보고 피크가 없었다고 주장하지 않는다.

## 4. maxmemory가 OOM killer를 막지 못하는 경로

OOM은 Out Of Memory다. 두 종류를 구분해야 한다. Redis가 자체 메모리 정책에 따라 명령에 OOM 오류를 반환하는 경우와, OS가 실제 메모리 압박 때문에 프로세스를 종료하는 경우다. 전자는 서버가 살아 있을 수 있고 읽기도 가능할 수 있다. 후자는 연결이 끊기고 프로세스가 사라지거나 컨테이너가 재시작한다.

예를 들어 컨테이너 한도가 4 GiB인데 `maxmemory`를 4 GiB로 잡았다고 하자. 데이터와 일반 관리비용이 한도 부근에 도달한 순간 RDB 작업을 시작하면 COW와 프로세스 관련 비용이 더해진다. Redis 축출 계산에 포함되지 않는 버퍼도 있다. OS 관점에서는 한도를 넘었는데 Redis 관점에서는 아직 축출로 모두 해결하지 못하는 상황이 생길 수 있다.

이를 막는 방법은 한 숫자를 보수적으로 정하는 것뿐 아니라 **평상시 예산과 작업 중 피크 예산을 구분**하는 것이다.

```text
환경의 메모리 한도
  ≥ Redis 평상시 상주량
  + 저장/재작성/재동기화 시 추가 피크
  + 같은 제한 범위의 다른 소비
  + 측정 오차와 성장에 대한 안전 여유
```

이 식은 설계용 사고 모델이며 모든 측정치를 무조건 더하라는 회계식은 아니다. 공유 메모리와 cgroup 계산이 겹칠 수 있으므로 최종적으로는 해당 환경에서 관찰한 피크를 검증해야 한다. “RAM의 80%면 안전하다” 같은 보편적 비율은 없다. 쓰기 패턴과 작업 시간이 다르면 필요한 여유가 달라진다.

## 내부 원리 보충 C. Redis의 OOM과 컨테이너 OOM을 사건 순서로 구별하기

Redis가 명령 오류를 반환하는 상황부터 보자. 클라이언트가 메모리를 늘리는 쓰기를 보낸다. Redis가 자신의 정책과 사용량을 판단한다. 요청을 처리할 수 없다고 판단하면 오류 응답을 보낸다. 이 경로에서는 서버 프로세스가 살아 있고 오류를 만들 능력도 있다. 애플리케이션이 명령 오류를 받았다는 사실 자체가 한 종류의 증거다.

컨테이너 메모리 한도에 도달해 OS가 프로세스를 종료하는 상황은 다르다. Redis 내부 정책이 어떤 값을 사용하든 OS는 자신이 관리하는 범위의 메모리를 기준으로 판단한다. 프로세스가 종료되면 Redis는 정상 오류 응답을 보낼 기회를 얻지 못할 수 있다. 클라이언트에서는 연결 종료나 타임아웃으로 보이고, 컨테이너 관리 계층에는 종료 이유와 재시작 기록이 남을 수 있다.

세 번째로 Java 애플리케이션 자체가 메모리 부족을 겪을 수 있다. Redis에서 큰 값을 읽은 뒤 Java가 응답 버퍼, 문자열, 역직렬화 객체를 동시에 보유하면 클라이언트 힙이 부족할 수 있다. 이 경우 Redis 서버의 maxmemory를 조정해도 Java 힙 문제를 직접 해결하지 못한다. 같은 “OOM”이라는 단어라도 **어느 프로세스가 어떤 자원을 다루다 실패했는지**부터 구분해야 한다.

| 증상 | 첫 조사 위치 | 성급한 조치의 예 | 더 나은 다음 질문 |
|---|---|---|---|
| Redis가 명령 오류 응답 | Redis 정책·사용량·오류 종류 | 무조건 인스턴스 재시작 | 어떤 명령이 왜 거절됐나? |
| Redis 프로세스 종료 | 컨테이너·커널 이벤트 | 클라이언트 timeout만 증가 | 실제 종료 원인과 피크는? |
| Java OutOfMemoryError | JVM 힙·응답 크기·동시성 | Redis maxmemory 증가 | 어떤 객체가 얼마나 겹쳤나? |
| BGSAVE 시작 실패 | fork 오류·OS 정책·제한 | 데이터가 적으니 오류 무시 | 실패 원문과 제한 범위는? |

관측 자료가 충분하지 않으면 “메모리 부족으로 보인다”처럼 가설의 수준을 표시한다. 확정하지 못한 원인을 확정한 것처럼 기록하면 후속 대응이 잘못된 전제 위에 쌓인다. 운영 기록에서 사실과 추측을 구분하는 것은 문체의 문제가 아니라 복구 정확성의 문제다.

## 5. Linux overcommit, THP, swap을 읽는 자세

**overcommit**은 프로세스들이 요청한 가상 메모리를 OS가 어떤 기준으로 허용할지에 관한 정책이다. Redis 공식 운영 문서는 Linux에서 `vm.overcommit_memory=1`을 권고한다. 이는 `fork` 시 실제로 전부 복사하지 않을 메모리를 지나치게 보수적으로 평가해 실패하는 문제를 완화하려는 목적이다. 하지만 이것이 RAM을 만들어 주거나 OOM을 방지하는 기능은 아니다. 허용 후 실제 페이지 수요가 커지면 여전히 메모리가 부족할 수 있다.

**THP**, Transparent Huge Pages는 작은 페이지보다 큰 단위의 페이지를 투명하게 사용하려는 커널 기능이다. 일부 워크로드에는 유리하지만 Redis의 지연과 COW에 좋지 않은 영향을 줄 수 있어 공식 문서는 비활성화 검토를 안내한다. 배포판과 커널, Redis의 THP 관련 지원 상태를 확인하고 운영 정책으로 관리해야 한다. 교육 문서의 `echo` 명령을 공용 호스트에서 무단 실행하면 다른 서비스에까지 영향을 준다.

**swap**은 메모리 페이지를 저장 장치로 내보내 RAM 압력을 완화하는 장치다. 프로세스가 즉시 죽는 것을 완화할 수 있지만, Redis가 필요한 페이지를 디스크에서 다시 가져오면 응답 시간이 크게 늘 수 있다. 따라서 “swap은 무조건 켜라”와 “무조건 꺼라” 모두 불완전한 답이다. 서비스 지연 목표, 컨테이너 swap 정책, 호스트 공유 여부, OOM 대응 전략을 함께 결정한다. 정상상태에서 swap에 의존하도록 용량을 설계하지 않는 것이 핵심이다.

이 장의 실습은 커널 설정을 변경하지 않는다. 읽기만 하여 현재 상태를 이해한다. 실제 변경은 플랫폼 담당자와 영향 범위를 확인하고 재부팅 후 지속 여부까지 검증할 운영 작업이다. [Redis 운영 가이드](https://redis.io/docs/latest/operate/oss_and_stack/management/admin/), [지연 진단](https://redis.io/docs/latest/operate/oss_and_stack/management/optimization/latency/)

## 6. 수치 예제로 만드는 메모리 예산

어떤 서비스의 실제 측정값이 다음과 같다고 **가정**하자. 이는 벤치마크 결과가 아니라 예산 계산 예시다.

| 항목 | 가정한 값 | 확인 방법의 예 |
|---|---:|---|
| 평상시 Redis RSS | 5.2 GiB | INFO와 OS 지표 비교 |
| 백그라운드 저장 중 추가 피크 | 1.8 GiB | 부하 재현 중 cgroup 피크 |
| 같은 제한 범위의 부가 소비 | 0.4 GiB | exporter 등 프로세스별 관찰 |
| 성장 및 관측 오차 여유 | 1.0 GiB | 정책으로 결정 |

단순 모델의 합은 8.4 GiB다. 따라서 이 조건에서 8 GiB 제한은 부족할 가능성이 높다. 10 GiB를 선택한다고 바로 합격하는 것은 아니다. 최악의 저장 시간이 길어지면 COW 피크도 커질 수 있고, 느린 복제본 때문에 버퍼가 늘 수 있다. 장애 시 복구와 재동기화가 정상 부하보다 더 큰 피크를 만들기도 한다.

평균값만 모으면 위험하다. 저장이 없는 평일 오전의 RSS 평균은 주말 배치와 백업이 겹치는 순간을 설명하지 못한다. 부하 시험에는 정상 읽기/쓰기, 저장 작업, 느린 디스크, 복제 재연결 등 실제 위험 구간을 포함하되 각각 격리해 원인을 알 수 있게 한다. 처음부터 모두 겹치면 피크는 보이지만 왜 피크가 생겼는지 알 수 없다.

## 계산 보충. 단위와 중복 집계를 피하는 Java 예산 모델

메모리 예산을 계산할 때는 기계적으로 더하기 전에 항목의 범위를 맞춰야 한다. 아래 코드는 이미 중복이 제거된 측정값을 입력받는다고 가정한다. 실제 Redis 정보를 자동 수집하지 않고, **관측값을 비교하는 산술과 정책을 분리하는 예제**다. Java 21에서 독립 실행할 수 있다.

```java
public final class RedisMemoryBudget {
    private static final long MIB = 1024L * 1024L;

    record Budget(long limitBytes, long baselineBytes,
                  long extraPeakBytes, long reserveBytes) {
        Budget {
            if (limitBytes <= 0 || baselineBytes < 0
                    || extraPeakBytes < 0 || reserveBytes < 0) {
                throw new IllegalArgumentException("invalid byte count");
            }
        }

        long requiredBytes() {
            return Math.addExact(Math.addExact(baselineBytes, extraPeakBytes),
                    reserveBytes);
        }

        long remainingBytes() {
            return Math.subtractExact(limitBytes, requiredBytes());
        }

        boolean fitsObservedScenario() {
            return remainingBytes() >= 0;
        }
    }

    static long mib(long value) {
        return Math.multiplyExact(value, MIB);
    }

    public static void main(String[] args) {
        Budget normalSave = new Budget(mib(8192), mib(5200),
                mib(1800), mib(800));
        Budget slowSave = new Budget(mib(8192), mib(5200),
                mib(2600), mib(800));

        if (!normalSave.fitsObservedScenario()) {
            throw new AssertionError("first scenario should fit");
        }
        if (slowSave.fitsObservedScenario()) {
            throw new AssertionError("second scenario should exceed limit");
        }
        System.out.println("normal remaining MiB="
                + normalSave.remainingBytes() / MIB);
        System.out.println("slow remaining MiB="
                + slowSave.remainingBytes() / MIB);
    }
}
```


위 코드의 `Math.addExact`, `Math.multiplyExact`는 정수 범위를 넘는 연산을 조용히 잘못된 숫자로 바꾸는 대신 예외로 드러낸다. 실제 예시의 숫자는 작지만, 용량 계산 도구가 다양한 입력을 받는다면 잘못된 단위나 지나치게 큰 값을 조기에 발견하는 데 도움이 된다. 음수 여유는 남는 공간이 아니라 부족분을 뜻한다.

첫 시나리오는 `5200 + 1800 + 800 = 7800 MiB`이므로 8192 MiB 한도에서 392 MiB가 남는다. 두 번째는 추가 피크만 2600 MiB로 늘어 합이 8600 MiB가 된다. 한도보다 408 MiB 많다. 저장이 느려진 상황에서 추가 피크가 커졌다는 **가상 관측값**을 넣은 것이다. 이 계산이 모든 서버에서 실제로 그런 피크가 나온다는 뜻은 아니다.

메서드 이름을 `isSafe` 대신 `fitsObservedScenario`로 정한 이유가 있다. 산술적으로 들어간다는 사실은 입력한 시나리오에 대해서만 성립한다. 측정하지 않은 복제 지연이나 다른 작업이 겹치면 결과가 달라질 수 있다. 코드의 이름이 보장 범위를 과장하지 않게 하는 것도 운영 도구 설계의 일부다.

특히 `baselineBytes`에 이미 컨테이너 전체 사용량을 넣었다면 exporter 메모리를 다시 더하면 안 된다. 반대로 Redis RSS만 넣었다면 같은 제한 범위의 다른 소비가 빠졌을 수 있다. 예제의 record에는 항목 수를 적게 두었지만, 실제 운영 문서에는 측정 범위와 수집 시각을 반드시 함께 적는다. 단위가 같은 숫자라도 측정 범위가 다르면 바로 더할 수 없다.

## 7. 격리 실습: 메모리 지표의 층을 관찰하기

아래는 로컬 전용 작은 인스턴스를 만드는 예시다. 업무 서버에 연결하지 않는다. `redis-server`, `redis-cli`, Python 3이 준비되어 있어야 한다. 포트 16380이 비어 있는지 확인한다. 서버는 별도 터미널에서 포그라운드로 실행한다.

```bash
LAB=$(mktemp -d /tmp/redis-memory-lab.XXXXXX)
redis-server --bind 127.0.0.1 --port 16380 \
  --protected-mode yes --daemonize no --dir "$LAB" \
  --save "" --appendonly no --maxmemory 64mb \
  --maxmemory-policy noeviction
```

다른 터미널에서 기준값을 저장한다.

```bash
redis-cli -h 127.0.0.1 -p 16380 INFO server
redis-cli -h 127.0.0.1 -p 16380 INFO memory
redis-cli -h 127.0.0.1 -p 16380 INFO persistence
```

이제 의도적으로 작은 데이터만 넣는다. Python 표준 라이브러리로 RESP 형식을 만들어 `redis-cli --pipe`에 전달하므로 외부 Python 패키지는 필요하지 않다. RESP는 Redis 명령을 전송하는 프로토콜이며, 아래에서는 각 문자열의 바이트 길이를 명시한다.

```bash
python3 - <<'PY' | redis-cli -h 127.0.0.1 -p 16380 --pipe
import sys
for i in range(5000):
    parts = [b'SET', f'lab:memory:{i}'.encode(), b'x' * 256]
    out = b'*3\r\n'
    for p in parts:
        out += b'$' + str(len(p)).encode() + b'\r\n' + p + b'\r\n'
    sys.stdout.buffer.write(out)
PY
redis-cli -h 127.0.0.1 -p 16380 DBSIZE
redis-cli -h 127.0.0.1 -p 16380 INFO memory
redis-cli -h 127.0.0.1 -p 16380 MEMORY USAGE lab:memory:1
```

예상 관찰은 값의 순수 바이트 합보다 전체 메모리 증가가 크다는 것이다. 정확한 증가량은 버전, allocator, 키 길이, 인코딩에 따라 다르므로 이 교재가 고정 숫자를 정답으로 제시하지 않는다. `DBSIZE`는 이 전용 인스턴스에서 5,000개를 기대할 수 있지만, 재실행이나 기존 데이터가 있다면 다른 값이 나올 수 있다. `--pipe` 요약에서 오류가 없는지 먼저 확인한다.

이어서 `BGSAVE`를 한 번 요청하고 `INFO persistence`를 관찰할 수 있다. 작은 데이터에서는 너무 빨리 끝나 진행 중 상태를 놓칠 수 있다. 그것은 실패가 아니라 표본 간격보다 작업이 짧았을 가능성이다. `rdb_last_bgsave_status`와 로그를 확인한다. **COW를 보기 위해 무작정 수백만 키를 채우거나 호스트 메모리를 고갈시키지 않는다.** 피크 실험은 제한된 별도 환경과 중단 기준을 갖춘 뒤 수행한다.

읽기 전용 OS 확인 예시는 다음과 같다. 파일이 없으면 해당 기능이나 경로가 환경에 제공되지 않는다는 뜻일 수 있다.

```bash
cat /proc/sys/vm/overcommit_memory
cat /sys/kernel/mm/transparent_hugepage/enabled
# cgroup v2를 쓰는 환경의 예시이며 경로와 가시성은 환경마다 다르다.
cat /sys/fs/cgroup/memory.max
cat /sys/fs/cgroup/memory.current
cat /sys/fs/cgroup/memory.events
```

실습 종료는 이 인스턴스에만 `SHUTDOWN NOSAVE`를 보낸다. 실습 경로의 파일을 업무 백업으로 착각하지 않도록 분리해 둔다. 여기 적힌 관찰 절차는 재현 가이드이며 실제 환경에서 테스트했다고 주장하는 측정 결과가 아니다.

## 실험 보충. 한 번에 한 조건만 바꾸어야 하는 이유

메모리 실험에서 데이터 크기, 키 개수, TTL, eviction, 저장 방식, 동시성을 한꺼번에 바꾸면 결과가 달라져도 무엇 때문인지 알기 어렵다. 과학 실험처럼 다른 조건을 가능한 한 고정하고 한 변수씩 바꾼다. 처음에는 서버를 비운 상태의 기준값을 기록하고, 동일한 데이터 생성 규칙으로 적재한 뒤 변화량을 본다. 그 다음에 저장 작업이나 읽기 부하를 추가한다.

권장하는 실험 순서는 **표현 비용 → 삭제 후 상태 → 정상 부하 → 백그라운드 작업 중 피크**다. 표현 비용을 모르면 키를 많이 넣어서 생긴 증가와 COW 증가를 구별하기 어렵다. 삭제 후 상태를 모르면 allocator가 보유한 공간을 저장 작업이 남긴 누수로 오해할 수 있다. 단계마다 정상 상태를 이해한 뒤 다음 조건을 추가하면 설명력이 생긴다.

작은 실험에서 BGSAVE 진행 상태를 못 봤다고 데이터 양을 무작정 늘리지 않는다. 작업이 관측 주기보다 빨리 끝났을 수 있다. 마지막 작업 결과와 시간, 로그를 먼저 확인한다. 피크를 관찰하려면 더 촘촘한 샘플링이 필요할 수 있지만 수집 자체도 비용을 만든다. 운영 데이터 전체에 무거운 명령을 반복하는 방식으로 정밀도를 높이려 하면 검사 때문에 문제가 생길 수 있다.

결과를 기록할 때는 평균뿐 아니라 최대값과 기간을 함께 적는다. “RSS 최대 2 GiB”는 언제부터 언제까지 얼마나 자주 관찰한 값인지 없으면 의미가 제한된다. 1초 간격으로 측정한 최고점은 그 사이의 짧은 피크를 놓칠 수 있다. 측정값이 거짓이라는 뜻이 아니라 측정 방법의 해상도를 함께 해석해야 한다는 뜻이다.

마지막으로 실험 종료 조건을 먼저 정한다. 학습 인스턴스에 작은 한도를 두고, 오류나 예상 밖 증가가 보이면 더 적재하지 않는다. 목표는 메모리를 실제로 고갈시키는 데 성공하는 것이 아니라 지표의 관계를 이해하는 것이다. 메모리를 모두 채우지 않고도 내용 바이트, 할당량, RSS가 다르다는 사실은 충분히 관찰할 수 있다.

## 8. Java 서비스에서 메모리 사고가 시작되는 순간

서버 메모리 부족이 늘 서버 설정만의 문제는 아니다. 예를 들어 Java 코드가 사용자 입력을 그대로 키에 포함하고 TTL 없이 저장하면 키 공간이 사실상 무한해진다. 사용자별 임시 검색 결과를 매번 다른 UUID 키로 저장하면서 수명을 주지 않는 경우가 대표적이다. 하나의 값은 작아도 하루에 수백만 개가 쌓이면 관리 비용이 커진다.

```java
// 짧은 수명의 재생성 가능한 결과에 한정한 개념 예시
String key = "search:result:" + requestId;
redisTemplate.opsForValue().set(key, resultJson, Duration.ofMinutes(3));
```

TTL만 넣었다고 모든 문제가 끝나지는 않는다. 같은 시각에 만료가 몰리면 원본 DB로 요청이 급증할 수 있고, 큰 JSON을 통째로 읽으면 네트워크와 클라이언트 힙에도 부담이 된다. “Redis는 메모리 DB니까 빠르다”는 말은 무제한 크기의 객체를 안전하게 저장해도 된다는 허가가 아니다. 요청 크기 제한, 키 수명, 직렬화 크기, 최대 결과 개수, 실패 시 원본 접근 정책을 애플리케이션 설계에 포함한다.

클라이언트 타임아웃이 발생했을 때 커넥션 풀을 무작정 늘리면 대기 중인 요청과 서버 버퍼가 더 늘 수 있다. 재시도가 원래 부하를 증폭시키는지도 확인해야 한다. 타임아웃은 “명령이 실행되지 않았다”는 증거가 아니므로, 상태 변경 명령에는 멱등성이나 중복 처리 대응이 필요하다. 메모리 관리는 서버와 애플리케이션 사이의 계약이다.

## 애플리케이션 보충. 큰 응답 하나가 서버와 JVM 양쪽을 압박한다

입고 화면에서 “오늘 처리한 상품 전체”를 Redis Hash 하나에 모아 저장하고 `HGETALL`로 가져온다고 가정하자. 개발 데이터에서는 상품이 20개라 문제가 없었다. 운영에서 상품 수와 각 상품의 속성이 증가하면 명령 하나가 훨씬 많은 데이터를 읽고 응답한다. 요청 횟수는 여전히 한 번인데 작업량은 커진다. **명령 수가 작다는 것과 처리량이 작다는 것은 다르다.**

서버는 응답을 준비하고 네트워크로 보내야 한다. 클라이언트가 천천히 읽거나 네트워크가 느리면 출력 버퍼가 늘 수 있다. Java는 받은 바이트를 해석하고 문자열이나 객체를 만든다. JSON 역직렬화까지 수행하면 원시 응답과 변환된 객체가 겹쳐 존재할 수 있다. 화면에 보이는 최종 데이터 크기만으로 순간 힙 사용량을 계산하면 이런 중간 표현을 놓친다.

이 요청이 동시에 100개 들어오면 개별 응답의 크기에 동시성이 곱해진다. 하지만 단순히 `평균 응답 크기 × 100`만으로 정확한 힙을 계산할 수도 없다. 버퍼 재사용, 객체 표현, GC 시점, 다른 요청의 생존 시간이 영향을 준다. 계산은 위험을 발견하는 출발점이고 실제 피크는 제한된 부하 시험과 프로파일링으로 확인해야 한다.

따라서 방어는 여러 단계에 둔다. API가 조회할 최대 기간과 최대 결과 수를 정한다. 데이터 모델을 시간 또는 업무 객체의 경계로 나눈다. 필요한 필드만 읽는다. 동시에 수행할 큰 조회의 수를 제한한다. 결과를 한꺼번에 반환해야 한다면 비동기 보고서 생성처럼 다른 경로를 고려한다. 커넥션 풀을 늘리는 것은 이런 작업량을 없애 주지 않는다.

Spring 서비스에서는 다음처럼 **입력 상한을 명시하는 정책**을 작은 코드로 시작할 수 있다. 이 예시는 명령을 어떤 단위로 보낼지 정하는 출발점이지 Redis의 모든 대량 조회 문제를 해결하는 완성 코드가 아니다.

```java
import java.util.List;

public final class GoodsLookupPolicy {
    private static final int MAX_IDS_PER_REQUEST = 100;

    public static List<Long> validate(List<Long> goodsIds) {
        if (goodsIds == null || goodsIds.isEmpty()) {
            throw new IllegalArgumentException("at least one goods ID is required");
        }
        if (goodsIds.size() > MAX_IDS_PER_REQUEST) {
            throw new IllegalArgumentException("too many goods IDs");
        }
        for (Long id : goodsIds) {
            if (id == null || id <= 0) {
                throw new IllegalArgumentException("invalid goods ID");
            }
        }
        return List.copyOf(goodsIds);
    }
}
```

100이라는 값은 예시다. 실제 상한은 응답 크기와 지연 목표를 측정해 정한다. ID 개수만 제한해도 값 하나가 매우 크면 여전히 위험하므로 값의 최대 크기와 결과 바이트도 별도로 고려해야 한다. 또한 중복 ID를 허용할지, 순서를 유지할지, 일부 키가 없을 때 어떻게 표시할지 API 계약을 정한다. 자원 관리와 업무 응답의 의미가 만나는 지점이다.

## 9. 장애 시나리오: 세 가지 OOM을 구분하는 진단 순서

**상황 1: 애플리케이션 로그에 OOM command 오류가 있지만 PING은 성공한다.** Redis 자체 정책일 가능성을 확인한다. `maxmemory`, 정책, `used_memory`, `evicted_keys`, 명령별 오류를 본다. 중요한 상태를 지키기 위해 `noeviction`을 사용했다면 무작정 eviction 정책을 바꾸지 않는다. 저장량과 수명 정책을 조정하거나 용량을 확장하는 편이 맞을 수 있다.

**상황 2: 저장 작업과 동시에 프로세스가 사라진다.** OS와 컨테이너 이벤트에서 OOM 종료 증거를 찾는다. Redis 로그의 마지막 줄에 오류가 없다고 Redis가 정상 종료한 것은 아니다. 커널이 강제로 종료하면 로그를 남길 기회가 없을 수 있다. 같은 시간의 cgroup 피크, COW, 디스크 지연을 비교한다. 저장이 느릴수록 공유 페이지가 깨지는 시간 창이 길어질 수 있다.

**상황 3: 메모리는 남는데 BGSAVE가 fork 오류로 실패한다.** 실제 사용 가능한 메모리뿐 아니라 overcommit 정책, 프로세스 제한, 컨테이너 제한, 커널 로그를 확인한다. 모든 fork 실패가 RAM 부족만으로 설명되지는 않는다. 오류 원문과 발생 시각을 보존하고 권한 있는 운영자에게 해당 OS 정책을 검토하게 한다.

세 상황의 공통 원칙은 무작정 재시작하지 않는 것이다. 재시작이 잠깐 RSS를 줄일 수 있어도 원인을 가리고, 복구와 전체 재동기화를 유발해 더 큰 피크를 만들 수도 있다. 안정화 조치와 원인 규명을 구분하고, 조치마다 기대 효과와 반증 조건을 적는다.

## 10. 운영 전 점검과 학습 과제

운영 준비 문서에는 “메모리 16GB” 한 줄 대신 한도의 기준을 적는다. 호스트 RAM인지 컨테이너 limit인지, 그 안에 무엇이 포함되는지, 평상시 RSS와 작업 피크는 얼마인지 명확히 한다. GB와 GiB도 구분한다. 1 GB는 십진 바이트 단위이고 1 GiB는 2의 거듭제곱 단위이므로 대형 환경에서는 차이가 무시할 수준이 아니다.

복제본도 동일하게 점검한다. 복제본은 읽기 전용이어도 메모리를 쓰며 기본 동작에서 primary의 축출 결정을 따라간다. primary보다 작은 컨테이너에 넣고 같은 `maxmemory`를 적었다고 안전해지지 않는다. 승격 뒤 정책이 달라지는지도 확인한다. 이를 자세히 다루는 08장까지 연결해서 읽으면 장애 전환 시 용량 문제가 왜 발생하는지 이해할 수 있다.

스스로 풀어 볼 문제: 같은 데이터와 같은 초당 쓰기 수를 가진 두 서버가 있다. A는 같은 1% 키만 갱신하고, B는 전체 키를 골고루 갱신한다. 저장 중 COW 피크가 같을까? 일반적으로 다를 수 있다. 핵심 변수는 쓰기 횟수만이 아니라 수정되는 페이지 범위와 저장 지속 시간이다. 단, allocator와 부가 구조의 쓰기까지 영향을 주므로 이론만으로 정확한 바이트 수를 예측할 수는 없다.

## 면접 질문과 상세 답변

<details><summary>1. used_memory와 used_memory_rss의 차이는 무엇인가요?</summary>

used_memory는 Redis가 할당기를 통해 사용하는 메모리 관점이고, RSS는 OS에서 실제 상주하는 메모리 관점이다. allocator가 확보한 뒤 아직 반환하지 않은 페이지, 단편화, 프로세스 부가 비용과 swap 등 때문에 달라질 수 있다. 둘 중 하나가 틀린 값이 아니라 측정 대상이 다르다. 추세와 절대 차이, allocator 세부 지표, OS 제한을 함께 보아야 하며 작은 데이터셋의 비율만 보고 누수를 단정하면 안 된다.

</details>

<details><summary>2. maxmemory를 설정했는데도 컨테이너가 OOMKilled 된 이유는요?</summary>

maxmemory는 프로세스 전체의 물리 메모리 상한이 아니다. 축출 계산에서 제외되는 일부 버퍼, allocator 상주 공간, fork 중 COW 등으로 OS가 보는 소비가 더 커질 수 있다. 컨테이너 한도에 여유가 없으면 Redis가 자체 정책으로 충분히 조절하기 전에 커널이 종료할 수 있다. 먼저 종료 이벤트를 확인하고, 정상 부하뿐 아니라 저장·재작성·재동기화 구간의 피크를 기준으로 예산을 다시 잡는다.

</details>

<details><summary>3. fork를 하면 메모리가 바로 두 배가 되나요?</summary>

일반적인 COW 경로에서는 물리 데이터를 즉시 전부 복사하지 않고 페이지를 공유한다. 이후 부모가 공유 페이지를 수정하면 별도 복사 비용이 발생한다. 쓰기가 넓은 영역에 걸치고 자식 작업이 오래 걸리면 추가 소비가 크게 늘어날 수 있다. 따라서 항상 두 배라고 말하는 것도, 거의 추가 비용이 없다고 말하는 것도 틀리다. fork 자체의 페이지 테이블 관련 지연과 이후 COW 소비를 분리해 설명하는 것이 좋다.

</details>

<details><summary>4. overcommit_memory=1이면 메모리 부족이 해결되나요?</summary>

아니다. 이 설정은 가상 메모리 요청을 허용하는 커널 판단을 바꾼다. COW를 활용하는 fork가 보수적인 예약 판단 때문에 거절되는 상황을 줄일 수 있지만 물리 RAM을 추가하지 않는다. 실제 페이지 수요가 한도를 넘으면 여전히 OOM이 발생할 수 있다. 운영 환경 전체에 영향을 주는 커널 정책이므로 승인된 변경 절차와 실제 여유 용량 검증이 함께 필요하다.

</details>

<details><summary>5. swap이 있으면 Redis 운영은 안전한가요?</summary>

일부 메모리 압박에서 즉시 종료를 늦출 수 있지만 응답 지연이 크게 늘어 서비스가 사실상 멈춘 것처럼 보일 수 있다. 안전성을 가용 프로세스 수명만으로 판단하면 안 되고 지연 SLO와 함께 보아야 한다. swap 사용을 정상 용량의 일부로 계획하지 말고, 호스트와 컨테이너 정책, 지연 경보, OOM 대응을 함께 설계한다. 환경마다 제약이 달라 일률적인 한 줄 답은 부정확하다.

</details>

<details><summary>6. 키를 많이 삭제했는데 RSS가 줄지 않으면 메모리 누수인가요?</summary>

반드시 그렇지는 않다. Redis 내부에서는 해제되어 재사용 가능하지만 allocator가 페이지를 보유하거나 같은 페이지에 다른 객체가 남아 OS에 반환하지 못할 수 있다. used_memory 감소 여부, allocator 지표, 이후 재사용 패턴을 함께 본다. RSS만 보고 재시작부터 하면 원인을 가리고 내구성·복제 비용을 추가할 수 있다. 실제 누수 가설은 객체 수와 할당량이 설명되지 않게 계속 증가하는지 같은 증거로 검증한다.

</details>

<details><summary>7. 메모리 단편화 비율은 어느 숫자부터 위험한가요?</summary>

모든 환경에 통하는 숫자는 없다. 비율은 기준량이 작을 때 과장될 수 있고, 큰 데이터셋에서는 낮은 비율도 상당한 절대 바이트를 뜻한다. 물리 한도와의 여유, 증가 추세, 작업 피크, 지연을 함께 판단한다. 경보는 비율 하나보다 사용 가능 여유와 OOM까지의 성장 속도, 관련 작업 상태를 함께 보도록 설계하는 편이 실용적이다.

</details>

<details><summary>8. 메모리 용량 시험에는 무엇을 포함해야 하나요?</summary>

실제 키 길이와 값 크기 분포, 자료형, TTL, 직렬화 방식, 읽기/쓰기 비율뿐 아니라 저장과 AOF 재작성, 느린 복제본과 재동기화도 고려한다. 같은 바이트 크기의 균일한 SET만으로 운영 피크를 대표할 수 없다. 각 요인을 먼저 분리해 측정하고, 실제로 겹칠 수 있는 조합을 제한된 환경에서 시험한다. 중단 기준과 컨테이너 한도를 두어 실험 자체가 공유 환경의 장애가 되지 않게 해야 한다.

</details>

## 추가 면접 문답: 메모리 숫자를 근거로 설명하기

<details><summary>9. 키 수가 같으면 메모리 사용량도 같아야 하지 않나요?</summary>

아니다. 값의 크기, 키 이름 길이, 자료구조의 필드 수, 내부 인코딩, 만료 관리, 연결과 버퍼, allocator 상태가 달라질 수 있다. 1,000개의 상품명과 1,000개의 전체 상품 JSON은 같은 키 수라도 저장 비용이 크게 다를 수 있다. 키 개수는 용량을 설명하는 여러 축 중 하나다.

면접에서는 먼저 데이터셋 자체의 크기 변화와 데이터셋 바깥의 소비를 나눈다. 그 다음 대표 키의 크기 분포와 INFO memory, 클라이언트 상태, 영속성 작업을 연결한다. 평균 키 크기만 보고 일부 거대한 키를 놓치지 않도록 상위 크기와 최대값도 관찰해야 한다.

</details>

<details><summary>10. 부모와 자식의 RSS를 더하면 저장 중 메모리 사용량 아닌가요?</summary>

공유 페이지가 있으면 중복 집계할 수 있다. fork 직후 부모와 자식은 같은 물리 페이지를 공유할 수 있는데, 프로세스별 RSS는 그 공유 관계를 단순 합계에 자동으로 제거해 주지 않는다. 따라서 두 RSS의 합을 그대로 물리 RAM 사용량이라고 결론 내리면 실제보다 크게 볼 수 있다.

목표가 컨테이너 한도 검증이라면 해당 cgroup의 집계 지표와 이벤트를 함께 본다. 프로세스별 지표는 누가 어떤 상태인지 진단하는 데 쓰고, 제한 범위 전체의 피크는 그 범위를 측정하는 지표로 확인한다. 서로 다른 질문을 같은 합계 하나로 풀려고 하지 않는 것이 핵심이다.

</details>

<details><summary>11. overcommit을 켜면 메모리 부족 문제가 해결되나요?</summary>

해결되는 범위를 좁혀 말해야 한다. overcommit 정책은 가상 메모리 요청을 허용하는 판단과 관련되고, 물리 RAM을 늘려 주지 않는다. Redis의 fork가 실제 전체 복사보다 보수적인 메모리 추정 때문에 실패하는 상황을 완화할 수 있지만, 이후 쓰기와 COW로 실제 메모리 수요가 늘면 여전히 부족할 수 있다.

은행의 승인 한도를 넓힌다고 통장에 실제 돈이 생기는 것은 아니라는 비유로 이해할 수 있다. 다만 OS의 구체적인 동작은 커널 정책에 따라 달라지므로 비유만으로 설정값을 정하면 안 된다. 운영 가이드, 플랫폼 정책, 실제 피크 측정을 함께 적용해야 한다.

</details>

<details><summary>12. p99 지연이 나쁜데 평균 메모리는 안정적입니다. 메모리는 원인에서 제외해도 되나요?</summary>

제외할 수 없다. 평균은 짧은 피크를 숨길 수 있고, 메모리 총량이 안정적이어도 페이지 폴트, swap, fork, 할당과 해제 비용이 지연에 영향을 줄 수 있다. 메모리 문제는 항상 총량이 계속 증가하는 형태로만 나타나지 않는다.

먼저 느린 요청의 시각과 백그라운드 작업, OS 메모리 이벤트, CPU 및 디스크 지표를 맞춘다. p99가 어느 구간의 지연인지도 확인한다. 클라이언트 전체 응답 시간과 Redis 명령 실행 시간은 다르므로, 서버 실행이 짧아도 네트워크와 큐 대기가 길 수 있다. 후보를 남겨 두되 지표로 좁혀야 한다.

</details>

<details><summary>13. 메모리 20% 여유를 두면 일반적으로 안전하다고 말할 수 있나요?</summary>

보편적인 안전 보장으로 말하면 안 된다. 쓰기 패턴, 저장 시간, 복제 버퍼, 값의 성장, 다른 프로세스와 컨테이너 계산 범위에 따라 필요한 여유가 달라진다. 같은 비율이라도 작은 인스턴스와 큰 인스턴스의 절대 여유가 다르고, 피크가 비례해서 늘어난다는 보장도 없다.

면접에서는 먼저 평상시 사용량과 실제 위험 작업 중의 피크를 측정하고, 성장과 불확실성에 대한 여유를 정책으로 추가한다고 답한다. 측정하지 못한 조건은 남은 한계로 적는다. 정답 비율을 외우는 것보다 어떤 조건에서 그 용량을 선택했는지 설명하는 것이 중요하다.

</details>
