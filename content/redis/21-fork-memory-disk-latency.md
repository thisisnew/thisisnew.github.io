## 메모리 데이터베이스도 운영체제 밖에서 살 수 없다

Redis 데이터가 RAM에 있다면 디스크가 느려도 GET은 빠를 것 같지만 실제 장애는 그렇게 단순하지 않다. 스냅샷을 만들기 위해 프로세스를 fork하고, 메모리 페이지가 부족하면 운영체제가 reclaim이나 swap을 수행하고, AOF가 쌓이면 파일 시스템과 디스크가 관여한다. 명령 자체는 짧아도 그 명령을 실행할 프로세스가 잠깐 멈출 수 있다.

이 장은 제공된 원문 21장의 fork, transparent huge pages, swapping, AOF I/O, expires와 watchdog을 설명한다. 오래된 문서의 특정 VM 성능 표, active expire의 고정 상수, 과거 AOF 재작성 구조를 모든 현대 버전에 그대로 적용하지 않는다. 불변에 가까운 원리와 버전별로 확인해야 할 구현을 나눠 읽는다. 수치 예제는 모두 계산을 위한 가정이며 실측 결과가 아니다.

## 1. 백그라운드 저장이라는 말의 정확한 뜻

`BGSAVE`는 RDB 파일을 만드는 긴 작업을 자식 프로세스에 맡기도록 한다. 그렇다고 시작부터 끝까지 부모 프로세스가 아무 비용도 내지 않는 것은 아니다. 자식을 만들기 위한 fork 단계는 부모가 수행하며, 그 후에도 부모와 자식은 CPU, 메모리 대역폭, 디스크와 물리 메모리를 공유한다.

회사 비유로 보면 관리자가 보고서 작성을 보조 직원에게 맡겨도 자료 접근 권한과 문서 사본을 준비하는 시간은 필요하다. 이후 두 사람이 같은 책상과 복사기를 쓰면 경쟁도 생긴다. 이 비유의 한계는 fork가 전체 데이터의 독립 사본을 즉시 복사하는 방식은 아니라는 것이다. Linux의 가상 메모리와 copy-on-write를 이해해야 시작 비용과 진행 중 비용을 구별할 수 있다.

구분할 단계는 세 개다. **fork 직전·순간의 정지**, **자식이 살아 있는 동안의 COW와 자원 경쟁**, **파일 작업 완료와 정리**다. latency spike가 저장 시작에 붙는지, 저장 내내 이어지는지, 종료 직후 발생하는지에 따라 가설이 달라진다.

## 2. 가상 주소와 페이지 테이블

애플리케이션은 가상 주소를 사용한다. 운영체제와 CPU는 페이지 테이블을 통해 그 주소가 실제 물리 메모리의 어디에 있는지 찾는다. 페이지는 메모리를 관리하는 일정 크기의 단위다. 기본 페이지 크기와 huge page 크기는 환경에 따라 다르므로 보통의 예시 숫자를 내 서버의 확정값으로 쓰지 않는다.

가정으로 16GiB의 메모리 범위를 4KiB 페이지로 나누고 각 leaf 매핑 항목을 8바이트로 계산하면 페이지 수는 4,194,304개, leaf 항목 크기의 합은 약 32MiB다. 실제 페이지 테이블은 여러 단계의 구조이며 주소 공간의 배치, huge page, 운영체제 구현에 따라 달라진다. 이 계산은 fork 때 전체 16GiB를 곧바로 복사하지 않더라도 관리 구조를 다루는 비용이 작지 않을 수 있음을 보여 준다.

따라서 작은 데이터셋에서 측정한 fork 시간을 큰 데이터셋으로 그대로 가져갈 수 없다. RSS, 주소 공간 구조, 페이지 테이블, 커널과 가상화 환경, CPU 경쟁이 영향을 준다. `INFO`의 `latest_fork_usec`는 마지막 fork 시간의 단서를 제공하지만 히스토리 전체나 이후 COW 비용을 대신하지 않는다. 단위가 µs이므로 밀리초 차트로 옮길 때 1,000으로 나누어야 한다.

## 3. Copy-on-write: 바뀌는 페이지를 나중에 복사한다

fork 직후 부모와 자식은 많은 물리 페이지를 공유한다. 자식은 스냅샷 시점의 데이터를 읽어 파일로 만들고, 부모는 이후에도 사용자 쓰기를 처리한다. 부모가 공유된 페이지를 변경하려 하면 이전 내용은 자식에게 필요하므로 운영체제가 페이지를 분리한다. 이것이 copy-on-write, 줄여서 COW다.

단계로 따라가 보자.

1. fork 시점에 페이지 P가 부모와 자식에게 공유된다.
2. 자식은 P의 옛 내용을 읽어 스냅샷에 기록할 필요가 있다.
3. 부모가 P 안의 어떤 값을 수정하려 한다.
4. 운영체제는 쓰기를 위한 페이지 분리·복사를 수행한다.
5. 부모는 새 내용을 보고 자식은 스냅샷 시점의 내용을 유지한다.
6. 자식이 종료되면 더 이상 필요하지 않은 공유·사본 관계가 정리된다.

키 하나가 작아도 페이지 단위로 비용이 발생할 수 있다. 여러 작은 키가 같은 페이지에 있으면 한 번의 변경으로 그 페이지가 분리되고 이후 그 부모 페이지의 여러 변경은 같은 fork 구간에서 추가 COW를 똑같이 반복하지 않을 수 있다. 반대로 넓은 데이터 영역을 조금씩 수정하면 많은 서로 다른 페이지가 분리된다. 단순 write QPS만으로 COW 메모리를 정확히 예측할 수 없는 이유다.

가정으로 저장 중 서로 다른 500,000개의 4KiB 페이지가 복사되었다면 복사된 페이지 데이터는 약 1.91GiB다. 그러나 이것을 “SET 500,000회면 1.91GiB”라고 바꾸면 틀린다. 요청과 페이지의 대응이 일대일이 아니며 allocator 메타데이터와 데이터 구조도 영향을 준다. 실제 변화는 persistence의 COW 관련 지표와 RSS, container 메모리 사용으로 관찰한다.

## 4. 메모리 예산에서 maxmemory가 전부가 아닌 이유

`maxmemory`를 호스트 RAM과 같은 값으로 잡으면 안전할 것 같지만 Redis의 데이터 정책 한도와 시스템 전체의 물리 메모리 한도는 다르다. allocator overhead와 fragmentation, 클라이언트 및 복제 버퍼, 배경 저장 중 COW, 프로세스 구조, 운영체제와 다른 프로세스의 사용량도 고려해야 한다. 무엇이 eviction 판단에 포함되거나 제외되는지는 해당 버전의 INFO와 문서를 확인한다.

가정상 컨테이너 메모리 한도가 8GiB이고 정상 Redis RSS가 6GiB이며 백그라운드 저장 중 추가 메모리가 1.5GiB 필요하다고 예상하자. 여기에 다른 메모리와 순간 증가가 더해지면 여유가 매우 작다. maxmemory를 7.5GiB로 높이면 키 eviction이 늦어질 수 있지만 컨테이너 OOM kill 위험은 더 커질 수 있다. maxmemory는 커널의 하드 메모리 제한을 무효화하지 않는다.

메모리 예산은 “항상 RAM의 몇 퍼센트” 같은 한 숫자로 끝내지 않는다. 대표 데이터 크기, 큰 값과 작은 값의 혼합, 쓰기 패턴, RDB/AOF 동시 활동, 복제본 동기화, 장애 복구 때의 최대 동시 작업을 실제와 비슷하게 실험한다. 평상시 평균이 아니라 예상 가능한 겹침 상황의 peak를 본다.

## 5. THP: 큰 페이지가 항상 좋은 것은 아니다

Transparent Huge Pages는 운영체제가 큰 메모리 페이지를 활용하여 주소 변환 비용 등을 줄이려는 기능이다. 그러나 Redis의 fork와 COW 상황에서는 페이지 처리와 분리 비용, 메모리 증가가 지연 문제로 이어질 수 있다. 공식 지연 진단 문서는 Redis 환경에서 THP를 비활성화하도록 안내한다. [공식 지연 진단: THP와 fork](https://redis.io/docs/latest/operate/oss_and_stack/management/optimization/latency/)

그렇다고 관리자 권한으로 호스트 설정을 즉시 바꾸는 것이 이 장의 실습은 아니다. 커널, 배포판, 컨테이너 정책과 관리형 서비스에 따라 설정 위치와 적용 가능 범위가 다르다. 컨테이너 안에서 보이는 파일을 바꾸면 호스트 전체에 영향을 줄 수 있다. 다른 워크로드도 같은 호스트를 쓰는지, 재부팅 후 유지되는지, 기존 할당 페이지와 프로세스 재시작에 어떤 절차가 필요한지 운영 담당자와 검토한다.

큰 페이지가 존재한다는 관측만으로 모든 latency spike의 원인을 확정할 수도 없다. fork 시각, COW 증가, RSS 변화, 지연 이벤트가 함께 나타나는지 확인한다. THP 설정 변경 전후를 비교할 때 데이터 크기와 쓰기 패턴이 다르면 인과를 잘못 판단할 수 있다. 단일 설정을 만능 치료제처럼 다루지 않는다.

## 6. swap: 메모리 조회가 디스크 읽기가 되는 순간

운영체제는 메모리 압박 상황에서 일부 페이지를 디스크의 swap 영역으로 옮길 수 있다. Redis가 그 페이지에 접근하면 페이지를 다시 메모리로 가져와야 하고 프로세스가 대기할 수 있다. 그래서 GET 명령이 논리적으로 O(1)이어도 실제 물리 접근은 긴 I/O가 될 수 있다.

swap 사용량과 swap 활동량을 구분한다. 이미 오래전에 swap으로 나간 일부 페이지가 남아 있는 것과 지금 초당 많은 페이지가 들어오고 나가는 것은 다른 상황이다. `/proc/<pid>/smaps` 또는 가능한 환경의 `smaps_rollup`으로 프로세스 단위 swap을 확인하고 `vmstat`의 `si`, `so`로 시스템 활동을 본다. 시스템 전체 si가 증가했다고 그것이 반드시 Redis 때문이라는 뜻은 아니므로 시간대와 프로세스 정보를 연결한다.

swap이 꺼져 있으면 안전하다는 결론도 틀리다. swap으로 버티지 못한 메모리 압박이 OOM kill로 나타날 수 있다. 원인은 메모리 부족인데 표현만 지연에서 프로세스 종료로 바뀐 셈이다. 충분한 여유 메모리, 데이터 크기 제한, 적절한 eviction, COW 예산과 동시 작업 제한이 먼저다. swap 설정은 전체 메모리 정책의 일부다.

호스트의 free memory만 보면 container limit을 놓칠 수 있다. 호스트에 50GiB가 남아 있어도 Redis 컨테이너 한도가 4GiB라면 그 경계를 넘을 때 제약을 받는다. 반대로 container 지표만 보면 호스트의 디스크·CPU 경쟁을 놓칠 수 있다. 애플리케이션 운영에서는 두 수준을 함께 보는 습관이 필요하다.

## 7. 파일 캐시와 dirty page: 메모리·디스크가 연결되는 길

AOF나 RDB 쓰기는 파일 시스템 캐시를 사용할 수 있다. 프로세스가 `write()`를 호출하여 바이트를 커널에 넘겼다고 곧바로 안정적인 저장장치에 기록이 완료되었다는 뜻은 아니다. 아직 디스크에 반영되지 않은 dirty page가 쌓일 수 있고, 커널은 이를 나중에 내보낸다.

디스크가 쓰기 속도를 따라가지 못하면 커널의 버퍼 여유가 줄고 write 경로가 기다릴 수 있다. 대용량 백업이나 다른 프로세스의 I/O가 같은 디스크를 쓰면 Redis의 AOF에도 영향을 줄 수 있다. 따라서 “AOF fsync가 백그라운드 스레드니까 Redis main thread는 디스크와 무관하다”는 주장은 잘못이다.

이 경로는 메모리 압박과도 연결된다. 파일 캐시, COW, 복제 버퍼가 동시에 늘면 reclaim과 I/O가 겹친다. 장애를 CPU·메모리·디스크 중 하나로만 분류하려 하면 실제 인과 고리를 놓치기 쉽다. 예컨대 저장 작업이 메모리 여유를 줄이고, reclaim이 디스크 I/O를 만들고, AOF write 대기가 증가하며, 앱 재시도가 더 많은 쓰기를 보내는 순환이 생길 수 있다.

## 8. write와 fsync의 역할 차이

AOF는 Redis 쓰기 작업을 복구 가능한 형태로 기록한다. `write()`는 데이터를 파일의 커널 경로로 보내는 단계이며, `fsync` 또는 `fdatasync` 계열의 동기화는 저장장치 반영을 요청하는 단계다. 구체적인 시스템 호출과 파일 구조는 구현·버전·플랫폼에 따라 확인한다.

`appendfsync always`는 강한 동기화 정책을 요청하며 응답과 디스크 동기화의 관계가 더 밀접하다. 저장장치 지연이 쓰기 응답에 직접 크게 영향을 줄 수 있다. Redis가 여러 작업을 묶어 동기화하는 구현도 있으므로 “모든 명령마다 독립적인 한 번의 물리 디스크 쓰기가 반드시 발생한다”고 단순화하지 않는다.

`appendfsync everysec`는 보통 백그라운드 동기화로 비용을 분산한다. 하지만 지연된 fsync와 write가 상호작용하거나 커널 버퍼가 막히면 main thread에도 영향이 올 수 있다. 이름에 every second가 들어 있다고 어떤 장애에서도 정확히 1초 이하의 데이터만 잃는다는 절대 보증으로 이해하지 않는다. 운영체제·디스크·프로세스 장애 조건과 지연 상태를 함께 본다.

`appendfsync no`는 Redis가 fsync를 직접 요청하지 않고 운영체제의 정책에 맡기는 방향이다. write 자체의 대기는 여전히 가능하며 내구성 위험은 달라진다. 디스크가 느리다고 무조건 no로 바꾸면 지연은 일부 줄어도 보존해야 할 데이터의 손실 범위가 커질 수 있다. 성능과 내구성은 함께 승인해야 하는 설계 선택이다.

## 9. 재작성과 저장 작업을 어떻게 해석할까

AOF rewrite는 과거 명령의 중복을 줄여 현재 상태를 재구성할 수 있는 형태로 정리하는 작업이다. 원문에 나오는 과거 재작성 이벤트와 버퍼 설명은 멀티파트 AOF를 사용하는 버전의 내부 구조와 동일하다고 가정하지 않는다. Redis 버전, persistence 설정, 실제 INFO 필드를 함께 기록한다. 현행 persistence 문서도 AOF의 파일 구성과 재작성 절차를 별도로 설명하므로 해당 버전의 복구 절차와 연결해서 읽는다. [공식 persistence 문서](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/)

`no-appendfsync-on-rewrite` 같은 옵션은 저장·재작성 중 디스크 경합을 줄이는 대신 내구성에 영향을 줄 수 있다. 옵션 이름을 보고 “rewrite만 더 빨라지는 설정”으로 취급하면 안 된다. 장애 시 어떤 시점까지의 AOF 동기화가 보장되는지와 업무가 허용하는 손실 범위를 먼저 검토한다.

복제 전체 동기화도 RDB 생성 또는 전송 방식에 따라 자원에 영향을 준다. 주기적 백업, AOF rewrite, 새 replica 추가, 대량 캐시 warm-up을 같은 시간에 배치하면 평소에는 충분했던 메모리·디스크가 부족해질 수 있다. 스케줄을 분산하는 것은 성능 튜닝이면서 장애 도메인 관리다. 단순히 Redis 명령 QPS만 같다고 동일한 부하라고 볼 수 없다.

## 10. 만료는 시간이 지나면 공짜로 사라지는 기능이 아니다

TTL이 지난 키는 논리적으로 만료되었지만 물리 메모리 회수에는 작업이 필요하다. Redis는 접근 시 만료를 확인하는 경로와 주기적으로 만료 키를 찾아 정리하는 경로를 사용한다. 따라서 많은 키를 같은 시각에 만료시키면 정리 작업이 몰릴 수 있다.

원문은 과거 active expire 알고리즘의 샘플 수와 반복 비율을 상세히 제시한다. 이 수치를 현재 모든 Redis 버전의 고정 계약으로 쓰지 않는다. 핵심은 **능동 만료가 제한된 시간 예산 안에서 적응적으로 일하며, 만료 분포와 설정에 따라 정리 비용이 달라진다**는 것이다. 관련 설정과 내부 구현은 배포 버전에 맞춰 확인한다.

가정으로 1,000,000개의 캐시 키를 오전 10시에 모두 30분 TTL로 생성하면 10:30 부근에 대규모 동시 만료와 재조회가 겹칠 수 있다. Redis의 만료 처리뿐 아니라 원본 DB의 cache miss 폭증이 더 큰 문제가 될 수 있다. TTL을 조금 분산하는 jitter는 이 동기화를 완화할 수 있지만 만료 시각이 업무적으로 엄격한 데이터에는 임의로 적용하면 안 된다.

예를 들어 상품 설명 캐시는 30분±2분이 허용될 수 있지만 일회성 인증 코드의 최대 유효 시간을 늘리는 방식은 보안 요구를 위반할 수 있다. 허용된 최대 수명을 넘기지 않는 방향으로만 조정하거나 별도 동기화 완화 방법을 택한다. TTL은 성능 파라미터이면서 데이터 유효성 계약이다.

## 11. Java/Spring: 안전한 TTL 분산과 payload 상한

다음 예시는 재생성 가능한 상품 설명 캐시이고, 업무가 28–30분 사이의 TTL을 허용한다고 가정한다. 최대 유효시간 30분은 넘기지 않는다. 인증·결제·권한 데이터에는 그대로 적용하지 않는다.

```java
final class ProductCache {
    private final StringRedisTemplate redis;
    ProductCache(StringRedisTemplate redis) { this.redis = redis; }

    void put(long productId, String json) {
        int bytes = json.getBytes(StandardCharsets.UTF_8).length;
        if (bytes > 64 * 1024) {
            throw new IllegalArgumentException("cache payload too large");
        }
        // 예제 상한 64KiB와 TTL 범위는 업무에서 정한 가정값이다.
        long seconds = ThreadLocalRandom.current().nextLong(1680, 1801);
        redis.opsForValue().set("product:" + productId + ":description",
                               json, Duration.ofSeconds(seconds));
    }
}
```

상한을 문자 수가 아니라 UTF-8 바이트로 확인하는 이유는 네트워크와 메모리 비용이 바이트와 관련되기 때문이다. 실제 코드에서는 바이트 배열을 중복 생성하는 비용도 고려하고 직렬화 계층에서 상한을 일관되게 적용할 수 있다. 예시의 64KiB는 Redis의 보편적인 권장값이 아니라 서비스가 결정해야 할 계약을 보여 준다.

jitter만으로 cache stampede가 완전히 사라지는 것은 아니다. 매우 인기 있는 하나의 키가 만료되면 여전히 많은 요청이 동시에 원본을 조회할 수 있다. 동일 키 요청 합치기, refresh-ahead, stale-while-revalidate가 허용되는지 등 별도 정책을 검토한다. 이때 오래된 값을 제공해도 되는 업무와 절대 안 되는 업무를 구분한다.

캐시 warm-up 작업도 속도를 제한한다. 대량 SET은 쓰기 페이지를 넓게 건드려 COW를 증가시키고 동시에 AOF와 복제 트래픽을 만든다. “트래픽이 적은 새벽”에 warm-up과 BGSAVE를 겹치면 오히려 가장 위험한 순간을 만들 수 있다. 배치의 concurrency와 pause 간격, 대상 key 수를 관찰 가능한 값으로 두고 시스템의 여유에 맞춰 실행한다.

## 12. 관찰 지표를 원인별로 연결한다

| 의심 경로 | 함께 볼 증거 | 잘못된 단정 |
|---|---|---|
| fork 자체 | latest_fork_usec, fork 이벤트, 저장 시작 시각 | BGSAVE 전체 시간이 곧 fork 시간이다 |
| COW 압박 | persistence COW 필드, RSS·container 사용, 쓰기 분포 | 쓰기 QPS만으로 추가 메모리를 계산한다 |
| swap/reclaim | 프로세스 Swap, vmstat si/so, memory pressure | swap 총량이 조금 있으면 현재 장애 원인이다 |
| AOF·디스크 | fsync 지연 관련 지표, AOF 이벤트, iostat, 디스크 대기 | fsync가 background라 main thread 영향이 없다 |
| 만료 집중 | expired_keys 변화, expire-cycle, miss·DB 부하 | TTL이 지나면 즉시 공짜로 메모리가 회수된다 |

INFO의 누적 카운터는 차분을 계산해야 해당 구간의 활동량을 볼 수 있다. 예를 들어 expired_keys가 1,000만이라고 해서 이번 1분에 1,000만 개가 만료된 것은 아니다. 서버 재시작으로 카운터가 초기화되면 차분 계산도 조정해야 한다. 마지막 이벤트 값과 누적값, 순간값을 이름만 보고 섞지 않는다.

`iostat`의 장치 utilization 하나로 병목을 확정하는 것도 피한다. 현대 저장장치와 가상화된 볼륨의 병렬성, queue, latency, 처리량을 함께 봐야 한다. CPU iowait가 낮다고 디스크 관련 지연이 없다고 단정할 수 없다. 한 프로세스의 중요한 write 경로만 막혀도 전체 CPU 평균은 낮을 수 있다.

## 13. 읽기 전용 진단 실습부터 시작한다

다음은 **미실행 실습 절차와 예상 해석**이다. localhost 포트 6389의 전용 폐기 인스턴스에서 먼저 확인한다. 운영 서버에서는 명령 권한, 관측 비용과 비밀 정보 포함 여부를 검토한다. Linux 전용 도구는 해당 OS에서만 사용한다.

```bash
redis-cli -p 6389 INFO server
redis-cli -p 6389 INFO memory
redis-cli -p 6389 INFO persistence
redis-cli -p 6389 INFO stats
redis-cli -p 6389 CONFIG GET appendonly
redis-cli -p 6389 CONFIG GET appendfsync
redis-cli -p 6389 LATENCY LATEST
```

예상 결과는 설정과 마지막 fork, persistence 진행 상태, 메모리 사용 정보를 읽을 수 있다는 것이다. 사용 버전에 없거나 이름이 다른 필드는 문서와 실제 출력에 맞춰 처리한다. LATENCY LATEST가 비어 있으면 threshold가 꺼져 있거나 해당 기간에 기록할 이벤트가 없었을 수 있다. 이것만으로 지연 원인이 없다고 결론 내리지 않는다.

PID를 읽어 사람이 대상 프로세스와 namespace를 확인한 뒤 다음을 조회할 수 있다. 여러 Redis가 실행되는 호스트에서 `pidof redis-server` 결과를 무검증으로 붙여 쓰지 않는다.

```bash
# 아래 <확인한_PID>는 실제 실습 Redis PID로 바꾼다.
# awk '/^Swap:/ {sum += $2} END {print sum " kB"}' /proc/<확인한_PID>/smaps
vmstat 1 5
# sysstat가 설치된 실습 Linux라면:
# iostat -xz 1 5
```

vmstat 첫 행은 부팅 후 평균 등 후속 행과 의미가 다를 수 있으므로 도구 설명을 확인한다. smaps 조회가 허용되지 않으면 무리하게 권한을 우회하지 않고 제공되는 메트릭을 사용한다. THP 상태는 읽기 전용으로 확인할 수 있지만 이 실습에서 호스트 설정을 변경하지 않는다.

## 14. 작은 BGSAVE 실험의 설계

폐기용 인스턴스에 충분히 작은 데이터만 넣고, 여유 RAM과 디스크를 확인한 뒤 단 한 번 BGSAVE를 시도하는 비교 실험을 설계할 수 있다. 이 문서에서는 실행하지 않았으며 예상 성능 수치도 제시하지 않는다. 먼저 INFO persistence로 다른 저장 작업이 없는지 확인한다. 진행 중이면 추가 작업을 겹치지 않는다.

```bash
# 이 명령은 저장 파일을 만드는 변경 작업이다. 전용 실습 환경에서만.
redis-cli -p 6389 BGSAVE
redis-cli -p 6389 INFO persistence
redis-cli -p 6389 INFO stats
```

관찰할 것은 시작 직후 latest_fork_usec의 갱신, rdb 관련 진행 상태의 변화, 완료 상태다. 동시에 별도의 CLI에서 PING 왕복을 기록할 수 있지만 작은 데이터셋에서는 뚜렷한 지연이 보이지 않을 수 있다. 보이지 않았다는 결과는 “백그라운드 작업은 영향이 없다”는 증명이 아니다. 실험 규모와 관찰 해상도가 작았다는 제한을 적는다.

COW를 보기 위해 다음 단계에서 쓰기 부하를 추가한다면 메모리 상한, 총 키 수, 값 크기, 최대 실행 시간과 중단 조건을 먼저 정한다. OOM을 일부러 만들거나 호스트 RAM을 채우는 실습은 하지 않는다. 일정 메모리 한계에 접근하거나 앱 지연·오류가 예산을 넘으면 즉시 부하를 중단하고 완료 중인 저장 상태를 확인한다. 복구를 위해 프로세스를 무작정 kill하지 않는다.

## 15. 장애 타임라인: 원인과 증상을 엮기

가상 사례다. 01:00:00에 캐시 warm-up이 시작되었다. 01:00:10에 RDB 저장이 시작되어 fork 이벤트가 관측되었다. 01:00:11부터 쓰기가 넓은 메모리 영역을 변경해 COW 사용량과 RSS가 상승했다. 01:00:20에는 컨테이너 여유가 작아지고 호스트에서도 I/O 대기가 늘었다. 01:00:25에 AOF 지연 관련 지표와 앱 p99가 함께 상승했다. 01:00:30부터 timeout 재시도가 write QPS를 더 키웠다.

초기 대응으로 Redis를 더 자주 재시작하면 로딩·동기화와 cache miss가 추가되어 악화될 수 있다. 우선 안전하게 중단 가능한 warm-up과 과도한 재시도를 제한하여 부하를 낮추고, 데이터 내구성 설정을 무단으로 약화시키지 않은 채 상태를 관찰한다. 그다음 저장 스케줄, COW headroom, 배치 속도와 timeout 정책을 수정한다.

다른 가상 사례에서는 저장 작업이 없지만 매 정각 expire-cycle과 DB 조회가 함께 튄다. 원인은 모든 키가 정각에 만료되도록 설정된 TTL 정책일 수 있다. 이 경우 디스크 증설보다 TTL 분포와 재생성 동시성 제어가 효과적인 가설이다. 다만 만료 키 정리와 cache miss의 영향을 각각 계측해야 어느 쪽이 주요 원인인지 알 수 있다.

## 16. 고급 도구는 마지막 수단이다

원문은 `strace`로 fsync/write를 추적하고 실험적 watchdog을 사용하는 방법을 소개한다. 이 도구들은 유용할 수 있지만 관측 자체가 성능에 영향을 주고 경로·인수 등 민감한 정보를 드러낼 수 있다. 운영에서 바로 붙이는 첫 단계가 아니다.

먼저 이미 있는 INFO, latency 이벤트, 시스템 메트릭과 로그를 모은다. 다음으로 좁은 시간 창과 대상 PID를 정한 통제된 profiling을 검토한다. 백그라운드 스레드의 호출까지 볼지 여부도 도구 옵션과 관련되며, 메인 스레드만 본 결과로 fsync가 없다고 단정해서는 안 된다. 권한과 수행 범위는 운영 정책을 따른다.

watchdog 관련 설정은 배포 버전에서 존재하고 지원되는지 확인해야 한다. 오래된 원문에 명령이 있다고 무조건 현재 운영 환경에서 켜지 않는다. 활성화했다면 원래 설정과 종료 절차를 기록하고 짧은 진단 범위 뒤 복원한다. 조사 도구를 상시 켜 놓아 새로운 지연과 로그 폭증을 만드는 일을 피한다.

## 면접과 설계 리뷰 Q&A

<details><summary>Q1. BGSAVE가 백그라운드인데 왜 요청이 멈추는가?</summary>

자식을 만드는 fork 자체는 부모가 수행하며 페이지 테이블 등 관리 구조를 다루는 비용이 있다. 이후에도 COW, CPU·메모리 대역폭·디스크 경쟁이 발생한다. 따라서 fork 순간 지연과 자식 실행 중 지연을 나눠 측정해야 한다. BGSAVE 전체 시간과 latest_fork_usec를 같은 지표로 취급하면 원인을 놓친다.

</details>

<details><summary>Q2. fork하면 메모리가 즉시 두 배가 되는가?</summary>

전체 데이터가 즉시 독립 복사되는 것은 아니다. 초기에는 공유 페이지가 많고 변경된 페이지가 COW로 분리된다. 그러나 쓰기 패턴과 저장 지속 시간에 따라 추가 메모리가 커질 수 있으므로 “처음에는 공유니까 여유가 필요 없다”는 결론도 틀리다. 실제 COW와 RSS peak를 측정해 예산을 잡는다.

</details>

<details><summary>Q3. 같은 write QPS인데 COW가 다르게 나오는 이유는?</summary>

같은 페이지를 반복 갱신하는 패턴과 넓은 영역의 서로 다른 페이지를 한 번씩 바꾸는 패턴이 다르기 때문이다. 값 크기, allocator 배치와 자료구조도 영향을 준다. 요청 수만이 아니라 수정되는 메모리 영역과 배경 저장의 지속 시간까지 고려해야 한다. 작은 키라는 이유만으로 COW 비용이 작다고 보장할 수 없다.

</details>

<details><summary>Q4. maxmemory를 컨테이너 한도와 같게 두면 왜 위험한가?</summary>

maxmemory는 Redis의 데이터 메모리 정책과 관련된 한도이지 프로세스·자식·버퍼·운영체제의 모든 메모리를 포괄하는 하드 제한이 아니다. COW와 기타 여유가 없으면 eviction이 동작하기 전에 container OOM이 발생할 수 있다. 실제 peak와 동시 작업을 기준으로 두 한도 사이의 여유를 설계해야 한다.

</details>

<details><summary>Q5. appendfsync everysec이면 디스크 지연이 앱에 전혀 안 보이는가?</summary>

아니다. 동기화를 배경으로 넘겨 비용을 완화하지만 write와 커널 버퍼, 지연된 fsync의 상호작용은 남는다. 디스크가 밀리거나 다른 I/O가 경쟁하면 명령 처리 경로에도 영향이 올 수 있다. AOF 지표와 OS 디스크 지표를 같은 시간대로 대조해야 하며 설정 이름만으로 지연을 배제하지 않는다.

</details>

<details><summary>Q6. swap을 끄면 메모리 문제를 해결한 것인가?</summary>

swap에 의한 페이지 재읽기 지연은 줄일 수 있지만 물리 메모리 부족이 사라지지는 않는다. 부족이 OOM kill로 나타날 수도 있다. 데이터 크기, fragmentation, COW, 버퍼와 동시 배경 작업에 충분한 여유를 마련하는 것이 먼저다. 호스트와 container 한도를 함께 확인해야 한다.

</details>

<details><summary>Q7. TTL jitter는 모든 키에 적용해도 되는가?</summary>

업무가 허용하는 유효 시간 범위 안에서만 적용한다. 재생성 가능한 캐시에는 도움이 될 수 있지만 인증 코드나 권한 회수 데이터의 최대 유효 시간을 임의로 늘리면 안 된다. 또한 인기 키 하나의 stampede는 jitter만으로 해결되지 않으므로 동시 재생성 제어도 필요하다.

</details>

<details><summary>Q8. 지연을 줄이려고 persistence를 꺼도 되는가?</summary>

성능 설정이 아니라 데이터 보존 계약을 바꾸는 결정이므로 업무 요구와 승인이 필요하다. 캐시라면 재생성 가능성과 원본 부하, warm-up 시간을 평가하고, 원장이라면 손실 허용 범위를 먼저 확인한다. latency가 줄었다는 사실만으로 좋은 변경이라고 할 수 없으며 복구 가능성과 RPO도 함께 검증해야 한다.

</details>

## 정리

Redis는 RAM을 중심으로 동작하지만 커널의 주소 변환, COW, reclaim, 파일 캐시와 저장장치에 의존한다. 백그라운드 작업은 비용을 없애지 않고 실행 위치와 시점을 바꾼다. 지연 조사는 fork 순간, 저장 진행 중, 완료 정리, 만료 집중을 시간선에 놓고 메모리·디스크·앱 재시도의 연결을 찾는 작업이다.

- 제공된 원문 21장: fork부터 watchdog까지의 원리를 재구성했으며 오래된 성능 수치와 구현 상수는 보편화하지 않았다.
- [공식 Redis 지연 진단](https://redis.io/docs/latest/operate/oss_and_stack/management/optimization/latency/): fork·THP·swap·AOF 경로 확인.
- 다음 22장에서는 이러한 가설을 Latency Monitor 이벤트로 좁히는 방법을 다룬다.
