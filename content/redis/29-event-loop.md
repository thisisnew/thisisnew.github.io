## 1. 연결 하나마다 직원 한 명이 꼭 필요할까?

식당 직원이 주문 한 건을 받았다고 그 손님의 식사가 끝날 때까지 테이블 앞에 서 있을 필요는 없다. 주문을 주방에 전달하고 다른 테이블을 살피다가 준비된 일이 생겼을 때 처리하면 된다. 이벤트 루프는 이처럼 준비된 작업을 반복해서 골라 처리하는 실행 구조다.

그러나 “직원 한 명이면 무한한 손님을 처리한다”는 뜻은 아니다. 주문 한 건을 처리하는 데 오래 걸리면 뒤의 손님도 기다린다. Redis가 많은 연결을 효율적으로 다룰 수 있다는 것과 오래 걸리는 명령에 영향을 받지 않는다는 것은 다른 이야기다.

이 장에서는 Redis 7.2 계열의 `ae` 이벤트 라이브러리를 구체적인 읽기 기준으로 사용한다. 제공된 학습 원문은 `redis.c`, 고정 배열 형태 등 오래된 코드 모양을 포함한다. 개념은 유용하지만 그 구조체와 함수 이름을 모든 최신 버전의 정확한 구현으로 외우지 않는다. Redis 8 이후 네트워킹 경로도 달라질 수 있으므로 실제 디버깅에서는 배포한 버전의 소스를 연다.

## 2. 먼저 다섯 단어를 분리하자

| 용어 | 쉬운 뜻 | 흔한 오해 |
|---|---|---|
| 소켓 | 네트워크 통신의 끝점 | 소켓 하나가 스레드 하나라는 생각 |
| 파일 디스크립터, fd | OS 자원을 가리키는 정수 번호 | 일반 파일만 가리킨다는 생각 |
| 비차단, non-blocking | 즉시 처리할 수 없으면 기다리지 않고 반환 | 작업 전체가 공짜라는 생각 |
| 준비 상태, readiness | 읽기·쓰기 진행이 가능하다는 알림 | 명령 전체가 도착했다는 생각 |
| 콜백 | 특정 사건에 실행하도록 등록한 함수 | 항상 별도 스레드라는 생각 |

Unix 계열 시스템에서 소켓도 파일 디스크립터로 다룬다. 따라서 이벤트 라이브러리의 **파일 이벤트**는 디스크 파일 내용 변경을 감시한다는 의미가 아니라, 소켓 같은 fd의 읽기·쓰기 준비 상태를 포함하는 용어다.

TCP는 바이트 스트림이다. SET 명령 하나를 보냈다고 서버의 read 한 번이 그 명령 전체를 정확히 돌려주는 것은 아니다. 명령이 여러 읽기에 나뉠 수 있고, 여러 명령이 한 번에 들어올 수도 있다. 준비 상태와 프로토콜 메시지 경계를 분리해야 Redis의 입력 버퍼가 왜 필요한지 이해된다.

## 3. 이벤트 루프의 두 가지 주요 사건

### 3.1 파일 이벤트

소켓에서 읽을 데이터가 생기거나 쓸 공간이 생기면 해당 콜백을 호출한다. 연결 요청을 받는 listen 소켓의 읽기 준비는 새 연결을 accept할 수 있음을 뜻하고, 연결된 소켓의 읽기 준비는 요청 바이트를 읽을 수 있음을 뜻한다. 같은 “읽기 가능”이지만 소켓 역할에 따라 할 일이 다르다.

쓰기 준비는 응답 전체를 상대가 받았다는 뜻이 아니다. 로컬 커널의 송신 버퍼에 더 보낼 수 있다는 뜻이다. 네트워크가 느리거나 클라이언트가 읽지 않으면 일부만 전송되고 나머지는 다음 기회로 남을 수 있다.

### 3.2 시간 이벤트

일정 시간이 지난 뒤 실행할 관리 작업도 필요하다. Redis의 `serverCron` 같은 주기 작업은 상태 관리, 클라이언트·메모리·저장 관련 점검 등 여러 유지 작업과 연결된다. 만료 처리를 포함한 내부 유지 작업은 여러 경로에서 수행될 수 있으므로 모든 작업이 하나의 타이머에서만 일어난다고 단정하지 않는다.

시간 이벤트는 하드 실시간 예약이 아니다. “100ms 뒤 실행 예정”은 정확히 그 시각에 CPU를 선점해서 실행한다는 뜻이 아니다. 앞의 명령이 오래 실행되면 콜백이 늦어질 수 있다. 이벤트 루프 구조에서는 작업 하나의 최대 실행 시간이 전체 지연에 영향을 준다.

## 4. aeEventLoop 구조체는 무엇을 기억하는가?

Redis 7.2의 `ae.h`를 개념적으로 읽으면 다음 상태가 중요하다.

```text
aeEventLoop
 ├─ 등록한 fd별 이벤트 정보: 읽기/쓰기 마스크와 콜백
 ├─ 이번 poll에서 준비된 이벤트 목록
 ├─ 시간 이벤트 목록
 ├─ 최대 fd와 이벤트 배열 크기
 ├─ 종료 플래그
 ├─ OS별 poll 구현의 내부 데이터
 └─ sleep 전후 훅
```

제공된 원문의 `events[AE_SETSIZE]`처럼 고정 배열을 그대로 현재 구조로 인용하지 않는다. 7.2 소스는 setsize에 맞춰 이벤트 배열을 할당하는 형태다. fd는 등록 이벤트 배열의 인덱스로 사용될 수 있지만 배열 크기와 최대 연결 수, OS fd 제한은 서로 관련된 별도 제약이다. [Redis 7.2 ae.h](https://github.com/redis/redis/blob/7.2/src/ae.h)

여기서 등록 목록과 준비 목록을 분리하는 이유가 중요하다. 등록 목록에는 관심 있는 소켓이 많이 있어도 이번에 준비된 소켓은 일부일 수 있다. 루프는 그 순간 해야 할 일에 집중한다. 수천 개 연결 대부분이 가만히 기다리는 경우에 연결마다 스레드를 두는 방식보다 효율적일 수 있다.

비유하면 등록 목록은 식당 전체 테이블 명단이고, 준비 목록은 지금 주문하거나 계산하려고 손을 든 테이블 목록이다. 다만 OS의 실제 알고리즘을 “손든 테이블만 O(1)로 찾는다”는 식으로 단순화하지 않는다. 준비 이벤트 수, 커널 자료구조, 등록 변경, 처리량에 따른 비용이 존재한다.

## 5. epoll, kqueue, select는 같은 역할의 다른 창구다

운영체제마다 여러 fd의 준비 상태를 기다리는 API가 다르다. Linux에서는 epoll, 다른 운영체제에서는 kqueue 또는 다른 백엔드를 사용할 수 있다. Redis의 `ae`는 OS별 차이를 추상화한다. 애플리케이션의 이벤트 등록과 처리 개념을 유지하면서 실제 대기 API를 바꾸는 것이다.

7.2의 Linux 백엔드에서 중요한 함수 역할은 다음과 같다.

- 생성: epoll 관리 객체와 결과 저장 공간을 만든다.
- 등록·수정: fd에 관심 있는 읽기·쓰기 이벤트를 알려 준다.
- 삭제: 더 이상 필요하지 않은 관심을 제거한다.
- 대기: 준비된 fd 목록을 받아 공통 이벤트 형식으로 변환한다.

`epoll_wait`가 반환했다고 작업 자체가 완료된 것은 아니다. 그 뒤 Redis가 read/write, 프로토콜 파싱, 명령 실행을 해야 한다. Redis 7.2의 epoll 백엔드는 EPOLLIN/EPOLLOUT 등을 매핑하며 일반적인 설명에서 무조건 edge-triggered라고 가정하면 안 된다. 실제 등록 플래그를 소스에서 확인한다. [Redis 7.2 ae_epoll.c](https://github.com/redis/redis/blob/7.2/src/ae_epoll.c)

### 5.1 준비 상태는 힌트이며 재확인이 필요하다

read를 호출했는데 지금은 더 읽을 데이터가 없어 EAGAIN 같은 결과가 나올 수 있다. 비차단 소켓에서는 이 결과를 “서버 고장”으로 보지 않고 다음 준비 알림을 기다리는 흐름으로 처리한다. write도 일부 바이트만 처리할 수 있으므로 남은 위치를 기억해야 한다.

이런 상태 관리는 이벤트 기반 서버의 핵심이다. 스레드가 함수 안에서 멈춰 기다리는 대신, 자료구조에 진행 상태를 저장하고 다음 이벤트에서 이어간다. 비동기 프로그래밍이 단지 문법이 아니라 상태 관리 방식이라는 점을 보여 준다.

## 6. GET 한 번이 지나가는 길

아래 흐름은 이해를 위한 단순화다. TLS, I/O threading, 클러스터, 복제, 스크립트 등은 추가 경로를 만든다.

```text
1. 클라이언트가 TCP 연결을 연다.
2. listen 소켓의 준비 이벤트를 처리해 연결을 수락한다.
3. 연결 상태와 입력·출력 버퍼를 준비한다.
4. 읽기 준비가 오면 요청 바이트를 읽는다.
5. 입력 버퍼에서 RESP를 파싱한다.
6. 완전한 명령이 있으면 인증·권한·상태를 검사한다.
7. GET을 실행해 키를 조회한다.
8. 응답을 출력 버퍼에 기록한다.
9. 가능한 만큼 소켓으로 보낸다.
10. 남은 응답은 쓰기 준비 시 이어서 보낸다.
```

실제 구현은 성능을 위해 응답을 바로 쓰려 하거나, 보류된 쓰기를 모아서 처리하거나, I/O 스레드에 일부 일을 나누는 등 최적화한다. 위 순서를 모든 호출의 정확한 함수 스택이라고 이해하지 않는다. 핵심은 **네트워크 입출력, 명령 해석, 명령 실행, 응답 전송이 서로 다른 단계**라는 점이다. [Redis 7.2 networking.c](https://github.com/redis/redis/blob/7.2/src/networking.c)

두 클라이언트가 동시에 데이터를 보냈더라도 전역적으로 “보낸 시간순” 실행을 보증한다고 해석하면 안 된다. 네트워크 도착과 poll 반환, 연결별 버퍼 처리 등 여러 요인이 있다. 단일 연결에서의 프로토콜 순서와 여러 연결 사이의 공정성·전체 순서는 다른 문제다.

## 7. aeMain과 aeProcessEvents를 읽는 순서

소스를 처음 읽을 때 모든 함수를 한 번에 외우려고 하지 않는다. 다음 의사코드를 머리에 두고 분기 조건을 확인한다.

```text
while stop이 아니면:
    sleep 전 처리 훅
    가장 가까운 시간 이벤트를 고려해 대기 시간 결정
    OS poll로 준비된 파일 이벤트 수집
    sleep 후 처리 훅
    준비된 파일 이벤트의 콜백 실행
    실행 시각이 된 시간 이벤트 처리
```

실제 `aeProcessEvents`의 플래그는 파일·시간 이벤트 처리 여부, 기다릴지 여부, 훅 호출 등을 제어한다. 읽기와 쓰기가 같은 fd에서 동시에 준비된 경우의 콜백 순서와 중복 호출 방지, barrier 플래그 같은 세부 조건도 있다. 이 세부 사항은 소스 버전에 묶어서 읽어야 한다. [Redis 7.2 ae.c](https://github.com/redis/redis/blob/7.2/src/ae.c)

“sleep”은 프로그램이 아무것도 할 수 없게 고장 난 상태가 아니다. 할 일이 없을 때 OS가 이벤트나 타임아웃까지 기다리게 하는 효율적 대기다. 반대로 매번 대기 시간을 0으로 두고 할 일도 없이 반복하면 CPU를 낭비하는 busy loop가 된다. 유휴 상태 Redis의 CPU가 낮은 이유를 이해하는 데 이 구분이 중요하다.

시간 이벤트가 가까우면 대기 시간을 줄이고, 파일 이벤트가 먼저 도착하면 그때 깨어날 수 있다. 네트워크와 주기 관리 작업을 하나의 루프에서 조정하는 것이다. 타이머의 사용 시계와 내부 구현은 버전별로 확인하되, 벽시계 변경과 경과 시간 측정을 혼동하지 않는 원칙은 유지한다.

## 8. 싱글 스레드라는 표현을 정확하게 쓰기

“Redis는 싱글 스레드다”는 표현은 보통 전통적인 핵심 명령 실행 경로가 주로 한 메인 스레드에서 직렬 처리된다는 뜻으로 사용된다. Redis 프로세스 안에 스레드가 하나뿐이라는 뜻은 아니다. 백그라운드 파일 작업, 비동기 메모리 해제, I/O threading 등이 존재할 수 있다.

I/O threading은 네트워크 읽기·쓰기 같은 일을 여러 스레드에 분담해 메인 스레드의 부담을 줄이는 데 목적이 있다. 버전과 설정에 따라 파싱 등 분담 범위도 달라질 수 있다. 그러나 **io-threads를 늘렸다고 일반적인 키 변경 명령이 전부 여러 코어에서 독립 병렬 실행되는 것은 아니다.**

그래서 다음 두 문장은 동시에 참일 수 있다.

- Redis 프로세스가 여러 코어를 사용한다.
- 오래 걸리는 한 명령이 다른 명령의 대기 시간을 늘린다.

이 모델이 단순한 원자성을 이해하는 데 도움이 되지만, 클라이언트의 여러 명령 사이까지 자동으로 원자적이라는 뜻은 아니다. GET 후 계산 후 SET을 각각 보내면 그 사이에 다른 클라이언트의 명령이 들어갈 수 있다. 이벤트 루프가 직렬 처리한다는 사실은 여러 요청을 하나의 트랜잭션으로 묶어 주지 않는다.

## 9. BLPOP은 왜 다른 클라이언트를 멈추지 않을까?

BLPOP의 “blocking”은 해당 클라이언트가 결과를 기다린다는 뜻이다. 빈 목록을 기다릴 때 Redis 서버 전체의 메인 스레드를 잠재워 모든 연결을 멈추는 방식이 아니다. 서버는 대기 중인 클라이언트와 키의 관계를 기록하고 다른 요청을 처리한다. 나중에 데이터가 들어오거나 타임아웃이 되면 해당 클라이언트에 응답한다. [BLPOP](https://redis.io/docs/latest/commands/blpop/)

반대로 큰 컬렉션을 한 번에 처리하는 명령이나 긴 Lua 실행은 실제 실행 구간을 오래 점유할 수 있다. “블로킹 명령”이라는 이름만 보고 서버 전체 정지 여부를 판단하지 않는다. 클라이언트 대기 상태와 서버 실행 스레드 점유를 구분해야 한다.

Java에서도 마찬가지다. 동기 `BLPOP` 호출을 실행한 애플리케이션 스레드는 기다릴 수 있다. Redis 서버가 다른 클라이언트를 처리한다는 사실과 그 Java 스레드가 다른 일을 할 수 있다는 사실은 별개다. 비동기 클라이언트를 쓰더라도 콜백 안에서 동기 대기를 하면 해당 이벤트 루프를 막을 수 있다.

## 10. 느린 클라이언트와 출력 버퍼

서버는 응답을 빨리 만들었는데 클라이언트가 천천히 읽으면 출력 버퍼에 데이터가 쌓인다. 이것은 Redis 명령 실행이 느린 경우와 다른 병목이다. 큰 응답을 요청하는 클라이언트, 잠시 멈춘 소비자, 느린 네트워크가 원인이 될 수 있다.

이때 무조건 연결 수를 늘리면 더 많은 출력 버퍼와 메모리를 소비할 수 있다. 응답 크기를 줄이고 읽는 속도를 높이며, 클라이언트 출력 버퍼 제한 정책을 점검한다. 파이프라인도 너무 깊으면 서버가 응답을 모아 두는 양이 커질 수 있다. 한 번에 많은 명령을 보낸다는 성능 기법은 무한히 크게 할수록 좋은 것이 아니다.

**백프레셔**는 받는 쪽의 처리 능력에 맞춰 보내는 양을 조절하는 개념이다. 시스템 각 단계의 큐가 무한하지 않다는 점을 인정하는 것이다. Redis 연결 풀, 비동기 대기 명령 수, 애플리케이션 작업 큐까지 함께 제한해야 메모리 증가와 긴 꼬리 지연을 막을 수 있다.

## 11. 안전한 로컬 실습: 클라이언트 대기와 서버 진행 분리

이 실습은 실제 실행 결과가 아니라 **기대 관찰을 안내하는 절차**다. 데이터가 없는 로컬 실습 인스턴스를 `127.0.0.1:16379`에 실행한다. 운영 서버에는 적용하지 않는다.

```bash
umask 077
LAB=$(mktemp -d)
redis-server --bind 127.0.0.1 --port 16379 --dir "$LAB" \
  --save '' --appendonly no
```

터미널 A에서 다음을 실행한다.

```bash
redis-cli -h 127.0.0.1 -p 16379 BLPOP lesson:queue 15
```

목록이 비어 있다면 A는 기다린다. 15초 안에 터미널 B에서 다음을 실행한다.

```bash
redis-cli -h 127.0.0.1 -p 16379 PING
redis-cli -h 127.0.0.1 -p 16379 LPUSH lesson:queue hello
```

예상 관찰은 A가 기다리는 중에도 B의 PING에 PONG이 오고, LPUSH 이후 A가 키와 값 `hello`를 받는 것이다. A의 타임아웃이 먼저 지나면 null 계열 응답이 올 수 있으므로 다시 시작한다. 타임아웃의 실제 출력 모양은 RESP와 CLI 버전에 따라 다를 수 있다.

이 실험은 서버가 대기 상태를 자료구조로 관리하며 다른 요청을 처리한다는 것을 보여 준다. 명령 실행 자체가 오래 걸리는 경우의 지연을 증명하지는 않는다. 이를 보겠다고 무한 Lua 루프나 DEBUG SLEEP을 운영 환경에서 실행해서는 안 된다.

실험을 끝내면 서버 터미널에서 Ctrl-C로 종료한다. 영속화를 껐으므로 실습 데이터가 사라진다. 다른 Redis가 같은 포트를 사용하지 않도록 시작 로그를 먼저 확인한다.

## 12. Java/Spring 설계로 옮기기

Lettuce는 Netty 기반 네트워킹을 사용한다. Redis 서버의 이벤트 루프와 Java 클라이언트의 이벤트 루프는 서로 다른 프로세스의 실행 구조다. 둘을 섞어 “Redis는 비동기니까 내 Java 코드도 블로킹하지 않는다”고 생각하면 안 된다.

```java
// 비동기 결과를 기다리는 개념 예제
CompletionStage<String> result = asyncCommands.get("lesson:item");
result.thenAccept(value -> {
    // 여기에서 오래 걸리는 CPU 작업이나 동기 외부 호출을 하지 않는다.
    // 필요한 작업은 목적에 맞게 크기가 제한된 별도 실행기로 넘긴다.
});
```

콜백이 어느 스레드에서 실행되는지는 API와 체이닝 방식에 따라 달라진다. 무조건 별도 업무 스레드라고 가정하지 않는다. 큰 JSON 파싱, 동기 HTTP 요청, 파일 쓰기를 네트워킹 이벤트 루프에서 수행하면 다른 Redis 응답 처리까지 늦어질 수 있다.

별도 executor로 넘겨도 큐를 무한히 만들면 문제를 이동시킬 뿐이다. 처리량, 최대 대기 작업 수, 거부 정책, 타임아웃을 함께 정한다. 동기 Spring API를 사용하는 서비스라면 웹 요청 스레드와 Redis 연결 대기의 관계를 계측한다. “비동기”라는 이름보다 실제 대기와 실행 위치를 보는 습관이 중요하다.

### 짧은 명령도 대기열이 길면 느려진다

명령 하나의 실행 시간이 0.1ms라고 해서 모든 요청이 0.1ms 안에 응답하는 것은 아니다. 앞에 처리할 요청이 많이 쌓이면 실행을 시작하기 전 대기가 생긴다. 특히 서버의 처리 능력에 가까운 부하에서는 작은 흔들림도 큐를 길게 만들 수 있다. 긴 명령 하나가 섞이면 그 뒤의 짧은 명령들도 영향을 받는다.

그래서 최대 처리량 수치만 보고 운영 목표를 정하지 않는다. 목표 부하에서 p99와 큐 길이가 안정적인지 확인하고 여유 용량을 둔다. 파이프라인과 연결 수를 늘려 처리량을 높이는 실험도 동시에 지연과 메모리를 관찰해야 한다. 이벤트 루프의 효율은 큐잉 문제를 없애는 것이 아니라 적은 자원으로 일을 배분하는 방식이다.

## 13. 면접 질문과 상세 답변

<details><summary>Q1. Redis는 한 스레드로 어떻게 많은 연결을 처리하나요?</summary>

많은 연결은 대부분 데이터가 오기를 기다린다. 이벤트 루프는 준비된 fd를 OS에서 받아 해당 작업만 처리하므로 연결마다 대기 스레드를 만들 필요가 없다. 비차단 소켓과 연결별 상태 버퍼가 이 구조를 가능하게 한다.

하지만 작업 한 건의 계산 시간이 길면 다른 작업의 대기가 늘 수 있다. 연결 수를 효율적으로 다룬다는 사실이 무한 처리량을 뜻하지 않는다. 네트워크 대기와 실제 명령 계산을 분리해서 설명해야 한다.

</details>

<details><summary>Q2. 읽기 가능 이벤트가 오면 명령 전체가 도착한 것인가요?</summary>

아니다. TCP는 바이트 스트림이고 읽기 한 번의 경계와 Redis 명령 경계는 일치하지 않는다. 명령이 여러 번에 나뉘어 도착하거나 여러 명령이 함께 들어올 수 있다. 입력 버퍼에 바이트를 모으고 RESP를 파싱해 완전한 명령인지 확인한다.

따라서 준비 알림, read 결과, 프로토콜 파싱, 명령 실행은 다른 단계다. 네트워크 라이브러리 구현을 이해할 때 가장 중요한 구분 중 하나다.

</details>

<details><summary>Q3. io-threads를 늘리면 GET과 SET도 모두 병렬 실행되나요?</summary>

일반적인 Redis 핵심 명령 실행을 그렇게 이해하면 틀리다. I/O threading은 읽기·쓰기 등 네트워크 처리 부담을 분산하는 것이며 분담 범위는 버전에 따라 달라진다. 메인 실행 경로의 직렬 구간은 여전히 중요하다.

그래서 CPU를 많이 쓰는 긴 명령이 병목일 때 I/O 스레드만 늘려도 해결되지 않을 수 있다. 먼저 프로파일로 I/O 비용인지 명령 계산 비용인지 확인하고 사용 버전의 구현을 기준으로 판단한다.

</details>

<details><summary>Q4. BLPOP이 blocking인데 왜 다른 요청은 처리되나요?</summary>

BLPOP은 조건이 충족될 때까지 해당 클라이언트의 응답을 보류한다. 서버 전체의 실행 스레드가 그 소켓 앞에서 잠드는 것이 아니라 대기 상태를 기록하고 다른 이벤트를 처리한다. 데이터가 생기거나 타임아웃이 되면 그 클라이언트를 깨운다.

반면 오래 실행되는 계산 명령은 메인 실행 구간을 점유할 수 있다. 클라이언트가 기다리는 상태와 서버가 계산 때문에 다른 일을 못 하는 상태를 구분해야 한다.

</details>

<details><summary>Q5. 이벤트 루프의 시간 이벤트는 정확한 시각을 보장하나요?</summary>

일반적인 이벤트 루프의 타이머는 하드 실시간 보증이 아니다. 실행 시각이 되어도 앞선 콜백이나 명령이 오래 걸리면 늦어질 수 있다. OS 스케줄링도 영향을 준다. 타이머 간격과 실제 실행 간격을 같은 것으로 보면 안 된다.

그래서 긴 작업을 줄이는 것이 명령 응답뿐 아니라 내부 유지 작업의 지연에도 중요하다. 정밀한 시간 보증이 필요한 업무를 Redis의 일반 타이머 동작만으로 설계해서는 안 된다.

</details>

<details><summary>Q6. epoll이 빠르니 연결 수를 무한히 늘려도 되나요?</summary>

아니다. 각 연결은 fd, 메모리 버퍼, 커널 소켓 자원, 인증 상태 등을 사용한다. 준비 이벤트 처리와 명령 실행에도 비용이 있다. OS 제한, Redis 최대 클라이언트 설정, 출력 버퍼와 네트워크 대역폭을 고려해야 한다.

특히 느린 클라이언트는 응답 버퍼를 늘릴 수 있다. 연결 수와 동시 진행 명령 수를 구분하고 적절한 백프레셔를 설계해야 안정적이다.

</details>

<details><summary>Q7. 한 스레드가 명령을 직렬 실행하면 GET 후 SET도 원자적인가요?</summary>

별도 요청 두 개는 자동으로 하나의 원자적 작업이 되지 않는다. GET과 SET 사이에 다른 클라이언트 명령이 실행될 수 있다. 직렬 실행은 각 명령의 실행 경로를 이해하는 데 도움이 되지만 여러 명령의 업무 원자성을 보장하지 않는다.

필요하면 원자적 단일 명령, 트랜잭션과 WATCH, 스크립트 등 적절한 수단을 선택한다. 어떤 범위가 원자적인지 요청 단위로 설명해야 한다.

</details>

<details><summary>Q8. 비동기 Java 콜백에서 큰 JSON을 파싱해도 괜찮나요?</summary>

콜백 실행 스레드를 먼저 확인해야 한다. 네트워크 이벤트 루프에서 실행되는 콜백을 오래 점유하면 다른 응답 처리도 늦어질 수 있다. 필요한 경우 제한된 별도 실행기로 넘기되 큐와 동시성을 제한한다.

서버의 이벤트 루프와 클라이언트의 이벤트 루프는 별개다. Redis 서버가 빠른데 애플리케이션 지연이 커지는 이유가 클라이언트 콜백 처리일 수 있으므로 양쪽을 함께 계측한다.

</details>
